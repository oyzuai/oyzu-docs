Tutorial: from an empty folder to a verified build

This walkthrough builds a tiny Go program end to end. Every block of output below was captured from a real run of the CLI on Windows 11 (windows/amd64), with NO_COLOR=1 and the output redirected to a file, which is how Oyzu renders in CI and logs. In an interactive terminal the same sections appear with color and live progress rows. Times, hashes and paths on your machine will differ.

You need the oyzu executable (Install Oyzu) and network access the first time, so Oyzu can fetch the Go toolchain. You do not need to install Go yourself.

1. Create the project​

mkdir hello && cd hello
git init

Create go.mod:

module example.com/oyzu/hello

go 1.22

Add main.go:

package main

import "fmt"

func greeting(name string) string { return "Hello, " + name + "!" }
func main()                       { fmt.Println(greeting("Oyzu")) }

and main_test.go:

package main

import "testing"

func TestGreeting(t *testing.T) {
	if got := greeting("Oyzu"); got != "Hello, Oyzu!" {
		t.Fatalf("unexpected greeting: %q", got)
	}
}

There is no Oyzu configuration file. Oyzu works from the files your ecosystem already has.

2. See what Oyzu found​

oyzu discover
1 target · 6 tasks discovered without running project code
Project root: …/hello

project · go/app
  Chosen by          detected from project files
  Location           .
  Manager            go
  Version            0.0.0
  Part of builds     build, format-check, lint, test
  Development tasks  format, install

Target names are what `oyzu build <target>` accepts.

Oyzu found one Go application from go.mod and main.go. It read the files only; it ran nothing. The tasks it inferred are real native commands:

oyzu run list
Available tasks · 6 across 1 target

Task                  Source         Command
project · go/app (6)

project:format        Inferred · go  gofmt -w .
project:format-check  Inferred · go  gofmt -l .
project:install       Inferred · go  go mod download
project:lint          Inferred · go  go vet ./...
project:test          Inferred · go  go test ./...

A plan is a promise about intent, not evidence. It tells you which stages will run and which tool versions are needed (here, Go 1.22 or newer, read from go.mod). The default build selects only the build stage; the checks are skipped. Use oyzu build --full to run all of them, as the next step does.

(The output above is trimmed to the rows that matter; a real run also lists a few more Prepare steps.) Read it top to bottom:

  • Prepare resolved the Go version from go.mod, installed or found it, and prepared an output bundle.
  • Plan is the matrix of stages that will run for each target.
  • Build has one row per action. Each row shows the real native command (go build, go test, go vet, gofmt -l), whether it was executed or reused, and how long it took.
  • Outputs lists the produced artifact.
  • The closing lines summarize tests run now, coverage, the overall result, and where the evidence lives.

Two files appeared next to your source: oyzu.lock, which records the exact tool identities Oyzu selected, and dist/, the output bundle. Commit oyzu.lock; keep dist/ out of version control.

Verified: every recorded file matches its digest. This does not show who produced the build or that it may be released.

inspect confirms the files in dist/ are exactly the ones the build recorded. It checks integrity, not authorship; the last line says so on purpose.

6. Build again and watch reuse​

Run the same command without changing anything:

oyzu build --full
-- Build -----------------------------------------------------------------------
  00:02  reused  project  build         reused    was 7.1s
  00:02  reused  project  test          reused    was 13.0s
  00:02  reused  project  lint          reused    was 1.7s
  00:02  reused  project  format-check  reused    was 0.2s

Reused test evidence  1 passed · 0 failed · 0 skipped (1 collected reports; not run now)
Coverage    project: 50.0% (1/2 statements) · reused from an earlier run, not run now

ok      Build succeeded   1 target · 4 reused · 2.1s

Nothing changed, so Oyzu reused the earlier results (2.1 seconds instead of 25). It is careful with wording: the tests are labelled reused, not run now, so a green result never silently claims fresh execution. See Understand your build results.

7. Break something and read the failure​

Change "Hello, " to "Hi, " in main.go and build again:

oyzu build --full
  00:02  ok      project  build         go build -trimpath -buildvc…  executed     0.7s
  00:04  FAIL    project  test          go test -json -coverprofile…  failed       1.7s
  00:04  ok      project  lint          go vet ./...                  executed     0.4s
  00:04  ok      project  format-check  gofmt -l .                    executed    <0.1s
-- Failure: project · test -----------------------------------------------------
  --- FAIL: TestGreeting (0.00s)
  FAIL example.com/oyzu/hello · TestGreeting
  Exit  1
  Log   dist/logs/0001.stderr
  Next  oyzu build project   re-run only this target
Tests run now  0 passed · 1 failed · 0 skipped (1 collected reports)

FAIL    Build failed   1 failed · 3 succeeded · 5.0s
  Note     Local binaries were not updated; existing binaries are from the previous successful
           build.

The process exits with status 1. The failure gets its own section with the failing test, the exit code, the full log path and the exact command to re-run. Because the build failed, Oyzu did not replace the previous good binary. Restore "Hello, " and the build passes again.

What you learned​

You ranIt does
oyzu discoverShows detected targets and which builder handles each, running no project code
oyzu run listLists the native tasks Oyzu inferred
oyzu build --planPreviews stages and tool needs without executing
oyzu build --fullBuilds, tests, lints and format-checks; produces dist/ and oyzu.lock
oyzu history / oyzu inspect distShows retained runs and verifies the recorded outputs
