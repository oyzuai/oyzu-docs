Install Oyzu

Oyzu is a single executable, oyzu. It needs no account, agent, daemon or desktop app, and no administrator rights to install.

Install with one command​

On Linux or macOS:

curl -fsSL https://docs.oyzu.ai/install.sh | sh

On Windows, in PowerShell:

irm https://docs.oyzu.ai/install.ps1 | iex

The script:

  1. Picks the newest release (previews included) that has an executable for your platform.
  2. Downloads it and refuses it unless its SHA-256 digest matches the one GitHub reports.
  3. Installs oyzu into ~/.oyzu/bin (%LOCALAPPDATA%\Oyzu\bin on Windows) and runs oyzu --version.
  4. Enables first-party preview plugins if plugins.preview is unset in your user configuration; preserves an existing true or false.
  5. Runs oyzu shell install to set up your shells and PATH (see What it sets up).

It prints the release it chose, one line with the tag, asset, digest and install location, and the installed version.

Preview releases

Every release is a preview. Releases are binaries and notices published on the public oyzuai/oyzu-releases repository, so you need no account or token. The scripts don't check release provenance yet.

All first-party builder plugins are previews, so the installer opts in for a new user. To undo this, run oyzu config set --global plugins.preview false. If you already turned previews off, the installer leaves that choice in place; enable them with oyzu config set --global plugins.preview true before your first build. Configuration setup failures are warnings; the CLI stays installed.

A GitHub token is optional. It lifts the anonymous API limit of 60 requests an hour:

curl -fsSL https://docs.oyzu.ai/install.sh | GH_TOKEN=$(gh auth token) sh
$env:GH_TOKEN = (gh auth token); irm https://docs.oyzu.ai/install.ps1 | iex

Read it first, or pin a version​

To read the script before you run it, download it first:

curl -fsSL https://docs.oyzu.ai/install.sh -o install.sh
less install.sh
sh install.sh --version v0.0.4

--version (or OYZU_VERSION) installs one release tag instead of the newest. In PowerShell, pass parameters like this:

& ([scriptblock]::Create((irm https://docs.oyzu.ai/install.ps1))) -Version v0.0.4

The install script reference lists every option, the exit codes and the errors.

What it sets up​

Your shells need to activate oyzu, and programs that never start a shell (IDEs, GUI apps, scheduled jobs) need to find oyzu and your tools. oyzu shell install handles both:

  • Shell activation goes into ~/.bashrc, ~/.zshrc and the PowerShell 7 profile, for each of those shells you use.
  • oyzu and the shims folder go on your PATH, so node, go or cargo run at the project's locked version everywhere, without oyzu exec --. On Windows this is your user Path in the registry. On Linux and macOS it is your login profile.

Open a new terminal, and restart any IDE, afterwards. You can run oyzu shell install again at any time.

To install the file only, pass --no-modify-path (-NoModifyPath in PowerShell). With fish or Windows PowerShell 5.1, the installer prints what to run or which folders to add yourself.

Upgrade and uninstall​

An installed oyzu keeps itself up to date. About once a day, a command you run in a terminal checks its release channel in the background, verifies the newest release's signatures and swaps it in; the next command tells you, and oyzu self rollback undoes it. If rollback restores a local build, oyzu self update returns to the recorded channel's newest release. With no recorded channel, start with oyzu self channel stable. Status names the previous local build so you can see what rollback restores. The useful commands:

oyzu self                 # installed version, channel and update mode
oyzu self update          # update now
oyzu self versions        # newest version in stable, beta and nightly
oyzu self channel beta    # follow release candidates too
oyzu self install 0.2.0   # install one exact version and pin it
oyzu self channel --manual  # notices only, no automatic updates

oyzu self shows named Download and Install steps, then the outcome and a runnable Next: command. Warnings explain non-fatal engine or shim failures; -v keeps full digests and child details. --json retains the machine-readable records.

Install from a channel other than stable with --channel beta (-Channel beta in PowerShell). Set OYZU_SELF_UPDATE=off to turn the automatic check off; CI runs never check. Updating oyzu itself covers channels, verification and rollback.

To uninstall, run oyzu shell remove to undo the shell and PATH setup, then delete oyzu, oyzu-shim, any *.previous files and .oyzu-install.json from the install folder.

Check that it works​

oyzu --version
oyzu --help

The version shows the release (or source revision) and platform of your build. A source build says local. oyzu --help groups commands by job: develop and build, project tools, environment and configuration, platform, and diagnostics. The platform group (auth, release, secrets) needs an Oyzu platform account. Everything else works without one. oyzu <command> --help works offline with no project open.

Then run it on a project. The tutorial builds a real program step by step, and Your first build is the short version. Something wrong? See troubleshooting.

You don't need to install Go, Node, Java or any other ecosystem toolchain first. Oyzu acquires the tools a project asks for. See Manage your first tool.

Supported platforms​

The install scripts are tested on Linux and Windows (x86-64). They also have asset names for macOS, ARM64 and musl Linux, but those aren't tested yet. Support for builds differs by ecosystem and tool provider. See what works today and known limits.

Build from source​

This is for contributors, or when you need an unreleased change or a platform with no release executable.

You need a checkout of the Oyzu repository and either an existing Oyzu, which provides the repository's managed Rust, or the Rust toolchain pinned in rust-toolchain.toml. The first run needs network access unless the managed Rust and the locked Cargo dependencies are already cached; the build uses --locked. On macOS, native builds also need Apple's Command Line Tools (xcode-select --install).

tooling/bootstrap-oyzu.sh --source
export PATH="$PWD/.oyzu/bin:$PATH"
oyzu build cli

Unless an oyzu that can read the checkout is already on your PATH or in .oyzu/bin, the script builds the CLI, the native shim and the Rust and Node plugins, copies them to .oyzu/bin and restores the repository's own locked tools. Without --source it downloads the newest release's oyzu instead and builds only when no release executable works on your machine. The source bootstrap section covers the user configuration it writes, when it refuses to run, and CARGO_TARGET_DIR.

Later, run oyzu run bootstrap from the checkout to make the oyzu on your PATH the newest release, which oyzu self then keeps up to date, or oyzu run bootstrap -- --source to rebuild the CLI from the checkout and install it in place. See Refreshing the oyzu on your PATH.

The source task checks actual plugin capabilities and keeps an absolute CLI path, so an older project-local build cannot hide a compatible installed CLI. If none qualifies, it uses Oyzu-managed Cargo to build a temporary seed CLI first. A version label alone does not establish compatibility; existing plugin admission and your configuration choices still apply.

Install a local engine package​

Isolated builds (oyzu build --isolated) run a Linux oyzu inside the container. On Windows and macOS the install scripts set this up from the release. For an oyzu you built yourself, pass the Linux oyzu built from the same source:

oyzu engine install --linux ./oyzu-linux-x86_64

If you have a compatible development engine archive with its identity and digest, you can install it for your user:

oyzu engine install --identity <BUILD_ID> --archive ./engine.tar.gz --sha256 sha256:<HEX>

This doesn't change your PATH or pin a project. The installed executable, and any byte-identical copy of it such as the oyzu on your PATH, supplies its own isolated-build workers without an engines.packages entry. Explicit project pins and administrator pin requirements still take precedence. Add --json for a machine-readable record.

The engine staging reference covers package requirements, offline use and recovery.
