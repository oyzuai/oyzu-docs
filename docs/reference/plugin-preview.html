Go builder preview: terms, support and recovery

CLI reference

Published from the canonical docs/reference/plugin-preview.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Experimental. The commitments for the first public plugin: the builder for Go projects, oyzu/go, published as an Oyzu OCI package on GHCR. It states how a preview is selected, which combinations are supported, how long releases are supported and retained, how each release status affects selection, adoption and replay, and what to do when a release or the catalog goes wrong. The design is authoring and publication and preview and stable contracts (PLG-COMPAT-01); tracking is #589.

Published. oyzu/go 0.1.0-preview.1 is on ghcr.io/oyzuai/plugins/go and listed by the official catalog from serial 21. The maintainer agreed the terms below on 2026-10-19 (relayed by the coordinator session); they are collected in Decisions. Everything else describes behavior the compiled CLI has today.

What a preview is​

oyzu/go 0.1.0-preview.1 (agreed version; a version is never reused) extracts the existing Go builder into a plugin that runs as a separate process. A preview promises:

  • Immutable releases. A published version never changes. A fix, a changed payload or an added platform is a new version and a new release root.
  • Verified bytes. The CLI accepts the release only when it is signed by plugin-release.yml on refs/heads/main from a GitHub-hosted runner, and checks every object by digest (plugin releases).
  • No surprises. A lock never silently changes the implementation. A newer release, a newer preview and a new catalog serial change nothing until you run oyzu plugins update.
  • Visible and reversible selection. The build shows which builder each target got and prints the line that undoes it (plugin catalog).

A preview does not promise the plugin interface (v1alpha1) is stable (it is edited in place until a second ecosystem validates it), that a later preview behaves like this one, that every platform in the package is qualified, or that a preview is supported after a newer release supersedes it. It is excluded from ordinary stable resolution and updates.

Selecting the preview​

Selection is deliberate and user-scoped; a project file cannot select a preview (CONFIG_SCOPE), because the release is code that runs. In user, machine or administrative configuration:

[plugins]
preview = true                      # makes preview releases eligible

That is all. The build acquires the release from the route in the verified official catalog (ghcr.io/oyzuai/plugins/go@sha256:25f830bd…f9bf; see the catalog) and shows the source as official default. Optionally a plugins.packages binding supplies the bytes instead and keeps precedence:

[plugins.packages]
"go/app" = { oci = "ghcr.io/oyzuai/plugins/go:0.1.0-preview.1" }

A tag binding has these consequences:

  • The tag can move. GHCR tags are mutable and plugin-oci.py push has an --allow-retag option for dry runs. The tag is resolved once, at first selection, so an unlocked project (a fresh checkout without a committed oyzu.lock) can resolve different roots at different times. The lock is what pins the release: oyzu.lock records the root digest, and later builds, --frozen replays and fresh stores fetch that digest, never the tag. Commit oyzu.lock, or bind by digest (ghcr.io/oyzuai/plugins/go@sha256:<root>).
  • It is a local package binding. A tag is never the catalog's route, so the catalog's supported, deprecated and unsupported statuses and its qualification do not apply to it when it supplies the release, and a withdrawal or revocation can refuse it only once #662 is on main. The preview flag still applies to oyzu plugins update, which never selects a preview it was not asked for by name (the binding path below). A digest binding equal to the release the catalog would select is that release's route and is shown as the official default.

CI. oyzu ignores the whole user scope when any CI marker is set (CI, GITHUB_ACTIONS and the other variables DETECTION_VARIABLES in src/config/context.rs lists; pinning OYZU_CONTEXT=local does not help), and a project file cannot select a preview or a binding, so the two lines above have no effect in a CI job and the build silently uses the built-in Go builder. Machine scope is not excluded, so the maintainer decided on 2026-10-19 (#670) that a CI job selects the preview through it: the job writes the same [plugins] settings to the root-owned machine configuration before it builds. On a GitHub-hosted Linux runner:

- name: Select the Go preview
  run: |
    sudo install -d -m 0755 /etc/oyzu
    sudo tee /etc/oyzu/config.toml > /dev/null <<'TOML'
    [plugins]
    preview = true
    TOML
- run: oyzu build

Keep the file owned by root and not writable by group or others. Oyzu does not check the ownership or mode of the machine config.toml (it does for the administrative policy file), so this is advice, not enforcement. The recipe replaces any machine configuration the runner already has, so use it on ephemeral runners. A project file cannot select the preview or a binding; the workflow that writes this file is reviewed like any other workflow change. It has run in a hosted workflow: a manual-only proof, plugin-preview-ci-proof.yml (script tooling/plugin-preview-ci-proof.sh), ran this recipe twice on GitHub-hosted ubuntu-24.04 runners on 2026-10-19 (15:53 and 15:54 US Eastern, EDT), both successful: run 39314759614 and run 39314889946, on main at 4a1635c. Each built the pinned oyzu from source, checked that the same settings in user scope are ignored (and are read outside CI), and, with the recipe's machine file, asserted the official-default Selection source, the release and oyzu.lock root sha256:25f830bd…f9bf, the artifact output Hello, Oyzu!, build --frozen replay (locked) and official default in plugins info. Details and limits are in the status entry. The Selection section of the build shows oyzu/go 0.1.0-preview.1 when it took effect. No new channel, setting or flag is added; accepting a preview opt-in from a CI-honored project or environment source is not part of this decision and would be a separate design. Earlier verified on Linux (2026-10-19) in a mount namespace with a scratch /etc, before the hosted runs above: a build with CI=true GITHUB_ACTIONS=true and that file selected the plugin and wrote its [[plugin]] lock entry, and the unit test plugin_preview_settings_survive_ci_from_machine_scope_but_not_user_scope keeps the scope rule. macOS (/Library/Application Support/Oyzu/config.toml) and Windows (%ProgramData%\Oyzu\config.toml) use the same rule but are untested. Acquiring from the catalog's own routes (#664) does not remove the need for the opt-in, which is also user, machine or administrative scope only.

oyzu build needs no account and no login, and no Docker. Undo with the line the build prints: rm oyzu.lock, then oyzu config unset --global 'plugins.packages."go/app"' and oyzu config set --global plugins.preview false.

With plugins.preview off, a build never refreshes the official catalog and a Go project uses the built-in builder as before. oyzu plugins update never moves a selection to a preview unless you name it (go/app@0.1.0-preview.2, which needs the opt-in); a routine update stays inside the adopted major and skips previews (updating plugins).

Support, deprecation and retention​

Agreed terms (nothing here is enforced by the client except where a status is described under Lifecycle statuses):

  • Support. Only the newest preview is supported. When a newer preview or a stable release supersedes it, the catalog marks it deprecated with an end of at least 30 days and a message naming the successor, then unsupported at the end. Fixes ship as a new preview; there are no backports.
  • Withdrawal. A defective release is withdrawn at once, without waiting for the deprecation period (runbook).
  • Retention of contents. Release roots, platform payloads and their signature referrers stay in GHCR for at least 12 months after the release is superseded, and are never removed by cache or Actions-artifact cleanup. The payload-* workflow artifacts are build intermediates with Actions retention and are not part of the release. A withdrawn or revoked release's bytes and evidence are kept as long as its withdrawal is listed.
  • Retention of catalog entries. The catalog lists supported releases within their retention; withdrawals are kept for good. A release pruned from the catalog is unlisted, not withdrawn: new resolution no longer offers it, but a lock that names it still replays while its bytes remain in the store or GHCR.
  • Transparency log. Each signature is a public Sigstore (Rekor) entry and cannot be deleted; withdrawing a release does not remove its entry.
  • Freshness. The catalog is re-signed daily and never valid more than 31 days; a client with the preview opt-in refreshes it at most hourly.

Support expiry, deprecation, unavailable bytes and denied execution stay distinct: a deprecated or unsupported release still replays; missing bytes fail with PLUGIN_PACKAGE_UNAVAILABLE; denial is PLUGIN_RELEASE_WITHDRAWN or PLUGIN_RELEASE_REVOKED.

For a plugins.packages binding (an optional override that takes precedence over the catalog's route) the catalog is consulted for withdrawals only:

Support is advice and withdrawal is authority: unsupported and deprecated never stop a lock, while withdrawn and revoked always do. Known limits, recorded rather than fixed here: a passed ends date does not change the status by itself (agreed: the catalog is re-published as unsupported), the build shows no deprecation warning, and revocation cannot reach a machine that never verified a catalog (#601) or stop an installed copy that is not replayed through a lock.

Incident and recovery runbook​

Owner (agreed): the release owner, Micah Martin (no second owner), who holds the right to merge oyzuai/tool-index changes and to run plugin-release.yml. The catalog source is config/plugins.toml in oyzuai/tool-index; every change there needs a person (code owner). A catalog change reaches clients as the next release serial of the tool index (the release workflow runs when config/plugins.toml changes and re-signs daily); clients with the opt-in pick it up at their next refresh, at most an hour later, and apply its withdrawals on every command.

IncidentActionWhat users see and do
A release is defectiveAdd a withdrawals entry (kind = "withdrawn", package, version, root digest, reason, optional replacement) and remove the release from the list. Publish a fixed version as a new releaseBuilds and --plan fail with PLUGIN_RELEASE_WITHDRAWN naming the catalog serial and the lock entry. Run oyzu plugins update go/app (needs a binding for the replacement, as above); oyzu plugins versions go/app shows why a release is excluded
Content or the signing path is compromisedWithdraw with kind = "revoked". If the signer identity itself is compromised, a new CLI release must change the pinned identity: tell users to upgrade; revoke each affected release by digestPLUGIN_RELEASE_REVOKED ("it will not run") on every command; recover as above. Installed copies outside a lock are not removed
The catalog is wrong or must be rolled backA serial never goes backwards: clients refuse a lower serial, the same serial with other bytes and a higher serial generated earlier. Fix forward with the next serialA rolled-back or stale copy is ignored and the last verified copy stays in force with its withdrawals
The catalog is tampered with, or its signature failsThe client refuses it and keeps its last verified copy. Restore the correct release assets and investigate the workflowUnlocked references: PLUGIN_CATALOG_UNAVAILABLE. A lock replays only against a verified copy. Offline or with an expired copy, withdrawals still apply and a PLUGIN_CATALOG_EXPIRED warning is shown. A user can bind a package explicitly to continue without the catalog
GHCR is unreachable or the package is privateNo change to releases. If the package was made private by mistake, restore public visibility (organization owner)PLUGIN_PACKAGE_UNAVAILABLE naming the missing object or "refused anonymous access". A release already in the store keeps working: builds that find it installed need no network
A release cannot be publishedHosted runners are required: the build matrix uses macOS and Windows runners, and clients accept only a signature from a GitHub-hosted runner on main. Check the dry run before publishingNothing changes for users; the catalog lists only what is available
A signed release must be removedThere is no deletion: the Rekor entry is permanent and the bytes stay for retention. Withdraw itAs a defective release

Order matters in both directions: publish bytes and signature first, the catalog entry last (a catalog never lists bytes that are not there); withdraw in the catalog first, then deal with bytes.

Agreed by the maintainer on 2026-10-19.

DecisionValue
First version0.1.0-preview.1

Support modelNewest preview supported; superseded preview deprecated for at least 30 days, then unsupported; no backports

Release owner and incident contactMicah Martin, the oyzuai organization maintainer; no second owner

Selection contractplugins.preview = true; the release is acquired from the catalog's own OCI route (#664); a plugins.packages binding is optional and takes precedence

Verification​

Compiled-CLI tests in tests/integration/plugin_lifecycle.rs (a signed organization catalog, a stand-in plugin so selection and lock behavior is measured, not the Go build): new_selection_offers_only_eligible_releases, adoption_offers_only_eligible_releases and replay_follows_the_lock_until_the_release_is_withdrawn_or_revoked (including recovery by update). They found one defect: a plugins.packages binding of a digest the catalog had withdrawn or revoked was adopted and launched on first use. It is fixed, with its own tests, in #662, which this page's withdrawn and revoked rows assume is on main. The real Go plugin under the real official catalog and GHCR is the publication proof in plugin releases.

Route proof, no binding (2026-10-19, linux/amd64): see the status entry: only plugins.preview = true, the Selection source reads official default and the package line names the catalog route.

Native Windows run (2026-10-19 21:30 US Eastern, MICAH-DESKTOP, Windows 10.0.26200 x86_64, main at 67a28f0): the same user-scope-only selection built the example, ran the windows/amd64 payload and printed Hello, Oyzu!; the CI control ignored the user scope. A frozen replay with the plugin store removed fails with PLUGIN_LOCK_UNUSABLE (the documented binding-only re-acquisition gap) and the machine-scope recipe was not run; see the status entry.

Earlier published proof, with a binding (2026-10-19, linux/amd64): from a clean store, anonymously and with only the official catalog (serial 21) and GHCR, oyzu build detected go/app, acquired and signature-verified oyzu/go 0.1.0-preview.1 (sha256:25f830bd740620e6a54a5eac922d1a9505e12f1e1db732f8538152447ba1f9bf), recorded exactly that release in oyzu.lock and produced a running artifact; oyzu build --frozen replayed it. The package was acquired through a user plugins.packages OCI binding (the Selection source read local package binding), before route acquisition (#664); the catalog supplied the detection, the reference and the preview listing. The binary was built against the Cargo.toml and Cargo.lock of 1febd94, because main did not build with --locked at the time. Exact commands, captured output and the time (about 09:40 US Eastern) are in the status entry. Other platforms are listed in the catalog but not proved end to end.
