Go builder preview

CLI reference

Published from the canonical docs/reference/plugin-preview.md file. Features marked experimental remain experimental; check support limitations before relying on them.

oyzu/go is the first published Oyzu builder plugin: it builds Go projects. It's a preview release, published as an OCI package on GHCR and listed in the official plugin catalog. This page says how to select it, what it supports, how long releases are supported, and what happens when a release is withdrawn.

Note: The Go builder is a preview. Its plugin interface (v1alpha1) can still change, and a later preview may behave differently.

Quick start​

Add this to your user configuration (see Selecting the preview):

[plugins]
preview = true

Then build any Go module:

oyzu build

Oyzu downloads oyzu/go 0.1.0-preview.1 from ghcr.io/oyzuai/plugins/go, checks its signature, records the exact release in oyzu.lock and builds with it. You need no account, login or Docker. The build's Selection section shows the source as official default.

To undo it, remove oyzu.lock, then run oyzu config unset --global 'plugins.packages."go/app"' and oyzu config set --global plugins.preview false. The build prints this line for you.

What a preview promises​

  • Immutable releases. A published version never changes. A fix, a changed payload or a new platform is a new version.
  • Verified bytes. Oyzu accepts a release only when it's signed by the plugin-release.yml workflow on refs/heads/main from a GitHub-hosted runner, and it checks every object by digest (signature rules).
  • No surprises. A lock never silently changes the implementation. A newer release, a newer preview or a new catalog serial changes nothing until you run oyzu plugins update.
  • Visible and reversible selection. The build shows which builder each target got and prints the line that undoes it.

A preview does not promise that the plugin interface is stable, that a later preview behaves like this one, that every platform in the package is tested, or that it's supported after a newer release replaces it. Previews are left out of ordinary stable resolution and updates.

Selecting the preview​

Selection is deliberate and per user. A project file can't select a preview (CONFIG_SCOPE), because the release is code that runs on your machine. Set it in user, machine or administrative configuration:

[plugins]
preview = true

The build then downloads the release from the route in the verified catalog (ghcr.io/oyzuai/plugins/go@sha256:25f830bd…f9bf). Optionally, a plugins.packages binding supplies the bytes instead and takes precedence:

[plugins.packages]
"go/app" = { oci = "ghcr.io/oyzuai/plugins/go:0.1.0-preview.1" }

A tag binding has these consequences:

  • The tag can move. GHCR tags are mutable. Oyzu resolves the tag once, at first selection, so a fresh checkout without a committed oyzu.lock can resolve different releases at different times. The lock is what pins the release: it records the root digest, and later builds, --frozen replays and fresh stores fetch that digest. Commit oyzu.lock, or bind by digest (ghcr.io/oyzuai/plugins/go@sha256:<root>).
  • It's a local package binding. The catalog's supported, deprecated and unsupported statuses don't apply to a release a tag supplies. A withdrawal or revocation still refuses it. oyzu plugins update still never selects a preview you didn't name. A digest binding equal to the release the catalog would select counts as the official default.

With plugins.preview off, a build never refreshes the official catalog and can't select the preview, so a Go build fails with PLUGIN_UNAVAILABLE unless you bind a package. oyzu plugins update never moves a selection to a preview unless you name it (go/app@0.1.0-preview.2, which needs the opt-in). A routine update stays inside the adopted major version and skips previews.

In CI​

Oyzu ignores the whole user configuration when it sees a CI marker (CI, GITHUB_ACTIONS and similar variables). A project file can't select a preview, so the settings above have no effect in a CI job. Instead, write them to the machine configuration before the build. On a GitHub-hosted Linux runner:

- name: Select the Go preview
  run: |
    sudo install -d -m 0755 /etc/oyzu
    sudo tee /etc/oyzu/config.toml > /dev/null <<'TOML'
    [plugins]
    preview = true
    TOML
- run: oyzu build

Keep the file owned by root and not writable by group or others. Oyzu doesn't check the owner or mode of the machine config.toml, so this is advice, not enforcement. The recipe replaces any machine configuration already on the runner, so use it on throwaway runners. The machine file is /Library/Application Support/Oyzu/config.toml on macOS and %ProgramData%\Oyzu\config.toml on Windows; those paths use the same rule but haven't been tested.

Support, deprecation and retention​

  • Support. Only the newest preview is supported. When a newer preview or a stable release replaces it, the catalog marks it deprecated for at least 30 days, with a message naming the successor, then unsupported. Fixes ship as a new preview. There are no backports.
  • Withdrawal. A defective release is withdrawn at once, without waiting for the deprecation period.
  • Retention. Release roots, platform payloads and signatures stay on GHCR for at least 12 months after the release is replaced. A withdrawn or revoked release's bytes and evidence are kept as long as its withdrawal is listed.
  • Catalog entries. The catalog lists supported releases within their retention. Withdrawals are kept for good. A release removed from the catalog is unlisted, not withdrawn: new builds no longer offer it, but a lock that names it still replays while its bytes are in your store or on GHCR.
  • Transparency log. Each signature is a public Sigstore (Rekor) entry. It can't be deleted, and withdrawing a release doesn't remove it.
  • Freshness. The catalog is re-signed daily and is never valid for more than 31 days. With the opt-in, oyzu refreshes it at most once an hour.

Oyzu treats these cases differently. A deprecated or unsupported release still replays. Missing bytes fail with PLUGIN_PACKAGE_UNAVAILABLE. A withdrawn or revoked release is refused with PLUGIN_RELEASE_WITHDRAWN or PLUGIN_RELEASE_REVOKED.

A withdrawn or revoked release is refused for every kind of binding, before it's installed.

Support is advice and withdrawal is authority: unsupported and deprecated never stop a lock, while withdrawn and revoked always do. Known limits:

  • A passed end date doesn't change a status by itself. The catalog is re-published as unsupported.
  • A build shows no deprecation warning.
  • A revocation can't reach a machine that never verified a catalog, or stop an installed copy that isn't replayed through a lock.

When something goes wrong​

A catalog change reaches you as the next serial of the tool index. With the opt-in, oyzu picks it up at its next refresh, at most an hour later, and applies its withdrawals on every command.

SituationWhat you seeWhat to do
A release is defective and withdrawnBuilds and --plan fail with PLUGIN_RELEASE_WITHDRAWN, naming the catalog serial and the lock entryRun oyzu plugins update go/app (it needs a binding or the store to supply the replacement). oyzu plugins versions go/app shows why a release is excluded
A release is revoked (its content or signing is compromised)PLUGIN_RELEASE_REVOKED ("it will not run") on every command. Installed copies outside a lock aren't removedRecover as above. Remove the copy with oyzu plugins prune
The catalog is wrong and rolled backOyzu ignores a lower serial, the same serial with other bytes, or a higher serial generated earlier, and keeps the last verified copy and its withdrawalsNothing to do
The catalog is tampered with or its signature failsOyzu refuses it and keeps the last verified copy. Unlocked references fail with PLUGIN_CATALOG_UNAVAILABLE. A lock replays only against a verified copy. With no network or an expired copy, withdrawals still apply and a PLUGIN_CATALOG_EXPIRED warning appearsBind a package explicitly to continue without the catalog
GHCR is unreachable or the package is privatePLUGIN_PACKAGE_UNAVAILABLE naming the missing object or "refused anonymous access". A release already in your store keeps working with no networkRetry when the registry is reachable

A signed release can't be deleted: the signature log entry is permanent and the bytes stay for the retention period. It can only be withdrawn.
