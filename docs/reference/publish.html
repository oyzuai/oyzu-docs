Publishing finalized artifacts

CLI reference

Published from the canonical docs/reference/publish.md file. Features marked experimental remain experimental; check support limitations before relying on them.

oyzu publish sends files from a finished build to an OCI registry or an existing GitHub release. It needs no Oyzu account: you configure destinations in oyzu.toml, supply signed build provenance, and Oyzu uploads the files, signs a record of what it published and reads everything back to check it. If you use the Oyzu platform, oyzu publish can instead register the build there and follow a publication the platform runs (see Governed publication).

Publishing is optional. oyzu build and every other command stay local and work without an account.

Note: Publishing is experimental. Supported destinations are OCI registries (files and single-platform images) and GitHub releases. npm, PyPI and tag-based OCI publishing are not supported.

Quick start​

Configure a destination and the evidence you accept, then publish a finished build:

# oyzu.toml
[publish]
default = "sandbox"

[publish.destinations.sandbox]
kind = "oci"
artifacts = ["app/archive"]      # optional when the build has exactly one artifact
registry = "https://registry.example.com"
repository = "team/artifacts"
usernameEnv = "REGISTRY_USERNAME"
passwordEnv = "REGISTRY_PASSWORD"

[publish.sets]
release = ["sandbox"]

[publish.requirements.provenance]
bundlePath = "evidence/build.sigstore.json"
publicKey = "<base64 raw 32-byte Ed25519 public key>"
builderId = "https://ci.example.com/builders/release"

[publish.requirements.signing]
keyEnv = "PUBLICATION_SIGNING_SEED"
publicKey = "<base64 raw 32-byte Ed25519 publication public key>"
oyzu build
oyzu publish --destination sandbox

This is an example: use your own public keys, provenance bundle and credentials. Keep secret values out of the TOML. The file names environment variables that hold them.

oyzu publish reads dist/manifest.json by default (or the configured build.bundleDirectory). Pass --manifest FILE to publish a different bundle.

How a publish works​

  1. Oyzu reads the build manifest, which must record a succeeded build, and selects the artifacts each destination asks for.
  2. It checks the selection and all evidence before it contacts any destination: the file's bytes and size, your signed provenance and the publication signature.
  3. It uploads the files and the evidence.
  4. It downloads what it uploaded and checks every digest and size. Upload acknowledgements alone never count as success.

Publishing never builds, scans, repackages or runs project hooks, and it never creates missing provenance. It needs network access, and there is no offline mode.

Standalone OCI publication​

Run oyzu publish --destination sandbox, or omit --destination to use publish.default.

  • Repeat --destination to publish to several destinations, or name a set from publish.sets. All selected destinations are required.
  • A later destination can fail without undoing earlier ones. Successful publications stay, and the receipt lists the unfinished destinations.

Settings​

Publishing settings use the ordinary configuration cascade, but only in the project root's oyzu.toml or oyzu.local.toml. A [publish] table in any other folder's file is a CONFIG_SCOPE error naming the file and line (root-only settings).

SettingValuesDefaultMeaning
publish.defaultA destination nameThe destination used when --destination is omitted.
publish.destinations.<name>.kindoci, github-releaseociThe destination kind.
publish.destinations.<name>.artifactsBuild output IDsThe outputs this destination publishes (see Selecting artifacts). You can omit it only when the manifest has one artifact.
publish.destinations.<name>.registryAn HTTPS URLThe OCI registry. Plain HTTP is allowed only on loopback (for example a local test registry).
publish.destinations.<name>.repositoryA repository nameThe OCI repository.
publish.destinations.<name>.usernameEnv, passwordEnvEnvironment variable namesRegistry credentials. Set both or neither. Registries that use the same-origin bearer token challenge work.
publish.setsNamed lists of destinationsSets you can select with --destination.
publish.requirements.provenancebundlePath, publicKey, builderId, or a byArtifact mapThe build provenance you accept (see Provenance evidence).
publish.requirements.signingkeyEnv, publicKeySigning for the publication record. keyEnv names an environment variable holding a base64 32-byte Ed25519 seed. Its public key must match publicKey.

Rules:

  • publish.destinations, publish.sets and publish.requirements each resolve as a whole. A later source in the cascade replaces the entire table and does not merge entries.
  • Profiles and mandatory configuration constraints apply.
  • An evidence path is relative to the file that declares the requirements. Artifact paths are relative to the bundle that holds the manifest.

Destination kinds​

  • kind defaults to oci, so older configurations need no change.
  • github-release uses the adapter described in Existing GitHub release.
  • npm, pypi and unknown kinds fail with CONFIG_INVALID_VALUE before Oyzu loads evidence, reads credentials or uses the network.
  • Unknown destination fields are errors.

Selecting artifacts​

Each destination lists the build outputs it publishes in artifacts. An ID is target/name for the output called name, or just target for that target's primary output. It is not the file's name.

  • artifacts = ["app/archive"] selects output archive of target app. artifacts = ["app"] selects the primary output of app.
  • Each destination can name different files. Nothing fans out implicitly.
  • Empty or duplicate entries fail with CONFIG_INVALID_VALUE.

Oyzu checks selectors long before you publish (names that cross files):

  • oyzu config validate, oyzu build --plan and every build refuse a selector (or byArtifact key) whose build does not exist, or whose @os/arch is not one of the build's platforms. The error is CONFIG_REFERENCE_UNKNOWN, with the file, line, column and the nearest build name.
  • Each build's Prepare step refuses an output name the build does not produce, and lists the outputs it does.
  • At publish time, an unknown or ambiguous ID, or a missing selection in a bundle with several artifacts, fails with PUBLISH_ARTIFACT_SELECTION_INVALID before any evidence loading, signing or upload.

Platform selectors​

Add @os/arch to select one platform of an output, such as cli/bin-oyzu@linux/x86_64.

  • The platform is the one the builder recorded for the file, in the canonical spelling x86_64 or arm64. amd64 and aarch64 are accepted and normalized.
  • An unqualified selector such as cli/bin-oyzu selects every platform of that output in the bundle. Each platform is a separate file with its own evidence.
  • A qualified selector fails with PUBLISH_ARTIFACT_SELECTION_INVALID, listing the platforms present, when the bundle lacks that platform or the output has no recorded platform. Two artifacts of one output and platform also fail.
  • Listing an output both with and without a platform, or the same platform twice, fails with CONFIG_INVALID_VALUE.
  • oyzu build writes one platform per bundle. To publish several platforms together, pass several bundles (see Incomplete platform sets).

A bound chart needs its image​

A helm/chart build whose bindings write an image's with.repository into its values is published only when the same oyzu publish also pushes that image to that repository. That means an OCI destination whose registry host and repository equal with.repository, and whose artifacts select the image.

  • Otherwise publishing fails with PUBLISH_BINDING_UNPUSHED before any evidence, signing or upload. The message names the chart's destination and the destination to add.
  • Mirrors elsewhere are still allowed.
  • Publish the chart and image together, for example oyzu publish --destination charts --destination images. See Publishing an OCI image.
  • Oyzu applies the same check to publish.default and each publish.sets entry when it reads the configuration (CONFIG_BINDING_UNPUSHED).

Provenance evidence​

Oyzu publishes only files it can tie to signed build provenance that you supply. The file must be a regular file whose bytes and size match its recorded SHA-256 digest. Other outputs in the manifest are validated but their files are not read or published.

The accepted provenance is:

  • a Sigstore v0.3 bundle with one DSSE application/vnd.in-toto+json envelope,
  • holding an in-toto Statement v1 with SLSA build provenance v1,
  • signed with the Ed25519 key in publicKey, from the exact builder in builderId, and
  • covering the exact digest of the file being published.

This profile uses keys you manage. It makes no transparency-log, trusted-time or keyless-identity claim and does not assert a SLSA level.

Standalone publishing rejects --no-upload, --provenance and --policy-evidence before reading configuration or using the network. It takes provenance only from publish.requirements.provenance.

If different outputs have different provenance, replace the single form with a map keyed by output ID:

[publish.requirements.provenance.byArtifact."app/archive"]
bundlePath = "evidence/app.sigstore.json"
publicKey = "<accepted base64 raw Ed25519 builder public key>"
builderId = "https://ci.example.com/builders/package"

[publish.requirements.provenance.byArtifact."cli"]
bundlePath = "evidence/cli.sigstore.json"
publicKey = "<accepted base64 raw Ed25519 builder public key>"
builderId = "https://ci.example.com/builders/cli"
  • Keys use the same IDs as artifacts. Only the selected output's entry is used and unselected bundles are not read.
  • A selected output with no entry fails with PUBLISH_EVIDENCE_MISSING. Oyzu never substitutes another output's evidence.
  • Combining byArtifact with the single form, an empty map or ID, or a malformed entry fails with CONFIG_INVALID_VALUE.

Provenance is one bundle per file, so an output published on several platforms needs one bundle per platform. Use a key per platform ("cli@linux/arm64"), or one unqualified key whose bundlePath contains {artifact.platform}:

[publish.requirements.provenance.byArtifact."cli"]
bundlePath = "evidence/{artifact.platform}/cli.sigstore.json"   # evidence/linux/x86_64/cli.sigstore.json
publicKey = "<accepted base64 raw Ed25519 builder public key>"
builderId = "https://ci.example.com/builders/cli"
  • {artifact.platform} is the only placeholder. Any other { or } in bundlePath fails validation.
  • An unqualified key without the placeholder that would cover several platforms, or a placeholder on an output with no recorded platform, fails with CONFIG_INVALID_VALUE.
  • A missing bundle for one platform fails the whole publish with PUBLISH_EVIDENCE_MISSING naming the key. Nothing is published.

Evidence problems report one of these codes: PUBLISH_EVIDENCE_INVALID (malformed bundle, bad signature, wrong statement type), PUBLISH_EVIDENCE_SUBJECT_MISMATCH (provenance does not cover this file's digest), PUBLISH_EVIDENCE_BUILDER_DENIED (builder is not the accepted builderId) and PUBLISH_EVIDENCE_UNSUPPORTED (the bundle carries transparency-log or timestamp material this profile does not accept).

What is published​

Before uploading, Oyzu signs a publication intent with your publication key. The intent is a small signed record of exactly what this publish will do: the file's identity and media type, where it will go, the digest of your provenance, the digest of the whole plan and the operation publish.

  • The intent cannot claim an earlier build origin or a finished upload.
  • It does not contain the invocation ID, so publishing the same plan again reuses the same OCI coordinate.
  • Oyzu verifies every signature before it uploads anything. A signing key that does not match publish.requirements.signing.publicKey fails with PUBLISH_SIGNING_INVALID.

The OCI artifact holds the unchanged file, plus your provenance bundle and the publication-intent bundle as layers that anyone can download.

  • The coordinate is registry/repository@sha256:<manifest-digest>.
  • Tags are not supported. A mutable tag could be replaced by another writer between the check and the upload.
  • Matching content already in the registry is reported as already-present. A different manifest, layer or digest at that coordinate is a PUBLISH_CONFLICT.
  • Success requires Oyzu to fetch the manifest, config and every layer back from the registry and match their digests and sizes.

Publishing an OCI image​

A docker/image build produces an OCI image archive (dist/<target>/<platform>/<target>-<version>.oci.tar). Select it by its output ID <build>/image, and Oyzu pushes it as an image rather than as a file:

[publish.destinations.images]
kind = "oci"
registry = "https://registry.example.com"
repository = "team/app"
artifacts = ["image/image"]
oyzu build
oyzu publish --destination images
docker pull registry.example.com/team/app@sha256:<image digest>
  • Oyzu pushes the image's manifest, config and layers unchanged, by digest. The coordinate is the image digest the build recorded as ociDigest, which is also what a bound chart writes into its values.
  • Before it touches evidence, signing or the network, Oyzu verifies the archive (every blob digest and layer diff ID) and checks that its image matches the recorded digest. If not, it fails with PUBLISH_ARTIFACT_CHANGED.
  • An archive that holds a multi-platform image index, or an image selected by a github-release destination, fails with PUBLISH_UNSUPPORTED.
  • The image cannot carry evidence without changing its digest. Oyzu pushes the provenance and publication-intent bundles as a separate artifact in the same repository whose subject is the image (an OCI referrer with artifactType application/vnd.dev.sigstore.bundle.v0.3+json). Its reference is the entry's evidenceReference, and registries that support the OCI referrers API list it under the image.
  • As for files, success means Oyzu fetched the image and the evidence back and matched every digest and size.
  • In the receipt, reference and manifestDigest name the image, and verification.artifactDigest is the archive's SHA-256. An image already present without this publication's evidence gets the evidence pushed and counts as published.

If the registry refuses a write, the entry fails with PUBLISH_UPLOAD_FAILED. If it cannot be reached, the entry fails with PUBLISH_REGISTRY_UNAVAILABLE. Both name the registry. Run the same publish again: content already pushed is matched by digest.

When one OCI destination selects images of the same output for two or more platforms, oyzu publish also pushes an OCI image index of them, by digest. Each platform usually builds on its own host, so pass each build's manifest:

oyzu build                                  # on an amd64 host, its dist/ copied to amd64/
oyzu build                                  # on an arm64 host, its dist/ copied to arm64/
oyzu publish --destination images --manifest amd64/manifest.json --manifest arm64/manifest.json
docker pull registry.example.com/team/app@sha256:<index digest>
  • The index lists each image by digest, size and platform, sorted by platform, so the same images always give the same index digest.
  • Images that share an OCI platform, such as glibc and musl builds for one architecture, form no index and are published alone, because the OCI platform has no ABI.
  • The signed plan covers the index digest and its members. If a member changed since the plan, publishing fails with PUBLISH_ARTIFACT_CHANGED or PUBLISH_PLAN_CHANGED before anything is sent.
  • Oyzu pushes the index only after every selected image succeeded, then reads it back. The receipt lists it under indexes, with output, artifactIds, manifestDigest, outcome and reference (or error). If an image failed, the index's outcome is unfinished.
  • Governed publication doesn't compose an index yet. It pushes each image alone.

Results and exit codes​

Human output shows the operation, each selected output, each destination's result, the exact reference and the digest Oyzu retrieved. With --json, the receipt has operationId, status, planDigest, artifacts and destinations.

  • Each destination has a kind and entries. An entry lists the artifact ID, coordinate, reference, payload outcome and how its evidence was stored and verified.
  • An artifact's id is output-id@os/arch when the file has a recorded platform (cli/bin-oyzu@linux/x86_64), and the output ID otherwise. Such artifacts also carry compatibility (kind target, native or independent, plus the canonical platform), which the signed intent covers.
  • unselectedArtifacts lists, in sorted order, outputs you did not select. Human output lists them as unselected and not published.
  • Each destination reports published, already-present, failed or unfinished, with the digests Oyzu verified.
OutcomeExit code
Published0
A failed or unfinished destination in the receipt2
A check failed before publishing (missing evidence, wrong subject, conflicting existing asset)1
Invalid command syntax2

After you fix a failure, run the same publish again. Successful destinations are matched by digest and not repeated.

Standalone limits​

  • Publishing needs network access.
  • Each file and each response is held in memory, so very large files need that much memory.
  • A destination's credentials come only from environment variables you name.

Existing GitHub release​

The GitHub adapter uses the same configuration, evidence checks and signing as OCI. It uploads files as assets of a release that already exists. It never creates tags or releases.

Replace the destination in the Quick start example with:

[publish.destinations.sandbox]
kind = "github-release"
apiUrl = "https://api.github.com"
repository = "your-owner/your-test-repository"
tokenEnv = "GITHUB_SANDBOX_TOKEN"
artifacts = ["app/archive", "cli"]
[publish.destinations.sandbox.evidence]
mode = "destination"
SettingValuesDefaultMeaning
kindgithub-releaseociSelects the GitHub Releases adapter.
apiUrlAn API originThe GitHub API root.
repositoryowner/nameThe repository that holds the release.
tokenEnvAn environment variable nameHolds a token with Contents read and write access to that repository.
artifactsOutput IDsAs for OCI.
evidence.modedestinationdestinationWhere evidence is stored. destination (evidence next to the files, downloadable from the destination) is the only supported value for OCI and GitHub. receipt and managed are not accepted.

Create the tag and release yourself first, and give Oyzu the token by environment variable.

  • Oyzu never creates refs or releases, publishes a draft, changes release metadata or deletes assets.
  • It records the repository, release ID, tag commit, upload route, draft and prerelease state, and filenames, and stops before writing if any of them changes.
  • A draft release can receive and verify assets. Publish the draft separately afterwards.
  • If GitHub's tag endpoint returns 404, Oyzu looks for the exact tag in the release list. No match, or more than one, fails. Authentication and other HTTP errors are not treated as a missing tag.

Which release: the release tag​

A GitHub destination stores no tag in configuration. oyzu publish picks the release in this order:

  1. --tag <tag>, if given. It applies to every GitHub destination in that publish. Use it for manually started releases or tags version inference does not read.
  2. Otherwise the exact version tag that version inference recorded for the packages the destination publishes. A single-package repository tagged v1.4.0 at the built commit publishes to release v1.4.0. The api package of a workspace tagged api/v1.4.2 publishes to api/v1.4.2, even if another package has the same version.

Oyzu decides the tag before any evidence loading, signing or network access, and the signed intent records it.

  • --tag need not point at the built commit. If it replaces a different recorded tag, Oyzu warns with PUBLISH_TAG_OVERRIDDEN and continues.
  • A tag key in a github-release destination is an error everywhere configuration is read: CONFIG_INVALID_VALUE: publish.destinations: PUBLISH_DESTINATION_TAG_REMOVED. Delete the key.

Without --tag, Oyzu stops and sends nothing in these cases:

CodeCauseFix
PUBLISH_TAG_UNKNOWNA published package has no recorded version tag: the built commit has no version tag that applies to it.Tag the built commit (v1.4.0, or <package>/v1.4.0 for one workspace package), rebuild and publish again, or pass --tag.
PUBLISH_TAG_CONFLICTThe destination's packages have different tags, a package has several tags, or some have a tag and some do not. The message lists each tag and package.One release has one tag. Give each independently versioned package its own destination, delete a duplicate tag, or pass --tag.
PUBLISH_TAG_AMBIGUOUSSeveral packages of a build share the artifact's version with different tags, and the build did not record which package made the artifact.Rebuild with this version of oyzu, or pass --tag.
PUBLISH_TAG_COMMIT_MISMATCHThe derived tag points at a different commit than the one built, in your checkout or on GitHub. Also when packages record the tag on different commits.Build the tagged commit and publish again, or pass --tag to publish to that release anyway.
PUBLISH_UNSUPPORTED--tag is given but no selected destination is a GitHub release, or the publication is governed.Drop --tag.

The recorded tags are what the checkout looked like when you built. Oyzu does not authenticate them against source control. The tag is tied to the built commit, not to a clean tree: a build of the tagged commit with uncommitted changes still publishes to that tag.

Asset names​

Oyzu derives each asset's name when you publish, from the file's local name and the compatibility its builder recorded. This lets one release hold several platforms of one operating system. File bytes and local dist/ names do not change.

Recorded compatibilityAsset nameExample
target (built for one platform)<stem>-<os>-<arch><ext>oyzu for linux/x86_64 becomes oyzu-linux-x86_64. oyzu.exe for windows/x86_64 becomes oyzu-windows-x86_64.exe. app.tar.gz for linux/arm64 becomes app-linux-arm64.tar.gz.
independent (no platform restriction)the filenamesite.tar.gz
native (the package's own name encodes the platform, such as a wheel)the filenamepkg-1.0-cp312-cp312-manylinux_2_28_x86_64.whl
pending, unknown or missingrefused with PUBLISH_ARTIFACT_SELECTION_INVALIDThe builder must record what the file is for.

Platforms use the canonical spelling (x86_64, arm64, never amd64). An ABI is added only when it differs from the OS default (GNU on Linux, MSVC on Windows, none elsewhere).

  • A GNU Linux build is oyzu-linux-x86_64, a musl build is oyzu-linux-x86_64-musl, and a GNU Windows build is oyzu-windows-x86_64-gnu.exe. Evidence files follow the derived name.
  • Qualified selectors (cli/bin-oyzu@linux/x86_64/musl) and {artifact.platform} paths use the same form, so a GNU and a musl build of one output can sit in one release. In the evidence path the platform renders as linux/x86_64 for the default ABI and linux/x86_64-musl otherwise.
  • A selector that names the default ABI (@linux/x86_64/gnu) never matches. Oyzu refuses it and shows the form to write.
  • Two artifacts that publish to the same platform are refused with PUBLISH_ARTIFACT_SELECTION_INVALID before any evidence loading or network access.
  • Names carry no version, so releases/latest/download/oyzu-linux-x86_64 keeps working across releases.
  • Assets uploaded earlier under unqualified names are left alone. They are never renamed or removed.

Extension rule: the extension is the longest case-insensitive match from .tar.gz, .tar.xz, .tar.zst, .tgz, .zip, .exe, .msi, .dmg, .pkg, .deb, .rpm, .dll, .so, .dylib, keeping its original case. Without a match, the platform is appended.

Name checks (all fail with PUBLISH_ARTIFACT_SELECTION_INVALID before any evidence loading, signing or network access):

  • Names use ASCII letters, digits, dot, underscore and dash only, at most 220 bytes, with no leading dot.
  • A name must not end in a reserved evidence suffix. The evidence assets are <asset>.provenance.sigstore.json and <asset>.publication.sigstore.json.
  • Two names that differ only in ASCII case collide.

Executor records: each artifact also records how it was built (host, cross-toolchain with its target, or container). That record is part of the plan, the signed intent and the receipt.

  • An unknown executor kind or field is PUBLISH_MANIFEST_INVALID. A cross toolchain whose target does not match the artifact's platform is PUBLISH_EXECUTOR_INVALID.
  • A release publication refuses a platform-specific (target or native) artifact that has no executor record, with PUBLISH_EXECUTOR_UNKNOWN. Rebuild it with this version of oyzu.
  • Publishing does not otherwise judge how the artifact was built.

Uploads and conflicts​

Before any upload, Oyzu checks the whole plan for name collisions and for assets that already exist on the release.

  • Identical existing content is reused. Different bytes at the same name fail with PUBLISH_CONFLICT. Oyzu never overwrites or deletes.
  • A GitHub API failure (an unexpected HTTP status, invalid JSON, or a release or asset list that is too large) fails with PUBLISH_GITHUB_API and the status.
  • It uploads and re-downloads your provenance and the signed publication intent before the file they describe.
  • Success requires downloading each asset and matching bytes, sizes, digests and evidence claims. An upload acknowledgement is not enough.

An interrupted upload can leave an asset on the release.

  • The receipt lists which assets were completed, failed or unfinished.
  • Run the same publish again. Matching assets stay and only missing work is done.
  • If the subject, coordinate or evidence changed, make a new plan. A same-name asset with different evidence is a conflict. Oyzu will not replace it.
  • Other people can still edit release metadata, so a read-back is a check at that moment and not a permanent guarantee.

GitHub hosts​

  • For GitHub.com, Oyzu talks to the configured API origin, the release's upload route on uploads.github.com and asset downloads on release-assets.githubusercontent.com.
  • API path prefixes are preserved. Requests stay on the same origin, and upload routes are tied to the repository and release ID.
  • Redirected downloads are anonymous. The token is never sent to a redirect target.
  • GitHub Enterprise endpoints are supported only when all routes are on the API origin under its prefix. Translating /api/v3 to /api/uploads is not supported.
  • GitHub Actions artifacts and GHCR are not supported destinations.

Incomplete platform sets​

A build records the platforms each target declares (platforms: in build.yaml). When you publish, Oyzu compares them with the platforms of the artifacts you selected, combining the variants of one target.

  • A declared platform with no selected artifact is a gap. It may never have been built (for example a build on only one runner) or you may not have selected it.
  • In the release context a gap refuses the whole publish with PUBLISH_PLATFORMS_INCOMPLETE, naming each missing target and platform, before any evidence loading, signing or network access. In any other context it is a warning.
  • A target that declares no platforms is not checked.
  • A bundle with no platform records (built by an older oyzu) is refused in release with PUBLISH_PLATFORMS_UNKNOWN and warned about elsewhere.
  • If you never ship a platform, remove it from the declared platforms. An allowance below covers one publication, not a standing exception.

To publish anyway, name each missing platform with a reason:

oyzu publish --destination github \
  --allow-incomplete darwin/x86_64=no-intel-mac-runner \
  --allow-incomplete windows/arm64="arm64 runner not available yet"
  • Each value is <platform>=<reason> (aliases are accepted; the reason is 1 to 200 printable characters).
  • A malformed value, a repeated platform, or a platform that no published target is missing fails with CONFIG_INVALID_VALUE, so the record never claims a gap that does not exist.
  • Every gap, with the reason you gave (or null for a warned gap), is part of the plan digest, is recorded in every signed publication intent as incompletePlatforms, and appears in the receipt.
  • Governed publication does not check completeness and refuses the flag (PUBLISH_UNSUPPORTED).

Several bundles as one publication. If you build one platform per job, publish every platform at once by repeating --manifest, one per bundle:

oyzu publish --destination github \
  --manifest bundles/linux-x86_64/dist/manifest.json \
  --manifest bundles/darwin-arm64/dist/manifest.json \
  --allow-incomplete windows/arm64=runner-unavailable
  • The artifacts from all bundles are selected, checked for completeness together and published in one plan.
  • Each artifact keeps its own bundle's files and executor record.
  • Giving the same bundle twice is PUBLISH_REQUEST_INVALID. Governed publication takes one manifest (PUBLISH_UNSUPPORTED).

Required verification evidence​

If the build's configuration requires verification for certain tool versions (verification.<tool>, usually set by policy), standalone publishing checks each line against the verification the given bundles recorded. This happens after selection and the completeness check, and before any evidence loading, signing or network access.

Each required line must be one of:

  • outside the build's native version range (so it does not apply),
  • covered by the build's own passing tests on a version in that line, or
  • covered by a passing verification run of the same build, from any --manifest bundle, that verified its source or the published artifact.

Otherwise publishing fails with PUBLISH_VERIFICATION_MISSING. The message names each uncovered line, why it is not covered and the commands of the runs the build left to other jobs.

  • Oyzu resolves the requirement at publish time, in the build's folder and the publication's context.
  • To cover a line, run a separate verification job (oyzu build --verify-only) and pass its bundle beside the platform bundles. That bundle is evidence only, and nothing is published from it.
  • The receipt lists under verification how each line was settled. See required tool lines.
  • Governed publication does not check verification evidence.

Releasing oyzu itself (interim)​

Oyzu publishes its own releases with this same path. Each platform is built in its own job. One oyzu publish then runs in the release context with a --manifest per platform and a --tag, uploading binaries as assets of a release in the public oyzuai/oyzu-releases repository. Follow that repository's releases to download them. Releases are binary-only, and the source repository stays separate.

To cut a release:

  1. Merge a commit whose Cargo.toml says X.Y.Z, tag it oyzu/vX.Y.Z and push the tag to oyzuai/oyzu.
  2. Create and publish the release with the same tag in oyzuai/oyzu-releases.
  3. Start the release workflow: gh workflow run release.yml -f tag=oyzu/vX.Y.Z.

The workflow attaches assets to that release. It never creates the release or the tag. It writes to oyzuai/oyzu-releases with the OYZU_RELEASES_TOKEN secret, a token with Contents read/write on that repository only, because the workflow's own token can't write to another repository. If OYZU_RELEASES_TOKEN is missing, or the release repository differs from the committed destination, the run stops before publishing. A fork sets the repository variable OYZU_RELEASE_REPO and edits the destination's repository.

The release build:

  • Runs one job per platform. Each downloads the newest earlier release's oyzu for its platform, builds the release tag with it (oyzu build cli) and signs provenance with the witness.
  • Audits the build for binary-only distribution, which refuses any shipped component that needs source delivery. The corresponding-source companion stays in the run's retained bundle and isn't uploaded.
  • Runs Linux x86_64 and the publish job, which hold the signing seeds and the release token, on the main runner pool named by the repository variable OYZU_MAIN_RUNNER (a JSON runs-on value that includes the oyzu-main label). If it's unset or lacks that label, the run stops in its first job, before anything that holds a secret, rather than falling back to a hosted runner. The first job runs on that pool too. The other five platforms build natively on GitHub-hosted runners; a platform the incomplete input leaves out only records that it was skipped, so it runs on the main pool and needs no hosted runner.
  • Never reads a shared action cache, so every shipped output is built by the release job itself.

The publish job first publishes each platform's oyzu-notices-<os>-<arch>.txt and reads it back, then publishes the binaries to the committed [publish.destinations.github] with --tag. It then attaches the configuration schemas build.yaml.schema.json and oyzu.toml.schema.json, printed by oyzu config schema, which editors reach at https://github.com/oyzuai/oyzu-releases/releases/latest/download/<asset> (see editor schemas). Re-run a release with the same gh workflow run command.

oyzu's own CI jobs​

Oyzu's own CI jobs start from the newest published release of oyzu and run Cargo through oyzu exec, so the project builds itself with the tool it ships.

  • Setup action. The setup step runs tooling/bootstrap-oyzu.sh --release --require-release --ci-machine-binding, reading releases from the public oyzuai/oyzu-releases (OYZU_RELEASE_REPO names another repository, for forks). It uses the downloaded executable only when its SHA-256 digest matches the one GitHub reports for the asset, as the install script does, then puts .oyzu/bin on PATH and writes one summary line naming the release tag, asset and digest of the oyzu used. CI ignores user configuration, so --ci-machine-binding builds only this checkout's Rust and Node plugins and binds them in a new machine configuration on the job's ephemeral runner (see CI machine binding).
  • Node and Python. Repository checks and the CLI job's harness scripts get Node and Python from the checks toolset in oyzu.toml, pinned in oyzu.lock (oyzu --toolset checks install --frozen), so they don't use actions/setup-node or actions/setup-python. The checkers' Python packages go into a virtual environment outside the tool store. The task and build scenario jobs still use the setup-* actions, because those host tools are what the scenarios run the candidate against.
  • No source build. The setup step never builds the oyzu CLI from source. If no release has an executable for the runner's platform, or the release's oyzu can't read this checkout's configuration, the step fails with that reason; publish a release to fix it. Run the bootstrap without --require-release locally to build from source.

The base execution image is published by a separate workflow using the released oyzu. With --root tooling/images, that folder is its own project root, so its configuration never mixes with the CLI's. Without --root, the repository root's configuration applies and refuses the folder's [publish] table with CONFIG_SCOPE. Each platform builds on a runner of its own architecture (linux/arm64 on GitHub's arm64 runner), which runs:

oyzu --root tooling/images lock --update base     # re-lock the apt packages on this runner
oyzu --root tooling/images build base             # RUN installs them offline from the lock
node tooling/release-witness.mjs sign --manifest tooling/images/dist/manifest.json \
  --out tooling/images/.oyzu/release-evidence --artifact base/image@linux/x86_64

A publish job then downloads both builds and publishes them together:

oyzu --root tooling/images --json publish --destination base \
  --manifest base-amd64/dist/manifest.json --manifest base-arm64/dist/manifest.json
  • Both images and their image index are pushed by digest to ghcr.io/oyzuai/oyzu-execution/base with the same release keys as the CLI, as in Publishing an OCI image. The registry credential is the job's GITHUB_TOKEN.
  • The lock is observed again on each run, because replaying debs.lock.yaml needs the signed apt metadata in the machine's own store (see OS package lock limits). The job summary shows how the lock changed against the committed one, and the run uploads the lock it built from. When it changed, the provenance records the source as dirty.
  • The job needs a released oyzu that has the Docker plugin, pins the published base image, locks Ubuntu packages with epoch versions and composes image indexes, plus a committed tooling/images/oyzu.lock that selects that release's Docker plugin. Until then, the job fails at its first oyzu step.
  • Each runner locks its own architecture and keeps the committed lock's entries for the other. After a Dockerfile change, run oyzu lock on an amd64 and an arm64 host and commit the result.
  • oyzu publish pushes by digest only, so a last step points the tag 1 at the index with docker buildx imagetools create --prefer-index=false, which copies it unchanged, checks the tag's digest and prints the index digest.
  • The job needs a Docker engine, so it runs on GitHub-hosted runners, and each run needs the maintainer's approval.

Governed publication and build registration​

With the Oyzu platform, oyzu publish registers the build, uploads its file, and asks the platform to run a publication. The platform decides which destinations and evidence requirements apply. Your command line cannot widen that authority.

Choose it by giving a server, account and project:

oyzu build
oyzu publish --server https://oyzu.example.com --account acme --project web --provenance evidence/build.sigstore.json
  • --provenance FILE is required. It is a signed provenance bundle you already have, sent unchanged.
  • --destination cannot be combined with this mode.
  • It publishes one staged file artifact. --no-upload does not work with it.
  • Optionally pass --policy-evidence FILE, an existing signed policy report that the platform's policy may require. Oyzu sends the file unchanged as policyEvidence.bundle. It does not verify the report, evaluate policy or treat it as an approval. The platform decides whether to accept it.

What the command does:

  1. Reads the manifest, uploads the artifact and registers the build with its components.
  2. Starts a publication operation: POST /publish/v1/accounts/{account}/projects/{project}/operations with the registration build, the artifact's identity and reference, and the provenance.
  3. Follows that operation (GET /operations/{operationId}) until it finishes and prints its decisions and receipts.

Registering or staging a build is never reported as completed distribution. If following the operation times out, the CLI reports status: "unfinished" and a recovery message. The operation continues on the platform, so inspect it before you submit another request. Server URL path prefixes are preserved, with or without a trailing slash.

Note: Governed publication needs an Oyzu platform that serves this API. It is separate from standalone publishing, which works on its own.

Prerequisites​

For governed publication:

  • A finished oyzu build whose manifest records status: succeeded. A failed, cancelled or interrupted build is refused before anything is sent (PUBLISH_BUILD_NOT_SUCCEEDED).
  • The platform URL, account and project, as flags or environment variables.
  • A credential the project accepts: the pipeline's OIDC token for a trusted CI connector, or a publish token from the project's CI connector. See Credentials.

Commit, repository and ref come from the CI system's environment or from flags.

Credentials​

oyzu publish uses the first credential it finds, in this order:

  1. --token-env NAME, else OYZU_ID_TOKEN: an OIDC token the pipeline already has. A --token-env variable that is unset or empty is an error and does not fall through.
  2. GitHub Actions: when ACTIONS_ID_TOKEN_REQUEST_URL and ACTIONS_ID_TOKEN_REQUEST_TOKEN are set (the job has permissions: id-token: write), the CLI requests a token for the audience and uses it.
  3. Bitbucket Pipelines: BITBUCKET_STEP_OIDC_TOKEN (a step with oidc: true). CircleCI: CIRCLE_OIDC_TOKEN_V2, then CIRCLE_OIDC_TOKEN.
  4. Buildkite: when BUILDKITE is set and buildkite-agent is on PATH, buildkite-agent oidc request-token --audience oyzu.
  5. OYZU_PUBLISH_TOKEN: a scoped, revocable publish token (oyzp_...) issued on the project's CI connector, for CI tools without OIDC.

How each CI system provides its token:

CI systemHow
GitHub ActionsSet permissions: id-token: write on the job. Oyzu finds the token automatically.
GitLab CI/CDAdd id_tokens: to the job, for example OYZU_ID_TOKEN: {aud: oyzu}. Oyzu reads OYZU_ID_TOKEN (or name another variable with --token-env).
Bitbucket PipelinesSet oidc: true on the step. Bitbucket fixes the audience, and the project's trust must accept it.
CircleCIOyzu finds CIRCLE_OIDC_TOKEN_V2 or CIRCLE_OIDC_TOKEN, whose audience is the CircleCI organization. For an oyzu audience, run circleci run oidc get --claims '{"aud":"oyzu"}' and put the result in OYZU_ID_TOKEN.
BuildkiteOyzu uses buildkite-agent oidc request-token. The pipeline's OIDC policy must allow it.
Jenkins with the OIDC provider pluginBind the plugin's credential to a variable and pass --token-env (or bind it as OYZU_ID_TOKEN).
Jenkins without OIDC, TeamCityUse OYZU_PUBLISH_TOKEN from a credentials store or secure parameter.
  • The platform decides which tokens a project accepts, based on the trusts on the project's CI connector.
  • Oyzu sends the token only in the Authorization header of the publish request. It never prints, logs or writes it to disk. Progress output names only the source, for example "a GitHub Actions OIDC token".

If a source is present but fails (GitHub refuses the token request, the Buildkite agent fails), the command stops with PUBLISH_CREDENTIAL_UNAVAILABLE and does not fall back to another credential. If none is found, it fails with PUBLISH_NO_CREDENTIAL. In GitHub Actions the message names the missing id-token permission.

One token per request attempt​

The platform accepts a CI OIDC token once per privileged operation (build registration, upload grant, and publication create or retry). Reusing a token for the same operation is refused with HTTP 401.

  • GitHub Actions and Buildkite can issue tokens on request, so Oyzu gets a new token for every attempt, including each retry after a connection failure or a 502, 503 or 504. Reads, such as polling an operation, use no token. Oyzu requests one token up front so a missing permission or failing agent stops the command before anything is sent. A failure to issue a later token stops the command with PUBLISH_CREDENTIAL_UNAVAILABLE.
  • A fixed token (--token-env, OYZU_ID_TOKEN, Bitbucket, CircleCI, OYZU_PUBLISH_TOKEN) is sent as is on every attempt. If a retry is refused with a 401 (or the platform says replayed), the command fails with PUBLISH_CREDENTIAL_REPLAYED. The earlier attempt may already have taken effect, so check the platform before you publish again with a new token.

The Buildkite helper has a fixed 30-second deadline, including output capture. If it stalls, Oyzu tries to stop it and fails with PUBLISH_CREDENTIAL_UNAVAILABLE and external command deadline exceeded.

  • Oyzu does not fall back to the publish token or wait on a process holding the output open. There is no timeout setting or automatic retry.
  • Token output stays in memory and is not included in the timeout message.
  • Check the Buildkite agent and its OIDC policy, then run oyzu publish again, or pass an already issued token with --token-env.
  • Stopping the helper does not guarantee that remote work or child processes stopped.

What is sent​

Artifact upload​

Before registering the build, Oyzu uploads each artifact that is not an OCI image or index to the platform's registry as an OCI artifact. Pass --no-upload or set OYZU_PUBLISH_UPLOAD=0 to skip this. Images and indexes keep their oci_digest and are not uploaded this way.

  • Only a regular file with its recorded size and SHA-256 digest is uploaded. A missing or changed file stops the publish with PUBLISH_ARTIFACT_CHANGED before Oyzu asks for any credential. A directory artifact is skipped with a warning and published without an oci_ref.
  • Oyzu asks the platform for temporary registry access (POST .../builds/uploads, 1 to 1000 artifacts) and signs in to the registry with the standard token flow. The registry and its token endpoint must be on https and on the same origin (plain http only on loopback), so the grant token never goes elsewhere.
  • It then pushes each file's bytes, skipping blobs the registry already has, and an OCI manifest addressed by digest (never a tag). The manifest carries the file's media type and name, and the output name in the annotation dev.oyzu.output.
  • If the platform answers 404 (no artifact storage), Oyzu warns and publishes without upload. 401, 403 and 422 fail the publish with the platform's problem, and 502, 503 and 504 are retried like the publish request. Registry requests that fail with a server error or in transport are retried up to three times. Any other registry refusal fails with PUBLISH_UPLOAD_FAILED and nothing is published.

Each uploaded artifact then carries "oci_ref": "<registry host[:port]>/<repository>@sha256:<manifest digest>".

The publish request​

POST {server}/publish/v1/accounts/{account}/projects/{project}/builds with Authorization: Bearer <credential> and a JSON body:

{
  "version": "1.4.2",
  "commit": "0123456789abcdef0123456789abcdef01234567",
  "repository": "acme/web",
  "ref": "refs/heads/main",
  "run_url": "https://github.com/acme/web/actions/runs/42",
  "outputs": [
    {"path": "dist/manifest.json", "kind": "manifest",
     "media_type": "application/vnd.oyzu.build-manifest.v1alpha1+json",
     "digest": "sha256:…", "size": 2101},
    {"path": "dist/api/linux/x86_64/server", "kind": "artifact",
     "media_type": "application/octet-stream", "digest": "sha256:…", "size": 123,
     "target": "api", "name": "binary", "version": "0.1.0-dev.g111111111111",
     "oci_ref": "registry.example/acme/web/artifacts@sha256:…"}

outputs lists the manifest file and one artifact per artifact in the manifest, with its path, media type, digest, size, target, name and version. OCI images and indexes also carry oci_digest. Fields Oyzu cannot determine are left out. Paths are relative to the checkout root (the manifest's directory relative to -C, then the artifact's bundle path).

Oyzu checks the platform's limits before sending (PUBLISH_MANIFEST_INVALID): at most 1000 outputs, paths up to 1024 bytes, media types 255, targets 256, names 64 and versions 255. Every artifact needs a target, name, version, SHA-256 digest and safe relative path.

The registration response​

The platform answers 200 with the build, its eligibility (candidate or snapshot), one entry per component and the outputs that belong to no component:

Build registered · 01jab7v3k9m2q8r4t6w0y1z5c7 (candidate)

  ✓ published api 1.4.2 (candidate)
  = already published web 2.0.0
  ! skipped worker 0.3.0: the build did not publish [worker/config]

Outputs in no component (never shipped)
  web/build-metadata

This only records components. Nothing is distributed until the publication operation finishes, and its receipt controls success.

A malformed response (missing build, eligibility or component fields) fails with PUBLISH_RESPONSE_INVALID. The server may already have published the build, so check its state and the platform and client versions. Retrying the same build is safe.

Errors and recovery​

Governed publishing failures exit 2 and print one diagnostic. Nothing the platform refused is retried.

Limits​

  • Publishing needs network access, and each file is read into memory.
  • Standalone destinations are OCI registries and existing GitHub releases. Native npm and PyPI publishing, mutable OCI tags and multi-platform image indexes are not supported.
  • Governed publication handles one staged file artifact and needs an Oyzu platform.
  • A registry whose token endpoint is on another origin is refused.
  • Commit, repository and ref are what the CI system reports. The platform decides what it trusts from the token's claims.
