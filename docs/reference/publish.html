Publishing finalized artifacts

CLI reference

Published from the canonical docs/reference/publish.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Status: experimental OCI and GitHub Releases publication. The standalone path distributes selected finalized files without a platform account, requires preexisting signed provenance, signs publication intent, and retrieves the registry objects to verify their bytes. Native npm, Python, OCI image archives and mutable OCI tag publication remain outside this slice. Authored code and tests are not a deployed-provider qualification; measured evidence belongs in implementation status.

Standalone OCI publication​

Run oyzu publish --manifest dist/manifest.json --destination sandbox, or omit --destination to use publish.default. Repeat the option for several named destinations or select a configured set. All selected destinations are required. The complete selection and evidence are checked and all publication signatures are verified before the first distribution. A later destination failure leaves earlier successful publications intact and reports unfinished destinations.

Configure through the ordinary configuration cascade:

[publish]
default = "sandbox"

[publish.destinations.sandbox]
kind = "oci"
# Optional when the build bundle has exactly one artifact:
artifacts = ["app/archive"]
registry = "https://registry.example.com"
repository = "team/artifacts"
usernameEnv = "REGISTRY_USERNAME"
passwordEnv = "REGISTRY_PASSWORD"

[publish.sets]
release = ["sandbox"]

[publish.requirements.provenance]
bundlePath = "evidence/build.sigstore.json"
publicKey = "<base64 raw 32-byte Ed25519 public key>"
builderId = "https://ci.example.com/builders/release"

[publish.requirements.signing]
keyEnv = "PUBLICATION_SIGNING_SEED"
publicKey = "<base64 raw 32-byte Ed25519 publication public key>"

This is an illustrative configuration: supply your own accepted public roots, preexisting signed evidence and independently provisioned credentials. Secret values never belong in the TOML. PUBLICATION_SIGNING_SEED contains a base64 32-byte Ed25519 seed. Its derived public key must match the configured public key. Registry username/password references are optional and must appear together. The same-origin registry bearer challenge flow is supported. HTTPS is required, with plain HTTP permitted only on loopback for local proof registries.

kind is optional and defaults to oci. Explicit kind = "oci" uses the same publication path and normalized request as an existing destination that omits it; existing configurations need no migration. GitHub Releases uses the native adapter described below. npm, pypi and unknown kinds fail configuration validation with CONFIG_INVALID_VALUE before evidence loading, credentials or network access. Remove the unsupported kind only when the destination is actually an OCI registry; omitting it does not enable a native package protocol. Unknown destination fields also remain errors.

publish.destinations, publish.sets and publish.requirements each resolve as one atomic value: a later cascade source replaces that entire map/object. They do not merge nested entries. Profiles and existing mandatory configuration constraints apply. An evidence path is relative to the source declaring the effective requirements. Artifact paths are relative to the build manifest's bundle.

Each destination may select distinct exact build output IDs with artifacts. The ID is the target for its primary output, otherwise target/name; it is not the file's basename or the manifest's internal artifact id. For example, artifacts = ["app/archive"] selects target app, output archive, while artifacts = ["app"] selects that target's primary output. Omission is valid only when the manifest contains one artifact. Empty or duplicate selectors fail configuration validation with CONFIG_INVALID_VALUE. Unknown or ambiguous output IDs or omitted selection in a multi-artifact bundle fail with PUBLISH_ARTIFACT_SELECTION_INVALID before evidence loading, signing or upload. Correct the exact IDs in each selected destination. Explicit entries support several files and different files per destination, without implicit Cartesian fan-out.

A selector may name one platform: output-id@os/arch, such as cli/bin-oyzu@linux/x86_64. The platform is the one the builder recorded for the file (its oyzu.dev/artifact-compatibility fact), written in the canonical spelling x86_64/arm64; amd64 and aarch64 are accepted and normalized. An unqualified selector such as cli/bin-oyzu selects every platform of that output in the bundle, each as a separate file with its own evidence, so a single-platform bundle keeps working unchanged. A qualified selector whose platform the bundle lacks fails with PUBLISH_ARTIFACT_SELECTION_INVALID and lists the platforms present; so does a qualified selector for an output without a recorded platform, and two artifacts of one output and platform (another variant axis), since variant selection is unsupported. Listing an output both unqualified and qualified, or the same platform twice, fails configuration validation with CONFIG_INVALID_VALUE. A bundle holds several platforms of one output only when its manifest lists them; today oyzu build writes one platform per bundle, and the release workflow publishes each platform's bundle to the same release.

The manifest must record a succeeded build. The selected artifact must be a finalized regular file; its bytes and size must match its SHA-256 identity. Other outputs retain manifest validation but their files are not read or distributed. Publication never builds, scans, repackages, executes project hooks, or creates missing historical evidence. The evidence profile is a Sigstore v0.3 bundle carrying one DSSE application/vnd.in-toto+json envelope, an in-toto Statement v1 and SLSA build provenance v1, verified against an independently configured Ed25519 public root and exact accepted builder identity. This self-managed-key profile makes no transparency-log, trusted-time, keyless identity or SLSA-level claim.

For a build with different provenance per output, replace the single [publish.requirements.provenance] fields with an exact output-ID map:

[publish.requirements.provenance.byArtifact."app/archive"]
bundlePath = "evidence/app.sigstore.json"
publicKey = "<accepted base64 raw Ed25519 builder public key>"
builderId = "https://ci.example.com/builders/package"

[publish.requirements.provenance.byArtifact."cli"]
bundlePath = "evidence/cli.sigstore.json"
publicKey = "<accepted base64 raw Ed25519 builder public key>"
builderId = "https://ci.example.com/builders/cli"

These illustrative entries use the same output IDs as destination artifacts; only the selected output's profile is used. Its bundlePath stays relative to the source declaring the effective requirements, and its exact subject, public key and builder are verified before signing or distribution. Unselected bundle files are not read. The existing single form remains supported; it still must cover the selected file. Combining that form with byArtifact, using an empty map/ID, or supplying malformed profile fields fails with CONFIG_INVALID_VALUE. A missing selected entry fails with PUBLISH_EVIDENCE_MISSING; add its exact profile rather than substituting another output's evidence. Mapping several profiles requires exact-subject evidence for each selected file. Signing settings are unchanged.

byArtifact keys use the selector grammar above. Provenance is one bundle per file, so an output selected on several platforms needs one bundle per platform: either a qualified key per platform ("cli@linux/arm64"), or one unqualified key whose bundlePath contains the {artifact.platform} placeholder. The placeholder renders as the canonical platform, which is also a relative path:

[publish.requirements.provenance.byArtifact."cli"]
bundlePath = "evidence/{artifact.platform}/cli.sigstore.json"   # evidence/linux/x86_64/cli.sigstore.json
publicKey = "<accepted base64 raw Ed25519 builder public key>"
builderId = "https://ci.example.com/builders/cli"

{artifact.platform} is the only placeholder; any other { or } in bundlePath fails configuration validation. An unqualified key without the placeholder that would cover several selected platforms, or a placeholder on an output without a recorded platform, fails with CONFIG_INVALID_VALUE before evidence loading. Qualified and unqualified keys for the same output together fail configuration validation. A missing bundle for one platform fails the whole plan with PUBLISH_EVIDENCE_MISSING naming the qualified key; nothing is published.

Standalone publication rejects --no-upload and the governed --provenance and --policy-evidence options before configuration or network access. It takes existing evidence only from the resolved publish.requirements.provenance.bundlePath setting.

The separately signed publication intent binds the exact artifact identity, media type, native coordinate, provenance digest, canonical plan digest, evidence placement and effect targets to the operation publish. It cannot assert a historical build origin or completed upload. Its deterministic contents exclude the invocation identifier, allowing identical republishing to reuse the native OCI coordinate. The signature is verified before distribution.

The OCI artifact contains the unchanged file plus the preexisting provenance bundle and publication-intent bundle as retrievable layers. The coordinate is registry/repository@sha256:<manifest-digest>. Tags are unsupported: a mutable tag's preflight read cannot prevent a concurrent writer from replacing it. Matching existing content is already-present; a wrong digest header, manifest, layer or declared artifact identity is a conflict. Success requires independent native GETs of the manifest, config and all layers with digest/size checks. Upload acknowledgements and HEAD responses alone never establish success.

Human output identifies the operation, selected artifact output ID, each destination outcome, exact reference and retrieved artifact digest. --json returns a v1alpha1 receipt with operationId, status, planDigest, artifacts and destinations. Each destination has kind and entries with artifact ID, coordinate, reference, payload/native-asset outcomes and evidence storage/verification. Artifact id is the exact selection key: output-id@os/arch for a file with a recorded platform (cli/bin-oyzu@linux/x86_64), the output ID otherwise. Such an artifact also carries compatibility (kind target, native or independent, and the canonical platform), which the signed intent binds. When other outputs exist, unselectedArtifacts lists their keys in sorted order. Human output lists them as unselected and not published. Each destination distinguishes published, already-present, failed and unfinished, and records the manifest/artifact/evidence digests actually verified. A failed or unfinished receipt exits 2; successful publication exits 0. Retry the unchanged plan after resolving the failure; successful destinations are reconciled by their digest. Preflight operation errors such as missing evidence, a wrong subject or a conflicting existing asset exit 1 through the shared CLI error path; JSON diagnostics carry the same exitCode. Invalid command syntax exits 2.

Publication needs network access. There is no offline publication success. Artifacts and GET responses are currently held in memory; streaming and larger artifact qualification are deferred. The implementation is shared across host platforms; only explicitly recorded native runs establish platform coverage. The Linux standalone selection proof built two real binaries and verified the selected output, its original provenance and signed intent through a disposable OCI registry. It also verified that the unselected payload was absent, matching repeat/recheck behavior and early refusals. That anonymous loopback run does not qualify authentication or governed execution.

Existing GitHub release​

The GitHub adapter uses the same configuration, whole-plan evidence acceptance, signing and restricted worker as OCI. The bounded GitHub.com proof passed on Windows x64, including native downloads, exact evidence/signature checks, matching/conflicting assets and controlled partial recovery. The GitHub qualification record records exact revisions and limits; broader hosts, enterprise routes and deployed platform execution remain unqualified.

Replace the destination in the preceding example with this illustrative entry:

[publish.destinations.sandbox]
kind = "github-release"
apiUrl = "https://api.github.com"
repository = "your-owner/your-test-repository"
tag = "existing-test-tag"
tokenEnv = "GITHUB_SANDBOX_TOKEN"
artifacts = ["app/archive", "cli"]
[publish.destinations.sandbox.evidence]
mode = "destination"

Provision the tag/release separately and supply a repository-scoped Contents read/write credential by environment reference. The adapter never creates refs or releases, finalizes releases, changes metadata or deletes assets. It freezes the API root, observed repository/release IDs, resolved tag commit, upload route, draft/prerelease state and exact filenames, then refuses changed identity before writes. Reported draft/private visibility does not imply public distribution.

Asset names are derived at publication from the file's local name and the compatibility its builder recorded, so one release holds several platforms of one operating system family. Bytes and local dist/ filenames never change:

The platform uses the canonical spelling (x86_64, arm64, never amd64); an ABI would appear only when the builder records one, and no builder records one today. ext is the longest case-insensitive match from .tar.gz, .tar.xz, .tar.zst, .tgz, .zip, .exe, .msi, .dmg, .pkg, .deb, .rpm, .dll, .so, .dylib, keeping its original case; without a match the platform is appended. A target file is qualified even when the release holds one platform, and names carry no version, so releases/latest/download/oyzu-linux-x86_64 stays stable. Extending the extension list renames matching assets.

Derived names must use ASCII letters, digits, dot, underscore or dash, at most 220 bytes, without a leading dot, and must not end in a reserved evidence suffix. Reserved evidence names follow the derived name: <asset>.provenance.sigstore.json and <asset>.publication.sigstore.json. Two planned names that are equal ignoring ASCII case collide. These checks fail with PUBLISH_ARTIFACT_SELECTION_INVALID before evidence loading, signing or network access. The plan freezes each derived name in the coordinate's assetName, which the signed intent binds; the worker re-derives it from the frozen artifact facts and refuses any other name. Earlier assets under unqualified names (oyzu) are left alone; they are never renamed or removed. Before any upload, the complete plan checks planned name collisions, aliases and independently retrieved existing assets. Matching content is reused; different bytes fail with PUBLISH_CONFLICT without overwrite or deletion. Original provenance and verified signed intent are uploaded and retrieved before their corresponding payload. Success requires exact native GET bytes, sizes/digests and evidence claims, rather than an upload acknowledgement.

The default and only supported evidence placement for both OCI and GitHub is evidence.mode = "destination". receipt and managed cannot be used to weaken remotely retrievable evidence requirements. This does not imply npm/PyPI support.

GitHub.com admits the configured API origin, exact release upload route on uploads.github.com and asset downloads on release-assets.githubusercontent.com. API path prefixes are preserved. Same-origin requests stay within that prefix; upload routes bind the repository and release ID. Redirected asset downloads remain anonymous, including a return to the API origin. Tokens never follow arbitrary redirects. Enterprise endpoints are initially limited to same-origin routes within the API prefix; translating /api/v3 to /api/uploads is unsupported. No enterprise, GitHub Actions artifact or GHCR qualification is implied.

An uncertain upload can leave a remote asset. Receipts retain verified completed, failed and unfinished native asset outcomes. Retry the unchanged plan under current authority: matching assets remain, and only missing work is attempted. Changed subjects, coordinates or evidence require a new plan; same-name different evidence is a conflict, not permission to replace it. Release metadata remains mutable by other writers; read-back is an observation, not permanent immutability.

The unreleased v1alpha1 worker, receipt and intent evolve in place to file sets, typed coordinates and entries. Old singular-subject worker bodies are rejected; there is no parallel legacy protocol. Existing OCI configuration still defaults to oci, but derived wrapper coordinates can differ because intent claims changed. Use a fresh proof namespace when comparing historical OCI qualification. Release asset naming changed every destination kind, not only GitHub: when a file has recorded compatibility, its receipt artifacts[].id, entry artifactId and unselectedArtifacts use the qualified key (cli/bin-oyzu@linux/x86_64), and its artifact identity, plan digest and signed intent include compatibility. An OCI destination still accepts files without recorded compatibility.

Releasing oyzu itself (interim)​

For preparation without publication, see the native Linux candidate review record. Its private covered-source rebuild proof demonstrates changing an embedded shell component and emitting it from a rebuilt CLI, with exact source/material identities and explicit cache/delivery limits. CLI distribution remains subject to the compliance gate; the workflow below does not grant distribution clearance.

Publishing a GitHub release triggers .github/workflows/release.yml. It runs one job per platform runner; each job downloads the newest earlier release's oyzu for its platform (tooling/bootstrap-oyzu.sh --release), builds the release tag with it natively (oyzu build cli), signs provenance and publishes its own platform's executables to the same release with oyzu publish. Asset names carry the platform, so jobs never collide and may run in parallel. When no earlier release has the qualified executable for the runner's platform, the workflow builds oyzu from the tag's source instead; that happens once per platform.

The bootstrap maps the host to its asset and verifies the digest GitHub reports before installing it as .oyzu/bin/oyzu (or oyzu.exe) with mode 755, since raw downloads lose the executable bit:

HostAsset
Linux x86_64 / aarch64oyzu-linux-x86_64 / oyzu-linux-arm64
macOS x86_64 / arm64oyzu-darwin-x86_64 / oyzu-darwin-arm64; under Rosetta (sysctl.proc_translated is 1) it takes arm64
Windows x86_64 / ARM64 (MSYS/MINGW)oyzu-windows-x86_64.exe / oyzu-windows-arm64.exe, read from PROCESSOR_ARCHITEW6432/PROCESSOR_ARCHITECTURE because uname -m reports x86_64 under emulation

tooling/bootstrap-oyzu.sh --print-asset prints the name for the current host. It does not look up the unqualified oyzu/oyzu.exe names of earlier interim releases; without a qualified asset it builds from source. Sidecar verification in the bootstrap is later work.

Create and publish the release (and its tag) first: the adapter attaches assets to an existing release found by tag, and GitHub's tag lookup does not return a draft, so a draft fails with PUBLISH_GITHUB_API: inspection returned HTTP 404. A prerelease on a private repository is visible only to collaborators and its assets need a token to download. Re-run a release with gh workflow run release.yml -f tag=<tag>.

Until a protected builder exists, the evidence comes from a local test-builder witness, tooling/release-witness.mjs. It signs SLSA provenance for the built outputs with a self-managed Ed25519 key. It is not a protected build, a trusted timestamp or a SLSA level claim. The accepted public keys are in oyzu.toml; the seeds are the repository secrets OYZU_RELEASE_BUILDER_SEED and OYZU_RELEASE_PUBLISHER_SEED in CI, or files in a directory outside the checkout:

node tooling/release-witness.mjs keys --key-dir <dir outside the checkout>    # once
gh secret set OYZU_RELEASE_BUILDER_SEED < <dir>/builder.seed
gh secret set OYZU_RELEASE_PUBLISHER_SEED < <dir>/publisher.seed

To release by hand, build, then sign with --started/--finished timestamps taken around the build (without them the witness falls back to approximate dist/ file times), then publish:

oyzu build cli
node tooling/release-witness.mjs sign --key-dir <dir> --artifact cli/bin-oyzu --artifact cli/bin-oyzu-shim
node tooling/release-witness.mjs publish --key-dir <dir> --arg --manifest --arg dist/manifest.json --arg --destination --arg github

The witness takes the same selectors as oyzu publish (cli/bin-oyzu signs every platform of that output in the manifest, cli/bin-oyzu@linux/x86_64 exactly one) and writes each bundle to .oyzu/release-evidence/<os>/<arch>/, the path the {artifact.platform} placeholder in oyzu.toml renders. Signing the same bundle again yields byte-identical evidence: the invocation ID derives from the manifest and artifact digests, and the build times and source state are recorded once per manifest in .oyzu/release-evidence/witness-run.json and reused. A retried publish over the same bundle therefore reuses the sidecars already uploaded.

Limitations:

  • Development-profile executables. oyzu build on the host compiles a development build; only --isolated uses cargo --release. The published executables report debug in --version.
  • Only Linux x86_64 is published by the workflow. Only the self-hosted Linux x86_64 runner exists while GitHub-hosted minutes are blocked. Linux arm64, macOS and Windows have no runner and are unpublished and unqualified; add a matrix entry for a runner that builds the platform natively.
  • A rebuild conflicts. A re-run that rebuilds produces different payload bytes under the same asset name, which is PUBLISH_CONFLICT. A workflow re-run rebuilds, so publish the same bundle again by hand, or delete the partial assets before re-running. Publishing a combined bundle handed off from build jobs is later work (build intent slice 6).
  • Hosted checks are unavailable. The workflow runs on the self-hosted Linux runner (as build.yml does) while GitHub-hosted minutes are blocked; it has not yet run on GitHub.

Governed publication and build registration​

With explicit --server, --account, --project (or the corresponding environment selection), the CLI stages/registers the build, then submits a durable publication operation. Pass --provenance FILE with the preexisting Sigstore bundle. The platform selects requirements and destinations centrally; caller-selected roots or signing credentials cannot grant governed authority. --destination cannot be combined with governed routing. The first slice requires one staged file artifact; --no-upload cannot satisfy this path.

Optionally pass --policy-evidence FILE with an existing signed policy report bundle when the central policy requires one. The CLI reads UTF-8 JSON and sends the original string unchanged as policyEvidence.bundle; omitting the flag omits that optional object. It does not verify the report signature, evaluate customer facts, select trusted roots, or treat report contents as approval. Central admission determines accepted producer, predicate, root and account/subject scope. A report that observes an issue is open is an observation, not an approval claim.

The operation POST is /publish/v1/accounts/{account}/projects/{project}/operations, carrying schemaVersion, registrationBuild, exact staged artifact identity/reference, and provenance.bundle. The CLI follows GET /operations/{operationId}. Build registration or staging success alone is never presented as completed distribution. The durable operation remains inspectable when following it times out; inspect that operation before submitting another request. Server URL path prefixes are preserved for staging, registration, operation submission and status following, with or without a trailing slash.

The complete governed flow and publisher isolation qualification are deferred by the maintainer's 2026-10-17 implementation-merge decision and tracked in issue #541. The standalone proof and component checks do not establish those governed guarantees in a live deployment.

Protected workers invoke the same built-in implementation through the hidden __publication-worker --request FILE bridge. This is an internal fixed contract, not a plugin ABI. The request freezes the exact file set, entries, native coordinates, evidence, signing references and operation/executor authority. Before signing and each registry mutation, the worker requests current central authorization bound to the exact operation, executor, subject, destination, provenance and signing intent. Mutation requests have no automatic transport replay. Roots and secrets are provisioned by the protected host, never returned to the caller.

The following sections document the existing registration/staging transport used before that operation, including its CI credential discovery.

Purpose​

In CI, governed oyzu publish first reads the completed build manifest (dist/manifest.json), stages its file artifact and registers its outputs and component versions. This registration uses the same output contract as platform build completion. The command then requests publication with the preexisting provenance and follows the durable operation. Its final result reports that operation's decisions, execution and verified receipts. Registration alone does not authorize external distribution.

Publishing is optional. oyzu build and everything else stay local and work without an account.

Prerequisites​

  • A finished oyzu build whose manifest records status: succeeded. A failed, cancelled or interrupted build is refused before anything is sent (PUBLISH_BUILD_NOT_SUCCEEDED).
  • The platform URL, account and project, as flags or environment variables.
  • A credential the project accepts: the pipeline's OIDC token for a trusted CI connector, or a publish token issued on the project's CI connector. See credentials.

Registration routing uses flags/environment; commit, repository and ref come from the CI system's environment or flags. Standalone publication uses the cascade above.

Credentials​

oyzu publish uses the first credential it finds, in this order:

  1. --token-env NAME, else OYZU_ID_TOKEN: an OIDC token the pipeline already holds. A --token-env variable that is unset or empty is an error, not a fall-through.
  2. GitHub Actions: when ACTIONS_ID_TOKEN_REQUEST_URL and ACTIONS_ID_TOKEN_REQUEST_TOKEN are set (the job has permissions: id-token: write), the CLI requests a token for the audience (GET $ACTIONS_ID_TOKEN_REQUEST_URL&audience=oyzu, authorized by the request token) and uses the answer's value.
  3. Bitbucket Pipelines: BITBUCKET_STEP_OIDC_TOKEN (a step with oidc: true); CircleCI: CIRCLE_OIDC_TOKEN_V2, then CIRCLE_OIDC_TOKEN.
  4. Buildkite: when BUILDKITE is set and buildkite-agent is on PATH, buildkite-agent oidc request-token --audience oyzu.
  5. OYZU_PUBLISH_TOKEN: a scoped, revocable publish token (oyzp_…) issued on the project's CI connector, for CI tools without OIDC.

A source that is present but fails (GitHub refuses the token request, the Buildkite agent fails) stops the command (PUBLISH_CREDENTIAL_UNAVAILABLE) instead of falling through to another credential. With none found the command fails with PUBLISH_NO_CREDENTIAL and, in GitHub Actions, names the missing id-token permission.

The Buildkite helper has a fixed 30-second deadline, including output capture. If it stalls, Oyzu attempts to kill the local helper and returns PUBLISH_CREDENTIAL_UNAVAILABLE with external command deadline exceeded; it does not wait indefinitely for a descendant holding an output pipe open or fall back to the publish token. Token output stays in memory and is not included in timeout diagnostics. There is no timeout setting or automatic helper retry. Check the Buildkite agent and its OIDC service/policy, then rerun oyzu publish, or explicitly select an already issued credential with --token-env. An absent agent still allows the normal discovery fallback. Killing the local helper does not guarantee remote work or descendants stopped, and the helper deadline does not bound the complete HTTP publication flow. Offline publication is unavailable. Deadline-runner regressions are authored but unexecuted on this desktop; see verification status.

Which tokens a project accepts is the platform's decision (the trusts on the project's CI connector), not the CLI's.

The token is sent only in the Authorization header of the publish request. It is never printed, logged or written to disk; progress names only where it came from (for example "a GitHub Actions OIDC token").

What is sent​

Artifact upload​

Before the build is POSTed, every artifact without an oci_digest (anything but an OCI image or index) is uploaded to the platform's registry as an OCI artifact, unless --no-upload or OYZU_PUBLISH_UPLOAD=0 is given. Images and indexes are not uploaded by the CLI; they keep their oci_digest.

  1. Check the files. Only an artifact whose path is a regular file in the bundle, of the recorded size and SHA-256 digest, is uploaded. A directory artifact is skipped with one warning and published without an oci_ref. A missing file or one whose bytes changed since oyzu build stops the publish with PUBLISH_ARTIFACT_CHANGED before any credential is requested. With no artifact left to upload, steps 2 to 4 are skipped.

  2. Upload grant. POST {server}/publish/v1/accounts/{account}/projects/{project}/builds/uploads with the same credential and headers as the publish:

    {"artifacts": [{"path": "artifacts/api/default/binary/server",
                    "media_type": "application/octet-stream",
                    "digest": "sha256:…", "size": 123}]}

    path is the artifact's path in the bundle as the manifest lists it (1 to 1000 entries, only the artifacts being uploaded). The platform answers 200:

    {"registry": "https://registry.example", "repository": "acme/web/artifacts",
     "token": "<jwt>", "expires_at": "2026-10-11T12:00:00Z"}

    404 means the platform has no artifact storage: one warning is printed and the build is published as without upload, with no oci_ref. 401, 403 and 422 fail the publish with the platform's problem, as for the publish itself; 502, 503 and 504 are retried the same way.

  3. Registry sign-in. The standard registry token flow: GET {registry}/v2/ answers 401 with WWW-Authenticate: Bearer realm="…",service="…"; the CLI calls the realm with ?service=<service>&scope=repository:<repository>:pull,push and HTTP Basic authentication (user oyzu, password the grant's token) and uses the answer's token (or access_token) as the bearer. The realm must be on the registry's own origin (scheme, host and port), so the grant token never goes elsewhere. The registry must be https, except plain http on loopback.

  4. Push. The empty config blob {} once (application/vnd.oci.empty.v1+json, sha256:44136fa355b3678a1146ad16f7e8649e94fb4fc21fe77e8310c060f61caaff8a, size 2), then for each artifact:

    • its file's bytes, uncompressed, as one blob whose digest is the artifact's digest, after HEAD /v2/<repository>/blobs/<digest>; a 200 skips the upload;

    • this manifest, serialized once in exactly this form and put to /v2/<repository>/manifests/sha256:<SHA-256 of those bytes> with Content-Type: application/vnd.oci.image.manifest.v1+json (never a tag):

      {"schemaVersion":2,"mediaType":"application/vnd.oci.image.manifest.v1+json","artifactType":"<media_type>","config":{"mediaType":"application/vnd.oci.empty.v1+json","digest":"sha256:44136fa355b3678a1146ad16f7e8649e94fb4fc21fe77e8310c060f61caaff8a","size":2},"layers":[{"mediaType":"<media_type>","digest":"<digest>","size":<size>,"annotations":{"org.opencontainers.image.title":"<file name>"}}],"annotations":{"dev.oyzu.output":"<output name>"}}

      <output name> is the target for its primary artifact and target/name otherwise, as components name build outputs.

    Registry requests that fail with a server error or in transport are retried up to three attempts; any other refusal fails the publish with PUBLISH_UPLOAD_FAILED and nothing is published.

Each uploaded artifact's output then carries "oci_ref": "<registry host[:port]>/<repository>@sha256:<manifest digest>" (no scheme).

POST {server}/publish/v1/accounts/{account}/projects/{project}/builds with Authorization: Bearer <credential>, Content-Type: application/json and Accept: application/json:

{
  "version": "1.4.2",
  "commit": "0123456789abcdef0123456789abcdef01234567",
  "repository": "acme/web",
  "ref": "refs/heads/main",
  "run_url": "https://github.com/acme/web/actions/runs/42",
  "outputs": [
    {"path": "dist/manifest.json", "kind": "manifest",
     "media_type": "application/vnd.oyzu.build-manifest.v1alpha1+json",
     "digest": "sha256:…", "size": 2101},
    {"path": "dist/image-index/image.oci.tar", "kind": "artifact",

     "digest": "sha256:…", "size": 123, "target": "image-index", "name": "primary",

     "oci_ref": "registry.example/acme/web/artifacts@sha256:…"}
  ]
}

Optional fields are omitted when unknown. outputs matches a platform runner's FinishOutput (runner contract):

  • one manifest output for the manifest file itself: its media type, the SHA-256 of its bytes and its size;
  • one artifact output per artifact the manifest lists, with the manifest's path, mediaType, digest, size, target, name and version, plus oci_digest (the manifest's ociDigest, the digest a registry addresses it by) for oci-image and oci-index artifacts only, or oci_ref for an artifact the CLI uploaded. oci_ref is the one field beyond the runner's FinishOutput. Directory artifacts carry their tree digest.

Paths are relative to the checkout root, as a runner reports them: the manifest's directory relative to -C (dist/ by default) followed by the artifact's bundle path. A --manifest outside the directory reports paths relative to its own bundle. Artifact digests are the ones oyzu build recorded; files that are uploaded are checked against them, and oyzu inspect checks the whole bundle.

The CLI checks the platform's limits before sending (PUBLISH_MANIFEST_INVALID): at most 1000 outputs, paths up to 1024 bytes, media types 255, targets 256, names 64 and versions 255; every artifact has a target, name and version, a sha256 digest, a safe relative path and, if it is an OCI image or index, a sha256 ociDigest.

Registration response (intermediate)​

The platform answers 200 with the build, its eligibility (candidate or snapshot), one entry per component and the outputs that belong to no component:

Build registered · 01jab7v3k9m2q8r4t6w0y1z5c7 (candidate)

  ✓ published api 1.4.2 (candidate)
  = already published web 2.0.0
  ! skipped worker 0.3.0: the build did not publish [worker/config]

Outputs in no component (never shipped)
  web/build-metadata

This registration response describes recorded components and does not establish external distribution. The public command proceeds to the durable publication operation; its final receipt and independently verified outcome control success. The displayed final result is the operation result described above.

A successful HTTP status alone is insufficient: the response must name the build, use candidate or snapshot eligibility, and provide components and unassigned outputs arrays. Every component names its component and version, uses published, already-published or skipped, and includes a reason when skipped. Malformed responses fail with PUBLISH_RESPONSE_INVALID in human and JSON modes. The server may already have published the build; inspect its state and check platform/client compatibility. Retrying the same build is safe.

Errors and recovery​

Every failure exits 2 and prints one diagnostic; nothing is retried that the platform refused.

CodeMeaning
PUBLISH_NOT_CONFIGUREDA server, account or project is missing or malformed.
PUBLISH_INSECURE_SERVERThe server uses plain http and is not localhost.
PUBLISH_MANIFEST_MISSING / PUBLISH_MANIFEST_INVALIDNo manifest at the path, or it breaks a rule above. Nothing is sent and no token is requested.
PUBLISH_BUILD_NOT_SUCCEEDEDThe manifest records a build that did not succeed.
PUBLISH_ARTIFACT_CHANGEDAn artifact to upload is missing, not a regular file, or no longer has its recorded size or digest. Nothing is sent; build again.
PUBLISH_UPLOAD_FAILEDThe registry refused or failed a sign-in, blob or manifest request (after retries for server errors). Nothing is published.
PUBLISH_RESPONSE_INVALIDThe platform's upload grant or answer is malformed, or names a registry that is not https (plain http only on loopback).
PUBLISH_NO_CREDENTIAL / PUBLISH_CREDENTIAL_UNAVAILABLENo credential found, or a CI system did not issue one.
PUBLISH_UNAUTHENTICATED (401)The platform did not accept the credential: expired, wrong audience or revoked.
403 (PUBLISH_<code>)"Oyzu refused this pipeline's token": the token is valid, but no trust on the project's CI connector accepts this pipeline (repository, branch or workflow).
other PUBLISH_<code>The platform's RFC 9457 problem: its detail, each errors[] entry as field: message, and the platform request id.
PUBLISH_UNREACHABLEThe platform could not be reached after retries.

Connection failures and 502, 503 and 504 answers are retried up to five attempts with backoff, honoring Retry-After (at most 30 seconds).

Limits​

  • Not qualified against a deployed platform; the endpoint is being built.
  • The first explicit publication slice accepts one finalized file. OCI images, indexes and directory publication require later native destination support.
  • Each uploaded file is read into memory for its push; very large files need that much memory. Streaming is a later refinement.
  • A registry whose token endpoint (realm) is on another origin is refused.
  • Commit, repository and ref are what the CI system says; the platform decides what it trusts from the token's claims.
  • Windows and macOS runners use the same code; the integration test runs on Linux CI.
