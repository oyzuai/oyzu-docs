Publishing finalized artifacts

CLI reference

Published from the canonical docs/reference/publish.md file. Features marked experimental remain experimental; check support limitations before relying on them.

oyzu publish distributes selected finalized files from a build bundle. The standalone path publishes to OCI registries or an existing GitHub release without a platform account; the governed path registers the build with the platform and submits a durable publication operation. Publishing is optional: oyzu build and everything else stay local and work without an account.

Status: experimental OCI and GitHub Releases publication. The standalone path distributes selected finalized files without a platform account, requires preexisting signed provenance, signs publication intent, and retrieves the registry objects to verify their bytes. Native npm, Python, OCI image archives and mutable OCI tag publication remain outside this slice. Authored code and tests are not a deployed-provider qualification; measured evidence belongs in implementation status.

Quick start​

Configure a destination and the evidence you accept, then publish a finished build:

[publish]
default = "sandbox"

[publish.destinations.sandbox]
kind = "oci"
# Optional when the build bundle has exactly one artifact:
artifacts = ["app/archive"]
registry = "https://registry.example.com"
repository = "team/artifacts"
usernameEnv = "REGISTRY_USERNAME"
passwordEnv = "REGISTRY_PASSWORD"

[publish.sets]
release = ["sandbox"]

[publish.requirements.provenance]
bundlePath = "evidence/build.sigstore.json"
publicKey = "<base64 raw 32-byte Ed25519 public key>"
builderId = "https://ci.example.com/builders/release"

[publish.requirements.signing]
keyEnv = "PUBLICATION_SIGNING_SEED"
publicKey = "<base64 raw 32-byte Ed25519 publication public key>"
oyzu build
oyzu publish --manifest dist/manifest.json --destination sandbox

This is an illustrative configuration: supply your own accepted public roots, preexisting signed evidence and independently provisioned credentials. Secret values never belong in the TOML.

Standalone OCI publication​

Run oyzu publish --manifest dist/manifest.json --destination sandbox, or omit --destination to use publish.default.

  • Repeat the option for several named destinations or select a configured set. All selected destinations are required.
  • The complete selection and evidence are checked and all publication signatures are verified before the first distribution.
  • A later destination failure leaves earlier successful publications intact and reports unfinished destinations.

Settings​

Configure through the ordinary configuration cascade, in the project root's oyzu.toml (or oyzu.local.toml) only: a [publish] table in any other folder's file is a CONFIG_SCOPE error naming its file and line (root-only, OEP-0022 OD7).

Rules:

  • publish.destinations, publish.sets and publish.requirements each resolve as one atomic value: a later cascade source replaces that entire map/object. They do not merge nested entries.
  • Profiles and existing mandatory configuration constraints apply.
  • An evidence path is relative to the source declaring the effective requirements. Artifact paths are relative to the build manifest's bundle.
  • HTTPS is required for the registry, with plain HTTP permitted only on loopback.

Destination kinds​

  • kind is optional and defaults to oci. Existing configurations need no migration.
  • GitHub Releases uses the native adapter described below.
  • npm, pypi and unknown kinds fail configuration validation with CONFIG_INVALID_VALUE before evidence loading, credentials or network access.
  • Remove the unsupported kind only when the destination is actually an OCI registry; omitting it does not enable a native package protocol.
  • Unknown destination fields also remain errors.

Selecting artifacts​

Each destination may select distinct exact build output IDs with artifacts. The ID is the target for its primary output, otherwise target/name; it is not the file's basename or the manifest's internal artifact id.

  • For example, artifacts = ["app/archive"] selects target app, output archive, while artifacts = ["app"] selects that target's primary output.
  • Omission is valid only when the manifest contains one artifact.
  • Empty or duplicate selectors fail configuration validation with CONFIG_INVALID_VALUE.
  • Explicit entries support several files and different files per destination, without implicit Cartesian fan-out.

Selectors are checked long before publishing (names that cross files):

  • oyzu config validate, oyzu build --plan and every build refuse a selector or byArtifact key whose build does not exist, or whose @os/arch is not one of the build's declared platforms, with CONFIG_REFERENCE_UNKNOWN, the file, line and column, and the nearest build name.
  • Each build's Prepare refuses an output name the builds it prepares do not produce, listing their outputs, before the first action runs.
  • At publication, unknown or ambiguous output IDs or omitted selection in a multi-artifact bundle still fail with PUBLISH_ARTIFACT_SELECTION_INVALID before evidence loading, signing or upload. Correct the exact IDs in each selected destination.

Platform selectors​

A selector may name one platform: output-id@os/arch, such as cli/bin-oyzu@linux/x86_64.

  • The platform is the one the builder recorded for the file (its oyzu.dev/artifact-compatibility fact), written in the canonical spelling x86_64/arm64; amd64 and aarch64 are accepted and normalized.
  • An unqualified selector such as cli/bin-oyzu selects every platform of that output in the bundle, each as a separate file with its own evidence, so a single-platform bundle keeps working unchanged.
  • A qualified selector whose platform the bundle lacks fails with PUBLISH_ARTIFACT_SELECTION_INVALID and lists the platforms present; so does a qualified selector for an output without a recorded platform, and two artifacts of one output and platform (the same platform in two bundles). Toolset verification runs never add an artifact (see verification toolsets).
  • Listing an output both unqualified and qualified, or the same platform twice, fails configuration validation with CONFIG_INVALID_VALUE.
  • A bundle holds several platforms of one output only when its manifest lists them; today oyzu build writes one platform per bundle, and the release workflow publishes each platform's bundle to the same release.

A bound chart needs its image​

A bound chart needs its image in the same publication (OEP-0022 OD5). A helm/chart build whose bindings point its values at an image's with.repository is published only when the same oyzu publish invocation also pushes that image to that repository: an OCI destination whose registry host and repository equal with.repository and whose artifacts select the image.

  • Otherwise publication fails with PUBLISH_BINDING_UNPUSHED before evidence, signing or upload, naming the chart destination and the destination to add.
  • Mirrors elsewhere remain allowed.
  • publish.default and each publish.sets entry are checked the same way when the configuration is read (CONFIG_BINDING_UNPUSHED).

Provenance evidence​

The manifest must record a succeeded build. The selected artifact must be a finalized regular file; its bytes and size must match its SHA-256 identity. Other outputs retain manifest validation but their files are not read or distributed.

  • Publication never builds, scans, repackages, executes project hooks, or creates missing historical evidence.
  • The evidence profile is a Sigstore v0.3 bundle carrying one DSSE application/vnd.in-toto+json envelope, an in-toto Statement v1 and SLSA build provenance v1, verified against an independently configured Ed25519 public root and exact accepted builder identity.
  • This self-managed-key profile makes no transparency-log, trusted-time, keyless identity or SLSA-level claim.
  • Standalone publication rejects --no-upload and the governed --provenance and --policy-evidence options before configuration or network access. It takes existing evidence only from the resolved publish.requirements.provenance.bundlePath setting.

For a build with different provenance per output, replace the single [publish.requirements.provenance] fields with an exact output-ID map:

[publish.requirements.provenance.byArtifact."app/archive"]
bundlePath = "evidence/app.sigstore.json"
publicKey = "<accepted base64 raw Ed25519 builder public key>"
builderId = "https://ci.example.com/builders/package"

[publish.requirements.provenance.byArtifact."cli"]
bundlePath = "evidence/cli.sigstore.json"
publicKey = "<accepted base64 raw Ed25519 builder public key>"
builderId = "https://ci.example.com/builders/cli"

These illustrative entries use the same output IDs as destination artifacts; only the selected output's profile is used.

  • Its bundlePath stays relative to the source declaring the effective requirements, and its exact subject, public key and builder are verified before signing or distribution.
  • Unselected bundle files are not read.
  • The existing single form remains supported; it still must cover the selected file.
  • Combining that form with byArtifact, using an empty map/ID, or supplying malformed profile fields fails with CONFIG_INVALID_VALUE.
  • A missing selected entry fails with PUBLISH_EVIDENCE_MISSING; add its exact profile rather than substituting another output's evidence.
  • Mapping several profiles requires exact-subject evidence for each selected file. Signing settings are unchanged.

byArtifact keys use the selector grammar above. Provenance is one bundle per file, so an output selected on several platforms needs one bundle per platform: either a qualified key per platform ("cli@linux/arm64"), or one unqualified key whose bundlePath contains the {artifact.platform} placeholder. The placeholder renders as the canonical platform, which is also a relative path:

[publish.requirements.provenance.byArtifact."cli"]
bundlePath = "evidence/{artifact.platform}/cli.sigstore.json"   # evidence/linux/x86_64/cli.sigstore.json
publicKey = "<accepted base64 raw Ed25519 builder public key>"
builderId = "https://ci.example.com/builders/cli"
  • {artifact.platform} is the only placeholder; any other { or } in bundlePath fails configuration validation.
  • An unqualified key without the placeholder that would cover several selected platforms, or a placeholder on an output without a recorded platform, fails with CONFIG_INVALID_VALUE before evidence loading.
  • Qualified and unqualified keys for the same output together fail configuration validation.
  • A missing bundle for one platform fails the whole plan with PUBLISH_EVIDENCE_MISSING naming the qualified key; nothing is published.

What is published​

The separately signed publication intent binds the exact artifact identity, media type, native coordinate, provenance digest, canonical plan digest, evidence placement and effect targets to the operation publish.

  • It cannot assert a historical build origin or completed upload.
  • Its deterministic contents exclude the invocation identifier, allowing identical republishing to reuse the native OCI coordinate.
  • The signature is verified before distribution.

The OCI artifact contains the unchanged file plus the preexisting provenance bundle and publication-intent bundle as retrievable layers.

  • The coordinate is registry/repository@sha256:<manifest-digest>.
  • Tags are unsupported: a mutable tag's preflight read cannot prevent a concurrent writer from replacing it.
  • Matching existing content is already-present; a wrong digest header, manifest, layer or declared artifact identity is a conflict.
  • Success requires independent native GETs of the manifest, config and all layers with digest/size checks. Upload acknowledgements and HEAD responses alone never establish success.

Results and exit codes​

Human output identifies the operation, selected artifact output ID, each destination outcome, exact reference and retrieved artifact digest. --json returns a v1alpha1 receipt with operationId, status, planDigest, artifacts and destinations.

  • Each destination has kind and entries with artifact ID, coordinate, reference, payload/native-asset outcomes and evidence storage/verification.
  • Artifact id is the exact selection key: output-id@os/arch for a file with a recorded platform (cli/bin-oyzu@linux/x86_64), the output ID otherwise.
  • Such an artifact also carries compatibility (kind target, native or independent, and the canonical platform), which the signed intent binds.
  • When other outputs exist, unselectedArtifacts lists their keys in sorted order. Human output lists them as unselected and not published.
  • Each destination distinguishes published, already-present, failed and unfinished, and records the manifest/artifact/evidence digests actually verified.
OutcomeExit
Successful publication0
A failed or unfinished receipt2
Preflight operation errors such as missing evidence, a wrong subject or a conflicting existing asset (through the shared CLI error path; JSON diagnostics carry the same exitCode)1

Retry the unchanged plan after resolving the failure; successful destinations are reconciled by their digest.

Standalone limits​

  • Publication needs network access. There is no offline publication success.
  • Artifacts and GET responses are currently held in memory; streaming and larger artifact qualification are deferred.
  • The implementation is shared across host platforms; only explicitly recorded native runs establish platform coverage.
  • The Linux standalone selection proof built two real binaries and verified the selected output, its original provenance and signed intent through a disposable OCI registry. It also verified that the unselected payload was absent, matching repeat/recheck behavior and early refusals.
  • That anonymous loopback run does not qualify authentication or governed execution.

Existing GitHub release​

The GitHub adapter uses the same configuration, whole-plan evidence acceptance, signing and restricted worker as OCI. The bounded GitHub.com proof passed on Windows x64, including native downloads, exact evidence/signature checks, matching/conflicting assets and controlled partial recovery. The GitHub qualification record records exact revisions and limits; broader hosts, enterprise routes and deployed platform execution remain unqualified.

Replace the destination in the Quick start example with this illustrative entry:

Which release: the release tag​

A GitHub destination commits no tag (OEP-0022 OD6). oyzu publish attaches to the release at:

  1. --tag <tag>, when given: for example a manually started release, or a release whose tags version inference does not read. It applies to every selected GitHub destination of that publication.
  2. Otherwise, the exact version tag that version inference recorded for the packages the destination publishes: the exactTags of each published artifact's version decision in its target record's extensions["oyzu.dev/versioning"]. The decision is the one for the package the artifact records (extensions["oyzu.dev/versioning"].package, written by the Rust builder and for Node workspace package archives), else the build's only decision, else the one whose version is the artifact's. A single-package repository tagged v1.4.0 at the built commit publishes to release v1.4.0; the api package of a workspace tagged api/v1.4.2 publishes to api/v1.4.2, even when worker in the same workspace has the same version.

Notes on the tag:

  • The tag is decided before evidence, signing or any network access, and then frozen in each entry's signed coordinate.
  • --tag is not tied to the built commit. When it replaces a different recorded exact version tag, publishing warns with PUBLISH_TAG_OVERRIDDEN and continues.
  • A committed tag in a github-release destination is refused in every command that reads the configuration (oyzu config validate, oyzu build, oyzu publish, ...) with CONFIG_INVALID_VALUE: publish.destinations: PUBLISH_DESTINATION_TAG_REMOVED, naming publish.destinations.<name>.tag: delete it. There is no compatibility path.

Without --tag, publishing refuses and sends nothing when:

CodeWhenRemedy
PUBLISH_TAG_UNKNOWNA published package records no exact version tag: the built commit carries no version tag that applies to it.Tag the built commit with its version (v1.4.0, or <package>/v1.4.0 for one package of a workspace), rebuild and publish again; or pass --tag.
PUBLISH_TAG_CONFLICTThe destination publishes packages whose exact version tags differ, a package records several tags, or one has a tag and another has none. The message lists each tag with its packages; when the tags all name one version (v1.4.0 and 1.4.0 on one commit) it says so.One release has one tag: give each independently versioned package its own destination, delete a duplicate tag, or pass --tag.
PUBLISH_TAG_AMBIGUOUSSeveral packages of a build share the artifact's version with different tags, and the build did not record which package produced it (another builder, or a build by an older oyzu).Rebuild with this oyzu, or pass --tag.
PUBLISH_TAG_COMMIT_MISMATCHThe derived tag points at another commit than the one the build recorded: in this checkout (when it has the tag), or on GitHub (resolved through annotated tags, checked before any write). Also when the packages record the tag on different commits.Build the tagged commit and publish again, or pass --tag to publish to that release anyway.
PUBLISH_UNSUPPORTED--tag is given but no selected destination is a GitHub release, or the publication is governed.Drop --tag.

One-time rebuild of oyzu. An oyzu built before this change requires the key, so it cannot read a configuration without it: every command, and an oyzu shim standing in for cargo, fails with CONFIG_INVALID_VALUE: invalid value for publish.destinations.

  • In this repository run tooling/bootstrap-oyzu.sh once.
  • It detects an oyzu that cannot read the configuration (oyzu config validate) and builds oyzu and oyzu-shim from source into .oyzu/bin, using that older oyzu's managed Rust with a temporary configuration holding only [tools] and oyzu.lock when cargo does not run on its own; then put .oyzu/bin first on PATH or reinstall from it.

Limits. The recorded tags are local observations of the checkout that was built, not authenticated source-control facts; the adapter still requires the tag and its release to exist on GitHub and never creates either. The tag is tied to the recorded built commit, not to a clean tree: a build of the tagged commit with uncommitted changes still records the tag (its source digest and version suffix differ) and is published to it.

Asset names​

Asset names are derived at publication from the file's local name and the compatibility its builder recorded, so one release holds several platforms of one operating system family. Bytes and local dist/ filenames never change:

Recorded compatibilityAsset nameExample
target (built for one platform)<stem>-<os>-<arch><ext>oyzu for linux/x86_64 → oyzu-linux-x86_64; oyzu.exe for windows/x86_64 → oyzu-windows-x86_64.exe; app.tar.gz for linux/arm64 → app-linux-arm64.tar.gz
independent (no platform restriction)the filenamesite.tar.gz
native (a package whose own name encodes the platform, such as a wheel)the filenamepkg-1.0-cp312-cp312-manylinux_2_28_x86_64.whl
pending, unknown or missingrefused with PUBLISH_ARTIFACT_SELECTION_INVALIDthe builder must record what the file is for

The platform uses the canonical spelling (x86_64, arm64, never amd64) and carries an ABI only when it differs from the OS's naming default ABI (GNU on Linux, MSVC on Windows, none elsewhere).

  • A GNU (glibc) Linux build is oyzu-linux-x86_64, a musl one oyzu-linux-x86_64-musl, a GNU Windows build oyzu-windows-x86_64-gnu.exe; sidecars follow the derived name.
  • The resolved ABI is always recorded in the artifact's compatibility, which the plan digest, signed intent and receipt carry.
  • Qualified selectors and output IDs (cli/bin-oyzu@linux/x86_64, cli/bin-oyzu@linux/x86_64/musl) and {artifact.platform} evidence paths use the same published form, so a GNU and a musl build of one output coexist.
  • A selector naming the default ABI (@linux/x86_64/gnu) can never match and is refused with the form to write.
  • Two artifacts whose published platforms are identical are refused with PUBLISH_ARTIFACT_SELECTION_INVALID before evidence or network access.
  • {artifact.platform} in an evidence bundlePath renders a non-nesting path form: linux/x86_64 for the default ABI, linux/x86_64-musl otherwise.

The extension rule:

  • ext is the longest case-insensitive match from .tar.gz, .tar.xz, .tar.zst, .tgz, .zip, .exe, .msi, .dmg, .pkg, .deb, .rpm, .dll, .so, .dylib, keeping its original case; without a match the platform is appended.
  • A target file is qualified even when the release holds one platform, and names carry no version, so releases/latest/download/oyzu-linux-x86_64 stays stable as long as each release builds Linux with GNU (the native Ubuntu runners do); a musl release build would publish oyzu-linux-x86_64-musl instead.
  • Extending the extension list renames matching assets.

Name validation:

  • Derived names must use ASCII letters, digits, dot, underscore or dash, at most 220 bytes, without a leading dot, and must not end in a reserved evidence suffix.
  • Reserved evidence names follow the derived name: <asset>.provenance.sigstore.json and <asset>.publication.sigstore.json.
  • Two planned names that are equal ignoring ASCII case collide.
  • These checks fail with PUBLISH_ARTIFACT_SELECTION_INVALID before evidence loading, signing or network access.
  • The plan freezes each derived name in the coordinate's assetName, which the signed intent binds; the worker re-derives it from the frozen artifact facts and refuses any other name.
  • Earlier assets under unqualified names (oyzu) are left alone; they are never renamed or removed.

Executor records:

  • Each artifact's identity also records the executor that built it (executor: host, cross-toolchain with its target, container) in the plan digest, signed intent and receipt.
  • The record is read strictly from the manifest: an unknown kind or field is PUBLISH_MANIFEST_INVALID, and a cross toolchain whose target triple does not build the artifact's platform is PUBLISH_EXECUTOR_INVALID (also checked again by the publication worker).
  • A release publication refuses a platform-specific (target or native) artifact without an executor record with PUBLISH_EXECUTOR_UNKNOWN; rebuild it with this oyzu.
  • Publication does not otherwise judge the executor: refusing cross-built or native output is a policy constraint planned for build intent slice 7.

Uploads and conflicts​

Before any upload, the complete plan checks planned name collisions, aliases and independently retrieved existing assets.

  • Matching content is reused; different bytes fail with PUBLISH_CONFLICT without overwrite or deletion.
  • Original provenance and verified signed intent are uploaded and retrieved before their corresponding payload.
  • Success requires exact native GET bytes, sizes/digests and evidence claims, rather than an upload acknowledgement.

An uncertain upload can leave a remote asset.

  • Receipts retain verified completed, failed and unfinished native asset outcomes.
  • Retry the unchanged plan under current authority: matching assets remain, and only missing work is attempted.
  • Changed subjects, coordinates or evidence require a new plan; same-name different evidence is a conflict, not permission to replace it.
  • Release metadata remains mutable by other writers; read-back is an observation, not permanent immutability.

GitHub hosts​

  • GitHub.com admits the configured API origin, exact release upload route on uploads.github.com and asset downloads on release-assets.githubusercontent.com.
  • API path prefixes are preserved. Same-origin requests stay within that prefix; upload routes bind the repository and release ID.
  • Redirected asset downloads remain anonymous, including a return to the API origin. Tokens never follow arbitrary redirects.
  • Enterprise endpoints are initially limited to same-origin routes within the API prefix; translating /api/v3 to /api/uploads is unsupported.
  • No enterprise, GitHub Actions artifact or GHCR qualification is implied.

Protocol notes​

The unreleased v1alpha1 worker, receipt and intent evolve in place to file sets, typed coordinates and entries.

  • Old singular-subject worker bodies are rejected; there is no parallel legacy protocol.
  • Existing OCI configuration still defaults to oci, but derived wrapper coordinates can differ because intent claims changed. Use a fresh proof namespace when comparing historical OCI qualification.
  • Release asset naming changed every destination kind, not only GitHub: when a file has recorded compatibility, its receipt artifacts[].id, entry artifactId and unselectedArtifacts use the qualified key (cli/bin-oyzu@linux/x86_64), and its artifact identity, plan digest and signed intent include compatibility.
  • An OCI destination still accepts files without recorded compatibility.

Incomplete platform sets​

A build records the platforms each target declares (platforms: in build.yaml) in its manifest (oyzu.dev/platforms, under the logical target that every platform variant shares). Standalone publication (every destination kind) compares them with the platforms its selected artifacts record, combining the variants of one target.

  • A declared platform of a published target with no selected artifact is a gap, whether it was never built (a build on one runner) or simply not selected (cli/bin-oyzu@linux/x86_64 only).
  • In the release context a gap refuses the whole publication with PUBLISH_PLATFORMS_INCOMPLETE before evidence loading, signing or network access, naming each missing target and platform; in any other context it is a warning and the gaps are recorded without a reason.
  • A target that declares no platforms is not checked.
  • A bundle whose manifest has no platform records (built before they existed) is refused in release with PUBLISH_PLATFORMS_UNKNOWN and warned about elsewhere.
  • A platform the project never ships belongs out of its declared platforms; an allowance is for one publication, not a standing exception.

To publish anyway, name each missing platform with a reason:

oyzu publish --destination github \
  --allow-incomplete darwin/x86_64=no-intel-mac-runner \
  --allow-incomplete windows/arm64="arm64 runner not qualified yet"
  • Each value is <platform>=<reason> (aliases accepted; the reason is 1 to 200 printable characters).
  • A malformed value, a repeated platform or a named platform that no published target is missing is CONFIG_INVALID_VALUE, so the record never claims a gap that does not exist.
  • Every gap (target, canonical platform and the allowance's reason, or null for a warned gap) is bound into the plan digest, recorded in every signed publication intent as incompletePlatforms and returned in the receipt.
  • Governed publication does not check completeness yet and refuses the flag (PUBLISH_UNSUPPORTED).

Several bundles as one publication. A release built one platform per job publishes every platform at once by repeating --manifest, one bundle each:

oyzu publish --destination github \
  --manifest bundles/linux-x86_64/dist/manifest.json \
  --manifest bundles/darwin-arm64/dist/manifest.json \
  --allow-incomplete windows/arm64=runner-unavailable
  • The bundles' artifacts are selected, checked for completeness (their target records combine, so the variants of one target cover its declared platforms together) and published in one plan.
  • Each artifact keeps its own bundle's files and executor record.
  • A bundle given twice is PUBLISH_REQUEST_INVALID; governed publication takes one manifest (PUBLISH_UNSUPPORTED).
  • The release workflow uses this.

Required verification evidence​

When a published build's configuration requires tool lines (verification.<tool>, usually from policy; OEP-0022 OD1 rule 3, R8), standalone publication (every destination kind) checks them against the verification evidence the given bundles recorded, after selection and completeness and before evidence loading, signing or network access.

Each line must be one of:

  • outside the build's native range (not applicable);
  • covered by the build's own passing tests on a version in the line;
  • covered by a passing verification run of the same build that verified its source or the published artifact, from any --manifest bundle.

Otherwise:

  • The publication fails with PUBLISH_VERIFICATION_MISSING, naming each line, why it is not covered and the commands of the runs the build left to other jobs.
  • The requirement is resolved when publishing, in the build's folder and the publication's context.
  • Pass a dedicated verification job's (oyzu build --verify-only) bundle beside the platform bundles: it is evidence only, and publication takes no artifact from it.
  • The receipt lists how each line was settled under verification. See required tool lines.
  • Governed publication does not check verification evidence yet.

Releasing oyzu itself (interim)​

For preparation without publication, see the native Linux candidate review record. Its private covered-source rebuild proof demonstrates changing an embedded shell component and emitting it from a rebuilt CLI, with exact source/material identities and explicit cache/delivery limits. CLI distribution remains subject to the compliance gate; the workflow below does not grant distribution clearance.

Publishing a GitHub release triggers .github/workflows/release.yml.

Build jobs​

It runs one build job per platform runner. Each job:

  • Downloads the newest earlier release's oyzu for its platform (tooling/bootstrap-oyzu.sh --release).
  • Builds the release tag with it natively (oyzu build cli).
  • Signs provenance with the witness (--artifact cli/bin-oyzu@<platform>; on Linux that is the GNU build, the naming default, while a musl release would need @linux/<arch>/musl).
  • Uploads its bundle (dist/, its evidence and a status) as a workflow artifact.

The bundle is staged under the runner's temporary directory, outside the checkout, so checkout's cleaning cannot delete it and the witness's source state stays clean. Build jobs have read-only repository access (contents: read); only the publish job can write the release (contents: write).

Each of the six declared platforms has a GitHub-hosted runner that builds it natively (ubuntu-24.04, ubuntu-24.04-arm, macos-15-intel, macos-15, windows-2025, windows-11-arm); the repository variable OYZU_LINUX_RUNNER (a JSON runs-on value) moves Linux x86_64 and the publish job to another runner. Paid hosted minutes are used for releases only; pull request and push checks stay on the self-hosted runner.

Publish job​

One publish job then downloads every bundle and runs oyzu publish once in the release context with one --manifest per built platform, so the declared platform set is complete; the completeness check (incomplete platform sets) refuses a release that leaves a declared platform out.

  • The publish job chooses its oyzu by the Linux x86_64 bundle's status: the executable this run built when that platform was built, otherwise (a re-run where it was already published) the release's own oyzu-linux-x86_64 through the bootstrap.
  • Before publishing it checks that this oyzu publish --help offers --allow-incomplete, repeatable --manifest and --tag, and fails with that reason if not.
  • It publishes to the committed [publish.destinations.github] with --tag "$TAG", the release that started the run, and writes no oyzu.local.toml.
  • The committed destination names oyzuai/oyzu and oyzu has no per-run repository override, so a run in a fork (another GITHUB_REPOSITORY) stops before publishing: a fork edits repository first.
  • tooling/test-release-workflow.py (run in CI) keeps the workflow, oyzu.toml and, with --cli <oyzu>, the CLI's publish flags in agreement.

Release tags:

  • The release tags so far (v0.0.2) are repository-wide: version inference reads only oyzu/v<version> tags for the oyzu package of this multi-package Cargo workspace, and a tag naming a version other than Cargo.toml's 0.1.0 would stop the build with version-conflict, so the bundles record no exact version tag to derive the release from.
  • The maintainer decided on 2026-10-20 that releases are tagged oyzu/vX.Y.Z on a commit whose Cargo.toml already says X.Y.Z (decision); a follow-up switches the workflow to tag-triggered releases without --tag.

After publishing, the publish job attaches the configuration schemas build.yaml.schema.json and oyzu.toml.schema.json, printed by the same oyzu with oyzu config schema, with gh release upload --clobber.

  • They are generated documents rather than build artifacts, so they carry no provenance sidecars, and a re-run replaces them with identical files.
  • Editors reach them through https://github.com/oyzuai/oyzu/releases/latest/download/<asset> (editor schemas), so that URL follows the release GitHub marks as latest.

Skipping and allowing platforms​

  • A job whose platform's payload and both sidecars are already on the release skips its build, and the publish job names that platform with --allow-incomplete <platform>=already-published-on-<tag>.
  • A platform deliberately not built in a release is named in the workflow's incomplete input (<platform>=<reason>, separated by ; or new lines, for example gh workflow run release.yml -f tag=<tag> -f incomplete="windows/arm64=runner unavailable"): its job is skipped and the reason goes to --allow-incomplete; nothing is allowed by default.
  • Every build job validates the whole input before doing anything else: each entry needs a = and a non-empty reason, and its platform must be one of the six canonical names (linux/amd64 and other aliases are refused).
  • linux/x86_64 cannot be named, because the publish job runs that platform's oyzu.

Re-runs and failures​

  • If any build job fails, nothing is published; re-run the failed jobs (GitHub keeps the successful jobs' bundles for the run, and a re-run job replaces its own bundle). Bundles are kept for 7 days.
  • A re-run after that finds no bundle for the expired platforms and stops with that reason; start the workflow again (gh workflow run release.yml -f tag=<tag>), which skips the platforms already on the release.
  • When no earlier release has the qualified executable for the runner's platform, the workflow builds oyzu from the tag's source instead; that happens once per platform.
  • When the earlier release's oyzu predates platform records (it has no publish --allow-incomplete), each build job also builds oyzu from the tag's source, because the publish job needs every bundle's platform and executor records: this is the case on the first release after build intent slice 6.
  • The same replacement happens when the earlier release's oyzu has no publish --tag: such an oyzu requires a committed release tag, so it cannot read this oyzu.toml; tooling/bootstrap-oyzu.sh detects that and builds oyzu from the tag's source (the first release after OEP-0022 D7).
  • A failed bootstrap stops the job; no step ignores it.
  • Create and publish the release (and its tag) first: the adapter attaches assets to an existing release found by tag, and GitHub's tag lookup does not return a draft, so a draft fails with PUBLISH_GITHUB_API: inspection returned HTTP 404.
  • A prerelease on a private repository is visible only to collaborators and its assets need a token to download.
  • Re-run a release with gh workflow run release.yml -f tag=<tag>.

Bootstrap​

The bootstrap maps the host to its asset and verifies the digest GitHub reports before installing it as .oyzu/bin/oyzu (or oyzu.exe) with mode 755, since raw downloads lose the executable bit:

  • It does not look up the unqualified oyzu/oyzu.exe names of earlier interim releases; without a qualified asset it builds from source.

Witness signing​

Until a protected builder exists, the evidence comes from a local test-builder witness, tooling/release-witness.mjs.

  • It signs SLSA provenance for the built outputs with a self-managed Ed25519 key. It is not a protected build, a trusted timestamp or a SLSA level claim.
  • The accepted public keys are in oyzu.toml; the seeds are the repository secrets OYZU_RELEASE_BUILDER_SEED and OYZU_RELEASE_PUBLISHER_SEED in CI, or files in a directory outside the checkout:
node tooling/release-witness.mjs keys --key-dir <dir outside the checkout>    # once
gh secret set OYZU_RELEASE_BUILDER_SEED < <dir>/builder.seed
gh secret set OYZU_RELEASE_PUBLISHER_SEED < <dir>/publisher.seed

To release by hand, build, then sign with --started/--finished timestamps taken around the build (without them the witness falls back to approximate dist/ file times), then publish:

oyzu build cli
node tooling/release-witness.mjs sign --key-dir <dir> --artifact cli/bin-oyzu --artifact cli/bin-oyzu-shim
node tooling/release-witness.mjs publish --key-dir <dir> --arg --manifest --arg dist/manifest.json --arg --destination --arg github --arg --tag --arg <tag>
  • The witness takes the same selectors as oyzu publish (cli/bin-oyzu signs every platform of that output in the manifest, cli/bin-oyzu@linux/x86_64 exactly one) and writes each bundle to .oyzu/release-evidence/<os>/<arch>/, the path the {artifact.platform} placeholder in oyzu.toml renders.
  • Signing the same bundle again yields byte-identical evidence: the invocation ID derives from the manifest and artifact digests, and the build times and source state are recorded once per manifest in .oyzu/release-evidence/witness-run.json and reused.
  • A retried publish over the same bundle therefore reuses the sidecars already uploaded.

Release limitations​

  • Optimized executables are not yet observed in a release run. The workflow's build step sets OYZU_CONTEXT=release (a release event's tag already implies it; a workflow_dispatch re-run runs on a branch ref), and since build intent slice 5 a release build is optimized (cargo build --release). No release has run with this yet; earlier published executables were development builds and report debug in --version. Optimized is not a publication-eligibility claim.
  • Hosted platforms are not yet qualified. Linux arm64, macOS and Windows jobs are configured for GitHub-hosted runners but have not completed a release run; until one does, treat those platforms as unqualified. Linux x86_64 has run on the self-hosted runner.
  • A partial platform conflicts on rebuild. A platform is skipped only when its payload and both sidecars are present. If an earlier attempt uploaded part of a platform, the re-run rebuilds different payload bytes under the same asset name, which is PUBLISH_CONFLICT; publish the same bundle again by hand, or delete the partial assets before re-running. Publishing a combined bundle handed off from build jobs is later work (build intent slice 6).

Governed publication and build registration​

With explicit --server, --account, --project (or the corresponding environment selection), the CLI stages/registers the build, then submits a durable publication operation.

  • Pass --provenance FILE with the preexisting Sigstore bundle.
  • The platform selects requirements and destinations centrally; caller-selected roots or signing credentials cannot grant governed authority.
  • --destination cannot be combined with governed routing.
  • The first slice requires one staged file artifact; --no-upload cannot satisfy this path.

Optionally pass --policy-evidence FILE with an existing signed policy report bundle when the central policy requires one.

  • The CLI reads UTF-8 JSON and sends the original string unchanged as policyEvidence.bundle; omitting the flag omits that optional object.
  • It does not verify the report signature, evaluate customer facts, select trusted roots, or treat report contents as approval.
  • Central admission determines accepted producer, predicate, root and account/subject scope.
  • A report that observes an issue is open is an observation, not an approval claim.

The operation:

  • The operation POST is /publish/v1/accounts/{account}/projects/{project}/operations, carrying schemaVersion, registrationBuild, exact staged artifact identity/reference, and provenance.bundle.
  • The CLI follows GET /operations/{operationId}.
  • Build registration or staging success alone is never presented as completed distribution.
  • The durable operation remains inspectable when following it times out; inspect that operation before submitting another request.
  • Server URL path prefixes are preserved for staging, registration, operation submission and status following, with or without a trailing slash.

The complete governed flow and publisher isolation qualification are deferred by the maintainer's 2026-10-17 implementation-merge decision and tracked in issue #541. The standalone proof and component checks do not establish those governed guarantees in a live deployment.

Protected workers invoke the same built-in implementation through the hidden __publication-worker --request FILE bridge. This is an internal fixed contract, not a plugin ABI.

  • The request freezes the exact file set, entries, native coordinates, evidence, signing references and operation/executor authority.
  • Before signing and each registry mutation, the worker requests current central authorization bound to the exact operation, executor, subject, destination, provenance and signing intent.
  • Mutation requests have no automatic transport replay.
  • Roots and secrets are provisioned by the protected host, never returned to the caller.

The following sections document the existing registration/staging transport used before that operation, including its CI credential discovery.

Purpose​

In CI, governed oyzu publish first reads the completed build manifest (dist/manifest.json), stages its file artifact and registers its outputs and component versions. This registration uses the same output contract as platform build completion.

  • The command then requests publication with the preexisting provenance and follows the durable operation.
  • Its final result reports that operation's decisions, execution and verified receipts.
  • Registration alone does not authorize external distribution.

Publishing is optional. oyzu build and everything else stay local and work without an account.

Prerequisites​

  • A finished oyzu build whose manifest records status: succeeded. A failed, cancelled or interrupted build is refused before anything is sent (PUBLISH_BUILD_NOT_SUCCEEDED).
  • The platform URL, account and project, as flags or environment variables.
  • A credential the project accepts: the pipeline's OIDC token for a trusted CI connector, or a publish token issued on the project's CI connector. See credentials.

Registration routing uses flags/environment; commit, repository and ref come from the CI system's environment or flags. Standalone publication uses the cascade above.

Credentials​

oyzu publish uses the first credential it finds, in this order:

  1. --token-env NAME, else OYZU_ID_TOKEN: an OIDC token the pipeline already holds. A --token-env variable that is unset or empty is an error, not a fall-through.
  2. GitHub Actions: when ACTIONS_ID_TOKEN_REQUEST_URL and ACTIONS_ID_TOKEN_REQUEST_TOKEN are set (the job has permissions: id-token: write), the CLI requests a token for the audience (GET $ACTIONS_ID_TOKEN_REQUEST_URL&audience=oyzu, authorized by the request token) and uses the answer's value.
  3. Bitbucket Pipelines: BITBUCKET_STEP_OIDC_TOKEN (a step with oidc: true); CircleCI: CIRCLE_OIDC_TOKEN_V2, then CIRCLE_OIDC_TOKEN.
  4. Buildkite: when BUILDKITE is set and buildkite-agent is on PATH, buildkite-agent oidc request-token --audience oyzu.
  5. OYZU_PUBLISH_TOKEN: a scoped, revocable publish token (oyzp_…) issued on the project's CI connector, for CI tools without OIDC.

How each CI system provides its token:

CI systemHow
GitHub Actionspermissions: id-token: write on the job; discovered automatically.
GitLab CI/CDid_tokens: on the job, for example OYZU_ID_TOKEN: {aud: oyzu}; read from OYZU_ID_TOKEN (or name another variable with --token-env).
Bitbucket Pipelinesoidc: true on the step; BITBUCKET_STEP_OIDC_TOKEN is discovered. Its audience is fixed by Bitbucket; the project's trust must accept it.
CircleCICIRCLE_OIDC_TOKEN_V2 / CIRCLE_OIDC_TOKEN are discovered. Their audience is the CircleCI organization; for an oyzu audience, mint one with circleci run oidc get --claims '{"aud":"oyzu"}' into OYZU_ID_TOKEN.

  • Which tokens a project accepts is the platform's decision (the trusts on the project's CI connector), not the CLI's.
  • The token is sent only in the Authorization header of the publish request. It is never printed, logged or written to disk; progress names only where it came from (for example "a GitHub Actions OIDC token").

A source that is present but fails (GitHub refuses the token request, the Buildkite agent fails) stops the command (PUBLISH_CREDENTIAL_UNAVAILABLE) instead of falling through to another credential. With none found the command fails with PUBLISH_NO_CREDENTIAL and, in GitHub Actions, names the missing id-token permission.

One token per request attempt​

The platform accepts a CI OIDC token once for each privileged publish operation (the build registration, the upload grant, and publication create or retry). A token sent again for the same operation is refused with HTTP 401.

  • GitHub Actions and Buildkite can issue tokens on request, so Oyzu requests a new token for every request attempt, including each retry after a connection failure or a 502, 503 or 504, (reads, such as polling a publication operation, do not consume a token and mint none). Discovery requests one first so a missing permission or a failing agent stops the command before anything is sent. A failure to issue a later token stops the command with PUBLISH_CREDENTIAL_UNAVAILABLE.
  • A fixed token (--token-env, OYZU_ID_TOKEN, Bitbucket, CircleCI, OYZU_PUBLISH_TOKEN) is sent as it is on every attempt. If a retry is refused with a 401 (or the platform's reason is replayed), the command fails with PUBLISH_CREDENTIAL_REPLAYED: a reused token is the likely cause and the earlier attempt may already have taken effect, so check the platform before publishing again, with a new token.

The Buildkite helper has a fixed 30-second deadline, including output capture. If it stalls, Oyzu attempts to kill the local helper and returns PUBLISH_CREDENTIAL_UNAVAILABLE with external command deadline exceeded.

  • It does not wait indefinitely for a descendant holding an output pipe open or fall back to the publish token.
  • Token output stays in memory and is not included in timeout diagnostics.
  • There is no timeout setting or automatic helper retry.
  • Check the Buildkite agent and its OIDC service/policy, then rerun oyzu publish, or explicitly select an already issued credential with --token-env.
  • An absent agent still allows the normal discovery fallback.
  • Killing the local helper does not guarantee remote work or descendants stopped, and the helper deadline does not bound the complete HTTP publication flow. Offline publication is unavailable.
  • Deadline-runner regressions are authored but unexecuted on this desktop; see verification status.

What is sent​

Artifact upload​

Before the build is POSTed, every artifact without an oci_digest (anything but an OCI image or index) is uploaded to the platform's registry as an OCI artifact, unless --no-upload or OYZU_PUBLISH_UPLOAD=0 is given. Images and indexes are not uploaded by the CLI; they keep their oci_digest.

  1. Check the files. Only an artifact whose path is a regular file in the bundle, of the recorded size and SHA-256 digest, is uploaded. A directory artifact is skipped with one warning and published without an oci_ref. A missing file or one whose bytes changed since oyzu build stops the publish with PUBLISH_ARTIFACT_CHANGED before any credential is requested. With no artifact left to upload, steps 2 to 4 are skipped.

  2. Upload grant. POST {server}/publish/v1/accounts/{account}/projects/{project}/builds/uploads with the same credential and headers as the publish:

    {"artifacts": [{"path": "artifacts/api/default/binary/server",
                    "media_type": "application/octet-stream",
                    "digest": "sha256:…", "size": 123}]}

    path is the artifact's path in the bundle as the manifest lists it (1 to 1000 entries, only the artifacts being uploaded). The platform answers 200:

    {"registry": "https://registry.example", "repository": "acme/web/artifacts",
     "token": "<jwt>", "expires_at": "2026-10-11T12:00:00Z"}

    404 means the platform has no artifact storage: one warning is printed and the build is published as without upload, with no oci_ref. 401, 403 and 422 fail the publish with the platform's problem, as for the publish itself; 502, 503 and 504 are retried the same way.

  3. Registry sign-in. The standard registry token flow: GET {registry}/v2/ answers 401 with WWW-Authenticate: Bearer realm="…",service="…"; the CLI calls the realm with ?service=<service>&scope=repository:<repository>:pull,push and HTTP Basic authentication (user oyzu, password the grant's token) and uses the answer's token (or access_token) as the bearer. The realm must be on the registry's own origin (scheme, host and port), so the grant token never goes elsewhere. The registry must be https, except plain http on loopback.

  4. Push. The empty config blob {} once (application/vnd.oci.empty.v1+json, sha256:44136fa355b3678a1146ad16f7e8649e94fb4fc21fe77e8310c060f61caaff8a, size 2), then for each artifact:

    • its file's bytes, uncompressed, as one blob whose digest is the artifact's digest, after HEAD /v2/<repository>/blobs/<digest>; a 200 skips the upload;

    • this manifest, serialized once in exactly this form and put to /v2/<repository>/manifests/sha256:<SHA-256 of those bytes> with Content-Type: application/vnd.oci.image.manifest.v1+json (never a tag):

      {"schemaVersion":2,"mediaType":"application/vnd.oci.image.manifest.v1+json","artifactType":"<media_type>","config":{"mediaType":"application/vnd.oci.empty.v1+json","digest":"sha256:44136fa355b3678a1146ad16f7e8649e94fb4fc21fe77e8310c060f61caaff8a","size":2},"layers":[{"mediaType":"<media_type>","digest":"<digest>","size":<size>,"annotations":{"org.opencontainers.image.title":"<file name>"}}],"annotations":{"dev.oyzu.output":"<output name>"}}

      <output name> is the target for its primary artifact and target/name otherwise, as components name build outputs.

    Registry requests that fail with a server error or in transport are retried up to three attempts; any other refusal fails the publish with PUBLISH_UPLOAD_FAILED and nothing is published.

Each uploaded artifact's output then carries "oci_ref": "<registry host[:port]>/<repository>@sha256:<manifest digest>" (no scheme).

Directory artifacts carry their tree digest.

Paths and digests:

  • Paths are relative to the checkout root, as a runner reports them: the manifest's directory relative to -C (dist/ by default) followed by the artifact's bundle path. A --manifest outside the directory reports paths relative to its own bundle.
  • Artifact digests are the ones oyzu build recorded; files that are uploaded are checked against them, and oyzu inspect checks the whole bundle.

The CLI checks the platform's limits before sending (PUBLISH_MANIFEST_INVALID): at most 1000 outputs, paths up to 1024 bytes, media types 255, targets 256, names 64 and versions 255; every artifact has a target, name and version, a sha256 digest, a safe relative path and, if it is an OCI image or index, a sha256 ociDigest.

Registration response (intermediate)​

The platform answers 200 with the build, its eligibility (candidate or snapshot), one entry per component and the outputs that belong to no component:

  web/build-metadata

This registration response describes recorded components and does not establish external distribution. The public command proceeds to the durable publication operation; its final receipt and independently verified outcome control success. The displayed final result is the operation result described above.

Validation:

  • A successful HTTP status alone is insufficient: the response must name the build, use candidate or snapshot eligibility, and provide components and unassigned outputs arrays.
  • Every component names its component and version, uses published, already-published or skipped, and includes a reason when skipped.
  • Malformed responses fail with PUBLISH_RESPONSE_INVALID in human and JSON modes. The server may already have published the build; inspect its state and check platform/client compatibility. Retrying the same build is safe.

PUBLISH_NO_CREDENTIAL / PUBLISH_CREDENTIAL_UNAVAILABLENo credential found, or a CI system did not issue one.
PUBLISH_CREDENTIAL_REPLAYED (401)The platform refused a fixed CI token on a retry (any 401), or said it was reused (reason replayed). After a retry, the earlier attempt may already have taken effect: check the platform, then publish again with a new token. Only fixed tokens can be reused; GitHub Actions and Buildkite send a new token per attempt.
PUBLISH_UNAUTHENTICATED (401)The platform did not accept the credential: expired, wrong audience or revoked.
403 (PUBLISH_<code>)"Oyzu refused this pipeline's token": the token is valid, but no trust on the project's CI connector accepts this pipeline (repository, branch or workflow).
other PUBLISH_<code>The platform's RFC 9457 problem: its detail, each errors[] entry as field: message, and the platform request id.
PUBLISH_UNREACHABLEThe platform could not be reached after retries.

Connection failures and 502, 503 and 504 answers are retried up to five attempts with backoff, honoring Retry-After (at most 30 seconds). Each retry carries its own token where the credential source can issue one (see One token per request attempt).

Limits​

  • Not qualified against a deployed platform; the endpoint is being built.
  • The first explicit publication slice accepts one finalized file. OCI images, indexes and directory publication require later native destination support.
  • Each uploaded file is read into memory for its push; very large files need that much memory. Streaming is a later refinement.
  • A registry whose token endpoint (realm) is on another origin is refused.
  • Commit, repository and ref are what the CI system says; the platform decides what it trusts from the token's claims.
  • Windows and macOS runners use the same code; the integration test runs on Linux CI.
