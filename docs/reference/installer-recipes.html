Installer-asset recipes

CLI reference

Published from the canonical docs/reference/installer-recipes.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Some npm packages download extra files while they install or run: Puppeteer downloads a browser, node-gyp downloads Node.js headers. A captured build (oyzu build --isolated) runs without network, so those downloads would fail. For packages Oyzu recognizes, it downloads the matching file during preparation, checks it against a pinned SHA-256 and points the tool at it through the tool's own settings. Your project declares nothing.

Note: Recipes cover Puppeteer and node-gyp on Linux x86-64 workers only, and there is no setting to turn one off yet. A native host build (without --isolated) has network access and downloads as the package intends.

How it works​

  1. After the package manager's captured install preparation, Oyzu reads the locked packages and the Node version.
  2. For each recognized package it looks up the pinned asset. If your version or platform has no pinned asset, Oyzu says so in the build log and guesses nothing (see When a package is recognized but not pinned).
  3. Oyzu downloads each asset the same way as a declared fetch, checks it against the pinned digest, stores it by digest under <user data>/cache/fetches/ and unpacks it under recipes/<recipe>/ in the prepared dependency tree.
  4. The build sees that tree read-only at /dependencies. Every command (install, tasks and package) gets the recipe's settings, so the install script skips its download and the tool finds the asset when it runs.

If an administrator restricts downloads with fetches.sources, the asset's host must be allowed there, as for any declared fetch.

Puppeteer​

RecognizedEvery locked version of the registry package puppeteer, in npm, pnpm or Yarn locks
AssetsChrome for Testing chrome and chrome-headless-shell for linux64, at the build Puppeteer pins for that release
URLhttps://storage.googleapis.com/chrome-for-testing-public/<build>/linux64/<browser>-linux64.zip
Layoutrecipes/puppeteer/<browser>/linux-<build>/<browser>-linux64/ (Puppeteer's cache layout)
SettingsPUPPETEER_CACHE_DIR=/dependencies/recipes/puppeteer, PUPPETEER_SKIP_DOWNLOAD=true
Pinned releasesPuppeteer 24.0.0 to 25.13.0, and 25.16.0

Puppeteer's install script sees PUPPETEER_SKIP_DOWNLOAD and doesn't try the network. puppeteer.launch() and puppeteer.executablePath() read PUPPETEER_CACHE_DIR and find the browser for their own pinned build, so your project needs no change. Both browsers are delivered because Puppeteer downloads both by default. Firefox is skipped by default and has no recipe.

Limits:

  • Only linux/amd64 workers have pinned assets. Chrome for Testing has no Linux arm64 build before Chrome 153. On other platforms the log says the browser isn't pinned.
  • If you select another browser build (PUPPETEER_CHROME_VERSION, chrome.version in .puppeteerrc) or another cache directory, your setting overrides the recipe for that value and the install fails offline.
  • The base execution image doesn't include the system libraries Chrome needs to start (libnss3 and others). The recipe delivers the browser. To launch it, use an image that has those libraries (--image npm=<image>).

node-gyp headers​

RecognizedA locked registry package whose archive has a top-level binding.gyp, or a binding.gyp in the project root
Assetnode-v<version>-headers.tar.gz for the Node version in use
URLhttps://nodejs.org/dist/v<version>/node-v<version>-headers.tar.gz
Layoutrecipes/node-gyp/<version>/node-v<version>/include/node/
Settingsnpm_config_nodedir=/dependencies/recipes/node-gyp/<version>/node-v<version>
Pinned releasesNode.js 18.0.0 to 26.11.1, plus the 22.23.4 security-release headers

node-gyp reads npm_config_nodedir and uses those headers instead of downloading them. The scripts that npm, pnpm and Yarn run inherit the variable.

The headers alone don't compile an addon. You also need Python, make and a C++ compiler in the image. The base execution image has make and g++ but no Python, so a build that compiles an addon needs an image of its own: provide one with --image npm=<image>. Addons that download a prebuilt binary first (prebuild-install, node-pre-gyp) still fail offline unless they fall back to compiling.

When a package is recognized but not pinned​

Preparation continues and the build log shows one line for the recipe:

Recipe puppeteer    puppeteer@25.14.0 has no pinned Chrome for Testing build in this Oyzu release; its install script will try to download one

Preparation doesn't fail here, because your project may already avoid the download with the tool's own settings. If it doesn't, the install fails as described next.

Downloads without a recipe​

When a captured npm install fails because a script couldn't reach the network, the error names the package, the URL and the fix, as far as npm's output shows them:

DEPENDENCY_INPUT_MISSING: the install script of cypress@13.6.0 tried to download https://download.cypress.io/desktop.json, and captured execution has no network. Oyzu has no recipe for this asset. Declare it as a pinned fetch in build.yaml (name, url, sha256) and point the package at OYZU_FETCH_<NAME> through its own setting; see the declared fetches reference.

The original npm output follows the message. If Oyzu can't find a URL it names the host instead, and if there was no network error it reports npm's failure unchanged. This diagnosis covers npm installs. pnpm and Yarn report their native error. For the root package, npm reports the build version that version inference applied, which can differ from the version in your manifest.

To supply the asset yourself, add a declared fetch and set the tool's own variable to its path. For Puppeteer on an unpinned release, fetch the Chrome for Testing zip with unpack: zip and set PUPPETEER_SKIP_DOWNLOAD=true and PUPPETEER_EXECUTABLE_PATH=/dependencies/fetches/<name>/chrome-linux64/chrome.

Spotless Eclipse P2 artifacts (unsupported)​

Spotless steps backed by Eclipse formatters (<eclipse>, <greclipse>, <eclipseWtp> and <eclipseCdt> in the Maven plugin, and their Gradle equivalents) download Eclipse P2 bundles from download.eclipse.org at run time, into Spotless's own cache. There is no recipe for this, and a declared fetch can't be pointed at that cache. In a captured Maven build, spotless-maven-plugin:check fails during preparation with java.net.UnknownHostException: download.eclipse.org.

To work around it, run that Spotless check outside the captured build, or keep the Eclipse step out of the captured lifecycle, for example with a Maven profile that sets spotless.check.skip=true.

Pinned digests and trust​

Every recipe asset has a SHA-256 in a table inside Oyzu. A download whose bytes don't match fails with INTEGRITY_MISMATCH and nothing is stored. Oyzu never takes a digest from the network at build time.

  • Chrome for Testing publishes no checksums. Oyzu's digests were computed from the downloaded zip after its bytes matched the checksum Google Cloud Storage reports for the file.
  • Node.js header digests come from each release's SHASUMS256.txt. The signature of that file was not checked.

The dependency snapshot records each asset with verification: digest-only: the bytes match the pinned digest, but no publisher signature was checked.

Build evidence​

Each asset becomes a package in the target's dependency snapshot:

FieldValue
idrecipe:<target>/<recipe>/<asset>/<version>, for example recipe:web/puppeteer/chrome/136.0.7103.94
name, versionThe asset name (chrome, chrome-headless-shell, node-headers) and its upstream version
sourceIdfetch:<host> for a standalone build, or fetches.sources/<index> under an allowlist
digest, sizeThe verified bytes
purpose, verificationbuild, digest-only

The extension oyzu.dev/recipes lists each applied recipe with the packages it serves, its settings and each asset's path and tree digest. Both are part of the snapshot digest, so the build plan is bound to the delivered assets.

Behavior to know​

  • Recipes apply automatically to every captured Node build that locks a recognized package.
  • The digest tables cover a fixed range of releases. A newer release needs an Oyzu update.
  • Recipe settings override the same variable from the builder plan. If a variable is delivered twice (for example by a recipe and a declared fetch), the build fails.

Errors​

Recipe assets use the declared fetch errors. The message names the recipe, the asset and the package, for example web: puppeteer recipe asset chrome 136.0.7103.94 for puppeteer@24.9.0.

CodeCauseRecovery
SOURCE_DENIEDAn administrative fetches.sources doesn't allow the asset's hostAsk an administrator to allow it, such as https://storage.googleapis.com/chrome-for-testing-public/
INTEGRITY_MISMATCHThe downloaded bytes differ from the pinned digestReport it. Don't change the digest without checking the upstream release.
DEPENDENCY_INPUT_MISSINGAn offline build needs an asset that isn't stored, or an install script without a recipe tried the networkRun one online build, or declare the asset as above
