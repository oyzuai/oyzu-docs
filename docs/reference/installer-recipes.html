Installer-asset recipes

CLI reference

Published from the canonical docs/reference/installer-recipes.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Some packages download extra files while they install or run: Puppeteer downloads a browser, node-gyp downloads Node.js headers. A captured build runs without network, so those downloads fail. For a package Oyzu recognises, the builder downloads the matching file during preparation and points the tool at it through the tool's own settings. The project declares nothing.

Status: experimental and provisional. This answers the "known recipes" open decision of the declared fetches design for the Node builder. The choices marked provisional below need maintainer review. Recipes have unit tests and a registered compiled-CLI check, which have not been run yet (see verification).

How a recipe works​

A recipe is a table owned by the builder: a recognised package, the asset URL for its locked version, a SHA-256 pinned in the repository, and the settings and cache layout the tool reads. Recipes reuse the declared fetches engine, with no second download path:

  1. After the package manager's captured preparation, the Node builder reads the locked packages, the verified registry archives and the captured Node version.
  2. For each recognised package it looks up the pinned asset. A version or platform without a pinned asset is reported (below) and nothing is guessed.
  3. Each asset is admitted against fetches.sources, downloaded through the broker, verified against the pinned digest, stored by digest under <user data>/cache/fetches/ and unpacked under recipes/<recipe>/ in the prepared tree, in the tool's own layout.
  4. Execution sees the prepared tree read-only at /dependencies. Every command action (install, tasks and package) gets the recipe's settings, so the install script skips its download and the tool finds the asset at run time.

Recipes apply to captured Node builds, which is oyzu build --isolated. A native host build runs with network and downloads as the package intends.

Puppeteer​

RecognisedEvery locked version of the registry package puppeteer, in npm, pnpm or Yarn locks
AssetsChrome for Testing chrome and chrome-headless-shell for linux64, at the build Puppeteer pins for that release
URLhttps://storage.googleapis.com/chrome-for-testing-public/<build>/linux64/<browser>-linux64.zip
Layoutrecipes/puppeteer/<browser>/linux-<build>/<browser>-linux64/, Puppeteer's cache layout
SettingsPUPPETEER_CACHE_DIR=/dependencies/recipes/puppeteer, PUPPETEER_SKIP_DOWNLOAD=true
PinnedPuppeteer releases 24.0.0 to 25.13.0, in puppeteer.tsv

Puppeteer's install script reads PUPPETEER_SKIP_DOWNLOAD and does not try the network. puppeteer.launch() and puppeteer.executablePath() read PUPPETEER_CACHE_DIR and resolve the browser for their own pinned build, so the project needs no change. Both browsers are delivered because Puppeteer's install script downloads both by default. Firefox is skipped by Puppeteer by default and has no recipe.

Limits:

  • Only linux/amd64 workers are pinned. Chrome for Testing has no Linux arm64 build before Chrome 153, and on other platforms the log reports that the browser is not pinned.
  • A Puppeteer configuration file or variable that selects another browser build (PUPPETEER_CHROME_VERSION, chrome.version in .puppeteerrc) or another cache directory overrides the recipe for that setting, and the install fails offline.
  • The toolchain image omits the system libraries Chrome needs to start (libnss3 and others). The recipe delivers the browser; a build that launches it needs an image that has them.

node-gyp headers​

RecognisedA locked registry package whose archive has a top-level binding.gyp, or a binding.gyp in the project root. Native install compiles these with node-gyp
Assetnode-v<version>-headers.tar.gz for the captured Node version
URLhttps://nodejs.org/dist/v<version>/node-v<version>-headers.tar.gz
Layoutrecipes/node-gyp/<version>/node-v<version>/include/node/
Settingsnpm_config_nodedir=/dependencies/recipes/node-gyp/<version>/node-v<version>
PinnedNode.js 18.0.0 to 26.11.1, in node-headers.tsv

node-gyp reads npm_config_nodedir and uses those headers instead of downloading them. The scripts npm, pnpm and Yarn run inherit the variable. The headers are not enough on their own: compiling an addon also needs Python, make and a C++ compiler in the image, and the default toolchain image has none. Addons that download a prebuilt binary first (prebuild-install, node-pre-gyp) still fail offline unless they fall back to compiling.

The authored npm-node-gyp-consumer fixture prepares a root Node-API addon with no package dependencies. Its native tests and standalone exported-addon consumer are written, not executed. Qualification must use a separately provisioned compiler/Python image through the existing build --image npm=<image> override, retaining the normal header recipe, network-denied execution and report gates. A Linux addon must be consumed in a matching Linux runtime; a Windows host Node process cannot establish that proof. The install analyzer now records the root binding.gyp probe and retains the existing unbounded lifecycle scope when npm implicitly runs node-gyp rebuild; see builder-owned stages. Its focused regressions and native proof remain unrun. This preserves native installation semantics without adding an explicit install script to the fixture.

The registered node-gyp-recipe acceptance check supplies the original fixture's exact Node request and tool lock, without a handcrafted dependency lock. It requires a real compiled addon and three native tests with JUnit/coverage, then extracts only the inspected archive's regular addon/wrapper/results files into a separate dependency-free consumer project. A second captured build executes that consumer in the selected Linux image, runs three additional native tests and packages its actual consumed.json. Both builds retain full quality gates, source/tool-lock equality and bundle inspection. Each temporary project selects its explicit fixture root, avoiding unrelated ancestor configuration. This flow remains unrun:

oyzu exec --store <verified-tool-store> -- python tooling/test-build-scenarios.py --suite node --only node-gyp-recipe --store <verified-tool-store> --image npm=<provisioned-native-image> --cli <compiled-oyzu-path> --evidence-dir <task-evidence-directory>

When a package is recognised but not pinned​

Preparation continues and the build log shows one fact per recipe, for example:

Recipe puppeteer    puppeteer@25.14.0 has no pinned Chrome for Testing build in this Oyzu release; its install script will try to download one

Preparation does not fail, because the project may already avoid the download with the tool's own settings. Otherwise the install then fails as described next.

Downloads without a recipe​

When a captured npm install fails because a lifecycle script could not reach the network, the error names the package, the URL and the remedy, where npm's output shows them:

DEPENDENCY_INPUT_MISSING: the install script of cypress@13.6.0 tried to download https://download.cypress.io/desktop.json, and captured execution has no network. Oyzu has no recipe for this asset. Declare it as a pinned fetch in build.yaml (name, url, sha256) and point the package at OYZU_FETCH_<NAME> through its own setting; see the declared fetches reference.

The original npm output follows the message. The package comes from npm's npm error path line and the URL from the script's output on the host named by its network error (getaddrinfo EAI_AGAIN, ENOTFOUND, connect ENETUNREACH, EHOSTUNREACH, ECONNREFUSED or Could not resolve host). Without a URL the host is named; without a network error the npm failure is reported unchanged. This diagnosis covers npm installs; pnpm and Yarn report their native error. For the root package, npm reports the effective build version applied by version inference, which may differ from the source manifest's version. The acceptance check compares that exact published identity alongside the URL and declared-fetch remedy.

To supply such an asset yourself, add a declared fetch and set the tool's own variable to its path in the target environment. For Puppeteer on an unpinned release, for example, fetch the Chrome for Testing zip with unpack: zip and set PUPPETEER_SKIP_DOWNLOAD=true and PUPPETEER_EXECUTABLE_PATH=/dependencies/fetches/<name>/chrome-linux64/chrome.

Spotless Eclipse P2 artifacts (unsupported)​

Spotless steps backed by Eclipse formatters (<eclipse>, <greclipse>, <eclipseWtp> and <eclipseCdt> in the Maven plugin, and their Gradle equivalents) provision Eclipse P2 bundles from download.eclipse.org at run time, into Spotless's own P2 cache rather than a file path. There is no JVM recipe, and a declared fetch cannot be pointed at that cache. In a captured Maven build spotless-maven-plugin:check fails during preparation with java.net.UnknownHostException: download.eclipse.org (observed for assertj/assertj in the captured-feasibility corpus).

Recovery: run that Spotless check outside the captured build, or keep the Eclipse step out of the captured lifecycle, for example with a Maven profile that sets spotless.check.skip=true.

Pinned digests and trust​

Every recipe asset has a SHA-256 in an in-repo table. A download whose bytes do not match fails with INTEGRITY_MISMATCH and stores nothing. Oyzu never takes a digest from the network at build time (no trust on first use).

  • Chrome for Testing publishes no checksums. Each digest was computed from the downloaded zip after its bytes matched the MD5 that Google Cloud Storage reports for the object (x-goog-hash), and its size matched. The build list comes from PUPPETEER_REVISIONS in each puppeteer-core release.
  • Node.js headers digests come from each release's SHASUMS256.txt and were checked against the downloaded bytes. The signature of SHASUMS256.txt was not checked when the table was written.

The snapshot records each asset as a package with verification: digest-only: the bytes match the pinned digest, but no publisher signature was checked. tooling/refresh-node-recipes.py regenerates both tables with the same checks; review the diff before committing.

Evidence​

Each asset becomes a package in the target's dependency snapshot:

FieldValue
idrecipe:<target>/<recipe>/<asset>/<version>, for example recipe:web/puppeteer/chrome/136.0.7103.94
name, versionThe asset name (chrome, chrome-headless-shell, node-headers) and its upstream version
sourceIdfetch:<host> standalone, or fetches.sources/<index> under an allowlist
digest, sizeThe verified bytes
purpose, verificationbuild, digest-only

The extension oyzu.dev/recipes lists each applied recipe with the packages it serves, its settings and each asset's path and tree digest. Both are part of the snapshot digest, so the plan binds the delivered assets.

Errors​

Recipe assets use the declared fetch errors. The label names the recipe, the asset and the package, for example web: puppeteer recipe asset chrome 136.0.7103.94 for puppeteer@24.9.0.

CodeCauseRecovery
SOURCE_DENIEDAn administrative fetches.sources does not admit the asset's hostAsk an administrator to admit it, such as https://storage.googleapis.com/chrome-for-testing-public/
INTEGRITY_MISMATCHThe upstream bytes differ from the pinned digestReport it; do not edit the table without checking the upstream release
DEPENDENCY_INPUT_MISSINGAn offline build needs an asset that is not stored, or an install script without a recipe tried the networkRun one online build, or declare the asset as above

Provisional decisions​

These need maintainer review:

  • Recipes apply automatically to every captured Node build that locks a recognised package. There is no setting to turn one off yet.
  • The digest tables live in the repository and cover a fixed range of releases. A newer release needs a table update and an Oyzu release.
  • A recognised package without a pinned asset is a build-log fact, not a preparation failure.
  • Recipe settings override the same variable from the builder plan, and a variable delivered twice (for example by a recipe and a declared fetch) fails.
  • fetches.sources governs recipes as well as declared fetches.

Verification​

The first functional proof combines the compiled CLI's ordinary captured build of the unchanged npm installer fixture with a separate native companion project, preserving each project's source and lock bytes during execution. Preparation must acquire and verify both pinned Puppeteer browsers through the existing broker; the network-denied install and build must produce an inspected, independently usable artifact. Dependency evidence must identify the two browser assets and their effective cache settings. An expected unsupported refusal alone does not establish this successful flow.

A second required flow compiles and consumes a native node-gyp addon using the captured headers and an explicitly identified compiler/Python runtime. This establishes recipe reuse beyond browser delivery. Browser startup remains a separate functional obligation when a browser-executing project is selected; the existing missing-system-library limitation is not silently waived. Keep additional hosts and architecture qualification separate from these bounded Linux/amd64 flows.

Unit tests cover the pinned tables, Puppeteer and node-gyp recognition from captured facts, unpinned versions and platforms, recipe capture, offline reuse, digest mismatch and allowlist denial (dependencies::fetches and builders::node::recipes), and the install diagnosis (node --test tooling/test-install-diagnosis.mjs). The installer-recipes check in the node suite builds tooling/fixtures/npm-installer-recipes (puppeteer 24.9.0, esbuild and sharp) with oyzu build --isolated, checks source and tool-lock preservation and inspects the bundle. It retains the diagnosis for an unrecognised download. Its native npm exclusion and build-only scripts remain unchanged; this baseline alone cannot establish artifact/report acceptance.

The separately selectable installer-recipes-consumer check uses npm-installer-consumer sources. Before the source snapshot, the harness derives its package manifest from the original and adds only ordinary native packaging/build/test declarations. It copies the original exact dependency/tool locks, tool request and ignore file. Its name, version and dependencies match the lock's root; no lock regeneration or second tracked dependency declaration is needed. Native files: ["dist"] declares packaging intent. Native esbuild compiles a TypeScript module and sharp generates a PNG; Node's three tests consume those outputs and check both prepared browser executables. The existing full_checks wrapper selects real test/lint/format stages and required JUnit/coverage collection.

Acceptance requires the inspected npm archive to deliver the module, PNG and dist/results.json. The standalone consume.mjs executable runs in a separate Node process selected through oyzu exec and imports the exported module, reads the PNG signature/dimensions and checks the four successful recipe results, without project dependencies or the private build workspace. Reports must come from the actual native tests; no XML is fabricated. Neither check starts a browser or proves node-gyp compilation.

The separately selected puppeteer-startup follow-up adds a real native Node test that calls Puppeteer's prepared headless-shell executable, evaluates a local page to 42, captures a 64-by-32 PNG and waits for the browser to exit. It requests Puppeteer's default sandbox, checks that neither --no-sandbox nor --disable-setuid-sandbox was supplied, and fails rather than skips when native libraries or sandbox prerequisites are missing. Absence of bypass flags is not a general browser-confinement qualification.

This check derives its native manifest from the same original installer fixture, reuses its exact dependency/tool locks and copies the completed companion's build/tests without changing those originals. Existing full_checks plus the isolated invocation select genuine native JUnit/coverage and quality gates. All four tests must pass, including the actual browser test, before packaging. The exported npm archive must contain the rendered HTML, screenshot and receipt in addition to the companion's original module/PNG/results. Independent built-in-only Node consumers check only files extracted from that final archive; they do not launch a host browser. Browser execution belongs to the captured producer, not these output-consumption checks.

The focused invocation is:

oyzu exec --store <verified-tool-store> -- python tooling/test-build-scenarios.py --suite node --only puppeteer-startup --store <verified-tool-store> --image npm=<qualified-browser-image> --cli <compiled-oyzu-path> --evidence-dir <new-evidence-directory>

Supply an explicitly qualified Linux/amd64 image with a matching compiled worker, the existing Node quality tooling, Chrome's native libraries and working default browser sandbox support under the ordinary executor. No image is provisioned or security setting changed by this check. The standard missing-library boundary above remains; this authored check has not yet established a passing browser startup. See the startup qualification checkpoint.

With managed Python, harness requirements and the Linux Docker worker available, the focused command from the repository root is:

oyzu exec --store <verified-tool-store> -- python tooling/test-build-scenarios.py --suite node --only installer-recipes-consumer --store <verified-tool-store> --cli <compiled-oyzu-path> --evidence-dir <task-evidence-directory>

The bounded Windows-controller/Linux-amd64 flows are now demonstrated. The unchanged original fixture passed its four build-only actions and inspection; the genuine unknown download produced the package, effective version, URL and pinned-fetch remedy. The separate companion passed all seven native actions, three tests, coverage, full quality gates and inspection, and an independent Oyzu-managed Node process consumed its delivered module, PNG and results. All source inputs and locks remained unchanged. Earlier failed registered summaries remain failed; detailed corrections are in qualification.

The registered node-gyp-recipe also passed end to end with a verified compiler/Python task image. It compiled the addon offline using captured Node 22.23.3 headers, packaged the regular ELF addon and transferred only the exported payload to a second Linux captured project. Both builds passed seven native actions, three genuine tests each, wrapper LCOV, full quality gates, packaging and inspection. The independent consumer loaded the addon and packaged its consumption result. All nine original inputs and the tool lock stayed unchanged in each project. Node LCOV covers the JavaScript wrapper; C is not instrumented.

With the same prerequisites, select that check and explicit provisioned image:

oyzu exec --store <verified-tool-store> -- python tooling/test-build-scenarios.py --suite node --only node-gyp-recipe --store <verified-tool-store> --image npm=<linux-amd64-image-IID> --cli <compiled-oyzu-path> --evidence-dir <task-evidence-directory>

Rust formatting, managed Python/JavaScript syntax, registration, tool-contract shape/schema and documentation checks pass. The isolated full workspace Rust rerun passed with 1,819 tests passed, zero failed and 37 ignored, including all 17 previously failing tests. The original failure and its test-only/launcher corrections remain recorded in qualification. Strict workspace/all-target Clippy also passes with warnings treated as errors. All nine reported real CLI development-task behaviors pass against the paired candidate, including Windows native launchers. The fresh-checkout proof is unavailable on this Windows host because its explicit platform guard supports Linux/macOS only. Unix host confinement, browser startup and wider platforms remain unproved. A Windows controller does not qualify Windows workers; macOS workers are not covered. Native candidate records do not establish exact Git-to-compiler byte binding or release provenance. See the qualification record for the actual commands, image and artifact identities, preserved failures and verification limits.
