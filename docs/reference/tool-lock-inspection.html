Tool lock files and inspection

CLI reference

Published from the canonical docs/reference/tool-lock-inspection.md file. Features marked experimental remain experimental; check support limitations before relying on them.

oyzu.lock records the exact tool versions, download URLs and digests a project uses. This page describes what the lock contains, how oyzu pin decides which platforms to lock, and how to check a lock file with oyzu tools inspect-lock.

Note: Experimental. The lock format may change.

What a lock contains​

All tool locks use format = 1. One file can hold two kinds of records, and neither implies the other:

  • resolved_environment and resolution records: what oyzu pin resolved (versions, URLs and digests per platform).
  • environment and tool records: verified installations.

It can also hold optional [[requirements]] records, which list what Oyzu discovered your builds need. Their resolved and installed fields are always false.

oyzu pin updates resolution records and keeps installation records; oyzu install keeps resolutions. Any other format value fails.

A set locked for a toolset carries toolset = "NAME". Sets for [tools] carry none. The label only decides which sets a command changes; the same requests get the same identity in every toolset. Entries have no scope or profile field. The format is described by the lock JSON schema.

If Oyzu rejects a lock written by an older development build, run oyzu pin --refresh, then oyzu install. Existing installed files are kept.

oyzu pin --dry-run previews what would be locked, and oyzu pin writes it without installing. See requirement discovery.

Checking a lock file​

oyzu tools inspect-lock [PATH] checks that a lock file is well formed. It doesn't resolve, download, install or run anything, and it doesn't check that the tools are installed.

oyzu -C /path/to/project tools inspect-lock
oyzu tools inspect-lock path/to/oyzu.lock
  • PATH defaults to oyzu.lock in -C, then --root, then the current directory. An absolute path also works.
  • Output is readable text by default; --json returns the structured result.
  • Exit 0 on success, 2 on a validation or read error.
  • The file must be a regular UTF-8 TOML file of at most 8 MiB. Symlinks to a regular file are followed; FIFOs are refused.
  • It doesn't read project configuration or mise files, make network requests or change the lock. The whole file is checked, whatever profile or toolset is selected.

What is checked​

The command rejects:

  • unknown or duplicate fields, an unsupported format and malformed digests;
  • record keys that don't match their content, and verification subjects that differ from artifact digests;
  • duplicate sets, missing dependencies, cycles, unreachable tools, conflicting IDs in one set and missing platform entries;
  • source or artifact identifiers containing colons, path separators or control characters.

Limits: 1,024 environments, 4,096 tools, 64 platform entries per tool, 16,384 dependency edges, depth 64 and 256 roots per environment.

What it reports​

  • The format, environment and tool counts, and the sorted list of platforms.
  • A selection digest for each environment and platform. It covers every tool in the set, including dependencies, their file digests, verification and layout. Comments and ordering don't affect it; changing any dependency's file changes it.
  • installation_keys, mapping each tool to the identity of its installation. Changing a dependency changes its key and the keys of tools that depend on it. Adding a platform leaves the existing keys unchanged. These keys name intended content; they don't mean the installation exists.

The result says validation: "structure-and-identity-only". A pass means the file is consistent. It doesn't prove the publisher is authentic, that policy allows the tools, or that installed files are intact. A carefully crafted malicious lock can pass. Request digests are checked for shape, not recomputed against your configuration.

If the check fails, fix the records or restore a known good lock (or regenerate it with oyzu pin). Don't edit digests to make it pass. The command never repairs files.

Execution-platform resolutions​

Node and Go projects can run oyzu pin --dry-run, oyzu pin, then oyzu install --frozen:

  • Set node or go in [tools]. For Go, the minimum in go.mod or go.work (the newer of the go and toolchain lines) is a request by itself when [tools] go is unset; see Go version selection.
  • Node also checks engines.node in package.json. Neither tool is run to find this out.
  • If a configured version is missing, the preview is incomplete, explains why and exits 2. It never writes an empty lock.
  • Pin records the selected version, the archive URL and its SHA-256. It doesn't download the archive.
  • Node and Go entries keep your request (including prefixes and ranges) next to the exact version. Validation checks that the version satisfies the request, using the provider's rules (including Node aliases). --frozen doesn't re-read the publisher's catalog.
  • Rust and Cargo helper requests must be exact versions.

Which platforms are locked​

By default, the lock covers the platforms declared by every build in the project, plus the host, whatever command you run.

  • Platforms a provider doesn't support are listed in platformsNotLocked (human output: Inferred platforms not locked).
  • The host and any platform you list explicitly must be covered. Oyzu never borrows another platform's artifact.
  • Offline pin needs existing matching entries; it may leave other inferred platforms unlocked.
  • oyzu install installs the host entry and keeps the rest of the lock. A repeat offline install reuses the verified copy in your store.

To lock platforms explicitly, for example for another machine that runs your builds, set tools.lockPlatforms:

[tools]
rust = "1.95.0"
lockPlatforms = ["windows/amd64/gnullvm", "linux/arm64/gnu"]
  • The list must not be empty and must use exact supported platforms. The host is always included.
  • tools.platforms is no longer accepted. Remove it, or rename it to lockPlatforms. See mapping and migration.

Rust platforms​

oyzu pin locks Rust for linux/amd64/gnu, linux/arm64/gnu, darwin/amd64/native, darwin/arm64/native, windows/amd64/msvc, windows/arm64/msvc, windows/amd64/gnullvm and windows/arm64/gnullvm.

  • Windows GNU/LLVM entries also lock the rust-mingw component. Windows amd64 installs use MSVC.
  • Pin resolves every requested platform and its components before writing. Missing publisher data fails without writing a partial lock.
  • Offline pin needs existing entries for every requested platform. Rust versions must be exact stable releases.
  • The Cargo helpers are cargo-nextest 0.9.146 and cargo-llvm-cov 0.9.1, with URLs and SHA-256 digests from their GitHub releases. Windows helpers are MSVC binaries, even next to a GNU/LLVM compiler. macOS cargo-nextest is a universal binary.

Locking a platform doesn't mean Oyzu can install or run tools on it. Windows GNU/LLVM component installation and ARM64 execution aren't supported yet.
