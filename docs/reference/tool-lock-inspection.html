Tool identity inspection

CLI reference

Published from the canonical docs/reference/tool-lock-inspection.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Single pre-release contract​

All Oyzu tool locks now use format = 1. One document can contain resolved_environment/resolution records for planned tools and environment/tool records for verified installation graphs, plus optional requirements discovery evidence. These record types do not imply each other's verification status. One parser validates both; unsupported format numbers fail. Pin updates resolution records without discarding installed records, and install preserves resolutions. Older development formats have no compatibility reader. Regenerate development locks deliberately; existing cache payloads are not deleted.

Every resolved_environment and environment entry may carry toolset = "NAME": the set was locked for that toolset ([toolsets.NAME.tools]). The [tools] sets carry no toolset. The label scopes which sets a command changes (a toolset's commands change only its own sets); it is not part of request_digest, so the same requests have the same identity in every scope. A name follows configuration identifier syntax. Entries have no scope or profile field; the lock JSON schema no longer lists them. The request/tool/selection identity domains are also version 1; earlier identity keys are not silently admitted as equivalent.

Provider identity is owned by src/tools/identity.rs: the digest domain is oyzu.tool-provider.v1 and its descriptor is {"provider":"oyzu","contract":1}. It identifies the maintained provider contract, not an upstream revision or the binary's dependency graph. Source provenance remains in the upstream notices.

The maintainer explicitly retired compatibility with unreleased development identities. Old locks are rejected: run oyzu pin --refresh, then oyzu install. These operations retain old payloads rather than relabeling receipts. Normal payload, recipe and selection verification still applies. The schema stays at version 1; no migration branch or automatic acceptance of old identities exists.

oyzu pin --dry-run previews discovered requirements and resolved tool recipes; oyzu pin publishes complete resolutions without installing tools. See requirement discovery. Optional [[requirements]] records remain discovery evidence only: their resolved and installed fields must both be false, and their digest binds the inventory. Inspection reports installation and resolution record counts separately.

oyzu tools inspect-lock [PATH] validates an experimental version-1 tool lock without resolving, downloading, installing or running a tool. PATH defaults to oyzu.lock relative to -C, then --root, then the current directory. An explicit absolute file path is also supported. Output defaults to readable text; --json returns the structured result. Success exits 0 and validation/read errors exit 2. See the CLI output contract for JSON errors.

oyzu -C /path/to/project tools inspect-lock
oyzu tools inspect-lock tests/fixtures/tool-lock/valid.toml

The second example uses synthetic identity data, not an installable artifact. The command requires a regular UTF-8 TOML file and reads at most 8 MiB plus one byte to detect overflow. All tool-record readers verify the opened object is a regular file; Unix uses nonblocking open so a FIFO is rejected without waiting for a writer. Explicit symlinks to regular metadata files remain supported; this is not the installation store's no-follow containment boundary. It does not read project configuration or mise files, use ambient mise settings, make network requests, or modify the lock. Profiles and other configuration options do not filter inspection: the whole document is validated. Scope paths are checked lexically; filesystem containment and current configuration compatibility are not assessed by this command.

Validation rejects unknown/duplicate fields, unsupported formats, malformed digests, record-key mismatches, verification subjects that differ from artifact digests, duplicate sets (installation sets by request digest; resolution sets by request digest, roots and toolset), missing dependencies, cycles, excessive depth, unreachable tools, conflicting canonical IDs in a closure and missing platform distributions. Different scopes may lock different versions. Limits are 1,024 environments, 4,096 tools, 64 distributions per tool, 16,384 edges, depth 64 and 256 roots per environment. Toolset names use configuration identifier syntax. Logical source/artifact identifiers currently reject colon and path separators in addition to controls; they cannot carry URLs or filesystem paths.

Output includes format, environment/tool counts, the sorted platform inventory and selection digests for each environment's common supported platforms. Each digest binds the exact transitive platform closure, including artifact bytes, verification metadata, layout and backend identities. Comments and set-like array ordering do not affect it. Changing a dependency artifact changes the selection digest even when its tool ID and version are unchanged.

Each selection also contains installation_keys, mapping tool keys to recursive installation identities. A dependency change invalidates its own installation and dependent installations. Adding an unselected platform leaves the existing platform's installation identities unchanged. These keys name intended content; they do not establish that an installation exists or is authorized.

validation: "structure-and-identity-only" is deliberate: success does not prove publisher authenticity, legal clearance, policy authorization, installed content integrity or backend admission. Request digests are checked for shape, not recomputed against current configuration/native constraints. Backend option allowlists, version canonicalization and package-closure admission require the future pinned backend adapter. A self-consistent malicious lock can pass this inspection; it is not an execution capability.

The current CLI does not yet install, activate, switch or execute tools through mise. Those operations remain work under OEP-0003. No automatic migration of experimental format 1 is provided. For invalid input, repair the source records or restore a known valid lock; do not change digests merely to suppress validation failures. Inspection does not repair files.

Unit tests cover graph failures, bounds and semantic identity. The CLI test checks an independently computed golden digest, ignores malformed adjacent mise and Oyzu configuration, preserves file bytes and rejects tampering. Local results and platform limits are recorded in implementation status.

Execution-platform resolutions​

Node and Go projects can also use oyzu pin --dry-run, oyzu pin, then oyzu install --frozen. Set the runtime request in [tools] (node or go; a Go module's go.mod minimum is a request by itself); the selected builder reads native runtime constraints without executing the tool. Node checks package.json's engines.node; Go reads the Go minimum (the newer of the go and toolchain lines) in go.mod/go.work and requests it when [tools] go is unset (Go version selection). A missing configured version produces an incomplete preview with an actionable diagnostic and exit 2; it never publishes an empty successful pin. Version selection uses the extracted upstream catalog semantics. Pin records the selected version, publisher archive SHA-256 and URL; it does not download or install the runtime archive. Portable Node/Go records retain the configured request (including numeric prefixes and ranges) separately from the exact resolved version. Lock validation checks that version against the request using the provider's selection rules, including Node aliases; an incompatible resolution is rejected. Frozen reads do not refresh the publisher catalog. Rust and Cargo helper requests remain exact versions.

The current Node/Go archive adapter admits linux/amd64/gnu, darwin/arm64/native and windows/amd64/msvc. These three are the defaults for those tools; tools.platforms restricts coverage to admitted tuples. Unsupported tuples fail rather than borrowing another platform's artifact. Metadata coverage does not qualify execution on an unavailable host. Installation consumes the pinned host recipe and preserves the portable lock; repeat offline installation reuses its verified user-store payload. Offline pin requires matching recipes. Existing installed-record locks remain readable and are not silently relabeled.

The first Node public pin/install/exec/frozen-offline flow passed on Windows. The expanded cross-host runner is tooling/test-tool-management.py --pin; see the extraction audit for completed checks and outstanding qualification.

oyzu pin now resolves Rust metadata for Linux GNU, macOS and Windows on AMD64 and ARM64. Windows compiler recipes distinguish MSVC and GNU/LLVM; GNU/LLVM recipes also pin the rust-mingw component. Windows amd64 installation selects MSVC; the GNU/LLVM recipes remain pinned metadata. Defaults cover eight tuples: linux/{amd64,arm64}/gnu, darwin/{amd64,arm64}/native, windows/{amd64,arm64}/msvc and windows/{amd64,arm64}/gnullvm (brace notation here is explanatory, not accepted configuration syntax).

Restrict coverage through the configuration cascade, independently of build targets:

[tools]
rust = "1.95.0"
platforms = ["windows/amd64/gnullvm", "linux/arm64/gnu"]

The list must be nonempty and use supported exact tuples. Pin resolves every requested compiler platform and its components before publishing. Missing publisher metadata fails without publishing a partial lock. Offline pin requires existing matching compiler records for all requested platforms. No tool payloads are downloaded or installed by pin. Exact stable Rust versions remain required.

The existing supported helper versions are nextest 0.9.146 and cargo-llvm-cov 0.9.1. Their platform URLs and SHA-256 digests come from their published GitHub release asset metadata. Windows helper executables are published as MSVC binaries; they retain that identity even alongside a GNU/LLVM compiler. This is explicit metadata selection, not permission to install an MSVC compiler or SDK. macOS nextest uses its published universal binary. Compiler recipes and output-target standard libraries remain separate facts.

This extends lock metadata coverage, not native installation qualification. Windows GNU/LLVM component installation and real ARM64 execution remain unproved; existing install paths are not automatically made portable by these records. Backend digests retain current compatibility checks and are not executable hashes. See the portable-lock design.
