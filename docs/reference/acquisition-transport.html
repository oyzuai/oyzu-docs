Scoped dependency acquisition transport

CLI reference

Published from the canonical docs/reference/acquisition-transport.md file. Features marked experimental remain experimental; check support limitations before relying on them.

When Oyzu downloads tools, helper archives and container-build dependencies, the requests go through one HTTP client with fixed rules: which sources may be contacted, how credentials are used, how retries work and how large downloads may be. This page explains those rules, how to use a corporate proxy, and what the download errors mean.

Native package managers still read their own lockfiles, resolve dependencies and check package integrity. Oyzu only fetches bytes from allowed sources; it doesn't resolve dependencies.

Note: The download client is experimental.

Sources and credentials​

Each builder supplies the sources it may use. A source is an HTTPS origin and path prefix, with an optional authorization header held on your machine.

  • Every request and every redirect must match an allowed source, or it fails with SOURCE_DENIED.
  • A redirect uses the destination source's credentials. A token is never forwarded to another source.
  • Some sources only accept redirects. For example, Go's proxy.golang.org sends large module zips to https://storage.googleapis.com/proxy-golang-org-prod/; a request that starts there is refused. go.sum still pins every zip.
  • Plain HTTP is only allowed for local loopback endpoints. Base URLs with credentials, a query or a fragment, and encoded path escapes, are refused.

Downloads happen while the build prepares, before the plan is frozen. Build actions then run with networking off. A missing input or integrity failure during an offline build never falls back to downloading. oyzu run tasks such as oyzu run install run on your host with normal network access.

Proxy and trust settings​

The download client reads the standard environment variables of the process that runs oyzu. They apply to tool metadata and archives, helper archives and container-build dependency downloads.

VariableEffect
HTTPS_PROXY / https_proxyProxy for HTTPS sources (CONNECT tunnel).
HTTP_PROXY / http_proxyProxy for HTTP sources.
ALL_PROXY / all_proxyUsed when the scheme-specific variable isn't set.
NO_PROXY / no_proxyHosts, domains and CIDR ranges that skip the proxy.
SSL_CERT_FILEA PEM bundle of extra trusted certificates, for corporate TLS inspection. The built-in public roots stay trusted.
  • Loopback addresses (localhost, 127.0.0.0/8, ::1) always skip the proxy, so local endpoints and their credentials never go through it.
  • Proxy URLs may include credentials. They are never printed.
  • An invalid proxy URL fails with PROXY_INVALID. An unreadable or empty SSL_CERT_FILE fails with TRUST_BUNDLE_UNREADABLE or TRUST_BUNDLE_INVALID. Oyzu never silently connects directly instead.
  • A proxy doesn't widen the allowed sources; it's only a route.
  • A TLS-inspecting proxy can see request headers, including source credentials. Only use a proxy you trust with them.
  • Extra trusted certificates don't replace signature checks: a tool's publisher signature is still verified against its own trust root.
  • Not supported: proxy authentication other than credentials in the URL, PAC files, system proxy settings and per-source proxies.

Proxy support is tested on Linux and Windows. macOS isn't supported yet.

Retries​

RuleValue
Retries per download2, after the first attempt
Network deadline per download45 seconds, shared across redirects and retries
Redirects per download5
Requests per session4096, counting retries and redirects
Backoff200 ms, then 400 ms, or longer if the server sends Retry-After
  • Statuses 408, 429, 502, 503 and 504, and connection or transfer failures, are retried. A partial download is discarded before retrying.
  • Statuses such as 401, 403, 404 and 500 fail at once. So do denied sources, invalid redirects and size limits.
  • If Retry-After asks for a wait longer than the remaining deadline, Oyzu returns the failure instead of retrying early.
  • These limits can't be configured.
  • A package manager may make its own further requests; its own retry behavior applies to those.

Delivery edges still filling. An organization's delivery edge that is still fetching an artifact from its publisher answers 503 with Oyzu-Fill: pending and Retry-After. Oyzu waits the Retry-After seconds (1 to 30, default 5) and asks again with a fresh deadline, for up to 15 minutes, without counting it as a retry. Without that header, a 503 is an ordinary retryable status.

Size limits​

  • Each successful response may be up to 256 MiB, and one session may read up to 1 GiB in total, including failed attempts.
  • Pinned tool archives (Rust, Node, Go, Python, JDK and Maven) download in sequential 8 MiB ranges, up to 512 MiB in total. Each range has its own 45-second deadline, so a large archive can take longer overall while a stalled request still times out. Ranges must line up exactly; an inconsistent server response fails with SOURCE_UNAVAILABLE, and a total over the cap with BYTE_LIMIT. The archive's SHA-256 is checked before use.
  • Up to eight downloads run at once, sharing the session limits.
  • Error response bodies from servers are discarded. You get a fixed message with the HTTP status.

Download errors​

Errors Oyzu generates include a code and a fixed message, without the URL, query, token or server error text:

StatusCodeMeaning and next step
400REQUEST_INVALIDA malformed request from a builder. Report it as a bug.
403SOURCE_DENIEDNo allowed source matches the request or redirect. Check the source configuration.
413BYTE_LIMITA size limit was exceeded. Check the dependency's size.
429REQUEST_LIMITThe session ran out of requests. Check how many dependencies are being resolved.
502SOURCE_UNAVAILABLEThe download failed after retries. Check the source and your connection, then rerun.
502REDIRECT_INVALID, REDIRECT_LIMITAn invalid or too long redirect chain. Fix the source endpoint.
504SOURCE_TIMEOUTThe network deadline expired. Check the source and your connection, then rerun.

For BYTE_LIMIT, the error also reports which limit was hit (response, session or artifact), the bytes observed and the limit. The pnpm adapter includes these in its failure message.

When a server itself returns an error, its real status is kept with a redacted body, and the package manager shows it its own way. Maven runs with -e so nested resolution causes appear in failed builds.

A failed preparation produces no dependency snapshot or build plan. The next build prepares fresh inputs.

Native npm cache failure diagnostics​

Container npm builds fill npm's cache with npm cache add, 16 archives or 16 MiB at a time. When that fails, the message names the batch, archive count and size, the exit status and signal, and any recognized OS error code, errno and system call, for example:

npm cache seed batch 1 (16 archives; 4066624 bytes): npm cache add failed (244): status=244; signal=none

Oyzu may read the end of npm's debug log for these codes. Raw log text, arguments, configuration and URLs aren't included, and the log isn't kept in the bundle. An exit status like 244 alone doesn't mean the worker ran out of memory; use the reported cause to decide.

Artifact set routes​

Artifact set installs use the same client, with one source per host route, and two differences:

  • A source with redirects = "server" treats any 3xx response as ROUTE_REDIRECT_UNEXPECTED and doesn't follow it.
  • A redirect to a host that no route allows fails with ROUTE_REDIRECT_UNROUTABLE. A redirect to a host with its own rule is fetched from that rule's destination.

With no tools route configured, redirects may reach any HTTPS host. Redirect targets and their query strings are never stored or reported.

Pinned Rust artifact ranges​

Rust helper archives (nextest and cargo-llvm-cov) download through this client. Public downloads use GitHub and its release-asset redirect host. A configured tool connector replaces that public source, with no fallback to the public one. The recipe is checked against its metadata before download, and the archive digest before extraction. See helper installation.

Limits​

  • Downloads in progress can't be interrupted immediately when a session ends.
  • Private registries other than those builders support, and automatic credential refresh, aren't supported.
  • A successful retry doesn't authenticate a dependency or make it eligible for release.
