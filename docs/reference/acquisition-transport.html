Scoped dependency acquisition transport

CLI reference

Published from the canonical docs/reference/acquisition-transport.md file. Features marked experimental remain experimental; check support limitations before relying on them.

The experimental dependency broker provides the approved HTTP fetch boundary used by captured builder preparation. Native managers retain lockfile interpretation, dependency resolution and package integrity verification. The broker fetches bytes from admitted routes; it does not run a resolver or install tools. This reference describes the current engine transport, not the planned corporate agent or a complete managed registry service.

Routing and credential boundary​

Builder preparation supplies explicit source routes. A route binds an identifier, HTTPS origin/path prefix and optional host-held authorization header. HTTP is allowed only for loopback test/local endpoints. Credential-bearing base URLs, query/fragment-bearing bases and encoded path escapes are rejected. Every request and redirect destination must match an admitted route. A redirect uses the destination route's credentials; the original token never follows it implicitly. A route can be marked redirect-only: it admits a hop that another route redirected to, but a request that starts there is SOURCE_DENIED. The Go builder's only such route is https://storage.googleapis.com/proxy-golang-org-prod/, where proxy.golang.org sends large module zips (such as google.golang.org/api); go.sum still pins every zip. Upstream fetches honor the standard proxy environment (see Proxy and trust settings); route admission and credential rules apply identically with or without a proxy.

Offline preparation containers use a private file channel to request downloads; they receive status, content type, source identity and body bytes, without upstream authorization or response headers such as cookies. Native Maven and Gradle adapters translate their loopback repository requests into this channel. Admitted standalone sources are currently selected by adapters; arbitrary private registries, corporate connector discovery and general managed credential refresh remain separate unfinished integrations.

oyzu build performs acquisition before freezing the execution plan. Later build actions use prepared inputs and denied networking. Retries described here occur only during approved acquisition; a missing input or integrity failure during offline execution never triggers a download fallback. Development commands such as oyzu run install retain their documented host/native execution behavior and are not made isolated by this broker.

Proxy and trust settings​

The broker's upstream HTTP client (tool metadata and archives, helper archives and captured-build dependency fetches) reads the standard environment of the process that runs oyzu:

VariableEffect
HTTPS_PROXY / https_proxyProxy for HTTPS routes (CONNECT tunnel)
HTTP_PROXY / http_proxyProxy for HTTP routes
ALL_PROXY / all_proxyFallback when the scheme-specific variable is unset
NO_PROXY / no_proxyHosts, domains and CIDR ranges that bypass the proxy
SSL_CERT_FILEPEM bundle of additional trust anchors for corporate TLS inspection; the built-in public roots stay trusted

Loopback destinations (localhost, 127.0.0.0/8, ::1) always bypass the proxy, so local endpoints and their host-held authorization never go through it. Local agent, native-session and npm-session endpoints are separate clients and remain proxy-free. Proxy URLs may carry credentials and are never printed. A set but invalid proxy URL or an unreadable/empty SSL_CERT_FILE fails with PROXY_INVALID, TRUST_BUNDLE_UNREADABLE or TRUST_BUNDLE_INVALID; there is no silent direct fallback. Admitted routes still decide which origins may be contacted; a proxy adds a path, not authority. Through a TLS-inspecting proxy the proxy can see request headers, including route authorization, so configure only a proxy you trust with that route's credential. Proxy authentication beyond credentials in the proxy URL, PAC files, system proxy stores and per-route proxies are not supported.

Verification: unit tests cover variable parsing, invalid values and secret redaction. On Linux, oyzu install of Node 22.15.0 through an authenticated-egress HTTPS proxy succeeded with this support and failed with SOURCE_UNAVAILABLE without it, with HTTP 403 when HTTPS_PROXY was removed, and with TRUST_BUNDLE_UNREADABLE for a bad SSL_CERT_FILE. The older mitmdump component fixture remains available in the corporate CA harness; it was not rerun for the complete plugin proof.

The native Linux and Windows plugin flows passed through a bounded loopback TLS-inspecting CONNECT fixture addressed as a reserved non-loopback host. Missing and unrelated additional CAs failed TLS before archive delivery or installation; correct CA trust permitted genuine signed official Go plugin acquisition, a full application build, expected executable output and passing native JUnit. The committed lock stayed unchanged. TLS inspection trust did not replace the official GitHub signer or production Sigstore root. See the qualification record for source/input attribution and retained setup failures.

This fixture delivers unchanged accepted archive bytes locally, without live upstream forwarding. It qualifies that HTTPS client path, not enterprise proxy products, OCI registry behavior, macOS, remote/container execution or real HTTP_PROXY/ALL_PROXY routes. The separate OCI client shares transport configuration but requires its own whole-flow qualification. Reserved-host controls rule out successful direct fallback, not every attempted connection.

Retry behavior and limits​

One logical fetch has at most two retries in addition to its initial attempt. The retry count and a 45-second network deadline are shared across redirect destinations; redirecting does not renew either budget. The existing maximum of five HTTP redirect-chain requests remains bounded separately. Each actual request also consumes the session's 4096-request allowance, including retries and redirects. The HTTP library's automatic protocol retries are disabled so they cannot silently extend this budget.

These are per-fetch broker bounds. A native manager can submit another logical request; its own retry behavior remains native and is constrained by the session and enclosing acquisition limits. This is not a per-package attempt counter or a persistent upstream cooldown shared across requests.

Retryable upstream statuses are 408, 429, 502, 503 and 504. Connection/request/body transport failures can also retry; partial transfers are discarded before a fresh request. A complete response still goes through its adapter's integrity checks. Statuses such as 401, 403, 404 and 500 are returned immediately. Denied routes, invalid redirects and resource-limit failures are terminal in the broker. Package checksum failures remain terminal at their adapter boundary.

Backoff is 200 ms, then 400 ms. A supplied Retry-After delay or HTTP date sets a longer minimum wait, using the standard HTTP semantics. Invalid headers or waits that cannot fit the remaining deadline return the current upstream failure instead of retrying early. A timeout may exhaust the whole deadline before any retry is possible. There is no new project setting for these bounds.

A delivery edge that is still filling an artifact from its publisher answers 503 with Oyzu-Fill: pending and Retry-After (problem code FILL_PENDING). That answer is not an ordinary failure: the client waits the Retry-After seconds (1 to 30, default 5), asks again with a fresh 45-second deadline and does not count it as one of the two retries, for up to 15 minutes per logical fetch. A large first download through an organization's edge therefore waits for the edge to finish verifying the artifact instead of failing. Without the header a 503 is an ordinary retryable status.

Requests send Accept: text/html unless the source serves a JSON API, in which case the source declares application/json (the Adoptium JDK catalog rejects the default with 406). Successful-response bodies are limited to 256 MiB each and 1 GiB read per session. Bytes from partial/failed attempts count toward the session total. Upstream error bodies are discarded without reading or relaying them; clients receive a fixed message containing the HTTP status. These are broker payload bounds, not a claim about total TCP traffic or native resolver memory use. Native acquisition has additional enclosing execution limits.

Failure interpretation and recovery​

The private channel now preserves the difference between denied access and unavailable transport. Broker-generated failures include a sanitized errorCode and a fixed body, with no requested URL, query, token or upstream error text:

HTTP statusBroker codeMeaning and next step
400REQUEST_INVALIDMalformed channel input; correct the adapter/request contract
403SOURCE_DENIEDNo approved route permits the request or redirect; fix the declared source integration
413BYTE_LIMITPayload/session bounds exceeded; inspect dependency size and acquisition scope
429REQUEST_LIMITSession request allowance exhausted; inspect resolution scope rather than retrying that exhausted session
502SOURCE_UNAVAILABLETransport failed after eligible retries; check availability/connectivity and rerun preparation
502REDIRECT_INVALID, REDIRECT_LIMITInvalid or excessive redirect chain; correct the source endpoint
504SOURCE_TIMEOUTNetwork deadline expired; investigate the source/connectivity before rerunning

Upstream HTTP failures retain their actual status and a redacted body; they do not acquire a fabricated broker code. Native managers determine how they display those statuses. Maven now requests native error stack traces (-e) to retain nested resolution causes in failed-build diagnostics; debug logging (-X) is not enabled. A failed preparation produces no successful dependency snapshot or executable build plan. A later explicit build prepares fresh inputs and evidence.

Previously, the channel reported every internal failure as 403. Consumers must handle non-success statuses generally rather than assuming every unsuccessful request is a permission denial. The optional errorCode field is additive; existing native clients still receive the original status/body fields. This does not change successful dependency records or artifact identities.

For broker-generated BYTE_LIMIT, the private response additionally provides limitScope (response, session, or artifact), observedBytes, and limitBytes. These numeric facts identify the exhausted existing bound without exposing the request URL, response body, or headers. The pnpm archive adapter includes them in its sanitized failed-preparation diagnostic; it also reports the count and stored bytes of publisher metadata captured before archive acquisition. Neither field changes the configured limits or permits a failed preparation to produce a snapshot.

The channel serves up to eight requests at once. One thread claims request files in arrival order and a pool of eight fetchers answers them; the pool shares one session's 4096-request and 1 GiB allowances, so concurrency does not raise either bound. The bundled clients use it: the npm, pnpm and Yarn adapters keep up to eight registry fetches in flight and record packages in lock order whichever fetch finishes first, npm seeds its private cache with one native npm cache add per 16 tarballs or 16 MiB of archives, whichever comes first, instead of one per package (the command unpacks every archive it is given at once into the worker's 512 MiB /tmp, and 200 archives of a large project ran it out of space; its memory also grows with the number of archives, and 64 or more small archives exceeded a 2 GiB worker), Go asks go mod download for the whole module set in one call, the Python adapter splits a locked, hashed export across four pip download --no-deps processes before the resolving download, and Cargo capture on the host fetches index entries and crate archives eight at a time with the same routes and shared allowances, then checks them in lock order. A request still has its 55-second client wait, so more than eight slow upstream requests can queue behind each other, and this does not eliminate every acquisition outage. Active blocking requests are not immediately interruptible on session shutdown. General cancellation, queue scheduling and managed retry-policy delivery remain work. A successful retry does not authenticate a dependency or establish release eligibility.

Native npm cache failure diagnostics​

When native npm cache add fails, the diagnostic names the one-based seed batch, archive count and compressed bytes. It keeps the native exit status and signal, and recognized spawn error codes, numeric errno and syscall names when available. For example, a silent exit can report npm cache seed batch 1 (16 archives; 4066624 bytes): npm cache add failed (244): status=244; signal=none.

The npm adapter can also read the final 16 KiB of a newly created private npm debug log for recognized OS error codes and errno numbers, and fixed syscall names. Raw debug text, arguments, configuration values and URLs are excluded from these additional fields. Earlier commands' logs are ignored, and missing or unreadable logs do not replace the original failure. Existing native stdout/stderr behavior is preserved. The temporary cache and its logs are removed through the existing cleanup path; the adapter does not retain raw debug logs in the build bundle.

A status such as 244 alone does not establish an out-of-memory cause. Use the reported native cause and worker evidence to decide whether the problem is resource pressure, filesystem access or another native failure. These diagnostics do not retry npm, change the 16-archive/16-MiB seed limits, or alter offline and lifecycle restrictions. Run oyzu exec -- node --test tooling/test-npm-native-diagnostics.mjs for the failure/privacy and cache-seeding regressions; their fixture transport requires no registry access.

Artifact set routes​

Resolved artifact set installs reuse this transport with one source per per-host route (artifact sets). Two additions apply only to that caller: a source marked redirects = "server" treats any 3xx as ROUTE_REDIRECT_UNEXPECTED (not followed), and a client-followed redirect hop that no route permits fails ROUTE_REDIRECT_UNROUTABLE instead of SOURCE_DENIED; a hop to a host with its own rule is fetched from that rule's destination. With no tools route configured, hops may reach any https host. Other callers keep SOURCE_DENIED and the redirect rules above. Redirect targets and their query strings are never stored or reported.

Pinned Rust artifact ranges​

Native tool preparation also sends the admitted nextest/LLVM-coverage release archives through this broker. Public helper acquisition admits GitHub and its release-assets redirect origin; configured tool connectors replace that public route and do not receive an automatic public fallback. The tool adapter validates the pinned recipe against its admitted metadata before download, and the store verifies the archive digest before extraction. This is archive installation, not arbitrary Cargo package resolution or source compilation. See native helper installation.

Pinned distribution inputs (Rust, and the Node, Go, Python, JDK and Maven archives) opt into sequential 8 MiB HTTP range requests. Each range is one bounded logical fetch under the retry, 45-second deadline, redirect and source-authorization rules above. Total artifact size is capped at 512 MiB, because a JDK archive is about 200 MB, with every transferred byte charged to the shared 1 GiB session budget. Unpinned responses keep the 256 MiB limit. Large progressing artifacts can therefore take longer than 45 seconds overall without permitting an individual stalled request to wait indefinitely.

Range responses must match the requested offsets and body lengths, be contiguous, and agree on the total size. A server may ignore the first range and return a complete response under the ordinary deadline. It may not return a full response after partial segments. Malformed or inconsistent ranges fail as SOURCE_UNAVAILABLE; oversize totals fail as BYTE_LIMIT. The Rust adapter checks the final locked SHA-256 before making any input available to rustup. This is neither persistent partial-download caching nor a change to native manager requests. Other fetch callers keep the ordinary single-response contract.

Verification​

cargo test --locked --test integration broker:: uses real local HTTP servers to verify retryable statuses, partial-body replacement, retry exhaustion, terminal statuses, authorization on retries/redirects, a retry budget shared across hosts, error-body redaction and channel failure classification. Owner-local tests verify delay/date/deadline decisions and terminal byte/request limits. These checks run in the Windows, macOS and Linux CLI jobs before captured scenarios.

The httpdate dependency owns HTTP-date parsing instead of a handwritten parser. Version 1.0.3 is MIT OR Apache-2.0, declares Rust 1.56 support and uses portable standard-library time types; its lock entry is generated by Cargo. It does not change route authorization or clocks used for monotonic request deadlines.

See implementation status for completed checks. Controlled HTTP failures prove transport behavior; they do not establish the cause or resolution of an unrelated Maven Central incident. Actual Java/native scenario success remains separate CI evidence.
