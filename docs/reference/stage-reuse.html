Stage reuse

CLI reference

Published from the canonical docs/reference/stage-reuse.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Stage reuse restores an earlier build action's outputs when its admitted inputs still match. Use this page to check which builders can reuse stages, which commands run again, and why an unchanged build can refuse reuse.

crun is the container runtime Oyzu uses to run isolated Linux actions without a Docker daemon.

Status: experimental. Complete-read lifecycle reuse is available for Maven, Gradle, Ant, npm, Helm, eligible go/app stages and conventional .NET compile/test/pack on Linux crun. Compatible Java plugins reuse eligible Maven modules and Gradle projects independently. Generated pip python/app builds reuse on Linux crun with a current plugin package; other Python lanes do not yet. Windows Rust compilation can still report incomplete reads on unchanged builds. Native Windows stages with incomplete reads run again.

See why a stage ran​

Illustrative commands, run from a project with a build target named app:

oyzu build app --explain
oyzu cache explain app
oyzu cache explain app:build

The build explanation reports reuse decisions for the current run. Cache explanation reads recorded key history for a target or action. Replace app:build with the action named by your builder. A reused action is labelled as reused; its tests and reports were not executed now.

When can a stage reuse a result?​

A matching key is necessary, but reuse also requires admitted reads, bounded outputs and a valid stored result. The key binds source inputs, command and environment, admitted tools and dependencies, execution identity and producer outputs. Restored artifacts and required reports still pass the current checks.

On the native host, reads must be complete through admitted native observations or fixed command semantics. A predicted source list or a private source copy alone does not establish completeness. Missing dep-info, unresolved runtime reads or unbounded outputs can require execution even when source is unchanged.

Docker and crun share results keyed on the whole target: a stage that one isolated backend ran is reused by the other. Results keyed on enforced runtime reads exist only on crun, and a Docker result never satisfies one.

An incomplete native stage cannot fall back to a whole-source key or be skipped by whole-target restoration. Other independently admitted stages can still hit. Adding inputs covers known files; it does not prove that a script, plugin or test reads nothing else.

Authored tasks with cache = true and declared outputs follow the same rule: only complete reads of that action admit reuse. Supported native Node commands on Linux can use crun per action with frozen source, bounded producer outputs, the locked native tool and an identified runtime root. Captured isolated Node targets retain their own complete-read path. Unsupported commands and native Windows/macOS actions rerun with a named explanation. An inherited builder contract cannot admit an authored replacement. See authored tasks for prerequisites, source visibility, output bounds, diagnostics and the author's ambient output-independence obligation.

An admitted native authored action keeps its lookup when a companion lacks a stage contract. The companion executes each time and no whole-target group can skip it. Only separately bounded, frozen producer bytes are visible to the consumer; equal hook output can hit and changed consumed bytes miss. Required checks still run or reparse restored reports. --no-cache preserves the selected read view, including denied outside reads, while disabling lookup, storage and history.

On native Windows, Maven/Gradle lifecycles and arbitrary npm scripts run again because their runtime reads are incomplete. build --explain and cache explain app name the refusal: native reads are incomplete on this host. Windows has no merged complete-read backend for Vite or uv lifecycles. An unchanged source tree or a private source copy cannot make them reusable. The explanation points to the isolated Linux crun path for supported builders; run that command on a Linux host. It does not enable native Windows reuse. Clearing the cache does not fix missing read admission. --no-cache executes the same native commands without action-cache reads or writes; an external input change must affect both ordinary and uncached builds. See native Windows refusal.

The experimental Windows ETW complete-read pipeline remains disabled by default. Capture and decoding exist, but live ETW coverage is unproven without an elevated validation run. Each capture retains at most 262,144 events and 64 MiB of event metadata plus payload bytes (allocator overhead is additional). Exceeding either limit permanently marks the capture incomplete, refusing reuse and publication. Malformed Close events also refuse. Path canonicalization refuses case-sensitive ancestor directories and unavailable case-sensitivity attributes, so distinct absence probes cannot be merged by case folding. There is no user-facing switch to enable this path.

Stage reuse is separate from Cargo incremental state, individual compiler-result caching, tool downloads and prepared dependencies. A stage that executes again may still benefit from those caches. See action-cache controls for disabling reuse or selecting local and remote storage. No account is needed for local reuse.

Rust's Windows x64/MSVC compile stage can report incomplete reads even on an unchanged build. Expect execution in that case. Fixed-read rustfmt, retained Cargo state and eligible individual compiler results have separate admission. Linux compilation can reuse when its observations are complete. See Rust native host builds for the current limits, including the distinction between declared-version compilation and full-build inferred-version finalization.

Java reuse keeps Maven's verify or Gradle's coupled lifecycle together inside each module/project, with a compatible Java plugin. Native models supply module membership and dependency edges; no additional configuration is needed. For a → b → c (each module depends on the one before it), an unchanged rebuild reuses all modules, a c source edit reruns only c, and an a source edit invalidates the chain. Module keys include their sources, shared native build definitions, declared producers and admitted tool/dependency identities. Reports retain module ownership and reused evidence is labelled reused. Ant keeps its selected target set together. This does not cache every native task or test class separately. Maven dependency preparation still runs on warm lifecycle hits. Plain Java builds remain native. See Maven, Gradle and Ant.

Ant's coupled lifecycle changes captured planning from 0.3.x, which planned build, test and archive as separate actions. oyzu build --isolated now runs the selected tests even without --full, and a failing test blocks the JAR, matching Maven and Gradle in 0.4.0. To retain separate Ant stages, use oyzu build --full without --isolated on the native host, with the native prerequisites. Plain oyzu build keeps native fast-mode check selection. There is no switch to restore split planning on the captured path; native host stages retain their incomplete-read limits and run without container isolation.

Node's package-local workspace actions use native package-manager membership and dependency edges. An unchanged rebuild reuses every admitted member. Editing a leaf's source reruns its build/tests; editing a shared member's source also reruns its native dependents. Each member follows its own version output and required workspace producers. All member manifests key shared installation. For a metadata-only member package.json edit, npm and Yarn Classic can reuse an untouched leaf's build/tests when installation output stays identical; the edited member and its native dependents rerun. pnpm changes shared installation bookkeeping and reruns every member, even when package code stays identical. This accepted precision limit retains all readable installation bytes in keys. --explain names a stored result matches this key for npm/Yarn leaf hits and the changed app:prepare-dependencies output for pnpm reruns. Changed shared installation output invalidates all members for any manager. Named JUnit/LCOV reports retain reused producer labels. Shared root configuration keeps the whole workspace visible and refuses member reuse with node-member-shared-configuration. Non-crun executors refuse it with node-member-reuse-requires-crun. pnpm hooks/patches and active Yarn rc configuration refuse manifest-only install narrowing. A failed command that names a hidden path can report confined-read-outside-contract; optional probes that succeed are not diagnosed. This does not trace every read. Root aggregate scripts and opaque root dispatch keep their whole-workspace boundary. See Node workspace reuse.

Helm retains the plugin's chart read bounds for bounded stages. Suites without complete observations use the entire admitted source view. Helm and helm-unittest bind their current locked tool identities, so a selected release or archive change invalidates reuse. oyzu install adopts the helm-unittest requirement without deleting existing installations. See Helm isolated reuse.

Go's isolated go/app path can reuse stages with complete admitted reads. Build-phase generated test manifests and compiled tests are explicit outputs, consumed as identified inputs in test-stage read sets and keys. A changed manifest invalidates reuse; undeclared carried files are refused. Runtime tests include the whole admitted source view, so source edits can invalidate additional tests. See Go isolated stage reuse.

Go's native build/vet read observations remain separate: incomplete native reads still refuse stage and whole-target reuse on Linux, Windows and macOS. Windows and macOS have no complete Go runtime-read enforcement backend.

.NET's captured stage reads admit conventional compile/test/pack under Linux crun, including cross-root reuse when their retained bytes are location-free. Native host execution still refuses incomplete reads; other executors do not gain this complete boundary. With a compatible plugin, eligible multi-project solutions reuse compile, test and pack per project along literal reference edges. Unchanged projects reuse their results; a source edit reruns its project and reference dependents. Shared configuration changes invalidate all affected projects. Failed actions execute again on repeated failing builds and never become reusable successes. Shared or nested project folders, solutions containing applications and unknown customizations retain the solution-wide path. See .NET project reuse.

Module splitting retains the whole Maven reactor or Gradle lifecycle when the source inventory contains links, exceeds the selector limit, has an invalid module graph, or contains module-local control files outside src/ and the native build definitions. This conservative fallback lets configurations share files such as build-tools/checkstyle.xml or x/version.txt on every captured executor, including Docker. It does not grant native-host reuse or relax isolated read enforcement. Runtime reads of sibling sources remain outside a split module's admitted view.

What makes isolated reads complete?​

For Maven, Gradle, Ant, npm, Helm, eligible go/app stages and .NET, select the existing Linux crun path:

oyzu build app --isolated --no-docker --explain

This requires the builder's locked tools, prepared dependencies, admitted base execution image and an available Linux crun runtime. See the execution image for provisioning. No extra reuse setting is needed. Docker, other executors and native Windows/macOS execution do not inherit this complete-read guarantee.

The executor enforces the identified source, dependency, tool/runtime and producer-output view. Live /proc and /sys data and undeclared host files are hidden except the closed startup allowance below; network access is denied. Private output state and validated phase handoffs prevent an action from reading unrelated bundle output. A handled file absence is stable within this view. A failed unsupported read stores no reusable success. This is enforcement, rather than a syscall trace.

The closed non-keying device allowance is /dev/random, /dev/urandom, /dev/null and /dev/zero. The closed self-proc startup allowance also supplies read-only files for the requesting process and its actual executable readlink, without exposing other processes' entries. Facts record self-proc presence only, never contents. These ambient values do not enter keys. Entropy must not affect retained outputs; workloads that embed random or ambient values are outside this reuse contract. Completion records retain these allowance facts under oyzu.dev/ambient-reads; they describe permitted reads, not observed syscalls. CPU count remains a separate keyed boundary fact.

--no-cache executes under the same isolation and report checks. It does not make an unsupported workload admissible. Offline execution still requires previously acquired tools, images and dependencies; stage reuse does not supply missing prerequisites.

Do temporary-directory changes invalidate native reuse?​

Native actions receive private TEMP, TMP and TMPDIR paths allocated by Oyzu. Inherited, configured and builder-declared values for those three names are replaced before launch and excluded from native action keys. Changing only those overwritten values does not invalidate an otherwise reusable action. Environment policy still validates authored values and the final environment.

This exception applies only to those executor-owned temporary variables. Passed HOME, USERPROFILE, APPDATA and LOCALAPPDATA values remain keyed. A configuration file read as ordinary program data also remains an input: editing its bytes can invalidate the stage. Private scratch does not establish complete reads or add host isolation. See native environment inputs and temporary directories.

Which tool and lock changes invalidate reuse?​

Typed locked-tool external inputs bind runtimes outside the source tree to core-admitted identities from oyzu.lock, such as Java's JDK, Node's runtime, Helm and its helm-unittest plugin, or the .NET SDK. Core resolves these identities before lookup; a missing binding fails admission. A changed identity invalidates its consumers. Naming a tool does not establish complete reads or grant arbitrary external file access.

Prepared native builds project mandatory oyzu.lock source/version identity to the selected closure: selected tool recipes, plugin pins and transitive tool dependencies. Unrelated toolsets, unused plugin pins and valid unused current resolutions do not themselves invalidate that identity. Selected tool or builder changes still do. The whole lock remains structurally validated.

This projection does not discard raw bytes when the lock is an authored input or read explicitly as program data. Unknown reads, incomplete tool declarations or missing preparation retain conservative fallbacks. See native cache keys for the full rules.

When does npm installation survive a source edit?​

A bounded single-root npm or script-free workspace install keys its manifests/lockfile, npm configuration, tool identity and other admitted execution inputs. Only the generated OYZU_VERSION default is omitted when the admitted model establishes that installation cannot read it. Build and test stages always keep their version input, and explicit environment values remain keyed.

Workspace installation uses native membership and checks admitted registry archive manifests for lifecycle or implicit native-compilation uncertainty. It keys every member manifest and manager control. On Linux, relative workspace links can restore when they stay inside the workspace and point directly to ordinary files or directories. Escapes, indirect links and unsupported file types refuse restoration. Ordinary source edits leave this install key unchanged.

Root or dependency install scripts, implicit native compilation, incomplete lock facts, interpolated manager configuration and runtime-loading hooks keep the version input and refuse install reuse. Reviewed dependency file-read allowances do not prove unread environment values. Arbitrary lifecycle code conservatively reads the whole admitted source view. See Node stage reads for configuration and package-manager limits.

Why did unchanged inputs still run?​

oyzu build --explain reports refusals as well as key changes. A typical refusal is native stage has no complete observed reads; native stage reuse requires complete reads. A whole-target refusal names the stage that needs complete reads and bounded outputs. An incomplete-read refusal means the stage executes again; it is not a failed test or a corrupt cache entry.

Read the named stage and reason; use oyzu cache explain <target> or the action ID for recorded decisions. Clearing the cache cannot supply missing read admission. Keep executing the stage, or update to a compatible builder/CLI when support is available. For ordinary misses, compare the named source, tool, builder, command/environment or producer input. See explaining reuse and failure recovery.
