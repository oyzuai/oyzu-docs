Updating plugins

CLI reference

Published from the canonical docs/reference/plugin-updates.md file. Features marked experimental remain experimental; check support limitations before relying on them.

oyzu plugins update changes the plugin selections already recorded in oyzu.lock. Use it for a routine update within the major version you adopted, to move to a new major version on purpose, or to select one exact version or release (which is also how you undo an update). A ready-made GitHub workflow can run it on a schedule and open a pull request.

Note: Plugins are experimental.

oyzu plugins update                     # every locked selection, each within its adopted major
oyzu plugins update go/app              # only go/app
oyzu plugins update go/app@v2           # move go/app to major 2
oyzu plugins update go/app@1.0.0        # exactly version 1.0.0 of go/app's package
oyzu plugins update go/app@sha256:…     # exactly this release (the printed undo)
oyzu plugins update --dry-run           # check and show the change without writing oyzu.lock

For how a selection is first adopted, see plugin catalog. For the [[plugin]] lock record, see plugin packages. For read-only views, see inspecting plugins.

Options​

OptionMeaning
--dry-runCheck everything and show the change, but don't write oyzu.lock.
--offlineUse the cached catalog only.
--store DIRThe plugin store, as for oyzu build --store.
--jsonOne JSON object on standard output.

No account is needed. Publishing or caching a newer plugin release never changes your lock; builds keep using the locked release. Only this command (or deleting the entry) changes it.

Selectors​

You writePicks
go/app, or nothing (every locked reference)The newest eligible release in the adopted major. Never an older one while the locked release can still be used.
go/app@v2 or go/app@2The newest eligible release of major 2.
go/app@1.4.2Exactly version 1.4.2 of the package the catalog binds, newer or older.
go/app@sha256:…Exactly this release, which also fixes the package. The printed undo uses this form.

"Eligible" means the same as for a build: listed by the catalog, not withdrawn or revoked, supported, on the current plugin contract, with the right builder profile and a payload for this host. A plugins.packages binding for the reference supplies the package instead, as it does for a build, and must still match the selector.

  • Previews. Routine and @v<major> updates never pick a preview release (PLUGIN_PREVIEW_NOT_SELECTED). A release is a preview if its version is a prerelease or the catalog lists it as one. An exact @<version> or @sha256:… can pick a preview, but only with plugins.preview on. If it is off, the catalog refusal names the opt-in command and leaves the lock unchanged.
  • Preview to stable. A routine update can replace a locked preview with a compatible stable release in the same adopted major, including major 0. For example, 0.1.0-preview.2 to 0.1.0 is a patch change: the major and minor numbers are unchanged. The report shows both versions and the lock changes only when the update succeeds. This also works after previews are turned off or the preview is withdrawn; the stable replacement must remain eligible.
  • Package changes. A routine update never switches to a different package. If an organization catalog or a binding now points the reference at another package, you get PLUGIN_PACKAGE_CHANGE; adopt it with an explicit selector such as @v1.

What an update does​

If oyzu.toml pins an exact engine, that engine is set up first (see engine staging). Required features it doesn't support fail before anything changes. Then:

  1. Refresh the catalog. Unless you pass --offline, the verified catalog is refreshed first. If there's no current verified catalog (refused, expired or missing), the whole update fails with PLUGIN_CATALOG_UNAVAILABLE. This is stricter than a build: a build continues with an older cached copy after a refused refresh; an update doesn't.
  2. Pick each candidate using the selector.
  3. Check it. Each new release is installed into the plugin store (from the store, a plugins.packages binding, or the OCI route in its catalog entry) and checked like a first adoption: digest, package and version, builder profile, protocol and a payload this host can run. It must also pass the build's lock rules: not withdrawn, not revoked, not rebound by an organization catalog.
  4. Write once. Only when every requested reference passes is oyzu.lock rewritten, replacing just those [[plugin]] entries (comments above them are kept). Other selections, tool records and the engine pin are untouched. If another process changed those entries in the meantime, nothing is written (PLUGIN_LOCK_CHANGED). Any failure leaves the lock exactly as it was.

An update never runs a plugin and never edits configuration or other project files. Releases it installed stay in the store, even after a failed or --dry-run update.

Undo and rollback​

The undo line selects each changed reference's earlier release by digest, so it fixes the package as well as the version. It goes through the same checks, so it works only while that release is still available and allowed:

  • A release the catalog has since withdrawn or revoked is refused with PLUGIN_UPDATE_UNAVAILABLE.
  • If a catalog now binds the reference to another package, the earlier package is refused. The message names both packages and your options: ask the catalog's owner to bind the package you want, or update the bound one with an explicit selector. Under an organization catalog, builds refuse a lock of the other package too (PLUGIN_BINDING_CHANGED), including a reverted oyzu.lock.
  • If a plugins.packages binding supplied the new release, the binding has to name the earlier release again (or be unset) before the undo works. The update's notes say so, and an undo against the binding fails with PLUGIN_UPDATE_CONFLICT and the oyzu config unset line to run.

Reverting the oyzu.lock change in version control has the same effect; the next build checks it under the same rules.

Errors​

Every failure says oyzu.lock was not changed.

CodeCause and fix
PLUGIN_CATALOG_UNAVAILABLENo current verified catalog. Restore access and run again.
PLUGIN_UPDATE_NOT_LOCKEDThe reference isn't in oyzu.lock. Run oyzu build to adopt it first.
PLUGIN_SELECTOR_INVALIDThe selector isn't v<major>, an exact version or a sha256: digest, or a reference appears twice.
PLUGIN_UPDATE_UNAVAILABLENo eligible release fits the selector. The reasons are listed (for example outside the adopted major 1, no payload for this platform). If the locked release is still fine, a routine update reports unchanged instead.
PLUGIN_MAJOR_CHANGEA binding supplies a release outside the adopted major. Run the printed @v<major> update.
PLUGIN_UPDATE_CONFLICTA plugins.packages binding supplies a different release from the one you asked for.
PLUGIN_PREVIEW_NOT_SELECTEDThe release would be a preview. Use an exact selector with plugins.preview on.
PLUGIN_PACKAGE_CHANGEA routine update would switch packages. Run the printed explicit selector.
PLUGIN_UPDATE_REFUSEDThe new selection fails the build's lock rules (PLUGIN_RELEASE_WITHDRAWN, PLUGIN_RELEASE_REVOKED or PLUGIN_BINDING_CHANGED).
PLUGIN_ROUTE_UNAVAILABLEThe release isn't in the store, no binding supplies it and the catalog lists no OCI route (or --offline prevents using it). The message shows the plugins.packages line to add.
PLUGIN_ROUTE_FAILEDThe catalog route couldn't be reached, doesn't hold the release, or has an unusable address. Nothing was installed.
PLUGIN_PLATFORM_UNSUPPORTED, PLUGIN_PACKAGE_MISMATCH, PLUGIN_PACKAGE_INVALID, digest errorsThe downloaded package failed its checks. No other release is picked instead.
PLUGIN_LOCK_CHANGEDoyzu.lock changed while the update ran. Run it again.

When a build fails with PLUGIN_RELEASE_WITHDRAWN, PLUGIN_RELEASE_REVOKED, PLUGIN_BINDING_CHANGED or PLUGIN_LOCK_MISMATCH, its suggested fix is oyzu plugins update <reference>.

Repository update workflow​

workflows/oyzu-plugin-update.yml is a standard GitHub workflow. Copy it to .github/workflows/ in a repository whose oyzu.lock selects plugins. It runs weekly and on demand, in three jobs, so that nothing an unreviewed plugin does can change what gets proposed:

  1. update runs oyzu plugins update --json, which never runs a plugin. If oyzu.lock didn't change, it stops. Otherwise it uploads the new oyzu.lock, the JSON report, the change levels and the pull request text as one artifact.
  2. verify puts that oyzu.lock into a fresh checkout and runs BUILD_COMMAND (default oyzu build --frozen), which runs the new plugin. It has no repository write credential and uploads nothing. It's a pass/fail gate only.
  3. propose runs only if both passed. It downloads the update job's artifact, refuses it unless it contains exactly body.md, levels, oyzu.lock and report.json, commits only oyzu.lock to the oyzu/plugin-update branch, force-pushes it, and opens (or refreshes) a pull request listing each change, its level, the reason, notes and the undo line. It never merges directly.

Setup:

ItemMeaning
OYZU_UPDATE_TOKEN secretA GitHub App or fine-grained token with contents and pull-requests write access, used by the propose job only. The default GITHUB_TOKEN won't do: pull requests it opens don't trigger your required checks.
Install oyzu stepsReplace with your pinned, checksummed oyzu installation.
AUTO_MERGE_PATCH: 'true'Optional. When every change is a patch, turn on GitHub auto-merge, which still waits for branch protection and required checks.
jqNeeded by the update job. GitHub-hosted Ubuntu runners include it.

When the workflow refreshes an open pull request with anything other than patch changes, it turns auto-merge off and confirms it's off before pushing, so an earlier auto-merge request never applies to the new proposal. If that check fails, the job stops without pushing.

Limitations​

  • Only this host's platform is checked for payloads. Other platforms you build for (a declared matrix, remote workers) aren't checked.
  • Only a catalog's OCI route is used for downloads. A release whose catalog entry lists only an HTTPS archive route needs a plugins.packages binding.
  • @vN works only on this command, not in uses:.
  • The verify job runs an unreviewed plugin. It has no repository write token, but on a GitHub-hosted runner the plugin runs as the job's user (with passwordless sudo). It can read the job's ACTIONS_RUNTIME_TOKEN and use it to write Actions caches for the default branch, which other workflows may restore, or to upload artifacts. The propose job is protected because it checks the artifact it uses; other workflows that restore default-branch caches are not. Setting permissions: {} doesn't help, since that limits GITHUB_TOKEN, not the runtime token. Where you can, run verify on an ephemeral, isolated runner and key important caches so this workflow can't produce them.
  • The workflow hasn't yet run on GitHub-hosted runners against a real plugin project.
  • Supported on Linux. Windows and macOS aren't supported yet.
