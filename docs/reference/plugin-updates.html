Updating plugins

CLI reference

Published from the canonical docs/reference/plugin-updates.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Experimental. oyzu plugins update replaces plugin selections that oyzu.lock already holds: a routine update within the adopted major, an explicit new major, or one exact version or release (an exact release root is how an update is undone). A standard GitHub workflow runs it on a schedule and opens a pull request. The design is the draft compatibility and updates proposal; this page records what is implemented (issue #587, tracking #578). How a selection is first adopted is in plugin catalog; the [[plugin]] lock record is in plugin packages; read-only views are in inspecting plugins.

Usage​

oyzu plugins update                     # every locked selection, each within its adopted major
oyzu plugins update go/app              # only go/app
oyzu plugins update go/app@v2           # adopt major 2 of go/app explicitly
oyzu plugins update go/app@1.0.0        # exactly version 1.0.0 of go/app's package
oyzu plugins update go/app@sha256:…     # exactly this release root: the printed undo
oyzu plugins update --dry-run           # preflight and show the change; oyzu.lock is not written

Options: --dry-run, --offline (update from the cached catalog only), --store DIR (the plugin store, as oyzu build --store) and the global --json. It works without an account. --help and syntax errors finish before a project, configuration, store or network is opened.

Publishing or caching a newer release never changes a lock: builds replay it (PLG-COMPAT-05). Only this command, or deleting the entry, changes it.

What an update does​

Before catalog or candidate evaluation, an exact engine pin uses the shared engine bootstrap. A mismatching active frontend must have an admitted source for that engine. The selected engine evaluates its own supported role features, including on warm package reuse; unsupported required capabilities fail before adoption or plugin roles. A compatible update changes only the requested plugin entries and retains engine and native-tool pins. Metadata-only inspection continues to use the running engine without staging.

  1. Refresh the catalog. Unless --offline, the verified catalog cache is refreshed from the permitted sources first, as a real build does. A refused catalog (failed trust, rollback, a verified copy gone missing) or an expired one refuses the whole update with PLUGIN_CATALOG_UNAVAILABLE: an update never adopts a release without a current verified catalog. This includes a refresh that obtained a newer copy and refused it while an older verified copy is cached: a build goes on with that copy, an update does not. With --offline, the cached copy is used as asked.

  2. Choose each candidate with the build's resolver and eligibility rule, within a selector:

    WrittenSelectorCandidate
    go/app (or nothing: every locked reference)the adopted majorthe newest eligible release in that major; never an older one while the locked release may still be used
    go/app@v2 or go/app@2major 2, explicitlythe newest eligible release of major 2
    go/app@1.4.2exactly version 1.4.2 of the package the catalog bindsthat release, newer or older
    go/app@sha256:…exactly this release root, which also names its packagethat release; the printed undo uses this form

    Routine and @v<major> updates never select a preview release, whatever supplies it, catalog or plugins.packages binding (ordinary updates exclude previews, PLG-COMPAT-01): PLUGIN_PREVIEW_NOT_SELECTED. A release is a preview when its version is a prerelease or when the catalogs list it (by root digest, or by package and version) as one. A listing by root digest decides before one by package and version. An exact @<version> or @sha256:… can select a preview, and only with plugins.preview.

    A routine update never changes the canonical package either: when an organization catalog rebinds the reference (or a binding supplies another package) it fails with PLUGIN_PACKAGE_CHANGE, and the change is adopted only with an explicit selector such as @v1.

    Eligible means what it means for a build: listed by the consulted catalog, not withdrawn or revoked (by package and version or root digest, in any consulted snapshot), not a preview without plugins.preview, supported, on the v1alpha1 contract, with the builder profile and a payload for this host. A plugins.packages binding for the reference supplies the package instead, as it does for a build; it must still fit the selector and replay under the lock rules below.

  3. Preflight. Each new release is installed into the plugin store from its route (already in the store, the plugins.packages binding that names its digest, or, with no binding, the OCI route in its verified catalog entry, as a build acquires it) and checked exactly as a first adoption is: archive or OCI digest, the catalog's package and version, the builder profile, the protocol generation, and an executable payload this host runs. The proposed selection must then pass the build's own lock rules (Context::check_locked): not withdrawn, not revoked, not rebound by an organization catalog.

  4. Write once. Only when every requested reference passes is oyzu.lock rewritten, in one lock-edit transaction that replaces exactly those [[plugin]] entries in place (comments above an entry are kept). Unrelated selections, tool records, the engine pin and the lock format are untouched. If another process changed one of those entries meanwhile, nothing is written (PLUGIN_LOCK_CHANGED). Any refusal leaves the lock byte for byte as it was.

An update never launches a plugin, edits configuration, or touches another project file. Releases it installed stay in the store (content-addressed and immutable), also after a refused or --dry-run update.

Undo and rollback​

The undo line selects each changed reference's earlier release root exactly (@sha256:…), so it names the package as well as the version: after a package change, two packages can share a version number. It goes through the same checks, so it succeeds only while that release remains available and authorized: a release the catalog has since withdrawn or revoked is refused (PLUGIN_UPDATE_UNAVAILABLE, naming the withdrawal), and so is the earlier package while a catalog binds the reference to another one. That refusal states only what is known: which package and version the release belongs to, which package the catalog holding the binding (named or primary) binds the reference to, that under an organization catalog a lock of the other package, such as a reverted oyzu.lock, is refused by builds too (PLUGIN_BINDING_CHANGED), and the two ways forward: ask the catalog's owner to bind that package, or update the bound one with an explicit selector. It does not claim the reference ever used the other package. Reverting the oyzu.lock change in version control restores the same records; the next build then replays them under the same rules. If a plugins.packages binding supplied the new release, the undo also needs that binding to name the earlier release again or be unset; the update says so in its notes, and an undo against such a binding fails with PLUGIN_UPDATE_CONFLICT and the oyzu config unset line.

PLUGIN_CATALOG_UNAVAILABLENo current verified catalog (refused, expired, or none usable). Restore access and run again
PLUGIN_UPDATE_NOT_LOCKEDThe reference has no selection in oyzu.lock; run oyzu build to adopt one first
PLUGIN_SELECTOR_INVALIDThe selector is not v<major>, an exact version or a sha256: release digest, or a reference is named twice
PLUGIN_UPDATE_UNAVAILABLENo eligible release fits the selector (with the reasons, such as outside the adopted major 1, no payload for this platform, or the withdrawal). A routine update whose locked release still replays reports unchanged instead
PLUGIN_MAJOR_CHANGEA binding supplies a release outside the adopted major; run the printed @v<major> update to adopt it explicitly
PLUGIN_UPDATE_CONFLICTA plugins.packages binding supplies another release than the requested @<version> or @sha256:…
PLUGIN_PREVIEW_NOT_SELECTEDThe release that would be adopted is a preview: routine and @v<major> updates never select one; an exact selector needs plugins.preview
PLUGIN_PACKAGE_CHANGEA routine update would change the canonical package (an organization rebinding, or a binding to another package); adopt it with the printed explicit selector
PLUGIN_UPDATE_REFUSEDThe proposed selection fails the build's lock rules (wrapping PLUGIN_RELEASE_WITHDRAWN, PLUGIN_RELEASE_REVOKED or PLUGIN_BINDING_CHANGED), for example a binding to a withdrawn release's archive
PLUGIN_ROUTE_UNAVAILABLEThe candidate is not in the store, no binding supplies it and its catalog entry has no OCI route (or --offline forbids using it); the message prints the plugins.packages line to bind its archive
PLUGIN_ROUTE_FAILEDThe candidate's catalog route could not be reached or does not hold the release, or lists an unusable address; nothing was installed or recorded. A signature, digest or package failure on the route keeps its own code
PLUGIN_PLATFORM_UNSUPPORTED, PLUGIN_PACKAGE_MISMATCH, PLUGIN_PACKAGE_INVALID, archive digest errorsPreflight of the installed package failed; no other release is chosen instead
PLUGIN_LOCK_CHANGEDoyzu.lock changed while the update ran; run it again

Each refusal says oyzu.lock was not changed. The build's remedies now point here: PLUGIN_RELEASE_WITHDRAWN, PLUGIN_RELEASE_REVOKED, PLUGIN_BINDING_CHANGED and PLUGIN_LOCK_MISMATCH end with oyzu plugins update <reference>, as does the Selection section's other-implementation remedy for a selection locked earlier.

Repository update workflow​

workflows/oyzu-plugin-update.yml is the standard workflow. Copy it to .github/workflows/ in a repository whose oyzu.lock selects plugins. Weekly and on demand it runs three jobs, so that nothing an unreviewed plugin does can change what is proposed:

  1. update runs only oyzu plugins update --json, which launches no plugin (it invokes the oyzu updater directly; no other dependency bot needs to understand oyzu.lock). It stops if oyzu.lock did not change; otherwise it uploads the proposed oyzu.lock, the JSON report, the change levels and the pull request body as one artifact and passes on its id.
  2. verify downloads that artifact by id, writes its oyzu.lock into a fresh checkout and runs BUILD_COMMAND (default oyzu build --frozen), which launches the newly adopted plugin. It has no write credential (the checkout keeps none and no token is in the job) and uploads nothing: it is a pass/fail gate only, and nothing it writes reaches the propose job. See the limitation below on what the plugin can still reach in this job.
  3. propose runs only if both passed. In a fresh checkout without persisted credentials it downloads the update job's artifact by id, refuses it unless it holds exactly body.md, levels, oyzu.lock and report.json as regular files, writes only oyzu.lock into the tree, commits it to the oyzu/plugin-update branch, force-pushes it, and opens a pull request, or refreshes the open one, whose body lists each change, its level, why, notes and the undo line. The token is in this last step only. With AUTO_MERGE_PATCH: 'true' and only patch changes, it enables GitHub auto-merge, which merges only after the repository's branch protection and required checks pass. When it refreshes an open pull request with anything else, it turns auto-merge off (gh pr merge --disable-auto) and confirms it is off before it pushes the new lock, so a request made for an earlier all-patch proposal never applies to the new one. Every gh call before the push fails closed: a failed pull request lookup (which counts only this repository's pull request, not a fork's with the same branch name), a failed --disable-auto, or auto-merge still requested afterwards stops the job with nothing pushed. It never merges directly.

It needs a secret OYZU_UPDATE_TOKEN (a GitHub App or fine-grained token with contents and pull-requests write access), used by the propose job only: pull requests opened with the default GITHUB_TOKEN do not start the repository's workflows, so required checks would never report. The Install oyzu steps are placeholders to replace with a pinned, checksummed installation: no oyzu release is published yet. The update job needs jq, which GitHub-hosted Ubuntu runners include.

A failing build proposes nothing. An artifact with an extra file is refused before any push. The stand-in plugin cannot run a full build, so the tests replay the updated lock with oyzu build --frozen up to the plugin launch, and the workflow test's build command checks that no credential is visible and runs oyzu plugins explain.

Limitations​

  • Only the host platform is evaluated for payloads; other required execution platforms (a declared matrix, remote workers) are not preflighted.
  • Only a catalog's OCI route is acquired from (as in a build); a candidate whose entry lists only an HTTPS layout-archive route needs a plugins.packages binding.
  • @vN in uses: references is not implemented; the selector exists only on this command.
  • The verify job runs the newly adopted, unreviewed plugin on the default branch, in scheduled runs and in runs started with workflow_dispatch. It holds no write token for the repository, but on a GitHub-hosted runner the plugin runs as the job's user (with passwordless sudo), so it can read the job's ACTIONS_RUNTIME_TOKEN, and with that write Actions caches scoped to the default branch, which other workflows restore, or upload artifacts of its own. The propose job is protected (it reads only the update job's artifact, by id, and checks it), but other workflows that restore default-branch caches are not. Today the workflow does nothing about this beyond running verify in its own job with no repository credential. Setting permissions: {} on the job would not prevent it either: that limits GITHUB_TOKEN, not the runtime token the Actions cache and artifact services use. Where possible, run the verify job on an ephemeral, isolated runner and keep workflows that matter from restoring caches the verify job could write (for example, key their caches so this workflow cannot produce them).
  • The workflow has been run locally against a bare remote with a stub gh, not yet on GitHub-hosted runners against a real plugin project; it has no oyzu installation step until a release exists.
  • Windows and macOS are untested.
