Native local builds

CLI reference

Published from the canonical docs/reference/local-builds.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Plain oyzu build runs your project's own tools (Cargo, Go, npm, pip, Maven, Gradle) directly on your machine and collects the results into a build bundle. These builders need no Docker. This page covers which builds run natively, how to choose platforms and executors, how to preview a build, and how to split a build into separate jobs.

Note: A native build runs with your user account's access to files and the network. It is not a sandbox. Use oyzu build --isolated when you need the container executor.

Platform scope: Use an x64 host and supported x64 build targets. ARM64 is unsupported. Feature-specific limits are listed in the support matrix.

Quick start​

oyzu build --plan                     # preview; installs and runs nothing
oyzu build                            # host build with fast checks
oyzu build --full                     # also run tests, lint and format checks
oyzu build --platform linux/arm64     # build for one other platform
oyzu build --isolated                 # use the container executor
oyzu inspect dist                     # verify the bundle

Run these commands from a project, or select one with oyzu -C <project> build. Build uses the same project-boundary check as oyzu run: Oyzu configuration, an Oyzu build.yaml, a Git boundary or a recognized native manifest identifies a project. A plain parent folder also builds as a zero-config workspace when the bounded lookup finds a project within three directory levels. Static markers are the fast path; eligible catalog detections also identify projects at the root or within that same lookup. The configured catalog uses normal verification and refresh rules (--plan and --offline use cached metadata), so configuration and catalog metadata may be loaded or refreshed before a refusal. If neither the root nor that lookup identifies a project, all build variants (including a named target, --plan, --full and --json) refuse with PROJECT_NOT_FOUND (exit 5) before deeper build discovery, workspace preparation, Prepare output or the Building … heading. Unreadable folders are skipped by the lookup. oyzu run still requires a project at the root and only suggests nearby projects. See missing projects and unreadable folders.

Native or isolated​

For a declared oyzu/plugin-package target, repeat --compose <bundle>/manifest.json to assemble already-built platform members instead of running the executable producer. Composition admits existing signed provenance and checks the target's declared platforms; deliberate gaps use --allow-incomplete <platform>=<reason>. See plugin packaging.

Plain oyzu build runs natively when every selected target has a native host build (see the table below). Otherwise it uses the container executor.

  • --isolated (or --image) always uses the container executor.
  • --affected picks its targets first, then follows the same rule.
  • --all-platforms builds every declared platform through the container executor and needs Docker.
  • A failed build never retries with another executor.
  • Running in CI doesn't change the choice.

Native output is a runnable binary or package for this machine. Use --isolated when you need the packaging that the container executor produces. The bundle manifest still records each artifact's version: the builder's own version where it has one, otherwise the target's resolved version.

When a consumer declares a platform other than the host, the build uses the container executor. For example, a docker/image with platforms: [linux/x86_64] that copies in a Go binary, built on Windows, gets a Linux Go binary built in the container. The container runs on the base execution image, and every tool comes from oyzu.lock there (see Go, Node and Helm). A tool that isn't locked for the platform is refused with the oyzu pin command that adds it.

Native host builds​

These builders build on the host. Oyzu installs any missing tool into the shared tool store, then runs the ecosystem's own commands.

An admitted plugin runs from its installed host path. A tool store under a folder named /workspace, /out or /oyzu keeps that exact executable path; these names do not move the plugin into the build's private source workspace. This also applies to conventional check tasks, including Java lint and format checks.

Automatic tool selection​

oyzu pin is optional for Rust, Go and Node. With no oyzu.lock, the first build resolves the tools, writes oyzu.lock and installs from it. Commit the lock to make later builds repeatable, or delete it to resolve again.

Tools a builder detects on its own follow the same rule. For example, a Rust project whose Cargo.lock lists prost-build needs protoc. Its version is your folder pin, else the detection's hint, else the latest stable release in the catalog.

  • The build locks and installs it with the other tools. oyzu pin records the same choice.
  • A detected tool that has no catalog entry or checksum, or that can't be installed, is shown as an attention row and the build continues. Set tools.ignore to silence it.
  • Only a tool you pinned in oyzu.toml fails the build when it can't be verified or installed.

Go host builds​

  • [tools] go = "1.24" wins when it is at least the Go minimum. A module-folder value below the minimum is refused.
  • The build runs go build -trimpath -buildvcs=false with GOTOOLCHAIN=local, so only the locked Go compiles and none is downloaded mid-build. --offline adds GOPROXY=off.
  • Compiler errors show their file and line, the exit status is kept, and no earlier binary is republished.
  • The artifact is the executable <target>-<version>. --full adds go test -json with coverage, go vet and gofmt -l.
  • Dependencies use Go's module cache from your Go environment. It isn't separate per project.

Native mixed-target build implementation​

One oyzu build can build several native targets, such as a Python wheel and a Node dist/ directory, into one bundle.

  • Oyzu selects the targets you named plus everything they depend on, prepares their tools, and runs one shared task graph.
  • Independent targets run at the same time, up to build.jobs. A depends_on in build.yaml makes the consumer wait for the producer's stages.
  • By default, a build-failing action stops the build, including unrelated work. With --keep-going, unrelated targets can finish and only dependents are blocked.
  • Stages within one target run in order, because they share the target's files.
  • Each target builds in its own private workspace. An ordering edge alone copies no files; use materialize to pass artifacts.
  • Required reports must be produced and artifacts collected before a target counts as built. See build tasks.
  • Two targets that would produce executables with the same file name are refused before anything runs.

On Unix, native private source workspaces preserve ordinary file and selected directory permissions (0777) on cold population and later refreshes, including mode-only changes with unchanged file bytes and modification times. This includes selected nested and empty directories and target directories below the source boundary. Directory modes are applied after population; read-only directories are temporarily writable only in the private copy during refresh and pruning. The authored source tree is unchanged.

The projection's engine-owned boundary root remains writable working storage; its mode does not reproduce the source boundary root. Captured execution views retain their existing directory behavior. ACLs, ownership and special bits are outside this native projection guarantee.

Regular-file source observations include the ordinary Unix mode as well as executable intent. A mode-only change invalidates affected action keys, while source versions remain permission-independent. Cached regular files restore their verified ordinary mode; Unix admission refuses missing, invalid or inconsistent mode facts instead of assuming 0644 or 0755. Hosts without Unix mode observation leave that fact absent.

Directory modes remain outside action-result cache identity and output metadata restoration. Use oyzu build --no-cache when directory permissions affect build outputs. ACLs, ownership and special bits remain outside this guarantee. See action caching for the current reuse limits.

Linux native host action keys bind the file-creation mask inherited by child processes. A build launched with umask 0077 cannot reuse a result keyed under 0022, even when source files are unchanged. Oyzu reads the mask without changing it, freezes it once before cache lookup, and records the same bounded value in the host action's invocation and native command identity.

If the mask cannot be read or validated on Linux, or cannot be observed on another Unix host, native host targets run without action-result reuse. Existing worker, builder and secret-environment restrictions retain their reasons. Image workers do not bind the coordinator's mask, and Windows has no Unix creation-mask fact. This does not establish full file/directory mode identity or output metadata restoration; the permission limits above still apply.

Ecosystem notes:

  • npm runs npm ci and needs a lockfile. Installation is the target's prepare step. It runs before pre_build hooks, is skipped on a full cache hit, and runs again with --no-cache. A failed install blocks the build and publishes nothing. npm lifecycle scripts run as usual.
  • pip uses its own PEP 517 wheel build, including downloading the build backend. CPython is installed as a managed tool and pip is the one bundled with it. The output is a wheel, not a runnable application.
  • Offline, npm runs in offline mode and pip uses --no-index. The build fails if what they need isn't already cached.

Independent nested projects​

Run oyzu build or oyzu build --plan in a nested folder that has its own build.yaml; you don't need --root.

  • A source subfolder uses the nearest build.yaml above it.
  • Repository configuration still applies, but the nested build has its own lock file and outputs.
  • A parent build doesn't include nested builds.

See configuration for how configuration is inherited.

When an action fails​

oyzu build stops at the first build-failing action, locally and in CI. It starts no further actions and stops running actions through the same process-tree and worker cleanup used by Ctrl-C. The build is failed, with the first failure's exit code. An advisory check that only warns does not stop the build.

Set build.failFast = false to finish independent actions and collect every failure in one run. Dependents of a failed required action remain blocked. Each target resolves this setting from its folder chain: the nearest folder wins, and a context value wins over the base value in the same file. A failure in a target with false blocks only its dependents; a build-failing failure in a target with true stops the whole build. For example, to keep going in CI:

[context.ci.build]
failFast = false

oyzu build --keep-going sets false for every target; --fail-fast sets true. These mutually exclusive flags override OYZU_BUILD_FAIL_FAST=true|false, which overrides files. Ordinary policy constraints still apply. An empty environment value is ignored; other values fail with CONFIG_INVALID_VALUE. The flags also apply to --slice. The plan and build record show each target's resolved value and source beside its check levels. Inspect configuration with oyzu config get build.failFast or oyzu config explain build.failFast. Changing the setting does not change cache keys. Remote submission and oyzu run task DAGs retain their existing behavior.

Actions that succeeded before the stop keep their normal action-cache entries. After fixing the failure, rerun the build to reuse them. Stopped actions export no outputs and are never cached. See stopped action records.

Requirement discovery and pinning​

oyzu pin --dry-run previews tool requirements and lock changes without installing anything or changing files. oyzu pin writes the lock; conflicts or incomplete inputs fail and leave the lock unchanged. See the lock file.

  • With no oyzu.lock, the first build resolves the tools, writes the lock (it never edits your TOML files) and installs them. You don't need a compiler already installed.
  • An existing lock is never changed by a build. A missing or incompatible entry fails with a request to run oyzu pin.
  • oyzu build --offline never resolves versions or writes a lock. It needs the metadata, archives or installations already cached.
  • Pinning reads files only. It works offline and currently runs from the workspace root.

For Rust, discovery reads:

  • rust-toolchain.toml or rust-toolchain, in every form rustup accepts (see Rust toolchain files). Having both files is an error.
  • Cargo rust-version minimums.
  • Declared components, targets and profile.
  • The tools each selected stage needs (rustfmt, Clippy, nextest, cargo-llvm-cov).

With no toolchain file, Rust is listed without a version and the build locks the latest stable release. A file with no channel keeps its components and uses your configured or default Rust. A local path toolchain fails unless oyzu.toml selects a release.

Node is resolved the same way. For pip wheels, CPython comes from requires-python or .python-version and is installed from Python Build Standalone. uv, Poetry and older Python tools are not installed for you.

System linkers and SDKs​

Oyzu names the system linker and SDK a Rust toolchain needs, but doesn't install them:

Toolchain channelNeeds
*-windows-gnullvmLLVM-MinGW (UCRT) with Clang linking
*-windows-msvcMicrosoft Build Tools and the Windows SDK
*-windows-gnuA toolchain with the profiler runtime if you need coverage
Unqualified, such as 1.95.0GNU/LLVM or MSVC, listed as alternatives

Discovery doesn't run rustup, search PATH or check whether these are installed. The build checks them when it runs (see executor readiness). Requirements of dependency build scripts and toolchain files in parent folders aren't detected.

Platforms and executors​

Two ideas stay separate. The target platform is what an artifact is built for. The executor is where its build steps run:

  • this host, for its own platform;
  • a native cross toolchain on this host;
  • the container executor (--isolated, --all-platforms);
  • a remote pool (--remote).

The executor is part of the build's identity. The plan and manifest record it on each target (oyzu.dev/platforms), and cache keys include it. A cross-compiled or container result never stands in for a host build of the same platform, or the reverse.

Platform names​

Write every platform as os/arch[/abi]: linux/x86_64, linux/arm64, darwin/arm64, windows/x86_64, windows/x86_64/msvc.

  • Input also accepts amd64 for x86_64 and aarch64 for arm64, in build.yaml platforms, --platform and --allow-incomplete. Output, records and dist/ folders always use the canonical form.
  • The ABI is optional: gnu or musl on Linux, msvc, gnu or gnullvm on Windows. Without one, the builder picks its default (see Rust).
  • The resolved ABI is recorded in the target's platform. For Rust it is musl for a Linux cross build, msvc on Windows and gnu on a Linux host.
  • Published names (dist/ folders, asset names) include the ABI only when it isn't the OS default (GNU on Linux, MSVC on Windows). See release asset names.
  • Container engines and registries keep their own spelling (linux/amd64).

Note: musl is the default for Linux cross builds. If your code depends on glibc (dlopen, NSS name lookup), declare linux/<arch>/gnu.

Selecting platforms​

  • A platform-independent target, such as a static site in dist/<target>/any/, is built once.

Declaring a platform's executor​

By default, a platform builds on the host when it matches, otherwise with a native cross toolchain if the builder has one (or the container executor under --isolated). You can fix the executor per platform in oyzu.toml, per folder and per context:

[build.executors]
"linux/arm64" = "cross-toolchain"   # always cross-compiled, never built on an arm64 host
"darwin/arm64" = "host"             # only on a macOS arm64 runner

[context.release.build.executors]
"linux/x86_64" = "container"        # releases build it in the container executor

Values: host, cross-toolchain, container.

  • A declared executor is the only one used for that platform. Nothing falls back to another.
  • When it isn't available here (no cross linker, the wrong host, container without --isolated, or host/cross-toolchain with --isolated), the platform isn't built and Plan says why. Asking for it explicitly fails with PLATFORM_UNAVAILABLE before anything runs.
  • In the release context the host platform counts as asked for, so a release build fails instead of skipping it.
  • Plan, the preview (declaredExecutor) and the CI matrix (executor) show the declaration.

A CI matrix from the plan​

oyzu build --plan --json includes a top-level matrix you can feed to a CI matrix strategy. It has one include entry per declared platform of every selected target, with:

  • platform;
  • runner: os (linux, windows, macos) and arch, the machine that builds it natively;
  • executor: the declared executor, else host;
  • targets: the targets that declare it.

The matrix doesn't depend on what the planning machine can build: a target that declares only darwin/arm64 still gets its entry when planned on Linux. unconstrained lists targets that declare no platforms. With --affected <ref>, the matrix holds only affected targets.

Each target in the preview also has a platforms record: declared, declaredExecutors, one row per platform (selected, executor, declaredExecutor, reason, refused, runner), and the platform and executor this run would use.

jobs:
  plan:
    runs-on: ubuntu-latest
    outputs:
      matrix: ${{ steps.plan.outputs.matrix }}
    steps:
      - uses: actions/checkout@v4
      - id: plan
        run: echo "matrix=$(oyzu build --plan --json --affected origin/main | jq -c .matrix)" >> "$GITHUB_OUTPUT"
  build:
    needs: plan
    strategy:
      matrix: ${{ fromJSON(needs.plan.outputs.matrix) }}
    runs-on: ${{ matrix.runner.os == 'macos' && 'macos-15' || matrix.runner.os == 'windows' && 'windows-2025' || 'ubuntu-24.04' }}
    steps:
      - uses: actions/checkout@v4
      - run: oyzu build ${{ join(matrix.targets, ' ') }} --platform ${{ matrix.platform }}
  • Your workflow maps runner to real runner labels, including any arm64 runner.
  • oyzu publish checks that every declared platform was built; see incomplete platform sets.
  • Toolset verification runs are listed separately under .verify. Run them in the platform jobs, or pass --skip-verification to the platform jobs and run each .verify command in its own job. See fanning runs out in CI.

Read-only build preview​

oyzu build --plan shows what a build would do without doing it. It chooses native or container execution exactly as a build would. --isolated, --all-platforms, named targets, profiles and --full mean the same as in a build. You don't need Cargo or Docker installed to run it.

The preview:

  • reads configuration and project files, and shows each target's discovery decisions, stages (run or skipped), task order and tool requirements;
  • doesn't install tools, download packages, run build tools or scripts, create a lock, or write a bundle;
  • with --affected, reads local Git history and hashes local files, with no network access or writes.

Some details are only known once a real build prepares: whether tools are installed, exact commands, artifact names and report paths. The preview marks these as unresolved. A stage marked run means configuration asks for it, not that its prerequisites will pass. A successful preview doesn't mean the build will succeed.

Preview output​

  • The Plan table shows targets by stage, with run, skip or - cells and one footnote per skip reason. A single target built for several platforms shows one row per platform. Above twelve rows, targets with identical stages share a counted row; -v lists every target. See result output.
  • When every target needs the same tool, the requirements table shows "all N targets". --json still lists every target.
  • Color follows your terminal (CLICOLOR_FORCE=1 forces it, NO_COLOR turns it off).
  • --json returns a build-preview record with resolved: false, the selection, targets (each with a discovery map of role to selected and reason), tasks, requirements, unresolved details, effect flags and timings.

The preview is not the executable plan. A real build writes that to dist/plan.json.

Preview timings​

timings reports where the preview spent its time, in milliseconds: totalMs and phases, in this order:

PhaseWhat it measures
discoveryConfiguration and target discovery.
selectionSelection, variants, task graph and requirements.
sourceListing the working tree from file metadata. Absent when analysis is off or fails.
analysisStatic analysis, with targets (one entry per target), finishMs and rulesMs. Absent when analysis is off or fails.
planningStage and task listing.

Timings describe one run and aren't part of the analysis record.

Selecting CI jobs​

Use oyzu build --plan --json --affected <base> after checking out the comparison history. The preview installs and runs nothing. Read the selected logical builds from selection.requested and the platform matrix, and repository-check tasks from selection.affected.tasks. See affected builds.

Only use selection.affected.inputModel: "stage-reads" with an explicit fallback: null to skip jobs. A missing or malformed fallback field runs every job; a nonempty fallback reason also runs everything and explains why. A missing marker (including release v0.2.2), missing base, unsupported change or preview failure must run every job and retain the reason. Scheduled, release and explicit dispatch runs should build everything. A job-level if: can report an intentional skip while an aggregate required check still verifies that every selected job passed; a workflow path filter cannot provide that result.

The repository's CI and docs-site gates use the PR base, or the last successful main CI commit for a main push. Inputs belong to build.yaml and the tasks in oyzu.toml, including workflow/setup files read by the workflow checks. The released CLI remains the driver; a candidate built from the PR cannot qualify its own selection. A fresh affected preview records absent generated declared inputs in selection.affected.absentDeclaredInputs instead of requiring their preparation. Executing the build still requires them. The repository's unbounded root Rust stages currently keep the CLI job selected for docs-only edits; a source-only edit can leave docs unselected when no docs task inputs changed. Remote pool webhook/trigger integration remains a later, separate design.

Planning a remote run​

oyzu build --remote --plan previews what oyzu build --remote would run on a platform pool. It doesn't contact the platform and needs no token. It uses the pool's settings: isolated execution, full checks and the normal platform selection.

  • --remote doesn't imply --all-platforms.
  • Named targets and --affected <base> work as in the remote run. --affected compares with the merge base of <base> and HEAD.
  • The record's execution is remote.
  • The preview reads your working tree, so it includes uncommitted changes, which a remote run never sends.
  • --isolated, --all-platforms, --image, --check and --download can't be combined with --remote.

Every preview target carries these placement facts:

FieldMeaning
platformThe artifact platform: from the target's variant, otherwise decided by the executor (unresolved until executor selection).
platformSourcevariant, executor or host (a native host target).
executionPlatformThe platform the executor must run on, or null when any will do. A Rust cross-compile in the container runs on linux/x86_64 whatever it targets. A Docker image needs its own platform when its final stage uses RUN.
needsDaemon, daemonReasonWhether the work needs a Docker engine, and why. false for native host targets, for Node, Rust, supported external go/app and pip Python (python/package, python/app, python/library) targets that can use the daemonless sandbox, and for RUN-free image assembly. Selected quality checks or hooks can make an image target need Docker.
isolationWhat the executor must provide: host, crun (Linux with unprivileged user namespaces, or Docker), in-process (Oyzu's own image assembly) or docker.
id, logicalTarget, variantThe concrete target ID, its logical name, and its variant axes. Use the returned id; don't construct one.
dependsOnTargetsThe concrete targets this one depends on.
sliceableWhether another slice could reuse this target's results. false means build it in the consumer's slice.
sliceReason, sliceDetailWhy it isn't sliceable, or null: ALWAYS_RUN_HOOK, UNCACHED_TASK, UNSCOPED_INPUTS, UNBOUNDED_OUTPUTS, SECRET_ENVIRONMENT, CACHE_DISABLED.
platformsHow each platform is built here; see a CI matrix from the plan.

A target isn't sliceable when it has a hook (hooks always run), an authored task without cache = true and declared outputs, inputs outside its folder, stages with unbounded outputs, a secret environment, or local caching turned off. Image targets with source projections can be reused across slices under the same cache-key and artifact-verification rules. A build can still fail to reuse a sliceable target, for example when the producer failed.

The top-level placement object says which facts can change. Each target's platform, executionPlatform and needsDaemon are final, as are tool requirements whose status is discovered. The target list, task graph, stages and unsupported requirements can grow when a real build discovers more targets. OYZU_NO_DOCKER=1 doesn't change the preview.

Building without Docker​

oyzu build --no-docker, or OYZU_NO_DOCKER=1, is for executors with no Docker engine, such as a Kubernetes pool. Oyzu then runs no Docker command at all. Any value other than empty or 0 turns it on.

Before preparing anything, the build works out the same placement as --plan. If any selected target has needsDaemon: true, it stops with exit status 3 and runs nothing:

oyzu build --isolated --no-docker --json
{"error":"NEEDS_DOCKER_DAEMON: cli need a Docker engine, which this executor does not provide (--no-docker); nothing was run","reason":"NEEDS_DOCKER_DAEMON","targets":["cli"],"exitCode":3}

Exit status 3 means "wrong kind of executor", so a runner can tell it from a failed build (1) or a refused command (2) and requeue the job on a pool with Docker.

What can still build without Docker:

  • native host targets;
  • Node, Rust, supported external go/app and pip Python (python/package, python/app, python/library) targets, in the daemonless sandbox;
  • a RUN-free Dockerfile with FROM scratch or a digest-pinned base, with --isolated --no-docker (see Docker image assembly).

--full adds Dockerfile lint and format checks, which need Docker, so the build refuses rather than skipping them. --no-docker can't be combined with --remote.

The daemonless sandbox​

On Linux, the isolated steps of Node (node/app, node/package), Rust (rust/app, rust/library) and pip Python (python/package, python/app, python/library) targets can run under crun, a rootless container runtime, instead of docker run.

External targets still need an admitted execution engine, a packaged plugin with captured-plan, and a detected native dependency provider. Builder options also require the package's build-options feature. An unpackaged development executable does not qualify. Python packages using uv or Poetry do not use this daemonless path.

Each step gets the same sandbox as under Docker: no network, a read-only image root, no capabilities, no-new-privileges, a seccomp filter, Docker's masked /proc paths, the same mounts and tmpfs sizes, inside a user namespace that maps the workspace owner to itself.

  • Each image's root filesystem is unpacked once per digest and shared by every build on the host.
  • A root process gives unpacked files their archived owners. In a user namespace that does not map IDs 0–65535 (for example a planner sandboxed with unshare --user --map-current-user), a file whose archived owner is unmapped keeps the unpacking process's owner, as it would for a non-root process, and each step runs with only the workspace owner mapped, as for a non-root user. Such a root keeps its own copy of each image root rather than sharing the full-range one.
  • Both backends produce the same cache keys and outputs, so a result cached by one serves the other.
  • Unchanged npm builds can reuse earlier dependency downloads; see captured npm acquisition.

Note: External Go and Rust plugin builds (go/app, rust/app) can also use crun on Linux x86-64. This is experimental. It needs a packaged plugin, a locked toolchain and a compatible Linux image; Go also needs a single application module. Commit the full oyzu.lock and build with --frozen; add --offline once everything is cached. On Linux, the locked Rust compiler is unpacked and checked by Oyzu itself, so a Rust build needs no Docker engine at any step.

Choosing the backend​

build.isolationBehavior

--no-docker and OYZU_NO_DOCKER=1 select crun for eligible targets whatever the setting says.

  • oyzu install downloads a pinned crun release (1.24), checks its SHA-256 and keeps it in your user data folder. Set OYZU_CRUN to use a crun the executor already has.
  • Images come from their digest-pinned published source, or from a running local Docker engine. A tag-only local image with no engine running fails before anything runs.
  • crun runs without its own cgroup, so the executor pool's limits apply instead of per-step memory and CPU limits.
  • Each action in the manifest records its sandbox in sandbox: backend (docker or crun), the crun runtime version, and resourceLimits (cgroup or pool).

When the sandbox cannot run​

Before dependency preparation or build actions run, a build that uses crun checks the runtime's actual namespace setup path. The cached check creates and deletes a stopped container with the same user, mount, network, PID, IPC and UTS namespaces as a real step; it starts no command. This applies to every ecosystem using isolated dependency preparation, including npm.

If setup is refused, Oyzu stops with NEEDS_USER_NAMESPACES (exit status 3). It reads host settings without changing them and names kernel.apparmor_restrict_unprivileged_userns=1 only for an EPERM / Operation not permitted setup error when that setting is enabled. Other causes include hybrid cgroups or a possible host/seccomp restriction. If the probe times out, the cause instead says that crun did not finish namespace setup within 30 seconds; a timeout does not establish an AppArmor refusal.

A later unshare/clone permission failure reported in crun's own setup log keeps the same reason and exit status. A runtime executable that cannot be launched keeps its launch error; EPERM alone does not establish a namespace refusal. A command that starts inside the sandbox and exits nonzero remains an ordinary build failure (exit 1). Oyzu never runs the refused step without its sandbox.

Inside a container (a CI job container, for example), the outer runtime must also leave /proc unmasked, because the kernel refuses a fresh /proc mount while parts of the outer one are covered, and its seccomp profile must allow unshare, clone, mount, umount2, pivot_root and sethostname without capabilities. Podman's and Docker's default profiles allow sethostname only with CAP_SYS_ADMIN, so a step under them fails with sethostname: Operation not permitted.

{"code":"NEEDS_USER_NAMESPACES","error":"NEEDS_USER_NAMESPACES: the daemonless sandbox (crun) cannot run on this host: cgroups are mounted in hybrid mode, which crun does not support; the refused step was not run","exitCode":3,"nextStep":"Run on a Linux executor that allows unprivileged user namespaces and has crun, or on one with a Docker daemon.","reason":"NEEDS_USER_NAMESPACES"}

Building a slice of a split run​

You can split a build into jobs that follow the target graph, each reusing what earlier jobs built. Each job builds a slice: the targets you name. Every other target it needs must come from a cache; it is never built.

oyzu build --slice --handoff oci://registry.example.com/acme/web/ci web
InputMeaning

--sliceBuild only the named targets (at least one). Every other target they need is looked up in the local cache and remote caches. A missing result fails with UPSTREAM_NOT_CACHED. Slices use the container executor. With --plan it prints the isolated preview of the slice.
--slice-plan <target-id>Repeat once for every concrete ID in the original preview, including targets built in other slices. Pass the same set to every slice and retry. It lets a miss report whether the producer was in the original plan (inPlan).
--handoff <oci-url>An OCI repository (oci://host/path, the same form as cache.remote).   • Plugin-built targets are handed off like any other: their results go to the --handoff repository, and their keys bind the plugin identity (action cache). For a development binding, cache.ciRemote and cache.remote are not read or written, so pass --handoff (or share one local cache) for a later slice to find its results. A plugin package's results also go to those shared remotes.

  • --slice can't be combined with --remote, --affected, --check, --no-cache or --verify-contract.
  • It needs an active action cache when any upstream target isn't named. With cache.local = false, naming every target lets the slice run without reuse.
  • With --no-docker, the same Docker check as an ordinary build applies.
  • A slice builds the optimized profile, because its results leave the machine.
  • Every upstream target's dependencies are still prepared, because its cache keys include them.

Slices don't change cache keys. Per-target slices of a commit produce the same keys and artifact digests as one whole build. A producer that built something different shows up as a miss, never as a wrong reuse. A handoff hit is verified like any remote cache hit.

Native execution​

Executor readiness​

Before compiling, a native Rust build runs a small Cargo compile-and-link check. It uses your Cargo linker settings and Rust flags, and asks for coverage instrumentation when tests are selected. Its temporary files are removed afterward.

  • A failure reports EXECUTOR_PREREQUISITE_UNAVAILABLE with the cause. Install or fix the toolchain, linker or SDK and rerun. Oyzu doesn't install OS components.
  • oyzu run runs the same check before a Rust task that compiles or links (cargo build, test, install, check, clippy, doc, run, rustc). Tasks like cargo fetch skip it.
  • Without a linker, the task fails in under a second with guidance. For windows-gnullvm, the guidance is to put LLVM-MinGW's bin folder on PATH.
  • Ready means the check passed. It doesn't check every library that dependency build scripts need.
  • oyzu pin and discovery don't run this check; they report availability as not checked.

Which stages run​

  • A plain local build runs compilation and checks set to required.
  • --full, the pr, ci and release contexts, or the CI profile also run tests (with JUnit, coverage and doctests), Clippy and a read-only format check, except checks set to off. See check levels.
  • Required checks, hooks and task prerequisites always run. Binaries are collected only after the selected stages succeed.
  • oyzu run test, oyzu run lint and oyzu run format-check run those tasks on their own.
  • Replacing the native build task isn't supported yet and is refused with a message.

Quality stages need their tools: rustfmt, Clippy, and for tests nextest, cargo-llvm-cov and the compiler's LLVM tools and profiler runtime. With a pinned Rust, the build installs nextest and cargo-llvm-cov automatically when tests are selected. See Rust test reports.

On Windows, test coverage needs MSVC or windows-gnullvm (LLVM-MinGW UCRT). The windows-gnu toolchain lacks profiler_builtins, so coverage fails there.

The native path builds the development profile unless the build is optimized: --optimized, build.optimized = true, or a build whose artifacts leave the machine (a slice, a shared remote cache write, a packaging target, the release context). Optimized Rust builds run cargo build --release. Tests keep Cargo's test profile. See optimized builds.

Development and optimized artifacts use separate cache entries. An optimized result never satisfies a development build. Shared-cache writers for profile-dependent builders (Rust and .NET) also compile and publish the development stage when their selected output is optimized. The reader's default stays development; --optimized selects the separate optimized compile entry. Both stages use the same preparation. Rust uses host-native stages; .NET uses captured Debug and Release stages. Builders whose commands do not differ by profile keep one entry. Tool-environment and computation-setting differences can still prevent reuse; see native action caching.

Native Rust versions​

Native Rust artifacts keep their inferred snapshot version. Their native compiled version depends on the build's use:

  • Plain local development, including remote-cache readers: compilation keeps the declared Cargo versions. The version record includes compiledVersion beside the inferred artifact version; CARGO_PKG_VERSION is the declared version. A hit on compile-development can supply the exported binary directly.
  • Full, CI, optimized, handed-off, shared-cache writer, packaged and release builds: a separate final Cargo stage projects inferred versions and produces the exported binary. Its actual CARGO_PKG_VERSION matches the artifact version. Explicit tag/history strategies also retain this final projection.

Compile-stage keys bind declared versions, and final-stage keys bind the inferred version map and projected manifests/lock. Development results cannot satisfy that final stage or packaging, publication and release requirements: those consumers reject a compiledVersion marker with VERSION_STAMP_REQUIRED. Rebuild with --full or --optimized before packaging or publishing.

The inferred OYZU_VERSION default still reaches compile commands and remains keyed, including on development readers. Stamp-only changes can therefore still miss the compile cache; no alternate environment default is supplied. Explicit environment overrides stay keyed too.

Versions are written only into private source copies; your manifests and lock stay unchanged. Stage restores include indexed binaries, but do not transfer Cargo compiler state. A full build after a development build may recompile workspace crates because final projection changes their Cargo package versions. See version inference.

Final compilation temporarily applies inferred manifests and the lock, checks their frozen identities around Cargo, then restores and revalidates the declared controls. Subsequent tests and quality checks use their exact declared-control guards, including when a hook makes stages share a workspace. The exported binary keeps its inferred native version; a guard failure is never suppressed by cleanup.

Automatic tool installation​

Before running builder commands, a native build installs any missing tool from your pins into the shared user store. It uses the same download, checksum and policy checks as oyzu install.

  • A build never changes pinned versions. Run oyzu pin for missing or stale entries.
  • --offline forbids downloads and needs the installers' cached inputs.
  • An installation error stops the build before compiling.
  • A denied or damaged tool is never replaced with an unverified one from PATH.
  • System linkers and SDKs are not installed. See helper installation.

Native dependency preparation​

The Rust builder first tries Cargo metadata offline. If something is missing and the build is online, it runs cargo fetch --locked with live output, then continues offline.

  • Cargo handles downloads, checksums and its own cache using your Cargo configuration, credentials and network settings. Oyzu doesn't rewrite Cargo.lock.
  • Compilation always runs offline.
  • --offline never fetches. It reports missing inputs and suggests an online build or a manifest fix.
  • Failures keep a category and recovery hint even when details that might contain credentials are withheld.

Image workers and BuildKit supervision​

A native build can include docker/image targets, which run in a BuildKit worker (see image workers). Oyzu watches both the docker exec client and the worker:

CodeMeaning
BUILDKIT_BUILDCTL_FAILEDThe client exited with a nonzero status.
BUILDKIT_WORKER_UNAVAILABLEThe worker stopped, was killed for running out of memory, or stopped answering.
  • The container and daemon are checked every five seconds. A stopped or OOM-killed container fails at once; probe failures need three in a row.
  • Diagnostics keep the buildctl exit code, the container exit and the memory limit. Exit 137 alone is reported as a possible OOM or external kill.
  • Restore the worker or give it more memory, then retry. Failed actions publish no artifacts.

Native compiler cache retention​

Captured Rust builds can read a compiler-state seed from cache.ciRemote. The seed binds the locked compiler archive, Cargo lockfile, target triple, compiler-visible workspace path and CARGO_HOME, together with the selected command, tool archives and environment. The captured executor already uses /workspace and /scratch/cargo/home; a different checkout path on the host therefore does not change those in-sandbox paths. Host-native builds do not consume these seeds: their compiler-visible paths vary by checkout.

A seed restores only into empty compiler state. Existing state is never replaced. Missing, mismatched, redirected, damaged or unavailable seeds leave Cargo to build normally. Successful restoration reports “compiler state restored from the team cache”. Fingerprints and dep-info are not rewritten. Incomplete native read information also binds the full source and preparation identity; changed inputs then build cold. Source modification times are retained only after comparing contents; changed inputs are newer than the restored compiler work.

Seed publication is disabled for all builds, including CI and pool jobs with write credentials. Enabling a trusted producer is separate work; this client only consumes seeds. See compiler-state seeds for the trust boundary and limits.

Native Rust builds keep Cargo's compiler state under .oyzu/native/rust/<host>/ in your project, so repeated builds stay incremental. Oyzu keeps Cargo.toml and Cargo.lock modification times unchanged when their contents didn't change, so Cargo doesn't rebuild for nothing. This also applies with --no-cache, which turns off Oyzu's action cache but keeps compiler caches.

The experimental Linux compiler-output tier can reuse eligible already non-incremental workspace libraries through the existing action cache. It preserves Cargo's native incremental choices and keeps fingerprints/dep-info local. Unsupported inputs, configuration, diagnostics and path-sensitive invocations execute normally. Logical debug/metadata paths and the admitted creation mask are part of that compiler contract; this tier does not make opaque Cargo state portable or establish successful tests/reports.

Cargo's integration-test scratch (CARGO_TARGET_TMPDIR) is disposable. Before measuring retained caches at preparation and finalization, Oyzu removes tmp/ and <target-triple>/tmp/ from each Cargo target directory, including the coverage target. Installed tool symlinks inside that scratch are removed without following them. Symlinks or redirected directories in retained compiler state are still refused; a redirected scratch root or ancestor is also refused. Coverage scratch includes tests/coverage-target/tmp/ and tests/coverage-target/<target-triple>/tmp/. Preparation also discards scratch left by earlier builds, including builds run with an older engine that retained it; links inside that scratch recover automatically before the first size measurement. Cleanup runs even after a failed test, so links left inside disposable scratch do not block the next build. It does not relocate Cargo's scratch while tests are running; peak scratch usage still counts toward build-time disk needs. If scratch cleanup fails or its root/ancestor is redirected, the error names the exact scratch path, preserves the cause and gives a command to move the validated compiler cache aside. Stop other builds for the project and ensure the .quarantine destination does not exist before running that command, then retry oyzu build. This rebuilds compiler state without following scratch links or deleting their destinations. Correct permissions first if the move itself fails. Quarantined data remains on disk until you remove it safely; it is no longer part of the retained cache budget.

The cache budget​

After each build, including a fail-fast test failure, Oyzu trims those compiler caches to a size budget. Native cleanup commands share a 60-second budget for that retention pass, with bounded output and process-tree cleanup. The original build failure remains recorded through native build finalization. User cancellation stops cleanup before scratch removal as well as before native commands; a cleanup failure includes the cleaner's exit status and bounded standard output/error, without discarding collected artifacts and reports.

Configure the retained size with:

How cleanup works​

When the caches are over budget:

  1. Oyzu runs cargo clean --workspace --offline on them, keeping compiled registry dependencies if that is enough.
  2. If still over budget, it removes whole cache folders with cargo clean, in this order: an old separate doctest target, the coverage target, the build target.

Under budget, compiler state is kept; test scratch is still removed. Oyzu adds the standard CACHEDIR.TAG file before asking Cargo to clean a cache folder, because Cargo won't clean a folder without one.

A budget smaller than your working set saves disk space but can cause a full recompile on every build.

Limits of the budget​

  • It limits what is kept after a build, not peak disk use. A crash or full disk can leave oversized caches until the next build.
  • If cleanup fails at the end of a build, you get NATIVE_CACHE_RETENTION_FAILED but the build result stands. The next build retries before it starts, and a failure there stops it.
  • Symlinked or redirected cache folders (including Windows reparse points) are refused. Use a normal folder.
  • Only the Rust caches under .oyzu/native count. Installed tools, downloads, .oyzu/bin, dist, Cargo's own target folder and oyzu run tasks aren't touched.

Outputs and incremental state​

Native actions keep independently writable source copies with retained native state. Unchanged builds preserve the paths and directory timestamps Cargo watches; action-cache hits leave these copies intact. A real source edit refreshes them before execution. Removing .oyzu/native clears both compiler outputs and these private copies; subsequent builds recreate them.

Successful binaries go to dist/<target>/<platform>/ (for example dist/cli/windows/x86_64/; see the bundle layout) with their usual names, and are also linked at .oyzu/bin/<name>[.exe].

  • Outputs labels each binary development or optimized. Each is checked to be an executable for the host before it is collected.
  • The bundle keeps the manifest, plan, reports and action logs. They record that the build ran on the host, the source it saw and the tools it used.
  • Rust state lives in .oyzu/native/rust/<host>/: target for compilation and tests for test and coverage builds. A build limited to some packages with with.packages keeps its own state in a p-<id> folder inside it. Cargo decides what to rebuild.
  • The previous bundle's artifacts move to history on every build, successful or not. Other files in dist are left alone. See bundle finalization and recovery.
  • A file in dist that no bundle owns causes a collision error instead of being overwritten.
  • A failed build exits nonzero and leaves .oyzu/bin at the last successful build.
  • On Windows, the previous executable is renamed to the hidden backup .NAME.previous before the new one takes its place, so a running program isn't overwritten. At most one backup is kept: the next build replaces it. If that backup is itself still running, the build fails with an error asking you to close those oyzu processes.

The source Oyzu records is hashed from your working tree with the usual source exclusions. Native builds read your checkout directly; they don't freeze a copy.

What a native build prints​

Output starts with Building <folder> (or Planning for --plan), the platform, local or isolated execution, and fast or full mode. Then it follows Preflight → Build → summary. Preflight covers configuration, discovery, tool preparation, dependency metadata and planning.

  • Each tool row shows the tool, the requested version and its status: downloaded and installed, then verified, or reused and verified.
  • External SDKs and linkers show as not checked until native tools run.
  • Formatting, lint and test tools are hidden in fast builds unless those stages run.
  • Press p for more environment and source detail, and d for detailed logs on small terminals.
  • Running tools and subprocesses show their last eight output lines on capable terminals. Success collapses them; failure keeps them.

Terminal behavior:

  • auto and plain output modes print a linear log that keeps your scrollback. --output interactive opens a dashboard instead.
  • ui.color=auto colors terminal output unless NO_COLOR is set; always also colors redirected output; never turns color off.
  • A terminal counts as capable when TERM isn't dumb and, on Windows, when the console accepts virtual terminal sequences.
  • --json emits a structured heading event on stderr; -q hides it. See build logging.

Using a separate tool store​

oyzu build --store <path> uses the same store as oyzu install --store <path>. The default is the shared user store.

  • A relative path resolves against the current folder (or --root).
  • The store is used for native installs and container tool preparation. It never changes pins, checks or image policy.
  • A missing or broken tool in that store doesn't fall back to another store.
  • Use the same --store on install, build and tool inspection commands, especially with --offline.

Limits​

  • Native execution has your user account's access. Cargo's offline mode doesn't stop a build script from using the network.
  • A local build, even with --isolated, can't grant production publication rights.
  • --require-release refuses the build unless it is an authenticated release-candidate or release tag build; ordinary local tags and --context release don't count. See release staging.
  • Native builds support Windows and Linux x86-64, with builder-specific limits. Intel macOS supports the Zig native path; other macOS builders are unsupported.

Building oyzu from source​

These notes are for building the oyzu CLI itself from a source checkout.

Build with cargo build --locked --release --bins, then copy target/release/oyzu[.exe] and target/release/oyzu-shim[.exe] together into a folder on your PATH outside the checkout. Check the build succeeded before copying, and keep a backup of the previous version.

Run oyzu reshim from that installed pair after replacing it. Windows tool launchers delegate to the frontend named in their adjacent .oyzu-frontend pointer, falling back to a sibling oyzu.exe when the pointer is absent. Unix tool shims remain symbolic links to oyzu; running oyzu-shim directly refuses with "launcher template, not a tool command". Both binaries support standalone --licenses output for their own dependencies.

On Windows, updating your user PATH doesn't change terminals that are already open. Update the current PowerShell session:

$fallbackBin = 'C:\path\to\oyzu-bootstrap\bin'
$env:Path = "$fallbackBin;$env:Path"
oyzu --version

The repository adds ./.oyzu/bin to PATH through [env] _.path. After shell activation (in PowerShell 7.5+: oyzu activate pwsh | Out-String | Invoke-Expression), oyzu build puts the freshly built CLI first on your PATH inside the project.

The Windows task flow uses a pinned MSVC toolchain, which needs Visual Studio Build Tools (the C++ workload) installed first. Then run oyzu pin, oyzu install and oyzu run install. If an older oyzu.lock fails with TOOL_LOCK_AMBIGUOUS, delete it and run oyzu pin and oyzu install again. Keep machine-specific linker and CMake paths in an ignored oyzu.local.toml under [env].

Refreshing the oyzu on your PATH​

oyzu run bootstrap installs the newest verified release as the oyzu you type, so oyzu self keeps it up to date from then on. With --source it builds the CLI from the checkout and installs that instead. Run it from the checkout. The default needs a release with an executable for your platform; elsewhere use --source:

oyzu run bootstrap                              # newest stable release
oyzu run bootstrap -- --channel beta            # follow beta (or nightly) instead
oyzu run bootstrap -- --dest ~/bin              # install into this folder instead
oyzu run bootstrap -- --source                  # development build of this checkout
oyzu run bootstrap -- --source --optimized      # optimized build of this checkout
oyzu run bootstrap -- --source --linux <file>   # use this Linux oyzu as the engine for --isolated

By default:

  • It installs into the folder holding the first oyzu on your PATH outside the checkout (a link is followed to the real folder), or --dest. With no such oyzu, it uses the install scripts' folder (~/.oyzu/bin, or %LOCALAPPDATA%\Oyzu\bin on Windows), and the install script there runs oyzu shell install so the folder stays first on PATH. Open a new terminal afterwards.
  • If the oyzu already there has oyzu self, it replaces itself: oyzu self update when it was installed from a release, otherwise oyzu self channel stable (or the --channel you give). That verifies the release's digest, provenance and publication, keeps the old executable for oyzu self rollback, sets up the Linux engine for isolated builds on Windows and macOS, and records the channel that automatic updates follow. An oyzu pinned to a version stays pinned unless you pass --channel. Otherwise, such as an oyzu from before oyzu self existed, it moves the old oyzu and oyzu-shim aside as NAME.previous and runs this checkout's install script into the folder. If that fails, for example because no release has an executable for your platform yet, it puts the old pair back and stops; oyzu self likewise changes nothing when it fails.
  • It moves an oyzu and oyzu-shim that an earlier source bootstrap left in the checkout's .oyzu/bin aside as NAME.previous, because that folder comes first on PATH inside the checkout and would hide the release.
  • On Linux, oyzu build in the checkout uses the published rust/app and node/app plugin releases oyzu.lock selects; tooling/bootstrap-oyzu.sh --locked-plugins-only installs them into the plugin store the first time (it needs Python). If that fails, the bootstrap warns and carries on, and oyzu build here fails until a later run installs them. macOS and Windows have no published plugin payload yet, so there it builds the two plugins from the checkout as --source does (first bullet below); bind them in your user configuration if the bootstrap prints the commands to.
  • It then runs oyzu install --frozen in the checkout and prints the installed path and oyzu --version. Locked plugin selections change only with oyzu plugins update.

With --source:

  • It checks the project-local CLI and other oyzu executables on PATH against the checkout's Rust and Node plugin manifests. The running engine's compiled capabilities decide compatibility, not its version label. It keeps the chosen executable's absolute path for plugin preparation and the CLI build, so an older project-local executable cannot shadow a compatible installed one.
  • If no candidate supports that check or the required capabilities, it asks an existing CLI to run cargo build --locked through Oyzu's managed execution contract, including configured Cargo session admission, to build a temporary seed CLI/shim. It checks the seed before selecting it; no direct or host Cargo fallback is used. The existing CLI must be able to resolve the checkout's Rust pin; otherwise bootstrap stops with the tool-selection cause. A failed seed build leaves installed executables unchanged. Seed executables are removed when bootstrap exits normally; Cargo's incremental output remains in CARGO_TARGET_DIR or the checkout's target directory for reuse.
  • It first builds the rust/app and node/app plugins from the checkout into .oyzu/bin, since oyzu build cli needs them. It also cross-compiles the Linux rust/app plugin for your machine's architecture and packs it with the host one as .oyzu/bin/oyzu-plugin-rust.tar.gz, a package archive binding, so oyzu build cli --isolated works from the checkout. If neither your user nor your machine configuration binds both plugins, it creates (or reuses) the checkout's own bootstrap file, .oyzu/bootstrap/config.toml, and uses it for this run only, as tooling/bootstrap-oyzu.sh does (see Repository source bootstrap). That file binds rust/app to the package. A file an earlier run wrote with the rust/app executable is rewritten to bind the package; a file you changed is never replaced. If your user configuration file binds rust/app to exactly this checkout's .oyzu/bin/oyzu-plugin-rust executable, the bootstrap changes that one entry to the package beside it, which holds the same plugin plus the Linux member --isolated needs, and leaves the rest of the file as it is. Any other binding in your own configuration is left alone, and the bootstrap prints how to bind rust/app to the package. When it uses the checkout's bootstrap file, it then prints how to make other terminals see the bindings: set OYZU_USER_CONFIG to that file, or bind both plugins with oyzu config set --global plugins.development.<reference> <path>. If you have a user configuration file that binds neither plugin, it stops and prints those two commands.
  • It runs oyzu build cli, then installs oyzu and oyzu-shim together into the checkout's .oyzu/bin and into the folder holding the first oyzu on your PATH outside the checkout (a link is followed to the real folder).
  • With no such oyzu, it installs into the install script's folder (~/.oyzu/bin, or %LOCALAPPDATA%\Oyzu\bin on Windows) and runs oyzu shell install so the folder stays first on PATH. Open a new terminal afterwards.
  • Each replaced file is renamed to NAME.previous first, which works while the old oyzu is running; one backup is kept. If the replacement fails, the old file is put back.
  • It then runs oyzu install --frozen in the checkout and prints the installed path and oyzu --version. A source build is a local build and never updates automatically. oyzu self update returns it to the recorded channel's newest release when a channel is recorded; otherwise, start with oyzu self channel stable. You can also run oyzu run bootstrap without --source to go back to a release.
  • Isolated builds run a Linux oyzu built from the same source. On Linux the new oyzu is its own. On Windows and macOS, the new oyzu then cross-compiles it for your machine's architecture (oyzu build cli --platform linux/<arch>, see cross-compiling on this host) and runs oyzu engine install --linux with it. To use Linux executables you built yourself instead, pass each with --linux <file> (repeat it for each architecture). If the Linux build fails, the bootstrap says that --isolated has no Linux engine and still installs oyzu.

Either way it needs Node.js on PATH. If your installed oyzu is too old to read this repository's configuration (CONFIG_INVALID_VALUE), run tooling/bootstrap-oyzu.sh (Git Bash on Windows), which downloads the newest release into .oyzu/bin, and then .oyzu/bin/oyzu run bootstrap.

Updating this repository's bootstrap with Cargo​

Rust projects get an install task automatically. To update your installed CLI from the checkout:

oyzu run install -- --bins --force --root "$env:LOCALAPPDATA/Oyzu/bootstrap"
  • This runs cargo install, not the full build checks. It builds the release profile; add --debug after -- for a development build.
  • CARGO_INSTALL_ROOT also sets the destination.
  • On Windows with an explicit root, Oyzu installs into a staging folder first, so your current CLI keeps working while Cargo compiles. Only after Cargo succeeds are the files replaced, keeping one .NAME.previous backup each.
  • Cancelling or a failed install leaves the installed CLI unchanged. A killed process may leave a .oyzu-install-* staging folder; don't remove one that belongs to a running install.
  • Files are replaced one at a time, not atomically. If replacement fails, check the named file and its backup, close programs still using the old copy, and retry.

If your installed CLI is too old to run this, use Cargo directly with the provisioned toolchain:

cargo install --path . --bins --locked --force --root "$env:LOCALAPPDATA/Oyzu/bootstrap"

oyzu run fetch downloads Cargo dependencies, oyzu run install installs project executables, and oyzu install installs development tools.

Python test-file units​

Captured pip/pytest package tests use native collection to define one test unit per Python test file. Collection follows pytest's configured paths and plugins; Oyzu's source inventory is only a conservative candidate list. Undeclared native units run without reuse. Preparing a unit exposes only its admitted source and runtime artifacts, and preserves the existing refusal of unsafe links.

With coverage.py available in the project environment and enforced runtime-read bounds, a changed unit can reuse individual passing cases. See case selection for inputs, release behavior, reports and limits. A native host run has no enforced read boundary and runs the whole changed unit.
