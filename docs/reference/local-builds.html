Native local builds (in development)

CLI reference

Published from the canonical docs/reference/local-builds.md file. Features marked experimental remain experimental; check support limitations before relying on them.

The current implementation connects host-native Cargo, Go applications, npm dist applications and pip wheel builds to the local development proposal. Qualification is recorded by scenario in the tool user-flow record. Do not interpret the commands below as completed qualification of every platform or build mode.

The host coordinator also admits existing captured docker/image workers, with per-target placement shown by --plan. See image workers and qualification limits. Host processes remain unrestricted; worker enforcement does not extend to the entire graph.

BuildKit actions supervise both the docker exec client and the worker. A nonzero client exit reports BUILDKIT_BUILDCTL_FAILED; a stopped, OOM-killed or unreachable worker reports BUILDKIT_WORKER_UNAVAILABLE. Container state and daemon probes run every five seconds with individual two-second deadlines; the final check runs immediately when the client exits. An observed stopped or OOM-killed container fails immediately. Failed inspection or daemon probes need three consecutive failures; a successful check resets the count. A dead daemon therefore does not wait for the action timeout. Diagnostics retain the buildctl exit code/signal when available, container exit and memory limit. State.OOMKilled confirms OOM; exit 137 alone is reported as possible OOM or external SIGKILL. If the Docker client is still stuck, its exit is explicitly unavailable. Cleanup has a separate five-second bound. Retry after restoring the worker or providing enough memory; failed actions do not publish artifacts.

Selection and prerequisites​

Requirement discovery and pinning​

oyzu pin --dry-run previews requirements and lock changes without installing native tools or changing project files. For a new project or a version-1 resolution lock it resolves compiler metadata; --offline requires matching cached metadata. oyzu pin publishes complete resolutions, with conflicts and incomplete inputs reported as failures. See tool planning.

All project locks use one version-1 contract. pin resolves requirements whether or not installation records already exist, and preserves those records when publishing resolutions. Incomplete resolution leaves the lock unchanged. Build preflight installs missing supported pinned tools; native host prerequisites still require external provisioning. Pinning itself does not install tools.

When a selected builder admits automatic tool resolution and the project has no oyzu.lock, native build preflight resolves its requirements and publishes the lock without editing authored TOML. It captures the published lock before installing and activating the exact selection for native actions. This uses the normal acquisition verification and installation leases; an ambient compiler is not required for supported managed tool requirements. Existing locks remain frozen: incompatible or missing selections require an explicit pin update rather than silently resolving during execution. Offline preparation requires the existing metadata, archive or installation needed by the selected provider. The empty-store qualification and current platform limits are recorded in the fresh-checkout record.

The initial adapter covers Rust: rust-toolchain.toml or the legacy rust-toolchain file, Cargo package/workspace rust-version minimums, declared components/targets/profile, and the tools/components required by the existing native build/test/lint/format stages. Every toolchain-file form rustup accepts is read; see Rust toolchain files. A file without channel keeps its components and uses the configured or default Rust; a local path toolchain fails resolution unless oyzu.toml selects a release. Both toolchain filenames together are an error. In the discovery inventory, no toolchain declaration means Rust is reported without a selected version; a build then locks the greatest stable release (pinning is optional). That inventory reports effective Oyzu tool settings separately without claiming resolution. The resolver resolves those inputs through the tool-planning contract described above. Each fact includes its source; repeated facts retain their sources.

System linker/SDK requirements are explicit. Windows discovery uses the declared toolchain channel: windows-gnullvm identifies LLVM-MinGW UCRT, Clang linking and a Rust profiler runtime; windows-msvc identifies Microsoft Build Tools and the Windows SDK. A windows-gnu declaration explicitly calls for a coverage-capable alternative. An unqualified channel such as 1.95.0 lists GNU/LLVM and supported MSVC as alternatives, rather than assuming the user's rustup default. This static discovery does not run rustup, inspect PATH or install Windows components. Dependency build-script requirements, compiler/profile compatibility and inherited parent-directory toolchain files are not inferred in this slice. Node requirements are also resolved through the shared tool contract. For the native pip wheel path, CPython is resolved from requires-python or .python-version and installed from Python Build Standalone (details); uv, Poetry and legacy Python tools are not provisioned. Other unsupported requirements remain explicit. The command works offline in standalone mode; existing configuration loading and managed policy rules still apply. Pinning currently requires the workspace root. On 2026-10-03 the compiled discovery implementation inspected this checkout's requirements with PATH empty. Two integration tests passed for toolchain-free inspection, unchanged lock bytes and conflicting manifest rejection. Other hosts are unverified.

Discovery evidence is available in pin JSON alongside the resolution preview. It is not installed-tool evidence. Unsupported prerelease lock versions are rejected; no legacy decoder or automatic migration is provided. Existing tool stores are left intact. See the lock contract.

Native execution​

Host cache paths and source projections​

Native Rust compilation retains compiler state under the original project's .oyzu/native/rust/<host>/, while source compilation runs in a private target projection. The Rust builder explicitly identifies its absolute cache and inventory arguments as host paths, including the separate test cache when quality stages are selected. These exact arguments retain their host locations even when a project is rooted under /workspace/, /out/ or /oyzu/. Captured workspace, output and runtime paths still translate into the source projection, report output and engine runtime. Path declarations do not relax native cache, binary inventory or artifact containment checks.

Isolated execution reuses completed read-only tool restorations (Docker volumes or daemonless directories) under the existing restoration locks. A completed restoration is trusted as an installed tool, so reuse does not hash its source archive again. A new restoration verifies the archive before worker launch/extraction; incomplete restoration is never a hit. This does not change archive acquisition checks or current tool/catalog admission.

Native Rust builds now project inferred snapshot package versions into the private manifests using the same resolver as captured builds. Each native member keeps its own package scope and tag baseline, augmented by the declared target prerequisite closure. Cargo reconciles only private workspace versions offline against the existing lock, preserving locked external packages. Compiled CARGO_PKG_VERSION, artifact version metadata and plan/manifest decisions use the projected version; executable filenames retain their native names. The original manifests and Cargo/tool locks remain unchanged. Conflicts and missing offline dependencies fail preparation with recovery guidance. This new Rust projection passes the Windows three-application pair with and without a declared producer edge, including native reports and independent compiled-version execution. This does not qualify other hosts or all native profiles; see version inference.

This fixes issue #384, where an absolute host cache was mistaken for a captured /workspace/ mount and compilation failed with COMMAND_FAILED: No such file or directory after successful preparation. Retry the same native build with the corrected CLI; no project configuration or cache migration is required.

python tooling/test-native-host-paths.py --cli <compiled-oyzu> --parent <writable-directory> checks two native binaries, repeat compilation, bundle inspection and unchanged source/configuration files. Use a parent under /workspace/ to exercise the original collision; --full additionally checks native quality-stage cache paths with provisioned test/coverage tools. This does not qualify captured builds or other operating systems.

Executor readiness​

Native Rust builds now check the selected environment with a temporary, dependency-free Cargo compile-and-link probe before compiling project code. The probe honors Cargo linker configuration and Rust flags; selected test stages also request coverage instrumentation. Success verifies this basic capability, not every library needed by dependency build scripts. Temporary probe files are removed after success or failure. No OS components are installed.

oyzu run performs the same probe before starting a Rust task that compiles or links (cargo build, test, install, check, clippy, doc, run, rustc), once per target and after tool preparation. Tasks that compile nothing, such as cargo fetch, skip it. Without a linker the task fails in under a second with the guidance below instead of a raw compiler error; a windows-gnullvm toolchain is told to put LLVM-MinGW's bin directory on PATH. Oyzu does not install LLVM-MinGW.

A failure reports EXECUTOR_PREREQUISITE_UNAVAILABLE with the native cause and external provisioning guidance. Correct the selected toolchain/linker/SDK and rerun. Discovery and pinning remain static and report availability as not checked; only actual preflight executes the probe. Managed tools and executor prerequisites are separate categories in the inventory. Compile-only inventory omits automatic quality-stage helpers; explicitly declared components remain requirements.

This check currently covers native Rust execution. It does not introduce remote executor probes, arbitrary system-package detection or OS provisioning. A ready host capability is not a claim of hermeticity or publication eligibility.

Plain oyzu build selects native development execution when every selected target is native-eligible (Rust, Go, Gradle, Maven, npm node/app and pip Python, plus admitted image workers). Other builder/workspace shapes retain their existing captured behavior. oyzu build --isolated explicitly uses the existing captured container executor; --image also retains that path. --affected computes its selection first and then follows the same native-eligibility rules as a plain build, falling back to the captured path only where a plain build would. A failed native or isolated build never retries through another executor. CI detection does not change this selection.

Plain local builds need pinned Rust/Cargo and provisioned native compilation prerequisites. Preflight verifies or installs the pinned tools before native dependency preparation. Declared platform relationships and target selection are validated before automatic pinning acquires tool metadata or publishes a lock. Invalid or ambiguous matrix relationships therefore fail without starting tool provisioning. Quality stages additionally need their tools: rustfmt for formatting, Clippy for linting, and nextest, cargo-llvm-cov and the compiler's LLVM tools/profiler runtime for tests with coverage. The Rust test prerequisites describe report tooling. Native dependency preparation first checks the Cargo cache and acquires missing locked inputs when online, as described below. The existing historical Windows coverage qualification includes the MSVC toolchain/linker/SDK. The locally provisioned windows-gnu 1.95 compiler failed a coverage probe with missing profiler_builtins on 2026-10-03. A separate Rust 1.95 x86_64-pc-windows-gnullvm experiment on 2026-10-04 passed two tiny-project tests through cargo-llvm-cov 0.9.1 and nextest 0.9.146, producing a Cobertura report with five of six lines covered using LLVM-MinGW UCRT 20260616 and Clang linking. The compiled CLI also passed oyzu run test on that probe; oyzu inspect dist confirmed both tests and the same collected coverage counts. This required no Microsoft Build Tools installation. It proves direct test and coverage execution, not the complete Oyzu self-build or automatic tool provisioning. The full Oyzu checkout also passed cargo check --locked --offline --bin oyzu with GNU/LLVM, Clang and native CMake/Ninja; final executable linking was not tested by that check. Coverage remains required when the test/coverage stage is selected; plain local compilation does not select it automatically.

The native path builds development-profile binaries unless the build is optimized: oyzu build --optimized, build.optimized = true, or a build whose artifacts leave the machine (a slice, a shared remote cache write, a packaging target, the release context) runs cargo build --release instead; see optimized builds. Tests keep Cargo's test profile. Plain local oyzu build automatically schedules compilation and any check at level required. oyzu build --full, the pr, ci and release contexts or the CI profile also schedule test/JUnit/coverage/doctest integration, Clippy and read-only formatting checks, except those whose check level is off. Required checks, hooks and task prerequisites remain enforced in fast mode. Binaries are collected only after the selected stages succeed. oyzu run test, oyzu run lint and oyzu run format-check remain explicit task entry points. Native build overrides are currently rejected with an explicit diagnostic. Ordinary hooks and task prerequisites use the shared task graph. Required configuration checks remain enforced; unsupported managed host execution fails before native preparation.

This repository sets Cargo's development and test profiles to debug = 0, omitting generated debug information while retaining debug assertions. The development profile optimizes the direct SHA-256 dependency (sha2 0.10.9) at level 3; the test profile inherits that package override. Oyzu's own code and other dependencies retain their existing optimization settings. This reduces the CPU cost of full tool-payload and evidence hashing without caching or skipping verification. Dependency upgrades must keep this version-specific override aligned with the direct sha2 dependency. Release settings are unchanged. Windows worker tests relaunch their own test executable; embedded debug information previously grew that executable beyond the worker's 512 MiB image limit and caused TOOL_WORKER_IMAGE_INVALID before launch. Source-level debugger information is unavailable in these default builds. Profile overrides that restore debug information can reintroduce this failure; rebuild with the repository defaults to recover. The image limit, integrity checks, test/report gates and scenario timeouts remain unchanged. Other projects retain their own native Cargo profile settings.

--all-platforms requests the declared matrix through the existing captured executor; it requires its provisioned Docker environment. Native execution cross-compiles only where a builder has a native cross toolchain (see platforms and executors) and never confers production publication eligibility. Native development output is a runnable binary, not a versioned source distribution; use the isolated path for the existing packaging contract. Its manifest record still carries the bundle's required version: the builder's own artifact version where it has one, otherwise the target's resolved version.

A consumer that declares a platform other than the host, such as a docker/image with platforms: [linux/x86_64] that materializes a Go binary on a Windows host, does not use the native path, because native producers are built for the host only. Plain oyzu build (and --plan) then selects the captured executor, which builds each producer for the platform its consumer requires, so the binary is a Linux executable. When the consumer's platform is the host's, the native path is unchanged. A pinned Go, Node or helm is restored from the lock in that captured worker (see Go, Node and Helm); any other pinned tool the worker cannot yet take from the lock is still refused there.

Platforms and executors​

Two terms stay distinct. The target platform is what an artifact is built for; the executor is where its build actions run: this host for its own platform, a native cross toolchain on this host, the container executor (--isolated, --all-platforms), or a remote pool (--remote, reported only). The executor is part of the build's identity: the manifest and plan record it on each target (oyzu.dev/platforms), and action keys bind every executor other than the host, so a cross-compiled or container result never satisfies a host build of the same platform or the reverse.

Platform names​

Every platform is written os/arch[/abi]: linux/x86_64, linux/arm64, darwin/arm64, windows/x86_64, windows/x86_64/msvc. Input also accepts the aliases amd64 (for x86_64) and aarch64 (for arm64), in build.yaml platforms, --platform and --allow-incomplete; output, records, variant IDs and dist/ directories always use the canonical form. The ABI is optional and only meaningful where an OS has several: gnu or musl on Linux, msvc, gnu or gnullvm on Windows. Without one, the builder chooses its default (see Rust). Container engines and registries keep their own spelling (linux/amd64) at that boundary only. The ABI a build resolves (Rust: musl for a Linux cross build, msvc on Windows, gnu on a Linux host) is recorded in the target's platform and its artifacts' compatibility. Published names (dist/ directories, asset names, selectors) carry an ABI only when it differs from the OS's naming default (GNU on Linux, MSVC on Windows); see release asset names. The musl default for Linux cross builds is a risk for glibc-dependent code (dlopen, NSS name lookup); declare linux/<arch>/gnu where it matters.

Declaring a platform's executor​

Without a declaration a platform takes the default route: the host for its own machine, otherwise a native cross toolchain when the builder has one (or the container executor under --isolated). A project can instead declare the executor of a platform in oyzu.toml, per target folder and, like other per-target settings, per context:

[build.executors]
"linux/arm64" = "cross-toolchain"   # always cross-compiled, never built on an arm64 host
"darwin/arm64" = "host"             # only on a macOS arm64 runner

[context.release.build.executors]
"linux/x86_64" = "container"        # releases build it in the container executor

A declared executor is the only one used for that platform, in every context: when it is unavailable here (no cross linker, the wrong host, container without --isolated, host or cross-toolchain under --isolated), the platform is not built here and Plan says why; an explicit request for it fails with PLATFORM_UNAVAILABLE before anything runs. Nothing falls back to another executor. In the release context the host platform the default selects is such a request too: a release build fails clearly instead of skipping it. So a release builds each platform exactly as its plan says, and the executor stays part of the build's identity (oyzu.dev/platforms and the action key). Plan, the preview rows (declaredExecutor) and the CI matrix entries (executor) show the declaration.

A CI matrix from the plan​

oyzu build --plan --json reports, for each selected target, a platforms record (target, the logical target; declared; declaredExecutors; one row per declared or requested platform with selected, executor, declaredExecutor, reason, refused and runner; and the platform and executor this run would use), and at the top level a matrix: one include entry per declared platform of every selected target with the runner (os as CI providers name it: linux, windows, macos; and arch) that builds it on its own host, the declared executor (else host) and the targets that declare it. The matrix does not depend on what the planning machine can build: a target declaring only darwin/arm64, planned on Linux, still gets its entry. unconstrained lists selected targets that declare no platforms. With --affected <ref> the selection, and so the matrix, holds only the affected targets and their platforms. A workflow can feed it to a matrix strategy:

jobs:
  plan:
    runs-on: ubuntu-latest
    outputs:
      matrix: ${{ steps.plan.outputs.matrix }}
    steps:
      - uses: actions/checkout@v4
      - id: plan
        run: echo "matrix=$(oyzu build --plan --json --affected origin/main | jq -c .matrix)" >> "$GITHUB_OUTPUT"
  build:
    needs: plan
    strategy:
      matrix: ${{ fromJSON(needs.plan.outputs.matrix) }}
    runs-on: ${{ matrix.runner.os == 'macos' && 'macos-15' || matrix.runner.os == 'windows' && 'windows-2025' || 'ubuntu-24.04' }}
    steps:
      - uses: actions/checkout@v4
      - run: oyzu build ${{ join(matrix.targets, ' ') }} --platform ${{ matrix.platform }}

Mapping runner to a provider's runner label (and choosing an arm64 runner) stays with the workflow. Publication then checks the declared platform set: see incomplete platform sets.

Read-only build preview​

oyzu build --plan previews the same execution-path selection as a build: local host when supported, otherwise the captured executor. --isolated, --all-platforms, named targets, profiles and --full keep their normal selection meaning. The preview itself needs neither Cargo nor Docker installed.

The preview reads configuration and native manifests, applies the shared target, matrix and task-selection rules, and shows each target's discovery decisions with their reasons, selected/skipped stages, declared task ordering and consolidated tool requirements. See discovery decisions and selectors. It does not install tools, fetch packages, execute build tools or project scripts, create a lock, open a tool store, write a source snapshot, or create/replace a build bundle. Application dependencies are acquired only by an actual build's preparation. --affected additionally hashes local source and reads the local Git baseline using Git; its existing conservative fallback rules still apply, with no network or checkout writes.

A preview is deliberately incomplete: installed-tool availability, executor capabilities, dependency cache readiness, exact commands, native-generated stages, artifact names and report bindings remain unresolved. A selected stage means configuration requests it, not that its prerequisites have passed. Dynamic target relationships may add work during real preparation. Success means the static preview was produced; it does not certify build success or publication eligibility.

Live build output shows one plan table once, before work starts: targets by stages with run, skip or - cells and one footnote per skip reason. A single target built for several platforms pivots to one row per platform; above twelve rows targets with identical stages share a counted row (-v lists every target). See Result output.

Matrix expansion (--all-platforms, --isolated) can yield targets that differ only by platform. In the live build output a single target built for several platforms is one plan table with a row per platform; the requirements table shows "all N targets" when every target shares a requirement. --json still reports every target individually. Targets whose plans differ keep their own sections.

Human output uses stage/requirement tables with semantic color on capable terminals (or CLICOLOR_FORCE=1); NO_COLOR preserves plain text. Owned styling is emitted once, after escaping project-controlled values. --json returns a version-1 build-preview record with resolved: false, selection, targets (each with a discovery map of role to selected and reason), tasks, requirements, unresolved details, effect flags and timings. It is not the executable build-plan retained by actual builds in dist/plan.json. The former captured --plan behavior that acquired dependencies is superseded; use an actual build and its retained plan for execution-level evidence. No schema version was bumped.

timings reports where the preview spent its wall-clock time, in milliseconds: totalMs and phases, in order discovery (configuration and target discovery), selection (selection, variants, task graph and requirements), source (inventorying the working tree for analysis from file metadata; no file is read until analysis asks for it), analysis (with targets, one entry per analyzed target, then finishMs for merging facts and rulesMs for the diagnostic rules) and planning (stage and task listing). source and analysis are absent when analysis is disabled or fails. Timings describe one run only and are never part of the analysis record, which stays identical between runs.

Planning a remote run​

oyzu build --remote --plan previews what oyzu build --remote would run on a platform pool, without contacting the platform or needing its settings or token. It is the same read-only preview with the pool's selection: isolated execution, full checks, and the ordinary isolated platform selection. --remote does not imply --all-platforms or introduce additional platform variants. Named targets and --affected <base> select as the remote run does; --affected compares with the merge base of <base> and HEAD. The record's execution is remote. The platform's planner runs this command with the project's pinned Oyzu on a checkout of the exact commit to learn each job's requirements before it is queued. The preview reads the working tree, so local uncommitted changes are included even though a remote run never sends them. --isolated, --all-platforms, --image, --check and --download are refused with --remote.

Every preview target carries these placement facts:

Platforms are written in the canonical form (linux/x86_64, darwin/arm64); a development-mode host target reports its routed platform (the host, or a native cross build's) that way too. The top-level matrix lists every declared platform of the selected targets with the runner that builds it. OYZU_NO_DOCKER=1 does not alter preview selection or placement facts. Plan-only requests never enable the execution guard. Remote planning needs no credentials.

Hooks always run, including hooks declaring outputs. Authored tasks need both cache = true and valid declared outputs; inputs outside their target cannot be cache scoped. Static analysis can identify native stages with unbounded outputs (omitted with --no-analysis). Secret environments and disabled local caching prevent storage. Image builders currently use source projections the action cache declines to store. sliceable describes upstream reuse, not whether a target may execute as a slice. Failed builds and runtime output-contract violations are not predictable by this read-only preview and still fail downstream reuse safely.

The top-level placement object names which facts are final and which can grow. Each target's platform, executionPlatform and needsDaemon are final, as are the tool requirements of targets whose requirement status is discovered. The selected targets, the task graph, each target's stages and the requirements of unsupported targets can grow: dynamic target relationships found during preparation can add targets, and each added target brings its own facts. The Dockerfile analysis uses the Docker builder's native assembly grammar to identify a clearly independent final stage. Unsupported syntax, stage references and ambiguous dependencies fall back to a whole-file RUN check, which can over-require but never under-require native execution.

Building without Docker​

oyzu build --no-docker, or OYZU_NO_DOCKER=1 in the environment, is for executors that have no Docker engine, such as a container or Kubernetes pool. In this mode Oyzu runs no Docker command at all. Before anything is prepared or run it works out the same preview as --plan for the build's selection; if any selected target has needsDaemon: true, the build stops with exit status 3 and nothing runs. Any other value of the variable than empty or 0 enables the mode.

oyzu build --isolated --no-docker --json
{"error":"NEEDS_DOCKER_DAEMON: cli need a Docker engine, which this executor does not provide (--no-docker); nothing was run","reason":"NEEDS_DOCKER_DAEMON","targets":["cli"],"exitCode":3}

Exit status 3 signals a placement mismatch, so a runner can tell it from a failed build (1) or a refused invocation (2) and requeue the job on a pool that has Docker. Placement normally comes from --remote --plan; this is the guard for when that plan was wrong. Node targets run in the daemonless sandbox in this mode. An admitted RUN-free Dockerfile with FROM scratch or a digest-pinned base can build in process with --isolated --no-docker; it needs no crun or user namespaces. A final stage independent of an unused earlier RUN stage can also use this path; see Docker image assembly. --full selects Dockerfile lint and format checks that still need the Docker worker, so the guard refuses that selection rather than skipping checks. Unsupported Dockerfile work such as RUN also requires Docker. Development builds of host targets run. --no-docker cannot be combined with --remote.

The daemonless sandbox​

Unchanged captured npm builds can reuse verified script-free dependency acquisition before action lookup. Current tool admission and the offline install, lifecycle scripts, hooks and report gates keep their existing rules. See acquisition reuse for invalidation, offline behavior and cache controls.

On Linux, the isolated steps of a Node target (npm, pnpm or Yarn) can run under crun, a rootless OCI runtime, instead of docker run. The step gets the same sandbox: no network, a read-only image root, no capabilities, no-new-privileges, a seccomp filter, Docker's masked and read-only /proc paths, the same mounts and the same tmpfs sizes, inside a user namespace that maps the workspace owner to itself. The image's root filesystem is unpacked once per image digest under the image cache and shared by every build on the host. The backend is not part of the action key: both backends produce the same keys and outputs, so a result cached by one serves the other.

The build.isolation setting selects the backend: auto (default) uses Docker when an engine answers and crun otherwise, docker always uses Docker, and crun uses crun for Node targets even with Docker present. --no-docker and OYZU_NO_DOCKER=1 select crun for Node targets whatever the setting says.

oyzu install downloads a pinned crun release (1.24), checks its SHA-256 and keeps it in the user data directory; OYZU_CRUN names a crun the executor already provides instead. Images come from their published, digest-pinned source, or from a local Docker engine's copy when one is running; a tag-only local image with no engine has no source and the build fails before running anything.

Before running anything, a build that selected crun checks that crun runs and that the host lets an unprivileged process create user, mount, network and PID namespaces. When it cannot, the build stops with NEEDS_USER_NAMESPACES, exit status 3 like NEEDS_DOCKER_DAEMON, naming what failed (for example kernel.apparmor_restrict_unprivileged_userns=1, a seccomp profile that blocks unshare, or cgroups mounted in hybrid mode). Oyzu never runs the step without the sandbox.

{"code":"NEEDS_USER_NAMESPACES","error":"NEEDS_USER_NAMESPACES: the daemonless sandbox (crun) cannot run on this host: cgroups are mounted in hybrid mode, which crun does not support; nothing was run","exitCode":3,"nextStep":"Run on a Linux executor that allows unprivileged user namespaces and has crun, or on one with a Docker daemon.","reason":"NEEDS_USER_NAMESPACES"}

crun runs without a cgroup of its own, so the executor pool's limits bound the step rather than per-step memory and CPU limits. Each action in the build manifest records how it was sandboxed in sandbox: backend (docker or crun), the crun runtime version, and resourceLimits (cgroup or pool).

Building a slice of a split run​

A build can be split into jobs queued along the target graph, each reusing the results its predecessors built. Each job runs a slice: a build of the named targets in which every other target the build needs may only be reused, never built.

The pinned worker's private admitted preparation and execution operations use the same executor preflight as ordinary builds: no-Docker refusal, resolved build.isolation selection, then the required sandbox probe before native preparation. They honor the existing OYZU_NO_DOCKER control. A read-only public preview still performs no executor preparation.

Private assigned execution emits its completed manifest even when the build fails, then returns the ordinary failure status: 1 for failed/interrupted work, 4 for unavailable upstream reuse or 5 for failed handoff publication. A failed manifest cannot appear to the worker as successful execution. Native admission still requires exact selected records; mismatch diagnostics name the record and changed field names without printing command/environment values.

oyzu build --slice --handoff oci://registry.oyzu.dev/acme/web/ci web

A slice runs the captured (isolated) path, as pool jobs do. With --plan it prints the isolated preview of that selection, with the same needsDaemon and isolation as --remote --plan. With --no-docker (or OYZU_NO_DOCKER=1) it is judged as an isolated build: a Node target runs in the daemonless sandbox, and any other target stops it with NEEDS_DOCKER_DAEMON (exit 3) before anything runs, so a pool without Docker requeues it rather than failing it. It cannot be combined with --remote, --affected, --check, --no-cache or --verify-contract, and it needs an active action cache when any selected upstream is unnamed. A URL this client cannot use is refused (exit 2) before anything runs.

None of these inputs changes a key: a slice derives every upstream key exactly as a whole build does, from the outputs it restores, so per-target slices of a commit produce the same action keys and artifact digests as one whole build. A producer that built something else than this checkout expects therefore shows up as a miss, never as a wrong reuse. The entries are the frozen OEP-0011 entries every remote tier holds; a handoff hit is verified and materialized like any remote hit.

Outputs and incremental state​

Successful binaries are collected in dist/<target>/<platform>/ (the host platform, such as dist/cli/windows/x86_64/; see the bundle layout) with their normal native names, then exposed at .oyzu/bin/<name>[.exe]. Outputs labels each one with the profile it was built with, development or, for an optimized build, optimized; each binary is statically verified as an executable for the host before it is collected (executable verification). The shared bundle store retains manifest, plan, envelope, reports and action logs. These disclose host execution, observed source and unverified tool identity; they do not confer production eligibility or assert enforced isolation.

Rust state lives under .oyzu/native/rust/<compiler-host>/: target holds native compilation state and tests holds separate instrumented/test state. Cargo owns native invalidation. Prepared package bytes remain in the already provisioned native package cache; this slice does not implement an acquisition proxy, import unmanaged caches as trusted evidence or add a shared artifact cache.

Native dependency preparation​

After tool admission, the Rust builder tries locked offline Cargo metadata. If the cache is sufficient, it proceeds without fetching. Otherwise an online build runs cargo fetch --locked through the host executor with live, labeled preflight output, then resolves metadata offline again. Cargo owns registry/Git downloads, checksums and its cache; Oyzu does not rewrite Cargo.lock. Compilation remains offline. oyzu build --offline never takes the fetch path and reports missing inputs with guidance to run an online build or correct the manifest/lock.

This is the standalone native path: Cargo uses its configured repositories, credentials and network settings. It is not a broker-controlled acquisition or network isolation guarantee. Managed host tool admission remains unavailable; this does not enable it or change captured-build acquisition. Native preparation failures retain a safe category and recovery guidance even when credential-bearing native details are withheld. Warm-cache qualification alone does not prove cold repository self-building; see the recorded qualification results.

Previous claimed artifacts move to bundle history on either successful or failed native builds; unrelated dist files stay protected. See bundle finalization and recovery.

Failure returns a nonzero exit and leaves .oyzu/bin at the last successful generation. Treat it as stale relative to the failed attempt. Promotion renames the previous image before replacing the stable name, avoiding direct overwrite of a running Windows image. An image that cannot yet be deleted may remain as a hidden previous generation; repeated Windows self-rebuilds still require proof.

Bootstrap and activation​

Build the initial executable with cargo build --locked --release --bins, then copy target/release/oyzu[.exe] and target/release/oyzu-shim[.exe] together to a dedicated user PATH directory outside the checkout, preserving any existing installation. Native compiler cache retention​

Rust source refresh and version projection preserve the modification times of final Cargo.toml files and Cargo.lock when their newly reconciled bytes are identical to the previous projection. This keeps Cargo and its build scripts from treating unchanged versions as changed source. Each current file is hashed before its time can be retained; changed bytes keep their fresh time. Expendable digest/time hints live in manifest-projection.json beside the native compiler cache. Missing, damaged or unwritable hints fall back to ordinary Cargo fingerprinting. Source admission, Cargo resolution/version decisions and action keys still run. This also applies with --no-cache, which disables Oyzu action reuse while retaining native compiler caches.

Oyzu's own build script watches existing Git metadata and the current loose ref or its existing parent. An absent optional path such as packed-refs no longer forces a build-script run on every invocation; unborn and packed branches still refresh the compiled identity when commits change.

Native Rust oyzu build retains at most cache.nativeMaxMiB MiB across its selected host's declared compiler caches after normal completion. The default is 8192 MiB (8 GiB). Configure it through the ordinary configuration cascade:

[cache]
nativeMaxMiB = 8192

Eviction runs Cargo's own cargo clean on the declared cache directory. Oyzu first marks that directory with the standard CACHEDIR.TAG, because current Cargo refuses to clean a target directory without one; a cache created before the tag existed would otherwise fail every build once the budget was exceeded.

The setting accepts 1–1048576 MiB, supports ordinary policy numeric constraints, and applies identically online and offline. It is separate from remote result cache preferences. Progress reports the measured size and any reclaimed roots; JSON builds keep those diagnostics on stderr and the result on stdout.

The build holds the workspace transaction lock while checking the budget before execution and after collecting artifacts and reports. If over budget, execution runs the selected Cargo's clean --offline --target-dir <validated-directory>. Cargo retains ownership of compiler-file cleanup and its own cache locking. Whole roots are evicted in this order until under budget: the obsolete separate doctest target, coverage target, ordinary build target. Under budget, no native cleanup runs. Doctests now reuse the ordinary build target; instrumentation keeps coverage in a separate target. A budget below the working set trades incremental reuse for space and can cause a cold compile on every invocation.

This is a retained-size policy, not a peak disk quota: compilation can temporarily exceed it, and a crash or full disk before collection may leave oversized state until the next invocation. End-of-build cleanup failure emits NATIVE_CACHE_RETENTION_FAILED without discarding build evidence or changing its result; the next pre-build check retries, and a failure there stops execution. Root/entry symlinks and Windows reparse points are rejected rather than followed. Use a normal directory or remove the redirection before retrying. No claim is made of protection against a hostile concurrent filesystem writer.

Only builder-declared roots under the selected target's .oyzu/native are eligible. Installed tools, downloads, .oyzu/bin, dist, history/recovery, proof files, other platform roots, direct Cargo's project target, and arbitrary oyzu run tasks are outside this policy. No schema changed and no legacy data was relabeled. The regression entry point is python tooling/test-native-cache-budget.py --cli <compiled-oyzu> with this checkout's pinned Rust/check tools and native linker prerequisites. It proves small-budget rebuilds, retained warm state, doctests, report inspection and failed-build preservation through the compiled CLI.

Native mixed-target build implementation​

The host coordinator selects declared targets and their dependency closure, prepares verified configured tools, asks each builder for its native build contract, and executes one shared task graph into one evidence bundle. Before preparation, host execution and --plan share logical selection, prerequisite/hook expansion and cycle validation. The executable host plan retains those dependency edges; the shared scheduler runs independent targets concurrently up to the resolved build.jobs ceiling. Build YAML depends_on gates consumers on the producer's selected stages. A failed dependency blocks its consumers while unrelated targets may finish. Stages within one target remain ordered to protect their shared native workspace. It does not claim process/network isolation or production eligibility. Explicit --isolated retains the isolated path and its existing tool-identity admission limits.

Native and captured builds use the same executable-action description and shared operation/hook/report composition. Native artifact locations remain machine-local collection bindings to the plan's logical outputs. This changes no executor selection or fast/full default: native build commands retain their own lifecycle, including Maven tests within verify. Internal action boundaries do not imply a separate native invocation for each module or more precise cache inputs. Required reports and successful collection still gate artifacts; private workspaces alone do not establish enforcement. See task composition.

Native support includes Cargo, Maven reactors producing jars, single-binary Go applications, explicit npm dist applications, and pip pyproject wheel distributions. Other Node/Python profiles retain the existing isolated path and its admission limits. npm uses npm ci for declared dependencies and requires a lockfile. Installation is the native target's prepare action: it runs before pre_build hooks on a cache miss, and an unchanged whole-target cache hit reuses it with the build. A failed installation blocks hooks/build and publishes no artifacts. --no-cache runs installation again. npm lifecycle scripts and offline behavior stay native; no node_modules directory is retained in the source projection. pip uses its native PEP 517 wheel builder, including build-backend acquisition. Offline adds npm offline/pip no-index behavior and may fail when native prerequisites are unavailable. CPython is provisioned as a managed tool (Python installation); pip is the one bundled with it. pip performs build-backend acquisition during its wheel command; this is visible native preparation output, not a separate Oyzu dependency graph. Host wheels are distribution artifacts, not a bundled runnable Python application.

The build performance assessment records the reviewed paths, measured repeated-build timings and remaining preparation costs. Reproduce its bounded npm checks with python tooling/test-build-performance.py --cli <compiled-oyzu>; both modes require the pinned Node and the provisioned npm worker image. Use --mode native for host checks alone. The probe checks reuse, source edits, fresh-output equivalence, native hook ordering and install failure propagation; timings are observations, not portable pass/fail thresholds.

First functional proof: run oyzu build from examples/tasks/grouped-targets/project without root overrides, produce the Python wheel and Node dist directory in one dist/manifest.json, then validate the bundle with oyzu inspect dist. Target selection, failure handling and a repeated invocation close the remaining functional checks. Broader native profiles remain separate follow-ups. Native builds now use private target workspaces and explicit artifact transfer. An ordering edge alone does not copy files. Additional shared-source inputs currently require the native host path.

Windows verification: the grouped API/web build and oyzu inspect dist succeeded with both artifacts. python tooling/test-native-multi-build.py --cli <compiled-oyzu> verifies real npm multi-target builds, a selected target, repeated publication, missing-fresh-output rejection and a native child failure that blocks dependent tasks. The concurrency proof uses a two-process rendezvous, and the dependency proof checks producer completion before consumer execution. Native executable filename collisions are rejected before build actions. These checks do not qualify full-quality dependency availability for every ecosystem.
