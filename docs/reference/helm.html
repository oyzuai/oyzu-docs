Helm charts and native chart tests

CLI reference

Published from the canonical docs/reference/helm.md file. Features marked experimental remain experimental; check support limitations before relying on them.

The helm/chart builder packages an application or library chart, renders it, lints it, checks its YAML formatting and runs your helm-unittest suites. It finds a chart at Chart.yaml or chart/Chart.yaml, so a basic chart needs no Oyzu configuration. If both locations exist, set the target paths in build.yaml, because ambiguous discovery fails. The chart example has a local library dependency and optional assertion suites.

Note: The Helm builder is experimental. It is supported on Linux (x86-64) and Windows. Builds never contact a cluster.

Quick start​

oyzu run list
oyzu run test
oyzu run lint
oyzu run format-check
oyzu run format
oyzu build --plan
oyzu build
oyzu inspect dist

oyzu run list shows the tasks without launching Helm or reading assertion files. The tasks are:

TaskRunsEffect
installhelm dependency buildMay download dependencies and update locks
buildhelm packageWrites a chart archive
linthelm lintNone
testValidation and helm-unittestWrites a test-only dist/ bundle
format-checkyamlfmt, read-onlyNone
formatyamlfmtRewrites your YAML files

The group is named project. Explicit targets use their own names.

Prerequisites​

Direct tasks need Helm and the helm-unittest plugin in Helm's plugin folder, and yamlfmt on PATH for formatting. Isolated builds use Helm 3.22.0, helm-unittest 1.2.0 and yamlfmt 0.21.0. Declared dependencies must already be prepared (for example with oyzu run install), because testing doesn't download them.

Builds do not install the plugin or run its installation hooks. The github:helm-unittest/helm-unittest@1.2.0 tool identifies the pinned plugin distribution.

Isolated builds need Docker and the base execution image, which has no Helm of its own. Everything a chart build runs comes from the lock or a pinned release:

  • helm must be in oyzu.lock for the worker's platform (see Pinned helm). Without it, preparation stops with a message that says how to lock it.
  • yamlfmt, used by the format stages, is a locked stage tool.
  • helm-unittest 1.2.0 is fetched when the test stage runs and the chart has unit test suites. Preparation picks the release for the worker's architecture (linux/amd64 or linux/arm64), checks it against the publisher's SHA-256 pinned in Oyzu and restores it read-only as the plugin folder /scratch/helm-plugins. The build fixes HELM_PLUGINS to that folder so a task can't redirect it to project code.

Oyzu never downloads Helm plugins other than that pinned release. The image identity is recorded in the build's evidence. A Linux amd64 isolated --full build of a chart with a unit test suite ran its tests, lint and format checks and packaged the chart.

The Helm plugin package​

The Helm builder comes from the compiled oyzu-plugin-helm package. The package finds your chart and declares the Helm commands, the image bindings and the report translation. Oyzu itself captures dependencies, admits the locked Helm, picks the package and image, decides the version and checks reports and artifacts.

Build staging preserves files already admitted into the prepared chart, including payload directories named dist. It changes the private chart's version before packaging and rendering. Source admission and native .helmignore rules still determine which authored files can reach the package. Direct tests retain their generated-output exclusions described below.

Test suites are recorded by the digest of their YAML or archive and their location inside it. Discovery never runs the assertions.

Chart documentation and development versions​

A README inside the chart directory is package content unless .helmignore excludes it. It is different from a README beside a nested chart at the project root. Captured builds with complete read declarations use these expectations:

EditDevelopment versionAction reuse
Chart README.md, stock .helmignoreChangesVersion-carrying actions rerun
Chart README.md, .helmignore containing README.mdUnchangedEvery action reuses
Project-root README.md outside the chart, in either setupUnchangedEvery action reuses
Chart source or .helmignoreChanges when admitted inputs changeAffected actions rerun

Helm's source-scope owner refines positive literal ignore entries into a file inventory and retains .helmignore as a control. Wildcards, escapes and negations keep conservative bounds; this is not a replacement for Helm's native ignore parser. A new shipped file enters the next captured plan. The inventory reads metadata and the ignore control once per chart in each planning request; it does not hash source payloads again. The formatter uses its runtime's own inventory and validation, so README bytes are outside its reads while links and custom formatter configuration still fail explicitly.

Preparation omits those proven exclusions from the private chart when there are no helm-unittest suites. Suites can read arbitrary values files, so their prepared view and unknown-read fallback remain conservative. These precision rules depend on the complete Helm read declarations; they do not admit native host execution or arbitrary custom commands.

Pinned helm in isolated builds​

Isolated chart builds need Helm in the lock. Pin the exact version:

# oyzu.toml
[tools]
helm = "4.3.0"
oyzu install helm@4.3.0

Helm takes an exact version only, and oyzu pin doesn't resolve it.

  • Oyzu reads the Linux (linux/amd64/gnu) archive recorded for that version in oyzu.lock.
  • It downloads the archive through the tool broker unless a cached copy under the user data folder still matches the locked SHA-256, and verifies the bytes against that digest.
  • It restores the archive read-only at /scratch/helmtool and puts that folder first on PATH for preparation and every build step.
  • The pinned version and archive are part of the dependency record, so a different pin or archive changes the step's identity.
  • A tampered lock is refused. Offline builds need the archive already cached, or they fail with TOOL_OFFLINE.

A pinned Helm must be able to run the helm-unittest plugin.

What each stage reads​

The plugin declares these source bounds using the shared read contract:

StageReads
build, lintThe chart directory, including metadata, locks, values, schema, templates, CRDs, .Files data and vendored charts; captured local file:// dependency trees are included
test, without helm-unittestThe same chart trees for local rendering/schema validation or library lint
test, with helm-unittestUnbounded: suites may name values files outside the chart and helm-unittest does not report those reads
format-checkThe target tree scanned for chart roots, YAML, links and unsupported formatter configuration
bindThe chart's values.yaml plus materialized OCI archives; unbounded until their read/write relationship with the prepared chart is admitted

Helm's directory loader fixes the package/lint/template boundary. The declared bound conservatively retains .helmignore-excluded files rather than reproducing Helm's ignore matcher, so an ignored edit can cause an extra miss. Formatting also retains file contents beyond the selected YAML because its current read prediction uses tree selectors rather than separate directory listings. Adding a source file is covered by the tree selectors. No explicit external values files are passed by the implicit build commands; chart with options remain unsupported. If local dependency traversal needs preparation first (for example, a vendored archive has not yet been unpacked), chart-consuming stages stay unbounded with the metadata path and traversal failure. Read planning does not reject the build.

Read analysis supplies the bounds before the captured-path confinement owner admits each stage. With captured per-action admission and hidden-copy dependency views, bounded build, lint and non-unittest test stages can reuse their own results when a file outside the chart changes. The formatter scans the whole target, so a root README edit may rerun format-check. A chart/README.md edit is inside the chart bound and invalidates chart-consuming stages. Image binding remains unbounded.

This combination requires a core release with hidden-copy dependency views (#1253) and the captured confinement/version-identity changes (#1246), followed by a Helm plugin release containing these read declarations. Read declarations alone do not enable independent stage reuse. Native host builds remain declined; no native observed-read collection is claimed. oyzu run tasks are not cached. The read-only --plan preview uses stage contracts from the target's last retained build, marked as facts from the last build. Stages without a retained contract say reported when the builder answers. Preview does not invoke Helm or the plugin and does not admit cache reuse.

Image bindings​

A chart can use the identity of an image built in the same oyzu build, so a deploy needs no --set image.digest=...:

builds:
  image:
    uses: docker/image
    with:
      repository: registry.example.com/team/greeting   # the image's eventual repository
  chart:
    uses: helm/chart
    path: chart
    bindings:
    - from: image
      artifact: image
      type: image-reference
      repository: /image/repository
      digest: /image/digest
FieldMeaning
from, artifactThe producer build and its output, as in materialize
typeimage-reference is the only type
referenceDestination that receives repository@sha256:...
repository and digestA pair of destinations, used instead of reference

Use reference or the repository and digest pair, not both and not neither. Binding the same values field twice fails during configuration.

Destinations are JSON Pointers into the chart's values.yaml, and each must already hold a string there. An empty digest: "" is the usual shape. Nothing is created or templated.

The image must set with.repository: a repository name without scheme, tag or digest. Building doesn't publish. The bound reference names the intended repository and the real manifest digest of the local archive, so the chart isn't deployable until the image is pushed there. If you change the repository, rebuild the chart.

How it runs:

  1. A binding makes the chart depend on the image and copies the image's OCI archive into the chart target (.oyzu-bindings/<n>.oci.tar, recorded in dist/inputs/<chart>.json).
  2. After the chart is copied to its private workspace and before it is packaged, linted or rendered, the bind step reads the archive's manifest digest and rewrites the destinations in that copy's values.yaml.
  3. The packaged default values and rendered.yaml carry the produced reference. Your checked-in chart is never edited.

The rewrite re-serializes values.yaml in the private copy, so comments in the packaged defaults are lost. A new image digest reruns the chart's steps, and an unchanged one reuses them. A failed or blocked image blocks every chart step.

Image bindings work on Windows with Docker Desktop. A multi-platform image (more than one manifest) is refused. Linux and macOS hosts, bindings through a platform matrix, publishing and deployed clusters are not supported yet.

YAML formatting​

Discovery adds a read-only format-check build stage and a format task that edits your files. Both use yamlfmt.

  • Selected files: .yaml and .yml files directly in each chart root (the folder with Chart.yaml), plus YAML below tests/ and crds/. Unpacked subcharts and sibling charts inside the target root are included.
  • Left out: Go templates in templates/, __snapshot__ baselines, packaged chart archives, Chart.lock, generated output and hidden folders. Dependency archives are never edited or repacked. Template formatting isn't supported, so a passing check says nothing about template style.

Oyzu runs yamlfmt with its own private configuration: LF line endings, a final newline, and yamlfmt's basic formatter defaults. Configuration in parent folders or your home folder is ignored. A formatter file in the target (.yamlfmt, .yamlfmt.yaml, .yamlfmt.yml, yamlfmt.yaml, yamlfmt.yml) fails the implicit task with a message telling you to override the tasks. Use normal TOML task overrides for custom formatting.

format-check lists the files that differ and exits non-zero without changing anything. Invalid YAML also fails, with yamlfmt's message. Run oyzu run format, review the changes and try again. format writes files as it goes, so if a later file fails, earlier edits stay.

Neither task downloads dependencies or contacts a cluster. Links and non-regular files are rejected. Limits are 100,000 traversed entries, 4 MiB per file and 64 MiB in total, and each yamlfmt run has a 30-second timeout. Direct tasks run as host processes with no sandbox. Isolated builds use the executor's isolation.

The chart is packaged and rendered in the build even when you don't select the test stage, so plain oyzu build still writes rendered.yaml.

Inference and native assertions​

Declare unpacked subcharts in the parent's native Chart.yaml dependencies. For a subchart inside the chart, give its name and version and leave repository empty. That selects the existing charts/<name> folder. If you skip this, strict lint fails, even when the subchart's assertions pass. Oyzu doesn't add the dependency for you or turn the lint gate off.

Keep checksum files out of charts/, or list them in .helmignore (for example charts/*.tgz.sha256), because Helm reads non-chart files there as dependencies.

What the test does​

Without assertion suites, the implicit test checks that an application chart renders and passes its values schema. A library chart is checked with strict lint with subcharts, because it can't be rendered as an installable chart. In isolated builds, rendering uses helm template --dry-run=client with an empty kubeconfig and no cluster access. This checks the chart. It doesn't show that a deployed application works.

Suites​

Oyzu finds helm-unittest suites in each chart, including unpacked subcharts and local charts/*.tgz subcharts, even when the parent has none:

  • flat tests/*_test.yaml
  • recursive unittests/**/*.yaml (any .yaml name)

Packaged suite evidence binds the original binary .tgz bytes and the suite location inside the archive. Text suite files still require UTF-8; discovery retains its bounded reads, path containment and symlink refusal.

.yml files, custom globs and recursive tests/ folders are not selected. Each subchart needs a regular Chart.yaml, and chart folders starting with a dot or underscore are ignored. Helm-unittest parses the YAML and runs the assertions, so malformed YAML is a native failure.

For example, chart/tests/deployment_test.yaml:

suite: deployment contract
templates:
  - templates/deployment.yaml
tests:
  - it: uses one replica
    asserts:
      - equal:
          path: spec.replicas
          value: 1

Oyzu passes both file patterns to helm-unittest explicitly, because helm-unittest 1.2.0 drops its defaults when you give it a pattern. Selected suites must produce at least one test case. You don't add a test section to build.yaml, and you don't set a glob.

oyzu run test shows the logical task helm unittest --strict <chart>. It unpacks packaged subcharts in a private copy before calling the plugin. Isolated builds run both the render and schema validation and the unit tests, and ask the plugin for JUnit output.

Suites are source files, so they go into the published chart archive unless you list tests/ in .helmignore. Oyzu doesn't change your packaging rules.

Static discovery inspects archives without extracting them into your checkout. It stops at these limits:

LimitValue
Suites128
Inspected entries4,096 per scope
Subchart levels16
Archive nesting16
Metadata file4 MiB
Expanded archive bytes64 MiB per scope

An archive needs one chart root with a Chart.yaml. Links, duplicate or case-alias paths, non-portable paths and mixed roots fail. Arbitrary tar layouts aren't accepted, only Helm-generated archives.

Build outputs and failure handling​

Preparation unpacks contained subcharts in its private workspace and captures the chart's local file:// dependencies. It rejects cycles and paths that escape, and runs dependency preparation offline. Existing locks are honored and stale locks fail. Lock timestamps and archive metadata are normalized. If a packed and an unpacked copy of a subchart both exist, the build fails instead of overwriting. Your source archives are never modified.

Locked HTTPS repositories​

A captured chart can use one public, credential-free HTTPS chart repository. Declare it in native Chart.yaml, generate Chart.lock with native helm dependency update, and commit that lock. Native Helm validates lock consistency and selects versions; Oyzu does not resolve chart versions itself. For example, a dependency may name vault, version constraint ~0.30.0, and repository https://helm.releases.hashicorp.com with a lock selecting 0.30.1. The same repository can be used by a contained sibling file:// chart. Its acquired archives are expanded and validated at that local chart's own path.

A single dependency can also set alias, for example name: vault with alias: secrets. Native Helm applies alias-scoped values under secrets and validates the native lock. The lock must uniquely match the raw chart name vault; captured index entries, archives, expanded paths and dependency records keep that raw identity. Repeated copies of one upstream chart under multiple aliases are outside this path's supported scope.

For example, declare the dependency in Chart.yaml:

dependencies:
  - name: vault
    alias: secrets
    version: ~0.30.0
    repository: https://helm.releases.hashicorp.com

Put its values under the alias in values.yaml:

secrets:
  injector:
    enabled: false

Generate the native lock normally; do not rename the locked chart or its archive to secrets.

The repository index, selected archive URLs and every redirect must remain under that repository's HTTPS origin and path prefix. Each selected index entry needs a SHA-256 archive digest. Oyzu captures the original index and archive, checks the complete archive before supplying it to Helm, and validates the acquired chart names, versions and vendored dependency closure. Original chart and lock files remain unchanged. Dependency records distinguish original archive digests from the prepared chart bytes; a chart lock alone is not archive integrity evidence.

An unchanged selection can reuse its verified acquisition snapshot. This reuses the recorded index, without claiming that the current upstream index is unchanged. Offline builds require that exact capture, locked tools and execution image to be available already. Missing inputs fail with a request to prepare the selection online; there is no network fallback during execution.

Repository aliases (@repo or alias:repo in the repository field), OCI, authentication, managed connector routing, multiple remote repositories and archives hosted outside the repository prefix are not supported by this path. Remote archives must include their complete vendored closure; Oyzu does not acquire additional remote dependencies from those charts. The index and each compressed archive are limited to 4 MiB, with at most 4,096 archive URL slots. Existing archive expansion and source containment limits also apply. The direct native install task keeps its existing native behavior.

FailureMeaning and recovery
HELM_LOCK_REQUIRED / HELM_LOCK_INVALIDGenerate and review an authored native lock matching the declared repository
HELM_SOURCE_UNSUPPORTEDUse the supported single public HTTPS repository form, or vendor the dependency locally
SOURCE_DENIEDAn archive or redirect leaves the original repository prefix; use a supported source or vendor it
HELM_INTEGRITYCaptured archive bytes differ from the advertised SHA-256; inspect the repository rather than bypassing verification
HELM_CAPTURE_INVALID / HELM_CLOSURE_INVALIDRequired native outputs, identity bindings or vendored dependencies are missing or inconsistent
OFFLINE_ASSET_UNAVAILABLEPrepare the exact selection online before retrying offline

The chart version comes from version inference over its native version and Git history, with a suffix from the source snapshot. appVersion and dependency versions keep their own meanings.

A build packages the chart, runs the tests, strict lint and the read-only YAML format check, and collects the outputs if all pass. Application charts produce a versioned .tgz and rendered.yaml. Library charts produce the .tgz only. Building, generated files and the version change happen in private workspaces, so your checkout stays unchanged. The format check covers your source YAML, not the regenerated dependency chart.

Reports are collected in dist/, and dist/manifest.json records their paths, digests and summaries:

  • junit.xml is one render and schema check, or the library validation
  • unittest.xml is required when suites are selected, and has the native test cases, failures and skips. A render success never covers a failed assertion
  • Coverage is recorded as inapplicable in the target's extensions["oyzu.dev/coverage-applicability"]: chart assertions have no application-source coverage denominator. This applies to isolated builds and direct tests, including named targets and runs with hooks. No coverage percentage is made up, and a required coverage minimum still fails

The manifest also lists framework discovery, step outcomes and artifacts. Testing fails for missing or invalid required reports, a plugin that won't launch, a native failure, a timeout, or a unittest run with zero test cases. Old report files are removed before each run, so an earlier success can't cover a failed launch. Validation and unit tests each time out after 120 seconds.

Task replacements and hooks work as usual. A replacement keeps the required reports, and one that exits 0 without them fails collection. Direct tests collect validation and unittest reports once, after the post-test hook; a failing hook still fails the run and retains the test reports. A valid bundle isn't a release approval.

If a build fails, read the retained logs and reports, fix the suite, tool, values or lock, and rebuild. A format difference needs oyzu run format or a task override.

Snapshot baselines are inputs​

Helm-unittest can create missing matchSnapshot baselines even without --update-snapshot. Oyzu compares the files under __snapshot__ folders before and after the run. Creating, changing or deleting a baseline fails the task and blocks artifacts. The native JUnit can still show a passing assertion, so read both the step status and the reports.

Create or update baselines on purpose with native helm-unittest outside the build, review them and commit them with the suite. Then a matching baseline passes and a changed value fails normally. Direct oyzu run test applies the same rule and also rejects creation or changes.

Direct tests run on a private copy of the chart that leaves out .git, .oyzu and dist, so the live bundle isn't visible to Helm. The copy holds the chart tree only, so relative references to files outside it don't work. It rejects links and is limited to 100,000 entries and 64 MiB. Baseline scanning has the same entry limit with 16 MiB per file and 64 MiB in total. Exceeding a limit fails the task. This checks baseline changes and is not a file write monitor. Direct tasks are not a sandbox. Isolated builds use the executor's isolation.

Checking a chart and current limits​

To check a chart before you commit, run oyzu build --full, or oyzu run test, oyzu run lint and oyzu run format-check for the quick version, and read the reports with oyzu inspect dist.

Not supported yet:

  • Custom suite globs, templated test charts, and suites in sibling file:// dependencies that aren't prepared are not discovered.
  • OCI, authenticated, cross-origin and managed chart repositories are not supported; see Locked HTTPS repositories.
  • Go-template formatting and custom yamlfmt configuration aren't supported.
  • Publishing and signing aren't part of the Helm builder.
  • Image bindings: see Image bindings.
