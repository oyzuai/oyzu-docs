Plugin packages, the plugin store and lock selections

CLI reference

Published from the canonical docs/reference/plugin-packages.md file. Features marked experimental remain experimental; check support limitations before relying on them.

A plugin package is the archive that holds a builder plugin: its manifest and one executable per platform. Oyzu verifies a package, installs it into a plugin store, pins the exact release in oyzu.lock and launches it for your builds. This page covers where packages come from, how they're verified, how they're locked and how builds record them.

Note: Plugins are experimental. Builders are not built into the CLI, so every target needs a package. A package comes from the plugin catalog, from a plugins.packages binding, or from a direct oci:// reference. Only the Go preview is published. For the other first-party builders, build the package yourself and bind it, or use a development binding.

Package format​

A package is a .tar.gz or .zip archive containing:

  • plugin.json at the root, the plugin manifest (schema);
  • the platform executables that the manifest's runtimes name by entrypoint.

Installation refuses a package that:

  • hashes to a different digest than the one configured (checked before extraction);
  • exceeds the archive bounds (512 MiB archive; at most 4096 entries, 1 GiB extracted, 512 MiB per file, depth 16, expansion ratio 100), or contains path traversal, absolute paths, hard links, symbolic links that leave the payload, or non-portable names. Relative symbolic links inside the payload are allowed, but an entrypoint must be a regular file;
  • has no valid plugin.json, or one with unknown fields. Fields that name another plugin (dependencies, preferences, successors) are unknown fields, so a plugin can't depend on another plugin;
  • names an entrypoint that's missing, isn't a regular file, or whose SHA-256 differs from the manifest's runtimes[].digest;
  • isn't the package the bound reference names (go/app needs package name go with builder profile app), or supports no protocol generation v1alpha1.

Nothing in a package runs during installation. There are no install hooks. To build a package for development, see plugin development.

Binding a reference: plugins.packages​

A binding tells oyzu which package serves a builder reference. Set it in user, machine or administrative configuration, never in a project file or profile (CONFIG_SCOPE):

[plugins.packages]
"go/app" = { archive = "/home/me/plugins/go-0.1.0.tar.gz", sha256 = "sha256:…" }
# or
"go/app" = { oci = "ghcr.io/oyzuai/plugins/go:0.1.0" }
  • Keys are short references without a major selector (go/app), or exact direct OCI target references. At most 64 entries.
  • archive is an absolute path. sha256 is sha256: plus 64 lowercase hex digits and must match the archive.
  • A reference can be bound by plugins.packages or by plugins.development, not both (PLUGIN_BINDING_INVALID).
  • A binding applies only to the references your project's targets use. A Go binding never affects a Python or Rust project, and writes no lock entry for it.

If the archive digest equals the release digest of the release the catalog selects, the binding is that release's local archive route, and the package must also be the catalog's package and version. Any other digest is a local package binding. Neither can bypass a catalog's withdrawal: a binding for a withdrawn or revoked release is refused with PLUGIN_RELEASE_WITHDRAWN or PLUGIN_RELEASE_REVOKED before it's recorded or launched.

Oyzu records how each OCI or HTTPS release was accepted (including whether it's a preview) alongside the installed release. A damaged record is an error; an older installation without one is treated as an ordinary release.

Direct OCI target references​

A uses entry in build.yaml can name an OCI release and builder profile directly:

builds:
  app:
    uses: oci://registry.example/team/opaque@sha256:aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa#app

The repository path says nothing about which package it is. Oyzu reads the package's own plugin.json, checks the requested profile, protocol and engine features, and records the original URI, the real package and version, and the release root in oyzu.lock.

  • A digest must equal the bound and locked release. A tag is resolved once, when the selection is adopted. Later builds use the locked root and never resolve the tag again.
  • A tag outside the official namespace needs a plugins.packages binding keyed by the complete URI, with the signer to require (see OCI sources). If you later remove that binding, an already installed release still replays without a registry request, but a missing one can't be downloaded until you restore the binding.
  • A configured archive can supply a direct digest only when the archive's digest equals that release.
  • A URI doesn't bypass a refused catalog, a withdrawal or the preview rules. A package named oyzu/* on any registry needs the official signature (below).
  • HTTPS is a catalog route, not a uses syntax.

OCI sources​

A binding can name a release in an OCI 1.1 registry, such as GHCR, a distribution registry or Harbor, whose token endpoint (if any) is on the registry's own origin. The release is laid out as the Oyzu OCI package contract defines: an immutable release root binding the plugin manifest and one manifest per platform payload, with a detached Sigstore signature attached to the root.

[plugins.packages]
# Official release by tag: signed by oyzuai/oyzu's plugin-release.yml.
"go/app" = { oci = "ghcr.io/oyzuai/plugins/go:0.1.0" }
# Another registry by tag: say whose signature to require.
"go/app" = { oci = "registry.example.com/team/go:1.2.0", identity = "https://github.com/acme/plugins/.github/workflows/release.yml@refs/heads/main" }
# By digest: the digest is the trust (no signature is checked unless identity is set
# or the reference is in the official namespace).
"go/app" = { oci = "registry.example.com/team/go@sha256:…" }

identityhttps:// certificate identity (SAN URI)The signer the root signature must come from: a GitHub Actions workflow identity. Signers other than the exact official identity require a GitHub-hosted runner, as with toolIndex.identity; the official identity also accepts self-hosted runners. Signature rules​

A reference under ghcr.io/oyzuai/plugins/ (also written ghcr.io:443/…) is official. It must be signed by exactly https://github.com/oyzuai/oyzu/.github/workflows/plugin-release.yml@refs/heads/main, issued by GitHub Actions OIDC on a GitHub-hosted or self-hosted runner and verified against Sigstore's production trusted root. A copy of the workflow on another branch signs as @refs/heads/<branch> and is refused.

Only that exact official identity accepts self-hosted. Every other signer requires github-hosted; missing or unknown runner environments are refused. v0.2.1 is the first client release that trusts self-hosted official signatures. Earlier clients reject them. The certificate does not identify a particular self-hosted pool; pool rotation and revocation remain unresolved.

  • An official binding with identity or trustedRoot is CONFIG_INVALID_VALUE. Configuration can't replace the official signer or let a private CA vouch for it.
  • Any other tag without identity is also CONFIG_INVALID_VALUE, when configuration loads.
  • A release found through a catalog (no binding) follows the package's publisher instead: publisher oyzu needs the same official signer on every route, a company mirror included, and any other publisher is trusted by the digest the signed catalog lists. See Who may sign a release.
  • A package named oyzu/* needs the official signature and production root on any network OCI route, even on an arbitrary registry or digest.

Choosing a payload for your machine​

On a glibc Linux host, when a release has no payload without an ABI or for gnu, oyzu uses the musl payload for that architecture. Musl payloads must be statically linked. A dynamically linked musl entrypoint is refused on a glibc host with PLUGIN_PLATFORM_UNSUPPORTED, naming the loader it needs. A package this machine can't run is refused before it's installed. The official Linux payloads are static musl.

How a download works​

Downloading runs only where an archive would be read: a real oyzu build adopting a selection, or installing a locked release that's missing from the store. It needs no Docker, ORAS, crane or login. Oyzu speaks the OCI Distribution API itself, anonymously, following a registry's Bearer challenge to its token endpoint without credentials, as public GHCR packages allow. A loopback registry (localhost, 127.0.0.1, ::1) uses plain HTTP; every other registry uses HTTPS through your configured proxy and certificate trust. It fetches, in order:

  1. The release root, by the locked digest, the binding's digest, or (only at first selection) the tag. The digest is the SHA-256 of the bytes received, never a registry header.
  2. The signature, when one is required: referrers of the root, through the referrers API or the sha256-<hex> referrers tag. Each Sigstore bundle is verified against the root digest, the signer and the trusted root until one verifies.
  3. The metadata manifest and plugin manifest, checked against the bound reference.
  4. The manifest and payload for this platform only. Other platforms are never downloaded.

Every object must hash to its descriptor before use, and the extracted entrypoint must match its manifest digest. Only then is the release published into the store. Moving a tag afterwards changes nothing, because later builds, --frozen replays and reinstalls into an empty store use the locked digest.

An archive digest and a root digest never match, so switching a binding from an archive to OCI is an explicit re-adoption (PLUGIN_LOCK_MISMATCH).

Not supported:

  • registries whose token endpoint is on another host (Docker Hub's auth.docker.io);
  • credentials for private registries. A private package fails with PLUGIN_PACKAGE_UNAVAILABLE;
  • payloads over 512 MiB (a payload is held in memory);
  • organization route settings (list a mirror as a catalog route instead), a command that fills a mirror, and offline export or import.

HTTPS layout-archive routes​

A verified catalog release can list a route such as {"type":"https","url":"https://mirror.example/plugins/go.tar.gz"}. The URL serves a tar or gzip tar of a standard OCI image layout: oci-layout, index.json and blobs/sha256/<hex> at the archive root. The index names the catalog's exact release root and any detached signature manifests. See the layout contract.

Unlike a local plugins.packages archive, the lock and the installed directory use the canonical OCI root digest, not the hash of the transport archive. Changing a release from an OCI route to an HTTPS mirror of the same root keeps the lock valid.

  • Oyzu checks the layout, blob digests, descriptor sizes, metadata, the selected runtime and the extracted entrypoint before installing.
  • Publisher oyzu still needs its fixed official release signer (GitHub-hosted or self-hosted) and the production Sigstore root. The mirror carries the original signature unchanged. Other publishers use the root digest the signed catalog lists. A catalog can't name another signer.
  • The transport uses your configured proxy and SSL_CERT_FILE. HTTPS is required even for loopback. URLs can't carry credentials, a query or a fragment, and redirects must stay within the same origin and directory.
  • Downloads are anonymous and limited to 256 MiB. The whole archive is downloaded, even if it includes other platforms; only your platform's payload is installed. Extraction uses the archive limits above and refuses links and unexpected paths.
  • An installed release needs no archive request. --offline makes no request. --frozen can refresh catalog metadata but never downloads this route.

Behind a TLS-inspecting proxy, set HTTPS_PROXY and SSL_CERT_FILE (a PEM file containing the inspection CA). This adds TLS trust only. It never changes the official signer, the production Sigstore root, the route or the locked release. Loopback destinations bypass proxies. Go builds through an inspecting proxy have been tested on Linux and Windows; see acquisition transport.

A failed route is PLUGIN_ROUTE_FAILED. Invalid contents keep PLUGIN_PACKAGE_DIGEST or PLUGIN_PACKAGE_INVALID, and missing signatures keep their signature errors. Builds never choose a newer release to recover from unavailable content. Restore the route or the exact content.

Store​

Packages live in the tool store (--store, default the shared user store) under plugins/<hex>/, where <hex> is the release digest (the archive digest, or the OCI release root digest). Releases sit side by side, and a build uses the payload for your platform.

  • Concurrent first builds extract once. A release is published with an atomic rename, so nobody sees a partial extraction.
  • A shared lease on the release is held for the whole command to protect a running executable (this matters on Windows).
  • An installed release is trusted. Later builds don't hash it again, and only a missing release needs the archive.

Explicit revoked-copy maintenance​

oyzu plugins prune removes a revoked release from your store. It previews by default and needs --apply to remove anything.

  • It acts only on exact digests you name, and only when the current verified cached catalog revokes that release. It doesn't refresh the catalog. A withdrawal, or an expired or unverified revocation, never allows deletion.
  • It takes the store's lock for the release, then an exclusive use lease, so a release in use by another oyzu command is kept. On Windows it also checks that no process has the executable open.
  • Uncertain, malformed, linked or inaccessible content is kept. If the operating system interrupts removal, the result says incomplete, not retained.
  • It touches only plugins/<hex> and the release's package-contents/plugin-<hex>.json. Other releases, catalogs, installed tools, the permanent locks/plugin-<hex> files and every project lock stay as they are.
  • It doesn't check whether other projects' locks name the release. A normal build can download it again if a later selection allows it.

To recover a project that still selects a revoked release, adopt an eligible one with oyzu plugins update. Pruning never changes a selection.

Lock selections​

The first time oyzu resolves a plugin for a project, it appends the selection to oyzu.lock in the project root. Existing records, comments and ordering aren't touched.

[[plugin]]
reference = "go/app"
profile = "app"
package = "oyzu/go"
major = 0
version = "0.1.0"
release = "sha256:…"

[[plugin.payloads]]
os = "linux"
arch = "amd64"
digest = "sha256:…"
FieldMeaning
reference, profileThe builder reference and its profile
packageThe publisher/name of the package
majorThe major version of the manifest, set at first resolution
versionThe exact release version
releaseThe archive digest, or the OCI release root digest
payloadsThe executable digest per platform from the plugin manifest. For an OCI release, every platform the root lists

The lock never records local paths, download times or the platform of the machine that wrote it. oyzu pin and other tool commands keep [[plugin]] entries. A lock that holds only a plugin selection doesn't count as pinned tools: your first oyzu build still pins the tools the builders need.

Only a real oyzu build (not --plan or --check) or a real oyzu pin (not --dry-run, and not with explicit tool specs) can install a bound package and record a selection. Only oyzu plugins update can install a release to replace a selection that's already locked. Every other command that discovers the project replays the lock and the store and writes nothing.

Only the plugins your selected builds need​

oyzu build <name>..., plain oyzu build, oyzu build --plan, oyzu run <build>:<task> and oyzu run <task> for a task your root oyzu.toml defines select, install, replay and launch only the plugins of the builds they asked for and the builds those need. In a project with a cli build (rust/app) and a docs build (node/app), oyzu build docs never needs the Rust plugin installed, and a missing rust/app release doesn't stop it. A root task such as oyzu run check-docs that depends on no build needs no plugin at all, because a root task never replaces a build's stage (which build a task belongs to).

oyzu decides which builds are needed before it selects any plugin, from build.yaml and your oyzu.toml files alone:

  • the builds you named, or every build without default: false when you name none (none for a root task)
  • each build they list in depends_on or materialize, and a chart's bound image
  • each build named in the depends_on of a task those builds can reach, including unqualified tasks and hooks such as pre_test

oyzu.lock keeps the selections of the builds left out exactly as they are; they're neither checked nor rewritten. --frozen only requires selections for the builds in play.

The whole project is discovered, and every plugin it uses is selected, for oyzu build --affected, oyzu run with an unqualified name the root doesn't define (which may be a build's own task, such as oyzu run test in a one-build project), a root task whose depends_on names a task by its bare name that the root doesn't define or that has a qualified hook such as [tasks."api:pre_check"], oyzu discover, oyzu lock, tool commands, and a name that isn't a build (such as a platform variant id, or a typo, which is then reported with every build's name).

Builds of different projects that share a store converge: a build that loses a race on the lock reuses the pins the other build published, or retries for up to 30 seconds, instead of failing with PIN_EDIT_CONFLICT.

Offline native builds also need their ordinary tool metadata in the same user context. oyzu tools check --catalog --json seeds the signed tool index into the default user metadata store; add --store DIR to target another store. An explicit plugin store doesn't replace the default metadata that native Go reads for its locked-version withdrawal check. Prepare both while online.

A catalog revocation refuses installed releases, even when replaying against an expired catalog. Selection refusal doesn't delete bytes; use oyzu plugins prune. @vN major selectors in bindings aren't supported.

Engine identity and pin​

Every build records the engine that ran it. A stamped release from a clean, matching oyzu/v<version> tag uses that release version, such as 0.2.4, even when the building oyzu supplies a snapshot suffix. Other stamped builds use a token such as 0.2.2-local.36bdcec27267. A development engine uses <package-version>-dev.engine.<sha256>, independently of its short --version display label. Copy the complete Engine value from the build Context or retained inventory to pin it by hand:

[engine]
identity = "0.1.0-local.36bdcec27267"

Compilation captures a deterministic inventory of engine source digests, the transitive local runtime/build dependency inputs, Cargo manifests/lock and the rustc release and shared profile facts (optimization, debug information, debug assertions, overflow checks and panic strategy), plus enabled features. Project Cargo profile tables and common CARGO_PROFILE_* overrides are bound too. Shared Rust flags (RUSTFLAGS, CARGO_BUILD_RUSTFLAGS and project build.rustflags) are bound; effective encoded flags are excluded only when identified as a declared target-only selection. Local dependency files follow Cargo's package include/exclude and ignore rules; ignored files and ignored symlinks do not change the identity, and packaged file symlinks are read through their targets. Development engine composition verifies compiled-file coverage from Cargo dep-info: consuming an omitted file fails with ENGINE_INPUTS_UNCOVERED, rather than silently widening that inventory. See engine staging for the required retained records and the non-Git-tree limit. The engine hashes that embedded inventory lazily on the first identity request and retains the result for the process. Development-only plugin dependencies do not enter this engine fingerprint. A docs-only commit keeps it stable; changed engine inputs change it. This is an input identity, not a signature or source attestation. Package admission separately binds every platform member's executable digest. Members packed together must carry the same engine identity. Development members need matching compiler releases, features and shared profile facts as well as source content. Host triples and target-only rustflags, linkers and C toolchains do not enter this shared identity. User [patch] overrides/source replacement and C toolchain inputs are not covered. Release members use the shared release stamp across targets. No source or executable hashing runs on public help, version or syntax-error paths.

A protected administrative policy can require this pin and a complete lock (policy-required pins). CI alone doesn't make the pin mandatory.

If the pinned engine isn't the one running, oyzu uses engine staging before discovering the project, when an allowed user or system source provides the archive. Otherwise it fails with ENGINE_PIN_MISMATCH. A development override keeps the running executable and records its actual content and the bypassed pin.

A package lists the engine features it needs (such as go-test-events or captured-plan). If the running oyzu lacks one, the build fails with PLUGIN_ENGINE_REQUIREMENT before any plugin operation, naming the missing feature and the running engine. Use an oyzu that supports it, or a compatible plugin release. The catalog skips releases whose required features oyzu doesn't support.

Java packages using Gradle's compiler observations require gradle-compiler-facts. The engine must support that preparation contract as well as the package's exact native API. Older engines skip that release and can keep selecting an eligible earlier package; a direct incompatible package binding fails before any plugin role runs. This does not waive preview opt-in, signature, withdrawal or platform checks.

.NET lock preparation requires dotnet-lock-admission on the selected package's builder role. The engine checks that declaration before admitting its native worker for private lock-facts/acquisition. An older exact lock is replayed as recorded, then refused at that boundary if the capability is missing; it is never silently replaced. Use oyzu plugins update dotnet/sdk to explicitly select an admitted capable package. A newer version label alone does not prove support. Catalog eligibility still selects the newest eligible release under the existing preview and organization-catalog rules; execution failures never trigger a downgrade.

Which bytes run, and how output records them​

Windows plugin stores support executable paths longer than 260 characters. No shortened store path or additional launch flag is required; filesystem component and total path limits still apply. This applies to plugin protocol operations and native stage actions. Long absolute application paths use the Windows verbatim form at launch without resolving filesystem links; short paths retain their existing spelling and require no additional filesystem lookup.

A package's entrypoint runs in place from the store, where its digest was verified at installation. A plugins.development executable is copied to a private per-command file and hashed as it's copied, so the recorded digest is that of the file as launched. Replacing the source afterwards changes nothing in the running command. The copy is removed when the command ends. If oyzu is killed by a signal, the copy stays in the temporary directory as oyzu-plugin-*; delete it by hand.

For a wrapper script, the digest covers only the script, not the program it starts, so its targets are never reused from the action cache. Bind the plugin executable itself.

Action cache keys include the plugin's identity (reference, release, version, executable digest and runtime), recorded on each target as extensions["oyzu.dev/builder-plugin"]; see external builder targets.

Every plan, execution envelope and manifest of a build or oyzu run carries extensions["oyzu.dev/plugins"] when a plugin is used, so plugin-built output is distinguishable from other output:

{"reference":"go/app","source":"package","package":"oyzu/go","version":"0.1.0",
 "release":"sha256:…","executableDigest":"sha256:…","selection":"adopted"}
{"reference":"go/app","source":"local-development",
 "executableName":"plugin","executableDigest":"sha256:…"}

A development record keeps only the executable's file name, never your absolute path. Nothing refuses to publish plugin-built output; the record makes it visible. oyzu inspect requires the records in the plan, manifest and envelope to be identical (see build bundles).

oyzu run --store DIR, oyzu scan --store DIR and oyzu lock --store DIR move the plugin store with the tool store, as oyzu build --store DIR does.

The set of bindings is fixed by the first discovery in a command. If a later discovery in the same command asks for different bindings (another executable, changed bytes or another reference), it fails with PLUGIN_BINDING_CONFLICT.

Isolated builds with plugins​

--isolated builds run in a sandbox with no network, in Docker or the Linux daemonless sandbox. The plugin plans the build without running it (the captured-plan feature), and oyzu does everything that needs the network or a toolchain: it installs the locked tools and dependencies, then runs the plan offline.

Note: Isolated builds with plugins are experimental and are limited to Linux amd64 targets.

An isolated build with a plugin needs all of these:

  • A package whose manifest declares captured-plan and has runtime members for both your host and the Linux execution platform. One member can serve both when the platforms match. For an isolated build, exactly one member must match the image's OS and architecture; none or several refuse selection.
  • An accepted engine archive and a usable immutable Linux image.
  • The locked tools for that platform.

A raw development executable binding can't run an isolated build; a development binding to a package archive can (see plugin development). Any missing piece fails explicitly with PLUGIN_ISOLATED_UNSUPPORTED or ENGINE_ASSET_UNAVAILABLE, and oyzu never falls back to another builder. The plugin supplies build, artifact and test report intent; it can't fetch dependencies in this role. JUnit and coverage reports stay required checks.

Isolated Go applications​

Supported: one conventional Go application module with one main package, with a Linux artifact and execution platform declared in build.yaml.

oyzu build app --isolated --platform linux/amd64 --full
  • Add --no-docker to require the daemonless sandbox.
  • On Linux amd64, a normal build adopts the package selection. Commit the complete oyzu.lock, then use --frozen to replay it, and add --offline when every exact input is retained. A missing input fails without using the network.
  • --full produces the executable with native JUnit and Go coverage.
  • Go libraries, workspaces, missing capabilities and unsupported execution settings fail explicitly.

Isolated pip Python packages​

Supported: python/package targets built with pip and PEP 517. The package must declare captured-plan. No Python plugin is published yet, so you supply the package and bind it yourself.

oyzu -C <fixture> --json build demo --isolated --full --frozen --no-cache --jobs 1

Oyzu freezes the selected CPython archive and the prepared dependencies, then lowers the plugin's intent to a wheel or sdist build. Put tool versions in native pin files or oyzu.toml, not in build.yaml. Installed-artifact tests and quality reports are required checks. Python builds with uv, Poetry or legacy distributions don't use this path. A refusal never falls back to another builder. See Python preparation.

Isolated npm applications​

Supported: npm node/app applications. The package must declare captured-plan. Until the Node plugin is published and public, you supply the package.

oyzu build app --isolated --platform linux/amd64 --full --frozen --image npm=<node-image>

Oyzu prepares the locked Node and npm archives and dependencies and runs an offline install before the plugin's build and check steps. JUnit and LCOV reports are required. A dist directory written by your project is moved aside in the private workspace before the build and exported with the usual containment checks. Select tools in oyzu.toml (they resolve into oyzu.lock). The image must be one your engine can run; a bare image without the right runtime fails explicitly. Yarn, workspaces and frameworks need their own pages (Yarn, npm workspaces, pnpm).

pnpm applications use the same flow with --image pnpm=<node-image>. Export of the native pnpm store currently needs exactly pnpm 10.11.0, selected in packageManager or the tool configuration, with pnpm-lock.yaml and oyzu.lock up to date. The default base execution image is enough: the YAML parser the pnpm adapter needs (yaml 2.9.1, ISC license, shipped with its license) comes in the Node plugin package. An image you pass with --image pnpm=<ref> must meet the bring-your-own requirements.

Isolated npm packages​

Supported: a single-root npm project that produces a .tgz through npm pack. Oyzu uses this path when build.yaml has uses: node/package, or when there's no build.yaml and the project's output facts select a package:

builds:
  package: {uses: node/package}
oyzu build package --isolated --platform linux/amd64 --full --frozen --image npm=<node-image>
oyzu inspect dist

You need a package.json with a package name, a current npm lock, selected Node and npm tools, the required checks and a matching package that declares captured-plan. With no build.yaml, the command is oyzu -C <project> --json build --isolated --platform linux/amd64 --full --no-cache --image npm=<node-image>.

  • Dependencies are installed offline. Oyzu applies the build's resolved version to a private copy of package.json and the lock, runs your build script and checks, then runs npm pack --json --ignore-scripts. Your checkout and its locks are not changed.
  • A package with no build script skips the build step.
  • Read the artifact's path, version and digest from its recorded manifest. Don't guess the file name npm produced.
  • Failed tests or missing required reports block packing and export.
  • Tested with Node 22.23.3 and npm 11.11.0 on a Linux amd64 worker.

Missing native lock, incompatible package or engine, or a workspace targetSupply current inputs, or use a flow that supports your project
Lock mismatch or install failureRegenerate the lock with npm, then update the frozen inputs. Nothing is projected or packed
Build, required report or pack failureFix the failure and rerun. No archive is exported
Packed archive name or version doesn't match, or the path is unsafeInspect the retained packing log and the package's name and version

Isolated pnpm packages​

An inferred single-root pnpm project produces a .tgz the same way, through pnpm pack --json --out. You need a real pnpm-lock.yaml, exactly pnpm 10.11.0 (tested with Node 22.23.3), the required checks, and a matching package that declares captured-plan. Vite projects and pnpm workspaces aren't covered here (see pnpm).

oyzu -C <project> --json build --isolated --platform linux/amd64 --full --no-cache --image pnpm=<node-image>

An explicit uses: node/package selects the same profile. A package with no scripts exports straight from the checked-in source with setup, checks and packing, and no build step.

Native npm packages​

Supported: an explicit single-root npm package built on your machine (no sandbox) with the Node plugin. Declare only the package intent and keep your npm lock:

builds:
  package: {uses: node/package}
oyzu --json build package --full --no-cache
  • The first build records any missing selection in oyzu.lock.
  • Lint and format checks prefer project-installed packages. Otherwise preparation installs the exact default quality set in oyzu.lock into the shared tool store. Missing pins or declared-but-uninstalled tools stop the build before export; see Node quality.
  • Oyzu applies the version to a private copy, runs your checks and hooks, then runs npm pack --json --ignore-scripts into a fresh scratch directory. Read the artifact's path, digest and version from the manifest.
  • Failed checks or missing reports prevent export.
  • Tested on Windows x86-64 with Node 22.23.3 and npm 11.11.0. Inferred and Vite packages, pnpm and Yarn packages, and other platforms aren't supported on this path.

For workspace packages, see npm workspaces and Yarn.
