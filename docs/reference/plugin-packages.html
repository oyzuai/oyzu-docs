Plugin packages, the plugin store and lock selections

CLI reference

Published from the canonical docs/reference/plugin-packages.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Experimental. Selects an external builder from a verified, installed package instead of a raw executable path, pins that selection in oyzu.lock, and records the engine identity of every build. The design is the draft external plugin proposal; this page records what is implemented. A package comes from a local archive or an OCI registry named in configuration. The plugin catalog can select a release; its bytes come from such a binding, from the store, or, with no binding, from the OCI route in the verified catalog entry (catalog), through the same installer as an OCI binding. How first-party releases reach GHCR is plugin releases.

Package format​

A package is a .tar.gz or .zip archive holding the plugins-v1alpha1 manifest as plugin.json at its root, and the platform payloads the manifest's runtimes name by entrypoint. tooling/package-plugin.py builds one for the host platform from a built executable:

oyzu exec -- cargo build --locked -p oyzu-plugin-go --features plugin
python3 tooling/package-plugin.py --executable target/debug/oyzu-plugin-go --out go.tar.gz
# prints sha256:<archive digest>

Installation refuses a package that:

  • hashes to a different digest than the one configured (before any extraction);
  • exceeds the archive bounds (512 MiB archive; at most 4096 entries, 1 GiB extracted, 512 MiB per file, depth 16, expansion ratio 100), or contains traversal, absolute paths, hard links, symbolic links whose target leaves the payload, or non-portable names (the shared archive extractor). Relative symbolic links that stay inside the payload are admitted, as for tool archives; an entrypoint must still be a regular file;
  • has no valid plugin.json, or one with unknown fields. Fields naming another plugin (dependencies, preferences, successors) are unknown fields, so peer plugin dependencies are refused;
  • names an entrypoint missing from the archive, not a regular file, or whose SHA-256 differs from the manifest's runtimes[].digest;
  • is not the package the bound reference names (go/app needs package name go with builder profile app) or supports no protocol generation v1alpha1.

Nothing in a package runs during installation: there are no install hooks.

Binding a reference: plugins.packages​

User or machine configuration (never project files or profiles; CONFIG_SCOPE, like plugins.development) binds a builder id to an archive and its expected digest, or to an OCI release:

[plugins.packages]
"go/app" = { archive = "/home/me/plugins/go-0.1.0.tar.gz", sha256 = "sha256:…" }
# or
"go/app" = { oci = "ghcr.io/oyzuai/plugins/go:0.1.0" }

A binding is a user-level default, so it applies only where it is used: only the references this project's targets actually use (explicit uses, or what detection finds) are resolved, adopted or required. A Go binding never touches a Python or Rust project: its discover, run and build neither fail nor write a lock entry for it.

Keys are short references without a major selector; archive is absolute; sha256 is sha256: plus 64 lowercase hex digits. The OCI form is described below. At most 64 entries. A reference may be bound by this setting or by plugins.development, not both (PLUGIN_BINDING_INVALID).

Something outside the project must name the implementation (a project cannot choose code to run), and the digest is the only identity available for local bytes. When the digest is the release digest of the release the catalog selects for the reference, the binding is that release's local archive route and the package must also be the catalog's package and version; any other digest is a local package binding, the explicit-source form. Neither form can bypass a catalog's withdrawal or revocation: a binding of a release a consulted catalog (the last verified copy, an expired one included) withdrew or revoked is refused with PLUGIN_RELEASE_WITHDRAWN or PLUGIN_RELEASE_REVOKED before it is recorded or launched (see plugin catalog).

OCI sources​

A binding can name a release in an OCI 1.1 registry whose token endpoint (if it has one) is on its own origin, such as GHCR, the distribution registry or Harbor, laid out as the Oyzu OCI package contract defines: an immutable release root (an image index) binding the plugin manifest and one manifest per platform payload, with a detached Sigstore signature attached as a referrer of the root.

[plugins.packages]
# Official first-party release by tag: signed by oyzuai/oyzu's plugin-release.yml.
"go/app" = { oci = "ghcr.io/oyzuai/plugins/go:0.1.0" }
# Another registry by tag: say whose signature to require.
"go/app" = { oci = "registry.example.com/team/go:1.2.0", identity = "https://github.com/acme/plugins/.github/workflows/release.yml@refs/heads/main" }
# By digest: the digest is the trust, as for an archive (no signature checked
# unless identity is set or the reference is in the official namespace).
"go/app" = { oci = "registry.example.com/team/go@sha256:…" }

A reference under ghcr.io/oyzuai/plugins/ (also spelled ghcr.io:443/…) is official: it must be signed by exactly https://github.com/oyzuai/oyzu/.github/workflows/plugin-release.yml@refs/heads/main, issued by GitHub Actions OIDC on a GitHub-hosted runner and verified against Sigstore's production trusted root, the same pinning as the tool index. A copy of the workflow on another branch signs as @refs/heads/<branch> and is refused. An official binding with identity or trustedRoot is CONFIG_INVALID_VALUE: configuration cannot replace the official signer or let a private CA vouch for it. Any other tag without identity is CONFIG_INVALID_VALUE at configuration load. These binding rules decide by the reference's namespace and are unchanged.

A release acquired from a verified catalog's route, with no binding, is decided by the package's identity instead (decision of 2026-10-20): a package of the official publisher oyzu requires the same official signer and production trusted root on every route, a company mirror included, and a package of any other publisher is trusted by the digest the signed catalog lists. See route trust.

On a glibc Linux host, when a release has no payload without an ABI or for gnu, oyzu uses its musl payload for that architecture: the contract requires musl payloads to be statically linked, and the official releases ship only musl Linux payloads. A musl entrypoint with an ELF PT_INTERP header (dynamically linked) is refused on a glibc host with PLUGIN_PLATFORM_UNSUPPORTED naming the loader it needs, before it is run. The host's runtime is validated on the extracted candidate before the release is published into the store (a runtime for this host, an executable entrypoint, the static-linking check), so a package this host cannot run is refused without leaving an installed release. An already installed release is not scanned again beyond the checks a launch makes.

Acquisition runs only where an archive would be read (a real oyzu build adopting a selection, or installing a locked release missing from the store). It needs no Docker, ORAS, crane or container daemon and no login: oyzu speaks the OCI Distribution API itself, anonymously, following a registry's Bearer challenge to its token endpoint without credentials, as public GHCR packages allow. A loopback registry (localhost, 127.0.0.1, ::1) is reached over plain HTTP; every other registry over HTTPS through the configured proxy and certificate trust. It fetches, in order:

  1. the release root: by the locked digest, by the binding's digest, or, only at first selection, by tag. The release digest is the SHA-256 of the bytes received, never a registry header;
  2. the signature (when a signer is required): referrers of the root through the referrers API, and the sha256-<hex> referrers tag for registries without it; each Sigstore bundle is verified against the root digest, the signer and the trusted root until one verifies;
  3. the metadata manifest and the plugin manifest blob, checked against the bound reference as for an archive;
  4. this platform's manifest and payload archive only. Other platforms' payloads are never downloaded.

Every object is fetched by digest and must hash to its descriptor (and size) before use; the root must carry the release artifact type, the payload descriptors must match the plugin manifest's runtimes one to one, and the extracted entrypoint must match its manifest digest. Only then is the release published into the store. A tag is resolved once: the lock records the root digest, and later builds, --frozen replays and reinstalls into an empty store fetch that digest, never the tag, so moving the tag changes nothing.

An OCI release in the store holds plugin.json and the payload of the platform that installed it. Bindings by archive and by OCI can name the same release only if their digests agree, which they never do (an archive digest and a root digest differ), so switching a binding's source is an explicit re-adoption (PLUGIN_LOCK_MISMATCH for a digest binding; a tag binding replays the lock).

Not implemented: registries that send clients to a token endpoint on another host (Docker Hub's auth.docker.io): the token realm must be on the registry's own origin, as for every Oyzu registry client; credentials for private registries (anonymous only; a private package fails with PLUGIN_PACKAGE_UNAVAILABLE naming the refusal), organization route configuration (a mirror is listed as a catalog route instead), a tool that populates a mirror, an offline export/import command, and streaming of very large payloads (a payload is held in memory, at most 512 MiB). A catalog's OCI route is acquired from, including an organization catalog's mirror of an official package. HTTPS layout archives follow the same release graph and signer contract, as described below.

HTTPS layout-archive routes​

A verified catalog release can list {"type":"https","url":"https://mirror.example/plugins/go.tar.gz"}. The URL serves a tar or gzip tar of a standard OCI image layout, with oci-layout, index.json and blobs/sha256/<hex> at the archive root. Its index names the catalog's exact release root and any detached signature referrer manifests. See the layout contract. This differs from a local plugins.packages archive: the lock and installed directory use the canonical OCI root digest, not the transport archive hash. Changing from an OCI route to an HTTPS mirror of that root preserves the lock.

The package owner checks the layout and blob digests, root and child descriptor sizes, metadata, selected runtime and extracted entrypoint before installation. Official publisher oyzu still requires its fixed GitHub-hosted release signer and production Sigstore root; a mirror carries the original evidence unchanged. Another publisher uses the root digest admitted by the signed catalog. No catalog field supplies an alternative official signer or signature root.

The shared HTTP transport applies the configured proxy and SSL_CERT_FILE additional certificate trust. HTTPS is required even for loopback. URLs carry no credentials, query or fragment; redirects must remain within the admitted origin and directory. Downloads are anonymous and bounded to 256 MiB. Extraction uses the plugin archive limits (4,096 entries, 1 GiB expanded, 512 MiB per file, depth 16, expansion ratio 100); links and unexpected layout paths are refused. The whole supplied archive is downloaded, even if it includes other platforms; only the host's selected payload is installed. Missing required blobs or signature evidence fail without installing or substituting another release.

For corporate TLS inspection, set HTTPS_PROXY and a PEM SSL_CERT_FILE containing the inspection CA through the existing transport contract. This adds TLS trust; it never changes the official package's fixed GitHub signer, production Sigstore root, admitted catalog route or exact locked release. No project authority flag or global trust-store edit is needed. Loopback endpoints always bypass proxies. Complete native Linux and Windows Go applications passed through a bounded inspecting fixture with missing/unrelated-CA refusals, unchanged lock, usable executable and native JUnit. macOS, OCI and live enterprise proxy qualification remain open; see transport qualification.

Existing binding precedence, catalog withdrawals and organization exclusivity apply before route contact. An already installed release needs no archive request or payload rehash. --offline makes no network request, and --frozen can refresh catalog metadata but never acquires this route. A failed route is PLUGIN_ROUTE_FAILED; invalid graph bytes retain PLUGIN_PACKAGE_DIGEST or PLUGIN_PACKAGE_INVALID, and required signatures retain their signature errors. Restore the exact admitted archive/evidence or route access; builds never choose a newer release to recover from unavailable content.

Store​

Packages live in the tool store (--store, default the shared user store) under plugins/<hex>/, where <hex> is the release digest (the archive digest, or the OCI release root digest). Releases sit side by side; a platform payload is selected from the manifest at launch. Installation takes a per-digest lock, so concurrent first builds extract once and the others reuse the published release; the release is published by an atomic no-replace rename, so readers never see a partial extraction. A shared lease on the release is held for the whole invocation to protect running executables (relevant on Windows). An installed release is trusted: later builds do not hash it again, and only a missing release needs the archive.

Explicit revoked-copy maintenance​

oyzu plugins prune is an explicit local store-owner operation. It previews selected exact digests by default and requires --apply to remove a currently revoked copy. It uses the current verified applicable cached catalog without network refresh. Ordinary withdrawal and expired or unverified revocation evidence cannot authorize deletion.

The store serializes maintenance with the existing digest mutation lock, then takes the exclusive existing plugin-use lease. It checks the anchored manifest's package/version against the exact revocation, and checks filesystem structure without hashing installed payloads. Active cooperative users and uncertain, malformed, linked or inaccessible content are retained. Windows also checks exclusive writable access before removal to detect open or mapped executables. Uncooperative filesystem changes and later operating-system failures can still interrupt removal; the result explicitly reports incomplete, not retained.

Effects are limited to plugins/<hex> and exactly identified package-contents/plugin-<hex>.json. Optional placement metadata is not a recovery hold: its absence does not prohibit cleanup, but damaged or mismatched metadata is retained for inspection. Identifiable metadata left after an interrupted root removal can be selected again. The permanent locks/plugin-<hex> and locks/plugin-<hex>.lease files, other releases, catalogs, tool installations and every project lock remain unchanged.

No global reference index or retention framework is introduced. This operation does not claim the release is absent from other projects' locks, and the normal installer may reacquire content when a future selection is eligible. To recover a project that still selects a revoked release, explicitly adopt an eligible alternative with plugins update; pruning never changes that selection on the user's behalf.

The revoked-copy maintenance qualification records the Windows and Linux real application flows, refused removals and remaining platform limits.

Lock selections​

First resolution writes the selection to oyzu.lock in the project root under the lock-edit transaction. The selection is appended to the file's existing bytes, so other records, comments and ordering are untouched:

[[plugin]]
reference = "go/app"
profile = "app"
package = "oyzu/go"
major = 0
version = "0.1.0"
release = "sha256:…"

[[plugin.payloads]]
os = "linux"
arch = "amd64"
digest = "sha256:…"
FieldMeaning
reference, profileThe logical reference and its profile
packageCanonical publisher/name

releaseArchive digest, or the OCI release root digest (the catalog's root_digest)
payloadsExecutable digest per platform runtime, from the plugin manifest (for an OCI release, every platform the root binds; the root digest binds the platform manifests themselves)

Machine-local paths, acquisition times and the platform an invocation used are not recorded. The schema is the in-place plugin and engine additions to tool-lock.schema.json; there is no new lock version. A lock keeps its [[plugin]] entries through oyzu pin and other tool operations.

Only a real oyzu build (not --plan or --check) may install a bound package and record a new selection, and only oyzu plugins update may install a release to replace a selection already locked. Every other command that discovers the project (build --plan, build --check, run, discover, lock --check, …) replays the lock and the store and writes nothing.

A lock that holds only a plugin selection does not count as pinned tools: a fresh project's first oyzu build still resolves and pins the tools its builders need (for example oyzu:go). Builds of different projects sharing a store converge: a build whose tool pinning loses a race on the lock reuses the pins the other build published (or retries for up to 30 s) instead of failing with PIN_EDIT_CONFLICT. Two builds of the same workspace are not allowed at all; the second is refused cleanly.

Offline native builds also need their ordinary tool metadata in the same user context. tools check --catalog --json seeds the configured signed tool index in the default user metadata store; adding --store DIR targets that explicit store instead. An explicit plugin store does not replace the default metadata used by native Go's locked-version withdrawal check. Prepare both required contexts online rather than copying caches or weakening offline checks.

Catalog revocations refuse installed releases, including during expired-history replay. Explicit revoked cleanup is a separate store-owner operation; selection refusal does not delete bytes. Limits: @vN major selectors in bindings are not implemented. Locked selections are updated with oyzu plugins update.

Engine identity and pin​

Every build records the actual engine (Context Engine fact and the retained inventory {"engine":{"identity","pinned"}}). The identity is the version token of oyzu --version (for example 0.1.0-local.36bdcec27267.dirty, without the profile, target and timestamp). An optional exact pin is written by hand:

[engine]
identity = "0.1.0-local.36bdcec27267"

An applicable protected administrative policy can require this pin and a complete lock. The policy-required pin contract describes its candidate enforcement and qualification status. CI or release context alone leaves the pin optional.

A different pin uses exact native engine staging before semantic discovery or plugin resolution when an allowed user/system source explicitly admits its development archive. Missing admission fails with ENGINE_PIN_MISMATCH. Staging preserves the installed frontend and project lock. An explicit development override retains the invoked executable when independently permitted, recording actual content and the bypassed pin without changing shared selections.

Package role features are requirements on the running engine. The preview builder supports go-test-events; unknown required features or unsupported role contracts fail with PLUGIN_ENGINE_REQUIREMENT before plugin operations, on first acquisition and warm replay. The message names required capabilities and the actual engine, and directs selection of a supporting admitted engine or a compatible plugin. No guessed minimum version or stable compatibility promise is inferred from development version labels. Catalog eligibility applies the same supported-feature rule.

Which bytes run, and how output records them​

A package's entrypoint is launched in place: it is the immutable store file whose digest was verified at installation. A plugins.development executable is copied to a private per-invocation file and hashed while it is copied, so the digest recorded is the digest of the bound file as launched (for a wrapper script, the script only: what it starts is not covered, so its targets are never reused from the action cache); replacing the source afterwards changes nothing in the invocation, and a second workspace discovery in the same invocation reuses the copy without hashing the source again. The copy is disposable, so it is not flushed to disk. The private copy is removed when the command finishes.

Action keys bind the plugin identity (reference, package release and version, executable digest and runtime) recorded on each plugin-built target as extensions["oyzu.dev/builder-plugin"]; see external builder targets.

Every plan, execution envelope and manifest of a build or oyzu run carries extensions["oyzu.dev/plugins"] when an external builder is bound (the plan digest therefore covers it), so plugin-built output is distinguishable from built-in output:

{"reference":"go/app","source":"package","package":"oyzu/go","version":"0.1.0",
 "release":"sha256:…","executableDigest":"sha256:…","selection":"adopted"}
{"reference":"go/app","source":"local-development",
 "executableName":"plugin","executableDigest":"sha256:…"}

A development record keeps only the executable's file name, never the user's absolute path; executableDigest is the identity. Nothing refuses to publish plugin-built output; the record only makes it visible. oyzu inspect requires the records to be identical in the plan, manifest and envelope (see build bundles).

oyzu run --store DIR, oyzu scan --store DIR and oyzu lock --store DIR move the plugin store with the tool store, as oyzu build --store DIR does.

Known limit: the private copy of a development executable is removed when the command finishes normally; if the process dies from a signal it stays in the temporary directory as oyzu-plugin-*, to be deleted by hand.

The invocation's bindings are fixed by the first discovery. A later discovery in the same process that asks for a different set (another executable, changed bytes, another reference) fails with PLUGIN_BINDING_CONFLICT instead of silently replacing the builders already handed out. The set is still a process-wide lookup, which is service-locator debt this page does not hide. The sites that read it directly are:

Remote execution is not qualified by those paths. Moving the lookup onto the workspace is left for when a second binding source per process exists.

Captured Go application planning (draft implementation)​

Issue #730 adds captured-plan to the existing plugin protocol. This path is under qualification; the published preview is not claimed to provide it. A locally admitted development package must declare the capability and contain both the host and selected Linux execution payloads. The host runs discovery roles; the Linux member runs captured-plan on read-only source, supplying build, artifact and test-report intent. Core supplies version, output paths, exact locked tools, immutable dependency inputs and execution controls. The plugin cannot use observations or acquire dependencies in this role.

The bounded implementation supports a single conventional Go application module with one main package, a matching Linux artifact/execution platform and the process container executor. It requires an admitted multi-platform engine archive, a usable immutable Linux environment, and a locked Go tool for that platform. Use oyzu build app --isolated --platform linux/amd64 --full with the Linux platform declared in build.yaml. Local native defaults are unchanged. Raw executable development bindings, Go libraries, workspaces, missing capabilities and unsupported execution controls fail explicitly.

The existing Go preparation provider owns native checksum validation, broker acquisition and the local module proxy. Its retained native metadata adapter remains existing implementation debt; the new planner and export orchestration are compiled Rust. Warm/offline preparation requires every exact input to be retained; a missing input fails without networking. The frozen dependency record binds engine archive/member, host and execution plugin members, environment, tool archives and the accepted plan. Required JUnit and Go coverage reports remain gates. A changed package control or missing engine never selects a baked fallback. See the first-proof contract for remaining functional qualification and explicit exclusions.

Captured npm applications​

The implementation in issue #789 extends the same package and engine contracts to npm node/app applications. The local Linux proof passed; this is not a capability claim for the published preview package. The matching development package must declare captured-plan and supply the selected Linux member.

Core prepares the locked Node/npm archives and dependency inputs, then performs the required offline install before the plugin's build and check operations. The plugin supplies intent; it does not acquire dependencies during planning. Required JUnit and LCOV reports pass through the common report gates, and project-written dist is retired only in the private execution workspace and exported with the common artifact containment checks.

The bounded command is oyzu build app --isolated --platform linux/amd64 --full --frozen --image npm=<admitted-node-seed>, with tools selected in oyzu.toml and resolved in oyzu.lock. It requires the same admitted engine assets and immutable Linux image as captured Go. Missing package capabilities, required reports, locked inputs or compatible assets fail explicitly. Yarn, workspaces and frameworks are outside this extension. See the captured npm proof and scope.

Captured pnpm uses the same package/engine contract with its own dependency provider, selected Node/pnpm archives and native offline setup. The provider's native-store export currently requires pnpm 10.11.0. Select that exact stable release in packageManager or the ordinary tool cascade and keep the native pnpm-lock.yaml and oyzu.lock current. The analogous command uses --image pnpm=<admitted-node-seed>; tools remain outside build.yaml.

The image must run the admitted engine's ABI and provide the existing pnpm adapter's YAML module at /opt/oyzu-pnpm/node_modules/yaml. A bare Node or Rust image is insufficient. The repository's pnpm image provisioning supplies that module from its committed npm lock. The selected Node and pnpm archives still determine the tools used by preparation and execution.

For a small compatible image, the following provisioning recipe is illustrative; build it from the repository root with both image arguments set to admitted immutable inputs. It installs runtime libraries, without a compiler toolchain, and retains the actual YAML license and acquisition lock:

ARG NPM_IMAGE
ARG RUNTIME_IMAGE
FROM ${NPM_IMAGE} AS yaml
COPY tooling/images/node-pnpm/package.json tooling/images/node-pnpm/package-lock.json /opt/oyzu-pnpm/
RUN npm ci --prefix /opt/oyzu-pnpm --ignore-scripts --omit=optional --no-audit --no-fund
FROM ${RUNTIME_IMAGE}
RUN apt-get update && apt-get install --no-install-recommends -y libstdc++6 libatomic1 && rm -rf /var/lib/apt/lists/*

Captured npm packages​

Status: experimental. The N4b candidate in PR #843 connects captured single-root npm node/package output. The bounded Windows x64 coordinator/Linux amd64 GNU worker archive, offline consumer, refusal gates and scoped repository checks passed. No published plugin, GNU-host or additional-platform qualification is implied.

Use package intent when the result must be installable by npm, rather than an application directory. The bounded candidate requires a native package.json with a package name and build script, its current npm lock, required checks, selected Node/npm tools and an admitted matching plugin/engine package. Raw development executable bindings cannot provide the captured execution member. The demonstrated worker selects Node 22.23.3, npm 11.11.0 and Linux amd64.

The verified example uses this package intent; supply your admitted image:

builds:
  package: {uses: node/package}
oyzu build package --isolated --platform linux/amd64 --full --frozen --image npm=<admitted-compatible-image>
oyzu inspect dist

Tools belong in the ordinary oyzu.toml cascade and resolved identities in oyzu.lock; the native npm lock owns dependencies. No output setting is added. The plugin supplies captured semantic intent and a frozen primary file source. After the provider validates the native lock and installs offline, compiled Node execution projects the core-resolved version into private package/npm lock metadata, runs the selected build/checks/hooks, then invokes native npm pack --json --ignore-scripts --pack-destination <fresh-directory>. The source checkout and its original locks remain inputs, not projection targets. Packing allocates its fresh directory from the explicitly declared executor scratch mount outside package input, independently of authored TMPDIR values.

Native npm owns the packlist and archive. The compiled owner validates one inventory entry's package name/version and contained regular archive, then normalizes that exact file into the planned .tgz. It does not guess npm's filename or scan for another archive. Read the artifact's recorded manifest path, version and digest; consumers must not construct a native filename. The logical producer remains the build, with native pack/export actions recorded in the plan. JUnit/LCOV and configured quality/report gates remain engine-owned.

To verify a delivered package, a fresh project can install the exact archive offline with an empty private npm cache, then import its installed export. The bounded harness verified the real example's greeting and installed version in a separate network-disabled container with only the delivered archive, selected completed Node/npm tool volumes and consumer code mounted read-only. The source checkout and dependency tree were absent; the fresh consumer installed offline with an empty private npm cache. The qualification records the 402-byte archive, actual JUnit/LCOV and separately retained refusal stages.

FailureBehavior and recovery
Missing native lock, incompatible package/engine or non-npm/workspace targetRefuse the bounded lane; supply current admitted inputs or use a separately supported flow. No built-in fallback is implied.
Native lock mismatch or install failureStop before private version projection; regenerate the native lock through native tooling, then update/review frozen inputs.
Selected action, required report or native pack failureBlock successful archive export and retain failure evidence. Correct the failure and rerun the affected scenario.
Inventory identity mismatch, unsafe path or missing archiveFail packaging rather than collect a guessed or stale file. Inspect the retained native packing log and frozen package/version intent.

Packing ignores npm pack lifecycle scripts, matching the built-in package operation. Native host packaging, pnpm/Yarn packages, workspaces, Vite and other platforms are outside this candidate. Acquisition retains existing trust/network controls; execution installs captured inputs offline and packing gains no network or tool-selection authority. Source/schema compatibility remains the unreleased v1alpha1 contract; no migration/version successor is introduced. See the design brief for functional acceptance and separately deferred qualification.

Verification​

The company/offline native qualification records real signed company HTTPS acquisition and locked offline application builds on Windows MSVC and GNU Linux, with missing-content, expiry and retained revocation controls. Installed payloads and receipts were neither copied nor rehashed; generated applications, native reports and committed locks were checked.

Store, lock and schema behavior has unit tests (src/tools/store/plugin.rs, src/tools/lock/tests.rs, src/tools/plugin_package/oci.rs), compiled-CLI tests (tests/integration/plugin_packages.rs, plugin_oci.rs, tool_lock.rs) and the shape check python3 tooling/check-tool-contracts.py. plugin_oci.rs runs the CLI against an in-process loopback registry that demands the anonymous token flow, with signatures from a test-only Sigstore instance. Acceptance held: PLG-PKG-02 (substituted bytes rejected before launch, archive and OCI), PLG-PKG-03 (a new platform payload is a new root; the old lock is never satisfied by it), PLG-PKG-04 (concurrent first installs publish once), PLG-PKG-08 (native package acquired from OCI without Docker or login), PLG-PKG-09 (missing payload or signature, or no payload for this platform, fails naming it, with no fallback), PLG-COMPAT-03, 04, 05, 10 and 11. The recorded end-to-end run on examples/builds/go-app/project is in implementation status.
