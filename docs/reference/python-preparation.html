Captured Python package preparation

CLI reference

Published from the canonical docs/reference/python-preparation.md file. Features marked experimental remain experimental; check support limitations before relying on them.

A captured python/package or python/app build first prepares its Python dependencies: a worker with access only to the public PyPI broker routes downloads binary wheels, then every build, test and quality action installs them offline. This page describes which authored inputs preparation reads and how it treats dependency-group includes, editable references to the project itself, dynamic versions and locked packages that must be built from source. Native pip, uv and Poetry semantics stay with those tools; Oyzu reads only the declarations listed here.

Selected interpreter and manager runtime​

Captured builds use the project CPython selection already resolved in oyzu.lock from [tools].python and supported native requirements. Ordinary oyzu pin records that selection; oyzu build --isolated --full --frozen consumes it without rewriting the lock. The existing Python provider supplies the Linux archive, verified against its locked digest and restored read-only through the executor. An explicit selection missing its locked platform recipe refuses with recovery guidance instead of silently using the image's Python. Offline acquisition needs the exact archive to be cached. Managed connector restrictions remain binding.

That interpreter governs markers, dependency inventory, pip downloads, wheel compatibility, project-version facts, virtual environments, source builds and tests. The same frozen archive and executable are retained for modern packages, legacy setuptools projects and application plans. Authored actions see the selected interpreter on PATH; the compiled adapter uses its exact executable. Dependency evidence records oyzu.dev/locked-tool independently of the image's package-manager identity and the selected Oyzu engine.

Poetry has a separate manager runtime: its exporter and manager-version API run in the image interpreter where Poetry is installed. Preparation does not replace that interpreter's PATH. uv continues to receive the project interpreter explicitly with managed Python and downloads disabled. The image still supplies the selected package manager and any native compiler/library prerequisites; choosing CPython does not rebuild or replace those image constituents.

A dependency context requested by a consumer image is different: its runtime-only pip/uv/Poetry preparation uses that consumer's interpreter, markers and compatibility. It does not inject the producer project's CPython archive. This preserves the consumer's runtime contract rather than treating a build tool as a deployment pin. The consumer's effective configuration is still checked before preparation: an explicit or policy-supplied Python pin is not waived by runtime-only mode. A conflicting pin refuses rather than silently choosing the image's interpreter. The implementation status records the demonstrated pip, uv, Poetry, legacy package, application and runtime-consumer flows, with their exact qualification limits. Legacy setup.py projects with runtime dependencies still refuse because metadata-driven legacy dependency acquisition is not implemented; selected-interpreter support does not remove that restriction. Legacy package versions bind to the captured shared version decision and its target input digest, which can differ from the whole workspace snapshot digest. Planning refuses metadata that disagrees with that decision or its source suffix.

What preparation captures​

The worker collects these declarations from the captured source:

InputPurpose recorded
project.dependencies in pyproject.tomlruntime
build-system.requires (or native locked legacy tools, with fixed defaults for unselected tools)build
The dev dependency group, with its includestest
requirements.txtruntime
Default test and quality tools not already declared or lockedbuild or test

A uv project contributes its native uv export --locked closure and a Poetry project its native lock export. That complete hashed export owns the selected project and group closure. Supplemental backend, requirements-file and injected tool requirements are resolved by native pip with the native registry lock as constraints, retaining their original extras and transitive dependencies. A pip project continues to resolve its complete declarations. Every original root remains available to native dependency inventory validation; separating download roots does not remove extra activation, closure/version checks or the guard against downloading a package already selected for a source build. Every wheel is digest-recorded in the dependency snapshot.

An authored build-system.requires remains authoritative, including native conflicts with a lock. When it is absent, the implicit setuptools/wheel backend uses active requirements already selected by the native lock. Only an unselected tool receives the fixed fallback (setuptools==80.9.0 or wheel==0.45.1). Native packaging interprets names and environment markers; every active locked constraint is retained for pip to resolve. No lock is refreshed and no authored requirement is dropped to make a conflict disappear.

The current package as a quality tool​

A captured package/library can itself provide the selected native quality tool, as when building Black with Black formatting. The offline build installs the project's wheel before quality checks, so those checks use the installed tool. Oyzu omits only the implicit quality fallback whose native canonical name equals the current package name; it does not download a second public copy of that package. Explicit requirements and native locked constraints, build/test-runner defaults, ordinary tool acquisition and required failure/report gates remain unchanged. This does not change app or runtime-only preparation or execute project/backend code during acquisition. The affected native Black replay passed offline preparation/build and actual installed self-formatting; its required coverage and lint failures still block full package delivery. See the qualification result.

Dependency-group includes​

[dependency-groups] follows PEP 735. An entry is either a requirement string or an { include-group = "name" } table, and an include is expanded in place. Group names compare after PEP 503 normalization, so Runtime_Checks and runtime-checks name the same group:

[dependency-groups]
dev = [{ include-group = "tests" }, "pytest-cov==6.0.0"]
tests = [{ include-group = "runtime-checks" }, "pytest==8.3.5"]
runtime-checks = ["packaging==24.2"]

Preparation captures packaging, pytest and pytest-cov as test inputs. An include of an undefined group, a group defined twice under equivalent names, a cyclic include or any other table entry fails preparation with a diagnostic naming the group. Only the dev group is selected, matching uv's default; for uv projects the native export applies the same includes.

The project itself as a requirement​

Requirements files commonly install the project under development, as in -e .[cli], and dependency groups commonly reference the project with extras, such as name[tests]. The project is built from the captured source, so preparation never downloads it. Such a reference is replaced by the requirements that installing the project adds: project.dependencies and the project.optional-dependencies tables for the selected extras, following extras that reference the project again. Extra names compare normalized. An undefined extra fails preparation, and a reference whose environment marker does not apply to the build interpreter is skipped, as pip skips it.

The editable forms accepted in requirements.txt are -e ., -e ./, --editable . and --editable=., each optionally followed by [extras]; the project needs a static project.name. Every other directive, including -r, -c, an editable path to another directory and option lines, still fails with Unsupported requirements directive; no alternate source fallback.

Current-project dependency back-edges​

In a package/library build, an exported dependency can itself require the current project, including an extra: for example, a Litestar plugin requires litestar[cli]>=2.0.1. The current project is built from captured source, so it is a provider for that dependency without being downloaded or represented as an external package ID. Native inventory checks its declared base requirements, requested optional groups and their captured closure using native marker and extra semantics. Unknown extras, missing dependencies, unapproved direct URLs and a duplicate downloaded/source identity fail. Dynamic dependency metadata cannot establish this closure without backend execution and is refused.

The original source version is not assumed equal to the final snapshot version. Active back-edge constraints remain explicitly pending in private prepared metadata. At the start of the existing package prepare action, after the private project version is bound to the shared version decision, native PEP 440 checks compare every pending constraint with actual OYZU_VERSION. A missing planned version, identity mismatch or incompatible constraint fails before creating the venv, installing dependencies or running a source backend. Acquisition does not run project code or invent a version for dynamic metadata. This provider is not available in app or runtime-only dependency contexts.

Dynamic versions​

A project may list version in project.dynamic instead of declaring it. For the selected pdm.backend, this native declaration supplies a version without running the backend or importing project code:

[project]
name = "example"
dynamic = ["version"]

[build-system]
requires = ["pdm-backend"]
build-backend = "pdm.backend"

[tool.pdm.version]
source = "file"
path = "example/__init__.py"

Oyzu reads that captured UTF-8 file and follows PDM's default syntax: the first line matching __version__ = "1.2.3" or VERSION = '1.2.3' wins, including an optional trailing comment. Native packaging.Version validates and normalizes the literal, and the existing shared version inference selects its source snapshot. The recorded nativeVersion retains the native value; wheel/sdist metadata carries the selected snapshot. Actual native PDM metadata, installed-artifact tests/coverage and an independent offline delivered-wheel consumer passed on Linux; see the bounded proof.

The path must be relative, contained in admitted captured source, free of links or reparse points, and name a regular file no larger than 4 MiB. Unsafe or missing paths, invalid UTF-8, a missing default literal and an invalid PEP 440 version fail preparation; correct the native declaration or version file and rerun. No project code in the file executes while facts are acquired.

Other dynamic forms retain name-only facts and tag-based inference: setuptools [tool.setuptools.dynamic] version = { attr = ... }, Hatch file/VCS providers, PDM call/SCM/custom-pattern providers, and PDM projects with backend-path, a configured tool.pdm.build.custom-hook or conventional pdm_build.py. These providers are not executed during preparation or claimed as native file facts. Without applicable tags their base remains 0.0.0, giving a PEP 440 snapshot such as 0.0.0.dev0+g0123456789ab; the native strategy fails with version-needs-native when no native version is available.

In its private build tree the build removes version from project.dynamic, removes tool.setuptools.dynamic.version when present and writes the selected snapshot as the static project.version, so the wheel, sdist and their metadata carry the same version. The checkout keeps its dynamic declaration. A pyproject.toml without either a static or a dynamic version still fails with Python project version must be static or listed in project.dynamic.

Packages built from source​

Some locked packages have no wheel to download: a uv.lock package whose source is a Git repository pinned to a commit, and a uv workspace member or path dependency, which uv export lists as -e ./PATH or ./PATH, and a registry package that uv.lock locks with only a source distribution (sdist) and no wheel. Following the maintainer decision of 2026-10-10, these are built from source, but the build runs only inside the isolated, network-denied build worker, never during preparation:

  1. Preparation splits these lines from the native export. Only registry lines are downloaded with their hashes; a project or group declaration that names such a package is satisfied by its source build and is not downloaded. This includes a declaration that repeats the source as a direct URL, such as advanced-alchemy @ git+https://github.com/... in an extra or dependency group, when uv.lock pins that package to a Git commit or member. A direct URL for a package that is not built from a locked source is still refused. A registry package with an sdist and no wheels in uv.lock is removed from the wheel download and treated as a source package of kind sdist. Its sdist is downloaded from the files.pythonhosted.org route of the scoped broker, checked against the SHA-256 in uv.lock (a missing hash or a URL outside that route fails preparation), and unpacked by Oyzu without running any of its code. Only regular files are written, names must be portable with one top-level directory, and archives are limited to 256 MiB. The tree is stored under sources/ and then follows steps 3 and 4. A package with any wheel keeps the wheel download.
  2. Each Git source is fetched at the commit uv.lock records, with the native Git client through a read-only route of the scoped broker. Only public HTTPS GitHub repositories have routes, as for Cargo Git sources. The checkout's tree, without Git metadata, is stored under sources/ in the prepared tree. No hooks, filters, submodules or credentials are used.
  3. Preparation reads each source's build-system.requires from its pyproject.toml (or native locked legacy tools, with fixed fallbacks, for a setup.py package without it) and captures those requirements as build wheels, resolved with the lock's constraints. No backend or package code runs.
  4. In the build worker, after the captured wheels are installed, each source is copied into the private build state and built with pip wheel --no-index --no-deps --no-build-isolation, so the backend and its requirements come only from the captured set. A build requirement missing from that set fails before the build runs. The wheel must carry the locked name and version; the wheels are then installed from a manifest of their digests with --require-hashes, and the project builds and tests against them.

For example, with this declaration uv locks sampleproject at the commit, and preparation records it with sourceId python-git-0:

[project]
dependencies = ["sampleproject"]

[tool.uv.sources]
sampleproject = { git = "https://github.com/pypa/sampleproject", rev = "621e4974ca25ce531773def586ba3ed8e736b3fc" }

The dependency snapshot records each Git source as a package whose digest is that of its captured tree, with verification digest-only, and lists every source package with its kind, path, commit, purpose and build requirements in the oyzu.dev/python-sources extension; an sdist source also records its URL and SHA-256, and its package record uses sourceId pypi. Workspace members are part of the captured project source and have no separate package record. Because Git metadata is not captured, SETUPTOOLS_SCM_PRETEND_VERSION is set to the locked version during the source build, so backends that read the version through setuptools-scm or hatch-vcs use it.

A source whose build requirements include maturin or setuptools-rust needs a Rust toolchain and Cargo crates, which Python preparation does not capture. Preparation fails naming the requirement before any build runs, as for the maturin-built pydantic-core workspace member of pydantic. Python applications (python/app) whose runtime closure includes a package built from source fail at packaging, because application archives install captured wheels only; runtime dependency contexts for Docker refuse such packages during preparation.

Private build state​

The build worker keeps everything it creates for a Python target outside the project tree, in /out/.oyzu-python of the target's private output root:

PathContents
venv/Build environment with the captured wheels and source builds installed
dist/Native wheel and sdist before packaging copies them
sources/, source-builds/, source-wheels/Copies and wheels of packages built from source
application/, application-project/, application.pyz, test-application/Application staging, archive and its extracted test copy

The output root persists across the target's actions and is never inside /workspace, so a project at the workspace root is covered too. Native build backends therefore cannot pack the build environment into the sdist (hatchling and other backends that include untracked files did, issue #315), and Ruff, Black and Flake8 check only project files without an added exclusion. Packaging still copies artifacts to the target's bundle directory /out/<target>/<platform>/ (named to the adapter as OYZU_OUTPUT) and reports are written to its reports/ directory, so bundle locations follow the shared bundle layout.

The state is private to the worker and not an input or output contract. Project hooks that ran against the former .oyzu-build/ folder inside the project no longer see it there. A Python target has no stage contract, so the action cache reuses it only as a whole target and never needs to restore this state.

Failures and recovery​

Preparation failures stop the build before any action runs and retain the worker diagnostic. Correct the authored input and start a new build.

DiagnosticCause and recovery

An editable project reference needs a static pyproject.toml project nameDeclare project.name statically

Git source NAME uses submodules, which preparation does not fetchThe locked commit has a .gitmodules file

Limits​

  • Source builds. Git sources, sdist-only registry packages and local members are built from source only for uv; Poetry Git and path sources and pip requirements-file Git or path lines are still refused. Git sources need a public HTTPS GitHub repository and a full commit; sdist-only packages need files.pythonhosted.org sdists in uv.lock and are refused in runtime contexts and applications like other source builds; submodules and Git LFS content are not fetched. Sources that build Rust (maturin, setuptools-rust) and other non-Python build toolchains beyond what the build image provides are not captured. A source package that is itself the build requirement of another source is refused, environment markers on member lines are refused, and virtual members are skipped as uv skips them. These choices are provisional and conservative.
  • Source build evidence. The source-built wheels are not reproducibility checked; their bytes come from the backend run in the build worker, and only the source tree and captured build requirements are digest-recorded.
  • Stale Poetry locks. A lock whose content hash no longer matches the project is rejected, as poetry install rejects it; Oyzu does not refresh or tolerate it. Confirmed by the maintainer on 2026-10-10.
  • Dynamic version evidence. Only the selected PDM default file form above supplies declarative native version facts; other computed versions use tags. Other dynamic metadata, such as dynamic dependencies, is not computed.
  • Groups. Only dev is selected; selecting other groups is not configurable.

Verification​

python tooling/test-build-scenarios.py --suite python --only python-captured --cli <compiled-cli> selects full checks and captured execution through its registered wrappers. It builds pip and uv fixtures with dependency-group includes, a pip project whose requirements.txt installs itself with an extra, a setuptools project with a dynamic version, a PDM default file-version project with an independent delivered-wheel consumer, explicit optional prerequisites/native formatter scope, uv workspace and local-path dependencies, a uv Git source pinned to a pypa/sampleproject commit, a uv sdist-only registry package (pyperclip 1.9.0), a real registry wheel depending on that locked source build, legacy root/member backends with native locked setuptools, and a positive Poetry main/dev export. Each successful build must retain unchanged source/lock bytes, deliver wheel/sdist artifacts, and collect passing installed-artifact tests and coverage with measured hits. Git dependency tests also exercise the project's installed module. Refusal cases cover cyclic includes, missing extras, external editable paths, unapproved direct URLs, maturin members, and stale uv/Poetry locks; they must retain unchanged authored inputs and deliver no successful artifacts.

Fixture lock setup uses the provisioned uv/Poetry images with --pull=never; network access there authors a native lock before the captured build starts and is not an execution fallback. When fixture setup needs a custom certificate authority, explicitly set SSL_CERT_FILE to a readable regular CA bundle. The harness mounts it read-only for native lock acquisition and supplies its path to uv, Requests/Poetry and Git, preserving TLS validation. An invalid explicit path fails before Docker starts. This fixture setting does not change captured-build trust or add the CA to an image.

The registered captured/full group passed all 22 expected outcomes on Linux: 14 successful artifact flows each collected passing installed-artifact tests and coverage, seven required preparation refusals emitted no actions/artifacts, and one required formatter failure retained real passing tests/reports while blocking every artifact. Source/lock guards and compiled inspection passed. The PDM flow additionally executed its delivered wheel independently offline. For stale uv declarations, the pinned native tool refuses offline resolution before its stale-lock diagnostic; a separate freshness guard is not claimed from that case. All eight affected pinned corpus baselines ran; Attrs completed its installed artifact/test/report/package flow, while the other repositories retained explicit failures or refusals. The captured helper, backend, transitive-source and Poetry fixtures passed. Litestar's real offline prepare/build corrections passed, but its own snapshot parser blocks collection/reports/package exports; that remains a named upstream compatibility outlier. Configured FastAPI selects its declared all extra and native formatter scope, clearing the earlier optional-CLI failure. Its installed tests report 3595 passed, one telemetry prerelease conflict and 22 skips; native Ruff rejects three translation-test Markdown fixtures and one skills reference document. Required reports are retained and packaging remains blocked. Black's implicit self-tool correction passes native prepare/build and actual installed Black formatting. Its 556 passing native tests and three skips still yield a failed test action because mandatory Cobertura is missing: native coverage configuration omits installed site-packages. Native Flake8/pycodestyle also crashes on its existing invalid-escape token fixture. No Black artifacts are exported. These distinct configured replays do not replace the original pinned baselines or imply corpus success. See captured Python completion for exact revisions, tools, native evidence, remaining scenarios and corpus obligations. The Rust unit tests in src/builders/python/adapter/requirements.rs cover include expansion, normalized names and the accepted editable forms, and those in src/builders/python/adapter/sources.rs cover Git source admission, export splitting and member lookup. Unit checks supplement the compiled native proof; they do not qualify the remaining source forms or pinned corpus.

Native coverage omits the installed package​

Installed-artifact tests measure the installed package, not the checkout. A native coverage configuration such as [tool.coverage.report] with omit = ["*/site-packages/*"] can therefore exclude every measured package file: native assertions may pass while coverage reports No data to report and the required Cobertura report is missing. The test action fails and packaging stays blocked. Narrow or remove that exclusion in the project's native coverage configuration so the installed package remains eligible, then rerun and retain the configuration change as an explicit captured input. Do not substitute checkout-only coverage, suppress the required report or infer coverage success from pytest's passing assertion count. This recovery guidance does not claim a configured Black coverage rerun has passed. See Python artifact testing.
