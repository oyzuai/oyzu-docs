Python dependency preparation

CLI reference

Published from the canonical docs/reference/python-preparation.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Before an isolated Python build runs, Oyzu prepares your dependencies. A worker that can reach only PyPI downloads binary wheels, and every build, test and quality step then installs them offline. This page explains which inputs Oyzu reads and how it treats dependency-group includes, editable references to your own project, dynamic versions and packages that must be built from source. pip, uv and Poetry keep their own behavior; Oyzu reads only the declarations listed here.

Note: Python builds are experimental. An isolated build needs Docker and the base execution image, plus any system libraries your dependencies need. See Python applications.

Isolated pip packages​

The python/package builder (also available as python/library) and python/app come from the oyzu/python plugin package. The plugin reads your project files, picks the package manager and quality tools you already use, and declares the commands, reports and artifacts. Oyzu itself downloads dependencies, runs the steps offline and checks the reports.

If the plugin refuses a project, the build fails. There is no fallback to another builder.

An isolated pip build needs a plugin package built for Linux, not a raw development executable. See plugin packages. A Linux environment image and its system libraries are also required; choosing a CPython version does not provide them.

Selected interpreter and manager runtime​

An isolated build uses the CPython version recorded in oyzu.lock. It comes from [tools].python and from your project's own requirements (requires-python, .python-version). oyzu pin records the choice, and oyzu build --isolated --full --frozen reads it without rewriting the lock.

  • Oyzu checks the CPython archive against its locked digest and mounts it read-only in the worker.
  • If the lock has no entry for the platform, the build stops and tells you how to fix it. It never falls back to the image's Python.
  • Offline builds need the archive already cached.

That one interpreter is used for environment markers, dependency inventory, pip downloads, wheel compatibility, the project version, virtual environments, source builds and tests. Your own task commands see it first on PATH.

How each manager uses it:

ManagerInterpreter
pipThe selected CPython
uvThe selected CPython, passed explicitly. uv's managed Python and downloads are turned off
PoetryThe exporter runs in the image's own interpreter, where Poetry is installed. Your PATH is unchanged

The image still supplies pip, uv or Poetry and any compilers or system libraries you need.

A Docker image that asks for runtime-only dependencies uses its own interpreter, markers and compatibility, not the producer project's CPython. If a Python pin from your configuration or policy conflicts with that interpreter, the build fails.

Legacy setup.py projects with runtime dependencies are refused. A legacy package takes its version from the shared version decision, and planning fails if its metadata disagrees.

Native pip full-build environment​

A native python/package pip build runs on your machine, not in a container. Supported on Linux x86-64 (glibc).

Oyzu installs the managed CPython and, before copying your source, reads its runtime. You provide the dependencies:

  • With no .venv in the target, Oyzu uses the managed CPython directly.
  • With a .venv, it must be a standard virtual environment created from that exact managed interpreter, with system site packages off. A mismatch fails the build.
  • A linked or shared environment root, or a source input inside .venv, fails the build. Ordinary interpreter symlinks inside a valid environment are fine.
  • Each check has a 20-second limit.

Install your project dependencies, pytest, pytest-cov, coverage and the quality tools you use into your own .venv by running the managed interpreter. Oyzu does not install them, copy the environment or repair it, and the source copy leaves .venv out. Missing packages fail as usual, and offline builds need them already present.

The interpreter is used for the wheel build and for pytest and coverage reporting. Ruff runs from the environment's own entry point. Black and Flake8 run through the interpreter with -I -m. Task replacements and hooks keep their commands and still owe their reports.

If the environment does not match, recreate it from the managed CPython.

This applies to full native builds only. It does not apply to direct tasks, to VIRTUAL_ENV selection, to environments found in parent folders, or to uv and Poetry.

What preparation reads​

InputUsed for
project.dependencies in pyproject.tomlRuntime
build-system.requires (or the locked legacy tools, with fixed defaults for tools not locked)Build
The dev dependency group, with its includesTest
requirements.txtRuntime
Default test and quality tools you have not declared or lockedBuild or test

How the closure is resolved:

  • A uv project uses uv export --locked, and a Poetry project uses its lock export. That hashed export decides the closure for the project and its groups.
  • Extra backend requirements, requirements.txt and injected tool requirements are resolved by pip, with your lock as constraints. They keep their extras and transitive dependencies.
  • A pip project resolves all its declarations.

Oyzu records every wheel's digest in the dependency snapshot.

An authored build-system.requires is always authoritative, even when it conflicts with a lock. When it is missing, the default setuptools and wheel backend uses versions your lock already selects. For a tool the lock does not select, Oyzu falls back to setuptools==80.9.0 or wheel==0.45.1. Oyzu never refreshes a lock or drops one of your requirements to hide a conflict.

The current package as a quality tool​

A package can provide its own quality tool, for example building Black and formatting with Black. The offline build installs your wheel before the quality checks, so the checks use that installed copy. Oyzu skips the default download of a quality tool whose name matches the current package. Explicit requirements, locked constraints and the report gates are unchanged.

Dependency-group includes​

[dependency-groups] follows PEP 735. An entry is a requirement string or an { include-group = "name" } table, and includes expand in place. Group names are compared after PEP 503 normalization, so Runtime_Checks and runtime-checks are the same group.

[dependency-groups]
dev = [{ include-group = "tests" }, "pytest-cov==6.0.0"]
tests = [{ include-group = "runtime-checks" }, "pytest==8.3.5"]
runtime-checks = ["packaging==24.2"]

This captures packaging, pytest and pytest-cov as test inputs. Preparation fails, naming the group, for an include of an undefined group, two groups with equivalent names, a cyclic include, or any other table entry.

Only the dev group is used, as in uv. For uv projects, the native export applies the same includes.

The project itself as a requirement​

Requirements files often install the project itself (-e .[cli]), and dependency groups often reference it with extras (name[tests]). Oyzu builds the project from your source, so it never downloads it. It replaces the reference with what installing the project would add: project.dependencies plus the project.optional-dependencies for the extras you chose, following extras that reference the project again.

  • Extra names are compared after normalization.
  • An undefined extra fails preparation.
  • A reference whose environment marker does not apply to the build interpreter is skipped, as pip skips it.

In requirements.txt, the accepted editable forms are -e ., -e ./, --editable . and --editable=., each optionally followed by [extras]. The project needs a static project.name. Any other directive (-r, -c, an editable path to another folder, option lines) fails with Unsupported requirements directive; no alternate source fallback.

Dependencies that require the current project​

A dependency can require the project you are building, with extras. For example, a Litestar plugin requires litestar[cli]>=2.0.1. Oyzu satisfies that from your own source, without downloading it.

Oyzu checks the declared requirements, the requested extras and their closure with native marker and extra rules. It fails on unknown extras, missing dependencies, unapproved direct URLs and a package that would be both downloaded and built from source. Dynamic dependency metadata can't be checked without running your build backend, so it is refused.

Your source version can differ from the final version of the build. Before creating the virtual environment, Oyzu compares each constraint with the version it assigned to the build. It fails if there is no planned version, the project identity differs, or a constraint doesn't accept the version. This does not apply to apps or runtime-only dependency contexts.

Dynamic versions​

A project can list version in project.dynamic. For the pdm.backend, Oyzu reads the version from a file without running the backend or importing your code:

[project]
name = "example"
dynamic = ["version"]

[build-system]
requires = ["pdm-backend"]
build-backend = "pdm.backend"

[tool.pdm.version]
source = "file"
path = "example/__init__.py"

Oyzu reads that UTF-8 file with PDM's default rule: the first line that matches __version__ = "1.2.3" or VERSION = '1.2.3' wins, with an optional trailing comment. The value is validated as a PEP 440 version. Version inference then picks the build's version from it. The wheel and sdist metadata carry the build version, and the manifest keeps the original as nativeVersion.

The path must be relative, inside your captured source, free of links, and name a regular file of at most 4 MiB. Bad paths, invalid UTF-8, a missing default literal and an invalid version fail preparation. Fix the declaration or the file and rebuild.

Other dynamic forms use tag-based inference and are not executed:

  • setuptools [tool.setuptools.dynamic] version = { attr = ... }
  • Hatch file and VCS providers
  • PDM call, SCM and custom-pattern providers
  • PDM projects with backend-path, a tool.pdm.build.custom-hook, or a pdm_build.py

Without applicable tags, the base is 0.0.0, which gives a version such as 0.0.0.dev0+g0123456789ab. The native strategy fails with version-needs-native when no native version exists.

In its private build tree, Oyzu removes version from project.dynamic, removes tool.setuptools.dynamic.version if present and writes the build version as the static project.version. The wheel, sdist and their metadata then agree. Your checkout is unchanged. A pyproject.toml with neither a static nor a dynamic version fails with Python project version must be static or listed in project.dynamic.

Packages built from source​

Some locked packages have no wheel to download:

  • a uv.lock package whose source is a Git repository pinned to a commit
  • a uv workspace member or path dependency, which uv export lists as -e ./PATH or ./PATH
  • a registry package that uv.lock locks with a source distribution (sdist) and no wheel

Oyzu builds these from source, only inside the isolated worker that has no network, never during preparation. This works for uv projects only.

  1. Splitting. Oyzu separates these lines from the uv export and downloads only the registry wheels, with their hashes. A declaration that names such a package, including one that repeats the source as a direct URL such as advanced-alchemy @ git+https://github.com/..., is satisfied by the source build. A direct URL for a package that uv.lock doesn't build from source is still refused.
  2. Sdists. An sdist is downloaded from the files.pythonhosted.org route, checked against the SHA-256 in uv.lock and unpacked without running any of its code. A missing hash or a URL outside that route fails. Only regular files are written, names must be portable with one top-level folder, and archives are limited to 256 MiB.
  3. Git sources. Oyzu fetches the commit recorded in uv.lock with Git over a read-only route. Only public HTTPS GitHub repositories work. The checkout is stored without Git metadata, and no hooks, filters, submodules or credentials are used.
  4. Build requirements. Oyzu reads each source's build-system.requires (or the locked legacy tools for a setup.py package) and downloads them as build wheels, using the lock as constraints. No backend code runs.
  5. Build. In the worker, after the captured wheels are installed, each source is copied into the private build state and built with pip wheel --no-index --no-deps --no-build-isolation. A missing build requirement fails before the backend runs. The wheel must carry the locked name and version. Then all wheels are installed from a digest manifest with --require-hashes.

For example, this declaration makes uv lock sampleproject at the commit:

[project]
dependencies = ["sampleproject"]

[tool.uv.sources]
sampleproject = { git = "https://github.com/pypa/sampleproject", rev = "621e4974ca25ce531773def586ba3ed8e736b3fc" }

The dependency snapshot records each Git source with the digest of its captured tree and lists every source package in the oyzu.dev/python-sources extension, with its kind, path, commit, purpose and build requirements. An sdist source also records its URL and SHA-256. Workspace members belong to your project source and have no separate record. Because Git metadata is not captured, Oyzu sets SETUPTOOLS_SCM_PRETEND_VERSION to the locked version during the source build, so setuptools-scm and hatch-vcs read it.

A source that requires maturin or setuptools-rust needs Rust and Cargo crates, which Python preparation doesn't capture. Preparation fails naming the requirement, as it does for pydantic's pydantic-core member.

A python/app whose runtime closure includes a package built from source fails at packaging, because application archives contain captured wheels only. Runtime dependency contexts for Docker refuse such packages.

Private build state​

The worker keeps everything it creates for a Python target outside your project, in /out/.oyzu-python of the target's private output root:

PathContents
venv/The build environment with captured wheels and source builds installed
dist/The wheel and sdist before packaging copies them
sources/, source-builds/, source-wheels/Copies and wheels of packages built from source
application/, application-project/, application.pyz, test-application/Application staging, the archive and its extracted test copy

The output root lasts across the target's actions and is never inside /workspace. Because of that, build backends can't pack the build environment into your sdist, and Ruff, Black and Flake8 check only your project files.

This state is private and not an input or output contract. Packaging copies artifacts to the bundle folder /out/<target>/<platform>/ (available to the adapter as OYZU_OUTPUT), and reports go to its reports/ folder. See the bundle layout. Hooks that used to look in a .oyzu-build/ folder inside the project no longer find it.

Coverage reports no data​

Installed-artifact tests measure the installed package, not your checkout. A coverage setting such as omit = ["*/site-packages/*"] under [tool.coverage.report] can exclude every measured file. Then the tests may pass but coverage reports No data to report, the required Cobertura report is missing and packaging is blocked.

Narrow or remove that exclusion in your coverage configuration so the installed package is measured, then rerun. See Python testing.

Limits​

  • Source builds work only for uv. Poetry Git and path sources, and Git or path lines in a pip requirements file, are refused. Git sources need a public HTTPS GitHub repository and a full commit. Sdist-only packages need files.pythonhosted.org sdists in uv.lock. Submodules and Git LFS content are not fetched.
  • Sources that build Rust (maturin, setuptools-rust) or need other non-Python toolchains beyond what the image provides are not supported.
  • A source package that is itself a build requirement of another source is refused, environment markers on member lines are refused, and virtual members are skipped as uv skips them.
  • Source-built wheels are not checked for reproducibility. Only the source tree and the captured build requirements are digest-recorded.
  • A Poetry lock whose content hash no longer matches the project is rejected, as poetry install rejects it. Oyzu doesn't refresh it.
  • Only the PDM default file form supplies a native dynamic version. Other computed versions use tags, and dynamic dependencies are not computed.
  • Only the dev dependency group is used, and you can't select others.
