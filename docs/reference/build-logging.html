Build logging

CLI reference

Published from the canonical docs/reference/build-logging.md file. Features marked experimental remain experimental; check support limitations before relying on them.

oyzu build shows its work as it happens: preparation steps, parallel targets, commands, live output and a final receipt. It also saves complete logs and an event journal in the bundle. How output is shown never changes what is built or which checks run.

oyzu build
oyzu build api web worker
oyzu build --output plain
oyzu build --output interactive
oyzu build --plan
oyzu build --json > result.json 2> events.jsonl

For the section-by-section layout of the default view (Prepare, Selection, Plan, Build, Failure, Outputs, Warnings, summary), see build transcript. This page covers the output modes, the interactive dashboard, CI output, saved logs and interruption.

Presentation selection​

OptionBehavior
--output auto (default)Compact linear view: named preparation steps, one row per action and one final receipt.
--output plainThe same linear view. Never uses an alternate screen, fixed panes, key input or full-screen redraws.
--output interactiveThe full-screen dashboard. Needs a terminal on stdin and stderr. Works in CI too.
--jsonStdout holds the final manifest or plan JSON; stderr holds JSON-line events only. Takes precedence over --output.
-qQuiet output. Takes precedence over --output.
  • On a capable terminal, each active step shows a header and its last eight output lines. Routine successes collapse; slow steps and problems stay in scrollback.
  • Redirected output is append-only, never redrawn.
  • Color is separate from interactivity: ui.color = auto | always | never. A nonempty NO_COLOR wins, and CLICOLOR_FORCE can color a pipe without turning on redraws.
  • GitHub Actions gets the same linear view, wrapped in collapsible groups.

Persistent terminal view​

--output interactive opens a dashboard that stays in place while the build runs.

  • The header shows the project, elapsed time, phases (Prepare, Build, Collect) and the selected platforms with readable OS and architecture names.
  • During preparation it shows how many tools are verified or pending, and up to two pending tools. Finished setup collapses when the build starts.
  • Each row shows its current operation, elapsed time and, for active rows, how long the output has been quiet.
  • One live pane shows the selected step's last seven output lines. New parallel work doesn't steal focus from the step you're watching. Warnings and failures stay pinned above the pane.
  • Reused actions show Reused · not executed now. After a process exits, a step may show Checking outputs until its reports and artifacts pass validation; a clean exit alone isn't success.
  • Blocked tasks show which prerequisite they're waiting for.
  • Resizing recalculates the layout; very small terminals show a resize hint. Long lines are clipped, and you can pan to see them.
  • Scrollback is kept in a temporary file on disk, deleted when the view closes. The saved build logs are the permanent record.
  • When the build ends (or fails), your previous screen is restored and the permanent receipt is printed.
KeyAction
Up / DownSelect the previous or next step.
EnterExpand or collapse the live output pane.
aFollow active work automatically.
pShow or hide preparation details, requested versions and the selected work's stages and outputs (up to eight setup rows; see oyzu build --plan --json for the rest).
d / lShow or hide the full combined log.
EscapeReturn to the compact live pane.
Page Up / Page DownScroll the log.
Left / RightPan long lines.
f / EndFollow new output again.
nSelect the next failed task. Failures only raise a notice; they never move your selection.
qClose the dashboard and continue the build with plain output. Doesn't cancel anything.
Ctrl+CRestore the terminal and interrupt the build.

The dashboard never needs input to finish.

CI and redirected output​

When output is redirected, or the build runs in a detected CI system, the view is append-only:

  • Each action prints a start line (00:12 .. api build started) and an end line with its outcome and duration, both led by the elapsed time since the build began. In builds with more than twelve actions, only end lines and the final tally are printed.
  • Every ten seconds a heartbeat line names what's still running: 00:31 still running: api build 10s · auth-lib test 12s · 6 waiting (up to three actions, then + N more). A heartbeat shows the build is alive, not that a tool is making progress.
  • Output is laid out at 100 columns on every host. Terminal width comes from the console, so COLUMNS doesn't change it.
  • Without color, marks are padded words (ok, reused, warn, FAIL) and rules use dashes. Terminal controls in every value are escaped. Redirected files never contain cursor movement.

Recognized CI systems: GitHub Actions, GitLab CI, Azure Pipelines, Buildkite, Jenkins and TeamCity, with a generic CI fallback. Detection only affects presentation (and the build context); it never grants any permission.

GitHub Actions. Preparation, dependency and planning phases are wrapped in collapsible groups, closed before actions run. When GITHUB_STEP_SUMMARY is set, Oyzu appends an HTML-escaped receipt to it; if that write fails you get a warning and the build result doesn't change. In JSON mode, no group commands are printed. Oyzu doesn't upload artifacts or add source annotations.

The sectioned view described in build transcript applies to local oyzu build runs. --plan, --check, remote runs, oyzu run, oyzu scan and the dashboard use their own layouts.

Stage overview​

The heading names the project, the host or platform selection, the execution mode and the requested checks. Which targets were selected, and why, is in the Selection section; stage status is in the plan table.

Preparation runs as named steps: configuration, tools, dependencies, output bundle, compiler cache, source snapshot, CLI identity and report setup.

  • › running, ✓ done, ✗ stopped by an error. A step that's still running when an error stops the build is shown as stopped, not done.
  • Fast successful steps collapse. Steps that take ten seconds or more, and failures, stay visible. A slow step that succeeds is still a success.
  • Tool installation shows the requested version. A reused tool collapses to one Ready line; a real download stays visible.
  • Host prerequisites say they're checked during compilation.
  • Optional tools that aren't used aren't listed.

Each running subprocess (formatting, linting, tests, compilation, hooks, tool installation) gets a short preview under its row, showing its latest eight lines in dim text. Each parallel task has its own preview. The preview area is limited by the terminal height and says when activity is hidden.

  • On success, the preview collapses into the totals.
  • On failure, the first useful eight lines of error context are kept (or the last eight lines if no error marker is found), with the exit code. The receipt names the saved log.
  • -v shows the full captured output, including successful preparation.

Steps and timings​

A finished step shows a mark, a name, a short result and its duration. Durations read <0.1s, 5.9s, 149s and 10m 06s.

  ✓ Source captured          2781 files · sha256:668b3844b9d7                          13.0s
  ✓ Rust compiler            1.95.0 · reused the packaged copy from an earlier build    0.8s
  ✓ Compiler in container    restored into a read-only volume                          19.5s
  ✓ Cargo crates             371 locked · all from the cache                            5.6s
  ✓ Project metadata         8 container runs · slowest `cargo metadata` 9.0s          25.0s
  ✓ Build inputs ready       compiler, crates and project metadata                     60.8s
  • On a terminal, a running step shows in the live pane (› name detail). Redirected output prints a step when it finishes, with heartbeats while it's slow.
  • With several targets, each step names its target (Cargo crates · cli · linux/x86_64).
  • While Cargo compiles, individual Compiling lines aren't printed. The running status shows the count and latest crate (Running · 60s elapsed · 271 crates compiled · latest oxc_ast_visit), and the finished line shows the total (Succeeded · 276 crates compiled). Warnings and errors still print in full. -v prints every crate.
  • With -v, a finished build also shows where the time went (Preflight 71s · Build 174s · Collect 4s).
  • After the last action finishes, Collect does its own work: it saves the private source copies for the next build (Source workspaces), records results and verification evidence (Build records), and writes the local bundle (Output bundle). Each is a step like the ones above. It shows in the live pane while it runs, a redirected run prints › Source workspaces saving private copies for the next build · 10s every ten seconds while it is slow, and a finished step appears only if it took ten seconds or more, failed or warned.
  • Generated platform IDs such as cli-platform-windows_x86_64-157f0d1f6adb are shown as cli · windows/x86_64.
  • The event journal has the same steps and durations (Step events with duration_ms).

Isolated build preparation​

An isolated (container) build prepares these steps for each target:

StepWhat it does
Rust compilerUnpacks the locked Rust installation once per build and packages it for the container. The package is cached under cache/rust-packaged in the Oyzu user data directory.
Compiler in containerRestores the package into a read-only Docker volume named oyzu-tools-<hash> (the hash covers the worker image, compiler archive and format). The volume is kept between builds, so a repeat build reuses it in under a second instead of about 20 seconds.
Cargo cratesCaptures every crate in Cargo.lock into an offline registry for the container, which has no network. Archives are checked against the lock's checksums and cached under cache/cargo-crates; registry index entries are cached for seven days.
Project metadataA few short container runs (cargo metadata, rustc -vV, lock file generation). Shown as one step naming the slowest run; -v lists them all.
Source snapshot, Dependency snapshotPrivate, hashed copies the offline build uses.
VersionThe version stamped into the artifacts.

About the compiler volumes:

  • A companion volume, oyzu-tools-<hash>-ok, marks a finished restore. A volume without it is rebuilt.
  • A lock file under cache/ in the user data directory stops concurrent builds from restoring the same volume twice.
  • Each new compiler or worker image adds a volume of about a gigabyte. After each build, Oyzu removes older oyzu-tools-* pairs, keeping the current one and the three most recent others. Volumes in use by a running container are skipped and retried next time.
  • Other Docker storage is limited by the Docker storage budget.

A native (non-isolated) build shows Source workspaces (a private copy of the sources) and one step per executor prerequisite (a small compile-and-link check of the linker). The › Tools determining… line is a placeholder while this runs.

Native output and warnings​

  • Native output is shown as it arrives. Oyzu can't show output a tool hasn't written yet, and Cargo can be quiet for a long time while compiling or linking. Silent tasks show elapsed time every ten seconds.
  • Each excerpt names its task once and keeps the tool's own indentation and carets.
  • Color codes from tools are removed in the human view; other terminal controls are escaped. The saved logs keep the original output.
  • Parallel tasks never interleave within a line. Lines from one stream stay in order; the order between different tasks or between stdout and stderr isn't a strict cause-and-effect order.
  • Cargo JSON is shown as short compiled-target and status lines. go test -json shows native output and failed test names instead of JSON. A single record over 1 MiB isn't shown; read the saved log instead.
  • Native warnings appear once, in the receipt's Warnings section, and as NATIVE_WARNING diagnostics in JSON. Cargo warnings keep their source location, and Cargo's repeated summary line doesn't add another warning. npm and Node warnings are recognized too. Oyzu never decides an action's result from warning or error text.
  • Warning and error excerpts have separate budgets, so warnings can't hide a later failure.
  • Installer messages from rustup go through the same view. Its advice to add a temporary folder to PATH is hidden, because Oyzu activates the installed tools itself; JSON and saved events keep it.
  • Rust doctests stream live; see Rust direct test evidence.
  • The command shown for an action is redacted for display. It isn't a portable shell script.

Final receipt and retained evidence​

The receipt is the summary at the end of a build. See receipts and history for what it counts.

  • A build that fails during preparation says Build failed during preparation and No build actions started, and keeps the count of selected targets.
  • Fresh tests and reused test results are counted separately. Reused results name where they came from and never count as tests run now.
  • Missing reports never mean zero failures or 100% coverage. Coverage isn't averaged across unrelated measures.
  • Receipt sections show up to eight entries and say how many were left out. -v adds the manifest and report paths.
  • An empty result says No artifacts produced.
  • Error and recovery paragraphs wrap at word boundaries (100 columns if the terminal width is unknown).

Saved logs​

Every build saves these files in its bundle (dist/ by default):

PathContents
logs/events.jsonlThe event journal, including preparation output.
logs/<target>/…Numbered stdout and stderr files for each action.
manifest.json, plan.jsonThe build's result and plan.
plans/Sealed plans for independent branches.
  • If setup fails before the bundle exists, no journal is saved. The terminal, JSON and redirected output still have the error.
  • oyzu run test and other bundled tasks also save their full stdout and stderr, in text and JSON modes. A task marked interactive = true uses your terminal directly, so its log files are empty. See task output.
  • oyzu build --plan creates no bundle; see read-only build preview.
  • See build bundles for how bundles are kept.

Event records​

Each line of events.jsonl (and each JSON event on stderr) has schemaVersion, sequence, elapsedMs, scope, severity, target, invocationId, operationId, parentOperationId and an event:

eventContents
diagnosticA warning, error or other message, with code.
heading, fact, inventoryThe build heading, context facts, and the selected targets, platforms, check mode and color preference.
preparation, phase, task, progressLifecycle changes.
planTarget IDs and builders, action IDs, dependencies and artifact versions. Never action environments.
commandThe redacted command.
outputstream, text and continued.
finishedstatus, and optional exit_code and duration_ms.
  • Every warning and error is saved, whatever the console showed. Debug and trace messages are saved only when enabled.
  • Environment maps are never included.
  • New event types may be added; ignore ones you don't recognize.
  • The format is experimental and separate from the plan's identity and from release records.

Privacy​

Logging uses no network. Your project's commands can print sensitive values, and Oyzu doesn't try to detect secrets in arbitrary output. Credentials Oyzu uses for downloads are never passed in a command's arguments or environment. A failure to write a log never changes a tool's result.

Shared verbosity​

Builds use the global diagnostic controls.

EventLevel
Routine lifecycleinfo
Command detailsdebug
Failed steperror
Blocked taskwarn

Native stdout and stderr are always saved, whatever the threshold. A line on a tool's stderr isn't an Oyzu error.

Interrupting a build​

The first Ctrl+C (or SIGTERM, or SIGHUP when the terminal closes) asks the build to stop. No new work starts and running container steps are removed. A signal that was already ignored when the build started (such as SIGHUP under nohup) stays ignored.

Steps blocked inside a native tool or Docker call can't respond right away, so Oyzu prints a notice ending waiting up to 10s for running steps. Press Ctrl-C again to force exit. The notice goes through the normal log, so it's a JSON line with --json.

After an interrupt:

  • Actions that never started are not-started, and the build is interrupted.
  • On Unix, native tasks that were stopped report cancelled. On other platforms the tool's own exit is reported.
  • In the dashboard, Ctrl+C restores your terminal first.

Forced cancellation​

A second Ctrl+C, or the end of the 10-second grace period, forces exit:

  • Oyzu removes the containers this build started (named oyzu-* or the build worker names). On Windows it also ends tracked child process trees. All of this shares one five-second deadline; cleanup that doesn't finish in time is abandoned.
  • It names any container or process tree it couldn't remove, then exits with status 130, even if Docker isn't responding.
  • These time limits are fixed.

Forced exit is best effort. It can leave containers, processes and partial staging behind, and there may be no failure bundle. Once Docker is responsive again, remove the named leftovers before retrying, and see bundle recovery. Cleanup messages go to stderr even with --json and aren't a JSON result.

Limits:

  • On Unix, forced exit doesn't kill native child processes in other process groups.
  • Containers left by an earlier hard kill (for example kill -9) aren't cleaned up.
