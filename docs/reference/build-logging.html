Build logging

CLI reference

Published from the canonical docs/reference/build-logging.md file. Features marked experimental remain experimental; check support limitations before relying on them.

oyzu build presents a pipeline in the terminal: phases, parallel targets, commands, live output and an evidence-based final receipt. Presentation never changes the task graph, execution policy or required checks.

oyzu build
oyzu build api web worker
oyzu build --output plain
oyzu build --output interactive
oyzu build --plan
oyzu build --json > result.json 2> events.jsonl

Presentation selection​

--output auto is the default and uses compact linear preparation, named work and one final receipt. --output plain uses the same flow: no alternate screen, fixed panes, input handling or whole-screen redraws. On capable terminals, active operations show a labeled header and the last eight output lines beneath it; routine successful steps collapse; slow steps and exceptions stay in scrollback. Redirected streams are strictly append-only. Colors are independent of interactivity (ui.color=auto|always|never); nonempty NO_COLOR takes precedence, and CLICOLOR_FORCE can style a pipe without enabling redraw. GitHub Actions uses the same bounded linear view with balanced phase groups. --output interactive requires terminal stdin/stderr and allows inspecting the dashboard even in CI. --json and quiet logging take precedence over either option. In JSON mode, stdout contains the final manifest/plan JSON and stderr contains JSON-line events only. No project configuration is needed.

The dashboard uses Crossterm's Windows/macOS/Linux terminal support. Only explicit interactive selection initializes the dashboard and can report its setup errors. Windows GNU builds using an older bundled GNU linker can encounter import-table incompatibility with terminal dependencies; the local proof uses the provisioned LLVM MinGW linker explicitly. Standard CI compilation remains registered on all three hosts; see implementation status for actual verification.

Persistent terminal view​

The explicit dashboard follows Prepare, Build and Collect. During preparation it shows verified/pending tool counts and up to two pending tools, without claiming that external prerequisites are installed. Completed setup collapses when execution starts. Optional quality tools stay out of a fast-build summary. p reveals requested versions, observed setup/context facts and the selected work's stage/output details. Setup facts use a height-dependent budget of at most eight rows, disclose omitted detail and point to detailed logs or oyzu build --plan --json. The live pane remains available with large tool inventories.

The project header, elapsed time, phase indicators and platform overview stay in place. Selected platforms appear before dependency preparation starts, with readable OS/architecture names. Each row shows its current operation and elapsed time. Active rows also show how long output has been quiet. Preparation is tracked separately from planned build actions.

One live pane shows the selected step's seven most recent output lines. Its last lines remain visible during silence, alongside time since the last output. New parallel work does not steal focus from a running step. Warnings and failures remain pinned above the pane. Native output is retained even when Oyzu does not recognize its content; detailed history preserves redacted command arguments, observed timing and event details. Successful process exit can show Checking outputs until collection validates the action.

Color reinforces status symbols and labels. NO_COLOR disables color, including an explicit force; the frozen ui.color configuration supports auto, always and never. Status remains readable without color.

A failed command or final action failure raises a notice without changing the selected task; n selects a failed task explicitly. Successful process exit does not establish action success: reports/artifacts can fail validation later. Blocked tasks expose their prerequisite reason. The interface does not require input to finish.

Terminal resizing recalculates panel sizes. Very small terminals show a resize hint. Output is clipped to display cells rather than wrapping into the pinned header; horizontal panning reveals long lines. Interactive scrollback uses a temporary disk spool with in-memory line offsets, retaining early output without holding every output byte in memory. It is removed when the view closes. Raw build logs and the event journal remain the durable record.

The alternate screen restores the previous terminal at normal completion or error, then prints the permanent receipt. q restores the screen immediately without cancelling work. Ctrl+C uses the build cancellation lifecycle below.

Forced cancellation​

The first Ctrl+C requests cooperative build cancellation; its notice uses the invocation logger, including JSONL framing and correlation. A second Ctrl+C, or expiry of the ten-second grace period, forces exit. Forced cleanup gives all tracked container removals one shared five-second deadline; on Windows, tracked child process-tree termination shares that budget. Unfinished cleanup clients are killed and reaped asynchronously rather than waited on indefinitely. Oyzu names containers or process trees whose removal failed or remained pending, then exits with status 130 even when Docker does not respond. These budgets are fixed.

Forced exit is best effort: it can leave containers, process trees and incomplete staging evidence, and does not promise a finalized failure bundle. After the daemon recovers, inspect the reported names and remove leftovers before retrying; use bundle recovery for retained build state. Emergency cleanup messages go to stderr even with --json; they are not a final JSON result. The authored stuck-Docker regression is Unix-specific; neither it nor the cross-platform cleanup tests ran on this desktop. See verification status.

CI and redirected output​

Stage overview​

The operation heading identifies the project, host/platform selection, execution mode and requested checks. A compact scope record names up to three selected targets and counts the rest. Affected work retains its baseline, overlapping category counts and any conservative fallback. Planner facts remain authoritative.

Routine queued/included stage rows do not produce tables. Deliberate skips are neutral, grouped by reason, naming up to three affected stages in each group, with up to three distinct reasons and an inspection route for further detail. Unavailable/unknown stages receive attention separately; up to eight such records appear, followed by an explicit omission and oyzu build --plan --json inspection route. -v shows additional stage/context records in the same linear design. The old Preflight, Selection, Stages and About this build sections have been removed from the linear renderer, including its verbose path. Explicit build --plan remains a read-only inspection view with its own grouped plan tables.

Concurrent plans preserve active work and register every target's readable label, including targets beyond the visible budget. JSON inventory stagePlans, action selection, dependencies, checks, caching and execution policy are unchanged.

The linear view uses status, subject and activity records, without table headers mixed into preflight updates. Installation progress includes the requested version when available. Routine checks and reused tool readiness collapse by default; actual acquisition and explicit installation results remain visible. System prerequisites explicitly say they are checked during compilation. Unselected optional tools stay out of the summary.

Native preflight uses named steps for configuration, tool preparation, dependencies, output bundle, compiler cache, source evidence, CLI identity and report preparation. Running steps use ›, explicitly completed steps use ✓, and interrupted-by-error preparation uses ✗; stopping a progress heartbeat is not a completion signal. On capable terminals active rows redraw. Fast successful preparation collapses; steps lasting at least ten seconds and failures remain visible. Completed slow work stays successful; duration alone does not turn it into a warning. Dependency readiness removes its running row, and entering execution retires preparation. Redirected output appends named long-wait feedback and remains readable without color. Report contracts and binding readiness share one completion row. Execution/isolation context remains in context facts and the build heading, not repeated · build progress prose. Structured JSON events and journal records retain these transitions; stdout, native child streams and exit status retain their existing contracts.

Each active build subprocess has a short preview immediately beneath its operation header. This applies uniformly to formatting, linting, tests, compilation, custom hooks and tool installation through the shared logging lifecycle. The latest eight lines scroll within that preview and use dim text when color is enabled. Successful operations collapse into receipt totals; slow action completions may remain visible. Failed operations retain the first useful eight-line diagnostic context, or their last eight lines when no diagnostic marker is recognized, with the failure status and available exit code; the receipt identifies retained build logs. Each parallel operation has its own preview. The active region is bounded by terminal height; excess activity is indicated explicitly. Long preview lines are clipped to terminal width, while retained output stays complete. This is a transient section of ordinary scrollback, with no alternate screen or keys.

Redirected human output is bounded and append-only. Routine captured native lines are retained for verbose output, failure excerpts and evidence. Preparation subprocesses retain the same eight-line failure tail, including native causes without a recognized warning/error prefix; successful preparation clears its tail, and -v expands its captured output. JSON events and raw build task logs never collapse. A late parallel preparation event does not reset the Build heading. Installer worker stderr is followed into the same logging owner; its stdout remains the private worker protocol. Commands intentionally exposing a native pass-through payload retain that separate contract.

Captured Rust compiler materialization also follows installer stderr through the invocation logger. Installer protocol stdout remains private; human views show bounded attention while JSON stderr and retained events preserve structured records instead of unframed rustup output.

Native excerpts identify their task once and preserve source indentation and carets beneath that label. Decoded multiline Cargo diagnostics are written together under the invocation output lock; unstructured native output retains line-level ordering without guessing diagnostic boundaries. When a registered Cargo compiler warning arrives line by line, successful collapse preserves its first bounded context from that same stream, without repeating its already printed header. Other streams do not fill that context, and it shares the eight-line warning budget. Native status lines or a new diagnostic end that source context. Cargo packaging uses the same registration and warning facts; identical packaging warnings appear once per action at normal verbosity, while verbose output and raw evidence retain them. Consecutive warnings share an excerpt label; changing work restores its label. Routine preparation narration is live status or verbose detail, and slow project metadata completion says Ready without listing internal worker calls. Native process success is omitted because it precedes validation. Task completion and the final receipt retain their distinct meanings; failures include available exit codes.

The linear view shows preparation and execution as named lifecycle records, then one receipt. At most four routine action starts and four slow completions appear by default; further work collapses into totals. Native warnings/errors retain bounded permanent context on both terminals and redirected streams. Warning and error budgets are separate so warnings cannot hide a later root failure, with omission notices and failure tails. -v expands captured output and successful preparation records. Context and command metadata remain in structured events and retained evidence. Every ten seconds it reports nonzero, disjoint action outcome counts, active work, dependency waits with causes/observed ages and elapsed time while execution remains unfinished. Graph growth updates known action totals without erasing existing outcomes. Action counts are never a time-remaining estimate; a liveness update is not progress. Cargo JSON compiler records are projected into concise compiled-target/status lines by the shared native projection, including native build-host workers; cached artifact records and build-script metadata are omitted from both human views. Registered go test -json streams show native output and failed test identities instead of JSON envelopes. Split records are assembled per scope and stream, bounded to one MiB per record; exceeding that display limit directs the reader to retained native logs. Compiler diagnostics and unknown output remain visible. Original output events, JSON mode, raw logs and artifact validation inputs are unchanged. Native processes retain their own buffering; Oyzu cannot show bytes before the process writes them. GitHub Actions keeps collapsible phase groups around the shared bounded view.

The ordinary terminal shows reconciled scheduler counts beside its bounded live work, including short builds before the first heartbeat. Closing the dashboard with q preserves active scopes, elapsed age and native projection in the linear view. Automatic focus advances from completed setup to active work until the user pins a selection; subsequent workers and failures do not steal that selection.

Native warnings are included in the receipt as NATIVE_WARNING diagnostics in human and JSON modes. Cargo's typed warnings retain primary source locations when available; its repeated summary does not add another warning. Recognizable plain native warning markers, including Node runtime and npm warnings, are retained; unrelated JSON is not reinterpreted as a warning. This reports native diagnostic facts and never infers an action result from a warning or error string.

Concurrent scopes share a synchronized sink so lines do not interleave at the byte level. Within-stream ordering is retained. Observation order between independent tasks or stdout/stderr is not a global causal order. Command-event argv is a redacted presentation value, not an authoritative command or portable shell script. Control characters are escaped. Text redirected to a file contains no dashboard cursor controls.

Detected provider names include GitHub Actions, GitLab CI, Azure Pipelines, Buildkite, Jenkins and TeamCity, with generic CI fallback. These are unverified presentation hints, never credentials or release authority.

In GitHub Actions, preflight, dependency and planning phases use collapsible groups. Groups close before action execution; individual concurrent tasks do not open overlapping groups. On completion, Oyzu appends an HTML-escaped receipt to GITHUB_STEP_SUMMARY if supplied. Failure to write the summary warns without changing build status. JSON mode still uses only JSON events on stderr, with no group commands. Local artifact paths are not presented as download links: artifact uploading, additional provider-native summaries and reliable source-location annotations are not implemented here.

Final receipt and retained evidence​

A build stopped during preparation preserves its known selected target count and says Build failed during preparation and No build actions started. Prepared action records remain empty; they are not described as an empty target selection. Available target identity and the original preparation cause remain in diagnostics. Human diagnostic and recovery paragraphs wrap at word boundaries with a hanging indent (100 columns when the terminal width is unavailable). History summaries and bundle inspection retain that selected scope as well; the shared record summary owns the count rather than treating an empty prepared target array as no selected work.

The completion summary leads with the build outcome and elapsed wall time. Successful builds show artifacts with target, bundle-relative path and recorded size, followed by actual manifest/event references or explicit unavailability. Multiple targets receive at most eight target rows with an omitted count; single-target builds omit that redundant table. Receipts distinguish selected targets from actions and reconcile disjoint action outcomes. Failed builds list failed and blocked actions with available exit codes/reasons; their detailed output stays beside the live operation above. Host failures explain that existing local binaries were not updated. Empty artifact results say “No artifacts produced”; empty Reports sections are omitted.

Fresh tests and reused test evidence have separate totals. Reuse identifies available producer provenance and never increments tests run now. A report with mixed or missing action ownership is labelled with unavailable origin. Coverage measurements remain visible when available. Missing reports do not imply zero failures or 100% coverage, and coverage is not averaged across unrelated metrics. Planned artifacts are labeled as planned. Diagnostic messages retain severity, code, affected action and available recovery. Success with warning diagnostics says so explicitly; warning detail remains visible. Default receipt sections are bounded to eight records and disclose omitted detail. -v (or a debug log level enabled for the command) additionally lists manifest and individual report paths; these files remain in the output bundle at normal verbosity. Human and structured views consume the same finalized facts; JSON retains the complete manifest. The summary uses semantic color on capable terminals and remains readable without color.

Normal builds retain dist/logs/events.jsonl, numbered action stdout/stderr files, manifest.json and plan.json. Preparation output is included in events. Independent branches emit partial plan events as they become ready; later aggregate plan events preserve running/completed task states. Branch action logs are namespaced under logs/<target>/, and sealed plans are retained under plans/. Preflight records are temporarily spooled and replayed into the existing journal when the bundle becomes available, so collapsed installer output is retained on completed preflight flows. If setup fails before a bundle is created, a durable build journal is not published; terminal error details and JSON/redirected output remain available. The final console build outcome follows publication of the bundle; the journal is closed before publication. --plan uses a separate read-only preview receipt with stage selection, tool requirements and unresolved details; it runs no dependency preparation and creates no bundle. History follows the bundle lifecycle.

Bundled development tasks (oyzu run test) also retain full stdout/stderr in their numbered log files in text and JSON modes. Text mode tees output live without duplicating it as console log events. The exception is a text-mode task explicitly marked interactive = true: it inherits terminal descriptors, which Oyzu cannot capture simultaneously without a pseudo-terminal. Its stdout/stderr files are empty; report collection still applies. See task stream behavior.

Event records have schemaVersion, sequence, elapsedMs, scope, severity, target, invocationId, operationId, parentOperationId and a tagged event: diagnostic, heading, fact, inventory, preparation, progress, phase, plan, task, command, output or finished. Observed warnings/errors are retained independently of console filtering; disabled debug/trace messages are not constructed or persisted. Fact events carry explicit section/name/value presentation observations, without environment maps. Inventory contains selected target labels, platforms, check mode and color preference, without environment maps. Preparation/phase/task events carry lifecycle facts. The plan event contains only presentation inventory (target ID/builder, action ID/target/dependencies and artifact versions), never action environments. Output includes stream, text and continued; completion includes status, optional exit_code and optional duration_ms. Consumers should tolerate new event types. This experimental observation format remains separate from deterministic plan identity and release evidence.

The logger adds no network calls. Environment maps are not dumped. Project commands/output can deliberately print sensitive values; arbitrary-output secret detection is not promised. Upstream broker credentials remain outside executor arguments/environment under the existing acquisition contract. Native raw-log size and process-time limits remain in force. Log sink failures do not override native process results; durable remote delivery is separate work.

Verification​

tooling/test-build-logging.py --cli <compiled-cli> --evidence-dir <new-directory> runs two real Rust targets, verifies live parallel streams, four snapshot artifacts, report collection, JSON failure/blocked events and bundle inspection. The Rust image must already be provisioned.

Add --linear to verify the linear view and human failure output instead of the GitHub grouped view. --image <reference> selects an explicit provisioned Cargo image containing the compiled worker and required quality tools.

For real terminal acceptance, install tooling/terminal-requirements.txt, then run tooling/test-build-terminal.py --cli <compiled-cli> --evidence-dir <new-directory>. This uses ConPTY on Windows and a pseudo-terminal on Unix to exercise the actual CLI, independent active panels, navigation, resizing, failure focus, hide/restore behavior and resulting bundles. Screen transcripts and representative text frames are retained. Unit tests cover the event projection, full spool history, control escaping and evidence-based receipts. Registration is not passing evidence; see implementation status.

Shared verbosity​

Builds use the global diagnostic controls. Routine lifecycle presentation is info; command observations are debug; failed completion is error and blocked tasks are warn. Native stdout/stderr events are always retained independently of threshold; a native stderr line is not an Oyzu error. Dashboard state and existing journal lifecycle facts continue to receive events even when console detail is filtered. Build journals retain observed diagnostic facts and the same correlation envelope as console JSON. They are observation evidence, not a complete execution audit; existing bundle retention remains in force; command argument redaction applies consistently to their presentation events as well.

Preflight status and native styling​

A tool has one evolving terminal status followed by a final Ready result. Redirected output retains the initial check and final result, without repeating intermediate reuse/verification notices. Native output remains attributed to its operation. The human child-output projection removes SGR color/style escapes; other terminal controls remain escaped. Original child events and raw evidence retain their existing contracts. Failed operations retain their diagnostic tail. Executor capability results appear after the selected native environment has been checked, rather than as an additional speculative unchecked row.

Managed installation and long-running native output​

Explicit installation and automatic build preparation send native installer stderr through the invocation-owned logger. JSON diagnostics stay on stderr; worker stdout remains its private protocol. Human output omits rustup's advice to add its temporary staging home to PATH, because Oyzu publishes and activates the verified installation itself. Native errors remain visible; raw events and JSON retain that advice. Redirected build progress emits changed task summaries once, with explicit omission notices when native previews are bounded. Multiline Oyzu diagnostics retain indented line boundaries while escaping terminal control sequences. Rust doctest compilation streams live output and retains bounded report diagnostics; see the Rust evidence contract.

Native task heartbeats are visible in the linear view: while a subprocess is silent, its active terminal row updates elapsed time every ten seconds. Redirected output appends an elapsed-time update instead. These are liveness indicators, not percentages or proof that a native tool is advancing. Native output continues to stream as it arrives; Cargo may remain quiet during compilation or linking.

Interrupting a build​

The first Ctrl+C (or SIGTERM) asks the build to stop: schedulers stop starting work and running container steps are removed. Steps blocked in a native or Docker call cannot observe the request, so the CLI prints Stopping build; waiting up to 10s for running steps. Press Ctrl-C again to force exit. A second Ctrl+C, or the end of the 10-second grace period, removes the containers this invocation started (named oyzu-* or the build worker names), ends the process tree and exits. On Windows the exit status of a forced exit is 1; on Unix it is 130. Unix forced exit does not yet kill native child processes in other process groups. Containers started before an earlier hard kill are not cleaned up by this mechanism.

Steps and timings​

Preparation is tracked as named steps. Fast routine success is collapsed by default; -v shows each successful step in completion order. A finished step has a mark, a name, a short result and its duration in a right-aligned column. A step of ten seconds or more remains visible; successful work retains its success marker. Durations read <0.1s, 5.9s, 149s and 10m 06s.

  ✓ Source captured          2781 files · sha256:668b3844b9d7                          13.0s
  ✓ Rust compiler            1.95.0 · reused the packaged copy from an earlier build    0.8s
  ✓ Compiler in container    restored into a read-only volume                          19.5s
  ✓ Cargo crates             371 locked · all from the cache                            5.6s
  ✓ Project metadata         8 container runs · slowest `cargo metadata` 9.0s          25.0s
  ✓ Build inputs ready       compiler, crates and project metadata                     60.8s

In a terminal a running step shows in the live pane (› name detail); its tail collapses when it completes. Redirected output prints a step when it finishes, and a heartbeat line while a step is slow. With more than one target a step carries its target (Cargo crates · cli · linux/amd64). Actions (prepare, build, archive, package) use the same column. While cargo compiles, the individual Compiling/Compiled lines are not printed: the running status shows the count and the latest crate (Running · 60s elapsed · 271 crates compiled · latest oxc_ast_visit), the completed line reports the total (Succeeded · 276 crates compiled), and warnings and errors still print in full. -v prints every crate line. With -v, the headline of a finished build is followed by where the time went (Preflight 71s · Build 174s · Collect 4s).

What an isolated build's preflight does, per target:

  • Rust compiler. The locked Rust installation is unpacked once per build, shared by all platforms, and packaged for the build container. The package is cached across builds under cache/rust-packaged in the Oyzu user-data directory, so a repeat build only reuses it.
  • Compiler in container. The package is restored into a read-only Docker volume named oyzu-tools-<hash> (the hash covers the worker image, compiler archive digest and restoration format). The restored copy grants read/search access while preserving executable bits, so actions assigned the source owner's UID can use compilers installed privately with 0700 modes. The original installation and archive are unchanged. Older private-mode volumes are retained; the new restoration format uses a separate derived key. The volume persists across builds, so a repeat build reuses it in under a second instead of re-extracting the compiler (about 20 s). A second volume, oyzu-tools-<hash>-ok, is created only after extraction and accessibility normalization succeed; a volume without it is treated as unfinished and rebuilt. A lock file under cache/ in the Oyzu user-data directory serializes concurrent builds. Each compiler or worker-image change adds one volume (about a gigabyte); remove old ones with docker volume rm. Without the lock the volume is private to the build and removed afterwards.
  • Cargo crates. Every crate in Cargo.lock is captured into a registry the container uses offline (the build container has no network). Archives are verified against the lock's checksums and cached across builds under cache/cargo-crates; registry index entries are cached for seven days.
  • Project metadata. Several short container runs (cargo metadata, rustc -vV, lockfile generation) read facts about the project. They are one step that names the slowest run; every run is listed at debug verbosity (-v).
  • Source snapshot and Dependency snapshot. Private, hashed copies the offline build uses.
  • Version. The version stamped into the artifacts (see the facts block below).

A native (non-isolated) build shows Source workspaces (a private copy of the sources) and one step per executor prerequisite (a small compile-and-link probe of the linker) in the same form. The live › Tools determining… line is a placeholder while any of this runs.

Long lines wrap under a hanging indent aligned with the message column, and a generated platform id such as cli-platform-windows_amd64-157f0d1f6adb is shown as cli · windows/amd64. The same steps and durations are in the event journal (Step events with duration_ms).

Build context and receipts​

Detailed version/source/configuration facts use labeled lifecycle records with -v; they are also retained in JSON events and the journal. The optional dashboard keeps its context inspection panel. Snapshot version facts do not confer release or publication authority.

The final receipt leads with the outcome and elapsed time, then target/action counts and nonzero disjoint outcomes. Successful targets do not generate a second result table. Executed and reused tests stay separate; accepted test details collapse while reused evidence keeps its producing run/time and cache origin. Incomplete, rejected or unknown test evidence stays visible; -v includes accepted per-action details too. Root failures precede dependent impact, and error diagnostics precede warnings within bounded excerpts. Omitted actions, evidence and diagnostics have explicit counts and inspection routes.

Artifact records give copyable paths under the published dist directory without padding to the longest path. Invocation identity, available manifest/event paths, missing evidence, cache fallback and failure recovery remain visible under quiet output. Help, shell code, selected-path and native pass-through contracts are unchanged. See executable selection when comparing installed and compiled output.

State, focus and inspection​

Waiting means a known dependency has not satisfied the action; ready means its dependencies are satisfied and it has not started. Neither means a process ran. Success/reuse/failure/blocking remain separate in the shared snapshot. Pending work prevented from launching by an interrupt is not-started, with a reason; the invocation is interrupted. Unix native tasks killed by the cooperative interrupt and reaped with SIGTERM/SIGKILL report confirmed cancelled; other platforms retain native outcome facts without inferring cancellation. Required checks, scheduling, permissions and exit semantics are unchanged.

The dashboard keeps its selected task until the user changes it. New failures raise a notice; n selects the next failed task, arrows select tasks, and the existing log keys inspect complete retained view detail. Ctrl-C uses the same cooperative interruption path as plain output and restores terminal state. oyzu history <invocation-id> --json provides a bounded summary after a local bundle is published; oyzu inspect <bundle-directory> --json verifies the full bundle. See history scope and limits.
