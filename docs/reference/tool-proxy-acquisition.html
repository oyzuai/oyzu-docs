Downloading tools through a proxy

CLI reference

Published from the canonical docs/reference/tool-proxy-acquisition.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Administrative tool routes send tool archives and metadata through an approved mirror or proxy. The acquisition owner uses the same route rules for built-in providers, registry recipe tools, the pinned short-name catalog, artifact sets, recipe evidence and tool-index metadata. Routing applies on Linux, Windows and macOS and does not depend on standalone or managed configuration. Each provider's supported installation platforms and managed admission requirements still apply.

Routes change the source of bytes. They do not grant approval or replace digest, publisher evidence, tool-index admission, layout or installation checks.

Administrative configuration​

An administrator adds routes to the protected admin-settings.json, inside its settings object, or supplies them through managed policy:

"registries.routes": {
  "locked": true,
  "value": [
    {"protocol": "tools", "scope": "node", "connectorId": "corp-node"},
    {"protocol": "tools", "scope": "static.rust-lang.org", "connectorId": "corp-rust"}
  ]
}

The scope is an exact lowercase host (optionally including a port), or a tool family such as node, go, rust or oyzu:node. Built-in oyzu: and core: spellings are aliases of the bare family name. A recipe's canonical aqua: ID can select that recipe's downloads. * supplies a fallback route.

  • For a family's own release metadata, checksums and archives, a matching family scope takes precedence over a matching host scope. Node headers prepared for node-gyp use the Node family route too; their declared-fetch source admission and pinned digest checks still apply.
  • Tool-index and organization-catalog requests, including catalog edge delivery, use their service's host route, then *. Selecting Node never sends those requests through the Node family mirror.
  • A host scope takes precedence over *.
  • Two rules for the same scope, including family aliases, fail with ROUTE_RULE_CONFLICT; configuration order does not choose a winner.
  • With no tools routes, providers download directly using their reviewed upstream host lists. Redirects outside that provider's hosts are refused; registry recipes may additionally admit their pinned public download hosts. Index/catalog metadata retains its own service hosts. Artifact sets retain their standalone direct behavior, including open HTTPS redirect hops.
  • Once any tools route exists, each download must match a family, host or fallback rule. Otherwise it fails before download with ROUTE_UNROUTABLE.
  • Only protocol tools participates. Routes cannot appear in project TOML, oyzu.local.toml or profiles.

Binding file​

The caller explicitly supplies a host binding file; Oyzu does not discover one in the project:

format = 1
[connectors.corp-node]
base_url = "https://mirror.example/node/"
authorization_env = "CORPORATE_NODE_AUTHORIZATION"
redirects = "server"

[connectors.corp-rust]
base_url = "https://mirror.example/rust/"
redirects = "client"
oyzu install --connector-bindings /absolute/path/to/host-bindings.toml
oyzu tools evidence --provider node --version 22.20.0 --connector-bindings /absolute/path/to/host-bindings.toml
oyzu tools trust refresh --connector-bindings /absolute/path/to/host-bindings.toml
KeyMeaning
base_urlHTTPS destination and fixed path prefix. Plain HTTP is permitted only for loopback fixtures. No credentials, query, fragment, dot segments or encoded path separators.
authorization_envOptional environment variable holding the complete Authorization header value.
redirects"client" (default): the client follows redirects and resolves each new host through the same table. "server": the destination must follow redirects itself; a 3xx reply fails.

The destination is base_url without its trailing slash, followed by the original URL's path and query. For example, Node's /dist/index.json goes to https://mirror.example/node/dist/index.json. This replaces Node's earlier special mapping, which removed /dist/; existing Node mirrors must serve the full upstream path. Go, Rust and every other family use the same rule.

A family route also applies to that family's own download redirect hops. A host-only client route requires a rule for each redirected host; an unlisted hop fails with ROUTE_REDIRECT_UNROUTABLE. Server routes reject redirects with ROUTE_REDIRECT_UNEXPECTED. Redirect targets and credentials are never recorded in locks or printed. The metadata commands tools versions, tools check --catalog and tools migrate also accept --connector-bindings. Keep credentials in secret provisioning, outside project files, binding files and arguments. Publisher credentials are not forwarded to a configured mirror; its binding supplies its authorization.

Failures, locks and offline use​

Missing bindings or credentials, denied requests and failed verification are terminal; Oyzu does not retry through an alternative public source. Fix the administrative rule or binding and retry. Removing every tools route restores direct acquisition without changing locked content identities.

The lock keeps logical source URLs and digests, never mirror destinations or credentials. Offline acquisition uses only already available store inputs and verified metadata; missing inputs fail without contacting a mirror. A cached provider installation needs no connector credentials. An online acquisition loads its binding table once and reuses its HTTP client while the destination origin and connector stay the same. Changes to bindings take effect in a new acquisition.

Managed catalog approval, index withdrawal and publisher verification remain binding. A route cannot make an unapproved tool installable. The sandbox runtime and Sigstore trust refresh also consult host routes. Plugin package downloads (OCI and HTTPS) retain their catalog routing contract; unifying those downloads is a follow-up.

Reproducing mirror installation checks​

tooling/test-tool-routes.py drives ROUTE-01, ROUTE-02, ROUTE-03 and ROUTE-05 through a compiled CLI. It requires a Linux amd64 disposable administrator host, Python 3.11+, OpenSSL, an empty /etc/oyzu administrative configuration, and space for three fresh tool stores. Do not run it on an enrolled workstation. It refuses existing administrative settings, restores its tampered fixture, and removes the stores and administrative file it creates. Recorded archives are retained for reproducibility and are never treated as verified publisher evidence. The mirror serves only recorded files over HTTPS.

From the repository root under /srv/dev, after building target/debug/oyzu, prepare the small pinned input in ignored storage. Name each tool explicitly and run one pin command per tool from that project root:

proof_dir="$PWD/.oyzu/tool-route-proof"
proof_project="$proof_dir/project"
mkdir -p "$proof_project" "$proof_dir/scratch"
printf '[tools]\nlockPlatforms=["linux/amd64/gnu"]\n' > "$proof_project/oyzu.toml"
target/debug/oyzu --root "$proof_project" -C "$proof_project" pin go@1.24.13
target/debug/oyzu --root "$proof_project" -C "$proof_project" pin node@22.20.0
target/debug/oyzu --root "$proof_project" -C "$proof_project" pin rust@1.99.1
python3 tooling/test-tool-routes.py --cli target/debug/oyzu --project "$proof_project" --archives "$proof_dir/archives" --scratch "$proof_dir/scratch" --record

Bare oyzu pin discovers the tools required by native projects or declared build targets. In this tools-only fixture, PROJECT_NOT_FOUND means that discovery found no native project or declared build target; a [tools] table alone is not such a target. Use the explicit tool specs above. Rust and archive tools use different resolution contracts, so combining Rust with Go or Node in one pin command raises TOOL_FLAGS_CONFLICT. Multiple archive-tool specs remain supported; the fixture uses separate commands for all three tools.

Create a local CA and a server leaf signed by it. The CA has CA:TRUE; the leaf has CA:FALSE, server-auth usage and a localhost subject alternative name:

openssl req -x509 -newkey rsa:2048 -nodes -keyout "$proof_dir/ca.key" -out "$proof_dir/ca.pem" -days 1 -subj '/CN=route proof CA' -addext 'basicConstraints=critical,CA:TRUE' -addext 'keyUsage=critical,keyCertSign'
openssl req -newkey rsa:2048 -nodes -keyout "$proof_dir/mirror.key" -out "$proof_dir/mirror.csr" -subj /CN=localhost
cat > "$proof_dir/leaf.ext" <<'EOF'
basicConstraints=critical,CA:FALSE
keyUsage=critical,digitalSignature,keyEncipherment
extendedKeyUsage=serverAuth
subjectAltName=DNS:localhost
EOF
openssl x509 -req -in "$proof_dir/mirror.csr" -CA "$proof_dir/ca.pem" -CAkey "$proof_dir/ca.key" -CAcreateserial -days 1 -extfile "$proof_dir/leaf.ext" -out "$proof_dir/leaf.pem"
cat "$proof_dir/leaf.pem" "$proof_dir/ca.pem" > "$proof_dir/mirror.pem"

ca.pem is the trust anchor. leaf.pem is the server certificate, and mirror.pem is the served chain, with the leaf first and the CA second. The harness serves mirror.pem with mirror.key and also sets SSL_CERT_FILE to that same --cert file; the included CA supplies its trust anchor. A client configured separately can use ca.pem as its trust bundle.

python3 tooling/test-tool-routes.py --cli target/debug/oyzu --project "$proof_project" --archives "$proof_dir/archives" --scratch "$proof_dir/scratch" --cert "$proof_dir/mirror.pem" --key "$proof_dir/mirror.key"

Record the actual outcomes in the implementing PR. A fixture precondition or upstream recording failure is a failed/not-run proof, not a passed scenario. For ROUTE-04, provision a protected node family route and a Node-only locked project on the Windows or macOS runner, set OYZU_ROUTE_TEST_PROJECT and OYZU_ROUTE_TEST_BINDINGS to those absolute paths, and run:

cargo test --locked --test integration tool_routes::node_family_route_compiled_installation -- --ignored --exact

Repeat under managed enrollment with the required signed index/catalog approval. The test does not supply enrollment or bypass protected policy. The acquisition owner's loopback integration tests run without provisioning on every host and exercise standalone and managed effective configurations; those tests alone do not establish real managed installation or native platform qualification.
