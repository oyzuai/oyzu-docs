The tool store

CLI reference

Published from the canonical docs/reference/tool-store-inspection.md file. Features marked experimental remain experimental; check support limitations before relying on them.

The tool store is the folder where Oyzu keeps downloaded archives and installed tools. Every project, shell and build on your machine shares it, so a tool version is downloaded and installed once. This page explains what's in the store, what Oyzu checks when it installs a tool, how concurrent installs and running tools are kept safe, and how to inspect an installed tool's files.

Note: Experimental. The store layout may change.

Where the store is​

PlatformDefault
Linux$XDG_DATA_HOME/oyzu/tools, or ~/.local/share/oyzu/tools
macOS~/Library/Application Support/Oyzu/tools
Windows%LOCALAPPDATA%\Oyzu\tools

Most tool commands accept --store DIR to use another store. A relative path is resolved from the current directory. Pass the same --store to install, inspect and activate. oyzu tools list --json shows the store in use.

Archive providers, registry packages and Rust all use the same store.

What is in the store​

FolderContents
installs/<key>/One installed tool: payload/ (its files) and receipt.json (what was installed, from where, and its commands).
i/<key>/Compact Windows installations: p/ holds the payload and receipt.json retains its logical paths. The key encodes the complete SHA-256 in lowercase base32.
blobs/sha256/<digest>Downloaded archives, named by their SHA-256.
staging/Installs and downloads in progress.
quarantine/Cached archives that failed their digest check, kept for you to inspect.
locks/Lock files that coordinate concurrent installs and running tools. Never delete these while Oyzu is running.
leases/Records of which installations are in use.
catalogs/, state/Cached tool index, catalogs and trust state.
shims/Command launchers (see using tools in your shell).

Verified at install, then trusted​

New Windows installations use i/ and p/ to leave more room for native library paths. Existing installs/ entries remain usable. The next oyzu install populates the compact location through normal archive and receipt verification; it never deletes or moves the older installation. Lock identities and lease identities do not change. Use oyzu tools list --details to find the selected physical paths instead of constructing paths from the lock.

Oyzu checks a tool thoroughly when it installs it, and trusts it afterward:

  • Every download must match the SHA-256 from the lock, index or publisher before it is used.
  • A new installation's files are checked against its receipt before it is committed.
  • Later commands, shells and builds check that the installation exists and that its receipt matches the lock. They don't re-hash the files.
  • A tool that is damaged or edited after install simply fails when it runs.
  • An organization catalog or the tool index can still refuse an unapproved or withdrawn version when you install or reuse it.

Tool installation receipts have no free-form annotation slot. Unknown receipt, verification, command or environment fields are rejected even when the receipt declares a newer minimum reader. The error says to reinstall the tool and retains the file unchanged. Run oyzu self update before retrying; do not remove unfamiliar fields to activate a tool. The self-install receipt has a separate compatibility contract.

Current readers understand the optional verification.strength field, including receipts that omit it. The field records publisher evidence and participates in verification identity; it is not an inert annotation. Historical readers that predate it can reject a shared store before selecting any tool. Use a current driver with current receipts. If an experiment must retain a historical driver, select a separately provisioned compatible store with --store; do not delete strength, rewrite receipts or change a lock to make the old reader accept them.

Downloads and the archive cache​

  • Archives are downloaded to a temporary file, checked and then moved into blobs/. Memory use doesn't grow with archive size.
  • A download is limited to 8 GiB and must be exactly the expected size. A short, long or mismatched download stores nothing.
  • A cached archive is checked again whenever it is used. If it no longer matches, it is moved to quarantine/ and downloaded again (online) or reported as missing with its path (offline).
  • If a lock records a digest but no size, Oyzu uses the cached archive's size.
  • Offline installs need the archive already in the cache. The error names the missing digest; retry online.

Supported archive contents​

Installs unpack tar, tar.gz, tar.xz, tar.zst, ZIP and single-file (raw) downloads, within these limits:

LimitValue
Entries200,000
Total size8 GiB
Single file1 GiB
Path depth64
Expansion ratio200:1 (some reviewed tools allow up to 1024:1)
  • Paths that escape the folder, absolute paths, Windows device names, names that differ only by case, and conflicting entries are refused.
  • Tar archives can contain files, directories and relative symbolic links. Hard links and sparse files aren't supported.
  • ZIP archives can contain stored or deflated files, directories and Unix relative symbolic links. Encrypted, multi-volume and ZIP64 archives aren't supported.
  • Symbolic links are created after all files are written, and must stay inside the tool's folder. This keeps macOS framework layouts intact.
  • Symbolic links inside archives aren't supported on Windows.
  • Ownership, set-ID bits and the archive's directory permissions aren't applied. Files are private to you, and Unix executable bits are kept.

Checking an installation before it is committed​

Before an installation is committed, Oyzu prepares it in staging/ and checks it:

  • The archive layout (how it's unpacked, which prefix is stripped, which files are commands) must match the layout recorded in the lock.
  • Every command file must exist. On Unix, declared executables are set to mode 0700.
  • Commands and environment values may only refer to files in the tool itself or its direct dependencies.
  • The receipt is written last, with the digests of the final files.

Nothing in the tool is run during this step, and oyzu.lock isn't changed. If a step fails, the staging folder is discarded and no installation is created.

Committing installations and tracking use​

Committing an installation​

  • Each installation is moved into installs/ in one atomic step, and never replaces an existing one.
  • When a tool has dependencies, each one is committed separately. If a later one fails, earlier ones stay as valid, unreferenced installations. The lock is never edited.
  • An existing valid installation is reused. A damaged one fails; Oyzu doesn't replace it or fall back to another download.
  • Windows supports long store paths, including UNC paths.

Concurrent installs and tools in use​

  • Tool installation for the same tool on the same platform takes turns across oyzu install, builds, developer commands and operation tools. A later caller prints that it's waiting, waits without a timeout, then reuses the installation the first one published instead of installing a second copy. The OS releases the install lock if its holder exits or crashes.
  • Publishing an installation or archive waits up to 30 seconds for another process publishing the same one.
  • If a store already holds several installations of one recipe with identical installed files, for example from older concurrent installs, Oyzu uses one of them. Installations of one recipe with different files still fail with TOOL_LOCK_AMBIGUOUS.
  • While a command, shell or build uses a tool, it holds a shared lock on the installation, so it can't be removed underneath it.
  • Each such use writes a small record in leases/ with its process ID, start time and installation keys. It contains no paths, environment values or credentials. The record is removed when the command ends.
  • A crash can leave a record or a .pending file behind. Oyzu cleans these up when it next starts an install, but only once their locks show nobody is using them. It never deletes an installation during cleanup.
  • Records it can't verify are left for manual review.

Lease records also reject unknown fields. Recovery retains such a record and counts it under unverified_or_failed; it does not interpret the extra data as permission to remove the record or an installation. The recorded process ID and creation time must match the lease ID; OS locks determine whether a lease is still in use.

Containers and sandboxes​

Give each container or sandbox its own store with --store DIR; use the same directory for installation and execution inside that environment. Avoid bind mounting a host store into a container, bwrap or Flatpak sandbox that has a different PID or mount namespace.

An unrestricted /proc mount (hidepid=0) only exposes processes visible in its PID namespace. Another namespace can hide a tool holder or show its files under different paths. A scan that finds no holder therefore does not prove a shared installation is unused. Keep shared installations until all environments using that store have stopped; do not manually remove them while tools run.

The collector must have Linux's initial PID namespace inode (4026531836); another or unrecognized value retains entries even if the collector and its PID 1 have matching namespaces. It compares PID and mount namespaces for same-user processes and processes with root UIDs or effective DAC capabilities. Nested or unknown NSpid information for privileged or foreign-user processes also retains entries, including a missing, empty or malformed field.

Bind/subtree mounts, overlay mounts, visible store aliases and mounts receiving propagation (master: or propagate_from:) retain entries. A store device that differs from the collector's root device also retains entries. Missing namespace or mount information, including unreadable /proc/1/ns, prevents collection. These conservative checks can retain an entire private store on an unrestricted host, a separate filesystem or a filesystem subvolume.

These are process and mount observations, not an inventory of every store export. User namespace identities are not compared. Use separate stores for containers and sandboxes. A foreign-user process with a single valid NSpid and no current root UID or effective DAC capability is excluded from holder inspection. It may still hold files opened before dropping privileges or received through descriptor passing (SCM_RIGHTS). This host-PID case, including a container using the host PID namespace, remains a gap even if it uses another mount namespace.

To reclaim an existing shared store, stop every environment using it and run oyzu tools prune on the host with unrestricted procfs access, then apply the preview. Keep locks and lease records intact.

Interrupted installs​

Installs work in their own folder under staging/. If an install is interrupted, the next install removes abandoned staging folders, but only when no other install is running. Older leftover staging files (.tmp* and top-level blob-*) and quarantined archives are kept for you to inspect and delete.

Payload tree observation​

oyzu tools inspect-tree lists the files of an installed tool, with their digests, so you can compare or audit an installation. It's a diagnostic command; Oyzu never runs it automatically.

oyzu tools list --details                       # find installation paths
oyzu tools inspect-tree <store>/installs/<id>/payload

  • --json returns bytes, digest, entries[] (path, type, size, digest, executable, target), manifest_digest and validation.
  • Each file's entry has its digest, size and Unix executable bits (always zero on Windows). Directories and relative symbolic link targets are listed. Timestamps, owners and ACLs aren't included.
  • It never runs files, follows links inside the tree or changes anything.
  • Exit 0 on success, 2 on error.
  • A relative path is resolved from -C, --root or the current directory. The path must not contain .. or pass through a symbolic link.
  • Hard links to files outside the tree, special files and files that change during the scan fail.
  • Limits: 200,000 entries, 8 GiB in total, 1 GiB per file, path depth 64 and 64 link hops.

validation: "payload-observation-only" means this is a snapshot of what was on disk when read. It doesn't prove the files are authentic or haven't been changed by another process at the same time.

Reclaim unreferenced content​

oyzu tools prune previews eligible tool installations, downloaded blobs and plugin installations, with their logical file size and a reason for every entry. Only --apply removes content. It runs offline and needs no account.

Illustrative usage:

oyzu tools prune
oyzu tools prune --store /path/to/private-store
oyzu tools prune --store /path/to/private-store --apply
oyzu --json tools prune --store /path/to/private-store
OptionDefaultMeaning
--store DIRShared user store aboveInspect or clean this store; relative to the invocation directory.
--applyOffRemove eligible entries instead of previewing.
--jsonOffReturn the same entries, states, byte counts and reasons as JSON.

What stays​

There is no index of other projects' current paths. Collection keeps everything named by the current project lock, the global lock next to the selected user configuration, and every recorded developer-selections lock snapshot. Snapshots are conservative historical references, so uninstalling a declaration may not make its installation eligible. Collection never scans your disk for projects.

Every installed tool receipt also protects the archive, installer and dependency installations it names. Installed plugins protect their archive blobs. Archive blobs protected by a removed receipt may become eligible on a later invocation. Action results remain owned by oyzu cache clear; collection leaves caches, engines, trust state, shims, staging, quarantine and permanent locks alone.

Active use leases and lease journals retain installations. Concurrent Oyzu commands keep their referenced installations while they run; collection holds the entry’s mutation and exclusive use locks through removal. Entries whose permanent mutation or use lock is missing or busy stay. The last recorded store access or use lease within 30 days also retains an entry, as does an uncertain timestamp. Store access refreshes lock-file timestamps without reading installed payloads. Older clients did not record every use this way; their lock-file timestamps only record creation. Known locks, receipts and active leases still protect them.

Linux additionally checks the current user's executable, working-directory, open-file and mapped-file process references through /proc, including readable /proc/<pid>/task/<tid>/fd tables for threads with separate file descriptors. An unreadable live thread table retains the entry; scanning continues to find definite holders in other readable tables. A missing table is ignored only when the thread is confirmed gone. The leader alias and kernel-confirmed shared tables are read once after successful inspection; unsupported or denied sharing checks fall back to independent scans. Collection requires a private store owned by that user (mode 0700). Before trusting the process listing, it checks /proc/self/mountinfo. A restricted mount (hidepid other than 0/off, or a subset option), unreadable mount information or an unrecognized procfs root prevents reclamation: the listing may omit a live holder entirely. This conservatively applies even to namespace root or callers with a mount's privileged group; prune does not attempt to prove a privilege bypass. It also checks namespace identities and the store's mounts as described under containers and sandboxes. Observed namespace sharing or unavailable evidence prevents reclamation even when hidepid=0.

On an unrestricted mount, a process is excluded only when its real, effective, saved and filesystem UIDs all belong to other users and are nonzero, and its readable CapEff has neither CAP_DAC_OVERRIDE nor CAP_DAC_READ_SEARCH, and NSpid contains exactly one valid positive process ID. Missing or malformed CapEff for a non-root foreign process retains entries. Missing, nested or invalid NSpid for that process also retains entries. A private store limits new opens; it cannot rule out previously opened or passed descriptors, as described under containers and sandboxes. Root UIDs and these capabilities can bypass a private store's permissions, so those processes remain subject to namespace and holder inspection. An unreadable identity or undecidable same-user process retains candidates, including a zombie whose descriptor directory cannot be read. Inspection continues after an undecidable process so a positively observed running-tool reference can still be reported. Permission errors identify the process path that could not be inspected. If the store is not private, it retains candidates because other users' process use cannot be established.

On CI container runners, a restricted /proc or an unreadable same-user process, including a zombie with an inaccessible descriptor directory, may therefore retain every candidate and reclaim nothing. Retention is the safe result: prune cannot establish that a hidden or unreadable process holds no file, mapping, working directory or executable in the store. For zombie retention, rerun after the parent has reaped the exited process. For a restricted mount, use a host with unrestricted procfs visibility. Do not remove locks or retention records to force cleanup.

Windows preflights every file with exclusive access: in-use or mapped files stay, without forced deletion. On macOS, direct process use cannot yet be established, so candidates stay.

Unreadable locks, snapshots, receipts or journals inhibit removal and appear in entry reasons. Unknown entry names, links, hardlinked files and layouts exceeding inspection bounds stay for manual inspection. Collection reads metadata and file sizes; it never hashes or re-verifies installed payloads.

Results and recovery​

Human output leads with the result, then lists kind, path, size, state and reason. JSON returns store, apply, bytes, entries, locksChecked, recentDays and note. Each entry has kind, path, bytes, state and reason; an unmeasured entry has bytes: null (shown as unknown in human output). bytes at the result root sums eligible or completely removed entries; it is a logical size, not a guarantee of filesystem space freed.

StateMeaning
eligiblePreview found this entry removable; no files changed.
removedApply completed removal.
retainedReferenced, recently used, busy, or uncertain; entry kept.
incompleteRemoval started but an OS error stopped it; some files may be gone.

Exit 0 means observation completed, including deliberate retention; exit 1 means an incomplete removal; exit 2 means a command/input/store access error. Resolve reported permissions, busy processes or filesystem errors, then preview again before applying. Do not delete permanent locks or retention records to force eligibility. Keep project lock files available when collecting; projects with no recorded snapshot and no visible lock cannot be discovered by this command. Process visibility can change between entries and invocations. A preview's eligibility is an observation, not a promise that a later apply will remove the entry; apply checks the same safeguards again.

Limits​

  • Collection is explicit; there is no automatic or background cleanup. Recorded lock snapshots can keep older versions indefinitely.
  • Locks coordinate Oyzu processes. They don't protect the store from other programs running as your user.
