The tool store

CLI reference

Published from the canonical docs/reference/tool-store-inspection.md file. Features marked experimental remain experimental; check support limitations before relying on them.

The tool store is the folder where Oyzu keeps downloaded archives and installed tools. Every project, shell and build on your machine shares it, so a tool version is downloaded and installed once. This page explains what's in the store, what Oyzu checks when it installs a tool, how concurrent installs and running tools are kept safe, and how to inspect an installed tool's files.

Note: Experimental. The store layout may change.

Where the store is​

PlatformDefault
Linux$XDG_DATA_HOME/oyzu/tools, or ~/.local/share/oyzu/tools
macOS~/Library/Application Support/Oyzu/tools
Windows%LOCALAPPDATA%\Oyzu\tools

Most tool commands accept --store DIR to use another store. A relative path is resolved from the current directory. Pass the same --store to install, inspect and activate. oyzu tools list --json shows the store in use.

Archive providers, registry packages and Rust all use the same store.

What is in the store​

FolderContents
installs/<key>/One installed tool: payload/ (its files) and receipt.json (what was installed, from where, and its commands).
blobs/sha256/<digest>Downloaded archives, named by their SHA-256.
staging/Installs and downloads in progress.
quarantine/Cached archives that failed their digest check, kept for you to inspect.
locks/Lock files that coordinate concurrent installs and running tools. Never delete these while Oyzu is running.
leases/Records of which installations are in use.
catalogs/, state/Cached tool index, catalogs and trust state.
shims/Command launchers (see using tools in your shell).

Verified at install, then trusted​

Oyzu checks a tool thoroughly when it installs it, and trusts it afterward:

  • Every download must match the SHA-256 from the lock, index or publisher before it is used.
  • A new installation's files are checked against its receipt before it is committed.
  • Later commands, shells and builds check that the installation exists and that its receipt matches the lock. They don't re-hash the files.
  • A tool that is damaged or edited after install simply fails when it runs.
  • An organization catalog or the tool index can still refuse an unapproved or withdrawn version when you install or reuse it.

Downloads and the archive cache​

  • Archives are downloaded to a temporary file, checked and then moved into blobs/. Memory use doesn't grow with archive size.
  • A download is limited to 8 GiB and must be exactly the expected size. A short, long or mismatched download stores nothing.
  • A cached archive is checked again whenever it is used. If it no longer matches, it is moved to quarantine/ and downloaded again (online) or reported as missing with its path (offline).
  • If a lock records a digest but no size, Oyzu uses the cached archive's size.
  • Offline installs need the archive already in the cache. The error names the missing digest; retry online.

Supported archive contents​

Installs unpack tar, tar.gz, tar.xz, tar.zst, ZIP and single-file (raw) downloads, within these limits:

LimitValue
Entries200,000
Total size8 GiB
Single file1 GiB
Path depth64
Expansion ratio200:1 (some reviewed tools allow up to 1024:1)
  • Paths that escape the folder, absolute paths, Windows device names, names that differ only by case, and conflicting entries are refused.
  • Tar archives can contain files, directories and relative symbolic links. Hard links and sparse files aren't supported.
  • ZIP archives can contain stored or deflated files, directories and Unix relative symbolic links. Encrypted, multi-volume and ZIP64 archives aren't supported.
  • Symbolic links are created after all files are written, and must stay inside the tool's folder. This keeps macOS framework layouts intact.
  • Symbolic links inside archives aren't supported on Windows.
  • Ownership, set-ID bits and the archive's directory permissions aren't applied. Files are private to you, and Unix executable bits are kept.

Checking an installation before it is committed​

Before an installation is committed, Oyzu prepares it in staging/ and checks it:

  • The archive layout (how it's unpacked, which prefix is stripped, which files are commands) must match the layout recorded in the lock.
  • Every command file must exist. On Unix, declared executables are set to mode 0700.
  • Commands and environment values may only refer to files in the tool itself or its direct dependencies.
  • The receipt is written last, with the digests of the final files.

Nothing in the tool is run during this step, and oyzu.lock isn't changed. If a step fails, the staging folder is discarded and no installation is created.

Committing installations and tracking use​

Committing an installation​

  • Each installation is moved into installs/ in one atomic step, and never replaces an existing one.
  • When a tool has dependencies, each one is committed separately. If a later one fails, earlier ones stay as valid, unreferenced installations. The lock is never edited.
  • An existing valid installation is reused. A damaged one fails; Oyzu doesn't replace it or fall back to another download.
  • Windows supports long store paths, including UNC paths.

Concurrent installs and tools in use​

  • Installs of the same tool or archive wait for each other, for up to 30 seconds.
  • While a command, shell or build uses a tool, it holds a shared lock on the installation, so it can't be removed underneath it.
  • Each such use writes a small record in leases/ with its process ID, start time and installation keys. It contains no paths, environment values or credentials. The record is removed when the command ends.
  • A crash can leave a record or a .pending file behind. Oyzu cleans these up when it next starts an install, but only once their locks show nobody is using them. It never deletes an installation during cleanup.
  • Records it can't verify are left for manual review.

Interrupted installs​

Installs work in their own folder under staging/. If an install is interrupted, the next install removes abandoned staging folders, but only when no other install is running. Older leftover staging files (.tmp* and top-level blob-*) and quarantined archives are kept for you to inspect and delete.

Payload tree observation​

oyzu tools inspect-tree lists the files of an installed tool, with their digests, so you can compare or audit an installation. It's a diagnostic command; Oyzu never runs it automatically.

oyzu tools list --details                       # find installation paths
oyzu tools inspect-tree <store>/installs/<id>/payload
Payload inspection

Bytes: 3
Digest: sha256:79a94bbfa8c76fb62b27ce178116533fb1e8239516c2015be5e8e8123793b851
Entries:
Digest                                    Executable  Path   Size           Target         Type
not specified                             73          bin    not specified  not specified  directory
sha256:98ea6e4f216f2fb4b69fff9b3a44842c3  73          bin/x  3              not specified  file
8686ca685f3f55dc48c5d3fb1107be4
Manifest digest: sha256:7a8aea237bd28004828e36b056b48fbdb164f8c7dd1cb244c288f9111ad1a718
Validation: payload-observation-only
  • --json returns bytes, digest, entries[] (path, type, size, digest, executable, target), manifest_digest and validation.
  • Each file's entry has its digest, size and Unix executable bits (always zero on Windows). Directories and relative symbolic link targets are listed. Timestamps, owners and ACLs aren't included.
  • It never runs files, follows links inside the tree or changes anything.
  • Exit 0 on success, 2 on error.
  • A relative path is resolved from -C, --root or the current directory. The path must not contain .. or pass through a symbolic link.
  • Hard links to files outside the tree, special files and files that change during the scan fail.
  • Limits: 200,000 entries, 8 GiB in total, 1 GiB per file, path depth 64 and 64 link hops.

validation: "payload-observation-only" means this is a snapshot of what was on disk when read. It doesn't prove the files are authentic or haven't been changed by another process at the same time.

Limits​

  • Store cleanup (pruning unreferenced installations) isn't available yet. oyzu tools list shows unreferenced installations.
  • Locks coordinate Oyzu processes. They don't protect the store from other programs running as your user.
