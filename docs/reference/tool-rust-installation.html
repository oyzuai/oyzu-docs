Rust installation

CLI reference

Published from the canonical docs/reference/tool-rust-installation.md file. Features marked experimental remain experimental; check support limitations before relying on them.

oyzu can install the Rust toolchain for your project (rustc, Cargo, rustdoc, rustfmt, Clippy and the LLVM coverage tools) and the Cargo helpers the Rust builder uses, so you don't need rustup or Rust installed on the machine. The exact release is recorded in oyzu.lock.

Usage​

Pinning is optional. With nothing declared, oyzu pin or your first oyzu build picks the newest stable Rust and records it in oyzu.lock. To choose a version, set it in oyzu.toml or in rust-toolchain.toml:

[tools]
rust = "1.95.0"
oyzu install rust
oyzu which cargo
rustc --version
cargo build
oyzu install rust --frozen --offline

In an activated shell, which the install script sets up, the plain tool commands run the pinned versions. Where a shell isn't activated, prefix them with oyzu exec --.

oyzu install rust checks that rust is configured, then installs the project's whole tool selection into one lock. Bare oyzu install does the same for every configured tool.

How the version is chosen​

SourceRole
rust-toolchain.toml or rust-toolchain, the nearest one from the build folder up to the project rootThe request. It's a native pin file; see Rust toolchain files
[tools] rust (or [tools]."oyzu:rust")The request when no toolchain file applies. Otherwise it must agree with the file
rust-version in Cargo.tomlA minimum every selection must meet
None of thesestable: the newest stable release

Accepted requests are an exact stable version (1.95.0) or stable. oyzu resolves stable to one exact release and keeps it in the lock; offline commands and oyzu pin --refresh don't move it. oyzu install rust and oyzu update rust need an exact version in configuration. Beta, nightly, partial versions such as 1.95, dated channels and ranges aren't supported.

A fresh stable request needs the network. Offline, it works only when the lock already has the selection.

How Rust is installed​

When it installs Rust, oyzu:

  1. Downloads the official channel manifest for the exact release and its published SHA-256, and checks that every needed component has a URL and digest.
  2. Downloads each component and a fixed rustup installer, checking each against its digest.
  3. Runs rustup against a private local copy of those files, with its own private Cargo and rustup homes, a minimal profile, the listed components and targets, and self-update turned off. Nothing outside those files is downloaded.
  4. Stores the finished toolchain as an archive in oyzu's tool store, with its license files.

Reinstalling from the lock (--frozen) restores that archive and doesn't run rustup. If both the installation and the archive are gone, run an online update; oyzu won't silently build a different archive for an existing digest.

The default profile also installs the standard libraries for the targets the Rust builder supports. Having a target's standard library doesn't mean you have a linker for it.

What oyzu sets when Rust runs​

  • The toolchain's bin directory goes first on PATH.
  • RUSTC and RUSTDOC point at the installed binaries.
  • RUSTUP_TOOLCHAIN points at the installed toolchain, so Cargo subcommands from your own Cargo home can't pick a different global Clippy or rustfmt.

Cargo still downloads crates and Git dependencies itself, and your Cargo cache and configuration are separate from the installed toolchain.

Prerequisites​

oyzu doesn't install system linkers or SDKs:

PlatformYou need
Windows (MSVC)Visual Studio Build Tools with the C++ workload and a Windows SDK. The IDE isn't needed
macOSApple Command Line Tools, which provide the SDK, linker and Git (oyzu uses Git to infer versions). Check with xcode-select -p, xcrun --show-sdk-path and git --version; install with xcode-select --install. Some builders may need full Xcode
GNU or LLVM targetsLLVM or MinGW installed yourself, if you select those toolchains

CMake and other build tools your crates need are also up to you.

Pinned native Rust and task execution​

On Windows x86-64, for a Rust-only project:

oyzu pin
oyzu install
oyzu run install

oyzu run install runs the Rust builder's executable installation task; it doesn't install tools. The compiler platform is windows/amd64/msvc. If an installation was made by an older oyzu or for a different pin, run oyzu install --update rust.

oyzu run uses tools from the default user-level tool store. It puts them on PATH (and sets RUSTC/RUSTDOC) for the whole task and its hooks. If a needed tool isn't installed, the task fails before any hook runs and tells you to run oyzu install. Listing tasks and help don't need tools. To use a custom store, use oyzu exec --store; oyzu run doesn't accept one.

Discovered native helper installation​

The Rust builder needs cargo-nextest 0.9.146 for tests and cargo-llvm-cov 0.9.1 for coverage. You don't have to list them: after oyzu pin,

  • oyzu install installs everything the enabled build stages need;
  • oyzu build --full installs and runs the quality stages;
  • plain oyzu build installs only what compiling needs, unless configuration turns on more checks;
  • oyzu run test uses the pinned helpers but needs them installed first.

You can also set them in [tools] as cargo:cargo-nextest and cargo:cargo-llvm-cov (short names work too). Other versions fail with a clear error. oyzu never runs cargo install or builds helpers from source.

oyzu tools current, oyzu which, oyzu exec and activated shells use the selection of the nearest build target. Child targets don't change a parent shell's tools. If pins are missing, run oyzu pin; oyzu build never re-pins on its own. If installations are missing, run an online install; --offline reuses installed tools and cached archives only.

Installations live in the shared user store and are reused across projects; the project lock stays portable.

Indexed Rust and organization catalogs​

When toolCatalog.url is set (see organization tool catalog), pin, install and build only use an approved release from the signed index:

  • The downloaded channel manifest must match the index's SHA-256, and its full component list must match the indexed one.
  • Every component selected by rust-toolchain.toml and the rustup installer must match an indexed URL and digest. There's no fallback to the public site.
  • Locked selections are checked against the current catalog before install or reuse.
ErrorCause
TOOL_NOT_IN_CATALOGThe release isn't approved
TOOL_NOT_IN_INDEXThe tool isn't indexed, or its record has no component list
TOOL_CATALOG_MISMATCHThe indexed and locked inputs differ

A downloaded file with the wrong digest fails before rustup starts. cargo: helpers are refused under a catalog. Corporate mirror routes for Rust aren't supported.

To see what an index entry would contain, run oyzu tools evidence --provider rust --version 1.95.0 (see tools evidence).

One lock file​

All tool selections live in one oyzu.lock (see lock inspection). oyzu pin updates what's selected; oyzu install records what's installed. Neither edits oyzu.toml or native files.

CommandWhat it does
oyzu pinResolves every tool the project needs, on every platform it builds for, and writes oyzu.lock. Doesn't install anything
oyzu pin --dry-runShows the result without writing. With --json, the proposed lock is in proposed_files. Exits 0 when complete, 2 when something couldn't be resolved
oyzu pin --refreshRe-fetches installation details for the versions already selected, without upgrading. Needs the network
oyzu pin --refresh --dry-runPreviews the refresh

A failed or incomplete pin doesn't replace the lock. If two sources disagree on a version, the error names both files and versions and confirms nothing changed.

oyzu writes the lock and related files through a recovery journal (.oyzu-pin-journal.json). If a pin is interrupted, the next pin finishes it. Commands that read tools refuse to run while the journal is unfinished. If a file was changed by something else in the meantime, pin keeps the journal and fails with PIN_EDIT_CONFLICT.

Builds in Docker​

Isolated builds use the locked compiler too. With no oyzu.lock, the first build resolves and writes one before it starts.

  • Linux ARM64 builds use the arm64 execution image, oyzu-execution/base:1-linux-arm64 until the image is published. oyzu checks its architecture but doesn't install emulators.
  • oyzu install never sets up a Linux worker just because build.yaml declares Rust targets.
  • The installer container gets 6 GiB of scratch space, 8 GiB of memory and two CPUs, with no network and a read-only root. Make sure Docker allows that much.

Offline Rust builds​

oyzu build --offline needs an existing lock and a cached compiler. It doesn't resolve versions or change the lock, and it fails without running an installer if the compiler is missing.

Offline builds work only for projects whose Cargo.lock has no registry or Git dependencies (local workspace packages are fine). Otherwise the build fails before fetching, because cached crate replay isn't available yet.

Supported platforms​

PlatformStatus
Linux x86-64 (glibc)Supported
Windows x86-64 (MSVC)Supported
macOS IntelSupported with an existing lock; automatic default pinning isn't available yet
Windows ARM64 (MSVC)oyzu install installs Rust from a lock that covers windows/arm64/msvc; building on this platform isn't verified yet
macOS Apple silicon, Linux ARM64Not supported yet

Helper installation (cargo-nextest, cargo-llvm-cov) is supported on Windows x86-64; on other platforms it isn't supported yet.

Missing installed components​

If a failed Rust command reports a missing component of its selected Oyzu installation, TOOL_COMPONENT_MISSING names Rust's version, the component and the install folder. Remove that folder and run the exact install command shown in the diagnostic; do not use rustup component add on the custom sysroot. Cargo's missing-Clippy command error is also diagnosed when the selected payload's Clippy executable is absent. Native action logs retain the tool's output. See missing installed executables and components for recovery, offline requirements and failure-path-only detection.
