Tool Rust Installation

CLI reference

Published from the canonical docs/reference/tool-rust-installation.md file. Features marked experimental remain experimental; check support limitations before relying on them.

See tool management for shared prerequisites, command conventions and qualification limits.

Rust installation through the frozen native worker​

The current implementation uses Oyzu's compiled worker to invoke rustup with broker-verified frozen inputs. Its command mechanics are adapted from the pinned mise source, without initializing mise settings, loading backends or consulting mise configuration. Cargo/Rustup homes remain private to the installation; rustup uses a minimal profile, explicit components/targets and disabled self-update. Both native streams go to diagnostics while the worker's stdout remains a private protocol. The returned sysroot must reside inside the private Rustup home. This extraction is undergoing real-host qualification; earlier evidence below describes the former embedded implementation and does not qualify this replacement.

The Rust integration is being verified through the same install, which, exec, environment and shell contracts as Node/Go. It requires a current Oyzu frontend and a Rust selection declared in native toolchain files or Oyzu TOML:

[tools]
rust = "1.95.0"
oyzu install rust
oyzu which cargo
oyzu exec -- rustc --version
oyzu exec -- cargo build
oyzu install rust --frozen --offline

An explicit install name must already be configured. It validates the name and installs the complete configured project selection, retaining one environment lock rather than creating a separate Rust installation workflow. Bare install continues to install all configured tools. Rust recipes use exact three-part stable versions. Pinning and isolated first-build resolution also accept the native stable channel, resolving it to one exact release before acquisition and plan freeze. Windows amd64 installations select the MSVC compiler (the host's platform, like Linux and macOS) and consume the matching pinned recipe, including its formatting, lint and coverage components. Windows selections retain a separate native platform identity for each helper; see discovered helper installation. The experimental Linux compiler profile also installs rustfmt, Clippy, LLVM coverage tools and standard libraries for the six binary targets supported by the Rust builder. Native rustup owns component and target installation. Discovery reads every rust-toolchain file form (see Rust toolchain files); resolving beta/nightly, partial-version or dated channels remains subsequent functional work.

For stable, the resolver first uses the admitted signed index and organization catalog. Standalone publisher fallback, when allowed by existing controls, reads the checksum-verified official stable channel manifest only to select the exact version. Its versioned manifest, components and installer still pass the existing exact recipe/acquisition checks. The lock retains request stable and its exact selection. Offline reuse and pin --refresh retain that selection; they do not move the channel. A fresh offline request without locked metadata remains unresolved. The original source and Cargo minimum remain binding. See the original stable qualification for the observed gap and current native verification status. This addition covers pinning, frozen reuse and isolated first-build selection; direct install/update entry points still require an exact configured Rust release.

The worker performs rustup installation in private homes. Oyzu packages the completed compiler sysroot into its existing cached archive/store format, retaining bundled notices; the receipt identifies the published Cargo/rustc/rustdoc commands. The lock's digest-only evidence covers that generated snapshot, not a claim of signed publisher verification or a captured bootstrap download closure. Frozen cached restoration does not invoke rustup. If both installation and archive are absent, restore online through explicit update; do not silently regenerate a different archive for an existing digest.

Pinned Rust installation captures and verifies each recipe input through Oyzu's broker, then gives rustup a private local distribution mirror. An organization catalog now governs indexed Rust releases and every selected component; see below. Configured Rust connector routes remain unsupported, with no direct fallback from an enforced route. Cargo package/Git acquisition remains ordinary Cargo behavior. Mutable Cargo cache/configuration is separate from the committed compiler payload. Execution sets RUSTC and RUSTDOC to selected native binaries and prepends their bin directory; no ambient rustup installation supplies the compiler. A compatible system linker is a prerequisite: Windows MSVC requires Visual Studio Build Tools with the C++ workload (no IDE) and its Windows SDK; macOS requires command line tools. A GNU/LLVM recipe, if selected explicitly, requires externally provisioned LLVM/MinGW. Installing Rust does not install MSVC, Windows SDKs or other system prerequisites.

Acceptance is exercised by tooling/test-tool-rust.py. At 9ddf621, Linux amd64 passed real installation with ambient Rust removed from PATH, store-owned Cargo/rustc/rustdoc version checks, dependency-free compilation and program execution, frozen reuse with unchanged lock bytes, and building the actual Oyzu checkout's default frontend using the installed compiler. The last check reused the provisioned Cargo dependency cache; it does not establish dependency capture or an isolated Oyzu build. A subsequent run with container networking disabled restored the removed installation from its cached snapshot and compiled the sample project again. Native Windows/macOS Rust qualification remains pending.

Local Linux Rust worker from Windows (experimental)​

Native Linux arm64 GNU is admitted. Remote arm64 installation uses the explicitly provisioned oyzu-toolchain/worker:v1-linux-arm64 sibling and verifies its actual architecture. Oyzu does not provision images or emulators. Native ARM64 and this worker sibling still need qualification.

Ordinary oyzu install now installs only the native development selection; it never provisions a Linux compiler worker merely because build.yaml declares Rust targets. Isolated build preparation remains a separate execution path.

Earlier acceptance proved Windows-to-Linux provisioning through a prebuilt oyzu-toolchain/worker:v1 image. That historical flow is no longer part of ordinary installation. The captured-build machinery and its image prerequisites remain independent; native installation does not qualify isolated builds.

The remote Linux installer uses a private 6 GiB executable tmpfs and an 8 GiB container memory limit with two CPUs. Rustup keeps downloaded inputs, expanded components and transaction scratch concurrently; the earlier 2 GiB scratch limit failed the repository's 12-component Rust 1.99.1 recipe during extraction. The larger bound completed that installation during qualification. Network denial, the read-only root and distribution inputs, dropped capabilities and no-new-privileges remain required. The separate restoration worker also uses 6 GiB scratch and an 8 GiB memory limit: its verified private archive, cached archive and extracted tree coexist. The measured repository recipe required at least 3,276,915,836 bytes before filesystem overhead and exhausted its earlier 3 GiB bound. That recipe completed restoration under the larger limit; this does not qualify the full isolated build. Neither stage removes locked components. Hosts must have sufficient container resources.

Pinned native Rust and task execution​

For a Rust-only Windows amd64 project, run oyzu pin, oyzu install, then oyzu run install. The last command is the Rust builder's executable installation task; it does not provision tools. An older MSVC or differently pinned installation requires explicit oyzu install --update rust; stale records are never relabeled. The native compiler's platform is windows/amd64/msvc. The pinned recipe's cross-target standard libraries may also be installed; their presence does not establish that cross-linkers are available.

Installation uses the existing verified store and records the recipe digest in the tool record's options. After publication, install --frozen --offline verifies and reuses the installed selection or restores its cached archive. Missing cached payloads fail. The version-1 lock retains its other platform resolution recipes.

oyzu run obtains verified tools from the default user-level store using discovery's resolved configuration snapshot. It holds installation leases for the complete task/hook sequence and prepends verified tool binaries to PATH; Rust also supplies explicit RUSTC/RUSTDOC paths. Other task-specific environment values are retained. Missing verified selections fail before task hooks, with an oyzu install remedy; listing/help do not acquire tool leases. Custom stores are available through oyzu exec --store, not through oyzu run in this slice. Native linker, CMake and other package-specific prerequisites remain external. Managed task environments and wider native platform qualification remain pending.

Rust compiler metadata preflight​

Before a new Rust installation, the admitted tool broker fetches the exact stable channel manifest and its published SHA-256 checksum. The adapter verifies the manifest and checks that every requested compiler component has a published URL and digest. Missing components or mismatched checksums fail before launching rustup. Metadata parsing itself installs nothing and creates no state.

Metadata acquisition also pins a versioned rustup installer using its published checksum. The broker verifies every selected input before the compiled worker invokes rustup. Existing locked offline archive reuse does not invoke this new-install metadata preflight.

Indexed Rust and organization catalogs​

oyzu tools evidence --provider rust --version 1.95.0 produces the existing artifact-set shape for all five index platforms, marking macOS amd64 unsupported. The approved artifact is the official channel manifest. Its checksum params carry all available xz component URL/digest pairs and a checksum-verified, versioned rustup bootstrap. The evidence collector checks rustc, Cargo, host rust-std, Clippy, rustfmt and LLVM tools availability. Cross-target standard libraries and target-independent components such as rust-src remain selectable from the same indexed manifest.

Under toolCatalog.url, pin/install/build acquisition selects an approved, verified indexed release. The manifest download must match the index's SHA-256, and its complete component map must equal the indexed map. Native declarations in rust-toolchain.toml select components/targets from those inputs. Every selected component and the bootstrap must match an indexed URL and digest; the broker then hashes their downloaded bytes before copying them into the temporary mirror. Rustup uses this local mirror, private homes, a minimal profile and disabled self-update. Missing mirror inputs fail; no live publisher fallback can add them. This retains rustup's native installation semantics instead of reimplementing them.

The release catalog entry governs delivery of its manifest and admitted component URLs: direct entries use the fixed publisher hosts, proxy entries use the edge's existing upstream URL route. The edge must serve those approved component URLs. Frozen recipes are checked against current catalog/index metadata before installing or reusing a selection. Installed payloads are trusted and never rehashed on reuse. Offline operations use the existing signed caches and archive/store rules.

Unapproved releases fail with TOOL_NOT_IN_CATALOG; absent tools or records without component metadata fail with TOOL_NOT_IN_INDEX; differing indexed/locked inputs fail with TOOL_CATALOG_MISMATCH. A downloaded input with the wrong digest fails before rustup starts. Older Rust index records need regeneration, without a schema version change. cargo: helpers still refuse under a catalog; their governance is deferred.

Unit tests cover the indexed component map and extra target/component selection. The compiled-CLI installation fixtures require Linux amd64 and check protocol and digest enforcement with a stand-in installer. They do not qualify real rustup, compilation or native platforms. See implementation status for verification results.

Refreshing pinned installation recipes​

After an embedded backend update, oyzu pin --refresh reacquires installation metadata for the already selected versions and configured execution platforms. It preserves version selection; it does not upgrade Rust, install tools, edit oyzu.toml, or reinterpret an old installation receipt as a new backend identity. Use oyzu pin --refresh --dry-run to review the proposed lock without writing it. Refresh requires online metadata acquisition and conflicts with --offline. An incomplete or failed resolution does not publish a replacement lock.

Then run oyzu build. Build looks up the exact refreshed recipe in the shared user store and installs it if missing. Historical installation records embedded in a development lock do not override portable resolution records. Existing installations remain intact; reuse requires the exact current recipe identity. The native build retains the installation's verified lease through task execution instead of hashing the payload again to activate it. No invocation re-hashes an already installed payload: tools are validated when installed and trusted afterwards, and this is not a same-user tamper boundary.

Experimental pin preview​

Mise-enabled builds now expose oyzu pin --dry-run (optionally --offline). The command discovers the full project's quality-stage requirements, expands platform declarations using the build planner, and prints a concise tool summary with unresolved explanations. Use --json for requirement provenance, available compiler metadata, and detailed diagnostics. A matching version-1 selection retains its exact compiler version and is checked against native constraints. New selections accept an exact stable version or the native stable request in configuration or a native toolchain declaration.

Pinning is optional. With no explicit [tools] rust, no rust-toolchain.toml channel and no oyzu.lock, oyzu pin or the first build resolves the requirement stable to the greatest stable release (which must satisfy any Cargo rust-version minimum, otherwise resolution fails) and records it in oyzu.lock. A toolchain-file channel (the nearest rust-toolchain.toml or rust-toolchain upward from the build folder, stopping at the project root) is a complete request; a [tools] rust value must agree with it, as described in native pin files. Offline resolution needs an existing lock, as for any stable request. Verified 2026-10-18 with the compiled CLI: an unpinned tiny Cargo project (rust-version = '1.80', committed Cargo.lock) built natively on Windows, locking Rust 1.99.1 and producing its executable.

The experimental resolver supports exact stable Rust selections, resolution of stable to an exact release, and the Rust adapter's supported helper defaults: cargo-nextest 0.9.146 and cargo-llvm-cov 0.9.1 for Linux amd64 execution. Their versioned archives and checksums are the same inputs already declared by the Rust worker recipe. Other helper versions remain unsupported; these metadata records do not establish installed availability.

A complete preview includes the exact proposed oyzu.lock text in JSON proposed_files and exits 0. Incomplete resolution exits 2 and proposes no files. oyzu pin revalidates discovery/configuration, then publishes a complete version-1 lock through the recoverable transaction. It does not install tools or change native files or TOML, preserving comments and avoiding duplicate declarations. --offline reuses existing matching version-1 compiler metadata and built-in helper metadata, or reports missing inputs without acquisition. The build handoff supports a pinned Rust compiler; native installation of the complete pinned component selection remains unfinished.

Configuration reads, frozen selection and installation lease acquisition reject an unfinished .oyzu-pin-journal.json. Pin recovery checks every destination against its recorded old/new bytes before rolling the entire set forward. Unexpected external changes retain the journal and fail with PIN_EDIT_CONFLICT. This is recoverable publication, not atomic replacement of multiple files. The transaction engine has focused stale-edit/interruption coverage. Pin captures the original lock before metadata acquisition and checks discovery/configuration again before commit.

Single version-1 lock​

The decoded TOML schema defines the sole tool lock contract. resolved_environment and resolution record exact plans before installation; environment and tool retain verified installation graph facts. Optional requirements records hold discovery evidence. All sections are validated by one parser. Missing sections mean no records, never permission to execute an unresolved tool.

Pinning retains installation records and updates resolution records. Installation retains resolution records. Resolution recipes are not receipts. The private materialization graph uses this same contract, with only installation records. No schema-version dispatch, legacy pin mode, or format migration is supported. Native installation of pinned components remains separate functional work.

Version conflicts in ordinary pin output show the two source files and versions, an explanation, and confirmation that no files changed. Generated matrix IDs and content hashes remain in structured evidence rather than the normal message. --json represents a conflict as a schema-versioned object with complete: false and a conflict record, retaining the native field and content digest.

The experimental preview treats native Rust toolchain channels as defaults. An explicit tools.rust (or canonical tools."oyzu:rust") selection overrides that channel. Cargo minimum Rust versions remain mandatory compatibility checks. Structured requirements distinguish native-default from compatibility origins. The accepted pinning direction preserves authored TOML and records exact selections in the lock. Ranges and other rolling or dated channels are not yet supported by this experimental resolver.

Experimental resolution materialization​

The mise-enabled build handoff can now read an exact Rust compiler from a version-1 lock and provision its declared components. It checks explicit versions, native defaults and Cargo compatibility using the same compatibility function as pin. The local Linux worker must be rebuilt with this protocol; the controller requires confirmation of the requested component set.

Generated archives are hashed after installation. A private materialization graph under .oyzu/tools/resolutions/<resolution-digest>/oyzu.lock binds the resolution ID to those actual archive bytes. This graph uses the existing version-1 receipt and lease verifier; it is not a conversion of the public resolution lock into an installation receipt. Publication follows successful Linux restoration and lease validation. Subsequent captures verify the cached archive through that same path.

The two-platform dependency-free fixture has passed a real build from an empty project tool store after pinning, followed by bundle inspection and ELF architecture checks (amd64 and arm64). A subsequent build and inspection also passed using the cached compiler without invoking rustup. Automatic first-build resolution and explicit offline build behavior are described below. Native helper installation is described below; isolated helper materialization is not qualified by that flow. Do not interpret a successful pin as installed-tool evidence.

Automatic first build resolution​

For a mise-enabled build with no oyzu.lock, preflight now sends the selected captured targets to the same tool planner used by pin. It publishes a complete resolution lock before capturing source, then uses the materialization path above. Authored TOML stays unchanged. Local fast builds select only their required stages; pin still selects all configured applicable gates. Existing locks retain their selections rather than being silently migrated or replaced.

This path supports exact Rust versions from configuration or native declarations. Without either, the Rust adapter supplies its supported default, Rust 1.99.1; discovery exposes that default and pin records the exact recipe in the lock. It does not select a compiler from PATH or copy the default into TOML. Native declarations take precedence over this fallback, and explicit TOML selections take precedence over native defaults. A missing-lock affected build is rejected until a full selection establishes the environment. The first run published the lock and installed the selected compiler, but exposed an unconditional coverage probe in Cargo preparation. Preparation now probes nextest and coverage only when the test stage is enabled by the captured configuration. The corrected fast build passed in 289.7 seconds using the cached compiler; bundle inspection and ELF checks confirmed amd64 (machine 62) and arm64 (machine 183). No nextest or coverage probe ran. A dry run on the repository's dependency-free Rust example also resolved the supported default successfully and proposed only oyzu.lock. The frozen compiler acquisition proof is recorded below.

Offline Rust builds​

oyzu build --offline requires an existing tool lock and a cached compiler archive. It does not resolve new versions or publish lock changes. The compiler still passes normal archive, receipt and lease verification before execution; an absent installation or archive fails without starting an installer.

This first offline path supports standalone Rust projects with dependency-free Cargo locks (including local workspace packages). Registry and Git package replay is not connected and fails before fetching those inputs. Other builders and managed configuration acquisition reject explicit offline mode. Worker images must already be provisioned, as for online builds. These limitations are explicit errors rather than permission to fall back to online acquisition. The missing installation CLI check passed: exit 1, unchanged lock, and no tool store created. Cached build replay passed in 270.25 seconds, with both ELF architectures verified, successful bundle inspection, an unchanged lock and no installer invocation. The latest CLI also passed pin --dry-run --offline against an existing full resolution lock without edits.

The repository example (examples/builds/rust-app/project, with a two-platform build declaration) passed plain oyzu build from an empty project tool store and without oyzu.lock, oyzu.toml or a native toolchain declaration. The run selected the adapter default, installed it through embedded mise and produced Linux amd64 and arm64 binaries. Bundle inspection and ELF machine checks passed. The measured run took 648.15 seconds on the available Windows/Docker host; this is functional evidence, not a performance claim. The successful offline replay used this exact example and retained its original Cargo manifests and source bytes.

Frozen Rust distribution integration​

The current controller stages every locked Rust acquisition input through its broker and checks its SHA-256 digest before launching installation. A private read-only distribution directory is passed to the embedded mise Rust installer through install_rust_from_directory; the Linux installer worker runs with --network=none. Bootstrap HTTP is answered from the same verified inputs. Unlisted requests fail rather than falling back to public acquisition. The existing store still records and verifies the actual generated compiler archive.

This uses mise revision 0105e9222972c0e5c6bd89f24aff1550f460de16, which changes the admitted backend identity. Prior backend locks are not silently rewritten or reused. Both controller and worker compiled successfully. A fresh copy of the dependency-free repository Rust example, with no lock or tool store, passed plain oyzu build in 522.51 seconds. Bundle inspection passed and ELF headers confirmed Linux amd64 and arm64 outputs. Source files remained byte-identical. Installer network mode none and the read-only input mount were captured during the run.

The first isolated run installed the compiler but failed when rustup attempted an unpinned self-update. The frozen-directory method now disables that update; the bootstrap version remains fixed by the recipe. The corrected run passed; the original failure remains recorded in implementation status. The subsequent oyzu build --offline passed in 254.27 seconds, with successful bundle inspection, both ELF architectures, an unchanged lock and no installer invocation. The final binary also passed pin preview/publication/idempotence and missing-offline-input checks. This completes the bounded dependency-free Rust workflow, not all builder or helper-tool installation coverage.

Portable Rust metadata coverage​

Pin now publishes platform-specific Rust and helper records as described in the lock reference. Earlier Linux-only pin descriptions above are superseded for metadata resolution. Native installation and worker paths retain their existing qualification limits; this change does not complete portable installation or backend compatibility work.

Discovered native helper installation​

With a portable oyzu.lock, native preparation combines builder requirements with the effective configuration instead of installing only literal [tools] entries. You do not need to repeat inferred helpers in TOML. Use oyzu pin, then oyzu install to prepare the containing target's full enabled tool selection, or oyzu build --full to install and execute the selected quality stages. Ordinary oyzu build prepares compile requirements only unless configuration requires additional checks. oyzu run test consumes the same pinned test selection but requires it to be installed first.

The admitted release archives are cargo:cargo-nextest 0.9.146 and cargo:cargo-llvm-cov 0.9.1. Their short names are also accepted in [tools]. Explicit configuration overrides builder defaults and still must satisfy native compatibility constraints and policy. Other helper versions/backends fail with a named unsupported or stale-pin error; there is no implicit cargo install, source build, or separate mise executable. Archives use the existing broker, published checksum verification, bounded extraction and installation lease contracts. Configured tool routes do not fall back to public downloads on failure.

The shared user store contains the installations; project locks remain portable version-1 resolution records. Reusing a compatible installation does not copy it into the project. Windows GNU/LLVM Rust and native MSVC helper executables retain their separate artifact platforms. This does not install MSVC or a Windows SDK. The selected Rust sysroot also binds rustup's RUSTUP_TOOLCHAIN so Cargo subcommand proxies in a user Cargo home cannot select a different global Clippy or rustfmt.

tools current, which, exec and shell activation recognize the inferred selection for the nearest containing target. Descendant targets do not change a parent shell's tool versions; native builds prepare each target against its own configuration. Existing explicitly provisioned flows without portable pins remain available. Missing pins require oyzu pin; build never silently repins them. Missing installations require online preparation; --offline reuses verified installed payloads and cached archives and cannot acquire missing inputs.

Windows native coverage is the first runtime qualification; Linux/macOS and isolated helper installation are separate qualification work. See implementation status for commands and results.
