Discovery decisions and build.yaml selectors

CLI reference

Published from the canonical docs/reference/discovery-selection.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Discovery works out each Node or Python target's tools, such as its package manager or formatter, from your project files. When the files settle the question, you need no Oyzu configuration. When they don't, discovery stops and tells you which line to add to build.yaml. This page also covers how build.yaml and discovery decide which builds exist, and how Rust toolchain files are read.

Discovery only reads files. It never runs a tool, script or configuration file, and it never picks a winner silently. oyzu build --plan shows every decision with its reason.

Quick start​

If discovery reports a conflict, add the selector the error names under with and run again:

builds:
  pytest:
    uses: python/package
    with:
      formatter: ruff
conflicting Python formatter candidates black, ruff: black via pyproject.toml tool.black; ruff via pyproject.toml tool.ruff; declare the intended one for this target in build.yaml with `with: {formatter: black}` or `with: {formatter: ruff}`

Then check the result with oyzu build --plan; see decisions in the build preview.

How a role is decided​

A role is one tool choice a target needs, such as its package manager, test framework, linter or formatter. Each candidate comes with evidence of a certain strength, and the strongest wins:

StrengthExamples
declaredA test script that runs exactly one recognized test runner.
nativeA lockfile, package.json packageManager, a framework configuration file, a pyproject.toml tool table.
conventionalA declared dependency, a settings-only pnpm-workspace.yaml, a uv.lock that locks no packages.
defaultThe default when nothing else applies: npm, ESLint, Prettier, pip or Ruff.

Two different candidates tied at the strongest level are a conflict. A candidate Oyzu has no support for, such as packageManager: nub@0.8.3, is unsupported. Both stop discovery; file order never decides.

Native rules that settle a role without configuration​

  • A lockfile beats a settings-only pnpm-workspace.yaml. pnpm can write this file just to store settings; only its packages list declares a workspace. Without packages, the file is conventional evidence, so package-lock.json (npm) wins. With no lockfile it still picks pnpm over the npm default. A file with packages, or one that isn't a YAML mapping, is native evidence and conflicts with another manager's lockfile.
  • The runner a compound test script names. If the test script isn't exactly a recognized command (jest, vitest run, mocha, …), but its &&, ||, ; and | parts name exactly one of jest, vitest, mocha or node --test, that runner wins.
    • Parts such as pnpm lint, npm run unit or yarn unit are followed into the referenced script.
    • Leading NAME=value assignments, cross-env, npx and <manager> exec are skipped.
    • A script with quotes, $, backticks, parentheses, redirection or flags such as --filter isn't read; other evidence decides.
    • The script still runs as written. Oyzu adds test reporting only to an exact recognized command.
  • A uv.lock that locks no packages. uv records the project itself in uv.lock, so a lock with no [[package]] entries is conventional evidence and yields to poetry.lock or [tool.poetry]. A uv.lock that locks packages is native evidence.

Which projects discovery finds​

  • With a build.yaml, its builds are the full list. Discovery only fills in an omitted uses and reports folders the file leaves out (see builds build.yaml leaves out).
  • Without a build.yaml, discovery uses a project at the root, or searches below the root for projects.
  • The search stops going deeper once it finds a project; that project's builder handles everything inside it. Nested Git repositories and folders with their own build.yaml also stop the search.
  • A build.yaml that belongs to another tool (its root has none of builds, members and exclude, such as Dart build_runner's file) doesn't stop the search. oyzu discover lists it under Skipped with its root keys (which build.yaml files are Oyzu's). If such a file is at the root, discovery works as if there were no build.yaml.
  • The search skips generated and dependency folders, goes at most 32 levels deep and finds at most 1,024 targets.

The configuration boundary​

Discovery stays inside the configuration boundary of the command.

  • An empty or broken .git marker in a parent folder doesn't make that folder the workspace. For sibling projects with no shared Oyzu configuration, oyzu -C first run list lists only first's tasks.
  • In a real Git workspace, discovery includes all its projects, and an unqualified task that several targets have is ambiguous. Use the qualified task name from the error, or --root first to choose a narrower root.
  • Linked worktrees and .git pointer files follow the same rules.

Selecting a role in build.yaml​

When discovery stops, declare the target and add the selector the error names under with (see the quick start). If the files match more than one builder, choose uses first. For example, a root with both package.json and Dockerfile needs builds: {app: {uses: node/app}} before the Node test runner can be decided.

Builderwith keyValues
node/app, node/packagepackage-managernpm, pnpm, yarn
test-frameworknode-test, jest, vitest, mocha, custom
lintereslint, biome
formatterprettier, biome
python/app, python/package, python/librarypackage-managerpip, uv, poetry
linterruff, flake8
formatterruff, black
java/appbuild-toolmaven, gradle, ant
  • The keys match the role names shown by --plan.
  • Your selection always wins. Discovery still records what it saw.
  • Any other value, a non-string value or any other with key fails.
  • A selection applies only to the target's own folder. It doesn't change packages inside a Node workspace.
  • Tool versions don't go here; set them in oyzu.toml.

Another example error:

conflicting Node package manager candidates nub, pnpm (nub unsupported): nub via package.json /packageManager; pnpm via pnpm-lock.yaml lockfile; declare the intended one for this target in build.yaml with `with: {package-manager: pnpm}`

The suggestions list the supported candidates that were seen, or every supported value if none was. Choosing a tool your project doesn't actually use can still fail later, when that tool runs.

Decisions in the build preview​

oyzu build --plan shows a Discovered table per target with each role, the chosen tool and the reason. With --json, each target has a discovery object mapping the role to selected and reason:

package-manager  npm  native package-lock.json lockfile; outranks pnpm (conventional pnpm-workspace.yaml settings without packages)
formatter        ruff build.yaml with.formatter; discovery also observed black

A reason names the winner's evidence and every candidate it beat (other than defaults). A real build keeps all observations and any selector in the plan's oyzu.dev/discovery extension.

Rust toolchain files​

The Rust builder reads rust-toolchain.toml and rust-toolchain in every form rustup accepts. Like rustup, it uses the nearest one, searching upward from the build folder and stopping at the project root.

FormMeaning
Legacy rust-toolchain holding only a name, such as stable, 1.95.0 or nightly-2020-07-10The toolchain name.
[toolchain] table, in either filechannel (stable, beta, nightly, <major.minor>, <major.minor.patch>, optionally dated or with a host triple), components, targets and profile.
A table without channelOyzu uses its own default ([tools] rust in oyzu.toml, else Oyzu's default Rust) and keeps the declared components, targets and profile.
path, a local toolchain folderNot supported. oyzu pin, oyzu build and build --plan fail with TOOL_NATIVE_PIN_INVALID; set toolchain.channel to a release instead. A [tools] rust value doesn't override it.

Which channels become a pin​

A channel acts as a native pin only when [tools] rust would accept it: stable or an exact stable release such as 1.99.1. Any other channel (nightly, beta, 1.99, a dated or host-qualified name) makes builds, build --plan and oyzu pin fail with TOOL_NATIVE_PIN_INVALID and a fix. oyzu discover still lists it.

Invalid files​

  • An empty [toolchain] table, channel together with path, or an empty channel or one containing whitespace fails.
  • Having both files fails with both rust-toolchain.toml and rust-toolchain exist, even though rustup itself would prefer rust-toolchain.

Builds build.yaml leaves out​

With a build.yaml, only its builds exist; discovery never adds one. It does two things instead: it fills in an omitted uses, and it reports folders the file doesn't mention.

Discovery supplies uses​

A build may leave out uses. When exactly one builder recognizes the build's folder, discovery uses it. oyzu discover shows the build as build.yaml; builder detected from project files (builder_selection: inferred in --json). Builds that name uses show as explicit.

builds:
  web: {path: web}            # discovery supplies uses: node/app
  cli:
    uses: rust/app            # written out: reviewers see exactly what was chosen
    platforms: [linux/x86_64, linux/arm64]
exclude: [tools/scratch, tooling/**]

If no builder or several builders recognize the folder, discovery, planning and builds fail with CONFIG_INVALID_VALUE, naming the candidates and the line to write:

build both: both is recognized by docker/image and node/app, so discovery cannot choose;
write the one you want in build.yaml, for example both: {uses: docker/image, path: both}

Discovery reports undeclared folders​

A folder that a builder recognizes but no entry covers is listed, never built.

CommandWhat it does
oyzu discoverLists each such folder, the builders that recognize it, and the line to add (web: {path: web} when one builder matches). A folder several builders match gets an example: line with a placeholder, such as both: {uses: <docker/image or node/app>, path: both}.
oyzu build --planNames up to five under Not in build.yaml, then a count of the rest. A real build doesn't look for them or fail because of them.
oyzu discover --checkWrites nothing. Exits 1 with error[INVENTORY_UNDECLARED] and a table of folders while any folder is neither declared nor excluded; otherwise exits 0 with Build inventory is current. Without a build.yaml, every discovered build counts as undeclared. Add it to CI to catch new folders that would silently not build.
oyzu discover --writeDeclares every undeclared folder that exactly one builder recognizes.

--check and --write can't be combined.

--write details:

  • Each folder is added as one line with uses written out (web: {uses: node/app, path: web}), at the end of the builds: block. Comments, order and your own entries stay as they were.
  • It creates build.yaml if there is none. It refuses a file whose builds: isn't a block mapping at the start of a line, a symlinked file, a file changed meanwhile, or another tool's build.yaml.
  • A folder several builders match isn't written. It's listed under Needs a choice and the command exits 1 (outcome incomplete). If nothing else was written, the first line says A choice is needed: …; nothing was written.
  • When it writes, it adds # yaml-language-server: $schema=https://github.com/oyzuai/oyzu-releases/releases/latest/download/build.yaml.schema.json as the first line unless a schema comment is already there, so editors can validate the file (editor schemas).

With --json, oyzu discover adds an inventory object with tracked, undeclared and excluded lists (or inventory.error, which never fails discovery). Plan JSON has undeclared: {total, folders, tracked}.

Inventory JSON​

--write and --check print a build-inventory record with --json:

FieldMeaning
modeThe command mode.
outcomecurrent, undeclared, written or incomplete.
path, trackedThe build.yaml path and how files were counted.
undeclared / added / needsChoice, excludedFolder lists. Each folder has path, builders, name, entry and, when excluded, glob.
workspaceMembersFolders covered as workspace members, each with path, builders and the owning build.
warningsWorkspace manifests that couldn't be read, and one summary of unreadable folders encountered by the inventory walk.
skippedBuildFilesOther tools' build.yaml files, each with its path and root keys. Plain oyzu discover --json lists them as skipped_build_files.

Workspace members​

A folder listed as a member by the workspace manifest in a declared build's folder belongs to that build. It's never reported as undeclared, and --write never declares it.

BuilderManifest in the build's folderMembers
rust/*Cargo.toml [workspace]members paths and globs (*, ?, […]), minus each exclude path and its subtree. A member listed by literal path stays a member even below an excluded path, as in Cargo.
go/*go.workEach use folder (one module each, not its subfolders).
node/*package.json workspaces (npm, Yarn; an array or {packages: [...]}) and pnpm-workspace.yaml packagesThe folder globs, minus those starting with !.
  • A crate under crates/ that members doesn't list isn't a member (Cargo wouldn't build it), so it's still reported.
  • Only the build's own builder counts: a docker/image build at the root doesn't own a Cargo workspace there. A build without uses asks every builder that recognizes its folder.
  • A member covers only its own folder; the search continues below it.
  • A manifest that can't be read owns nothing and never fails the check, plan or build. Its members stay reported, with a warning such as warning: build web: cannot read the workspace manifest package.json: …. Fix the file and run the check again.
  • Human output counts members: Build inventory is current · 2 builds declared, 10 workspace members.

How the inventory walk works​

  • The walk starts at the build root and skips dependency and output folders, nested Git repositories and folders with their own build.yaml. It stops below a folder a builder recognizes.
  • A declared folder owns everything below it, whether or not a builder recognizes it.
  • The root never owns the whole tree while a build.yaml exists. A build declared at the root (path omitted or .) covers the root folder only; its workspace members are covered, and any other project below is listed until declared or excluded.
  • Without a build.yaml, a recognized root is the only build, so --write declares just that.
  • The walk continues below an excluded folder.

Unreadable folders and missing projects​

Zero-config discovery and the inventory walk skip folders they cannot read because access is denied or the folder disappeared. One Could not read folders: summary names up to five root-relative paths with their OS reasons, followed by and N more when needed. With a discovered project, the build reports this summary in its existing Warnings section; JSON diagnostics carry it on stderr.

Before build discovery, oyzu build checks the same project boundary as oyzu run: Oyzu configuration, an Oyzu build inventory, a Git boundary or a recognized native manifest. If the root is not a project, the same bounded lookup used by oyzu run searches within three directory levels without opening child configuration; unreadable folders are skipped. Static markers are checked first. If none are found, eligible detections from the configured plugin catalog also count as project markers, at the root or within that same bounded lookup. This uses normal catalog verification and refresh rules; --plan and --offline use cached metadata. Configuration and catalog metadata may be loaded or refreshed before refusing. When either check finds a project, build discovery proceeds normally, supporting a zero-config workspace over child projects. A root build.yaml always passes the boundary check.

If neither the root nor the nearby lookup finds a project, build refuses with PROJECT_NOT_FOUND (exit 5), before deeper build discovery, preparing a workspace or printing Building … or Prepare output. This applies with a target, --plan, --full and --json. Next: suggests oyzu -C <project> build. oyzu run keeps its navigation behavior: outside a project it refuses and lists nearby projects instead of running their tasks.

Inside a recognized project, the discovery summaries described above still apply. If discovery finds no readable native project or declared build target, its PROJECT_NOT_FOUND error retains any unreadable-folder summary in human and JSON output. Select the intended project, or restore folder access and retry.

This does not change which folders count as projects. Errors reading required files still fail, and skipping a folder during discovery does not exempt it from source capture or build input validation when a build needs that path.

Build names​

  • Without a build.yaml, --write keeps the existing zero-config names (project at the root, project-<path> below it, such as project-web), so dist/ paths and cache identity don't change.
  • With a build.yaml, a new folder is named after the folder, then its path joined with -, then a numbered variant if needed.

exclude:​

exclude: lists folder globs relative to the build root. It silences the listing and the check; it never changes which builds exist.

  • Use / on every platform. Matching is case-sensitive, as in Git.
  • * stays within one folder, tooling/** covers everything below tooling, and . is the build root.
  • Absolute paths, .., backslashes and drive letters are refused.
  • The key is exclude, not ignore, so it isn't confused with tools.ignore.

Git​

Inside a Git work tree only tracked files count, so a file a CI job creates can't fail the check. A folder is considered when Git tracks a file directly in it (read with git ls-files, no network, no index writes). Outside Git, or without git, every file counts and the output says so (tracked: all-files).

Limits​

  • Selections are read once from build.yaml. When npm workspace tests and checks run on the host, each package (including the root) is detected again without them, so a root that needed a selection fails there.
  • Node output profiles and the Python test framework have no selector.
  • Undeclared-folder detection works per folder: an untracked manifest next to tracked files still counts.
  • The catalog detection budget applies to the whole walk. Going over it fails --check and --write (with a fix) and is reported, not fatal, in the plan.
  • Workspace members come from the manifests listed above only. Cargo path dependencies that are automatically members, Maven modules, Gradle include, .NET solutions and uv workspaces aren't read, so those folders are reported until you declare or exclude them.
  • npm doesn't document ! in workspaces; Oyzu reads a leading ! as pnpm does.
  • Discovery is tested on Windows. The walk uses no platform-specific paths.
