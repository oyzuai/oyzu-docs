Discovery decisions and build.yaml selectors

CLI reference

Published from the canonical docs/reference/discovery-selection.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Experimental. Static discovery decides each exclusive role of a Node or Python target, such as its package manager or formatter, from native project files. It reads bounded metadata, never runs a tool, script or configuration file, and never breaks a tie silently. When native evidence settles a role, no Oyzu configuration is needed. When it does not, discovery fails and names both the conflicting inputs and the build.yaml declaration that settles the role. oyzu build --plan shows every decision with its reason.

How a role is decided​

With a build.yaml, its builds are the inventory and discovery only supplies an omitted uses and reports folders the file leaves out (builds build.yaml leaves out). Without build.yaml, discovery selects a native project at the root or searches below that root for targets. The inventory walk stops descending as soon as it finds a target; the selected native builder owns discovery within that target. Nested Git repositories and directories with their own build.yaml inventory also stop the walk. A build.yaml that belongs to another tool (its root has none of builds, members and exclude, such as Dart build_runner's targets: file) does not: the walk continues below it, and oyzu discover lists it under Skipped with its root keys (which build.yaml files are Oyzu's). With such a file at the root, discovery runs as if there were no build.yaml. Existing generated/dependency directory exclusions, the depth limit of 32 and the limit of 1,024 targets still apply. Ordinary files below an already selected target do not add inventory traversal work. These rules apply equally to human and JSON discovery output.

The invocation's configuration boundary also bounds conventional target discovery. An empty or malformed ancestor .git marker does not select that ancestor as a workspace: for standalone sibling projects with no enclosing Oyzu configuration, oyzu -C first run list discovers only first's tasks. In a real Git workspace, discovery still includes its conventional targets, and an unqualified task exposed by several targets remains ambiguous. Use the target-qualified task named by the error, or --root first when deliberately selecting a narrower root. Gitdir-pointer repositories and linked worktrees follow the same boundary rules.

Each detector reports a candidate with evidence of one strength. The strongest evidence wins:

StrengthExamples
declareda test script that runs exactly one recognized test runner
nativea lockfile, package.json packageManager, a framework configuration file, a pyproject.toml tool table
conventionala declared dependency, a settings-only pnpm-workspace.yaml, a uv.lock that locks no packages
defaultthe documented default when nothing else applies, such as npm, ESLint, Prettier, pip or Ruff

Two different candidates with the strongest evidence are a conflict. A candidate the builder has no adapter for, such as packageManager: nub@0.8.3, is unsupported. Both fail discovery; neither registration order nor file order picks a winner.

Native rules that settle a role without configuration:

  • Lockfiles beat a settings-only pnpm-workspace.yaml. pnpm reads settings from pnpm-workspace.yaml and can write the file on its own; only its packages list declares a workspace (the pnpm adapter already treats a settings-only file as no workspace). A file without packages is conventional pnpm evidence, so package-lock.json (npm) outranks it, while with no lockfile it still selects pnpm over the npm default. A file with packages, or one that is not a YAML mapping, stays native and conflicts with another manager's lockfile.
  • The runner a compound test script names. When the test script is not exactly a recognized command (jest, vitest run, mocha, ...) but its &&, ||, ; and | segments name exactly one of jest, vitest, mocha or node --test, that runner is declared evidence. Segments such as pnpm lint, npm run unit or yarn unit are followed into the referenced package script. Leading NAME=value assignments, cross-env, npx and <manager> exec are skipped. A script with quotes, $, backticks, parentheses, redirection or manager flags such as --filter is not read; its framework is then decided by the remaining evidence. The script itself still runs natively, without report instrumentation unless it is an exact recognized command.
  • A uv.lock that locks no packages. uv records the project itself in uv.lock, so a lock without any [[package]] cannot belong to this project's manager. It is conventional evidence and yields to poetry.lock or [tool.poetry]. A uv.lock that does lock packages stays native.

Selecting a role in build.yaml​

When discovery fails, declare the target and add the selector the error names under with:

builds:
  pytest:
    uses: python/package
    with:
      formatter: ruff

If native files identify more than one builder, select uses first. For example, the pinned Mermaid root contains both package.json and Dockerfile; its build.yaml needs builds: {mermaid: {uses: node/app}} before the Node test-runner decision can be made. That choice does not require a with.test-framework selector: pnpm lint && vitest run selects Vitest from the native test script.

Builderwith keyValues
node/app, node/packagepackage-managernpm, pnpm, yarn
test-frameworknode-test, jest, vitest, mocha, custom
lintereslint, biome
formatterprettier, biome
python/app, python/package, python/librarypackage-managerpip, uv, poetry
linterruff, flake8
formatterruff, black

The keys match the role names in --plan and in the target's oyzu.dev/discovery plan extension. A selection wins over every observation; discovery still records the observations, and the selected value must be one of the listed values. Any other value, a non-string value or any other with key fails. A selection applies to the declared target's own root only; it does not change the decisions of packages inside a Node workspace. Tool versions are not selected here: they belong in oyzu.toml.

Example errors:

conflicting Python formatter candidates black, ruff: black via pyproject.toml tool.black; ruff via pyproject.toml tool.ruff; declare the intended one for this target in build.yaml with `with: {formatter: black}` or `with: {formatter: ruff}`
conflicting Node package manager candidates nub, pnpm (nub unsupported): nub via package.json /packageManager; pnpm via pnpm-lock.yaml lockfile; declare the intended one for this target in build.yaml with `with: {package-manager: pnpm}`

The suggestions list the supported candidates that were observed; when none was, they list every supported value. Selecting a manager or runner the project does not natively use can still fail later, in that tool's own preparation or test run.

Decisions in the build preview​

oyzu build --plan shows a Discovered table per target with each role, the selected candidate and the reason. With --json, each entry of targets has a discovery object mapping the role to selected and reason. For example:

package-manager  npm  native package-lock.json lockfile; outranks pnpm (conventional pnpm-workspace.yaml settings without packages)
formatter        ruff build.yaml with.formatter; discovery also observed black

A reason names the strength and evidence of the winner and every candidate it outranked with non-default evidence. Executed builds keep the complete observations, detector registry and any selector in the plan's oyzu.dev/discovery extension.

Rust toolchain files​

The Rust builder reads rust-toolchain.toml and rust-toolchain in every form rustup accepts:

  • the legacy rust-toolchain file holding only a toolchain name, such as nightly-2020-07-10, stable or 1.95.0;
  • the TOML [toolchain] table, in either file, with channel (stable, beta, nightly, <major.minor>, <major.minor.patch>, optionally dated or with a host triple), components, targets and profile;
  • a table without channel, which rustup resolves to the default toolchain: Oyzu then uses its own default (the [tools] rust selection in oyzu.toml, otherwise the adapter baseline) and keeps the declared components, targets and profile;
  • path, a local toolchain directory. Oyzu cannot provision it, so oyzu pin and build tool resolution fail with toolchain.path names the local toolchain ...; select a Rust release in oyzu.toml with [tools] rust = "<version>". An explicit [tools] rust overrides it.

An empty [toolchain] table, channel together with path, or an empty or whitespace-containing channel fails. Both files together still fail with both rust-toolchain.toml and rust-toolchain exist, although rustup itself prefers rust-toolchain. Reading a channel is not resolving it: the Rust tool backend currently resolves exact three-part stable versions, and other channels report that backend version selection is needed.

Builds build.yaml leaves out​

With a build.yaml, only its builds exist: discovery never adds one (OEP-0022 OD13). It does two things for the inventory instead.

It supplies uses. A named build may omit uses. When exactly one builder, built in or from a catalog detection, recognizes the build's folder, discovery uses it, freezes it into the inventory before planning, and oyzu discover shows the build as chosen by build.yaml; builder detected from project files (builder_selection: inferred in --json). Builds that name uses stay explicit.

builds:
  web: {path: web}            # discovery supplies uses: node/app
  cli:
    uses: rust/app            # written out: review sees exactly what was chosen
    platforms: [linux/x86_64, linux/arm64]
exclude: [tools/scratch, tooling/**]

A folder no builder recognizes, or several do, fails discovery, planning and builds with CONFIG_INVALID_VALUE naming the candidates and the entry to write:

build both: both is recognized by docker/image and node/app, so discovery cannot choose;
write the one you want in build.yaml, for example both: {uses: docker/image, path: both}

It reports undeclared folders. A folder where a builder recognizes a project that no entry covers is listed, never built:

  • oyzu discover lists every such folder with the builders that recognize it and the shortest line to add (web: {path: web} with one builder). A folder several builders recognize gets an example marked example: with a placeholder to replace, both: {uses: <docker/image or node/app>, path: both}, never one candidate presented as the choice. --json adds an inventory object with tracked, undeclared and excluded lists; a failure to list them is reported there as inventory.error and never fails discovery.
  • oyzu build --plan names at most five of them under Not in build.yaml, then the count of the rest and oyzu discover for the full list. Plan JSON has undeclared: {total, folders, tracked} (or {error}). Only the plan lists them: a real build, including its --no-docker and sandbox guards, neither walks the tree for them nor fails because of them.
  • oyzu discover --check writes nothing and exits 1 while a folder holds a build that build.yaml neither declares nor excludes, printing error[INVENTORY_UNDECLARED], a table of folders and the fix. Without a build.yaml, every discovered build is undeclared. It exits 0 with Build inventory is current otherwise. Add it to CI to catch a new folder that would silently not build.
  • oyzu discover --write declares every undeclared folder one builder recognizes, each as one line with uses written out (web: {uses: node/app, path: web}), appended to the builds: block so comments, order and hand-written entries (including ones without uses) stay as they were. It creates build.yaml when there is none, and refuses one whose builds: is not a block mapping at the start of a line. A folder several builders recognize is not written: it is listed under Needs a choice and the command exits 1 (outcome incomplete); when nothing else was written, the first line says A choice is needed: …; nothing was written. The result is parsed as an inventory before it replaces the file; a symlinked build.yaml or one changed meanwhile is refused, and so is another tool's build.yaml at the root, which is left unchanged. When it writes, it also adds the first line # yaml-language-server: $schema=https://github.com/oyzuai/oyzu/releases/latest/download/build.yaml.schema.json unless the file already has a yaml-language-server: $schema= comment, so editors validate and complete the file (editor schemas); a byte order mark stays first.

--write and --check print the build-inventory record with --json (mode, outcome = current, undeclared, written or incomplete, path, tracked, undeclared/added/needsChoice and excluded; each folder has path, builders, name, entry and, when excluded, glob). --check and the inventory object of oyzu discover --json also list workspaceMembers, the folders covered as workspace members, each with path, builders and the owning build (named apart from the planned build.yaml root key members). --check, --write and, when there are any, the inventory object list warnings for workspace manifests that cannot be read. --check and --write list skippedBuildFiles, the inventory object lists it when there are any, and plain oyzu discover --json without an inventory lists skipped_build_files: other tools' build.yaml files the walk passed over, each with its root-relative path and its root keys. The two options cannot be combined.

Workspace members. A folder that the native workspace manifest in a declared build's folder lists as a member is covered by that build: it is never reported undeclared and --write never declares it. Ownership comes from the manifest, not from where the folder sits:

BuilderManifest in the build's folderMembers
rust/*Cargo.toml [workspace]members paths and globs (*, ?, […]), minus each exclude path and its subtree; a member listed as a literal path stays a member even below an excluded path, as in Cargo
go/*go.workeach use folder, one module each; a use never covers modules in its subfolders
node/*package.json workspaces (npm, Yarn; an array or {packages: [...]}) and pnpm-workspace.yaml packagesthe folder globs, minus those written with a leading !

A crate below crates/ that members does not list is not a member (Cargo would not build it as part of the workspace), so it is still reported. The build's own builder answers: a docker/image build at the root does not own a Cargo workspace there. A build that omits uses asks every built-in builder recognizing its folder. A member covers only its own folder, so the walk continues below it, and a declared folder, a separate repository or a nested build.yaml keeps its own rules. A manifest that exists but cannot be read or parsed owns nothing and never fails the check, the plan or a build: its members stay reported as undeclared, and oyzu discover, --check and --write print warning: build web: cannot read the workspace manifest package.json: … (fix the file, then run the check again). Human output counts the members (Build inventory is current · 2 builds declared, 10 workspace members, or Covered as workspace members: cli 10 folders. below the table of undeclared folders).

The walk follows zero-config discovery: it starts at the build root, skips the dependency and output folders listed above, nested Git repositories and folders with their own build.yaml inventory (another tool's build.yaml is listed as skipped and the walk continues), and stops below a folder a builder recognizes, which owns its subtree. A declared folder below the root owns its subtree too, whether or not a builder recognizes it (a development plugin may build it) and whether or not Git tracks a file directly in it. The build root never owns the tree while a build.yaml exists: a build declared at the root (path omitted or .) covers the root only, and every folder below it is still checked; the members its workspace manifest lists are covered (above), and any other project below it is listed until it is declared or excluded. Without a build.yaml a recognized root is the only build zero-config discovery has, so --write declares just that. An excluded folder is deliberately not a build, so the walk continues below it.

Names: without a build.yaml the folders already are builds, so --write keeps their zero-config names (project at the root, project-<path> below it, for example project-web); writing the inventory never renames a build, its dist/ paths or its cache identity. With a build.yaml, an undeclared folder is not a build yet and is named after the folder, then its path joined with -, then a numbered variant.

exclude: holds folder globs relative to the build root, written with / on every platform and matched case-sensitively as Git matches paths: * stays within one folder, tooling/** covers the whole subtree below tooling, and . is the build root itself. Absolute paths, .., backslashes and drive letters are refused. The key is exclude, not ignore, so it is not confused with tools.ignore. It only silences the listing and the check; it never changes which builds exist.

Git. Inside a Git work tree only tracked files count, so a file a CI job creates cannot fail the check: a folder is considered when Git tracks a file directly in it (read from the index with git ls-files, no network and no index writes). Outside Git, or without a git executable, every file counts and the output says so (tracked: all-files).

Limits and verification​

Selections are read once, at discovery, from the frozen build.yaml inventory. Captured workspace planning reuses the target's decisions for its root. The host development composition of npm workspace tests and quality checks re-detects each package, including the root, without them, so a root that needed a selection fails there. Node output profiles and the Python test framework have no selector.

The six discovery stops in the feasibility corpus are covered by fixtures in tests/integration/discovery.rs; the shared resolver by discovery::detectors unit tests; Rust toolchain forms by builders::rust::requirement_evidence unit tests. The pinned-corpus qualification records a compiled-CLI Windows plan against all six real source commits, including required selector reruns and its limits. It does not qualify builds or other host platforms.

Undeclared-folder detection approximates "tracked" by folder: an untracked manifest beside tracked files still counts. The Plan and oyzu discover open a second configuration session to list folders, and the catalog detection budget of zero-config discovery applies to the whole walk; exceeding it fails --check and --write (with a remedy) and is reported, not fatal, in the plan. Workspace members are read from the manifests alone: Cargo's automatic membership of path dependencies inside the workspace folder, Maven modules, Gradle include, .NET solutions and uv workspaces are not read yet, so such members are still reported until declared or excluded. npm documents globs in workspaces but not !; Oyzu reads a leading ! there as pnpm defines it. One-line entries, the inventory commands and the Plan listing are covered by the compiled-CLI tests in tests/integration/build_inventory.rs (human, NO_COLOR and --json output, exit codes, Git tracking, --write text preservation, a Cargo workspace's members), the walk, naming and the Cargo, Go, npm and pnpm member rules by discovery::coverage unit tests, each manifest reader by its builder's workspace unit tests, the text edit by config::build_write unit tests and the root keys by config::build_model unit tests. Verified on Windows; the walk uses no platform-specific paths.
