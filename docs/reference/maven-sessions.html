Managed Maven launch sessions (prototype)

CLI reference

Published from the canonical docs/reference/maven-sessions.md file. Features marked experimental remain experimental; check support limitations before relying on them.

This client prototype prepares an admitted Maven invocation through oyzu exec and bare mvn in an Oyzu-activated Bash shell. The same endpoint selects the approved source for captured oyzu build dependency acquisition. It requires a separately provisioned local agent; the qualification uses a disposable simulator, not platform login or policy.

Configuration and use​

Provision Maven 3.9.11 and a JDK with java, javac and jar on the selected launch PATH. Set the endpoint once in user or administrative Oyzu configuration:

[maven]
sessionEndpoint = "http://127.0.0.1:43199/session"

The port is illustrative. The endpoint must be numeric-loopback HTTP without userinfo, query or fragment. Project, local and invocation overrides fail the resolved-authority check. The setting is absent by default, cannot be selected through a profile, and removing it restores ordinary standalone execution. Existing configuration rules exclude user configuration in CI; this proof does not establish CI authentication. No new schema version is introduced.

oyzu exec -- /opt/maven/bin/mvn verify
# With that native Maven on PATH:
eval "$(oyzu activate bash)"
mvn verify

These examples show the entry points. The settings-composition fixture binds a purpose-built plugin to package; it does not qualify the full default lifecycle. No project authentication files or extension copies are required. Only the installation's mvn executable is supported, not mvnw or arbitrary launch wrappers. Linux with Maven 3.9.11 and JDK 17 is the qualification target. Windows/macOS native execution and Windows session shell shims remain unqualified; the latter are not implemented.

Per-invocation behavior​

  1. Resolve current Oyzu configuration and native executable.
  2. Ask the agent to admit the directory, tool and arguments before preparing or launching Maven, including when the native dependency cache is warm.
  3. Receive an ordered set of admitted native mirror mappings. The directory is a context hint, never verified source provenance.
  4. Compile/package Oyzu's bundled minimal Java extension against that Maven's libraries. Write a temporary credential-free admission projection. Maven reads its normal user/global settings, including explicit -s/-gs selections.
  5. The native execution-request hook compares existing mirrors with admission, preserves blocking mirrors, and installs admitted mirrors plus a blocked catch-all. It retrieves credentials into native memory and supplies Resolver authentication for the admitted mirror ID and exact endpoint. Profiles and properties retain Maven's native merge behavior; Oyzu does not merge policy in the client.
  6. Remove temporary source, classes, JAR and admission projection after success or ordinary failure. Native caches and project outputs remain native-owned.

The experimental native-launch response is:

{
  "sources": [
    {
      "id": "approved-libraries",
      "mirrorOf": "company-libraries",
      "access": {
        "repository": "https://packages.example.com/maven/",
        "username": "reader",
        "credentialEndpoint": "http://127.0.0.1:43199/credential/session"
      }
    }
  ]
}

Use mirrorOf: "*" for one aggregate repository, or separate mappings for central, company-libraries and company-plugins. Maven matches repository IDs, not artifact group names. The ordered mappings use native mirror precedence; exact matches precede wildcard patterns. IDs and selector strings must be unique, with 1-64 mappings. The reserved oyzu-source-denied ID cannot be supplied. An unmatched repository is blocked, including repositories discovered from POMs.

Existing nonblocking mirrors must match an admitted URL, selector and layout; otherwise the invocation fails with settings-file paths. Matching mirrors can have a different local ID; admission owns the effective ID and authentication. Ambient server credentials are not used as a fallback. Native profiles, properties, proxies and JVM configuration remain native-owned; proxy authentication and custom TLS settings are not separately qualified by this proof.

Admission uses POST JSON; the extension retrieves a bounded UTF-8 password via GET. This evolves the unreleased prototype response in place: native-launch agent simulators must return sources. Captured acquisition and Gradle retain their existing single-repository response. This is not authenticated IPC or a frozen platform API. Temporary credential locators are access-sensitive even though upstream passwords are absent from those files.

Artifact traffic goes directly from Maven to the selected repository. Oyzu is not a package data proxy. Passwords are not placed in settings, arguments or launcher environment variables; Maven and its plugins share a process that can access them. Upstream credentials enforce read-only permission. No hostile-code containment or inability to bypass the managed path is claimed.

Failures, output and limitations​

Agent denial or unavailability fails before native launch, without a direct fallback or offline grant. Public CLI help and Maven --help/--version do not contact the agent. Native output/exit status follow the existing exec contract; --json returns its captured-child representation.

NATIVE_SESSION_CONFIG, NATIVE_SESSION_DENIED, NATIVE_SESSION_UNAVAILABLE and NATIVE_SESSION_INVALID identify configuration/admission transport failures. Correct authorized configuration, restore the agent or resolve its denial. MAVEN_SESSION_INVALID identifies malformed Maven response data; MAVEN_SESSION_PREPARE requires a usable JDK/Maven installation. MAVEN_SESSION_UNSUPPORTED rejects installations without the expected lib directory. MAVEN_SESSION_CONFLICT identifies incompatible mirrors, conflicting mapping identities/selectors, extension overrides or deployment-shaped arguments. Correct the reported settings or admission mapping; publishing belongs to oyzu publish.

MAVEN_ARGS and MAVEN_OPTS remain available. Oyzu rejects extension-path replacement through arguments or JVM options and project .mvn/extensions.xml, whose bootstrap downloads can precede the lifecycle hook. Existing .mvn argument files are checked for conflicting extension/deploy options. This is bounded compatibility checking, not a hostile-code sandbox or complete Maven grammar. Arbitrary plugin networking is outside Resolver admission. Wrappers, additional Maven versions, concurrent credential rotation, abrupt termination cleanup and adapter compilation caching remain unqualified/deferred.

See settings composition qualification and the historical initial integration proof.

Captured build acquisition​

With the endpoint configured at user/admin scope, oyzu build admits a Maven acquisition session before preparation. The experimental request uses tool mvn and arguments ["oyzu-build-acquire"]; this is a purpose marker, not an actual native command. The host retrieves the read credential into memory and supplies Basic authentication to the existing acquisition broker for the selected source. This path requires a credential-free repository base URL ending in /.

The preparation worker gets only the repository URL and existing filesystem broker transport. It remains --network=none, as does subsequent execution. The broker mediates acquisition; execution consumes the resulting captured Maven repository offline. Unlike the native-launch path, Maven does not receive the upstream credential. With no endpoint configured, the standalone Maven Central source remains available. Configured denial or failure never falls back to it. Snapshot versions are admitted only from administratively listed snapshot repositories; a snapshot the approved repository serves fails preparation.

Preparation is not proof that arbitrary Maven plugins have disclosed every input. A plugin resolving an undeclared coordinate during execution can fail offline. Declare the dependency through the plugin's supported Maven configuration where possible, then build again. Oyzu does not rerun the build online automatically. Publishing remains a separate operation; these sessions do not enable native Maven deploy. This prototype does not establish real-platform authorization, credential rotation, CI provisioning or general dynamic-dependency support.

See the captured-flow qualification for the actual build proof and its limits.
