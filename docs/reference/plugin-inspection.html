Inspecting plugins

CLI reference

Published from the canonical docs/reference/plugin-inspection.md file. Features marked experimental remain experimental; check support limitations before relying on them.

oyzu plugins shows which plugins the catalogs offer, which are installed, and which one each target in your project uses and why. Inspection never installs or runs anything and never changes a file.

Note: Plugins are experimental.

oyzu plugins search go
oyzu plugins versions go/app
oyzu plugins explain

For catalogs, detection and the build's Selection section, see plugin catalog. For the store and oyzu.lock records, see plugin packages. To change a locked selection, use oyzu plugins update. To clean up revoked copies, use oyzu plugins prune.

Commands​

CommandShows
oyzu plugins search [QUERY] [--type build]The uses references the catalogs offer, with package, capability, description, newest stable version, the version oyzu build would pick, and status.
oyzu plugins versions REFERENCEEvery known release of a reference, labelled, with why each can or can't be selected here.
oyzu plugins info REFERENCE[@VERSION]One release: package, publisher, contracts, profiles, platforms, payload digests, download routes and what is verified.
oyzu plugins listReleases installed in the plugin store, with the references that name them. A release a catalog has withdrawn or revoked is marked (withdrawn) or (revoked) (JSON catalogStatus).
oyzu plugins currentThis project's locked selections: installed or not, still eligible or not, the update candidate, and one line per plugin-backed target.
oyzu plugins explain [TARGET]Why each target uses its plugin, and how to change it.

Options​

OptionMeaning
--jsonOne JSON object on standard output. Before or after the subcommand.
--store DIRThe plugin store to read, as for oyzu build --store.
--refreshUpdate the cached catalog first. Never downloads a plugin.
--offlineNever use the network. Can't be combined with --refresh.
--type buildFilter search by capability. build is the only value.

The commands work in any folder. Outside a project, search, versions, info and list work as usual, and current and explain find no targets.

What they read​

search, versions and info read the same catalog a build uses (see the catalog snapshot): the verified official catalog, or your organization's catalog, which replaces it. A version shown as selectable is one a build can select.

ModeBehavior
defaultUses the cached catalog. Nothing is fetched.
--refreshUpdates the catalog cache first. The official catalog is fetched only when plugins.preview is on, as for builds.
--offlineNever fetches. Anything not cached is shown as unavailable, with the reason.

An expired catalog is shown as history only: eligibility is reported as snapshot expired, and current shows it as unknown. Its withdrawals still apply. A catalog that failed verification isn't shown; you're told why no catalog is usable.

Search covers the official and organization catalogs only; it doesn't crawl OCI registries. A plugin you name directly (in uses: or plugins.packages) can work without being listed. Under an organization catalog the official one isn't consulted, so a company replacement shows as its own package (for example acme/go for go/app).

Prune revoked copies​

oyzu plugins prune removes plugin releases from your local store after a catalog has revoked them. You name each release by its exact digest. Without --apply, it only previews.

oyzu plugins list --refresh --store /path/to/store
oyzu plugins prune sha256:<64-lowercase-hex-digits> --store /path/to/store
oyzu plugins prune sha256:<64-lowercase-hex-digits> --apply --store /path/to/store
  • Each argument must be sha256: and exactly 64 lowercase hex digits. Copy it from the list output.
  • Only a current revocation of that exact release allows removal. A withdrawal, a release missing from the catalog, an expired catalog or unavailable metadata doesn't.
  • Prune uses the cached catalog only. Run plugins list --refresh first if you need a newer one.
  • --apply checks eligibility again; an earlier preview doesn't count.
  • There's no whole-store scan, no force option, and builds, updates and inspection never prune on their own.
  • A release in use by a running Oyzu command is kept. So is one with uncertain identity, malformed metadata or unreadable files.
  • Project lock files aren't changed. If a project still locks a pruned release, Oyzu can install an eligible release again the normal way.

See store maintenance.

With --json, the result is kind: "plugin-prune" with apply, store, the catalog used, and releases (each with release, state and reason):

StateMeaning
eligiblePreview: revoked, identity matches and not in use.
retainedNot removed. The reason says why.
removedThe release and its metadata were removed (including leftovers from an interrupted earlier removal).
absentNothing of the release remains.
incompleteRemoval started but an operating-system error or an outside change stopped it. Some files may be gone. Fix the reported error; you may need to clean up the remaining files by hand.

Preview exits 0 when it returns a result. --apply exits 1 if any release is retained or incomplete, otherwise 0. Invalid digests fail before anything is opened. Each release is handled independently.

Version labels​

LabelMeaning
latest-stableNewest release that isn't a prerelease or withdrawn. It may be incompatible or outside your adopted major version.
latest-compatibleNewest stable release that fits this engine and host: contract, builder profile, support status and platform.
update-candidateNewest selectable release inside the major version your project has locked.
adoption-candidateWhat oyzu build would adopt now, for a reference your project doesn't lock yet.
lockedThe release oyzu.lock holds.

A compatible major version 3 can be latest-stable and latest-compatible for a project locked to major 1; it shows outside the adopted major 1 and is never the update candidate. A prerelease shows preview only unless plugins.preview is on, and is never a default.

Reasons (in JSON reasons): withdrawn, revoked, preview only, stable releases come from the official catalog, unsupported, no supported protocol generation, no such builder profile, no payload for this platform, outside the adopted major N, snapshot expired.

Compatibility is checked for the running engine and this host only. A requested [engine] pin is shown separately (JSON requestedPin, human "Engine pin"), but its capabilities aren't guessed. Remote worker platforms aren't checked, and the output says so.

explain and current​

explain shows the same record oyzu build prints in its Selection section, for every plugin-backed target, followed by what it was checked against. With --json: { "kind": "plugin-explain", "target", "evaluation", "coverage", "lock", "selection" }.

coverage.choice (also selection.catalogChoice) says which catalog was used:

ValueMeaning
publishedThe official catalog.
organizationYour organization's catalog.
no-indextoolIndex.url = false, so there is no catalog.
official-unavailableThe official catalog was never fetched, failed verification or expired. coverage.unavailable gives the reason.

Two states appear only in inspection, because a build would act on them:

stateMeaning
not-adoptedA release is selected but oyzu.lock has no entry yet. The next oyzu build records it.
not-installedoyzu.lock selects a release that isn't in the store, and a source for it is known. The next online, non-frozen oyzu build installs it without changing the lock. JSON route (and the explain human view) names the source.

Where a build would fail, explain and current fail with the same error:

ErrorCause
PLUGIN_LOCK_UNUSABLEThe locked release isn't in the store and no binding or catalog entry supplies it.
PLUGIN_LOCK_MISMATCHA binding names a different release from the lock.
PLUGIN_ROUTE_UNAVAILABLEA catalog release isn't in the store and has no download route.
PLUGIN_CATALOG_UNAVAILABLEThe catalog failed verification.
PLUGIN_DETECTION_CONFLICTTwo detections match the same folder. The error shows the smallest build.yaml selector that settles it.

oyzu build --plan never downloads. With an empty store it stops with PLUGIN_ROUTE_UNAVAILABLE; the message mentions --offline even if you didn't pass it.

For a selection you disagree with, the output lists the same fixes as a build: declare the target in build.yaml (or set uses:), bind a different package, undo an adoption, or pin a tool in oyzu.toml.

A plugin's tool requirements come from running the plugin, which inspection never does. So tools is absent from the JSON, the human view says deferred, and a generic oyzu pin <tool>@<version> suggestion appears instead. oyzu build lists the real tools.

current returns { "kind": "plugin-current", "evaluation", "coverage", "lock", "locked", "selection" }. lock has path, exists, selections and enginePin. Each locked entry has the reference, package, major, version, release, installed, eligible (null when no usable catalog lists it), reasons, latestStable, latestCompatible and updateCandidate.

A newer release in the store doesn't change what oyzu.lock selects. list shows both; current shows the locked one.

list​

list reads <store>/plugins/* and shows package, version, release digest, profiles, platforms, the references that name each release, and whether this project locks it. It can't tell which other projects use a release; the store doesn't track that.

Output​

Human output leads with the outcome and uses aligned tables that wrap without losing text on narrow terminals. Meaning never depends on color. --json prints one object per command, and errors use the usual error shape. Human and JSON output always agree.

Errors​

CodeCause
PLUGIN_REFERENCE_UNKNOWNNo catalog lists that reference. The error names what is listed.
PLUGIN_VERSION_UNKNOWNNo release matches the version you asked for.
PLUGIN_TARGET_UNKNOWNNo plugin-backed target has that name or path.

Build resolution errors (PLUGIN_DETECTION_CONFLICT, PLUGIN_CATALOG_UNAVAILABLE, PLUGIN_RELEASE_REVOKED and others) are reported unchanged.

Limitations​

  • Inspection doesn't run the platform and package checks a build runs when it installs a plugin. A release already in the store that this host can't run shows as not-adopted, where a build would fail with PLUGIN_PLATFORM_UNSUPPORTED. A bound source that isn't installed isn't opened or checked.
  • Only the host platform is evaluated, not remote workers.
  • --type has one value, build.
  • Organization policy beyond the catalog's own withdrawals isn't shown.
  • The official catalog is refreshed only with plugins.preview on.
  • Inspection is supported on Linux. prune is supported on Linux and Windows. macOS isn't supported yet.
