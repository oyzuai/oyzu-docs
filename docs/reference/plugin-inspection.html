Inspecting plugins

CLI reference

Published from the canonical docs/reference/plugin-inspection.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Experimental. oyzu plugins shows which plugins the catalogs offer, which are installed, and which one each target of a project uses and why, without installing or launching anything. The design is the draft discovery proposal; this page records what is implemented (issue #586, tracking #578). Catalogs, detection and the build's Selection section are in plugin catalog; the store and oyzu.lock records are in plugin packages; changing a locked selection is oyzu plugins update.

Commands​

CommandShows
oyzu plugins search [QUERY] [--type build]The uses references the effective catalogs offer, with their package, registered capability, description, newest stable version, the version oyzu build would select, and status
oyzu plugins versions REFERENCEEvery known release of a reference, labelled, with why each can or cannot be selected here
oyzu plugins info REFERENCE[@VERSION]One release: package, publisher, contracts, profiles, platforms and payload digests, acquisition routes, qualification, what is verified
oyzu plugins listThe plugin releases installed in the plugin store, side by side, with the references that name them; a stored release a consulted catalog withdrew or revoked is marked (withdrawn) or (revoked) (JSON catalogStatus)
oyzu plugins currentThis project's locked selections: installed or not, still eligible or not, the update candidate, and a line per plugin-backed target
oyzu plugins explain [TARGET]Why each target uses its plugin: the build's Selection record, with the ways to change it

Every command takes the global --json (before or after the subcommand), --store DIR (the plugin store, as oyzu build --store), --refresh and --offline (--refresh conflicts with --offline). --type accepts build, the only capability the preview registers; it filters by core-registered role, never by author-defined category. The commands work in any directory. Without a project, search, versions, info and list need nothing else, and current and explain find no target.

None of them installs a package, launches a plugin, runs a project tool, adopts a selection, or writes oyzu.lock, configuration or any project file. --help and syntax errors finish before a project, configuration, the store or the network is opened (checked by the startup tests).

What they read​

search, versions and info read the same snapshots the build resolves with (see the catalog snapshot): the verified published official catalog, or an organization catalog, which is exclusive. Release eligibility is the build's own rule (Context::refusals), so a version shown as selectable is the one a build can select.

  • Default: the cached snapshot. Nothing is fetched.
  • --refresh: update the verified catalog cache from the permitted sources first, bounded to the catalog document. It never downloads a plugin. (An official catalog is fetched only with plugins.preview, as for builds.)
  • --offline: never touch the network. Metadata that is not cached is reported as unavailable, with the reason, rather than guessed.

An expired authentic snapshot is shown as history only: rows and versions say so, release eligibility is reported as snapshot expired, and current reports eligibility as unknown. Its withdrawals still apply, as for builds. A snapshot that was refused (failed trust, rolled back) is not shown; the view says no catalog is usable and why.

Search covers the effective official and organization catalogs only. It does not crawl OCI registries. A plugin referenced explicitly (uses: or plugins.packages) can be usable without being listed. Under an organization catalog the official catalog is not consulted, so a company replacement shows as its own canonical package (acme/go for go/app) and the official package does not appear beside it.

Version labels​

LabelMeaning
latest-stableNewest non-prerelease, non-withdrawn release in the displayed snapshot. It can be incompatible or outside the adopted major.
latest-compatibleNewest stable release whose contract generation, builder profile, support status and platform payload fit this engine and host.
update-candidateThe newest selectable release inside the project's adopted major (the project locks this reference).
adoption-candidateWhat oyzu build would adopt now (the project does not lock this reference).
lockedThe release oyzu.lock holds for this reference.

A contract-compatible major 3 is latest-stable and latest-compatible for a project that adopted major 1, and shows outside the adopted major 1; it is never the update candidate. A prerelease shows preview only unless plugins.preview is on, and never becomes a default.

Reason strings (stable, in --json reasons): withdrawn, revoked, preview only, stable releases come from the official catalog, unsupported, no supported protocol generation, no such builder profile, no payload for this platform, outside the adopted major N, snapshot expired.

Compatibility is judged for the actual running engine, its supported required role features, the v1alpha1 contract and the host platform only. The requested [engine] identity is shown separately as requestedPin in JSON and Engine pin in human output; inspection does not stage that engine or infer its capabilities from its label. A remote worker's platform is not evaluated and the view says so.

explain and current​

explain computes the same record oyzu build prints in its Selection section and records as extensions["oyzu.dev/plugin-selection"]: the typed Explanation built by the same resolver (Context::decide), the same lock and store replay and the same renderer. Human output is the build's section with every plugin-backed target in full, followed by what it was evaluated against. --json is { "kind": "plugin-explain", "target", "evaluation", "coverage", "lock", "selection": <Explanation> }.

coverage.choice says why the snapshot is the one it is, or is absent: published (the official catalog), organization (the organization's catalog, exclusive), no-index (toolIndex.url = false: there is no catalog) and official-unavailable (the official catalog was never obtained, or is refused or expired; coverage.unavailable gives the reason). The value in selection.catalogChoice is the same. With plugins.preview on and no catalog, the notes say so and that running online is the remedy.

Two states exist only here, because a build would adopt or install and inspection must not:

stateMeaning
not-adoptedThe catalog or a binding selects a release but oyzu.lock has no entry. The next oyzu build records it.
not-installedoyzu.lock selects a release the plugin store does not hold, and a binding or its current verified catalog entry supplies a source for that exact digest. The next online, non-frozen oyzu build installs it without changing the lock. For a catalog route, the JSON route names the route that would be used, and explain shows it in its human view (the compact current table shows only the state); inspection does not contact it. A real build never shows this state, since it installs the release.

For the lock and binding state, inspection does not show as installable what a build refuses. Where the build would fail on that state, explain and current fail with the same error: a locked release missing from the store with neither a binding nor a current catalog listing is PLUGIN_LOCK_UNUSABLE; a binding that names another release is PLUGIN_LOCK_MISMATCH; a catalog release that is not in the store and has no OCI route is PLUGIN_ROUTE_UNAVAILABLE; one with an OCI route is not-adopted (inspection never downloads). (not-adopted states that a bound source or an installed copy exists for the release the build would adopt.) Withdrawals, revocations and organization rebinding (including an authentic expired copy) are the build's same refusals. A Refused catalog remains PLUGIN_CATALOG_UNAVAILABLE; Absent and Expired snapshots never offer routes. build --plan never downloads, because its preview pass runs offline: with a clean store it stops with PLUGIN_ROUTE_UNAVAILABLE and installs nothing. That message names --offline even though the flag was not passed, a known wording limit that it shares with first adoption.

Known gap: inspection does not run the host-platform and archive or manifest checks a build runs when it acquires a package (launch_target, check_manifest). A catalog release already in the store that this host cannot run shows as not-adopted, where the build fails with PLUGIN_PLATFORM_UNSUPPORTED; a bound source that has not been installed is likewise not opened or verified. Recorded on #601.

For a selection you dispute, the same copyable remedies appear as in the build: declare the targets in build.yaml (or an explicit uses:), bind another package for the reference, undo an adoption, and pin a tool in oyzu.toml. Ambiguous evidence (two catalog detections, or a catalog detection and a built-in one) is the build's focused conflict, printed with the smallest build.yaml selector; explain fails with it and installs nothing.

Native tool requirements come from the plugin's requirements operation, which runs the plugin. Inspection never does, so tools is absent from the record, the human view says deferred, and a generic tool-version remedy (oyzu pin <tool>@<version>) stands in; oyzu build lists the tools.

current returns { "kind": "plugin-current", "evaluation", "coverage", "lock": { path, exists, selections, enginePin }, "locked": [...], "selection": <Explanation> }. Each locked entry carries the reference, package, major, version, release, installed, eligible (null when no usable catalog lists the release), reasons, latestStable, latestCompatible and updateCandidate. A newer release cached in the store does not change what oyzu.lock selects: list shows both immutable packages, current shows the locked one.

list​

Lists <store>/plugins/* read-only: package, version, release digest, profiles, platforms, the references a consulted catalog or this project's lock names for it, and whether this project locks it. It cannot know other projects' selections: the store keeps no inventory of the projects that use it, and the view says so.

Output​

Human output leads with the outcome, uses aligned tables, wraps without loss at narrow widths, escapes untrusted terminal controls and uses color only for emphasis; meaning never depends on color alone (the Selection marks are words without color). --json prints one typed object per command on stdout and errors in the usual error shape. Both are serialized from the same value (plugins::inspect results and resolve::Explanation); the human renderer (src/presentation/output/plugins.rs) recomputes nothing and the Selection text is rendered by logging::plugin_selection_section, the build's own view.

Errors: PLUGIN_REFERENCE_UNKNOWN (no consulted catalog lists it; names what is listed), PLUGIN_VERSION_UNKNOWN (no release matches the selector), PLUGIN_TARGET_UNKNOWN (no plugin-backed target of that name or path), plus the build's own resolution errors (PLUGIN_DETECTION_CONFLICT, PLUGIN_CATALOG_UNAVAILABLE, PLUGIN_RELEASE_REVOKED, ...), unchanged.

The agreement test compares explain's selection with Workspace.plugin_selection from oyzu discover --json on an adopted project, ignoring tools and the generic tool-version remedy. That is the value oyzu build renders and records; the stand-in plugin cannot run a full build.

Limitations​

  • Host platform only; remote workers are not qualified.
  • Tools of a target are deferred (see above); no plugin is launched.
  • --type has one value, build; publish and deploy are not registered roles yet.
  • No policy admission view: organization policy beyond the catalog's own withdrawals is not modelled by the client yet.
  • The official catalog is refreshed only with plugins.preview, as for builds, because it lists nothing else yet.
  • Windows and macOS behavior is untested here (the new tests are Unix-only, as the catalog tests are).
