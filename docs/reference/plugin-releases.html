Plugin releases

CLI reference

Published from the canonical docs/reference/plugin-releases.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Experimental. How a first-party plugin becomes an Oyzu OCI package in GHCR that any oyzu can acquire without Docker or an account. The package layout is the Oyzu OCI package contract; how the CLI acquires and verifies it is plugin packages; the design is plugin authoring and publication.

No release has been published. The GHCR package ghcr.io/oyzuai/plugins/go does not exist yet; publishing waits on the organization-owner checklist on issue #619, on GitHub-hosted runners (see Limitations) and on maintainer authorization. The terms the first release carries are in Go builder preview.

Pieces​

PieceRole
tooling/plugin-oci.pyRelease tooling, Python standard library only: assemble builds the release root as an OCI image layout directory from one executable per platform and prints the root digest; push copies it to a registry under a tag (refusing to move an existing tag to a different root); assemble-downloaded does the same from the workflow's downloaded payload artifacts; attach attaches a Sigstore bundle as a referrer of the root and in the sha256-<hex> referrers tag; catalog-entry prints the oyzuai/tool-index config/plugins.toml release entry from an assembled layout (every field the catalog schema requires; tested = [] unless --tested CORE=os/arch[/abi],... names platforms of the release; bad input exits nonzero with a message), checked by python3 tooling/test-plugin-oci-catalog-entry.py, which validates the entry against catalog.schema.json. The CLI never runs it
.github/workflows/plugin-release.ymlManual (workflow_dispatch) workflow: validates the inputs (semantic version, package name), builds oyzu-plugin-<package> for linux/amd64 and linux/arm64 (static musl), darwin/arm64, darwin/amd64 and windows/amd64 (msvc), assembles the root, then runs either the dry-run job (read-only token) or the publish job (packages: write, id-token: write, main only)

Local release, step by step​

oyzu exec -- cargo build --locked -p oyzu-plugin-go --features plugin
python3 tooling/plugin-oci.py assemble --out layout --version 0.1.0 \
    --revision "$(git rev-parse HEAD)" \
    --executable linux/amd64=target/debug/oyzu-plugin-go
# prints sha256:<root digest>
python3 tooling/plugin-oci.py push --layout layout --to localhost:5000/oyzuai/plugins/go:0.1.0

--executable takes os/arch[/abi]=PATH (OCI spelling: linux, darwin, windows; amd64, arm64; gnu, musl, msvc) once per platform. The plugin manifest comes from docs/contracts/plugins-v1alpha1/examples/manifest.go.json (--manifest to change it) with the version, revision and one runtime per executable filled in; each payload archive holds the executable at bin/<file name>. Archives and manifests are reproducible (fixed times, sorted keys), so the same executables give the same root.

Any OCI 1.1 registry whose token endpoint is on its own origin works as a target. Without Docker, the distribution registry binary serves one on loopback: registry serve config.yml with http: {addr: 127.0.0.1:5000} and a filesystem storage directory.

A user binds the pushed release by digest (no signature needed outside the official namespace) and builds:

[plugins.packages]
"go/app" = { oci = "localhost:5000/oyzuai/plugins/go@sha256:<root digest>" }

The workflow​

gh workflow run plugin-release.yml -f version=0.1.0 (dry run, the default): builds the payloads, assembles the root, starts the distribution registry binary on the runner (checksum-verified, no Docker), pushes to it, bootstraps the oyzu of this commit and builds examples/builds/go-app/project with the release bound by digest, checking that oyzu.lock records the root and that --frozen replays. Nothing leaves the runner and nothing is signed (a dry run writes no public transparency-log entries).

-f publish=true, from main only:

  1. pushes the release to ghcr.io/oyzuai/plugins/<package>:<version> with the workflow's GITHUB_TOKEN (packages: write);
  2. signs the root keylessly: tooling/plugin-oci.py statement writes an in-toto statement (predicate https://sigstore.dev/cosign/sign/v1) naming the root digest, and cosign attest-blob --statement --bundle (cosign v3.0.2, checksum-verified) signs it with the workflow's OIDC identity (id-token: write), giving a Sigstore bundle v0.3 with a DSSE envelope from a Fulcio certificate for https://github.com/oyzuai/oyzu/.github/workflows/plugin-release.yml@refs/heads/main, logged in Rekor. This is the tool index's signing path. cosign sign-blob is not used: it writes a message-signature bundle, which the client does not accept;
  3. attaches the bundle as a referrer of the root.

The signature is detached: it never changes the root. Clients require it for ghcr.io/oyzuai/plugins/* and verify it against exactly that identity, on a GitHub-hosted runner, before installing. Two separate checks apply. The certificate's identity is pinned to the workflow at @refs/heads/main: a branch that edits the workflow signs as @refs/heads/<branch> and is refused, and the publish job also runs only on main. And the certificate must record a github-hosted runner environment, refusing a self-hosted or an unrecorded one. Neither check protects against someone who can merge to main (their workflow is the pinned one) or against a compromised GitHub-hosted runner; hosted runners are ephemeral, which limits the second. The workflow uses ubuntu-24.04, macos-15 and windows-2025 (the organization enabled hosted runners on 2026-10-19; hosted minutes are reserved for releases). A self-hosted signer was merged in #663 and reverted before any release was signed; see the decision.

This signing path differs from the CLI's GitHub release workflow (PR #617), which signs build provenance with a self-managed witness key: plugin packages use portable keyless Sigstore as the design requires, the same trust model as the public tool index.

Publishing the Go preview (runbook)​

The ordered sequence for PLG-AUTHOR-04 (private source, public binary, catalog last). Every step after 2 has outward effects that cannot be undone: a package in GHCR, a permanent public Sigstore (Rekor) entry, a public package and an advertised catalog entry. Run it only with the maintainer's authorization of the exact version. Commands assume gh authenticated as an organization member and a checkout of main. VERSION=0.1.0-preview.1 is the agreed version (decisions); a version is never reused.

  1. Preconditions.
    • GitHub-hosted runners are available to the organization (enabled by the maintainer on 2026-10-19) and a dry run on main is green on them. The workflow uses hosted runners for the five builds and the signing, and the client accepts only a certificate whose runner environment is github-hosted, which the maintainer kept. Before that, with the repository private and hosted runners off, every job failed within seconds with no runner (the 2026-10-18 dry run, run 39173379822). The self-hosted signer merged in #663 was reverted before any release was signed.
    • The #619 checklist: public packages allowed for the organization (done); the workflow may write plugins/go (item 2, below).
    • #662 (a bound withdrawn or revoked release is refused before install) and this documentation pull request are merged, so main carries the workflow, the refusal and catalog-entry.
    • oyzuai/tool-index can advertise a release whose evidence is under the referrers tag: its .github/scripts/plugin-availability.sh must fall back from the referrers API to the sha256-<hex> tag, because ghcr.io answers the API with 404 (checked 2026-10-19 against an image that has tag-schema referrers). Without that change the catalog silently omits the release. That change is oyzuai/tool-index#39 (under review, not merged when this was written); it is a dependency of step 5, and plugins.json must be checked to list the release (below).
  2. Dry run (read-only, nothing leaves the runner, nothing signed). The helper dispatches the workflow and selects the run it created: newer than the dispatch, on the head of main, and named for the package and version (the workflow's run-name), so two dispatches at the same moment are told apart: 
    dispatch() {   # dispatch VERSION [publish]; sets RUN to the new run's id
      local t sha; t=$(date -u +%Y-%m-%dT%H:%M:%SZ); sha=$(git rev-parse origin/main)
      gh workflow run plugin-release.yml --ref main -f package=go -f version="$1" ${2:+-f publish=true}
      RUN=
      for _ in $(seq 30); do
        RUN=$(gh run list --workflow plugin-release.yml --event workflow_dispatch --json databaseId,createdAt,headSha,displayTitle --limit 10 \
          -q "[.[] | select(.createdAt >= \"$t\" and .headSha == \"$sha\" and (.displayTitle == \"Plugin release go $1\" or .displayTitle == \"Plugin release go $1 (publish)\"))][0].databaseId // empty")
        [ -n "$RUN" ] && break; sleep 5
      done
      [ -n "$RUN" ] || { echo "no run found for the dispatch" >&2; return 1; }
      gh run watch "$RUN" --exit-status
    }
    git fetch origin main && dispatch 0.0.0-dryrun.1
    gh run download "$RUN" -n catalog-entry -D dry-run-entry && grep -c '^\[\[packages.releases.platforms\]\]' dry-run-entry/catalog-entry.toml   # 5
    Hosted runner minutes are reserved for this workflow, so this is the one pre-release dry run: it must be on the final workflow, with the proof fix, on main. Run 39191353142 proved the five hosted build legs and the steps through the bootstrap only, and a workflow that differs from the one that ran it by more than runner labels or run-name needs the maintainer's word before another dry run. Expect validate, the five Build jobs and Dry run green and five platforms in the entry. Fix any failure before going on; a dry-run version may be reused.
  3. Publish (from main only, the signer identity requires it): 
    git fetch origin main && dispatch 0.1.0-preview.1 publish
    ROOT=$(gh run view "$RUN" --log | grep -o 'ROOT=sha256:[0-9a-f]\{64\}' | tail -1 | cut -d= -f2) && echo "$ROOT"
    gh run download "$RUN" -n catalog-entry -D release-entry     # the tool index entry, tested = []
    The Publish job pushes ghcr.io/oyzuai/plugins/go:0.1.0-preview.1, signs the root keylessly and attaches the bundle. ROOT is also in the job summary line Published …; step 4 checks that the lock records exactly it. If the push is refused with a permission error, the package does not yet grant this workflow write access: an organization owner opens github.com/orgs/oyzuai/packages → plugins/go → Package settings → Manage Actions access → add oyzuai/oyzu with role Write (item 2 of #619; the first publish creates the package, so this can only be done now), then re-run the failed job. If the push succeeded but a later step failed, a re-run is only safe when it produces the same root; a rebuild that yields a different root makes push refuse the tag, and the version is spent: publish 0.1.0-preview.2 instead.
  4. Make the package public (an organization owner, GitHub UI): plugins/go → Package settings → Danger Zone → Change visibility → Public. Visibility is per package and does not expose the repository. This is reversible (set it back to private if step 4 fails), but the bytes were public meanwhile.
  5. Anonymous pull and signature proof with the CLI's own verifier, from a clean state, no Docker and no credentials, in an ordinary shell (not a CI job: user-scope settings are ignored in a CI context): 
    S=$(mktemp -d) && mkdir "$S/home" && cp -r examples/builds/go-app/project "$S/project"
    printf '[plugins]\npreview = true\n[plugins.packages]\n"go/app" = { oci = "ghcr.io/oyzuai/plugins/go:0.1.0-preview.1" }\n' > "$S/user.toml"
    run() { env -u GITHUB_TOKEN -u GH_TOKEN HOME="$S/home" XDG_DATA_HOME="$S/xdg" OYZU_USER_CONFIG="$S/user.toml" OYZU_PROJECT_TRUST=off oyzu -C "$S/project" "$@" --store "$S/store"; }
    run build                                   # acquires, verifies the signature, installs, builds
    grep -F "release = \"$ROOT\"" "$S/project/oyzu.lock"
    run build --frozen                          # replays by digest
    Success is a build whose Selection section names oyzu/go 0.1.0-preview.1 as a local package binding, the lock recording ROOT, and the artifact running. PLUGIN_PACKAGE_UNAVAILABLE … refused anonymous access means step 3 is not effective; PLUGIN_SIGNATURE_* means the release must not be listed.
  6. Catalog entry last. In oyzuai/tool-index, open a pull request that adds the step-2 TOML entry to config/plugins.toml under oyzu/go, with [[references]] go/app and go/library and the go-module and go-workspace detections copied from the Go entry below (they were the bundled snapshot in src/plugins/bundled-catalog.json before its removal), and qualification.tested set to the core and platforms actually proved (agreed: 0.1.0, linux/amd64 musl). tooling/plugin-oci.py catalog-entry --layout … --tested CORE=os/arch/abi prints the entry from a layout. A person reviews it (code owner). On merge the tool-index release workflow checks the root and evidence anonymously and signs plugins.json; verify the new release lists the package, not just that the asset exists (a release whose catalog step failed or left the package out still has the tools assets): 
    D=$(mktemp -d) && gh release download --repo oyzuai/tool-index --pattern 'plugins.json*' --dir "$D"
    jq -e --arg root "$ROOT" '.content.packages[] | select(.publisher == "oyzu" and .name == "go")
        | .releases[] | select(.version == "0.1.0-preview.1" and .root_digest == $root)' "$D/plugins.json"
    jq -e exits nonzero when no release matches. The CLI verifies the bundle in step 7.
  7. Remove the bundled preview source (separate pull request, merged only after step 5 is verified live): the compiled-in catalog, its generator and the "temporary" notes are gone, so the published catalog is the only source. The bundled catalog's archive digest stood in for a root that was never published; leaving it would list a second 0.1.0-preview.1 with different bytes.
  8. Final proof from a clean store, with only the official catalog and GHCR: the step-4 commands again, now with plugins.preview = true and the binding only (no archive, no local bytes), then oyzu plugins info go/app showing the release from official catalog serial N. Record the commands, the output and the date in the status entry and Go builder preview.

Rules​

  • A version is published once. push refuses to move a tag to a different root; a fix, a changed payload or an added platform is a new version and a new root.
  • Releases and their signature referrers are retained; no cleanup policy applies to ghcr.io/oyzuai/plugins. A lock cannot recreate deleted bytes.

Limitations and verification​

  • The first dry run (2026-10-18, run 39173379822, main at a3c1127) failed in validate after two seconds with no runner: the repository is private and GitHub-hosted runners were off (the logs are gone, so this is inferred). The organization enabled them on 2026-10-19.
  • The second dry run (2026-10-19, run 39191353142, the first on hosted runners, main at be81775, version 0.0.0-dryrun.3) passed validate, the five build legs (linux amd64 and arm64 musl, darwin amd64 and arm64, windows amd64) and the steps through "Bootstrap the oyzu of this commit", then failed in "Acquire the release and build with it": the build succeeded but used the built-in Go builder, so oyzu.lock had no [[plugin]] entry and the grep for the release root failed. Cause: the runner sets CI and GITHUB_ACTIONS, oyzu detects a CI context, and in a CI context user-scope settings (the proof's plugins.packages binding in OYZU_USER_CONFIG) are ignored. The proof now runs with every variable CI detection reads cleared (a list checked by tooling/test-plugin-release-workflow.py, and exercised locally with all of them set: the plugin is selected with the list and not without it). The skipped step "Verify signatures through the test path" has not run on a hosted runner; its tests (plugin_oci) pass locally with the CI markers set. The same rule applies to anyone using the preview in CI: a user-scope binding or plugins.preview has no effect there, machine scope does (Go builder preview).
  • Platform qualification: only linux/amd64 has run the plugin end to end (Milestone A, and the musl payload on a glibc host below); linux/arm64, darwin/arm64, darwin/amd64 and windows/amd64 payloads are built but not qualified.
  • The dry run's acquisition binds by digest; its last step runs the compiled-CLI OCI tests (tests/integration/plugin_oci.rs), which verify signatures with a test Sigstore instance.
  • No keyless bundle for a release root was produced: that needs the workflow's OIDC token. The format path is covered by a real bundle from the pinned cosign v3.0.2 attest-blob --statement over a real release root, signed with a throwaway key (tests/fixtures/plugin-oci/): a unit test checks the DSSE in-toto statement names the root digest, verifies the DSSE signature, and shows the client parses it and stops only at the missing transparency-log entry. The certificate, identity and Rekor checks are covered by the verifier's tests (a real public DSSE bundle, test Sigstore instances, Rekor v2 bundles built to the sigstore-go format), not by a real release-root bundle.

Local dry run, 2026-10-18, reproducing the dry-run job's steps (distribution registry 3.0.0 binary on 127.0.0.1:5000, no Docker daemon): the release builds of oyzu-plugin-go for x86_64-unknown-linux-musl and aarch64-unknown-linux-musl (rust-lld), both static, were assembled with assemble-downloaded and pushed; the glibc debug oyzu of this branch acquired the release by digest (linux/amd64 musl payload), recorded release and built examples/builds/go-app/project, and --frozen replayed. The darwin and Windows build jobs and the integration-test step were not run.

Earlier local record (same registry): assemble + push of linux/amd64 and darwin/arm64 payloads; re-push idempotent; pushing another root under the same tag refused; attach twice wrote one referrer in the sha256-<hex> tag (the registry has no referrers API), which the CLI found (PLUGIN_SIGNATURE_MISSING before, PLUGIN_SIGNATURE_INVALID for the deliberately unsigned bundle after). See implementation status for the build run.
