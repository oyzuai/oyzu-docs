Go applications, libraries and workspaces

CLI reference

Published from the canonical docs/reference/go.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Oyzu builds Go modules and go.work workspaces with no Oyzu configuration: it discovers go.mod and go.work, runs the native go tooling and collects binaries, module archives, test reports and coverage into a build bundle. Use this page to see what the Go builder runs, how it chooses the Go version, and what it produces.

Status: experimental. The Go builder and its action decomposition are experimental. Linux/amd64 is the best-qualified path; Windows results are noted where they exist. See Verification and limits.

Quick start​

oyzu run list
oyzu run test
oyzu run lint
oyzu run format-check
oyzu build --plan
oyzu build
oyzu inspect dist
  • oyzu run <task> executes development tasks on the host with your provisioned go and gofmt.
  • oyzu build plans and builds the module; captured builds require Docker and a Linux toolchain image (see Toolchain image).
  • oyzu inspect dist checks the resulting bundle.

What gets discovered​

  • A workspace owns its declared modules.
  • Static task listing does not run Go. Explicit development execution and captured preparation use native metadata to select package patterns.
  • Native preparation determines whether the project has main packages. A project with no main package produces module artifacts instead of failing as an unsupported library.
  • An explicit uses: go/library selects module packaging even when commands are present.
  • An experimental external build of the same host lane can be selected with a local development plugin binding; without one the built-in builder described here is used.

Usage and toolchain​

Development tasks​

  • Development tasks use provisioned go and gofmt.
  • The implicit tasks include dependency installation, compile, test, vet, formatting and formatting checks.
  • oyzu run format modifies source. Builds use format-check, whose native gofmt -l output must be empty.
  • Native go.work members supply the package patterns for development build/test/vet commands.
  • Direct tests produce the test-only evidence described under Direct test evidence. Other development tasks do not produce a collected build bundle.

Toolchain image​

Captured builds require Docker and a Linux toolchain image. Oyzu can acquire the default amd64 Go image from the published toolchain image set; offline hosts and custom profiles need the image already provisioned. To build the default CI image locally:

docker build -f tooling/images/go.Dockerfile -t oyzu-toolchain/go:1.24-mod0.25.0 .
  • The current recipe extends golang:1.27-bookworm with the owned module packaging adapter linked against checksum-locked golang.org/x/mod 0.25.0.
  • Dependency downloads occur in this provisioning step, not in project build execution.
  • The image retains the upstream BSD license notice.
  • Its bootstrap compiler is separate from the admitted, locked compiler selected for the project.
  • Rebuild the embedded worker from the same candidate as the CLI and verify it executes inside the image; an existing image tag does not establish worker freshness.
  • Native local checks use Go 1.24.13 on Windows. New cross-host module packaging checks and isolated library builds are wired into CI but still require revision-specific confirmation.

This changes the default Go image from the base Go distribution:

  • Custom --image go=<image> profiles must now include oyzu-go-modulezip as well as the existing compiler/native tools, and require explicit provisioning.
  • Oyzu does not install a missing adapter into an image.
  • Image content identity enters the build evidence.
  • A missing executable fails preparation; it does not disable library packaging silently.

Docker consumers can separately request the experimental Go module dependency context. It reuses native metadata/acquisition but only exports the captured module cache; the consumer's standard Go image does not need the module packaging helper. This exception applies to dependency preparation, not ordinary Go artifact builds or their report obligations.

Go version selection​

Oyzu runs Go with GOTOOLCHAIN=local, so Go never switches or downloads a toolchain itself. Oyzu selects the Go from the project's own files instead (OD10 rule 9; the other ecosystems' exact pins are in native pin files).

The Go minimum is the newer of the go and toolchain lines in the build folder's go.work when it has one, and in its go.mod otherwise. Go orders versions as 1.24 < 1.24rc1 < 1.24.0 < 1.24.5.

  • A toolchain line is always honored. A suffixed name is read as Go reads it (go1.24.3-bigcorp and go1.24.3+auto as 1.24.3); toolchain default and toolchain local are ignored; any other value that is not a Go release name is refused with a remedy.
  • A go line from Go 1.21 on is a toolchain minimum. Before Go 1.21 it was a language level, so a go 1.16 line only constrains the selection: with no toolchain line and no [tools] go, the newest stable Go is used, and a configured value below the line fails resolution.
  • In a workspace, the go.work lines decide. A go.mod beside the go.work keeps its go line as a constraint and its toolchain line is ignored, as Go ignores it. Modules in subfolders are not read: Go itself refuses a workspace whose go line is older than a module's.
ProjectGo selected
toolchain go1.24.5 (or go 1.24.5), no [tools] goexactly 1.24.5
go 1.24 with no patch, or toolchain go1.25rc1the newest stable release of that line (1.24.x, 1.25.x): Oyzu acquires stable releases only, so a line with only a release candidate fails resolution
[tools] go at or above the minimum, in any folderthat value (1.25, 1.24 for a 1.24.5 minimum, latest); the minimum still binds its resolution
[tools] go below the minimum in a folder above the module (the project root, or user configuration), in oyzu.toml or oyzu.local.tomlthe minimum: the farther value loses, and the Tools row shows overrides 1.23.4 from oyzu.toml
[tools] go below the minimum in the module's folder or below it, in oyzu.toml or oyzu.local.tomlrefused before any work with TOOL_NATIVE_MINIMUM_CONFLICT, naming both files
a command-line or environment value, or a policy value below the minimum (a toolset value is exempt)refused with TOOL_NATIVE_MINIMUM_CONFLICT, naming its source and the native file; a policy value cannot be changed in the project, so the remedy is to ask the policy owner or lower the minimum

For example, with toolchain go1.24.5 in app/go.mod, a root [tools] go = "1.25" and [tools] go = "1.24.0" in app/oyzu.toml, oyzu build stops after loading the configuration with exit status 3:

✗ TOOL_NATIVE_MINIMUM_CONFLICT: hello: [tools] go = "1.24.0" in app/oyzu.toml is below the go minimum 1.24.5 that app/go.mod declares (toolchain line); set [tools] go to 1.24.5 or later in app/oyzu.toml, or remove it so the native file decides
  Next: Make the configured tool version reach the native minimum, or change the native file, then retry.

With only a root [tools] go = "1.23.4", the build uses the minimum and says so in the Tools block:

  ✓ Tools                   1 tool pinned · 0 installed now                 1.9s
      go          1.24.5   already installed  detected from go.mod · overrides 1.23.4 from oyzu.toml

How requests are compared

  • Only plain releases and lines (1.23.4, 1.23) are compared with the minimum where they are written. Another request form (a range) is resolved against the minimum and fails resolution when nothing satisfies it.
  • Tool policy (a tools.go lock or allowed set) applies to the selected version whichever file requested it, the minimum included. When policy refuses the minimum itself, TOOL_NATIVE_MINIMUM_CONFLICT names the policy source and says it cannot be changed in the project.
  • In a workspace that builds in the isolated executor, the same refusal stops the build in preparation with nothing run, exit status 3, and the code in the bundle's diagnostics.
  • oyzu config explain tools.go still shows the configured value; the override is shown only in the Tools block.

Locking

The selection is locked in oyzu.lock like any request, with the minimum recorded as the native constraint go-minimum:>=1.24.5.

  • Changing [tools] go needs oyzu pin before the next build, as for any explicit request.
  • So does a changed minimum: go get and go mod tidy rewrite the go and toolchain lines, and the next build stops with the cause named:
✗ TOOL_LOCK_STALE: oyzu:go 1.24.5; app/go.mod declares go 1.24.5 (toolchain line) but oyzu.lock pins 1.27.2; run oyzu pin
  • Run oyzu pin and commit oyzu.lock. An oyzu.lock written before the Go minimum was read holds the request * and needs the same step once.

Pinned Go in the captured worker​

A project that pins Go ([tools] go = "1.23", locked with oyzu install go@1.23) builds with that exact Go in the captured worker, not the image's copy. Preparation:

  1. Reads the Linux (linux/amd64/gnu) archive recorded for the pinned version in oyzu.lock.
  2. Downloads it through the tool broker, unless a copy cached under the user data directory still matches the locked SHA-256.
  3. Verifies the bytes against the locked digest.
  4. Restores them read-only in the worker at /scratch/gotool.
  5. Puts that go first on PATH (GOROOT is set to it) for preparation and every build action.
  • The plan records the archive digest under oyzu.dev/locked-tool, so a different pin or archive changes the action identity.
  • Without a pin, the Go that build preflight locked from the Go minimum is used the same way, so the selected compiler can satisfy a newer native minimum independently of the image's bootstrap compiler.
  • A project whose existing oyzu.lock has no Go entry, a managed build or a non-Linux worker uses the image's Go.
  • A tampered lock is rejected by the lock's own identity check, and a corrupted cached archive is replaced by a verified download.

Direct test evidence​

oyzu run test instruments the implicit go test ./... command with -json, a fresh -coverprofile destination and -count=1.

  • Native Go owns test discovery and compilation.
  • Oyzu converts its JSON events to JUnit and retains the native coverage profile under dist/, with digests and summaries in the manifest.
  • Statement coverage does not claim branch or line coverage.
  • Packages with no tests retain an honest zero-test summary; native Go may succeed in that case.
  • Missing/malformed reports and configured coverage thresholds can still fail the invocation.

Workspaces and selectors​

  • For a go.work root, native workspace metadata selects contained member package patterns and the invocation combines their actual test events and coverage. Members outside the task root fail.
  • Forward selectors through oyzu run test -- -run TestGreeting. Forwarded arguments go only to the requested task.
  • The default disables reuse of Go's cached test results, while Go may still reuse its native compilation cache.

Hooks and custom commands​

  • The shared collector normalizes JUnit before post_test, exposing OYZU_TEST_REPORT and OYZU_COVERAGE_REPORT to hooks. Final validation and capture follow the hook, so report transformations are retained.
  • Invalid native event streams or preexisting normalized outputs remain failures even if a hook subsequently writes valid XML.
  • A failed test skips its success-only post hook and retains available evidence.
  • Exact argv = ["go", "test", "./..."] and run = "go test ./..." overrides receive the same instrumentation.
  • Other custom bodies remain unchanged and must write their required JUnit and Go coverage reports.
  • An explicit coverage declaration can redirect the native profile. An explicit JUnit declaration selects file-based reporting and requires the custom task or hook to produce that XML. The default Go command itself emits JSON, not JUnit.
  • Declared paths must be fresh; see direct report binding.

Prerequisites and scope​

  • This workflow needs a provisioned Go compiler and available dependencies, without Docker or a platform account.
  • Host execution retains native environment/network behavior. Use existing dependencies and native GOPROXY=off, GOSUMDB=off, GOTOOLCHAIN=local settings when verifying an offline fixture.
  • It is not an isolated build, does not produce application artifacts and confers no publishing authority. Direct test evidence describes host provenance, output preservation, errors and recovery.
  • python tooling/test-go-direct.py --cli <compiled-oyzu-path> --go <native-go-path> exercises real modules and workspaces, report inspection, test selection, failures, skips, empty suites, hooks, thresholds and custom-command obligations. CI runs it with provisioned Go 1.24.13 after compiling the CLI on each host. Current local and cross-host results are recorded separately in implementation status.

Preparation and execution​

Native Go commands own manifest parsing, workspace membership, main package discovery, dependency selection and cgo detection.

  • Captured inputs must contain local modules and replacement paths; escapes and missing inputs fail.
  • Public module acquisition uses the existing scoped Go proxy broker and go.sum verification. The proxy's redirect of a large module zip to its own storage bucket is followed as a redirect-only route (acquisition transport). Private source routing and direct VCS acquisition remain unfinished.
  • The compiler/ABI is recorded for cgo, and execution cannot turn off required cgo support through an environment override.

What preparation captures​

Preparation captures the native dependency cache and module artifact candidates.

  • Go works in a module cache on an engine tmpfs (/scratch/gomodcache), and the prepared store keeps only its download cache: module zips with their .mod, .info and .ziphash files.
  • Each build action serves that store to Go as a file:// module proxy and extracts the modules it needs into its own tmpfs module cache, where go.sum verifies every zip.
  • Extracted modules are many small files, and writing them through a Docker Desktop bind mount of a Windows path made preparation of a mid-size backend take about fifteen minutes.
  • Library candidates come from captured source before build outputs or private compiler caches exist.

What a build action runs​

  • The build runs compile, native tests, vet and read-only formatting checks with denied networking and the prepared module cache.
  • Final artifact collection occurs only after required gates pass. Prepared candidates are not successful build artifacts by themselves.
  • Application builds retain their existing single primary binary or named multiple binaries, using -trimpath and disabled ambient VCS stamping.
  • Libraries compile package patterns without fabricating an executable.
  • Native test JSON becomes JUnit, and native Go coverage retains its statement denominator. Shared collection stores these under dist/, with paths, digests and summaries in dist/manifest.json.
  • Failed tests, vet, formatting, missing reports or compilation prevent final artifact collection. Source files remain unchanged during captured execution; inspect task logs and reports to repair the failing native input.

Scratch space​

  • Each engine-owned scratch tmpfs keeps a 2 GiB minimum size ceiling and grows to match its action's memory reservation when that is larger. This does not raise the action's memory reservation; where cgroups are available, the limit covers combined process and tmpfs use.
  • Go build actions reserve at least 4 GiB, so /scratch/gotmp can hold larger compiler and test-linker intermediates than the separate 512 MiB /tmp mount.
  • The Docker and daemonless execution paths use the same ceiling.

Native action boundaries (experimental)​

Root-owned captured pure-Go application targets describe each main-package build and each selected real package test as separate native actions.

  • Production inputs come from fresh native package/import/file/embed metadata. Synthetic Go test variants do not become binary inputs or extra test actions.
  • Newly selected source and embed files change the captured read set.
  • Native observation happens during admitted preparation, never static discovery or pure planning.

Binary builds

  • Binary compilation writes private bytes without consuming the injected snapshot version. Export applies the current versioned filename after required build and report gates, including when compilation restores earlier bytes.
  • Explicit native or user environment values remain real inputs. The new path fixes the native context used for metadata selection; a conflicting task environment fails validation before reuse. It does not silently reinterpret a changed build flag.

Package tests

  • Package tests use go test -json -count=1 with distinct package-attributed JUnit and native statement-coverage reports.
  • Each test receives the entire original captured workspace and its own initially empty output and scratch directories. It cannot consume another action's reports or workspace mutations.
  • Declared prepared proxy resources and the selected tool/image/environment remain bound. The compiler cache lives in scratch, outside retained binary-result changes.
  • Restored reports retain their producing-run evidence and pass current report gates. These isolation bindings also apply with --no-cache.

What keeps the coarse plan

  • This path requires the compiled private Oyzu worker in the Go executor image; a missing worker fails the action.
  • Libraries, cgo, nested targets, native workers, targets with materialized inputs and configurations with any authored tasks or hooks retain the existing coarse plan. This preserves their actual command and hook lifecycle, including generated inputs and post-test report transformations.
  • The decision uses the resolved preparation configuration.
  • Tests requiring generated or materialized workspace state need an actual supported input binding; the private-source path must not silently discard those inputs.

Measured results

  • The measured candidate passes a Linux-host/Docker shared-production edit with unrelated compilation reuse, an independent fresh oracle, test-only reuse and source-only second-checkout restoration with original producers.
  • Its agreed finite cases also pass, including source/embed membership, runtime data, changed image identity, required failure/report gates and coarse hook/cgo boundaries.
  • An original hook fixture failure remains retained separately from its corrected supplemental result.
  • Existing library, workspace/cgo, multi-binary materialization, immutable dependency capture and locked-Go regressions also pass.
  • The original stale proxy assertion remains visible separately from its corrected registry supplement; see the qualification record.

Embedded files on Windows

On Windows, a public single-module fixture embedding seed/hello.sql through //go:embed completed oyzu build --isolated --full with the provisioned Go image: the embedded-byte test passed, JUnit and Go coverage were collected, and the resulting Linux/amd64 binary printed the SQL text. The compiled CLI was built at 25939715; its Go preparation, builder and snapshot sources match origin/main at d5b77871, while its Windows Go ZIP bound differs. This confirms that captured preparation includes that input in this flow; other embed patterns and platforms have not been qualified by this fixture.

Direct oyzu exec -- gofmt uses the selected Go installation's bundled formatter after its layout has been admitted; see Go installation.

Native module artifacts​

Each library/workspace module produces three independently identified files:

ArtifactContents
module-<index>-<version>.zipNative Go module archive with the <module>@<version>/ prefix
module-<index>-<version>.modThe exact projected go.mod included in that archive
module-<index>-<version>.infoNative proxy version metadata; no invented release timestamp
  • Indices follow the captured, sorted module directory order. Manifest artifact names are module-<index>-zip, module-<index>-mod and module-<index>-info.
  • Each artifact records its native module snapshot version.
  • dist/dependencies/<target>.json records module paths/directories, filenames, versions and native h1: zip/go.mod checksums in oyzu.dev/go-module-artifacts, allowing later publication code to map files to registry identities. Publishing itself is not implemented by this increment.

Module versions​

Versions use shared version inference with a tag-derived base when available and the build's source-derived -dev.g... suffix.

  • Without applicable tags, the logical base is 0.0.0. Native module packaging maps that fallback to the module path's major where required, for example v2.0.0-dev.g... for /v2.
  • An explicitly inferred/tagged version must satisfy native module path rules: v3.0.0 for an unchanged /v2 module fails instead of silently changing the selected version.
  • These are snapshot prereleases, not Go VCS pseudo-versions or release authorization. Exact RC tags preserve their qualifier, for example v2.6.0-rc.2.dev.g....
  • Application binary filenames and manifest coordinates use their owning module's inferred version; Oyzu does not inject application version variables.

An upstream Conventional Commit can declare a breaking tool-minimum change without changing the Go module path. Under the default auto strategy that still infers a major bump, and native packaging refuses an incompatible module coordinate.

  • Projects whose released tags define their desired development line can explicitly select the existing tag strategy. That choice is recorded in configuration and version evidence; native path-major validation, tool selection and required build/report checks still apply.
  • The original Gin default refusal and separately configured proof are recorded in toolchain selection qualification.

Workspace version plans​

Go preparation captures module directory/path identities and native local import and test-import edges before version resolution. Each module receives its own transitive input scope and decision.

  • Directory-scoped tags such as math/v2.4.2 and api/v1.4.2 supply independent workspace baselines.
  • Root tags are admitted for a module at the Git root; a workspace root tag does not coordinate its children.
  • The root module's decision subject is the Oyzu target name; other subjects are their target-relative module directories.
  • Paths outside module directories are conservative shared inputs.
  • Custom namespaces and special major-directory layouts require further integration.

The host freezes a native-path-keyed version-plan.json; the native module adapter uses each selected version when creating zip/mod/info candidates and rewriting local requirements.

  • Captured dependency extensions retain oyzu.dev/go-module-versions and oyzu.dev/go-metadata.modulePaths, while ordinary version decisions retain baseline tags, commits and input scopes.
  • Native archive versions, including any path-major fallback mapping, are recorded in oyzu.dev/go-module-artifacts.
  • Dependency layout version 4 and the new version-plan argument require rebuilding the provisioned Go image and recreating older captures. Dependency-context-only preparation still requires neither the module adapter nor artifact version inference.

How archives are built​

The adapter uses Go's native module zip library for allowed files, nested-module/vendor exclusions, case collisions and archive limits. It uses native module/manifest APIs for identity and projection, and native dirhash for checksums. It does not reimplement zip rules or infer source files from extensions.

  • Workspace dependencies are projected to their matching snapshot module versions.
  • Native package imports, including test imports, supply local dependency edges even when a workspace member has no explicit require entry yet.
  • Contained local replacements to a captured workspace module with the same module identity are removed from published go.mod files. The source manifests remain unchanged.
  • These files use the Go module proxy protocol; independent consumer checks provision them into a local file proxy and compile a separate project with a fresh module cache.

Module proxy diagnostics​

When the Go client cannot publish or consume an acquisition spool request, its local proxy returns HTTP 502 with a fixed category, for example module acquisition failed: BROKER_RESPONSE_BODY (broker HTTP 200).

  • The received broker status is retained for body-read/size failures; it describes the broker response, not a successful module download.
  • Diagnostics exclude raw filesystem/JSON errors, spool paths, credentials and redirect URLs.
CategoryMeaning and recovery
BROKER_REQUEST_IDRequest ID generation failed; inspect the worker's runtime availability.
BROKER_REQUEST_WRITE, BROKER_REQUEST_PUBLISHThe worker could not write/publish its request; inspect the engine-owned spool mount and permissions.
BROKER_RESPONSE_READ, BROKER_RESPONSE_METADATAThe worker could not read/decode response metadata; inspect broker delivery and the spool mount.
BROKER_RESPONSE_BODY, BROKER_RESPONSE_LIMITThe response body was unreadable or exceeded the existing 256 MiB client limit; inspect broker delivery or module size.
BROKER_TIMEOUTThe broker did not answer within the existing 55-second client wait; inspect host broker execution.

Upstream HTTP statuses and the broker's sanitized source/authorization failure messages continue to pass through unchanged. These categories do not identify an upstream root cause by themselves or change retries, deadlines, size limits, offline behavior or source authorization.

The opt-in contributor check is oyzu --toolset go-test exec -- node tooling/test-go-acquisition.mjs. It exercises the actual proxy handler/client against a local test spool with network access disabled. See contributor tool setup.

Verification and limits​

Action decomposition​

The #477 candidate retains separate native production/test package graphs, selected file/embed facts and native context during preparation.

  • Pure-Go application plans describe one native build per main package and one fresh go test -json -count=1 invocation per selected real package, with separate JUnit/statement-coverage reports. Synthetic test variants remain metadata.
  • Compiled Rust exports private binary outputs under the current module version after required checks.
  • Library and cgo paths retain their existing coarse flow.

This action decomposition is experimental.

  • Linux/amd64 with selected Go 1.27.2 passes the agreed incremental and finite native proof, including usable binary stdout, fresh/restored report attribution and a second absolute checkout using an explicit shared local result store.
  • The original full-group hook-authoring failure remains visible; its corrected qualified-hook and cgo supplemental checks pass.
  • Existing Go regressions also pass, including current-version module artifacts, workspace/cgo, digest-preserving multi-binary OCI assembly, immutable dependency capture and captured Go 1.23.12 selection/lock refusal.
  • The earlier Windows controller's unrelated-reuse failure remains unwaived; Linux results do not qualify every host or native mode.
  • See the bounded qualification record.

Pinned Go​

Pinned Go in the captured worker was verified on Windows 11 with Docker Desktop: with go = "1.23" locked (1.23.12) and the worker image carrying Go 1.24.13, a Go binary built for a linux/amd64 image embeds go1.23.12.

  • A second build reused the cached archive; a corrupted cached archive was re-downloaded and verified; a lock with a changed digest was refused.
  • Only linux/amd64 workers were exercised, and only the Go archive layout (go/ prefix, tar.gz) is admitted.
  • The Go module dependency context and native-path builds are unchanged.
  • Offline builds need the archive already cached (TOOL_OFFLINE otherwise).

Module packaging probes​

The checked-in library variant has no Oyzu configuration. The native probe is:

python tooling/test-go-modulezip.py --adapter <provisioned-modulezip> --go <provisioned-go>
python tooling/test-go-metadata.py --go <provisioned-go> --cli <compiled-oyzu>
  • The module probe checks single-module and workspace consumption, major-version identity, matching go.mod bytes, native checksums, repeatable bytes, unchanged inputs, projected implicit dependencies and invalid local replacement rejection.
  • Rust checks cover inferred/explicit library planning and artifact path admission.
  • CI additionally requires measured test/coverage evidence and snapshot artifacts from an actual captured library build, repeats it for byte identity, then verifies a real failed test blocks collection.

tooling/test-go-workspace-version-inference.py --cli <compiled-cli> --evidence-dir <new-directory> creates scoped tags for a three-module workspace.

  • It exercises independent library archive versions and local requirements, two binaries owned by different modules, RC snapshots and a native major-path conflict.
  • The probe checks actual outputs, reports, bundle inspection and unchanged original source files.
  • It requires a provisioned gofmt (or --gofmt <path>) for fixture setup and the current Go build image.
  • Measured results are recorded in implementation status; registration alone does not prove acceptance.

Not supported or unfinished​

  • Registry replacements that require different publication semantics, local replacement modules outside the selected workspace, private/VCS routing, cross compilation and module publication remain unfinished.
  • Standalone direct test bundles are implemented for modules and contained workspaces; their host provenance is separate from captured-build evidence.
  • Unsupported replacement projection fails preparation rather than producing a module known to depend on an unreproducible local path.
  • Native source archives do not claim a compiled ABI or production provenance.
  • Full cgo/sysroot portability and all authored scenario acceptance remain part of the active goal; see implementation status.
  • Platform matrices can select matching provisioned Go toolchains through platform selection. Preparation verifies actual Go OS/architecture, and tests execute in each selected runtime. The authored Go-to-container matrix is now required by Linux CI; its new ARM execution result is pending. General cross-compilation, ABI admission and all EX-027 cases are not established by this selection capability.
