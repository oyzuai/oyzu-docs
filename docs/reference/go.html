Go applications, libraries and workspaces

CLI reference

Published from the canonical docs/reference/go.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Oyzu builds Go modules and go.work workspaces without any Oyzu configuration. It finds go.mod and go.work, runs the native go tooling, and collects binaries, module archives, test reports and coverage into a build bundle. Use this page to see what the Go builder runs, how it picks the Go version and what it produces.

Note: The Go builder is experimental. Captured builds run in a Linux amd64 container (Docker required) and work from Linux and Windows hosts. macOS is not supported yet. The builder is supplied by the oyzu-plugin-go plugin; see plugin catalog.

Quick start​

oyzu run list
oyzu run test
oyzu run lint
oyzu run format-check
oyzu build --plan
oyzu build
oyzu inspect dist
  • oyzu run <task> runs a development task on your machine with your provisioned go and gofmt.
  • oyzu build plans and builds the module in a Docker container (see Toolchain image).
  • oyzu inspect dist checks the resulting bundle.

What gets discovered​

  • A go.work workspace owns the modules it declares.
  • Listing tasks (oyzu run list) does not run Go.
  • A project with no main package produces module artifacts instead of failing as an unsupported library.
  • uses: go/library selects module packaging even when the project has commands.
  • go/app and go/library are the two Go builds. Oyzu reads the module and package facts from Go, picks the tools and versions, and runs the build, test and archive steps.

Usage and toolchain​

Development tasks​

Development tasks use your provisioned go and gofmt. The implicit tasks install dependencies, compile, test, vet, format and check formatting.

  • oyzu run format changes your source. Builds use format-check, which fails when gofmt -l prints anything.
  • In a go.work workspace, the member modules supply the package patterns for the build, test and vet commands.
  • oyzu run test writes the test bundle described under Direct test evidence. Other development tasks don't produce a bundle.

Toolchain image​

Captured builds need Docker and the base execution image, which has no Go of its own. Go comes from oyzu.lock (see Pinned Go in isolated builds), and Oyzu mounts its engine and the Go plugin into each action.

  • Preparation compiles the module archive adapter with the locked Go, against the golang.org/x/mod copy that the Go distribution vendors for its own go command. No image carries the adapter, and building it downloads nothing.
  • Your own image (--image go=<image>) needs no adapter either. It must meet the bring-your-own requirements, and a locked Go takes the place of the image's own.

Docker projects can also ask for an offline Go module context. It exports only the captured module cache, so the consuming image doesn't need the module archive adapter.

Go version selection​

Oyzu runs Go with GOTOOLCHAIN=local, so Go never switches or downloads a toolchain itself. Oyzu picks the Go from your project files instead. Other ecosystems' exact pins are in native pin files.

The Go minimum is the newer of the go and toolchain lines in the build folder's go.work if there is one, otherwise in its go.mod. Go orders versions as 1.24 < 1.24rc1 < 1.24.0 < 1.24.5.

  • A toolchain line is always honored. A suffixed name is read as Go reads it (go1.24.3-bigcorp and go1.24.3+auto mean 1.24.3). toolchain default and toolchain local are ignored. Any other value that isn't a Go release name is refused with a remedy.
  • A go line from Go 1.21 on is a toolchain minimum. Before Go 1.21 it was a language level, so a line like go 1.16 only constrains the choice: with no toolchain line and no [tools] go, Oyzu uses the newest stable Go, and a configured value below the line fails resolution.
  • In a workspace, the go.work lines decide. A go.mod beside the go.work keeps its go line as a constraint, and its toolchain line is ignored, as Go ignores it. Modules in subfolders are not read, because Go itself refuses a workspace whose go line is older than a module's.
ProjectGo selected
toolchain go1.24.5 (or go 1.24.5), no [tools] goExactly 1.24.5
go 1.24 with no patch, or toolchain go1.25rc1The newest stable release of that line (1.24.x, 1.25.x). Oyzu only installs stable releases, so a line that has only a release candidate fails resolution.
[tools] go at or above the minimum, in any folderThat value (1.25, 1.24 for a 1.24.5 minimum, latest). The minimum still binds its resolution.
[tools] go below the minimum, in a folder above the module (the project root, or user configuration)The minimum. The farther value loses, and the Tools row shows overrides 1.23.4 from oyzu.toml.
[tools] go below the minimum, in the module's folder or below itRefused before any work with TOOL_NATIVE_MINIMUM_CONFLICT, naming both files.
A command-line, environment or policy value below the minimum (a toolset value is exempt)Refused with TOOL_NATIVE_MINIMUM_CONFLICT, naming its source and the native file. A policy value can't be changed in the project, so ask the policy owner or lower the minimum.

For example, take toolchain go1.24.5 in app/go.mod, a root [tools] go = "1.25" and [tools] go = "1.24.0" in app/oyzu.toml. oyzu build stops after loading the configuration with exit status 3:

✗ TOOL_NATIVE_MINIMUM_CONFLICT: hello: [tools] go = "1.24.0" in app/oyzu.toml is below the go minimum 1.24.5 that app/go.mod declares (toolchain line); set [tools] go to 1.24.5 or later in app/oyzu.toml, or remove it so the native file decides
  Next: Make the configured tool version reach the native minimum, or change the native file, then retry.

With only a root [tools] go = "1.23.4", the build uses the minimum and says so in the Tools block:

  ✓ Tools                   1 tool pinned · 0 installed now                 1.9s
      go          1.24.5   already installed  detected from go.mod · overrides 1.23.4 from oyzu.toml

How requests are compared:

  • Only plain releases and lines (1.23.4, 1.23) are compared with the minimum where they are written. Any other form, such as a range, is resolved against the minimum and fails when nothing satisfies it.
  • Tool policy (a tools.go lock or allowed set) applies to the selected version, whichever file requested it, the minimum included. When policy refuses the minimum itself, TOOL_NATIVE_MINIMUM_CONFLICT names the policy source.
  • In a workspace that builds in the isolated executor, the same refusal stops the build during preparation with exit status 3, and the code appears in the bundle's diagnostics.
  • oyzu config explain tools.go shows the configured value. The override appears only in the Tools block.

Locking:

  • The selection is locked in oyzu.lock like any request, with the minimum recorded as the constraint go-minimum:>=1.24.5.
  • Changing [tools] go needs oyzu pin before the next build, as for any explicit request.
  • So does a changed minimum. go get and go mod tidy rewrite the go and toolchain lines, and the next build stops and names the cause:
✗ TOOL_LOCK_STALE: oyzu:go 1.24.5; app/go.mod declares go 1.24.5 (toolchain line) but oyzu.lock pins 1.27.2; run oyzu pin
  • Run oyzu pin and commit oyzu.lock. An oyzu.lock written before Oyzu read the Go minimum holds the request * and needs the same step once.

Pinned Go in isolated builds​

A project that pins Go (for example [tools] go = "1.23", locked with oyzu install go@1.23) builds with that exact Go inside the container. During preparation Oyzu:

  1. Reads the Linux (linux/amd64/gnu) archive recorded for the pinned version in oyzu.lock.
  2. Downloads it through the tool broker, unless a copy in your user data directory still matches the locked SHA-256.
  3. Checks the bytes against the locked digest.
  4. Restores them read-only at /scratch/gotool.
  5. Puts that go first on PATH (and sets GOROOT) for preparation and every build action.
  • The plan records the archive digest, so a different pin or archive changes the action identity.
  • Without an explicit pin, the Go that preflight locked from the Go minimum is used the same way.
  • The base image has no Go, so a captured build there needs Go in oyzu.lock. Run oyzu pin. Only your own image can supply its own Go when the lock has none.
  • A lock with a changed digest is rejected, and a corrupted cached archive is replaced by a verified download.
  • Offline builds need the archive already cached, or they fail with TOOL_OFFLINE.

Direct test evidence​

oyzu run test runs the implicit go test ./... command with -json, a fresh -coverprofile and -count=1.

  • Go owns test discovery and compilation.
  • Oyzu converts Go's JSON events to JUnit and keeps the native coverage profile under dist/. The manifest records digests and summaries.
  • Coverage is statement coverage, not branch or line coverage.
  • A package with no tests gets an honest zero-test summary, and Go may succeed in that case.
  • Missing or malformed reports, and configured coverage thresholds, can still fail the run.

Workspaces and selectors​

  • For a go.work root, Oyzu uses the workspace's member packages and combines their test events and coverage. Members outside the task root fail.
  • Forward selectors with oyzu run test -- -run TestGreeting. Forwarded arguments go only to the task you asked for.
  • Go's cached test results are not reused, though Go may still reuse its compilation cache.

Hooks and custom commands​

  • Hooks get OYZU_TEST_REPORT and OYZU_COVERAGE_REPORT. The JUnit report is normalized before post_test runs and validated after it, so changes a hook makes are kept.
  • An invalid event stream stays a failure even if a hook later writes valid XML.
  • A failed test skips the success-only post hook and keeps the evidence it has.
  • Exact argv = ["go", "test", "./..."] and run = "go test ./..." overrides get the same treatment.
  • Other custom commands run unchanged and must write their own JUnit and Go coverage reports.
  • An explicit coverage declaration redirects the native profile. An explicit JUnit declaration switches to file-based reporting, so your task or hook must produce that XML. The default Go command emits JSON, not JUnit.
  • Declared paths must be fresh. See direct tests.

This workflow needs a provisioned Go compiler and your dependencies. It needs no Docker and no account.

  • It runs on your machine with your environment and network. For an offline run, use dependencies you already have and set GOPROXY=off, GOSUMDB=off and GOTOOLCHAIN=local.
  • It is not an isolated build and produces no application artifacts. Direct tests covers provenance, output handling and recovery.

Preparation and execution​

Go itself reports manifests, workspace members, main packages, dependencies and cgo use.

  • Captured inputs must contain local modules and replacement paths. Paths that escape the project, or are missing, fail.
  • Public modules are downloaded through Oyzu's scoped Go proxy and verified against go.sum. A redirect from the proxy to its storage bucket is followed (acquisition transport). Private modules and direct VCS downloads are not supported.
  • Oyzu records the compiler and ABI for cgo, and an environment override can't turn off required cgo support.

What preparation captures​

  • Preparation captures the dependency cache and the module artifact candidates. Library candidates come from captured source, before any build output exists.
  • Go works in a module cache on a container tmpfs (/scratch/gomodcache). The prepared store keeps only the download cache: module zips with their .mod, .info and .ziphash files.
  • Each build action serves that store to Go as a file:// module proxy and extracts what it needs into its own tmpfs cache. go.sum verifies every zip.

What a build action runs​

  • Compile, test, vet and the read-only formatting check run with networking denied and the prepared module cache.
  • Artifacts are collected only after the required checks pass.
  • Applications build one primary binary or named multiple binaries, with -trimpath and without ambient VCS stamping.
  • Libraries compile package patterns and produce no executable.
  • Go's test JSON becomes JUnit, and Go coverage keeps its statement denominator. Both go under dist/, with paths, digests and summaries in dist/manifest.json.
  • A failed test, vet, formatting check, missing report or compile error stops artifact collection. Your source is never changed. Read the task logs and reports, fix the problem and rebuild.

Each scratch tmpfs has a 2 GiB minimum size and grows with the action's memory reservation. Go build actions reserve at least 4 GiB, so /scratch/gotmp holds large compiler and linker intermediates. The 512 MiB /tmp mount is separate.

Separate build and test actions​

For an application with pure-Go code, Oyzu plans one build action per main package and one test action per package. Only the actions whose inputs changed run again.

  • Each test action gets the whole captured workspace and its own empty output and scratch directories. It can't see another action's reports or changes.
  • Package tests run go test -json -count=1 and produce a separate JUnit report and statement coverage report per package.
  • Binaries are written privately and exported with the module's current version in the file name after the required checks pass.
  • A conflicting task environment fails validation before any result is reused.

These targets run as one combined action instead: libraries, cgo, nested targets, native workers, targets with generated inputs, and configurations with any authored tasks or hooks. That keeps their command and hook order, including generated inputs and post-test report changes.

This path runs the engine that Oyzu mounts into the execution image. Without one, the build stops with ENGINE_ASSET_UNAVAILABLE.

Direct oyzu exec -- gofmt uses the formatter bundled with the selected Go (Go installation).

Native module artifacts​

Each library or workspace module produces three files:

ArtifactContents
module-<index>-<version>.zipThe Go module archive, with the <module>@<version>/ prefix
module-<index>-<version>.modThe exact go.mod included in that archive
module-<index>-<version>.infoGo proxy version metadata, with no invented release timestamp
  • The index follows the sorted order of module directories. Manifest artifact names are module-<index>-zip, module-<index>-mod and module-<index>-info.
  • dist/dependencies/<target>.json lists module paths and directories, file names, versions and the h1: zip and go.mod checksums, so other tools can map the files to registry identities. Oyzu does not publish the modules.

Module versions​

Versions come from version inference: a base from Git tags when there is one, plus the build's -dev.g... suffix from the source.

  • With no applicable tags the base is 0.0.0. Go packaging maps that to the module path's major where needed, for example v2.0.0-dev.g... for a /v2 module.
  • A version from a tag must satisfy Go's module path rules. v3.0.0 for an unchanged /v2 module fails instead of silently changing the version.
  • These are snapshot prereleases, not Go pseudo-versions, and they don't authorize a release. An exact RC tag keeps its qualifier, for example v2.6.0-rc.2.dev.g....
  • Binary file names and manifest coordinates use their module's inferred version. Oyzu doesn't inject version variables into your program.

A Conventional Commit that declares a breaking change in the tool minimum doesn't change the Go module path. Under the default auto strategy that still infers a major bump, and packaging refuses the mismatch. A project whose released tags define its development line can choose the tag strategy instead. Path-major checks, tool selection and the required build and report checks still apply.

Workspace versions​

Each module in a workspace gets its own version, based on the tags and changes that affect it.

  • Directory-scoped tags such as math/v2.4.2 and api/v1.4.2 give each module its own baseline.
  • A root tag applies only to a module at the Git root. It doesn't coordinate the other modules.
  • Files outside module directories count as shared inputs for every module.
  • Custom tag namespaces and special major-directory layouts aren't supported yet.

Oyzu freezes the versions in version-plan.json, uses them when it creates each zip, mod and info file, and rewrites local requirements to match. Recreate older captures after updating Oyzu.

How archives are built​

The archive tool uses Go's own module zip library for allowed files, nested-module and vendor exclusions, case collisions and size limits, and Go's dirhash for checksums. It doesn't apply its own zip rules.

  • Workspace dependencies point at the matching snapshot versions. Local imports, including test imports, supply the links between members even without a require entry.
  • A local replace to a workspace module is removed from the packaged go.mod. Your source go.mod is unchanged.
  • The files follow the Go module proxy protocol, so you can serve them from a local file proxy.

Module proxy diagnostics​

When the build container can't fetch a module, its local proxy answers HTTP 502 with a fixed category, for example module acquisition failed: BROKER_RESPONSE_BODY (broker HTTP 200). The HTTP status shown is the broker's reply, not a successful download. Messages never include file paths, JSON errors, credentials or redirect URLs.

CategoryMeaning and fix
BROKER_REQUEST_IDThe worker couldn't generate a request ID. Check the worker's runtime.
BROKER_REQUEST_WRITE, BROKER_REQUEST_PUBLISHThe worker couldn't write or publish its request. Check the spool mount and its permissions.
BROKER_RESPONSE_READ, BROKER_RESPONSE_METADATAThe worker couldn't read the broker's reply. Check the spool mount.
BROKER_RESPONSE_BODY, BROKER_RESPONSE_LIMITThe reply body was unreadable or larger than the 256 MiB limit. Check broker delivery or the module's size.
BROKER_TIMEOUTThe broker didn't answer within 55 seconds. Check the broker on the host.

Upstream HTTP errors and the broker's own source and authorization messages pass through unchanged.

Limits​

  • Linux amd64 is the supported captured platform. Arm builds and general cross compilation are not supported yet.
  • Not supported: private module sources and direct VCS downloads, replace directives that point outside the selected workspace, registry replacements that need different publishing rules, and module publishing.
  • An unsupported replace fails preparation instead of producing a module that depends on a local path.
  • Source archives claim no compiled ABI and no build provenance.
  • Full cgo and sysroot portability is not available.
  • A platform matrix can pick the matching Go toolchain for each platform (platform selection). Preparation checks the actual Go OS and architecture, and tests run in each selected runtime.
  • Pinned Go in the worker supports only linux/amd64 workers and the go/-prefixed tar.gz Go archive layout.
  • Embedded files (//go:embed) are captured with the source that Go reports for them.
