Shell activation

CLI reference

Published from the canonical docs/reference/shell-activation.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Shell activation puts a project's tools and [env] settings into your terminal as you cd into it, and puts your environment back when you leave. Use it for everyday work in an interactive shell. For a single command, use oyzu exec; to see what would be applied, use oyzu env.

Supported shells: Bash and Zsh on Linux and macOS, and PowerShell 7.5 or newer on Windows.

Quick start​

Bash or Zsh:

eval "$(oyzu activate bash)" # or: oyzu activate zsh
cd ./project-a
cd ../project-b
oyzu deactivate

PowerShell:

oyzu activate pwsh | Out-String | Invoke-Expression
Set-Location ./project-a
Set-Location ../project-b
oyzu deactivate

Entering a project applies its environment and tools. Moving to another project or leaving restores what you had before. The first time, a project's [env] values may be skipped until you trust the folder.

To set up every supported shell and keep oyzu and the shims on the persistent PATH, run oyzu shell install (the install scripts do); for one shell, run oyzu shell install SHELL --rc-file PATH. See installing activation in a shell profile.

Declare [env] values​

A project that only sets environment variables needs no tools, lock file, install or account.

[env]
APP_MODE = "development"
_.path = ["./bin", "./node_modules/.bin"]

_.path adds directories to the front of PATH, in order. To add some to the end as well:

[env]
_.path = { prepend = ["./bin"], append = ["./scripts"] }

Shell activation, oyzu exec and shims apply these values once the folder is trusted. oyzu run and oyzu build always apply them.

Rules for values and paths​

  • env._ is reserved for settings like _.path. It's never exported as a variable.
  • Values are literal. There's no variable expansion, scripts, .env loading or command substitution.
  • Setting env.PATH directly is an error. Use _.path.
  • Relative paths are relative to the file that declares them (including local and profile files), not to your current folder. Use "." for the declaring folder.
  • Directories don't have to exist. Empty entries, NUL, control characters and an embedded PATH separator are errors.

Precedence and PATH order​

  • Normal configuration precedence applies.
  • The winning _.path replaces any inherited one entirely. [] clears project additions.
  • The final PATH order is: tool shims, project prepends, your existing PATH, then project appends.
  • Directories already on your PATH stay where they are.

Project root and tool store​

  • Inside Git, the project root is the repository root unless you pass --root. Outside Git, it's the outermost folder with Oyzu configuration. Nested files affect only their own subtree.
  • Installed tools live in the shared user store, not in the project.
  • oyzu activate --store <dir> uses a different store. A relative path is resolved from where you run the command. Use the same store for install and activate.

Selecting the store for tasks​

oyzu run <task> --store <path> runs a task with tools from that store.

  • The path is resolved from where you run the command, and applies to the whole task, including hooks and prerequisites.
  • Missing tools aren't installed and there's no fallback to another store.
  • oyzu run list --store <path> only lists tasks; it doesn't open or create the store.
  • Put task arguments after --. A --store after -- goes to the task.

Activate and unload​

  • You can activate outside any project.
  • Starting PowerShell in an unconfigured directory such as Windows System32 keeps activation ready for the next directory change. Unrelated files there are not stored in the shell session's input inventory.
  • Changing folder applies the new environment before your next command. Edits to configuration are picked up at the next prompt. Run _oyzu_hook to refresh by hand.
  • Hooks never install tools, run tasks or use the network.
  • Tools in [tools] must already be installed and locked.
  • Each terminal keeps its own state. A nested shell can activate and change projects without affecting its parent.
  • oyzu deactivate restores the environment the shell started with.
  • Ordinary oyzu commands in an activated shell run the first oyzu on PATH (so a project-local build of oyzu takes over). Activation hooks keep using the oyzu that activated the shell.
  • For activation fixes, update the installed CLI named by the shell profile and start a new shell or reactivate. Rebuilding only a project-local CLI does not replace the frontend already running its hooks.
  • Bash has no native folder-change hook, so Bash activation defines cd, pushd and popd functions that call the builtin with the same arguments. A failed change returns the builtin's status and runs no hooks. After a successful change, a defined chpwd function runs first, then each defined function named in the chpwd_functions array, in order, stopping at the first failing hook; the change still succeeds. Oyzu adds its own _oyzu_hook_chpwd entry, keeps entries other tools registered and works under set -u; oyzu deactivate removes only Oyzu's entry. Activation replaces a cd, pushd or popd function of your own. Zsh uses its native chpwd hook. PowerShell 7 uses its native location-changed event. Windows PowerShell 5.1 has no such event, so there the new environment is applied at the next prompt: cd .\project; node -v typed on one line still runs with the previous folder's variables.

Removing the profile block affects new shells only. Run oyzu deactivate in the current one.

Restoration and errors​

Switching and restoring​

  • Switching projects first undoes the previous project's changes.
  • A variable is restored only if it still has the value Oyzu set. If you edited or unset it, your change is kept.
  • A new project's value can override your edit temporarily; your edit comes back when you leave.
  • An empty variable and an unset one are treated as different.
  • PATH restoration keeps directories you added and removes the ones Oyzu added, even if they were reordered. If a duplicate makes that ambiguous, the entry is kept and you get a message.

To unset a variable inside a project:

[overrides]
remove = ["env.APP_MODE"]

It's restored when you leave, unless you changed it.

Errors​

  • If configuration is invalid or a required tool isn't available, the previous project's changes are undone and OYZU_TOOL_STATUS is set to unavailable. Nothing from the failing project is half-applied. Fix the configuration or install the tools; the next prompt tries again. A working environment sets ready.
  • Managed environment values and secret references aren't supported and fail with an error.
  • Hooks never sign in or refresh credentials.

Trust a project folder​

Environment variables can make shells, loaders and interpreters run code, so Oyzu won't apply a checkout's [env] and _.path in your shell until you say you trust it. Review the settings, then:

CommandEffect
oyzu trust [path]Trust the project root (the current project if no path).
oyzu trust --revoke [path]Remove the trust record.
oyzu trust --listList trusted folders.

All forms support --json. Trust is tied to the folder's real path (symlinks resolved) and survives edits to oyzu.toml. It never writes into the checkout or contacts a service. Records live under trusted-projects in the user state directory.

What an untrusted folder does​

  • Tools still work. Only project and local [env], _.path and their removals are skipped. Your user-level environment values still apply.
  • Prompt hooks, shims, exec and oyzu env --shell follow the same rule.
  • A short hint about oyzu trust is printed once per command, or once per activated shell.
  • oyzu run, oyzu build and build planning always apply project environment settings, trusted or not, so they match CI. oyzu config also shows them.

Changing the trust policy​

SettingWhereDefaultEffect
[trust] enabled = falseUser or administrator configurationtrueTurns the check off.
[trust] parents = ["/absolute/projects"]User or administrator configurationnoneTrusts every project under these folders (for example E:\\projects on Windows).
OYZU_PROJECT_TRUST=falseEnvironment, one commandTurns the check off.
OYZU_PROJECT_TRUST=trueEnvironment, one commandTurns the check on, overriding files.
CI (including CI=true)AutomaticTrusted. Platform executors count as CI.
  • Project and local files can't change these settings.
  • Local coding agents get no exemption.
  • --revoke removes only the explicit record. A parent rule, a disabled check or CI can still trust the folder.

Headless execution and inspection​

Inspecting with oyzu env​

oyzu env shows configuration sources, the resulting variables and the selected executables in separate tables. It doesn't change your shell.

  • Sources show which file and profile won for each value, including oyzu.local.toml and _.path.
  • PATH entries are listed in search order. Tool-provided variables and your existing PATH are included.
  • In an untrusted folder, project entries are marked skipped until trusted. The PATH shown is the configured one, not what activation has applied.

oyzu env --json lists the values and selected commands, with sources in the configuration array. projectEnvironmentSkipped says whether project values are being held back, and affected rows carry the same skipped until trusted status.

Redaction​

  • Ordinary values are shown in human and JSON output.
  • Values with credential-like names (token, secret, password, API key, auth, private key) are redacted, as are values that look like credentials.
  • This is a best-effort guess. Don't put secrets in innocently named variables.

Running commands and one-shot changes​

  • oyzu exec -- program runs a command with the trust-filtered environment, including unsets, without changing your shell. A bare command name must be a declared tool; use an absolute path for anything else.
  • oyzu env --shell SHELL prints one-time changes with no hooks. Use activate if you want them undone when you leave.
  • _.path isn't passed to tasks as a variable and isn't a build input.

Windows notes​

  • Directories Oyzu adds to PATH use normal drive or UNC paths, without \\?\ prefixes. Your existing entries keep their original spelling.
  • Windows PowerShell 5.1 activates and switches environments when you change folder, applying the change at the next prompt rather than mid-line. Keeping empty variables needs PowerShell 7.5 or newer.

Limits and status​

  • Supported shells are Bash, Zsh and PowerShell 7.5+. PowerShell before 7.5 can't keep empty environment values (Microsoft documentation).
  • Other shells, managed values and secret references aren't supported.
