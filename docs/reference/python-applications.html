Python application artifacts

CLI reference

Published from the canonical docs/reference/python-applications.md file. Features marked experimental remain experimental; check support limitations before relying on them.

A python/app target with static PEP 621 metadata and one console script produces a runnable, versioned .pyz application next to the usual wheel and source distribution. Use it to ship a Python service or tool as a single archive built from tested inputs.

The application holds the built wheel's files and the runtime dependencies. It doesn't copy other files from your checkout.

Note: Python applications are experimental. Isolated builds run in Linux containers, so they need the base execution image and either Docker or, for pip projects, the daemonless sandbox on a Linux host without an engine. See Compiled builder and provisioned images.

Quick start​

Declare the target in build.yaml:

builds:
  api:
    uses: python/app

Your pyproject.toml says what to build:

[project]
name = "example-api"
version = "0.1.0"
dependencies = []

[project.scripts]
example-api = "api:main"

[build-system]
requires = ["setuptools==80.9.0"]
build-backend = "setuptools.build_meta"

[tool.setuptools]
packages = ["api"]

Build, inspect and run it:

oyzu run list
oyzu build
oyzu inspect dist
python <application-path-from-manifest>

api.main is an ordinary console function. Oyzu doesn't add a server, port, health check or supervisor. Read the application artifact's path from dist/manifest.json.

Outputs and versions​

ArtifactNameNotes
application<target>-<version>.pyzThe runnable archive. The version is the package's PEP 440 build version, such as 0.1.0.dev0+g0123456789ab
wheelNative wheelA separate artifact
sdistNative source distributionA separate artifact

Select artifacts by name, not by position: an application build produces more than two files.

Version inference combines your metadata with exact tags, the nearest release tag and Conventional Commits. A v1.4.2 baseline plus a feature commit can give 1.5.0.dev0+g... for all three artifacts without editing your checkout. A local build or tag doesn't authorize a release.

Applications with only a requirements.txt use SemVer versions such as 0.0.0-dev.g<source>, and no distribution metadata is invented.

Entrypoints​

  • With several console scripts, or none, planning fails with a message. There is no setting yet to choose one.
  • Auto-detected python/package projects may have several console scripts.
  • A requirements-only application runs app.py or __main__.py.

How the build works​

  1. Oyzu prepares the dependencies (Python dependency preparation).
  2. It runs your native build backend once.
  3. It assembles the application.
  4. It tests the sources extracted from that archive.
  5. It runs the lint and read-only format checks.

Reports go to dist/ with their paths, digests and summaries in the manifest. See Python testing for overrides, empty suites and coverage thresholds.

Direct tasks (oyzu run) run your native commands. They don't assemble archives or collect build reports.

Assembly and archive checks​

Assembly:

  • checks the wheel's name and console entry point against the plan
  • installs the runtime wheels only (offline, without resolving dependencies) with pip. Build and test tools stay out
  • removes installer-specific provenance and launchers tied to one interpreter
  • generates a launcher from the package's entry point metadata
  • records the source, version, project files, runtime packages, entry point and original wheel digest in oyzu-application.json inside the archive

The archive has sorted paths and normalized ZIP metadata. Oyzu refuses unsafe paths, case collisions, symlinks and oversized payloads. Packaging confirms the archive is the one that was tested and that the wheel and sdist didn't change.

If tests, quality checks or reports fail, or an artifact changed, the artifacts aren't collected. Read the logs and reports in dist/. These checks guard the build and are not a security boundary against malicious tests.

Platforms and limits​

  • Native pip builds run on your machine and make a wheel only. Oyzu can install CPython for them from requires-python or .python-version (Python installation). See native local builds.
  • The .pyz application comes from isolated builds, which also handle requirements-only, uv, Poetry and legacy projects. They use Linux containers through Docker with Python 3.12 and pip, uv or Poetry. CPython comes from oyzu.lock, so installing CPython on your machine doesn't replace it.
  • Isolated builds download dependencies during preparation. After that, assembly and tests run with the network off. If an input is missing, fix it during preparation. There is no network fallback in the build.
  • The archive needs pure Python wheels and ZIP-compatible code and data. Native extensions, .pth startup files and libraries that need real files fail with an error. Test the app to check how it loads resources.
  • Python is not bundled. Running the .pyz needs a compatible interpreter.
  • Legacy setup.py applications, dynamic console metadata, editable installs, entry point overrides and native application layouts are not supported.

To put the archive in an OCI image, see Python application containers.

Compiled builder and provisioned images​

Isolated builds run on the base execution image. Oyzu mounts its engine and the Python plugin into each action, so no image carries an Oyzu worker and none needs rebuilding when the CLI changes.

  • CPython comes from oyzu.lock and is restored into each action. The base image has no Python.
  • uv and Poetry aren't restored from the lock yet. For those builds, pass an image that provides the manager: --image uv=<ref> or --image poetry=<ref>.
  • An image you pass must meet the bring-your-own requirements. A locked CPython still takes the place of the image's own.

The oyzu CLI itself doesn't need Python. Builds run Oyzu's own steps in compiled code. Small embedded Python helpers run inside the selected Python only to call the packaging, Poetry export, setuptools, pytest, coverage and quality-tool APIs. Ruff runs as a native program.

The container that runs your finished application uses a plain python:3.12-slim-bookworm and doesn't need the Oyzu engine.
