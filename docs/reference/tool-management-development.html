Core tool-management development integration

CLI reference

Published from the canonical docs/reference/tool-management-development.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Node, Go and Rust installation use Oyzu configuration, internal tool mechanics, version-1 locks and the shared installation store. The mise application and fork are not runtime dependencies. Adapted code retains its upstream notices. This remains development functionality, not a distribution-qualified release.

All archive providers now share indexed pin/install governance, including npm, pnpm and Yarn. Native host support includes Linux ARM64 GNU alongside Linux amd64 GNU, macOS arm64 and Windows amd64 MSVC. Node ARM64 archives use the vendor's linux-arm64 spelling. Historical proofs below do not establish native ARM64 qualification. See implementation status for current verification. See provider coverage, indexed Rust and pin declarations.

Build with Rust 1.95 or newer using cargo build --locked --bins. A private Oyzu worker installs Rust from frozen inputs; Node and Go use internal metadata and archive mechanics through the acquisition broker. No separate mise executable is used.

The provider contract now has an Oyzu-owned identity. Unreleased locks from the retired adapter must be regenerated with oyzu pin --refresh, followed by oyzu install. There is no legacy compatibility reader or receipt relabeling; existing payloads are retained. See provider identity.

Native npm dependency boundary​

Pin output separates managed tool requirements from executor prerequisites. Inventory JSON includes category (managed-tool, executor-prerequisite or constraint); category does not claim provider support or installed availability. Pinning records managed resolutions, not observed machine paths or SDK inventory. Installation remains limited to admitted tool providers and never installs OS components. Native project dependencies retain their native manifest/lock owner. See native build readiness and the design boundary.

Native npm execution uses the selected Node installation's bundled npm/npx through Oyzu's verified execution environment. No aube installer or mise application is embedded. Native npm retains its own registry, authentication and cache semantics; Oyzu controls prerequisite selection, execution and evidence.

Bundled commands need no separate tool declaration. Explicit npm/pnpm/Yarn releases use their own providers; selecting npm overrides Node's bundled copy. Python similarly exposes its interpreter aliases and bundled pip through the selected Python, including Windows module-only layouts. Developer commands use the shared composed-PATH lookup, including host commands; controlled builds retain their separate admission rules. Mise's aube-dependent Node workspace task provider is omitted; Oyzu owns its own task discovery and execution.

First user flow​

The shared-store/portable-lock realignment is in progress. Resolution records now contain request facts and recipe roots without scope/profile labels. Rust lookup uses version, execution platform and required components and selects the smallest pinned recipe that contains them; incomparable matching recipes fail with TOOL_LOCK_AMBIGUOUS. A cross target's request includes its target-platform standard library. Configuration continues to own profile and directory precedence. Installation records are also keyed by effective requests, and store leases consume an exact selection digest rather than a directory or profile. Schema version remains 1. Earlier development records containing scope/profile or the obsolete requirements inventory are rejected by the strict decoder rather than silently reused. Regenerate these unreleased locks with the current CLI; retain existing payloads until reuse is verified.

User-origin requirements use the lock beside the user configuration file; project-origin requirements use the project lock. An arbitrary invocation directory does not acquire a lock for user defaults. A project overriding one tool retains unrelated user defaults. Configuration chooses the owner before lock matching; owner labels and paths are not persisted in portable records. OYZU_USER_CONFIG can select an absolute user configuration file without changing machine policy locations; see the configuration reference.

Inspect installed and selected tools​

oyzu tools list
oyzu tools current
oyzu tools current --details
oyzu tools current --json
oyzu which node

tools list reads installation receipts in the selected store independently of project configuration. tools current resolves effective configuration and its locks, showing selected versions, missing installations, configuration provenance and component purposes. Both support --details for full locations, identities and cross-compilation targets, --store, and the global --json flag. Inspection does not install tools, update locks or acquire over the network. A nonexistent store remains nonexistent. Human output uses a concise aligned summary with configuration filenames; --details includes full paths. JSON always retains the complete structured records.

These inventory commands report stored metadata, not freshly verified payload integrity. which and execution use verified installation selections and can therefore reject an installation whose receipt was visible in inventory. A missing lock is reported as stale lock; stale, ambiguous or incompatible locked selections fail rather than selecting an unrelated installed version. Install the declared selection explicitly to resolve missing payloads. Declaring, updating and removing tools and browsing versions are covered by tool commands, which also defines the current status words (ok, not installed, blocked, deprecated, stale lock, ambiguous); pruning remains separate follow-up work.

Successful installation output reports installed or reused for each selected tool, its version and Rust components. Reuse still verifies the selected payload; these result labels do not change lock selection or acquisition. Errors retain their failure exit status and do not produce a successful installation summary. Native installer diagnostics use the shared invocation logger on stderr, including structured records under --json; stdout remains the command result. Use oyzu build --store <path> when building with a store selected by oyzu install --store <path>. Omitting the override always selects the shared user store, not a store remembered from an earlier command. See local builds.

Install and execute​

Create oyzu.toml at the workspace root:

[tools]
node = "22.15.0"

[env]
APP_MODE = "development"

Then run the Oyzu binary:

oyzu install
oyzu install --frozen
oyzu install --frozen --offline
oyzu which node
oyzu env --json
oyzu exec -- node --version
oyzu exec -- node -e 'console.log(process.env.APP_MODE)'

The shell quoting in the last example is suitable for Bash and PowerShell. -C DIRECTORY, explicit root and profile selection use the existing configuration resolver. Installation supports Node, Go and Rust selections at the workspace root. The Node selector is interpreted by the extracted metadata library against the actual Node catalog. Existing locks retain the exact version unless an update is explicitly requested.

If a maintained adapter changes an installation layout (for example, adding the bundled npm entrypoint to Node), ordinary or frozen reuse reports TOOL_LAYOUT_STALE. Run oyzu install --update node to explicitly rebuild the selected layout from verified archive inputs. This uses the normal online update contract: version constraints still apply and metadata refresh requires access. Repinning alone does not replace an existing installation. The replacement is staged and verified before publication; the older installation and its receipt remain intact, including for existing leases. Subsequent selection prefers the currently admitted layout and still verifies its payload. Updating a different tool does not authorize changing Node's layout. Duplicate equally eligible receipts remain an ambiguity error. No schema migration or receipt relabeling is performed.

Tool names are resolved locally from the admitted adapter definitions, with upstream alias provenance retained in the extracted registry. Name resolution does not start a backend worker, inspect an installation or access the network. Version/catalog resolution and acquisition still use their existing backend and verification contracts. For the currently admitted backends, node and "oyzu:node" identify the same tool, as do go and "oyzu:go", and rust and "oyzu:rust". Oyzu's own providers were named core:<name> before 2026-10-10; core:node is still accepted as an input alias for oyzu:node (in configuration, commands and route scopes), but the lock and every report use oyzu: ids. Registry packages follow the same rule; see tool ids. Quote canonical TOML keys containing a colon. Changing only between these names preserves the normalized request identity and existing lock; it does not require installation or relocking. Defining both names for one tool fails with TOOL_ALIAS_AMBIGUOUS, even if their versions agree. Unknown registry names fail with TOOL_ALIAS_UNSUPPORTED. This does not enable additional backends or make alias names executable commands: use node, go, cargo, rustc or rustdoc for exec. Selective updates accept the same registry names. Administrative tools.allowed values are compared through that same alias map; this setting remains admin-only. The real acceptance runner is python tooling/test-tool-aliases.py --cli PATH --workspace NODE_ACCEPTANCE_PATH; it reuses the two-version Node workspace above without changing its projects. Add --update for online canonical-name resolution. On a disposable root Linux host only, --disposable-linux-host temporarily creates an administrative policy to check both allowed-name spellings and denial; it refuses an existing policy and removes its own file afterwards. Linux offline replay with networking disabled and the separate online update passed on 2026-10-02. Native CI remains pending.

After editing the Node requirement in TOML, run:

oyzu install --update node
oyzu exec -- node --version

For a Node-only project, bare --update and --update oyzu:node select the same root. The command resolves through the Oyzu provider, prints the previous and proposed exact version, installs the result and then commits the lock using the existing compare-and-swap transaction. It never edits TOML. Ordinary install rejects changed requirements with TOOL_LOCK_STALE and an update remedy. --update conflicts with --frozen and --offline; unsupported tool names fail. A failed update leaves the previous lock intact. An unchanged resolution preserves lock bytes.

A newly configured Node/Go project can reuse an exact installation even before it has its own installation lock. After backend version resolution, installation looks up the matching user-store receipt before downloading an archive to learn its size. It validates the layout and verifies the payload through the same publication/lease contract, then writes the project's portable lock. Version resolution can still require catalog metadata; this is distinct from downloading or extracting the tool again. Offline/frozen installation still requires pins.

Updates operate on effective requests grouped by their configuration-owned lock. Replacing a request set preserves other request sets and platform distributions; conflicting acquisition facts for the same exact identity/platform fail rather than being overwritten. Other projects sharing the store keep their own locks and versions. Publication is atomic per lock owner, not across user and project locks together. Installation prepares the current host selection; it does not materialize every platform recorded in a portable lock.

The default store is user-level: %LOCALAPPDATA%/Oyzu/tools on Windows, ~/Library/Application Support/Oyzu/tools on macOS, and ${XDG_DATA_HOME:-~/.local/share}/oyzu/tools on Linux (relative XDG values use the home fallback). On Windows, an absolute HOME different from the native profile selects <HOME>/AppData/Local/Oyzu/tools; unset HOME or use the normal profile to retain the native LocalAppData location. All default consumers resolve this location independently of the project directory. Explicit --store PATH overrides remain available for install, which, exec and environment commands; relative overrides resolve from the invocation directory. Use --store .oyzu/tools explicitly to inspect/reuse a previous project-local store. Existing contents are not automatically moved or deleted. Store routing is implemented; complete context-independent lock matching, automatic existing-content reuse and user-global selection remain under the active implementation brief.

Installation requests metadata and the archive through Oyzu's existing HTTP host fetcher, using https://nodejs.org/dist/ unless an administrative connector route applies (see below). It checks the archive against Node's declared SHA-256, derives the layout from the extracted metadata library, stages and publishes the installation, then commits the lock through the existing lock-edit transaction. The lock explicitly records digest-only verification; it does not claim a verified publisher signature. An existing incompatible lock fails rather than being silently replaced. A failed installation does not publish a new lock.

install --frozen requires an existing compatible lock and never resolves a new version. Both ordinary and frozen installs reuse an already installed selection after verifying its receipt and contents; this path needs no network and leaves the lock unchanged. If the installation is absent, Oyzu first verifies the cached archive against the locked digest and size, then restores the installed tree. Only a missing archive requires acquisition from the selected route; invalid cached content fails instead of silently downloading a replacement.

install --offline forbids metadata and artifact networking. It requires an existing compatible lock and either a verified installation or its cached archive. Combine it with --frozen to explicitly prohibit lock edits. Missing locks or archives fail with an online-install remedy. Run ordinary install online to create the initial lock and acquire the required bytes.

which node prints the selected receipt entrypoint. Trusted PATH overrides can choose another program during exec. Inspection shares read-only developer selection and verified installation lookup, makes no network request and does not install or launch anything. A missing installation fails instead of returning a system PATH executable. Without a compatible pin, inspection can reuse matching recorded installations; it never creates a lock.

Developer exec composes configured tools with ordinary executable lookup on PATH. Missing configured tools install on invocation by default through Oyzu's existing acquisition, lock and receipt machinery. Compatible locked versions are retained; a new configured selection may publish oyzu.lock. This behavior is separate from controlled build admission: system PATH cannot satisfy a locked build requirement. See invocation controls. The selected installation leases remain held during native execution. Arguments, streams, cwd and native exit status pass through; no shell expression is inferred.

exec also accepts an explicit absolute or relative executable path. It resolves relative paths against -C/the invocation directory and applies the same developer selection, configuration eligibility and environment. For example:

oyzu exec -- ./bin/development-runner "argument with spaces"
oyzu exec -- /usr/bin/python3 scripts/check.py

On Windows, use a full executable path such as oyzu exec -- C:\Python313\python.exe scripts\check.py. Drive-relative paths such as C:python.exe are rejected as ambiguous. A program started this way can find the selected Node at the front of PATH; the explicit program itself is a requested development command, not a verified locked tool. This is ordinary development execution, not the hermetic build executor. Invoke an interpreter explicitly for scripts that need one. No implicit shell parsing is added.

Bare commands use the composed PATH, including ordinary globally installed executables. Commands absent from PATH fail with COMMAND_NOT_FOUND. Explicit missing paths and directories fail lookup; invocation preparation may first install configured tools when automatic installation is enabled. which npm returns the bundled npm JavaScript entry point; exec npm and the npm shim launch it with the same verified Node interpreter. Managed execution and process-tree/signal supervision remain unfinished. Exercise the actual explicit-path flow against the retained two-project acceptance workspace with:

python tooling/test-tool-exec.py --cli PATH_TO_FEATURE_ENABLED_OYZU --workspace PATH

Linux amd64 passed this scenario with container networking disabled on 2026-10-02. Native Windows/macOS explicit-path execution acceptance remains pending in CI.

Host POSIX shells​

oyzu exec -- bash scripts/check.sh and oyzu exec -- sh scripts/check.sh use the same developer selection, composed PATH, tool environment and child-stream/exit contracts as other exec commands. Configured tools follow invocation install controls; Oyzu does not install the host shell or add implicit shell parsing. Linux/macOS resolve these shell names normally on PATH. Trusted project PATH prepends precede selected tool directories.

On Windows, bare bash/sh select a native shell in this order:

  1. bash.exe/sh.exe on the composed PATH, excluding %SystemRoot%\System32 and %LOCALAPPDATA%\Microsoft\WindowsApps WSL launchers/aliases.
  2. Git for Windows' bin\bash.exe/bin\sh.exe, derived from git.exe found on PATH under cmd, bin, mingw64\bin, mingw32\bin or usr\bin.
  3. Git\bin under %ProgramFiles% or %ProgramFiles(x86)%, then %LOCALAPPDATA%\Programs\Git\bin.

If no native shell is found, the error describes the search and requires Git for Windows' shell. Make an existing Git installation discoverable or supply its explicit executable path. No WSL fallback occurs. Explicit paths still select exactly the requested executable. The host shell itself is not a locked tool. Git Bash/MSYS converts ordinary Windows PATH entries to its POSIX form on startup; Oyzu continues exporting ordinary drive paths, not verbatim \\?\ paths or a manually rewritten POSIX PATH.

The same resolver serves host tasks, including shell-string tasks. tooling/test-tool-exec.py also checks bare bash/sh, argv tasks and shell-string tasks against the real pinned Node executable in its provisioned acceptance workspace. These additions still need desktop/CI execution on Windows, Linux and macOS; earlier explicit-path results do not establish this coverage.

Mixed projects and selective updates​

A project can request both tools in the same TOML file:

[tools]
node = "22.15.0"
go = "1.24.13"
oyzu install
oyzu which node
oyzu which go
oyzu exec -- node --version
oyzu exec -- go version
oyzu install --update node

Installation resolves the configured roots, prepares missing installations and publishes one version-1 lock only after the complete selection is available. Existing content-addressed installations can be reused across single-tool and mixed projects. Failure leaves the previous lock intact; acquired cache entries may remain for reuse.

--update node or --update oyzu:node resolves only Node and retains Go's exact record, version and artifact identity. The equivalent Go names preserve Node. Multiple update names select those roots; bare --update selects all configured roots. Adding a tool requires an update that includes it. Removing a tool from TOML requires bare --update. Changing an unselected request fails with TOOL_LOCK_STALE; include that tool in the update or restore its requirement. The command never edits TOML. Unchanged requests/records retain their existing text through the lock-edit contract.

For portable pins, updates refresh the selected tool's recipes for every platform already recorded for that request. Unselected recipes retain their identities; the host installation is verified before the candidate portable lock is committed. Exact requests and Node/Go ranges use the same provider selection rules as pinning. The candidate passes the same native-constraint and component validation as frozen execution; updates do not bypass that contract. Adding a tool resolves its recipes using the same platform defaults and tools.platforms selection as oyzu pin. Ambiguous prior requests still require explicit pinning. Removing a configured tool changes the active selection; it does not delete shared installations or portable pins that another selection may use.

Exec and shell activation acquire one verified lease for the complete selection. Both bin directories are prepended in deterministic configuration-key order, and each backend adds its environment. A Node process can therefore launch the selected Go, and vice versa. An incomplete or stale environment fails as a whole; execution does not silently use one valid tool while replacing another from ambient PATH. Shell selection identity includes every selected executable, so changing either locked tool causes the next hook to recompute the environment.

env --json now includes tools (canonical IDs to executables) and executables (command names to executables). The existing tool and executable fields remain for single-tool projects; mixed projects use the maps. Sensitive environment values remain protected; ordinary configured values are visible. which accepts either selected command and still returns its path.

The real runner installs both tools, changes only Node, verifies the complete Go record is unchanged, and runs Node with a Go child under the composed environment:

python tooling/test-tool-mixed.py --cli PATH_TO_FEATURE_ENABLED_OYZU --workspace PATH

Use --store PATH to reuse an existing shared store. Retain the workspace and repeat with --offline-check under externally disabled networking to verify frozen reuse and both tools without acquisition. Add --pin for portable pinning, multi-platform recipe refresh, exact/ranged Node updates and unchanged Go recipes. Add --add-tool with --pin to start with Node alone, add Go through a selected update, remove Go from configuration, and restore it using frozen offline reuse. Ambiguous scoped/profile selections still require explicit pinning. Add --shell bash, --shell zsh or --shell pwsh to exercise both commands through an activated shell. Linux frozen replay, Node-to-Go child execution, redacted inspection and mixed Bash activation passed with networking disabled on 2026-10-02. Windows mixed execution and Linux portable add/remove/update flows also passed during extraction on 2026-10-05; native macOS remains unverified.

Consolidated build requirements​

oyzu pin --dry-run and oyzu pin show one requirement row per kind, name and constraint across the selected matrix, with an affected-target count. Different constraints remain distinct. Rust components retain their formatting, linting and coverage purposes. Installation support describes the current host's capability, not proof that the tool is installed: pin does not check availability. Use oyzu tools current for that metadata observation.

The JSON inventory includes consolidated requirements with targets and sources, while retaining the original per-target facts. Native and isolated build diagnostics use the same summary, emitting a request only once even during replanning. This presentation consolidation does not merge lock identities, platform recipes, constraints or execution requirements. Unsupported discovery remains explicit. External linker/SDK prerequisites remain separately provisioned.

Human tables wrap long cells within columns at ordinary terminal widths; only very narrow terminals use labeled records. Pin platform coverage uses OS, architecture and ABI columns. A dry-run success does not mean tools were installed.

Pin shows the requested version separately from the tool name. It uses the resolver-selected request before lock metadata resolution, including configured requests and builder defaults. Components marked With Rust share the selected Rust toolchain; they are not independently pinned. Multiple target requests remain visible. JSON retains these requests by tool and target in requested_versions.

Large pinned Rust downloads​

Pinned Rust distribution inputs use 8 MiB HTTP range requests. Each request keeps the broker's 45-second deadline, source/redirect authorization and bounded retries; a progressing large download no longer has to fit into a single request deadline. The response ranges must be contiguous, match the requested offsets and lengths, and agree on the total size. The complete artifact must still match its locked SHA-256 before rustup can use it. The existing 256 MiB artifact and 1 GiB session byte limits include partial/failed transfer bytes as before.

A server that ignores ranges may return a complete first response, still subject to the ordinary request timeout and byte limit. A full response after partial segments, inconsistent ranges or digest mismatch fails closed. No alternate source or unpinned download is used. Errors identify the pinned Rust input name without including upstream URLs or credentials. Other acquisition paths retain their existing request behavior.

Experimental bundled npm launch​

With Node configured in oyzu.toml, a fresh oyzu install records both Node and its bundled npm in the verified installation. oyzu exec -- npm ci and bare npm ci in an oyzu activate shell use that installation. Persistent native shims produced by activation can also run without an active shell session; they resolve the current project on each invocation. No global npm is selected. oyzu which npm reports the JavaScript entry point, not a standalone Windows executable; use exec npm rather than attempting to execute that path directly.

npm's existing version is the one bundled with the selected Node release. There is no separate npm request or version pin for that bundled copy. An explicit npm selection can override it. Known bundled npx and Python/pip aliases are discovered inside an already leased installation, so accepted existing receipts and frozen locks do not need edits or reinstalling. This does not revive rejected legacy lock/receipt formats. which pip reports the backing Python interpreter; exec pip and the pip shim supply -m pip.

Ordinary environment configuration is passed to npm through existing execution and shell contracts. The local broker experiment sets proxy and CA variables without storing upstream tokens in npm configuration. This is a laboratory integration, not automatic platform connector discovery or authorization. Without the experimental session setting below, explicit native command-line settings can still override environment routing. No machine-wide network enforcement or prevention of deliberate bypass is claimed.

Publishing is supported only through oyzu publish. Developer sessions must use an upstream read-only identity and never receive a publish connector. The npm launcher is not itself a method filter or a security boundary against a user who owns the host. The publishing command's platform integration is outside this proof.

The Node/npm layout covers Windows and Unix distributions; measured results and OS qualification belong in the linked qualification record, not inferred support.

Experimental automatic npm session​

For the isolated local-agent experiment, configure this once in user configuration:

[npm]
sessionEndpoint = "http://127.0.0.1:43100/session"

This is an opt-in laboratory integration, not a working platform login workflow. The local agent must already be running and supply the experimental session contract. The compiled CLI has no developer login command; existing managed-mode enrollment safeguards remain unchanged. Remove the setting to return to standalone behavior.

npm.sessionEndpoint is absent by default and follows normal configuration precedence/constraints. It accepts numeric-loopback HTTP only, with no credentials, query or fragment. No project-specific proxy settings are required. After installing the requested Node into a fresh store, use oyzu exec -- npm ci or activate the shell and run npm ci. Each invocation resolves its current project and contacts the endpoint; shell activation itself remains offline.

User transport settings are intentionally excluded when Oyzu detects CI. This user-level setup therefore covers local developer sessions, including non-TTY shells, but does not configure CI jobs. CI needs an eligible job/administrative configuration source and its own authorized agent session; automatic CI bootstrap is not implemented by this experiment. An absent effective endpoint retains standalone behavior; it is not a managed fail-closed configuration.

The experiment supports command-first install, i, ci, run, run-script, view and session-approved audit. Help/version skip the agent. Other command spellings, flags before the command, and native npm publish are unsupported in this mode. Publishing requires oyzu publish, whose integration is not part of this experiment. These restrictions do not certify that arbitrary npm scripts cannot bypass Oyzu; developers still control their machines.

The child receives proxy, registry/scope, audit and public CA settings, never an upstream credential from this adapter. No .npmrc is generated. The installed npm resolves its effective configuration before execution; conflicting proxy, registry, bypass, audit or TLS overrides stop with NPM_ROUTING_CONFLICT. Remove the conflicting option/configuration and retry. Nonempty inherited NO_PROXY also conflicts. Approved environment values can legitimately supersede project settings through npm's normal precedence. Audit defaults to disabled because it submits dependency names; an unapproved explicit audit returns NPM_AUDIT_DENIED.

NPM_SESSION_UNAVAILABLE means the agent is absent, denies access or cannot prepare it. Start/restore the agent and retry; there is no direct network fallback, even for cached dependency commands. NPM_SESSION_INVALID identifies an invalid response or missing public CA file. NPM_CONFIG_UNAVAILABLE means native effective config could not be inspected. npm execution retains native exit status after preparation. Native caches and installed packages persist normally; child settings do not modify the parent shell. Working directory association is unverified local context. Nested npm lifecycle commands re-enter the shim and request their own session; frontend recursion markers end at the verified native tool handoff.

This proves neither hostile-host isolation nor production IPC authentication/TLS provisioning. Upstream ACLs must supply narrow read-only authority. The Linux merge regression covers managed installation, private retrieval and Bash with Node 22.15.0 using a loopback HTTP fixture. macOS, broader Linux transport coverage, other npm versions and real local-agent/account lifecycle need qualification. Measured outcomes and failed attempts are recorded in automatic-session qualification.

Installation progress​

oyzu install uses the shared linear progress display: a checking status per tool followed by a ready or failed marker. Interactive terminals update the active status and show bounded installer output beneath it; redirected output retains a start and completion line without repeating intermediate verification messages. --json retains structured diagnostics on stderr and a machine-readable result on stdout. -q suppresses progress. Verification is still performed before a tool is marked ready.

Inherited configured tools during pinning​

Pin/build requirement resolution includes explicit tools from each selected target’s resolved configuration, even when that target’s builder does not request them. For example, repository tools.rust remains a resolvable configured requirement inside a nested Node project. Builder requirements retain their components and native constraints; configured entries do not fabricate build stages. Unsupported tool adapters still fail explicitly. This does not supply missing versions for other tools or add native multi-target execution support.
