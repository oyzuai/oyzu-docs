Cascading configuration (experimental)

CLI reference

Published from the canonical docs/reference/configuration.md file. Features marked experimental remain experimental; check support limitations before relying on them.

The configuration engine implements the public OEP-0002 draft in Rust. Its CLI and wire formats remain experimental; implementation authorization does not change the proposal's maintainer-review status. See the acceptance contract and measured implementation status.

oyzu config show presents resolved status and profile first, followed by setting tables grouped by namespace and the computation digest. Keys retain their exact spelling; booleans use true/false and empty lists use []. Environment values and task bodies remain redacted under configuration inspection's contract; use oyzu env for environment inspection. --json retains the structured result. See the CLI style guide.

Local and CI execution context​

Oyzu captures caller environment hints once when opening the configuration session, before build workers set their own CI=true. Detection is offline and independent of terminals, hostnames, network access and operating system. This is unverified execution context, never runner authentication, authorization or release eligibility.

The following nonempty markers identify providers. Empty values and the trimmed, case-insensitive values false, 0, no, and off disable that individual marker.

TaskCluster requires both TASK_ID and RUN_ID to be nonempty (RUN_ID=0 is valid). Additionally, exact CI=woodpecker, CI_NAME=sourcehut, and CI_NAME=codeship identify those providers. Any enabled CI value selects CI behavior even when the provider is unknown. Multiple provider matches are retained in sorted order; CI=false disables only the generic hint, not an enabled vendor marker. With no matching signal the context is local. Unknown platforms without a recognized marker must supply the conventional CI=true; no detector can identify every future or privately hosted system without a signal. Generic variables such as BUILD_ID alone are deliberately insufficient.

config explain exposes executionContext with ci, sorted providers, and matched variable names in signals. Values and private runner URLs are not recorded. Build plans retain the same context in oyzu.dev/execution-context. The detector follows the environment-marker approach used by ci-info; its implementation is first-party and adds no dependency or copied vendor dataset.

Plain oyzu build defaults to artifact building and packaging locally. In CI it also admits the builder's available test, lint and format-check stages. Existing checks.required, a positive coverage minimum, and explicit task prerequisites remain effective locally. oyzu build --full enables all available quality gates regardless of context; it does not change context detection or profile selection. config explain includes the resolved fullBuild request (default false); build plans record fullRequested. The existing oyzu --profile ci build also requests full stages but selects the CI profile. CI needs no extra flags. A different profile or --no-profile does not turn off detected CI checks. See build context behavior.

Trusted environment and credential destinations​

Project trust controls are trust.enabled (boolean, default true) and trust.parents (absolute folder paths, default []). They and platform.url, platform.account, cache.remote, cache.ciRemote are rejected in project/local scope, including profile overlays. Set them in user/global, machine or administrative configuration. Supported invocation environment sources are OYZU_PROJECT_TRUST, OYZU_PLATFORM_URL, OYZU_PLATFORM_ACCOUNT, OYZU_CACHE_REMOTE and OYZU_CACHE_CI_REMOTE; each overrides ordinary files while remaining subject to administrative constraints. OYZU_PROJECT_TRUST accepts true/false, on/off, yes/no or 1/0. See folder trust for the environment application boundary and native user-state records.

Build inventory migration​

build.yaml now accepts a builds mapping with uses, path, platforms, depends_on, materialize, bindings and with per entry. depends_on is an ordering-only list of producer build names; it does not transfer artifacts. bindings remains discovery-only and fails captured-build admission. Configuration owns normalization and freezes all declared platforms; builders own validation of with. See the Rust build options for the implemented options and execution limits. This is a partial implementation of the proposed build model, not support for every future example. Tool requirements remain in TOML and lock identities remain in oyzu.lock. The previous flat inventory is retained for compatibility; do not mix it with a builds envelope.

Prerequisites and quick start​

Configuration commands default to human-readable output. Pass global --json for structured results and errors; see CLI output.

Use an Oyzu CLI built from this branch; these commands are not a promise about older releases. Standalone configuration inspection and editing require no platform account, Docker, native ecosystem toolchain or network service. The client has Windows, macOS and Linux implementations; platform qualification and measured checks are tracked in implementation status. Running tasks or builds additionally requires their explicitly provisioned native tools.

In an otherwise empty directory named config-demo, save this as oyzu.toml:

[build]
jobs = 2

[profile]
default = "dev"

[profiles.dev.build]
jobs = 3

[ui]
color = "never"

Run these commands from its parent directory. Expected values assume standalone operation with no administrative constraints, local overrides or OYZU_PROFILE selection:

oyzu --root config-demo config get build.jobs
oyzu --root config-demo --no-profile config get build.jobs
oyzu --root config-demo config validate --strict --all-profiles
oyzu --root config-demo --profile dev config set build.jobs 4 --project
oyzu --root config-demo config get build.jobs
oyzu --root config-demo --profile dev config unset build.jobs --project
oyzu --root config-demo config get build.jobs

The successive get results are 3, 2, 4, and 2. Validation reports success; with --json it returns valid: true. Removing the profile assignment exposes the base value; it does not restore the old value of 3. Set/unset return the destination path and updated key. No project task runs in this walkthrough.

Inspection and selection​

oyzu --root path/to/project config show --json
oyzu --root path/to/project config explain build.jobs --json
oyzu --root path/to/project config profiles
oyzu --root path/to/project config validate --strict --all-profiles
oyzu --root path/to/project --profile integration run test
oyzu --root path/to/project --no-profile run test

--root explicitly fixes both build and configuration roots. Otherwise the nearest ancestor build.yaml within the current Git worktree selects the build; configuration still inherits from the Git worktree root. Outside Git, the outermost ancestor with Oyzu configuration or a build declaration bounds inheritance, falling back to the invocation directory. With no build declaration, that boundary remains the conventional-discovery root. -C / --directory selects the invocation directory; --root alone also selects that directory.

Git boundaries require recognizable repository metadata: HEAD plus the common objects and refs directories. A .git file must contain a gitdir: <path> pointer to that metadata; linked worktrees use its commondir pointer for the common directories. Relative pointers are resolved from their declaring directory. An unborn repository and packed refs remain valid boundaries; no commit or loose branch ref is required. Empty .git directories, malformed pointers and missing metadata do not define a workspace. They are left intact. Recognition reads bounded local metadata without running Git, executing configuration or establishing repository integrity. Conservative nested repository/submodule exclusions during target traversal remain in effect.

Entering an independent nested example and running oyzu build --plan therefore selects the example without --root. Its oyzu.lock and build outputs belong to that selected root. Parent inventories are not merged, and automatic discovery skips nested build roots. An explicit parent target path remains authoritative. Configuration retains normal project/local precedence, relative paths retain their declaring-file origin, and machine/enterprise constraints remain enforced. A selected build root may declare its default profile; ordinary target subdirectories cannot. Explicit composition and shared-workspace lock ownership are not implemented.

Relative task cwd values are now relative to the TOML file that declares them. For a root-file override of api:test, use cwd = "api/checks" to select that directory. Multiple targets cannot own the same native build unit; use distinct project paths or distinct builders where appropriate.

Sources resolve in this order: built-ins, verified corporate defaults, protected local administrative defaults, machine configuration, user configuration, root-to-target oyzu.toml, eligible root-to-target oyzu.local.toml, and invocation compatibility inputs. Each source applies its base followed by the selected profile. Siblings receive separate snapshots. Arrays replace, tasks replace atomically, and [overrides].remove removes explicit environment/task entries. Environment removals also unset inherited variables during development task execution. A task environment can replace a global variable with the same spelling, but case aliases such as TOKEN and token are rejected across the combined environment on every host.

Known tool aliases share that same precedence. For example, project node = "22" overrides global "oyzu:node" = "latest"; a selected profile can override its base through either spelling. Inspection retains the spellings with their effective value and winning provenance. Lock ownership follows the winning source. Declaring multiple aliases for one tool in the same overlay remains ambiguous. Administrative constraints bind the selected value regardless of its spelling.

Profile selection uses explicit --profile or --no-profile, inherited task selection, OYZU_PROFILE, the eligible root/default selector, inferred CI's empty ci profile, then no profile. Names grant no authority. Inferred CI excludes user computation settings and local files; --local-overrides requests local files, subject to administrative restrictions. Excluded local files are not parsed.

config show, get, explain, profiles, and validate do not execute project tasks. If resolution is blocked, show and explain return an explicit unresolved status without effective values; validate remains the failing validation command. The credential-origin and trust-control scope ban is an exception: platform.url, platform.account, cache.remote, cache.ciRemote, trust.enabled and trust.parents in project/local sources are hard errors even for show and explain, in human and JSON output and in CI when that source is included. The error names the key, source and user/global or administrative remedy. Configuration inspection displays ordinary environment settings and path arrays; credential-like environment names and recognizable sensitive values remain redacted, as do task bodies. Discovery/task listing also redacts environment values. Explain includes source histories, byte spans, exclusions, constraint source IDs and the effective computation digest. Warnings carry severity, source byte spans when available, target scope, and a remedy without including the configured value. Unknown optional settings warn and stay inert; known invalid values, unsupported required capabilities, duplicate keys and unsupported schema majors fail. --strict rejects optional warnings. --all-profiles validates inactive capability requirements and profile outcomes.

Editing​

oyzu --root path/to/project config set build.jobs 8 --project
oyzu --root path/to/project config set checks.required '["tests"]' --json-value --local
oyzu --root path/to/project --profile dev config set ui.color never --global
oyzu --root path/to/project config unset build.jobs --project

Exactly one of --global (the user configuration file), --project, or --local is required. --directory can select a contained nested project scope. unset removes an assignment in that file and exposes inherited values; it does not create a removal tombstone. Ordinary edits remain available to repair invalid values even when resolution is blocked; they do not activate values or alter protected records. Edits preserve unrelated comments and unknown syntax, validate known types/scopes, and compare the original bytes before atomic replacement. Concurrent changes produce CONFIG_EDIT_CONFLICT. A small .oyzu-config-edit.lock coordinates Oyzu writers and is excluded from source snapshots.

Only an explicit --profile NAME directs an edit into that profile. An inferred/default profile does not change the write destination: an edit without --profile writes the base section. Scalar booleans and numbers are parsed by type; strings are literal. Use --json-value for arrays or objects. The array example above uses shell quoting supported by PowerShell and POSIX shells. Edits cannot repair malformed TOML syntax; correct that syntax in an editor first. They cannot modify administrative or enrollment records.

Commands and output contracts​

All config commands default to human-readable output. Add global --json for structured results and errors. The JSON schema is experimental.

CommandResult and important behavior
showEffective values, selected profile, digest, diagnostics and resolution status
get KEYOne effective value (a JSON value with --json); fails if the key has no effective value
explain [KEY]Resolution evidence, optionally narrowed to a key; includes origins and constraints
profilesAvailable profiles, selected profile and selection reason
validate [--strict] [--all-profiles]valid: true on success; nonzero exit on validation failure
statusStandalone/enrolled state and managed cache health; does not refresh over the network
refreshExplicit online policy acquisition; returns revision and offline deadline; requires protected enrollment
set / unsetChanges one ordinary file and reports its destination; does not establish that the edited value is effective

show, get and explain accept mutually exclusive --global, --project and --local flags. These inspect only the selected file: the user configuration, oyzu.toml in the selected directory, or oyzu.local.toml there, respectively. For example, oyzu config get build.jobs --global reads the user declaration; oyzu -C packages/api config show --project shows that directory's declarations. Without a scope flag, the merged effective configuration remains the default. Scoped reads do not inject defaults, inspect other sources, contact policy services or execute tasks. They preserve the normal inspection redaction. An explicit --profile NAME overlays only that profile from the selected file; automatic/default profile selection does not apply to file inspection. show/explain report the source, scope and whether the file exists, with empty values when absent; get fails when the key is not declared there. These are declarations, not a claim that execution policy allows the requested values.

TOML syntax failures identify file:line:column (one-based Unicode character coordinates) and the parser's reason, including during set/unset. Source snippets are omitted to keep configuration values out of diagnostics. Correct malformed syntax in an editor before retrying. Strict validation retains every warning's key, source, available line/column and byte span, message and remedy; human errors list them and JSON errors include a diagnostics array. Strict validation still fails instead of silently accepting the warnings.

Human explain groups exact setting keys with effective values and their last source. Multiple origins appear as an ordered resolution history; the last source does not imply it supplied every element of a merged value. Only nonempty policy restrictions, exclusions and diagnostics are expanded. With no restrictions it prints one policy summary rather than an empty entry for every setting. Source paths omit Windows extended-path prefixes for display. Ordinary environment paths and compiler settings remain visible. Sensitive values stay redacted. explain <key> narrows the view; --json retains the complete metadata, including byte spans, constraint source IDs, context signals and digest.

show and explain can exit successfully with status: "unresolved" and no effective values. status can likewise return an unhealthy managed state successfully. Automation must inspect these fields or use validate as its configuration gate. Execution errors are reported on stderr with a nonzero exit status. Inspection does not run tasks, but resolving an enrolled configuration can contact the policy endpoint and update its cache. Thus inspection is not necessarily network-free or free of persistent state changes.

Environment names use ASCII letters, digits and underscores, beginning with a letter or underscore; the OYZU_ prefix is reserved case-insensitively. Values are not expressions or interpolation programs. Inspection redaction does not make literal environment values a secret store: literals can participate in build inputs/evidence. Do not use a literal as a substitute for the deferred secret consumer.

Task records select either run (a shell command) or argv (an argument array), and accept shell, cwd, env, depends_on, inputs, outputs, cache, interactive and reports. cache = true with outputs makes an authored task cacheable by oyzu build (its inputs may only add paths inside its target); outputs on a hook lets the cache follow it; see authored tasks. Local oyzu run inherits stdin. Text-mode tasks recording a bundle tee stdout/stderr live and retain them in dist/logs; interactive = true instead preserves real output terminal descriptors, with no captured stdout/stderr logs. Tasks without a bundle inherit output directly. For PowerShell run scripts, interactive = true also omits -NonInteractive; it does not make captured builds interactive. JSON mode captures output while retaining stdin; see task streams and limits. Task env contains strings. Task execution also requires a discoverable native project. For example, with Node explicitly provisioned and a package.json containing {"name":"config-demo","version":"1.0.0"}, add this to oyzu.toml:

[tasks.hello]
argv = ["node", "-e", "console.log('hello')"]

oyzu --root path/to/project run hello executes that command. A higher-priority task record replaces the entire record rather than merging its fields. To remove inherited environment/task entries, use dotted key strings in a removal list:

Additional arguments after -- are appended to an argv task, including an argv that already contains -c or -Command (for example a Python expression). Tasks authored with run reject additional arguments; choose argv when a task needs parameters. This distinction follows the declared task form, not the spelling of arguments passed to the native executable.

[overrides]
remove = ["env.DEMO_MODE", "tasks.hello"]

Windows paths come from native known-folder APIs. Relative XDG paths warn and use the home fallback. The machine directory contains ordinary config.toml, protected admin-settings.json, and protected enrollment management.json. Project/local files are named oyzu.toml and oyzu.local.toml; keep personal local overrides out of version control. Oyzu does not auto-enroll the machine.

For persistent user data, including the tool store, an absolute Windows HOME that differs from the native profile selects <HOME>/AppData/Local/Oyzu. This lets disposable homes isolate tool caches and rollback records. With HOME unset or naming the normal profile, native LocalAppData redirection is preserved. A relative HOME fails with CONFIG_SCOPE; use an absolute path or unset it. This data override does not redirect the configuration and managed policy state locations in the table, or the separate action/image cache locations. Existing data is not moved or deleted when selecting another home.

OYZU_USER_CONFIG optionally selects an absolute user configuration file, useful for disposable environments and testing user defaults without modifying a real profile. Relative paths are rejected. The file retains user-level precedence and authority; this setting cannot redirect machine policy, enrollment or state. Its sibling oyzu.lock owns user-default tool pins. Unset the variable to return to the native user configuration location. Help/version do not read this setting.

Managed state includes signed policy entries under the user state directory and integrity pointers/high-water state in the native credential store. Ordinary configuration edits do not change that state. Source capture enforces size/complexity budgets, including a 1 MiB file limit, and detects concurrent source changes rather than mixing revisions. This configuration format has no include mechanism or executable configuration language.

Administrative policy​

Native locations follow OEP-0002: Windows known folders, macOS Application Support, and Linux /etc/oyzu plus absolute XDG user locations. Protected files require administrative ownership and permissions. Windows uses native ACL/handle checks; Unix checks root ownership and write permissions; macOS also examines extended ACL entries on the opened object and rejects non-root mutation grants using the native descriptor ACL API. An insecure, unreadable or malformed enrollment never becomes standalone mode.

admin-settings.json uses the same typed constraint evaluator as corporate policy. Locks, allowed whole values, numeric bounds and required sets intersect independently of ordinary precedence. Required checks cannot be removed by empty ordinary arrays. The build planner requires configured checks to have actual actions/report contracts; report collection enforces the coverage minimum, including missing/zero-denominator failures.

config status reports enrollment and cached-policy status. config refresh performs a headless request to the enrolled platform's public configuration-context endpoint. Signed responses use pinned Ed25519 keys, canonical JSON, identity/context binding, monotonic sequences, expiry and explicit offline permissions. Cache entries are content-addressed and flushed before an OS credential-store pointer commits them. A corrupt entry can only be repaired from a newly verified online response. Windows Credential Manager, macOS Keychain and Linux Secret Service hold integrity state. If that service is unavailable, managed execution fails; standalone use does not need it. Transport backoff never extends signed deadlines. Server denial cannot become offline permission.

Build inventory options​

Rust targets can declare a finite rust object with optional features and a targets list of Cargo triples. Tool requirements remain in TOML and resolved identities in oyzu.lock; the YAML object rejects toolchain pins. It produces explicit native binary task definitions, described in Rust binary targets, including the unfinished locked-tool execution handoff. It cannot be combined with captured platform matrices. Isolated builds reject that native-only intent instead of dropping its requirements.

build.yaml describes target intent separately from the TOML cascade. Its optional application container field is a boolean or a finite object with base, user, workdir and entrypoint; see Python application containers for types, defaults and current runtime support. Capture validates and freezes that object with the target inventory. config validate rejects malformed option values without resolving images or executing a build. The object introduces no task language or additional precedence layer. Administrative execution checks and resolved owner settings still apply to generated image actions.

Existing settings migration and boundaries​

The Docker adapter registers docker.apparmorProfile. It replaces direct adapter reads of OYZU_BUILDKIT_APPARMOR_PROFILE; the legacy environment variable remains a diagnosed invocation input and faces the same policy constraints. The default still detects the host's AppArmor user-namespace restriction. Builder namespaces stay behind the crate-private Builder contract.

A frozen build configuration contributes its digest to target/action records. Formatting, profile names and presentation preferences do not affect that configuration digest. Policy revision and online/offline context remain separate evidence. No policy snapshot grants signing, publishing or credential issuance.

Build preparation and planning require the resolved invocation snapshot and every selected target's snapshot, including inferred targets without configuration files. Missing internal snapshots fail with CONFIG_INVALID_VALUE; they never disable policy checks or cause adapters to recalculate defaults. Library callers must use discovery to obtain this state; serialized discovery JSON is an inspection result, not a resumable workspace. Rediscover the workspace if that state is missing. Docker reads its execution profile from the admitted snapshot before preparation starts. Later edits to live configuration files do not change an already frozen plan; start a new invocation to resolve them.

The current native tool-store, authenticated platform-session, connector-binding and shell-secret-consumer implementations are not completed by this configuration change; the remote action cache is an experimental development-scope implementation that signs in only with a token from OYZU_CACHE_TOKEN or a CI job's ID tokens (see the action cache). Explicit tool requests that cannot be bound to a verified installation are rejected before builds. Enforced routes/catalogs requiring unavailable bindings fail before public acquisition. Managed builders that still require public dependency preparation are blocked; offline-capable local Docker and Helm preparation remains separate from those network paths. Development secret references require an authorized consumer and are not substituted into build literals. build.jobs bounds concurrent ready actions. The invocation uses the smallest admitted root/target ceiling; each target retains serial mutation and hook order. Targets have private workspaces and output roots. Dependency or deferred-report failure blocks consumers while independent targets can finish. ui.color controls human-readable task labels and outcome statuses: always emits ANSI color, never disables it, and auto enables it only when the relevant output stream is a terminal. Task-specific resolved preferences apply to that task; root tasks use root preferences. JSON output remains unstyled. Cache preferences do not grant cache credentials or trust: a remote hit is a development result.

These boundaries are deliberate failures rather than claims that all OEP-0002 ecosystem and platform integration acceptance cases pass. Three-host ACL/keychain qualification, signed server interoperability, authenticated logout/account-switch flows, complete connector routing and tool-store integration remain release gates.

Development execution checks tool eligibility, explicit tool requests and protected routing/catalog requirements before any prerequisite or hook runs. Managed host tasks remain blocked until approved development execution and connector bindings exist; the host runner cannot claim to enforce managed network routing. Task-specific and native-adapter environment additions must satisfy administrative environment restrictions. In a single-target nested project, the target's final task cascade determines whether a root operation is replaced or removed, consistently with inspection and build planning.

Recovery and authentication follow-up​

CONFIG_SYNTAX, duplicate keysCorrect the source file's syntax/duplicate declaration, then validate
CONFIG_INVALID_VALUE, CONFIG_SCOPEUse the registered type and permitted scope; ordinary set/unset can repair invalid values

Unsupported schema major or required capabilityUse a compatible client; do not remove a requirement unless the project no longer needs it

CONFIG_EDIT_CONFLICTRe-read the file and retry the intended edit; do not overwrite another writer's changes
CONFIG_LIMITReduce file size, nesting or configuration entries, including inactive profile data
POLICY_INVALIDInspect enrollment protection and policy/cache validity; an administrator may need to repair bootstrap permissions or signing configuration
POLICY_EXPIRED, POLICY_UNAVAILABLERestore endpoint/native credential-store availability and run config refresh; failure never converts an enrolled machine to standalone
POLICY_CLOCK_UNCERTAINCorrect clock problems and reconcile online; do not erase rollback-protection state to bypass the error

Offline execution requires explicit signed permission and remains bounded by both signed expiry and maximum offline age (at most 24 hours). CI requires online policy. Transport retry/backoff preserves these deadlines; denial and malformed responses do not authorize offline fallback. Explicit refresh can fail while an older valid cache remains stored. A corrupt cache entry requires a newly verified online response; damaged integrity-store state can require administrator intervention. Refresh rechecks time after I/O, so a request that finishes after a deadline does not extend authorization.

Changing protected bootstrap pins invalidates the previous cache binding. Recovery requires an online response verified against the current pins with a strictly newer policy sequence; existing high-water state remains in force. Do not delete credential-store state as a key-rotation procedure. Cache commit ordering preserves the old committed pointer until the new entry has been flushed; full crash/reboot qualification remains a release gate.

There are no login, logout or enrollment commands in this delivery. When authentication is designed, revisit session-to-policy identity binding, account/organization switching, logout invalidation, credential lifecycle, authenticated refresh and CI identity, plus end-to-end server interoperability. Configuration policy is not a login session and does not grant publishing/signing authority. Connector credentials, shell secrets, verified tool installation and remote action caching also remain separate integrations.

Verification evidence​

The implementation status records tested revisions and host coverage. The current contracts have focused coverage in resolution and editing tests, CLI tests, execution enforcement tests, and signed managed-policy tests. Agent transition tests beside the policy agent cover key rotation, elapsed deadlines and denial/clock behavior. These tests do not establish interoperability with a production authenticated service.

Documentation structure is checked with node tooling/check-docs.mjs; that check does not validate product behavior. The quick-start command sequence and the provisioned-Node task example were separately exercised against the compiled CLI on Windows during this documentation update.

Development PATH metadata​

The project environment reference documents env._.path, its atomic replacement and file-relative paths. The optional compatibility capability is config.env-path/v1. This metadata is not exported into task/build environments.

Bootstrap presentation options​

Global verbosity and OYZU_LOG are typed invocation-only presentation inputs, resolved before any project session. They are not project keys and never enter effective execution snapshots or configuration digests. Explicit CLI controls override the complete environment filter. Help/version do not resolve it. See CLI diagnostic controls for grammar and errors.

Tool lock execution-platform coverage​

[tools] declarations can also be written, replaced and removed with oyzu install SPEC, oyzu uninstall and -g/--local/--profile, which keep comments and lock the result; see tool commands.

A declaration is a version string, or mise's option-table form with only a version key (node = { version = "22" }), which validation normalizes to that string so every consumer sees one form. Edits change only the table's version. Any other option key, or a table without a version string, fails with CONFIG_INVALID_VALUE naming the key; see option tables.

tools.platforms is an optional project/profile string set consumed through the normal configuration cascade. It restricts Rust lock metadata coverage, not the artifact matrix or installation authority. When absent, pin uses the finite default metadata platforms. An empty or unsupported selection fails pin. Values are exact OS/architecture/ABI tuples; this setting is not a tool version request. No schema version changes.
