Cascading configuration (experimental)

CLI reference

Published from the canonical docs/reference/configuration.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Standalone publication settings​

publish.default selects a named OCI destination or publication set when oyzu publish has no --destination. publish.destinations is a typed map of names to registry, repository, and optional paired usernameEnv/passwordEnv credential references. publish.sets maps names to nonempty destination lists. Destination and set names must be distinct. Every selected destination is required.

publish.requirements contains provenance (bundlePath, accepted Ed25519 publicKey, builderId) and signing (keyEnv, publicKey). Public keys are base64 raw 32-byte keys; keyEnv references a separately provisioned base64 32-byte signing seed. Never store secret values in project configuration. Evidence paths resolve relative to the source declaring effective requirements.

Configured once, at the project root. publish.* follows the root-only scope rule (OEP-0022 OD7, the rule [constraints] follows too): only the project root folder's oyzu.toml and oyzu.local.toml may set it, in a base, [context.<name>] or profile table. A [publish] table anywhere else is a configuration error that names the file and line, for every command that reads the configuration:

CONFIG_SCOPE: <root>/api/oyzu.toml:1:1: [publish] is allowed only in the root oyzu.toml (<root>/oyzu.toml); move it there: publishing is configured once, for the whole project

Before this rule a sub-folder's [publish] was accepted and silently ignored, because oyzu publish reads the root; move any such table to the root. oyzu config explain publish.default reports resolution: projectRoot. Independently released packages still publish separately: destinations select artifacts by build.

These settings use the ordinary cascade (user, root project and root local files), selected profiles and mandatory constraints. Each destinations map, sets map, and requirements object is atomic: a later source replaces the whole value instead of merging nested entries. The settings govern standalone safeguards; they cannot grant managed publication authority. The builds, outputs and platforms their selectors name are checked before any build action runs (see names that cross files). See publishing for the complete example, evidence profile, digest-only coordinates and current limits.

Local and CI execution context​

Oyzu captures caller environment hints once when opening the configuration session, before build workers set their own CI=true. Detection is offline and independent of terminals, hostnames, network access and operating system. This is unverified execution context, never runner authentication, authorization or release eligibility.

The following nonempty markers identify providers. Empty values and the trimmed, case-insensitive values false, 0, no, and off disable that individual marker.

TaskCluster requires both TASK_ID and RUN_ID to be nonempty (RUN_ID=0 is valid). Additionally, exact CI=woodpecker, CI_NAME=sourcehut, and CI_NAME=codeship identify those providers. Plain oyzu build defaults to artifact building and packaging locally, plus any check at level required. In the pr, ci and release contexts it also runs every builder check (test, lint, format-check) that is not off; see check levels. oyzu build --full runs every check that is not off regardless of context; it does not change context detection or profile selection. config explain includes the resolved fullBuild request (default false); build plans record fullRequested. oyzu --profile ci build also runs every check that is not off (oyzu's built-in ci profile sets checks.run = "all"). CI needs no extra flags. A different profile or --no-profile does not turn off the checks of a detected CI context; a project turns a check off, or narrows a context to required checks, in oyzu.toml. See build context behavior.

Build context​

Status: implemented for detection, pinning, display, recording and explain (build intent slice 1, BIN-01, BIN-25 and the context part of BIN-22). The context selects per-context values, including oyzu's own check level defaults, and policy constraints can be limited to contexts with when/unless selectors (policy constraints and selectors, slice 7).

Every build resolves one context: local, pr, ci or release. Detection is the default and needs no flags. With no signal the context is local; any CI marker is at least ci; a documented pull/merge request or tag signal of a matched provider raises it to pr or release. When signals conflict the more demanding wins (release over pr over ci). Detection never fails a build.

Every other provider, and a bare CI, resolve to ci; Gitea Actions is left at ci until its documentation is checked. Signals are read only from the matched provider, and only fixed literals (=tag) are ever recorded, never values.

Overrides. oyzu build --context <name> or OYZU_CONTEXT=<name> pins the context (the flag wins). An unknown name is the only context error (CONTEXT_INVALID); because every command that opens a configuration session resolves the context, an invalid OYZU_CONTEXT fails install, exec and config get as well as build. The rule is one-directional: under a vendor CI marker a pin may raise the context but not lower it (the request is ignored and a CONTEXT_OVERRIDE_IGNORED warning names why); with only the generic CI hint, or no signal, a pin may also lower it. Use OYZU_CONTEXT=release once in a manually triggered release workflow, which carries no tag signal.

Resolved fact. extensions["oyzu.dev/execution-context"].context carries detected and detectedSource, requested (value, source), effective and its source, policy (the stricter of detected and requested, which policy constraints will evaluate against) and note. The one-line title shows only the value (context pr, context local); the Build context fact in Prepare gives the full detected via … or requested by … source text; build plans (--plan, --plan --json) and manifests record the same object in extensions["oyzu.dev/execution-context"]. oyzu config explain context reports the value, source and deciding signal. Facts are unverified hints: they never grant publication, credentials or cache authority. The same record carries fork (beside context) for task conditions: false outside a detected pull request; inside one, whether it comes from a fork, read from the GitHub Actions event payload (GITHUB_EVENT_PATH: head versus base repository) or GitLab's CI_MERGE_REQUEST_SOURCE_PROJECT_ID and CI_MERGE_REQUEST_PROJECT_ID; absent when the provider does not say.

Per-context values​

Status: implemented (build intent slice 2, BIN-02 and the settings-resolution part of BIN-20). This section covers ordinary values; policy constraints limited to contexts and folders are described in policy constraints and selectors (slice 7). Check levels (slice 3) use it for their context defaults.

Any registered setting can take a value that applies only when a given context is the build's effective context, in the same oyzu.toml that holds its base value:

[checks]
coverageMinimum = 50

[context.release.checks]
coverageMinimum = 90

[context.pr]
checks.coverageMinimum = 70

The table name is [context.<name>] with <name> exactly local, pr, ci or release; below it, tables and dotted keys are written as they are for the base value. The tables are valid in every scope that holds the setting (user, project root, component folder, oyzu.local.toml) and follow its scope rules: a project file still cannot set cache.remote or trust.enabled under a context.

Precedence. Within one file the order, lowest first, is: the base value; the ci profile when CI inference (not the user) selected it; the effective context's value; a profile the user chose (--profile, OYZU_PROFILE, a task's inherited profile or profile.default). So an inferred [profiles.ci] table loses to the same file's [context.ci.*] table, while --profile ci beats it. This is the maintainer's decision of 2026-10-18 (decisions). Between files, the nearer scope wins, as for every other setting: built-in defaults, then user, then the project root oyzu.toml, then each component folder's oyzu.toml (nearest last), then oyzu.local.toml, then invocation inputs. So a component folder's base value beats the root's [context.release] value; to vary a component by context, write a [context.release] table in that component's file. A context table never applies when its context is not the effective one, whatever the other tables say. A lowered release check is warned about (R6 of the configuration split decision): in a release build, when a nearer folder's value (a base or profile value, or oyzu.local.toml) leaves a check level (checks.tests, checks.coverage, checks.lint, checks.format) below what a farther folder's [context.release] table asked for, every command that resolves it reports a CONFIG_RELEASE_LOWERED warning naming both files and lines, relative to the farther file's folder (checks.tests = advisory from app/oyzu.toml:2 lowers required from oyzu.toml:5 [context.release] in this release build). Plan shows it as a lowered note, oyzu build --plan as a Lowered: line and --plan --json as releaseLowerings per target, and plan and manifest targets record it under extensions["oyzu.dev/release-lowerings"] (setting, value, source, releaseValue, releaseSource). Precedence does not change: the nearer value still wins. The nearer folder's own configured value is compared, never the resolved one, so a constraint that changes the level afterwards (a policy or project cap below the release value) neither blames the folder nor hides its lowering; value is that folder's value. A nearer folder's own [context.release] value is deliberate and never warns. To make lowering impossible, use a project constraint. Constraints always win. Project constraints and then administrative constraints are evaluated after every ordinary value, including context values and chosen profiles, exactly as for a base value: a required member is added to the set a context chose, and a lock or bound replaces a value outside it, visibly, as described in policy constraints and selectors.

Per target or once per build. The registry declares how each setting resolves. A per-target setting (the default: checks, task and environment settings and most others) resolves from each target's folder chain exactly as tool pins do (build tool scope): a root value applies to every target, a value in docs-site/oyzu.toml to the targets under docs-site/, and targets sharing a folder share settings. There are no target-keyed sections and nothing in build.yaml. A once-per-build setting is one the build treats as a property of the whole run: the scheduling, presentation and selector settings (build.jobs, build.isolation, ui.color, profile.default, config.*) and the cache.* family. Its [context.<name>] values are accepted in the user file, the project root oyzu.toml and oyzu.local.toml, and a component folder's [context.<name>] table for it is a configuration error. Of that list, profile.default and the administrative config.* settings cannot vary by context at all, and cache.remote, cache.ciRemote and cache.dir are accepted only from user scope; the rest (build.jobs, build.isolation, ui.color and the other cache.* settings) can. scan.jobs is a per-target setting.

A component folder's base value for a once-per-build setting is still read for its targets, and the build combines them: build.jobs is the minimum over the build root and every selected target. Explain therefore reports that minimum for build.jobs, with the folders that have their own value listed under targetValues and the rule under combine.

A root-only setting (publish.*, resolution projectRoot) goes one step further: no file outside the project root folder may hold a value for it at all, base, context or profile table alike (see standalone publication settings); the root-only [constraints] table follows the same rule.

Errors. An unknown context name ([context.relese]), a table that is not a table, an invalid value, a selector or trust setting that cannot vary by profile or context, compatibility/overrides inside a context, a once-per-build setting in a component folder, and tool pins ([context.<name>.tools], which are not supported yet) are configuration errors reported as CONFIG_CONTEXT_UNKNOWN or CONFIG_CONTEXT_INVALID with file:line:column and the table. A setting that a project or local file may never set (such as cache.remote or trust.enabled) keeps its typed CONFIG_SCOPE refusal, which now names the full key (context.release.cache.remote) and file:line:column. An unknown setting under a context table is, as in the base, an inert warning with its line.

Explain. oyzu config explain <setting> [--context <name>] [--target <name>] resolves as that build context (default: the detected or pinned one) for the named build.yaml target (default: the current folder) and prints the value, every scope that set it with the table's context (origins[].context), the contextValues considered for the setting (applied says the table's context matched, effective says that value is the one that took effect, so a matching value that a nearer scope overrode is applied but not effective; the human view labels these applied, overridden and not this context), resolution (perTarget, perBuild or projectRoot) and the target. A once-per-build or root-only setting is read at the project root whatever --target names (target.resolvedAt is build root), combined with component values as described above. When a pin was ignored because a CI provider marker is present (--context local under GitHub Actions), the human view prints that note and explains as the context actually in effect. --context and --target cannot be combined with --global, --project or --local, which read one file without resolving. An unknown target fails with CONFIG_TARGET_UNKNOWN listing the declared targets.

Recorded. oyzu build --plan --json (per target as contextValues) and the plan and manifest targets of a build bundle (extensions["oyzu.dev/context-values"]) list the settings whose effective value was written in a context table, with the setting, value, context, source file and scope, so a build can be reproduced under --context. The configuration digest already covers the resolved values. Settings that the base value or a nearer scope decided are not listed. Known gap: isolated docker/image container plan targets (built through build/containers.rs) do not record oyzu.dev/context-values yet.

Not covered here: per-context tool pins (follow-up) and when/unless selectors on context tables (follow-up). Tasks and hooks take when/unless with the same selector form policy constraints use; see task and hook conditions.

Check levels​

Status: implemented (build intent slice 3, BIN-04, BIN-05 and BIN-06). Policy can set a minimum level, optionally only in some contexts or folders, through an ordered bound (policy constraints and selectors, slice 7).

Each check a builder offers has one level. The registered checks are tests, coverage, lint and format; they replace the former checks.required set, which is no longer a setting (an old checks.required line is an unknown-setting warning and has no effect).

[checks]
format   = "off"
lint     = "advisory"
coverage = "required"

[context.release.checks]
tests = "required"

Which builds run every check is the setting checks.run: required runs only required checks, all runs every check that is not off. Its oyzu defaults are per-context values at the lowest scope, shown by oyzu config explain checks.run with the source built-in:

Contextchecks.runChecks that run
localrequired (base default)required only (fast build)
pr, ci, releaseall (built-in context values)every check that is not off

A project can change them like any other value, per context and per folder, for example [context.ci.checks] run = "required" for pushes to a main branch, or [checks] run = "all" to run every check locally. --full and --profile ci (whose built-in value is checks.run = "all") run every check that is not off. No flag skips a check the project chose: turning a check off is a committed change in oyzu.toml.

Each builder stage serves checks: the test stage serves tests and coverage (coverage is collected by the tests, so tests = "off" also turns coverage off), lint serves lint and format-check serves format. A stage runs when any check it serves runs; it is off when every check it serves is off. A test stage is advisory when tests is advisory. Each report is judged by its own check: a failing test report of an advisory test stage is a warning, while its coverage report follows checks.coverage, so required or enforced coverage (including a shortfall below checks.coverageMinimum) still fails the build; an advisory coverage shortfall is a warning.

Coverage off is validation-only. Coverage is collected by each builder's test command (for example cargo llvm-cov with nextest for Rust, c8 for Node), and that command does not yet change with the coverage level: with checks.coverage = "off" and tests running, coverage is still collected and its tools are still prepared, but it is never judged (no minimum, its report is not required, a missing or invalid coverage report is a warning). Plan and --plan --json say Collected with test; not judged (checks.coverage = off). Running tests without coverage collection is a recorded follow-up.

Levels resolve per target from the folder chain, like every per-target setting: the nearest folder wins, and a context value beats the base value in the same file. An administrative constraint still wins: a lock or a minimum level replaces a project value below it and Plan says so (format enforce · admin policy minimum in pr, release (project oyzu.toml sets off)); an allowed set such as ["enforce", "required"] refuses a project value outside it with CONFIG_OVERRIDE_DENIED. See policy constraints and selectors.

Errors. A level other than the four is CONFIG_INVALID_VALUE. A positive checks.coverageMinimum with checks.coverage = "off" (or checks.tests = "off") is CONFIG_INVALID_VALUE naming both sources. A required check, or a positive coverage minimum, that the selected builder cannot run fails in Plan with CONFIG_OVERRIDE_DENIED: <target> cannot satisfy required <check> check. A policy lock or minimum of enforce or above on a check that this build runs but the builder has no action for fails in Plan naming the constraint and its source: CONFIG_OVERRIDE_DENIED: <target> has no format check, which admin policy minimum enforce in pr, release (local-administration) requires; its builder cannot run one. Narrow such a constraint with a path selector. An authored task that depends on the stage of an off check is CONFIG_INVALID_VALUE naming the action and where the check was turned off. A required test or coverage check also makes its report mandatory (report-missing when absent), as checks.required did.

Shown and recorded. Plan shows an off cell with its source (format · disabled in oyzu.toml, test · disabled in oyzu.toml [context.pr]), a skip cell with its reason (fast local build, or only required checks run in ci (checks.run)), and an advisory note for advisory stages that run (build view). --plan --json reports stage status off with the same reason. Plan and manifest targets record extensions["oyzu.dev/build-checks"] with mode (fast or full), levels (each check's level) and off (each off stage and its source); each check action records extensions["oyzu.dev/check-levels"], and an advisory one has required: false (as do the report intents of advisory or off checks), so its failure is recorded with status failed, one CHECK_ADVISORY warning carries the native cause, the target's artifacts are still collected, the manifest status stays succeeded, the exit code is 0 and oyzu inspect dist accepts the bundle. This holds on the native host path and the isolated path alike. The plan policy's requiredChecks lists the checks at required.

Tools follow checks. Builder tool requirements are derived from the stages that run, so a builder's own requirement for an off or skipped check is not prepared: with format = "off" the Rust builder no longer adds rustfmt. A component the project declares itself, such as components = ["rustfmt"] in rust-toolchain.toml, stays a declared requirement of the toolchain.

Optimized builds​

Slice 5 of the build intent draft (BIN-08 to BIN-11). Each target is built with the development profile (a fast edit-build loop) or the optimized profile. Optimization follows where the output goes: a target is optimized when this build sends its artifacts off the machine, and development otherwise.

build.optimized (boolean, unset by default) decides instead whenever it is set. It is an ordinary per-target setting: a folder's oyzu.toml sets it for the targets under that folder, optionally per context ([context.release.build] optimized = false), and policy can set or lock it. oyzu build --optimized and --no-optimized set it for one invocation, above every file; giving both is a usage error (CLI_USAGE, exit 2). Policy constraints still win: a locked build.optimized replaces a flag or file that contradicts it, and the override is shown, as for any constrained setting. A build.optimized in user configuration is ignored in CI, like every non-presentation user setting.

# cli/oyzu.toml: the self-installed CLI is always fast
[build]
optimized = true

# oyzu.toml: never optimize release builds of this folder
[context.release.build]
optimized = false

Test stages keep each builder's test mode (Cargo's test profile) in both profiles. The profile is resolved once per target before builder planning and recorded on the plan and manifest target as extensions["oyzu.dev/optimization"] (requested, applied, reason, builder); --plan prints it as Profile: optimized · --optimized (cargo build --release) and --plan --json reports it as each target's optimization with a summary. Each artifact's profile is optimized only when the builder's own optimizing commands produced it, so an authored replacement of the build stays development (build bundles).

Optimized is not publishable. The profile never implies reproducible output or publication eligibility; native host output still confers none.

Local development plugin bindings​

plugins.development maps a built-in builder id such as go/app to an absolute plugin executable path. It is accepted only from user, machine or administrative configuration and replaces that builder's native host operations for the invocation. See local development plugin bindings.

plugins.packages maps such an id to { archive, sha256 } or { oci, identity?, trustedRoot? }: a verified, installed package whose selection oyzu.lock pins. Same scopes. See plugin packages.

plugins.preview (boolean, default false) makes preview plugin releases from the catalog eligible. Same scopes, and never from a profile: a project file, oyzu.local.toml or profile that sets it fails with CONFIG_SCOPE. See plugin catalog.

Trusted environment and credential destinations​

engines.packages admits exact development engine archives; engines.development (boolean, default false) independently permits the explicit local build --engine-development invocation. Both are restricted to user, machine and administrative sources, never project/local files or profiles. Engine permission uses actual-root path constraints and the strictest caller context; CI/PR/release cannot use the development override. See engine staging for selection, evidence and errors.

engines.requirePin is an administrative-only Boolean, default false. An applicable protected locked: true, value: true policy constraint requires an exact engine pin and complete build lock; a policy default alone does not. Ordinary machine/user/project/local/invocation settings and profiles cannot set it. See policy-required pins for the candidate behavior and qualification status.

Project trust controls are trust.enabled (boolean, default true) and trust.parents (absolute folder paths, default []). They and platform.url, platform.account, platform.authentication.provider, cache.remote, cache.ciRemote are rejected in project/local scope, including profile overlays. Set them in user/global, machine or administrative configuration. Supported invocation environment sources are OYZU_PROJECT_TRUST, OYZU_PLATFORM_URL, OYZU_PLATFORM_ACCOUNT, OYZU_PLATFORM_AUTH_PROVIDER, OYZU_CACHE_REMOTE and OYZU_CACHE_CI_REMOTE; each overrides ordinary files while remaining subject to administrative constraints. OYZU_PROJECT_TRUST accepts true/false, on/off, yes/no or 1/0. See folder trust for the environment application boundary and native user-state records.

Build inventory migration​

build.yaml accepts a builds mapping with uses, path, platforms, depends_on, inputs, materialize, bindings, fetches and with per entry; any other field fails with CONFIG_INVALID_VALUE naming it. depends_on is an ordering-only list of producer build names; it does not transfer artifacts. inputs names extra source paths a build reads (declared inputs), fetches declares pinned downloads (declared fetches), and bindings writes a produced image's reference into a chart's values during the build (image bindings records its verification and limits). Configuration owns normalization and freezes all declared platforms; builders own validation of with. See the Rust build options for the implemented options and execution limits. This is a partial implementation of the proposed build model, not support for every future example. Tool requirements remain in TOML and lock identities remain in oyzu.lock.

The root keys of an inventory are builds, members and exclude; any other root key fails with CONFIG_INVALID_VALUE naming it. members (split inventories, OEP-0022 M18) is refused as not supported yet. exclude lists folders where discovery recognizes a build that is deliberately not one. In a build entry uses is optional (OEP-0022 OD13): web: {path: web} is a complete entry when exactly one builder recognizes web, and discovery freezes that builder into the inventory before planning. A folder no builder or several builders recognize fails naming the candidates and the line to write. Folders discovery recognizes that the inventory leaves out are listed by oyzu discover and oyzu build --plan, never built; oyzu discover --write declares them and oyzu discover --check fails on them in CI. A folder the native workspace manifest of a declared build lists as a member (Cargo members, go.work use, npm/Yarn/pnpm workspaces) is covered by that build and needs no entry (discovery decisions). oyzu config validate checks chart bindings (unknown producers, repository and values fields) without discovery. Checks that depend on an omitted uses (the with options of that build, bindings only on helm/chart builds, a docker/image producer) wait until discovery infers the builder, as oyzu discover and oyzu build --plan do.

builds: is the only shape (OEP-0022 M1, step D5). The former flat shape, with build entries at the top level, is refused with CONFIG_INVALID_VALUE; the message shows the file's own lines indented under builds:, which is the whole move:

# Refused: builds at the top level
cli:
  uses: rust/app
# Accepted: the same entries, indented two spaces under builds:
builds:
  cli:
    uses: rust/app

Fields the flat shape once carried have their homes: matrix is refused (runtime versions are toolsets in oyzu.toml, see verification toolsets) with CONFIG_INVALID_VALUE showing the toolset form. Artifact platforms are only platforms: [<os/arch[/abi]>, ...]: platform: <os/arch>, matrix.platform and the rust object are refused naming the replacement (platforms: [...]; Cargo features in with.features and cross-compilation targets as platforms entries). A build that declares one platform keeps its name; several platforms give each instance a platform-qualified ID (platform requirements). container is the python/app option with.container (Python application containers), dependencies is the docker/image option with.dependencies (Docker dependency contexts), and docker/image's former with.load is the docker.load setting; the old spellings fail with CONFIG_INVALID_VALUE naming the new location. A builder checks its with options when the inventory is read, so oyzu config validate reports them. See the migration plan and the 2026-10-19 configuration split decision.

Which build.yaml files are Oyzu's​

Other tools use the same file name: Dart's build_runner reads a build.yaml with targets:, builders: and global_options: in each package. A build.yaml is an Oyzu inventory only when its root has builds, members or exclude, or the refused flat shape (a top-level entry whose mapping has uses); a file that is not valid YAML also counts, so its syntax error is reported rather than the file skipped. A misspelled envelope counts too, so it fails naming the root keys (found build (did you mean builds:?)) instead of being skipped: a root key equal to builds, members or exclude ignoring case, the key build, or any root key with uses two levels below it (buildz: {web: {uses: node/app}}). A leading UTF-8 byte order mark is ignored. Any other build.yaml, including an empty one, belongs to another tool (OEP-0022 R7):

  • it never makes its folder a build root, a project root or a configuration boundary;
  • discovery and oyzu discover --check continue below its folder as if it were absent, so a Flutter package inside a monorepo no longer hides the builds under it;
  • at the project root, zero-config discovery decides the builds, as without a build.yaml, and every discovering command (oyzu build, --plan, discover, run) warns CONFIG_BUILD_FILE_IGNORED: build.yaml: ignored, not an Oyzu inventory … naming its root keys (a JSON diagnostic event on stderr with --json);
  • oyzu discover (and --check, --write) lists it under Skipped with its root keys; JSON records it in skipped_build_files (plain oyzu discover without an inventory) or skippedBuildFiles (the inventory record), each entry {path, keys}.

oyzu discover --write never edits another tool's build.yaml at the project root: it fails with CONFIG_INVALID_VALUE naming the file's root keys and leaves it unchanged. An Oyzu inventory cannot share that file, so such a folder can only use zero-config discovery (a known limitation of keeping the build.yaml name, OD2).

Where a build.yaml error is​

Every refusal of a build.yaml names the place to fix, as build.yaml:LINE:COLUMN: after the diagnostic code (OEP-0022 M22). This covers YAML syntax errors (CONFIG_SYNTAX), anchors, aliases, tags, merge keys and duplicate keys, which an inventory never uses (CONFIG_SYNTAX, CONFIG_DUPLICATE), the flat shape and wrong root keys, unknown, moved or retired build fields, uses, platforms, materialize, bindings and fetches values, unknown dependencies, a builder discovery cannot infer, and with options a builder refuses (at the option itself when the message names it, else at with). For example:

✗ CONFIG_SYNTAX: build.yaml:3:6: invalid YAML: while parsing a flow mapping, did not find expected ',' or '}'
✗ CONFIG_INVALID_VALUE: build.yaml:5:7: docker/image with.repository must be a repository name without scheme, tag or digest

With --json the same text is the error record's error. Lines and columns start at 1. A leading UTF-8 byte order mark (written by some Windows editors and PowerShell 5) is ignored. The file is read by Oyzu's one YAML reader (crates/oyzu-yaml), which follows the YAML 1.2 core schema: true, ~, 12 and 1.5 are a boolean, null, integer and float, and yes, on or 1.2.3 stay strings.

Editor schemas​

Oyzu generates a JSON Schema for each of its two files, so an editor can complete keys and flag a value or a key in the wrong file while you type. The build.yaml schema comes from the build model (the root keys and every build field above); the oyzu.toml schema comes from the settings registry (every registered setting, nested by its dotted key) and the sections the reader accepts (profiles, context, toolsets, constraints, overrides, compatibility). Builder with options and settings a plugin registers are left open.

A schema follows the reader, with two deliberate exceptions where it is stricter. In build.yaml it flags what the reader refuses: an unknown root key or build field, and a value of the wrong type or form. The exception: its path pattern (path, inputs, materialize to and into) refuses \ and : anywhere in a path, so a file stays portable across Windows, macOS and Linux, while the reader decides such a path where it is used. In oyzu.toml it flags a value of the wrong type for a registered setting and the wrong-file case: a build.yaml key such as [builds.web], exclude or a top-level uses is refused by the schema, while the reader only warns about it as an unknown section (CONFIG_UNKNOWN_OPTIONAL). Any other unknown key inside a section, or unknown section, stays open in the schema because the reader only warns about it and oyzu config validate --strict refuses it. The CLI's own checks stay the authority, including rules a schema cannot express (a value accepted only from user configuration, a root-only section, which ABIs an OS has).

To point an editor at them:

  • build.yaml: the YAML language server (VS Code's YAML extension and others) reads a first-line comment # yaml-language-server: $schema=https://github.com/oyzuai/oyzu/releases/latest/download/build.yaml.schema.json. oyzu discover --write adds it when it creates or edits build.yaml and the file has no yaml-language-server: $schema= comment yet; add it by hand to a file you write yourself. build.yaml is not registered with SchemaStore, because SchemaStore already lists Dart's build configuration for that name.
  • oyzu.toml: point Taplo or Even Better TOML at the URL (Taplo's [[schema]] setting, or a #:schema <URL> first line). Registration with SchemaStore, so editors find it by file name, is a maintainer action and is pending.

Prerequisites and quick start​

Configuration commands default to human-readable output. Pass global --json for structured results and errors; see CLI output.

Use an Oyzu CLI built from this branch; these commands are not a promise about older releases. Standalone configuration inspection and editing require no platform account, Docker, native ecosystem toolchain or network service. The client has Windows, macOS and Linux implementations; platform qualification and measured checks are tracked in implementation status. Running tasks or builds additionally requires their explicitly provisioned native tools.

In an otherwise empty directory named config-demo, save this as oyzu.toml:

[build]
jobs = 2

[profile]
default = "dev"

[profiles.dev.build]
jobs = 3

[ui]
color = "never"

Run these commands from its parent directory. Expected values assume standalone operation with no administrative constraints, local overrides or OYZU_PROFILE selection:

oyzu --root config-demo config get build.jobs
oyzu --root config-demo --no-profile config get build.jobs
oyzu --root config-demo config validate --strict --all-profiles
oyzu --root config-demo --profile dev config set build.jobs 4 --project
oyzu --root config-demo config get build.jobs
oyzu --root config-demo --profile dev config unset build.jobs --project
oyzu --root config-demo config get build.jobs

The successive get results are 3, 2, 4, and 2. Validation reports success; with --json it returns valid: true. Removing the profile assignment exposes the base value; it does not restore the old value of 3. Set/unset return the destination path and updated key. No project task runs in this walkthrough.

Inspection and selection​

oyzu --root path/to/project config show --json
oyzu --root path/to/project config explain build.jobs --json
oyzu --root path/to/project config profiles
oyzu --root path/to/project config validate --strict --all-profiles
oyzu --root path/to/project --profile integration run test
oyzu --root path/to/project --no-profile run test

--root explicitly fixes both build and configuration roots. Otherwise the nearest ancestor build.yaml inventory within the current Git worktree selects the build (another tool's build.yaml never does; see which build.yaml files are Oyzu's); configuration still inherits from the Git worktree root. Outside Git, the outermost ancestor with Oyzu configuration or a build declaration bounds inheritance, falling back to the invocation directory. With no build declaration, that boundary remains the conventional-discovery root. -C / --directory selects the invocation directory; --root alone also selects that directory.

Git boundaries require recognizable repository metadata: HEAD plus the common objects and refs directories. A .git file must contain a gitdir: <path> pointer to that metadata; linked worktrees use its commondir pointer for the common directories. Relative pointers are resolved from their declaring directory. An unborn repository and packed refs remain valid boundaries; no commit or loose branch ref is required. Empty .git directories, malformed pointers and missing metadata do not define a workspace. They are left intact. Recognition reads bounded local metadata without running Git, executing configuration or establishing repository integrity. Conservative nested repository/submodule exclusions during target traversal remain in effect.

Entering an independent nested example and running oyzu build --plan therefore selects the example without --root. Its oyzu.lock and build outputs belong to that selected root. Parent inventories are not merged, and automatic discovery skips nested build roots. An explicit parent target path remains authoritative. Configuration retains normal project/local precedence, relative paths retain their declaring-file origin, and machine/enterprise constraints remain enforced. A selected build root may declare its default profile; ordinary target subdirectories cannot. Explicit composition and shared-workspace lock ownership are not implemented.

Relative task cwd values are now relative to the TOML file that declares them. For a root-file override of api:test, use cwd = "api/checks" to select that directory. Multiple targets cannot own the same native build unit; use distinct project paths or distinct builders where appropriate.

Sources resolve in this order: built-ins, verified corporate defaults, protected local administrative defaults, machine configuration, user configuration, root-to-target oyzu.toml, eligible root-to-target oyzu.local.toml, and invocation compatibility inputs. Each source applies its base followed by the selected profile. Siblings receive separate snapshots. Arrays replace, tasks replace atomically, and [overrides].remove removes explicit environment/task entries. Environment removals also unset inherited variables during development task execution. A task environment can replace a global variable with the same spelling, but case aliases such as TOKEN and token are rejected across the combined environment on every host.

Known tool aliases share that same precedence. For example, project node = "22" overrides global "oyzu:node" = "latest"; a selected toolset can override it through either spelling. Inspection retains the spellings with their effective value and winning provenance. Lock ownership follows the winning source. Declaring multiple aliases for one tool in the same overlay remains ambiguous. Administrative constraints bind the selected value regardless of its spelling.

Profile selection uses explicit --profile or --no-profile, inherited task selection, OYZU_PROFILE, the eligible root/default selector, inferred CI's empty ci profile, then no profile. Names grant no authority. Inferred CI excludes user computation settings and local files; --local-overrides requests local files, subject to administrative restrictions. Excluded local files are not parsed.

Toolsets​

A toolset is a named set of tool versions, for testing builds on other tools than the ones they ship with and for running commands with them (OD1, OD16). oyzu build adds a toolset's verification run for each build whose builder uses one of its tools: in every context but local unless the toolset lists contexts, and locally with oyzu build --verify-with NAME. A run repeats the build's build and test stages with the toolset's tools and never ships an artifact; verification toolsets describes runs, their evidence and CI fan-out. A profile cannot change tools: [profiles.<name>.tools] (or a tools key inside a profile table) is refused by oyzu config validate and by every command that reads the configuration, in every file, with CONFIG_PROFILE_TOOLS naming the file and line and showing the toolset that replaces it:

CONFIG_PROFILE_TOOLS: oyzu.toml:4:1: [profiles.x.tools] is not allowed: a profile cannot change tools, so the tools a build uses never depend on the selected profile. Move the table to a toolset:
  [toolsets.x.tools]
  go = "1.24.13"
and select it with `oyzu --toolset x exec -- …` (also run, env, activate, which, install, update and uninstall)

Define a toolset in a project's oyzu.toml or oyzu.local.toml:

[tools]
rust = "1.99.1"

[toolsets.go-test.tools]
go = "1.24.13"

[toolsets.node24]
contexts = ["ci", "release"]          # optional; default: every context but local
platforms = ["linux/x86_64"]          # optional; default: one run, on the build's first declared platform or the host
tools.node = "24"

and select it for one invocation with the global --toolset NAME option, written like --profile:

oyzu --toolset go-test install --frozen
oyzu --toolset go-test exec -- go version
  • Commands. --toolset serves exec, run, env, activate (an activated shell keeps the toolset on every prompt), which, pin (locks only that toolset's tools), and the project-scoped install (without specs it installs, and locks when needed, the toolset's tools; with specs it declares them in [toolsets.NAME.tools]), update and uninstall (both act on that toolset's declarations and lock sets only). Every other command refuses it with TOOLSET_UNSUPPORTED, as do activate --shims and --global installs, updates and removals. oyzu build refuses it with TOOLSET_BUILD_REFUSED naming oyzu build --verify-with NAME: a build always uses the [tools] versions, so a toolset never changes what ships; --verify-with adds the toolset's verification run instead.
  • Verification runs. contexts lists the contexts (local, pr, ci, release) whose builds run the toolset's verification runs; without it a toolset runs in pr, ci and release, never local, and contexts = [] turns it (or an inherited definition) off. platforms lists the os/arch[/abi] platforms to make one run each for; without it there is one run, assigned to the build's first declared platform (the host's when the build declares none), and a job builds the runs assigned to the platform it builds. A toolset applies only to builds whose builder uses one of its tools, so a Go toolset adds nothing to a Node build in the same folder.
  • Precedence. The toolset's tool requests replace the cascade's, above every file (a nearer folder's [tools] value included) and below policy: administrative and project constraints still bind a toolset's tools, and a value outside a policy lock fails with CONFIG_OVERRIDE_DENIED. Tools the toolset does not name keep their cascade value. A toolset is exempt from native pin agreement (OD10 rule 6): a toolset Go below the go.mod minimum is used as written, wherever the toolset is defined, never refused or replaced by the minimum. oyzu tools current --all lists toolset declarations with their toolset.
  • Inheritance. One definition of a name applies, whole, as tasks do: the last one in the source order, which is every oyzu.toml from the root to the folder, then every included oyzu.local.toml from the root to the folder. So a nearer oyzu.toml replaces a farther one, and any included oyzu.local.toml that defines the name, even the root's, replaces every oyzu.toml, including a nested folder's. The folder the command runs from must have the name in its chain, or the command fails with CONFIG_TOOLSET_UNKNOWN, listing the toolsets defined there; a build target in another folder chain, which no file defining the toolset reaches, keeps its cascade tools. A build sees, per build, the toolsets its own folder chain defines, the nearest definition of each name applying whole.
  • Nested folders lock nothing yet. The lock labels a toolset's sets by its name alone, so only a toolset whose applied definition is in the project root's oyzu.toml or oyzu.local.toml is locked. For one defined (or redefined) in a nested folder's file, --toolset NAME install, install SPEC, update, uninstall and pin, and any exec, run or verification run that would install or lock its tools, fail with TOOLSET_NESTED_LOCK, naming the file, and change nothing; exec, run, env and which with tools already locked still work. Plain oyzu pin and oyzu update (without --toolset) leave such a toolset out, name it under Toolsets not locked (toolsetsNotLocked in JSON) with the reason, and still succeed; so do they for a toolset whose tools policy refuses. A lock identity for nested-folder toolsets is a named follow-up.
  • Nested commands. A task run with oyzu --toolset NAME run sets OYZU_INHERITED_TOOLSET (to @none when the task runs without one), so a nested oyzu exec, run, env, activate, which, install, update or uninstall keeps the task's toolset. Every other nested command, oyzu build included, removes the variable from its own environment before it starts anything, so neither it nor its native steps (and their nested oyzu exec) see a toolset its plan and cache keys do not record.
  • Validation and additions. A toolset holds its tools table and optionally contexts and platforms. Unknown optional fields warn and are ignored, allowing a newer configuration to be read by an older CLI with this behavior. Unknown contexts, repeated or empty platform lists, and non-tool keys such as platforms or ignore under tools remain CONFIG_TOOLSET_INVALID errors. Toolsets are refused in user, machine and administrative configuration and inside [profiles.*] or [context.*] tables (CONFIG_SCOPE).
  • Lock and caches. The tools a toolset supplies (declares itself) are locked in oyzu.lock as its own request sets, labelled toolset = "NAME", beside the [tools] sets, which carry no label; the tools it inherits from [tools] stay in the [tools] sets. A toolset install (or exec, run, update) first gives [tools] its own copy of any pin it requests that only the toolset's sets held (a tool moved from the toolset into [tools]), then drops the toolset's copies of tools it no longer supplies that another set still pins; a pin no other set holds is kept, since another toolset may rely on it. Tool identity, request digests and cache keys depend on the requests alone, never on the profile or the toolset name. A toolset's install, install --update, update, declaration (install SPEC), uninstall and the automatic installation of exec and run add or change only that toolset's sets: they never rewrite a [tools] request or another toolset's, and the [tools] commands never rewrite a toolset's. Without names, oyzu --toolset NAME update and install --update re-resolve only the tools the toolset declares, never the [tools] tools it leaves alone. One request string resolves to one version in the whole lock, so a request a toolset shares with [tools] (the same rust = "1.99.1") uses the same pin, and updating it updates it wherever it appears. A scope ([tools] or a toolset) that installs with a pin only another scope's set holds gets a labelled set of its own with that pin, and removing the tool from one scope gives every other scope that still declares it a set of its own first, so uninstall in one scope never takes away a pin another scope uses; it says where the tool is still declared. oyzu install --frozen writes nothing, so it adds no such set. oyzu install --frozen with or without a toolset replays the pins its requests need. oyzu pin covers every toolset: beside the [tools] sets it locks, for each build, the tools each toolset its folder sees supplies, in that toolset's labelled set, whatever the context and whether or not the build's builder uses them (a toolset can serve only oyzu --toolset NAME exec). oyzu --toolset NAME pin locks only that toolset's tools. Plain oyzu update re-resolves the [tools] tools and then each toolset's, each in its own sets, and its table names the set of each row; oyzu update TOOL updates the tool wherever [tools] or a toolset declares it. Locks written before D4a can hold a toolset's tools in an unlabelled set, which keeps working.

This repository's opt-in Go adapter checks use the go-test toolset; see CONTRIBUTING.md.

config show, get, explain, profiles, and validate do not execute project tasks. If resolution is blocked, show and explain return an explicit unresolved status without effective values; validate remains the failing validation command. The credential-origin and trust-control scope ban is an exception: platform.url, platform.account, cache.remote, cache.ciRemote, trust.enabled and trust.parents in project/local sources are hard errors even for show and explain, in human and JSON output and in CI when that source is included. The error names the key, source and user/global or administrative remedy. Configuration inspection displays ordinary environment settings and path arrays; credential-like environment names and recognizable sensitive values remain redacted, as do task bodies. Discovery/task listing also redacts environment values. Explain includes source histories, byte spans, exclusions, constraint source IDs and the effective computation digest. Warnings carry severity, source byte spans when available, target scope, and a remedy without including the configured value. Unknown optional settings warn and stay inert, including unknown sections, fields under [toolsets.<name>], controls under [env._], and unknown fields inside understood objects: tool requests, environment secret references and path controls, task report declarations, publication destinations and their evidence options, registry routes, and engine/plugin package source declarations. Known fields, including required identifiers and digests, still validate. Unknown enum values or destination kinds cannot be executed and remain errors. They are not exported to the environment or applied to effective configuration. Similarity to a known section name supplies a spelling hint, not a failure. This compatibility behavior applies to clients containing this fix; already installed older binaries retain their original parsing behavior. New functionality that is essential for correct execution must declare a required capability through [compatibility].requires rather than rely on an ignored setting. Constraint entries, policy rules, required publication evidence and selector expressions retain their documented validation; ignoring optional configuration does not authorize bypassing required controls. Known invalid values, unsupported required capabilities, duplicate keys and unsupported schema majors fail. --strict rejects optional warnings. --all-profiles validates inactive capability requirements and profile outcomes.

Editing​

oyzu --root path/to/project config set build.jobs 8 --project
oyzu --root path/to/project config set checks.tests required --local
oyzu --root path/to/project --profile dev config set ui.color never --global
oyzu --root path/to/project config unset build.jobs --project

Exactly one of --global (the user configuration file), --project, or --local is required. --directory can select a contained nested project scope. unset removes an assignment in that file and exposes inherited values; it does not create a removal tombstone. Ordinary edits remain available to repair invalid values even when resolution is blocked; they do not activate values or alter protected records. Edits preserve unrelated comments and unknown syntax, validate known types/scopes, and compare the original bytes before atomic replacement. Concurrent changes produce CONFIG_EDIT_CONFLICT. A small .oyzu-config-edit.lock coordinates Oyzu writers and is excluded from source snapshots.

Only an explicit --profile NAME directs an edit into that profile. An inferred/default profile does not change the write destination: an edit without --profile writes the base section. A profile cannot hold tools: config set tools.NAME VALUE --profile P fails with CONFIG_PROFILE_TOOLS; declare toolset tools with oyzu --toolset P install NAME@VERSION (see toolsets). Scalar booleans and numbers are parsed by type; strings are literal. Use --json-value for arrays or objects. The array example above uses shell quoting supported by PowerShell and POSIX shells. Edits cannot repair malformed TOML syntax; correct that syntax in an editor first. They cannot modify administrative or enrollment records.

Inspection does not run tasks, but resolving an enrolled configuration can contact the policy endpoint and update its cache. Policy constraints and selectors​

Status: implemented (build intent slice 7, BIN-03 and the selector part of BIN-20). This section is the client contract: what a constraint can say and how a build applies it. How an organization authors, composes and delivers its policy is not described here.

Central policy has two forms. A default ("default": …) is an ordinary inherited value at the policy's scope that a project can override. A constraint is a limit applied after every ordinary value (base, context and profile values, flags), which a project cannot go past:

ConstraintApplies toWhen the ordinary value is outside it
"locked": true, "value": vany settingthe lock replaces it; shown as an override
"minimum" / "maximum"numbers (build.jobs, checks.coverageMinimum, cache sizes) and ordered levels (checks.tests, checks.coverage, checks.lint, checks.format: off < advisory < enforce < required)the bound replaces it; shown as an override
"required": [...]setsthe members are added; shown as an override
"allowed": [...]any settingrefused with CONFIG_OVERRIDE_DENIED naming the setting and the policy source (the set names no single winner)

Tools. A tool version request (tools.<name>) under a lock or allowed set is refused, not replaced, because a requested tool version is never silently substituted. A tool constraint binds every spelling of the tool: a lock on tools.rust also refuses [tools] "oyzu:rust" = "1.90" or "core:rust", and the reverse. An unconditional tool lock supplies the request. A tool lock limited by a selector supplies its version under the tool's id and short name and binds every target whose builder needs or detects the tool, exactly as an unconditional lock does, whether or not the project pins it (deleting [tools] rust cannot evade a release lock on Rust; if the locked version cannot be resolved the build fails). The version a target's builder needs (a pin, the builder's default such as lts, a detected tool's latest, or a toolset verification run's request) is also checked against every tool constraint wherever tools are prepared (build preflight and the isolated worker, oyzu run and oyzu install, scanner preparation): outside an allowed set or a lock it is refused naming the constraint (CONFIG_OVERRIDE_DENIED: tools.node violates administrative constraints: 24 is outside allowed ["20","22"] in release (local-administration); pin an allowed version …; a tool a builder only detected can instead be silenced with tools.ignore). An allowed or locked version matches by version components: 22 admits 22, 22.14 and 22.14.0 (not 220.1); any other value (lts, latest) matches only itself. The version oyzu.lock resolves a request to is checked as well, before anything is installed or activated (oyzu install, --frozen included, exec, run, operation tools and the isolated worker), so a hand-built or stale lock that maps an allowed 22 to 26.1.0 is refused naming the constraint and the lock file. Write allowed sets as majors or exact versions: an allowed lts or latest admits the request but cannot vouch for the version it resolves to, so a locked version under such a set is refused. A tool constraint never affects a target whose builder does not use the tool, and a missing request alone is never a violation.

A version a context-scoped lock supplies is locked per context: oyzu.lock keeps one entry per tool request, so a local build (rust = stable) and a release build (rust = 1.95.0 from the lock) need one entry each. The entries coexist and a later local build does not change the lock, but a build in a context whose entry is missing fails with TOOL_LOCK_STALE: oyzu:rust 1.95.0; it is locked by policy local-administration for this build and oyzu.lock has no entry for it; on a machine with the same policy, run OYZU_CONTEXT=release oyzu pin … (a build does not add it while other tools are already locked, and --frozen never does). Run oyzu pin and OYZU_CONTEXT=release oyzu pin once, on a machine where the same policy is installed, and commit the lock; frozen release builds and oyzu install --frozen then succeed. Setting the context does not reproduce other facts: for a lock limited by provider or path, pin from a build that has them (in that CI job, or in that folder).

Not bound by tool constraints (known limits, follow-ups recorded): custom tasks that run tools by argv; plugin builders that run host tools without declaring them as requirements; oyzu exec, which activates only requested tools; a tool the isolated worker image supplies with no declared builder requirement (Helm, npm without packageManager, Yarn) or whose default request is missing from oyzu.lock, which runs the image's copy unchecked (a tools.helm allowed set with no pin is not enforced); and tool recipe artifacts (recipe:* entries in oyzu.lock), which oyzu install replays without tools.allowed or tool constraints. A project's configuration otherwise never breaks a build merely because policy tightened: policy wins and the CLI says so.

Check levels. A policy lock or minimum of enforce or above on a check means the check runs wherever the constraint applies, whatever checks.run says: a project's [context.pr.checks] run = "required" does not skip a check policy requires in pr. The lift is recorded with the override (runs although checks.run = required) and changes the configuration digest. required additionally makes the check run in every build, including a fast local one, and makes its report mandatory. A minimum on checks.coverage also lifts checks.tests to at least the same level, because the tests collect coverage (coverage is collected by the tests), so tests = "off" cannot evade it. A policy minimum on checks.coverageMinimum lifts an off checks.tests or checks.coverage to enforce, or to advisory where a policy maximum or allowed set caps it there (a coverage minimum of 80 needs coverage) instead of the CONFIG_INVALID_VALUE a project's own minimum with coverage off gets; an advisory level is not lifted (it is judged, as a warning), so a policy coverage percentage with a policy lock of advisory works. A lift never overrides another policy constraint: a coverage percentage with a policy checks.coverage lock (or maximum, or allowed set) that keeps it off, or a coverage level with a lower tests lock, is CONFIG_POLICY_CONFLICT naming both, when the policy is read if both are unconditional, else when a build meets both.

Selectors. A constraint can be limited with when and unless tables over the shared fact vocabulary: every key in when must match (a list matches when any listed value does), any matching key in unless excludes. The facts that have a value when policy is applied are context (local, pr, ci, release), provider (detected CI providers such as github-actions) and path (the target's folder, matched as a /-separated glob). A setting can carry one entry or a list of entries with different selectors:

{
  "schemaVersion": 1,
  "kind": "local-admin-policy",
  "settings": {
    "checks.format": {"minimum": "enforce", "when": {"context": ["pr", "release"]}},
    "checks.tests": [
      {"minimum": "required", "when": {"path": "services/**"}, "unless": {"context": "local"}},
      {"minimum": "enforce", "when": {"context": "release"}}
    ]
  },
  "profiles": {},
  "requiredCapabilities": []
}

Contexts cannot be dodged. A build is taken as every context it detected, runs as or requested: the detected context, the effective one and the stricter of detected and requested (release over pr over ci over local). A when context matches when it names any of them, and an unless context excludes only when it names all of them. So neither lowering nor raising the context evades a constraint: a pull request job under GitHub Actions run with --context local (ignored) or --context release (honored for its values) still meets when context = pr, is not excluded by unless context = release, and a job with only the generic CI hint meets when context = ci with --context pr or --context local. explain reports these facts as policyFacts (contexts, providers, path).

Folders. path is the target's folder relative to the repository boundary: the nearest Git boundary above the build root, climbing from a submodule (a .git file whose gitdir lies under <superproject>/.git/modules/) to its superproject. A linked worktree, a nested clone (its own .git folder) and any other repository are their own root, and the boundary is never the user's home folder or above it (a home under Git is ignored). Without Git it is the nearest folder holding oyzu.toml, oyzu.local.toml or build.yaml, else the build root. --root, a nested build.yaml and the current folder never move it, so building the submodule services/pay on its own still sees services/pay. A submodule of a linked worktree climbs to that worktree. A target folder outside the boundary (reached through a link) is a CONFIG_SCOPE error, never the root.

Path selectors are not containment. They select by repository layout: a git init (or a nested clone) in a subfolder makes it its own root, and a when path services/** constraint then no longer matches it. Write rules that must hold everywhere as unconditional constraints (or limit them by context or provider), not by path. Patterns are normalised (./services/ is services) and compared without case. services/** matches services and every folder below it; * matches one folder level. The repository root itself (.) is matched only by . and **, so a pattern for subfolders never reaches it.

Conflicts. Constraints on one setting that can apply to the same folder in the same context are compared when the policy is read: an unconditional lock off with minimum required when context = release, or two constraints scoped to a shared context that cannot both hold, fail the policy with POLICY_INVALID naming both entries. Constraints for different contexts load (lock off when local with minimum required when release); when one build is taken as several contexts and they cannot all hold, the constraints of the strictest context (local < ci < pr < release) win: its lock, minimum or maximum, and the intersection of its allowed sets. The rank is the context's, not the value's: a local build raised with --context release gets the release constraint even when it is looser than the local one. Constraints whose when.path patterns lead to different folders (services/**, docs/**) never meet. Allowed sets that agree pairwise but share no value when one build meets all of them fail closed at resolution with CONFIG_POLICY_CONFLICT.

Errors. An unknown fact, a fact without a value at this point (fork is not detected yet; target, platform, artifact and optimized are decided after settings), an unknown context, a non-string value, an empty table, an absolute, .., .-segment or // path pattern, an unknown entry field (wehn, named in the message) and when/unless on a default are POLICY_INVALID naming the setting. A bound that is not a valid value of the setting (a level that is not one of its levels) is CONFIG_INVALID_VALUE. A minimum or maximum on a setting that is neither a number nor an ordered level, a non-integer numeric bound, reversed bounds, and unconditional constraints that cannot hold together are CONFIG_POLICY_CONFLICT. Like every policy error these stop the session before a build starts.

Shown and recorded. When a constraint replaces the value configuration chose:

  • oyzu config explain <setting> lists it under Policy overrides (checks.format enforce admin policy minimum in pr, release (project oyzu.toml sets off)), adds a policy-<kind> step to the resolution history, and marks each constraint with applies; --json has policyOverrides (setting, value, kind, bound, source, selector, the replaced value and its origin, and its label) and policyFacts. org policy labels enrolled (corporate) policy, admin policy the machine's admin-settings.json.
  • Plan prints one policy note per distinct override (see the build view); oyzu build --plan prints Policy: lines (Constraint: for a project constraint) per target and --plan --json has policyOverrides per target.
  • Plan and manifest targets record extensions["oyzu.dev/policy-overrides"]: the setting, value, constraint (source, label, kind, bound, selector), replaced (value, source relative to the project root, scope) and the note. The configuration digest covers the resolved value as before.
  • Every command that resolved an overridden setting (exec, run, scan, env, build, config …) reports a CONFIG_POLICY_OVERRIDE warning once per override, naming the setting, the policy source and the value that lost (checks.format = enforce by admin policy minimum in pr (local-administration) instead of off from oyzu.toml), shown in human output by default and in the configuration result's diagnostics. The shell prompt hook does not repeat it. config validate --strict reports it without failing.

A value a task passes on as written (a task's own env) is still checked without replacement, so a locked environment value a task contradicts is refused with CONFIG_OVERRIDE_DENIED. A policy lock or minimum of enforce or above on a check the builder cannot run fails in Plan naming the constraint (see check levels). Signed, cached corporate policy carries the same entries and keeps working offline within its expiry.

Verification. Unit and library-level tests cover selectors, ordered bounds, overrides, the context rules, repository-relative folders, load-time conflicts, the check lifts, explain, Plan notes and the Plan failure. The compiled-CLI proof with a root-owned policy file is recorded in the status entry.

config status reports enrollment and cached-policy status. config refresh performs a headless request to the enrolled platform's public configuration-context endpoint. Signed responses use pinned Ed25519 keys, canonical JSON, identity/context binding, monotonic sequences, expiry and explicit offline permissions. Cache entries are content-addressed and flushed before an OS credential-store pointer commits them. A corrupt entry can only be repaired from a newly verified online response. Project constraints​

Status: implemented (configuration split step D9, migration item M20, OD17; status entry).

A project without central policy can make a rule hold in every folder with a [constraints] table in its root oyzu.toml. It uses the policy constraint and selector vocabulary and is applied after every ordinary value and before central policy, so a component folder cannot undercut it:

# root oyzu.toml only
[constraints."checks.tests"]
minimum = "required"
when = { context = ["release"] }

With services/oyzu.toml setting [checks] tests = "advisory", a release build of services runs its tests as required, and a local build keeps advisory.

Vocabulary. Each entry is a table, or a list of tables ([[constraints."checks.tests"]]), with the policy fields locked = true with value, minimum, maximum, allowed, required, when and unless; they mean exactly what they mean in policy, including ordered check levels, tool version matching and the "tools are refused, not replaced" rule. Name the setting by its whole path in quotes ([constraints."checks.tests"]). A default is refused: a project default is an ordinary value, written in the setting's own table. Only settings a project file can set may be constrained, and not env.* or tasks.*; credential destinations, trust controls and administrative settings are refused naming the setting.

Selectors. context and provider behave as in policy. path is the target's folder relative to the root oyzu.toml's folder (the configuration root: the Git top level, else the outermost folder with oyzu.toml, oyzu.local.toml or build.yaml, or --root), not the repository boundary policy paths use, so a project's own rules keep matching when it moves or sits inside a larger repository. explain --json reports it as policyFacts.projectPath.

Only the root file. A [constraints] table in any other file is an error naming the file: a component folder's oyzu.toml (CONFIG_SCOPE: app/oyzu.toml:1:1: [constraints] is allowed only in the root oyzu.toml, with the full paths), oyzu.local.toml, user or machine configuration, and a [context.<name>] or [profiles.<name>] table. Unknown optional sections are ignored with a warning, including names close to known sections ([Constraints], [constraint], [constriants], [check]). These warnings suggest the intended section; config validate --strict rejects such warnings when checking for spelling mistakes. An invalid entry is CONFIG_CONSTRAINT_INVALID naming the file, line and setting; entries that cannot hold together in one context fail as policy entries do.

Policy always wins. Project constraints are the inner layer, and a project can never loosen policy. A project constraint that cannot hold together with the policy constraints that apply to a build is set aside for that build:

  • a floor or ceiling of an ordered or numeric setting is clamped to what policy allows: a project minimum = "required" under a policy maximum = "enforce" becomes minimum = "enforce" and still raises a lower folder value to enforce, recorded as a project constraint override; a project maximum = "off" under a policy minimum = "enforce" becomes maximum = "enforce", and policy raises the value;
  • a lock, an allowed set or a required set policy rejects, or any project constraint where policy limits the setting with an allowed set, is dropped;
  • a coverage floor that would lift another check level across layers is resolved the same way: a policy coverage percentage lifts tests over a project lock of off (the project lock is dropped), and a project coverage floor that needs tests above a policy cap is dropped and lifts nothing.

Every command reports each one as a CONFIG_PROJECT_CONSTRAINT_SET_ASIDE warning naming the project constraint, the policy constraint and the value the build uses (checks.tests: project constraint minimum required in release (oyzu.toml [constraints]) is clamped to minimum enforce by admin policy maximum enforce (local-administration); checks.tests = enforce), so a project floor never disappears silently. When both layers apply and hold together, the project constraint replaces the folder value first and policy then replaces the project's value; each step is recorded.

Shown and recorded as policy overrides are, labelled project constraint instead of admin policy or org policy, with source oyzu.toml [constraints]: oyzu config explain lists it under Constraint overrides (checks.tests required project constraint minimum in release (project services/oyzu.toml sets advisory)) with a project-<kind> step in the resolution history and label in --json; Plan prints a project note; oyzu build --plan prints a Constraint: line; plan and manifest targets record it in extensions["oyzu.dev/policy-overrides"] with constraint.label; every command reports a CONFIG_CONSTRAINT_OVERRIDE warning (checks.tests = required by project constraint minimum in release (oyzu.toml [constraints]) instead of advisory from oyzu.toml). A project minimum of enforce or above on a check makes it run whatever checks.run says, as a policy one does. oyzu config validate --strict does not fail on CONFIG_CONSTRAINT_OVERRIDE or CONFIG_PROJECT_CONSTRAINT_SET_ASIDE (a constraint tightening a folder value is not a configuration error), but does fail on CONFIG_RELEASE_LOWERED, which asks for a deliberate [context.release] value or a fix.

Limits. --root selects the configuration root: oyzu --root app build reads app/oyzu.toml as the root file, and the repository root's [constraints] does not apply to that build. This is an accepted, known limit. The registered-section rule covers constraints and toolsets; targets joins it when that section is implemented (OD18).

Build inventory options​

Rust targets take Cargo features from with.features and cross-compilation targets from platforms entries, built by the native cross toolchain or the executor build.executors declares (Rust platforms). The former rust object (features and a targets list of Cargo triples that generated build-<triple> tasks) is refused naming that replacement.

build.yaml describes target intent separately from the TOML cascade. The python/app builder's optional with.container option is a boolean or a finite object with base, user, workdir and entrypoint; see Python application containers for types, defaults and current runtime support. The builder validates it when the inventory is read, and it is frozen with the target inventory. config validate rejects malformed option values without resolving images or executing a build. The object introduces no task language or additional precedence layer. Administrative execution checks and resolved owner settings still apply to generated image actions.

Existing settings migration and boundaries​

The Docker adapter registers docker.apparmorProfile, docker.frontends and docker.load. A builder applies a registered setting that adds a task (such as docker.load) from the target's resolved snapshot during discovery, never by reading files itself. docker.apparmorProfile replaces direct adapter reads of OYZU_BUILDKIT_APPARMOR_PROFILE; the legacy environment variable remains a diagnosed invocation input and faces the same policy constraints. The default still detects the host's AppArmor user-namespace restriction. Builder namespaces stay behind the crate-private Builder contract.

A frozen build configuration contributes its digest to target/action records. Formatting, profile names and presentation preferences do not affect that configuration digest. Policy revision and online/offline context remain separate evidence. No policy snapshot grants signing, publishing or credential issuance.

Build preparation and planning require the resolved invocation snapshot and every selected target's snapshot, including inferred targets without configuration files. Missing internal snapshots fail with CONFIG_INVALID_VALUE; they never disable policy checks or cause adapters to recalculate defaults. Library callers must use discovery to obtain this state; serialized discovery JSON is an inspection result, not a resumable workspace. Rediscover the workspace if that state is missing. Docker reads its execution profile from the admitted snapshot before preparation starts. Later edits to live configuration files do not change an already frozen plan; start a new invocation to resolve them.

The current native tool-store, authenticated platform-session, connector-binding and shell-secret-consumer implementations are not completed by this configuration change; the remote action cache is an experimental development-scope implementation that signs in only with a token from OYZU_CACHE_TOKEN or a CI job's ID tokens (see the action cache). Explicit tool requests that cannot be bound to a verified installation are rejected before builds. Enforced routes/catalogs requiring unavailable bindings fail before public acquisition. Managed builders that still require public dependency preparation are blocked; offline-capable local Docker and Helm preparation remains separate from those network paths. Development secret references require an authorized consumer and are not substituted into build literals. build.jobs bounds concurrent ready actions. The invocation uses the smallest admitted root/target ceiling; each target retains serial mutation and hook order. Targets have private workspaces and output roots. Dependency or deferred-report failure blocks consumers while independent targets can finish. ui.color controls human-readable task labels and outcome statuses: always emits ANSI color, never disables it, and auto enables it only when the relevant output stream is a terminal. Task-specific resolved preferences apply to that task; root tasks use root preferences. JSON output remains unstyled. Cache preferences do not grant cache credentials or trust: a remote hit is a development result.

These boundaries are deliberate failures rather than claims that all OEP-0002 ecosystem and platform integration acceptance cases pass. Three-host ACL/keychain qualification, signed server interoperability, authenticated logout/account-switch flows, complete connector routing and tool-store integration remain release gates.

Development execution checks tool eligibility, explicit tool requests and protected routing/catalog requirements before any prerequisite or hook runs. Managed host tasks remain blocked until approved development execution and connector bindings exist; the host runner cannot claim to enforce managed network routing. Task-specific and native-adapter environment additions must satisfy administrative environment restrictions. Each build's own task cascade determines whether a root hook or stage replacement reaches it, is replaced by a nearer or qualified definition, or is removed, consistently with inspection and build planning (task binding).

Offline execution requires explicit signed permission and remains bounded by both signed expiry and maximum offline age (at most 24 hours). CI requires online policy. Transport retry/backoff preserves these deadlines; denial and malformed responses do not authorize offline fallback. Explicit refresh can fail while an older valid cache remains stored. A corrupt cache entry requires a newly verified online response; damaged integrity-store state can require administrator intervention. Refresh rechecks time after I/O, so a request that finishes after a deadline does not extend authorization.

Changing protected bootstrap pins invalidates the previous cache binding. Recovery requires an online response verified against the current pins with a strictly newer policy sequence; existing high-water state remains in force. Do not delete credential-store state as a key-rotation procedure. Cache commit ordering preserves the old committed pointer until the new entry has been flushed; full crash/reboot qualification remains a release gate.

Platform sign-in is the separate oyzu auth; there are no enrollment commands in this delivery. Revisit session-to-policy identity binding, account/organization switching, logout invalidation, credential lifecycle, authenticated refresh and CI identity, plus end-to-end server interoperability. Configuration policy is not a login session and does not grant publishing/signing authority. Connector credentials, shell secrets, verified tool installation and remote action caching also remain separate integrations.

Bootstrap presentation options​

Global verbosity and OYZU_LOG are typed invocation-only presentation inputs, resolved before any project session. They are not project keys and never enter effective execution snapshots or configuration digests. Explicit CLI controls override the complete environment filter. Help/version do not resolve it. See CLI diagnostic controls for grammar and errors.

Tool lock execution-platform coverage​

[tools] declarations can also be written, replaced and removed with oyzu install SPEC, oyzu uninstall and -g/--local, and in a toolset with oyzu --toolset NAME install SPEC, which keep comments and lock the result; see tool commands.

A declaration is a version string, or mise's option-table form with only a version key (node = { version = "22" }), which validation normalizes to that string so every consumer sees one form. Edits change only the table's version. Unknown option keys warn and are ignored; they do not install hooks, select platforms or change acquisition. A table without a valid version string still fails with CONFIG_INVALID_VALUE; see option tables.

tools.platforms is an optional project string set (never a profile value) consumed through the normal configuration cascade. It restricts Rust lock metadata coverage, not the artifact matrix or installation authority. When absent, pin uses the finite default metadata platforms. An empty or unsupported selection fails pin. Values are exact OS/architecture/ABI tuples; this setting is not a tool version request. No schema version changes.
