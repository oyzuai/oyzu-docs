Configuration behavior

CLI reference

Published from the canonical docs/reference/configuration.md file. Features marked experimental remain experimental; check support limitations before relying on them.

This page explains how Oyzu combines configuration: where the files live, which value wins, how contexts, profiles and toolsets change values, and how policy limits them. For every oyzu.toml section and key with examples, see the oyzu.toml reference. The build.yaml rules are further down.

Note: Configuration commands, their JSON output and several policy features are experimental and may change.

Try it​

Configuration commands need no platform account, Docker, native toolchain or network. Save this as oyzu.toml in an empty directory named config-demo:

[build]
jobs = 2

[profile]
default = "dev"

[profiles.dev.build]
jobs = 3

[ui]
color = "never"

From its parent directory:

oyzu --root config-demo config get build.jobs
oyzu --root config-demo --no-profile config get build.jobs
oyzu --root config-demo config validate --strict --all-profiles
oyzu --root config-demo --profile dev config set build.jobs 4 --project
oyzu --root config-demo config get build.jobs
oyzu --root config-demo --profile dev config unset build.jobs --project
oyzu --root config-demo config get build.jobs

The get commands print 3, 2, 4 and 2. Validation succeeds (valid: true with --json). Removing the profile assignment exposes the base value; it does not restore the old 3. set and unset print the file they changed and the key.

  • The machine directory holds config.toml plus the protected files admin-settings.json (administrative policy) and management.json (enrollment). See administrative policy.
  • Project files are oyzu.toml (commit it) and oyzu.local.toml (personal overrides; keep it out of version control).
  • A relative XDG_* path produces a warning and the home fallback is used.
  • OYZU_USER_CONFIG selects an absolute path for the user configuration file, which is useful for disposable environments. Relative paths are rejected. The file keeps user-level precedence, its sibling oyzu.lock holds user-default tool pins, and the variable cannot redirect machine policy, enrollment or state.
  • On Windows, an absolute HOME that differs from the native profile moves persistent user data, including the tool store, to <HOME>/AppData/Local/Oyzu. This isolates tool caches in disposable homes. A relative HOME fails with CONFIG_SCOPE. Configuration and policy state locations and the action and image caches do not move, and existing data is not moved or deleted.
  • Managed policy entries live under the user state directory. Integrity pointers are kept in the operating system credential store.
  • A configuration file may be at most 1 MiB. There is no include mechanism and no executable configuration language.
  • Oyzu does not enroll a machine automatically.

Inspection and selection​

oyzu --root path/to/project config show --json
oyzu --root path/to/project config explain build.jobs --json
oyzu --root path/to/project config profiles
oyzu --root path/to/project config validate --strict --all-profiles
oyzu --root path/to/project --profile integration run test
oyzu --root path/to/project --no-profile run test

Which project root is used​

  • --root fixes the build root and the configuration root. -C / --directory sets the invocation directory; --root alone also sets it.
  • Without --root, the nearest ancestor build.yaml that is an Oyzu inventory (see which build.yaml files are Oyzu's) within the current Git worktree selects the build. Configuration still inherits from the Git worktree root.
  • Outside Git, the outermost ancestor with Oyzu configuration or a build declaration bounds inheritance, falling back to the invocation directory.
  • A folder counts as a Git root when it has HEAD plus the objects and refs directories, or a .git file whose gitdir: pointer leads to them. Linked worktrees use their commondir pointer. An empty .git directory or a malformed pointer does not define a workspace. Oyzu reads this metadata without running Git.
  • Entering an independent nested example and running oyzu build --plan selects that example. Its oyzu.lock and outputs belong to it, parent inventories are not merged, and automatic discovery skips nested build roots. An explicit parent target path still works. Composing roots and sharing a lock between roots are not supported.
  • A selected build root may declare profile.default. Ordinary target subdirectories may not.
  • A task cwd is relative to the TOML file that declares it. Two targets cannot own the same native build unit.

Precedence​

Lowest first:

  1. built-in defaults
  2. organization policy defaults (when the machine is enrolled)
  3. administrative defaults on the machine
  4. machine configuration
  5. user configuration
  6. each oyzu.toml from the project root down to the build's folder
  7. each included oyzu.local.toml in the same order
  8. invocation inputs (flags and OYZU_* variables)

Each source applies its base values, then the selected profile. Each sibling target gets its own snapshot. Administrative constraints and project constraints are applied last.

  • Arrays replace; they do not merge. A task replaces the whole task record.
  • [overrides].remove removes explicit environment and task entries. Removed environment entries are also unset in development task environments.
  • A task env can replace a global variable of the same spelling. Names that differ only in case (TOKEN and token) are rejected on every host.
  • Tool aliases share the same precedence: a project node = "22" overrides a global "oyzu:node" = "latest". Inspection keeps the spellings with the winning source. Two aliases of one tool in the same overlay are ambiguous. Constraints bind a tool whatever its spelling.

Profiles​

Oyzu picks the profile in this order: --profile or --no-profile, the profile a task inherited, OYZU_PROFILE, the root profile.default, the inferred ci profile (empty unless you define it), then no profile. Profile names grant no authority.

In CI, user computation settings and local files are left out and are not parsed. --local-overrides asks for local files, subject to administrative restrictions.

What the config commands do​

show, get, explain, profiles and validate never run project tasks.

  • If resolution is blocked, show and explain report an unresolved status with no effective values, and exit successfully. validate is the failing command.
  • Project and local files may not set platform.url, platform.account, cache.remote, cache.ciRemote, trust.enabled or trust.parents. Even show and explain fail with a CONFIG_SCOPE error that names the key, the file and where to set it instead.
  • Environment values, credential-like names, recognizable sensitive values and task bodies are redacted. Use oyzu env to inspect the environment.
  • Unknown optional settings produce a warning and have no effect. This covers unknown sections, fields under [toolsets.<name>], controls under [env._], and unknown fields inside tool requests, secret references, task report declarations, publication destinations, registry routes and engine or plugin package sources. A close spelling gets a hint. Known fields still validate. Unknown enum values and destination kinds are errors.
  • If a project needs a feature older CLIs lack, declare it in [compatibility].requires so they refuse instead of ignoring it.
  • Duplicate keys, known invalid values, unsupported required capabilities and unsupported schema majors fail. --strict also fails on warnings. --all-profiles also validates profiles that are not selected.
  • Resolving an enrolled configuration can contact the policy endpoint and update its cache, so inspection is not always network-free.

Environment and tasks​

  • A literal [env] value is the only value a task placeholder can read ({env.NAME}). Ambient variables and secret references never are.
  • Literals can enter build inputs and evidence, so do not use one as a secret store. Secret references need an authorized consumer and are not substituted into build values yet.
  • A task has either run (a shell command) or argv (an argument array), plus optional shell, cwd, env, depends_on, inputs, outputs, cache, interactive, reports, when and unless. argv elements and the task's own env values can use {namespace.name} placeholders. See task and hook conditions.
  • cache = true with outputs makes an authored task cacheable by oyzu build. See authored tasks.
  • Arguments after -- are appended to an argv task. A run task rejects them.
  • oyzu run inherits stdin. Tasks that record a bundle copy stdout and stderr live and keep them in dist/logs. interactive = true keeps the real terminal and captures no logs, and for PowerShell it also drops -NonInteractive. JSON mode captures output and keeps stdin. See task streams and limits.
  • A task needs a discoverable native project to run.
[tasks.hello]
argv = ["node", "-e", "console.log('hello')"]

[overrides]
remove = ["env.DEMO_MODE", "tasks.inherited"]

oyzu --root path/to/project run hello runs the first task. [overrides].remove takes dotted keys.

Local and CI execution context​

Oyzu reads CI hints from the environment once, when the configuration session opens (before build workers set their own CI=true). Detection is offline and does not depend on terminals, hostnames, networks or the operating system. Detected context is a hint only. It never proves who is running the build and never grants publication, credentials or cache authority.

A marker counts when it is set to a nonempty value other than false, 0, no or off (case-insensitive).

What plain oyzu build runs​

A plain oyzu build builds and packages artifacts and runs any check at level required. In the pr, ci and release contexts it also runs every check that is not off (see check levels). oyzu build --full runs every check that is not off in any context. oyzu --profile ci build does too, because the built-in ci profile sets checks.run = "all". A different profile or --no-profile does not turn off the checks of a detected CI context. To change that, edit oyzu.toml. See build context behavior.

Build context​

Every build resolves one context: local, pr, ci or release.

  • With no CI signal the context is local. Any CI marker gives at least ci. A pull request or tag signal of a matched provider raises it to pr or release. When signals conflict the more demanding one wins (release over pr over ci). Detection never fails a build.
  • Only fixed literals (such as =tag) are ever recorded as signals, never values.

Overrides. oyzu build --context <name> or OYZU_CONTEXT=<name> pins the context. The flag wins. An unknown name is the only context error (CONTEXT_INVALID), and because every command that opens a configuration session resolves the context, a bad OYZU_CONTEXT also fails install, exec and config get.

Under a vendor CI marker a pin can raise the context but not lower it. The pin is ignored with a CONTEXT_OVERRIDE_IGNORED warning. With only the generic CI hint, or no signal, a pin can also lower it. Set OYZU_CONTEXT=release once in a manually triggered release workflow, which carries no tag signal.

Where the context is recorded. Build plans (--plan, --plan --json) and manifests record it in extensions["oyzu.dev/execution-context"].context: detected, requested, effective, policy (the stricter of detected and requested, which policy constraints evaluate) and a note. oyzu config explain context shows the value, source and deciding signal.

The same record has fork for task conditions. It is false outside a detected pull request. Inside one it says whether the pull request comes from a fork, read from the GitHub Actions event payload (GITHUB_EVENT_PATH) or from GitLab's CI_MERGE_REQUEST_SOURCE_PROJECT_ID and CI_MERGE_REQUEST_PROJECT_ID. It is absent when the provider does not say.

Per-context values​

Any setting can take a value that applies only in one context. Write it in the same oyzu.toml as the base value:

[checks]
coverageMinimum = 50

[context.release.checks]
coverageMinimum = 90

[context.pr]
checks.coverageMinimum = 70

The table is [context.<name>] with <name> exactly local, pr, ci or release. Inside it, tables and dotted keys are written as for the base value. Context tables are valid wherever the setting is valid (user, project root, component folder, oyzu.local.toml) and follow its scope rules. A project file still cannot set cache.remote or trust.enabled under a context.

Precedence within and between files​

Within one file, lowest first:

  1. the base value
  2. the ci profile, when CI detection (not you) selected it
  3. the value for the effective context
  4. a profile you chose (--profile, OYZU_PROFILE, a task's inherited profile or profile.default)

So an inferred [profiles.ci] loses to the same file's [context.ci.*], while --profile ci beats it.

Between files, the nearer scope wins as for any setting. A component folder's base value beats the root's [context.release] value. To vary a component by context, write a [context.release] table in the component's own file. A context table never applies when its context is not the effective one.

Project constraints, then administrative constraints, apply after every ordinary value, including context values and chosen profiles. See policy constraints and selectors.

Release lowering warning​

In a release build, if a nearer folder's value leaves a check level (checks.tests, checks.coverage, checks.lint or checks.format) below what a farther folder's [context.release] table asked for, every command that resolves it reports CONFIG_RELEASE_LOWERED, naming both files and lines:

checks.tests = advisory from app/oyzu.toml:2 lowers required from oyzu.toml:5 [context.release] in this release build
  • The nearer value still wins. The warning only makes the lowering visible.
  • A nearer folder's own [context.release] value is deliberate and never warns.
  • oyzu config validate --strict fails on this warning.
  • Plans show it as a lowered note (oyzu build --plan prints Lowered:, --plan --json has releaseLowerings), and plan and manifest targets record it under extensions["oyzu.dev/release-lowerings"].

To make lowering impossible, use a project constraint.

Per target or once per build​

Most settings (checks, tasks, environment) resolve per target from the target's folder chain, like tool pins. A root value applies to every target, a value in docs-site/oyzu.toml applies to targets under docs-site/, and targets in one folder share settings. There are no target-keyed sections.

Some settings are decided once for the whole build:

  • scheduling, presentation and selector settings: build.jobs, build.isolation, ui.color, profile.default, config.*
  • the whole cache.* family

For these, [context.<name>] values are accepted in the user file, the project root oyzu.toml and oyzu.local.toml. In a component folder they are a configuration error. profile.default and config.* cannot vary by context at all, and cache.remote, cache.ciRemote and cache.dir are accepted only from user scope. scan.jobs is per target.

A component folder's base value for a once-per-build setting is still read for its targets, and the build combines them. build.jobs is the minimum over the build root and every selected target. explain reports that minimum and lists the folders with their own value under targetValues.

Root-only settings (publish.* and build.bundleDirectory) go further: no file outside the project root folder may hold a value at all, in a base, context or profile table. The [constraints] table follows the same rule.

Errors​

These are configuration errors with file:line:column:

  • an unknown context name ([context.relese]), reported as CONFIG_CONTEXT_UNKNOWN
  • a context table that is not a table, an invalid value, a setting that cannot vary by profile or context, compatibility or overrides inside a context, a once-per-build setting in a component folder, and tool pins ([context.<name>.tools] is not supported), reported as CONFIG_CONTEXT_INVALID

A setting a project may never set (such as cache.remote) keeps its CONFIG_SCOPE refusal, now naming the full key (context.release.cache.remote). An unknown setting under a context table is an inert warning, as in the base.

Explaining and recording​

oyzu config explain <setting> [--context <name>] [--target <name>] resolves the setting as that context (default: the detected or pinned one) for that build.yaml target (default: the current folder). It prints the value, every scope that set it with the table's context, the contextValues considered (applied, overridden or not this context in the human view), and resolution (perTarget, perBuild or projectRoot). A once-per-build or root-only setting is read at the project root whatever --target names.

--context and --target cannot be combined with --global, --project or --local. An unknown target fails with CONFIG_TARGET_UNKNOWN and lists the declared targets. oyzu build --plan --json (per target as contextValues) and the plan and manifest targets of a bundle (extensions["oyzu.dev/context-values"]) list the settings whose effective value came from a context table, so a build can be reproduced under --context. Docker image builds do not record this yet.

Check levels​

Each check a builder offers has one level. The checks are tests, coverage, lint and format. An old checks.required line is an unknown-setting warning with no effect.

How checks map to stages​

  • The test stage serves tests and coverage. Tests collect coverage, so tests = "off" also turns coverage off.
  • lint serves lint, and format-check serves format.
  • A stage runs when any check it serves runs, and is off when every check it serves is off.
  • Each report is judged by its own check. With tests = "advisory", a failing test report is a warning, but the coverage report follows checks.coverage, so required or enforced coverage (including a shortfall below checks.coverageMinimum) still fails the build.
  • Builders derive tool requirements from the stages that run. With format = "off" the Rust builder no longer adds rustfmt. A component you declare yourself, such as components = ["rustfmt"] in rust-toolchain.toml, stays a requirement.

Coverage off only turns off judging. Builders collect coverage with the test command, which does not change with the level. With checks.coverage = "off" and tests running, coverage is still collected and its tools are still prepared, but it is never judged: no minimum, the report is not required, and a missing or invalid coverage report is a warning. Plans say Collected with test; not judged (checks.coverage = off). Running tests without coverage collection is not available yet.

Levels resolve per target from the folder chain: the nearest folder wins, and a context value beats the base value in the same file. An administrative constraint still wins. A lock or minimum replaces a project value below it and the plan says so (format enforce · admin policy minimum in pr, release (project oyzu.toml sets off)). An allowed set such as ["enforce", "required"] refuses a project value outside it with CONFIG_OVERRIDE_DENIED.

Toolsets​

A toolset is a named set of tool versions for testing builds on other tools than the ones they ship with, and for running commands with them. oyzu build adds a toolset's verification run for each build whose builder uses one of its tools: in every context but local unless the toolset lists contexts, and locally with oyzu build --verify-with NAME. A run repeats the build and test stages with the toolset's tools and never ships an artifact. See verification toolsets.

Define a toolset in a project's oyzu.toml or oyzu.local.toml:

[tools]
rust = "1.99.1"

[toolsets.go-test.tools]
go = "1.24.13"

[toolsets.node24]
contexts = ["ci", "release"]          # optional; default: every context but local
platforms = ["linux/x86_64"]          # optional; default: one run, on the build's first declared platform or the host
tools.node = "24"

Select it for one invocation with the global --toolset NAME option:

oyzu --toolset go-test install --frozen
oyzu --toolset go-test exec -- go version

A profile cannot change tools. [profiles.<name>.tools] (or a tools key in a profile table) is refused in every file with CONFIG_PROFILE_TOOLS, which shows the toolset that replaces it:

CONFIG_PROFILE_TOOLS: oyzu.toml:4:1: [profiles.x.tools] is not allowed: a profile cannot change tools, so the tools a build uses never depend on the selected profile. Move the table to a toolset:
  [toolsets.x.tools]
  go = "1.24.13"
and select it with `oyzu --toolset x exec -- …` (also run, env, activate, which, install, update and uninstall)

Commands that accept --toolset​

--toolset works with exec, run, env, activate (an activated shell keeps the toolset on every prompt), which, pin (locks only that toolset's tools), and the project-scoped install (without specs it installs, and locks when needed, the toolset's tools; with specs it declares them in [toolsets.NAME.tools]), update and uninstall (both act on that toolset's declarations and lock sets only).

Every other command refuses it with TOOLSET_UNSUPPORTED, as do activate --shims and --global installs, updates and removals. oyzu build refuses it with TOOLSET_BUILD_REFUSED and points to oyzu build --verify-with NAME: a build always uses the [tools] versions, so a toolset never changes what ships.

Verification runs​

  • contexts lists the contexts (local, pr, ci, release) whose builds run the toolset's verification runs. Without it a toolset runs in pr, ci and release, never local. contexts = [] turns it (or an inherited definition) off.
  • platforms lists the os/arch[/abi] platforms to make one run each for. Without it there is one run, assigned to the build's first declared platform (the host's when the build declares none).
  • A toolset applies only to builds whose builder uses one of its tools, so a Go toolset adds nothing to a Node build in the same folder.

Precedence​

  • The toolset's tool requests replace the cascade's, above every file (a nearer folder's [tools] value included) and below policy. Administrative and project constraints still bind a toolset's tools, and a value outside a policy lock fails with CONFIG_OVERRIDE_DENIED.
  • Tools the toolset does not name keep their cascade value.
  • A toolset is exempt from native pin agreement. A toolset Go below the go.mod minimum is used as written.
  • oyzu tools current --all lists toolset declarations with their toolset.

Inheritance​

One definition of a name applies, whole, as tasks do: the last one in source order, which is every oyzu.toml from the root to the folder, then every included oyzu.local.toml from the root to the folder. A nearer oyzu.toml replaces a farther one, and any included oyzu.local.toml that defines the name replaces every oyzu.toml.

The folder you run from must have the name in its chain, or the command fails with CONFIG_TOOLSET_UNKNOWN and lists the toolsets defined there. A build target in another folder chain keeps its cascade tools.

Validation​

A toolset holds its tools table and optionally contexts and platforms. Unknown optional fields warn and are ignored. These are CONFIG_TOOLSET_INVALID errors: unknown contexts, repeated or empty platform lists, and non-tool keys such as platforms or ignore under tools. Toolsets are refused in user, machine and administrative configuration and inside [profiles.*] or [context.*] tables (CONFIG_SCOPE).

Lock file and nested commands​

  • The tools a toolset declares itself are locked in oyzu.lock as their own request sets, labelled toolset = "NAME", beside the unlabelled [tools] sets. Tools it inherits from [tools] stay in the [tools] sets.
  • A toolset's install, update, uninstall, install SPEC and the automatic install of exec and run change only that toolset's sets. The [tools] commands never rewrite a toolset's. oyzu --toolset NAME update re-resolves only the tools that toolset declares.
  • One request string resolves to one version in the whole lock, so a request a toolset shares with [tools] uses the same pin, and updating it updates it everywhere. uninstall in one scope never removes a pin another scope uses, and tells you where the tool is still declared.
  • oyzu pin locks, for each build, the tools each toolset in that folder supplies. oyzu --toolset NAME pin locks only that toolset's tools. Plain oyzu update re-resolves [tools] and then each toolset. oyzu install --frozen writes nothing and replays the pins its requests need.
  • A task run with oyzu --toolset NAME run sets OYZU_INHERITED_TOOLSET (@none when the task runs without one), so a nested exec, run, env, activate, which, install, update or uninstall keeps the task's toolset. Every other nested command, oyzu build included, removes the variable, so plans and cache keys never depend on a toolset they do not record.

Toolsets in nested folders are not locked. Only a toolset defined in the project root's oyzu.toml or oyzu.local.toml is locked. For one defined (or redefined) in a nested folder's file, --toolset NAME install, install SPEC, update, uninstall, pin, and any exec, run or verification run that would install or lock its tools, fail with TOOLSET_NESTED_LOCK, name the file and change nothing. exec, run, env and which still work when the tools are already locked. Plain oyzu pin and oyzu update leave such a toolset out, list it under Toolsets not locked (toolsetsNotLocked in JSON) with the reason, and still succeed. They do the same for a toolset whose tools policy refuses.

Standalone publication settings​

oyzu publish reads these settings. See publishing for a complete example, the evidence profile and current limits.

  • publish.default selects a named destination or set when oyzu publish has no --destination.
  • publish.destinations maps names to registry, repository and optional paired usernameEnv / passwordEnv credential references.
  • publish.sets maps names to nonempty destination lists. Destination and set names must differ. Every selected destination is required.
  • publish.requirements holds provenance (bundlePath, an accepted Ed25519 publicKey, builderId) and signing (keyEnv, publicKey). Public keys are base64 raw 32-byte keys. keyEnv names a separately provisioned variable holding a base64 32-byte signing seed. Never store secret values in project configuration. Evidence paths resolve relative to the file that declares the requirements.

Configure it once, at the project root. Only the project root folder's oyzu.toml and oyzu.local.toml may set publish.*, in a base, [context.<name>] or profile table. A [publish] table anywhere else is a configuration error, for every command that reads configuration:

CONFIG_SCOPE: <root>/api/oyzu.toml:1:1: [publish] is allowed only in the root oyzu.toml (<root>/oyzu.toml); move it there: publishing is configured once, for the whole project

oyzu config explain publish.default reports resolution: projectRoot. Independently released packages still publish separately, because destinations select artifacts by build.

Otherwise these settings use the normal cascade (user, root project and root local files), selected profiles and constraints. The destinations map, sets map and requirements object are replaced whole by a later source, not merged. They set standalone safeguards only and cannot grant managed publication authority. The builds, outputs and platforms their selectors name are checked before any build action runs (see names that cross files).

Build inventory migration​

build.yaml says what is built. A builds mapping holds one entry per build with these fields: uses, path, platforms, depends_on, inputs, materialize, bindings, fetches and with. Any other field fails with CONFIG_INVALID_VALUE naming it.

  • depends_on orders builds only; it does not transfer artifacts.
  • inputs names extra source paths a build reads (declared inputs).
  • fetches declares pinned downloads (declared fetches).
  • bindings writes a produced image's reference into a chart's values during the build (image bindings).
  • with holds builder-specific options, validated by the selected builder (for Rust, see build options).

Tool requirements stay in TOML, and resolved tool identities stay in oyzu.lock. Configuration normalizes the inventory and freezes all declared platforms.

The root keys are builds, members and exclude. Any other root key fails with CONFIG_INVALID_VALUE naming it. members is not supported yet and is refused. exclude lists folders where discovery recognizes a build that is deliberately not one.

Letting discovery fill in uses​

uses is optional. web: {path: web} is a complete entry when exactly one builder recognizes web, and discovery freezes that builder into the inventory before planning. A folder that no builder or several builders recognize fails, naming the candidates and the line to write.

  • Folders discovery recognizes but the inventory leaves out are listed by oyzu discover and oyzu build --plan, and never built. oyzu discover --write declares them, and oyzu discover --check fails on them in CI.
  • A folder that a declared build's native workspace manifest lists as a member (Cargo members, go.work use, npm, Yarn or pnpm workspaces) is covered by that build and needs no entry. See discovery.
  • oyzu config validate checks chart bindings (unknown producers, repository and values fields) without discovery. Checks that depend on an omitted uses (the build's with options, bindings only on helm/chart builds, a docker/image producer) wait until discovery infers the builder, as oyzu discover and oyzu build --plan do.

Which build.yaml files are Oyzu's​

Other tools use the same file name. Dart's build_runner reads a build.yaml with targets:, builders: and global_options:. A build.yaml is an Oyzu inventory only when its root has builds, members or exclude, or the refused flat shape (a top-level entry whose mapping has uses). A file that is not valid YAML also counts, so its syntax error is reported instead of the file being skipped.

A misspelled envelope counts too, and fails naming the root keys (found build (did you mean builds:?)). That covers a root key equal to builds, members or exclude ignoring case, the key build, or any root key with uses two levels below it (buildz: {web: {uses: node/app}}). A leading UTF-8 byte order mark is ignored.

Any other build.yaml, including an empty one, belongs to another tool:

  • It never makes its folder a build root, a project root or a configuration boundary.
  • Discovery and oyzu discover --check continue below its folder as if it were absent, so a Flutter package in a monorepo no longer hides the builds under it.
  • At the project root, zero-config discovery decides the builds, and every discovering command (oyzu build, --plan, discover, run) warns CONFIG_BUILD_FILE_IGNORED: build.yaml: ignored, not an Oyzu inventory … naming its root keys (a JSON diagnostic event on stderr with --json).
  • oyzu discover lists it under Skipped with its root keys. JSON records it in skipped_build_files (plain oyzu discover without an inventory) or skippedBuildFiles (the inventory record), each entry {path, keys}.

oyzu discover --write never edits another tool's build.yaml at the project root. It fails with CONFIG_INVALID_VALUE naming the file's root keys and leaves it unchanged. An Oyzu inventory cannot share that file, so such a folder can only use zero-config discovery.

Where a build.yaml error is​

Every refusal of a build.yaml names the place to fix it as build.yaml:LINE:COLUMN: after the code. Lines and columns start at 1. This covers YAML syntax errors (CONFIG_SYNTAX), anchors, aliases, tags, merge keys and duplicate keys (an inventory uses none of them; CONFIG_SYNTAX or CONFIG_DUPLICATE), the flat shape and wrong root keys, unknown, moved or retired build fields, bad uses, platforms, materialize, bindings and fetches values, unknown dependencies, a builder discovery cannot infer, and with options a builder refuses (at the option when the message names it, otherwise at with).

✗ CONFIG_SYNTAX: build.yaml:3:6: invalid YAML: while parsing a flow mapping, did not find expected ',' or '}'
✗ CONFIG_INVALID_VALUE: build.yaml:5:7: docker/image with.repository must be a repository name without scheme, tag or digest

With --json the same text is the error record's error. YAML follows the 1.2 core schema: true, ~, 12 and 1.5 are a boolean, null, integer and float, while yes, on and 1.2.3 stay strings.

Build inventory options​

Rust targets take Cargo features from with.features and cross-compilation targets from platforms entries, built by the native cross toolchain or the executor build.executors declares (see Rust platforms).

The python/app builder's optional with.container is a boolean or an object with base, user, workdir and entrypoint. See Python application containers for types and defaults. The builder validates it when the inventory is read, so oyzu config validate rejects malformed values without resolving images or running a build.

Editor schemas​

Oyzu generates a JSON Schema for each of its two files, so an editor can complete keys and flag a wrong value or a key in the wrong file while you type. The build.yaml schema covers the root keys and every build field. The oyzu.toml schema covers every registered setting and the sections the reader accepts (profiles, context, toolsets, constraints, overrides, compatibility). Builder with options and settings a plugin registers are left open. Defaults that depend on the host (the CPU count for build.jobs, the Docker AppArmor profile) are described, not written into the schema's default.

The schemas flag what the CLI refuses, with two deliberate differences:

  • In build.yaml, paths (path, inputs, materialize to and into) may not contain \ or :, so a file stays portable across Windows, macOS and Linux. The CLI decides such a path where it is used.
  • In oyzu.toml, a build.yaml key such as [builds.web], exclude or a top-level uses is refused by the schema, while the CLI only warns (CONFIG_UNKNOWN_OPTIONAL). Other unknown keys stay open in the schema because the CLI warns about them and oyzu config validate --strict refuses them.

The CLI's own checks stay the authority, including rules a schema cannot express (a value accepted only from user configuration, a root-only section, which ABIs an OS has).

FilePublished at (every release, unversioned)
build.yamlhttps://github.com/oyzuai/oyzu-releases/releases/latest/download/build.yaml.schema.json
oyzu.tomlhttps://github.com/oyzuai/oyzu-releases/releases/latest/download/oyzu.toml.schema.json

oyzu config schema prints them without a project, configuration session or network, so you can keep a saved copy for offline machines:

oyzu config schema                       # both files, their URLs and how to print each
oyzu config schema build.yaml > build.yaml.schema.json
oyzu config schema oyzu.toml  > oyzu.toml.schema.json
oyzu --json config schema build.yaml     # {"kind": "config-schema", "file", "asset", "url", "print", "schema"}

With a file named, the schema itself is the output, printed as JSON in both modes (--json wraps it in the record above). Without one, --json prints {"kind": "config-schemas", "schemas": [...]}.

To point an editor at them:

  • build.yaml: the YAML language server (VS Code's YAML extension and others) reads a first-line comment, # yaml-language-server: $schema=https://github.com/oyzuai/oyzu-releases/releases/latest/download/build.yaml.schema.json. oyzu discover --write adds it when it creates or edits build.yaml and the file has no such comment. Add it by hand to a file you write yourself. build.yaml is not registered with SchemaStore, because SchemaStore already lists Dart's build configuration for that name.
  • oyzu.toml: point Taplo or Even Better TOML at the URL, using Taplo's [[schema]] setting or a #:schema <URL> first line. Oyzu's schema is not registered with SchemaStore, so editors do not find it by file name.

Editing​

oyzu --root path/to/project config set build.jobs 8 --project
oyzu --root path/to/project config set checks.tests required --local
oyzu --root path/to/project --profile dev config set ui.color never --global
oyzu --root path/to/project config unset build.jobs --project
  • Exactly one of --global (the user configuration file), --project or --local is required. --directory can select a nested project scope.
  • unset removes the assignment from that file and exposes inherited values. It does not leave a removal marker.
  • Edits keep unrelated comments and unknown syntax, validate known types and scopes, and compare the original bytes before an atomic replace. A concurrent change gives CONFIG_EDIT_CONFLICT. A small .oyzu-config-edit.lock file coordinates Oyzu writers.
  • Edits work even when resolution is blocked, so you can repair invalid values. They cannot repair malformed TOML (fix the syntax in an editor first) and cannot change administrative or enrollment records.
  • Only an explicit --profile NAME writes into that profile. Without it the edit goes to the base section, even when a profile is inferred or defaulted.
  • A profile cannot hold tools: config set tools.NAME VALUE --profile P fails with CONFIG_PROFILE_TOOLS. Use oyzu --toolset P install NAME@VERSION.
  • Booleans and numbers are parsed by type and strings are literal. Use --json-value for arrays or objects.

Trusted environment and credential destinations​

Some settings decide trust or where credentials go. Project and local files (including profiles) may not set trust.enabled, trust.parents, platform.url, platform.account, platform.authentication.provider, cache.remote or cache.ciRemote. Set them in user, machine or administrative configuration.

  • trust.enabled (boolean, default true) and trust.parents (absolute folder paths, default []) control folder trust.
  • These invocation environment variables override ordinary files and remain subject to administrative constraints: OYZU_PROJECT_TRUST (true/false, on/off, yes/no or 1/0), OYZU_PLATFORM_URL, OYZU_PLATFORM_ACCOUNT, OYZU_PLATFORM_AUTH_PROVIDER, OYZU_CACHE_REMOTE and OYZU_CACHE_CI_REMOTE.
  • The plugin and engine settings are in the same group (see plugins and engines). In CI, PR and release contexts the engine development override is not available.

Administrative policy​

Administrators can add limits that ordinary files cannot override. They live in protected files that must be owned and writable only by an administrator: Windows uses ACL checks, Unix checks root ownership and write permissions, and macOS also rejects non-root ACL grants. An insecure, unreadable or malformed enrollment never turns into standalone mode.

admin-settings.json uses the same constraint evaluator as organization policy. Locks, allowed values, numeric and ordered bounds and required sets combine independently of ordinary precedence. An empty ordinary array cannot remove a required check. The planner requires every configured check to have a real action and report, and report collection enforces the coverage minimum, including missing or zero-denominator coverage failures.

Policy constraints and selectors​

Central policy has two forms. A default ("default": …) is an ordinary inherited value that a project can override. A constraint is a limit applied after every ordinary value (base, context and profile values, flags) that a project cannot go past.

Tool versions​

A tool request (tools.<name>) under a lock or allowed set is refused, not replaced, because a requested version is never silently substituted.

  • A constraint binds every spelling of the tool. A lock on tools.rust also refuses [tools] "oyzu:rust" = "1.90" or "core:rust".
  • A tool lock supplies the request and binds every target whose builder needs or detects the tool, whether or not the project pins it. Deleting [tools] rust cannot avoid a release lock on Rust. If the locked version cannot be resolved, the build fails.
  • The version a builder needs (a pin, the builder's default such as lts, a detected tool's latest, or a verification run's request) is checked against every tool constraint wherever tools are prepared. A violation is refused with the constraint named (CONFIG_OVERRIDE_DENIED: tools.node violates administrative constraints: 24 is outside allowed ["20","22"] in release (local-administration); pin an allowed version …). A tool a builder only detected can be silenced with tools.ignore.
  • The version oyzu.lock resolves a request to is checked too, before anything is installed or activated (--frozen included). A stale lock mapping an allowed 22 to 26.1.0 is refused, naming the constraint and the lock file.
  • Versions match by components: 22 admits 22, 22.14 and 22.14.0 (not 220.1). Any other value (lts, latest) matches only itself. Write allowed sets as majors or exact versions: an allowed lts or latest cannot vouch for what it resolves to, so a locked version under such a set is refused.
  • A tool constraint never affects a target whose builder does not use the tool.

A version supplied by a context-scoped lock is locked per context. oyzu.lock keeps one entry per tool request, so a local build (rust = stable) and a release build (rust = 1.95.0 from the lock) need one entry each. A build in a context whose entry is missing fails with TOOL_LOCK_STALE. Run oyzu pin and OYZU_CONTEXT=release oyzu pin once, on a machine with the same policy, and commit the lock. For a lock limited by provider or path, pin from a build that has them (in that CI job or folder). A build does not add such an entry while other tools are already locked, and --frozen never does.

Not bound by tool constraints: custom tasks that run tools through argv; plugin builders that run host tools without declaring them; oyzu exec, which activates only requested tools; a tool the isolated worker image supplies with no declared requirement (Helm, npm without packageManager, Yarn) or whose default request is missing from oyzu.lock, which runs the image's copy unchecked; and tool recipe artifacts (recipe:* entries in oyzu.lock), which oyzu install replays without tools.allowed or tool constraints.

Otherwise a project's configuration never breaks a build merely because policy tightened. Policy wins and the CLI says so.

Check levels under policy​

A policy lock or minimum of enforce or above on a check makes the check run wherever the constraint applies, whatever checks.run says. A project's [context.pr.checks] run = "required" does not skip a check policy requires in pr. The override is recorded (runs although checks.run = required) and changes the configuration digest. required also makes the check run in every build and its report mandatory.

  • A minimum on checks.coverage also lifts checks.tests to at least the same level, because tests collect coverage.
  • A policy minimum on checks.coverageMinimum lifts an off checks.tests or checks.coverage to enforce (or advisory where a policy maximum or allowed set caps it). An advisory level is not lifted.
  • A lift never overrides another policy constraint. A coverage percentage with a policy lock that keeps coverage off, or a coverage level with a lower tests lock, is CONFIG_POLICY_CONFLICT naming both, raised when the policy is read if both are unconditional, otherwise when a build meets both.

Selectors​

A constraint can be limited with when and unless tables. Every key in when must match (a list matches when any listed value does), and any matching key in unless excludes. Facts available when policy applies:

  • context: local, pr, ci or release
  • provider: detected CI providers such as github-actions
  • path: the target's folder, matched as a /-separated glob

A setting can carry one entry or a list of entries with different selectors:

{
  "schemaVersion": 1,
  "kind": "local-admin-policy",
  "settings": {
    "checks.format": {"minimum": "enforce", "when": {"context": ["pr", "release"]}},
    "checks.tests": [
      {"minimum": "required", "when": {"path": "services/**"}, "unless": {"context": "local"}},
      {"minimum": "enforce", "when": {"context": "release"}}
    ]
  },
  "profiles": {},
  "requiredCapabilities": []
}

Contexts cannot be avoided. A build counts as every context it detected, runs as or requested (the detected context, the effective one and the stricter of the two). A when context matches when it names any of them, and an unless context excludes only when it names all of them. So a pull request job under GitHub Actions run with --context local or --context release still meets when context = pr. explain reports these as policyFacts (contexts, providers, path).

Folders. path is the target's folder relative to the repository boundary: the nearest Git boundary above the build root, climbing from a submodule to its superproject. A linked worktree, a nested clone and any other repository are their own root, and the boundary is never the user's home folder or above. Without Git it is the nearest folder holding oyzu.toml, oyzu.local.toml or build.yaml, else the build root. --root and the current folder never move it. A target folder outside the boundary (reached through a link) is a CONFIG_SCOPE error.

Patterns are normalized (./services/ is services) and compared without case. services/** matches services and every folder below it, and * matches one folder level. The repository root (.) is matched only by . and **.

Path selectors are not containment. They select by repository layout. A git init in a subfolder makes it its own root, and a when path services/** constraint no longer matches it. Write rules that must hold everywhere as unconditional constraints, or limit them by context or provider.

Conflicts. Constraints on one setting that can apply to the same folder in the same context are compared when the policy is read. An unconditional lock off with minimum required when context = release, or two constraints for a shared context that cannot both hold, fail the policy with POLICY_INVALID naming both. Constraints for different contexts load. When one build counts as several contexts and they cannot all hold, the strictest context wins (local < ci < pr < release): its lock, minimum or maximum, and the intersection of its allowed sets. Allowed sets that agree pairwise but share no value for one build fail closed with CONFIG_POLICY_CONFLICT.

Errors. These fail with POLICY_INVALID naming the setting: an unknown fact, a fact with no value at this point (fork is not detected yet; target, platform, artifact and optimized are decided after settings), an unknown context, a non-string value, an empty table, an absolute, .., .-segment or // path pattern, an unknown entry field, and when or unless on a default. A bound that is not a valid value of the setting is CONFIG_INVALID_VALUE. A minimum or maximum on a setting that is neither a number nor an ordered level, a non-integer bound, reversed bounds, and unconditional constraints that cannot hold together are CONFIG_POLICY_CONFLICT. Policy errors stop the session before a build starts.

When a constraint replaces your value​

  • oyzu config explain <setting> lists it under Policy overrides (checks.format enforce admin policy minimum in pr, release (project oyzu.toml sets off)), adds a policy-<kind> step to the history, and marks each constraint with applies. --json has policyOverrides (with the replaced value, its origin and a label) and policyFacts. The label is org policy for enrolled organization policy and admin policy for the machine's admin-settings.json.
  • The plan prints one policy note per distinct override. oyzu build --plan prints Policy: lines (Constraint: for a project constraint) per target, and --plan --json has policyOverrides per target.
  • Plan and manifest targets record extensions["oyzu.dev/policy-overrides"]: the setting, value, constraint (source, label, kind, bound, selector), replaced (value, source, scope) and a note.
  • Every command that resolved an overridden setting reports a CONFIG_POLICY_OVERRIDE warning once per override, naming the setting, the policy source and the value that lost (checks.format = enforce by admin policy minimum in pr (local-administration) instead of off from oyzu.toml). The shell prompt hook does not repeat it. config validate --strict reports it without failing.

A value a task passes on as written (a task's own env) is checked without being replaced, so a locked environment value a task contradicts is refused with CONFIG_OVERRIDE_DENIED. A policy lock or minimum of enforce or above on a check the builder cannot run fails in the plan, naming the constraint (see check levels). Signed, cached organization policy carries the same entries and keeps working offline within its expiry.

Enrolled policy​

config status reports enrollment and cached-policy status. config refresh asks the enrolled platform's public configuration endpoint for current policy. Enrollment is done by your administrator; there is no enrollment command in the CLI.

  • Signed responses use pinned Ed25519 keys, canonical JSON, identity and context binding, increasing sequence numbers, expiry and explicit offline permission.
  • Cache entries are content-addressed and flushed before an operating system credential-store pointer commits them. Windows Credential Manager, macOS Keychain and Linux Secret Service hold integrity state. If that service is unavailable, managed execution fails. Standalone use does not need it.
  • A corrupt entry can be repaired only by a newly verified online response.
  • Retry backoff never extends signed deadlines, and a server denial never becomes offline permission.
  • Offline execution needs explicit signed permission and is bounded by the signed expiry and a maximum offline age of 24 hours. CI requires online policy.
  • Changing the protected bootstrap pins invalidates the previous cache binding. Recovery needs an online response verified against the current pins with a strictly newer policy sequence. Do not delete credential-store state to rotate keys.

Policy is not a login session and grants no publishing or signing authority. Platform sign-in is the separate oyzu auth.

Project constraints​

A project without central policy can make a rule hold in every folder with a [constraints] table in its root oyzu.toml. It uses the constraint and selector vocabulary and is applied after every ordinary value and before central policy, so a component folder cannot undercut it:

# root oyzu.toml only
[constraints."checks.tests"]
minimum = "required"
when = { context = ["release"] }

With services/oyzu.toml setting [checks] tests = "advisory", a release build of services runs its tests as required, and a local build keeps advisory.

Vocabulary. Each entry is a table, or a list of tables ([[constraints."checks.tests"]]), with locked = true with value, minimum, maximum, allowed, required, when and unless. They mean what they mean in policy, including ordered check levels, tool version matching and the rule that tools are refused, not replaced. Name the setting by its whole path in quotes. A default is refused, because a project default is an ordinary value written in the setting's own table. Only settings a project file can set may be constrained, and not env.* or tasks.*. Credential destinations, trust controls and administrative settings are refused naming the setting.

Selectors. context and provider behave as in policy. path is the target's folder relative to the folder of the root oyzu.toml (the Git top level, else the outermost folder with oyzu.toml, oyzu.local.toml or build.yaml, or --root), not the repository boundary that policy paths use. So a project's own rules keep matching when it sits inside a larger repository. explain --json reports it as policyFacts.projectPath.

Only the root file. A [constraints] table in any other file is an error naming the file: a component folder's oyzu.toml (CONFIG_SCOPE: app/oyzu.toml:1:1: [constraints] is allowed only in the root oyzu.toml), oyzu.local.toml, user or machine configuration, and a [context.<name>] or [profiles.<name>] table. A misspelled section ([Constraints], [constraint], [constriants]) is ignored with a warning and a hint, and config validate --strict rejects it. An invalid entry is CONFIG_CONSTRAINT_INVALID naming the file, line and setting. Entries that cannot hold together in one context fail as policy entries do.

Policy always wins. A project can never loosen policy. A project constraint that cannot hold together with the policy constraints that apply is set aside for that build:

  • A floor or ceiling of an ordered or numeric setting is clamped to what policy allows. A project minimum = "required" under a policy maximum = "enforce" becomes minimum = "enforce" and still raises a lower folder value to enforce. A project maximum = "off" under a policy minimum = "enforce" becomes maximum = "enforce", and policy raises the value.
  • A lock, an allowed set or a required set that policy rejects, or any project constraint where policy limits the setting with an allowed set, is dropped.
  • A coverage floor that would lift another check level is resolved the same way. A policy coverage percentage lifts tests over a project lock of off (the project lock is dropped). A project coverage floor that needs tests above a policy cap is dropped and lifts nothing.

Every command reports each case as a CONFIG_PROJECT_CONSTRAINT_SET_ASIDE warning naming the project constraint, the policy constraint and the value the build uses (checks.tests: project constraint minimum required in release (oyzu.toml [constraints]) is clamped to minimum enforce by admin policy maximum enforce (local-administration); checks.tests = enforce). When both layers apply and hold together, the project constraint replaces the folder value first and policy then replaces the project's value. Each step is recorded.

What you see. Project constraint overrides are shown like policy overrides, labelled project constraint with source oyzu.toml [constraints]. oyzu config explain lists them under Constraint overrides (checks.tests required project constraint minimum in release (project services/oyzu.toml sets advisory)). The plan prints a project note and oyzu build --plan a Constraint: line. Plan and manifest targets record them in extensions["oyzu.dev/policy-overrides"] with constraint.label. Every command reports a CONFIG_CONSTRAINT_OVERRIDE warning. A project minimum of enforce or above on a check makes it run whatever checks.run says, as a policy one does.

oyzu config validate --strict does not fail on CONFIG_CONSTRAINT_OVERRIDE or CONFIG_PROJECT_CONSTRAINT_SET_ASIDE, since tightening a folder value is not a configuration error. It does fail on CONFIG_RELEASE_LOWERED, which asks for a deliberate [context.release] value or a fix.

Limit. --root selects the configuration root. oyzu --root app build reads app/oyzu.toml as the root file, and the repository root's [constraints] does not apply to that build.

Existing settings migration and boundaries​

How resolved settings reach a build:

  • Builders register their own settings (docker.apparmorProfile, docker.frontends, docker.load). A builder reads the target's resolved snapshot, never the files.
  • A frozen build configuration contributes its digest to target and action records. Formatting, profile names and presentation preferences do not change it. A policy snapshot grants no signing, publishing or credential authority.
  • Planning needs the resolved snapshot of the invocation and of each selected target, including targets inferred without configuration files. A missing snapshot fails with CONFIG_INVALID_VALUE and never disables policy checks. Edits to configuration files after a plan is frozen apply to the next invocation.
  • Each target keeps serial mutation and hook order and has private workspaces and output roots. A failed dependency blocks its consumers while independent targets can finish.
  • Explicit tool requests that cannot be bound to a verified installation are rejected before builds. Enforced registry routes or catalogs that need unavailable bindings fail before any download. Managed host tasks stay blocked because the host runner cannot enforce managed network routing. Task and native-adapter environment additions must satisfy administrative environment restrictions.
  • Connector credentials and shell secret consumers are not available. The remote action cache is experimental and signs in only with a token from OYZU_CACHE_TOKEN or a CI job's ID tokens (see the action cache).

Tool lock execution-platform coverage​

[tools] declarations can be written, replaced and removed with oyzu install SPEC, oyzu uninstall and -g / --local, and in a toolset with oyzu --toolset NAME install SPEC. These keep comments and lock the result. See tool commands.

A declaration is a version string, or mise's option table with only a version key (node = { version = "22" }), which validation turns into that string. Edits change only the table's version. Unknown option keys warn and are ignored. They do not install hooks, select platforms or change acquisition. A table without a valid version string fails with CONFIG_INVALID_VALUE (see option tables).

tools.lockPlatforms is an optional list of execution platforms, set in the normal folder cascade. It cannot vary by profile or context.

  • Without it, lock coverage comes from the declared platforms of every build in the complete inventory, plus this host. Selecting fewer builds, a profile, a context or host-only execution does not narrow that default. With no declared platforms, coverage is this host.
  • An explicit nonempty list replaces the inferred candidates and still includes this host. Use it to prelock tools for another executor even when no build declares that output platform, or to check its approved catalog coverage.
  • Values are exact execution tuples such as linux/arm64/gnu and darwin/amd64/native, unlike the artifact platform names in build.yaml. Linux musl output maps to GNU execution metadata. Windows GNU and LLVM compiler recipes keep their ABI, while native helper and archive tools use MSVC.
  • Platforms the provider supports bound the inferred coverage. Unavailable foreign auxiliary recipes appear in pin's platformsNotLocked warnings. An unsupported host or explicit platform fails without writing a partial lock. Catalog checks need the host plus the explicit platforms, while foreign inferred candidates stay optional.
  • It selects lock metadata only, not output platforms or install authority.

tools.platforms was removed. Rename it to tools.lockPlatforms, or remove it to use the inventory default. The old key gives a configuration error, never a silent alias.

They read installed package metadata without refreshing the catalog, installing or adopting a package, or launching a plugin. The selected package must contain the builder profile, satisfy the required engine features and have a usable payload for this host.

Verbosity and logging​

Global verbosity flags and OYZU_LOG are invocation-only presentation inputs, resolved before any project session. They are not project keys and never enter resolved configuration or its digest. Explicit CLI controls override the whole environment filter, and help and version do not resolve them. See CLI diagnostic controls.
