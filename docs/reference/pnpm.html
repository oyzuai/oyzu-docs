pnpm builds

CLI reference

Published from the canonical docs/reference/pnpm.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Oyzu builds Node projects that use pnpm and a pnpm-lock.yaml. Single projects and conventional pnpm workspaces need no Oyzu build configuration. Use it to build, test and package a pnpm project with dependencies captured from the public registry and checked against the lockfile's SHA-512 integrity values.

Note: pnpm support is experimental. Oyzu captures and verifies the archives, then lets native pnpm validate the frozen lock and install. It is not full pnpm compatibility (see Limits).

Builds use the Node builder plugin (profiles node/app and node/package), which must be installed and selected. See plugin packages.

Platform scope: Use an x64 host and supported x64 build targets. ARM64 is unsupported. Feature-specific limits are listed in the support matrix.

Quick start​

Pin Node and pnpm (see Prerequisites and use), then run from the project:

oyzu --root path/to/project run list
oyzu --root path/to/project build
oyzu --root path/to/project inspect dist
  • oyzu run list shows your package scripts and the inferred test and quality tasks.
  • oyzu build produces a snapshot-versioned .tgz under dist/ with its test and coverage reports.
  • oyzu inspect dist checks the bundle's recorded content integrity.

Prerequisites and use​

Isolated builds run on the base execution image with Docker. Node and pnpm both come from oyzu.lock, so pin both: Node in [tools], pnpm with an exact packageManager (or pnpm in [tools]). The tested profile is pnpm 10.11.0 on Node 22.

How tasks run:

  • oyzu run <task> uses the tools installed on your machine. oyzu run list shows native package scripts and inferred test and quality tasks.
  • oyzu build runs native build and test work plus read-only lint and format checks in the isolated worker.
  • Node's built-in test runner gets JUnit and LCOV reporting. Other frameworks use their own adapters.
  • Formatting during a build never rewrites your checkout.
  • See Node quality for quality selection and defaults.

To test other Node versions, use verification toolsets in oyzu.toml. matrix.node in build.yaml is refused. Verification runs execute on the native host executor, and pnpm builds use the isolated executor. A pnpm build that has verification runs fails with VERIFICATION_RUN_UNSUPPORTED. Private registry configuration is not supported.

Workspace builds​

A pnpm workspace has a private root, a native pnpm-workspace.yaml, a version 9 lock and locally linked packages (see the pnpm workspace example). Run oyzu build from the root with no Oyzu configuration file.

  • oyzu run list shows build, test, lint and format-check.
  • Development builds dispatch pnpm --recursive run build.
  • Development tests use the workspace report collector.

How a workspace build runs​

Acquisition runs a frozen pnpm install with scripts disabled, then asks pnpm to list its members.

  • Workspace commands use the first pnpm executable on PATH, including a standalone executable. They do not fall back to a lower-priority pnpm.
  • Corepack pnpm shims are refused because they can download a package manager.
  • JavaScript pnpm layouts run through the selected Node.
  • Version projection reads the project lock with the yaml package the Node plugin ships (an OYZU_PNPM_YAML path takes precedence).

Planning and execution:

  • Local links come from the lock's importer records. They must point to captured members or to a named, publishable workspace root. A private root can't be a link target.
  • Oyzu orders the root and members, fixes their snapshot versions and declares each package's JUnit and LCOV.
  • In its private tree, Oyzu rewrites root and member versions, workspace dependency selectors and matching importer specifiers, then runs a fresh frozen install.
  • pnpm pack turns workspace selectors into published snapshot dependencies.
  • The publishable root is packed once, separately from member packages.
  • Your source and lock are unchanged.

Isolated workspace packages​

Select node/package to build a pnpm workspace into package archives in the isolated worker.

Supported: pnpm 10.11.0 and Node 22.23.3, on a Windows x64 coordinator with a Linux amd64 worker. Three archives install in a fresh offline pnpm project with the source absent. Frozen reuse and failures in dependencies or package tests are caught. Not supported: private roots, other pnpm versions, native-host workspace packages, Linux coordinators, Linux ARM64, Windows ARM64 and macOS.

It needs:

  • A publishable root and publishable members.
  • Native pnpm-workspace.yaml membership.
  • A genuine version 9 lock.
  • Recognized package-local build lifecycles and implicit Node tests.

Aggregate or opaque root builds, explicit test scripts and replaced build or test tasks are not supported.

How it works: Oyzu fixes versions and dependency decisions from native pnpm facts. In the private tree, it changes local workspace specifiers and importer specifiers but keeps link: resolutions and registry integrity data. pnpm builds each package and packs the archives. Each package must produce its JUnit and LCOV before anything is published. Your source and lock stay unchanged.

Use the ordinary package binding and a matching coordinator and worker engine. Tool versions come from native pins or the configuration cascade. build.yaml only selects uses: node/package. The first build with a real, non-frozen run adopts the plugin and creates oyzu.lock. Later --frozen runs reuse it:

oyzu -C <workspace> --json build workspace --isolated --platform linux/amd64 --full --no-cache --image pnpm=<image>

Generate the lock with pnpm 10.11.0. For oyzu exec, select pnpm in the tool configuration, because packageManager alone doesn't select it.

Scripts and stages​

  • A root script keeps ownership of its stage. Otherwise member build scripts run in dependency order, and member tests and quality use native scripts or inferred defaults.
  • Required test or quality failures stop artifact collection. Available reports stay in the failed bundle.
  • Overrides, prerequisites and hooks come from Oyzu's shared task scheduling.
  • Format checks during a build are read-only.
  • Registry inputs come from a local loopback server (see Acquisition and execution). pnpm's connection to it doesn't allow external downloads.

An opaque root build keeps the native root script and runs it once. Oyzu does not guess which member scripts it covered.

A root test script of the form tsc -p <relative-config> && vp test --run keeps its native pnpm script and TypeScript step, while Oyzu adds JUnit and LCOV reporters to the final vp test command.

  • The Vitest and Vite configuration comes from your Vite+ package graph. The coverage provider must be a declared dependency matching the runner's version.
  • Other custom root scripts must write their own reports. Oyzu adds no flags to them.

A root format script that is only vp fmt --check with directory-prefixed operands can serve as the format check when you have no format-check, format:check, preformat or postformat script. An opaque or mutating format script does not become a check.

Public entry checks before packing​

Before packing, Oyzu resolves each concrete public import and require entry from the package and requires the selected file to be a regular file.

  • Declaration files selected by the types condition and a literal legacy declaration path must also exist. Existence is checked, not TypeScript validity.
  • A missing declared JavaScript entry fails the build. Types-only and assets-only packages need no JavaScript entry.
  • Null exclusions and conditional alternatives are left to Node.
  • Wildcard-only entries without a concrete specifier can't be checked.
  • One pnpm pack --json result records the archive's name, version, file name and files. An archive missing a selected public file is rejected before its artifact receipt is written.
  • Browser or custom conditions, declaration validity and every wildcard path are not checked.

Cyclic workspace graphs, affected selection, member task groups and full direct host build and quality composition are not supported. pnpm's own layout and peer rules stay in charge.

Native dependency patches​

Checked-in patchedDependencies work in a single project's pnpm-workspace.yaml or in the pnpm object in package.json:

patchedDependencies:
  is-number@6.0.0: patches/is-number@6.0.0.patch
  • Create the patch with pnpm patch and pnpm patch-commit, and commit the patch, settings and updated lock together.
  • No Oyzu setting is needed.
  • A pnpm-workspace.yaml with patch settings doesn't make the project a workspace. A packages list turns on workspace discovery. Patch-only settings stay single-project.
  • The workspace settings below are also accepted. Other configuration keys are not.

Checks:

  • Declared and locked patch paths must be regular files inside the project. Absolute paths, .. segments, backslashes, symlinks, missing files and patches over 4 MiB are refused.
  • pnpm checks the lock and configuration agree and verifies patch hashes, then applies the patch in its private installation. Oyzu has no patch engine of its own.
  • A changed patch with a stale lock fails before project lifecycle hooks run.
  • Your source files and the registry archives stay unchanged.

Recorded in the build output:

  • The dependency inventory still identifies the original downloaded archives.
  • The oyzu.dev/pnpm.sourcePatches extension records each patch's selector, captured relative path, SHA-256, size and the native lock hash.
  • The source digest and dependency-snapshot digest include the patch inputs. Patched source is distinguished from the pristine upstream archive. This is not a full runtime SBOM.

Workspace settings​

Captured builds honor these pnpm-workspace.yaml settings as declared: catalog and catalogs, overrides, minimumReleaseAge, allowBuilds and trustPolicy. Each is either fixed by the committed lock or makes acquisition stricter, so none can widen what a build downloads or runs. No Oyzu configuration is needed.

catalog:
  is-odd: 3.0.1
  is-number: 6.0.0
overrides:
  is-number: 'catalog:'
minimumReleaseAge: 1440
trustPolicy: no-downgrade
allowBuilds:
  esbuild: false

Oyzu never re-resolves dependencies for these settings. It checks them before any native invocation, then native pnpm applies its own --frozen-lockfile checks. See the settings example.

Other configuration keys​

In package.json, the pnpm object may hold only patchedDependencies and overrides, because pnpm 10 reads other settings only from pnpm-workspace.yaml.

  • Any other key in either file fails with pnpm capture does not yet support configuration <key> in <file>. The message names the key, not its value.
  • That includes minimumReleaseAgeExclude, trustPolicyExclude, trustPolicyIgnoreAfter, onlyBuiltDependencies, ignoredBuiltDependencies and blockExoticSubdeps. Remove such keys to build.

Recorded policy and recovery​

After pnpm validates the lock, the oyzu.dev/pnpm.workspacePolicies extension records the declared minimumReleaseAge, trustPolicy and allowBuilds values, which leave no trace in the lock. The dependency-snapshot digest includes them. A recorded policy states what the project declared. It does not prove pnpm enforced it. Catalogs and overrides are covered by the recorded lock and source digests.

If a catalog or override check fails, regenerate and commit the lock with the pnpm version the project declares.

Newer pnpm releases can enforce minimumReleaseAge and trustPolicy during a frozen install, using publisher metadata. The captured adapter supplies the full publisher metadata and the attestation responses pnpm requests (see Acquisition and execution). pnpm makes the decision. Oyzu doesn't invent acceptance or treat a broker failure as missing metadata. With pnpm 12.6.0, a satisfiable release age passes and an unsatisfiable one fails with ERR_PNPM_MINIMUM_RELEASE_AGE_VIOLATION before any action or artifact.

Projects that use these settings together with other unsupported keys or .npmrc files, or that pin a pnpm version that isn't provisioned (10.33, 11.9, 12.4), still fail.

Acquisition and execution​

This section explains what is downloaded, from where, and what is checked.

Lock format​

Oyzu reads lock format v9 with a root importer and, for workspaces, member importers. pnpm 12 can write the lock as two YAML documents: an environment document pinning pnpm itself under packageManagerDependencies, then the usual v9 project document.

  • The project document is captured exactly like a single-document lock.
  • The environment document is checked but not captured, because Oyzu provisions the package manager. It may hold only lockfileVersion, importers, packages and snapshots, one . importer, and only configDependencies and packageManagerDependencies in it. A non-empty configDependencies fails, because it would need its own captured inputs.
  • Version projection rewrites only the project document and writes the environment document back unchanged.
  • A lock with more than two documents fails.

pnpm 10.11.0 can't read a two-document lock. An exact packageManager release is a locked tool requirement when the tool provider offers it, for both older and pnpm 12 packages. A full isolated build with pnpm 12.3.4 and a two-document lock works. Other pnpm 12 projects aren't supported yet.

What acquisition captures​

  • Every registry package in the project document's packages section needs an exact SHA-512 integrity value.
  • Native frozen pnpm install in the build image asks for the archives it needs. Oyzu captures only those requests, through the scoped npm-public route to https://registry.npmjs.org/. Optional archives for other platforms are fetched only if pnpm asks for them.
  • Your lock is unchanged, and project lifecycle scripts are disabled during acquisition.
  • Unsupported pnpm configuration and hook files are rejected before any native invocation, including the version query.
  • Archive digests are verified before the bytes reach pnpm. An unknown route, or a failed broker or integrity check, fails preparation even if pnpm would tolerate a missing optional package.
  • The snapshot holds content-addressed tarballs in lock order. It does not keep pnpm's mutable store.
  • pnpm requests at most eight packages at once. Its loopback wait is 120 seconds during acquisition and 15 seconds when replaying captured bytes. Neither raises the broker's network deadline or byte allowance.

How installation runs​

Oyzu creates a fresh private store and serves the captured archives to pnpm from a loopback port. The isolated worker has no external network.

  • The server holds no registry credentials, forwards nothing, and fails unknown routes and methods. During execution it serves only the frozen subset. pnpm needs HTTP access to it, so pnpm's own --offline flag isn't used.
  • For pnpm 12, Oyzu also captures full publisher metadata for the locked packages through the npm-public broker, and the attestation responses pnpm requests for locked name and version pairs. It records their bytes and digests in extensions["oyzu.dev/pnpm"].attestations and policyMetadata (source ID, URL, locked versions, SHA-256, size). A source-backed 404 records absence. A broker denial or timeout never becomes absence. This is source and content data, not proof of authenticity or a runtime SBOM.
  • pnpm evaluates its own attestation and supply-chain policy. Oyzu doesn't set trustLockfile.
  • Execution mounts no broker, rechecks captured response identity, and turns native lifecycle behavior on. The private store lives in scratch space and is discarded.
  • Lock and manifest checks run with --frozen-lockfile. Oyzu verifies the lock bytes are unchanged and that the pnpm and Node versions match between preparation and execution.
  • oyzu build --offline is rejected for this builder before preparation. Capture online, then execute with no network.
  • pnpm 10's dependency-script approval rules apply. Oyzu doesn't approve scripts for you.
  • Credentials never enter the inventory or loopback endpoint. Private registries are not supported.

Outputs and failures​

A successful build produces a snapshot-versioned .tgz under dist/. The package's embedded version matches the artifact version.

  • The manifest records artifacts and the collected test and coverage reports. Native logs and the dependency snapshot are in the bundle.
  • Failed tests keep their reports and block packaging.
  • oyzu inspect dist checks content integrity. It doesn't check release eligibility or who produced the bundle.

Dependency records use adapter layout 1. They list each captured archive with its name, version, source ID, size and SHA-256, and record lockfile-sha512 verification in oyzu.dev/pnpm. Every package counts as a build input. Runtime and test classification and registry dependency edges aren't recorded, so this is not a runtime SBOM. Workspace captures also keep local package edges for planning and version projection.

FailureRecovery
Stale lockRegenerate and commit the lock with the intended pnpm version, then rebuild.
Digest mismatch, denied acquisition, missing captured archives, metadata or attestation responses, or changed runtime versionsFails instead of refetching during execution. Fix the cause and rebuild from acquisition.

Your sources are never changed by an isolated build.

Isolated single-root packages​

The Node plugin can build a single-root pnpm project into one native .tgz. You need an installed Node plugin package, Docker, a genuine pnpm-lock.yaml, and Node 22.23.3 and pnpm 10.11.0 in your tool configuration. No build.yaml is needed for the package fallback. An explicit node/app keeps its directory output (see Node applications). Vite projects are not supported here. See plugin packages for usage.

Inferred, explicit node/package and scriptless packages each produce a versioned archive, Node test JUnit and LCOV, and install in a source-free, network-free consumer. A package with no build script has no build action. A failing assertion blocks packing and export.

Supported: an empty dependency graph, a Windows x64 coordinator and Linux amd64 execution. Native-host single-package builds are npm only. Other versions, macOS, Windows ARM64 and publication are not supported.

Limits​

This is incremental pnpm support, not full compatibility.

  • Supported: single-project public registry packages with integrity-only lock resolutions, native dependency patches, the workspace settings above, and captured workspace packaging.
  • pnpm 11 and later: Oyzu passes pmOnFail=ignore so pnpm doesn't download itself, and still checks the selected locked version.
  • Not supported yet: .npmrc, .pnpmfile.cjs, .pnpmfile.mjs, other configuration, packageExtensions, explicit tarball, Git or file resolutions, and private registries.
  • hoistPattern and nodeLinker settings are refused.
  • Workspace registry dependencies, peer and alias combinations, and framework variations beyond those above aren't covered.
  • Yarn Classic has its own adapter.
