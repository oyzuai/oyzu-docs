pnpm builds

CLI reference

Published from the canonical docs/reference/pnpm.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Oyzu recognizes a conventional Node project using pnpm and its pnpm-lock.yaml. Single projects and conventional native workspaces need no Oyzu build configuration. The experimental adapter captures public-registry dependency archives, verifies their SHA-512 lockfile integrity, and uses native pnpm for frozen-lock validation and installation. Native pnpm retains responsibility for dependency layout and peer resolution.

Prerequisites and use​

The current provisioned profile is pnpm 10.11.0 on Node 22. Build the common quality image, then the pnpm image:

docker build -t oyzu-toolchain/node:quality tooling/images/node-quality
docker build -t oyzu-toolchain/node:pnpm10.11.0-node22 tooling/images/node-pnpm
oyzu --root path/to/project run list
oyzu --root path/to/project build
oyzu --root path/to/project inspect dist

The build requires Docker and these explicitly provisioned images; Oyzu does not install them. --image pnpm=<image> selects an already provisioned compatible image. The image must include the owned runtime prerequisites, including yaml 2.8.1 at /opt/oyzu-pnpm/node_modules/yaml, and the Node quality tools. Its immutable image identity binds those tools. A project's exact packageManager, when present, must agree with the pnpm that runs. An exact stable release is a pinned tool, locked as oyzu:pnpm and run in place of the image's pnpm, so pnpm never downloads itself in the worker. A Corepack digest suffix such as pnpm@10.11.0+sha512.<hex> is accepted and ignored for that comparison. Native strict engine validation rejects incompatible Node requirements.

Development tasks use installed host tools. oyzu run list exposes native package scripts and inferred test/quality tasks; oyzu run <task> uses the development environment. Captured builds run native build/test work and read-only lint/format checks. Node's native test runner receives JUnit and LCOV reporting through the existing Node builder; other supported framework reporting remains framework-specific. See Node quality for quality selection and provisioned defaults. Formatting during a build never rewrites the checkout.

Acquisition and execution​

Other Node versions are tested with verification toolsets in oyzu.toml, never in build.yaml (matrix.node is refused). Toolset verification runs execute on the native host executor; pnpm builds use the isolated executor, so a pnpm build that has verification runs fails with VERIFICATION_RUN_UNSUPPORTED until runs reach that executor. Workspace support is described below; private registry configuration remains unfinished.

The admitted lock format is v9 with a root importer and, for workspaces, native member importers. pnpm 12 can write pnpm-lock.yaml as two YAML documents: an environment document whose root importer pins pnpm itself under packageManagerDependencies (with its pnpm and @pnpm/exe.* packages), followed by the usual v9 project document. Oyzu reads such a lock as follows:

  • The project document is admitted and captured exactly as a single-document lock is.
  • The environment document is validated but not captured, because Oyzu provisions the package manager itself. It may contain only lockfileVersion, importers, packages and snapshots, a single . importer, and only configDependencies and packageManagerDependencies in that importer. A non-empty configDependencies fails, because configuration dependencies would need their own captured inputs.
  • Workspace version projection rewrites only the project document and writes the environment document back unchanged.
  • A lock with more than two documents fails.

This reading is in place. The provisioned default profile is pnpm 10.11.0, which cannot read a two-document lock. An exact packageManager release is a locked tool requirement when the tool provider offers it. The provider selects the publisher's platform executable package for both the older and pnpm 12 package families. The compiled CLI completed a full isolated build of the two-document fixture with pnpm 12.3.4, including tests, coverage and a package (see implementation status). Other pnpm 12 projects, versions and platforms remain unqualified. Every registry package in the project document's packages section is admitted and checked for an exact SHA-512 integrity value. Native frozen pnpm installation in the selected build image requests the archives it needs; acquisition captures only those requests through the scoped npm-public route to https://registry.npmjs.org/. Optional archives for other platforms are not fetched unless native pnpm requests them for the selected image and declared configuration. The lockfile remains unchanged.

Acquisition disables project lifecycle scripts. Unsupported pnpm configuration and hook files are rejected before any native invocation, including the version query. Preparation verifies archive digests before handing bytes to pnpm. The snapshot contains content-addressed tarballs in lock identity order for the selected native requests; it does not retain pnpm's timestamped mutable store. Repeated native requests for one archive share a single broker fetch. Native pnpm requests at most eight packages concurrently, matching the broker client bound. Its acquisition-only loopback wait is 120 seconds so a broker request can complete within its existing 55-second client window; replay of captured local bytes retains the 15-second wait. Neither setting raises the broker's network deadline or byte allowance. An unknown route or failed broker or integrity check fails preparation even if native pnpm would tolerate a missing optional package.

For installation, the adapter creates a fresh private store and serves exact captured archives on an ephemeral loopback port. For pnpm 12, it also serves full publisher packuments for the admitted locked package names. Native admission runs on a private copy of the project first; Rust captures the publisher responses through the active scoped npm-public broker before freezing the prepared tree. Native pnpm may also request attestation responses for exact admitted locked name/version pairs. The bridge captures only those native requests through the same broker; Rust validates their source and 200 or 404 status, stores the returned bytes and digest, and binds the selected responses in extensions["oyzu.dev/pnpm"].attestations. A source-backed 404 records absence; broker denial or timeout cannot become absence. pnpm evaluates its own attestation policy and cryptographic evidence. The dependency snapshot's policyMetadata also lists each captured packument's sourceId, URL, locked versions, SHA-256 digest and size; the preparedTree digest binds the raw bytes. This is source and content evidence, not a complete authenticity or runtime SBOM claim. The isolated worker has no external network. During acquisition its loopback server asks the broker only for exact admitted locked archive and attestation identities; during execution it serves only the frozen selected subset and never forwards requests. A native HEAD probe receives headers only when its exact route already has captured metadata or archive bytes; it never fetches or selects an archive. The server holds no registry credentials, and unknown routes and methods fail. Native pnpm needs HTTP access to this local server, so its own --offline switch is not used. Native supply-chain policy evaluation remains enabled; Oyzu does not set trustLockfile. Execution mounts no acquisition broker, rechecks captured response identity, and enables native lifecycle behavior. Its private pnpm store uses an invocation-scoped scratch mount and is discarded afterward. Explicit Oyzu build --offline still rejects this builder before preparation; online capture followed by network-isolated execution is the verified mode. pnpm 10's dependency-script approval rules still apply; Oyzu does not silently approve dependency scripts.

Native lock/manifest checks run with --frozen-lockfile. The adapter checks that the lock bytes remain unchanged and requires the same pnpm/Node versions during preparation and execution. Credentials are absent from the inventory and loopback endpoint. Managed/private registry routes remain unimplemented for this profile.

Native dependency patches​

Checked-in patchedDependencies settings are supported in a single project's pnpm-workspace.yaml or the native pnpm object in package.json. For example:

patchedDependencies:
  is-number@6.0.0: patches/is-number@6.0.0.patch

Use native pnpm patch and patch-commit to generate the patch, settings and updated lock; commit those inputs together. Oyzu needs no additional setting. A pnpm-workspace.yaml containing these settings does not itself require multiple projects. A packages list enables native workspace discovery; patch-only settings retain single-project planning. The workspace settings below are also admitted; other configuration keys remain unsupported.

All declared and locked patch paths must reference regular files inside the captured project. Absolute paths, parent traversal, backslashes, symbolic links, missing files and patches over 4 MiB fail admission. Native pnpm verifies lock/configuration agreement and patch hashes, selects matching dependencies and applies the patch to its private installation. Oyzu does not parse diff hunks or implement its own patch engine. Modified patch bytes with a stale lock fail before project lifecycle hooks run. Source files and the content-addressed registry archives remain unchanged.

Registry inventory records continue to identify the original downloaded archives. The oyzu.dev/pnpm.sourcePatches extension separately records each locked patch selector, captured relative path, SHA-256 digest, size and native lock hash. The source digest binds the patch inputs, and the dependency-snapshot digest includes the patch evidence. This distinguishes source modifications from pristine upstream archive identity; it is not a complete runtime SBOM.

Outputs and failures​

Successful builds produce a snapshot-versioned native .tgz package under dist/, with its embedded package version matching the artifact version. The manifest records actual artifacts and collected test/coverage reports; native logs and the dependency snapshot accompany the bundle. Failed tests retain collected reports and block packaging. oyzu inspect dist checks recorded content integrity, not release eligibility or producer trust.

Dependency records use adapter layout 1, inventory every captured archive with its name, version, source ID, size and SHA-256 digest, and record lockfile-sha512 verification in oyzu.dev/pnpm. Package purpose currently means build input; runtime/test classification and registry dependency edges are not modeled. Workspace captures additionally retain native local package edges for planning and version projection. No complete runtime SBOM is claimed.

A stale lock requires regenerating and committing the lock with the intended native pnpm version before rebuilding. Digest mismatch, denied acquisition, missing captured archives, packuments or selected attestation responses, or changed runtime versions fail rather than refetch during execution. The current captured registry inventory uses layout version 1, including a dependency-free pnpm 12 project with empty response allowlists. Project sources remain unchanged by the captured build.

Workspace builds​

The EX-020 pnpm variation has a private root, a native pnpm-workspace.yaml, a committed v9 lock and locally linked app/shared packages. Run oyzu build from that root without an Oyzu configuration file. run list exposes build/test/lint/format-check; direct host build dispatch uses native pnpm --recursive run build, while direct tests use the workspace report collector.

Acquisition runs native frozen installation with scripts disabled, then asks pnpm to list its members. Workspace commands use the first provisioned pnpm executable on PATH, including a standalone executable; they do not fall through to a lower-priority pnpm when that executable is selected. Corepack pnpm shims are refused because they can acquire a manager. JavaScript pnpm layouts continue to run through the selected Node interpreter. Workspace lock projection uses the same provisioned YAML module path required by the pnpm image (/opt/oyzu-pnpm/node_modules/yaml by default), independently of the selected command shape. Local links come from the validated importer records and must resolve to captured members or a named, publishable workspace root. A private root is not a link target. The common Node workspace planner orders the root and members, freezes their snapshot identities and declares package-owned JUnit/LCOV. Execution projects root and member versions, workspace dependency selectors and matching importer specifiers in its private tree before a fresh frozen installation. Native pnpm pack converts workspace selectors to published snapshot dependencies. The publishable root is packed once, separately from member packages. The committed source and lock remain unchanged.

For an opaque root build, Oyzu keeps the native root script once instead of guessing which member scripts it covered. Before packing, the selected Node runtime resolves each concrete public import and require entry from its package and requires the selected file to be regular. It also checks concrete declaration files selected by Node's types condition, and a literal legacy declaration path; these checks establish file presence, not TypeScript validity. A missing declared JavaScript entry fails the build; no JavaScript entry is invented for types-only or assets-only packages. Null exclusions and native conditional alternatives remain Node's decision. Wildcard-only public entries without a concrete specifier cannot be certified. For pnpm, one native pack --json result binds the archive's name, version, filename and included files; an archive omitting a selected public file is refused before its artifact receipt is written. Compiled fixture checks cover missing and omitted public files, and the pinned Hono product proof produced all nine packages. Other managers retain their existing packing behavior. Browser/custom conditions, declaration validity and every wildcard path remain outside this gate.

Root scripts retain stage ownership. Otherwise member build scripts run in dependency order and member tests/quality use native scripts or inferred defaults. Required test/quality failures block artifact collection, with available reports retained in the failed bundle. Shared task scheduling owns overrides, prerequisites and hooks. Build formatting is read-only. Registry inputs use the captured loopback server described above; pnpm's HTTP transport to that local server does not permit external downloads.

A root test script of the bounded form tsc -p <relative-config> && vp test --run keeps its native pnpm script and TypeScript preflight while forwarding Vitest JUnit/LCOV instrumentation to the final VP command. The runner's Vitest/Vite configuration comes from the selected Vite+ package graph; the coverage provider remains a declared project dependency and must match that runner's version. Other custom root scripts retain their existing report obligation without inferred flags. For the read-only formatting stage, a root format script consisting solely of vp fmt --check with directory-prefixed operands may serve as the native check when no explicit format-check or format:check script and no preformat/postformat hook exists. An opaque or mutating format script does not become a check. These paths have focused dispatch tests and real pinned Hono product evidence, including TypeScript preflight, native VP tests, JUnit/LCOV, lint and read-only formatting. The qualification record preserves earlier timeout failures and the later passing runs; it does not establish the underlying timing cause or a general timing guarantee.

A small publishable-root fixture passed compiled isolated full builds on Windows and Linux: root, app and shared packages had projected local versions, the root build script ran once, JUnit/LCOV were collected and bundle inspection passed. The pinned Hono flow uses a package-local root producer and eight adapter producers in dependency order. Its ordinary product proof at 88e7ed09 produced nine usable packages and required reports. Two further fresh full products at 01cfff24 passed from one live held prepared input set, with separate installed workspaces, run identities and outputs, no restored action results, and unchanged source and tool lock. Each passed 5,196 tests with 44 skipped and no failures or errors. An offline consumer of the ordinary product's nine local archives resolved the checked public files and executed the root package through both import and require. This is a bounded Linux proof, not tar-byte reproducibility or every export/platform combination; a separate native peer-check command failed and remains an explicit limit. Current workspace regression and integration status is in the qualification record. Cyclic graphs, affected selection, member task groups and complete direct host build/quality composition remain functional gaps. Workspace registry dependencies, peer/alias combinations and framework variations still need their own scenario evidence. Native pnpm package layout and peer rules remain authoritative.

python tooling/test-native-workspace-build.py --manager pnpm passed Windows native acquisition, fresh captured-input replay, two snapshot packages with matching local dependency versions, real JUnit/LCOV, lint/read-only formatting and failed-test reports using Node 24.14.1/pnpm 10.11.0. The same probe supports --manager yarn; host adapter checks alone do not prove worker isolation. The focused native-prepared binding proof at d816 verified that direct, nested bare and helper commands all selected locked standalone pnpm 12.6.0 and completed the YAML-backed version projection before its intentional consumer stop. Later compiled Hono product and held-input proofs are recorded separately, retaining attribution to their exact source and dependency subjects.

Compatibility and evidence​

This increment supports single-project public registry packages with conventional integrity-only lock resolutions, native dependency patches and the decided workspace settings, and experimental captured workspace packaging. The pnpm 12.3.4 two-document fixture and a dependency-free single-document lock have measured end-to-end builds; other pnpm 12 projects, versions and platforms remain unqualified. For pnpm 11+, Oyzu passes native pmOnFail=ignore to prevent executable self-download and still checks the selected locked version. .npmrc, .pnpmfile.cjs, .pnpmfile.mjs, configuration other than packages, patchedDependencies and those settings, packageExtensions, explicit tarball/Git/file resolutions and private registries still require adapter work. Yarn Classic has a separate native adapter. This is an incremental implementation, not full pnpm compatibility.

Pinned Hono f78a245abc393368583085e19c7f5b28b460bf51 now has the bounded nine-package full product, consumer and two-fresh-product evidence described above using Node 24.22.0/pnpm 12.6.0. The original Vite corpus still stops on hoistPattern, and Docusaurus on nodeLinker; those settings remain unsupported. The qualification record preserves the original admission, acquisition and native-test failures alongside the later Hono successes. This does not qualify other corpus revisions or complete pnpm compatibility.

The Windows native probe in tooling/test-node-registry-acquisition.py --manager pnpm --native-cli <pnpm.cjs> exercises real pnpm with a direct and transitive package, repeated fresh captures, offline replay of captured bytes, lifecycle isolation, stale locks, corrupted archives and rejected source hooks. This replaces the former test-pnpm-acquisition.py --pnpm-cli entry point. The native manager probe also covers version/engine rejection, JUnit/LCOV and repeatable packages. These host probes do not prove container isolation. The Linux compiled-CLI Node suite builds the registry fixture, validates reports and dependency records, repeats snapshot packages and exercises failed tests; revision-specific CI results remain in implementation status. Full captured-build execution on Windows/macOS is not established by native adapter tests.

Add --patches to the acquisition probe to exercise the native patch example, both native configuration locations, changed-patch rejection before hooks and denied patch paths. The Linux compiled-CLI suite includes that fixture's snapshot artifact, four JUnit cases, coverage, source-patch evidence, repeatability and preflight failure bundle. Consult implementation status for whether that revision has passed isolated acceptance.

Workspace settings​

On 2026-10-10 the maintainer decided that captured builds honour these pnpm-workspace.yaml settings as declared: catalog and catalogs, overrides, minimumReleaseAge, allowBuilds and trustPolicy. Each one is either fixed by the committed lock or makes acquisition stricter, so honouring it never widens what a build may fetch or run. They need no Oyzu configuration. For example:

catalog:
  is-odd: 3.0.1
  is-number: 6.0.0
overrides:
  is-number: 'catalog:'
minimumReleaseAge: 1440
trustPolicy: no-downgrade
allowBuilds:
  esbuild: false

Oyzu never re-resolves dependencies for these settings. Before any native invocation, acquisition and execution check them as follows; native pnpm --frozen-lockfile then applies its own checks.

SettingWhat Oyzu checksEffect with the provisioned pnpm 10.11.0
catalog, catalogsEach catalog maps names to specifier strings. catalog is the default catalog, so declaring catalogs.default too fails. Every lock importer dependency whose specifier is catalog: or catalog:<name> must have a lock catalogs entry whose specifier equals the declared one, as native frozen installation requires.Native pnpm compares the same entries and installs the locked versions.
overridesThe lock's overrides section must equal the declared map after native normalization: $name takes the root package.json specifier and catalog: takes the catalog entry for the override's target package. Overrides come from pnpm-workspace.yaml, or else from package.json pnpm.overrides merged over resolutions; declaring them in both places fails. A difference fails with pnpm lock overrides differ from configuration for <selector>.Native pnpm makes the same comparison (LOCKFILE_CONFIG_MISMATCH). The locked graph already reflects the overrides.
minimumReleaseAgeA whole number of minutes.Not read: pnpm 10.11.0 predates it (10.16). The frozen lock resolves nothing new, so no release-age decision arises; Oyzu fetches no registry metadata to evaluate ages.
trustPolicyno-downgrade or off.Not read: pnpm 10.11.0 predates it (10.21). Releases that have it apply it during resolution, which a frozen install does not perform.
allowBuildsEach value is true or false; a placeholder such as set this to true or false fails. When any entry is true, the provisioned pnpm must be 10.26.0 or newer, the first release that reads it; otherwise acquisition fails with pnpm allowBuilds approves <selector>, but provisioned pnpm <version> predates allowBuilds.Denials are honoured: pnpm 10 runs no dependency build scripts unless approved, and acquisition disables lifecycle scripts entirely. An approval needs a newer provisioned pnpm, which then runs only the approved packages' scripts during execution.

In package.json, the native pnpm object may hold only patchedDependencies and overrides, because pnpm 10 reads the other settings only from pnpm-workspace.yaml. Any other key in either place fails with pnpm capture does not yet support configuration <key> in <file>. This includes the companion settings minimumReleaseAgeExclude, trustPolicyExclude and trustPolicyIgnoreAfter, the pnpm 10 build settings onlyBuiltDependencies and ignoredBuiltDependencies, and blockExoticSubdeps; admitting them needs a further decision. The message names the key, never its value.

After native validation, the oyzu.dev/pnpm.workspacePolicies extension records the declared minimumReleaseAge, trustPolicy and allowBuilds values, which leave no trace in the lock, and the dependency-snapshot digest includes them. Recording a policy states what the project declared, not that the provisioned pnpm enforced it. Catalogs and overrides are bound through the recorded lock digest and the source digest.

To recover from a catalog or override failure, regenerate and commit the lock with the native pnpm version the project declares. An undecided key must be removed until a maintainer decision admits it. Newer pnpm releases can evaluate minimumReleaseAge and trustPolicy against publisher metadata during frozen installation; the captured pnpm adapter supplies the full admitted publisher packuments and selected native attestation responses described in acquisition and execution. Native pnpm owns the policy decision; Oyzu does not synthesize acceptance or convert a broker failure into missing metadata. The registered pnpm-policy proof at f2e86155 used real pnpm 12.6.0: its ordinary release-age setting passed, while changing only the age to an intentionally unsatisfiable value produced ERR_PNPM_MINIMUM_RELEASE_AGE_VIOLATION before actions or artifacts. That one measured denial is not qualification of every policy combination or authenticity claim.

The settings example declares a catalog dependency, a catalog-referenced override and the three policies; its committed lock uses pnpm 10.11.0's format. Supplemental admission, record and native-acquisition helpers remain available. The later pnpm-policy scenario qualifies the release-age flow on a task-owned copy declaring pnpm 12.6.0, with frozen source/lock records, genuine captured metadata, native positive and negative outcomes and a failed bundle containing no artifacts. Consult implementation status and the qualification record for revision-specific evidence; this does not imply every helper or corpus combination has passed.

The corpus projects that use these settings also use undecided keys or .npmrc files and pin pnpm 10.33, 11.9 or 12.4, none of which is provisioned, so they still fail admission.
