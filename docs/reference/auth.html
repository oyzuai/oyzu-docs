Platform sign-in and the credential provider

CLI reference

Published from the canonical docs/reference/auth.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Status: experimental client. oyzu auth login|status|logout and the shared credential provider implement the initial client contract of the draft connected-client authentication companion. The OEP stays a draft. They are verified against a local conformance fake (oyzu auth conformance); they have not been run against a real identity provider, a real platform or each operating system's credential store. The platform surfaces they rely on (protected-resource metadata, the registered oyzu-cli client and the self access-context route) are built separately; until a platform serves them these commands report discovery as unsupported.

Purpose​

Sign a person in to a platform account once, keep the session in the operating system's protected credential store, and let oyzu build --remote, oyzu run --remote, oyzu secrets and oyzu release check use it. Everything else Oyzu does stays local and needs no account.

Prerequisites​

  • platform.url and platform.account in user, machine or administrative configuration (a project or local file is refused, so a checkout cannot choose where credentials go):

    oyzu config set --global platform.url https://platform.example.com
    oyzu config set --global platform.account payments

  • A platform that publishes OAuth protected-resource metadata (RFC 9728) naming exactly one issuer that allows the device authorization grant (RFC 8628) for the registered public client oyzu-cli, and the draft self access-context route.

  • For login: a terminal where you can read a code and approve it in a browser (any browser, on any device).

  • A protected credential store: macOS Keychain, Windows Credential Manager, or a running Linux Secret Service provider (GNOME Keyring, KWallet). There is no plaintext fallback; without a store login stops before asking you to approve anything.

Usage​

CommandDoes
oyzu auth loginDiscover the issuer, show a verification address and code, wait for approval, confirm you are an active member of platform.account, then store the session
oyzu auth statusShow the platform, account and local session state: absent, active, refreshing, reauthentication-required or logged-out. Reads local state only and asks no server
oyzu auth logoutFence renewal, delete this account's local session, then ask the issuer to revoke it and report that separately
oyzu auth conformanceRun the client conformance suite against a local fake; needs no account

Login discovery, step by step:

  1. GET /.well-known/oauth-protected-resource (with the platform URL's path appended when it has one). resource must equal platform.url and exactly one authorization_servers entry is accepted; zero, several or a mismatch stop the login.
  2. The issuer's RFC 8414 metadata (else its OpenID configuration). Its issuer must equal the advertised one; the device authorization and token endpoints (and a revocation endpoint if offered) must be HTTPS (HTTP only for a loopback host), carry no credentials, query or fragment, and sit on the issuer's own origin. The device grant must be advertised and public clients (none authentication) allowed. No bearer is sent to any of this and no redirect is followed.
  3. The device grant for client oyzu-cli: no client secret, password grant or dynamic registration; no scope parameter (the issuer's session defaults) and never offline_access. The verification address must be on the issuer's origin or it is not shown. Polling honors the issuer's interval and slow_down and is bounded to 15 minutes.
  4. GET /api/v1/access-context?account=<platform.account> with the new access token: the response must be oyzu.access/1 and name an active membership of exactly that account. Another membership is never a fallback. An account that needs stronger authentication is reported as AUTH_STEP_UP_REQUIRED; a missing membership as AUTH_NOT_A_MEMBER. Either way the sign-in is revoked and nothing is stored.

Only then is the session stored, so a cancelled, denied, expired or failed login leaves no usable partial session. The device code is never shown or logged.

Which credential a command uses​

secrets, release check and --remote obtain their credential from one provider. Selection is deterministic and never falls through to another identity after a failure:

SituationResult
platform.authentication.provider is workload, private-key or executionAUTH_PROVIDER_UNSUPPORTED (not implemented yet)
Provider environmentOYZU_PLATFORM_TOKEN is required; without it AUTH_PROVIDER_UNAVAILABLE
Provider sessionThe stored session; with OYZU_PLATFORM_TOKEN also set, AUTH_PROVIDER_CONFLICT
No provider selected, OYZU_PLATFORM_TOKEN setThat bearer, as supplied: never stored, refreshed or replaced
No provider selected, stdin and stderr are terminalsThe stored session
No provider selected, unattended (CI, scripts, agents)AUTH_PROVIDER_REQUIRED; a stored session is never used implicitly

A bearer the platform rejects is reported (*_UNAUTHENTICATED); it is not replaced by a stored session. An explicit session selection is human authority, not an automation identity.

The credential is delivered only to the origin of platform.url. A request to any other origin (a redirect, a download link from a checkout) gets none.

Settings​

SettingValuesMeaning
platform.authentication.providersession, environment, workload, private-key, execution; absentHost-owned provider selection, see above. Contains no credential. Environment input OYZU_PLATFORM_AUTH_PROVIDER. User, machine or administrative scope only

OYZU_PLATFORM_TOKEN stays a credential, not a setting.

Storage, renewal and logout​

  • Refresh state and the cached access token are separate protected entries, keyed by platform, issuer, client, subject and account. Selection metadata (issuer, subject, state, expiry) is a small non-secret file under the user data directory (auth/), created private.
  • Renewal takes a per-session cross-process lock plus an in-process single flight, rereads state after waiting and renews only if still needed, so concurrent commands renew once.
  • Before a refresh credential is spent it is marked pending. If the answer is lost (timeout, crash, failed store write) the session is ended (AUTH_REFRESH_AMBIGUOUS, AUTH_STORE_FAILED) and you are asked to sign in again; a possibly spent rotating credential is never retried. A rejected renewal also ends the session (AUTH_REAUTHENTICATION_REQUIRED). An issuer outage or an unreachable network leaves the session untouched.
  • logout starts a new session epoch under the commit lock before deleting, so a renewal already in flight cannot recreate the session; it discards its result and revokes the credential it just received. A new login also starts a new epoch.
  • Local removal can succeed while remote revocation is unavailable; the record says so (remote: refused|unreachable|not-advertised). Access tokens already issued stay valid until they expire. A separately supplied OYZU_PLATFORM_TOKEN is unaffected.

Output​

Human output leads with the outcome. --json prints one record: auth-login, auth-status, auth-logout or auth-conformance, holding session facts only. The verification address and user code go to standard error and only when it is a terminal, so JSON on standard output stays machine-readable; without a terminal login fails with AUTH_INTERACTION_REQUIRED before any request.

Errors and recovery​

Exit status is 1 on failure. Codes: AUTH_NOT_CONFIGURED, AUTH_INTERACTION_REQUIRED, AUTH_STORE_UNAVAILABLE (start or unlock the store), AUTH_STORE_FAILED, AUTH_DISCOVERY_UNSUPPORTED, AUTH_DISCOVERY_UNAVAILABLE, AUTH_DISCOVERY_INVALID, AUTH_DISCOVERY_AMBIGUOUS, AUTH_ISSUER_MISMATCH, AUTH_ISSUER_UNTRUSTED, AUTH_REDIRECT_REFUSED, AUTH_GRANT_UNSUPPORTED, AUTH_DEVICE_EXPIRED, AUTH_DEVICE_UNTRUSTED, AUTH_LOGIN_DENIED, AUTH_LOGIN_CANCELLED, AUTH_NOT_A_MEMBER, AUTH_STEP_UP_REQUIRED, AUTH_CONTEXT_UNAVAILABLE, AUTH_LOGIN_REQUIRED, AUTH_REAUTHENTICATION_REQUIRED, AUTH_REFRESH_AMBIGUOUS, AUTH_ISSUER_UNREACHABLE, AUTH_ISSUER_CHANGED, AUTH_DESTINATION_MISMATCH, AUTH_AUDIENCE_UNSUPPORTED and the provider codes above. Commands that use the provider report *_UNAUTHENTICATED when no credential is available. Recovery for a session that cannot be renewed is always oyzu auth login.

Security​

  • Tokens, device codes and refresh credentials never appear in output, logs, configuration, command arguments, error text or the metadata file; debug formatting is redacted and credential handles cannot be serialized.
  • No plaintext credential file exists. The conformance suite's file-backed store holds synthetic credentials for its own fake and is not selectable by a command.
  • A coding agent or unattended job does not inherit a developer's session. Do not give an agent a person's OYZU_PLATFORM_TOKEN; a copied bearer still identifies that person.

Conformance​

oyzu auth conformance (or oyzu --json auth conformance) starts a fake issuer and protected resource on loopback and runs the real client against it, with synthetic credentials and stores and real child processes for refresh contention. It exits 1 if any scenario fails. Covered client-side criteria of the authentication contract:

CriterionCovered
AUTH-CLIENT-01Device login, membership validation, an authorized call, revoked membership denying a fresh call and login (against the fake)
AUTH-CLIENT-02Provider selection without fallback, unattended refusal, one renewal for concurrent callers, expiry and logout
AUTH-CLIENT-03Store failure, cancelled, denied and expired login, foreign verification address, destination binding, no partial session
AUTH-CLIENT-06 / 07Self-context subset: step-up challenge, no implicit membership fallback, independent accounts, local state versus authority, remote revocation reported separately
AUTH-CLIENT-08Ambiguous, mismatched or untrusted metadata and endpoints, redirects, checkout-selected settings
AUTH-CLIENT-09Two-process contention, failed replacement store, ambiguous renewal, refresh racing logout
AUTH-TEL-01 / 03 (client side)No credential in output, errors, debug text or state files

Not covered: AUTH-CLIENT-04, 05 and 10 (server-side or later work), a real identity provider, real per-OS credential stores, and a real platform remote build with membership revocation. Those need a platform and each operating system, and are not claimed.

Limitations​

  • The OS store implementation compiles for macOS, Windows and Linux but has not been exercised on each here; Linux additionally needs a Secret Service provider in the session.
  • workload, private-key and execution providers, loopback PKCE login, account switching beyond re-running login for another platform.account, and a local background agent are not implemented.
  • Pagination of the self access-context response follows an optional next_cursor; the exact wire shape awaits the platform implementation.
  • The subject of the access-context response may be a string or an object with an id.

Verification​

oyzu exec -- cargo test --locked --test integration authentication runs the compiled CLI (help opens no store or network, status/logout without a session, provider selection and no fall-through against real consumers, supplied-bearer mode, conformance). oyzu exec -- cargo test --locked --lib auth:: runs the library suite, including the full conformance scenarios. Neither qualifies a real identity provider, platform or OS store.
