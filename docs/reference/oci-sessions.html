Native OCI launch sessions (prototype)

CLI reference

Published from the canonical docs/reference/oci-sessions.md file. Features marked experimental remain experimental; check support limitations before relying on them.

This isolated prototype adds automatic session preparation for explicitly provisioned Helm and BuildKit clients. It implements client mechanics only; a production agent, account login, policy evaluator and OCI tool installation are not supplied. The proof record distinguishes simulator behavior from product code and measured results.

Configure the local agent​

The user or an administrator configures a numeric-loopback HTTP endpoint in their existing Oyzu configuration file. For the laboratory:

[oci]
sessionEndpoint = "http://127.0.0.1:43199/session"

Use the normal configuration cascade. Project/local/invocation sources cannot set this endpoint; the launch adapter checks its resolved authority. User settings are excluded in CI by existing configuration behavior. This is a local developer prototype, not CI workload authentication. OYZU_USER_CONFIG can select an absolute user file for isolated testing, without changing its authority.

The endpoint must have no username, password, query or fragment. Authentication of this IPC connection remains future work; use only the disposable fixture agent. The setting does not create an authenticated platform account. Removing it returns the existing standalone behavior; an absent setting is not a governed denial.

Execute​

With provisioned native executables and the prototype CLI:

oyzu exec -- /usr/local/bin/helm pull oci://registry.example.com/charts/sample --version 0.1.0
oyzu exec -- /usr/local/bin/buildctl --addr tcp://builder.example.com:1234 build --frontend dockerfile.v0 --local context=. --local dockerfile=. --output type=local,dest=dist

These are invocation-shape examples, not reachable fixture endpoints. The reproduction harness supplies local registries and builders. Configure appropriate TLS independently for real transports. Supported managed Helm command-first forms are pull, dependency and template; BuildKit requires a build argument. This is not a comprehensive native argument parser or general Docker CLI adapter. Native credential override flags (--registry-config, --username, --password) are rejected. push=true is rejected; publication remains an oyzu publish path. Help/version do not request an access session. Other executables retain ordinary standalone execution.

On Unix, normal shell environment composition installs credential-free launch shims for provisioned helm and buildctl found on PATH. Bash activation routes bare invocations through the same exec adapter; each invocation resolves current configuration and asks for a fresh session. The prototype does not install those tools. Windows automatic shell shims are not implemented here; explicit launch code is present but native Windows/macOS execution is unqualified.

Effects and credential boundary​

Before starting a supported command, the compiled adapter sends its directory, tool and arguments to the local agent. The agent either denies or returns a credential endpoint and registry hosts. This is an experimental message shape, not a new versioned public platform schema. The agent is responsible for source admission even for cached inputs. The adapter does not evaluate Rego or parse all native manifests.

For an admitted invocation, Oyzu creates temporary Helm/Docker helper configuration, provides a same-image credential helper on the child PATH, and launches the native command. The native helper requests credentials from the session endpoint only when needed. Upstream credentials remain in process memory and helper pipes, not in those configuration files. The native client receives them; this is not an agent-only-secret boundary. The upstream credential enforces read-only access.

Each child has separate configuration and session environment. Temporary files are removed after completion, including ordinary child failure. Credential-free shell shim inventory remains in the user tool store. Abruptly killing the parent may leave temporary paths; crash recovery is not qualified.

No automatic direct fallback occurs after configured-agent denial or failure. Native stdout/stderr and exit status use the existing exec contract; global --json uses the existing captured-child representation. Helper stdout is the native credential JSON protocol, with only generic failure text on stderr.

Admitted source projection and cache operations​

The prototype admission response can include projection alongside credentialEndpoint and registries. The agent returns one resolved decision; the client does not combine permissions or evaluate policy. No schema version is introduced. For example (digest placeholders must be replaced):

{
  "credentialEndpoint": "http://127.0.0.1:43199/credential/session",
  "registries": ["mirror.example.com", "cache.example.com"],
  "projection": {
    "imageMappings": [{
      "from": "origin.example.com/team/base@sha256:<64-hex-digits>",
      "to": "mirror.example.com/team/base@sha256:<same-64-hex-digits>"
    }],
    "cacheReads": ["cache.example.com/team/build:shared"],
    "cacheWrites": []
  }
}

BuildKit​

With nonempty imageMappings, Oyzu writes a temporary native BuildKit source policy and passes --source-policy-file to buildctl. Exact, fully qualified image references are converted to their admitted destinations. Destinations must be digest-pinned and use an admitted registry authority. A digest-pinned source cannot change digest. Other image sources are denied through BuildKit's native source-policy mechanism. The Dockerfile and shared daemon configuration are not rewritten. Caller-supplied source-policy files conflict with managed admission.

The qualified native versions are BuildKit/buildctl 0.25.0 on Linux. This is source substitution, not daemon registry-mirror configuration. The controlled proof has no additional daemon mirror chain: a missing substituted image does not fall back to the original reference. This does not certify arbitrary shared daemon mirrors, redirects, custom frontends or hostile executors. HTTP/Git sources and arbitrary RUN networking are outside this image-source projection.

Omitting the projection or using no image mappings retains the earlier credential-helper prototype; it does not claim native image allowlisting. Session admission still occurs before launch, including warm-cache invocations.

Native registry cache import/export is separate from image publication:

oyzu exec -- buildctl --addr tcp://builder:1234 build \
  --frontend dockerfile.v0 --local context=. --local dockerfile=. \
  --output type=local,dest=dist \
  --import-cache type=registry,ref=cache.example.com/team/build:shared

--import-cache type=registry,ref=... requires the exact cacheReads reference; --export-cache type=registry,ref=... requires the exact cacheWrites reference. Both separated and equals-style flags are supported. Missing grants fail before native execution. Local/inline native cache types remain supported; other transports and ambiguous type declarations fail explicitly. Cache grants do not allow image exporters to publish: push=true and type=registry output remain unsupported in this launch path. Publication belongs to oyzu publish.

The helper still supplies one identity per registry authority for that invocation. The issuer must choose a narrowly scoped upstream identity covering the admitted operations. When independent credentials cannot fit that native constraint, use separate authorities or invocations; the client does not combine credentials. Cache hits retain their producer/evidence meaning and do not prove tests reran. This adds native BuildKit cache transport, not Oyzu action-cache key generation or cache-trust evaluation.

Helm​

A Helm response uses helmMappings instead of image/cache grants:

{
  "helmMappings": [{
    "from": "origin.example.com/charts/service",
    "to": "mirror.example.com/charts/service"
  }]
}

This projection currently supports one explicit helm pull oci://... reference. Oyzu substitutes only that argument, preserving version and other native arguments, working directory and environment. The destination authority must be admitted. Download the chart and then render the local archive with Helm. No Chart.yaml or lock file is rewritten. Mapped dependency or template operations fail as unsupported; the earlier unmapped helper flows remain distinct. BuildKit source policies never govern Helm retrieval.

Intermediate artifacts and evidence​

OCI intermediate storage is a separate storage purpose from cache or publication. The proof includes a digest-preserving manifest/blob round trip with scoped read/write identities. It does not add an Oyzu intermediate-upload command or implement platform RBAC and catalog binding.

Original source, substituted reference, observed request endpoint and digest are distinct facts. The proof records each using its controlled registry observers; this adapter does not yet emit a durable source-evidence report. Native logs are not independent attestations. In particular, a warm cache may produce no new registry request and must not claim a newly observed origin.

Errors and limits​

CodeMeaning and recovery
NATIVE_SESSION_CONFIGMove the agent endpoint from project configuration to authorized user/admin configuration
NATIVE_SESSION_UNAVAILABLEStart/reconnect the fixture agent; native execution has not started
NATIVE_SESSION_DENIEDAgent denied the requested context/source; resolve authorization rather than retrying directly
NATIVE_SESSION_INVALID, OCI_SESSION_INVALIDAgent transport or OCI response/registry addresses are invalid; repair the adapter/agent contract
OCI_ROUTING_CONFLICTCorrect conflicting source-policy/credential overrides, duplicate mappings, missing authorities or changed pinned digests
OCI_OPERATION_UNSUPPORTEDUse supported retrieval/cache arguments and obtain the specific cache grant; native publication is outside this route
OCI_SHIM_INVALIDRepair/recreate the generated native shim inventory

The prototype requires the configured local agent even for cached content. There is no offline grant implementation. Source validation in the proof uses fixed literal references and fixture policy; arbitrary Dockerfiles, dynamic arguments, transitive dependencies and third-party providers need their own qualification. Native helper selection follows Docker's accepted host-and-port model. No automatic combining of connector permissions occurs.

No lock/schema migration is introduced. The new setting is experimental and does not turn on behavior unless configured. The main reference's standalone tool installation and shell lifecycle contracts continue to own those responsibilities.

The shared native admission transport now reports NATIVE_SESSION_* for configuration, availability, denial and transport validation. This replaces the prototype transport's earlier OCI_SESSION_* names; OCI response validation and operation-specific diagnostics retain their OCI prefix.
