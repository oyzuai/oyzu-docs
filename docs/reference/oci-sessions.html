Private OCI registries

CLI reference

Published from the canonical docs/reference/oci-sessions.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Use this when Helm or BuildKit (buildctl) should pull charts and images from private OCI registries without credentials in Docker or Helm config files. Each time you run helm or buildctl through oyzu, oyzu asks a local credential agent which registries are allowed, and a credential helper hands the client credentials only when it needs them. The agent can also redirect images and charts to approved mirrors and grant access to BuildKit cache references.

Note: Experimental. You need a credential agent running on the same machine; oyzu doesn't include one, and it doesn't install Helm or BuildKit. Supported on Linux (BuildKit 0.25.0).

Configure​

Add the agent's address to your user or administrator configuration (not the project's oyzu.toml):

[oci]
sessionEndpoint = "http://127.0.0.1:43199/session"
SettingValuesDefaultMeaning
oci.sessionEndpointhttp://127.0.0.1:<port>/<path>, no user name, password, query or fragmentNot setThe local agent to ask for sessions. Remove it to go back to plain Helm and BuildKit

Project, local and command-line configuration and profiles can't set this value. User configuration isn't read in CI, so this doesn't work there. OYZU_USER_CONFIG can point at a different user configuration file.

Run Helm or BuildKit​

oyzu exec -- /usr/local/bin/helm pull oci://registry.example.com/charts/sample --version 0.1.0
oyzu exec -- /usr/local/bin/buildctl --addr tcp://builder.example.com:1234 build \
  --frontend dockerfile.v0 --local context=. --local dockerfile=. \
  --output type=local,dest=dist

In an activated Bash shell, oyzu adds shims for helm and buildctl found on PATH, so bare helm and buildctl go through oyzu too. Each run asks the agent for a fresh session.

ClientSupported
Helmpull, dependency, template
BuildKitCommands with build

--help, -h and helm version run without asking the agent. Other executables run normally. Configure TLS for your registries and builder yourself.

These are refused:

  • --registry-config, --username and --password (OCI_ROUTING_CONFLICT);
  • push=true and registry image outputs (OCI_OPERATION_UNSUPPORTED). Publish with oyzu publish.

What oyzu does for you​

  1. Sends the agent a POST with {"directory": "<working dir>", "tool": "helm" or "buildctl", "arguments": [...]}. This happens on every run, even when content is cached.

  2. Reads the agent's answer:

    {
      "credentialEndpoint": "http://127.0.0.1:43199/credential/session",
      "registries": ["registry.example.com"]
    }

  3. Writes a temporary Helm and Docker config whose credHelpers point each listed registry at oyzu's credential helper, and puts the helper on the child's PATH.

  4. When the client needs credentials, the helper POSTs {"registry": "<host>"} to credentialEndpoint, which must answer {"username": "...", "secret": "..."}.

  5. Removes the temporary files when the command finishes or fails.

The agent decides what's allowed, including for cached content. oyzu doesn't evaluate policy or read every manifest itself.

Admitted source projection and cache operations​

The agent's answer can also include a projection that redirects sources and grants cache access. Replace the digest placeholders with real digests:

{
  "credentialEndpoint": "http://127.0.0.1:43199/credential/session",
  "registries": ["mirror.example.com", "cache.example.com"],
  "projection": {
    "imageMappings": [{
      "from": "origin.example.com/team/base@sha256:<64-hex-digits>",
      "to": "mirror.example.com/team/base@sha256:<same-64-hex-digits>"
    }],
    "cacheReads": ["cache.example.com/team/build:shared"],
    "cacheWrites": []
  }
}

BuildKit images​

With imageMappings, oyzu writes a temporary BuildKit source policy and passes it with --source-policy-file:

  • Each exact, fully qualified image reference is replaced with its mapped destination. Destinations must be pinned by digest and on a listed registry. A pinned source can't change digest.
  • Every other image source is denied.
  • Your Dockerfile and the BuildKit daemon configuration aren't changed.
  • Passing your own --source-policy-file conflicts with this.

If a mapped image is missing from the mirror, the build fails; it doesn't fall back to the original reference. HTTP and Git sources and network access from RUN steps aren't covered. Without a projection, or with no image mappings, oyzu only supplies credentials and doesn't restrict images.

BuildKit cache​

oyzu exec -- buildctl --addr tcp://builder:1234 build \
  --frontend dockerfile.v0 --local context=. --local dockerfile=. \
  --output type=local,dest=dist \
  --import-cache type=registry,ref=cache.example.com/team/build:shared
  • --import-cache type=registry,ref=... needs that exact reference in cacheReads.
  • --export-cache type=registry,ref=... needs that exact reference in cacheWrites.
  • Both --flag value and --flag=value forms work. Missing grants fail before BuildKit runs.
  • local and inline caches work as usual. Other cache types, or unclear ones, fail.
  • Cache grants don't allow publishing images.

The helper supplies one identity per registry host for a run, so the agent should issue one identity that covers everything allowed on that host. Use separate hosts or runs if you need different credentials. A cache hit means BuildKit reused a result; it doesn't mean tests ran again.

Helm charts​

For Helm, the agent returns helmMappings instead:

{
  "helmMappings": [{
    "from": "origin.example.com/charts/service",
    "to": "mirror.example.com/charts/service"
  }]
}

This works for one helm pull oci://... reference. oyzu replaces just that argument and keeps the version and other options. The destination host must be listed. Chart.yaml and lock files aren't changed. Pull the chart first, then render the local archive with Helm. Mapped dependency and template commands fail as unsupported.

Credentials and security​

  • Credentials never go into the temporary config files. They pass through the helper into the client's memory, so the client can read them.
  • Read-only access has to be enforced by the registry identity the agent uses.
  • The helper prints only a generic error on failure.
  • Denial or an unreachable agent stops the command with no fallback. There's no offline mode: the agent must be reachable even for cached content.

Output​

The client's output and exit code pass through unchanged. With --json, they're captured in the usual oyzu exec result.

Errors​

CodeCauseFix
NATIVE_SESSION_CONFIGThe endpoint is set in project or local configurationMove it to user or administrator configuration
NATIVE_SESSION_UNAVAILABLEThe agent can't be reached. The command hasn't startedStart the agent and retry
NATIVE_SESSION_DENIEDThe agent refused the requestGet access granted; don't work around the agent
NATIVE_SESSION_INVALIDThe endpoint isn't 127.0.0.1 HTTP, or the response is too largeFix the endpoint or the agent
OCI_SESSION_INVALIDThe response or its registry addresses aren't validFix the agent's response
OCI_ROUTING_CONFLICTCredential or source-policy overrides, duplicate mappings, a destination on an unlisted registry, or a changed digestRemove the override or fix the mapping
OCI_OPERATION_UNSUPPORTEDAn unsupported command, publishing, or a cache reference without a grantUse a supported command and get the cache grant. Publish with oyzu publish
OCI_SHIM_INVALIDThe generated shims are damagedRecreate them by activating the shell again

Limits​

  • Not a general Docker CLI integration.
  • Arbitrary Dockerfiles, dynamic arguments and transitive dependencies aren't checked by oyzu beyond the source policy.
  • oyzu doesn't record which source each image came from in a report.
  • Temporary files may be left behind if oyzu is killed.
  • Windows has no shell shims, and Windows and macOS execution aren't supported yet.
