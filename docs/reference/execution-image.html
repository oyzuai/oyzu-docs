Execution image

CLI reference

Published from the canonical docs/reference/execution-image.md file. Features marked experimental remain experimental; check support limitations before relying on them.

oyzu build --isolated runs every container action on one small Linux image, the base execution image oyzu-execution/base:1. It holds operating system pieces and a C toolchain and nothing else. Oyzu mounts everything a build needs into it: the invocation's own engine, the builder's plugin package and the tools oyzu.lock selects. Native builds (plain oyzu build on a host that has a native build for the project) don't use it.

This page lists what the image contains, how Oyzu gets it, and what an image of your own must provide when you pass --image.

Platform scope: Use an x64 host and supported x64 build targets. ARM64 is unsupported. Feature-specific limits are listed in the support matrix.

Quick start​

oyzu build --isolated                          # every builder runs on the base image, pulled on first use
oyzu build --isolated --image npm=node:22-trixie-slim   # one manager on your own image

What runs in a container action​

Each action is assembled the same way, whichever builder it belongs to:

  1. Image. An explicit --image <manager>=<ref> for that manager, otherwise the base image for the action's architecture.
  2. Engine. The invocation's engine is mounted read-only. With an installed engine package (oyzu engine install, which the Windows and macOS install scripts run for you, or an [engine].identity pin in oyzu.lock), Oyzu mounts its Linux member for the image's architecture (the static musl one when the package has several). Without one, a Linux CLI of the same architecture mounts its own executable. On Windows and macOS hosts an engine package is required; without it the build stops with ENGINE_ASSET_UNAVAILABLE before any work. No image carries an Oyzu worker, so a new CLI release never needs a new image.
  3. Tools. Every language toolchain and stage tool comes from oyzu.lock and is restored read-only into the action: Rust and its components, cargo-nextest, cargo-llvm-cov, Go, Node with npm, pnpm or Yarn, CPython, the .NET SDK, the JDK with Maven, Gradle or Ant, Helm and yamlfmt, and Zig. A builder whose tool isn't locked for the platform stops with the oyzu pin command that fixes it; the image has no copy to fall back to.
  4. Plugin. The selected builder plugin package is mounted read-only at /oyzu-plugin, with any helpers it ships: the Docker plugin's metadata, image and snapshot helpers, BuildKit frontend and dockerfmt, and the Node plugin's pnpm and Yarn lockfile parsers.
  5. Pinned integration files. A few upstream files that aren't tools in the lock are fetched once, checked against a SHA-256 pinned in Oyzu, stored with your declared fetches and restored read-only: the default Node lint, format and coverage packages (Node quality), Checkstyle, google-java-format, JaCoCo, JUnit and Ant for Java builds (Java quality), the helm-unittest plugin when a chart has unit test suites (Helm), and the cross linkers of a Rust cross build (Rust).

The plan and the build evidence record the image digest, the engine member, the plugin release and each tool's locked identity.

In the daemonless Linux executor, each invocation has a fresh private /tmp. When its declared HOME is a directory beneath /tmp, that directory is also created as a private temporary filesystem owned by the action's user, with mode 0700. This applies separately to compilation and each test invocation; a home created by an earlier phase is not reused. The executor keeps the declared HOME value, imports no host home contents, and discards the temporary home when the sandbox ends. Homes outside /tmp retain the image's existing behavior.

Docker image builds that run RUN steps use a second image, the rootless BuildKit worker oyzu-execution/buildkit:0.34.0. It is the upstream moby/buildkit 0.34.0 rootless image pinned by digest, with nothing of Oyzu's added. See Docker image inputs.

What the base image contains​

The image is Ubuntu 24.04 (ubuntu:24.04, pinned by digest) with these packages, built for the supported linux/amd64 platform:

PackageWhy it is there
gcc, g++, libc6-dev, make, cmake, ninja-build, pkg-configC and C++ compilers and build tools for Rust build scripts, cgo, native npm and Python extensions and Zig's C interop. Rust links with cc.
musl-toolsmusl-gcc, for C code in a static musl build.
gitNative tools that read Git metadata, such as Go VCS stamping and Cargo Git dependencies.
ca-certificates, tzdataTLS roots and time zones for tools and tests.
libssl3t64, libgssapi-krb5-2, libicu74, zlib1g, libatomic1Shared libraries the locked .NET SDK and Node releases load.
bzip2, xz-utils, zstd, zip, unzip, patch, fileArchive and patch tools native builds call, and .tar.xz restoration of locked tools.

Oyzu builds and publishes the Linux amd64 image itself from tooling/images/build.yaml, installing the packages from an OS package lock that lists every version, including the dependencies apt pulled in; tooling/images/base/debs.lock.yaml is the committed copy, and each publishing run uploads the lock it actually built from. Publication uses the single image's manifest digest, without composing a multi-platform index. See Dogfooding in workflows.

The source lock selects libbrotli1 1.1.0-2ubuntu0.1 for amd64, Ubuntu's fix for CVE-2026-111497. This applies to images rebuilt from that lock. Updating it does not replace the CLI's published image pin, existing local images or running containers.

The source lock and required image-build matrix use amd64. ARM64 image builds are unsupported.

There is no language runtime, package manager, Oyzu engine or Oyzu plugin in it. PATH is the standard Ubuntu one; each action prepends the restored tools.

glibc 2.39​

Ubuntu 24.04 ships glibc 2.39. Anything a build links against glibc in the container needs glibc 2.39 or newer wherever it later runs. A Rust or Go binary built for linux/* with the GNU target won't start on an older distribution such as Debian bookworm (glibc 2.36) or Ubuntu 22.04 (glibc 2.35).

If your binaries must run on older Linux systems, build them statically: target musl in Rust (x86_64-unknown-linux-musl, aarch64-unknown-linux-musl; Oyzu's isolated cross builds already link those with rust-lld), or build Go with CGO_ENABLED=0. A Docker image's own base decides its libc at run time; this note is about binaries built in the execution image and copied elsewhere.

How Oyzu gets the image​

When the image isn't in the local Docker engine, Oyzu pulls it from ghcr.io/oyzuai/oyzu-execution/base by the digest pinned in the CLI, so a moved tag can't substitute another image. The package is public and needs no login. An image already present locally is used as it is.

  • To use an image built from source instead, build it under the same name before the first isolated build: docker build -t oyzu-execution/base:1 tooling/images/base from a checkout of the Oyzu repository. A local image of that name is used as it is, without a digest check.
  • Set OYZU_NO_TOOLCHAIN_PULL=1 to forbid every pull, for example on an air-gapped host that preloads the image.
  • The BuildKit worker is pulled the same way from docker.io/moby/buildkit by its pinned digest.
  • Oyzu records pulled images and keeps them within the Docker storage budget.

An organization registry allow-list and mirror for Oyzu-published images is designed in the platform repository and not implemented in the CLI yet.

Bring your own image​

--image <manager>=<ref> runs that manager's isolated actions on an image you choose, for example one with OS packages your native build links against:

oyzu build --isolated --image cargo=registry.example.com/build/rust-base:2026-10

The manager is the one the target's builder uses, for example cargo, go, npm, pnpm, yarn, pip, uv or poetry. The reference must already be in the local Docker engine; Oyzu never pulls a bring-your-own image. The image's immutable identity is recorded in the plan and evidence.

The image must provide:

  • Linux on the action's architecture. A linux/arm64 action needs an arm64 image.
  • A C runtime the engine can start on. An engine package's static Linux member runs on any libc. When a Linux CLI mounts its own executable instead, that executable's glibc requirement applies; release builds need glibc 2.39 or newer.
  • A C runtime the locked tools can start on. The official Node, .NET, JDK and Rust releases need glibc, and Rust and cgo need a working cc. Alpine and other musl images only suit tools that are static.
  • tar that extracts .tar.gz and .tar.xz archives with --strip-components, and sleep: Oyzu restores locked tools with the image's own tar and keeps tool volumes in use with sleep.
  • Whatever OS packages the project's native build needs.

Oyzu still mounts the engine, the plugin and the locked tools; an image's own copy of a tool is never used in place of the locked one.

Limits​

  • Isolated uv builds restore uv from oyzu.lock. Poetry builds still need an image with Poetry installed, passed with --image poetry=<ref>.
  • Rust builds for macOS link against Zig's libSystem stubs, with no Apple SDK in the image. Crates that link other Apple frameworks need an image that provides an SDK (SDKROOT).
  • Only linux/amd64 workers are supported. ARM64 is unsupported.
  • Remote pools don't use this image yet.
