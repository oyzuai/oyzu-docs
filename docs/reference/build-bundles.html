Build bundles and retention

CLI reference

Published from the canonical docs/reference/build-bundles.md file. Features marked experimental remain experimental; check support limitations before relying on them.

oyzu build finalizes its results under the workspace's dist/. The bundle contains the manifest, frozen plan when planning succeeded, execution envelope, native logs, retained reports and collected snapshot artifacts. A failed build can still produce a useful bundle; consult manifest.json for actual outcomes. oyzu inspect (no argument: this project's dist/) or oyzu inspect dist checks recorded content integrity and does not establish trusted CI identity or release eligibility.

Layout​

Every artifact a target produces, and that target's reports, is written below dist/<target>/<platform>/ (build intent BIN-07). The platform is the canonical os/arch name (linux/x86_64, windows/arm64, darwin/arm64), with -<abi> on the architecture only when the platform was declared or requested with an ABI that is not the OS's naming default (linux/arm64-musl; see below); output a builder declares platform-independent uses any instead:

dist/
  manifest.json  plan.json  envelope.json  logs/
  cli/windows/x86_64/oyzu.exe
  cli/windows/x86_64/oyzu-shim.exe
  cli/windows/x86_64/reports/junit.xml
  docs/windows/x86_64/application-0.1.0/

The layout is the same for local, multi-platform and CI builds, so bundles for different platforms merge without collisions. Which platform a target uses:

BuildPlatform directory
Native host buildThe host (windows/x86_64 on 64-bit Windows)
Isolated (captured) buildThe platform the toolchain image builds for, such as linux/x86_64, or the target's one declared platform (platforms)
Captured worker under a native build (Docker image targets)The worker's platform
Builder declares the output platform-independent (independent artifact compatibility)any; no built-in builder declares this for a whole target yet
OCI image indexany; the index spans its member platforms

Node applications, including static dist/ and Vite sites, stay per target platform as before (maintainer decision of 2026-10-18); an explicit opt-in for platform-neutral Node output is a follow-up.

The manifest and plan record each artifact's bundle-relative path (cli/windows/x86_64/oyzu.exe); consumers such as oyzu inspect, publication, the action cache and bundle handoff read that path and never assume a layout. Plan target records carry the directory as the oyzu.dev/output extension. reports is reserved: no artifact may be named reports, because it is the target's report directory. A builder-internal file, such as Docker's intermediate container/image.tar, also lives in the platform directory; Vite's vite-state.json stays at dist/<target>/.

Each artifact record also carries profile: development or optimized, the build profile its producing commands actually used, shown on its Outputs row. Which profile a target builds follows where its output goes, build.optimized and --optimized/--no-optimized (optimized builds); the target records the decision as extensions["oyzu.dev/optimization"]. optimized is recorded only for an artifact the optimizing profile actually changes: Rust binaries, native or isolated (cargo build --release; .crate source archives stay development), and .NET packages (--configuration Release). Builders whose output optimization does not change keep development. When the target's build or the artifact's producer is an authored task replacing the builder's command, the artifact is development.

Platform and executor. Each target record's platform is the platform it was built for (canonical os/arch[/abi]), with the ABI its toolchain resolved when the OS has several ({"os":"linux","arch":"arm64","abi":"musl"}; Rust records it today); its artifacts' compatibility carries the same platform. The dist/<target>/<platform>/ directory uses the published form of the declared or requested platform: an ABI appears only when it is not the OS's default, as a sibling folder that never nests inside another (--platform linux/arm64/musl writes dist/<target>/linux/arm64-musl/, linux/arm64/gnu writes dist/<target>/linux/arm64/), so builds of both ABIs merge into one tree without collisions when the ABI is declared or requested. The folder follows the declared or requested platform, not the resolved ABI, which is known only after planning: a target declaring linux/arm64 that is cross-built to musl lands in dist/<target>/linux/arm64/ although its asset is -musl and its evidence path linux/arm64-musl, and a native GNU build and a musl cross build of that undeclared ABI share one folder. Declare the ABI (linux/arm64/musl) to keep them apart; a folder that follows the resolved ABI is a recorded follow-up, and extensions["oyzu.dev/platforms"] records how it was built: target (the logical target every platform variant shares), declared (the platforms the target declares), declaredExecutors, platform and executor ({"kind":"host"}, {"kind":"cross-toolchain","toolchain":"rust-lld","target":"aarch64-unknown-linux-musl"} or {"kind":"container"}), and one rows entry per declared or requested platform with selected, executor or reason, and the runner that builds it on its own host. Image-worker targets record target, declared, platform and the container executor. Publication reads declared to refuse an incomplete platform set. An executor other than the host is part of the target's action-cache identity. See platforms and executors.

Executable verification. An artifact the builder declares a native executable (Rust and Go binaries; an external plugin's executable flag only promotes a file to .oyzu/bin and is not verified) is verified statically when it is collected, on the native and isolated paths: the file must be a valid executable for its target platform (an ELF, Mach-O, including a universal binary's matching slice, or PE header), name that platform's architecture, and contain every loadable segment or section it declares (not empty or truncated). The artifact is never run, so cross-built artifacts are verified too. The record carries extensions["oyzu.dev/executable"]: platform from planning and, once verified, verified.format (elf, mach-o, pe) and verified.architecture. A failure is EXECUTABLE_INVALID: artifact <id> is not a valid <platform> executable: <cause> and fails the build; the artifact keeps its ordinary kind (file). Known architectures are x86_64, arm64, 386, arm, riscv64, ppc64le and s390x; another is refused as unknown.

Limitations: a Python wheel whose compatibility is inspected after the build stays in the target's platform directory even when it turns out to be py3-none-any. A direct oyzu run <target>:test places reports under the host platform. A native artifact named reports is refused with a reserved-name error before the build runs.

Integrity​

When a frozen plan exists, inspection also requires matching manifest target records and declared artifact target/variant identities. Relabeling a runtime variant in the manifest without changing the corresponding plan is rejected. A target finalized after declared generator hooks must match its existing recorded post-hook plan. Inspection verifies that plan's bytes, base, fresh successful hooks, native version identity and unchanged context; only declared version followers may change their version values. Missing or altered finalization evidence fails inspection. Runtime-specific reports remain attributable through their concrete target records; see runtime matrices. This consistency check does not authenticate either record.

A successful bundle must contain every planned artifact and every required successful action and report. Inspection reuses the report collector's native parsers and current plan gates, including coverage policy, instead of accepting stored summaries alone. Missing required records, changed bytes or a failing native report fail inspection. Reused reports retain their original producer.

For an OCI image artifact, inspection additionally verifies that the archive's actual OS/architecture matches its target record. Collection enforces the same check, including after custom test or packaging tasks. A valid archive digest alone cannot establish that the image was built for the requested platform. See Docker target selection; structural image checks do not prove application execution on that target.

Workspace ownership​

An invocation holds an operating-system file lock on .oyzu/build.lock through staging and finalization. Another cooperating build in that workspace fails before execution with a workspace-lock diagnostic. The existence of the lock file alone does not indicate a live build: the operating-system lock is authoritative and is released when its owning process exits. Different workspace roots have independent locks.

The engine creates its staging directory under .oyzu/bundle-* on the destination filesystem. It admits an existing dist only when it is a directory containing an Oyzu build manifest. A preexisting application-owned dist must be preserved or moved by its owner before building; Oyzu does not delete it. State, lock, bundle marker and destination paths reject symbolic links, including dangling links, and Windows reparse points. History paths receive the same checks before use.

The invocation records the existing manifest's content identity, or the absence of a destination. Immediately before finalization it rechecks that state. A newly created destination, changed manifest, invalid destination or existing history slot stops finalization instead of overwriting it. This is a change check, not a proof that every byte in the older bundle remained unchanged.

Finalization and recovery​

When records are finalized, the previous dist is moved to .oyzu/history/<new-run-id>, and the staged directory becomes dist. No reports or artifacts are appended to the old manifest. If the second rename fails, Oyzu attempts to restore the prior bundle. If restoration also fails, the diagnostic identifies the history path containing the previous bundle.

Native builds retire the previous bundle's claimed artifacts into history even when the new build fails. They do not copy those artifacts back into dist as unclaimed files, which would prevent a later successful retry. Unrelated native files remain preserved and collision-protected; .oyzu/bin stays at the last successful build. Test-only output preservation retains its separate contract. If an older bundle already records old binaries as unclaimed host output, preserve or relocate that bundle before rebuilding: a matching filename alone does not authorize replacement.

A finalization error retains the new staging directory and includes its exact path in the error. Inspect that path directly when its records are complete:

oyzu inspect .oyzu/bundle-EXAMPLE

Use the path from the diagnostic, not the literal example name. Preserve the conflicting destination and resolve the filesystem problem before rebuilding. Retained staging directories are not automatically considered successful builds or reused as input. An ordinary abandoned staging scope is cleaned up; read-only --plan creates no staging scope. Failures while writing records, abrupt termination and full disks can leave incomplete evidence; a retained directory alone does not prove a valid bundle.

The filesystem publication step does not contact a registry or require network access. It adds no configuration or UI dependency. --plan is a read-only preview; it performs no image/dependency preparation and never replaces dist.

Complete slice contributions​

The executable plan's existing target extensions retain the final native placement facts under oyzu.dev/execution (needsDaemon, executionPlatform) and the separate result/effect facts under oyzu.dev/slice (transferable, repeatable, reason, detail). A transferable contract is not an actual cache hit. Missing bounded native result coverage keeps transferability false; safe repetition additionally requires supported confined commands. These facts do not grant authority to repeat hooks or unknown effects. Coupled work can remain one invocation without new user placement configuration.

Experimental implementation for #479: a successful --slice --handoff <repository> offers its sealed complete bundle before filesystem publication, in addition to existing computation-result handoffs. The selected plan, envelope, logs, directory/file artifacts and native reports travel together. The registry is required for this explicit slice flow; ordinary local finalization remains offline.

The existing v1alpha1 OCI layout is extended in place:

PartBinding
Repository and tag<handoff>/v1alpha1/<first two manifest-digest hex>:bundle-<64 hex>
Artifact typeapplication/vnd.oyzu.build-bundle.v1alpha1
ConfigCanonical manifest.json bytes, application/vnd.oyzu.build-manifest.v1alpha1+json; SHA-256 equals the tag identity
LayerOne application/vnd.oyzu.build-bundle.v1alpha1.tar+zstd archive containing the other bundle entries
Annotationsdev.oyzu.build.manifest names the config digest; dev.oyzu.bundle.uncompressed-digest names the raw tar digest

Archive entries are sorted portable paths with zero uid/gid/mtime, regular files at 0644/0755 and directories at 0755, including empty artifact directories. Links are rejected by the existing snapshot owner. Config plus compressed layer and the expanded tar each have a 256 MiB bound. The existing OCI client supplies authentication, transport retries and immutable publication. An identical entry converges; a different or corrupt entry at that identity fails.

Upload retries reuse the sealed bytes without native command replay. If delivery still fails, the invocation records HANDOFF_PUSH_FAILED and exit 5 while preserving its actual successful action outcomes. Its ordinary bundle evidence retains the successful config, compressed layer and OCI entry bytes for a private transfer-only retry. That retry validates all retained identities and leaves the finalized failed invocation immutable. It does not authorize a new execution or make an unverified platform attempt successful.

This transport does not authenticate the producer or decide run-wide completion. The platform must accept the live attempt and verify complete selected obligations. See the qualification record for measured transport coverage and the still-pending real-service proof.

Retained invocation lookup​

oyzu history
oyzu history <invocation-id>
oyzu history <run-id> --json
oyzu inspect <bundle-directory> --json

history reads the current dist/manifest.json and finalized manifests under .oyzu/history/. It looks up the recorded identity inside each manifest, because a history directory is named for the replacing run. Old bundles lacking invocationId remain selectable by their runId. It performs no installation, network calls, execution or artifact hashing; inspect separately verifies a named complete bundle. Invalid identifiers fail with INVOCATION_ID_INVALID; missing identities fail with INVOCATION_NOT_FOUND and a listing next action.

Listing returns at most twenty summaries, ordered by available envelope start time, plus omitted counts and up to eight incomplete-bundle notices. A selected summary contains reconciled action counts, fresh/reused/unknown-origin test totals, warnings, at most eight exceptional actions and eight diagnostics, bounded diagnostic excerpts, available reuse provenance and evidence paths. It also contains at most eight recorded action decisions (decisions, with omittedDecisions), the recorded selection, and cache status/reason. Nested inventories keep at most eight entries with adjacent *Omitted counts; selection reason/variant maps also retain at most eight keys with omission counts. Recorded cacheLimitations retain unavailable local/remote tiers and selectionFallback retains a fallback reason independently of warning diagnostics. Each decision preserves its actual outcome, execution/reuse reason, available captured-source comparison and original producer. Human history and build --explain share this projection; the complete manifest retains omitted details. It does not include native log bodies or environments. Missing event/plan/action logs are explicitly unavailable. The complete manifest and available files can be opened using the returned paths. Summary availability is not artifact verification or proof that a journal contains every execution event.

Later source/configuration changes or cache clear do not rewrite these selected invocation decisions. History never substitutes current preview analysis or the latest cache-key history. Older or incomplete records without file comparison detail explicitly report it unavailable, preserving known outcomes and producer provenance. A reused test report remains evidence of earlier execution.

A plan or manifest target whose configuration a policy constraint changed records extensions["oyzu.dev/policy-overrides"]: one entry per override with the setting, the effective value, the constraint (source, kind of lock, minimum, maximum or required, bound, selector), what it replaced (value, source relative to the project root, scope) and the human note (see policy constraints and selectors). The constraint's label is org policy, admin policy or, for the root oyzu.toml's project constraints (source oyzu.toml [constraints]), project constraint. A release build's target whose check a nearer folder lowered below a farther [context.release] value records extensions["oyzu.dev/release-lowerings"]: one entry per check with the setting, the value used, its source (app/oyzu.toml:2), the releaseValue and its releaseSource (oyzu.toml:5), relative to the farther file's folder (per-context values).

The checks summary projects captured target oyzu.dev/build-checks facts: selected action IDs, logical operations and native report kinds, explicit omitted operations, and outcomes joined to the finalized action records. targets keeps eight rows, with omission counts; aggregate counts include all recorded rows. tests on each target is selected, not-requested or unknown. Only a valid complete captured selected array establishes absence of selected tests; missing or malformed historical selection remains unknown. Current configuration and report counts never fill that gap. Aggregate checks.status is recorded when every target has captured selection, partial for a mix, and unknown when none do; unknownTargets retains the count.

Test totals remain split by fresh/reused/unknown origin. Each bucket adds zeroTestReports for collected native reports explicitly recording total: 0. Missing passed, failed or skipped facts make that aggregate field null, rendered unavailable; a bucket with no reports also has unknown numeric totals. Zero tests, native skips, missing required reports and absent evidence remain distinct. Human receipts and history use the same shared check projection; build JSON retains the full target selection and report facts in its manifest.

This is local build/test-bundle history, governed by existing filesystem access and bundle retention. Nothing is uploaded or granted to another user. There is no automatic history expiry or deletion command; bundles remain until their owner explicitly removes them. An operation ending before bundle creation has no retained entry. Abrupt termination, sink/write failures, incomplete staging, externally removed bundles and interactive native streams can leave partial or missing evidence. Remote run history and general command transcripts remain unimplemented; remote portal links are the available inspection route.

Plugin provenance​

When an external builder is bound (see plugin packages), the plan, execution envelope and manifest each carry extensions["oyzu.dev/plugins"]: one record per bound reference with its source (package or local-development), identity and executableDigest. The plan digest covers the plan's copy. oyzu inspect fails with plugin records differ from plan or … from envelope when the manifest's or envelope's copy is missing or edited. Like every inspect check this is integrity of recorded content, not proof of who produced it.

Verification and limits​

Rust tests cover lock contention, first/repeated finalization, history retention, ordinary staging cleanup, changed or newly created destinations, history collisions, invalid run IDs, incomplete staging records and retained failure evidence. Windows tests create real directory junctions and verify rejection without modifying the target. Unix symlink checks run in the Linux/macOS test jobs. The existing captured-build suites exercise the same lifecycle with native artifacts, repeated builds and failed-build reports; consult implementation status for revision-specific evidence.

The two renames are not a power-loss-safe transaction. There is no automatic journal recovery if the process or machine stops between them. Path checks and locks also do not make the store race-free against a hostile process with permission to replace directories. Inspection verifies recorded outputs separately from these destination checks. Remote storage and automatic history retention limits remain unfinished.

The direct Node/Python/Go test workflow reuses this transaction with host output preservation. Unlike captured builds, it can admit native application output in dist, copy that output into the new test-only bundle and retain the original directory in history. These bytes have a separate integrity inventory and are not new build artifacts. It removes prior engine report/evidence claims from the current bundle, preserves their original bytes in history, and rejects reserved-path collisions. Other direct test profiles remain to be integrated.
