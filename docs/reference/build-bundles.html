Build bundles and retention

CLI reference

Published from the canonical docs/reference/build-bundles.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Every oyzu build writes its results to a bundle, in dist/ by default. The bundle holds the manifest, the plan, the execution record, logs, reports and the artifacts themselves. Use oyzu inspect to check a bundle and oyzu history to look up earlier builds.

oyzu build
oyzu inspect          # check this project's bundle
oyzu history          # recent builds

A failed build still writes a bundle. Read manifest.json for what actually happened.

Bundle destination​

If your project already uses dist/ for its own files, put the Oyzu bundle somewhere else in the root oyzu.toml:

[build]
bundleDirectory = ".oyzu/bundle"
SettingValuesDefaultWhere
build.bundleDirectorydist, .oyzu/bundledistRoot oyzu.toml only (including root context and profile sections, and policy). Component, local and per-folder values are refused.
  • Other paths aren't supported, and Oyzu doesn't pick a destination for you.
  • The destination doesn't change artifact names or identities. Artifact paths in the manifest are relative to the bundle.
  • .oyzu/bundle is never treated as source. If a build reads your own dist/, declare it with inputs: [dist] in that build's build.yaml entry. Being tracked in Git isn't enough.
  • oyzu inspect (with no argument), history, scan, publish and local image loading all use the chosen destination. They never fall back to an old dist/.
  • oyzu inspect <path> with an explicit path reads that bundle directly, without opening project configuration.
  • Connected publishing (oyzu publish --server ...) and oyzu release check read dist/manifest.json by default. Pass --manifest .oyzu/bundle/manifest.json if you moved the bundle.
  • The manifest records the destination in extensions["oyzu.dev/bundle-directory"]. To inspect a bundle you moved by hand, pass its path.

Layout​

Each target's artifacts and reports go under <bundle>/<target>/<platform>/:

dist/
  manifest.json  plan.json  envelope.json  logs/
  cli/windows/x86_64/oyzu.exe
  cli/windows/x86_64/oyzu-shim.exe
  cli/windows/x86_64/reports/junit.xml
  docs/windows/x86_64/application-0.1.0/

The layout is the same for local, multi-platform and CI builds, so bundles from different platforms merge without collisions.

Platform directory names​

  • The platform folder is os/arch, such as linux/x86_64, windows/arm64 or darwin/arm64.
  • An ABI is added to the architecture only when you declared or requested one that isn't the OS default: --platform linux/arm64/musl writes linux/arm64-musl/, while linux/arm64/gnu writes linux/arm64/.
  • Output that is platform-independent uses any.
BuildPlatform folder
Native host buildThe host, such as windows/x86_64.
Isolated buildThe platform of the execution image the action runs on (such as linux/x86_64), or the target's single declared platform.
Docker image target under a native buildThe worker's platform.
Output a builder declares platform-independentany. No built-in builder does this for a whole target yet.
OCI image indexany, since it covers several platforms.

Node applications, including static dist/ and Vite sites, are kept per platform.

The folder follows the platform you declared or requested, not the ABI the toolchain picked. If a target declares linux/arm64 and is cross-built to musl, it lands in linux/arm64/ even though the asset is -musl. Declare the ABI (linux/arm64/musl) to keep GNU and musl builds apart.

Paths in the manifest and plan​

  • The manifest and plan record each artifact's path relative to the bundle (for example cli/windows/x86_64/oyzu.exe). oyzu inspect, oyzu publish and the action cache read that path; they never assume a layout.
  • reports is reserved for a target's reports. No artifact can be named reports.
  • Builder-internal files, such as Docker's container/image.tar, also live in the platform folder. Vite's vite-state.json stays in dist/<target>/.

Build profile​

Each artifact records profile: development or optimized, the profile its build actually used. It's shown on its Outputs row.

  • Which profile a target uses depends on where its output goes, build.optimized and --optimized / --no-optimized; see optimized builds.
  • optimized is recorded only where the profile changes the output: Rust binaries (cargo build --release) and .NET packages (--configuration Release). Rust .crate archives and other builders' output stay development.
  • Output from a custom task that replaces the builder's command is development.

Platform and executor​

Each target records the platform it was built for (os/arch[/abi]), including the ABI when the OS has several, for example {"os":"linux","arch":"arm64","abi":"musl"} (recorded for Rust today).

extensions["oyzu.dev/platforms"] records how the target was built:

FieldMeaning
targetThe logical target all platform variants share.
declaredThe platforms the target declares.
declaredExecutorsThe executors declared.
platform, executorWhat this record was built for and with: {"kind":"host"}, {"kind":"cross-toolchain","toolchain":"rust-lld","target":"aarch64-unknown-linux-musl"} or {"kind":"container"}.
rowsOne entry per declared or requested platform with selected, executor or reason, and the runner that builds it.

oyzu publish uses declared to refuse an incomplete platform set. See platforms and executors.

Executable verification​

When Oyzu collects a native executable (Rust and Go binaries), it checks the file without running it, so cross-built binaries are checked too.

  • It must be a valid ELF, Mach-O (including the matching slice of a universal binary) or PE file for the target platform and architecture, and must not be empty or truncated.
  • The record gets extensions["oyzu.dev/executable"] with platform and, once checked, verified.format (elf, mach-o, pe) and verified.architecture.
  • A failure stops the build with EXECUTABLE_INVALID: artifact <id> is not a valid <platform> executable: <cause>.
  • Known architectures: x86_64, arm64, 386, arm, riscv64, ppc64le, s390x.
  • A plugin's executable flag only places a file in .oyzu/bin; it isn't checked.

Layout limitations​

  • A Python wheel that turns out to be py3-none-any still stays in the platform folder.
  • oyzu run <target>:test puts reports under the host platform.

Retained invocation lookup​

oyzu history
oyzu history <invocation-id>
oyzu history <run-id> --json
oyzu inspect <bundle-directory> --json

oyzu history reads the current bundle and earlier ones kept under .oyzu/history/. It doesn't load project configuration, so old builds stay readable even if your configuration is broken or the bundle moved. It doesn't install, use the network, run anything or hash artifacts.

  • Look up a build by the invocation ID or run ID from its summary. Old bundles without an invocation ID can be found by run ID.
  • An invalid ID fails with INVOCATION_ID_INVALID; an unknown one with INVOCATION_NOT_FOUND.

What a listing and a summary contain​

A listing shows up to 20 builds, newest first, with counts of what was left out and up to 8 notices about incomplete bundles.

A summary of one build shows:

  • action counts, test totals (fresh, reused, unknown origin), warnings, and up to 8 failed or unusual actions and 8 diagnostics, with short excerpts;
  • up to 8 recorded action decisions (why each ran or was reused), the selection, and cache status;
  • unavailable cache tiers (cacheLimitations) and selection fallbacks (selectionFallback);
  • paths to the full records.

Lists are capped at 8 entries, with a *Omitted count beside each. The full manifest has everything. oyzu build --explain shows the same summary.

What it leaves out​

  • Native log bodies and environments aren't included. Open the returned paths for the full records.
  • A summary isn't artifact verification. Use oyzu inspect for that.
  • Later source or configuration changes, or oyzu cache clear, don't rewrite a past build's recorded decisions.
  • Older records without file-comparison detail say it's unavailable.

Checks summary​

checks shows which checks each target ran, from the build's recorded oyzu.dev/build-checks facts.

  • Up to 8 targets are listed; totals count all of them.
  • Each target's tests is selected, not-requested or unknown. Missing or malformed records stay unknown; current configuration never fills the gap.
  • checks.status is recorded when every target has a record, partial for a mix, and unknown when none do. unknownTargets gives the count.

Test totals​

  • Totals are split into fresh, reused and unknown origin. Each also counts zeroTestReports: reports that say they ran 0 tests.
  • If passed, failed or skipped is missing, that total is null (shown as unavailable).
  • Zero tests, skipped tests, missing required reports and missing records are always reported separately.

Policy overrides and release lowerings​

When a policy constraint changed a target's setting, the plan and manifest record extensions["oyzu.dev/policy-overrides"], one entry per override:

  • setting and the effective value;
  • constraint: source, kind (lock, minimum, maximum or required), bound, selector, and label (org policy, admin policy or project constraint);
  • replaced: the value, source and scope it replaced;
  • a human note.

See policy constraints and selectors and project constraints.

In a release build, when a nearer folder lowered a check below a farther [context.release] value, the target records extensions["oyzu.dev/release-lowerings"]: the setting, the value used and its source (such as app/oyzu.toml:2), and the releaseValue and its releaseSource (such as oyzu.toml:5). See per-context values.

Retention and privacy​

  • History is local. Nothing is uploaded or shared.
  • Nothing expires automatically and there's no delete command. Remove old bundles yourself when you no longer need them.
  • A command that stops before the bundle is created leaves no history entry.
  • Crashes, write failures and full disks can leave partial or missing records.
  • Remote runs don't appear in history. Use the platform's run link.

Integrity​

oyzu inspect checks a bundle against its own records. It confirms the files match what was recorded; it doesn't prove who produced them. To check a downloaded artifact against signed GitHub provenance, see release provenance verification.

  • Plan and manifest agree. Target records and artifact identities must match the plan. Relabeling a variant in the manifest alone fails.
  • Generated versions. A target whose version was set by declared hooks must match its recorded post-hook plan; only the declared version fields may differ.
  • Successful bundles are complete. Every planned artifact, required action and required report must be there. Reports are re-parsed and checked against the plan's rules (including coverage), rather than trusting stored summaries.
  • OCI images. The image's OS and architecture must match the target. See Docker target selection.
  • Plugins. See plugin provenance.
  • Reports for runtime variants are tied to their own target records; see runtime matrices.

Workspace ownership​

  • A build holds an OS file lock on .oyzu/build.lock until it finishes. A second build in the same workspace fails before running anything. The lock file existing on disk doesn't mean a build is running; the lock is released when the process exits.
  • Staging happens in .oyzu/bundle-* on the same filesystem as the destination.
  • An isolated build only replaces an existing destination that contains an Oyzu manifest. Any other existing folder, even an empty one, is refused. Oyzu never deletes files it doesn't own. Use .oyzu/bundle if your project writes its own dist/.
  • With .oyzu/bundle, native builds and direct tests also require Oyzu ownership. Your native dist/ stays where it is and isn't copied into the bundle.
  • Symlinks (including broken ones) and Windows reparse points are refused for the lock, state, bundle and history paths.
  • Just before replacing the bundle, Oyzu checks that the destination hasn't changed since the build started. A new destination, changed manifest or existing history slot stops it rather than overwrite anything.

Finalization and recovery​

When a build finishes, the previous bundle moves to .oyzu/history/<new-run-id> and the staged one becomes current. Nothing is appended to the old manifest. This step is local and never uses the network.

  • If the second step fails, Oyzu tries to put the previous bundle back. If that fails too, the error names the history folder holding it.
  • oyzu build --plan is a read-only preview and never replaces the bundle.

After a failed native build​

  • The previous bundle's artifacts move to history even when the new build fails. They aren't copied back into dist/, which would block a later retry.
  • Unrelated native files are kept. .oyzu/bin stays at the last successful build.
  • If an older bundle recorded old binaries as unclaimed output, move that bundle aside before rebuilding. A matching file name alone doesn't allow replacing them.

After a finalization error​

The new staging folder is kept and its path is in the error. If its records are complete, inspect it directly:

oyzu inspect .oyzu/bundle-EXAMPLE
  • Use the path from the error message.
  • Keep the conflicting destination and fix the filesystem problem before rebuilding.
  • A kept staging folder is never treated as a successful build or reused.
  • Abandoned staging folders are cleaned up normally.

Plugin provenance​

When a build uses an external builder (see plugin packages), the plan, execution record and manifest each carry extensions["oyzu.dev/plugins"]: one entry per plugin with its source (package or local-development), identity and executableDigest.

oyzu inspect fails with plugin records differ from plan or ... from envelope if the manifest's or execution record's copy is missing or edited.

Slice builds and bundle handoff​

Note: Slice handoff is experimental and is mainly used by platform pools.

oyzu build --slice --handoff oci://host/path builds only the named targets and, on success, uploads the complete bundle (plan, execution record, logs, artifacts and reports) to the OCI repository before writing it locally. Ordinary builds never need a registry.

PartValue
Repository and tag<handoff>/v1alpha1/<first two manifest-digest hex>:bundle-<64 hex>
Artifact typeapplication/vnd.oyzu.build-bundle.v1alpha1
ConfigThe manifest.json bytes, application/vnd.oyzu.build-manifest.v1alpha1+json. Its SHA-256 is the tag.
LayerOne application/vnd.oyzu.build-bundle.v1alpha1.tar+zstd archive with the other bundle files
Annotationsdev.oyzu.build.manifest (config digest), dev.oyzu.bundle.uncompressed-digest (raw tar digest)
  • The archive is reproducible: sorted paths, zero owner and timestamps, files 0644 or 0755, folders 0755. Links are refused.
  • The config plus layer, and the unpacked tar, are each limited to 256 MiB.
  • Your normal registry credentials and proxy settings are used. Uploading the same bundle again is harmless; a different bundle at the same tag fails.
  • The plan records each target's oyzu.dev/execution (needsDaemon, executionPlatform) and oyzu.dev/slice (transferable, repeatable, reason, detail) facts. transferable doesn't mean a cache hit.

If the upload still fails after retries, the build ends with HANDOFF_PUSH_FAILED and exit status 5. The actions' real outcomes are kept, along with the exact upload bytes, so the upload can be retried without rebuilding.

Limits​

  • Replacing the bundle is two renames, not a crash-safe transaction. If the process or machine stops in between, there's no automatic recovery; the error or history folder tells you where the previous bundle is.
  • The path checks and lock protect against other Oyzu commands, not against a hostile process that can replace folders.
  • Bundles aren't stored remotely, and there are no automatic retention limits.

Direct test bundles​

Direct Node, Python and Go tests use the same process.

  • With the default dist destination, a test run can copy your existing native dist/ output into the new test bundle and keep the original in history. Those copies are listed separately and aren't build artifacts. With .oyzu/bundle, your native dist/ is left alone.
  • Earlier reports in the current bundle move to history.
