Tasks in captured builds

CLI reference

Published from the canonical docs/reference/build-tasks.md file. Features marked experimental remain experimental; check support limitations before relying on them.

For the in-development single inferred or declared Rust target, plain oyzu build now selects the native local path. Use oyzu build --isolated for the captured behavior described on this page. Other target shapes retain their current captured selection. Native self-bootstrap acceptance remains pending.

oyzu build composes the selected builders' stages with discovered tasks, explicit replacements, prerequisites and hooks. It captures source and dependencies before executing the resulting graph in private target workspaces. Provision the CLI's native toolchain images and supported Docker executor first; see image provisioning and acceptance checks. This reference describes the current experimental executor, not native Windows/macOS target compilation.

Builds now show live progress and multiplexed command output by default. Add --json when consuming the final manifest/plan programmatically.

Local fast builds and CI checks​

A plain local oyzu build is a fast build: it runs the build and package stages and skips test, lint and format-check. --full runs every quality stage locally. A detected CI context, the ci profile and --remote builds always run the full stages. Explicit check requirements and report validation remain enforced for every stage that runs.

For the supported single Rust target, plain oyzu build selects the current host and development compilation profile, including when build.yaml declares a platform matrix. --all-platforms requests the complete declared matrix through the existing captured executor; --isolated explicitly selects captured execution and, like a plain build, keeps only the host platform from a declared platform matrix unless --all-platforms is also given. A target that does not declare the host platform keeps its full matrix. The matrix backend currently requires Docker and provisioned worker images. Unsupported native relationships fail explicitly rather than ignoring them. Platform selection and isolation are distinct concepts; this implementation does not yet supply a host executor for every matrix variant.

Plan records continue to report the actual scheduled stages and context without asserting production eligibility. See native local builds for caches, outputs and qualification limits.

Select targets​

oyzu build
oyzu build api
oyzu build api web --plan

No target arguments means all discovered targets. Positional arguments are exact target IDs, not task names, globs or paths. Repeated IDs are deduplicated; unknown IDs fail before image resolution or dependency acquisition. Use oyzu discover to inspect target IDs and oyzu run list for task names.

Selection includes transitive depends_on and materialize.from producers, plus the owners of prerequisites and hooks reached from admitted builder stages. Each added target receives its complete applicable build/check/package sequence, not just the requested helper. Native preparation can reveal additional task contracts, so the engine expands selection until no new owner is needed; each target is prepared and planned once. An arbitrary custom task that is not reached from a build stage does not select its dependencies.

Unrelated targets have no resolved toolchain, dependency acquisition, actions or artifacts in this invocation. Image overrides for a manager present elsewhere in the discovered workspace are accepted but are only resolved if that manager is selected. Selected targets retain their configuration and required checks; concurrency uses the smallest ceiling from root configuration and selected targets. Selecting one target in a multi-target workspace does not turn an unqualified root task into that target's override.

Completed plans and their manifests record extensions["oyzu.dev/selection"]: sorted requested and selected IDs, mode (all, explicit or affected), and excluded targets with reason outside-selection. Excluded targets are not reported as successful. oyzu inspect dist rejects disagreement between the manifest's selection and its frozen plan. Older bundles with no selection extension in either record remain inspectable. A failure before planning can have no selection record.

Discovery, configuration validation and source capture still cover the workspace. Malformed metadata in an unrelated project can therefore prevent a selected build; selection is not lazy discovery or a security boundary. The source digest remains repository-wide, while the plan digest binds selection. --plan instead performs a read-only preview, without source capture, image resolution or dependency preparation; native-derived details remain unresolved. Normal builds retain prior bundles under .oyzu/history as before. Finite Node runtime matrices expand logical selections to concrete variants; affected builds optionally select changed targets and their consumers from a local Git baseline. Native member-level impact and action-cache reuse remain unfinished.

Discovery captures the bounded build.yaml contents and parsed target declarations once per invocation. Dependency selection, target ordering, platform constraints and materialization planning consume that same inventory. After source capture, the build checks that its inventory bytes match discovery before resolving toolchain images or preparing dependencies. Adding, removing or changing build.yaml during this interval fails with build.yaml changed between discovery and source capture; finish the edit and rerun. Byte identity includes comments and optional fields. Changes after capture do not modify the frozen inventory used by that invocation. This closes an inventory consistency gap; it does not imply that every native metadata race or full matrix expansion is implemented.

Defaults and customization​

Ordinary projects need no task configuration. Builders supply applicable build, test, lint and read-only format-check operations. oyzu run list shows discovered tasks without running them. Mutating format tasks are for explicit development use and are rejected if included in a captured build. Explicit replacements retain the builder's mandatory report and policy obligations.

A qualified prerequisite uses the existing TOML task syntax:

[tasks."api:pre_test"]
argv = ["node", "scripts/check-api-inputs.mjs"]
depends_on = ["schema:verify"]

[tasks."schema:verify"]
argv = ["node", "scripts/verify-schema.mjs"]

Here api and schema are targets discovered or declared in build.yaml; their scripts are relative to their respective target roots. The example requires Node-compatible toolchains for both tasks. A custom command does not implicitly provision a new tool. Use the native ecosystem's command where appropriate; no new build-file task language is introduced.

The schema:verify operation runs once per invocation even if several selected tasks require it. Its working directory, toolchain, resolved configuration, environment constraints and output/report paths belong to schema. Its dependencies and schema:pre_verify / schema:post_verify hooks run under the same ownership rules. api:pre_test waits for the prerequisite's post-hook and any deferred report validation before api:test can start. Hook names do not recursively acquire their own hooks.

Builder stage order remains in force. A stage already selected as an earlier task's prerequisite is not executed again. Newly selected local prerequisites follow the previous local stage and retain their local dependency-list execution order, including sibling prerequisites. This ordering remains enforced while an earlier stage waits on foreign work; a later helper cannot run early simply because the target's worker is idle. Another target's prerequisites follow their own pipeline. Cycles involving task prerequisites, hooks, builder stage order, target dependencies or materialized artifacts fail before action execution. Error diagnostics currently identify an action cycle without providing its shortest path. Fix the ordering relationship and rebuild; rearranging YAML entries does not resolve a cycle.

An explicit unqualified root task still takes precedence for a workspace containing one target. A root helper reached through a qualified prerequisite inherits that prerequisite's target/toolchain context while retaining its declared root-relative working directory. In multiple-target builds, a root task requested from more than one owner is rejected as ambiguous; qualify a shared task with its actual target. This prevents the first target visited from silently choosing its toolchain or private workspace. Task names and command bodies otherwise keep their existing configuration precedence.

Isolation, evidence and failure​

Shared captured source inventory​

Captured builds inventory and freeze the admitted source once. Independent branches and aggregate execution use that inventory to materialize private, mutable target workspaces, instead of capturing the whole tree again for each branch. An existing planned source projection selects only its admitted entries; without a projection, the target still receives the full capture. There is no new option and no inferred narrowing of arbitrary task inputs. Final assembly of already completed branches does not materialize their workspaces again.

Materialization hashes each selected file while copying it and compares its size, digest and executable bit with the capture. Files are independent copies, never writable hard links to another target or the frozen source. Changed or missing captured entries, symlinks/reparse points, or copy failures abort materialization; resolve the filesystem problem and rerun the build for a fresh capture. Disposable target copies do not repeat capture's second hash pass or per-file sync. This is not a zero-copy implementation: selected bytes are still copied and verified per target, the full-copy fallback remains, and dependency preparation is still target-specific. Native host workspaces use their existing separate contract. No performance gain has yet been measured for this change; see verification status.

Docker preparation deadlines​

Docker preparation commands have fixed deadlines independent of action timeouts:

OperationDeadline per command
Image/platform inspection, daemon probes, tagging, worker control and volume operations30 seconds
Image pulls/exports, worker file copies and container tool restoration30 minutes
Failed restoration or running-worker forced removal5 seconds

These limits have no configuration override. Expiry fails the operation with an external-command deadline error and attempts to kill the local client; waiting for child output pipes cannot extend the deadline. Normal failed pulls and image operations preserve Docker's stderr in their error. Optional probes retain their existing fallback behavior. The limits apply per invocation, not to the whole preparation phase, and do not grant network access or supply missing images. Offline reuse still requires the previously provisioned inputs.

Check daemon health, registry access and available disk space before retrying. Killing a Docker client does not prove daemon-side work stopped: failed tool restoration attempts a separate five-second removal, and cleanup is best effort. Inspect and remove leftover Oyzu containers after the daemon recovers. Build forced cancellation has a separate shared cleanup budget. These changes await runtime qualification on all three hosts.

Workspace ownership​

Task prerequisites are ordering relationships. They do not transfer generated files between private target workspaces. Use declared artifacts and materialize when a consumer needs producer bytes; see directory artifacts. A prerequisite cannot read another target's mutated execution tree just because its task completed.

Each action records its owner, tool identity, dependencies, environment and report obligations in dist/plan.json. The manifest records actual action results, retained reports and versioned artifacts. Bundle storage governs locking, replacement, history and recovery after finalization errors. Packaging waits for every selected task owned by that target, including custom tasks required by another target. A failed prerequisite, post-hook or required report blocks dependent actions and packaging; available evidence remains in the failure bundle. Independent targets may still finish successfully. oyzu inspect dist verifies recorded content integrity, not release eligibility.

build.jobs bounds both independent dependency preparation and ready actions, using the smallest configured ceiling among the invocation and selected targets. Its default follows available CPU parallelism. Preparation uses private per-target destinations and container identities, and returns results in target order for planning. Builders declare preparation memory reservations, and worker-memory admission bounds every parallel phase by what fits in three quarters of the container engine's memory (docker info MemTotal), including default 2 GiB workers: a 16 GiB engine runs at most six at once, whatever the CPU count. Dependency-acquisition workers (brokered fetches, image capture, Python and Rust preparation) reserve 4 GiB each and may run for 30 minutes, since 2 GiB and 10 minutes failed mid-size npm, Python, Cargo, Maven and Gradle projects (#167). Measured with parallel fetches on the #160 corpus, the largest worker (uptime-kuma, 1,304 locked npm packages) peaked at 2.4 GiB of cgroup memory, about 1.0 GiB of it resident and the rest page cache and /tmp, and the slowest preparation took 2.2 minutes, so both limits keep at least 1.6 times headroom; see the throughput record. Without an engine to ask (the native host path), build.jobs alone applies. Each long-running isolated action receives an even share of the container engine's CPUs among the actions that may run at once, capped at one CPU per 512 MiB of its memory reservation and never below two. A single 8 GiB cross build on a 24-CPU engine therefore gets 16 CPUs instead of a fixed two; the chosen share is printed in the execution context. Cargo sizes itself from that allowance, so Oyzu no longer sets CARGO_BUILD_JOBS.

Worker ceiling​

Set the ceiling for one invocation without editing configuration files. Remote and CI runners use this to fit a build inside a fixed memory allowance:

oyzu build --jobs 4          # or -j 4
OYZU_BUILD_JOBS=4 oyzu build

Precedence is --jobs, then OYZU_BUILD_JOBS, then build.jobs from configuration files and profiles, then the CPU-count default. Both invocation inputs replace every root and target build.jobs value, so the whole build shares one ceiling. Administrative constraints on build.jobs still apply on top, and worker-memory admission can still lower concurrency. --jobs accepts 1–65535; an OYZU_BUILD_JOBS value outside that range, or not an integer, fails before any work with CONFIG_INVALID_VALUE, and an empty value is ignored. The build prints the resulting Shared budget or Preparation worker count in its context, the plan records it in oyzu.dev/execution.jobs, and oyzu config explain build.jobs names OYZU_BUILD_JOBS as the origin when the variable set it. oyzu run has no --jobs flag because development tasks already run one at a time; the ceiling does not limit threads a native compiler starts inside one action.

Execution refills free slots as individual actions finish and their reports/artifacts are validated, without waiting for unrelated slower actions. The executor never runs two actions concurrently in one target's mutable workspace: the check stages of one target (test, lint, format-check) may overlap only when each runs confined in its own private view, and their changes reach the workspace in plan order (see checks that run at once). A failed check no longer blocks the next check; it still blocks packaging. When an action fails because its worker ran out of memory (exit 137, or ENOMEM, cannot allocate memory or a heap-limit message at the end of its output), the build adds the diagnostic worker-out-of-memory, which names the action, its memory reservation and how many actions could run at once, and points at build.jobs and the engine's memory setting. The diagnostic also records the reservation as memoryMiB and that concurrency as jobs. A dependency preparation worker that fails the same way (phase prepare) gets the same diagnostic, naming <target>:preflight and its 4 GiB reservation. Detection ignores case, so Go's cannot allocate memory counts. On Windows the message adds that Docker Desktop's file sharing can fail a large write into the build directory with the same error while the worker is well under its limit (#132), and that building from a checkout inside WSL avoids it. Oyzu does not retry it. On Windows, an action whose output ends with an I/O error (input/output error, or (I/O error) as hadolint prints it) gets the diagnostic worker-file-sharing-error: in #132 Docker Desktop's file sharing failed reads of Dockerfiles that were fine on disk. It names the action and suggests building from a checkout inside WSL. Other platforms do not get it, because there an I/O error usually means a disk fault. Failed prerequisites block dependent actions. Independent targets can now prepare, freeze their branch plan, execute and package while other targets are preparing. Preparation and execution share the configured job ceiling and 75% of worker memory; a ready branch can wait when its reservation would exceed that budget. Each branch plan is saved before execution in plans/, retained as bundle evidence and checked against the final aggregate plan by oyzu inspect. Cross-target dependencies, materialization, container composition and shared root tasks retain aggregate planning after preparation. Equivalent locked Rust compiler verification and archive extraction are shared within the build. Native target metadata and dependency preparation remain separate. Native compilers may also have their own thread limits. Execution uses captured offline inputs; task dependencies do not grant network, credential or host access. Development oyzu run uses the host environment. Integrated oyzu run test profiles produce test-only bundles that disclose host execution; they do not claim captured-build isolation.

Verification and limits​

Rust checks cover requested-target validation, transitive selection, root-task semantics, selection integrity, cross-target ownership, required report paths, post-hook collection boundaries, local sibling order and cycles visible only after combining build stages. The core captured-build suite exercises a shared custom prerequisite with two consumers, private workspace effects, successful snapshot packages and failure propagation from the producer post-hook. It also exercises explicit selection with an unprovisioned unrelated toolchain, deduplicated requests, exclusions and selected materialization producers. It tests local prerequisites while compilation waits on a foreign task, and a Node consumer requesting a Go-owned task through the materialization scenario. Its checks execute the compiled CLI with real native tools; suite registration alone is not acceptance. See implementation status for revision-specific local and CI evidence.

This adds qualified task composition to the existing builders. It does not complete generated-output inference, task caching, matrix expansion, interactive services or tool installation. Use the authored scenarios and their acceptance criteria to track those remaining capabilities.

Live development task output​

Host shells and pinned tools​

Host tasks receive the selected project's pinned tool directories on PATH, plus tool environment values such as GOROOT and JAVA_HOME. For example, argv = ["bash", "scripts/test-database.sh"] can invoke the pinned go by name. The tools must already be installed for the matching lock; oyzu run does not install them. Use oyzu install first (or install --frozen --offline with the required cached tools).

Bare bash and sh use the shared host-shell lookup. On Windows, Oyzu skips System32 and WindowsApps WSL launchers, looks for a native shell on PATH, then derives Git for Windows' shell from git.exe on PATH, then checks standard Git install locations. A missing native shell fails with the search locations and an explicit-path remedy; it never silently enters WSL. Git Bash/MSYS converts the ordinary Windows PATH at startup, so pinned Windows tools remain available to the script without an Oyzu PATH conversion layer. Linux/macOS keep normal PATH lookup.

Shell-string tasks with shell = "bash" or shell = "sh" use the same lookup. The default shell remains PowerShell on Windows and sh on Linux/macOS. Explicit shell executable paths remain caller-selected. This is host development execution; isolated builds use their executor's shell and tool environment.

Streams and progress​

oyzu run <task> reports configuration/discovery, selected task, pinned tool environment verification, and native execution as work begins. Preparation that has no native output emits a ten-second activity update; execution reports a heartbeat while its child is running. Required tool verification still completes before task launch and is not bypassed to shorten startup.

Local tasks inherit stdin, including redirected pipes, in both text and JSON modes. Text-mode tasks without a bundle inherit stdout/stderr directly. Tasks recording a bundle (integrated oyzu run test, including its prerequisites and hooks) instead tee stdout/stderr to the caller's streams and retain the full output in the bundle's numbered dist/logs/*.stdout and *.stderr files. Output is forwarded without waiting for a newline and is not replayed on completion. -q suppresses routine Oyzu progress while preserving child output and logs.

For a bundled task that needs real stdout/stderr terminal descriptors, set interactive = true: text mode then inherits those streams directly. Oyzu does not allocate a pseudo-terminal, so this interactive output cannot also be captured; that task's bundle stdout/stderr logs are empty. Ordinary tee capture preserves terminal stdin and live output, but the child's stdout/stderr are pipes, which can change native buffering, color and terminal detection. Required report files are collected in either mode. Use JSON capture when retained output matters more than terminal-dependent interaction.

JSON mode keeps stdout as one final result with captured task output and streams structured diagnostics on stderr. Its child stdout/stderr are not terminals, so prompts on those streams are only visible after completion; use text mode for interactive prompting. Tasks with an empty-stdout validation contract also retain captured output so the check remains enforceable. Captured builds and internal probes continue to receive null stdin. PowerShell shell tasks need interactive = true to omit -NonInteractive; an explicit argv is passed as authored. Inherited native streams retain the child's own color and control-byte behavior, including its handling of NO_COLOR.

For example, with a discoverable project and a provisioned POSIX shell, a task argv = ["sh", "-c", "read x; printf 'got:%s\\n' \"$x\""] can consume printf 'hello\n' | oyzu run ask -q and print got:hello. On Windows, use a provisioned native command or PowerShell task appropriate to that shell. An EOF or native input error remains the child's result; Oyzu does not synthesize input or restart the task. This stream change does not add remote terminal forwarding or service supervision.

Host process completion wakes the coordinator through a waiter immediately; there is no mandatory 50 ms completion delay. The 50 ms maintenance wakeup remains for captured log following and cooperative cancellation, and heartbeats remain ten seconds. Wait/launch failures remain execution errors and trigger best-effort termination where a child exists. No task speedup numbers are available yet. Regressions cover piped input, live tee output, successful and failed bundle logs, the interactive capture exception and Unix terminal descriptors. See verification status and Windows lifecycle qualification for the platforms and stream scenarios actually checked. Native tools can still buffer their own output; Oyzu's heartbeat is not a claim that a silent tool is making measurable progress. Exit codes and task arguments remain unchanged by presentation.

Windows task process lifetime​

Each local oyzu run <task> command, prerequisite and hook on Windows runs in a private, noninheritable kill-on-close job. The native task starts suspended, enters its job, then resumes its verified primary thread. Descendants inherit the job; breakaway is not enabled. Hard-killing the Oyzu controller closes its job handles and stops its task trees, releasing descendant-held ports. Ordinary task completion also terminates remaining descendants before joining output pipes. Tasks must not leave background services running after their command returns; run a service in the foreground for the intended lifetime.

This applies to terminal, tee and JSON-captured local tasks. Native stdin, argument/batch handling, exit codes, console membership and Ctrl-C broadcast remain unchanged. The controller is not assigned to its own task job, and existing enclosing jobs remain in force. The job provides process lifetime containment, not filesystem/network isolation or permission to execute. Containment uses local OS APIs and needs no account or network access. Captured build processes, metadata probes and remote tasks retain their separate execution contracts; this repair does not change Unix behavior.

Job creation/assignment and primary-thread lookup/resume failures abort launch and kill/reap the owned suspended child. Missing or multiple primary threads fail explicitly; there is no uncontained fallback. TASK_JOB_* and TASK_PRIMARY_THREAD_* diagnostics retain the launch failure details. An incompatible enclosing job or denied OS handle access must be corrected before retrying. Normal cleanup confirms job-wide exit within ten seconds; a failure is reported as TASK_JOB_CLEANUP_FAILED rather than successful completion. An externally killed controller cannot report cleanup evidence itself.

The disposable compiled-CLI proof covers hard kill, normal exit and Ctrl-C in text and JSON modes, checking task/child/grandchild exits and loopback port release. See Windows lifecycle qualification for platform, commands and remaining verification limits.

Host scheduling​

Native builds use the shared logical task planner and bounded dependency scheduler. Independent targets may overlap up to build.jobs; declarations such as depends_on: [api] under builds.web delay web until API's selected stages finish successfully. Failed dependencies block consumers, not unrelated targets. Same-target stages and hooks remain ordered because they share native files. --plan exposes the logical edges without installation or execution; native preparation subsequently resolves exact commands and report contracts into the executable evidence plan. Artifact transfer through materialize is also supported in private host target workspaces, after producer actions and report obligations succeed. Ordering alone still transfers no files.
