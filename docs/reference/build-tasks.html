Build tasks, stages and hooks

CLI reference

Published from the canonical docs/reference/build-tasks.md file. Features marked experimental remain experimental; check support limitations before relying on them.

oyzu build runs each selected builder's stages (format, lint, test, build, package), together with your own tasks, prerequisites and hooks, and collects the results into a bundle. Use this page to choose which targets and checks run, to add or replace tasks in oyzu.toml, and to understand how oyzu run tasks behave.

Builds show live progress and command output. Add --json to get the final manifest and plan as JSON.

Quick start​

oyzu build                   # fast local build
oyzu build --full            # run every check that isn't off
oyzu build api web --plan    # preview two targets
oyzu build --jobs 4          # limit concurrency for this run
oyzu run list                # list discovered tasks
oyzu run test                # run a development task
oyzu run --isolated test     # run just this task in its builder's isolated image

Choose which checks run, per context, in oyzu.toml:

[checks]
format = "off"        # never run; rustfmt isn't prepared for it
lint   = "advisory"   # failures are warnings; the build still succeeds

[context.release.checks]
tests = "required"

Local fast builds and CI checks​

A plain local oyzu build is a fast build. It runs the build and package stages and only the checks set to required. Other test, lint and format-check stages are skipped (skip · fast local build in Plan).

Every check that isn't off runs in the pr, ci and release build contexts, and with --full, the ci profile or --remote. You change these defaults per context with checks.run, and set each check's level in oyzu.toml (check levels):

LevelBehavior
offNever runs. Plan shows off and where it was turned off. The builder doesn't prepare the check's tools.
advisoryRuns where checks run. A failure is a CHECK_ADVISORY warning.
enforce, requiredSee check levels. Required checks and report validation always apply to stages that run.

Test and coverage requirements apply to each target as a whole. The compile step doesn't need to produce coverage when the test step does. A positive checks.coverageMinimum needs a selected step that produces coverage and a valid report that meets the minimum. Missing coverage, a disabled test with no other coverage source, or a replacement task that omits required reports fails the build. oyzu run tasks have their own report rules; see direct test reports.

On the native Rust path, --full can reuse an unchanged build while format, lint and test run at the same time, within --jobs. A failed required check still fails the build. See native cache behavior.

A native build command may run tests itself. For example, Maven runs tests in verify. Skipping the separate test stage doesn't turn those off.

Optimized and development builds​

A local build that only writes its own dist/ uses each builder's development profile. A build is optimized when its artifacts leave the machine: handed off (--slice), written to a shared remote cache, packaged by another selected target, or published (the release context). A development plugin binding's results are handed off but never written to a remote cache (action cache), so a remote cache alone does not optimize them; a plugin package's results are written like a built-in builder's.

  • --optimized and --no-optimized choose for one run. build.optimized in a folder's oyzu.toml (optionally per context) chooses for the targets under it. Policy wins over both.
  • Optimized Rust runs cargo build --release; optimized .NET uses --configuration Release. Builders where it makes no difference stay development.
  • Plan shows each target's profile and why (profile cli · optimized · --optimized), and Outputs labels each artifact.
  • Optimized and development results never reuse each other from the action cache. For Rust and .NET, a CI build that writes the remote cache (optimized) doesn't serve a local development build; build with --optimized to reuse it. See optimized builds.

Platform selection is covered in platforms and executors.

Select targets​

oyzu build
oyzu build api
oyzu build api web --plan

With no arguments, every discovered target builds, except a build that sets default: false in build.yaml. Use that for builds you only want on request, such as release-only packaging: oyzu build <name> builds it, and a selected build that lists it in depends_on or materialize still pulls it in. Arguments are exact target IDs, not task names, globs or paths. Duplicates are ignored. An unknown ID fails before anything is prepared. Use oyzu discover to see target IDs and oyzu run list to see task names. Only the plugins of the selected builds and the builds they need are installed and run; see only the plugins your selected builds need.

What gets selected​

  • The targets you name, plus their depends_on and materialize.from producers, transitively.
  • The owners of prerequisites and hooks reached from those targets' stages.
  • Each added target runs its full set of build, check and package stages, not just the task that was needed.
  • A custom task that no build stage reaches doesn't select its dependencies.
  • Unselected targets get no tools, downloads, actions or artifacts.
  • Concurrency uses the smallest build.jobs among the root configuration and the selected targets.

Selection doesn't change which build a task belongs to: an unqualified root hook belongs to every build it reaches, selected or not.

Discovery, configuration checks and source capture still cover the whole workspace. Broken metadata in an unrelated project can stop a build of another target.

Selection records​

  • The plan and manifest record oyzu.dev/selection: requested and selected IDs, the mode (all, explicit or affected), and excluded targets with reason outside-selection. Excluded targets aren't reported as successful.
  • oyzu inspect dist fails if the manifest's selection doesn't match its plan.
  • Runtime toolsets and affected builds also change the selection.

One consistent build.yaml per invocation​

Oyzu reads build.yaml once per run and uses that copy for selection, ordering, platforms and artifact passing. If the file changes between discovery and source capture, the build fails with build.yaml changed between discovery and source capture. Finish the edit and run again. Changes after capture don't affect the running build.

Defaults and customization​

Most projects need no task configuration. Builders supply build, test, lint and read-only format-check tasks. oyzu run list shows them.

  • A format task that rewrites files is for running by hand. It is refused inside a container build.
  • You can replace a builder stage with your own command. The replacement runs instead of the original. It keeps the stage's hooks, required reports and policy, so it must write the required reports to their assigned paths. Oyzu adds native reporting only to commands it recognizes.

Prerequisites​

A prerequisite uses the normal TOML task syntax:

[tasks."api:pre_test"]
argv = ["node", "scripts/check-api-inputs.mjs"]
depends_on = ["schema:verify"]

[tasks."schema:verify"]
argv = ["node", "scripts/verify-schema.mjs"]

Here api and schema are targets. Each script path is relative to its target's folder. Both tasks need Node available; a custom command doesn't install new tools.

  • schema:verify runs once per build, even if several tasks need it.
  • It runs with schema's folder, tools, configuration, environment and report paths.
  • Its own dependencies and schema:pre_verify / schema:post_verify hooks follow the same rules.
  • api:pre_test waits for the prerequisite and its post-hook before api:test starts. Hooks don't get hooks of their own.

Ordering​

  • Builder stage order always applies. A stage that already ran as an earlier prerequisite doesn't run again.
  • A target's own prerequisites run in the order listed, after the previous stage. Another target's prerequisites follow that target's order.
  • A cycle between prerequisites, hooks, stages, target dependencies or artifact passing fails before anything runs. Fix the relationship; reordering YAML entries doesn't help.
  • A root workspace task (neither a hook nor a stage) reached through a prerequisite uses that prerequisite's target and tools, but keeps its own working folder.
  • In a build with several targets, a root workspace task needed by more than one target is refused as ambiguous. Qualify it with the target that should run it.

Which build a task belongs to​

A task key in any oyzu.toml belongs to builds by these rules. They are checked when configuration is read, before anything runs.

KeyBelongs toErrors
[tasks."api:pre_test"] (qualified)Build api only. Wins over an unqualified definition of the same name for api.Unknown build (CONFIG_REFERENCE_UNKNOWN); file outside api's folder chain (CONFIG_REFERENCE_MISPLACED); a hook of a task api doesn't have (CONFIG_REFERENCE_UNKNOWN, with the nearest name).
[tasks.post_build] (unqualified hook, pre_* or post_*)Every build whose folder chain reads the file and that has the hooked task (package always counts). A root hook reaches every build, including the root's own. At the root it is also the hook of a workspace task with that name.A hook of a task none of those builds has (CONFIG_REFERENCE_UNKNOWN).
[tasks.test] at the root (any name that isn't a hook)A workspace task (oyzu run test), run once at the root. It never replaces a build's stage, even where builds run a stage with that name.—
[tasks.test] in a subfolder (unqualified builder stage)Replaces that stage in every build below the folder that runs it.Reaching builds with different builders: CONFIG_TASK_AMBIGUOUS. Qualify it per build.
[tasks.lint-docs] in a subfolder (any other name)A task of every build below it.—

To replace a stage of a build at the project root, qualify the key with the build's name, such as [tasks."app:test"]; oyzu run list shows the name. Because a root name is always the workspace's own task, oyzu run <name> for a task the root defines only selects the plugins of the builds that task depends on, often none. See only the plugins your selected builds need.

  • A nearer folder's definition, or a qualified key, replaces a farther one for that build.
  • Hooks can be narrowed further with when/unless. Stage replacements take no conditions.
  • A task runs in its build's folder unless cwd says otherwise, relative to the file that declares it.
  • Every depends_on entry must name an existing task, by id (schema:verify) or name (verify).
# root oyzu.toml, with builds cli (rust/app), docs (node/app) and the root's own
[tasks.post_build]            # every build, the root's included
argv = ["scripts/attest.sh", "{artifact.path}"]

[tasks."docs:test"]           # one build's stage: docs only
argv = ["npm", "run", "test:ci"]

[tasks.lint-docs]             # a workspace task: oyzu run lint-docs
argv = ["node", "tooling/check-docs.mjs"]

Writing that docs:test replacement as [tasks.test] would also reach cli, a Rust build, and is refused:

CONFIG_TASK_AMBIGUOUS: oyzu.toml:5:1: [tasks.test] replaces the test stage of builds with different builders: cli (rust/app), docs (node/app); one command cannot replace stages of different builders. Qualify it for each build instead, such as [tasks."cli:test"]

In a single-build project, [tasks.test] works as before. Its task id is the build's own (project:test), and oyzu run test still finds it.

oyzu config validate checks task keys' build names and placement. Hook targets and depends_on need the discovered tasks, so oyzu build (including --plan), oyzu run and other commands that discover the project check them. See names that cross files.

Task and hook conditions​

A task or hook in oyzu.toml can say when it applies (when, unless) and receive build values through {namespace.name} placeholders. Both are plain data from a fixed vocabulary. Anything that needs logic belongs in the program argv runs.

For example, a post_build hook that runs the built binary:

[tasks."cli:post_build"]
argv   = ["{artifact.path}", "--version"]
when   = { optimized = true, platform = ["linux/x86_64"] }
unless = { artifact = ["bin-oyzu-shim"] }

Conditions​

when and unless are tables over these facts. They use the same form as policy constraint selectors.

FactValuesNotes
contextlocal, pr, ci, releaseThe context the build runs as (--context, OYZU_CONTEXT or detection).
providerCI provider names (github-actions, gitlab, …)
forktrue, falsefalse outside a pull request. Read from GitHub Actions and GitLab; using fork where the provider doesn't report it is an error.
targetTarget namesMatches the target's id and, for a platform variant (cli-platform-linux-x86_64), its declared target (cli). An unknown name is an error that lists valid names.
platformos/arch[/abi], with the usual aliasesA value without an ABI matches every ABI.
optimizedtrue, falseThe target's build profile.
artifactLogical artifact names (bin-oyzu, as Outputs and the manifest show them, not file names)Only on post_build and post_package hooks. An unknown name is an error, except for a target with several platforms, where it may be built elsewhere.
  • Every when key must match; a list matches when any value does. One matching unless key excludes the task. A task with neither always applies.
  • Unknown keys, wrong value types, artifact on other tasks, and conditions on a stage replacement fail with CONFIG_INVALID_VALUE when configuration is read. Put conditions on the stage's pre_ or post_ hook instead.
  • A task under [context.release.tasks."cli:post_build"] already applies only in release; it needs no condition.

Note: Conditions aren't a security control. A job with only the generic CI variable can lower its context with --context local. Use check levels and policy for checks that must run.

Conditions are decided when the build is planned. A task that doesn't apply isn't scheduled, and anything that waited on it keeps its order. Plan shows one task note per conditional task:

  task     pre_build · skip · unless context = local
           post_build · run for bin-oyzu · unless artifact = bin-oyzu-shim

The plan and manifest record each conditional task under oyzu.dev/task-conditions: the conditions as written, run or skip and why, and for each run its action id, artifact and resolved argv. oyzu build --plan shows the same notes and taskConditions records; a per-artifact hook shows once per matching artifact there.

Placeholders​

A placeholder is {namespace.name}. It is replaced with plain text inside one argv element at a time, and in the task's own env values. Nothing goes through a shell.

PlaceholderValue
{build.context}, {build.provider}, {build.optimized}, {build.version}The context, comma-separated providers, true/false, and the version this build gives the target. In oyzu run, the version the project declares. Not available in container builds for builders that set versions after hooks, such as Node.
{build.root}The build root, relative to the task's working folder.
{target.name}, {target.dir}, {target.builder}The task's target. dir is relative to the working folder.
{platform.platform}, {platform.os}, {platform.arch}, {platform.abi}The target's platform (abi only when it has one).
{artifact.path}, {artifact.name}, {artifact.kind}, {artifact.platform}, {artifact.os}, {artifact.arch}In a post_build/post_package hook, the artifact it runs for. path is the packaged file, relative to the working folder.
{env.NAME}A literal value from [env] in oyzu.toml. In argv, only when it doesn't look sensitive.
{build.<target>.artifact.<field>}Another target's artifact, only along a declared depends_on or materialize edge. A producer with several artifacts needs materialize.artifact.

What counts as a placeholder:

  • Only {word.word…}. Everything else is left as written: {.Dir}, {a,b}, a lone brace. Go and Docker templates such as {{.Id}} or {{json .}} pass through unchanged.
  • To write a literal placeholder, double the braces: {{env.HOME}} gives {env.HOME}. This applies only to the namespaces build, target, platform, artifact, env and tool.
  • Doubled braces in other namespaces are ordinary text, so Jinja, Ansible and GitHub expressions ({{item.name}}, ${{github.sha}}) pass through. A single-brace {item.name} is still PLACEHOLDER_UNKNOWN.
  • There are no functions, defaults or filters, and a substituted value is never expanded again.

A run script can't use placeholders, because it goes through a shell. Use argv.

Per-artifact hooks. A hook that uses the artifact fact or an {artifact.*} placeholder runs once per matching artifact, as actions such as cli:post_build[bin-oyzu], one after another.

  • post_build runs for the artifacts the build produced; post_package for every artifact packaged into dist/.
  • A target with no package stage (such as a native Rust build) still runs a declared post_package hook, after all its other actions.
  • Before each run, the artifact is copied to .oyzu/artifacts/<target>/<platform>/<file> in the target's private workspace; {artifact.path} points there.
  • A hook with no matching artifact is skipped, with the reason.
  • Every run executes even if an earlier one failed; then any failure fails the build.
  • Oyzu never runs an artifact unless you declare a hook that does.
  • A per-artifact hook can't declare outputs (CONFIG_INVALID_VALUE).

Sensitive values. argv is recorded as written in the plan, manifest and command log, while task env values are recorded as [REDACTED]. So an {env.NAME} whose name or value looks sensitive (names containing TOKEN, SECRET, PASSWORD, API_KEY, CREDENTIAL, AUTH and similar, or a value that looks like a credential) is refused in argv with PLACEHOLDER_SENSITIVE. Pass it through the task's env instead (TOKEN = "{env.API_TOKEN}"), or use the tool's own credential mechanism.

Path values are relative to the task's working folder, in the platform's path form, and never expose your checkout path. That way the same build resolves the same argv on every machine, and cache keys match.

Placeholder errors. Placeholders are resolved when the build is planned. Errors name the task and argv element:

CodeCause
PLACEHOLDER_UNKNOWNUnknown name. Lists valid names and the nearest one.
PLACEHOLDER_UNDECLAREDAn {env.NAME} not declared in [env] or the environment.
PLACEHOLDER_UNAVAILABLEAn [env] entry that is a secret reference, path list or table; or a value that doesn't exist where it's used, such as {artifact.path} outside a post_build/post_package hook.
PLACEHOLDER_UNREACHABLEAnother target's artifact without a declared edge.
PLACEHOLDER_SENSITIVEA sensitive-looking {env.NAME} in argv.

Where conditions apply​

CommandConditionsPlaceholders
oyzu build (native)Evaluated per targetAll, including per-artifact hooks
oyzu build --isolatedEvaluated per targetAll but artifacts: a hook that reads artifacts fails with PLACEHOLDER_UNAVAILABLE
oyzu build --planEvaluated; per-artifact hooks pendingRendered for decided tasks. {build.version} shows (resolved during the build)
oyzu runEvaluated with the host platform and development profileA hook that reads artifacts is skipped (TASK_SKIPPED). A requested task that doesn't apply fails with TASK_NOT_APPLICABLE

Limits:

  • {build.dist}, {artifact.digest} and {tool.NAME.*} aren't available (PLACEHOLDER_UNAVAILABLE).
  • Placeholders in cwd are refused.
  • Artifacts built by an image worker aren't staged for hooks.
  • Per-artifact runs of one hook run one after another.
  • when/unless on [context.*] setting tables isn't supported.

Worker ceiling​

Limit how many workers run at once for one build, without editing configuration. Remote and CI runners use this to fit a build into a fixed amount of memory:

oyzu build --jobs 4          # or -j 4
OYZU_BUILD_JOBS=4 oyzu build
Source (highest first)Notes
--jobs / -jAccepts 1–65535.
OYZU_BUILD_JOBSA value outside 1–65535, or not an integer, fails with CONFIG_INVALID_VALUE. An empty value is ignored.
build.jobsFrom configuration files and profiles.
CPU countThe default.
  • --jobs and OYZU_BUILD_JOBS replace every build.jobs value, so the whole build shares one limit. Policy constraints on build.jobs still apply, and available memory can lower it further.
  • The build prints the worker count, the plan records it in oyzu.dev/execution.jobs, and oyzu config explain build.jobs shows where it came from.
  • oyzu run has no --jobs, because tasks run one at a time. The limit doesn't affect threads a compiler starts inside one action.

Concurrency and memory​

build.jobs limits both dependency preparation and build actions.

  • In container builds, each worker reserves memory, and Oyzu runs only as many as fit in three quarters of the container engine's memory (docker info MemTotal). With default 2 GiB workers, a 16 GiB engine runs at most six at once.
  • Dependency download workers reserve 4 GiB each and may run for up to 30 minutes.
  • Native host builds have no engine to ask, so build.jobs alone applies.
  • Each long-running container action gets an even share of the engine's CPUs, at most one CPU per 512 MiB of its memory reservation and never fewer than two. The chosen share is printed. Cargo sizes itself from it.

How execution schedules actions​

  • Free slots are refilled as soon as an action finishes and its reports and artifacts check out.
  • Two actions never write to the same target's workspace at once. A target's check stages (test, lint, format-check) can overlap only when each runs in its own private view (see checks that run at once). A failed check doesn't block the next check, but it blocks packaging.
  • A failed prerequisite blocks the actions that depend on it.
  • Independent targets can prepare, run and package while others are still preparing.
  • Each target's plan is saved in plans/ in the bundle, and oyzu inspect checks it against the final plan.
  • Container execution uses the inputs captured during preparation. Task dependencies don't grant network, credential or host access. oyzu run uses your host environment.

Out-of-memory and file-sharing diagnostics​

DiagnosticWhenWhat it tells you

On Windows, the out-of-memory message also notes that Docker Desktop file sharing can fail large writes with the same error, and that building inside WSL avoids it. Oyzu doesn't retry these.

Isolated tasks​

oyzu run --isolated <task> resolves the same task names, depends_on, and pre_<task> / post_<task> hooks as an ordinary task run. It captures source and configuration, prepares the owning builder's dependencies and toolchain image, and runs that task graph through the isolated executor. It does not add the builder's other build, check or package stages. A native task can still require a producer through its builder's declared data dependencies.

The run writes the usual bundle with its plan, action logs, isolation evidence and required reports. Test/report failures fail the run; a native command's nonzero exit code is returned. --json prints the final manifest. Only outputs whose artifact producers actually ran are collected; arbitrary files written inside the captured workspace are not copied into your checkout. The task gets no interactive stdin. An unavailable isolation backend fails without executing the task on the host.

As with ordinary task runs, an artifact-reading hook is skipped because the task invocation does not stage build artifacts. Other selected hooks and dependencies still run. A full isolated build continues to refuse hooks that read artifacts.

Successful actions record their enforced sandbox controls. A failed or interrupted action currently omits those fields, so its manifest alone cannot establish that action's isolation. Qualifying those cases requires retained execution logs and trusted observations of the actual runtime processes. Cancellation qualification also checks process cleanup; pool jobs include the outer job container's teardown in that check.

A qualified target task uses that target's existing builder/image. An unqualified root task needs exactly one target, or must be reached from a qualified task whose owner it can inherit. Missing or ambiguous ownership is refused before task execution. This first version refuses extra task arguments (-- args), platform/runtime matrices that change the task's owner, and owners with build-level depends_on or materialize artifact inputs. Use oyzu build --isolated for those artifact pipelines. It adds no separate task image setting. Configured report obligations, disabled checks and administrative check requirements remain binding; unrelated stages are never added to satisfy them.

Native tasks also need an explicit captured operation from their builder. A conventional placeholder that only supplies the host-discovered command is refused with TASK_CAPTURED_OPERATION_UNSUPPORTED, including authored replacements of native check slots whose report obligations are unavailable. The selected package must supply the captured task contract. Maven and Gradle require admitted native JVM model preparation before they can provide native test commands and JUnit/coverage duties; legacy metadata or a placeholder is insufficient. Windows wrapper commands such as mvnw.cmd and gradlew.bat are never substituted into a Linux captured task. The current Node provider supplies captured test and build operations; their selection/report lowering and authored custom tasks are checked separately from runtime qualification. Use oyzu build --isolated for the full captured build lifecycle. Ordinary host tasks are unchanged.

Live development task output​

Host shells and pinned tools​

oyzu run tasks get the project's pinned tool folders on PATH, plus tool variables such as GOROOT and JAVA_HOME. For example, argv = ["bash", "scripts/test-database.sh"] can call the pinned go by name.

  • The tools must already be installed. oyzu run doesn't install them; run oyzu install first (or install --frozen --offline when cached).
  • On Windows, a bare bash or sh skips the WSL launchers in System32 and WindowsApps. Oyzu looks for a native shell on PATH, then Git for Windows' shell next to git.exe, then standard Git install folders. If none is found, the task fails with the places searched; it never silently enters WSL.
  • Git Bash converts the Windows PATH itself, so pinned tools work in scripts.
  • shell = "bash" or shell = "sh" tasks use the same lookup. The default shell is PowerShell on Windows and sh elsewhere.

Streams and progress​

oyzu run <task> reports configuration, the selected task, tool verification and execution as they happen. Silent preparation shows an activity update every ten seconds, and a running task shows a heartbeat.

Task kindOutput
Text mode, no bundleUses your terminal's stdout and stderr directly.
Records a bundle (oyzu run test, with its prerequisites and hooks)Shows output live and also saves it in the bundle's numbered dist/logs/*.stdout and *.stderr files.
Bundled task with interactive = trueUses your terminal directly. Its output can't also be saved, so its bundle logs are empty.
--jsonStdout is one final result including captured output. Diagnostics stream on stderr. The task's streams aren't terminals, so prompts appear only at the end; use text mode for interactive prompts.
  • Tasks receive your stdin, including piped input, in text and JSON mode. Container builds get no stdin.
  • -q hides Oyzu's progress and keeps the task's output and logs.
  • When output is saved, the task's stdout and stderr are pipes, which can change its buffering, color and terminal detection.
  • PowerShell shell tasks need interactive = true to drop -NonInteractive.
  • The task's own color handling, including NO_COLOR, is unchanged.

For example, a task with argv = ["sh", "-c", "read x; printf 'got:%s\\n' \"$x\""] prints got:hello for printf 'hello\n' | oyzu run ask -q.

Windows task process lifetime​

On Windows, each oyzu run command, prerequisite and hook runs in its own job object that is killed when closed.

  • Child processes stay in the job. If Oyzu is killed, the whole task tree stops and releases the ports it held.
  • When a task finishes, any processes it left behind are stopped. Don't leave background services running after a task returns; run a service in the foreground instead.
  • stdin, arguments, exit codes and Ctrl-C behave as usual.
  • This is process cleanup, not file or network isolation.

If the job can't be created or the task's main thread can't be found or resumed, the task doesn't start and you get a TASK_JOB_* or TASK_PRIMARY_THREAD_* error. An enclosing job that doesn't allow nesting, or denied OS access, must be fixed first. If leftover processes don't exit within ten seconds, the task fails with TASK_JOB_CLEANUP_FAILED.

Host scheduling​

Native builds use the same task planner as container builds. Independent targets run in parallel up to build.jobs. depends_on: [api] under builds.web makes web wait for api's stages to succeed. A failed dependency blocks its consumers, not unrelated targets. Use materialize to pass files between targets; see target workspaces.

Isolation, evidence and failure​

Container builds run each target in its own private workspace.

Workspace ownership​

Prerequisites order tasks; they don't pass files between targets. When a consumer needs a producer's files, declare artifacts and use materialize (see directory artifacts).

  • dist/plan.json records each action's owner, tools, dependencies, environment and required reports. The manifest records results, reports and artifacts. See build bundles.
  • Packaging waits for every selected task of that target.
  • A failed prerequisite, post-hook or required report blocks dependent actions and packaging. Whatever evidence exists stays in the failure bundle, and independent targets can still succeed.
  • oyzu inspect dist checks the bundle's integrity, not whether it may be released.

Source copies in container builds​

Container builds capture your source once and give each target its own copy from that capture.

  • Capture follows in-tree .gitignore rules (case-sensitive), including rules above a nested build root. Untracked files that aren't ignored are included. Tracked files that are ignored are left out with a SOURCE_TRACKED_IGNORED warning.
  • To include an ignored file, list it in the target's inputs. This never includes Oyzu state, Git metadata or a nested repository. Listing a file includes its ignored parent folders but not their other contents; listing a folder includes everything ordinary inside it.
  • Global Git excludes and tool-specific ignore files don't affect capture.
  • Each copy is checked against the capture (size, digest, executable bit). A changed or missing file, a symlink or reparse point, or a copy failure stops the build; fix the problem and rerun.
  • The plan and manifest record the selection in source.selection (container builds) or source.projections (native builds), so it can be replayed later. Compare the result with source.treeDigest to confirm the bytes are the same.

When oyzu.lock is part of a container build's source, it is recorded with the source and tool evidence but hidden from the builder's view of the project, so license scanners don't treat it as project source. Listing it in a target's inputs keeps it visible.

Docker preparation deadlines​

Captured plugin actions default to a 30-minute timeout, including cold native compilation and tests within the same action. A builder can supply its own execution deadline; the plan records the selected limit. A timeout fails the action with exit 124 and blocks dependent artifact export. There is currently no user setting for this action timeout.

Docker preparation commands have fixed time limits, separate from action timeouts:

OperationLimit per command
Image and platform inspection, daemon checks, tagging, worker control and volume operations30 seconds
Image pulls and exports, worker file copies and tool restoration30 minutes
Removing a failed restoration or a running worker5 seconds
  • They can't be configured. When one expires, the command fails with a deadline error and the Docker client is killed.
  • Failed pulls keep Docker's error message.
  • Before retrying, check the daemon, registry access and free disk space.
  • Killing the client doesn't stop work inside the daemon. After the daemon recovers, look for and remove leftover Oyzu containers.

Cancelling a build has its own cleanup budget; see forced cancellation.

Frozen plugin selections​

oyzu build --frozen uses the plugin selections pinned in oyzu.lock and fails with PLUGIN_LOCK_MISSING instead of resolving or rewriting the lock. --store picks the store that holds installed plugins. See plugin packages.

Limits​

  • Error messages for cycles don't yet show the shortest cycle path.
  • Oyzu doesn't infer a task's generated outputs; declare them. Long-running interactive services aren't supported as tasks.
