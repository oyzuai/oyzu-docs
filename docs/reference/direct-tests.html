Direct test reports

CLI reference

Published from the canonical docs/reference/direct-tests.md file. Features marked experimental remain experimental; check support limitations before relying on them.

oyzu run test runs your project's tests on your machine and writes a test-only dist/ bundle with JUnit results, coverage and logs. Use it for a quick test run that still produces the same reports a full build would.

oyzu run list
oyzu pin
oyzu install --frozen
oyzu run test
oyzu inspect dist
oyzu run test -- --test-name-pattern=greeting

It needs no Docker or account. Pin the project before a direct Node test and use oyzu install --frozen to install its selected runtime (see Node selection). Task preparation installs the locked Node quality set in the shared store when needed, including fallback reporting tools. Install your project's own dependencies and reporters first; the task does not install missing declared packages. Source admission and offline rules apply to managed preparation. See locked quality tools.

Supported projects​

ProjectTest runner and reports
Node, single package or npm/pnpm/Yarn workspacenode:test, Jest, Vitest or Mocha, with JUnit and LCOV coverage. See npm workspaces and native workspace tests.
Python with pip, uv or Poetrypytest, with JUnit and Cobertura coverage. See Python test reporting.
Go module or workspacego test, with JUnit and Go coverage profiles. See Go testing.
Rust app or workspacenextest JUnit, Cobertura coverage and doctests. See Rust test reports.
Helm chartLocal validation and optional helm-unittest suites. Coverage is recorded as not applicable. See Helm.
AntAssertion and JUnit targets. See Ant.
Maven reactorNative tests and JaCoCo. See Maven.
Gradle multi-project or composite buildNative test reports. See Gradle.

Docker targets don't produce test-only bundles. A supported test that depends on an unsupported one fails before running.

The examples on this page use Node.

How it runs​

  • The builder recognizes the usual test runner, or an exact supported test command, and adds JUnit and coverage reporting.
  • npm pretest and posttest scripts run as usual.
  • A qualified name such as api:test uses that target's configuration and folder.
  • A Go command-folder build such as path: cmd/api tests that selected package with native JUnit and Go coverage reporting; see Go direct tests.
  • Your pre_/post_ hooks and prerequisites run in the usual task order.
  • Arguments after -- go only to the requested task.
  • Hooks and commands get OYZU_TEST_REPORT and OYZU_COVERAGE_REPORT, the paths to write reports to. Each run uses a fresh private report folder.

Test runs don't run packaging, lint or formatting. Use oyzu build for those and for artifacts.

Task resolution and report integration​

oyzu build and oyzu run <target>:test pick the same test command: your Oyzu task if you defined one, else the package.json test script, else the builder's default. The command runs in one of three modes, shown in the summary and in the manifest's oyzu.dev/report-integration extension:

ModeWhenWhat Oyzu does
builder-defaultNo test script or task.Runs node --test with JUnit and LCOV reporters. No extra packages needed.
native-runnerThe script is exactly node --test plus plain --flag options.Runs the script through npm (so pretest/posttest still run, once) and appends reporter and coverage options after --. Scripts that name paths, reporters, coverage or watch options aren't changed, because Node ignores flags after paths.
opaqueAny other command.Runs it exactly as written. Reports are collected only if the command writes them to OYZU_TEST_REPORT / OYZU_COVERAGE_REPORT (or a declared reports path). Missing reports are recorded as status: missing.

Each test also gets a test-evidence record (oyzu.dev/test-evidence in the manifest, the Test evidence block in the output, evidence in oyzu run --json) with the status of the command, test results and coverage, and a verdict:

CaseVerdict
Builder default or native runner, reports collectedaccepted
Opaque command passed, reports missing, not requiredincomplete ("command passed; test results missing; coverage missing"); the run still succeeds
Test command failed (any mode)rejected; the command fails and partial reports are kept
A required report is missing (checks.tests = "required", checks.coverage = "required", checks.coverageMinimum, or a reports entry on the task)rejected with a report-missing error
Builder default, but a report is missingThe command fails

Only reports written during this run count; older files are rejected. Oyzu never edits package.json or your configuration.

An opaque task replacement has the same report rules as an opaque package.json script. Replacing node --test with a command such as argv = ["node", "-e", "process.exit(0)"] can succeed with incomplete evidence; it does not prove tests ran. Set checks.tests = "required" or checks.coverage = "required" to reject missing results. A positive coverage minimum or a task's declared reports entry also remains binding.

You can also declare where a supported command writes a report:

[tasks."project:test"]
argv = ["node", "--test"]
reports = [{ kind = "test", format = "junit", path = "reports/junit.xml" }]
  • The path is relative to the task's folder. Missing parent folders are created.
  • A recognized native Node command with one test owner writes to the declared destination, including when it runs through the workspace-test adapter. Redirecting JUnit leaves the coverage destination unchanged unless you declare that too. The assigned host paths preserve Windows drive and UNC forms.
  • Declaring one report doesn't remove the other required kinds.
  • No file may already match a declared path or glob before the run. Move or delete old files first.
  • For a glob, your command must produce the matching files.

Outputs and failures​

dist/manifest.json links the JUnit and coverage reports (LCOV for Node, Cobertura for Python and Rust, Go coverage profiles for Go), their summaries, the plan and the logs. It lists no new artifacts.

The command fails when tests fail, a required report is missing or malformed, or coverage is below the configured minimum. Failed test reports are kept when available.

Native Node JUnit and coverage are copied independently. If one is missing, the available report stays in the bundle; the missing required report still rejects the command. No earlier report substitutes for a missing current one.

  • A failing pre-hook blocks its test.
  • A failing test skips its post-hook.
  • A failing post-hook keeps the test's reports.
  • Reports are collected after the post-hook, so a hook can transform them.
  • A test that can't start is recorded as failed. Actions that never ran are marked blocked.

Output is shown live and also saved in the bundle's numbered log files, including when tests fail. A task with interactive = true uses your terminal directly, so its output isn't saved. See task output.

Only one oyzu run test can write a bundle at a time; a second one fails with a workspace-lock error.

Existing application output​

Host tasks often build into dist/ before testing. A direct test keeps those files next to its reports and records their paths, sizes and digests under oyzu.dev/host-outputs. They aren't listed as artifacts of the test run. oyzu inspect checks this list. Earlier Oyzu reports and logs move to history.

  • The previous dist folder moves to .oyzu/history/<run-id>.
  • Native output must be ordinary files and folders. Links, reparse points and files that collide with new reports fail.
  • manifest.json, plan.json, envelope.json and logs are reserved names in dist. Move an application file with one of these names before running.
  • If the command fails early, the earlier bundle may still be in place. Check the command's result and run ID rather than assuming dist belongs to the last attempt.

A later full build can keep a preserved file at an artifact's destination only when it matches the new artifact exactly (kind, digest, size and executable flag). Different content at the same path fails. See bundle retention and recovery.

What the bundle claims​

A direct test run is local development evidence. The plan, envelope and manifest record oyzu.dev/invocation with:

FieldValueMeaning
kindtestA test-only run.
executionhostRan on your machine.
isolationnoneNo sandbox; tests have your network and file access.
sourceobserved-before-runSource was hashed before the run; later changes aren't captured.
toolIdentityunverifiedAmbient tools weren't verified.
  • Actions declare network: host and aren't cached.
  • Environment values are redacted in the plan. The tests' own output isn't scanned for secrets.
  • In CI the producer is recorded as ci-unverified.
  • A test run doesn't satisfy full-build checks and grants no publishing or signing rights. oyzu inspect checks integrity, not authenticity.

Native Node framework prerequisites​

No test configuration is needed. Detection picks the runner, and the exact scripts jest, jest --ci, vitest, vitest run and mocha keep npm's pretest/posttest while Oyzu adds JUnit and LCOV. Your framework configuration still decides which tests run, reporters and coverage scope.

FrameworkTested versionAlso needs
Jest29.7.0—
Vitest5.0.3@vitest/coverage-v8 of the same version
Mocha11.8.0c8 10.x in the project, or the locked default in Oyzu's managed quality set. See Mocha reporting.

Single-package implicit Mocha tests currently fail because the host reporter asset is not staged. See Mocha limits.

  • Install project dependencies before oyzu run test. Missing reporters aren't installed for you.
  • Other major versions aren't tested.
  • On Windows, npm is called through its JavaScript entry point, not a .cmd file.
  • Scripted pnpm and Yarn combinations on the host aren't tested yet.

Node selection​

With no Node pin, oyzu build picks the latest LTS release that satisfies every engines.node range. If no LTS release does, it picks the latest matching stable release, and the plan explains why. For example, with 24.x as LTS and 26.x as Current, >=22 selects 24.x and >=26 selects 26.x.

  • Pins in configuration (latest, 26, exact versions, lts/<name>) work as usual and must satisfy engines.
  • The build writes oyzu.lock and installs Node before any action runs. It doesn't run tests at this point.
  • .nvmrc and .node-version aren't read.
  • oyzu build --connector-bindings <file> supplies host bindings for tool sources routed by an administrator.

See Node selection.

Limits​

  • Direct tests are supported on Windows, Linux and macOS for Node frameworks and Rust (Rust on Windows needs MSVC; the windows-gnu toolchain lacks the profiler runtime). Helm direct tests are tested on Windows only.
  • Docker targets have no test-only bundle.
  • With the development node/app plugin binding, only single-package node --test and opaque report commands are supported. The built-in Jest, Vitest, Mocha and workspace integrations don't apply.
  • Host tests aren't hermetic.
