Node static analysis in oyzu build --plan

CLI reference

Published from the canonical docs/reference/node-static-analysis.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Status: experimental, OEP-0020 slices S1 to S4 and S5 step C. The design lives in OEP-0020; this page describes only what is implemented and measured. Nothing here is a stable contract, and the analysis does not yet change caching, selection or sandboxing. S1 added the fact model, manifest/tsconfig/import-graph analysis and the plan view. S2 added framework profiles, the constant evaluator, environment-file rules and per-stage narrowing for test. S3 added the script graph and exact TypeScript input sets. S4 added advisory diagnostic rules. S5 step C added rule levels, suppressions and oyzu build --check.

What it does​

oyzu build --plan now ends each Node target with a Static analysis section: for each stage it lists the files the stage is predicted to read, the paths it writes, the environment variables it reads, the workspace targets it depends on, the tools it needs and anything the analysis could not bound. Every line carries its confidence and source (file:line).

The analysis reads and parses files. It never runs project code, scripts, package managers or the network, and it is read-only.

ConfidenceMeaning
exactProven from literal text (for example copyFileSync("../shared/src/greeting.mjs", ...)).
over-approximateA superset that contains the truth (a glob, several resolution candidates, a bounded dynamic import).
unknownNot pinned down (computed require, computed file path, a command the analyzer does not model). unknown only ever widens; it never removes another fact. An unknown with a bound (a missing relative import, an unexpanded test pattern, a command with no tool profile) widens a confined stage only by that bound (rung widened); one without a bound widens the stage to the whole target scope. See bounded unknowns.

Usage​

oyzu build --plan api                 # analysis for every stage of the target
oyzu build --plan api --stage build   # one stage
oyzu build --plan api --why ../shared/src/greeting.mjs
oyzu build --plan api --unknown       # only unknown and over-approximate facts
oyzu build --plan api --facts         # raw facts, one table row per fact
oyzu build --plan api --no-analysis   # skip analysis; whole-target scope
oyzu build --plan api --json          # everything, including the full analysis record

All five flags require --plan and are read-only. --why accepts a path relative to the target (../shared/src/x.mjs) or to the repository root. Its answer per stage is input (facts name it), not-an-input, covered-by-bound (no fact names it but the bound of an unknown fact covers it), or covered-only-by-fallback (no fact names it but an unbounded unknown fact widens the stage to the whole target).

Where the bytes come from​

  • A normal oyzu build analyzes the captured snapshot after capture and before planning, silently. In S1 it only reports: unknown facts and analysis failures are logged at debug level (--log-level debug) with the file, line, construct and what widens. A build is never failed or changed by the analysis.
  • build --plan does not capture source, so it analyzes the working tree through the same bounded reader and says so ("analyzed from the working tree"). The preview inventories the tree from metadata alone (paths, kinds and sizes, with capture's exclusions and path checks) and opens only the files analysis reads, so planning a large checkout costs a directory walk, not a read of every file. The reader checks each file it reads against the inventoried size. The preview and a captured snapshot of an unchanged tree yield identical facts and diagnostics; this is checked by the preview_and_captured_snapshot_yield_identical_facts test. Only the record's snapshotDigest differs: for the working tree it is the inventory digest (domain oyzu.tree-inventory.v1alpha1, over paths, kinds and sizes), never a captured tree's digest, and it does not change when a file's bytes change at the same size.

Output​

Human output follows the shared presentation standard: outcome first, aligned lossless tables, labelled confidence, readable without color. --json adds an analysis object to the build-preview document: analyzedFrom (working-tree or captured-snapshot), snapshotDigest, per-target stage views with confidence, fallback (predicted or target-directory) and counts, the query, diagnostics and record, the complete analysis record. The record follows the draft analysis schema (v1alpha1, evolved in place; no version was introduced). Real output was validated against that schema during S1.

Diagnostic rules (S4)​

Rules read the facts and report problems that are only visible across files and targets. They are advisory by default: a finding never fails oyzu build --plan, and fails oyzu build --check or oyzu build only when you set its rule to enforce (rule levels). Findings are the record's diagnostics (rule, severity, message, facts), so they appear with the existing view and in --json:

Warning (phantom-dependency): app:build imports `left-pad` at packages/app/build.mjs:2, but packages/app/package.json does not declare it; it resolves today only because package.json declares it and the package manager hoists it.
  Fix: add `left-pad` to the dependencies of packages/app/package.json.

facts lists the ids of the facts behind the finding, so --json consumers can walk from a finding to its evidence. Variable names appear in messages, never values.

Rule levels, suppressions and build --check (S5 step C)​

Experimental. Policy about rules is configuration, so it lives in the oyzu.toml cascade (see configuration); the names follow the design.

[analysis.rules]
phantom-dependency = "enforce"      # off | advisory (default) | enforce

[[analysis.suppress]]
rule = "escaping-reference"
path = "legacy/**"                  # optional glob over the finding's file
reason = "vendored fork, tracked in the migration plan"   # required
LevelMeaning
offThe rule's findings are dropped from --check and from build logs
advisoryReported, never fails anything (the default for every rule)
enforceA blocking finding fails oyzu build --check and oyzu build

A finding is blocking only if its rule is enforce, it is a warning (never a note), and every fact it cites is exact. An enforced finding that rests on an over-approximate or unknown fact is reported as not blocking with its confidence and never fails a build; --check counts those so enforcement is never silently weaker than it looks.

A suppression needs a rule and a non-empty reason; path is a project-relative glob (* stays within a directory, ** crosses directories) over the file the finding cites first, and omitting it covers every file. A suppressed finding does not fail and is listed under Suppressed (with its reason in --json as suppressedBy). A suppression that matches no finding is reported as a stale note and never fails a build. Suppression changes reporting only; it never changes a stage input or cache key.

oyzu build --check                    # analyze and apply the rules; runs nothing
oyzu --json build --check             # the build --plan --json document plus a `check` object

oyzu build --check is static analysis only: it prepares, installs, downloads and executes nothing. Selection follows build --plan (targets, --affected); it cannot be combined with --plan or the analysis view flags. Exit status is 0 unless at least one finding is blocking (1); usage errors keep their exit status 2, and help, version and syntax errors finish before any project is opened. If analysis cannot complete, --check fails with that error rather than reporting a pass.

✗ Check failed: 1 blocking finding in enforced rules

Blocking packages/app/build.mjs:2
  app:build imports `left-pad` at packages/app/build.mjs:2, but ...
  Fix: add `left-pad` to the dependencies of packages/app/package.json.

The check object in --json has outcome (passed or failed), counts (blocking, advisory, nonBlocking, suppressed, staleSuppressions), findings (rule, level, severity, status, target, path, line, message, fix, confidence, and suppressedBy when suppressed) and staleSuppressions.

A normal oyzu build applies the same levels, through the same function, to the snapshot it captured (or, for native host builds that capture nothing, to the working tree it observes) before any action runs. A blocking finding stops the build with the same file, line and fix and the failed bundle records it. Advisory findings stay in the debug log. A native host build that enforces no rule skips this analysis.

Limits:

  • Only the ten implemented rules can be named; an unknown id, a level other than the three, an empty reason, an unknown suppression field or an invalid glob is a configuration error naming the valid ids.
  • analysis.rules and analysis.suppress are whole-value settings: the nearest scope that sets one replaces the lower ones rather than merging per rule. Managed policy can pin a value through the existing constraint mechanism; per-rule "cannot loosen" semantics and platform-managed pinning belong to the platform and are not implemented here.
  • build --plan still lists every finding and ignores levels and suppressions.
  • Per-rule severity overrides, expiring suppressions and authored inputs semantics are deferred.
  • lockfile-manifest-drift uses the lockfile nearest the target (a directory with several uses the one packageManager names, else the order shrinkwrap, package-lock.json, pnpm-lock.yaml, yarn.lock). It does not check transitive entries, pnpm catalogs' resolved ranges or .pnpmfile.cjs/yarn plugin rewrites.
  • Verified on Linux. Windows and macOS were not run.

Script graph (S3)​

Each stage script (build, test, lint, with pre<name> and post<name>) is read with a closed shell grammar and resolved into a command graph whose leaves are tool invocations. Scripts are read, never run. Every visited script is a stage-script fact (exact, sourced at the script's line in package.json) that records its command, its leaves (tools and unknown constructs), the scripts it calls, its depth and, below the root, the via chain (build > build:compile > compile), the hook (pre or post) and the workspace member it belongs to.

TypeScript input sets (S3)​

tsc -p, tsc -b, project lists and a bare tsc (which searches upward for tsconfig.json; tsc -b looks only in its directory) predict the compiler's own file list: the extends closure (including extends of a workspace-member package, read from the snapshot through the member's package.json tsconfig field or subpath; any other package stays unknown), files/include/exclude (the default exclude applies only when none is set), allowJs and the extension priority between a.ts, a.d.ts and a.js, references (each referenced project's own set), composite/incremental build-info files as warm state (at the compiler's default path: beside the config, under outDir, or with rootDir also set at the config's path relative to rootDir resolved from outDir), and the imports reached from those files. The compiler also reads the package.json of every directory above each program file (module format) and of every workspace member an import resolves to (exports/types/main); both are exact reads (package-scope, package-resolution).

The measurement harness checks the prediction against the compiler itself: tsc -p <project> --listFilesOnly in the prepared copy, restricted to files in the copy outside node_modules. This is test tooling; the product has no probe action and runs no native tool during analysis.

Framework profiles (S2)​

A profile is a versioned row of data (src/builders/node/analysis/profiles.rs) that the analyzer interprets: the commands that run the tool, the configuration file names, the configuration keys that refine the convention, conventional reads, outputs, warm state and environment-file rules. A profile only refines: a value found in the configuration beats the convention (an explicit Next.js distDir or Vite build.outDir replaces .next/dist), and a value the evaluator cannot read makes only the facts derived from it unknown.

The table has no hand-maintained version number. Its identity is a digest of its content: the first 16 hex characters of a SHA-256 over a fixed JSON serialization of every framework table in profiles.rs (profile rows, the SvelteKit layer, entries, templates and adapters, the Astro vocabularies, integrations, conventional modules and shipped tsconfig bases, the React Router, Angular and Nest tables, PostCSS/Tailwind CSS companions, Browserslist, Vitest/Jest match defaults and Next.js route roots). The serialization keeps declaration order and holds only strings, booleans and sequences, so the same table gives the same digest on every host and run, and editing any row changes it. The digest is part of the node-framework analyzer version in the record's analyzers list (4+profiles-<digest>, for example 4+profiles-0123456789abcdef), so a record says which rules produced it without anyone bumping a number. The script analyzer's utility table, also in profiles.rs, is not part of it.

A profile applies when a stage's script runs its command (vite build, vitest [run], next build, jest, eslint, nest build, ...), and each run emits a framework fact for that stage: framework, profile, profileVersion, tableDigest (the same digest as in the analyzer version), engine, mode and evidence. Because fact ids are content hashes, a profile table edit also changes every framework fact's id, while facts the table does not shape keep theirs.

SvelteKit (tier 4)​

SvelteKit is not a command of its own: vite build plus sveltekit() in the Vite configuration is a SvelteKit build, so the vite profile detects the plugin and applies the SvelteKit layer (framework/sveltekit.rs, data in profiles.rs) in place of the index.html entry, the public/ directory and the dist output. The layer emits its own framework fact (sveltekit, layeredOn: vite) next to the Vite one. Everything is read statically; no project code runs.

The same layer applies to Vitest when its configuration (vitest.config.*, else vite.config.*) lists sveltekit(): the plugin loads svelte.config.*, syncs .svelte-kit (it scans the routes, params, hooks and templates and writes generated types), loads .env* for mode test from kit.env.dir and resolves $lib, $env/* and kit.alias for the tests. The framework fact then says layeredOn: vitest and engine: Vitest. No adapter runs under Vitest, so a modeled adapter adds only the environment variables its module reads when the configuration imports it; an unmodeled adapter stays unknown, since importing its module can read files. The prediction is an over-approximation for tests: route modules and what they import are predicted although Vitest only lists them.

  • Components. The import graph reads a .svelte file through its <script> blocks (instance and module, lang="ts" honored) and <style> blocks (@import and url()), by blanking everything else, so facts carry the file's own line numbers. Markup is never guessed: import( or import.meta in markup is unknown, and so is a <style lang="scss">-style preprocessor.
  • Routes. Only +-prefixed files in the routes directory are graph entries (the rest of the directory is covered by its glob and by import edges).
  • Generated base configuration. tsconfig.json normally extends the tsconfig.json SvelteKit writes into kit.outDir. The layer registers that path as generated, so the extends is not unknown; without the layer the same extends stays unknown (the framework, not the tsconfig analyzer, models it).
  • Generated route types. import type { PageData } from './$types' in a route file names a module SvelteKit writes under <outDir>/types and maps beside the route through rootDirs. The layer registers <dir>/$types for every routes directory holding a + file, so the import is neither read nor unknown; the bundler erases it. A $types import elsewhere stays an unresolved import.
  • Adapters are modeled from the published source of adapter-static 3.0.10, adapter-node 5.5.7, adapter-vercel 6.3.2 and adapter-netlify 6.0.4 (the SvelteKit 2 line; 7.x requires SvelteKit 3); the table is data in profiles.rs. Other versions are not qualified. adapter-netlify publishes to netlify.toml build.publish (read with a TOML parser; absent or empty means build), writes its functions (lambda, split or edge) under .netlify and its temporary edge bundle under kit.outDir, copies _headers and _redirects from the working directory when they exist, and reads NETLIFY_SVELTEKIT_USE_EDGE.
  • adapter-cloudflare is modeled from the published source of 7.2.9 with Wrangler 4.149.0 (unstable_readConfig, which does not follow a .wrangler/deploy/config.json redirect). The Wrangler file is the config option's path, else the first wrangler.json, then wrangler.jsonc, then wrangler.toml found by searching the working directory and each ancestor up to the source root, one name at a time (an ancestor's wrangler.json wins over a local wrangler.toml). Every candidate probed is an input, found or not. The file is parsed as JSONC or TOML, and main, assets.directory and pages_build_output_dir, at the top level and in every env section, are outputs relative to the file. The union means neither CF_PAGES (Pages mode) nor CLOUDFLARE_ENV (the section) can move an output outside the prediction; both are reads-env facts. The adapter also writes <outDir>/cloudflare and <outDir>/cloudflare-tmp, copies _headers and _redirects from the working directory, and rejects a _routes.json there. Options other than config, fallback, routes and platformProxy, a file that does not parse, a path value that is not a string or leaves the source, and any route option module (+page, +layout, +server, with .server variants, .js/.ts) that names prerender or re-exports a whole module are unknown. Prerendering starts Wrangler's platform proxy (Miniflare), which is not modeled.
  • adapter-auto is modeled from 7.0.1. It loads the adapter of the first environment whose variable is set: VERCEL, CF_PAGES, NETLIFY, GITHUB_ACTION_REPOSITORY (Azure), SST and GCP_BUILDPACKS (adapter-node). With none set, it only warns. A captured action sees only the variables its task sets (oyzu.toml env and task environments), never the caller's environment. The analyzer therefore reads the build task's variable names (names only, never values). With none of the six set, the adapter adds nothing but the six reads-env facts. For each one that is set, the selected adapter's model applies with default options. A set variable whose adapter is not declared in package.json is unknown, because adapter-auto installs it at build time. So is one whose adapter is not modeled (Azure, SST). Since a set variable may be empty, every set candidate is applied, not only the first.
  • Absent inputs. Missing hook, service-worker and instrumentation modules are recorded as one candidate glob each, since creating one changes the build.
  • Not modeled (their reads are not predicted): code that runs at prerender time beyond literal file access the import graph already sees, svelte-kit sync/svelte-check as separate script commands, Tailwind CSS v4, @sveltejs/enhanced-img, adapter environment variable names other than adapter-vercel's two, adapter-netlify's one, adapter-cloudflare's two and adapter-auto's six (Wrangler's own logging variables are not listed), Wrangler's log files under the home directory (outside the source), kit.paths/CSP/version options (they read no files), and Svelte 4 only syntax beyond what the script parser accepts.
  • Components. A <script> or <style> tag inside an HTML comment in a component's markup is markup, not a block.
  • Build identifier. SvelteKit stamps the build time into client chunks unless kit.version.name is fixed, so their content and content-hashed names change on every build. The confinement gate compares such files by name shape (below); the sveltekit-app fixture fixes the version, sveltekit-netlify does not.

Astro (tier 4)​

astro build is its own engine (AstroBuild, framework/astro.rs, data in profiles.rs). It was modeled from Astro 7.3.8's published source (resolveConfigPath, createFileBasedRoutes, the content and actions file searches, env/env-loader.js) and checked against real astro build traces. Everything is read statically; no project or Astro code runs.

  • Static output by default. The default output: "static" (and "server") is modeled; outputs are outDir and .astro, warm state is cacheDir (the content data store and image and font caches).
  • Configuration. astro.config.* is evaluated with the constant evaluator and checked against a closed vocabulary (ASTRO_CONFIG_KEYS and the vite, markdown and image sub-vocabularies in profiles.rs). Keys that change no file access (site, base, trailingSlash, build, server, redirects, i18n, security, ...) are accepted; any other key is unknown.
  • Integrations and adapters. @astrojs/sitemap (3.7.4, any options: it reads no project file and writes into outDir) and @astrojs/mdx (8.0.3, without options: adds .mdx routes and entries) are modeled. Every adapter (@astrojs/node, -vercel, -netlify, -cloudflare) and every other integration (UI frameworks such as @astrojs/react, @astrojs/markdoc, Starlight, Tailwind) is unknown.
  • Environment. Files load the Vite way from vite.envDir (default the root); names with PUBLIC_ (or vite.envPrefix) are reported from the files, every import.meta.env.NAME read in frontmatter, scripts or markup is reported from the graph (server-side private names are inlined at build time too), and every env.schema key is an exact reads-env fact (role: env-schema), since the build validates them. astro:env/* imports are virtual.
  • Virtual modules. Specifiers starting with astro: (astro:content, astro:assets, astro:env/client) are neither files nor packages: the graph skips them and the phantom-dependency rule does not see them.
  • Components. A .astro file is read through its frontmatter, the <script> tags Astro bundles (no attributes, or only src; is:inline, type or define:vars leave a script inline), <style> blocks (is:inline excluded) and import.meta.env.NAME in markup, by blanking everything else, so facts carry the file's own line numbers. HTML comments are ignored.
  • Markdown and MDX. The frontmatter layout is an import; every path-like frontmatter string (for image() schemas), Markdown image syntax, <img src> and reference definitions is a read when it resolves to a project file (relative, bare relative or alias). MDX import/export blocks outside code fences are parsed as JavaScript. References are over-reported (code blocks included).
  • Shipped tsconfig bases. extends: "astro/tsconfigs/base|strict|strictest" is not unknown: those files set compiler options and include/exclude only (no paths, baseUrl, files or references), checked in 7.3.8.
  • Not modeled (their reads are not predicted or are unknown): injectRoute and other integration hooks, server islands and on-demand rendering behind an adapter, astro check/astro sync as script commands, Sass/Less in <style>, Astro.glob (absent from Astro 7), a warm .astro directory from an earlier build (it is treated as an output), and Astro versions other than 7.3.8.

Nuxt (tier 4)​

nuxt build and nuxt generate (from nuxt or @nuxt/cli, also run as nuxi) have their own profile (framework/nuxt.rs, data in profiles.rs). It was written against the source of Nuxt 4.5.2, @nuxt/cli 3.37.0 and Nitro 2.13.4 and checked with real builds of those versions; Nuxt 3 defaults come from @nuxt/schema 3.21.11 and were not built. Nothing of the project runs.

  • Configuration. The script forms of nuxt.config are read by the constant evaluator, with defineNuxtConfig (a global in Nuxt) as an identity wrapper. The other forms c12 accepts (JSON, YAML, TOML, nuxt.config/index.*, .config/nuxt.*) and Nitro's own nitro.config.*/.nitrorc make the stage unknown; one candidate glob records that creating any of them changes the build. A .nuxtrc in the project is unknown (the user's ~/.nuxtrc is outside the snapshot and not modeled), and so are the $production block (or the block --envName names) and $env, which c12 merges over the configuration.
  • Version and srcDir. The major version of the declared nuxt dependency picks the defaults. Nuxt 4 uses app/ unless that directory is absent, or holds only router.options.* and spa-loading-template.html while the root has app.vue or a pages-style directory; Nuxt 3 uses the root unless future.compatibilityVersion is 4. In Nuxt 3 server/ and public/ follow srcDir; in Nuxt 4 they stay at the root.
  • Scanned directories. Nuxt imports by scanning, not only by import edges, so each scanned directory is a bounded glob, present or absent, and every .vue, .js or .ts file in it is also a graph entry. server/, shared/ and public/ are globs too.
  • Components. .vue files are read like .svelte files (<script> with lang="ts"/tsx, <style> @import and url()), and the template's static asset URLs are followed as Vue compiles them (img/source src and srcset, video src/poster, image/use href; ~/x drops the tilde). A template in another language (lang="pug") or file (src=), a <script src> or <style src>, and an asset that does not resolve are unknown. An import of a .vue file without its extension does not resolve and is unknown.
  • Environment. Nuxt's own loader reads the root .env (not mode files); Vite runs with srcDir as its root, so its .env, .env.local, .env.production and .env.production.local are read from srcDir (VITE_ names are inlined). NITRO_PRESET, SERVER_PRESET, the compatibility-date variables and NUXT_APP_BASE_URL, NUXT_APP_BUILD_ASSETS_DIR and NUXT_APP_CDN_URL are build inputs. runtimeConfig overrides (NUXT_API_SECRET, NUXT_PUBLIC_API_BASE, with NITRO_ as the second prefix) are read by the server at run time, so a plain nuxt build does not depend on them; a real build confirmed that a NUXT_PUBLIC_ value does not reach .output. When routes are prerendered (nuxt generate, --prerender, routeRules, nitro.prerender, nitro.static), the prerenderer runs the server and the value is baked into the HTML (also confirmed), so every key path of runtimeConfig becomes a reads-env fact under both prefixes (NUXT_PUBLIC_* with publicPrefix: true), plus NITRO_ENV_PREFIX and NITRO_ENV_EXPANSION. A runtimeConfig the evaluator cannot read is unknown in that case.
  • Presets and outputs. The build writes .nuxt and .output. Nitro picks the preset from --preset, NITRO_PRESET/SERVER_PRESET, nitro.preset, then the deployment provider it detects; without a configured preset the output layout depends on where the build runs, so the stage is unknown and the detail says to set nitro.preset or pass --preset. node-server (and its aliases) and node-cluster write .output; static, nuxt generate and prerendering also create the dist link to .output/public. A preset variable set in the environment is a recorded input, but the predicted writes follow the configured preset.
  • Unknown options. modules, extends/theme, rootDir, hooks, builder (webpack and Rspack), components, serverHandlers, spaLoadingTemplate, build.templates, build.transpile, typescript.typeCheck, vite.plugins, vite.resolve, vite.css, vite.root, vite.vue, vite.build, vue.transformAssetUrls, the Nitro options that add code or directories (plugins, handlers, publicAssets, serverAssets, srcDir, scanDirs, modules, hooks, rollupConfig, output.publicDir/serverDir), postcss.config, PostCSS plugins other than the inert ones, and local layers/ and modules/ directories make the stage unknown.
  • Not modeled (their reads are not predicted): what a module reads (the realism ui/tailwindcss project's tailwind.config.js is covered only by the stage's unknown), presets other than the five names above, the webpack and Rspack builders, nuxi typecheck/prepare/analyze as script commands, Nuxt Content and other module conventions, Sass/Less, and Nuxt 3 behavior beyond the directory defaults.

Constant evaluator for script-form configs​

Script configs (.js, .mjs, .cjs, .ts, .mts, .cts) are parsed to an AST and evaluated by a closed interpreter (consteval.rs), never eval, never the project's code. It understands object and array literals, string and template concatenation, path.resolve/join/dirname/normalize/basename, __dirname, import.meta.dirname/filename/url, fileURLToPath, new URL(x, import.meta.url), spread, await (of a constant or a package call), conditionals and logical operators with constant operands, top-level const bindings, defineConfig(x)/defineConfig(() => ({…})) wrappers (and Nuxt's global defineNuxtConfig), and relative imports of other config files and JSON. Everything else — any other call, a loop, a function parameter, process.env.X (recorded as a reads-env fact from the import graph, value unknown), a binding mutated after its declaration — evaluates to unknown for that value only. Budgets: 50,000 evaluation steps, 10,000 items per array or object, 64 KiB per string, six levels of config imports, 200 levels of expression nesting and 400 bracket depth; hitting one makes the value unknown and names the limit.

Per-stage narrowing and test-only edits​

Facts belong to the stage that needs them, so the test stage lists the runner's test files and setup files and the build stage does not. A test-only edit (a new test file, a new helper imported by tests, an edited setup file) therefore leaves every build fact unchanged and changes the test facts:

oyzu build --plan --why tests/extra.test.ts --stage build   # not-an-input
oyzu build --plan --why tests/extra.test.ts --stage test    # input

When the runner's configuration is not statically readable (a computed test.include, a config built by next/jest), only the test stage falls back: it gets an unknown fact, fallback: target-directory, and --why can no longer claim a path is not an input. The build stage does not depend on test discovery and stays bounded.

Vitest's test action also retains this complete target view when discovery is bounded: Oyzu's reporting adapter always enables native coverage, which can read unimported source files. The Node profile therefore records coverage reads as unknown whether authored coverage.enabled is absent, false or true. The final test action is target-directory and not confined to its predicted import graph; other stages keep their existing contracts. Native coverage configuration and thresholds remain effective over the supplied files. This conservative scope avoids incorrectly reporting full coverage after omitting an unimported source. The vitest-coverage fact identifies the owned reporting effect; unreadable project configuration retains its separate config-unreadable diagnostic.

Builder-owned stages​

Five stages of a Node package run commands the builder chooses rather than a project script: the version stamp (version), the npm install (prepare), npm pack (package), and, for a package without a lint or format-check script, the default ESLint and Prettier checks (node-quality.mjs). Their reads follow from the command, so analysis/owned.rs models them and --plan lists them under those stages (oyzu build --plan --stage package). Each such fact names its command in runner (node-version-stamp, npm-install, npm-pack, node-quality-eslint, node-quality-prettier); the builder tags the same command with the same runner, and a stage contract uses the facts only for an action that runs it. The full table of reads and of what is unknown is in the stage/action contract.

  • Absent files are reads. A tool that looks for a file reads its absence: the version stamp probes npm-shrinkwrap.json, npm .npmrc and .npmignore, ESLint every eslint.config.* and .eslintrc* in and above the target, Prettier every configuration name and .editorconfig in and above it. Creating one changes the stage's key.
  • Whole-package reads. npm pack without files (or with a glob in it) reads the whole package directory; the quality checks read every JavaScript and TypeScript file below the target.
  • Implicit native installation. npm's install probes binding.gyp, including its absence. If it exists, gypfile is not false, and there is no nonempty install or preinstall script, npm defaults to node-gyp rebuild. The analyzer marks that implicit lifecycle as unbounded unknown, just like an authored install script, so preparation retains the target-directory scope instead of hiding native sources in a predicted confined view. A postinstall script does not suppress the native default. This does not parse gyp actions or bypass the existing confinement contract. Formatting and the captured native addon/independent-consumer flow pass with a Windows controller and Linux/amd64 worker. Focused Rust regressions, the full workspace suite and strict all-target Clippy pass. Unix host confinement qualification remains pending; container execution does not qualify that host source-view path.
  • Not modeled. Workspace roots and members, pnpm and Yarn installs and packs, application package commands, Biome, legacy ESLint configuration, Prettier script configurations and plugins, install lifecycle scripts, unreviewed dependency install scripts and local, Git or URL dependencies. Each is unknown for its stage only (or, for another command, simply not joined), so that stage keeps the target-scope key and the others stay confined.

Confinement gate​

python tooling/measure-node-analysis.py --cli <oyzu> --confinement (no strace; it runs the real native stages, so it needs the project toolchains: npm, and pnpm for ts-monorepo). For every stage of every authored project whose analysis has no unbounded unknown fact it runs the stage twice from the same prepared copy: once with the whole project visible and once with every file the stage's predicted reads and bounds do not cover removed, the stage contract's projection. It compares the exit code and every file the stage created or changed. A second whole-project run finds output that differs run to run on its own (Next.js writes a random build identifier); that output is excluded and counted in the noise column. A directory or file named by such an identifier (Nuxt's builds/meta/<uuid>.json) is compared under one placeholder name, so a third value in the confined run is not a difference. A build that stamps its time into its output (SvelteKit's default kit.version.name) also renames every content-hashed chunk that embeds it (start.BXjHf8fU.js, 6hRs4Xk-.js): a hashed name that differs between the two whole-project runs is compared by its shape (start.*.js) and count, not by its name or bytes, and counted in the renamed column; the confined run must produce the same number of files of each such shape. A shape whose count differs between the two whole-project runs is noise. Stages with an unbounded unknown fact are reported as not confined; a bounded one keeps its bound visible (bounded unknowns). A negative control removes shared/src/greeting.mjs from the EX-033 api prediction and requires the gate to report the stage as diverged.

Every run of a stage (whole, repeated and confined) happens at one fixed path, because Nuxt embeds absolute paths in its output and content-hashed chunk names would otherwise differ between copies.

For a check the verdict (exit code and report) is compared, so a check that fails must fail the same way confined. Windows trace prototype​

Status: prototype; probe and the tier 0 to 2 corpus passed on one Windows host, 2026-10-10, with zero soundness failures (see Tier 0 to 2 on Windows). tooling/node_analysis_etw.py gives the harness a Windows tracer with the same contract as the Linux strace one: it runs a native stage, fails if the stage fails, and returns the checkout-relative files (outside node_modules, .git and .oyzu) that the stage or any process it started opened or queried. On Windows the traced measurement (--cli <oyzu> with no mode flag) uses it in place of strace; nothing else in the harness changes.

How it works: an ETW session started with the in-box logman records the Microsoft-Windows-Kernel-File Create events (every open, including the opens behind attribute queries) and the Microsoft-Windows-Kernel-Process start and stop events to an .etl file while the stage runs. tracerpt decodes it to XML. The session is system-wide, so the tracer follows the stage's process tree the way strace -f follows forks and drops every other process. It keeps opens of existing files only (the FILE_OPEN disposition, not directories), maps NT device names (\Device\HarddiskVolume3) to drive letters, and matches paths case-insensitively against the checkout, reporting each file with its on-disk spelling. A trace whose header reports lost events, or no lost-event count at all, is rejected, because a lost Create event would hide a read.

Prerequisites: Windows, an elevated prompt or membership in Performance Log Users (kernel providers need one of them; a new group membership applies after signing in again), logman and tracerpt (both in-box), Python 3.11+, and for the measurement itself Node, npm and pnpm as on Linux.

Check the tracer before trusting a measurement:

python tooling/measure-node-analysis.py --trace-probe
python tooling/measure-node-analysis.py --cli target\debug\oyzu.exe --only vite-spa

--trace-probe needs no CLI. It runs a small Python program (and a Node one when node is on PATH) that reads a file, stats one, queries one with GetFileAttributesW, opens one with the wrong case, starts a child that reads a file, writes and appends to files, and reads one in node_modules and one outside the checkout. The tracer must report exactly the reads, stats and the child's read. It prints TRACE PROBE RESULT: tracer saw exactly the probe's reads and exits 0, or names each missed or extra file. It runs on Linux too, against strace, where it passes (2026-10-10, Node 22); a tracer that drops a read makes it fail.

The ETW decoding is unit-tested on any host (python tooling/test-node-analysis-etw.py: event order, the lost-event header, tracerpt's RenderingInfo block, the process tree with a reused process id, the disposition and directory filters, device-name mapping and checkout matching).

Windows path audit (Linux review, not a Windows run)​

The analysis code was reviewed for Windows path risks. This is what was found:

  • Fixed: a leading UTF-8 byte order mark (written by Notepad and Windows PowerShell 5) was kept in the text offered to the parsers, which dropped facts (a .env file whose first variable is hidden by the mark, a tsconfig or manifest that failed to parse) and could raise a false undeclared-env finding. SnapshotReader now drops one leading mark; provenance byte offsets index the text after it. Unit test: leading_byte_order_mark_is_not_part_of_the_text.
  • Verified correct, test added: line and column numbers are computed from \n only, so a CRLF file reports the same lines and columns as the LF file (crlf_text_has_the_same_lines_and_columns_as_lf_text); the harness checks the same for every corpus project.
  • Already handled by the snapshot, unchanged: the inventory converts \ to /, rejects non-portable names and case-colliding paths, and refuses symlinks and reparse points; analysis paths are POSIX relative strings and the code in src/analysis and src/builders/node/analysis never formats a host path (the harness checks the records for leaks).
  • Not changed, limitation: join rejects a relative specifier containing \ or :. It is not exercised by the corpus.
  • Fixed later (2026-10-10), case-insensitive resolution: the resolver matched specifiers case-sensitively, whereas Windows and default macOS open a file whose name differs only by case. A mismatched import became unknown (sound but imprecise), and one case was unsound: with A.js and a.ts beside each other, ./a.js was predicted to read only a.ts (TypeScript's mapping), while Node on Windows opens A.js. Each resolver probe (relative and alias specifiers, member entries, directory index and package.json lookups) now also matches the one inventoried path that differs only by ASCII case and records it under its real spelling, so the prediction is the superset on every host and facts stay host-independent. Capture already rejects case-colliding paths, so the match is unique; if a snapshot ever held two, the probe matches neither and the import stays unknown. A path with non-ASCII characters is matched exactly, because NTFS (upcase table) and APFS (normalization) fold those differently. Every other exact-name lookup the analyzers make (a framework config, a tsconfig.json, a directory convention) is not changed one by one: the snapshot reader remembers each lookup that missed only by case, and the analysis adds a target-wide case-variant-path unknown naming the asked and found paths, so a Vite.config.ts where Vite asks for vite.config.ts widens the target instead of being predicted absent. Tests: case_insensitive_lookups_name_the_inventoried_entry_and_remember_near_misses, imports_differing_only_by_case_resolve_to_the_inventoried_file and non_ascii_case_variants_and_exact_name_lookups_widen_to_unknown. Plans of every authored corpus project and all 27 pinned real projects are byte-identical before and after the change on Linux (none has a case mismatch). Not run on Windows or macOS. The residual gap for Unicode normalization was closed the same day (below).
  • Fixed later (2026-10-10), Unicode normalization: APFS and HFS+ open a name in either normalization form (NFC é or NFD e plus a combining accent), and a Mac can commit either, while Linux and Windows treat them as different names. Before, an import spelled in one form of a file inventoried in the other stayed an unresolved unknown (sound but imprecise), and an exact-name analyzer lookup that missed only by normalization was predicted absent without widening. A probe for a non-ASCII path now also matches the one inventoried entry with the same NFC spelling and records it under its real spelling, which is again the superset on every host. When several entries share that spelling and none is the asked one, nothing matches and the target widens; a miss by case and normalization together widens too, since non-ASCII case folding differs between hosts. The snapshot reader's near-miss key is now the lowercased NFC spelling, so exact-name analyzer lookups that miss only by normalization also add the case-variant-path unknown, whose detail now says "differs only by case or Unicode normalization". Capture still rejects only case collisions; a tree holding both forms of a name is kept. NFC comes from icu_normalizer, already compiled in through reqwest's url/idna. Tests: normalization_insensitive_lookups_need_one_spelling and imports_differing_only_by_unicode_normalization_match_one_file_or_widen. Not run on macOS.
  • Fixed later (2026-10-10): a package.json that starts with a byte order mark was rejected by Node target discovery (src/builders/node, outside the analysis), so oyzu discover and oyzu build --plan failed on such a project. The Node builder's Rust-side manifest reads now drop one leading mark with the same helper the snapshot reader uses. Tests: byte_order_marked_package_json_is_discovered_like_an_unmarked_one and compiled_build_plan_reads_a_byte_order_marked_package_json. The Node runtime adapters used in isolated builds read package.json through the shared runtime/manifest.mjs, which drops the mark the same way. quality.mjs and version-stamp.cjs run as node -e, so they drop it inline. Proof: node --test tooling/test-node-manifest.mjs. A real isolated build of a marked project has not been run (the worker image pull returned 403 where this was checked).
