Node static analysis

CLI reference

Published from the canonical docs/reference/node-static-analysis.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Oyzu can read a Node package's source and scripts, without running anything, and predict what each build stage will read and write. Use it to see why a build depends on a file, to catch problems that only show up across files (an undeclared dependency, a secret in a browser variable), and to let the isolated build give each stage only the files it needs.

Note: This feature is experimental. Names, output and rules can change.

Quick start​

Preview the analysis for a target:

oyzu build --plan api

Each Node target ends with a Static analysis section. This target never declares ../shared, but its build script copies a file from it, and the analysis reports that read with the script line that does it:

api:build · confidence: over-approximate · scope: predicted
10 exact, 1 over-approximate, 0 unknown
Reads
Path or name            Confidence  Source               Why
package.json            exact       api/package.json     manifest
../shared/src/greeting  exact       api/build.mjs:3      file-read · copyFileSync · outside the target directory
.mjs
build.mjs               exact       api/package.json:7   script-entry
! ../shared/src/greeting.mjs is outside api/. Declare it as a source input or a dependency, ...

Output shortened.

For each stage the section lists the files it is predicted to read, the paths it writes, the environment variable names it reads, the workspace targets it depends on, the tools it needs, and anything the analysis could not bound. Every line shows a confidence and a source (file:line).

The analysis only reads and parses files. It never runs project code, scripts, package managers or the network.

Usage​

oyzu build --plan api                 # analysis for every stage of the target
oyzu build --plan api --stage build   # one stage
oyzu build --plan api --why ../shared/src/greeting.mjs
oyzu build --plan api --unknown       # only unknown and over-approximate facts
oyzu build --plan api --facts         # raw facts, one table row per fact
oyzu build --plan api --no-analysis   # skip analysis; whole-target scope
oyzu build --plan api --json          # everything, including the full analysis record
oyzu build --check                    # apply the rule levels; runs nothing
FlagMeaning
--stage <name>Show one stage, for example build or test. Needs --plan.
--why <path>Say, for each stage, whether the path is an input and why. The path is relative to the target or to the repository root. Needs --plan.
--unknownShow only facts that are unknown or over-approximate. Needs --plan.
--factsAlso list every raw fact, grouped by kind. Needs --plan.
--no-analysisSkip the analysis. Every stage uses the whole target. Needs --plan.
--checkApply rule levels and exit non-zero on a blocking finding.

The answer to --why is one of:

AnswerMeaning
inputA fact names the path.
not-an-inputNo fact names it and nothing could cover it.
covered-by-boundNo fact names it, but the limit of an unknown fact covers it.
covered-only-by-fallbackNo fact names it, but an unknown fact with no limit widens the stage to the whole target.

--plan analyzes your working tree. A normal oyzu build analyzes the snapshot of the source it captured, before any action runs. Both give the same facts for the same files. When planning, Oyzu lists the tree from file names and sizes and opens only the files the analysis reads, so a large checkout costs a directory walk, not a read of every file.

Confidence​

ConfidenceMeaning
exactProven from literal text, for example copyFileSync("../shared/src/greeting.mjs", ...).
over-approximateA superset that contains the truth: a glob, several resolution candidates, a dynamic import with a known directory.
unknownNot pinned down: a computed require, a computed file path, a command the analysis does not model.

An unknown only ever widens the result. If it has a limit (a relative import that is missing, a test pattern that is not expanded, a command with no tool profile), it widens its stage only by that limit. If it has none, the stage falls back to the whole target. See bounded unknowns.

What it reads​

SourceWhat the analysis takes from it
package.json, lockfiles, .npmrcAncestor manifests, lockfiles, engines and packageManager tools, main, module, types, bin and exports entry points, files as outputs, and workspace:, file: and workspace-name dependencies
Workspacesworkspaces globs and pnpm-workspace.yaml members. A bare import of a member resolves to its exports or main.
Scriptsbuild, test and lint, with their pre and post hooks, using the script graph
tsconfigThe extends chain, include, exclude and files, paths aliases, references, and outDir and tsBuildInfoFile outputs
Importsimport, export ... from, require, literal import() and import x = require(), for relative, alias and workspace specifiers. Every resolution candidate is kept (all extensions, the TypeScript .js to .ts mapping, index files).
File accessfs read, write, copy, stat and readdir calls with constant paths, including path.join(__dirname, ...), import.meta.dirname, new URL(..., import.meta.url) and process.cwd(). Computed paths are unknown.
Environment variablesprocess.env.X, process.env["X"], import.meta.env.X and destructuring. Computed names and whole-object use are unknown.
Dynamic accessrequire(expr) and import(expr). A template with a literal directory prefix is limited to that directory (over-approximate). Anything else is unknown, and so is every child_process call.

Paths in facts are snapshot-relative with forward slashes, so results are the same on every checkout path and host. Only the build, test and lint stages are modeled.

Output​

Human output leads with the outcome, uses aligned tables and reads fine without color. With --json, oyzu build --plan adds an analysis object to its document:

FieldContents
analyzedFromworking-tree or captured-snapshot
snapshotDigestFor the working tree, a digest of paths, kinds and sizes. It does not change when a file's bytes change at the same size.

A normal oyzu build reports unknown facts and analysis failures only in the debug log (--log-level debug), with the file, line, construct and what it widens.

Diagnostic rules​

Rules read the facts and report problems that are only visible across files and targets. They are advisory by default. A finding never fails oyzu build --plan. It fails oyzu build --check or oyzu build only when you set its rule to enforce.

Warning (phantom-dependency): app:build imports `left-pad` at packages/app/build.mjs:2, but packages/app/package.json does not declare it; it resolves today only because package.json declares it and the package manager hoists it.
  Fix: add `left-pad` to the dependencies of packages/app/package.json.

With --json, each finding has rule, severity, message and facts, the ids of the facts behind it. Messages name variables, never values. Severity is warning for a violation and note when the rule could not decide. A finding that rests on an over-approximate fact says so.

RuleReports
phantom-dependencyA bare package import that the importing file's own package.json does not declare (any dependency section, its own name, or the matching @types package). When the import works only through hoisting, the message names the ancestor manifest that declares it.
escaping-referenceAn import, import glob, CSS reference or literal file read that leaves the target's directory, when the target has no workspace dependency on the package that holds the path.
undeclared-envA literal process.env.X or import.meta.env.X read for a name that no task environment of that stage sets and no environment file the stage reads defines. NODE_ENV, MODE, BASE_URL, DEV, PROD, SSR and CI are never reported. A computed name is a note.
public-env-secret-nameA variable inlined into browser output (VITE_, NEXT_PUBLIC_, PUBLIC_, NUXT_PUBLIC_) whose name has a SECRET, TOKEN, PASSWORD or PRIVATE segment. A bare KEY is not reported, so publishable keys are left alone.
exports-target-missingA main, module, types, bin or exports path that is neither in the source nor under anything the build is known to write. If the build's outputs are unknown, the finding is a note. Patterns containing * are not expanded.
output-outside-declaredA build script or source write to a path outside every output location the build is known to use (a compiler outDir, a framework output or generated directory, warm state). A target with no known output location is not judged.
config-unreadableA configuration file (framework config, tsconfig, manifest, environment file, test-runner config such as next/jest) the analysis could not read statically. Always a note. The stage falls back to the whole target.
script-wrapper-opaqueA script step the closed shell grammar cannot resolve, for example a redirection. Always a note.
lockfile-manifest-driftThe nearest lockfile no longer matches the target's package.json: a declared range differs from or is missing in the lockfile, or the locked version does not satisfy the range. The fix names the package manager's command (npm install --package-lock-only, pnpm install --lockfile-only, yarn install).
redundant-declarationA build.yaml inputs entry inside the target's own directory, which is always captured. An input outside the directory is never reported.

lockfile-manifest-drift reads package-lock.json or npm-shrinkwrap.json (version 2 or 3), pnpm-lock.yaml (version 5 to 9) and both Yarn lockfile formats. If a directory has several lockfiles, it uses the one packageManager names. It skips what it cannot judge: non-semver specs (tags, git, URLs, file:, link:, workspace:, catalog:, npm: aliases), prerelease locked versions, and packages under overrides, resolutions or pnpm overrides. It does not check transitive entries.

phantom-dependency compares manifests only. It cannot see installed node_modules, so it cannot confirm whether an import resolves through hoisting today. A file is judged against its nearest package.json.

escaping-reference ignores authored inputs, so a path you already list there is still reported.

Rule levels, suppressions and build --check​

Set a level for each rule in the oyzu.toml cascade (see configuration):

[analysis.rules]
phantom-dependency = "enforce"      # off | advisory (default) | enforce

[[analysis.suppress]]
rule = "escaping-reference"
path = "legacy/**"                  # optional glob over the finding's file
reason = "vendored fork, tracked in the migration plan"   # required
LevelMeaning
offThe rule's findings are dropped from --check and from build logs.
advisoryReported, never fails anything. This is the default for every rule.
enforceA blocking finding fails oyzu build --check and oyzu build.

A finding blocks only if its rule is enforce, it is a warning (never a note), and every fact it cites is exact. An enforced finding that rests on an over-approximate or unknown fact is reported as not blocking, with its confidence, and never fails a build. --check counts those so you can see how much enforcement is held back.

A suppression needs a rule and a non-empty reason. path is a project-relative glob over the file the finding cites first (* stays within a directory, ** crosses directories). Without path, the suppression covers every file. A suppressed finding does not fail and is listed under Suppressed. With --json its reason is in suppressedBy. A suppression that matches no finding is reported as a stale note and never fails a build. Suppression changes reporting only, never a stage input or cache key.

oyzu build --check​

oyzu build --check is static analysis only: it prepares, installs, downloads and executes nothing. It selects targets the way build --plan does (including --affected), and you cannot combine it with --plan or the analysis view flags.

Exit statusMeaning
0No blocking finding.
1At least one blocking finding, or the analysis could not complete (the error is shown, never a pass).
2Usage error.
✗ Check failed: 1 blocking finding in enforced rules

phantom-dependency · enforce
Blocking packages/app/build.mjs:2
  app:build imports `left-pad` at packages/app/build.mjs:2, but ...
  Fix: add `left-pad` to the dependencies of packages/app/package.json.

With --json, the build --plan --json document gains a check object:

FieldContents
outcomepassed or failed
countsblocking, advisory, nonBlocking, suppressed, staleSuppressions
findingsrule, level, severity, status, target, path, line, message, fix, confidence, and suppressedBy when suppressed
staleSuppressionsSuppressions that matched nothing

A normal oyzu build applies the same levels to the snapshot it captured (or, for native host builds, to the working tree) before any action runs. A blocking finding stops the build with the same file, line and fix, and the failed bundle records it. Advisory findings stay in the debug log. A native host build that enforces no rule skips the analysis.

Limits:

  • An unknown rule id, a level other than the three, an empty reason, an unknown suppression field or an invalid glob is a configuration error that names the valid ids.
  • analysis.rules and analysis.suppress are whole-value settings. The nearest scope that sets one replaces the lower ones instead of merging per rule. A managed policy can pin a value.
  • build --plan lists every finding and ignores levels and suppressions.
  • Per-rule severity overrides and expiring suppressions are not available.

Script graph​

Each stage script (build, test, lint, with pre<name> and post<name>) is read with a closed shell grammar and resolved into a graph whose leaves are tool invocations. Scripts are read, never run. Every script it visits is reported as an exact fact at its line in package.json, with its command, the tools and unknown constructs it ends in, the scripts it calls, and the chain that led to it (build > build:compile > compile).

ConstructHandling
&&, ||, ;, newline, |Every segment is analyzed, which is a superset of what runs. Comments, quotes and \ escapes are honored.
$VAR, ${VAR}A read of that variable, except inside single quotes or after \$.
NAME=value cmd, cross-env, env, npx, pnpx, time, commandStripped, and the real program is classified. Unknown flags of these wrappers are unknown.
dotenv [-e file] -- cmdThe env files are exact reads (default .env). -c cascades are unknown.
cd dirLater commands in the same script use that directory.
npm run, npm test, pnpm run, pnpm <script>, yarn <script>, node --runDelegation to the script of the same package, with hooks. --prefix, -C, --dir and --cwd select another package. --if-present tolerates a missing script. A missing script is unknown.
-- and trailing argumentsAppended to the last command of the delegated script.
npm run s -w <name>, --workspaces, pnpm -r, pnpm --filter, yarn workspace, yarn workspaces foreachFan out to the workspace members that define the script. A selector that matches nothing is unknown. A dependency or git-range selector selects every member, which is a superset.
npm-run-all, run-s, run-pScript names and name:* patterns. A pattern that matches nothing is unknown.
node, tscEntry files, preloads (--require, --import, --env-file), --test, directories and extensionless names resolved like Node. For tsc: -p, -b, project lists, files on the command line, and --outDir, --declarationDir, --tsBuildInfoFile and --outFile as writes. node -e, node -p and watch modes are unknown.
rimraf, del, rm, mkdir, touch, cp, copyfiles, mv, cat, echo, sleep, ...Known utilities. Deletes, creates and copies are writes (over-approximate), reads are reads, and echo-like commands have no effect. A glob or computed target of a write is unknown.
Tools with a framework profileRun through the profile when the command runs in the analyzed target's directory. In another workspace member it is unknown.
./script.sh, bash fileThe file is an exact read. Its body is not analyzed, so it is also unknown.
>, >>, <The command is still analyzed. Each target other than /dev/null is unknown.
Subshells, $(...), backticks, &, eval, unterminated quotes, other programsunknown.

Delegation deeper than 8 levels, or more than 256 script instances in a stage, stops with an unknown fact that names the chain. A cycle is an unknown fact that names the cycle. An unknown leaf widens only its own stage.

The generated build command for npm, pnpm and Yarn workspaces runs the member builds, checks their public entries and packs them as one operation. Native packing also reads each package's files selection, ignore rules and lifecycle inputs, so the analysis treats this command as an unbounded read of the target source and keeps the whole target for confinement and cache inputs. An authored root build script keeps its own analyzed bounds.

Not supported in scripts: if, for, while, case, functions, aliases, here-documents, glob expansion of shell arguments (an argument glob is unknown except for cp-like reads), concurrently, turbo, nx, lerna, bun and Yarn plug-and-play specifics. Arguments passed to a hook script and .npmrc settings that change scripts (script-shell, ignore-scripts) are not modeled.

This is the build stage of a project that uses run-s build:*:

Entry points, scripts and frameworks
Path or name   Confidence  Source           Why
prebuild       exact       package.json:7   npm run clean
build          exact       package.json:8   run-s build:*
build:assets   exact       package.json:9   build > build:assets · cross-env NODE_ENV=production node scripts/assets.mjs --minify
build:compile  exact       package.json:10  build > build:compile · npm run compile -- --pretty false
compile        exact       package.json:11  build > build:compile > compile · node scripts/stamp.mjs && tsc -p tsconfig.build.json
postbuild      exact       package.json:12  node scripts/report.mjs

The entries these scripts reach (scripts/assets.mjs, scripts/stamp.mjs, scripts/report.mjs) are listed as well. In the same project, --stage lint lists redirection to or from "lint.log" is not analyzed as an unknown fact.

TypeScript input sets​

tsc -p, tsc -b, project lists and a bare tsc (which searches upward for tsconfig.json; tsc -b looks only in its own directory) predict the compiler's own file list from:

  • The extends chain. This includes extends of a workspace-member package, read through the member's package.json. Any other package is unknown.
  • files, include and exclude. The default exclude applies only when none is set.
  • allowJs, and the priority between a.ts, a.d.ts and a.js.
  • references, with each referenced project's own set.
  • Build-info files for composite and incremental, as warm state.
  • The imports reached from those files, plus the package.json of every directory above each program file and of every workspace member an import resolves to.

Not predicted: extends of an installed package, types and typeRoots, lib files and anything under node_modules. Command-line compiler options other than -p, -b, the output flags and files are not applied to the file set. Oyzu does not run tsc --listFilesOnly to check its prediction.

Framework profiles​

A profile tells the analysis what a build tool reads and writes. It is used when a stage's script runs the tool's command. A value in your configuration beats the convention: an explicit Next.js distDir or Vite build.outDir replaces .next or dist. A value the analysis cannot read makes only the facts derived from it unknown.

Script configs (.js, .mjs, .cjs, .ts, .mts, .cts) are evaluated by a small built-in interpreter, never by running your code. It understands object and array literals, string concatenation, path helpers, __dirname, import.meta.dirname and import.meta.url, new URL(...), spread, top-level const, defineConfig(...) wrappers, and relative imports of other config files and JSON. Anything else (another call, a loop, a function parameter, a binding changed after its declaration) is unknown for that value only. process.env.X is recorded as an environment read with an unknown value. Very large or deeply nested configs also become unknown and the message names the limit.

Next route-handler GET default​

From Next 15, app-router GET route handlers are dynamic unless the file opts into static generation. Environment reads inside a handler that runs only at request time are not build inputs. The analysis decides this per build and per route file, and records its decision as next-get-handler-default with the Next version it used and where that version came from.

Reads inside POST, PUT, PATCH, DELETE and OPTIONS exports are always request-time. A handler defined in another module and re-exported is not recognized, so its reads stay exact. Partial prerendering is not modeled.

Environment files​

For the mode of the command (production for vite build and next build, test for Vitest, or the value of --mode), the candidate environment files are inputs whether they exist or not, because creating one changes the build.

ToolFiles read, lowest precedence first
Vite, Vitest.env, .env.local, .env.<mode>, .env.<mode>.local in envDir (default: the project root)
Next.js.env, .env.<mode>, .env.local, .env.<mode>.local (.env.local is skipped in mode test)
Nuxt.env at the root, then Vite's .env, .env.local, .env.production, .env.production.local in srcDir

Each file fact lists the variable names it defines. Values never enter facts. Names with a prefix the framework inlines into browser output (VITE_* or your envPrefix, NEXT_PUBLIC_*) are reported as public. A mode that is not a constant name, for example --mode $MODE, is unknown.

Per-stage narrowing​

Facts belong to the stage that needs them. The test stage lists the runner's test files and setup files, and the build stage does not. A test-only edit therefore leaves every build fact unchanged:

oyzu build --plan --why tests/extra.test.ts --stage build   # not-an-input
oyzu build --plan --why tests/extra.test.ts --stage test    # input

When the runner's configuration cannot be read statically (a computed test.include, a config built by next/jest), only the test stage falls back to the whole target. The build stage does not depend on test discovery and stays bounded.

Vitest's test action always keeps the whole target view. Oyzu's reporting adapter turns on native coverage, which can read source files that no test imports. Your Vitest coverage settings and thresholds still apply.

Where the analysis is used​

On the isolated (captured) executor path, the analysis narrows the cache key and the source each action can see, for analyzed node/package and node/app operations whose final command it models: build, test and the builder-owned stages below. See confined actions. --affected and the native host path do not use it. Rule findings fail a build only when you enforce them.

Builder-owned stages​

Five stages of a Node package run commands the builder chooses instead of a project script. --plan lists their reads under these stages (for example oyzu build --plan --stage package).

StageCommand
versionThe version stamp
prepareThe npm install
packagenpm pack
lint, format-checkThe default ESLint and Prettier checks, for a package without such scripts

The same analysis supplies contracts for plugin-planned operations. Oyzu matches the final native command to its model, so an operation named node-pack receives the npm pack reads and node-version receives the version-stamp reads. An authored replacement cannot inherit the original command's model. Unsupported commands and workspace operations retain their explicit whole-target reasons.

A README edit can reuse stages that do not read it. npm pack always includes README and license files, even with an explicit files list, so changing a packed README reruns packaging. Default ESLint and Prettier checks read test sources too; a test-only edit can rerun those checks as well as tests. Bare node --test keeps a root-directory read for recursive discovery, so even unread documentation can rerun that test stage. Selecting explicit test files permits the narrower file/import closure. Reuse also requires unchanged version, command and prepared-dependency identities. Inferred-version or whole-target projection changes can still rerun stages after an unread edit; a bounded read contract alone does not guarantee a hit.

  • Absent files are reads. A tool that looks for a file reads its absence. The version stamp probes npm-shrinkwrap.json, .npmrc and .npmignore. ESLint probes every eslint.config.* and .eslintrc* in and above the target. Prettier probes every configuration name and .editorconfig. Creating one changes the stage's cache key.
  • Whole-package reads. npm pack without files (or with a glob in it) reads the whole package directory. The quality checks read every JavaScript and TypeScript file below the target.
  • Implicit native install. If a package has a binding.gyp, gypfile is not false, and there is no install or preinstall script, npm defaults to node-gyp rebuild. The analysis treats this as an unbounded unknown, so preparation keeps the whole target. A postinstall script does not stop the native default.
  • Locked npm preparation. A single-root npm install needs a v2/v3 package-lock.json or npm-shrinkwrap.json inventory before its outputs can be bounded. This also applies to dependency-free packages. Without that inventory, preparation runs every time and has no reusable action result; adding a lock does not admit unmodeled lifecycle scripts or native install effects.
  • Not modeled. Workspace roots and members, pnpm and Yarn installs and packs, application package commands, Biome, legacy ESLint configuration, Prettier script configurations and plugins, install lifecycle scripts, dependency install scripts, and local, Git or URL dependencies. Each is unknown for its stage only, so that stage keeps the whole-target key and the others stay confined.

Limits​

  • Supported on Linux and Windows. macOS is not supported yet.
  • Profiles cover the tools in the table above. Other build tools, and commands or builders they do not model, are unknown.
  • package.json exports conditions, packages in node_modules, .d.ts lookups in @types and tool installations are not analyzed. A bare import of an installed package yields no read fact, only evidence for phantom-dependency.
  • Limits protect the analysis from hostile input: 1 MiB per file, 256 MiB and 20,000 files per snapshot, 400 open brackets (or an estimated 1,000 levels of nesting) per parse, and a 5,000-file import graph. A file that hits a limit makes its stage unknown and the message names the construct. The depth check over-estimates, so a very deep but legitimate file can lose precision.
  • Non-UTF-8 files are treated as opaque. Symlinks are never followed.
  • A specifier that differs from a file name only by case or Unicode normalization resolves to that file. Other lookups that miss only that way make the target unknown (case-variant-path).
  • A leading byte order mark in a file is ignored, and CRLF files report the same lines and columns as LF files.
  • The analysis is not a replacement for the tools themselves. A prediction is a superset, so a build may read fewer files than listed.

Checking predicted reads​

The Oyzu repository has a development script, tooling/measure-node-analysis.py, that compares predictions with what real builds read and checks that hiding every file a stage was not predicted to read changes nothing. It is not part of the oyzu CLI.

Vite application lint and format-check stages that load vite.config.* remain unbounded. The native Vite API executes that configuration and its imports, so these stages keep the whole-target source view and report the Vite config as the reason. The ordinary owned quality-worker read model does not apply to them.

For the captured-path reuse regression, developers can run python tooling/test-node-captured-reuse.py --cli <compiled-cli> --plugin-package <node-package.tar.gz> --workdir <new-directory>. It uses an isolated build with an admitted plugin archive, managed Node and the existing execution image. The default fixture selects its test file explicitly. It checks cold, unchanged, unpacked README, test-only and source edits, including cache explanations, delivered module contents and bundle inspection. Use --profile node/app for the application variant, or --test-discovery to keep bare node --test and verify its conservative README-triggered test rerun. Use --add-source to select a build script that copies the source tree, then check that adding a module reruns the build and delivers that module in the artifact. The following unchanged build must reuse every stage. The test requires the shared engine's narrow version and dependency identities; it does not qualify Windows and macOS.
