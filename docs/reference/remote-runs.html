Remote runs

CLI reference

Published from the canonical docs/reference/remote-runs.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Add --remote to oyzu build or oyzu run <task> to run the same command on a platform or standalone pool instead of your machine. The pool checks out the exact commit you pushed, runs the build with full checks or the selected task in isolation, and streams the output back. Oyzu follows the run to the end and exits with the remote exit code.

Note: Remote runs are experimental and have been run on Linux pools only. Everything else Oyzu does is local and works without an account.

git push
oyzu build --remote

Prerequisites​

  • A Git checkout whose HEAD is pushed to a github.com repository that the pool allows (or that is linked to a project in your platform account). git must be on PATH. The Actions flow can run without a checkout.

  • platform.url and platform.account in user, machine or administrator configuration. Project and local files can't set them, so a checkout can't send your credential somewhere else.

    oyzu config set --global platform.url https://platform.example.com
    oyzu config set --global platform.account payments

    In CI you can set OYZU_PLATFORM_URL and OYZU_PLATFORM_ACCOUNT instead.

  • A platform credential: an oyzu auth login session (used at a terminal, or when platform.authentication.provider is session) or a token in OYZU_PLATFORM_TOKEN. See which credential a command uses. Unattended runs with neither fail with REMOTE_UNAUTHENTICATED. Standalone pools can instead use network or workload, as below.

Standalone pools​

Pool workers execute builds with oyzu build --isolated --full and tasks with oyzu run --isolated <task>. Task runs select only the requested task, its prerequisites and hooks, using their existing builders' images and report contracts. They never fall back to a host task. See isolated task limitations.

A standalone pool serves the same runs API without a platform sign-in. Ask its operator for the URL, account and network access, then configure:

oyzu config set --global platform.url https://pool.example.com
oyzu config set --global platform.account example
oyzu config set --global platform.authentication.provider network
git push
oyzu build --remote

The network provider sends no authorization header. The pool authenticates you through its network access rules. HTTPS is required except on loopback. A rejected caller receives REMOTE_UNAUTHENTICATED; check access with the operator. The CLI never falls back to a local build. Standalone output downloads are not available; omit --download.

With a configured shared cache, only pool runs created by GitHub Actions main push jobs from commits may write it; PR, terminal and working-tree snapshot runs only read it.

Build local changes without pushing​

Use --worktree with a standalone pool to build the checkout as it is on disk:

oyzu build --remote --worktree
oyzu run app:test --remote --worktree

The CLI captures the Git repository root in a source manifest, uploads missing file contents, then submits the manifest and starts the run. HEAD may be unpushed and files may be changed or untracked. The manifest includes every tracked file, even when it matches an ignore rule, and untracked files that Git does not ignore (git ls-files -z --cached --others --exclude-standard). Deleted tracked files stay absent. .git is never uploaded. File permissions and nanosecond modification times are retained. The limit is 512 MiB of logical file contents and 200,000 entries, checked before uploading.

Repeated working-tree submissions send only missing file contents; unchanged files are not sent again.

The Remote submission phase reports the transfer, for example Uploaded 1 of 812 files (4.1 KiB). At most eight file blobs transfer at once. The CLI reuses its existing source stat cache for unchanged file digests and rehashes recently modified files. If pool cleanup removes a blob before the manifest is accepted, the CLI uploads the missing contents and retries once.

The transport carries regular files and relative symlinks whose targets stay inside the selected source tree. Outside, dangling and cyclic links are refused before upload. This does not extend the build engine's source-link support: snapshot builds apply the same source filtering and symlink refusals as local and commit builds. A link accepted by the upload may still be refused when the build captures its source.

Both remote modes run at the repository root. -C <directory> locates the Git checkout; it does not change the remote working directory. Select a subproject by its existing target name or qualified task name. --worktree requires --remote and cannot be combined with --plan.

Snapshot runs read shared caches when configured, never write them, and cannot be published. Their run and result include source.kind: snapshot, a source digest and, when available, the informational base commit. No files are downloaded to the caller. Servers without snapshot support reject the upload with REMOTE_SOURCE_KIND_UNSUPPORTED; the CLI does not create a commit-based run instead. Actions workload callers remain restricted to their signed commit and cannot submit snapshots to a standalone pool.

From GitHub Actions​

permissions:
  id-token: write
  contents: read
steps:
  - uses: oyzuai/setup-oyzu@v1
  - run: oyzu build --remote
    env:
      OYZU_PLATFORM_URL: https://pool.example.com
      OYZU_PLATFORM_ACCOUNT: example
      OYZU_PLATFORM_AUTH_PROVIDER: workload

The job must be able to reach the pool. workload requests a fresh Actions OIDC token for each API attempt, with the normalized pool URL as audience. Outside GitHub Actions it fails with AUTH_PROVIDER_UNAVAILABLE; see authentication.

Without a Git checkout, this provider reads GITHUB_REPOSITORY as an exact owner/repository, GITHUB_SHA as a full lowercase 40-character commit ID and GITHUB_REF as a full Git ref such as refs/heads/main or refs/pull/12/merge. Missing or invalid values fail with REMOTE_ACTIONS_SOURCE_INVALID before any token or run request. With a checkout, the normal pushed-HEAD checks still apply. --affected requires a checkout to compute its merge base. The pool validates the repository, commit and ref against the caller's identity.

An Actions job may check out source to bootstrap its own CLI, then invoke that CLI from an empty directory outside the checkout. This exercises the checkout-less submission path; it does not mean the job has no checkout step.

GitHub stage checks​

Commit builds on a standalone pool can report a separate GitHub check for each target and stage, named oyzu / <target> / <stage>. The pool's GitHub App needs Checks write permission on the repository. A repository maintainer can mark an individual stage check as required in branch protection; Oyzu does not change those settings. Working-tree snapshot runs do not post checks.

Each check starts while its stage runs and completes with that stage's result. JUnit failures from reports listed in the build manifest appear as file and line annotations when the report supplies a location; failures without a file appear in the check summary. Up to 200 failures are sent, with each message limited to 1 KiB. A stage that ends without a reported result fails its check, or is cancelled when the run is cancelled.

Repositories without an installation of the pool's GitHub App receive no checks. A GitHub API outage can delay or prevent check updates; it does not change the remote build's exit code.

Usage​

CommandRuns remotely
oyzu build --remoteEvery target.
oyzu build --remote --worktreeEvery target from local disk contents.
oyzu build cli web --remoteTargets cli and web, plus what they depend on.
oyzu build --affected origin/main --remoteTargets affected since the merge base of origin/main and HEAD.
oyzu run policy-check --remoteTask policy-check (target:task also works).
... --remote --download outThe same, then downloads every output into out/.

To see what a pool would run without starting anything, use oyzu build --remote --plan; see planning a remote run.

Oyzu sends the repository from the current branch's remote (or origin), the full HEAD commit and the branch. For --affected it sends the merge-base commit, not a local ref name. Without --worktree, uncommitted changes aren't part of the run; you get a warning.

Output​

The terminal view looks like a local build. Each streamed log line is attributed to the target or task that wrote it, and the pool's own lines (checkout, start, finish) appear under runner. At the end you get a summary:

✓ Remote build succeeded
  Run       01jab7v3k9m2q8r4t6w0y1z5c7
  Commit    3f2a9c1d4b5e (main)
  Project   oyzu/platform
  Oyzu      0.9.0

  Outputs
    manifest dist/manifest.json   4.0 KiB  sha256:aaaaaaaaaaaa
    report   dist/cli/linux/x86_64/reports/junit.xml   2.0 KiB  sha256:bbbbbbbbbbbb

  Use --download <DIR> to fetch outputs; nothing was written locally.

With --json, standard error carries the same events a local build emits, and standard output carries one remote-run record:

FieldMeaning
invocationIdThis invocation.
submissionWhat was sent: repository, commit and selection.
runThe final run resource.
resultState, exit code, reason and outputs. resultAvailable says whether the full result was fetched.
downloadsEach downloaded path, digest and local file.
observationThe last seen run state, time and log position, and any known log gaps.
cancelledThis invocation asked for cancellation. It doesn't mean the run stopped.
cancellationrequested, acknowledged and confirmed, as separate facts.

If Oyzu loses track of a run after creating it, the outcome is unknown, with the last state it saw. That doesn't mean the run failed, and Oyzu never starts local work instead. Check the run in the platform (using the web link, if one was shown) before starting another.

Exit status​

Remote outcomeExit code
Succeeded0
Oyzu exited non-zero on the poolThat exit code
Failed before Oyzu ran, skipped, cancelled, timed out, or unknown1
Refused before or while creating the run (configuration, Git or platform problem)1
Interrupted with Ctrl-C130

Cancellation​

  • The first Ctrl-C asks the platform to cancel and keeps following the log while the pool stops the work. cancellation.confirmed is set once the run reports cancelled.
  • A second Ctrl-C exits at once with 130.
  • There's no confirmation prompt, so it behaves the same in CI. Cancelling a run that just finished is harmless; you see its real outcome.
  • Closing the terminal (SIGHUP) doesn't cancel. It stops only the local follower; the run continues on the pool.

Outputs​

Outputs are listed by digest and never written into dist/. With --download <DIR>, Oyzu fetches each one through a short-lived download link (no platform credential is sent to it), checks its SHA-256 digest and writes it at its recorded path under DIR. A path that would land outside DIR is refused.

Outputs are the manifest, artifacts and required reports. They aren't a complete local build bundle, so oyzu inspect can't check them as one.

If the platform can't verify the work a pool sent back, the run fails with CONTRIBUTION_UNVERIFIED and no outputs, even if the native build succeeded. Check the run's diagnostics before retrying.

Errors and recovery​

A refused remote run never falls back to a local build. Platform errors keep the platform's code with a REMOTE_ prefix, plus the platform request id.

CodeCauseFix
REMOTE_NOT_CONFIGUREDplatform.url or platform.account is missing or set in the wrong scope.Set them at user scope.
REMOTE_NOT_A_CHECKOUTNot a Git checkout.Run from a checkout.
REMOTE_REPOSITORY_UNSUPPORTEDThe remote isn't on github.com.Only github.com is supported.
REMOTE_COMMIT_NOT_PUSHEDHEAD isn't on any branch of the remote.Push first.
REMOTE_SOURCE_INVALIDA snapshot contains an unsupported path, file type or outside link.Keep source files and relative links inside the checkout.
REMOTE_SOURCE_TOO_LARGEThe snapshot exceeds 512 MiB.Ignore untracked generated files, and stop tracking generated files that should not be uploaded.
REMOTE_SOURCE_KIND_UNSUPPORTEDThe server does not accept snapshots.Use a snapshot-capable standalone pool or push and omit --worktree.
REMOTE_AFFECTED_BASE_INVALIDThe --affected ref can't be resolved.Fetch the ref or pick another.
REMOTE_UNAUTHENTICATEDNo credential, or it was refused.Run oyzu auth login, or set a current token.
REMOTE_REPOSITORY_NOT_LINKEDThe repository isn't linked to a project.Link it in the platform.
REMOTE_COMMIT_NOT_FOUNDThe platform can't see the commit.Push first.
REMOTE_VALIDATION_FAILEDThe platform rejected the request.Correct the named field.
REMOTE_RESPONSE_INVALIDThe run result is missing output details.Check CLI and platform compatibility. The run isn't restarted.
CONTRIBUTION_UNVERIFIEDSee Outputs.Check the run's diagnostics.

Requests that fail on the network or get a 503 are retried up to five times with backoff, honoring Retry-After. Retried creation uses the same idempotency key, so it never starts a second run. Logs are followed with 30-second long polls over plain HTTPS, which works through proxies (HTTPS_PROXY, NO_PROXY, SSL_CERT_FILE) with outbound access alone.

Security​

  • The credential is sent only to platform.url. platform.url must use HTTPS; plain HTTP is accepted only for a loopback host.
  • Never put a token in command arguments, copy a browser session, or give a coding agent your personal token.
  • Run ids and digests from the platform are checked before they're used in a URL or file name. Streamed log text is escaped before it reaches your terminal.

Limitations​

  • Only GitHub repositories on github.com.
  • Task arguments (-- args) aren't supported remotely.
  • There's no --detach, no way to list runs and no way to reattach to a run.
  • Tested on Linux pools only.

Private files in isolated native actions​

A platform executor can hand private files, such as a signing key, to the native actions of a remote run. You don't configure this in your project, and ordinary local builds don't use it. The runtime-input contract describes the details.

  • Files are mounted read-only at /oyzu-runtime, and an environment variable points to each file only while the action runs. The project can't name host files.
  • The files never affect source, plans or cache keys. Affected targets skip the action cache so tests always see the current files.
  • Where the executor provides an egress gateway, an HTTP client that can use a Unix socket can reach it through OYZU_HTTP_PROXY_SOCKET. Direct TCP networking stays off.
  • Supported for Unix process actions on Linux x86-64 in Docker. Anything that doesn't match (unsupported host, missing or unsafe files, conflicting variables) is refused. Fix it and submit a new job.
  • Removing the files afterward is cleanup, not secure erasure.
