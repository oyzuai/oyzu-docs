Remote runs

CLI reference

Published from the canonical docs/reference/remote-runs.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Status: experimental client. oyzu build --remote and oyzu run <task> --remote implement the CLI side of the draft remote runs contract (design page). Client checks use a scripted local server and the contract mock. The bounded connected Linux build flow also has recorded qualification; broader host/service support remains incomplete. Sign-in is the experimental oyzu auth, verified only against a local conformance fake.

Purpose​

--remote runs the same invocation on a platform pool instead of this machine: the pool checks out the exact pushed commit, runs oyzu build or oyzu run <task> there with full checks in isolation, and streams the output back. The CLI follows it to the end and exits with the remote exit code. Everything else Oyzu does stays local and works without an account; --remote is the optional platform path.

Prerequisites​

  • A Git checkout whose HEAD is pushed to a github.com repository linked to a project in your platform account. git must be on PATH.

  • platform.url and platform.account in user/global, machine or administrative configuration. Project/local scope is rejected with a diagnostic naming the key:

    oyzu config set --global platform.url https://platform.example.com
    oyzu config set --global platform.account payments

    CI can supply OYZU_PLATFORM_URL and OYZU_PLATFORM_ACCOUNT through the configuration contract. These invocation sources override ordinary files and remain subject to administrative constraints. A checkout cannot redirect a developer's platform credential, even when its environment is trusted.

  • A platform credential from the shared credential provider: the session stored by oyzu auth login (used when you run from a terminal or select it with platform.authentication.provider), or a bearer supplied in OYZU_PLATFORM_TOKEN (never stored or refreshed; it is a credential, so it is read from the environment and never from a configuration file). Unattended runs with neither fail with REMOTE_UNAUTHENTICATED instead of looking for a developer's session.

Usage​

CommandRuns remotely
oyzu build --remoteEvery target
oyzu build cli web --remoteTargets cli and web (and what they depend on)
oyzu build --affected origin/main --remoteTargets affected since the merge base of origin/main and HEAD
oyzu run policy-check --remoteTask policy-check (target:task also works)
… --remote --download outThe same, then downloads every output into out/

oyzu build --remote --plan previews a remote build locally without creating a run; see planning a remote run.

The CLI resolves the repository from the current branch's remote (else origin), the full HEAD commit and the checked-out branch ref. For --affected it sends the full merge-base commit, never a local ref name.

Output​

Text mode uses the same linear view as a local build. Each log line the pool streams is attributed to the target or task that wrote it (scope in the contract), so task starts, native output and task results look like local ones. The runner's own lines (checkout, start, finish) appear under runner. The receipt on stdout leads with the outcome, then the run id, commit, project, Oyzu version, portal link when there is one, and the outputs the run produced:

✓ Remote build succeeded
  Run       01jab7v3k9m2q8r4t6w0y1z5c7
  Commit    3f2a9c1d4b5e (main)
  Project   oyzu/platform
  Oyzu      0.9.0

  Outputs
    manifest dist/manifest.json   4.0 KiB  sha256:aaaaaaaaaaaa
    report   dist/cli/linux/x86_64/reports/junit.xml   2.0 KiB  sha256:bbbbbbbbbbbb

  Use --download <DIR> to fetch outputs; nothing was written locally.

With --json, stderr carries the same structured events a local build emits (output events keep the remote scope as operationId) and stdout carries one remote-run record: run (the final run resource), result (state, exit code, reason and outputs), downloads (path, digest, local file) and cancelled.

The record also contains invocationId, the exact submission body (repository, commit and selection), observation and a cancellation object. After a run has been created, failure to follow or retrieve its result produces an unknown outcome with the last observed run state/time and log position; it does not assert failed remote execution or start local work. The last run-resource state can predate subsequent scoped task log events. Known log gaps remain explicit in the result even after a connection recovers. Complete observation means the client received terminal records, not that every log entry or required artifact transfer is complete.

Bounded retry notices describe observation loss and recovery. Submission, observation and requested artifact transfer are distinct phases. The current public contract supplies queued/running/final states and scoped task lifecycles; worker identity, assignment and detailed worker preparation/transfer telemetry are unavailable and are not inferred from illustrative studies.

Exit status​

Remote outcomeExit code
Succeeded0
Oyzu exited non-zero on the poolThat exit code
Failed before Oyzu ran, skipped, cancelled, timed out, or an unknown state1
Refused before or while creating the run (configuration, Git, platform problem)2
Interrupted with Ctrl-C130

An unknown remote outcome after submission exits non-zero (1); an interrupt retains exit 130. Use the supplied Web link, or check the run ID with the platform operator when no link was supplied, before starting a replacement run. Reattachment and CLI retrieval of a previous remote run are not implemented.

Cancellation​

The first Ctrl-C asks the platform to cancel the run and keeps following its log while the pool stops it; a second Ctrl-C exits at once with 130. The observer keeps following beyond the local cleanup grace period so it can retain the execution owner's confirmed outcome. Cancelling is retry-safe, so a cancel that races the run's own finish is harmless. There is no confirmation prompt, so cancelling works the same in CI.

Closing the terminal (SIGHUP) is not a cancellation: it ends only the local follower, and the remote run continues on the pool.

cancelled records that this invocation requested cancellation. It is not confirmation that execution stopped. cancellation.requested, acknowledged and confirmed expose separate facts; confirmation follows a terminal cancelled result. A finished-run conflict is followed to its actual outcome. The receipt preserves pending or unknown cancellation and any known log gaps.

Assigned native workers use the same cooperative interruption lifetime as a local captured build. A running cancellation acknowledgement requires the execution owner's normal process wait and fresh finalized native build record; revoking a lease or receiving a success response alone is insufficient. Forced or unconfirmed stops remain explicit failures. The real Linux service/worker proof passed cancellation during the shared native action: the observer retained all three cancellation facts and exited 130 after confirmed cleanup. A second real run preserved an already accepted shared contribution while stopping API and preventing the final bundle from starting; see the distributed qualification record. resultAvailable distinguishes a fetched result from a partial observation. When the final run resource is already confirmed, losing access to its result retains that execution outcome and identifies unavailable metadata/outputs. The invocation still fails if requested observation cannot complete. Last-observed timestamps advance on actual responses; elapsed waiting is not execution progress.

Outputs​

Outputs are listed by digest and never written into dist/. --download <DIR> fetches each one through the platform's short-lived download link, which receives no platform credential, verifies its SHA-256 digest before writing, and writes it at its recorded path under DIR. A path that would leave DIR is refused.

For accepted native split builds, these are the manifest, artifacts and required reports. The output projection excludes the private admitted plan, execution envelope and logs; it is not a complete local build bundle for oyzu inspect. The existing run log view retains remote observation separately. Native contribution validation precedes final platform success; downloaded file digests are checked again by the client.

Reported native success does not guarantee platform acceptance. If the complete transferred contribution cannot be verified, the run fails with CONTRIBUTION_UNVERIFIED and no accepted outputs. This does not turn successful native actions into failed tests or grant permission to replay their commands. Inspect the run's diagnostic and retained native evidence before retrying.

The result must contain an outputs array, including an empty array when there are no outputs. Every output supplies its kind (manifest, report or artifact), media type, nonnegative size, path and digest. A missing or malformed array or missing output metadata fails with REMOTE_RESPONSE_INVALID before downloads start, in human and JSON modes, even when the platform reports that the run succeeded. Check the platform's result and client compatibility; the remote run itself is not restarted.

Errors and recovery​

Refusals never fall back to a local build. Platform problems keep their stable code with a REMOTE_ prefix and the platform request id, for example REMOTE_UNAUTHENTICATED (set a current token), REMOTE_REPOSITORY_NOT_LINKED, REMOTE_COMMIT_NOT_FOUND (push first) and REMOTE_VALIDATION_FAILED. Local checks fail before any request: REMOTE_NOT_CONFIGURED, REMOTE_NOT_A_CHECKOUT, REMOTE_REPOSITORY_UNSUPPORTED (not github.com), REMOTE_COMMIT_NOT_PUSHED (HEAD is on no branch of the remote) and REMOTE_AFFECTED_BASE_INVALID. Uncommitted changes produce a warning: they are not part of the run.

Requests that fail in transport or answer 503 are retried up to five times with backoff, honoring Retry-After. Creation is retried under the same Idempotency-Key, so a retry never starts a second run. Logs are followed with 30-second long polls over plain HTTPS and resume from the last cursor, so the client works through proxies (HTTPS_PROXY, NO_PROXY, SSL_CERT_FILE) with outbound access alone.

Security​

Supply only a credential intended for this client, account and operation through the supported authentication setup. The environment input is a transport, not proof of how a token was issued or its allowed actions. It does not provide token creation, refresh or a safe way to share a person's session with an agent. Never copy a browser session token or put a bearer value in command arguments.

The token is sent only to platform.url as a bearer credential. platform.url must be HTTPS; plain HTTP is accepted only for a loopback host, for local development against a mock. Run ids and digests from the platform are validated before they are used in a URL or a file name, and log text is escaped before it reaches the terminal like local child output.

Limitations​

The #479 implementation candidate connects internal admitted native preparation and assigned-plan verification separately from public read-only preview. This has passed the connected real-service flow on Linux, including distinct API/Web workers, an independent whole-build artifact/report comparison, cancellation, retained-byte upload retry, safe worker replacement, coupled prerequisites and required output/report/contribution refusals without implicit replay. The agreed finite cases and exact qualification limits are recorded in distributed build completion.

  • No interactive login; the token comes from OYZU_PLATFORM_TOKEN.
  • GitHub repositories on github.com only, matching the contract's github provider.
  • Task arguments (-- args) are not supported remotely.
  • --detach, listing runs and re-attaching to a run are not implemented.
  • Broader platform/host qualification remains incomplete; see the linked distributed qualification record and RUNS-08/RUNS-09 in the design page.

Verification​

  • oyzu exec -- cargo test --locked --test integration remote_runs: the compiled CLI against a scripted server for a successful build with scoped log replay and verified download, a failing task's exit code and JSON event stream, an expired token and an unpushed HEAD.
  • python tooling/check-runs-contract.py: the contract and its mock, including scoped log entries.
  • python tooling/test-remote-cli.py --cli <compiled-oyzu>: the compiled CLI against the contract mock end to end.
