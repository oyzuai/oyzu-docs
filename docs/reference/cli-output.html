CLI output

CLI reference

Published from the canonical docs/reference/cli-output.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Every public command defaults to readable text for people and accepts the global --json flag for machine-readable output. This page describes what each kind of output looks like, which flags and environment variables control it, and what scripts can rely on.

Output selection never changes policy, configuration, lock contents or exit codes. DEC-033 and AGENTS.md record this product rule.

The CLI design guide is the draft shared standard for mission, guardrails, state meanings, large-repository presentation and review criteria. This reference describes current interfaces, including bounded retained build history. Other target experiences in the guide require their own implementation evidence.

Output controls at a glance​

-v, -vvDebug and trace diagnostics; deeper detail in build output.
-q, --quietWarn threshold; hides routine progress, keeps results, warnings and errors.
--log-level error|warn|info|debug|traceExplicit threshold. See Diagnostic controls.
OYZU_LOGPer-target log directives.
NO_COLORDisables color.
CLICOLOR_FORCEForces color (nonzero value); NO_COLOR overrides forcing.

Command help​

Run oyzu or oyzu --help for a workflow-oriented overview. Its groups are Develop & build, Project tools, Environment & configuration, Platform and Diagnostics, with common examples.

  • oyzu <command> --help or oyzu help <command> shows command-specific arguments and options, including nested commands such as oyzu config set --help.
  • Help works offline without a project, installed tool selection or platform account. Hidden shell hooks stay out of the public command list.
  • Bare oyzu exits successfully and uses the same stdout, color controls and static startup path as oyzu --help; neither opens project configuration or initializes a runtime.
  • Use oyzu --json --help for the overview in a JSON envelope.
  • The help masthead uses the compact lowercase oyzu. wordmark. Terminals choose their own fonts; no Segoe UI or point-size claim is made for terminal output.

Help color​

  • Help uses cyan headings, green command/option names and yellow placeholders on color-capable terminals. Redirected help is plain text by default.
  • Set NO_COLOR=1 to disable help color or CLICOLOR_FORCE=1 to request it explicitly (avoid setting both). These are clap's help-rendering controls; project ui.color does not apply because help runs before project configuration is loaded.
  • JSON help always contains unstyled text.
  • The layout and palette use the same CLI implementation on Windows, macOS and Linux; native verification is recorded in the implementation status.
  • This design draws on GitHub CLI's command groups, uv's help navigation and the CLI Guidelines' restrained color guidance. No upstream source or new dependencies are included.

Shim refresh and shell profiles​

oyzu reshim appears under Project tools and refreshes the fixed shim folder and existing activation launchers owned by this frontend. Human output reports the shims folder and recorded commands; --json returns directory and commands. See shim refresh for store selection, Windows prerequisites and recovery. shell groups startup profile install and remove; shim refresh has no nested spelling or alias.

Build identity​

oyzu --version identifies the compiled local build, for example:

oyzu 0.1.0-local.8aee8560a0ca.dirty (debug; x86_64-pc-windows-gnu; build 1791211857)

The suffix records:

  • the abbreviated source commit;
  • whether the worktree was dirty when compilation captured its identity;
  • Cargo profile and target triple;
  • the build Unix timestamp (seconds since the UTC epoch). SOURCE_DATE_EPOCH overrides that timestamp at compilation for reproducible inputs.

Without Git metadata, source identity is explicitly unknown.source-unknown.

  • This is diagnostic identity, not a release version, source attestation or production eligibility claim.
  • All current builds are labelled local, including optimized release-profile builds (oyzu build --optimized); optimized never implies a release or publication eligibility.
  • Identity is embedded at compile time. Version/help never opens project configuration, starts a worker, runs Git or contacts a service.
  • --version --json uses the existing structured output/exit-code envelope.

Which executable is running​

A pull changes source; it does not replace an installed executable. oyzu --version reports the identity compiled into the selected executable.

  • Use command -v oyzu in POSIX shells or Get-Command oyzu -All in PowerShell to inspect command routing.
  • Compare it with the project-local binary directly:
./.oyzu/bin/oyzu --version
./.oyzu/bin/oyzu build --output plain

On Windows use .\.oyzu\bin\oyzu.exe.

  • oyzu build publishes collected artifacts under dist and promotes executable artifacts into the current project's .oyzu/bin only after a successful native build. Failed builds retain the previous binaries.
  • A direct Cargo compilation through oyzu exec writes Cargo's target output and does not perform that promotion.
  • Do not assume target/debug/oyzu identifies the executable selected by your shell.

The repository bootstrap reuses an existing executable; it is not an update command.

  • Activation can prepend the configured project-local .oyzu/bin to PATH; ordinary shell-wrapper commands select the application on PATH, while lifecycle hooks retain the bootstrap frontend.
  • Preserve this architecture when updating: verify the successful build's artifact, promoted binary and selected version before changing any installation.
  • No global bootstrap replacement is required for a project-local build.
  • Native Windows routing qualification is recorded separately from cross-platform source/tests.

Result output​

Discovered build facts​

Ordinary builds show Facts after preparation and before Selection, Plan and the corresponding actions. No extra flag, builder setting, login or network access is needed. The shared view reads existing frozen plan records; it does not rerun discovery or query source-control APIs.

FactMeaning and limits
Branch / CommitLocal branch observation and commits recorded by version history/decisions; different target commits keep their attribution. They do not attest that Git HEAD equals the captured input tree.
Git stateExplicitly not verified. Existing source records use conservative dirty/commit placeholders; display does not interpret those as a clean/dirty Git observation.
Source digestContent identity of admitted build inputs. Ordinary output abbreviates hashes; -v and structured evidence retain full values.
Version / BasisEach target/package's planned version and recorded reason. Identical versions/bases within a target are grouped (package count normally, names with -v); differing package versions stay separate. Artifact intent versions are a fallback when decisions are absent, with the missing basis stated. Distinct native artifact coordinates remain visible in an Artifact row even when logical version decisions exist.
KindRecorded version intent, currently snapshots; a release context does not establish release classification.
ContextEffective local/PR/CI/release context with its detection or override source.
Protectionunknown · not queried; display adds no provider API discovery.
ReleaseRecorded production ineligibility and its target scope, or explicit unknown where decisions are missing. Version facts never authorize publication.
  • Captured independent targets may execute while others are preparing. Each newly prepared plan shows new/changed facts before its actions; unchanged rows are not repeated.
  • Hook-dependent versions say pending post-hook finalization; the existing post-hook event displays the final version under Build. Initial facts describe the initial plan; final bundle records describe produced artifacts.
  • Quiet builds suppress this routine section.
  • JSON contains no human heading: the allowlisted buildFacts field of each plan event carries structured inputs, alongside context fact events and bundle records. Environments, credentials and arbitrary extensions are excluded.
  • Terminal controls are escaped; narrow text uses labelled records and hanging indents.
  • Git/protection uncertainty does not change exit status, action/cache identity or release rules.

Build transcript​

Default builds use compact linear progress, preceded by one plan table (targets by stages, or platforms by stages for a single target) shown before work starts. The dashboard remains an explicit option.

  • The old linear preparation/context/stage tables and the per-stage Skipped lines are removed.
  • Routine successes and accepted per-action test details collapse. -v, planning, inspection, history and JSON retain deeper detail.
  • A build prints named sections in a fixed order and omits any that has nothing to say.
  • Every row, the title and the section rules share one width (80 columns, or less on a narrower terminal).
SectionWhat it shows
Title lineProject name and, right-aligned, the facts listed under Title line.
── Prepare ──One row per preparation step, then the pinned tools.
── Selection ──Plugin builder selection, and why the build is not every declared target.
── Plan ──A table of targets by stages, with reason lines.
── Build ──One row per finished action.
── Failure: <target> · <stage> ──The native cause of a failed action.
── Outputs ──Artifacts with sizes and build profile.
── Warnings (N) ──Each distinct warning once, with its owner.
SummaryThe outcome and counts, then a dim Details line.

Title line​

The title line names the project and, right-aligned:

  • the host platform;
  • local or the CI provider;
  • the build context value only (context pr, context local). The deciding signal or pin is shown in Facts and by config explain context, see Build context;
  • fast or full, followed by optimized or development when --optimized or --no-optimized asks for one.

The CI provider label alone nearly fills 80 columns, so under a CI provider the subtitle may continue on the line below the project. A pin that a CI provider marker forbids lowering prints a CONTEXT_OVERRIDE_IGNORED warning.

Prepare​

── Prepare ── lists every preparation step as a row: mark, name, detail, duration, and the warning count of the work that raised them.

  • The Tools row summarizes the pinned tools (2 tools pinned · 0 installed now) and lists each beneath it with its version, already installed or installed now, and the detected requirement that needs it (or pinned in oyzu.toml), followed by detected toolchain components and host prerequisites of the selected targets.
  • With several targets the block prints once, when Prepare closes, listing each tool once. A tool whose reason differs between targets shows each reason (detected from …; pinned in … · not detected for <target>).
  • When another build holds the workspace, a Build lock row waits for it (waiting for pid N, started Ns ago) before any other preparation instead of failing; Ctrl-C stops the wait.
  • Routine housekeeping that finishes after Prepare closes (end-of-build cache retention) is shown only when slow, failed or warned, or with -v.

Attention rows. Best-effort detection adds attention rows (yellow !) beneath the tools. They warn and never fail the build; tools.ignore silences a detection, visible only with -v.

RowMeaning
! protoc needed by prost-build · no catalog entry; pin or provide itAn unknown tool. A detected tool that Oyzu can manage, pinned or not, is an ordinary detected from Cargo.lock row that resolves, locks and installs.
! protoc needed by prost-build in Cargo.lock · no usable checksum; pin it in oyzu.toml or silence it with tools.ignoreA detected tool that could not be resolved or installed; the build continues, only an explicit pin fails.
host prerequisite … · not found on PATHA host prerequisite is missing.
fetches <what> outside the lock (<file>)The build fetches something outside the lock.
detection failed: <reason> · nothing extra detectedDetection could not run.

Rules and patterns: build tool scope.

Live and redirected progress​

  • In an interactive terminal, work in progress shows under its section heading as one line per step or action with an animated spinner, redrawn several times a second. Long status is shortened with … rather than wrapped.
  • Redirected and CI output never redraws. Each action prints a start line (.. target stage started) and an end line with its outcome and duration, both led by the elapsed mm:ss. The ten-second heartbeat names what is still running, for example still running: api build 10s · auth-lib test 12s · 6 waiting.
  • Redirected output is rendered at 100 columns on every host. Failure text wraps instead of exceeding it, Windows extended-length (\\?\) prefixes are not shown, and a long log path keeps its tail.
  • In a narrow terminal or without color every table falls back to records and nothing is dropped.
  • On a terminal the live pane shows ○ <target> · <stage> waits for <target> · <stage> for queued actions with unfinished prerequisites (at most three, then + N more waiting) and an N of M finished line.
  • Interrupted, --plan and --check builds keep their existing receipts.

Selection​

── Selection ── prints when a target is built by a plugin and when the build is not every declared target.

  • Plugin-built target: its builder selection: the full record with remedies when the build adopted or installed one, otherwise one line per target; see plugin catalog.
  • --affected: shows what it was compared with (compared with origin/main at 0123456), the changed targets and changed paths, their dependents and the unaffected count.
  • Conservative fallback: shows ! Not narrowed with its reason, the recorded code and a fix only when one is known.
  • Explicit request: shows requested and required (prerequisites pulled in).

Plan​

── Plan ── then prints once. Rows are targets; columns are the stages the builders declare, in the order format, lint, test, build, package and then any other stage.

CellMeaning
runSelected.
skipThe builder has the stage but this build does not run it (for example a fast local build), or it is not available.
offA check level of off: never run and its tools not prepared.
-The builder declares no such stage.

Below the table, after a blank line, one dim line per distinct reason names the stages it covers:

LabelWhat the line says
offWhere the check was turned off (format · disabled in oyzu.toml, test · disabled in oyzu.toml [context.pr]).
skippedWhy stages were skipped (lint and test · fast local build).
advisoryRun stages whose failure is only a warning (lint · failures are warnings; the build still succeeds).
profileOne line per distinct build profile, naming its targets with the profile and why (cli · optimized · --optimized, cli and docs · development · local dist only, cli · optimized · release builds are published).
policyOne line per distinct policy override: the setting (a check reads as its name), the value policy made effective and why (format enforce · admin policy minimum in pr, release (project oyzu.toml sets off)), prefixed with the targets it applies to when not every target shares it.
projectOverrides by the root oyzu.toml's project constraints, in the same form (tests required · project constraint minimum in release (project app/oyzu.toml sets advisory)).
loweredIn a release build, each check a nearer folder lowered below a farther [context.release] value (tests advisory · app/oyzu.toml:2 lowers required from oyzu.toml:5 [context.release]).
taskOne line per conditional task or hook, prefixed with its target when the plan has several: whether it runs (and for which artifacts) or why it was skipped (pre_build · skip · unless context = local, post_build · run for bin-oyzu · unless artifact = bin-oyzu-shim). A per-artifact run's Build row names its artifact (post_build[bin-oyzu]).
noteTable notes, so none reads as a table row.

oyzu build --plan prints the same task lines as Task: lines under each target.

Large and multi-platform plans

  • A single target built for several platforms (--all-platforms) pivots to one row per platform and says 1 target · N platforms.
  • Above twelve rows, targets with identical stages share a counted row (29 targets) and a note line says so. A narrowed build's trailer reads N of M targets, and an affected build adds a why column (changed, uses <target>). -v lists every target.
  • When the table would not fit the terminal width each row becomes a record (cli build run · package -, then its skipped stages on the next line) so no value is lost.
  • When a build routes a platform off the host, or a target declares platforms this run does not build, every row names its platform (hello · linux/arm64) and a built by column names the executor (host, cross toolchain (rust-lld)); when it does not fit, a built by footnote carries it instead.
  • An other footnote lists declared platforms this machine could build with --platform and a not here footnote lists the rest with the reason (darwin/arm64 · needs a macOS runner (Apple SDK and linker)). A host-only build keeps the plain table. See platforms and executors.
  • The table renders the planner's recorded stage, check-selection and platform routing facts and does not recompute them.
  • The read-only --plan preview adds a Platforms · how each is built here table (target, platform, what builds it here, the CI runner it needs, and the reason).

Grouping by directory. When the selected targets live in more than one top-level directory below the project root (./ for targets at the root):

  • the plan table groups its rows under a dim services/ heading;
  • a prerequisite in another directory shows in a final needs column when it fits;
  • Outputs are listed under their directory;
  • the summary gains one line per directory (services/ ✓ 2 targets 58.1s, where the time is the sum of that directory's action durations);
  • identical-stage grouping above twelve rows applies within each directory.

A build in a single directory is unchanged.

Build​

── Build ── has one row per finished action: mark, target, stage, the command shortened with … to fit the width, executed or reused, and its duration.

  • In a build of more than twelve actions, clean successes fold into one ✓ 91 finished · 78 reused · 13 executed tally (-v lists every action). Running, warned, waiting, blocked and failed actions keep their rows, and the Build heading says 143 actions.
  • A failed advisory check is shown once, as a warning: its Build row reads warn … failed · advisory, it gets no Failure block, Warnings holds one CHECK_ADVISORY entry with the action, exit code and native cause, and the summary counts it apart from failures (1 advisory failed). The build still succeeds.

Failure​

A failed action's Build row reads ✗ … failed <duration> (FAIL without color).

  • After Build, a ── Failure: <target> · <stage> ── section shows the native cause (line breaks kept, terminal controls escaped, the first error context or the last lines written), the exit code, Log with the retained log path, and Next oyzu build <target> re-run only this target.
  • Actions that did not run because a prerequisite failed are blocked (⊘), counted apart from failed. A blocked row says needs <target> · <stage>; only the first three get a row and the rest become + N more blocked · -v lists them.
  • The summary counts only non-zero outcomes (✗ Build failed 1 failed · 12 blocked · 130 succeeded · 4m 02s) and is followed by Details and, for a host build, the note that local binaries were not updated.
  • A preparation failure ends after Prepare with a ── Failure: preparation ── block and no Build section.
  • -q prints only Failure, Warnings and the summary line.

Outputs, warnings and summary​

Outputs. ── Outputs ── lists artifacts as project-relative paths under dist/<target>/<platform>/ (any for a platform-independent target; see the bundle layout) with sizes and the build profile each was built with, development or optimized (cli dist/cli/windows/x86_64/oyzu.exe 64.1 MB development). -v and --json keep absolute paths, and the JSON artifact record carries the label as profile.

Warnings. ── Warnings (N) ── lists each distinct warning once, with its owner (for example docs · npm); it is not repeated inline during the run. The generic NATIVE_WARNING code is hidden in the default view and shown with -v and in JSON, while Oyzu-owned diagnostic codes are always shown.

Summary. The summary line carries the outcome and counts only the outcomes that happened (2 targets · 1 executed · 1 reused · 235.3s), followed by a dim Details line with the manifest and event paths and the invocation id.

  • The separate Action cache line, the "counts do not estimate time remaining" sentence and the "Check selection unavailable … retained evidence is incomplete" sentence are not part of the default build view.
  • -v adds the Reuse and Cache facts, history keeps the selection caveat, and JSON is unchanged.

Marks and colors​

  • With color, state is a glyph: ✓ ok, ↺ reused, ! warning, ✗ failed.
  • Without color (NO_COLOR, TERM=dumb, redirected output) every mark becomes a padded word (ok, reused, warn, FAIL) and headings use -- Name ---, so no state depends on color.
  • -q prints only warnings and the summary line (failures keep their existing receipt).
  • The titles, rows and receipt are produced by the shared presentation and logging layer; JSON stdout, JSON events and exit status are unchanged.

Receipts and history​

Build receipts include separate target/action totals and nonzero disjoint action outcomes, fresh tests, reused test evidence, warnings and available evidence references.

  • Receipts distinguish captured checks selected (with their action outcomes) from checks not requested. Selection comes from the executed graph's retained target facts, including required checks in fast mode; a fast/full label or missing report never establishes that tests were not requested.
  • A native report with an explicit zero total is labeled Native zero-test reports; native skips keep their own counts. Missing numeric facts display unavailable, not zero.
  • Legacy records without captured selection say Check selection unavailable in history and failed receipts.
  • Required report validation still fails the build, and a successful build does not itself establish release eligibility. Selected history uses the same labels.
  • Successful target totals remain separate from actions labeled executed or reused.
  • Expanded build --explain and selected history retain recorded selection and reuse decisions, source comparison context when available, native provenance and explicit uncertainty; they do not recompute causes from the current checkout.
  • Ordinary misses remain ordinary execution, while material fallback warnings and required failures keep their existing visibility and exit semantics.
  • Successful receipts say Build succeeded, including with warnings when warning diagnostics are present. Native warnings are listed once in the Warnings section, and both human views share compiler/test output projection; raw native records remain in JSON events and retained logs.
  • Intentional stage skips use neutral grouped reasons; missing required work still receives attention.
  • Lifecycle records use compact spacing and a simpler nested description at narrow widths; source excerpts preserve native indentation rather than repeated columns.
  • invocationId correlates a build result with its live and retained events; runId remains the producing build identity.
  • oyzu history lists up to twenty retained build summaries; oyzu history <invocation-or-run-id> --json is a bounded agent-readable result with causes and evidence availability. See retained invocation lookup for scope, limits, access and retention. This does not create an agent-only output mode or a general history service for every command.

Contract check​

oyzu build --verify-contract adds a Contract check block after the Outputs of the final receipt.

  • It shows the outcome (passed, failed, nothing to verify), how many confined actions ran again with their whole target visible, how many matched, diverged or were not confined, and one Diverged row per mismatch naming the extra files and the declaration that fixes them.
  • The same data is manifest.extensions["oyzu.dev/contract-verification"] in --json. A divergence is also an error diagnostic and a non-zero exit.
  • A confined action's undeclared read is the diagnostic confined-read-outside-contract with the stage, path, missing fact and fix as indented lines (plain text; no color is needed to read it).
  • See Local action cache.

Human views for other commands​

Inspection, configuration and discovery use titled, indented human views; pin shows a concise requirement inventory. Builds retain their progress and receipt, task lists retain readable labels, and which prints the selected path.

  • All human diagnostics use the shared status/subject/message renderer, including env -v, which -v and shell/payload commands. The old severity/target/timestamp logger envelope and separate build timeline renderer are removed.
  • Verbosity expands observations within the same design. Multiline causes keep their line boundaries.
  • Lookup and payload diagnostics are append-only and create no preparation spool, redraw worker or cursor controls; their stdout contracts (selected paths, environment data and shell code) are unchanged.
  • Plain command views render events without a background redraw worker. Build views retain their ten-second progress heartbeat; interactive builds redraw at up to ten frames per second. Closing either timed build view wakes its wait immediately, so command completion does not wait for the next redraw or heartbeat.

JSON results and errors​

The flag works before or after the subcommand. Arguments after -- belong to the invoked task/program, so its own --json does not select Oyzu's output mode.

oyzu pin --dry-run
oyzu pin --dry-run --json
oyzu --json config show
oyzu tools inspect-lock --json
oyzu --json tools resolve --registry registry.yaml --tool hashicorp/terraform --version v1.16.5
oyzu exec --json -- ./my-program argument

JSON stdout contains one result without Oyzu-added headings, ANSI styling or progress.

  • Existing structured result shapes are retained where available.
  • Oyzu diagnostics on stderr use JSON Lines, including non-build warnings. Read stdout for the command result. Native pass-through streams retain their documented behavior.
  • Setup, operation and argument-parsing errors contain error and exitCode, with a nonzero process exit.
  • JSON help/version return their text in output with exitCode: 0.

exec --json and run​

  • exec --json captures child output in stdout and stderr strings and returns exitCode, also preserving that exit code in Oyzu. Input remains inherited; captured output appears when the child exits, not as a live terminal.
  • The result's capture object discloses inherited stdin, piped stdout/stderr, no output TTY, non-streaming delivery and lossy UTF-8 decoding; invocationId correlates diagnostics. Non-UTF-8 bytes use replacement characters.
  • JSON run outcome records disclose file-based stdout/stderr capture, inherited stdin, non-TTY/non-streaming output, lossy decoding and invocation correlation. Default execution remains pass-through.

Shell payloads​

activate, deactivate, environment hooks and env --shell SHELL emit executable shell code by default: headings would break evaluation.

  • With --json, they return { "shell": "…", "script": "…" }. Evaluate raw code, never the JSON envelope. JSON mode retains the same activation/session-record effects.
  • env inspection stays redacted; explicitly requested shell payloads contain actual assignments in both modes.
  • oyzu config schema build.yaml and oyzu config schema oyzu.toml emit one JSON Schema document as their payload in human mode too, so the output can be redirected to a file. With --json they return the config-schema record that holds it under schema. oyzu config schema without a file is an ordinary listing. See editor schemas.

Tool lifecycle results​

install SPEC, update and uninstall lead with the outcome (✓ Installed go 1.26.8), then indented facts: what was declared and where, the lock and its platforms, replaced requirements and notes about other scopes. --dry-run starts with Dry run · no files were changed.

  • The inspection commands use an outcome line, an aligned table and an Attention section for unresolved rows.
  • Statuses are words (ok, not installed, blocked, deprecated, stale lock, ambiguous), never colour alone.
  • All of them support --json. See tool commands.

Installed tools​

oyzu tools list groups installations by tool (rust (core) · 12 installations · 17.0 GB), each with a Version / Platform / Size / Used by / ID table.

  • ID is the start of the installation digest: it tells apart installs of one version that differ by recipe or platform ABI.
  • --details adds location, tool identity and the full installation digest per row.
  • The lead line totals installations, tools, unreferenced installs and disk use.

Recipe resolution and evidence​

tools resolve and tools evidence (see reference) use the inspection pattern: a title, an outcome line (✓ complete, ! attention), the snapshot, an aligned table of records (status words, never colour alone), then Unsupported platforms, Errors, Needs attention and Next steps sections.

  • --json prints exactly one artifact-set document on stdout (the diagnostic lines of evidence, such as EVIDENCE_FETCH, go to stderr).
  • Exit 3 means a complete document with undecided or unverified items.
  • Recipe-supplied text is control-character escaped.
  • Verified by the compiled-CLI tests in tests/integration/recipe_resolve.rs (human no-colour text, both JSON exit codes and error envelopes) and the proof runner. Narrow-terminal wrapping reuses the shared table and was observed at 80 columns only.

Project discovery​

oyzu discover answers "what does Oyzu see here?". It prints one block per target (the name oyzu build <target> accepts): builder, whether build.yaml or detection from native files chose it, package manager, version, location relative to the project root, which tasks are part of builds and which are development-only (with the reason when one is unavailable).

  • It reads configuration and native files without running project code.
  • The task catalogue and commands belong to oyzu run list; --json returns the complete discovery record.
  • With no targets it explains what to add or where to run. See build tasks.

With a build.yaml​

A Not in build.yaml section lists every folder where discovery recognizes a build the file leaves out, as a Folder / Recognized by / Line to add table, and --json adds the inventory object.

CommandHuman output
oyzu discover --checkLeads with Build inventory is current (exit 0) or error[INVENTORY_UNDECLARED] with the same table and a fix: line (exit 1).
oyzu discover --writeLeads with what it declared (Declared 1 build in …, Created build.yaml with 2 builds, Nothing to write, or, in yellow, A choice is needed: …; nothing was written), a Build / Uses / Folder table, and a Needs a choice table (exit 1) for folders several builders recognize. A row for such a folder is marked example: with a <…> placeholder for uses.
  • Folders a declared build's workspace manifest lists are counted, never tabled: Build inventory is current · 2 builds declared, 10 workspace members, (10 workspace members) after plain oyzu discover's all-declared line, and Covered as workspace members: cli 10 folders. below a table of undeclared folders.
  • A workspace manifest that exists but cannot be read adds a yellow warning: build web: cannot read the workspace manifest package.json: … line, and its members stay in the table.
  • Both print the build-inventory record with --json (workspaceMembers, warnings). See builds build.yaml leaves out.

Inspecting a build​

A bundle is the directory oyzu build writes (dist/ by default) or an exported OCI archive. oyzu inspect with no argument verifies the current project's dist/; a project root is accepted for its dist/.

  • A missing bundle names where Oyzu looked and suggests oyzu build.
  • On success the human view leads with ✓ Bundle contents verified · build succeeded|failed, then the run and source identity and tables of targets (builder, platform), actions (status, exit, gate), artifacts (path, size, platform, short digest), reports and diagnostics.
  • It states that verification checks recorded digests, not who produced the build.
  • An OCI archive shows kind, platforms, size and digests.
  • --json keeps the full manifest. See build bundles.

Task listing​

oyzu run list opens with a count (Available tasks · 8 across 1 target), then shows one table: the Task / Source / Command header appears once and every group shares its column widths.

  • Tasks are grouped by target (for example cli and docs), with ungrouped user tasks under Project; each group heading shows its builder and task count.
  • Listing is a quick lookup, so it prints no progress or logger lines.
  • Each row shows the qualified runnable name, source and effective command arguments.
  • Builder-discovered tasks are labeled Inferred with their provider; TOML-defined tasks show the effective source file, relative to the project when possible. (override) indicates a replacement of an inferred task or an earlier configuration definition.
  • Native package scripts discovered through a builder are also labeled inferred; this distinguishes discovery from an Oyzu TOML definition, not script authorship.

Color and layout​

  • Cyan headings separate groups, inferred sources are muted and authored sources are purple.
  • ui.color, NO_COLOR and terminal detection control color. Explicit ui.color=always/never wins; in auto mode NO_COLOR disables color and CLICOLOR_FORCE=1 enables it when NO_COLOR is absent.
  • Long rows use lossless labeled records on narrow terminals. Unavailable tasks retain their reason.
  • Commands quote arguments descriptively; they are not a portable shell script. Dependencies and hooks may add execution beyond that row.
  • Credential-like command previews are withheld and terminal controls escaped. Do not embed credentials in task command arguments; use the supported environment or secret mechanisms instead.

JSON and effects​

Listing reads discovery and resolved configuration but executes no tasks or native tools. JSON retains the task map and adds each task's origin object: kind (inferred or user-defined), source (full configuration source or null) and override (boolean). Existing argv and redacted environment fields retain their contracts. No configuration or lock files are changed by listing.

Outside a project and unknown tasks​

Outside a project, oyzu run lists nearby projects by relative directory rather than importing their tasks under generated identifiers.

  • The navigation lookup searches at most three directory levels, skips hidden/generated directories, stops below a project boundary and returns at most 32 projects. It reads no child configuration or native metadata and runs no tools.
  • Change into a listed project or use oyzu -C <project> run.
  • JSON returns status: "outside-project", directory, projects, searchDepth, limit and nextStep.
  • An empty lookup fails with PROJECT_NOT_FOUND and the searched directory; requesting a task from the parent fails with TASK_PROJECT_REQUIRED before loading a child project.
  • Explicit workspace roots remain workspaces and use the ordinary task listing.

An unknown task returns TASK_NOT_FOUND, the selected project directory, available task names and a close spelling suggestion when one exists. It also points to oyzu run and oyzu -C <project> run <task> for recovery. No task-running preamble appears for this failure.

Native execution is announced only after task selection and preparation. Completed task rows include the exit code and duration, for example Failed (exit 7 after 0.20s). The process preserves the failed child's exit code; task JSON records retain exit_code and add duration_ms (execution time excluding discovery and tool preparation).

Task streams​

Local run tasks retain stdin.

  • In text mode, tasks recording a bundle tee full stdout/stderr to the caller and dist/logs, including in quiet mode, without replaying output at completion. Their output descriptors are pipes.
  • Tasks marked interactive = true instead inherit terminal stdout/stderr; those streams cannot also be captured, so their bundle stdout/stderr files are empty.
  • Non-bundled tasks also inherit output directly.
  • JSON captures task output and keeps stdout as the final result. See task streams.

Diagnostic controls​

Global -v/--verbose enables debug, -vv enables trace, -q/--quiet selects warn, and --log-level error|warn|info|debug|trace selects an explicit threshold. Default is info.

  • Options work on either side of a subcommand; arguments after -- belong to the child.
  • More than two -v or one -q, or combining these controls, is an argument error before project loading.
  • One explicit CLI control overrides all of OYZU_LOG.

Otherwise this optional UTF-8 environment value accepts a level or comma-separated target=level directives, optionally preceded by a default level (info when omitted):

$env:OYZU_LOG = 'warn,oyzu::executor=trace'
oyzu run foo
oyzu run foo --json -v
Remove-Item Env:OYZU_LOG
  • Targets are oyzu::commands, oyzu::config, oyzu::discovery, oyzu::tools, oyzu::acquisition, oyzu::executor, oyzu::builders and oyzu::reports. An exact target directive overrides the default.
  • Unknown or duplicate targets, empty directives and invalid levels fail. Overridden environment filters are not read.
  • Help/version ignore OYZU_LOG, including invalid values.
  • These are invocation presentation options, not oyzu.toml settings. RUST_LOG does not control Oyzu diagnostics or enable dependency payload logging.

What the controls change​

  • Quiet hides routine Oyzu progress and the interactive dashboard. It preserves command results, warnings, errors and native child output.
  • Verbosity does not change native flags/environment, plans, cache inputs, report gates or production eligibility.
  • Logging is local, offline-capable and needs no account, service or new persistent sink.
  • All thresholds use the same field admission. No environment/header maps or unrestricted argument arrays are logged. Command events withhold arguments; credential-bearing parts of diagnostic prose are redacted (see Redaction).
  • Arbitrary child output and explicitly requested shell payloads are not rewritten and may contain secrets. Trace is not an HTTP dump or a secret-inspection mode.

Diagnostic content and JSON events​

  • Human diagnostics identify severity and the affected work. Operational failures also identify the running executable/version, selected directory, host platform and observation identity when available. Help/version/syntax remain independent of runtime initialization.
  • JSON diagnostic envelopes retain the existing event fields and add severity, target, invocationId, operationId and parentOperationId. Diagnostic events contain type, code and message, with numeric duration_ms for completed operations.
  • Retained build journals now carry the same correlation fields and observed warning/error diagnostics, independently of console detail filtering. Filtered console projections may have sequence gaps.
  • Sequence orders observations within an invocation; it does not establish causal ordering between native processes. Consumers must tolerate additive fields and event kinds.
  • The existing unreleased manifest/envelope schemas gain optional invocationId in place; actions can carry namespaced log references and the explicit not-started outcome for interruption before launch. Reuse can identify the serving cache tier (local or remote), independently of its producer.
  • Pin's human output includes a deduplicated execution-platform coverage section. It describes resolved metadata, not installed availability or platform execution qualification. JSON retains the full platform-specific compiler_metadata recipes.

Failures and lifecycle labels​

Human failures from a command print ✗ <what failed and how to recover> with the diagnostic code underneath (for example COMMAND_FAILED), not a raw [Error] [oyzu::commands] envelope.

  • A message that already leads with its own stable code (✗ CONFIG_SYNTAX: …, ✗ REMOTE_COMMIT_NOT_PUSHED: …) omits the generic code underneath.
  • --json keeps its {"error", "exitCode"} object and -q keeps the plain error line.
  • Internal pipeline scopes are shown as words (Setup, Preflight, Source, Plan); generated platform target ids are shown as target · os/arch.
  • Running a task prints a heading, shared lifecycle rows and the task result, followed by the native tool output unchanged.

Redaction​

Diagnostic prose redacts only the credential-bearing part. Ordinary URLs and prose stay readable.

PatternResult
A URL with userinfo[sensitive diagnostic detail withheld]
URL queries and fragments?[redacted]
key=value / key: value forms for credential namesThe name is kept; the value is replaced.
Authorization: or BearerThe rest of the line is redacted.

Configuration display still hides any value that looks credential-bearing. Native child output is not rewritten.

Human presentation standard​

This section is the normative style guide for every public command's human experience: startup, progress, subprocess output, results and failures. Command-specific presenters must follow it; a generic recursive data dump or raw diagnostic envelope is not a finished public interface. These are review requirements, not a claim that all existing commands have been audited.

  • Lead with the outcome and relevant selection (such as the active profile).
  • Use short, descriptive section headings and aligned columns for comparable records. Keep empty collections compact ([] for configuration values); omit empty diagnostic sections. Do not omit failures or unresolved requirements.
  • Preserve identifiers exactly: env.CARGO_HOME, env._.path, checks.coverageMinimum and cargo-llvm-cov are copyable identifiers, not prose. Never title-case, split capitals, or replace their underscores and punctuation.
  • Humanize only labels owned by the presenter. Group configuration settings by namespace, retaining full setting keys. Render booleans as true/false in configuration tables to match their authored types.
  • Put long identities and low-priority metadata after the useful settings. Wrap long cells without losing characters; use labeled records on narrow terminals. Normalize Windows extended-path notation for human display, while preserving machine payloads.
  • Use cyan headings, green success, yellow attention and red failures. Always include textual meaning; color cannot be the only signal. Preserve readable no-color output, escape terminal controls, and honor each command's redaction contract. Presentation must not recover upstream-redacted values.
  • Verify the compiled command in human, no-color and JSON modes. Cover long identifiers and narrow layouts with focused rendering checks. JSON schemas and executable/native payloads are independent of presentation.

Human output leads with the operation outcome, then groups details into named sections. Comparable records use aligned tables; nested or long records use labeled fields without dropping values. The shared renderer uses terminal width when available (100 columns otherwise), falling back to labeled records when a table would overflow. Color is supplementary: headings use cyan, success uses green and attention uses yellow; errors retain explicit severity labels.

Color controls​

  • Shared result views enable color on terminals, omit it for redirected output or TERM=dumb, accept nonzero CLICOLOR_FORCE to force color, and let NO_COLOR override forcing.
  • No project configuration is opened solely to style a result.
  • JSON never gains ANSI sequences. Shell code, native streams and which path output retain their payload contracts.
  • Untrusted control characters in shared human result values are escaped before styling.

Pin output​

pin shows one compact setup table per target. For Rust it lists each compiler component and test/coverage helper separately, with a purpose column.

  • Formatting, linting, testing and coverage tools are required when those checks are enabled by the build or policy; the labels do not make selected checks optional.
  • Installation support is distinct from installed availability: pin does not probe or install tools.
  • Sources, profiles, compatibility constraints, configured requests and discovery limitations remain in --json, rather than repeated human tables. Unknown requirements remain visible. Existing resolution-conflict diagnostics are unchanged.
  • Preview/pinned outcomes distinguish completed and incomplete resolution. Incomplete resolution includes actionable diagnostics below the setup table.
  • Environment inspection and shell-profile receipts also use the shared layout.

Consistency means shared hierarchy, vocabulary and state semantics, not adding identical headings to payload commands. Select the pattern in the CLI presenter before starting effects. Application commands return outcomes and lifecycle facts; they do not select colors, terminal modes or human/JSON formatting.

Operation lifecycle​

  • Before potentially slow work, show the operation and what is currently being checked or performed. Do not delay all feedback until the final result. Immediate lookups need no synthetic progress.
  • Name the item or step (rust, Dependencies, Source evidence), not an internal scope such as command or a repeated generic build label. Context statements belong in subtitles or explanatory text; do not make them look like work items.
  • Use one shared state vocabulary: › running, ✓ completed/ready, ✗ failed, ! attention, and explicit Skipped, Blocked, or Unresolved labels. Starting verification is not completion. Mark ready only after the owning operation confirms its required checks. Close started steps on failure as well as success; never leave an apparently running step in a completed receipt.
  • Use elapsed/still-working feedback for genuinely long operations. Use a percentage only when the operation supplies a meaningful total. Do not invent progress or claim stalled work is healthy merely because a heartbeat exists.
  • Keep the default linear. Small redraws may update active rows and bounded subprocess tails on capable terminals; persistent panes, alternate screens and interactive input must not be prerequisites for ordinary use.
  • Group concurrent work by stable target/task/tool identity. Indent and dim each captured subprocess tail beneath its owner, allowing about eight lines subject to the shared terminal budget. Collapse successful tails; retain relevant failure context. Never merge unattributed lines from parallel processes. Native pass-through commands retain their documented stream contract.
  • Finish with a concise outcome and useful results, artifacts or recovery steps. Avoid repeating the complete progress history in the receipt. Partial success, failed verification and missing requirements must remain visible.

Routine human progress must not default to envelopes such as [Info] [oyzu::commands] [00:00.045] [command]. Subsystem identifiers, timestamps and diagnostic metadata belong in explicitly requested diagnostic detail and structured logging. Warnings/errors still explain severity and retain useful codes; do not suppress them to make a display look clean.

Illustrative shared lifecycle (values are examples, not measured output):

Installing tools
  › rust                   Checking pinned installation…
  ✓ rust                   Ready · 1.95.0 · reused
  › cargo-nextest          Installing…
      Downloading package…
  ✓ cargo-nextest          Ready · installed

Installation complete
2 tools verified · 1 installed · 1 reused

The live terminal may replace the running rows; a redirected stream keeps a readable start/completion sequence. Both must communicate the same outcome.

Terminal, diagnostics and data contracts​

  • Use the shared renderer's semantic palette and color controls above. Never add command-local ANSI strings or a second styling policy.
  • Dim native previews, not essential status or recovery instructions.
  • When terminal capabilities are absent, use append-only text with no cursor controls; disabling color alone must not remove information. Forced color may style redirected output without enabling redraws.
  • Handle narrow widths without truncating copyable identifiers or paths.
  • Keep progress/diagnostics on stderr and final results on stdout. Preserve the JSON, shell-payload and native-stream exceptions documented above.
  • Quiet removes routine progress, not results or failures; verbosity adds diagnostics without changing execution.
  • Preserve legitimate values under the owning sensitive-field policy: do not blanket-redact ordinary configuration, paths or version information, and never reveal protected values merely because verbose output is enabled.

Implementation and review checklist​

For every new or changed public command:

  1. Identify its output pattern and reuse presentation result primitives plus the invocation-owned logging/linear view. Search existing renderers first; extend the shared owner when behavior is missing instead of building a local spinner, logger, color palette or table formatter.
  2. Exercise the real compiled entry point. Check startup feedback, one successful outcome and an applicable failure, including meaningful terminal step closure. A renderer unit test alone does not prove the command selected that renderer.
  3. Check ordinary human output, redirected/no-color output, JSON stdout/stderr separation and quiet behavior. Use focused rendering checks for narrow/long layouts and concurrent output when relevant; use a capable terminal for changed redraw behavior. State unavailable terminal/platform qualification explicitly.
  4. Confirm the payload exceptions, exit codes, sensitive-field handling and help/version fast path remain intact. Presentation must not change tool flags, plans, cache identity, evidence or policy.
  5. Update the owning reference and record actual verification. Fix inconsistencies in the changed command; record unrelated command-family gaps rather than claiming repository-wide compliance or launching an unbounded visual rewrite.

Help and startup​

oyzu --help, oyzu help build, nested --help, --version and unknown-command diagnostics use the built-in command catalog.

  • They work with an empty PATH, malformed project files and a nonexistent -C directory.
  • They do not load project configuration, refresh enterprise policy, open tool stores, initialize backend workers or contact services. No installation or platform account is required.
  • The operating system still loads the binary and Oyzu checks its executable identity to distinguish native tool shims.
  • Actual run list/discover inspect a project; which validates the frozen tool selection. Those are explicit operations, not static command help, and retain their configuration and verification requirements.
  • A native tool shim's help continues to invoke that selected tool.
  • The public CLI and reusable application command layer share execution behavior; see the architecture boundary.

Configuration inheritance in nested projects​

oyzu.toml settings (including tools.* pins) inherit from the Git worktree root, while build.yaml does not inherit: the nearest ancestor build.yaml inventory selects the build (another tool's build.yaml never does).

A project nested in a repository therefore sees the repository's tool pins. Pass --root . to fix both roots at the current directory and stop inheritance (see configuration).

Migration and verification​

Scripts parsing formerly JSON-only pin, discovery, bundle/tool inspection or configuration output must now pass --json. Human formatting is not a parsing contract. Result schemas remain command-specific; this does not change build evidence or introduce a universal result schema.

CLI tests cover human defaults, both flag positions, structured errors, help/version, child execution and shell payloads. Measured results and outstanding checks are in implementation status. Windows verification does not qualify other hosts.
