CLI output

CLI reference

Published from the canonical docs/reference/cli-output.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Every public command prints readable text for people by default and accepts the global --json flag for machine-readable output. This page shows what each kind of output looks like, which flags and environment variables control it, and what scripts can rely on.

Choosing an output mode never changes policy, configuration, lock contents or exit codes.

Output controls at a glance​

ControlEffect
--json (before or after the subcommand)One machine-readable result on stdout; diagnostics on stderr as JSON Lines. See JSON results and errors.
-v, -vvDebug and trace diagnostics; more detail in build output.
-q, --quietHide routine progress. Results, warnings and errors stay.
--log-level error|warn|info|debug|traceSet the threshold explicitly. See Diagnostic controls.
OYZU_LOGPer-area log levels.
NO_COLORTurn color off.
CLICOLOR_FORCEForce color (any nonzero value). NO_COLOR wins over it.
ui.colorProject or user setting: always, never or auto. Doesn't apply to help.

Command help​

Run oyzu or oyzu --help for an overview of every command. Bare oyzu prints the same help and exits 0. See CLI help for nested help, help color and JSON help.

Shim refresh and shell profiles​

oyzu reshim (under Project tools) refreshes the shims folder and existing activation launchers. Human output shows the shims folder and the commands it holds; --json returns directory and commands. See the shims folder. oyzu shell install and oyzu shell remove manage shell startup profiles.

Build identity​

oyzu --version prints the compiled display label. A development build is independent of the checkout's commit, dirty state and wall-clock time:

oyzu 0.2.2-dev (development; x86_64-pc-windows-gnu)
PartMeaning
0.2.2-devDevelopment display label based on the compiled package version.
x86_64-pc-windows-gnuTarget triple.
  • Development includes optimized local and CI builds unless release stamping is explicitly supplied. Their engine pin/admission identity is a separate content fingerprint; see engine identity.
  • Release compilation supplies a full OYZU_RELEASE_COMMIT and Unix seconds in SOURCE_DATE_EPOCH. Its existing form is preserved, for example 0.2.2-local.8aee8560a0ca (release; x86_64-pc-windows-gnu; build 1791211857). Missing or malformed release inputs fail compilation. A timestamp alone does not turn a development build into a release build.
  • A stamped release compilation from a clean checkout of the release tag oyzu/v<version> that matches the package version reports just that version, for example oyzu 0.2.4 (release; x86_64-unknown-linux-gnu; build 1793100000). Every platform built from that tag reports the same version, whichever oyzu built it, so a Windows install and the Linux engine it installs agree. The tag is read from Git at compile time; it isn't a signature, and release provenance remains the trusted evidence.
  • --version never opens project configuration, runs Git or contacts a service. It does not hash the executable or source tree. Development compilation also reads no Git state; its embedded original notices omit the source revision.
  • --version --json returns the text in the usual JSON envelope.

Which executable is running​

Pulling new source doesn't replace an installed oyzu. To see which one your shell runs, use command -v oyzu (POSIX shells) or Get-Command oyzu -All (PowerShell), then compare versions:

oyzu --version
./.oyzu/bin/oyzu --version

On Windows, use .\.oyzu\bin\oyzu.exe.

  • oyzu build copies executable artifacts into the project's .oyzu/bin only after a successful native build. A failed build keeps the previous binaries.
  • Compiling with Cargo through oyzu exec writes Cargo's own target/ output and doesn't update .oyzu/bin. Don't assume target/debug/oyzu is the one your shell runs.
  • In an activated shell, ordinary commands run the first oyzu on PATH, so a project-local .oyzu/bin on PATH takes over. See shell activation.

Result output​

Discovered build facts​

Ordinary builds show a Facts section after preparation and before Selection, Plan and the actions. It needs no flag, login or network.

FactMeaning
Branch / CommitThe local branch and the commits recorded for versioning. Different targets keep their own commit. This doesn't prove that Git HEAD matches the files that were built.
Git stateAlways shown as not verified.
Source digestContent identity of the build inputs. Shortened by default; -v and JSON show it in full.
Version / BasisEach target's or package's planned version and why. Packages in a target that share a version and basis are grouped: by count, or by name with -v. When some differ, each differing package gets its own row, the rest are grouped as others, and a basis they all share is shown once; -v lists every package with its own Version and Basis rows. Distinct native artifact versions get their own Artifact row.
KindThe version kind; currently snapshots. A release context alone doesn't make a release.
ContextThe build context (local, pr, ci, release) and where it came from.
Protectionunknown · not queried. Oyzu doesn't ask your Git host.
ReleaseWhether the build is eligible for release, or unknown. Version facts never allow publishing on their own.
  • When independent targets prepare at different times, each new plan shows only new or changed facts before its actions.
  • A version set by a hook shows pending post-hook finalization; the final version appears under Build.
  • --quiet hides this section.
  • In JSON, each plan event carries the facts in buildFacts. Environments, credentials and arbitrary extensions are never included.
  • Uncertain Git or protection facts don't change the exit status, cache identity or release rules.

Build transcript​

A default build shows compact linear progress, with one plan table before work starts. Sections always appear in the same order, and any section with nothing to say is left out. Every row, the title and the section rules share one width (80 columns, or less on a narrower terminal). Routine successes are collapsed; -v, --plan, oyzu inspect, oyzu history and --json keep the detail.

SectionWhat it shows
Title lineProject name and, right-aligned, the facts under Title line.
── Prepare ──One row per preparation step, then the pinned tools.
── Selection ──Plugin builder selection, and why the build isn't every declared target.
── Plan ──A table of targets by stages, with reason lines.
── Build ──One row per finished action.
── Failure: <target> · <stage> ──The native cause of a failed action.
── Outputs ──Artifacts with sizes and build profile.
── Warnings (N) ──Each distinct warning once, with its owner.
SummaryThe outcome and counts, then a dim Details line.

Title line​

The title line names the project and, right-aligned, shows:

  • the host platform;
  • local or the CI provider;
  • the build context (context pr, context local). Where it came from is shown in Facts and by oyzu config explain context; see build context;
  • fast or full, then optimized or development when you passed --optimized or --no-optimized.

Under a CI provider the right-hand side may wrap onto the next line. If you pin a lower context while a CI provider marker is present, you get a CONTEXT_OVERRIDE_IGNORED warning.

Prepare​

── Prepare ── shows each preparation step as a row: mark, name, detail, duration and warning count.

  • The Tools row summarizes the tools (2 tools pinned · 0 installed now) and lists each one with its version, already installed or installed now, and why it's needed (the detected requirement, or pinned in oyzu.toml). Toolchain components and host prerequisites follow.
  • With several targets, the tool list prints once and each tool appears once. If the reason differs by target, each reason is shown (detected from …; pinned in … · not detected for <target>).
  • The Plugins row follows the tools on every build that uses a builder plugin (2 plugins · 1 installed now). Each plugin release gets one line with its version, where it came from this time and the targets it builds: plugin store, installed now from <registry> (with its size when known), local package binding, or local development executable · not locked. A newly locked plugin adds recorded in oyzu.lock now. A plugin missing from the store, or not yet adopted, gets a warn mark and says what the next build does. Why each plugin was chosen stays in Selection. -v adds the release digest and the full route.
  • The Images row follows on every build that runs in an execution image, such as --isolated (1 image · 1 pulled now). Each image gets one line with its digest, where it came from and the targets it runs: local Docker engine, pulled now from <registry>, unpacked now from … or unpacked root reused (from …) for the daemonless sandbox, or no image; built in process. -v shows full digests and sources. Plugin and image lines wrap rather than being cut, so no target or source is lost. In --json runs, the event stream carries the same facts as an executionImages inventory event (target, reference, digest, and origin with its kind).
  • If another build holds the workspace, a Build lock row waits for it (waiting for pid N, started Ns ago) instead of failing. Ctrl-C stops waiting.
  • Housekeeping after Prepare (such as cache cleanup at the end) is shown only when it's slow, fails or warns, or with -v.

Attention rows. Tool detection is best-effort. Problems show as yellow ! rows under the tools. They warn and never fail the build (only an explicit pin can). tools.ignore silences a detection; ignored detections show with -v.

RowMeaning
! protoc needed by prost-build · no catalog entry; pin or provide itOyzu doesn't know this tool. A tool Oyzu can manage shows as an ordinary detected from Cargo.lock row and is locked and installed.
! protoc needed by prost-build in Cargo.lock · no usable checksum; pin it in oyzu.toml or silence it with tools.ignoreA detected tool couldn't be resolved or installed. The build continues.
host prerequisite … · not found on PATHA host prerequisite is missing.
fetches <what> outside the lock (<file>)The build downloads something the lock doesn't cover.
detection failed: <reason> · nothing extra detectedDetection couldn't run.

Live and redirected progress​

  • Interactive terminal. Work in progress shows under its section as one line per step or action with a spinner. Long status is shortened with …, never wrapped. Queued actions waiting on others show as ○ <target> · <stage> waits for <target> · <stage> (at most three, then + N more waiting), with an N of M finished line.
  • Redirected and CI output never redraws. Each action prints a start line (.. target stage started) and an end line with outcome and duration, both led by the elapsed mm:ss. Every ten seconds a heartbeat names what's still running, for example still running: api build 10s · auth-lib test 12s · 6 waiting.
  • Redirected output uses 100 columns on every host. Failure text wraps, Windows \\?\ prefixes are hidden, and long log paths keep their tail.
  • On a narrow terminal or without color, every table turns into records. Nothing is dropped.
  • Interrupted, --plan and --check builds have their own summaries.

Selection​

── Selection ── appears when a target is built by a plugin or when the build isn't every declared target.

  • Plugin-built target: the builder selection. The full record with fixes appears when the build adopted or installed a plugin; otherwise one line per target. See plugin catalog.
  • --affected: what it compared with (compared with origin/main at 0123456), the changed targets and paths, their dependents and the unaffected count.
  • Fallback: ! Not narrowed with the reason, the code, and a fix when one is known.
  • Explicit request: requested and required (prerequisites pulled in).

Plan​

── Plan ── prints once. Rows are targets; columns are the stages the builders declare, in the order format, lint, test, build, package, then any others.

CellMeaning
runRuns in this build.
skipThe builder has the stage but this build doesn't run it (for example a fast local build), or it isn't available.
offThe check level is off: never run, and its tools aren't prepared.
-The builder has no such stage.

Under the table, one dim line per distinct reason names the stages it covers:

LabelWhat the line says
offWhere the check was turned off (format · disabled in oyzu.toml, test · disabled in oyzu.toml [context.pr]).
skippedWhy stages were skipped (lint and test · fast local build).
advisoryStages whose failure is only a warning (lint · failures are warnings; the build still succeeds).
profileEach build profile in use, its targets and why (cli · optimized · --optimized, cli and docs · development · local dist only, cli · optimized · release builds are published).
policyEach policy override: the setting, the value policy enforced and why (format enforce · admin policy minimum in pr, release (project oyzu.toml sets off)), prefixed with its targets when not all targets share it.
projectOverrides from the root oyzu.toml's project constraints, in the same form (tests required · project constraint minimum in release (project app/oyzu.toml sets advisory)).
loweredIn a release build, each check a nearer folder lowered below a farther [context.release] value (tests advisory · app/oyzu.toml:2 lowers required from oyzu.toml:5 [context.release]).
taskEach conditional task or hook: whether it runs (and for which artifacts) or why it's skipped (pre_build · skip · unless context = local, post_build · run for bin-oyzu · unless artifact = bin-oyzu-shim). A per-artifact run's Build row names its artifact (post_build[bin-oyzu]).
noteNotes about the table.

oyzu build --plan prints the same task lines as Task: lines under each target.

Large and multi-platform plans

  • One target built for several platforms (--all-platforms) shows one row per platform and says 1 target · N platforms.
  • Above twelve rows, targets with identical stages share a counted row (29 targets) with a note. A narrowed build says N of M targets, and an affected build adds a why column (changed, uses <target>). -v lists every target.
  • If the table doesn't fit, each row becomes a record (cli build run · package -, then its skipped stages on the next line).
  • When a platform is built off the host, or a target declares platforms this run doesn't build, each row names its platform (hello · linux/arm64) and a built by column names the executor (host, cross toolchain (rust-lld)), or a footnote if it doesn't fit.
  • An other footnote lists declared platforms you could build here with --platform; a not here footnote lists the rest with the reason (darwin/arm64 · needs a macOS runner (Apple SDK and linker)). See platforms and executors.
  • --plan adds a Platforms · how each is built here table: target, platform, what builds it here, the CI runner it needs, and why.

Grouping by directory. When targets live in more than one top-level folder (./ for targets at the root):

  • plan rows are grouped under a dim folder heading such as services/;
  • a prerequisite in another folder shows in a final needs column when it fits;
  • Outputs are listed by folder;
  • the summary adds one line per folder (services/ ✓ 2 targets 58.1s, the sum of that folder's action times);
  • the twelve-row grouping applies within each folder.

Build​

── Build ── has one row per finished action: mark, target, stage, the command (shortened with …), executed or reused, and the duration.

Test actions that declare units also show N ran, M reused on that same row. These counts remain visible in interactive, redirected and no-color views; annotated test rows remain visible when clean successes fold into a tally. The JSON action record includes units with each unit's name, key and outcome (ran, reused or failed). Operations without units retain their existing output.

  • With more than twelve actions, clean successes fold into one tally such as ✓ 91 finished · 78 reused · 13 executed (-v lists them all). Running, warned, waiting, blocked and failed actions keep their rows, and the heading says 143 actions.
  • A failed advisory check is shown once, as a warning: its row reads warn … failed · advisory, it gets no Failure section, Warnings has one CHECK_ADVISORY entry with the exit code and cause, and the summary counts it separately (1 advisory failed). The build still succeeds.

Failure​

A failed action's row reads ✗ … failed <duration> (FAIL without color).

  • After Build, a ── Failure: <target> · <stage> ── section shows the native cause (line breaks kept, terminal controls escaped), the exit code, Log with the log path, and Next oyzu build <target> re-run only this target.
  • Actions that didn't run because a prerequisite failed are blocked (⊘) and counted separately. A blocked row says needs <target> · <stage>. Only the first three get a row; the rest become + N more blocked · -v lists them.
  • The summary counts only outcomes that happened (✗ Build failed 1 failed · 12 blocked · 130 succeeded · 4m 02s), then Details and, for a host build, a note that local binaries weren't updated.
  • A preparation failure ends after Prepare with a ── Failure: preparation ── section and no Build section.
  • -q prints only Failure, Warnings and the summary line.

Outputs, warnings and summary​

Outputs. ── Outputs ── lists artifacts as project-relative paths under dist/<target>/<platform>/ (any for platform-independent output; see the bundle layout), with size and build profile (cli dist/cli/windows/x86_64/oyzu.exe 64.1 MB development). -v and --json show absolute paths; the JSON artifact record has the profile as profile.

Warnings. ── Warnings (N) ── lists each distinct warning once, with its owner (for example docs · npm). Warnings aren't repeated inline during the run. Discovery summarizes unreadable folders in one warning, naming up to five root-relative paths with OS reasons and and N more for the rest. The generic NATIVE_WARNING code is hidden by default and shown with -v and in JSON; Oyzu's own codes are always shown.

Summary. The summary counts only outcomes that happened (2 targets · 1 executed · 1 reused · 235.3s), followed by a dim Details line with the manifest and event paths and the invocation ID. -v adds reuse and cache details.

Marks and colors​

  • With color, state is a symbol: ✓ ok, ↺ reused, ! warning, ✗ failed.
  • Without color (NO_COLOR, TERM=dumb, redirected output), marks become padded words (ok, reused, warn, FAIL) and headings become -- Name ---. No state depends on color.
  • -q prints only warnings and the summary line (failures keep their full report).

Receipts and history​

The final summary of a build is its receipt.

  • It counts targets and actions separately, and shows fresh tests, reused test results, warnings and where the records are. Combined test reports retain each unit's contribution: reused cases are not counted as run now. A test action whose units all reused still counts as executed (actions.succeededNow), because preparation, finalization, coverage and any doctests execute. Doctests contribute fresh cases. Only whole-action reuse counts in actions.reused.
  • It separates checks that were selected (with their outcomes) from checks that weren't requested. That comes from the recorded build, not from a fast/full label or a missing report.
  • Reports that recorded zero tests are labelled Native zero-test reports. Skipped tests keep their own count. Missing numbers show as unavailable, not zero.
  • Old records without check selection say Check selection unavailable.
  • A missing required report still fails the build. A successful build doesn't by itself make it eligible for release.
  • A successful build says Build succeeded, or Build succeeded with warnings.
  • invocationId ties a build result to its live and saved events; runId identifies the build that produced the bundle.
  • oyzu build --explain and oyzu history <id> show recorded selection and reuse decisions; they never recompute causes from your current checkout.
  • oyzu history lists up to twenty builds, and oyzu history <invocation-or-run-id> --json gives a compact summary with causes. See retained invocation lookup.

Contract check​

oyzu build --verify-contract adds a Contract check block after Outputs.

  • It shows the outcome (passed, failed, nothing to verify), how many confined actions ran again with the whole target visible, how many matched, diverged or weren't confined, and one Diverged row per mismatch naming the extra files and the declaration that fixes them.
  • --json has the same data in manifest.extensions["oyzu.dev/contract-verification"]. A divergence is also an error diagnostic and a nonzero exit.
  • An undeclared read by a confined action is the diagnostic confined-read-outside-contract, with the stage, path, missing fact and fix on indented lines.
  • See verifying a contract.

Human views for other commands​

Inspection, configuration and discovery commands use titled, indented views. pin shows a compact requirements table, task lists show readable labels, and which prints the selected path. oyzu self uses the sectioned step view: Download and Install work, concise Warnings, a marked outcome and one final Next: command.

  • Diagnostics from every command use the same status / subject / message layout, including env -v, which -v and shell payload commands.
  • -v adds detail within the same layout. Multiline causes keep their line breaks.
  • Lookup and payload commands print diagnostics append-only, with no redraws or cursor movement. Their stdout (paths, environment data, shell code) is unchanged.

JSON results and errors​

--json works before or after the subcommand. Arguments after -- belong to the task or program, so its own --json doesn't affect Oyzu.

oyzu pin --dry-run
oyzu pin --dry-run --json
oyzu --json config show
oyzu tools inspect-lock --json
oyzu --json tools resolve --registry registry.yaml --tool hashicorp/terraform --version v1.16.5
oyzu exec --json -- ./my-program argument
  • Stdout holds one result, with no headings, color or progress.
  • Oyzu's diagnostics go to stderr as JSON Lines, including warnings. Read stdout for the result. Native pass-through streams keep their own behavior.
  • Errors (setup, operation or argument parsing) contain error and exitCode, and the process exits nonzero.
  • JSON help and version return their text in output with exitCode: 0.

When neither static markers nor eligible catalog detections identify a project at the root or in the bounded nearby lookup, build reports PROJECT_NOT_FOUND with exit 5 before build discovery, workspace preparation, Prepare output or the Building … heading. This includes named targets, --plan, --full and --json. The error uses run's project check and message, with recovery guidance naming oyzu -C <project> build. Finding a nearby project within three directory levels allows normal build discovery over child projects; run only suggests them. Configuration and catalog metadata may be loaded or refreshed before refusal, using the same catalog source and refresh rules as normal discovery. If discovery inside a recognized project skipped unreadable folders, the error includes up to five root-relative paths with OS reasons and and N more for the rest. Human output keeps the Next: line; JSON keeps the details in its error result. See unreadable folders.

exec --json and run​

  • exec --json captures the child's output in stdout and stderr strings and returns its exitCode, which Oyzu also exits with. Input is still inherited. Output appears when the child exits, not live.
  • The capture object says how streams were handled: inherited stdin, piped stdout and stderr, no terminal, not streamed, and UTF-8 decoding with replacement characters for invalid bytes. invocationId ties it to diagnostics.
  • run --json outcome records describe capture the same way. Without --json, task output passes straight through.

Shell payloads​

activate, deactivate, environment hooks and env --shell SHELL print shell code by default, because headings would break evaluation.

  • With --json they return { "shell": "…", "script": "…" }. Evaluate the raw code, never the JSON envelope.
  • oyzu env inspection redacts credential-like values; shell payloads you ask for contain the real assignments in both modes.
  • oyzu config schema build.yaml and oyzu config schema oyzu.toml print a JSON Schema document even in human mode, so you can redirect it to a file. With --json they return a config-schema record with it under schema. See editor schemas.

Tool lifecycle results​

install SPEC, update and uninstall lead with the outcome (✓ Installed go 1.26.8), then what was declared and where, the lock and its platforms, replaced requirements and notes about other scopes. --dry-run starts with Dry run · no files were changed.

  • Inspection commands show an outcome line, a table and an Attention section for unresolved rows.
  • Statuses are words (ok, not installed, blocked, deprecated, stale lock, ambiguous), never color alone.
  • All support --json. See tool commands.

Installed tools​

oyzu tools list groups installations by tool (rust (core) · 12 installations · 17.0 GB), each with a Version / Platform / Size / Used by / ID table.

  • ID is the start of the installation digest. It tells apart installs of one version that differ by recipe or platform ABI.
  • --details adds location, tool identity and the full digest.
  • The first line totals installations, tools, unreferenced installs and disk use.

Recipe resolution and evidence​

tools resolve and tools evidence (see tool resolve) show a title, an outcome line (✓ complete, ! attention), the snapshot, a table of records, then Unsupported platforms, Errors, Needs attention and Next steps.

  • --json prints exactly one document on stdout. Diagnostics such as EVIDENCE_FETCH go to stderr.
  • Exit 3 means the document is complete but some items are undecided or unverified.
  • Text from recipes has control characters escaped.

Project discovery​

oyzu discover answers "what does Oyzu see here?". It prints one block per target (the name oyzu build <target> accepts): builder, whether build.yaml or native files chose it, package manager, version, location, which tasks are part of builds and which are for development only.

  • It reads configuration and native files without running project code.
  • oyzu run list shows tasks and their commands. --json returns the full discovery record.
  • With no targets, it explains what to add or where to run. See build tasks.

With a build.yaml​

A Not in build.yaml section lists each folder where discovery recognizes a build the file leaves out, as a Folder / Recognized by / Line to add table. --json adds an inventory object.

CommandHuman output
oyzu discover --checkBuild inventory is current (exit 0), or error[INVENTORY_UNDECLARED] with the table and a fix: line (exit 1).
oyzu discover --writeWhat it declared (Declared 1 build in …, Created build.yaml with 2 builds, Nothing to write, or, in yellow, A choice is needed: …; nothing was written), a Build / Uses / Folder table, and a Needs a choice table (exit 1) for folders several builders recognize, with an example: row and a <…> placeholder for uses.
  • Folders listed as workspace members of a declared build are counted, not tabled: Build inventory is current · 2 builds declared, 10 workspace members, or Covered as workspace members: cli 10 folders. below a table.
  • An unreadable workspace manifest adds a yellow warning: build web: cannot read the workspace manifest package.json: … line, and its members stay in the table.
  • Both print a build-inventory record with --json (workspaceMembers, warnings). See builds build.yaml leaves out.

Inspecting a build​

A bundle is the folder oyzu build writes (dist/ by default) or an exported OCI archive. oyzu inspect with no argument checks the current project's bundle; a project root also works.

  • A missing bundle says where Oyzu looked and suggests oyzu build.
  • On success the view starts with ✓ Bundle contents verified · build succeeded|failed, then the run and source identity and tables of targets, actions, artifacts (path, size, platform, short digest), reports and diagnostics.
  • It says that it checked recorded digests, not who produced the build.
  • An OCI archive shows kind, platforms, size and digests.
  • --json returns the full manifest. See build bundles.

Task listing​

oyzu run list starts with a count (Available tasks · 8 across 1 target), then one table with a Task / Source / Command header shared by every group.

  • Tasks are grouped by target (for example cli and docs); your own ungrouped tasks are under Project. Each group heading shows its builder and task count.
  • Listing prints no progress.
  • Each row shows the full task name, its source and its command arguments.
  • Tasks found by a builder (including package scripts) are labelled Inferred with their provider. Tasks from TOML show their file, relative to the project when possible. (override) marks a task that replaces an inferred or earlier one.

Color and layout​

  • Cyan headings separate groups; inferred sources are muted and your own are purple.
  • ui.color, NO_COLOR and terminal detection control color. ui.color=always or never wins; in auto mode NO_COLOR turns color off and CLICOLOR_FORCE=1 turns it on when NO_COLOR isn't set.
  • Long rows become labelled records on narrow terminals. Unavailable tasks show why.
  • Commands are shown for reading, not as a portable shell script. Dependencies and hooks may run more than the row shows.
  • Command previews that look like they contain credentials are hidden, and terminal controls are escaped. Don't put credentials in task arguments.

JSON and effects​

Listing runs no tasks or tools and changes no files. JSON has the task map, and each task has an origin object: kind (inferred or user-defined), source (the configuration source, or null) and override (boolean).

Outside a project and unknown tasks​

Outside a project, oyzu run lists nearby projects by folder.

  • It searches up to three levels down, skips hidden and generated folders, stops at each project and lists at most 32. It reads no child configuration and runs nothing.
  • Change into a listed project or use oyzu -C <project> run.
  • JSON returns status: "outside-project", directory, projects, searchDepth, limit and nextStep.
  • With nothing found, it fails with PROJECT_NOT_FOUND. Asking for a task from the parent folder fails with TASK_PROJECT_REQUIRED.

An unknown task fails with TASK_NOT_FOUND, the project folder, available task names and a spelling suggestion when there's a close match.

When a task runs, its result row includes the exit code and duration, for example Failed (exit 7 after 0.20s). Oyzu exits with the task's exit code. JSON records have exit_code and duration_ms (run time only, not discovery or tool setup).

Task streams​

Local tasks keep stdin.

  • In text mode, tasks that record a bundle copy stdout and stderr both to your terminal and to dist/logs, even with --quiet. Their output is a pipe, not a terminal.
  • Tasks with interactive = true get your terminal directly; their output can't be saved, so their bundle log files are empty.
  • Tasks that don't record a bundle also get your terminal directly.
  • With --json, task output is captured and stdout holds only the final result. See task output.

-q, --quietwarn
--log-level error|warn|info|debug|traceAs given
  • Flags work on either side of the subcommand. Arguments after -- belong to the child.
  • More than two -v, more than one -q, or combining these flags is an argument error.
  • Any of these flags overrides OYZU_LOG entirely.

Without a flag, OYZU_LOG can set a level or comma-separated area=level entries, optionally starting with a default level (info if omitted):

$env:OYZU_LOG = 'warn,oyzu::executor=trace'
oyzu run foo
oyzu run foo --json -v
Remove-Item Env:OYZU_LOG
  • Areas: oyzu::commands, oyzu::config, oyzu::discovery, oyzu::tools, oyzu::acquisition, oyzu::executor, oyzu::builders, oyzu::reports.
  • Unknown or repeated areas, empty entries and invalid levels are errors.
  • Help and version ignore OYZU_LOG, even invalid values.
  • These aren't oyzu.toml settings. RUST_LOG has no effect on Oyzu.

What the controls change​

  • --quiet hides routine progress and the interactive dashboard. Results, warnings, errors and child output stay.
  • Verbosity never changes native flags, environment, plans, cache inputs, report checks or release eligibility.
  • Logging is local and works offline.
  • Environment variables, headers and full argument lists are never logged. Credential-bearing parts of messages are redacted (see Redaction).
  • Child output and shell payloads you ask for aren't rewritten and may contain secrets. Trace isn't an HTTP dump.

Diagnostic content and JSON events​

  • Human diagnostics name the severity and the affected work. Operational failures also name the executable and version, the folder, the host platform and an ID when available.
  • JSON diagnostic events have type, code and message, plus severity, target, invocationId, operationId and parentOperationId. Completed operations add duration_ms.
  • Saved build logs carry the same IDs and every warning and error, whatever the console showed. Filtered console output can have gaps in its sequence numbers.
  • Sequence numbers order events within one command; they don't show cause and effect between processes. New fields and event kinds may be added, so tolerate unknown ones.
  • Reused actions can say which cache tier served them (local or remote).

Failures and lifecycle labels​

A failed command prints ✗ <what failed and how to recover> with the diagnostic code underneath (for example COMMAND_FAILED).

  • A message that already starts with its own code (✗ CONFIG_SYNTAX: …, ✗ REMOTE_COMMIT_NOT_PUSHED: …) doesn't repeat it underneath.
  • --json prints {"error", "exitCode"}, and -q prints the plain error line.
  • Internal phases are shown as words (Setup, Preflight, Source, Plan), and platform-specific targets as target · os/arch.
  • Running a task prints a heading, the shared lifecycle rows and the result, followed by the tool's own output, unchanged.

TOOL_COMPONENT_MISSING identifies a missing executable or component of a selected tool installation. Human and JSON diagnostics name the tool/version, install folder and recovery. Launch errors expose this value in JSON's code and the recovery command in nextStep. The human error leads with the code. When a failed action's diagnostic supplies a nextStep, the human build failure section shows its message above the native cause and uses that recovery in place of the generic retry hint; native output stays in its action logs. See recovery.

Redaction​

Messages redact only the credential-bearing part. Ordinary URLs and text stay readable.

PatternResult
A URL with a user name or password[sensitive diagnostic detail withheld]
URL query and fragment?[redacted]
key=value or key: value with a credential-like nameThe name stays; the value is replaced.
Authorization: or BearerThe rest of the line is redacted.

Configuration display hides any value that looks like a credential. Child output isn't rewritten.

Human presentation standard​

This is the style guide for every public command's human output: startup, progress, child output, results and failures. New and changed commands must follow it. A generic data dump or raw diagnostic envelope isn't a finished interface. Not every existing command has been reviewed against it yet.

  • Lead with the outcome and the relevant selection (such as the active profile).
  • Use short, descriptive section headings and aligned columns for comparable records. Keep empty collections compact ([] for configuration values) and leave out empty diagnostic sections. Never leave out failures or unresolved requirements.
  • Keep identifiers exact: env.CARGO_HOME, env._.path, checks.coverageMinimum and cargo-llvm-cov are copyable identifiers, not prose. Never title-case them, split them, or change their underscores and punctuation.
  • Humanize only labels the presenter owns. Group configuration settings by namespace, keeping full keys. Show booleans as true/false in configuration tables.
  • Put long identities and low-priority metadata after the useful settings. Wrap long cells without dropping characters, and use labelled records on narrow terminals. Show Windows extended paths in normal form for people, but keep machine payloads unchanged.
  • Use cyan headings, green success, yellow attention and red failures. Always include the meaning in text; color is never the only signal. Keep no-color output readable, escape terminal controls, and follow each command's redaction rules. Presentation must never reveal a value that was redacted upstream.
  • Check the compiled command in human, no-color and JSON modes. Cover long identifiers and narrow layouts. JSON schemas and executable or native payloads don't depend on presentation.

Human output leads with the outcome, then groups details into named sections. Comparable records use aligned tables; nested or long records use labelled fields without dropping values. The shared renderer uses the terminal width when it's known (100 columns otherwise) and switches to labelled records when a table would overflow. Color is extra: cyan headings, green success, yellow attention; errors keep explicit severity labels.

Color controls​

  • Shared result views use color on terminals and drop it for redirected output or TERM=dumb. A nonzero CLICOLOR_FORCE forces color, and NO_COLOR overrides forcing.
  • No project configuration is opened just to style a result.
  • JSON never contains ANSI sequences. Shell code, native streams and which paths keep their payload formats.
  • Untrusted control characters in result values are escaped before styling.

Pin output​

pin shows one compact setup table per target. For Rust it lists each compiler component and test or coverage helper separately, with a purpose column.

  • Formatting, linting, testing and coverage tools are required when those checks are enabled by the build or policy. The labels don't make checks optional.
  • Being installable isn't the same as being installed. pin doesn't check for or install tools.
  • Sources, profiles, compatibility constraints, configured requests and discovery limits are in --json rather than extra human tables. Unknown requirements stay visible.
  • Results say whether resolution completed. Incomplete resolution lists what to do below the table.
  • A platform coverage section lists the execution platforms the resolved metadata covers. That isn't a statement that tools are installed or run there. JSON keeps the full per-platform compiler_metadata.
  • Environment inspection and shell profile results use the same layout.

Choose an existing output pattern​

Quick lookup (which, version)Keep its short documented payload. No progress or decoration.

Consistency means a shared hierarchy, vocabulary and state meanings, not identical headings on payload commands. Choose the pattern in the presenter before any work starts. Application commands return outcomes and lifecycle facts; they don't choose colors, terminal modes or human versus JSON formatting.

Operation lifecycle​

  • Before slow work, show the operation and what is being checked or done. Don't hold all feedback until the end. Instant lookups need no progress.
  • Name the item or step (rust, Dependencies, Source evidence), not an internal scope like command or a repeated generic build. Context belongs in subtitles or explanatory text, not in something that looks like a work item.
  • Use one state vocabulary: › running, ✓ done or ready, ✗ failed, ! attention, and the words Skipped, Blocked or Unresolved. Starting a check isn't finishing it: mark ready only after the owning operation confirms its checks. Close started steps on failure as well as success; never leave a step looking like it's still running in a finished receipt.
  • Show elapsed or still-working feedback for long operations. Show a percentage only when there's a real total. Don't invent progress, and don't imply stalled work is healthy just because a heartbeat is printing.
  • Keep the default linear. Small redraws may update active rows and short child output on capable terminals. Persistent panes, alternate screens and interactive input must never be required.
  • Group concurrent work by target, task or tool. Indent and dim each child's recent output under its owner (about eight lines, within the shared terminal budget). Collapse it on success and keep the relevant part on failure. Never mix unattributed lines from parallel processes. Native pass-through commands keep their documented stream behavior.
  • Finish with a short outcome and the useful results, artifacts or recovery steps. Don't repeat the whole progress history. Partial success, failed checks and missing requirements must stay visible.

Routine progress must never default to envelopes like [Info] [oyzu::commands] [00:00.045] [command]. Subsystem names, timestamps and diagnostic metadata belong in requested diagnostic detail and structured logs. Warnings and errors still state their severity and keep useful codes; don't hide them to make output look clean.

Example lifecycle (illustrative):

Installing tools
  › rust                   Checking pinned installation…
  ✓ rust                   Ready · 1.95.0 · reused
  › cargo-nextest          Installing…
      Downloading package…
  ✓ cargo-nextest          Ready · installed

Installation complete
2 tools verified · 1 installed · 1 reused

A live terminal may replace the running rows; redirected output keeps a readable start and finish sequence. Both must show the same outcome.

Terminal, diagnostics and data contracts​

  • Use the shared renderer's palette and color controls. Never add command-specific ANSI codes or a second styling policy.
  • Dim native previews, not essential status or recovery steps.
  • Without terminal capabilities, print append-only text with no cursor movement. Turning off color must not remove information. Forced color may style redirected output without turning on redraws.
  • Never truncate copyable identifiers or paths at narrow widths.
  • Keep progress and diagnostics on stderr and final results on stdout, apart from the JSON, shell payload and native stream exceptions above.
  • --quiet removes routine progress, not results or failures. Verbosity adds diagnostics without changing what runs.
  • Follow the owning redaction rules: don't redact ordinary configuration, paths or versions, and never reveal protected values just because verbose output is on.

Implementation and review checklist​

For every new or changed public command:

  1. Pick its output pattern and reuse the shared presentation layer and invocation logging view. Look for an existing renderer first; extend the shared one rather than adding a local spinner, logger, palette or table formatter.
  2. Run the real compiled command. Check startup feedback, one successful outcome and a relevant failure, including that started steps are closed. A renderer unit test alone doesn't prove the command uses that renderer.
  3. Check normal human output, redirected or no-color output, JSON stdout/stderr separation and quiet mode. Check narrow and long layouts, and concurrent output where relevant. Use a real terminal for redraw changes. Say which terminals or platforms you couldn't check.
  4. Confirm payload exceptions, exit codes, redaction and the fast help/version path still work. Presentation must not change tool flags, plans, cache identity, recorded results or policy.
  5. Update the owning reference page and record what you checked. Fix inconsistencies in the command you changed; note unrelated gaps rather than claiming the whole CLI complies.

Help and startup​

oyzu --help, oyzu help build, nested --help, --version and unknown-command errors come from the built-in command list.

  • They work with an empty PATH, broken project files and a -C folder that doesn't exist.
  • They don't load project configuration, refresh policy, open tool stores, start workers or contact services. No installation or account is needed.
  • A native tool shim's --help still runs that tool's help.
  • oyzu run list, oyzu discover and oyzu which are real operations, not help; they read the project and its configuration.

Configuration inheritance in nested projects​

oyzu.toml settings, including tool pins, inherit from the Git worktree root. build.yaml doesn't inherit: the nearest build.yaml up the tree decides the builds (a build.yaml belonging to another tool never does).

So a project nested in a repository sees the repository's tool pins. Pass --root . to make the current folder the root for both and stop inheritance. See configuration.

Scripts and parsing​

Human output can change between releases; don't parse it. Pass --json for pin, discovery, bundle and tool inspection, and configuration output. Each command has its own result shape; there's no universal result schema.
