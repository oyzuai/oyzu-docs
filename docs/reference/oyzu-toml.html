oyzu.toml reference

CLI reference

Published from the canonical docs/reference/oyzu-toml.md file. Features marked experimental remain experimental; check support limitations before relying on them.

oyzu.toml says how, where and how strictly your builds run: tool versions, environment variables, tasks, check levels, caching and the values that change between your laptop, a pull request and a release. It never says what is built; that is native manifests and build.yaml (which file a setting belongs in).

Most projects need no oyzu.toml at all. Add one when you want to pin a tool, add a task, or change a default. Every key on this page is checked against the CLI's settings registry by a test, so the complete list is exactly what the current CLI accepts.

A complete example​

#:schema https://github.com/oyzuai/oyzu/releases/latest/download/oyzu.toml.schema.json

# Tool versions. A prefix ("22") picks the newest matching release;
# oyzu.lock records the exact version for every platform.
[tools]
node = "22"
go   = "1.27.3"

# Environment for tasks, builds and activated shells.
[env]
APP_MODE = "development"

# A task: run it with `oyzu run seed`.
[tasks.seed]
argv = ["node", "scripts/seed.mjs"]

# How strict each check is. Fast local builds run only `required` checks.
[checks]
lint = "advisory"
coverageMinimum = 70

# Stricter values for one context: local, pr, ci or release.
[context.release.checks]
tests = "required"
coverageMinimum = 85

# Build-wide scheduling and caching.
[build]
jobs = 8

[cache]
local = true

# A named set of other tool versions, for verification runs in CI.
[toolsets.node24]
tools.node = "24"

Check it without running anything:

oyzu config validate --strict
oyzu config explain checks.coverageMinimum

Files and precedence​

Oyzu reads several files and combines them. A nearer, more specific file wins over a farther one.

FileWhereTypical useCommit it?
Machine configurationWindows: ProgramData Oyzu\config.toml; macOS: /Library/Application Support/Oyzu/config.toml; Linux: /etc/oyzu/config.tomlDefaults for everyone on a host—
User configurationWindows: RoamingAppData Oyzu\config.toml; macOS: ~/Library/Application Support/Oyzu/config.toml; Linux: $XDG_CONFIG_HOME/oyzu/config.toml (else ~/.config/oyzu/config.toml)Your personal defaults, credentials destinations, trust—
Root oyzu.tomlThe project root (the Git top level)Team settings for the whole projectYes
Folder oyzu.tomlAny folder below the rootSettings for the builds in that folderYes
oyzu.local.tomlNext to any oyzu.tomlPersonal overrides for one checkoutNo
InvocationFlags such as --jobs, --profile; OYZU_* variablesOne command—

OYZU_USER_CONFIG=/absolute/path.toml replaces the user file, which is useful for disposable environments.

The order, lowest first: built-in defaults, organization policy defaults, machine, user, each oyzu.toml from the root down to the build's folder, each oyzu.local.toml in the same order, then the invocation. Each file applies its base values, then its context values, then the selected profile. Administrative policy and [constraints] are applied last and cannot be overridden by an ordinary file.

Values replace, they don't merge. A list in a nearer file replaces the whole list; a task in a nearer file replaces the whole task record. To delete an inherited environment variable or task, see [overrides].

In CI, user configuration (other than presentation settings) and oyzu.local.toml files are left out, so a CI build depends only on committed files. --local-overrides asks for local files, if policy allows it.

To see where a value came from:

oyzu config explain build.jobs
oyzu config show --json

A section name Oyzu doesn't know produces a warning (with a spelling hint when it is close to a known one) and has no effect; oyzu config validate --strict turns those warnings into errors. A build.yaml key written here, such as [builds.web], is only such a warning to the CLI; the editor schema flags it as belonging in build.yaml.

[tools]​

Tool versions, by tool name. Oyzu resolves each request to an exact version, records it in oyzu.lock, installs it once into the shared tool store and puts it on PATH for builds, tasks and shells.

[tools]
node = "22"            # newest 22.x
go = "1.27.3"          # exactly 1.27.3
rust = "1.99.1"
"oyzu:gh" = { version = "2.49.2" }   # table form; same meaning
KeyValuesDefaultMeaning
tools.<name>A version request string ("22", "1.27", "1.27.3", "latest"), or { version = "…" }noneRequests that tool. A prefix selects the newest matching release; latest the newest eligible one. Short names (node) and canonical ids ("oyzu:node") name the same tool.
tools.ignoreList of tool namesnoneSilences best-effort tool detection for builds in this folder and below. Never removes a primary toolchain; an explicit [tools] entry still provides the tool.
tools.platformsList of os/arch/abi platformsbuilt-in setWhich platforms oyzu pin resolves lock metadata for. Not a profile value; it does not change which platforms are built.
  • Native pins come first. A version a native file already pins (rust-toolchain.toml, Go's go.mod minimum, and others as each ecosystem is adopted) is the request; a [tools] value in the same or a nearer folder must agree with it. See tools and toolchains.
  • Tools never vary by profile or context. [profiles.x.tools] and [context.release.tools] are refused; use a toolset to try other versions.
  • Edit with commands instead of by hand: oyzu install node@22, oyzu update, oyzu uninstall node. See tool commands.

[env]​

Environment variables for tasks, builds and activated shells.

[env]
APP_MODE = "development"

[env._]
path = { prepend = ["tools/bin"] }     # relative to this file
KeyValuesDefaultMeaning
env.<NAME>A string, or { secret = "<reference>" }noneSets the variable. Names use ASCII letters, digits and _, starting with a letter or _; the OYZU_ prefix is reserved. Values are literal: no interpolation. Secret references are accepted but not yet delivered to tasks.
env._.pathA list of folders, or { prepend = […], append = […] }noneAdds folders to PATH, relative to the declaring file. A nearer file's value replaces a farther one's.

Literal values can enter build inputs and evidence, so never put a secret in [env]. Inspection redacts credential-like names, but that does not make [env] a secret store. See shell activation for how [env] reaches your shell and how it is restored when you leave the folder.

[tasks]​

Commands you run with oyzu run <name>, and hooks that run around build stages (pre_build, post_test and so on). In a multi-target project, prefix the target: [tasks."api:test"].

[tasks.seed]
argv = ["node", "scripts/seed.mjs"]        # argument array: no shell
env = { SEED_SIZE = "small" }

[tasks.lint]
run = "eslint . && prettier --check ."     # a shell command
shell = "bash"

[tasks."api:post_build"]
argv = ["node", "scripts/stamp.mjs"]
outputs = ["dist/stamp.json"]
cache = true                               # cacheable by `oyzu build`
FieldValuesMeaning
runStringA shell command. Use either run or argv. Extra arguments after -- are refused.
argvList of stringsA program and its arguments, with no shell. Arguments after oyzu run name -- are appended. Elements may use {namespace.name} placeholders.
shellStringThe shell for run, such as bash or sh.
cwdPathWorking directory, relative to the declaring oyzu.toml.
envTable of stringsVariables for this task only.
depends_onList of task namesTasks to run first.
inputsList of pathsExtra inputs for caching (inside the target).
outputsList of pathsFiles the task produces.
cacheBooleanWith outputs, lets oyzu build reuse the task's result.
interactiveBooleanKeep the real terminal instead of capturing output to dist/logs.
reportsReport declarationsTest and coverage reports the task writes.
when, unlessCondition tablePlan-time conditions (context, platform…). See task and hook conditions.

A nearer file's task replaces the whole record; fields are never merged. See build tasks for hooks, streams and limits.

[checks]​

How strict each check is, and which checks a build runs.

[checks]
format = "off"
lint = "advisory"
coverageMinimum = 70

checks.coveragesameenforceLevel for coverage collection.
checks.lintsameenforceLevel for linters.
checks.formatsameenforceLevel for format checks.
checks.runrequired · allrequired; all in pr, ci and releaseWhich checks a build runs: only required ones, or every check that is not off.

So a plain local oyzu build runs only required checks, CI runs everything that is not off, and oyzu build --full runs everything locally. See check levels.

[context]​

Values that apply only in one build context. <name> is exactly local, pr, ci or release; the context is detected from the CI provider and Git ref, or forced with --context or OYZU_CONTEXT.

[checks]
coverageMinimum = 50

[context.pr.checks]
coverageMinimum = 70

[context.release]
checks.coverageMinimum = 90
build.optimized = true
  • Write settings under it as you would at the top level. Settings that a profile can't hold can't vary by context either (trust controls, directories, profile.default, plugin and engine bindings, session endpoints); the Scope column marks them "no profiles or contexts".
  • Within one file, a context value beats the base value and an inferred ci profile, but loses to a profile you chose with --profile.
  • Between files, the nearer file still wins: a folder's base value beats the root's [context.release] value. To vary a folder by context, put a context table in that folder's file.
  • Tools can't vary by context, and build-wide settings (build.jobs, cache.*, ui.color…) take context values only in the root file.

See per-context values and build context.

[profiles]​

A named set of values you choose per command with --profile <name> (or OYZU_PROFILE). [profile] default picks one when nothing else does.

[profile]
default = "dev"

[profiles.dev.build]
jobs = 3

[profiles.integration.env]
API_URL = "http://localhost:8080"
oyzu --profile integration run test
oyzu --no-profile build
oyzu config profiles

A profile never grants authority and never changes tools (CONFIG_PROFILE_TOOLS; use a toolset). Settings that pick executable code or trust (plugins.*, engines.*, trust.*, directories and keys) are refused in profiles. In CI with no profile chosen, Oyzu's built-in ci profile applies, which sets checks.run = "all".

[toolsets]​

Other tool versions to verify a build with, without changing what ships. Each toolset adds a verification run (build and test stages, no artifact) for builds whose builder uses one of its tools.

[tools]
node = "22"

[toolsets.node24]
tools.node = "24"
contexts = ["ci", "release"]   # default: every context except local
platforms = ["linux/x86_64"]   # default: one run on the build's first platform
FieldValuesDefaultMeaning
toolsTable like [tools]—The versions this toolset replaces. Tools it doesn't name keep their [tools] value.
contextsList of local · pr · ci · releasepr, ci, releaseContexts whose builds add this toolset's verification run. [] turns it off.
platformsList of os/arch[/abi]the build's first platformOne verification run per listed platform.
oyzu --toolset node24 exec -- node --version
oyzu build --verify-with node24

Toolsets live in project files (oyzu.toml, oyzu.local.toml) only, not in profiles, contexts, user or machine configuration. The nearest definition of a name applies whole. See toolsets and verification toolsets.

[constraints]​

Rules that hold in every folder of the project. Only the root oyzu.toml may contain [constraints]; they apply after every ordinary value, so no folder can undercut them. Name the setting by its full key, in quotes.

# root oyzu.toml
[constraints."checks.tests"]
minimum = "required"
when = { context = ["release"] }

[constraints."checks.coverageMinimum"]
minimum = 60

[[constraints."build.optimized"]]
locked = true
value = true
when = { context = ["release"] }
FieldMeaning
locked + valueThe setting is exactly this value.
allowedThe value must be one of these.
minimum, maximumBounds for numbers and ordered levels (off < advisory < enforce < required).
requiredItems a list must contain.
when, unlessSelectors: context, provider, path (relative to the root).

Settings that only user or machine files can hold, administrative settings, env.* and tasks.* can't be constrained here. See project constraints.

[overrides]​

KeyValuesMeaning

Editor completion​

Add the schema line at the top of the file and an editor with Taplo (for example VS Code's Even Better TOML) completes keys and flags wrong values:

#:schema https://github.com/oyzuai/oyzu/releases/latest/download/oyzu.toml.schema.json

oyzu config schema oyzu.toml prints the same schema offline. The CLI's own checks stay authoritative; see editor schemas.

Commands​

CommandDoes
oyzu config validate [--strict] [--all-profiles]Checks every file; --strict also fails on warnings.
oyzu config get <key>Prints the effective value.
oyzu config explain <key>Shows the value, every source that set it, and why it won.
oyzu config showPrints the whole effective configuration.
oyzu config set <key> <value> (--project | --local | --global)Writes a value to the project oyzu.toml, its oyzu.local.toml or the user file; exactly one is required. Add --profile NAME to write inside that profile.
oyzu config unset <key> (--project | --local | --global)Removes it from that file, exposing inherited values.
oyzu config profilesLists profiles and which is selected.
oyzu config schema oyzu.tomlPrints the JSON Schema.

None of them run project tasks. Add --json for machine-readable output.

Errors​

CodeMeansFix
CONFIG_INVALID_VALUEA value has the wrong type or is out of rangeThe message names the file, line and allowed values.
CONFIG_SCOPEThe setting isn't allowed in this file (a credential destination in a project file, [publish] in a folder, a trust setting in a profile)Move it where the message says.
CONFIG_PROFILE_TOOLS[profiles.<name>.tools]Use [toolsets.<name>.tools].
CONFIG_TOOLSET_UNKNOWN--toolset names a toolset this folder doesn't seeThe message lists the toolsets defined here.
CONFIG_TOOLSET_INVALIDBad contexts or platforms, or a non-tool key under a toolset's toolsFix the toolset fields.
CONFIG_OVERRIDE_DENIEDA value contradicts a policy or project constraintUse an allowed value, or change the constraint.
CONFIG_CONSTRAINT_INVALIDA [constraints] entry is malformed or names a setting a project can't constrainFollow the message.
CONFIG_UNKNOWN_OPTIONALUnknown section or key (a warning)Check the spelling hint; --strict makes it an error.
