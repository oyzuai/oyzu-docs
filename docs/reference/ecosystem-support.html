Ecosystem support and maturity

CLI reference

Published from the canonical docs/reference/ecosystem-support.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Use this page to choose a build path and understand what has actually been demonstrated. Oyzu is experimental and unreleased. A working example is not a promise that every project, operating system or architecture in that language works. No row below claims general release qualification.

Reviewed against merged documentation on 2026-10-21. Evidence links retain their original tested revisions; this documentation update did not rerun builds. Detailed usage belongs to the linked ecosystem reference. The ecosystem expansion roadmap records future CMake, SwiftPM, Xcode and Android integrations separately.

How to read maturity​

LabelMeaning
PlannedA roadmap item; no usable builder is claimed
Implemented, unverifiedCode or an adapter exists, but the named end-to-end product flow has no passing proof in the linked record
Functionally verifiedA real compiled-CLI flow produced its expected artifact, applicable reports and the stated consumer/inspection result on the named platform
Broadly qualifiedA declared compatibility matrix and its acceptance checks have passed; no ecosystem is assigned this label here

Unsupported means the current path cannot serve that scenario. Unverified means evidence is missing; it is not a statement that the scenario cannot work. Native-tool probes, discovery and unit tests alone do not earn a functionally verified label for an Oyzu build. Individual rows can have verified subsets and unverified extensions. Maturity is about that subset, not an ecosystem-wide score.

Keep these dimensions separate:

  • Profile: package manager, project layout, artifact type and native test/build integration. Here this is descriptive terminology, not a new configuration key or an Oyzu configuration profile.
  • Mode: native host execution versus captured/isolated execution. One mode's proof does not establish the other. Native execution does not promise isolation.
  • Implementation: a built-in builder versus a selected external plugin. Their supported subsets can differ; selecting a plugin does not provide automatic fallback to the built-in builder.
  • Platform: the host that runs Oyzu and the execution/artifact target. A Windows host running Linux containers proves Linux execution, not native Windows builds.

Framework/report support is another dimension. The built-in integration has dedicated Node quality, direct testing and workspace reporting contracts. The external plugin's proved automatic integrations are Node's built-in test runner and the bounded native npm/Vitest row above. Jest and Mocha still require authored reports in that plugin. Captured/workspace Vitest and other versions remain unqualified. Its Vite admission is limited to the native npm row above; workspace and other admission exclusions remain explicit in the plugin reference.

For example, “pnpm works” may mean a native single-root application produces a directory, or a captured workspace produces several publishable packages. Those are two separate promises. “Yarn support” must identify Classic versus modern Yarn. None of these labels asks users to configure a new profile: native manifests, locks and the selected builder determine the applicable integration.

Platform coverage and future work​

Windows, macOS and Linux are intended host platforms. Windows ARM64 and macOS (Intel and Apple Silicon) are not yet supported or tested for this matrix's builder coverage. The evidence above is deliberately narrower than the intended host list. In particular, Linux container execution on Windows does not qualify Windows SDKs or Windows containers, and a multi-platform tool lock does not prove a build on every listed architecture. Windows ARM64, macOS, Linux ARM64 and additional Windows x86_64 flows need individually scoped implementation/qualification work before expanding the relevant support claim.

C/C++ through CMake, Swift packages through SwiftPM, Apple applications through Xcode, and Android through Gradle are planned. See the roadmap and first proofs. Running one of their tools through oyzu exec or an authored task does not by itself establish a native builder with discovery, artifacts and report gates.

Keeping this table current​

Update the affected row in the same PR that changes a supported flow, admission limit or qualification result. Keep detailed usage in its owning reference and commands, source revisions, reports and failures in the qualification/status record. Add a profile row when manager, mode or artifact support differs; do not promote an entire language because one fixture passed. Preserve historical evidence attribution when a later change removes a limitation.

This page is the current support index; it does not duplicate proof logs or replace the documentation maintenance standard. Public evidence is available in the repository's qualification records and dated status records.
