Tool Python Installation

CLI reference

Published from the canonical docs/reference/tool-python-installation.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Indexed installation and pinning use the organization catalog contract. A matching verified index record is preferred without a catalog; with one, only approved indexed releases install. The provider evidence command uses the same metadata adapter as installation. Linux ARM64 GNU joins the native host/lock matrix (Tailscale remains Linux-only); macOS amd64 and musl are excluded. See implementation status for automated verification. Live publisher evidence and native ARM64 qualification remain pending.

Oyzu can prepare CPython itself for a Python build, so a fresh checkout needs no Python installed. See tool management for shared prerequisites and native host builds for which projects use it.

Usage​

Pinning is optional. For a project the native Python build supports, oyzu build resolves a CPython release, writes oyzu.lock, installs it into the shared tool store and builds with it:

oyzu build            # no Python on PATH, no pin needed
oyzu pin              # optional: preview or refresh the selection
oyzu exec -- python --version

Pin explicitly with a request in oyzu.toml; an explicit request takes precedence:

[tools]
python = "3.12"       # latest 3.12.x; ranges such as ">=3.11 <3.14" also work

How a version is chosen​

SourceRole
[tools] python in oyzu.tomlThe request, when present
.python-version (one release such as 3.12 or 3.12.4)The default request
[project] requires-python in pyproject.tomlA constraint every selection must satisfy
NeitherThe greatest stable release available

The selection is the greatest stable CPython satisfying the request and every constraint. Pre-releases, free-threaded and debug builds are never selected. requires-python is translated with PEP 440 meaning (<=3.12 is exactly 3.12.0, ~=3.10 is >=3.10, <4). !=, === and local/pre-release specifiers cannot be expressed as a tool range and fail with the specifier named; set [tools] python to choose a version instead. A request nothing satisfies names the tool, the request, each constraint and the file it came from.

Source and verification​

Distributions come from Python Build Standalone (install_only archives for Linux amd64/arm64 GNU, macOS arm64 and Windows amd64). Oyzu reads the publisher's latest-release.json, then that release's SHA256SUMS, and records the archive URL (which embeds the release tag) and declared digest in oyzu.lock. A pinned lock restores without network access to the catalog. Digests come from the publisher's checksum manifest, not a signature; downloaded bytes are verified against them. Oyzu does not redistribute these archives.

Administrative tools routes scoped to python, oyzu:python or * use the same host connector bindings as Node and Go: a base serving latest-release.json and the release assets under the same relative paths. There is no public fallback from a configured route.

What the installed tree omits​

The distribution bundles a terminfo database whose entries differ only by letter case (for example 2621A and 2621a). No case-insensitive filesystem can hold both and the store refuses such archives, so the layout declares exclude_paths: ["share/terminfo"] (see archive layout). The exclusion is part of the digest-bound layout, applies to tar archives only, and may never remove a required path, launcher or executable. CPython's curses finds terminfo on the system at run time; builds do not need the bundled copy. The python command launches the real interpreter (bin/python3.X); bin/python, python3 and pip remain in the tree and on PATH.

Installed interpreter and bytecode​

The installed CPython is verified when it is installed (archive digest and layout) and trusted afterwards; later builds, tasks, oyzu exec and shells do not re-hash it (see the decision). Python therefore runs normally and may write __pycache__ bytecode beside the standard library, as it does in any install, without affecting later builds. Earlier builds re-hashed the installed payload on every run, so the first bytecode write made the second build fail with installed payload differs from receipt, as root and as an unprivileged user.

  • Editing or damaging the installed tree is not detected up front. A broken interpreter fails when it runs; delete that tool install to reinstall it.
  • A store whose earlier build hit the old failure works again without being discarded.

Limits and verification​

  • Only the native pip wheel path uses this today (pyproject.toml with the pip manager). requirements-only, uv, Poetry and legacy projects still use the isolated executor, which needs Docker.
  • Python supplies python, python3 and its python3.X alias through frozen execution and shims. When the installation includes pip, pip, pip3 and pip3.X run the selected interpreter with -m pip; Windows does not need a Scripts/pip.exe launcher. No separate pip declaration is required. Existing installed records and frozen locks remain valid. After upgrading Oyzu, refresh an existing fixed shims directory with oyzu reshim.
  • pip fetches the project's build backend from the package index during the wheel build; --offline builds fail when it is not already cached.
  • The newest stable CPython is chosen when a project declares nothing, which can be a very recent release; declare requires-python or pin to avoid surprises.
  • Two consecutive builds against one store pass as root and as an unprivileged user on Linux x86_64 (2026-10-07); tooling/test-fresh-checkout.py --project python repeats the second build. macOS and Windows are not verified.
  • Verified on Linux x86_64 only (2026-10-07): the python-api fixture built a wheel from an empty store with no Python on PATH in about 20 seconds, and an explicit python = "3.12" selected 3.12.15. Windows, macOS, offline restoration, proxy/connector routing and real third-party license review of the bundled components are not verified. See the fresh-checkout record.
