npm workspace builds and development tasks

CLI reference

Published from the canonical docs/reference/npm-workspaces.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Oyzu builds and tests an npm workspace using npm's native workspace membership and installed dependency graph. It supports private aggregation roots and publishable root packages, with independent snapshot packages and test reports. Use it from a conventional npm workspace root with no Oyzu configuration.

Status: experimental. This integration does not yet complete every EX-020 requirement; affected selection, member task groups and duplicate target selection remain unfinished.

Prerequisites and quick start​

From a conventional npm workspace root containing package.json and its native lock, with dependencies installed:

oyzu run list
oyzu run build
oyzu run test
oyzu run lint
oyzu run format-check
oyzu run format

For a captured build, which needs Docker and a provisioned npm toolchain image:

oyzu build
oyzu inspect dist

Prerequisites:

RequirementDetail
Node and npmProvide Node/npm and install the project's native dependencies yourself. Oyzu does not install tools.
Measured versionsNative development verification uses Node 24/npm 11 on Windows; CI provisions Node 22/npm 11 on Windows, macOS and Linux. These measured versions do not establish compatibility with every older version.
Oyzu configurationNone required.
Quality toolsDefault quality tasks additionally require the selected ESLint/Prettier or Biome tools and their supporting packages. Installed project packages take precedence; a declared but missing tool fails.

For a project without those quality tools, supply the provisioned defaults described in the Node quality reference, using OYZU_NODE_QUALITY_HOME for development. That directory contains the quality toolchain's package.json and node_modules. Oyzu does not fetch missing checkers.

Versions​

Captured builds resolve artifact versions per native member using scoped Git baselines and the transitive local dependency graph.

  • Unrelated member changes do not advance a package's base.
  • Shared root inputs conservatively affect all members.
  • Packaged local references use each dependency's selected version.

Static listing and installed workspaces​

run list is static and does not invoke Node/npm or project scripts. Explicit execution resolves installed workspace facts with npm's bundled membership library and Arborist. Missing dependencies or native tools can therefore allow listing but prevent execution. Provision dependencies with the project's normal npm workflow, then retry.

Checks before member commands run:

  • Installed workspace links must resolve to their declared member directories. Identity comparison uses native canonical paths so directory aliases do not change ownership.
  • A link to a different directory or a copied package in place of a workspace link fails before member commands run; repair the native installation and retry.
  • A root package's declared workspace dependency is validated against its actual version/specification using npm's native validator. Arborist's synthetic membership edge describes a local path and is not a substitute for that dependency constraint.
  • Invalid required declarations fail before member execution even when a workspace link exists; optional dependency handling retains native edge semantics.

Task selection and ownership​

  • Native script names remain visible in task listing, including a root format:check alias. When that alias owns the operation, use oyzu run format:check; Oyzu does not add a duplicate format-check task.
  • Existing TOML task replacements take precedence over inferred tasks. See configuration for settings, profiles and task override behavior.

Tests​

Workspace tests resolve each member's installed framework, including hoisted dependencies. Native Jest/Vitest/Mocha entrypoints come from their package bin declarations.

  • Implicit Node suites use native test filename patterns; implicit parent suites exclude nested members and engine state.
  • Explicit scripts keep their own selection semantics, so a script can deliberately aggregate other packages.
  • A private root without a test script is an aggregation container and has no additional implicit root suite.
  • Native assertion failures fail the aggregate while allowing later suites to run; discovery, missing-runner or selection errors can stop the operation before later suites start.
  • Missing Node tests currently fail explicitly instead of producing an empty successful suite.
  • The bounded Node selection allows at most 4,096 files and 24,000 path characters.

Development test commands preserve native console output and script argument forwarding and export the test-only bundle described below. Use oyzu build for captured execution and snapshot artifacts. Native scripts and framework configuration execute on the host during run test; only static listing is nonexecuting.

Quality checks​

  • Default root checks exclude workspace members. Default member checks exclude nested members, so a parent default cannot bypass a child's explicit script ownership.
  • The current quality file scope is JavaScript/TypeScript and their supported JSX, CommonJS and ESM extensions. Dependency directories, engine state, build output and coverage are excluded; source symlinks are not followed.
  • Native ESLint configuration and Prettier configuration/ignores are respected. This is not yet a general formatter for all repository file types.
  • Default checks are read-only. format writes files and is never selected as an implicit build check.
  • A user-authored script can perform its own effects; its name does not establish that it is read-only.
  • A failed member build stops dependent compilation. Quality failures continue through the other members to collect diagnostics, then fail the aggregate.
  • Already executed script effects or explicit formatting writes are not rolled back.

Arguments and limits​

  • Native scripts receive forwarded arguments through npm.
  • A composed operation containing any default quality checker rejects extra arguments before invoking member operations; define a native script or explicit argv task for custom checker options.
  • Native Biome configuration can select Biome instead of the ESLint/Prettier defaults for a member; see Node quality for supported versions and scope.
  • Cyclic workspace build dependencies currently fail before member build execution.
  • Large development plans exceeding the current 20,000-byte encoded plan bound fail with a host argument-limit error.

Public entry checks before packaging​

For a coarse native root build, the shared captured workspace runtime checks concrete public JavaScript entries selected by Node's import and require conditions before packaging.

  • It also checks concrete declaration files selected by Node's types condition and literal legacy declaration paths; file presence does not establish TypeScript validity.
  • A missing selected regular file fails the build, while null exclusions and conditional alternatives remain native Node decisions.
  • This prepack check does not certify that npm included those files in its archive, nor does it validate browser/custom conditions or every wildcard path.
  • See the pnpm qualification record for the bounded native omission evidence; it is a shared workspace check, not pnpm-specific packaging behavior.

Direct test bundles​

oyzu run test writes a test-only dist/ bundle with JUnit and LCOV for each package. No reporting section is needed. Run oyzu inspect dist to check the bundle. See direct test evidence for history, preserved host output and host-isolation disclosures.

  • An explicit root test script owns one aggregate report pair; otherwise each member has a pair, plus an implicit root suite when the root is publishable.
  • Named report IDs use the same native package identity as captured builds.
  • A failing assertion fails the command but retains available sibling reports; Oyzu's success-only post hook is blocked.

What it uses​

This workflow uses already installed native dependencies.

  • Native membership and installed link identities are observed only after an explicit, admitted test request; run list still executes no native code.
  • The frozen report contract is built before hooks or prerequisites execute, so install the workspace dependencies before invoking tests.
  • This does not acquire dependencies, update package versions or rewrite the lockfile. Ordinary host network access and native npm configuration remain in effect.

The same package test adapter now serves captured and host execution.

  • Implicit suites exclude nested members, and Jest/Vitest/Mocha resolve configuration from the package being tested, including native scripted members.
  • Native scripts retain their npm lifecycle and forwarded arguments.
  • Framework/reporting prerequisites match the single-package profiles; notably Vitest needs its matching coverage provider and Mocha needs native c8.

Custom commands​

  • Custom commands keep their body but must supply required reports. They receive per-package OYZU_TEST_REPORT and OYZU_COVERAGE_REPORT paths when invoked by the native workspace composition.
  • Replacing the entire workspace task must fulfill its package report obligations or declare explicit report collection paths through the shared task contract.
  • A marker-only command that previously returned success now fails for missing evidence; no successful test report is invented for it.
  • Root aggregate report declarations can redirect the single pair of native destinations. Individually redirecting every native member report through configuration is not implemented.

Probe​

python tooling/test-npm-workspace-direct.py --cli <compiled-path> copies EX-020, provisions its native local npm links, and proves direct tests, separate member reports, hooks, failed/sibling evidence, unchanged metadata and bundle inspection.

  • The mixed-framework probe below also checks a publishable root and nested members through report bundles.
  • CI runs these only after the CLI is compiled.
  • Measured host results and pending CI results are recorded in implementation status.

Captured builds and evidence​

oyzu build requires Docker and a provisioned npm toolchain image; see CLI image provisioning. It captures source and locked dependencies, resolves the native graph, and prepares snapshot versions in a private execution copy.

oyzu build
oyzu inspect dist
  • Execution replays prepared dependencies offline. Acquisition can access configured sources; the build does not authorize arbitrary new downloads.
  • Development run tasks use the host environment and normal npm configuration, so they do not provide this isolation guarantee.

Packages​

  • Each member declares its own npm archive with a version containing the captured source identity.
  • A root without private: true additionally produces a root package; a private aggregation root does not.
  • Local dependency references are projected to the member snapshot versions.
  • Native npm selects package contents. Engine state is excluded; root staging rejects symlinks, inconsistent inventories and selections above 100,000 files or 1 GiB.
  • The repository's manifests and lock are not version-edited in place.
  • Creating an artifact, including one for a private member, does not authorize publication.
  • Members that share a package name, or are versioned latest, fail before acquisition; see member names.

Lock records​

  • Acquisition requires a lock record for every native member whose recorded name, if present, matches the member.
  • A member's own version in the lock is left to native npm ci, which reconciles it with that member's package.json; planning reads versions from package.json and projects them into the private copy's lock.
  • A lock that is stale in a way npm itself rejects, such as a member version that no longer satisfies a sibling's dependency, still fails during acquisition with npm's own error.

Local folder dependencies​

file: dependencies on local folders are admitted, in workspaces and single projects alike. npm records each one as a link ("link": true) plus a lock record for the folder, for example "@oyzu-example/fixture-helper": "file:tools/fixture-helper" in the EX-020 npm-file-link variation.

  • The folder must be a relative path inside the captured source, outside node_modules, with its own lock record and package.json, and no symbolic link on the way.
  • Native npm links it during installation; the folder is captured as source, never acquired.
  • Registry packages that npm locks beneath the folder (tools/fixture-helper/node_modules/...) are captured like a member's.
  • A link to anything else fails acquisition with npm link is not a captured native workspace or local folder.
  • The folder is not a workspace member, so it gets no artifact, tests or version projection of its own; root quality checks cover its source as root-owned files.

Tests and reports​

  • An explicit root test script owns one aggregate invocation. Otherwise member suites run individually and a publishable root also requires its own tests.
  • Supported native Node/Jest/Vitest/Mocha integrations produce JUnit and coverage; arbitrary custom commands must satisfy their report obligations.
  • A publishable root with no discoverable Node tests currently fails.
  • Root framework filtering excludes members and engine state while retaining native project exclusions; Jest filtering handles canonical and aliased root paths.
  • Implicit member tests in captured builds use the same package-owned scope selection as development tests. Planned exclusions prevent a parent implicit suite from rediscovering its nested members; explicit scripts retain native selection.

Bundle​

  • The resulting dist/manifest.json records retained artifacts, reports and status alongside the plan, envelope and logs.
  • Test and quality failures block final artifact collection.
  • Native package receipts detect archive changes between packaging and collection.
  • Missing or invalid required reports remain failures, including under task overrides.
  • inspect checks bundle integrity, not production trust or release eligibility.
  • Earlier bundles are preserved under .oyzu/history.

Member names​

Every workspace member is packaged as its own snapshot archive, under its package name and a version derived from its own version. A root without private: true is packaged too; a private root is not. On 2026-10-10 the maintainer decided that members which cannot be packaged that way fail with an error that names every affected member and its path, and are never skipped silently. Two conditions fail:

  • a package name is used by more than one member, or by a publishable root and a member;
  • a member's version is latest.

npm membership is resolved first, before any dependency is acquired, so both conditions are reported together in one error with the stable code NPM_WORKSPACE_MEMBER_NAMES. Paths are relative to the workspace root. For the EX-020 npm-member-names variation:

NPM_WORKSPACE_MEMBER_NAMES: npm workspace members need distinct package names and real versions to be packaged
  package name "@oyzu-example/core" is used by "." (publishable workspace root), "packages/core"
  version "latest" is not a package version: "test", "test/installation"
Remedy: rename packages so each name is used once, or mark the workspace root "private": true so the root is not packaged; give each listed member a semver "version" such as "0.0.0" in its package.json; "private": true on a member does not exclude it, because every member is packaged.
  • In oyzu build this text appears inside the npm dependency preparation failed diagnostic. Nothing has been acquired, no artifact is produced and the source is unchanged.
  • oyzu run workspace tasks resolve the same membership and stop with the same error; static oyzu run list does not resolve membership and is unaffected.

To recover:

  • Rename members so each package name is used once. When the root only coordinates the workspace, "private": true on the root also works, because a private root is not packaged. The nestjs/nest repository has this shape: its root and packages/core are both named @nestjs/core.
  • Give each latest member a semver version, such as 0.0.0. Marking the member "private": true does not help: private members are packaged like any other, and excluding a member from packaging is not implemented. The puppeteer/puppeteer repository has this shape: its test and test/installation members are already private and versioned latest.

Other messages:

  • npm itself refuses members that share a name. Oyzu takes those members from npm's report and lists them with the other problems.
  • If npm cannot list the remaining members after excluding them, which happens when a duplicate's path contains glob syntax, the error says that other members were not checked.
  • Other invalid member names or versions still fail with npm workspace requires a valid native name/version, and a publishable root with an invalid name or version with Publishable npm workspace root requires a valid native name/version.
  • This check covers npm workspaces only; pnpm and Yarn keep their existing checks.

node --test tooling/test-npm-member-names.mjs covers the error text, private roots and npm's duplicate report with the provisioned npm; python tooling/test-npm-workspaces.py runs the npm-member-names variation through native acquisition, and the compiled-CLI node-workspaces group builds it. None of these has been run for this change yet, and the nestjs/nest and puppeteer/puppeteer repositories have not been re-run; see implementation status.

Verification and current limits​

The native probes exercise real npm packaging, snapshot dependency references, relocated archive reproducibility, root/member reports, failures and quality ownership:

python tooling/test-npm-workspace-build.py
python tooling/test-npm-workspace-tasks.py --cli target/debug/oyzu
python tooling/test-npm-workspace-tests.py --cli target/debug/oyzu
  • node --test tooling/test-node-lock.mjs covers file: link admission and member-version ownership without npm; python tooling/test-npm-workspaces.py acquires and replays the npm-file-link variation with native npm, and the compiled-CLI node-workspaces group builds it. Those native and compiled-CLI runs have not yet been recorded for this change; see implementation status.
  • Use target/debug/oyzu.exe on Windows and provision native quality tools first.
  • The workspace test probe also needs the native dependencies from tooling/fixtures/jest and tooling/fixtures/vitest; override their locations with --jest-modules and --vitest-modules. It verifies native Node, Jest 29 and Vitest 5, not arbitrary framework versions.
  • The Jest reporter probe additionally needs --jest-cli pointing to an installed native Jest entrypoint.
  • CI builds the CLI before these host checks and runs separate compiled-CLI captured-build scenarios on Linux. Native probes do not by themselves prove sandbox behavior.
  • Revision-specific results and outstanding cross-host verification are recorded in implementation status.

Mocha 11 workspace reporting additionally uses native c8 10, preserves package-local reporters and produces per-package evidence for implicit and recognized scripted suites.

  • python tooling/test-mocha-reporting.py --cli target/debug/oyzu provisions and exercises its native workspace fixture; the captured Node suite independently checks versioned package outputs and failed-member gating.
  • Implicit Mocha suites use native --ignore options for member/engine-state exclusions; explicit native scripts retain their selection scope.

Other limits:

  • Additional test frameworks, complete framework configuration inheritance, cyclic graphs, affected selection, caching and publication remain separate work.
  • Native workspace test bundles now also support pnpm/Yarn direct execution.
  • Direct test bundles contain host test evidence, not the captured build's versioned artifacts.
  • This reference describes the npm integration, not a claim of complete builder or scenario support.

Related​

  • Yarn Classic workspace builds now share captured artifact/report planning and stage composition, while native acquisition, version projection and packing remain manager-owned. See that reference for its narrower evidence and remaining gaps.
  • pnpm workspace builds also consume the common artifact/report planner, with pnpm-owned importer projection and native archive creation. Their isolated CLI acceptance remains pending.
