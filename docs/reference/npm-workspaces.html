npm workspace builds

CLI reference

Published from the canonical docs/reference/npm-workspaces.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Oyzu builds and tests an npm workspace using npm's own workspace membership and installed dependency graph. It handles private aggregation roots and publishable root packages, producing an independent package archive and test reports for each package. Run it from a conventional npm workspace root with no Oyzu configuration.

Note: npm workspace support is experimental. Affected-only selection, member task groups and duplicate target selection are not available. See Limits.

Builds use the Node builder plugin, which must be installed and selected (see plugin packages). There are three ways to build a workspace:

ModeWhere it runsOutputSection
Development tasksYour machine, with oyzu runTest-only bundleDirect test bundles
Native workspace packagesYour machine, with oyzu buildOne archive per packageExternal native workspace packages
Captured workspace packagesIsolated Linux worker (Docker)One archive per packageExternal captured workspace packages

Quick start​

From a workspace root that has package.json, its native lock and installed dependencies:

oyzu run list
oyzu run build
oyzu run test
oyzu run lint
oyzu run format-check
oyzu run format

For an isolated build, which needs Docker and the base execution image:

oyzu build
oyzu inspect dist

Prerequisites​

RequirementDetail
Node and npmProvide Node and npm and install the project's dependencies yourself. Oyzu does not install them for development tasks. Tested with Node 22 and 24 and npm 11.
Oyzu configurationNone required.
Quality toolsDefault quality tasks need the ESLint and Prettier (or Biome) tools and their packages. Installed project packages take precedence. A declared but missing tool fails.

If your project has no quality tools, oyzu pin records the defaults described in Node quality. Task preparation installs that exact set in the shared tool store. Project-installed tools win, and a declared but uninstalled dependency fails instead of falling back.

Static listing and installed workspaces​

oyzu run list is static. It does not run Node, npm or any project script. Running a task reads the installed workspace using npm's own libraries, so missing dependencies or tools let you list tasks but stop you from running them. Install dependencies with your normal npm workflow, then retry.

Before any member command runs, Oyzu checks that:

  • Each installed workspace link resolves to its declared member directory. A link to another directory, or a copied package where a link belongs, fails. Repair the installation and retry.
  • A root package's declared workspace dependency matches the member's actual version, using npm's own validator. An invalid required declaration fails even when a link exists. Optional dependencies keep npm's usual behavior.

Versions​

Isolated builds version each member using scoped Git baselines and the local dependency graph.

  • A change to an unrelated member does not advance a package's version.
  • Shared root inputs affect all members.
  • Local references in packaged members use each dependency's selected version.

Task selection and ownership​

OperationRoot script existsNo root script
buildRuns once with npm's lifecycle hooksRuns member build scripts in dependency order. Members without a script are reported as not requesting compilation
testRuns once with npm's pretest and posttest hooksRuns each member's test script or detected Node, Jest, Vitest or Mocha runner. A publishable root also runs its own implicit suite
lintRuns onceChecks root-owned source. Uses each member's lint script or the selected ESLint or Biome
format-checkRuns format-check or format:check onceChecks root-owned source. Uses each member's script or the selected Prettier or Biome check
formatRuns once, only when you askFormats root-owned source. Uses each member's format script or the selected Prettier or Biome
  • Native script names show up in task listings, including a root format:check. When that alias owns the operation, run oyzu run format:check. Oyzu does not add a second format-check task.
  • Task replacements in your TOML configuration take precedence over inferred tasks (see configuration).

Tests​

Each member's installed test framework is found, including hoisted dependencies. Jest, Vitest and Mocha entry points come from their package bin declarations.

  • Implicit Node suites use native test filename patterns and skip nested members and engine state.
  • Explicit scripts keep their own selection, so a script can deliberately cover other packages.
  • A private root with no test script is just a container and gets no implicit suite.
  • A failing assertion fails the run but lets later suites run. Discovery, missing-runner or selection errors can stop the run before later suites start.
  • A package with no Node tests fails instead of producing an empty successful suite.
  • Node test selection handles at most 4,096 files and 24,000 path characters.
  • A publishable root without a test script joins the conventional workspace fan-out as an implicit suite. Its planned command retains the selected workspace invocation; the native adapter dispatches the root's detected framework without recursively running the workspace command. Member report collection remains required. Authored task replacements and explicit root scripts retain their original invocation and run once as an aggregate.

Development test commands keep native console output and forward script arguments. Native scripts and framework configuration run on the host during oyzu run test. Only listing runs nothing.

Quality checks​

  • Default root checks skip workspace members. Default member checks skip nested members, so a parent default cannot bypass a child's own script.
  • The default file scope is JavaScript and TypeScript (including JSX, CommonJS and ESM extensions). Dependency directories, engine state, build output and coverage are excluded, and source symlinks are not followed.
  • Native ESLint, Prettier and Biome configuration and ignore files are respected. Oyzu does not format other file types.
  • Default checks are read-only. format writes files and is never run as an implicit build check.
  • Your own scripts can do anything. A script named lint is not assumed to be read-only.
  • A failed member build stops the builds that depend on it. A failed quality check lets the other members continue, so you see all diagnostics, then fails the run.
  • Files already written by scripts or by format are not rolled back.

Arguments and limits​

  • Arguments are forwarded to native scripts through npm.
  • An operation that runs a default quality checker rejects extra arguments. Define a native script or an explicit argv task to pass options to a checker.
  • A Biome configuration makes a member use Biome instead of ESLint and Prettier (see Node quality).
  • A cycle in workspace build dependencies fails before any member build starts.
  • A plan larger than 20,000 bytes fails with a host argument-limit error.

Public entry checks before packaging​

For a coarse root build, Oyzu checks the concrete JavaScript files your packages publish before packing:

  • Files selected by Node's import and require conditions must exist.
  • Declaration files selected by the types condition and literal legacy declaration paths must exist. Existence is checked, not TypeScript validity.
  • A missing regular file fails the build. Null exclusions and conditional alternatives are left to Node.
  • The check does not confirm npm put those files in the archive, and it skips browser or custom conditions and wildcard-only paths.

Direct test bundles​

oyzu run test writes a test-only dist/ bundle with JUnit and LCOV for each package. No reporting configuration is needed. Run oyzu inspect dist to check the bundle. See direct tests for how existing output is preserved and what the bundle does and does not claim. For pnpm and Yarn Classic workspaces, see workspace test bundles.

  • An explicit root test script owns one aggregate report pair. Otherwise each member has a pair, plus a pair for the root when it is publishable.
  • Report names use the same package identity as isolated builds.
  • Each suite's allocated filenames include its report identity, such as package-api-junit.xml and package-api-coverage.lcov, within that suite's report directory. Members can use the same native report basenames without colliding in the protocol. Bundle manifest paths identify the collected files; destinations remain unique ignoring ASCII case, including on Windows.
  • A failing assertion fails the command but keeps the reports that exist, and Oyzu's success-only post hook is skipped.
  • These bundles hold host test results. They are not versioned build artifacts.

What it uses:

  • Your installed dependencies. Oyzu does not download dependencies, update versions or rewrite the lock. Normal host network access and npm configuration apply.
  • Install dependencies before running tests. The report contract is built before hooks and prerequisites run.
  • Membership and installed links are read only after you ask for a test run. Listing still runs no native code.
  • Jest, Vitest and Mocha read configuration from the package under test. Prerequisites match the single-package profiles. Vitest needs its matching coverage provider and Mocha needs c8. See Mocha.

Custom commands​

  • A custom command keeps its body but must write the required reports. It receives per-package OYZU_TEST_REPORT and OYZU_COVERAGE_REPORT paths when run by the workspace composition.
  • Replacing the whole workspace test task means your task must write each package's reports or declare report collection paths.
  • A command that exits successfully without writing reports now fails. Oyzu never invents a passing report.
  • Report declarations on a root aggregate can redirect the single pair. Redirecting each member's report through configuration is not supported.

Isolated builds and evidence​

oyzu build runs isolated. It needs Docker and the base execution image, with Node (and any pinned npm) restored from oyzu.lock. It captures your source and locked dependencies, resolves the workspace graph and prepares versions in a private copy.

oyzu build
oyzu inspect dist
  • Execution replays prepared dependencies offline. Acquisition uses your configured sources, and the build itself cannot download anything else.
  • Development oyzu run tasks use the host environment and do not have this isolation.
  • Isolated builds also recognize package-local lifecycles (pre, build, post), including literal copy outputs beside the manifest. Members and a publishable root are built in dependency order, even when npm's membership data doesn't name the root as a link target. Known protected or foreign writes are refused before any fallback. Opaque or fan-out root scripts keep the root-owned route with public-entry validation.

Packages​

  • Each member produces its own npm archive. Its version contains the captured source identity.
  • A root without "private": true also produces a root package. A private aggregation root does not.
  • Local dependency references are rewritten to the members' snapshot versions.
  • npm selects package contents. Engine state is excluded. Root staging rejects symlinks, inconsistent file lists and selections over 100,000 files or 1 GiB.
  • Your manifests and lock are never edited in place.
  • Making an archive, even for a private member, does not publish it.
  • Members that share a package name, or are versioned latest, fail before acquisition (see Member names).

Lock records​

  • Every member needs a lock record, and its recorded name (if present) must match the member.
  • A member's own version in the lock is left to npm ci, which reconciles it with package.json. Planning reads versions from package.json and writes them into the private copy's lock.
  • A stale lock that npm itself rejects, such as a member version that no longer satisfies a sibling's dependency, fails during acquisition with npm's own error.

Local folder dependencies​

file: dependencies on local folders work in workspaces and single projects. npm records each as a link ("link": true) plus a lock record for the folder, for example "@oyzu-example/fixture-helper": "file:tools/fixture-helper" (see the npm-file-link example).

  • The folder must be a relative path inside the captured source and outside node_modules. It needs its own lock record and package.json, with no symbolic link on the way.
  • npm links it during installation. The folder is captured as source, never downloaded.
  • Registry packages that npm locks under the folder (tools/fixture-helper/node_modules/...) are captured like a member's.
  • A link to anything else fails with npm link is not a captured native workspace or local folder.
  • The folder is not a workspace member. It gets no artifact, tests or version of its own, and root quality checks cover its source as root-owned files.

Tests and reports​

  • An explicit root test script runs once as one aggregate. Otherwise member suites run individually, and a publishable root needs its own tests too.
  • Node, Jest, Vitest and Mocha produce JUnit and coverage automatically. Custom commands must write their reports.
  • A publishable root with no discoverable Node tests fails.
  • Implicit suites use the same package-scoped test selection as development tests. A parent suite never rediscovers its nested members.

Bundle​

  • dist/manifest.json lists artifacts, reports and status next to the plan, envelope and logs.
  • Test and quality failures stop artifact collection.
  • Package receipts detect archive changes between packing and collection.
  • Missing or invalid required reports fail the build, even with task overrides.
  • inspect checks bundle integrity, not trust or release eligibility.
  • Earlier bundles are kept under .oyzu/history.

Native workspace packages​

For a conventional npm workspace with a publishable root and package-local builds, select the node/package builder. It runs on your machine, without Docker.

builds:
  package: {uses: node/package}
oyzu --json build package --full --no-cache
oyzu inspect dist

Keep the genuine package-lock.json. The builder produces one archive and one JUnit/LCOV report pair for each publishable package. A project with a root, an app member and a shared member produces three archives and six reports.

Supported: Windows x64, with Node 22.23.3 and npm 11.11.0. Each package declares its native version, exports and files. Builds are flat literal copies (for example copy source.cjs dist.cjs on Windows), and each package has implicit Node tests. Lint and read-only format checks need working project scripts or provisioned checkers. The builder does not install fallback quality tools.

How it works:

  1. Oyzu runs npm ci --ignore-scripts in a private workspace to read membership and installed links, then fixes each package's version, commands, archive location and report location.
  2. The ordinary npm ci then runs once with native lifecycle scripts and Oyzu hooks. Its result is checked before versions and local references are rewritten in the private copy.
  3. Packages build in dependency order (shared, then app, then root). Native pre, build and post scripts and selected Oyzu hooks run as usual.
  4. Each package's implicit Node tests write its own JUnit and LCOV. A publishable root cannot borrow a member's report.
  5. npm pack --json --ignore-scripts runs after the required checks, writing to a fresh output location.

Your source and native locks are unchanged. The first normal build may add the plugin selection to oyzu.lock. Use each artifact's recorded path, digest and version instead of guessing npm's file names.

Installing the three archives into an empty project with an empty npm cache and --offline works, and root imports through app and shared. Producer-side downloads still follow your configuration and network controls.

ProblemWhat to do
Stale or missing lock, or an invalid installed workspace linkRepair the manifests and lock with npm and retry.
Replaced install task, or install unavailable or disabledUse the ordinary npm ci task. The builder refuses other install setups before preparing the workspace.
Failed build or check, missing package report, or an invalid pack file listFix that package. A failed required step blocks all archive export.
Aggregate or opaque build, replaced build or test task, or a write outside the packageNot supported by this builder. Package-local ownership rules stay in force.

Not supported yet: private aggregation roots, authored aggregate tasks, framework builds, pnpm and Yarn in this mode (see their pages), macOS, Windows ARM64, Linux hosts and Linux ARM64. For isolated builds see captured workspace packages.

Native TypeScript workspace packages​

Note: Experimental. Supported on Linux x86_64 (GNU) only. Windows, macOS and ARM64 are not supported for this profile.

A publishable root and one shared member each build with tsc -p tsconfig.json. The root imports shared through its package metadata, so shared compiles first. Each package's main or exports and types point to JavaScript and declarations under its own dist/. Tested with Node 22.23.3, npm 11.11.0 and TypeScript 7.0.2.

Keep contained rootDir and outDir values with separate source and output folders, and set noEmitOnError: true:

{
  "compilerOptions": {
    "target": "ES2022",
    "module": "NodeNext",
    "moduleResolution": "NodeNext",
    "rootDir": "src",
    "outDir": "dist",
    "declaration": true,
    "noEmitOnError": true
  },
  "include": ["src/**/*.ts"]
}

Set type: commonjs in each package (the CommonJS output is what is supported). Select node/package and run the build as above. You get two npm archives and four JUnit/LCOV reports. A TypeScript error in shared stops the root compile and both archives. TypeScript owns type resolution, diagnostics, emitted files and exit codes.

Before building, Oyzu checks every JavaScript and declaration output path, and any build-info path, against protected and prepared-owner paths inside the package's dist/.

  • Incremental and composite builds need an explicit, checked tsBuildInfoFile.
  • noEmitOnError alone does not guarantee the compiler writes nothing.
  • Configuration inheritance (extends), project references, outFile, JSON-module copying, unchecked emission and extra command-line forms are refused.

Isolated workspace packages​

For isolated builds, select the node/package builder and an installed Node plugin package whose engine includes the coordinator and execution runtimes:

builds:
  workspace:
    uses: node/package

Keep tool requests in oyzu.toml or native pins, and the genuine npm lock next to the workspace manifests. Build YAML contains no tool pins. For example, the tested project requests Node 22.23.3 and npm 11.11.0 under [tools]. With the npm image and tool archives available:

oyzu --json build workspace --isolated --platform linux/amd64 --full --no-cache --image npm=<image>

An unadopted package makes oyzu pin refuse with PLUGIN_NOT_ADOPTED. Run a normal build once to adopt the plugin and create oyzu.lock, then keep that lock for later --frozen runs.

Supported: a publishable root with publishable members, Node 22.23.3 and npm 11.11.0, on a Windows x64 coordinator with a Linux amd64 worker. Three archives and six reports (one pair per package) are produced, and the archives install in a source-free offline consumer. Not supported: Linux hosts as the coordinator, native-host workspace packages and other platforms.

How it works:

  • Oyzu reads npm's prepared membership and installed links, then fixes each package's version, Node test files, report locations and archive slot.
  • Versions and local references are rewritten only in the private copy. Dependency builds are ordered, and npm packs each package.
  • npm still runs each package's prebuild, build and postbuild. Oyzu's build hooks wrap the whole build once.
  • Each publishable package needs discoverable implicit Node tests. Reports are collected before packing and export.
  • Your manifests and the lock are unchanged.

Package-local copy builds and hooks are recognized. Replaced build or test tasks, and a root aggregate test, are refused before any task or hook runs. Dependency preparation may already have happened. Dependency or package-test failures block archive delivery.

Aggregate root builds​

An opaque root build, or one that is not package-local, runs its original npm run build once at the workspace root. It does not add member builds. Recognized package-local builds keep their ordering. A local root with opaque or nonlocal member dispatch is refused.

  • The root script must produce every package's outputs.
  • Each package still needs implicit Node tests and its own JUnit and LCOV before packing.
  • Protected configuration writes, writes to another package's output, and reads or writes outside the source are refused even inside a coarse root body.
  • An explicit npm --workspace call may write only its own member's ordinary outputs through its lifecycle and same-owner helpers. That permission does not carry to later root commands. Changing directory or --prefix does not change which package owns the writes.

You can also replace the whole build with a task in oyzu.toml:

[tasks."workspace:build"]
argv = ["npm", "run", "build"]

Even identical argv counts as a replacement, so all native member builds are skipped. npm lifecycle scripts run only if your command invokes npm. Oyzu build hooks wrap the selected build once. No setting picks the build route.

Aggregate root tests​

An explicit root test script runs unchanged, once, with pretest and posttest. No implicit package suites run afterward. A workspace:test task replacement can run the same script. Either way, the script must write JUnit and LCOV for every package.

Default report locations use the package name. For g17-shared, the member writes .oyzu/plugin-reports/package-g17-shared/junit.xml and coverage.lcov under its own folder, such as packages/shared/.oyzu/plugin-reports/package-g17-shared/. The root and other members have their own named pairs. No single OYZU_TEST_REPORT or OYZU_COVERAGE_REPORT is provided for these multiple packages.

A task.reports declaration on the test task is refused before the task or hooks run, because it cannot guarantee a report for each package. Dependency capture may already have happened. Redirecting package reports is not supported. Without a root aggregate test, npm workspaces keep implicit suites.

Archive versions​

Archive versions come from Oyzu's version rules, not from the manifests. For example, with every manifest at 0.1.0, the root might get 0.0.0-dev.<source-id> and the members 0.1.0-dev.<source-id>. Dependency references inside the archives match.

Member names​

Every workspace member is packaged as its own archive, under its package name and a version derived from its version. A root without "private": true is packaged too. A private root is not. Members that can't be packaged this way fail with an error naming every affected member and path. Two conditions fail:

  • A package name is used by more than one member, or by a publishable root and a member.
  • A member's version is latest.

Oyzu resolves npm membership first, before acquiring dependencies, and reports both conditions in one error with the code NPM_WORKSPACE_MEMBER_NAMES. Paths are relative to the workspace root. For the npm-member-names example:

NPM_WORKSPACE_MEMBER_NAMES: npm workspace members need distinct package names and real versions to be packaged
  package name "@oyzu-example/core" is used by "." (publishable workspace root), "packages/core"
  version "latest" is not a package version: "test", "test/installation"
Remedy: rename packages so each name is used once, or mark the workspace root "private": true so the root is not packaged; give each listed member a semver "version" such as "0.0.0" in its package.json; "private": true on a member does not exclude it, because every member is packaged.
  • In oyzu build, this text appears inside the npm dependency preparation failed diagnostic. Nothing is acquired, no artifact is produced and the source is unchanged.
  • oyzu run workspace tasks stop with the same error. oyzu run list does not resolve membership and is unaffected.

To fix it:

  • Rename members so each package name is used once. If the root only coordinates the workspace, "private": true on the root also works, because a private root is not packaged.
  • Give each latest member a semver version, such as 0.0.0. Marking the member "private": true does not help. Private members are packaged like any other, and excluding a member from packaging is not supported.

Other messages:

  • npm itself refuses members that share a name. Oyzu takes them from npm's report and lists them with the other problems.
  • If npm can't list the remaining members after the duplicates are excluded (this happens when a duplicate's path contains glob syntax), the error says that other members were not checked.
  • Other invalid member names or versions fail with npm workspace requires a valid native name/version. A publishable root with an invalid name or version fails with Publishable npm workspace root requires a valid native name/version.
  • This check covers npm workspaces only. pnpm and Yarn keep their own checks.

Limits​

  • Frameworks other than Node's runner, Jest, Vitest and Mocha, full framework configuration inheritance, cyclic workspace graphs, affected selection, caching and publication are not supported.
  • Direct test bundles contain host test results, not the versioned artifacts of an isolated build.
  • Platform support is listed with each mode above. Platforms not listed there are not supported yet.
