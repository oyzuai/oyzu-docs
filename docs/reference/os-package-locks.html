OS package locks (oyzu lock)

CLI reference

Published from the canonical docs/reference/os-package-locks.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Experimental. oyzu lock writes debs.lock.yaml and apks.lock.yaml for Docker targets: a reviewed record of every Debian or Alpine package file an image installs, with its URL, version, checksum and Package URL. It implements the observation and lock half of the OS package locks draft. When a target has a lock, oyzu build installs from it: RUN steps see only a loopback snapshot repository that serves the locked files (see Frozen builds). Regenerated metadata and Alpine HTTPS trust are not implemented yet; see Limitations.

Tool versions are locked by oyzu pin, not by this command.

What it does​

Nothing in build.yaml or the Dockerfile changes. For each docker/image target, oyzu lock:

  1. Finds the stages that contribute to the final image (through FROM <stage>, COPY --from and RUN --mount=from=) and have at least one RUN.
  2. Pins each external base to its index digest and pulls it for this host's platform. A tag keeps the digest already in the lock unless you pass --update.
  3. Builds each of those stages once with docker buildx build --load --target, substituting the pinned bases through named build contexts, with the network the host has. This runs the team's own RUN steps.
  4. Copies the package database out of each built stage and its base (/var/lib/dpkg/status or /lib/apk/db/installed) without starting either, and takes the difference. That difference is the lock. The RUN shell is never parsed, so a literal apt-get install line, a variable, a heredoc or a copied script all lock the same packages.
  5. Asks where each new package comes from:
    • Debian and Ubuntu. apt runs inside the built stage (apt-get update, apt-get download --print-uris, apt-cache madison). apt verifies each repository's signed InRelease against the image's own keyring, so the URL, size and SHA-256 come from verified metadata. Any apt signature warning is a failure (OS_PACKAGE_UNVERIFIED), because apt can report a bad signature as a warning and continue.
    • Alpine. Oyzu reads /etc/apk/repositories and /etc/apk/arch from the built stage, fetches each repository's APKINDEX.tar.gz, finds the exact version, downloads the .apk, checks its size against the index and records its SHA-256.
  6. Writes the lock next to the Dockerfile and prints what changed.

Package files and repository metadata seen while locking are kept by SHA-256 in a local store (<user data>/os-packages/blobs), ready for prepared frozen builds.

Usage​

oyzu lock                   Write missing locks and regenerate stale ones
oyzu lock --check           Fail if any lock is missing or stale; writes nothing
oyzu lock --update          Re-observe every lock with fresh bases and no build cache
oyzu lock --update api      Re-observe only the api target's locks (or name a lock path)
oyzu lock --inputs --json   List locked packages and bases for Renovate; resolves nothing

Every form accepts the global --json flag.

$ oyzu lock
api-image  locked 9 OS packages (2 requested, 7 dependencies) in services/api/debs.lock.yaml
note: commit services/api/debs.lock.yaml with your change

"Requested" packages are those apt did not mark Auto-Installed, or that are new in Alpine's /etc/apk/world.

Prerequisites and platforms​

Docker with Linux containers and buildx on PATH (Docker Desktop on Windows and macOS, or Docker Engine on Linux), with network access to the base image registry and the distribution mirrors. Standard HTTPS_PROXY/NO_PROXY and SSL_CERT_FILE settings apply to Oyzu's own Alpine downloads.

Locks cover this host's architecture only: amd64 or arm64 (x86_64 or aarch64 in Alpine terms). A non-final stage must have a name (AS <name>) to be observed, because BuildKit can only target named stages.

The lock file​

# debs.lock.yaml, written by oyzu lock. Do not edit; run `oyzu lock` after changing the Dockerfile.
lockfileVersion: 1
lockfileVendor: oyzu
inputDigest: sha256:9f2c…
stages:
- stage: '0'
  base: docker.io/library/python@sha256:a6e3…
  observed: true
arches:
- arch: amd64
  repositories:
  - repoid: debian-bookworm
    uri: http://deb.debian.org/debian
    suite: bookworm
    release: sha256:61d0…
  packages:
  - url: http://deb.debian.org/debian/pool/main/p/postgresql-15/libpq5_15.8-0%2bdeb12u1_amd64.deb
    repoid: debian-bookworm
    name: libpq5
    evr: 15.8-0+deb12u1
    checksum: sha256:7a3c…
    size: 191234
    purl: pkg:deb/debian/libpq5@15.8-0%2Bdeb12u1?arch=amd64&distro=debian-12
    sourcerpm: postgresql-15
    requested: true
    stage: '0'

url, repoid, checksum and size follow Hermeto's lock schema; name, evr and sourcerpm follow rpm-lockfile-prototype. inputDigest, stages, repositories, purl, requested and stage are Oyzu additions. Unnamed stages are named by index. Packages are sorted by name, version and stage, with no timestamps, so the same inputs and repository state produce the same bytes.

release is the SHA-256 of the repository's verified InRelease (apt) or of the APKINDEX.tar.gz the package was found in (apk). url is the live mirror URL apt or apk used; snapshot-service URLs are not written yet.

A Dockerfile whose stages use both Debian and Alpine bases gets both files. When an image stops installing one kind of package, oyzu lock removes that file.

Staleness​

A lock is stale when its inputDigest differs from the current inputs. The digest covers, for each locked stage:

  • the FROM references and the stage's instructions up to its last RUN that looks like a package install, including the same span of any stage it starts from;
  • the contents of build-context files that COPY/ADD instructions in that span read, with line endings normalized so Windows and Linux checkouts agree;
  • the stage's pinned base digest;

plus global ARG lines and the locked architecture set. A RUN "looks like an install" when it names apt-get, apt, aptitude, dpkg or apk, or runs a file copied earlier in the stage. That is only a hint for where the digest stops: a miss can only make a lock look stale or let a later frozen build fail with OS_PACKAGE_NOT_LOCKED, never produce a wrong lock. Files copied after the last install, such as application source, never make the lock stale.

oyzu lock --check is offline. A digest-pinned FROM is compared with the lock's base; a tag keeps the lock's digest for the same repository, so a tag that moves upstream makes the lock behind, not stale. oyzu lock --update picks up the new digest.

Stale reasons, in the order checked: a locked stage was removed; its base digest changed; its FROM now names another repository; a stage now installs packages and is in no lock; this host's architecture is not locked; the Dockerfile or the files its install steps copy changed.

Machine-readable report​

{
  "format": 1,
  "mode": "write",
  "outcome": "written",
  "locks": [
    {
      "path": "services/api/debs.lock.yaml",
      "target": "api-image",
      "reason": "base digest changed for stage 0 (… -> …)",
      "written": true,
      "packages": 9,
      "requested": 2,
      "changes": [
        {"purl": "pkg:deb/debian/libpq5?arch=amd64&distro=debian-12", "stage": "0",
         "from": "15.7-0+deb12u1", "to": "15.8-0+deb12u1", "requested": true}
      ]
    }
  ]
}

mode is write, update, check or inputs. outcome is written or current for writes, current or stale for --check, and listed for --inputs. A change with no from is an added package and one with no to was removed. reason is created, update, removed, current or the stale reason.

--check entries carry status (current, stale or missing), and for the latter two code: OS_PACKAGE_LOCK_STALE, reason and fix: oyzu lock. A missing entry's path is the target's directory.

--inputs entries list dependencies: each base as {depName, currentDigest, datasource: docker} and each package as {depName, currentValue, datasource: deb|apk, registryUrl, purl, requested, stage}. A Debian registryUrl carries Renovate's suite, components and binaryArch parameters.

Frozen builds​

When a Docker target has debs.lock.yaml or apks.lock.yaml, oyzu build prepares a snapshot repository before execution and never writes the lock:

  1. A stale lock fails with OS_PACKAGE_LOCK_STALE. Run oyzu lock first.
  2. For the host architecture, Oyzu collects each locked Debian repository's InRelease and the index files it lists (also under by-hash), each Alpine APKINDEX.tar.gz, and every locked package file, from the local store at <user data>/os-packages/blobs. Packages missing from the store are downloaded and must match the lock's checksum and size. apt may keep its lists recompressed, so for each index apt read at lock time (recorded under <user data>/os-packages/indexes; otherwise each component's Packages), a variant the InRelease signs is downloaded by hash when the store holds none, and must match that hash.
  3. The prepared tree (index.json mapping URL to SHA-256, plus blobs/) is copied into the BuildKit worker, which has no network, and served by oyzu-docker-snapshot on 127.0.0.1:3128. Its digest is part of the build record (extensions."oyzu.dev/docker".osPackages).
  4. RUN steps get host networking inside the worker (--allow network.host, which only reaches loopback there) and http_proxy/https_proxy build arguments pointing at the server.

apt verifies the served InRelease with the image's own keyring and every file against its checksums, exactly as at lock time. The server always answers with the full locked file and never with 304 Not Modified, so lists an image already carries (python:*-slim ships an InRelease) cannot stand in for the locked metadata. A request for anything not in the lock gets 404, and a failed build reports it as OS_PACKAGE_NOT_LOCKED naming the package, in the build's error output and its retained log. Targets without a lock build as before.

The worker image must include oyzu-docker-snapshot; rebuild the local oyzu-toolchain/docker image (tooling/images/docker-metadata.Dockerfile) after updating Oyzu.

Exit status​

ExitMeaning
0Locks written or already current; --check found every lock current
1An operational error, such as a failed observation build
2Invalid command arguments
3Configuration or policy validation failed
4--check found a missing or stale lock

Errors​

CodeWhenRecovery
OS_PACKAGE_LOCK_STALE--check found a missing or stale lockoyzu lock
OS_PACKAGE_UNRESOLVABLEapt or apk cannot locate an installed version in the stage's configured repositories, for example a .deb installed by file, or a version replaced upstream between the build and the lookupInstall from a configured repository, or run oyzu lock again
OS_PACKAGE_UNVERIFIEDapt reported a signature problem, or a repository has no signed InReleaseFix the repository's signing key in the image
OS_PACKAGE_UNAVAILABLEOyzu could not download an Alpine index or package, a locked file no longer matches its checksum, or a frozen build needs signed metadata this machine's store does not hold (a lock written elsewhere)Check network and proxy settings, or run oyzu lock --update on this machine
OS_PACKAGE_NOT_LOCKEDA frozen build's RUN step asked for a package file the lock does not containoyzu lock --update, or remove the install
OS_PACKAGE_METADATA_EXPIREDA frozen build's locked Debian InRelease is past its Valid-Untiloyzu lock --update
OS_PACKAGE_UPDATE_SELECTOR--update pkg:… selects a single packageUpdate the whole lock or its target

A failed observation build reports the last lines of BuildKit's output.

Limitations​

  • Frozen builds replay original metadata only. Debian metadata past its Valid-Until, or absent from this machine's store, needs regenerated metadata signed with a per-build key (proven in oyzu#152); that is not built yet, so those builds fail with OS_PACKAGE_METADATA_EXPIRED or OS_PACKAGE_UNAVAILABLE.
  • Alpine HTTPS trust. The snapshot server terminates TLS for locked Alpine hosts with a per-build CA, but injecting that CA into RUN steps without leaving it in the image is not implemented, so HTTPS Alpine repositories fail certificate checks in frozen builds.
  • Host architecture only. Frozen builds serve the lock entries for the host architecture.
  • Observation is not recorded through the broker. The observation build has the host's ordinary network, and the lock is cross-checked against the package manager's own metadata rather than against a record of fetched files.
  • Single package updates. --update pkg:deb/debian/libpq5 is refused; updating one package while keeping the others needs observation through the snapshot repository.
  • Not implemented from the draft: input files (debs.in.yaml), --suggest, RPM locks, multiple architectures, snapshot-service URLs and Alpine index signature verification (Oyzu relies on HTTPS for APKINDEX.tar.gz; the size check binds each .apk to the fetched index).
  • Dockerfile reading covers stages, global ARG defaults, line continuations, heredocs and COPY --from/RUN --mount=from=. .dockerignore is not applied to the digest, and files read by RUN --mount=type=bind are not covered. A RUN that runs a file it bind-mounts from the build context still counts as an install, so its stage is observed and locked; a later edit to that file leaves the lock current, and a frozen build refuses any package it adds.

Verification​

Unit tests cover Dockerfile stages and install hints, package database parsing, PURLs, lock round trips, change reports, staleness reasons and Renovate inputs. tests/integration/os_package_locks.rs drives the compiled CLI against real Docker builds for Debian (OSLOCK-02, 03, 08 and the lock half of 01), a copied-in script (lock half of 06), Alpine (lock half of 07) and a multi-stage build (lock half of 09), plus a frozen Debian build from the snapshot (frozen half of 01) and a bind-mounted script that later asks for an unlocked package, which the frozen build refuses as OS_PACKAGE_NOT_LOCKED naming it (frozen half of 06). They are ignored by default because they need Docker, network and a rebuilt oyzu-toolchain/docker image:

oyzu exec -- cargo test --locked --test integration os_package_locks -- --ignored --test-threads 1

All five passed on 2026-10-10 on Windows 11 with Docker Desktop (Linux containers), against a freshly rebuilt oyzu-toolchain/docker:buildkit0.25.0.
