Python application containers

CLI reference

Published from the canonical docs/reference/python-containers.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Set with.container: true on a python/app build to package the tested application archive into an OCI image. You need no Dockerfile and no second application build.

Note: Experimental. Supported for isolated builds on Linux. There is no startup smoke test of the application, and the image is built for CPython 3.12 only.

builds:
  api:
    uses: python/app
    with:
      container: true

Build with oyzu build --isolated. A native build refuses a container request with native build does not support these declared relationships; select --isolated explicitly.

oyzu build runs the application's build, test, lint and format steps as usual, and then adds the image steps under a derived target named api-container in the plan and manifest. You can't run those derived steps directly with oyzu run or override them with hooks. If one of your own targets already has the derived name, the build fails instead of overwriting it.

with.container belongs to python/app. oyzu config validate and every command that reads your builds check it. It is refused on any other builder, including python/library, and so is the older top-level container: field (the message names with.container).

Prerequisites​

  • The Python toolchain and dependencies described in Python applications
  • python:3.12-slim-bookworm in your local Docker image store
  • The base execution image. The image helpers ship in the Docker plugin package (Docker images)
  • The right AppArmor profile, where your host needs one

Oyzu doesn't pull any other missing image, install Docker or change host security settings.

Default image​

The python-pure-zip-3.12-v1 profile needs a pure-Python, ZIP-compatible application and CPython 3.12.

Oyzu checks the local base image's implementation and Python version without using the network and uses exactly that image content. If the image changes during the build, the build fails. Provision base images by a process you trust. Oyzu does not authenticate to registries, and a matching image is not an approval of its contents.

Oyzu doesn't add ports, health checks, a server lifecycle, deployment settings or secrets. Nothing is installed during image assembly. The archive already contains its runtime dependencies.

Focused overrides​

Use an object to change the defaults. Every field is optional, and {} behaves like true.

builds:
  api:
    uses: python/app
    with:
      container:
        base: registry.example/python-runtime:3.12
        user: "1000:1001"
        workdir: /srv/api
        entrypoint: [python, /app/application.pyz]
FieldValuesNotes
baseAn image reference, up to 512 bytesMust already be in your local store with CPython 3.12. It gets the same check as the default base. No pull and no public fallback
userNumeric UID:GID, each up to 4294967295Names and negative IDs fail. This identity also owns the copied archive
workdirAbsolute path, up to 1,024 bytes, using letters, digits and /._-, with no ..Doesn't move the archive from /app/application.pyz
entrypoint1 to 64 non-empty arguments, up to 4,096 bytes each, no control charactersUsed as given. No shell or variable expansion

Unknown keys, wrong types and explicit null values fail validation.

A custom entrypoint is recorded as launch metadata. It doesn't prove that the program exists or that your service starts. The runtime check still runs, and changing the entrypoint doesn't choose between several console scripts in the application. The overrides give no production approval.

with.container: false means no container everywhere. The build counts as having no image.

Outputs and checks​

The application, wheel and sdist artifacts are still produced. The derived target adds an image artifact, for example api-container/artifacts/api-0.1.0-dev.g<source>.oci.tar. The image version uses the SemVer spelling, not Python's PEP 440 version. The manifest records the file digest and the OCI digest.

Image steps start after the application's tests, required reports and quality checks pass. A failure there blocks the image.

  • Oyzu copies the exact tested archive into an empty private build context. Generated image files never enter your checkout.
  • Assertions on the image's content and platform produce their own JUnit report. No application coverage is invented for the image.
  • Failed image assertions block the image from reaching the bundle. Read the logs and reports, fix the error and rebuild.

The configuration engine applies precedence and policy. Docker's eligibility is checked together with the application before preparation. docker.apparmorProfile comes from your resolved configuration and is fixed for the image step, and no environment variable overrides it. A profile name doesn't grant signing or publishing rights. In a managed setup, connector restrictions apply to application downloads, and there is no managed fallback.

Limits​

  • The application's startup is not tested. Passing archive tests and image assertions doesn't show that it starts.
  • Legacy and native Python application layouts, container matrices, other language runtimes and centrally configured runtime profiles are not supported.
  • Discovery doesn't turn on containers for you.
