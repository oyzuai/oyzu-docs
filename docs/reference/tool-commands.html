Tool commands: install, update, uninstall and inspection

CLI reference

Published from the canonical docs/reference/tool-commands.md file. Features marked experimental remain experimental; check support limitations before relying on them.

These commands declare, lock, install, update and inspect the tools a project or your user account needs. They change what a scope requires ([tools] in configuration) and what it has locked (oyzu.lock) together, so the two never drift apart. Use them instead of editing oyzu.toml and oyzu.lock by hand.

Status: implemented for the tools Oyzu admits today; experimental. The design is the accepted OEP-0021 tool commands proposal (design accepted 2026-10-07). Syntax, error codes and the choices listed under accepted choices may still change. Developed and verified on Linux x86-64 only; Windows and macOS are unverified (see verification). No account is needed.

oyzu install go@1.26          # this project: declare, lock, install
oyzu install -g node@22       # your user configuration, all projects
oyzu install go               # declared: ensure installed; undeclared: go@latest
oyzu update go                # newer version within the requirement; config untouched
oyzu uninstall go             # remove the project declaration and lock entry
oyzu tools current            # what is in effect here
oyzu tools list               # what is in the store, and what references it
oyzu tools versions go        # what could be installed
oyzu tools info go            # provider, verification, eligibility

The commands use the existing providers:

  • Archive providers: node, go, python, java, maven, gradle, helm, kubectl, k3d, liquibase, tailscale, npm, pnpm, yarn.
  • Rust-family providers: rust and the Cargo helpers cargo-nextest and cargo-llvm-cov.
  • Experimental registry packages written aqua:<owner>/<repo> (see the aqua: backend) or github:<owner>/<repo> (see the github: backend).

Scope​

Every command acts on one scope. The default is the current project; flags select another.

Installation and update scope​

FlagConfiguration writtenLock
none, inside a projectproject oyzu.toml (created if absent)project oyzu.lock
-g, --globalthe user configuration file (OYZU_USER_CONFIG or the native location)the oyzu.lock beside it
--localoyzu.local.tomlproject oyzu.lock
--toolset NAME (global option; install, update, uninstall, pin)that toolset's [toolsets.NAME.tools] in project oyzu.toml, or oyzu.local.toml with --localthat toolset's sets in the project oyzu.lock; the [tools] sets are never changed (toolsets)
  • A project is --root, or the workspace root when it holds oyzu.toml, oyzu.local.toml, build.yaml or a Git marker.
  • Outside a project, a command without -g fails with TOOL_NO_PROJECT and writes nothing; it never guesses.
  • --global and --local conflict, and --toolset is refused with --global.
  • A profile never holds tools (toolsets): an explicit --profile on install SPEC or uninstall fails with TOOL_PROFILE_DECLARATION and writes nothing.
  • A command acts on the selected scope only and prints a note when the same tool is declared elsewhere.
  • -g ignores project files entirely, including when run inside a project.

install​

oyzu install with no arguments installs everything declared in the effective configuration. It accepts --frozen, --offline and --update.

oyzu install --global installs the global selection independently of the current project, using the user configuration and its sibling oyzu.lock.

  • It accepts the same frozen, offline, update and store controls, and never edits project declarations or locks.
  • oyzu install --global --frozen --offline restores a previously locked global selection using locally available installation or acquisition data.
  • Missing locks fail with TOOL_LOCK_MISSING; an offline installation still requires the needed cached data.

Installing with specs​

A spec is [provider:]name[@version], split at the last @.

SpecMeaning
go@1.26A prefix.
go@1.26.8An exact version.
go@latestThe newest eligible version.
goKeeps a declared requirement (ensuring it is installed), or takes latest when undeclared.

What happens:

  • Several specs are applied together or not at all. Naming a tool twice is TOOL_SPEC_INVALID.
  • Configuration stores what you typed ("1.26"); the lock stores the exact version.
  • Core tools (node, go, python, java, maven, gradle, rust) are written under the name you typed. Other tools (cargo-nextest) are written under their canonical ID ("cargo:cargo-nextest") so a later alias change cannot alter the file. An existing declaration keeps its spelling.
  • Existing TOOL_ALIAS_UNSUPPORTED and TOOL_ALIAS_AMBIGUOUS behavior is preserved, and an ambiguous bare name fails listing the exact retry spellings.
  • Replacing a requirement reports Replaced "1.25" (1.25.9) -> "1.26" (1.26.8) and reuses an installation already in the store.
  • Declared tools of the same lock that are not yet in the portable lock layer are resolved in the same run, keeping the exact version they already had, and are installed too, so the whole selection remains consistent.

Order of operations:

  1. Parse specs.
  2. Evaluate tools.allowed.
  3. Resolve every platform in the default set (Linux x64, macOS arm64, Windows x64 for archive tools; tools.platforms overrides).
  4. Install only the host archive.
  5. Publish configuration and lock in one journaled transaction.

Any failure leaves both files unchanged. Concurrent edits fail with PIN_EDIT_CONFLICT.

Flags that do not combine​

  • --dry-run resolves (reading publisher catalogs) and reports versions, files and platforms; it downloads no archive and writes nothing.
  • Specs with --frozen, --offline or --update fail with TOOL_FLAGS_CONFLICT before any project, configuration or network access, as do --dry-run and --local without specs.
  • Archive tools and Rust-family tools resolve through different contracts; one command cannot mix them (TOOL_FLAGS_CONFLICT: run two commands).

Result​

Human output, then the shape of --json: tools[] with tool, key, request, version, previous, status, platforms, otherScopes; plus configuration, lock, scope, store.

✓ Installed go 1.26.8
    Declared "1.26" in ./oyzu.toml (project)
    Locked in ./oyzu.lock for 3 platforms (darwin/arm64/native, linux/amd64/gnu, windows/amd64/msvc)

From a resolved artifact set (experimental)​

install recipe:owner/name@version --artifact-set FILE [--artifact-set-digest sha256:D] supplies the tool from a resolved artifact set instead of a built-in provider. tools info … --artifact-set shows the same eligibility without side effects, and --dry-run reports eligibility only. Details, output and limits are in artifact sets.

  • The flags are provisional and apply to the project scope only (-g/--local fail TOOL_FLAGS_CONFLICT).
  • The install downloads and verifies the artifact and writes the lock, but does not yet extract or activate a recipe tool.
  • install --frozen replays locked recipe: tools from the lock alone.

update​

update [TOOL...] re-resolves within the existing requirement, locks the result for all platforms, installs the host selection and never edits configuration.

  • No arguments updates every tool of the selected scope. It takes names, not versions.
  • In a project without --toolset it also covers every toolset (toolsets): the [tools] tools first, then each toolset's, each in its own lock sets.
  • A named tool is updated wherever [tools] or a toolset declares it. The table's Set column names [tools] or the toolset of each row (toolset in JSON).
  • install --update remains as a deprecated alias with its old behavior (all scopes).
  • A tool still missing from the portable layer is migrated, keeping its version.
  • Hand-edited removals are not pruned from the lock.

uninstall​

uninstall TOOL... removes the declaration (comments elsewhere in the file are kept) and every lock record for the tool at the selected scope, in one transaction.

  • Shared payloads are never deleted: they remain in tools list as unreferenced.
  • A tool not declared at that scope fails with TOOL_NOT_DECLARED and names the scope that does declare it.
  • --dry-run writes nothing.

Pin declarations without installing​

oyzu pin kubectl@1.34 helm@3.22.0 edits the project's [tools] requests and locks their exact archives for the configured platforms in one transaction. All archive providers use this path, including Python, Maven, Gradle, npm and pnpm. Run oyzu install --frozen afterward to install.

  • --dry-run previews the result without writing.
  • Explicit specs cannot be combined with --refresh or --offline; bare oyzu pin retains discovery-driven pinning, refresh and offline behavior.
  • Normal configuration precedence and policy still apply, and overridden requests fail without changing files.
  • Bare oyzu pin covers every toolset: it locks each toolset's tools in that toolset's labelled sets beside the [tools] sets, and oyzu --toolset NAME pin locks only that toolset's (toolsets).

The result uses the shared declaration presentation: requested/selected versions, covered and unavailable platforms, configuration path and lock path. oyzu --json pin kubectl@1.34 helm@3.22.0 returns the same facts with status: "pinned".

  • Pinning does not install payloads or prepare shims.
  • Publisher metadata acquisition may verify archive bytes where its checksum format requires conversion; indexed pinning reads the index/catalog only (Rust also reads the approved manifest).
  • The defaults include linux/arm64/gnu; locks can carry it on any host. An unavailable provider/platform is omitted and reported. macOS amd64 and musl are not added to installation support. See implementation status for explicit-spec and ARM64 verification results.

Inspection​

All inspection is read-only, performs no installation, never re-hashes installed payloads (installs are verified once, then trusted) and prints the store path.

CommandShows
tools current [-g] [--all] [--details]One row per effective tool with the requested and selected versions, scope and status. --global shows only global declarations; --all adds declarations a more specific scope overrides.
tools listInstallations in the store with size and what references each: global (the user lock), project (this project's lock) or unreferenced.
tools versions TOOLSelectable versions, newest first.
tools info TOOLProvider, accepted names, commands, platforms, verification, eligibility, declarations by scope and current state.
tools check --catalog, tools migrate [--write]Check declarations against the tool index, and move mise.toml tools and aqua: ids to Oyzu names. See the tool index reference.

Statuses in tools current​

StatusMeaning
okInstalled and locked.
not installedLocked but absent from the store.
blockedExcluded by tools.allowed; names the rule.
stale lockNo lock, no matching entry, or no entry for this platform or provider.
ambiguousConflicting lock records or names.
deprecatedReserved; no provider reports it yet.

Notes​

  • tools list: other projects are not indexed, so an installation reported unreferenced may be used elsewhere.
  • tools versions reads the publisher's catalog, or the tool index when one is configured and lists the package (which also works offline from its cached copy). Otherwise it requires network (TOOL_OFFLINE with --offline).
  • Pre-release, snapshot and nightly versions are not offered by the adapters, so excluded is always empty today. A tool blocked by tools.allowed reports why.
  • Rust and Cargo helpers have no catalog (TOOL_VERSIONS_UNSUPPORTED).

Accepted choices​

Recorded in the proposal's decision record (accepted 2026-10-07): no provider prefix beyond canonical IDs; core tools stored as typed; no allow-list patterns; no prerelease flag; tools versions has no offline source; no project index; bare oyzu tools unchanged.

Platforms without an artifact​

A platform for which the provider publishes no artifact for the requested version is omitted from the lock and reported as unavailable (a warning in the human view, unavailablePlatforms in --json).

  • The other platforms lock and the host installs normally; selecting the unavailable platform fails.
  • Example: oyzu install node@14 locks Linux and Windows only, because Node 14 has no macOS arm64 build.
  • This applies when a tool is first declared or re-declared with a new request, and only for the Node, Go and JDK catalogs. An update re-resolves only the platforms already locked, and a tool with no artifact on any platform fails.
  • Any other resolution failure (for example a missing checksum file) still fails the command.

Limitations​

  • Linux only verified.
  • Mixed archive and Rust-family specs need separate commands.
  • Installing one tool also installs the other declared tools of its lock group.
  • Config and lock publication is journaled, with recovery as described under Interrupted publication.
  • Managed (enrolled) mode is rejected as for the other tool commands.

TOOL_NATIVE_PIN_CONFLICTA [tools] value that names another version line than a native pin file (rust-toolchain.toml, .nvmrc, .node-version, .python-version, packageManager) was written in the pin file's folder or nearer the build, or set by policy; names both sources, exit status 3 (native pin files)
TOOL_NATIVE_PIN_INVALIDA native pin file holds a value [tools] does not accept (an alias such as lts/* or nightly, a range, several versions, a Rust toolchain.path); names the file and a remedy, exit status 3

Interrupted publication​

An interrupted configuration/lock publication is recovered before reading configuration when retrying oyzu install, oyzu update or oyzu uninstall. oyzu pin also recovers it.

  • Install recovery precedes configuration preflight and artifact-set replay, including plain, --frozen, --offline, spec and artifact-set forms. Offline configuration reads also use the offline session policy.
  • Read-only commands report PIN_RECOVERY_REQUIRED with the affected directory and a recovery command.
  • Unexpected external edits stop recovery with PIN_EDIT_CONFLICT; the journal remains for investigation.
  • Configuration and lock readers capture one consistent pair under the shared edit lock, then release it before acquiring or launching tools. A concurrent first edit or a change while capturing additional targets reports CONFIG_EDIT_CONFLICT; retry the command.

Recipes and preparation failures​

  • Recipe-staleness errors identify the actual tool, version and lock path. Use oyzu pin --refresh to refresh recipes while retaining selected versions, then oyzu install to materialize them.
  • Tool-preparation failures identify the tool, requested or pinned version, store path and recovery command.
  • Windows paths in these diagnostics use the plain C:\... or \\server\share\... form in both human and JSON output; the extended \\?\ prefix remains an internal filesystem detail. Unix diagnostic paths are unchanged.

Verification​

tooling/test-tool-commands.py drives the compiled CLI against real Go and Node downloads; tests/integration/tool_commands.rs covers the no-download cases. See the qualification record.
