Tool commands: install, update, uninstall and inspection

CLI reference

Published from the canonical docs/reference/tool-commands.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Use these commands to add, lock, install, update and inspect the tools a project or your user account needs. Each command changes the declaration ([tools] in configuration) and the lock (oyzu.lock) together, so the two never drift apart. Use them instead of editing oyzu.toml and oyzu.lock by hand.

Note: These commands are experimental, and their syntax and error codes may change. They are fully tested on Linux x86-64; Windows x86-64 works with less test coverage, and macOS isn't supported yet. No account is needed.

oyzu install go@1.26          # this project: declare, lock, install
oyzu install -g node@22       # your user configuration, all projects
oyzu install go               # declared: make sure it is installed; undeclared: go@latest
oyzu update go                # newer version within the requirement; config untouched
oyzu uninstall go             # remove the project declaration and lock entry
oyzu tools current            # what is in effect here
oyzu tools list               # what is in the store, and what uses it
oyzu tools versions go        # what could be installed
oyzu tools info go            # provider, verification, eligibility

Supported tools:

  • Archive providers: node, go, python, java, maven, gradle, helm, kubectl, k3d, liquibase, tailscale, npm, pnpm, yarn.
  • Rust: rust and the Cargo helpers cargo-nextest and cargo-llvm-cov.
  • Experimental registry packages: aqua:<owner>/<repo> (see the aqua: backend) and github:<owner>/<repo> (see the github: backend).

Platform scope: Use an x64 host and supported x64 build targets. ARM64 is unsupported. Feature-specific limits are listed in the support matrix.

Scope​

Each command acts on one scope. The default is the current project.

FlagConfiguration writtenLock written
none, inside a projectproject oyzu.toml (created if missing)project oyzu.lock
-g, --globalyour user configuration file (OYZU_USER_CONFIG or the platform default)the oyzu.lock next to it
--localoyzu.local.tomlproject oyzu.lock
--toolset NAME (global option)[toolsets.NAME.tools] in oyzu.toml, or in oyzu.local.toml with --localthat toolset's entries in oyzu.lock; [tools] entries are untouched (toolsets)
  • The project is --root, or the workspace root when it holds oyzu.toml, oyzu.local.toml, build.yaml or a Git marker.
  • Outside a project, a command without -g fails with TOOL_NO_PROJECT and writes nothing.
  • -g ignores project files, even when you run it inside a project.
  • --global and --local can't be combined, and --toolset can't be used with --global.
  • Profiles never hold tools. --profile with install SPEC or uninstall fails with TOOL_PROFILE_DECLARATION.
  • If the same tool is declared in another scope, the command prints a note.

install​

oyzu install with no arguments installs configured tools and the native tool requirements of the project containing the current directory. A conventional project needs no oyzu.toml, build.yaml or existing oyzu.lock: installation selects its builder plugin, discovers tool requests from native files, and records the verified tools in oyzu.lock. It does not install application dependencies; the builder prepares those during oyzu build.

It accepts --frozen (require matching tool and plugin locks), --offline (use only locks, installations and cached archives) and --store DIR. First-time plugin acquisition needs network access and an eligible published plugin; Preview plugins require the Preview opt-in. Existing locked tool versions are retained. Global installation uses only global tool declarations.

An online, non-frozen install in a project with builds also records the project's captured build requirements through the same resolution and lock transaction as bare oyzu pin. Installation records alone cannot restore a tool in a captured build worker. An image-and-chart project can run oyzu install, then oyzu build, without a separate pin step. This records requirements for the project's builds; host installation still follows the selected tools.

The human result reports Recorded build requirements for N build(s).; JSON includes recordedBuildRequirements with that build count. These are omitted for tools-only folders, global installs and frozen/offline installs. Repeating an install with unchanged inputs and a complete lock keeps the lock byte-identical and retains selected versions. Online installation can still refresh signed tool-index and catalog metadata for current admission; captured resolution reuses complete locked recipes.

--frozen never adds missing recipes, and --offline never resolves them from publisher metadata. If a captured build has installation records but lacks its tool recipe, it stops during preparation, before build actions, with TOOL_LOCK_MISSING. Run oyzu pin online in the project, then retry. Global installs do not resolve project build requirements.

Captured requirement resolution follows verified host installation. If that final resolution fails, installed tools and their installation records remain available; correct the reported requirement and rerun oyzu pin or oyzu install online.

oyzu install --global installs your global tools using your user configuration and its oyzu.lock, independent of the current project. oyzu install --global --frozen --offline restores a locked global selection from local data. A missing lock fails with TOOL_LOCK_MISSING.

Installing with specs​

A spec is [provider:]name[@version], split at the last @.

SpecMeaning
go@1.26Newest version starting with 1.26.
go@1.26.8Exactly this version.
go@latestNewest eligible version.
goKeep the declared requirement and make sure it is installed; if undeclared, use latest.
  • Several specs are applied together or not at all. Naming a tool twice fails with TOOL_SPEC_INVALID.
  • Configuration stores what you typed ("1.26"). The lock stores the exact version.
  • Core tools (node, go, python, java, maven, gradle, rust) are written under the name you typed. Other tools are written under their full ID (for example "cargo:cargo-nextest"). An existing declaration keeps its spelling.
  • An ambiguous bare name fails and lists the exact spellings to retry with.
  • Replacing a requirement prints Replaced "1.25" (1.25.9) -> "1.26" (1.26.8) and reuses an installation already in the store.
  • Other declared tools in the same lock that aren't locked yet are locked and installed in the same run, keeping their current versions.

What install does, in order:

  1. Parses the specs.
  2. Checks tools.allowed.
  3. Resolves lock entries for every platform your builds declare, plus the host. tools.lockPlatforms replaces the inferred platform list (the host is always kept).
  4. Downloads and installs only the host archive.
  5. Writes configuration and lock in one transaction.

Any failure leaves both files unchanged. A concurrent edit fails with PIN_EDIT_CONFLICT.

Flags that don't combine​

  • --dry-run resolves versions (reading publisher catalogs) and reports versions, files and platforms. It downloads no archive and writes nothing.
  • Specs with --frozen, --offline or --update fail with TOOL_FLAGS_CONFLICT, as do --dry-run and --local without specs.
  • Archive tools and Rust tools can't be mixed in one command (TOOL_FLAGS_CONFLICT). Run two commands.

Result​

✓ Installed go 1.26.8
    Declared "1.26" in ./oyzu.toml (project)
    Locked in ./oyzu.lock for 3 platforms (darwin/arm64/native, linux/amd64/gnu, windows/amd64/msvc)

With --json the result has tools[] (tool, key, request, version, previous, status, platforms, otherScopes) plus configuration, lock, scope and store.

Platforms without an artifact​

If the publisher has no artifact for a platform, that platform is left out of the lock and reported as unavailable (a warning in human output, unavailablePlatforms in JSON). The other platforms lock and the host installs normally. Selecting the unavailable platform later fails.

For example, oyzu install node@14 locks Linux and Windows only, because Node 14 has no macOS arm64 build.

  • This applies when a tool is first declared or its request changes, and only for Node, Go and Java.
  • update uses current lock coverage (the declared build platforms, or tools.lockPlatforms, plus the host). Platforms left over from an earlier default or declaration do not become new requirements.
  • A tool with no artifact on any platform fails, as does any other resolution problem (for example a missing checksum file).

From a resolved artifact set​

oyzu install oyzu:NAME@VERSION --artifact-set FILE [--artifact-set-digest sha256:D] installs a tool from a resolved artifact set instead of a built-in provider. This is experimental, works in the project scope only, and doesn't yet make the tool runnable. See artifact sets.

update​

oyzu update [TOOL...] moves locked versions forward within each existing requirement, locks the result for all platforms and installs the host selection. It never edits configuration.

  • With no arguments it updates every tool in the scope. It takes names, not versions.
  • In a project without --toolset, it also updates every toolset: [tools] first, then each toolset. The Set column (toolset in JSON) shows which one each row belongs to.
  • A named tool is updated wherever [tools] or a toolset declares it.
  • --dry-run reports the versions that would be locked.
  • Tools you removed from configuration by hand aren't pruned from the lock.
  • Only selected tools are re-resolved for current platform coverage. Valid recipes for unselected tools stay unchanged; unreferenced recipes are pruned without fetching their metadata again.
  • install --update still works but is deprecated.

uninstall​

oyzu uninstall TOOL... removes the declaration and every lock entry for the tool in the selected scope, in one transaction. Comments elsewhere in the file are kept.

  • Installed files stay in the store and show as unreferenced in oyzu tools list.
  • A tool that the scope doesn't declare fails with TOOL_NOT_DECLARED, naming the scope that does.
  • --dry-run writes nothing.

Pin declarations without installing​

oyzu pin kubectl@1.34 helm@3.22.0 adds the requests to the project's [tools] and locks their exact archives for the configured platforms, in one transaction. It installs nothing. Run oyzu install --frozen afterward to install.

  • --dry-run previews the result.
  • Specs can't be combined with --refresh or --offline. Bare oyzu pin locks what your builds need, and accepts --refresh and --offline.
  • Bare oyzu pin covers every toolset. oyzu --toolset NAME pin locks only that toolset.
  • Pin removes recipes no request set references, including with --offline. Recipes still referenced by other sets stay unchanged. This cleanup does not require refreshing their versions or resolving their platforms again.
  • A separate bare oyzu pin is optional after an online, non-frozen project install. It remains useful for reviewing a resolution without installing, and for preparing a lock before oyzu install --frozen.
  • Configuration precedence and policy still apply. A request that another scope overrides fails without changing files.
  • oyzu --json pin ... returns the same facts with status: "pinned".
  • Pinning reads publisher metadata or the tool index. For some checksum formats it downloads the archive to compute a SHA-256.
  • Pin uses the current platform coverage. Inferred foreign platforms the provider doesn't publish are left out and reported.

Locked quality tools​

Node, Java and Docker default quality tools are exact stage-tool selections in oyzu.lock, under quality.node, quality.java and quality.docker. Bare oyzu pin records the sets your enabled checks need. It records versions, upstream URLs, upstream integrity and SHA-256 values together with support files such as Node's package lock and Java's default rules. Commit the lock; do not edit versions or hashes by hand.

The pin result lists each locked quality set's name, version and snapshot digest in the Locked quality sets table. A dry run labels these as proposed sets. --json exposes the same metadata in qualitySets, an array of {name, version, digest} records. These describe the lock snapshot; they do not claim the tools are installed or available on the current platform.

pin selects metadata. Before a quality task runs, preparation installs its locked bundle in the shared tool store if needed. Local builds, isolated builds and oyzu run use the same set. Downloads are admitted and verified at install; installed payloads are trusted on reuse. Native project tools and authored task replacements retain their documented precedence. No separate checker-home environment variable or repository provisioner is required.

Concurrent tasks needing the same bundle share its installation. In a cold store, one caller publishes the verified bundle while others wait and then reuse it. Active consumers can keep using it while later callers acquire it. A caller waits up to 30 minutes for another publisher; acquisition and task execution retain their own limits. Malformed installed metadata is refused and retained unchanged.

New default sets ship with Oyzu releases. Ordinary builds, runs and oyzu pin keep an existing exact selection. Two explicit operations adopt the current CLI's defaults:

  • oyzu pin --refresh refreshes default quality sets required by the selected build scope while preserving selected native runtime versions.
  • oyzu update with no tool names in the project scope refreshes its already locked quality sets, including Docker projects with no runtime declaration. Named tool updates, global updates and toolset-only updates leave them alone.

Both update the lock; the next task installs any newly selected quality bundle. oyzu update --dry-run reports the proposed set versions without writing or installing them. Checker eligibility and source restrictions remain binding. Offline operation requires the exact lock and the needed installation or admitted cached inputs in the same store. Run an online check first to populate it.

Missing quality pins report QUALITY_LOCK_REQUIRED; run oyzu pin and retry. An unavailable complete tool pair reports QUALITY_PLATFORM_UNAVAILABLE rather than taking a tool from ambient PATH. Versions, project-tool precedence and platform limits are described in Node quality, Java quality and Docker quality.

Maintaining shipped quality defaults​

Repository maintainers regenerate defaults with the compiled tooling/refresh-quality-tools operation. Activate Oyzu's checks toolset first; its npm verifies registry signatures and available package provenance without running lifecycle scripts. Refresh, reports and the GitHub bot live in the repository-only oyzu-quality-tools binary; they are not shipped with the CLI or plugins. Build the non-default target first. Set OYZU_QUALITY_TOOLS to a specific maintenance executable when testing a resolver change.

eval "$(oyzu --toolset checks activate bash)"
oyzu build quality-tools
tooling/refresh-quality-tools --update
tooling/refresh-quality-tools --check
tooling/refresh-quality-tools --report --json

--update (the default) selects stable versions in each currently allowed major, with a seven-day publication cooldown. Maven formatter selection also preserves the existing Java 17 runtime baseline: base classes requiring a newer JVM are excluded, while optional multi-release classes do not raise the baseline. This bytecode check limits candidate selection but cannot establish compatibility with the JDK's compiler APIs. The formatter remains capped below 1.29 on its Java 17-compatible line; 1.28.0 is the default. The native Java acceptance suite still verifies the selected formatter on Java 17. Freshness reports continue to show newer minor and major releases for maintainer review; the cap does not declare those releases current or compatible. Raising the baseline or cap requires an explicit compatibility change. --regenerate verifies the versions in the native inputs and regenerates their pin records and hashes without selecting new versions. --set node|java|docker restricts the refresh; the default is all three. --check is an offline consistency gate and directs manual pin/hash drift back to this command. It does not download tools or prove upstream freshness.

Refresh verifies npm SHA-512, Maven checksums and detached OpenPGP signatures, and GitHub release SHA-256 values and available artifact attestations. Published proofs that cannot be verified fail the operation. Maven signer continuity is anchored in the previously pinned artifact and retained signer fingerprint; a signer change requires maintainer investigation. npm's native signature audit also covers optional platform packages, without executing their binaries. All verification completes before generated source files are replaced. Project locks are never changed by this maintainer operation.

--security may bypass cooldown only when the currently pinned set has an affecting advisory and every changed release younger than seven days fixes an advisory affecting its prior version. The resulting set must be clear of known advisories. A missing date, unavailable advisory service, unsupported proof or remaining advisory fails visibly; it is not treated as a clean result.

The report compares every pinned asset with upstream stable releases, including new majors, after checking native-pin consistency. It counts current, held and stale rows, plus affecting advisories. A row is held when newer releases exist but none is permitted by all applicable constraints. Reasons come from the recorded native lock's parent dependency ranges (including optional and peer requirements) and the explicit compatibility policies: Checkstyle major 10, google-java-format below 1.29 for Java 17, and TypeScript major 6 while the quality root pins that line. Other direct version pins do not themselves justify holding an update.

Held rows do not fail the report. Each run recomputes their reasons: widening a parent range or lifting a compatibility cap makes newly permitted updates actionable. The report still shows unrestricted upstream lag from the earliest newer stable release. Its actionable lag starts at the earliest newer release permitted by every constraint, even if a later release is blocked. More than 60 days of actionable lag makes the row stale and fails the report. An affecting advisory always fails, including on held and transitive packages. Advisory coverage includes npm packages, Maven coordinates, Dockerfmt's Go module and the release repositories' published advisories; this is not a complete inventory of dependencies embedded inside upstream executable or all-dependencies JARs.

A completed --report prints the full report on stdout and exits 0 when the check passes, or 1 when actionable lag or an advisory fails it. Human output shows the counts, held rows grouped by reason (one line per tool), and freshness and affecting-advisory tables. --json includes counts, the same reason groups in held, and each tool's status, heldReason, actionableLagDays and firstAllowedNewerPublishedAt. It preserves every tool observation and advisory in the structured result, including status: "failed". A transport, metadata or advisory-service error remains a failing diagnostic, rather than an incomplete report presented as a completed check.

Dependabot watches the Node native lock on the repository's weekly cadence. The existing scheduled tool-management job runs this same verifier and opens a draft refresh PR, and regenerates hashes for eligible same-repository Dependabot PRs. It executes trusted main code and reads only allowlisted PR data. Delivery needs a GitHub App installed on this repository only, with Contents and Pull requests permissions set to write. Configure the repository variable QUALITY_TOOLS_APP_CLIENT_ID and secret QUALITY_TOOLS_APP_PRIVATE_KEY. Token creation and refresh delivery skip when the client-ID variable is absent; the independent freshness report still runs. The bot adds no CI label and grants no release or compliance approval. --pull-request is the automation entry point and requires that App's token and bot identity. Source files, workflows and scripts from the proposed PR are never executed.

Inspection​

oyzu tools list --details includes Publisher evidence for each stored installation. The JSON row uses evidenceStrength, with digest-only, checksum-file, signature or provenance. These are receipt facts, not a fresh integrity check. An older receipt without a strength reports digest-only. See publisher evidence and release age for pin-time verification, the seven-day default cool-down, security exceptions and explicit early-version warnings. Human and JSON modes use the same facts.

These commands are read-only. They install nothing, don't re-check installed files (tools are verified when installed, then trusted) and print the store path. All accept --store DIR.

CommandShows
oyzu tools current [-g] [--all] [--details]One row per tool in effect: requested and selected versions, scope and status. -g shows only global declarations; --all adds declarations a closer scope overrides.
oyzu tools list [--details]Installations in the store, with size and what uses each: global, project or unreferenced.
oyzu tools versions TOOL [--offline]Versions you can install, newest first.
oyzu tools info TOOLProvider, accepted names, commands, platforms, verification, eligibility, declarations by scope and current state.
oyzu tools check --catalog, oyzu tools migrate [--write]Check declarations against the tool index, or move mise.toml tools to Oyzu names. See tool index.

Statuses in tools current:

StatusMeaning
okInstalled and locked.
not installedLocked but not in the store. Run oyzu install.
blockedExcluded by tools.allowed; the rule is named.
stale lockNo lock, or no entry for this tool, platform or provider. Run oyzu pin.
ambiguousConflicting lock entries or names.

Notes:

  • tools list only knows about the global lock and the current project. An "unreferenced" installation may still be used by another project.
  • tools versions reads the publisher's catalog, or the tool index when it lists the package (which also works offline). Otherwise it needs the network and fails with TOOL_OFFLINE under --offline.
  • Pre-release and nightly versions aren't offered. A version blocked by tools.allowed says why.
  • Rust and the Cargo helpers have no version catalog (TOOL_VERSIONS_UNSUPPORTED).

Limitations​

  • Supported on Linux x86-64 only.
  • Archive and Rust tools need separate commands.
  • Installing one tool also installs the other declared tools in its lock.
  • These commands don't run in managed (enrolled) mode.

Errors​

CodeCause and fix
TOOL_SPEC_INVALIDUnparseable spec, empty version or a tool named twice.
TOOL_NO_PROJECTNo project here. Run inside a project or use --global.
TOOL_NOT_DECLAREDuninstall or update of a tool this scope doesn't declare.
TOOL_FLAGS_CONFLICTFlags that don't combine, archive and Rust tools mixed, or a declaration overridden in this invocation.
CONFIG_OVERRIDE_DENIEDtools.allowed excludes the tool. The rule is named; nothing is written.
TOOL_NATIVE_MINIMUM_CONFLICTA configured version is below the minimum in Go's go.mod or go.work. Both sources are named. Exit status 3. See Go version selection.
TOOL_NATIVE_PIN_CONFLICTA [tools] value in the pin file's folder or nearer the build, or set by policy, names a different version than a native pin file (rust-toolchain.toml, .nvmrc, .node-version, .python-version, packageManager). Exit status 3. See native pin files.
TOOL_NATIVE_PIN_INVALIDA native pin file holds a value [tools] doesn't accept (an alias such as lts/* or nightly, a range, several versions, or a Rust toolchain.path). The file and a fix are named. Exit status 3.
TOOL_NATIVE_PIN_OVERRIDDENWarning: oyzu.local.toml overrides a native pin. oyzu pin locks the pin, not the override.
TOOL_LOCK_STALEThe lock has no entry for a request, or a native pin or minimum changed (for example go get rewrote go.mod). Run oyzu pin.
PIN_EDIT_CONFLICTAnother process changed the files at the same time. Retry.

Interrupted publication​

If a configuration and lock write was interrupted, the next oyzu install, oyzu update, oyzu uninstall or oyzu pin finishes or rolls it back before doing anything else.

  • Read-only commands report PIN_RECOVERY_REQUIRED with the affected folder and the command to run.
  • If the files were edited by something else in the meantime, recovery stops with PIN_EDIT_CONFLICT and leaves its journal for you to inspect.
  • A concurrent edit while a command reads configuration reports CONFIG_EDIT_CONFLICT. Retry the command.

Recipes and preparation failures​

  • If installation recipes are out of date, the error names the tool, version and lock. Run oyzu pin --refresh (keeps selected versions), then oyzu install.
  • Tool preparation failures name the tool, version, store path and the command to recover.
  • Windows paths in errors use the plain C:\... or \\server\share\... form.
