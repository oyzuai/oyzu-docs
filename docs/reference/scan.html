Experimental scan command

CLI reference

Published from the canonical docs/reference/scan.md file. Features marked experimental remain experimental; check support limitations before relying on them.

oyzu scan runs policy-selected SonarQube, Trivy, Gitleaks and/or Grype adapters against an existing successful dist build bundle. This is a development experiment, not the complete managed scanning service. No platform account is required. The experiment plan owns the acquisition and handoff acceptance scenarios.

Scope relative to current build and task contracts​

The five first-flow native Gitleaks cases have passed on Windows at the recorded checkpoint. The local administrative container fixture is a test configuration, not a requirement for ordinary standalone builds or a public platform policy wire model. Optional managed execution follows the client boundary.

scan remains explicit: it does not rebuild, run test tasks, or publish. Builder test overrides and their reporting integrations remain owned by the task/build lifecycle. This command replays the build manifest's frozen whole-tree source.selection or host source.projections, including authored inputs and effective ancestor rules. Whole-tree and aggregate host projection digests retain their existing meanings and must match exactly. Replay does not rediscover declarations or load current ignore rules. Nested host replay retains and binds authored sibling inputs in its staged repository, but adapters receive the workspace path; scanning those external sibling inputs remains unqualified. It does not retrieve Git revisions or prepare build-coupled scanner instrumentation. Such layouts are not qualified by the Java fixture and must not be described as supported by this experiment. Artifact copies remain scan-owned, digest-verified inputs; they do not mutate the producer bundle or implement new build materialization syntax.

Inputs and setup​

The first native Gitleaks selection flow is demonstrated under #533. The typed project settings scan.gitleaks.enabled and scan.gitleaks.failOnFindings are booleans, both defaulting to false, and use the ordinary configuration cascade and enforced constraints. Native installation/execution is connected and has compiled on Windows at the recorded checkpoint: it uses the shared tool owner's acquired installation, lease and exact executable, with no PATH or container fallback. Native acquisition, reuse, finding rejection, informational findings and execution failure passed through genuine Rust build bundles. The complete harness also passed the exact source-mismatch refusal before scanner launch. No selected scanner produces SCAN_SELECTION_REQUIRED, with the minimal setup instruction. Existing administrative container selections remain required and cannot be replaced by these project settings; enabling failOnFindings can only tighten Gitleaks' finding criterion to zero.

The native selection uses ordinary project TOML:

[scan.gitleaks]
enabled = true
failOnFindings = true

Omit failOnFindings to retain findings without a finding-based rejection criterion; execution failures still fail. Native Gitleaks uses an explicit tool request under [tools] when present, a compatible captured pin, or the shared resolver's default otherwise. A first unpinned operation prepares portable tool metadata under a temporary private lock owner and installs only the host payload. Verified installation/leases and remembered selections remain owned by the shared tool subsystem. This does not edit project/global configuration or oyzu.lock.

oyzu scan --store <DIR> selects the native tool store for that invocation, using the same path semantics as install/build/exec. Relative paths resolve from the project root. Omitting it keeps the shared user store. Store location does not change tool identity, required verification, policy or lock authority; container images remain in Docker's store. This permits a separate initially empty scanner store without changing routine project configuration. With --offline, a compatible recorded installation or pin and cached inputs must already be available; an unpinned empty store refuses before online resolution. The native Gitleaks qualification record owns the runnable first-flow proof and its measured results and limits.

The command reads configuration through the normal session. Only administrative configuration may supply scan.policy; project Gitleaks enablement uses the typed settings above. Tool version requests belong under [tools], not scanner settings. This initial fixture is not an OPA or server wire contract. In the existing protected admin-settings.json format:

{
  "schemaVersion": 1,
  "kind": "local-admin-policy",
  "settings": {
    "scan.policy": {
      "locked": true,
      "value": {
        "sonar": {
          "image": "sonarsource/sonar-scanner-cli@sha256:a3f4215076706c95a17a68c19322ee916e40a3acd081a8c1a1e839e0194afa57",
          "endpoint": "https://sonarqube.example.com",
          "projectKey": "example",
          "sources": ["app/src/main/java", "library/src/main/java"],
          "requireClasses": true
        },
        "trivy": {
          "image": "aquasec/trivy@sha256:af6acf9a6b85dfe389a1941505c0ce9efef52a4719635e1a962f022a3d855daa",
          "maximumFindings": 0
        },
        "requireQualityGate": true
      }
    }
  },
  "profiles": {},
  "requiredCapabilities": []
}

Provision Docker and the SonarQube project and service. Preflight acquires missing policy-selected, digest-addressed scanner images through the shared container-tool provider and verifies/reuses existing images. Docker owns image storage; this is not native archive-tool installation. Managed acquisition, nonpublic tool catalogs and configured registry routes are rejected until connector projection is connected; there is no direct-download fallback for those configurations. Provide SONAR_TOKEN in the invoking process environment; do not put a token in the policy file. It needs analysis submission and permission to read task, quality-gate and project-issue data. The isolated experiment supplies a temporary development token and revokes it afterward; this is not credential brokering qualification. HTTP is supported for the isolated local service proof.

oyzu build
oyzu scan
oyzu scan --json

Each call starts a separate scan. Global --json works before or after scan. The current source tree is captured with the build's recorded snapshot selection and must match the build's recorded tree digest. A Git HEAD value alone never satisfies that check. Changed source fails before scanner launch; restore the matching inputs or explicitly build again. This initial path does not yet fetch source from Git or retrieve remote bundles. Cross-host filesystem differences can prevent a digest match and are not silently normalized.

A bundle without either source replay contract fails with SCAN_SOURCE_SELECTION_MISSING; malformed or ambiguous contracts fail with SCAN_SOURCE_SELECTION_INVALID. Build explicitly with the current CLI to record the required selection, then scan that bundle. There is no guessed selection for earlier development bundles. Source replay, native execution and exact mismatch refusal passed in the recorded Windows proof; consumer regression tests passed in this branch's full workspace suite. This does not establish cross-host scan qualification.

Source paths are relative directories. requireClasses selects this adapter's retained-class mode: it requires classes extracted from digest-verified JARs. It is not a claim that all SonarQube Java analysis requires bytecode. There is no Maven invocation, implicit build or scan during build. Original dist is verified before and after scanning and is not modified by scan.

Results and failures​

Completed attempts are finalized at .oyzu/scans/<run-id>/manifest.json. plan.json records frozen policy, resolved tool identities and prepared subjects; events.jsonl retains execution progress. Their digests are included in the result. Each check records tool.disposition (installed/reused). Container tools record tool.image; native tools record the exact tool, version, platform, backend, selection digest and installation key. Established run preparation failures retain a failure manifest and journal with the failed phase; invalid configuration rejected before establishing a run does not create evidence. Scanner acquisition does not pin tools or write the project oyzu.lock. Human output uses the shared build-style terminal renderer: a scan heading, Preflight installation/reuse and readiness, a distinct Scan phase, scoped scanner activity and completion with elapsed time. The final aligned table identifies each scanner, analysis type, subject, execution result and duration. Separate details show findings, provider gates, acceptance, report links and the result path. Narrow terminals use lossless stacked rows. Redirected output preserves chronological readable text; NO_COLOR disables color and quiet mode suppresses progress without hiding the result. JSON stdout contains only the result; structured progress events go to stderr. The terminal view is finalized before reporting preflight errors or the final result. Native output is retained as sonarqube/native.log rather than interleaved with progress. sonarqube/provider.json retains the provider response snapshot.

The native CLI exiting zero is only submission success. Oyzu waits up to three minutes for the server task, then obtains the analysis-specific quality gate. Any execution failure skips aggregate acceptance while independent scanners still run and retain their evidence. Otherwise the fixture can require a passing provider gate and a maximum Trivy finding count. Exit zero means accepted; exit one means execution failure or rejected acceptance. Ordinary input-preparation and finalization errors also use the shared command failure classification: SCAN_SOURCE_MISMATCH is exit one, supported flag/specification diagnostics are exit two, and CONFIG_*/POLICY_* diagnostics are exit three. Other diagnostics retain their shared categories. The specific diagnostic code remains available in human and JSON modes. No incomplete attempt is reported as a finalized success. oyzu scan --offline permits local Trivy checks when their images and inputs already exist. Missing images fail with TOOL_OFFLINE; SonarQube selections fail with SCAN_OFFLINE before analysis. Checks are never omitted to make an offline invocation succeed.

The project dashboard and issue search are current project views, not immutable analysis references. The result labels that distinction, retains the analysis/task IDs and records issue-snapshot truncation above 500 issues. Issue snapshots do not drive this experiment's acceptance decision. A passing provider gate does not mean zero findings or permission to publish.

Trivy source secret scanning​

sonar and trivy are independent optional selections; at least one is required. requireQualityGate requires SonarQube and defaults to false. Trivy runs source secret detection only, with no vulnerability database, network, upstream credentials or Docker socket inside the scanner. It uses the same verified source snapshot. This does not qualify container, dependency-vulnerability or infrastructure scanning.

Trivy's native JSON is retained at trivy/report.json, its stderr at trivy/native.log, and file digests in the result manifest. Each check carries its own resolved tool identity. Finding counts are facts; maximumFindings is the administrative acceptance threshold (omission means no count limit). Native findings never alone imply an execution failure. A nonzero native exit or malformed report is an execution failure. Repository trivy.yaml, ignore files and secret rules do not supply this administrative configuration.

Administrators may supply trivy.rules, an array of native custom secret rules with id, title, regex and severity (LOW, MEDIUM, HIGH or CRITICAL). Built-in rules remain active. Native Trivy validates regex semantics; an invalid rule fails the check. This experiment uses a custom rule matching a harmless existing Maven metadata to demonstrate acceptance rejection without introducing an actual credential. Raw secret reports may contain sensitive source; protect the local result directory. Only counts, not matched secret text, appear in human output.

Limits​

Independent container adapters run concurrently after all selected checks complete preflight. scan.jobs defaults to 2 and bounds active checks (1–65535); set it to 1 for serial execution through the normal configuration cascade. Administrative locks apply. SonarQube waiting for remote analysis occupies its slot while Trivy may run in another. Reports use separate scanner directories and results retain plan order regardless of completion order. A failed check does not cancel independent checks. Acquisition and input preparation remain sequential. Native tool installation, scanner-specific build extraction and immutable remote report storage remain unimplemented. Inputs retained under the experiment result include source and classes; treat that task-owned directory as sensitive project data. Local results provide content integrity, not authenticated provenance or RBAC. Docker administrators can inspect process environments. No scanner receives the Docker socket; the controller requires local Docker access.

Linux Docker execution is the first qualification target; Windows/macOS native CLI qualification remains pending. See the qualification record for measured results and failed expectations rather than inferring support from this reference.

Gitleaks source secret scanning​

Add gitleaks to the administrative scan.policy alongside other scanners, or select it alone. For example:

{
  "gitleaks": {
    "image": "zricethezav/gitleaks@sha256:691af3c7c5a48b16f187ce3446d5f194838f91238f27270ed36eef6359a574d9",
    "maximumFindings": 0
  }
}

This example selects Gitleaks 8.30.0. Versions remain policy-controlled, acquired through shared preflight and recorded in the frozen plan. The adapter runs dir on the verified source snapshot, not Git history. It requires Docker and supports offline execution after image acquisition. scan.jobs bounds concurrency with other scanners; use three to admit all three together.

config optionally supplies administrative native Gitleaks TOML. Omission uses bundled default rules through an explicit owned config. Project .gitleaks.toml, .gitleaksignore and inline gitleaks:allow comments do not override this selection. Native config errors are execution failures. The scanner has no network, upstream credentials or Docker socket, and reads source through a read-only mount.

Native JSON and diagnostics are retained at gitleaks/report.json and gitleaks/native.log, with report digests in the result. Gitleaks is invoked with full native redaction; treat reports as sensitive source metadata nonetheless. Human output shows counts, not matched values. maximumFindings is optional; omission imposes no count limit. Findings do not make execution fail: acceptance compares their count to the configured threshold after required checks finish. A nonzero native exit or malformed report prevents acceptance evaluation.

This qualifies snapshot secret scanning only, not history scanning, exhaustive secret detection, native archive installation or managed credential acquisition. See Gitleaks usage for native rule semantics. Oyzu does not copy or redistribute the scanner image.

Grype artifact vulnerability scanning​

Add grype to the administrative scan.policy. The initial adapter consumes all recorded application/java-archive artifacts from the verified build bundle:

{
  "grype": {
    "image": "anchore/grype@sha256:af65fbc0c664691067788fe95ff88760b435543e45595eb2ca6f102fc476fbe1",
    "maximumFindings": 0
  }
}

This selects Grype 0.110.0. Preflight acquires the policy-selected image, copies and verifies JAR digests, then invokes native grype db update without mounting source or artifacts. Each run owns its database; its tree digest is captured in prepared inputs. Analysis reads that database and the retained artifacts with networking disabled. Project Grype configuration is not loaded. Database age/hash validation remains enabled. Database download failures prevent analysis and retain diagnostics.

Results identify dependency-vulnerability and artifact, retain native JSON at grype/report.json, diagnostics at grype/native.log and preparation diagnostics at grype/database.log. Native database metadata accompanies the evidence. Findings count vulnerability matches, not unique CVEs; omission of maximumFindings means no count limit. Execution failure skips acceptance; findings are evaluated afterward. Independent scanners share scan.jobs; four admits all four supported scanners.

The current implementation downloads a fresh database for every run and retains it in the run directory. It can consume significant disk and network bandwidth. Offline invocation fails explicitly with SCAN_DB_OFFLINE; cache reuse is not implemented. Missing JAR artifacts fail with SCAN_INPUT_MISSING. This does not qualify OCI image, SBOM, source-lockfile, or transitive dependency coverage: only packages Grype catalogs from the recorded JARs are analyzed. A clean result is not a complete dependency audit. Native scanner installation and managed database routing remain outside this proof.

See Grype database behavior and CLI reference.
