Scanning a build

CLI reference

Published from the canonical docs/reference/scan.md file. Features marked experimental remain experimental; check support limitations before relying on them.

oyzu scan runs security and quality scanners against a build you already made: Gitleaks, Trivy, Grype and SonarQube. It checks the same source files and artifacts that oyzu build recorded in dist/, and tells you whether the result passes the thresholds you set. No platform account is needed.

Note: oyzu scan is experimental and has been tested on Windows only (native Gitleaks, and container scanners through Docker Desktop with Linux containers).

oyzu build
oyzu scan
oyzu scan --json

scan never rebuilds, runs tests or publishes. Each call starts a new scan.

Inputs and setup​

There are two ways to choose scanners:

MethodScannersWhere
Project settingsGitleaks, run natively[scan.gitleaks] in oyzu.toml
Administrator policySonarQube, Trivy, Gitleaks, Grype, run in Dockerscan.policy in administrator configuration only

If no scanner is selected, you get SCAN_SELECTION_REQUIRED with the setting to add.

Native Gitleaks​

[scan.gitleaks]
enabled = true
failOnFindings = true
SettingValuesDefaultMeaning
scan.gitleaks.enabledbooleanfalseRun Gitleaks natively on the recorded source.
scan.gitleaks.failOnFindingsbooleanfalseFail the scan if Gitleaks finds anything. When false, findings are recorded but don't fail the scan; Gitleaks errors still fail it.

These settings follow the normal configuration cascade and its constraints. They can't replace or loosen an administrator's container selection; failOnFindings can only make it stricter.

Oyzu installs Gitleaks like any other tool: from your [tools] request if there is one, otherwise a compatible pin or the default version. It doesn't edit your configuration or oyzu.lock, and it never falls back to a Gitleaks on PATH or a container.

Options​

OptionMeaning
--store <DIR>Use this native tool store instead of the shared user store. A relative path is resolved from the project root.
--offlineUse only tools, images and inputs already on this machine. See offline scans.
--jsonPrint only the result on standard output; progress events go to standard error. Works before or after scan.

Administrator scan policy​

Only administrator configuration can set scan.policy. In the protected admin-settings.json file:

{
  "schemaVersion": 1,
  "kind": "local-admin-policy",
  "settings": {
    "scan.policy": {
      "locked": true,
      "value": {
        "sonar": {
          "image": "sonarsource/sonar-scanner-cli@sha256:a3f4215076706c95a17a68c19322ee916e40a3acd081a8c1a1e839e0194afa57",
          "endpoint": "https://sonarqube.example.com",
          "projectKey": "example",
          "sources": ["app/src/main/java", "library/src/main/java"],
          "requireClasses": true
        },
        "trivy": {
          "image": "aquasec/trivy@sha256:af6acf9a6b85dfe389a1941505c0ce9efef52a4719635e1a962f022a3d855daa",
          "maximumFindings": 0
        },
        "requireQualityGate": true
      }
    }
  },
  "profiles": {},
  "requiredCapabilities": []
}

Each scanner (sonar, trivy, gitleaks, grype) is optional, but at least one is required. Images must be pinned by digest. Oyzu pulls missing images through Docker before scanning and reuses ones you already have. Private tool catalogs and custom registry routes aren't supported for scanner images.

KeyMeaning
<scanner>.imageThe scanner image, by digest.
<scanner>.maximumFindingsThe most findings allowed before the scan fails. Omit for no limit. (Trivy, Gitleaks, Grype.)
requireQualityGateRequire a passing SonarQube quality gate. Needs sonar. Default false.
sonar.endpoint, sonar.projectKeyThe SonarQube server and project.
sonar.sourcesSource folders to analyze, relative to the project.
sonar.requireClassesGive SonarQube compiled classes taken from the build's JAR artifacts.
trivy.rulesExtra Trivy secret rules; see Trivy.
gitleaks.configGitleaks TOML rules; see Gitleaks.

Container scanners need Docker on the machine running oyzu scan. Scanners never get the Docker socket.

For SonarQube, set up the SonarQube server and project yourself, and put SONAR_TOKEN in the environment (never in the policy file). The token needs permission to submit analysis and read tasks, quality gates and project issues. endpoint may use HTTP for a local server.

Tool versions belong under [tools] or in the policy image, not in other scanner settings.

Which source is scanned​

scan rebuilds the exact list of source files the build recorded, and their digest must match the build's. It doesn't rediscover inputs or reread ignore files, and a Git commit alone isn't enough.

  • If source changed since the build, the scan fails with SCAN_SOURCE_MISMATCH before any scanner runs. Restore the files or build again.
  • A bundle without a recorded source selection fails with SCAN_SOURCE_SELECTION_MISSING; a malformed one with SCAN_SOURCE_SELECTION_INVALID. Build again with the current CLI.
  • For Cargo, adding an ignored release.toml or a file that could become a workspace member can make the scan refuse even if the recorded digest still matches. Declare the file as a build input or fix the workspace members, then build again.
  • Differences between machines' filesystems can prevent a match. They aren't smoothed over.
  • Artifacts are copied and digest-checked for the scan. The original dist/ is checked before and after and never changed.
  • Source isn't fetched from Git and remote bundles aren't downloaded.

Results and failures​

Each scan is saved under .oyzu/scans/<run-id>/:

FileContents
manifest.jsonThe final result, with digests of the other files.
plan.jsonThe policy, tool versions and inputs used.
events.jsonlProgress events.
<scanner>/report.jsonThe scanner's own JSON report (Trivy, Gitleaks, Grype).
<scanner>/native.logThe scanner's own output.
sonarqube/provider.jsonThe SonarQube server's response.
grype/database.logGrype database download output.

Each check records whether its tool was installed or reused, and the exact image or native tool version. If a scan fails partway, a failure manifest names the phase. A configuration error caught before the scan starts writes nothing. Scanning never pins tools or writes oyzu.lock.

Reports can include secrets or source text, so protect .oyzu/scans. Human output shows only counts, never matched text.

Output​

The terminal view follows the build layout: a Preflight phase (install or reuse each scanner), a Scan phase with each scanner's progress, then a table of scanner, analysis type, subject, result and duration. Details below list findings, quality gates, the pass or fail decision, report links and the result path. NO_COLOR turns color off and --quiet hides progress, not the result.

Exit codes​

ExitMeaning
0Every check ran and the result passes.
1A scanner failed, a threshold or quality gate failed, or SCAN_SOURCE_MISMATCH.
2Invalid flags or input.
3Configuration or policy errors (CONFIG_*, POLICY_*).

If one scanner fails, the others still run and keep their reports, but the overall pass/fail decision is skipped. Findings by themselves never count as a scanner failure; they're compared with the threshold afterwards. A nonzero scanner exit or a malformed report is a failure.

SonarQube​

A successful scanner exit only means the analysis was submitted. Oyzu then waits up to three minutes for the server to finish and reads that analysis's quality gate.

The dashboard and issue links in the result show the project's current state, not a snapshot of this analysis; the result says so and keeps the analysis and task IDs. Issue snapshots are cut off at 500 issues and don't affect the result. A passing quality gate doesn't mean zero findings or permission to publish.

Trivy source secret scanning​

Trivy runs secret detection on the recorded source only. It has no vulnerability database, network, credentials or Docker socket. Repository trivy.yaml, ignore files and secret rules are ignored.

Administrators can add trivy.rules: an array of custom secret rules with id, title, regex and severity (LOW, MEDIUM, HIGH or CRITICAL). Built-in rules stay on. An invalid regex fails the check.

Gitleaks source secret scanning​

Add gitleaks to scan.policy, alone or with other scanners:

{
  "gitleaks": {
    "image": "zricethezav/gitleaks@sha256:691af3c7c5a48b16f187ce3446d5f194838f91238f27270ed36eef6359a574d9",
    "maximumFindings": 0
  }
}

This selects Gitleaks 8.30.0.

  • It scans the recorded source files (gitleaks dir), not Git history.
  • gitleaks.config can supply Gitleaks TOML rules. Without it, Gitleaks' default rules apply. Project .gitleaks.toml, .gitleaksignore and gitleaks:allow comments are ignored. A config error fails the check.
  • Source is mounted read-only. There's no network, credentials or Docker socket.
  • Gitleaks redacts matches in its report, but treat reports as sensitive anyway.

See the Gitleaks documentation for rule syntax.

Grype artifact vulnerability scanning​

Add grype to scan.policy to check the build's JAR artifacts (application/java-archive) for known vulnerabilities:

{
  "grype": {
    "image": "anchore/grype@sha256:af65fbc0c664691067788fe95ff88760b435543e45595eb2ca6f102fc476fbe1",
    "maximumFindings": 0
  }
}

This selects Grype 0.110.0.

  • Each scan downloads a fresh vulnerability database into the scan folder, then analyzes the JARs with networking off. This uses disk space and bandwidth on every run.
  • Project Grype configuration is ignored. Grype's own database age and hash checks stay on.
  • Findings count vulnerability matches, not unique CVEs.
  • Only packages Grype finds in the recorded JARs are checked. Container images, SBOMs, lock files and other artifacts aren't. A clean result isn't a full dependency audit.

See Grype database behavior and the Grype CLI reference.

Limits​

  • Concurrency. scan.jobs (1 to 65535, default 2) sets how many scanners run at once. Set 1 for one at a time, or 4 to run all four together. A failed scanner doesn't stop the others. Results keep plan order.
  • Offline scans. oyzu scan --offline works when tools, images and inputs are already on the machine. A missing image fails with TOOL_OFFLINE, native Gitleaks without a recorded installation or pin fails before resolving a version, SonarQube fails with SCAN_OFFLINE and Grype with SCAN_DB_OFFLINE. Checks are never skipped to make an offline scan pass.
  • Scanners are never run during oyzu build, and scan never runs Maven or other build tools.
  • Native installation is available for Gitleaks only. Trivy, Grype and SonarQube run in Docker.
  • Grype's database isn't cached between scans.
  • Results prove the files weren't changed; they aren't signed provenance. Docker administrators on the machine can see scanner environment variables, including SONAR_TOKEN.
  • Missing JAR artifacts for Grype fail with SCAN_INPUT_MISSING.
  • For nested projects, inputs from sibling folders outside the project are checked against the build but may not be passed to scanners.
