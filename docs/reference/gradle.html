Gradle builds and tests

CLI reference

Published from the canonical docs/reference/gradle.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Status: experimental. Oyzu detects build.gradle or build.gradle.kts without a build YAML file. A native multi-project or composite build is one Oyzu target: Gradle owns project membership, included builds, task dependencies and native output paths. Oyzu uses that model to plan artifacts and collect reports. The EX-024 project demonstrates an application, library and included support build.

Commands and prerequisites​

oyzu run list
oyzu run test
oyzu inspect dist
oyzu build

Static task discovery does not execute Gradle. It exposes native build and test tasks and the shared Java lint/format tasks. Native build already includes tests, so captured builds do not repeat a separate test stage. Qualified task names and TOML replacements follow the common task engine. No test/report configuration is needed for the default Java test tasks.

Plain oyzu build uses the supported host Gradle path. Its native build lifecycle can run tests even under Oyzu's fast selection; --full additionally selects Oyzu's separate quality operations. Use --isolated --full to request the captured path with full checks. A custom native JUnit directory does not change the independently observed JaCoCo destination: both remain required host build evidence, and missing coverage blocks successful artifact export. This report-binding correction and missing-coverage export gate passed the Linux native host regression.

Direct tests require provisioned Gradle 8.14.3, JDK 17 and native project/test dependencies, including JaCoCo 0.8.13. Set GRADLE_HOME or put Gradle on PATH, and configure JAVA_HOME for the JDK. The native Gradle user home and project repositories remain authoritative. An existing wrapper is used when discovered; its distribution must already be provisioned. Direct-test invocation uses these provisioned tools. Host oyzu build separately uses shared tool preparation and records its selected versions in oyzu.lock; a tool on PATH alone does not pin that build's identities. Product model/test commands pass --offline and disable automatic Java toolchain downloads. Missing cached dependencies fail explicitly; offline dependency resolution does not sandbox arbitrary native build logic or prevent a wrapper from trying to provision itself.

Captured builds additionally require Docker and the provisioned toolchain image:

docker build -f tooling/images/gradle.Dockerfile -t oyzu-toolchain/gradle:8.14.3-jdk17 .
oyzu -C examples/builds/java-gradle-multi-project/project build --isolated --full

Locked JDK in the captured worker​

A JDK the project selects, by [tools] java or native requirements, is locked by build preflight and restored read-only in the worker at /scratch/jdktool from the verified Temurin archive in oyzu.lock, as for Maven.

An explicit toolchainVersion in gradle/gradle-daemon-jvm.properties selects and constrains the daemon JDK's feature release. For example, toolchainVersion=25 normally selects a stable Java 25 release; an explicit [tools] java override must satisfy the same native constraint. The declared vendor remains binding at native launch. The existing provider supplies Temurin; explicit vendors other than ADOPTIUM/Eclipse Adoptium and native-image-capable daemon requirements are refused before acquisition with the source path and field. Literal generated property names and integer feature releases are supported; malformed or escaped criteria require correction or a matching provisioned native runtime.

When daemon criteria are absent, existing inference uses the highest literal Java level in root/first-level build scripts (JavaLanguageVersion.of(21), sourceCompatibility) as a compiler floor, or Java 21 when none is declared. With explicit daemon criteria, compilation and optional toolchain declarations remain unchanged for Gradle to enforce; they do not replace the daemon runtime. The worker restores one selected JDK. Builds requiring another JDK for a task can still fail natively with automatic downloads disabled; this is not multi-JDK provisioning.

The selected installation is always offered through -Dorg.gradle.java.installations.paths, including before Gradle's daemon JVM selection; automatic toolchain downloads stay disabled. The standard image's Gradle 8.14.3 runs on the selected JDK when it is release 24 or older. For a newer JDK the launcher retains the image's bootstrap JDK while offering the selected installation to native Gradle. A suitably provisioned newer Gradle can use that installation for its declared daemon criterion; Gradle 8.14.3 compatibility remains a native limit. A project's own wrapper version is not yet provisioned in the captured worker. A selected JDK older than 17 is refused with TOOL_UNSUPPORTED_VERSION.

The CLI does not pull a missing image. Captured acceptance runs on Linux; portable host tasks do not establish isolated executor support on every platform.

Direct test bundles​

After common task admission, the builder evaluates native models for the root and included builds. The observation command requests only Oyzu's metadata tasks; it does not deliberately execute project lifecycle tests or compilation. Gradle configuration, plugins and native build logic still execute normally. This is explicit host execution, not static discovery or a security boundary.

The model identifies enabled test tasks with attributable source files, their native JUnit destinations and injected JaCoCo destinations. Projects without test sources do not create test obligations. Builds with no discovered tests fail rather than manufacturing a passing suite. The exact implicit command is instrumented to run the discovered tests across the composite, respecting native dependencies. Custom command bodies remain unchanged and must fulfill the required reports; forwarded extra arguments are not yet supported by the default reporting adapter.

Before each run, the adapter removes previous XML from the selected native test directories and their selected coverage XML. Native rerun semantics produce current evidence. JaCoCo finalizers generate coverage, including after failed assertions. Native suites are combined per test task without replacing their test cases, and fresh private JUnit/JaCoCo files enter the shared collector. dist/manifest.json links each report and its summary, plan and logs. Native output remains in project build directories; source files and versions are unchanged. Direct tests create no application artifact records and do not run packaging, lint or formatting.

Common pre/post hooks apply; a failed test blocks its success-only post hook. Failed assertions, missing or malformed reports and unmet configured coverage thresholds fail the command while retaining available evidence. oyzu inspect dist verifies the resulting bundle. See direct test reports for output preservation, history, report overrides and host provenance limits. Direct execution is not hermetic, and a local passing test grants no publication or signing authority.

Captured snapshot builds​

Preparation evaluates native models and acquires Maven-layout dependencies through the scoped public repository adapter. Build execution uses the captured repository offline. Private/custom repository connectors are not yet supported. Gradle plugins come from the admitted plugin portal. Version inference resolves native versions, scoped tags and commit impacts before projecting source snapshots in the private build. Gradle archive tasks supply filenames and archive versions; supported file kinds include JAR/WAR/EAR, ZIP, TAR and gzip archives. The bundle records their planned versions and digests.

The first native model pass retains original versions. The host freezes a version-plan.json keyed by project directories across the composite, then native preparation validates original versions and applies each decision. Offline execution uses that same projection. Unique native project names supply scoped tag subjects; repeated names use directory paths. An unspecified native version can use a tag baseline without inventing a native declaration. Captured native resolution supplies local project dependencies with full build-tree identities, including substituted projects in included builds. Project identities come from Gradle's public Project.buildTreePath; selected dependency edges retain Gradle's resolved ProjectComponentIdentifier.buildTreePath. Detached configuration roots are not used as project identities. The shared resolver computes transitive version impacts; unrelated project directories retain independent bases. Missing or unresolved graph facts fail preparation. Host metadata-only queries do not resolve this graph. Prepared layout version 3 adds these facts; recreate older captures. JAR manifest attributes remain native build behavior rather than being rewritten to add implementation-version metadata.

Native Java tests supply JUnit and JaCoCo, with source-free projects omitted. Shared Java quality gates run before successful artifact publication into dist. Report injection is shared with direct testing; repository routing, snapshot projection and isolation belong to the captured path. Missing archives, unresolved dependencies and required stage/report failures remain build failures.

Gradle plugin portal​

Captured acquisition admits two public sources: Maven Central and the Gradle plugin portal (https://plugins.gradle.org/m2/). The broker also admits the portal's artifact host, https://plugins-artifacts.gradle.org/, so that portal redirects for plugin JARs stay authorized; redirects to Maven Central use the Central source. Plugins applied in settings.gradle or a project plugins {} block, and gradlePluginPortal() declared in pluginManagement, buildscript or project repositories, resolve through the broker during preparation:

// settings.gradle
plugins { id 'com.gradle.develocity' version '4.2' }

The init script adds an Oyzu Central entry and an Oyzu portal entry to pluginManagement, which takes the place of Gradle's implicit portal default, and routes each recognized repository to its own loopback broker path. Any other repository URL still fails preparation with Gradle repository requires an approved source adapter. Captured files from both sources land in one Maven-layout repository that the offline build reads. The prepared tree records the serving source of each file in repository-sources.json, and the dependency snapshot attributes every inventoried package to maven-central, gradle-plugin-portal or gradle-plugin-artifacts accordingly. A redirect to any other host fails with a source denial rather than widening admission.

Settings plugins are resolved while Gradle evaluates the settings script, before Oyzu can reroute repositories the script itself declares; Oyzu's own entries come first, so a plugin they serve is found there. Plugin behavior that downloads at run time (for example Gradle toolchain provisioning) is outside this admission. The native probe python tooling/test-gradle-preparation.py --gradle-home <gradle-home> --java-home <jdk-home> includes a portal settings-plugin case. The positive portal/JMH composite supplement now passes a captured/full build, required reports and fresh delivered-JAR consumers at source 47363a03; original corpus failures retain their separate scope in the JVM qualification.

Verification and current limits​

python tooling/test-gradle-metadata.py --gradle-home <gradle-home> --java-home <jdk-home> checks metadata-only host observation and an offline captured-graph fixture with duplicate project paths across an included build. It requires native project identities and the actual substituted local edges without external dependencies. The Gradle 9.8.0/Java 26.0.2.1 diagnosis confirmed that an empty detached configuration has a separate non-project root while public project build-tree paths retain the composite identities. The corrected adapter and regression passed native metadata qualification on Gradle 9.8.0/Java 26.0.2.1 and Gradle 8.14.6/Java 17. At source 47363a03, the seven registered captured cases also pass, including usable delivered App/Support JARs and required failure gates. The host direct report/coverage probe passes separately. The original RxJava :bundle failure and Mockito/Pioneer/SpotBugs preparation failures remain recorded separately; these bounded results do not complete the JVM corpus.

python tooling/test-gradle-direct.py --cli <compiled-path> --gradle-home <gradle-home> --user-home <native-cache> exercises EX-024 and an included-build test variation with custom JUnit paths, repeated runs, hooks, actual failed assertions, source preservation and bundle inspection. Install tooling/design-requirements.txt for the harness. Its optional --acquire explicitly provisions fixture dependencies before offline product invocation. CI provisions a checksum-pinned Gradle distribution and runs the probe on Windows, macOS and Linux after compiling the CLI. Both native direct variations passed locally on Windows with Gradle 8.14.3/JDK 17.0.20.1; the direct probe also passed on Linux and macOS at c15008b in run 37054773923 (jobs 110998609377 and 110998609418). The Windows CI step remains pending. Current results are recorded in implementation status; CI registration alone is not acceptance.

tooling/test-gradle-preparation.py separately exercises native repository capture, a fresh offline Gradle home, snapshot archives and report generation. It passed on Windows after the shared reporting extraction, including successful and failed-test reports. It uses an explicit fixture download proxy, not the product executor. The captured Java suite passed at revision 039f83a in job 110970888463, before the direct-reporting extraction.

The bounded normalized composite qualification adds root/included-build report ownership, custom native JUnit destinations, per-module JaCoCo classes, usable delivered JARs and failed-check blocking to the existing Gradle group. The direct probe additionally checks a plain host build with custom JUnit output and a zero-exit native run that omits required coverage. On 2026-10-16, the first normalized captured flow passed on Linux, including actual delivered App/Support execution, attributed native reports and bundle inspection. The complete direct probe and both independent host cases also passed. The full registered Gradle group passed repeatability, native lint/format/test failure gates, custom/included paired JUnit/JaCoCo ownership and included-test failure export blocking. See the qualification record for exact runtime identities and the distinction between provisioned direct tools and managed host tools. This qualifies the bounded Linux fixture, not the complete authored Gradle scenario catalog.

Broader Gradle versions, non-Java languages, custom coverage plugins/source ownership, generated test sources and all plugin/composite configurations are not qualified by these fixtures. Native disabled tests and source-free tasks are omitted; unknown test source ownership fails explicitly. Release authorization, private connectors and full authored-scenario coverage remain separate implementation work.

The compiled Oyzu worker owns process sequencing and native report composition. Native Java integrations remain embedded assets; Python is not required to execute these builder operations. Rebuild captured images after updating the worker.

The observed daemon-JVM selection gap and pending native proof are recorded in Gradle daemon JVM qualification.
