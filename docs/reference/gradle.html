Gradle builds and tests

CLI reference

Published from the canonical docs/reference/gradle.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Oyzu detects build.gradle or build.gradle.kts without any build YAML, then builds, tests and packages the project with Gradle. A multi-project or composite build is one Oyzu target. Gradle still owns project membership, included builds, task dependencies and output paths, and Oyzu uses that model to plan artifacts and collect reports. The multi-project example has an application, a library and an included support build.

Note: The Gradle builder is experimental. Captured builds run on Linux (Docker required). It's the Gradle side of the java/app builder, supplied by the oyzu/java plugin, which selects Gradle for a folder with build.gradle or build.gradle.kts (or with.build-tool: gradle); see plugin catalog and selecting a role.

What each stage reads​

With the next Java plugin release and a compatible CLI supporting private stages, native host format-check reuses independently through its fixed reads and empty private-output declaration. Editing an existing README's contents does not change its source-read key, but a source-derived snapshot version can change the action definition and still cause a miss. Whole-target projection identity can also cause conservative misses. Editing a formatted Java file reruns it. Lifecycle builds (including tests) and Checkstyle currently have unbounded output contracts and rerun even on unchanged native builds. This mixed pipeline cannot restore a whole-target result. Captured copy/export behavior is unchanged. See Java quality for the read boundary.

Gradle build and test stages stay unbounded. settings.gradle, build.gradle and their Kotlin variants are programs; the current native integration does not report all configuration-script reads and task inputs. Tests can also read files at run time. Conventional source directories do not establish a complete boundary for those stages.

The captured package operation consumes only its build producer's archives, using an upstream-only contract. Shared Java formatting and lint declare their own boundaries. These declarations reach users with the next release of the Java plugin.

Quick start​

oyzu run list
oyzu run test
oyzu build
oyzu inspect dist

Captured builds also need Docker and the base execution image. The JDK and, for a project without a Gradle wrapper, Gradle itself are restored from oyzu.lock:

oyzu -C examples/builds/java-gradle-multi-project/project build --isolated --full

Note: Isolated Gradle builds on the base execution image are not supported yet. Isolated builds run in a Linux container.

Tasks​

  • oyzu run list doesn't run Gradle.
  • It lists Gradle's build and test tasks and the shared Java lint and format tasks.
  • Gradle's build already includes tests, so captured builds don't run a separate test stage.
  • Qualified task names and TOML replacements work as in the common task engine.
  • The default Java test tasks need no test or report configuration.

Build modes​

CommandRunsNotes

A custom Gradle JUnit directory doesn't change where JaCoCo coverage is read. Both are required evidence for a host build, and missing coverage blocks artifact export.

Tools​

DependenciesYour project and test dependencies, including JaCoCo 0.8.13. Gradle's user home and your project's repositories stay in charge.
  • Direct tests need these tools installed.
  • oyzu build on your machine prepares tools through the shared tool management and records the versions in oyzu.lock. A tool on PATH alone doesn't pin the build.
  • Oyzu runs Gradle's model and test commands with --offline and turns off automatic Java toolchain downloads. Missing cached dependencies fail with an error.
  • Offline resolution doesn't sandbox arbitrary build logic, and doesn't stop a wrapper from trying to install itself.

Locked JDK in isolated builds​

A JDK your project selects, through [tools] java or native requirements, is locked by build preflight. It is restored read-only at /scratch/jdktool from the verified Temurin archive in oyzu.lock, the same way as for Maven.

Daemon JVM criteria​

An explicit toolchainVersion in gradle/gradle-daemon-jvm.properties selects the daemon JDK's feature release.

  • For example, toolchainVersion=25 normally selects a stable Java 25. An explicit [tools] java must satisfy the same constraint.
  • The declared vendor still applies when Gradle launches.
  • Oyzu supplies Temurin. It refuses vendors other than ADOPTIUM or Eclipse Adoptium, and daemon requirements for a native-image-capable JDK, before downloading anything. The message gives the source path and field.
  • Literal property names and whole-number feature releases are supported. Malformed or escaped criteria need to be corrected, or a matching JDK must already be installed.

Without daemon criteria, Oyzu uses the highest literal Java level in the root build script (JavaLanguageVersion.of(21), sourceCompatibility) as the startup minimum, or Java 21 if none is declared. Adjacent or nested scripts do not prove native membership and do not contribute static startup requirements. oyzu pin does not execute Gradle to discover nested compiler requirements.

  • With explicit daemon criteria, your compilation and toolchain declarations are left for Gradle to enforce. They don't replace the daemon JDK.
  • The container restores one JDK. A build that needs a second JDK for some task can still fail, because automatic downloads are off.

Compiler availability​

The Java package advertises the required gradle-compiler-facts engine capability for this preparation behavior. Catalog selection excludes it on an older engine; use an engine implementing that capability or an eligible earlier package. The core's prepared API digest must still equal the selected package's Gradle runtime digest. See package compatibility.

During native model preparation, Gradle resolves the effective compiler provider of enabled compileJava and compileTestJava tasks that have existing sources. This includes nested native member projects. The check runs after configuration and before metadata tasks collect dependencies or reports; it does not compile sources or substitute the daemon JVM for a task-specific compiler or vendor. The actual compiler must support the task's effective options.release, or both sourceCompatibility and targetCompatibility when no release is set. An explicit release takes precedence over the source and target defaults.

If a compiler is unavailable, the native diagnostic contains OYZU_GRADLE_COMPILER_UNAVAILABLE, the build directory, project, task and known toolchain or target level, followed by Gradle's original cause. Provide the requested native compiler, or select a matching daemon JDK. For example, a single-JDK build needing a Java 25 compiler can declare:

# gradle/gradle-daemon-jvm.properties
toolchainVersion=25

Without daemon criteria, explicitly pin both a suitable [tools] java and a compatible [tools] gradle; Java 25 needs Gradle 9. A Java pin alone does not change the Gradle line inferred from the root script. A wrapper must itself support the chosen daemon JDK.

Settings or plugin configuration can fail before this check. Custom compilation tasks, generated sources absent during preparation, conditional execution and compiler changes after the guard remain native execution concerns. This is not complete static inference of every compiler in a Gradle build.

JDK installation and Gradle versions​

  • The selected JDK is always offered to Gradle through -Dorg.gradle.java.installations.paths, including before daemon JVM selection. Automatic toolchain downloads stay off.
  • The image's Gradle 8.14.3 runs on the selected JDK when that is release 24 or older.
  • For a newer JDK, the launcher keeps the image's bootstrap JDK and offers the selected one to Gradle. A newer Gradle can then use it for the daemon criterion, but Gradle 8.14.3 may not support the newer JDK.
  • A project's own wrapper version isn't installed in the container yet.
  • A selected JDK older than 17 is refused with TOOL_UNSUPPORTED_VERSION.

Direct test bundles​

oyzu run test writes its reports to a bundle under dist/. After the usual task checks, Oyzu asks Gradle for the model of the root build and its included builds.

  • The query runs only Oyzu's metadata tasks. It doesn't run your tests or compile your code on purpose.
  • Gradle configuration, plugins and build logic still run normally. This is ordinary execution on your machine, not a security boundary.

What the model finds​

  • Enabled test tasks that have test source files, with their JUnit destinations and JaCoCo destinations.
  • Projects with no test sources don't create test obligations. A build with no tests fails instead of producing a passing empty suite.
  • The implicit command runs the discovered tests across the composite, respecting task dependencies.
  • Custom commands run unchanged and must produce the required reports. Forwarded extra arguments aren't supported by the default reporting.

Reports​

  • Before each run, Oyzu removes previous XML from the selected test directories and the selected coverage XML.
  • JaCoCo coverage is generated even after failed assertions.
  • Each test task's suites are combined without dropping test cases, and fresh private JUnit and JaCoCo files are collected.
  • dist/manifest.json links each report to its summary, plan and logs.
  • Output stays in your project's build directories. Sources and versions are unchanged.
  • Direct tests create no application artifact records and don't package, lint or format.

Hooks and failures​

  • Pre and post hooks apply. A failed test skips its success-only post hook.
  • Failed assertions, missing or malformed reports and unmet coverage thresholds fail the command and keep the evidence available.
  • oyzu inspect dist checks the bundle.
  • See direct tests for output handling, history, report overrides and provenance.
  • Direct execution isn't isolated, and a passing local test grants no publishing or signing authority.

Isolated snapshot builds​

Preparation reads Gradle's models and downloads Maven-layout dependencies through Oyzu's scoped public repository adapter. The build then runs offline against the captured repository.

  • Private and custom repositories aren't supported.
  • Gradle plugins come from the plugin portal.
  • Version inference resolves native versions, scoped tags and commit changes, and Oyzu applies the versions in a private copy of the source.
  • Gradle's archive tasks supply the file names and archive versions. JAR, WAR, EAR, ZIP, TAR and gzip archives are supported, and the bundle records their planned versions and digests.
  • JAR manifest attributes are not rewritten to add implementation-version metadata.

Tests and checks:

  • Java tests supply JUnit and JaCoCo reports. Projects without sources are skipped.
  • The shared Java quality checks run before artifacts are published to dist.
  • Missing archives, unresolved dependencies and failed required stages or reports fail the build.

Version plan​

Oyzu reads the original versions first and freezes a version-plan.json for the project directories in the composite. Preparation checks the original versions and applies each decision, and the offline build uses the same result.

  • A unique Gradle project name supplies the scoped tag name. Repeated names use directory paths.
  • An unspecified version can take its version from a tag without adding a version to your build.
  • Local project dependencies keep full build-tree identities, including substituted projects in included builds.
  • Missing or unresolved graph facts fail preparation. Metadata-only queries on your machine don't resolve this graph.
  • Changes in one project affect the projects that depend on it. Unrelated project directories keep independent bases.

Gradle plugin portal​

Captured downloads come from two public sources: Maven Central and the Gradle plugin portal (https://plugins.gradle.org/m2/).

  • The portal's artifact host, https://plugins-artifacts.gradle.org/, is also allowed so portal redirects for plugin JARs work. Redirects to Maven Central use the Central source.
  • Plugins applied in settings.gradle or a project plugins {} block, and gradlePluginPortal() in pluginManagement, buildscript or project repositories, resolve through Oyzu during preparation:
// settings.gradle
plugins { id 'com.gradle.develocity' version '4.2' }

How it works:

  • An init script adds an Oyzu Central entry and an Oyzu portal entry to pluginManagement (replacing Gradle's implicit portal default) and routes each recognized repository to its own local path.
  • Any other repository URL fails preparation with Gradle repository requires an approved source adapter.
  • Files from both sources go into one Maven-layout repository that the offline build reads.
  • repository-sources.json in the prepared tree records which source served each file, and the dependency snapshot lists each package under maven-central, gradle-plugin-portal or gradle-plugin-artifacts.
  • A redirect to any other host fails with a source denial.

Limits:

  • Settings plugins resolve while Gradle evaluates the settings script, before Oyzu can reroute repositories that the script declares. Oyzu's own entries come first, so a plugin they serve is found.
  • Plugin behavior that downloads at run time, such as Gradle toolchain provisioning, isn't covered.

Current limits​

  • Java projects are the supported case. Non-Java languages, custom coverage plugins, generated test sources and unusual plugin or composite setups may not work.
  • Disabled tests and source-free tasks are skipped. Test tasks whose sources can't be attributed fail with an error.
  • Private repositories and release authorization aren't supported.
  • Daemon JVM selection for a Gradle build that needs a JDK newer than the image supports is limited by Gradle 8.14.3 itself (see JDK installation and Gradle versions).
