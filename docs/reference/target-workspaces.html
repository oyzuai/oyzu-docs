Host target workspaces and artifact inputs

CLI reference

Published from the canonical docs/reference/target-workspaces.md file. Features marked experimental remain experimental; check support limitations before relying on them.

A native oyzu build gives each target its own private copy of its source before it prepares dependencies. The target's hooks and stages share that copy, but other targets can't see the files it generates. To pass files from one target to another, use materialize. This page covers which source goes into a target's workspace, how artifacts are passed between targets, and how Python wheels and Docker images fit in.

Note: Private workspaces keep targets apart; they aren't a sandbox. Native processes still have your user's access to files and the network. oyzu run tasks run in your checkout as usual.

Platform scope: Use an x64 host and supported x64 build targets. ARM64 is unsupported. Feature-specific limits are listed in the support matrix.

Source selection​

Each target's folder is copied with your current edits and untracked files, minus the usual exclusions (.git, .oyzu, dist, target, node_modules, virtual environments). Files outside the target's folder must be listed in inputs, unless they already belong to the same native project:

builds:
  api:
    uses: node/app
    path: api
    inputs: [../../shared/schemas]
  • inputs is a list of file or folder paths relative to the build.yaml that declares them, not to the target's path.
  • Paths must stay inside the Git repository, or inside the build root when there is no repository. Absolute paths and paths that escape fail.
  • On the container path, an input must stay under the folder holding build.yaml and match at least one captured file. It becomes part of the target's cache scope (declared inputs).
  • Declared inputs also join each stage's source read set, including stages with explicit captured-provider contracts. A declaration such as inputs: [docs/data] keeps that folder visible to a confined stage and includes its files in the stage's key. Paths remain relative to build.yaml even for a target in a subfolder. Declarations add reads; they cannot make an unbounded stage confined.
  • Copies keep the repository-relative layout. Each target gets its own copy.
  • Symlink and reparse-point restrictions still apply.

Only selected targets and their dependencies need their inputs. For example, oyzu build cli doesn't need the docs target's inputs, but oyzu build docs and a full build do. A missing input of a selected target fails before anything runs.

Use artifact relationships, not inputs, for another build's generated output. Oyzu doesn't infer what a script reads.

Repeated builds​

Private workspaces live in .oyzu/host-workspaces and persist between builds:

  • Each build updates them in place. Files whose size, modification time and read-only flag match aren't rewritten; others are copied again, and files no longer selected are removed.
  • A source file is read and hashed only when it changed. Oyzu remembers each file's digest with its size, modification time and file identity in .oyzu/source-stat-cache.json; while those still match and the private copy is current, the remembered digest is used without opening the file. Builds with --require-release read and hash every file.
  • Like Git's index, this trusts file metadata. On Linux and macOS the status-change time catches a rewrite that keeps the size and restores the modification time; on Windows such a rewrite isn't noticed. Delete .oyzu/source-stat-cache.json to make the next build read everything.
  • The build's source revision, recorded for verification evidence, hashes each file with line endings normalised. Oyzu remembers that hash by the file's content digest in .oyzu/source-revision-digests.json, so only content it hasn't seen is read again. Its time is part of the Source evidence step. Builds with --require-release read every file for it too.
  • Between builds the copies are parked outside the checkout (see source parking).
  • At the end of a build, files the build generated inside the workspace are removed.
  • An interrupted build leaves state that the next build cleans up.
  • Copies keep modification times, and paths stay the same between builds, so native tools can stay incremental.
  • Rust compiler caches stay in the original project's .oyzu/native/rust, under the cache budget.

Cleaning workspaces never removes bundles, installed tools or compiler caches.

Artifact placement​

builds:
  server:
    uses: rust/app
    path: server
  consumer:
    uses: node/app
    path: consumer
    materialize:
      - from: server
        to: inputs/server
      - from: server
        into: inputs/original
FieldMeaning
fromThe producer target. Required.
artifactThe producer's logical output name. Optional when the producer has one primary artifact.
toExact destination for a file, or the folder to fill with a directory artifact's contents.
intoFolder to place a file in, keeping its file name. If the file name is only known after the build (a native wheel), the real name is used; see file name discovery. Directory artifacts use to.
usageruntime (default), build or data; see artifact compatibility.
runtimeA local image that must accept a native Python wheel; see native wheels. Only with usage: runtime.

Set exactly one of to and into.

  • Destinations are relative to the consumer target.
  • Archives aren't extracted, source files aren't overwritten, and destinations can't overlap.
  • materialize already orders the targets; don't add depends_on as well.
  • Platform compatibility and artifact identity are checked.

Artifacts are passed after all of the producer's actions and required reports succeed, and before the consumer's first action. Each consumer gets its own copy, checked against the collected digest, and the manifest records each handoff. Inputs that the consumer needs during dependency preparation (for example, files npm ci reads) aren't supported.

The producer's pre_build, build and post_build actions share its workspace, so changes a post-hook makes to the output are included. A failure in any of them means no artifact is passed, even if output files were written. A failed producer blocks its consumers; independent artifacts can still appear in the failed bundle.

A host-built Python output is a wheel folder named primary, so use to. A python/package built in a worker image (--image pip=<image>) exports files named wheel and sdist; choose one with artifact: wheel and into.

Artifact compatibility​

materialize.usage says how the consumer uses the artifact:

usageCompatibility checked against
runtime (default)The consumer artifact's platform.
buildThe platform the consumer's build runs on, for a tool that runs during the build. The producer must be unambiguous.
dataNothing: the bytes are included without any runtime claim. The output must still be unique, the producer successful and the bytes verified.

Artifacts carry oyzu.dev/artifact-compatibility:

ValueMeaning
targetBuilt for a specific platform.
pendingMust be inspected by the builder before use.
independentRuns anywhere, such as a pure Python wheel.
nativeBound to one platform, and checked against the consumer's runtime.
unknownCompatibility can't be established.

pending and unknown artifacts can't be used at runtime. The handoff record notes the consumer's platform and usage under oyzu.dev/artifact-consumer. These checks don't certify arbitrary binaries or ABIs.

When a consumer has several platforms, each gets the producer variant built for its platform. A producer with no platforms that outputs a python/package wheel can serve several consumer platforms: pure wheels are shared, native wheels go through the runtime check. A plain native build always uses host outputs; for a native binary feeding an image for another platform, use --all-platforms.

Host coordinator with image workers​

A native build can also include docker/image targets. Images build in a rootless BuildKit worker, while the other targets still run on the host. Docker is needed only when an image target is selected. No build container gets the host Docker socket, and no nested Docker daemon is started.

Note: Image workers in native builds are experimental and tested on Windows.

Image targets need the base execution image and, for RUN steps, the pinned rootless BuildKit worker; the Docker plugin package supplies the helpers. Oyzu pulls both by pinned digest on first use.

Base images must already be in the Docker daemon. Preparation records their identities, and worker actions run offline. Your docker.apparmorProfile setting still applies. An image tag doesn't satisfy a tool pin.

A Linux producer and image:

builds:
  package:
    uses: python/package
    path: package
  image:
    uses: docker/image
    path: image
    materialize:
      - from: package
        to: payload

oyzu build image --plan shows the producer, the artifact edge and each target's executor without contacting Docker. oyzu build image runs it. The Dockerfile can use COPY payload/ /wheels/ without knowing the wheel's versioned name. Installing the wheel into the image is up to the Dockerfile.

  • The image's build context follows its source selection and .dockerignore, plus the materialized artifacts.
  • Files your hooks generate don't join the context unless they were already part of it.
  • Named image platforms must include the worker's platform. Use --all-platforms for several platforms.
  • Fast builds assemble and verify the image. --full adds image assertions, lint and formatting.
  • Image content and platform are always verified before publication.
  • --isolated builds the whole graph in containers instead.

Host Python wheel folders are inspected after collection. A wheel tagged pure Python and none-any can go to any platform. A host-built wheel whose tags all name one Linux x86_64 or aarch64 platform (linux_*, manylinux*, musllinux_*) is native and goes through the runtime check below. Other native tags, such as Windows or macOS, fail the handoff, even on the same OS.

Native wheels and the consumer runtime​

Before a native wheel enters the consumer's workspace, Oyzu runs pip install --dry-run --no-index --no-deps for it in the consumer's runtime image, with networking off. pip decides whether the Python version, ABI and wheel tag fit. The runtime image is:

  1. the input's runtime: <image>, a local image (never pulled) that must match the consumer's platform; else
  2. the consumer's pip dependency base image (a requirements.txt used with a pinned base; see Docker images).
materialize:
  - from: package
    to: inputs
    runtime: registry.example/python:3.12-slim   # only needed without a pip base

A consumer with neither, such as a plain COPY into scratch, can't receive a native wheel. Use usage: data to include it without the check.

For generic linux_x86_64 and linux_aarch64 wheels, Oyzu also checks:

  • libc. Oyzu inspects the wheel's .so files and the consumer's Python. A clear glibc/musl mismatch is refused before the image builds, naming the wheel, file, linkage and image. If it can't tell, it reports NATIVE_WHEEL_LIBC_UNVERIFIED and lets pip decide.
  • Extension suffix. For a *.cpython-<version>-<platform>.so file, Oyzu compares the suffix with the consumer Python's supported suffixes. A mismatch, or a consumer that can't report them, gives the warning NATIVE_WHEEL_EXTENSION_SUFFIX_UNVERIFIED. The build continues. If you see it, check that the module imports in the final image; if not, build the wheel with that image's Python. Plain .so and .abi3.so files aren't compared.

manylinux* and musllinux_* wheels skip these extra checks; pip decides.

A rejection fails the consumer with the wheel name, the image and the libc mismatch or pip's message. It appears as an ERROR line, in diagnostics with --json, and in full in the action log.

Wheels built for a version (cp313-cp313-linux_x86_64) are accepted only by the matching Python; abi3 wheels are accepted by any compatible Python.

Host-built native wheels need a Linux host. Windows and macOS hosts build win_*/macosx_* wheels, which a Linux consumer refuses.

Wheels built in a worker image​

To get a Linux native wheel from any host with Docker, build it in a container with oyzu build --image pip=<image>. Use an image with a C compiler (not -slim) that meets the bring-your-own requirements; Oyzu mounts its engine, so the image needs no Oyzu worker. The wheel's tag comes from the Python that runs the build, the locked CPython when there is one, for example cp313-cp313-linux_x86_64. Oyzu finds the file (below), reads its tags from the wheel's WHEEL metadata and records it as native for the image's platform, so the consumer check applies.

Artifact file name discovery​

A planned output normally has an exact file name. The one exception is when a builder can only know the name after building:

  • Python's python/package wheel output: if no file exists at the planned path, Oyzu looks for the single file {name}-{version}-*.whl next to it. No match fails with missing bundle path; several matches fail and name them.
  • A file at the planned name, such as a pure py3-none-any wheel, is always used as is.
  • Symlinks are ignored, and the usual containment, regular-file, digest and size checks apply.
  • The bundle records the real file. The plan and --plan keep the planned name, so the two can differ for a native wheel.
  • materialize with into writes the real name. to needs an exact name, so use into for a discovered file. An existing file is never overwritten.
  • sdist, applications and other builders don't use discovery.

This also applies to an older setup.py wheel whose planned tag is missing: a different tag is collected and classified from its metadata.

Inspection, storage and recovery​

oyzu build --plan shows declared inputs and artifact relationships without installing, copying or building.

During a build, Ctrl+C on Windows or SIGINT/SIGTERM on Unix cancels it. Oyzu stops starting actions, stops running processes and workers, keeps available logs and a failed bundle, blocks pending dependents, and exits with code 130. Post-hooks aren't guaranteed to run. After a forced kill (SIGKILL), check for leftover processes and build files yourself.

To recover from an invalid input path, artifact selector, collision or failed command, fix it and rebuild. You never need to copy files into a consumer by hand. Each rebuild starts from a fresh private copy of the source.

Limits​

  • Private workspaces are separation, not sandboxing, and don't make a build eligible for production publication.
  • Native workspaces support Linux and Windows x86-64. macOS support is limited to the Zig path. Image-worker limits depend on the builder.
  • The usage: build path is tested on Linux x86-64.
  • Native wheel handling supports Linux x86_64 tags. ARM64 consumers, deeper libc version checks and Windows or macOS tags are unsupported.
  • Choosing a build tool from a producer with several platform variants isn't supported.
