Host target workspaces and artifact inputs

CLI reference

Published from the canonical docs/reference/target-workspaces.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Native oyzu build prepares a separate source workspace per selected target before native dependency preparation. Target hooks and stages share that target workspace; ordering dependencies do not expose another target's generated files. Direct oyzu run tasks retain their intentional checkout behavior.

This is workspace separation, not enforced filesystem or network sandboxing. Host processes retain ambient host access. This behavior does not establish production publication eligibility.

Source selection​

Named builds require explicit source inputs only for their selected targets and required dependencies, including task prerequisites and hooks. A missing prepared input belonging to an unselected target does not block the build or its read-only preview. For example, oyzu build cli needs no prepared docs input; oyzu build docs and an all-target build still require it. Missing inputs of a selected target or dependency fail before native execution. Affected selection observes inputs across the workspace to determine which targets changed. Captured source retains available authored inputs for prerequisites discovered during native preparation, such as archive hooks; their inputs become required when that target joins the selection. Existing snapshot boundary and link restrictions still apply to those retained inputs.

The target's source directory is captured with current edits and eligible untracked files using the existing snapshot exclusions (including .git, .oyzu, dist, target, node_modules and virtual environments). Native project ownership still belongs to discovery. Files outside the target directory require explicit source inputs when not already part of that native ownership unit:

builds:
  api:
    uses: node/app
    path: api
    inputs: [../../shared/schemas]

inputs is a list of literal file/directory paths relative to the declaring build.yaml, not the target's path. Paths must resolve within the enclosing Git repository. Without a Git repository, the selected build root is the boundary. Absolute paths and boundary escapes fail. On the captured execution path the captured source is the boundary: an input must stay under the directory holding build.yaml and name at least one captured file, and it joins the target's action-cache scope and stage contracts (declared inputs). Snapshot link/reparse restrictions remain in force. Captures preserve repository-relative layout; each target receives its own copies. Additional source contents participate in recorded source-projection identity. This does not enable host action-result caching.

Generated outputs from another build must use artifact relationships, not source inputs. A snapshot detects changes while copying individual files; it is not an atomic repository-wide snapshot. Unsupported native inputs fail through their native tools; arbitrary script dependencies are not automatically inferred.

Source capture caches directory ignore decisions within one invocation; explicit inputs and mandatory metadata/repository exclusions keep their existing rules. Temporary source captures and complete admitted-source copies used by dependency preparation preserve modification times and do not flush each file to durable storage. Complete copies keep already-admitted inputs without reapplying ignores. Content hashing, change detection and independent copies remain required. Prepared dependency/output snapshots and final bundle/store publication retain their durability boundaries. Completed prepared trees are inspected directly when only their validated identity is needed; no discarded duplicate is created for that observation.

Artifact placement​

builds:
  server:
    uses: rust/app
    path: server
  consumer:
    uses: node/app
    path: consumer
    materialize:
      - from: server
        to: inputs/server
      - from: server
        into: inputs/original

from selects a producer. Optional artifact selects its logical output name; omission requires an unambiguous primary artifact. Exactly one destination is required:

  • to: exact destination for a file, or contents-under-destination for a directory.
  • into: destination directory for a file, preserving its exported basename. When the producer fixes the file name only as it runs (a native wheel), the collected name is used, not the planned one; see file name discovery. Directory artifacts use to.

Optional runtime names a provisioned local image that must accept native files (such as a Python wheel) for this input; see native wheels. It is valid only with usage: runtime, the image must match the consumer's platform, and it is never pulled.

Destinations are relative to the consumer target. No implicit archive extraction, source overwrite, overlapping destination, or scraping of old output trees is allowed. Producer platform compatibility and artifact identity are validated. materialize establishes ordering automatically; do not repeat depends_on.

Native metadata and dependency preparation still precede action execution. Inputs that generate a consumer manifest or are needed by npm ci during preparation are not supported by this slice; handoff occurs before the consumer's first action.

Artifacts are collected once all required producer actions and report obligations succeed, before its consumers run. Each consumer receives an independent copy verified against the collected digest. The manifest records handoff receipts. A failed producer blocks dependents; successful independent artifacts can remain in a failed bundle, without making that bundle successful.

The producer's pre_build, build and post_build actions share its private tree. Post-hook changes to declared output are included in the artifact handed to the consumer. A failure in any of those actions prevents producer artifact publication, even if the build already wrote output files. Native failure diagnostics remain in the failed bundle; fixing the hook or command and rebuilding starts with a fresh private source tree. This is not a guarantee that post-hooks run on cancellation.

A host-built (native local) Python output is a wheel directory named primary, so use to for it. A python/package target built in a worker image (--image pip=<image>) exports file outputs named wheel and sdist; select one with artifact: wheel and into. Typed image bindings remain separate work. Host-coordinated image execution is described below.

Host coordinator with image workers​

The experimental host coordinator admits docker/image alongside supported native targets. It reuses the existing captured Docker metadata and rootless BuildKit executor; ordinary host targets still run as host processes. Docker is required only when an image target is selected. No build container receives the host Docker socket, and no nested Docker daemon is started.

Provision the existing worker image explicitly from this repository:

docker build -f tooling/images/docker-metadata.Dockerfile -t oyzu-toolchain/docker:buildkit0.25.0 .

Image bases must already be available to the provisioned Docker daemon. Preparation captures their identities; worker actions remain offline. This does not install Docker or change host security settings. Existing docker.apparmorProfile configuration and executor enforcement still apply. Explicit tool pins must be satisfied by their supported executor contract; an image tag does not verify pins.

An intended Linux producer/consumer flow is:

builds:
  package:
    uses: python/package
    path: package
  image:
    uses: docker/image
    path: image
    materialize:
      - from: package
        to: payload

oyzu build image --plan includes the producer, artifact edge and each target's executor without contacting Docker. oyzu build image runs that graph. The image's Dockerfile can use COPY payload/ /wheels/ without predicting a versioned wheel filename. This assembles a wheel payload; installing it into an application runtime is a separate Dockerfile responsibility. Native source selection and Dockerignore filtering apply to the image's context; materialized artifacts are explicitly added. Additional source files outside that context do not become Docker COPY inputs.

Artifact compatibility is separate from producer execution provenance. Captured matrix expansion selects the declared producer variant matching each consumer platform; it does not select by filename or matrix enumeration order. Host Python wheel directories are inspected after collection: every wheel must report pure Python and none-any tags before the directory is admitted across platforms. Python tags remain in evidence; the image's package manager must check interpreter and other runtime requirements. A host-built wheel whose tags all name one Linux x86_64 or aarch64 platform (linux_*, manylinux*, musllinux_*) is recorded as native and is consumed only as described under native wheels. Any other native wheel tags (for example Windows or macOS) remain unqualified and fail runtime handoff, including on the same OS. Platform-independent sharing of native wheels through captured matrix expansion is not implemented. Plain native builds still select host producer outputs. For a native binary matrix feeding a foreign-platform image, use --all-platforms; the CLI does not automatically switch that producer to a cross-compilation executor.

materialize.usage defaults to runtime. Explicit usage: data permits deliberate inclusion without claiming runtime compatibility. It still requires a unique logical output, successful producer, verified bytes and safe placement. Data edges do not propagate consumer platform requirements into producers; ambiguous matrix outputs still fail. to and into retain their existing placement semantics.

Artifacts carry extensions.oyzu.dev/artifact-compatibility: target records the resolved artifact platform, pending requires builder inspection before use, independent retains native runtime tags, native binds package files to one platform plus the builder that verifies them against the consumer runtime, and unknown explains absent qualification. Bindings/receipts record oyzu.dev/artifact-consumer platform and usage. Pending or unknown artifacts cannot satisfy runtime consumption. This extends the existing version-1 contracts; it does not certify arbitrary binaries or runtime ABIs.

Native wheels and the consumer runtime​

A native wheel is accepted only after the consumer runtime check. For generic linux_x86_64 and linux_aarch64 wheels, Oyzu inspects ELF .so dependencies in the wheel and probes the exact consumer image's Python process. A positively identified glibc/musl mismatch is refused before the consumer image build, naming the wheel, ELF member, linkage and consumer image. If linkage or consumer libc is inconclusive, the check reports NATIVE_WHEEL_LIBC_UNVERIFIED and continues to pip. This includes wheels with no identifiable libc dependency and wheels with other unidentified .so members. A missing Python runtime remains an error. UNVERIFIED means Oyzu has no libc conclusion. Separately, for generic Linux wheels with a recognized interpreter-specific *.cpython-<version>-<platform>.so member, Oyzu compares that filename suffix with importlib.machinery.EXTENSION_SUFFIXES from the exact consumer Python. When its CPython-specific suffix is absent, or the consumer cannot report those suffixes, Oyzu emits NATIVE_WHEEL_EXTENSION_SUFFIX_UNVERIFIED in human and JSON diagnostics, naming the wheel, member, observed suffix and consumer. Pip still decides wheel tags and ABI, and a warning does not block the build. A plain .so or .abi3.so does not trigger this specific comparison. The member may be a helper or data library, so this check does not claim that every .so is a required import module. A warning calls for checking the module import in the final image and, if it fails, building the wheel with that consumer's Python and native toolchain. For manylinux* and musllinux_* tags, pip retains its existing decision without the extra ELF or suffix checks. Pure *-none-any wheels keep their independent handoff.

Before a native wheel enters the consumer workspace, Oyzu runs pip install --dry-run --no-index --no-deps for it in that image with networking disabled. Pip decides whether the interpreter version, ABI and wheel tag fit; the extra refusal handles only positively identified libc mismatches for generic Linux tags. The suffix comparison is diagnostic only. The runtime image is, in order:

  1. the input's explicit runtime: <image> (a provisioned local image; it overrides the captured base and must match the consumer platform), else
  2. the consumer's captured pip dependency base (a requirements.txt consumed from the pinned base image; see Docker images).
materialize:
  - from: package
    to: inputs
    runtime: registry.example/python:3.12-slim   # only needed without a pip base

A consumer with neither (for example a plain COPY into scratch) cannot receive a native wheel; usage: data still includes it without a runtime claim. A rejection fails the consumer with the wheel name, the image reference and either the linkage mismatch or pip's message. The human summary shows it as an ERROR line (terminal controls escaped, line breaks kept); --json carries it in diagnostics, and the action log keeps the full text.

Wheel classification covers Linux wheels whose tags all name x86_64 or aarch64 (linux_*, manylinux*, musllinux_*), including abi3 wheels. The proof shows version-specific tags (cp313-cp313-linux_x86_64) accepted only by the matching Python and an abi3 wheel accepted by both Python 3.12 and 3.13. Because pip is the authority, Python versions need no Oyzu list. Not covered: a Linux arm64 consumer (classification is unit-tested; no arm64 build or execution was available), broader libc version and transitive library checks, and Windows/macOS tags, which stay unknown and are refused. These and the Windows/macOS host qualification are tracked in implementation status.

Qualification: python tooling/test-native-wheel-abi.py --cli <compiled-oyzu> (needs Docker, a host C compiler and oyzu-fixture/python-abi:<version> images; the script header describes them). The producer's CPython is pinned with .python-version; Oyzu provisions it. These host-built cases need a Linux host: a Windows or macOS host builds win_*/macosx_* wheels, which stay unknown and are refused by a Linux consumer.

Wheels built in a worker image​

A Linux native wheel can be produced from any host with Docker by building it in a worker image: oyzu build --image pip=<image>, where the image is a Python image with a C compiler (not a -slim image) and the Oyzu worker at /usr/local/libexec/oyzu/oyzu. The wheel's tag comes from that image's interpreter, for example cp313-cp313-linux_x86_64. Collection finds it (below), reads its tags from the wheel's own WHEEL metadata and records native compatibility for the image's platform, so the consumer check above applies unchanged. The case is tooling/test-native-wheel-abi.py --worker-image <image>; on Windows add --captured-only to skip the host-built cases.

Artifact file name discovery​

A planned file output has an exact name and collection requires that file. The one exception is a builder-declared discovery, used when the name cannot be known until the build has run:

  • It is consulted only when no file exists at the planned path, so an output that exists under its planned name, such as a pure py3-none-any wheel, is collected exactly as before and never reinterpreted.
  • Python implements it for the wheel output of python/package: the single regular file {name}-{version}-*.whl next to the planned file. No match keeps the original missing bundle path failure; more than one match fails and names them. sdist, applications and other builders have no discovery.
  • The result is a file name in the planned directory, never a path; symlinks are ignored and the usual containment, regular-file, digest and size checks still apply.
  • The bundle's artifact record carries the file actually collected, and compatibility is inspected from that file's metadata, not from its name. The frozen plan, --plan output and plan digest keep the planned name (py3-none-any), so the planned and collected names can differ for a native wheel.
  • materialize with into writes the consumer's file under the collected name; the receipt records where it was written. to names an exact file and therefore cannot address a name that is only known after the build; use into for a discovered file. Collisions with the collected name are detected when the file is written, not at planning, and an existing file is never overwritten.

Limits: the lookup also applies to a legacy setup.py wheel whose planned tag is absent, so a mismatched tag there is collected and classified from its metadata rather than failing. The Windows/macOS wheel tags are not classified (below).

Named image platform lists must include the resolved worker platform for this path; use the existing --all-platforms captured path for matrix execution. Worker task replacements and pre/post hooks run through the shared task executor and retain report obligations. Hooks share the private target workspace. Docker context membership is frozen during preparation: hooks may modify admitted files, but newly generated undeclared files do not automatically enter the context. --isolated continues to select the captured build path for the whole graph.

Fast builds assemble and verify the OCI image without selecting optional checks. --full adds the existing image assertions, lint and formatting stages, with reports collected through the shared owner. Image content and platform integrity are always verified before publication, including fast builds. The bundle records worker image identity, dependency evidence and per-action enforcement; this does not imply that host producer actions were sandboxed or establish production publication eligibility.

Windows image-only fast/full flows have passed. The Windows Python-to-Linux runtime fixture installs/imports the wheel in Linux and verifies exact materialized bytes. Failed-producer blocking, unknown native-wheel rejection and explicit data-only inclusion also passed. See the three-platform Rust-to-image proof, which independently exports Linux amd64, Linux arm64 and Windows amd64 binaries and executes only the matching Linux amd64 binary in its consumer image, in the qualification record.

Inspection, storage and recovery​

During an executing build, Windows Ctrl+C or Unix SIGINT/SIGTERM requests coordinated cancellation. Oyzu stops admitting actions, terminates owned native process groups/trees or removes active named workers, retains available logs and a failed bundle, blocks pending dependents, and returns exit code 130. Normal private workspace cleanup then runs. Windows console, Linux SIGINT and Windows-coordinated image-worker flows are verified. Post-hooks are not guaranteed to run.

Forced termination (SIGKILL), deliberately detached descendants, every acquisition phase and macOS runtime behavior are not qualified. Inspect remaining processes and build-owned storage after an unhandled termination; do not assume cleanup.

oyzu build --plan shows declared shared source inputs and artifact relationships without tool installation, copying source, or running a build. Physical artifact selection and source admission are verified during preparation.

Private trees use .oyzu/host-workspaces under the existing build transaction lock. They persist between builds as exact source copies: each build refreshes them in place, rewriting only files whose bytes changed and removing anything outside the selection, and at the end of a build removes what the build generated inside them. On Windows this avoids re-creating every source file per build, which on-access scanning made the slowest preparation step (about 46 seconds for this repository's 2,600-file CLI projection). Interrupted builds leave state that the next build reconciles under that same lock. Native Rust compiler caches remain in the original target's .oyzu/native/rust store with existing budget controls. Copies preserve modification times and use stable paths for repeat builds. Tool stores and native download caches remain shared. This does not promise unchanged cache keys after target selection or source layout changes. Offline runs still require tools and native dependencies already available.

Fix an invalid input path, artifact selector, collision or failed native command, then rebuild. No manual copying into a consumer is required. Private workspace cleanup does not remove finalized bundles, tools, or compiler caches.

Verification and limits​

tooling/test-host-workspaces.py --cli <compiled-oyzu> exercises real host producer/consumer builds, shared parent inputs, edits, verified handoff, clean checkout behavior, preview, hook continuity, pre/build/post failure blocking, diagnostic retention, recovery and cleanup. Qualification results are recorded in implementation status. Linux/macOS runtime qualification and enforced sandboxing are not implied by Windows checks.

Artifact handoff follow-up checkpoint​

An explicitly selected python/package output named wheel can bind one producer to multiple consumer platforms when the producer declares no platform matrix. Collection inspects the actual wheel before runtime consumption; pure Python platform-independent wheels can be shared. Explicit producer platforms remain authoritative. A Linux native wheel is native and is accepted only after pip accepts it in the consumer runtime (native wheels); unknown wheel compatibility (for example Windows or macOS tags) still fails closed. A wheel built in a worker image keeps its real file name through discovery.

materialize.usage: build selects compatibility against the execution platform, while the default runtime uses the consumer artifact platform and data carries no executable compatibility claim. The current build-tool path requires an unambiguous producer; selection from a multi-variant generator matrix remains unfinished. Its end-to-end qualification passed on Linux amd64 (2026-10-07): an amd64 generator ran on the executor and a linux/arm64 consumer built from its output. Rust recipe lookup selects the smallest pinned recipe that contains the requested components and still fails with TOOL_LOCK_AMBIGUOUS for incomparable recipes; a cross target's request includes its target-platform standard library. Windows, macOS and other Docker versions are not qualified.

See the qualification record for measured portable-wheel and worker-hook results and remaining limitations.
