Docker image inputs and offline builds

CLI reference

Published from the canonical docs/reference/docker-images.md file. Features marked experimental remain experimental; check support limitations before relying on them.

The experimental Docker builder supports scratch, internal stages and image references already provisioned in the executor's Docker image store, including bases selected through global ARG defaults. The same path captures external COPY --from and literal image-backed mount references reported by the native Dockerfile parser. No extra project configuration is needed:

FROM alpine:3.22
COPY greeting.txt /greeting.txt
RUN test -f /etc/alpine-release

Daemonless assembly for RUN-free Dockerfiles​

A Dockerfile whose final stage only adds files to one base and edits image settings is built without Docker, BuildKit or any container engine. Earlier stages may contain RUN when the final stage is clearly independent; those earlier stages are not executed or included in the image. Oyzu fetches the final base from its registry, writes each COPY as a new layer and edits the image configuration itself. This is the same approach as ko, Jib and crane append. No configuration selects it; the Dockerfile's content does:

FROM gcr.io/distroless/base-debian12:nonroot@sha256:7f0c72cd138b442ae0deeb69c08b1acf5525439ba251a49ad93c320a061567e5
COPY bin/server /server
USER 65532:65532
EXPOSE 8080
ENTRYPOINT ["/server"]

What is admitted​

InstructionSupported form
FROMThe final base is scratch or a reference pinned by @sha256: digest (a tag may also be present), optional AS name. No --platform. Earlier stages must also use literal scratch or digest bases.
COPYContext sources (files or directories, no wildcards), shell or JSON form, --chown=user[:group] (names or ids) and --chmod=<octal>. Relative destinations resolve against WORKDIR.
WORKDIR, USER, STOPSIGNALOne literal value.
ENV, LABELkey=value pairs with shell quoting; legacy ENV KEY value without quotes.
EXPOSEPorts with optional /tcp, /udp or /sctp; no ranges.
CMD, ENTRYPOINTJSON (exec) form or shell form, which becomes /bin/sh -c.

The independent-stage case uses the same recognized instruction grammar in earlier stages, except that their RUN instructions are skipped. For example, FROM scratch AS unused, RUN exit 99, FROM scratch, COPY greeting.txt /greeting.txt assembles only the final COPY. A final-stage RUN, stage references such as FROM unused or COPY --from=unused, ADD, ARG, HEALTHCHECK, VOLUME, SHELL, ONBUILD, unsupported COPY flags, heredocs, variable expansion, a # syntax= or non-default # escape= directive, a base pinned only by tag, and a .dockerignore or Dockerfile.dockerignore file keep the BuildKit worker. The choice is made per target; a project can mix both paths.

Base images​

Oyzu first checks whether the exact digest-pinned reference is provisioned in the local Docker image store. An available OCI index or manifest is exported and admitted by immutable identity: the index must uniquely bind the requested platform, and the manifest, configuration and every layer must verify. A present image with an identity, platform or export error fails; it does not select a different registry image. Classic Docker stores exposing only a configuration ID cannot supply this native local capture. Missing Docker, an unavailable daemon, --no-docker, or a genuinely absent local image preserves registry acquisition.

Registry acquisition uses the OCI Distribution API by digest, so a moved tag can never select different content. For an index, the entry for the target platform (linux/amd64 or linux/arm64) is used. Verified content is retained in the native user image cache (%LocalAppData%\Oyzu\cache\images on Windows, ~/Library/Caches/Oyzu/images on macOS, $XDG_CACHE_HOME/oyzu/images or ~/.cache/oyzu/images on Linux). Project cache.dir cannot relocate image admission records. Later builds trust admitted content; offline registry builds require retained content, while provisioned local images can be admitted without network. Builds under managed configuration never contact a public registry.

Only anonymous pulls are supported: a registry's bearer-token challenge is answered without credentials, which covers public images on Docker Hub, gcr.io, ghcr.io and similar registries. A private base fails preparation with an explanation; it does not fall back to BuildKit. HTTPS_PROXY, NO_PROXY and SSL_CERT_FILE apply as for other Oyzu downloads. A loopback registry (localhost:5000/...) is contacted over plain HTTP. A base with ONBUILD triggers, zstd or foreign layers, or a platform other than the target fails explicitly.

What the image contains​

  • Base layers are copied byte for byte. Docker schema 2 bases are written with the equivalent OCI media types.
  • Each COPY is one gzip layer, and so is a WORKDIR that creates a directory. Entries are sorted, timestamped with the export epoch (1980-01-01 UTC) and carry numeric ownership with no user or group names.
  • Files are 0644, or 0755 when they are executable on a Unix host or start with an ELF header or #!. Directories are 0755. --chmod overrides both.
  • New files and any directories COPY creates are owned by --chown, or root. Names resolve against the base image's /etc/passwd and /etc/group; an unknown name fails the build. Without a group, the user id is also the group id, as in Docker. Directories that already exist in the base keep their ownership.
  • The configuration is the base's, with Env, Labels, User, WorkingDir, ExposedPorts, Cmd, Entrypoint and StopSignal edited as in Docker. An ENTRYPOINT discards an inherited CMD unless the Dockerfile sets one. An image without PATH gets Docker's default. created and the appended history entries use the export epoch.

COPY reads the same inputs BuildKit would: the files under each COPY source in the target directory, plus explicitly materialized artifacts. Nothing else in the workspace is visible.

The output is the same <target>-<version>.oci.tar layout with the same name annotations, the same integrity and platform validation and the same evidence. Rebuilding unchanged inputs produces the same image digest on every host. It is not byte-identical to an image BuildKit would build from the same Dockerfile.

Evidence​

The target's dependency record (dist/dependencies/<target>.json) names the adapter docker/oci-assembly, records imageSource: registry or provisioned-local, the typed recipe under extensions.oyzu.dev/docker.assembly, the base's requested reference, manifest digest, configuration digest and store-tree digest under images, the selected context files and the Dockerfile digest. The executor checks the Dockerfile and base store against those identities before writing anything. The build action records the oci-assembly execution mode and its enforced properties (no-container-engine, no-project-code-execution). Local capture uses the daemon only to export already provisioned content; assembly itself remains in-process.

Without Docker​

When Docker cannot provide the oyzu-toolchain/docker image, for example on a host or pod with no Docker engine, an admitted target still builds: its worker identity becomes Oyzu's own executable (oyzu-builtin/in-process), whose platform is the Linux platform of the host's architecture. oyzu build --isolated --no-docker admits this target when its selected work is the native build and packaging path; the plan reports needsDaemon: false and isolation: in-process. In-process preparation and actions do not probe Docker's memory, and do not require crun or user namespaces. Other targets retain their worker-capacity checks. Tasks that need the toolchain image remain required: --full selects Dockerfile lint (hadolint) and format checks (dockerfmt), so the no-Docker guard stops with NEEDS_DOCKER_DAEMON before preparation. Unsupported Dockerfiles also retain that refusal. A digest-pinned base with ONBUILD triggers fails explicitly during assembly without running those triggers or falling back to BuildKit. Measured commands and limits cover the Windows qualification.

Building a replacement execution image​

The execution image dogfood recipe connects an ordinary Rust producer to RUN-free image assembly through a runtime artifact materialization edge. It stages exact source and notices as inputs, builds the Linux CLI, then copies only the accepted producer artifact into the replacement's default CLI and compiled-worker paths. Required producer reports, Dockerfile quality checks and OCI validation remain gates.

Use independently available, compatible execution seeds. In particular, the Rust seed's compiled reporting adapter must implement the current required report contract; compiling newer source does not update the adapter executing that build. Native concurrency can be set through ordinary resolved [env] configuration without raising isolation limits. The recipe documents the exact inputs and commands. Its complete seed-to-replacement runtime qualification is in progress; a compiled binary alone is not acceptance. The initial runtime base is a local development asset, not a publicly distributed bootstrap or an official release.

Prerequisites and commands​

Provision Docker with a Linux image store and the selected BuildKit user-namespace/AppArmor profile. The builder image (oyzu-toolchain/docker:buildkit0.25.0, built from tooling/images/docker-metadata.Dockerfile) includes BuildKit 0.25.0, native metadata/image adapters and the quality tools; Oyzu pulls it itself when it is missing (see Published toolchain images). For Dockerfiles that use the BuildKit worker, provision the declared base images separately using your organization's approved mechanism; Oyzu does not pull missing base images or read registry credentials in that profile. Daemonless assembly needs none of this.

After a successful BuildKit action, Oyzu waits up to 30 seconds for Docker to confirm removal of its isolated worker before accepting the exported image. If Docker does not confirm cleanup within that bound, the build fails and the output is not accepted; check Docker daemon health and retry the build.

oyzu run list
oyzu build --plan
oyzu build
oyzu inspect dist

Planning includes input preparation and therefore requires the provisioned images. oyzu run build remains a native development command; it does not provide this captured-build boundary. Windows and macOS hosts require a suitable Linux Docker environment; native Windows images and emulation remain unfinished.

Some Docker Desktop Linux daemons report an empty AppArmor profile after starting an explicitly unconfined worker. Oyzu accepts this representation only when the container's security options retain apparmor=unconfined and an independent daemon capability query confirms that AppArmor is absent. Named profiles still require an exact observed match. Missing or contradictory evidence fails startup; network isolation, unprivileged execution and the process sandbox remain required.

The daemon query is docker info --format '{{json .SecurityOptions}}'. Docker Desktop 29.8.1 on Windows 11 answers with a list such as ["name=seccomp,profile=builtin","name=cgroupns"], which satisfies the check. A running Linux engine always lists some security options, so an answer that is not a list of strings (for example null) is missing evidence, not an empty list. The build then stops with cannot verify the BuildKit worker's AppArmor boundary, naming the name=apparmor requirement and what Docker reported. Retry once the Docker engine is fully running; an engine that keeps answering this way cannot run isolated BuildKit builds with an unconfined worker.

Artifact target and worker platform​

An explicit target can differ from the BuildKit worker for image assembly that does not execute target code:

builds:
  image:
    uses: docker/image
    platforms: [linux/arm64]

With a Dockerfile containing only FROM scratch and COPY operations, a provisioned amd64 worker can assemble this arm64 image. Supported explicit Docker targets are currently linux/x86_64 and linux/arm64 (linux/amd64 and linux/aarch64 are accepted aliases; an ABI is refused). Omitted platforms retains the selected worker's platform; this increment does not introduce a new global default. Architecture-variant suffixes and unsupported OS/architectures fail admission. No image or emulator is installed automatically.

Preparation records the toolchain platform under manager.platform and the artifact target under targetPlatform. Plans retain tool/worker identity separately from target identity, pass the artifact target to BuildKit, and check that captured facts match the request and resolved toolchain. Base image inputs must match the platform of the stage that uses them: the artifact target, or the worker for a FROM --platform=$BUILDPLATFORM stage. A locally provisioned base with the wrong architecture fails before export; a matching tag alone is insufficient. Materialized producers must also have the same artifact OS/architecture as their consumer. Explicit consumer platforms propagate to producer variants through materialization; this does not establish platform independence or a capable executor.

The native parser records required targetExecution evidence for any RUN, including commands in intermediate stages. Until suitable native/emulated executor admission is implemented, a Dockerfile with RUN requires matching worker and target platforms. A foreign-platform RUN fails preparation before application actions, even if the host happens to have an emulator. OCI integrity/platform assertions verify bytes and metadata; they do not execute the image or replace required application tests.

Every OCI image is checked against its artifact target during default testing, collection and bundle inspection. A valid image for the wrong architecture cannot be retained as a successful output merely because its archive hash is valid. Snapshot artifacts, JUnit and lint/read-only-format gates otherwise retain their existing behavior. List several platforms, platforms: [linux/x86_64, linux/arm64], to expand separate image builds. Each produces its own versioned OCI archive and reports. Complete selected image families additionally produce an OCI index; see matrix builds for selection, producer propagation and compatibility details.

Published toolchain images​

When a build needs one of Oyzu's own oyzu-toolchain/* images that the local Docker engine does not have, Oyzu pulls it from ghcr.io/oyzuai and tags it with the name the builder expects. The packages are public, so no registry login or credentials are involved. The pull is by digest, using the pins committed in src/executor/published_images.json, so the registry verifies the content and a moved tag cannot substitute another image. A fresh machine therefore needs only Docker:

oyzu build        # first run: "Pulling toolchain image oyzu-toolchain/helm:3.22.0 from ghcr.io/oyzuai/..."

Published today: builder-worker:v1, docker:buildkit0.25.0, go:1.24-mod0.25.0, helm:3.22.0 and node:npm11.11.0-node22, all linux/amd64. Every other image, including base images and the remaining toolchain images, is still provisioned by hand from tooling/images and never pulled. An image already present locally is used as is and never replaced, so locally built images keep working. Set OYZU_NO_TOOLCHAIN_PULL=1 to forbid pulling (for example on an offline or air-gapped host); a missing image then fails with the existing provisioning message.

Limits: the pinned digests are not yet recorded in oyzu.lock, a pulled image is trusted by its pin and not re-verified on later runs, and routing pulls through the tool broker or a private mirror is not implemented. The Helm and worker images embed a compiled Oyzu worker, so their pins move when a CLI release republishes them.

Docker storage budget​

Isolated builds add Docker resources, so Oyzu bounds the ones it creates. It never touches anything it did not create: a resource is Oyzu's only when it carries the label dev.oyzu.owner=oyzu or is recorded in the per-user ledger docker-storage.json (in the cache directory of the Oyzu user-data directory). Containers and volumes are labelled when created. Docker cannot label an image after a pull, so images are recorded instead: one pulled from the published toolchain namespace ghcr.io/oyzuai/oyzu-toolchain/ (including those pulled by earlier releases, which are adopted on the first pass) or a container tool Oyzu installed. Locally built oyzu-toolchain/* images, base images and everything you pulled yourself are neither listed, measured nor removed.

After an isolated build that used a Docker image, under a lock shared by builds:

  • Images. Recorded images that lost their tag to a newer pinned image, and those unused for 60 days, are removed. Beyond that, the least recently used are removed until the recorded images total at most cache.dockerMaxMiB (default 20 GiB). Images used by the finishing build are never selected, and Docker refuses to remove an image a container uses.
  • Containers and anonymous volumes. Labelled containers that exited over an hour ago are removed with their anonymous volumes. This includes the BuildKit worker's private store, which is where BuildKit's build cache lives, so that cache cannot outlive its worker.
  • Volumes. Unused labelled volumes are removed. Persistent oyzu-tools-* volumes keep their own retention (see build logging).

The pass is best effort: a failure leaves the work to the next isolated build and never changes a build's result. Host builds add no Docker resources and run no pass. Set cache.dockerMaxMiB (1–1048576 MiB; it is not part of any action key) in the ordinary configuration cascade to change the image budget; the 60-day and one-hour ages are fixed. oyzu cache status reports the recorded image count, size and budget on its Docker line and under docker in --json; it is omitted when Oyzu has recorded no image or Docker cannot be queried. oyzu cache clear empties the action cache only.

Capture, execution and evidence​

  1. The native parser identifies image requirements without executing Dockerfile commands. Global ARG defaults resolve base/platform selections through BuildKit's expansion library. Unsupported dynamic mount references, remote ADD, secret/SSH mounts and host networking fail admission. A # syntax= frontend builds only when it is on the digest-pinned docker.frontends list; see Oyzu's BuildKit frontend, which runs every Dockerfile build. To bring in a pinned download instead of remote ADD or RUN curl, declare a fetch and copy from the reserved named context oyzu-fetch-<name>; such references are never treated as images.
  2. The host executor inspects each provisioned image and exports its immutable config identity, so a tag change between inspection and export cannot substitute another image. It never starts that image or gives project code the host Docker socket.
  3. An offline Go adapter uses go-containerregistry 0.20.6 to read the native transport archive, verify image integrity/platform and write an OCI content store. It preserves native config/layer content and media types. Images containing ONBUILD instructions fail because their hidden inputs are not yet part of discovery.
  4. Preparation freezes the store. Plans record the requested reference, normalized native context name, config digest, manifest digest and store-tree digest. Before worker startup, the executor copies each store into private storage and verifies its planned tree identity.
  5. BuildKit receives native OCI named contexts through its client session. The worker and Dockerfile RUN processes remain offline. Image stores are read-only worker inputs, not arbitrary host mounts or mounts inside RUN containers. No shared result cache is imported.

Inputs are recorded under extensions.oyzu.dev/docker.images in the target's dist/dependencies/<target>.json; imageSource identifies the current provisioned-daemon source. These identities also affect the dependency and build plan digests. The OCI manifest digest may differ from a registry's original manifest identity because a Docker save transport does not preserve every registry representation. The config identity and captured content are verified; no original registry provenance is invented.

The same extension's metadata.selection records targetPlatform and sourceDateEpoch. Preparation supplies these facts to the native adapter, and planning rejects facts that differ from the selected artifact target or export epoch. The export epoch has one owner in the executor contract and is used both during selection and native export; it is currently 315532800 (1980-01-01 UTC).

Before worker startup, Oyzu also sets the private source, Dockerfile, materialized-artifact and prepared-context copies' file/directory access and modification times to that same epoch. Original source and prepared stores are unchanged. Content identity excludes acquisition/copy times, so exposing them to RUN would make identical inputs behave differently. On Unix, the existing private-copy mode normalization still preserves executable intent while removing host umask/setuid differences. Timestamp updates are required; an unsupported file type or failed metadata update stops worker startup rather than silently using host timestamps. This does not freeze application clocks, process randomness or every filesystem metadata field.

This corrects a native uv repeatability failure: uv embedded the input wheel's varying copy-time mtime in uv_cache.json and changed its RECORD hash. OCI export-time normalization alone could not repair those file contents. Installers keep their normal metadata; no Dockerfile change or metadata-deletion option is required. Regenerate affected images with the updated executor. The existing plan's content identities do not authorize reuse of an output produced by the older executor.

Successful builds retain the versioned <target>-<snapshot-version>.oci.tar artifact and its OCI digest in dist/manifest.json, plus default integrity/platform JUnit and native quality results. Container integrity checks do not measure application code coverage; materialized producers retain their own test/coverage evidence. Version inference supplies a tag-derived base when available and a source-derived snapshot suffix. The exported OCI reference uses that same version. Changed base-image inputs change the plan/content digests even if that version string is unchanged.

Image repository​

with.repository declares the image's approved registry repository (a name without scheme, tag or digest, for example registry.example.com/team/app). Building never publishes or contacts it. A helm/chart image binding reads it to name the image it consumes. docker/image accepts two with options: repository and dependencies. oyzu config validate and every command that reads the build inventory check them; any other key is refused. Where the built image is loaded locally is not a with option but the docker.load setting.

Loading the image locally​

The docker.load setting lists where oyzu run load puts an image you have already built, so a local cluster can run it with no custom docker load step. Which cluster is personal, so the list lives in the configuration cascade, not in build.yaml (OEP-0022 OD4): a team default in oyzu.toml, your own cluster in oyzu.local.toml, or user configuration. Like any per-target setting it applies to the docker/image builds in its folder and below, the nearest file wins, and [context.<name>] and profile tables can vary it. The image is named by the build's with.repository:

# build.yaml
builds:
  image:
    uses: docker/image
    with:
      repository: registry.example.com/team/app   # names the loaded image
# oyzu.local.toml (Git-ignored), or oyzu.toml for a team default
[docker]
load = ["docker", "k3d:dev"]
oyzu build
oyzu run load            # or: oyzu run image:load when several targets exist
oyzu config explain docker.load --target image   # where the list came from

A list holds zero to eight distinct destinations; an empty list (load = []) in a nearer file turns a farther default off. When docker.load reaches a build without with.repository, the load task is listed as unavailable with that reason instead of failing other commands. An unknown or repeated destination is refused as the value is read, naming docker.load, so oyzu config validate reports it and every command that reads that configuration fails. The setting never changes an action key, so changing it does not rebuild anything. The earlier with.load key is refused with a message pointing at this setting. oyzu.local.toml is ignored in CI unless --local-overrides is given (inspection and selection).

The task never builds, never pushes and never contacts a registry. It reads the latest dist/manifest.json (the build must have succeeded and the archive must still match its recorded digest), selects the single OCI archive produced by this target, and makes the image resolvable as <repository>@<manifest digest>, the reference a bound chart uses, so a deploy pulls nothing.

Docker Desktop's own Kubernetes was not enabled or exercised; k3d was run by hand, not by the harness; Linux and macOS hosts were not run. That run used the earlier with.load key; after the move to docker.load the same scenario passed on Windows 11 with Docker Desktop on 2026-10-19, reading the list from oyzu.toml (status); k3d was not rerun.

Global argument defaults​

Image selection can use conventional Dockerfile defaults without an Oyzu configuration file:

ARG REGISTRY=docker.io/library
ARG VERSION=3.22
ARG BASE=${REGISTRY}/alpine:${VERSION}
FROM ${BASE}
RUN test -f /etc/alpine-release

Only global declarations before the first FROM participate in base/platform selection. Defaults expand in declaration order using BuildKit's native quoting, escape and parameter-expansion rules. Later declarations with values replace earlier ones; declarations without a value retain an existing default. A missing value can use a native expression such as ${BASE:-alpine:3.22}. An empty resolved base or explicit platform fails preparation. Stage-local arguments do not become global defaults, and host environment variables are never consulted.

Captured metadata records resolved stage bases/platforms and image requirements; source identity still binds the original Dockerfile. An argument resolving to scratch or a prior stage does not create an external image dependency. A resolved stage platform must be the selected artifact target or the worker's own platform (FROM --platform=$BUILDPLATFORM); any other platform fails admission. A base for a worker-platform stage is captured for the worker's platform and bound as the BuildKit context <name>::<platform>, so the same reference can serve both a build stage and the target stage.

Automatic TARGETPLATFORM, TARGETOS, TARGETOSVERSION, TARGETARCH and TARGETVARIANT use the captured target platform, parsed by the same pinned containerd platform library used by BuildKit. TARGETSTAGE names the final stage, or default when it is unnamed. Global declarations retain native scope and can replace these defaults. For example, ARG BASE=registry.example/runtime:${TARGETARCH} selects a provisioned architecture-specific image without reading the host architecture.

The executor supplies SOURCE_DATE_EPOCH as a build argument. A global declaration makes that value available to image selection and overrides any Dockerfile default for it. Without a global declaration, it is not part of global selection scope. A stage-local declaration can expose it to native RUN commands independently. These facts do not establish target execution capability; RUN still requires matching target and worker platforms. Native lint/format policy continues to apply, including Hadolint's checks on explicit FROM --platform flags.

Automatic worker arguments (BUILDPLATFORM, BUILDOS, BUILDOSVERSION, BUILDARCH, BUILDVARIANT) use the Docker toolchain worker's platform, recorded as metadata.selection.buildPlatform and checked against the worker during planning; the target platform is never assumed to describe the worker. RUN in a stage pinned to the worker's platform is not target execution, so the common cross-compile pattern (FROM --platform=$BUILDPLATFORM golang AS build, then COPY --from=build into a target-platform stage without RUN) builds an arm64 image on an amd64 worker. RUN in a target-platform stage of a cross build still fails before any action runs. Public build-argument overrides and stage-local mount expansion remain unfinished.

Failures, limits and migration​

A missing image fails preparation with a provisioning diagnostic; there is no automatic internet fallback. Platform mismatch, malformed transport, config mismatch, hidden ONBUILD, mutated frozen stores or native worker failures block artifacts. Correct the input or provisioned toolchain, then create a new plan. Native lint/format failures retain their existing gates; adding a usable base does not waive them.

There are at most 64 distinct image references, a 10 GiB transport/captured-tree limit and 100,000 transport entries per image. Transport inspection rejects traversal, duplicate member names and transport links without extracting layer files on the host. The offline adapter is also constrained by executor resource/time limits. Images using unsupported transport forms fail explicitly. Equivalent references such as alpine:3.22 and docker.io/library/alpine:3.22 share one BuildKit context when their captured manifest, config and store-tree identities agree. Both requested references remain in the evidence. Conflicting identities fail planning; reference order never chooses between different images.

Dockerfile-free packaging status​

Provisioned image capture is shared through dependencies/images; Dockerfile parsing still determines Docker's required references. The capture path preserves existing immutable config/platform checks and OCI-store evidence. This internal relocation adds no registry fallback or configuration precedence rule.

Within one oyzu build, each distinct base is exported with docker image save and converted once. Other targets that need the same base, matched by reference, the daemon's immutable image ID, the target platform and the converter image, wait for that capture and receive a verified copy of its store; the copy must have the same tree digest. Before this, several targets on one large base (for example three Liquibase migration images) each exported and converted it at the same time, holding several copies in the Docker engine's memory at once; on a 16 GB Docker Desktop those builds failed reading the base with cannot allocate memory. Evidence and plan digests are unchanged, since every target still records the same identities. The kept stores live in the system temporary directory and are deleted when the build finishes. A failed capture is not reused; the next target tries again. Separate oyzu build processes do not share captures.

The isolated BuildKit worker receives each captured base store as a private copy made with docker cp before the worker starts, not as a host bind mount. BuildKit reads a base's layers more than once (unpacking it, then again for COPY). On Docker Desktop for Windows, those large reads through a host bind mount failed with cannot allocate memory under VM memory pressure. The copy has the verified tree digest, is owned by root inside the worker, and is removed with the worker. The source context, definition and output directories are still bind-mounted.

The first application container: true integration is Python application packaging, whose default and override profiles passed Linux CI. It uses the internal typed assembly boundary and shared captured-base acquisition. Additional runtime profiles, application-container matrices and startup smoke tests remain unfinished. Existing Dockerfile builds continue to use their captured source definition. The worker verifies the bytes actually staged for BuildKit against the planned digest, so a definition changed during copying is rejected rather than executed.

The executor's prepared dependency-context transport has native conformance verified in Linux CI. The Docker package-manager integrations are the experimental Python, Node-manager, Go-module and Cargo profiles below. The pip context passed its captured checks in the dependency job linked below; the complete suite remains unverified. Other ecosystems, private sources and full EX-058 credential-policy acceptance remain unfinished.

Offline pip dependency context (experimental)​

For a Docker target, an external context named dependencies requests a prepared package store. With a single Python ecosystem and requirements.txt, no dependency selector is needed. Select the Docker builder explicitly when the project also looks like an application:

builds:
  image:
    uses: docker/image
FROM python:3.13-slim-bookworm
WORKDIR /app
COPY requirements.txt .
RUN --mount=type=bind,from=dependencies,target=/dependencies \
    pip install --no-index --no-cache-dir --no-compile --find-links=/dependencies -r requirements.txt
COPY app.py .
CMD ["python", "app.py"]

Supply application files with the Dockerfile's ordinary COPY instructions. --no-compile avoids installation-time bytecode timestamps in this example; use python -B for build-time import checks to avoid creating timestamped bytecode afterward. Arbitrary Dockerfile commands are not automatically made reproducible. A requirements entry such as six==1.17.0 is resolved by pip inside the exact provisioned base image, using that image's Python, pip, ABI and platform. Preparation downloads binary wheels through Oyzu's scoped public-PyPI broker. It does not add application-build, test or quality tools to this runtime store. No project code or source build runs during resolution. The subsequent Docker build remains offline and installs from the captured store; Oyzu does not rewrite RUN commands.

When other ecosystem manifests make automatic selection ambiguous, the docker/image builder's with.dependencies option names the provider:

builds:
  image:
    uses: docker/image
    with:
      dependencies: python/pip

The value must be one provider name; oyzu config validate refuses anything else. The earlier top-level dependencies: build field is refused with a message naming with.dependencies. Offline npm dependency context (experimental)​

node/npm exports verified registry tarballs using the Node builder's existing native locked acquisition. A Docker target with package.json and a v2/v3 package-lock.json or npm-shrinkwrap.json can infer this provider. Shrinkwrap takes precedence, as it does in npm. Multiple ecosystems require with.dependencies: node/npm in the build declaration. The shared runtime, platform, policy and context rules above also apply; the captured consumer base must already contain Node and npm. A declared packageManager must match that provisioned npm version, and native npm validates engine constraints. The tested profile uses npm 11.11.0 with Node 22 in CI fixtures and Node 24.14.1 in a Windows native probe. A package that npm records as bundled by its parent (inBundle, nested under the parent's node_modules, with no resolved URL or integrity of its own, such as the optional @emnapi/* packages under Tailwind 4's @tailwindcss/oxide-wasm32-wasi) is not acquired separately: it ships inside the parent's tarball, whose integrity is verified. Any other inBundle entry is refused with a message naming the package. Packages outside the public registry, such as a source-only package pinned to a public GitHub commit tarball (declared as that HTTPS tarball URL in package.json and recorded in the lockfile; a git spec is refused), are acquired only from locations the project declares in npm.sources; their locked integrity is still verified.

For the provisioned CI image, a complete Dockerfile example is:

FROM oyzu-toolchain/node:npm11.11.0-node22
WORKDIR /app
COPY package.json package-lock.json ./
RUN --mount=type=bind,from=dependencies,target=/dependencies \
    for archive in /dependencies/*.tgz; do npm cache add "$archive" --offline --cache /tmp/npm-cache --ignore-scripts; done \
    && npm ci --offline --cache /tmp/npm-cache --ignore-scripts --omit=dev --no-audit --no-fund \
    && rm -rf /tmp/npm-cache
COPY app.js .
CMD ["node", "app.js"]

Use your already-provisioned compatible base instead of the CI image as appropriate. Copy all required workspace manifests/sources for a workspace install, and copy npm-shrinkwrap.json instead when using shrinkwrap. The shown glob expects at least one captured registry package; dependency-free projects can run native offline npm without seeding a store. No generated Dockerfile or automatic rewrite of RUN commands is involved.

The store contains only <sha256>.tgz files. Preparation fetches all locked registry tarballs through the scoped public npm broker, validates SHA-512 lock integrity, and invokes native npm offline with lifecycle scripts disabled to reject stale locks and incompatible installations. Local workspace links stay in the source graph; native npm owns dependency resolution and installation layout. Development and optional packages are captured too, with their existing evidence purposes; this is an all-lock store rather than a runtime-only pruning resolver. The shown consumer decides to omit development installation through native --omit=dev. Acquisition does not execute project lifecycle scripts; the example also disables them during the offline build. Packages requiring lifecycle compilation need an explicitly provisioned compiler and a deliberate offline Dockerfile command.

Only tarballs enter the named context. npm's temporary cache, logs, user/global configuration, acquisition workspace and broker state are not exported. The consumer seeds its own disposable cache and removes it in the same RUN instruction, avoiding both cache log timestamps and an extra cache layer. Native npm verifies the lock again during installation. Package names, versions, purposes, content hashes, lock/source identity, observed Node/npm versions and immutable base identity remain in dist/dependencies/<target>.json; the normal versioned OCI artifact, JUnit and Docker quality checks remain mandatory. This does not promise reproducibility for arbitrary lifecycle scripts or other Dockerfile commands.

Missing/stale locks, unsupported lock versions, integrity failures, incompatible engines or a mismatched declared package manager fail preparation. Correct the native inputs or provisioned base and rebuild; preparation failures emit no actions/artifacts. The current public route is https://registry.npmjs.org/; private registries, VCS/direct non-registry sources, managed connector authorization and npm-specific credential canaries are not implemented. There is no persistent acquisition cache or internet fallback during execution.

Existing native tests, Clippy, verified packaging and altered-archive rejection also passed. This uses fixture acquisition bytes and does not prove a read-only container mount. The exact Dockerfile passed native Hadolint and read-only dockerfmt with the builder's trailing-newline convention. The registered dependencies suite's docker-rust-context group requires actual compiled-CLI preparation, offline compilation/run, no reporting-tool requirement, unchanged native versions, runtime image output, OCI/JUnit/quality, repeatability and pre-action checksum rejection. Container execution remains pending; final-image startup and full EX-058 acceptance are separate unfinished obligations.

Dependency runtime identity​

For an external dependencies context, Oyzu verifies that the provisioned runtime still has the captured OCI config digest, then executes its immutable Docker image ID. These identities can differ with Docker's containerd image store, where the image ID of a single-platform image is its manifest digest: Oyzu then exports the image, verifies the manifest bytes against that ID and reads the config digest from it. Classic storage reports the config digest as the ID directly. A changed base reference fails before dependency execution; Oyzu never silently substitutes a newer base. Version-1 dependency-context evidence records runtime_config separately from runtime.digest (the execution ID).

Compiled worker in the consumer runtime​

The Python (python/pip, python/uv, python/poetry) and Cargo (rust/cargo) providers orchestrate preparation with Oyzu's compiled Linux worker running inside the consumer image, so that the image's own interpreter or compiler resolves the packages. A Dockerfile base such as python:3.13-slim-bookworm does not contain that worker, and Oyzu never rebuilds or modifies it. Before preparation, Oyzu copies the worker executable out of the provisioned oyzu-toolchain/builder-worker:v1 image (pulled by its published digest when it is absent and pulling is allowed) into a Docker volume private to the build, and mounts that volume read-only at /usr/local/libexec/oyzu for the preparation containers only. An idle holder container (oyzu-worker-<pid>-<n>-hold, no network, read-only, no capabilities) keeps the volume in use throughout preparation, so another build's storage cleanup on the same Docker engine cannot remove it. Holder and volume are removed when preparation ends, including when an interrupted build unwinds; the offline Dockerfile build never sees them. A forced exit (second Ctrl-C) removes the holder like other tracked containers. If the process dies without cleanup, the holder (labelled dev.oyzu.owner=oyzu, started with --rm) exits by itself after 6 hours, and the then-unused volume is removed by the storage cleanup after the next isolated build. Before preparation, Oyzu starts the worker once in the consumer image (--version) to check that it can run there. The worker image's identity is recorded as worker in the captured context (extensions.oyzu.dev/docker.dependencyContext of dist/dependencies/<target>.json), so a different worker changes the dependency and plan identities. Go and Node providers run native tools only and receive no worker.

Requirements and failures:

  • The worker image must be available: provisioned locally (see Prerequisites and commands) or pullable from the published toolchain images. Otherwise preparation fails with the usual missing-toolchain-image message.
  • Its platform must equal the consumer runtime's platform. The published image is linux/amd64; any other runtime platform fails with the compiled Oyzu worker image ... is linux/amd64, but runtime image ... is ... until a matching worker image is provisioned.
  • The worker is a glibc executable built on Debian bookworm. The consumer base must provide a compatible glibc (bookworm or newer, and other glibc distributions of similar age). A musl base such as Alpine cannot run it: the start check fails with the compiled Oyzu worker cannot start in runtime image ..., naming the glibc requirement.
  • Supplying the worker needs the Docker executor; the daemonless sandbox refuses it.

The worker executable is the one built into the provisioned image, not the running CLI, as for every other toolchain image. Rebuild oyzu-toolchain/builder-worker:v1 from the same source when developing the worker protocol.

Provisioned image capture also supports attestation-bearing OCI indexes by selecting and exporting the runnable manifest for the requested platform. Oyzu verifies its digest and captured config while retaining the immutable index identity for execution. This requires Docker image inspection/export support for --platform; Docker 29.8 was verified. It does not verify signatures or establish trust in attestations. Unsupported selection/export fails rather than substituting an image.

A Windows-coordinated compiled-CLI proof acquired pip dependencies and consumed them offline in the actual indexed Linux image, verified six 1.17.0 in the final image, and passed bundle inspection. Other Docker versions remain unqualified.
