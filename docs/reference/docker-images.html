Docker image inputs and offline builds

CLI reference

Published from the canonical docs/reference/docker-images.md file. Features marked experimental remain experimental; check support limitations before relying on them.

The docker/image builder turns a Dockerfile into a verified OCI image archive. Simple Dockerfiles that only add files to a base image build without any container engine. Everything else builds in an isolated, offline BuildKit worker. This page covers what the builder accepts, how base images and dependencies reach the build, and what a build records.

Note: Image builds are experimental. The builder supports scratch, earlier stages in the same Dockerfile and base images that are already in your local Docker image store (or, for daemonless builds, public registry images pinned by digest).

Image build actions run without network access. On the captured lane, --offline also forbids network acquisition during preparation. That lane does not support offline Docker preparation yet and refuses before any action, even with cached declared fetches. Repeat an online oyzu build --isolated to reuse verified fetch bytes.

What each stage reads​

The Docker plugin declares the following source contracts for captured builds:

StageReads
build (daemonless assembly)Dockerfile, .dockerignore, Dockerfile.dockerignore, and admitted COPY source roots, including directory descendants and newly added files.
build (BuildKit)The same Docker controls and the native frontend's frozen context inventory after Docker ignore filtering. The worker receives only that inventory; a changed inventory changes the operation.
lintDockerfile, .hadolint.yaml, .hadolint.yml.
format-checkDockerfile, .editorconfig when the target's own file declares root = true; otherwise unbounded because ancestor EditorConfig files may apply.
testThe upstream image archive. Validation inspects OCI structure; it does not execute image code.
packageThe upstream image archive copied into the published artifact.

To describe source reads, oyzu build --plan uses stage contracts from the target's last retained build plan, without preparing inputs or invoking the plugin or native frontend. Recorded reasons are marked as facts from the last build and do not admit cache reuse. Stages without a retained contract say reported when the builder answers. BuildKit's frozen context inventory is available only after native preparation.

The typed image build embeds core's supplied version, not a separately computed source identity. Its source reads are bounded by the admitted context. Core can bind a development version and its frozen image name to the admitted shipping reads; a README outside those reads then leaves that version unchanged.

For BuildKit, the reads include the whole context after ignore filtering. A README is therefore an input even when no COPY instruction names it, unless an ignore rule excludes it. Add README.md to .dockerignore if it is not an image input (or to the Dockerfile-specific ignore file when one takes precedence). Daemonless assembly instead selects only its admitted COPY source roots and Docker controls.

dockerfmt keeps native EditorConfig support. A target-local .editorconfig with root = true stops the ancestor search, so format-check can use a bounded contract. Captured plugin planning receives a target source view without the project's ancestor view or project-root boundary. Without a locally provable root = true, it conservatively reports EditorConfig reads an unknown path above the target; captured planning does not expose project ancestors and keeps format-check unbounded, even if no ancestor file is visible. An unreadable file or an unsupported root declaration also keeps that fallback; no EditorConfig option is disabled or rewritten.

Core retains a conservative version when it cannot admit that boundary: source projections, hooks or authored tasks, materialized inputs, cross-target prerequisites, unsupported confinement, and versions without a safely replaceable source hash. A changed supplied version still changes the image operation and its cache key. Declaring bounded context reads does not bypass these fallbacks.

Absent configuration candidates remain reads, so creating one invalidates the stage. Base images, frontend, captured dependency/fetch contexts and OS package snapshots remain explicit prepared inputs with their captured identities. Remote ADD, dynamic sources and unsupported capabilities still fail admission rather than acquiring undeclared inputs. The builder exposes no native-host build operation, so it does not produce host observed-read records. Context inventories exceeding the wire contract's 65,536 selectors retain a whole-target key with an explicit reason.

Selective reuse needs a core release with projection-aware caching and captured version rebinding, followed by a Docker plugin release with these declarations. Older cores retain their conservative behavior. Source projections currently retain the wider version scope, and prepared dependencies that include copied source can still miss after an unread edit. Until version admission covers Docker projections, a docs-only edit can still change the supplied version and rerun all stages. These declarations do not remove the action-cache limitation for host-coordinated image workers: those builds still run every action.

Quick start​

FROM alpine:3.22
COPY greeting.txt /greeting.txt
RUN test -f /etc/alpine-release
oyzu run list
oyzu build --plan
oyzu build
oyzu inspect dist

No extra project configuration is needed. oyzu build prepares the inputs, so the base image must already be provisioned and the base execution image must be available. oyzu build --plan only previews the build. The output is dist/<target>/<platform>/<target>-<version>.oci.tar, with its digest in dist/manifest.json.

For an image with a Helm chart, run oyzu install, then oyzu build. An online, non-frozen install records captured tool recipes as well as installing Helm. A frozen install consumes an already complete lock. A missing captured recipe stops build preparation with TOOL_LOCK_MISSING and the recovery command oyzu pin; no build action runs.

oyzu run build is a native development command. It does not give you the isolated, verified build that oyzu build does.

The Docker plugin never takes the native host path. A workspace that selects an image target, including an image that packages a host-platform binary, takes the captured path along with its producers. That path needs a supported engine. Without one the build stops with ENGINE_PIN_MISMATCH (see plugin development).

The Docker plugin package​

The Docker builder ships as an external plugin package (oyzu-plugin-docker). It reads your Dockerfile and tells Oyzu what to run: assemble an image, run BuildKit, validate the result and copy outputs. Oyzu itself still fetches base images and OS packages, selects source files, runs the isolated steps, enforces policy and records artifacts. A plugin cannot grant itself credentials, mounts, frontends or publishing rights.

A preview release needs user-level opt-in (oyzu config set --global plugins.preview true); a stable catalog release does not. A project cannot opt you into previews. Oyzu selects the signed catalog release and records its version and digest in oyzu.lock, without a package or development binding. See plugin catalog.

The small compiled Go helpers that read Dockerfiles and image metadata, serve OS package snapshots and carry the BuildKit frontend ship inside the plugin package. Oyzu mounts them at /oyzu-plugin, so your machine needs no Go installation.

Prerequisites and commands​

For BuildKit builds you need a Linux Docker engine. Docker Desktop on Windows and macOS works if it runs a Linux engine. Windows containers are not supported.

  • Preparation and the quality checks run on the base execution image. The plugin package carries the metadata helpers, Oyzu's BuildKit frontend and the lint and format tools.
  • RUN steps run in the rootless BuildKit worker oyzu-execution/buildkit:0.34.0, the upstream moby/buildkit 0.34.0 rootless image. Oyzu pulls it by its pinned digest when it is missing (see Published execution images).
  • Base images for BuildKit builds must already be in your local Docker image store. Oyzu does not pull them or read registry credentials on this path. Provision them with your usual process.
  • Daemonless builds need none of this.

After a BuildKit action succeeds, Oyzu waits up to 30 seconds for Docker to confirm that the worker container is gone. If Docker does not, the build fails and its output is not accepted. Check the Docker daemon and build again.

If a build stops with cannot verify the BuildKit worker's AppArmor boundary, Docker did not report its security options in the expected form (docker info --format '{{json .SecurityOptions}}' should return a list of strings). Wait until the Docker engine is fully running and try again.

Artifact target and worker platform​

An image can target a different platform than the worker when building it runs no target code. For example, a Dockerfile with only FROM scratch and COPY can build an arm64 image on an amd64 worker:

builds:
  image:
    uses: docker/image
    platforms: [linux/arm64]
SettingValuesDefaultMeaning
platformslinux/x86_64, linux/arm64 (linux/amd64 and linux/aarch64 are accepted; no ABI)The worker's platformThe image's target platform. Variant suffixes and other platforms fail.
  • List several platforms (platforms: [linux/x86_64, linux/arm64]) to build one image for each. Each has its own versioned archive and reports. A complete set also produces an OCI index. See matrix builds.
  • Oyzu installs no image or emulator for you.
  • A base image must match the platform of the stage that uses it: the target platform, or the worker's platform for a FROM --platform=$BUILDPLATFORM stage. A base with the wrong architecture fails before export, even if the tag matches.
  • A target built from another target's output (see target workspaces) must have the same OS and architecture as its consumer. Setting the image's platform sets the producers' platforms too.
  • Every image is checked against its target platform when it is tested, collected and inspected, so a valid image for the wrong architecture is never kept as a success.

RUN and the target platform. Oyzu cannot run foreign-platform code. A Dockerfile with RUN in a target-platform stage needs the worker and target platforms to match. If they differ, preparation fails before any action runs, even if your machine has an emulator. RUN in a FROM --platform=$BUILDPLATFORM stage is fine.

Daemonless assembly for RUN-free Dockerfiles​

If the final stage of a Dockerfile only adds files to one base and edits image settings, Oyzu builds the image itself without Docker, BuildKit or any container engine. Earlier stages may contain RUN if the final stage does not depend on them. They are skipped and not part of the image.

Oyzu fetches the final base from its registry, adds each COPY as a layer and edits the image configuration. This is the approach ko, Jib and crane append use. Nothing selects it: the Dockerfile's content decides, per target.

FROM gcr.io/distroless/base-debian12:nonroot@sha256:7f0c72cd138b442ae0deeb69c08b1acf5525439ba251a49ad93c320a061567e5
COPY bin/server /server
USER 65532:65532
EXPOSE 8080
ENTRYPOINT ["/server"]

Use JSON COPY when a source or destination needs quoting, for example COPY ["greeting.txt", "/greeting.txt"]. Shell-form COPY greeting.txt "/greeting.txt" selects BuildKit so its native frontend handles quotes and escapes; they never become literal image-path characters.

Use JSON exec form to specify the command and its arguments explicitly when inheriting a base image. It does not depend on that base's configured shell. Oyzu cannot assume an inherited base uses /bin/sh, so shell-form CMD or ENTRYPOINT selects BuildKit even when the base is pinned by digest. An explicit WORKDIR does not change this shell rule. With scratch, /bin/sh is only a configured command: your image still needs that executable if you intend to run it.

When using a digest-pinned base, set an absolute WORKDIR before relative COPY destinations or relative WORKDIR instructions. This makes their location explicit instead of depending on the base image's inherited working directory. Without it, those relative paths select BuildKit. scratch starts at /, so relative paths there can use daemonless assembly immediately. Absolute COPY destinations alone do not change the working directory.

In an unused earlier stage the same instructions are read, but its RUN instructions are skipped. For example, FROM scratch AS unused, RUN exit 99, FROM scratch, COPY greeting.txt /greeting.txt builds only the last COPY.

These use the BuildKit worker instead:

  • a RUN in the final stage,
  • stage references such as FROM unused or COPY --from=unused,
  • ADD, ARG, HEALTHCHECK, VOLUME, SHELL and ONBUILD,
  • unsupported COPY flags, heredocs and variable expansion,
  • a # syntax= or non-default # escape= line,
  • a base pinned only by tag, and
  • a .dockerignore or Dockerfile.dockerignore file.

Base images​

Oyzu first looks for the exact digest-pinned reference in your local Docker image store.

  • A matching OCI index or manifest is exported and checked: the index must contain the requested platform exactly once, and the manifest, config and every layer must verify.
  • A local image that fails the identity, platform or export checks is an error. Oyzu does not go and pull a different image.
  • Classic Docker stores that expose only a config ID cannot be used for local capture.
  • If Docker is missing or not running, you pass --no-docker, or the image is not in the local store, Oyzu pulls from the registry instead.

Registry pulls use the OCI Distribution API by digest, so a moved tag can never change the content. For an index, Oyzu uses the entry for the target platform (linux/amd64 or linux/arm64).

  • Verified content is kept in your image cache: %LocalAppData%\Oyzu\cache\images on Windows, ~/Library/Caches/Oyzu/images on macOS, $XDG_CACHE_HOME/oyzu/images or ~/.cache/oyzu/images on Linux. The project's cache.dir does not move it.
  • Later builds trust content already in the cache. Offline registry builds need it cached. Local images can be used offline.
  • Under managed configuration, builds never contact a public registry.
  • Only anonymous pulls are supported: Oyzu answers the registry's token challenge without credentials. That covers public images on Docker Hub, gcr.io, ghcr.io and similar. A private base fails preparation with an explanation and does not fall back to BuildKit.
  • HTTPS_PROXY, NO_PROXY and SSL_CERT_FILE apply as for other Oyzu downloads. A loopback registry (localhost:5000/...) is contacted over plain HTTP.
  • A base with ONBUILD triggers, zstd or foreign layers, or a different platform from the target fails.

What the image contains​

  • Base layers are copied byte for byte. Docker schema 2 bases are written with the equivalent OCI media types.
  • Each COPY becomes one gzip layer, and so does a WORKDIR that creates a directory. Entries are sorted, stamped with 1980-01-01 UTC and carry numeric ownership only.
  • Files are 0644, or 0755 when they are executable on a Unix host or start with an ELF header or #!. Directories are 0755. --chmod overrides both.
  • New files and directories that COPY creates belong to --chown, or root. Names are looked up in the base image's /etc/passwd and /etc/group, and an unknown name fails the build. Without a group, the user id is also the group id, as in Docker. Directories already in the base keep their owner.
  • The configuration comes from the base, with Env, Labels, User, WorkingDir, ExposedPorts, Cmd, Entrypoint and StopSignal edited as Docker does. An ENTRYPOINT drops an inherited CMD unless the Dockerfile sets one. An image without PATH gets Docker's default.

COPY can read the files under each source in the target folder, plus artifacts you materialize into it. Nothing else in the workspace is visible.

The output has the same layout, name annotations, checks and reports as a BuildKit build. Rebuilding the same inputs gives the same image digest on any machine. It is not byte-identical to what BuildKit would build from the same Dockerfile.

What is recorded​

dist/dependencies/<target>.json names the adapter docker/oci-assembly and records:

  • imageSource: registry or provisioned-local.
  • The base's requested reference, manifest digest, config digest and content-tree digest (under images).
  • The files selected from the context and the Dockerfile digest.

The selected context is a source projection, which is eligible for the action cache. Its definition and captured file identities enter the target key. Bounded stages key the projected files they read; other stages retain the whole-target key. A changed projected input invalidates its readers, and oyzu cache explain names a changed projection. This does not expand Docker's supported context or COPY paths.

Oyzu checks the Dockerfile and base against those identities before it writes anything. The build action records oci-assembly as its execution mode and that it used no container engine and ran no project code.

Without Docker​

If Docker cannot provide the execution image (for example on a host or pod with no engine), a daemonless target still builds. Oyzu's own executable acts as the worker.

Captured plugin planning still runs in isolation, with read-only source and no network. It uses the base execution image as an unpacked Linux root filesystem through the daemonless sandbox. The image is selected by its published digest and reused after installation. A compatible Linux engine member, plugin package and working crun/user namespaces are required, including for FROM scratch. If that runtime is unavailable, preparation refuses; the planner never runs directly on the host. Build and packaging retain their separate in-process identity, and the frozen preparation records the planning runtime and its asset placements.

In-process assembly does not stage Dockerfile lint or format tools. Its planner still requires the admitted plugin package and runtime described above.

  • oyzu build --isolated --no-docker accepts such a target when its selected work is just the build and packaging. The plan shows needsDaemon: false and isolation: in-process.
  • Tasks that need the execution image still need Docker. --full adds Dockerfile lint (hadolint) and format checks (dockerfmt), so the build stops with NEEDS_DOCKER_DAEMON (exit 3) before preparation. Dockerfiles that are not daemonless have the same refusal.
  • A digest-pinned base with ONBUILD triggers fails. Oyzu does not run the triggers or fall back to BuildKit.

Global argument defaults​

Image selection can use ordinary Dockerfile ARG defaults, with no Oyzu configuration:

ARG REGISTRY=docker.io/library
ARG VERSION=3.22
ARG BASE=${REGISTRY}/alpine:${VERSION}
FROM ${BASE}
RUN test -f /etc/alpine-release

Only ARG lines before the first FROM take part in choosing the base and platform.

  • Defaults expand in order using BuildKit's own quoting, escaping and expansion rules. A later declaration with a value replaces an earlier one. A declaration without a value keeps the existing default.
  • You can use expressions such as ${BASE:-alpine:3.22}.
  • An empty base or empty explicit platform fails preparation.
  • ARG inside a stage is not a global default, and host environment variables are never read.
  • If an argument resolves to scratch or an earlier stage, it adds no external image.
  • A stage's platform must be the target platform or the worker's (FROM --platform=$BUILDPLATFORM). Anything else fails.
  • A base for a worker-platform stage is captured for the worker's platform and bound as the BuildKit context <name>::<platform>, so one reference can serve both a build stage and the target stage.

  • You cannot override build arguments on the command line, and variables in stage-level mounts are not expanded.

Image repository​

with.repository names the image's registry repository (no scheme, tag or digest), such as registry.example.com/team/app. Building never publishes to it or contacts it. A helm/chart image binding reads it to name the image it uses.

with optionValuesMeaning
repositoryA repository name without scheme, tag or digestThe image's repository.
dependenciesA provider nameSelects the offline dependency provider.

docker/image accepts only these two with options. oyzu config validate and every command that reads the build inventory reject others. Where a built image is loaded locally is set by docker.load, not by with.

Loading the image locally​

The docker.load setting lists where oyzu run load puts an image you already built, so a local cluster can run it without a custom docker load step.

# build.yaml
builds:
  image:
    uses: docker/image
    with:
      repository: registry.example.com/team/app   # names the loaded image
# oyzu.local.toml (Git-ignored), or oyzu.toml for a team default
[docker]
load = ["docker", "k3d:dev"]
oyzu build
oyzu run load            # or: oyzu run image:load when several targets exist
oyzu config explain docker.load --target image   # where the list came from

Which cluster you use is personal, so the list lives in configuration and not in build.yaml.

  • Put a team default in oyzu.toml and your own cluster in oyzu.local.toml or user configuration.
  • Like other per-target settings, it applies to the docker/image builds in its folder and below. The nearest file wins, and [context.<name>] and profile tables can vary it.
  • The image is named by the build's with.repository.
  • oyzu.local.toml is ignored in CI unless you pass --local-overrides (inspection and selection).
  • Changing it does not rebuild anything.

Rules and failures:

  • A list holds zero to eight distinct destinations. load = [] in a nearer file turns off a default from a farther one.
  • If docker.load reaches a build without with.repository, the load task is listed as unavailable with that reason. Other commands are not affected.
  • An unknown or repeated destination is rejected when the value is read. oyzu config validate reports it and every command that reads that configuration fails.
  • The old with.load key is rejected with a message that points here.
  • A platform matrix with several image variants is refused. Loading one chosen variant is not supported.
  • Pushing to a registry is not part of loading. Use oyzu publish.

Published execution images​

When a build needs one of Oyzu's execution images and your Docker engine doesn't have it, Oyzu pulls it by the digest pinned in src/executor/published_images.json and tags it with the name the build expects. The registry verifies the content, so a moved tag can't swap in a different image. No login or credentials are involved.

  • Pinned today: the base execution image oyzu-execution/base:1, from ghcr.io/oyzuai/oyzu-execution/base (linux/amd64 and linux/arm64), and the BuildKit worker oyzu-execution/buildkit:0.34.0, from docker.io/moby/buildkit (0.34.0 rootless).
  • Dockerfile base images and --image references you bring are never pulled.
  • An image already on your machine is used as is, never replaced.
  • Set OYZU_NO_TOOLCHAIN_PULL=1 to forbid pulling, for example on an air-gapped host. A missing image then fails with a message that says how to provide it.

Limits:

  • The pinned digests are not yet recorded in oyzu.lock.
  • A pulled image is trusted by its pin and not re-checked on later runs.
  • Pulls cannot go through a tool broker or private mirror.

Docker storage budget​

Isolated builds add Docker resources, so Oyzu limits the ones it creates. It never touches anything it did not create. A resource is Oyzu's only if it carries the label dev.oyzu.owner=oyzu or is recorded in the per-user ledger docker-storage.json (in the cache folder of Oyzu's user data directory).

  • Containers and volumes are labelled when created.
  • Docker cannot label an image after a pull, so images are recorded instead: an execution image Oyzu pulled by its pin (images in ghcr.io/oyzuai/oyzu-execution/ that an earlier run pulled are adopted on the first pass) and container tools Oyzu installed.
  • A locally built base image, Dockerfile base images and anything you pulled yourself are never listed, measured or removed.
SettingValuesDefaultMeaning
cache.dockerMaxMiB1 to 1048576 MiB20 GiBThe budget for recorded images. Set it in the ordinary configuration cascade. It is not part of any action key.

After an isolated build that used a Docker image, Oyzu cleans up under a lock shared by builds:

  • Images. Recorded images that lost their tag to a newer pinned image, and those unused for 60 days, are removed. Then the least recently used are removed until the recorded images fit in cache.dockerMaxMiB. Images used by the build that just finished are never removed, and Docker refuses to remove an image a container uses.
  • Containers. Labelled containers that exited over an hour ago are removed along with their anonymous volumes. This includes the BuildKit worker's private store, so BuildKit's cache cannot outlive its worker.
  • Volumes. Unused labelled volumes are removed. Persistent oyzu-tools-* volumes follow their own retention (see build logging).

Cleanup is best effort. A failure leaves the work to the next isolated build and never changes a build's result. Host builds add no Docker resources and run no cleanup. The 60-day and one-hour ages are fixed.

oyzu cache status shows the recorded image count, size and budget on its Docker line (and under docker in --json). It leaves the line out if Oyzu has recorded no image or cannot query Docker. oyzu cache clear empties the action cache only.

How BuildKit builds work​

  1. A native parser reads your Dockerfile to find the images it needs, without running any Dockerfile command. Global ARG defaults are expanded with BuildKit's own expansion library. Dynamic mount references, remote ADD, secret and SSH mounts and host networking are rejected. A # syntax= line builds only if it is on the digest-pinned docker.frontends list (see Oyzu's BuildKit frontend). To bring in a pinned download instead of remote ADD or RUN curl, declare a fetch and copy from the named context oyzu-fetch-<name>.
  2. Oyzu inspects each provisioned image and exports it by its immutable config identity, so a tag change in between cannot substitute another image. It never starts that image and never gives project code the host Docker socket.
  3. An offline Go adapter reads the exported archive, verifies its integrity and platform, and writes an OCI content store that keeps the original config, layers and media types. Images containing ONBUILD fail, because their hidden inputs are not part of discovery.
  4. Oyzu freezes the stores and records the reference, config digest, manifest digest and store digest for each image. Before the worker starts, it copies each store to private storage and checks it against the plan.
  5. BuildKit receives the stores as OCI named contexts. The worker and RUN steps stay offline. The stores are read-only inputs to the worker and are not mounted into RUN containers. No shared build cache is imported.

The identities are recorded under extensions.oyzu.dev/docker.images in dist/dependencies/<target>.json, and they feed the dependency and build plan digests. metadata.selection records the target platform and the export epoch. Planning rejects values that disagree with the selected target.

The manifest digest of a captured image can differ from the registry's original manifest, because docker save does not keep every registry representation. Oyzu verifies the config identity and the captured content, and does not invent registry provenance.

A successful build keeps the versioned <target>-<snapshot-version>.oci.tar archive and its OCI digest in dist/manifest.json, plus integrity and platform JUnit results and lint and format results.

  • These checks do not measure application code coverage. Producers you materialize into the image keep their own test and coverage reports.
  • Version inference supplies a tag-derived base version and a source-derived snapshot suffix. The image reference uses the same version.
  • A changed base image changes the plan and content digests even if the version string is the same.

File times in the worker​

Before the worker starts, Oyzu sets the file and directory access and modification times of its private copies of the source, Dockerfile, materialized artifacts and dependency contexts to the export epoch (1980-01-01 UTC). This makes identical inputs behave identically. Your originals and the prepared stores are unchanged. On Unix, file modes are also normalized, keeping executable bits and dropping umask differences. If a timestamp cannot be set, the worker does not start.

Oyzu passes the same fixed epoch explicitly to both the Dockerfile frontend (SOURCE_DATE_EPOCH) and the OCI exporter (source-date-epoch), with BuildKit layer timestamp rewriting enabled. The exporter uses it for image creation metadata, layer timestamps and the OCI descriptor creation annotation, including when a frontend returns only platform-scoped epoch metadata. No image post-processing is performed.

This does not freeze application clocks, randomness or other file metadata. Installers keep their normal metadata, and the Dockerfile needs no change. Images built by an older Oyzu need to be rebuilt.

Sharing base images and copying them in​

Within one oyzu build, each distinct base is exported with docker image save and converted once. Other targets that need the same base (same reference, Docker image ID, target platform and converter image) wait for it and get a verified copy. This keeps several targets on one large base from holding several copies in Docker's memory. Captures are kept in the system temporary directory and deleted when the build finishes. A failed capture is not reused, and separate oyzu build processes do not share captures.

Oyzu gives the BuildKit worker each captured base as a private copy made with docker cp before the worker starts, not as a bind mount. The source context, definition and output folders are still bind-mounted. The copy is checked against its planned digest, owned by root inside the worker, and removed with it. A Dockerfile that changes while it is being copied is rejected rather than run.

Python application packaging with container: true uses this path (see Python containers).

Offline dependency contexts​

A dependency context is a read-only package store that Oyzu prepares before the offline build. A Dockerfile reads it through an external context named dependencies. The sections below each give a complete example.

Dockerfile RUN instructions own the reproducibility of files they create. Oyzu does not rewrite user-authored layers. A stable plan and verified offline dependency archives do not make timestamp-bearing installer state or runtime caches reproducible; remove unnecessary state in the Dockerfile or use the native tool's controls.

All providers:

  • Oyzu installs none of the tools. A missing tool in the base fails preparation.
  • Preparation downloads from the public registry for that ecosystem, then the build runs offline. Private registries, direct URL or VCS dependencies, managed connector authorization and a persistent download cache are not supported.
  • Oyzu puts no registry token in the image, build arguments or Dockerfile.
  • Stale lock files, failed integrity checks and unsupported inputs fail preparation, before any action runs. Fix the inputs or the base and build again.
  • The dependency record (dist/dependencies/<target>.json) keeps package identities and digests, source and lock identities, the observed tool versions and the base image identity. Package integrity is not a release approval.
  • One matching provider is picked automatically. If several match, set with.dependencies (see Selecting a provider).

Offline pip dependency context (experimental)​

For a Docker target, an external context named dependencies asks for a prepared package store. With one Python ecosystem and a requirements.txt, you do not need to select a provider. Choose the Docker builder explicitly if the project also looks like an application:

builds:
  image:
    uses: docker/image
FROM python:3.13-slim-bookworm
WORKDIR /app
COPY requirements.txt .
RUN --mount=type=bind,from=dependencies,target=/dependencies \
    pip install --no-index --no-cache-dir --no-compile --find-links=/dependencies -r requirements.txt
COPY app.py .
CMD ["python", "app.py"]
  • Add application files with ordinary COPY.
  • --no-compile avoids bytecode timestamps in the example. Use python -B for import checks during the build.
  • A requirement such as six==1.17.0 is resolved by pip inside the exact base image, with its Python, pip, ABI and platform.
  • Preparation downloads binary wheels through Oyzu's public-PyPI proxy. It adds no build, test or quality tools to the store and runs no project code or source builds.
  • The Docker build then installs from the store with no network. Oyzu does not rewrite your RUN commands.

Selecting a provider​

If other ecosystems' manifests make automatic selection ambiguous, name the provider with with.dependencies:

builds:
  image:
    uses: docker/image
    with:
      dependencies: python/pip

The value must be one provider name. oyzu config validate rejects anything else. The old top-level dependencies: build field is rejected with a message pointing at with.dependencies.

  • Several matching managers need an explicit with.dependencies, even within Python.
  • Unknown providers and missing native manifests fail.
  • with.dependencies without an external dependencies reference also fails.
  • A Dockerfile stage that is actually named dependencies stays a normal stage. Other external names are treated as image references.

uv and Poetry​

  • uv uses its locked, offline export with --no-default-groups. Poetry uses its export plugin for the main group, with project plugins off.
  • Stores exclude development groups and optional extras. A stale lock or hash mismatch fails.
  • Local, path and VCS dependencies and extra indexes are not supported.
  • uv and Poetry projects use their own lock, not a nearby requirements file.

All three Python providers add a generated requirements.txt next to the wheels, pinning the whole selected closure with SHA-256 hashes. A uv or Poetry project can install from it without copying its lock into the image:

RUN --mount=type=bind,from=dependencies,target=/dependencies \
    pip install --no-index --no-deps --require-hashes --no-cache-dir --no-compile --find-links=/dependencies -r /dependencies/requirements.txt

uv's uv pip install can use the same file. uv sync and poetry install are not supported inside the build.

Runtime image and evidence​

  • The base image must already be local and provide Python 3.11 or later with pip.
  • The worker and target platforms must match for package preparation, even if the Dockerfile only copies files.
  • With earlier named stages, the consumer is the stage's original base. Several different consuming bases, a scratch consumer or mismatched platforms fail instead of sharing an unchecked set of packages.
  • Preparation uses the base's captured config, not a tag that may have moved.
  • If later commands change the interpreter or libraries in the stage, compatibility is up to you.
  • The dependency record keeps wheel identities and digests, source and lock identities, the interpreter and manager versions and a digest of the store. Only the wheels and the generated requirements enter BuildKit's context.
  • Direct URL requirements, alternate-index directives and source distributions are rejected.
  • Remote syntax frontends and secret mounts are not supported.

Offline npm dependency context (experimental)​

node/npm exports verified registry tarballs using the Node builder's locked acquisition. A Docker target with package.json and a v2 or v3 package-lock.json or npm-shrinkwrap.json picks this provider automatically (shrinkwrap wins, as in npm). With several ecosystems, set with.dependencies: node/npm.

FROM registry.example.com/build/node:22-npm11
WORKDIR /app
COPY package.json package-lock.json ./
RUN --mount=type=bind,from=dependencies,target=/dependencies \
    export NODE_DISABLE_COMPILE_CACHE=1 \
    && for archive in /dependencies/*.tgz; do npm cache add "$archive" --offline --cache /tmp/npm-cache --ignore-scripts; done \
    && npm ci --offline --cache /tmp/npm-cache --ignore-scripts --omit=dev --no-audit --no-fund \
    && rm -rf /tmp/npm-cache
COPY app.js .
CMD ["node", "app.js"]
  • The example base is one you provision that contains Node and npm.
  • npm enables Node's module compile cache. The example uses Node's native NODE_DISABLE_COMPILE_CACHE=1 control for the install RUN, so this execution-time optimization is not shipped in the application image. It leaves the installed packages and application runtime unchanged.
  • Copy all workspace manifests and sources for a workspace install. Copy npm-shrinkwrap.json instead when you use shrinkwrap.
  • The glob needs at least one captured package. A project with no dependencies can run npm offline with no store.
  • A declared packageManager must match the base image's npm version, and npm checks engines.
  • A package npm records as bundled inside its parent (inBundle, with no resolved URL or integrity of its own) is not fetched separately. It ships in the parent's tarball, whose integrity is verified. Any other inBundle entry is refused, naming the package.
  • Packages outside the public registry, such as a package pinned to a public GitHub commit tarball (an HTTPS tarball URL in package.json and the lockfile, not a git spec), are fetched only from locations the project declares in npm.sources. Their locked integrity is still checked.

The store contains only <sha256>.tgz files. Oyzu fetches every locked registry tarball, verifies the SHA-512 lock integrity and runs npm offline with lifecycle scripts off, which rejects stale locks and incompatible installs. Workspace links stay in the source. Development and optional packages are fetched too (the example omits development packages with --omit=dev). npm's cache, logs, configuration and Oyzu's own state are not exported. The example seeds a throwaway cache and deletes it in the same RUN, so no cache layer is left.

Oyzu does not run project lifecycle scripts while preparing. Packages that need a compile step need a compiler in the base and an explicit offline command in your Dockerfile.

Failures and limits:

  • Missing or stale locks, unsupported lock versions, failed integrity checks, incompatible engines or a mismatched package manager fail preparation.
  • The registry is https://registry.npmjs.org/. Private registries, VCS or direct non-registry sources and managed connector authorization are not supported.
  • There is no persistent download cache or internet fallback during the build.

Offline Yarn Classic dependency context (experimental)​

node/yarn exports a Yarn offline mirror after Oyzu validates the locked dependency graph. With package.json and yarn.lock and no competing ecosystem, it is selected automatically. With several native locks, set with.dependencies: node/yarn. A modern Yarn lock is not treated as Classic.

FROM registry.example.com/build/node:22-yarn1
WORKDIR /app
COPY package.json yarn.lock ./
RUN --mount=type=bind,from=dependencies,target=/dependencies \
    --mount=type=tmpfs,target=/tmp \
    export DISABLE_V8_COMPILE_CACHE=1 \
    && printf 'yarn-offline-mirror "/dependencies"\ndisable-self-update-check true\n' >/tmp/oyzu.yarnrc \
    && yarn install --offline --non-interactive --frozen-lockfile --ignore-scripts --use-yarnrc /tmp/oyzu.yarnrc --cache-folder /tmp/yarn-cache \
    && yarn cache clean --offline --non-interactive --cache-folder /tmp/yarn-cache \
    && rm -rf /tmp/yarn-cache /tmp/oyzu.yarnrc
COPY app.js .
CMD ["node", "app.js"]
  • The image must already have Node and Yarn Classic 1.22.22. Oyzu installs neither. The @yarnpkg/lockfile 1.1.0 parser that reads yarn.lock ships in the Node plugin package, so the image doesn't need it. An OYZU_YARN_LOCKFILE path set in the image takes precedence.
  • Yarn Classic bundles v8-compile-cache. The example disables it with its native DISABLE_V8_COMPILE_CACHE=1 control for both Yarn commands. The temporary /tmp mount keeps install scratch out of the image layer.
  • Only the verified mirror archives enter dependencies. The temporary configuration in the example lives inside the RUN and is removed there. Lifecycle scripts stay off.
  • Preparation uses the base's Node and Yarn, checks engines and package-manager constraints and rejects a graph that changed. Yarn applies registry-only resolutions.
  • Oyzu records every locked input with purpose build. It does not prune to runtime-only packages.

Supported: a single project, Classic v1 locks, SHA-512 or legacy SHA-1 lock integrity, scoped and transitive registry packages, registry version-range resolutions, and the root .yarnrc and .npmrc settings listed in Yarn project settings. Copy those files into the consumer stage too if Yarn should apply them there.

Not supported: workspaces, other .yarnrc and .npmrc settings, .yarnrc.yml, path and VCS dependencies, modern Yarn, private registries and managed connectors. Missing tools, stale locks, changed integrity or a changed base fail before any artifact is built. The build cannot fetch missing packages, and there is no persistent download cache.

Offline pnpm dependency context (experimental)​

node/pnpm prepares a pnpm store in the exact base image, using the Node builder's registry downloads and frozen-lock checks. package.json and a single-project v9 pnpm-lock.yaml select it if unambiguous. Otherwise set with.dependencies: node/pnpm.

FROM registry.example.com/build/node:22-pnpm10.11
WORKDIR /app
COPY package.json pnpm-lock.yaml ./
RUN --mount=type=bind,from=dependencies,target=/dependencies \
    cp -r /dependencies /tmp/pnpm-store \
    && pnpm --config.manage-package-manager-versions=false install --offline --frozen-lockfile --ignore-scripts --ignore-pnpmfile --config.verify-store-integrity=true --config.side-effects-cache=false --store-dir /tmp/pnpm-store \
    && rm -rf /tmp/pnpm-store \
    && rm node_modules/.modules.yaml node_modules/.pnpm-workspace-state.json
COPY app.js .
CMD ["node", "app.js"]
  • The image must already have Node and pnpm 10.11.0. The yaml 2.9.1 parser that reads pnpm-lock.yaml ships in the Node plugin package. An OYZU_PNPM_YAML path set in the image takes precedence. Other pnpm versions fail at export, because the store format is tied to this version.
  • The example produces a runtime-only image: it removes pnpm's timestamp-bearing install bookkeeping (.modules.yaml and .pnpm-workspace-state.json) in the same authored RUN. Native Node imports and pnpm exec node work without those files. Keep the files if the image must support later installs; their timestamps can change image digests.
  • The context is read-only. Copy it so pnpm has a private writable store, and delete the copy in the same RUN. Installed packages keep working after the store is gone.
  • Oyzu exports only pnpm's v10/files and v10/index records, sets each index file's checkedAt to zero and writes index keys in a fixed order. Package bytes and integrity values are unchanged, and pnpm rechecks the copied content. Links, special files, unknown store paths and side-effect caches are rejected, with limits of 100,000 files, 10 GiB and 16 MiB per index.
  • An empty lock exports an empty store. User configuration and Oyzu's own state are not included.
  • For a patched project, copy pnpm-workspace.yaml and patches/ before installing, or use the package.json patch declaration. pnpm applies and verifies the patches, and the record keeps the original package integrity and patch digests.
  • Lifecycle scripts and side-effect caching are off. Every locked registry input is captured and recorded with purpose build.

Not supported: workspaces, .npmrc, .pnpmfile.cjs, unsupported overrides, direct, path and VCS dependencies, other pnpm versions and private or managed registries. Stale locks, changed integrity, missing tools or unrecognized store data fail preparation. The build has no registry access, so an incomplete store fails and is never topped up from the internet.

If pnpm reports a native-mirror HTTP 502 during preparation, check the build diagnostic for the original acquisition cause. A SHA-512 integrity mismatch means the downloaded archive differs from the lock's publisher checksum; no build action or artifact is produced. Verify the lock and registry source before retrying. Do not disable integrity verification to accept different bytes.

Offline Go module context (experimental)​

go/modules gives the build Go's checksum-verified module download cache through dependencies. A Docker target with go.mod or go.work picks it automatically. With mixed ecosystems, set with.dependencies: go/modules.

For a pure-Go command with a complete go.sum:

FROM golang:1.24-bookworm AS build
WORKDIR /src
COPY . .
RUN --mount=type=bind,from=dependencies,target=/dependencies \
    GOMODCACHE=/tmp/gomodcache GOPROXY=file:///dependencies/cache/download GOSUMDB=off GOTOOLCHAIN=local CGO_ENABLED=0 go build -mod=readonly -trimpath -buildvcs=false -o /app .
FROM scratch
COPY --from=build /app /app
ENTRYPOINT ["/app"]
  • Go resolves workspace members, local replacements and test imports from your source and checksum files. Oyzu fetches the required modules through the public Go proxy, and Go verifies go.sum. Preparation does not change your manifests or checksum files.
  • The base must already have Go and a POSIX shell, plus a C compiler for cgo. The example uses the standard golang:1.24-bookworm image. Preparation compiles a small metadata helper with that Go using only the standard library. It does not need oyzu-go-modulezip, version projection or module packaging, which belong to ordinary go/app and go/library builds.
  • Toolchain download, VCS access and user Go configuration are off during preparation.
  • The store is Go's download cache (module zips with their .mod and .info files), mounted read-only. The build uses it as a file proxy and extracts what it needs into its own writable GOMODCACHE, and Go verifies each zip against go.sum. Extracted trees are not stored, because many small files on a Docker Desktop bind mount were slow. No broker, credentials or acquisition metadata are in the store.
  • Compiler output stays in the build stage, and the final scratch stage holds only the binary. Use a real runtime image instead of scratch for cgo or other runtime libraries.
  • The record keeps the Go version and platform, lock and source digests and the module archives used. Its module-artifact list is empty because preparing dependencies does not publish your own module.
  • The image's JUnit report checks the image, not your source. Build a separate Go target if you need source tests and coverage.

Failures: missing checksums, stale manifests, workspace or replacement paths that escape the project, or an incompatible base fail preparation. Update and commit your Go files, or fix the base, and build again. Private modules, direct VCS sources, checksum database integration and a persistent cache are not supported.

Offline Cargo registry context (experimental)​

rust/cargo gives the build a Cargo local registry. A Docker target with Cargo.toml and a checked-in Cargo.lock picks it automatically when no other ecosystem is present. Otherwise set with.dependencies: rust/cargo. The lock file is required even for a local-only workspace.

FROM rust:1.94.0-slim-bookworm AS build
WORKDIR /src
COPY . .
RUN --mount=type=bind,from=dependencies,target=/dependencies \
    CARGO_HOME=/tmp/cargo-home CARGO_TARGET_DIR=/tmp/cargo-target CARGO_INCREMENTAL=0 cargo \
    --config 'source.crates-io.replace-with="oyzu-captured"' \
    --config 'source.oyzu-captured.local-registry="/dependencies"' \
    build --release --locked --offline \
    && cp /tmp/cargo-target/release/oyzu-registry-example /app
RUN test "$(/app)" = "Answer: 42"
FROM debian:bookworm-slim
COPY --from=build /app /app
ENTRYPOINT ["/app"]
  • The base must already have Rust/Cargo 1.94.0, a POSIX shell and the compiler and linker your project needs. The example uses rust:1.94.0-slim-bookworm. Preparation does not need Python, nextest or llvm-cov.
  • Oyzu checks the whole lock before downloading, using only crates.io registry sources whose index and archive SHA-256 checksums match. Cargo then validates the workspace and lock offline inside the exact base image. Preparation runs no build scripts, does not rewrite your lock and does not produce your crates' artifacts.
  • Only *.crate archives and their index/ entries enter the read-only context. It uses Cargo's local-registry source replacement. Cargo unpacks into a fresh private home.
  • The example's final stage copies the binary onto a Debian runtime that has the dynamic libraries it needs.
  • A workspace with no dependencies needs no source replacement. Local workspace packages remain source inputs.
  • The record keeps Cargo's metadata, the compiler and manager versions, the base identity, source and lock digests and the verified packages. It has no nextest or coverage evidence. The image's JUnit report checks the image, not your Rust tests. Build a separate Rust target if you need tests and coverage.

Failures: a missing or stale lock, mismatched checksums, Git or alternate-registry sources, local paths that escape the project or missing tools fail before any artifact is built. Managed or private registries, a persistent download cache and other Rust versions are not supported.

Dependency runtime identity​

For a dependencies context, Oyzu checks that the base image still has the captured OCI config digest, then runs it by its immutable Docker image ID.

  • With Docker's containerd image store, a single-platform image's ID is its manifest digest. Oyzu then exports the image, checks the manifest bytes against the ID and reads the config digest from it. Classic storage reports the config digest as the ID.
  • If the base reference changed, the build fails before the dependencies run. Oyzu never silently switches to a newer base.
  • The dependency record keeps runtime_config separate from runtime.digest (the execution ID).

Compiled worker in the base image​

The Python and Cargo providers run Oyzu's compiled Linux worker inside the base image, so the image's own interpreter or compiler resolves the packages. Go and Node providers run only native tools and use no worker.

Your base image does not contain the worker, and Oyzu never changes it. Oyzu mounts the invocation's engine read-only into the preparation containers, as in every other container action (see What runs in a container action). The selected engine member is recorded with the dependency record, so a different engine changes the plan.

Requirements:

  • An engine must be available for the base image's platform. Without an engine package, a Linux CLI of the same architecture mounts its own executable. Otherwise preparation stops with ENGINE_ASSET_UNAVAILABLE.
  • An engine package's static Linux member runs on glibc and musl bases alike. When a Linux CLI mounts its own executable instead, the base needs that executable's glibc (2.39 or newer for release builds).

Attestation-bearing indexes​

Oyzu can use a base whose OCI index carries attestations. It selects and exports the runnable manifest for the requested platform, verifies its digest and config, and keeps the index identity for execution. This needs Docker image inspect and export to support --platform (Docker 29.8 is known to work). It does not verify signatures or trust the attestations. If selection or export is unsupported, the build fails and no image is substituted.

Failures, limits and migration​

A missing image fails preparation with a provisioning message. There is no automatic internet fallback for BuildKit builds.

  • A platform mismatch, malformed export, config mismatch, hidden ONBUILD, a modified frozen store or a native worker failure blocks artifacts. Fix the input or base image and build again.
  • Lint and format failures still block the build (see Dockerfile linting and formatting).

Limits:

  • At most 64 distinct image references per build, 100,000 entries per image export and 10 GiB for an export or captured tree. Unsafe archive paths, duplicate member names and links are rejected without extracting layers on your machine. Unsupported archive forms fail.
  • Equivalent references such as alpine:3.22 and docker.io/library/alpine:3.22 share one BuildKit context when their identities agree. Both requested references stay in the record. Conflicting identities fail planning, and reference order never picks between different images.
  • Registry credentials, managed registry access, secret mounts, other package managers and a Dockerfile-free application image profile are not supported. An image in your local Docker daemon is not a statement that it is trusted or approved for release.

Upgrading:

  • Captures and plans made by older tools must be regenerated. They fail rather than assume defaults for missing platform or frontend facts.
  • No project file changes are needed.

Checking an image​

Check a build's result with oyzu inspect dist. For an image it confirms that the archive's digests and platform match what the build recorded. The build itself checks every image against its target platform, so an image for the wrong architecture is never kept as a success, and a valid archive hash is not enough.

An image archive also carries a JUnit report with its integrity and platform assertions. These do not run the image or replace your application tests.
