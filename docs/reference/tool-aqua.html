Registry packages (oyzu: ids, from the aqua registry)

CLI reference

Published from the canonical docs/reference/tool-aqua.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Registry packages are command-line tools described by the aqua registry, the same catalog mise's aqua backend reads. Oyzu installs them with an oyzu: tool ID and verifies each download against the publisher's SHA-256. Use them for tools Oyzu doesn't provide itself, such as terraform, gh or ripgrep.

Note: Experimental. Error codes, field names and the pinned registry snapshot may change. Supported on Linux x86-64; Windows and macOS are not supported yet.

When a tool index is configured (the default), packages it lists install from the index. The rest of this page describes what Oyzu does when it resolves a recipe from the registry itself.

Platform scope: Use an x64 host and supported x64 build targets. ARM64 is unsupported. Feature-specific limits are listed in the support matrix.

Usage​

oyzu install terraform@1.9.8            # a curated name
oyzu install gh@2.49.2                  # a catalog short name, stored as oyzu:gh
oyzu install oyzu:burntsushi/ripgrep@14.1.1
oyzu install aqua:go-task/task@3.54.0   # mise spelling, rewritten to oyzu:task
gh --version                            # runs the installed binary
oyzu tools info oyzu:gh                 # provider, source, commands, platforms, verification
oyzu tools versions oyzu:gh             # releases, newest first, with excluded ones explained
oyzu uninstall oyzu:gh

In an activated shell, which the install script sets up, the plain tool commands run the pinned versions. Where a shell isn't activated, prefix them with oyzu exec --.

Configuration stores the tool's canonical ID:

[tools]
"oyzu:task" = "3.54.0"
"oyzu:gh" = "2.49.2"
terraform = "1.9.8"            # curated names can be written bare

All tool commands work (scopes, --dry-run, --frozen, --offline, update, tools current, tools list). No account and no mise executable are needed.

Option tables​

mise's table form of a [tools] entry is accepted for every tool, with one option, version. It means the same as the plain string:

[tools]
"oyzu:gh" = { version = "2.49.2" }

[tools."oyzu:jq"]
version = "1.7.1"
  • oyzu install gh@2.50.0 changes only version inside the table, keeping its form and comments. A table under an aqua: or core: key is replaced by a plain entry under the new key.
  • Other options (os, exe, bin, asset_pattern, install_env, postinstall, ...) are ignored with a warning. They never run hooks or change the installation. oyzu config validate --strict turns the warnings into errors.
  • A table without a valid version string is refused (CONFIG_INVALID_VALUE).
  • Arrays of versions aren't supported.

Tool ids​

Every spelling of a package resolves to one canonical ID, and configuration and the lock store that ID, so how you typed it never changes the lock. IDs never carry an aqua: prefix.

PackageCanonical IDAlso accepted
In the curated set (for example hashicorp/terraform)oyzu:<name> (oyzu:terraform)terraform, oyzu:hashicorp/terraform, aqua:hashicorp/terraform
Any other registry packageoyzu:<owner>/<repo>[/<name>], lowercased (oyzu:burntsushi/ripgrep)aqua:BurntSushi/ripgrep; a catalog short name (ripgrep) with oyzu install
A GitHub repository's release assetsgithub:<owner>/<repo>
Oyzu's own providers (Node, Go, Rust, ...)oyzu:<name> (oyzu:go)go, and the older core:go
  • Curated names are built into Oyzu, so they resolve without the network. Each is the package's primary name in mise's catalog, except cli/cli, which is oyzu:gh (mise's github-cli also works). Names that would clash with an Oyzu provider (kubectl, helm, k3d) or a Cargo helper aren't curated; those packages keep their owner/repo ID.
  • aqua: is accepted as input wherever an ID is (commands, [tools] keys, policy) and rewritten. Oyzu never writes it. Installing a tool declared under an aqua: or core: key moves the declaration to the new key.
  • The lock records the origin. Each lock entry lists the registry package in components (package:<owner>/<repo>), next to registry: and tag:.
  • Older locks with aqua: or core: IDs are stale. oyzu install reports TOOL_LOCK_STALE naming the rename, and oyzu install --frozen fails. Run oyzu update to re-lock the same versions under their oyzu: IDs (same archives and digests). [tools] keys written as aqua: keep working and aren't rewritten.

Short names​

As in mise, oyzu install gh@2.49.2 looks up a short name that Oyzu neither provides nor curates in mise's name catalog, expands it to the first backend Oyzu supports (aqua:cli/cli) and stores the canonical ID (oyzu:gh). oyzu:gh is looked up the same way.

$ oyzu install gh@2.49.2
$ cat oyzu.toml
[tools]
"oyzu:gh" = "2.49.2"
  • The catalog is the registry/*.toml data from the mise crate release 2026.10.5. Oyzu downloads it from static.crates.io, checks it against a pinned SHA-256 and caches it as <store>/catalogs/mise-registry-<digest>.crate. Once cached, it works offline. No mise code is run.
  • A name Oyzu provides itself (node, go, ...) always resolves to Oyzu's provider.
  • Short names work with oyzu install only. Other commands and [tools] keys need a curated name or the canonical ID.
SituationResult
Unknown nameTOOL_NAME_UNKNOWN, suggesting the oyzu:<owner>/<repo> spelling.
Only available through backends Oyzu lacks (cargo:, npm:, asdf:, ...)TOOL_BACKEND_UNSUPPORTED, listing them.
Catalog can't be fetched, or its digest differsTOOL_REGISTRY_UNAVAILABLE or TOOL_REGISTRY_DIGEST_MISMATCH.

Requests​

RequestMeaningNeeds the GitHub release list
3.54.0 or v3.54.0Exactly this release.No
latestNewest stable release the recipe covers.Yes
2.49Highest stable 2.49.x the recipe covers.Yes
  • An exact version tries the tag spellings <version_prefix>v<version> and <version_prefix><version>, and uses the first whose checksum file exists. Pinned installs make no GitHub API request, so they can't hit its rate limit.
  • latest and prefixes read GitHub's releases API (the newest 300 releases). Set GITHUB_TOKEN to raise the anonymous limit; it's sent to api.github.com only.
  • Drafts are never offered. Pre-releases are only used when named exactly.
  • The lock keeps your request and the exact release. A latest lock stays valid without re-reading the release list.

What is installed, and from where​

  • Registry. One pinned snapshot, aqua-registry v4.573.0, downloaded from raw.githubusercontent.com, checked against its SHA-256 and cached in the tool store as catalogs/aqua-registry-<digest>.yaml. Each Oyzu build uses a fixed snapshot.

  • Resolution. Declaring or updating a tool evaluates its recipe for each default platform (linux/amd64/gnu, darwin/amd64/native, windows/amd64/msvc) with the recipe evaluator, reads the publisher's checksum file and writes one lock entry per platform. A platform with no build is recorded as unavailable.

  • Recipe types. github_release (a GitHub release asset) and http (a direct download URL, such as https://releases.hashicorp.com/...). Other types (go_install, cargo, github_content, ...) are refused with SOURCE_KIND.

  • Formats. The recipe's format decides how the download is unpacked:

    formatInstalled as
    tar.gz, tgzgzip tar
    tar.xz, txzxz tar
    tar.zstzstd tar
    tarplain tar
    zipZIP
    raw (or an asset with no archive extension)The file is the executable. It's stored under the first command's name (<name>.exe on Windows) and every declared command runs it.

    Other formats (tar.bz2, tbz, single-file gz, bz2, xz or zst, 7z, dmg, pkg) fail with TOOL_ARCHIVE_UNSUPPORTED. Archives are unpacked with limits on entries, size, depth and expansion ratio.

  • The lock is the pin. Each lock entry holds the archive URL, its SHA-256, and in components what install needs: kind:, bin:<command>=<path in the archive>, tag: and registry:. A locked tool installs without the registry, and oyzu install --frozen into an empty store needs only the locked URLs.

  • Download. Only the host archive is downloaded, and its SHA-256 must match the lock. GitHub's release hosts are always allowed. A recipe that downloads from elsewhere is allowed that host only over HTTPS on port 443, with a public DNS name (no IP address, single-label or .local-style name) and no credentials in the URL. Tool routes for registry packages aren't supported (TOOL_ROUTE_UNSUPPORTED).

  • Commands. The executables a recipe declares (files) become the tool's commands. Without files, the command is the last part of the package name (kubectl for kubernetes/kubernetes/kubectl). On Windows, .exe is added as the registry specifies. With several commands, each is available through oyzu exec -- <command>, and each command's folder is added to PATH for child processes. When several names share one file (superfly/flyctl declares flyctl and fly), each works through oyzu exec, but a child process searching PATH only finds the file's own name.

Install checks​

Install checks the publisher's SHA-256: the lock records the checksum from the recipe's checksum file for each platform, and the download must match it. A checksum file whose body is a single digest with no file name (like dl.k8s.io's kubectl.sha256) is read as that asset's digest.

Recipes can also declare GitHub artifact attestations, cosign, SLSA provenance or minisign. Oyzu doesn't check those yet, and they don't stop an install. For example, oyzu install oyzu:gh@2.102.0 installs on its checksum even though the recipe declares an attestation. tools info says so.

A successful install means the archive matches the checksum the publisher listed when you resolved it. It doesn't prove the publisher or the checksum file is authentic.

CodeCause
TOOL_CHECKSUM_MISSINGThe recipe declares no checksum, and the package isn't on the GitHub-reported digest list.
TOOL_CHECKSUM_UNSUPPORTEDThe checksum isn't SHA-256, or the checksum file uses the regexp format.
TOOL_CHECKSUM_UNVERIFIABLEThe checksum file doesn't list the archive, or lists conflicting values.

GitHub-reported digests​

A recipe without a checksum normally can't be locked. For a short, reviewed list of packages, Oyzu instead locks the SHA-256 that GitHub reports for the release asset in the package's own repository. The list currently holds protocolbuffers/protobuf/protoc. It isn't open to every checksum-less recipe, because that would weaken checks for tools nobody reviewed.

Any other checksum-less package reports TOOL_CHECKSUM_MISSING. For a tool a builder detected, that's a warning row and the build continues; for a tool you pinned, it's an error.

Other errors​

CodeCause and fix
TOOL_ALIAS_UNSUPPORTEDAnother backend (asdf:, vfox:, ...) isn't supported. The message lists what is.
TOOL_SPEC_INVALIDNot oyzu:<name>, oyzu:<owner>/<repo> (or <owner>/<repo>/<name>), github:<owner>/<repo> or the aqua: alias.
TOOL_NAME_UNKNOWNoyzu:<name> isn't curated. Use oyzu:<owner>/<repo>, or oyzu install <name>.
TOOL_NOT_IN_REGISTRYThe package isn't in the pinned snapshot. Check the spelling.
TOOL_VERSION_NOT_FOUNDNo such release, or nothing matches a prefix in the newest 300 releases. Run oyzu tools versions.
TOOL_RATE_LIMITEDGitHub refused the release list (anonymous limit or access policy). Set GITHUB_TOKEN, or request an exact version.
TOOL_ARCHIVE_UNSUPPORTEDThe format isn't in the format table.
CONFIG_INVALID_VALUEA [tools] table has no valid version string. See option tables.
TOOL_RECIPE_UNSUPPORTEDThe recipe uses something the evaluator doesn't support. See recipe resolution.
TOOL_REGISTRY_UNAVAILABLE, TOOL_REGISTRY_DIGEST_MISMATCHThe pinned snapshot couldn't be fetched, or doesn't match its digest.

tools versions and tools info​

oyzu tools versions oyzu:<name> lists releases, newest first, for this host. A release the recipe doesn't cover, with no build for this platform, or whose verification Oyzu can't perform appears under excluded with the reason, so the list shows what install would accept.

oyzu tools info shows the provider, source, commands (once locked), platforms, eligibility under tools.allowed, declarations and the verification rule. Both support --json.

Limits and known gaps​

  • Supported on Linux x86-64 only.
  • Formats: tar.gz, tar.xz, tar.zst, tar, zip and raw executables only. Only SHA-256 checksum files. Attestations, cosign, SLSA and minisign aren't checked.
  • A command name that differs from its file's name (such as flyctl's fly) works through oyzu exec but isn't on the child PATH.
  • Option tables honor only version. Other mise backends aren't supported (github: is separate; see the github: backend).
  • A hand-written declaration with no lock entry needs oyzu install <id> or oyzu update; plain oyzu install reports TOOL_LOCK_STALE.
  • The registry snapshot is fixed per Oyzu build. Your own registries and a floating registry aren't supported.
  • Tool routes aren't supported for registry packages, and version listing needs GitHub's API.
  • Recipe vars and musl builds aren't supported.
  • tools.allowed matches the canonical oyzu: ID.
