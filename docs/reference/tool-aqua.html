Registry packages (oyzu: ids, from the aqua registry)

CLI reference

Published from the canonical docs/reference/tool-aqua.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Status: experimental, provisional. First install proof (A1) of the draft backend compatibility direction: Oyzu reads the aqua registry catalog that mise's aqua backend reads, inside oyzu.toml, and names each package with an Oyzu tool id. Error codes, field names and the pinned registry snapshot may change. Qualification is Linux x86-64 only; see qualification for what ran and what did not.

Usage​

oyzu install terraform@1.9.8            # a curated name
oyzu install gh@2.49.2                  # a catalog short name, stored as oyzu:gh
oyzu install oyzu:burntsushi/ripgrep@14.1.1
oyzu install aqua:go-task/task@3.54.0   # mise spelling, rewritten to oyzu:task
oyzu exec -- gh --version               # runs the installed, verified binary
oyzu tools info oyzu:gh         # provider, source, commands, platforms, verification
oyzu tools versions oyzu:gh     # releases, newest first, with excluded ones explained
oyzu uninstall oyzu:gh

The declaration is the tool's canonical id:

[tools]
"oyzu:task" = "3.54.0"
"oyzu:gh" = "2.49.2"
terraform = "1.9.8"            # curated names may also be written bare

All the tool commands apply (scopes, --dry-run, --frozen, --offline, update, tools current, tools list). No account is needed and no mise executable is used.

Option tables​

mise's table form of a [tools] entry is accepted with one option, version, for every tool (not only registry packages). It means exactly the same as the plain string:

[tools]
"oyzu:gh" = { version = "2.49.2" }

[tools."oyzu:jq"]
version = "1.7.1"

oyzu install gh@2.50.0 changes only the version inside such a table, so the file keeps its form and comments. (A table under an aqua: or core: key is replaced by a plain entry under the new key when that tool is installed.) Unknown options (os, exe, bin, asset_pattern, install_env, postinstall, ...) and unknown sub-tables are ignored with optional configuration warnings. Only version affects the request: ignored fields never run hooks or modify installation. Use oyzu config validate --strict to reject these warnings; declare a required capability when correct execution depends on new behavior. A table without a valid version string is still refused.

Arrays of versions are not supported.

Tool ids​

Maintainer decision of 2026-10-10 (naming): tool ids carry no aqua: prefix. Every spelling of a package resolves to one canonical id, and configuration and the lock store that id, so the spelling never changes the lock.

PackageCanonical idAlso accepted
In the curated set (for example hashicorp/terraform)oyzu:<name> (oyzu:terraform)terraform, oyzu:hashicorp/terraform, aqua:hashicorp/terraform
Any other registry packageoyzu:<owner>/<repo>[/<name>], lowercased (oyzu:burntsushi/ripgrep)aqua:BurntSushi/ripgrep; a catalog short name (ripgrep) with oyzu install
A GitHub repository's release assetsgithub:<owner>/<repo> (unchanged)
Oyzu's own providers (Node, Go, Rust, ...)oyzu:<name> (oyzu:go)go, and the earlier core:go
  • Curated names. The curated set is the proposed launch set (platform governed-tool-catalog-coverage.md, section C), each named by its primary name in the pinned mise catalog, except cli/cli, which is oyzu:gh (mise calls it github-cli; both short names install it). It is built into the client (src/tools/development_backend/names.rs), so curated names resolve without the network. A name that would collide with an Oyzu provider (kubectl, helm, k3d) or an admitted Cargo helper is not curated; those packages keep their owner/repo id. The public tool index is expected to supply these names later.
  • aqua: is an input alias. aqua:<owner>/<repo> is accepted wherever an id is (commands, [tools] keys, policy) and rewritten; Oyzu never writes it. Installing a tool that is declared under an aqua: or core: key moves the declaration to the new key.
  • Origin is provenance. Each lock resolution records the registry package in its components (package:<owner>/<repo>), next to registry: and tag:.
  • Earlier locks. A lock written with aqua: or core: ids is stale. oyzu install reports TOOL_LOCK_STALE naming the rename; oyzu install --update drops those pins and re-pins the same tools under their oyzu: ids, re-reading each publisher checksum (exact versions resolve to the same archives and digests). oyzu install --frozen fails until then. [tools] keys written as aqua: keep working and are not rewritten by --update.

Short names​

oyzu install gh@2.49.2 works as in mise: a short name that Oyzu neither provides nor curates is looked up in the catalog and expands to the first backend in its entry that Oyzu supports (aqua:cli/cli), which is then stored under its canonical id (oyzu:gh). oyzu:gh is looked up the same way.

$ oyzu install gh@2.49.2
$ cat oyzu.toml
[tools]
"oyzu:gh" = "2.49.2"

The catalog is the registry/*.toml data of the mise crate release 2026.10.5 (MIT), downloaded at run time from static.crates.io, checked against a pinned SHA-256 and cached as <store>/catalogs/mise-registry-<digest>.crate (re-checked on every read; offline use works once cached). None of it is stored in this repository, no mise code is compiled or run, and a core tool name that Oyzu already admits (node, go, ...) keeps resolving to Oyzu's own provider. Catalog short names are accepted by oyzu install; other commands and [tools] keys take a curated name or the canonical id.

SituationResult
Unknown nameTOOL_NAME_UNKNOWN, naming the explicit oyzu:<owner>/<repo> spelling
Listed only under backends Oyzu lacks (cargo:, npm:, asdf:, ...)TOOL_BACKEND_UNSUPPORTED, listing them
Catalog cannot be fetched / digest differsTOOL_REGISTRY_UNAVAILABLE / TOOL_REGISTRY_DIGEST_MISMATCH

Requests​

RequestMeaningNeeds the release listing
3.54.0 or v3.54.0Exactly this releaseNo
latestNewest stable release the recipe coversYes
2.49Highest stable 2.49.x the recipe coversYes

An exact version tries the tag spellings <version_prefix>v<version> then <version_prefix><version> and takes the first whose checksum file exists, so pinned installs make no GitHub API request and cannot hit its rate limit. The release listing uses GitHub's releases API for the newest 300 releases. Set GITHUB_TOKEN to raise the anonymous limit; it is sent to api.github.com only. Drafts are never offered; pre-releases only when named exactly.

The lock retains the original request and a concrete normalized release. Its validation uses the package selector's same exact-tag, version-prefix and stable latest rules; it does not compare the word latest literally with the selected version or consult a mutable release listing. An incompatible version or damaged resolution identity is still refused. Raw tags must agree with the normalized version; ambiguous numeric suffixes are refused. Registry tag prefixes ending in a digit are not qualified by this matcher.

What is installed, and from where​

  • Registry. One pinned snapshot, aqua-registry v4.573.0 (SHA-256 52a43b0b…0228), fetched from raw.githubusercontent.com, checked against that digest, and cached in the tool store at catalogs/aqua-registry-<digest>.yaml (re-checked on every read). A different snapshot is a reviewed source change. No registry data is copied into this repository or the binary.

  • Resolution. Declaring or updating a tool evaluates the recipe for every default platform (linux/amd64/gnu, darwin/arm64/native, windows/amd64/msvc) with the recipe evaluator, reads the publisher's checksum file, and writes one lock resolution per platform. A platform with no build is recorded as unavailable, as for other tools.

  • Recipe types. type: github_release (the asset of a GitHub release) and type: http (a direct download URL the recipe renders, such as https://releases.hashicorp.com/... or https://storage.googleapis.com/...). Both resolve exact versions without the release listing: the tag spellings above are rendered into the URL and checksum URL, and the first whose checksum file exists is taken. Other types (go_install, cargo, github_content, ...) are refused with SOURCE_KIND ("not a release download"); nothing is installed.

  • Packaging. The recipe's format decides how the download is unpacked:

    formatInstalled as
    tar.gz, tgzgzip tar
    tar.xz, txzxz tar (pure-Rust decoder, lzma-rust2)
    tar.zstzstd tar, concatenated frames included (the ruzstd decoder Oyzu already uses)
    tarplain tar
    zipZIP32
    raw (or an asset with no archive extension)the asset is the executable: it is stored under the first command's name (<name>.exe on Windows) and marked executable off Windows; as in aqua, files[].src is ignored and every declared command runs that file

    Every tar kind is streamed through the same bounded extractor (entry, size, depth and a 200:1 expansion limit). Other formats (tar.bz2, tbz, single-file gz/bz2/xz/zst, 7z, dmg, pkg) are reported as TOOL_ARCHIVE_UNSUPPORTED, naming the supported list.

  • The lock is the pin. Each resolution holds the archive URL and SHA-256, and in components the facts install needs: kind: (one of the kinds above, as the evaluator's layout kind: tar.gz, tar.xz, tar.zst, tar, zip, raw), bin:<command>=<path in the archive>, tag: (the release tag) and registry: (the snapshot digest). This reuses the existing components field; no schema changed. A locked tool restores and runs without the registry, and oyzu install --frozen into an empty store needs only the pinned archive URLs.

  • Download. Only the host archive is downloaded and its SHA-256 must equal the locked value. Hosts: GitHub's release hosts and the registry file are fixed. A recipe that downloads from elsewhere (for example a vendor's release server) has that host admitted from its pinned URL: HTTPS on port 443, a public DNS name only (no IP literal, single label, or .local/.internal- style name), no credentials. A tool route configured for registry packages is refused (TOOL_ROUTE_UNSUPPORTED) because routing for this backend is not connected.

  • Commands. The executables a recipe declares (files) become the tool's commands; a recipe without files gets one command named after the last segment of the package name (kubectl for kubernetes/kubernetes/kubectl), as in aqua. On Windows .exe is completed as the registry does (complete_windows_ext). When a package has several commands, every one is an entry point (oyzu exec -- <command>), each distinct command file must exist after unpacking and is marked executable, and each distinct command directory is put on PATH for child processes, the primary command's directory first. The primary command is the first by name, not by recipe order. Several names may share one file (superfly/flyctl declares flyctl and fly, both flyctl): each name runs through oyzu exec, but only the file's own name is found by a child process searching PATH, because Oyzu does not create links in the installed tree.

Verification​

Install verifies the publisher's SHA-256 checksum: the lock records the checksum the recipe's checksum file lists for each platform, and the downloaded archive must equal it. A per-asset checksum file whose whole body is one digest with no file name (dl.k8s.io's kubectl.sha256) is read as that asset's digest, as aqua does. This is the check the open-source backend performs today.

Recipes may declare more (GitHub artifact attestation, cosign, SLSA provenance, minisign). Those checks are not performed yet and do not stop an install; for example oyzu install oyzu:gh@2.102.0 installs on its checksum even though the recipe also declares an attestation. tools info says so. A later milestone can add the verifiers, and a stricter, curated backend can require them; neither is part of this one.

What the lock cannot hold yet is reported instead of installed:

CodeCause
TOOL_CHECKSUM_MISSINGThe recipe declares no checksum to lock and the package is not on the GitHub-reported digest allow-list
TOOL_CHECKSUM_UNSUPPORTEDThe recipe's checksum is not SHA-256 (the lock records SHA-256 only) or its checksum file is regexp format
TOOL_CHECKSUM_UNVERIFIABLEThe checksum file does not list the archive, or lists conflicting values

GitHub-reported digests​

A recipe that declares no checksum normally cannot be locked. For a short, curated allow-list of packages Oyzu instead locks the SHA-256 GitHub reports for the release asset the recipe downloads from the package's own repository (the evidence github: packages use). The list is GITHUB_DIGEST_ALLOWED in src/tools/development/aqua.rs; it currently holds protocolbuffers/protobuf/protoc, the one recipe proven end to end. The fallback is deliberately not available to every checksum-less recipe, because that would loosen acquisition checks for tools nobody reviewed. Any other checksum-less package reports TOOL_CHECKSUM_MISSING; for a tool a builder merely detected that is an attention row and the build continues, for an explicit pin it is an error.

To add a package: open a PR that adds its registry name to the list, with a test or proof that the recipe downloads from the package's own GitHub releases and that GitHub reports a digest for the asset, and the rationale in the PR. Review of that entry is the approval; see third-party compliance for the notice rules that apply to any new tool.

A successful install means the archive equals the checksum the publisher listed at resolution time; it does not prove the publisher or the checksum file is authentic.

TOOL_RECIPE_UNSUPPORTEDThe recipe uses a construct the evaluator does not implement; see recipe resolution
TOOL_REGISTRY_UNAVAILABLE / _DIGEST_MISMATCHThe pinned snapshot could not be fetched, or its bytes differ from the pin

tools versions and tools info​

tools versions oyzu:<name> lists the newest releases, newest first, evaluated for this host. A release the recipe does not cover, has no build for this platform, or whose verification this build cannot perform appears under excluded with its reason, so the list shows what install would accept. tools info shows provider, source, commands (after the tool is locked), platforms, eligibility under tools.allowed, declarations and the verification rule. Both support --json.

Limits and known gaps​

  • Linux x86-64 only has been run. Windows and macOS behavior (including the .exe completion, raw .exe assets and zip extraction) is covered by unit tests only.
  • Archives: tar.gz, tar.xz, tar.zst, tar, zip and raw executables. Not tar.bz2 (41 registry entries; no bzip2 decoder is in the build), single-file gz/bz2/xz/zst executables, 7z, dmg or pkg. Only SHA-256 checksum files. Attestation, cosign, SLSA and minisign checks that recipes declare are not performed.
  • A command name that differs from its file's name (an alias such as flyctl's fly) runs through oyzu exec but is not on the child PATH.
  • Option tables honor only version; unknown options warn and remain inert. The other mise backends are not implemented (github: is separate and experimental; see tool-github); catalog short names resolve only to aqua registry entries and only for oyzu install.
  • A hand-written declaration with no lock entry needs oyzu install <id> or oyzu install --update to resolve; plain oyzu install reports TOOL_LOCK_STALE, for the string form and table form alike.
  • The snapshot is fixed per build; customer registries and a floating registry are not supported.
  • A configured tool route is refused rather than honored. Version listing needs GitHub's API.
  • The evaluator is independent and unverified against the registry's own engine beyond observed recipes; vars and musl builds are unsupported.
  • Registry packages are admitted by their well-formed id, so tools.allowed matches the canonical oyzu: id; how an aqua: entry in that list is read was not exercised. Behavior of that policy for registry packages was not exercised (the setting is managed-scope only).

Verification​

python tooling/test-tool-aqua-install.py --cli <oyzu> --workspace <dir> drives the compiled CLI against the pinned registry and real publishers; unit tests live in src/tools/development/aqua.rs, acquisition.rs and declare/spec.rs; tests/integration/recipe_resolve.rs covers rejected specs. Archive kinds are unit-tested in src/tools/store/archive.rs (xz, single- and multi-frame zstd), option tables in src/config/registry.rs and src/config/edit.rs. The 2026-10-10 live runs of tar.xz, raw, http and multi-command packages and option tables are in the qualification record. Results: qualification record.
