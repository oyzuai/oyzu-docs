Oyzu's BuildKit frontend

CLI reference

Published from the canonical docs/reference/docker-frontend.md file. Features marked experimental remain experimental; check support limitations before relying on them.

docker/image builds run every Dockerfile through oyzu-buildkit-frontend, a BuildKit frontend that ships in the Docker plugin package. It runs the standard Dockerfile frontend of BuildKit v0.34.1 (the version its Go module pins) unchanged and adds two things: an approved list for Dockerfiles that request their own frontend with # syntax=, and a way to inject files into RUN steps. You normally only meet it when a Dockerfile starts with # syntax=.

Oyzu loads the frontend from an OCI layout in the plugin package (share/buildkit-frontend), never from a registry. Preparation copies the layout into the prepared dependencies, which the BuildKit worker mounts at /oyzu-docker. A different plugin package changes the frontend and therefore the build plan.

Using a # syntax= frontend​

A Dockerfile whose first line is # syntax=<reference> builds only if that reference is on the docker.frontends list (see configuration). Every entry must be pinned by digest:

# oyzu.toml, user or managed configuration
[docker]
frontends = ["docker/dockerfile:1.17@sha256:<index digest>"]

A request matches an entry when it has the same repository (docker/dockerfile and docker.io/docker/dockerfile are the same) and either the same digest, or the same tag if the request names no digest. An untagged request means latest.

Oyzu copies the approved frontend image from your local Docker engine, for the build's platform, and loads it by digest. It never resolves the tag again.

Anything else fails during preparation, before a worker starts:

FRONTEND_NOT_APPROVED: Dockerfile requests frontend docker/dockerfile:1, which is not on the approved list; approved: docker/dockerfile:1.17@sha256:...

An entry without a digest fails with CONFIG_INVALID_VALUE. Oyzu never ignores the # syntax= line or substitutes its own frontend.

Oyzu still parses the Dockerfile with the plugin's pinned BuildKit parser during preparation. Syntax that parser does not understand fails even if the frontend you requested would accept it.

Injecting files into RUN steps​

When a build plan carries injection files, the frontend gives every RUN step:

  • a read-only mount of those files at /oyzu-inject, and
  • APT_CONFIG and SSL_CERT_FILE set to the named files inside it (a RUN's own value for either variable is replaced).

The mount and variables exist only while that step runs. No layer, image configuration entry or history line carries them, and the base image keeps its digest. Your Dockerfile is not edited. A RUN that mounts something at /oyzu-inject fails because the path is reserved.

Nothing in Oyzu supplies injection files yet, so builds currently run without injection and RUN steps are unchanged.

Limits​

  • Injection reaches only RUN steps. A requested frontend's own planning steps (for example, reading a file from a stage) run before Oyzu rewrites its graph and do not see the mount.
  • The frontend follows the Dockerfile frontend of the BuildKit release its Go module pins. Updating it means releasing the Docker plugin again.
  • Generated image recipes (such as Python containers) use BuildKit's built-in dockerfile.v0, not this frontend.
  • A Docker plugin package built without its Linux helpers has no frontend and fails preparation.
