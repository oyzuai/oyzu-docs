Artifact version inference

CLI reference

Published from the canonical docs/reference/version-inference.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Version inference is being connected to the captured build path. The current increment supports Cargo, Node and Helm package snapshots from native SemVer, exact local tags, nearest first-parent release tags and Conventional Commit impacts. Full OEP-0013 release/candidate operation authorization is not implemented. Go applications and Docker images use the same tag/bump inference without requiring a native version. Python maps compatible native PEP 440 versions into the same logical inference, then encodes the result for its wheel, source archive and application artifact. Maven, Gradle and Ant now consume the shared resolver through native JVM metadata.

Usage and prerequisites​

Run oyzu build in a supported project with its existing native inputs and the corresponding provisioned build image. No new Oyzu configuration is required. Git must be available on the host. Git metadata is observed locally before native preparation; no automatic fetch occurs. An exported directory without Git uses native source snapshots, or 0.0.0 snapshots when the builder has no native application version. See Rust builds and build verification for native preparation and execution prerequisites. The implementation uses portable Git subprocesses; cross-host acceptance is pending.

An ordinary single-package repository at version 1.4.2, with ancestor tag v1.4.2 and a subsequent feat: add endpoint commit, resolves the next base to 1.5.0. Artifacts receive 1.5.0-dev.g<12-character-source-hash>. The suffix remains content-derived, not the Git commit SHA. No wall-clock counter is used. Artifact digests, not version strings, identify final bytes.

Versions finalized after hooks (captured Node builds, OEP-0011 handoff K2). For a target with a pre_build hook that declares outputs, the hash covers the target's source scope without the hook's own script plus the digest of the files the hook wrote under its declared outputs. The hook therefore counts as a generator: editing its script without changing what it writes keeps the version, and a change in what it writes changes the version and the package. The script stays in the hash when a builder stage reads or writes it, or when it is not named as an argument of the hook's command. plan.json records the pre-hook source version (the hash without the hook output), which the actions before the hook run with; the final version is recorded in the target's post-hook plan (plans/<target>.post-hooks.json) and the manifest. See hooks as always-run actions. The same version results with and without --no-cache. Other builders, other hook phases and the native host path keep the plain source hash.

Final-command development scope​

On the captured Unix executor path, a target can refine its development source suffix after preparation and final command selection. Every selected command must have a complete, bounded, confinable stage contract and remain cacheable. The source membership is the union of shipping-command reads, declared inputs, and configuration/build/lock paths captured by their existing inventory owners. Check-only reads can leave the version scope only when their complete writes cannot reach a shipping read, directly or through another check.

This is a positive native read boundary: unowned shared files need a consumer instead of changing every eligible target's version. Literal optional reads stay in the boundary while absent, so creating the file changes its consumers' source suffix. Source identity and native dependency captures remain whole-tree facts.

The existing builder version-revision and plan compiler bind the revised version before execution, including independent target branches. Membership and command contracts must remain stable when the plan is rebuilt; otherwise the original plan, dependencies and versions remain together. Acquisition is not repeated. Reuse-disabled execution retains the same private views and source boundary.

Windows, unsupported host paths, cross-target prerequisites, hooks, authored replacements, projected sources and materialized artifact inputs retain their established conservative scope. Missing captured control provenance or incomplete command evidence also keeps that scope. Existing hook finalization remains a separate supported path. The connected shared-source candidate is still awaiting its unchanged Linux acceptance run; see the qualification record.

Resolution and evidence​

The default is auto. An optional ordinary setting in oyzu.toml selects one of four fixed strategies; this is not an expression language:

[version]
strategy = "tags"
StrategyBase selection
autoReconcile native metadata, exact tags, nearest stable tags and Conventional Commit impacts; fall back to native metadata or 0.0.0 when history cannot supply a baseline
nativeUse the native version and ignore tag/bump selection; fail if the project has no native version
tagsUse an exact applicable tag, otherwise the nearest stable first-parent tag; do not infer a bump or require native metadata to match
conventionalUse the auto reconciliation rules, requiring complete history and an applicable baseline or exact tag; reject unclassified relevant commits after the baseline

All four still generate source snapshots. A strategy never changes publication or signing authority. The setting follows the normal configuration cascade, profiles, local-override eligibility and administrative constraints. Builders consume the frozen effective value, and it participates in computation identity. Omit the setting for existing behavior. Unknown values fail configuration validation.

version-needs-native, version-needs-tags and version-needs-history identify missing strategy inputs. Supply the native declaration or complete local Git history/tags, or select a suitable strategy. version-unclassified-commits requires clarifying commit intent or selecting a less strict strategy. For native version schemes without a supported logical mapping, auto and native retain native snapshots; tags and conventional fail with unsupported-version-strategy.

What history is read, and when​

Git history is observed once per repository per build, shared by every target in it. How much commit detail is read depends on what can change the result:

  • Bounded (CI, --full, a ci profile, and the tags and conventional strategies). Commit messages and changed paths are read only for commits after the oldest of every tag subject's nearest stable first-parent release tag. Resolution excludes ancestors of each baseline, so older history cannot change a decision; the bounded read gives the same decisions as reading everything (tested against the full history, including merges and subject-scoped tags). Without any stable release tag no baseline exists and no commit detail is read. A shallow clone is read as it is.
  • Head only (local fast builds on the default auto strategy, and native). The head commit, prefix, shallow state and tag list are still recorded, and an exact tag on the built commit still sets the version, but no commit messages are read. The version falls back to the native version (or 0.0.0) plus the source suffix, with reason native-fallback-local-history-skipped and historyComplete: false; the history record's traversal is head-only. Use --full, the CI context or an explicit tags/conventional strategy for the commit-driven version a release build would stamp. A local artifact's version can therefore differ from CI's for the same commit.

The first applicable stable tag walking first-parent ancestry is the baseline. Merged commits still contribute declared impacts: breaking change, feature and fix choose the maximum major/minor/patch increment once. Other conventional types have no bump. Unclassified relevant commits are retained in evidence; this increment never claims sufficient release evidence. A native version already ahead of the baseline is retained if it meets the computed minimum. Incompatible exact tags, ambiguous versions on one tagged commit and insufficient explicit version advances fail with version-conflict or ambiguous-version-tags diagnostics. Correct the native declaration/tag intent and rerun; the builder never edits checkout metadata.

Exact local tags still produce source snapshots and cannot authorize publication. They do name the release: oyzu publish reads the exactTags a published build records as its GitHub release tag, so the version and the release tag come from the same fact and no tag is committed. Builds of one destination must agree, and oyzu publish --tag overrides; see which release. Only a tag that applies to the package is recorded (the tag namespace rules below): an unscoped v1.4.0 on a member of a multi-package Cargo workspace records nothing, so such a release passes --tag. Artifact records of the Rust builder and Node workspace package archives carry extensions["oyzu.dev/versioning"].package, naming the package whose decision they come from. An RC tag matching a stable native core retains its prerelease label in the snapshot. Shallow history conservatively falls back to native source snapshots with an explicit reason; users can provision complete history before retrying. No network request is made to repair history. An unresolvable repository error is reported rather than being interpreted as an unversioned export.

Cargo evaluates original metadata and then projects inferred versions and local package references only in its private preparation tree. Node managers capture native package/workspace facts and project the same decisions during isolated execution, including the root and member package metadata and local references. The native package version, planned coordinate and collected artifact version agree. Build output explains each package decision. Target records in dist/plan.json and dist/manifest.json retain extensions["oyzu.dev/versioning"]: native version, resolved base/version, source digest, commit, baseline tag/commit, exact tags, contributing/unclassified commits, history completeness, reason, algorithm strategy, configured requestedStrategy, snapshot intent and denied production eligibility. These are local observations, not authenticated source-control facts.

The plan and manifest also retain extensions["oyzu.dev/version-history"], keyed by build target. Each entry contains a digest and the captured local history record: HEAD, repository prefix, shallow status, local tag names/object IDs/peeled commits, annotated-versus-lightweight identity, and reachable commit parents/messages/paths. Decisions reference this record through historyDigest and record first-parent baselineDistance and scoped analyzedCommits. The plan digest binds these inputs. The record labels remote freshness unknown and verification local-observation; a full local clone is not proof of the remote tag inventory. Failed preparation retains any history already captured in the failed manifest. History records include commit messages and paths; treat bundles as repository information when sharing.

Helm projects the root chart version in private preparation; appVersion and dependency chart versions keep their native meanings. Go uses inferred versions for application artifact names and the manifest; it does not inject a version variable into compiled application code. Docker uses the version in the OCI archive name, exported image reference and manifest. Go and Docker record nativeVersion: null: an exact tag supplies their base, while an ancestor tag supplies the baseline for impact analysis. Without either, the base is 0.0.0. Go resolves each native workspace module independently using captured import and test-import edges. Directory-scoped tags supply module baselines, binary coordinates use their owning module's decision, and module zip/mod/info outputs retain native v prefixes and RC snapshot qualifiers. A path-major fallback is permitted only without a selected version baseline; incompatible explicit versions fail native module validation. See Go versions.

Python's native packaging.version.Version supplies normalized facts; the shared resolver does not parse PEP 440. Stable versions with up to three release components and alpha/beta/RC versions can participate in SemVer tag inference. For example, base 1.5.0-rc.2 becomes 1.5.0rc2.dev0+g<source-hash>. Unrepresentable tag prerelease labels fail rather than losing their qualifier. Native epochs, postreleases, existing development versions and longer release tuples retain a native snapshot with reason native-ecosystem-source; Git bump inference for those version schemes is pending. Snapshots use development counter zero and replace original local labels with source identity; the original normalized native version remains recorded. The native parser's version API owns normalization and validity.

Static PEP 621 pip/uv/Poetry projects project the selected version in their private pyproject.toml. A project that lists version in project.dynamic has no native version during preparation: its base comes from tags (or 0.0.0) and maps to a PEP 440 snapshot, which the private pyproject.toml receives as a static version; see dynamic versions. Legacy setuptools captures native facts offline, then projects the version through its distribution metadata. Its sdist stages a generated setup.py wrapper containing the original program and a fixed version override so rebuilding the source archive retains the artifact's version. Checkout sources and the source used by test/quality tasks remain unchanged. The wrapper supports native setuptools and distutils setup entry points; arbitrary custom distribution construction is not a qualified version provider. Requirements-only applications have no native version and retain SemVer application coordinates, including tag inference. Python dependency captures use adapter layout version 2; recreate older captures for version evidence.

JVM preparation removes the conventional native -SNAPSHOT suffix when the remaining value is SemVer, while retaining the original declaration in evidence. Other native version forms keep their existing base and receive a source snapshot with reason native-ecosystem-source; arbitrary Maven/Gradle qualifiers are not silently reinterpreted as SemVer. Gradle's unspecified version permits a tag-derived base. Ant retains its native metadata adapter's 0.0.0 fallback when no version property exists.

Maven and Gradle first capture native models in an isolated preparation worker. The host resolves versions and writes a frozen version-plan.json; native tooling then applies it in the same private workspace before dependency capture is frozen. Maven makes inherited module versions explicit using its native raw model writer in the private copy, then uses the versions plugin for module/parent/dependency projection and checks the resulting reactor coordinates. Gradle uses project directory identities across the root and included builds; archive tasks consume each selected version again during offline execution. Ant reevaluates its native model using the selected version properties and records the version in the exported JAR manifest.

Maven modules use unique artifact IDs as tag subjects, or groupId.artifactId when artifact IDs collide. Gradle projects use unique native names, or project directory paths when names collide. Root tags are admitted only for a single native project; multi-project builds use scoped tags such as library/v1.4.2. Equal native versions alone do not imply a coordinated group. Maven captures local upstream projects from the native reactor graph, including reactor parent relationships. Gradle captures resolved project-component identities across root and included builds, using native build-tree paths to distinguish projects. Both feed the same transitive input-scope resolver as Cargo and Node; no dependency resolver is recreated in Rust. Gradle resolves these edges only during captured preparation/execution, through its existing repository boundary. Lightweight host metadata observation does not resolve them. Unresolved Gradle graph results fail preparation rather than omit a dependency. This requires the provisioned Gradle 8.14.3 profile and the current Maven metadata extension. Reprovision an older Maven image if native reactor edges are missing. Maven/Gradle dependency adapter layouts are now 4/3 respectively; older captures must be recreated. Coordinated inherited-version release groups remain unfinished.

Independent Cargo and Node members admit package-name tag namespaces. Unscoped root tags are used only for a single Cargo workspace package or standalone Node package at the Git repository root. Cargo and Node use captured native local dependency edges to compute each member's transitive input scope before commit analysis. Development, build, optional and peer edges participate when represented by the native model; this is conservative build-input impact, not a claim that every dependency change changes the consumer's public API. Cycles form a finite input closure and do not imply that packages share a release version.

For example, with app -> bridge -> shared and a separate independent package, a feat changing only shared advances the first three bases from 1.4.2 to 1.5.0; independent remains 1.4.2. Each package evaluates impacts against its own scoped baseline. Native packaging projects each dependency's chosen version into the consumer's metadata, even when their versions differ. Checkout manifests and locks remain unchanged.

The most specific native member directory owns a changed path. Paths outside member directories, such as workspace manifests, lock files and root build inputs, count as shared inputs for all members. This deliberately favors conservative impact over guessing file imports. The decision's inputScope records selected directories and workspaceDirectories, making the scope inspectable. A root package does not implicitly own every sibling member; its declared local edges select those inputs. This does not yet infer undeclared cross-member imports, Oyzu task-input closures across separate targets, or coordinated release groups. Other builders' native dependency closures and explicit tag namespace settings remain unfinished.

Remaining scope and verification​

The implementation finish line is recorded in the audited completion checklist. It distinguishes missing functional behavior and its acceptance evidence from broader compatibility, hardening and the separate publication implementation.

Native dynamic version providers beyond the captured native adapters, verified CI release/candidate versions, provider evidence, history acquisition, remote tag inventory verification and destination-specific mappings are pending. No release or publication capability follows from this increment.

Each compares plan/manifest versions, checks required reports and preserves checkout metadata. Go/Docker also exercise an exact tag without native version metadata, verifying that it still produces a snapshot. --builder python, python-uv, python-poetry and python-legacy inspect wheel METADATA and sdist PKG-INFO; python-pip checks the requirements application's embedded manifest. The native legacy probe separately rebuilds a wheel from the sdist offline and executes the installed artifact. java-ant, java-maven and java-gradle exercise Ant, a Maven reactor and a Gradle composite respectively, checking versioned artifacts, native Maven/Ant embedded metadata, module decisions and collected reports. Gradle archive filenames/coordinates are checked; arbitrary JAR manifest attributes remain native Gradle behavior. Native workspace inference and pnpm/Yarn packaging use the workspace probe below; measured results and remaining manager limitations are recorded in implementation status. Unit checks cover real Git ancestry, merged features, exact-tag conflicts and bump selection. Results are recorded in implementation status after execution; this description alone is not acceptance evidence.

tooling/test-workspace-version-inference.py --builder node|rust --cli <compiled-cli> --evidence-dir <new-directory> exercises dependency changes, a separately changed member and a shared root input through real scoped-tag repositories. It checks independent native archive versions, rewritten local dependency references, plan/manifest scopes, reports, bundle inspection and unchanged checkout metadata. For Node, --manager npm|pnpm|yarn selects the native lock and packaging flow (npm is the default). pnpm and Yarn locks are generated offline using the explicitly provisioned host manager before capture; Node fixture sources are formatted with the provisioned native Prettier. The corresponding build images must also be provisioned. This is test setup, not installation during a build.

The same probe accepts --builder java-maven|java-gradle --scenario dependency-feature for a Maven reactor or Gradle composite. It adds an unrelated module and scoped tags, changes a shared library, then checks consumers' inferred versions and unchanged unrelated bases. Maven checks seven POM/JAR artifacts, embedded package versions, parent and local dependency references; Gradle checks four versioned JARs, including the included build. Both check recorded scopes, reports, bundle inspection and unchanged native source files. This representative JVM acceptance does not claim the later independent-fix/shared-root scenarios have been executed on those managers.

Third-party impact​

The resolver uses semver 1.0.28, already present in Cargo.lock and now a direct dependency. Its registry source declares MIT OR Apache-2.0, Rust 1.68, and includes LICENSE-MIT and LICENSE-APACHE. No upstream source is copied or modified and no license alternative or distribution approval is selected. The factual compliance baseline tracks the direct dependency; release audit obligations remain unchanged.
