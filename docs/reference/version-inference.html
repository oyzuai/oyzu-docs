Artifact version inference

CLI reference

Published from the canonical docs/reference/version-inference.md file. Features marked experimental remain experimental; check support limitations before relying on them.

oyzu build works out a version for every artifact from your native version declarations, your Git tags and your Conventional Commit messages. You don't configure anything: build as usual and each artifact gets a version that says which release it's heading for and exactly which source it came from.

Supported builders: Cargo, Node (npm, pnpm, Yarn), Helm, Go, Docker, Python, Maven, Gradle and Ant.

Example​

A single-package repository declares version 1.4.2, has the tag v1.4.2, and one newer commit feat: add endpoint. oyzu build resolves the next version to 1.5.0, and artifacts get:

1.5.0-dev.g<12-character-source-hash>
  • The suffix comes from the content of the build's source files, not the Git commit SHA. There's no counter or timestamp, so the same source always gives the same version.
  • The suffix is the same on every platform. It covers file paths and contents but not the executable bit, which Windows can't see, so a Windows build and a Linux build of one commit get the same version. (Action-cache keys still include the bit, because changing it can change what a command does.)
  • Artifact digests, not version strings, identify the exact bytes.
  • Every ordinary build produces a snapshot version like this. Only release staging produces exact release versions.

Usage and prerequisites​

  • Run oyzu build in a supported project. No Oyzu configuration is needed.
  • Git must be on the host. Oyzu reads your repository before the build starts.
  • If history is missing (for example in a shallow CI clone), Oyzu can fetch it read-only.
  • A folder exported without Git uses the native version, or 0.0.0 when the builder has no native version, plus the source suffix.
  • Oyzu never edits your checkout. Inferred versions are written only into the private copies of manifests used for the build.

Resolution and evidence​

Choose a strategy in oyzu.toml if the default doesn't suit you:

[version]
strategy = "tags"
StrategyHow the base version is chosen
auto (default)Combine the native version, exact tags, the nearest stable tag and commit impacts. Fall back to the native version or 0.0.0 when history can't supply a baseline.
nativeUse the native version. Ignore tags and commit bumps. Fails if there's no native version.
tagsUse an exact tag on the commit, otherwise the nearest stable tag. No bump is inferred and the native version doesn't have to match.
conventionalLike auto, but requires complete history and a baseline or exact tag, and rejects relevant commits that aren't Conventional Commits.

Every strategy still produces snapshot versions, and none changes who may publish or sign. The setting follows the normal configuration cascade, including profiles and administrative constraints. Unknown values fail validation.

How the version is computed​

  • The first stable tag that applies to the package, walking first-parent history, is the baseline.
  • Commits after it (including merged ones) bump the version once, by the largest impact: a breaking change bumps major, feat bumps minor, fix bumps patch. Other Conventional Commit types don't bump.
  • A native version already ahead of the baseline is kept if it's at least the computed minimum.
  • An RC tag matching a stable native version keeps its prerelease label in the snapshot.

Exact tags and publishing​

An exact tag on the built commit still produces a snapshot version and doesn't allow publishing by itself. It does name the release: oyzu publish uses the exactTags a build records as its GitHub release tag, so the version and the release tag always agree. Builds for one destination must agree, and oyzu publish --tag overrides it. See which release.

Only tags that apply to the package are recorded (see tag names). For example, an unscoped v1.4.0 on a member of a multi-package Cargo workspace records nothing, so publishing it needs --tag. Artifacts from the Rust builder and Node workspace packages carry extensions["oyzu.dev/versioning"].package, naming the package their version came from.

What is recorded​

Each target in dist/plan.json and dist/manifest.json has extensions["oyzu.dev/versioning"] with the native version, resolved base and version, source digest, commit, baseline tag and commit, exact tags, contributing and unclassified commits, whether history was complete, the reason, the strategy used and the configured requestedStrategy.

Cargo keeps unselected workspace entries as native facts; they have no inferred tag or minimum-version obligation. When release subjects are recorded, selectedPackages identifies the selected scope, including complete fixed groups.

extensions["oyzu.dev/version-history"] records the Git facts each decision used: HEAD, the repository prefix, shallow status, tags (names, object IDs and commits), and the commits read (parents, messages, paths). Decisions point to it with historyDigest, and record baselineDistance and analyzedCommits.

These are local observations. They aren't authenticated source-control facts and don't make a build releasable. History records include commit messages and paths, so treat bundles as repository information when you share them.

Errors​

CodeCauseFix
version-needs-nativeThe strategy needs a native version and there isn't one.Declare the version natively, or pick another strategy.
version-needs-tags, version-needs-historyThe strategy needs tags or complete history.Fetch complete history and tags, or pick another strategy.
version-unclassified-commitsconventional found relevant commits that aren't Conventional Commits.Reword the commits' intent, or pick a less strict strategy.
unsupported-version-strategytags or conventional on a native version scheme Oyzu can't map. (auto and native keep a native snapshot instead.)Use auto or native.
version-conflict, ambiguous-version-tagsAn exact tag conflicts with the native version, one commit has two version tags, or the native version is too low.Fix the native declaration or the tags and rerun.

What history is read, and when​

Oyzu reads Git history once per repository per build. How much it reads depends on the build:

BuildWhat is read
CI, --full, a ci profile, or the tags / conventional strategyCommit messages and changed paths back to each package's nearest stable tag. Older history can't change the result. If an origin is configured and the build is online, Oyzu also fetches complete ancestry and a fresh tag list first.
Local fast build with auto, or nativeOnly the head commit, shallow state and tag list. No commit messages.

So in a local fast build with auto, an exact tag can still set the version, but otherwise the version falls back to the native version (or 0.0.0) plus the source suffix, with reason native-fallback-local-history-skipped and historyComplete: false. A local artifact's version can therefore differ from CI's for the same commit. Use --full, the CI context or the tags/conventional strategy to get the version a release build would use.

Acquiring missing history​

When a build needs history it doesn't have, Oyzu can fetch it read-only from a public https://github.com/owner/repository origin.

  • Credentials, SSH and file URLs, queries and fragments are refused. Plain HTTP is allowed only for loopback hosts. The administrative fetches.sources allowlist also applies.
  • Fetching is refused whenever organization management or registries.routes is in effect. Authenticated or managed Git connections aren't supported; provide complete history locally instead.
  • History is fetched into a private store under cache/git-history in the user data directory. Your checkout's refs, tags, index and commit are never touched.
  • A checkout that moves during the build, or a local tag that disagrees with the remote one, stops the build. Fetched tags never grant release permission.
  • --offline never fetches, but reuses earlier fetched history for the same origin and HEAD.
  • Local fast auto builds, native and --plan never fetch.

If history can't be fetched, auto keeps its snapshot fallback; tags and conventional stop before any build actions if their inputs are still missing.

DiagnosticCauseFix
SOURCE_DENIEDThe origin URL or fetches.sources doesn't allow this source.Use a credential-free HTTPS GitHub origin, or ask your administrator to allow it.
CONFIG_OVERRIDE_DENIEDOrganization management or registry routing is in effect.Provide complete history and tags locally.
HISTORY_INPUT_MISSINGOffline, with no earlier fetch for this origin and HEAD.Run once online, or provide complete history.
HISTORY_ACQUISITION_UNAVAILABLEThe source couldn't be reached or exceeded its limits.Restore access or provide complete history.
HISTORY_INTEGRITY_CONFLICTFetched or stored history failed validation. The build stops.Investigate, remove the bad stored copy and retry.
version-conflictLocal and remote tags disagree, or the checkout moved.Reconcile the tags and retry from a stable checkout.

The manifest records fetch outcomes and times in extensions["oyzu.dev/history-acquisition"]; they don't affect the version.

Each online fetch currently downloads a full fresh copy, even if an earlier one had the same objects, and old copies aren't cleaned up. This can add network and disk use to full builds.

Tag names in monorepos​

For Cargo builds, with.packages limits version inference and release staging to the named workspace packages. An unselected package's inferred minimum cannot block the build. Its native version remains unchanged in the private workspace; the complete workspace inventory still determines tag ownership and dependency input paths. Omitting with.packages selects the whole workspace. Changes to an unselected local dependency still contribute to the selected consumer's inferred minimum. That dependency keeps its native coordinate rather than acquiring a snapshot or release version from the consumer's build.

Selecting one member of an explicitly declared fixed release group selects that whole release subject and preserves its common-version requirements. Independent packages outside the selection are not staged, even if the event tag names one of them. A selected independent package uses its own native version and package tag, such as oyzu-plugin-go/v0.1.0; selecting it alone does not admit root tags.

  • A standalone package at the repository root, or a single-package Cargo workspace, uses unscoped tags such as v1.4.2.
  • Independent Cargo and Node members use package-name tags. Maven modules use the artifact ID (or groupId.artifactId when IDs collide). Gradle projects use the project name (or directory path when names collide). Multi-project builds need scoped tags such as library/v1.4.2.
  • Go workspace modules use directory-scoped tags.
  • Equal native versions never imply that packages are released together. For that, see Cargo fixed release subjects.

Dependencies between packages​

Within a workspace, a change to a package also bumps the packages that depend on it.

For example, with app -> bridge -> shared and a separate independent package, a feat that changes only shared moves the first three from 1.4.2 to 1.5.0; independent stays at 1.4.2. Each package is compared with its own tag, and each consumer's metadata gets its dependencies' chosen versions.

  • Dependencies come from the native model (Cargo and Node local dependency edges, Maven's reactor, Gradle's resolved project graph, Go imports). Development, build, optional and peer dependencies count. This is a cautious view of build inputs, not a claim about public API changes.
  • A changed file belongs to the most specific member folder that contains it. Files outside every member (workspace manifests, lock files, root build inputs) count for all members.
  • inputScope in each decision records the directories and workspaceDirectories used.
  • Oyzu doesn't guess undeclared imports between members.

Declared cross-target inputs​

Separate targets can depend on each other through depends_on, tasks and artifact relationships, and through inputs paths in build.yaml (including paths outside the producer's folder). A change in a producer can then bump its consumer's version against the consumer's own tag, without bumping unrelated targets.

  • Changed paths are matched against the build's recorded source selection, including your ignore overrides. Deleted paths count too.
  • Git paths are relative to the repository root, even in a nested workspace.
  • Decisions record inputScope.declaredPaths.
  • Inputs in a different Git repository fail with version-inputs-outside-repository.

This works for Node (isolated builds), and for native Go and Rust builds.

Final-command development scope​

For isolated builds on Unix, Oyzu can narrow a target's source suffix to the files its shipping commands actually read, so an unrelated shared file doesn't change every target's version.

  • It applies only when every selected command has a complete, confinable stage contract and stays cacheable.
  • The scope includes files the shipping commands read, declared inputs, and the configuration, build and lock files. Files only checks read are left out when the checks' outputs can't reach a shipping command.
  • An optional file that a command would read stays in scope while absent, so creating it changes the version.
  • Windows, native host builds, cross-target prerequisites, hooks, custom replacements and materialized inputs keep the full source scope. So does any target whose command details are incomplete.

Versions finalized after hooks​

For isolated Node builds, a pre_build hook that declares outputs counts as a generator.

  • The version hash covers the target's source without the hook's own script, plus the files the hook wrote to its declared outputs. Editing the script without changing what it writes keeps the version; changing what it writes changes it.
  • The script stays in the hash if a build stage reads or writes it, or if it isn't an argument of the hook's command.
  • plan.json records the version before the hook runs; the final version is in plans/<target>.post-hooks.json and the manifest. See hooks as always-run actions.
  • --no-cache gives the same version. Other builders and hook phases use the plain source hash.

Builder notes​

Rust (Cargo)​

  • Inferred versions and local package references are written only into Cargo's private build copy.
  • Full, CI, tags/conventional, optimized and distributed builds compile the inferred version into CARGO_PKG_VERSION.
  • Local fast development builds keep the declared Cargo versions so incremental compilation can reuse work, and record the actual compiledVersion beside the artifact version. --full alone doesn't change this. See local builds.
  • Executable names don't change.

Node​

  • The native package name and version from package.json drive the version, for isolated and native host builds alike.
  • With native, a package without a version fails before the build; add the version to package.json.
  • Native host builds never change package.json. Isolated builds write the version into private copies of the root and member manifests and their local references.

Native Node facts and host policy​

Node plugins report the native package name and version with their source path and digest. A target's alias is separate from the package name. The decision sets the plan version, the artifact file name and version, and the default OYZU_VERSION. The native compiled version may differ from the artifact's snapshot; both are recorded.

Helm​

The root chart version is written into the private build copy. appVersion and dependency chart versions keep their native meaning.

Go and Docker​

  • Go uses the version in artifact names and the manifest. It doesn't inject a version into compiled code. Docker uses it in the OCI archive name, image reference and manifest.
  • Both record nativeVersion: null. An exact tag supplies the base; otherwise an ancestor tag is the baseline for commit impact, or 0.0.0.
  • Go resolves each workspace module separately, using imports and test imports. Module zip, mod and info outputs keep native v prefixes and RC qualifiers. See Go native module artifacts.

Python​

  • Native PEP 440 versions are normalized by Python's packaging library. Stable versions with up to three components, and alpha, beta and RC versions, take part in tag inference. For example, base 1.5.0-rc.2 becomes 1.5.0rc2.dev0+g<source-hash>.
  • Epochs, post-releases, existing dev versions and longer version tuples keep a native snapshot (reason native-ecosystem-source).
  • Static PEP 621 projects (pip, uv, Poetry) get the version in their private pyproject.toml. Projects with a dynamic version take it from tags (or 0.0.0); see dynamic versions.
  • Legacy setuptools projects get the version through their distribution metadata. The source archive includes a generated setup.py wrapper so rebuilding it keeps the version. Custom distribution code beyond standard setuptools and distutils entry points isn't supported.
  • Requirements-only applications have no native version and use SemVer application versions.
  • Recreate dependency captures made by older Oyzu versions.

Maven, Gradle and Ant​

  • A trailing -SNAPSHOT is removed when the rest is SemVer. Other forms keep their value and get a native snapshot. Gradle's unspecified lets tags set the base. Ant falls back to 0.0.0 when there's no version property.
  • Maven and Gradle read native models in an isolated step, then apply the chosen versions in the private workspace. Maven writes module, parent and dependency versions; Gradle archive tasks use the chosen versions; Ant records it in the JAR manifest.
  • Requires the Gradle 8.14.3 profile and a current Maven image. Reprovision an older Maven image if reactor dependencies are missing. Recreate older dependency captures.
  • Releasing inherited Maven versions together isn't supported.

Cargo fixed release subjects​

Cargo workspaces can declare packages that always share one version, using cargo-release's shared-version setting:

  • shared-version = true joins the shared group.
  • A string names a separate group.
  • false opts out of an inherited group.

See Rust fixed version groups for an example, field precedence, and the supported tag-prefix and tag-name forms. Membership comes from all packages in the workspace, including private and unselected ones. Other ecosystems don't support fixed groups.

  • A change to any member bumps the whole group once, by the largest impact. A package that depends on a member sees that change too, while keeping its own tag.
  • Every member must declare the same native version, including qualifiers.
StrategyGroup behavior
auto, fast localCommon native snapshot, with exact group tags. No commit history read.
auto, full or CICommon exact tag or nearest stable baseline, and the combined commit impact.
nativeCommon native snapshot. Ignores tags and commits.
tagsNeeds a declared tag prefix and enough tags.
conventionalNeeds a tag prefix, complete history and Conventional Commits.
  • If no member declares a tag prefix, auto and native record a native snapshot with reason native-group-missing-namespace, and strict strategies refuse. A prefix on only some members is refused.
  • Non-native strategies reject conflicting per-package tags on HEAD or the baseline commit.
  • Private Cargo manifests, local requirements and the lock get the chosen versions. Your checkout isn't changed. Fast local builds report compiledVersion as usual.
  • extensions["oyzu.dev/version-subjects"] records the group, members, tag prefixes and resolution; each member's oyzu.dev/versioning entry points to it with releaseSubject.
  • --plan never runs Cargo or fetches history to fill in missing facts.

Fixed groups are supported on Linux x86_64.

Authenticated release staging​

Release staging builds exact release-candidate or stable versions, instead of snapshots, in a CI job triggered by a tag push. Request it explicitly with --require-release; ordinary builds retain snapshot coordinates.

Note: Release staging is experimental. It supports only a GitHub Actions job triggered by a tag push in the same repository. Cargo targets support Linux x86_64/arm64 (GNU or musl), Darwin x86_64/arm64 and Windows x86_64 MSVC. Plugin packages inherit their executable's staging. Staged versions are never marked production-eligible. Other builders and providers are unsupported.

oyzu -C app build app --require-release --full

The native version and the tag together choose the version. Native 1.5.0-rc.1 with a matching exact tag stages a release candidate; native 1.5.0 with its tag stages a stable release. Each needs a fresh build: renaming an RC archive doesn't make it stable. A native/tag conflict fails, and native doesn't let a tag override the native version.

OptionBehavior
(none)Keeps snapshot versions, including in a tag-event job.
--require-releaseMissing, offline, unsupported or contradictory evidence refuses the build before any build, check or package action runs.
--release-profile FILEAccept only the exact reusable workflow and source in this release profile.
--context release, OYZU_CONTEXTOnly set the context. They never authenticate a release.
--optimizedOnly chooses the build profile.
--planRead-only preview. Shows what evidence is missing.
--check --require-releaseReports missing release evidence as a blocking finding.

A staged build always runs every required check, including real test and coverage reports. A nested target can't turn those off.

Requirements​

  • Job permissions: contents: read, actions: read and id-token: write.
  • Oyzu requests a fresh GitHub OIDC token and checks the signed repository, ref, commit, workflow, run attempt and job against GitHub's API (using the job's GITHUB_TOKEN). CI variables, a local tag, a JWT file or OYZU_ID_TOKEN can't stand in for this.
  • The built files must match the tagged commit byte for byte, and the tag must stay the same until the build finishes. Unix also compares executable bits. Windows has no POSIX executable bit: the immutable Git tree supplies that identity, recorded as sourceFileModes: git-tree-no-posix-mode. Git's CRLF conversion is not applied to the comparison; use a byte-preserving checkout.
  • Refused: uncommitted changes, forks, the wrong job or attempt, a moved tag, repository hooks, Git symlinks or submodules in the selected source, and inputs outside the repository.
  • Reusable workflows need --release-profile, and both signed workflow claims must match.

The manifest records GitHub's answers and any unresolved reasons in extensions["oyzu.dev/release-staging"]. If a check fails, or the source or tag changes before the end, no final output is accepted.

A job token proves the job's identity and event. It doesn't prove where Oyzu ran, who built the artifact, that checks were correct, or that the build was isolated.

Cross-compiled Cargo checks​

Required tests and coverage run for the same selected Cargo packages and features on the prepared compiler's host triple, in the same build invocation. A positive passing native test result and all mandatory reports remain required; missing, skipped or failing checks refuse staging. Format and lint remain mandatory. --require-release disables action-result reuse so earlier runs' reports cannot satisfy this invocation. Native compiler caches can still accelerate the work; the test and check commands execute again.

The staging record's testEvidence names the packages, host and target triples, and report IDs. For a cross build, targetRuntimeTested is false. These host tests do not establish target-specific behavior, linking at runtime, or tests behind target-only conditional compilation. Run target-runtime qualification separately.

Plugin members and composed roots​

An oyzu/plugin-package member takes the exact version only from its staged executable artifact and package decision. Build each member with --require-release --full in the matching package tag event. For a Cargo workspace member, use its package tag namespace, for example oyzu-plugin-go/v0.1.0.

Composition with --compose ... --require-release needs every admitted member's staging record to agree on repository, tag, peeled commit, package and version. The current composing job must independently authenticate that same tag and source; saved member records never replace fresh GitHub evidence. The root records the exact version in its artifact, plugin metadata and OCI version annotation. Composition still enforces ordinary provenance, content integrity and platform completeness. Without --require-release, composition produces a snapshot and does not carry release staging.

When staging can't run​

If GitHub is unavailable or permissions are missing, a build without --require-release keeps snapshot versions. With --require-release it fails, naming the missing fact. Retry online in the matching job after fixing access. Saved manifests and earlier attempts can't authenticate a new invocation, and offline builds can't stage. Admitted staged members can be composed only after fresh authentication of the composing job.

ErrorRecovery
release-profile-unsupportedSelect a supported Cargo platform and remove repository hooks.
release-member-unstagedRebuild every executable and plugin member with --require-release --full.
release-member-mismatchRebuild members for one repository, package tag, commit and version.
release-required-checkRestore all mandatory checks and positive passing host test evidence in this invocation.
release-source-mismatch, release-tag-mismatchUse the members' unchanged tagged commit in the matching tag-event job.

Limits​

  • Release staging is limited as described above. No other CI providers, events, builders or platforms are supported.
  • Fixed release groups are Cargo-only.
  • Native version schemes Oyzu can't map to SemVer (some Python, Maven and Gradle forms) keep native snapshots and don't get tag or commit bumps.
  • History can be fetched only from public GitHub HTTPS origins.
