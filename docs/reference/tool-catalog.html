Organization tool catalog (toolCatalog)

CLI reference

Published from the canonical docs/reference/tool-catalog.md file. Features marked experimental remain experimental; check support limitations before relying on them.

An organization tool catalog lists the tools and versions your organization approves. Set toolCatalog when your organization runs a delivery edge (the server that publishes the catalog and serves approved downloads): Oyzu then installs registry packages and Oyzu's own providers (oyzu:java, oyzu:node, ...) only from that signed catalog.

Note: Experimental. Setting names, error codes and the catalog format may change. Supported on Linux x86-64 and Windows x86-64; macOS is not supported yet.

Platform scope: Use an x64 host and supported x64 build targets. ARM64 is unsupported. Feature-specific limits are listed in the support matrix.

Quick start​

Point Oyzu at the signed tool index and the delivery edge, and pin the edge's public signing key:

# ~/.config/oyzu/config.toml
[toolIndex]
url = "https://index.example.test/"

[toolCatalog]
url = "https://dl.example.test/"
keys = ["ed25519:7sb4o1W0lRKR712+E7DQ8uYEeTX2sUXSzJMTpKc0lzI="]

Put the organization token in OYZU_TOOL_CATALOG_TOKEN. Then:

  • oyzu tools versions <tool> lists the versions your organization approves.
  • oyzu tools check --catalog checks the declared tools the way an install would.
  • oyzu tools request <tool>@<version> asks for a version the catalog doesn't offer yet.

Purpose​

The catalog is the signed public tool index, narrowed to the approved versions, with each version's state and how its files are delivered. With a catalog configured:

  • Only approved versions resolve. Any other version fails before anything is downloaded.
  • A blocked or quarantined version fails with your organization's reason.
  • Oyzu only uses a catalog signed by a key in toolCatalog.keys.
  • The catalog can only narrow the index. An entry whose SHA-256 differs from the signed index is refused, so the edge can't substitute other files.
  • Files the catalog marks proxy download from the edge with the organization token. Files marked direct (for licenses that forbid redistribution) download from the publisher, and Oyzu still checks the catalog's SHA-256.
  • Oyzu doesn't fall back to local recipes, registry files, GitHub release lists or publisher APIs.
  • If the edge is unreachable, Oyzu uses the last good catalog for a limited time (toolCatalog.maxOfflineAge) and warns you.

Node's moving lts alias​

The signed tool index doesn't yet carry Node's LTS markers. Under a catalog, node@lts fails with TOOL_LTS_METADATA_UNAVAILABLE, and tools check --catalog reports it unavailable. Use an approved exact version or a named line such as lts/krypton.

Without a catalog, an unpinned Node requests lts, even when engines.node is set. Oyzu picks the newest stable LTS release that satisfies every engine constraint, or, if none does, the newest stable release that does. The build plan explains which rule applied. Explicit latest, major, exact and named LTS requests keep their meaning and must satisfy the engines. A locked lts version installs offline without refreshing.

Prerequisites​

  • A signed tool index (toolIndex.url). The catalog approves versions from the index; it isn't an index by itself.
  • An organization token from the edge's operator.
  • The edge's catalog signing public key (ed25519:<base64>), from the edge's operator.

Configuration​

Setting or variableValuesDefaultMeaning
toolCatalog.urlHTTPS URL (HTTP only on loopback)unsetBase URL of the delivery edge. Unset means registry packages resolve from the index or locally.
toolCatalog.keysOne to eight ed25519:<base64> public keysunsetKeys the catalog must be signed with. Required when toolCatalog.url is set. Pin two while the edge rotates its key. User or machine configuration only.
toolCatalog.maxOfflineAge0, <n>h or <n>d (up to 366d)7dHow long after the edge built it the last good catalog can be used while the edge is unreachable. 0 turns this off. User or machine configuration only.
toolCatalog.adminUrlHTTPS URL (HTTP only on loopback)unsetDelivery admin API, used by tools request. Also OYZU_TOOL_CATALOG_ADMIN_URL. Can't be set in a project file, because your sign-in token is sent there.
OYZU_TOOL_CATALOG_TOKENenvironment variableunsetOrganization token, sent as Authorization: Bearer. It is never a setting, so it can't end up in a committed file.

Settings marked "user or machine configuration only" fail with CONFIG_SCOPE in a project file.

Oyzu fetches <url>v1/catalog once per command, with the ETag of its saved copy, so an unchanged catalog isn't downloaded again. Proxied files are fetched from <url>v1/upstream/<host><path>.

Lockdown​

To make the catalog mandatory on a machine, set it as a locked setting in the machine's protected admin-settings.json (see configuration). User and project files can then neither remove nor change it:

{
  "schemaVersion": 1,
  "kind": "local-admin-policy",
  "settings": {
    "toolCatalog.url": { "locked": true, "value": "https://dl.example.test/" },
    "toolCatalog.keys": { "locked": true, "value": ["ed25519:7sb4o1W0lRKR712+E7DQ8uYEeTX2sUXSzJMTpKc0lzI="] },
    "toolCatalog.maxOfflineAge": { "locked": true, "value": "3d" },
    "toolIndex.url": { "locked": true, "value": "https://index.example.test/" }
  },
  "profiles": {},
  "requiredCapabilities": []
}

Pair it with a network allowlist that permits the edge and the index host but not the publishers' hosts. Distribute both through device management.

Behavior​

For an aqua: package:

  1. The index picks the version from those the catalog approves on any platform, so every platform in the lock gets the same version.
  2. Each platform's entry must be approved for that platform, not refused, and carry the index's SHA-256. A version approved only for other platforms is treated like a release with no build for this one, and that platform is left out of the lock.
  3. The download follows the catalog's delivery for that URL: proxy through the edge, direct from the publisher. A URL the catalog doesn't list is refused.

Reinstalls and the lock:

  • Reinstalling from a cached archive still checks the current catalog first. A cached, verified archive isn't downloaded again.
  • install --offline uses the saved catalog (under the rules in When the edge is unreachable) and never contacts the edge. Both the catalog and the archive must be available locally.
  • The lock is the same as without a catalog: the publisher URL and SHA-256, never the edge's host or the token.
  • github: packages are refused under a catalog, because the catalog doesn't list their files.

Withdrawn versions​

A version withdrawn from the signed index (see the index) stays in the catalog with state withdrawn, and the edge won't serve it. Oyzu refuses it with TOOL_VERSION_WITHDRAWN, the reason and the newest version the catalog serves for your platform:

TOOL_VERSION_WITHDRAWN: oyzu:golang-migrate 4.20.0 was withdrawn from the tool index: upstream release assets were deleted (404). The newest version the acme tool catalog serves for linux/amd64/gnu is 4.19.1.
  • If nothing else is available, the message suggests oyzu tools request.
  • A prefix or latest skips withdrawn versions. A lock that names one is refused on the next install.
  • tools versions lists it under excluded, and tools check --catalog reports it as withdrawn.

Oyzu's own providers (oyzu:java)​

Oyzu's archive providers (Java, Node, Go, Python, Maven, Gradle, kubectl, k3d, Helm, Liquibase, Tailscale, npm and pnpm) follow the same three steps under a catalog, instead of reading the publisher's live metadata.

  • The index lists them under their oyzu: ID (for example oyzu:java, from core:java). The catalog can use either name.
  • The version and SHA-256 come from the index as narrowed by the catalog.
  • The lock records oyzu:java, the publisher URL and the SHA-256, the same as without a catalog.

Accepted requests:

  • An exact release (21.0.8), a release-line prefix (21, 1.25) or latest.
  • For Java, lts and * pick the newest approved LTS release (8, 11, 17, 21, 25, ...).
  • Node's named lines (lts/jod, lts-iron). The moving lts alias is refused, as described above.
  • A range (^20, ~1.24, >=3.12 <3.14) picks the newest approved release it matches.
  • Native constraints (>=17) narrow every request.

Tools the index doesn't carry:

  • A provider missing from the index fails with TOOL_NOT_IN_INDEX.
  • oyzu:rust installs from an approved Rust channel manifest in the index, and each download is verified. See indexed Rust. An unapproved version fails with TOOL_NOT_IN_CATALOG.
  • cargo: helpers (cargo:cargo-nextest, cargo:cargo-llvm-cov) are refused with TOOL_NOT_IN_INDEX.

tools check --catalog​

With toolCatalog.url set, oyzu tools check --catalog fetches the catalog (or reads the saved copy with --offline) and judges each declared tool as an install would. The selected version must be approved for the host and for every platform listed in tools.lockPlatforms. Other default lock platforms are optional.

StatusMeaningRefused
approvedInstalls version through the catalog.no
not-in-catalogNo approved release matches the request. Also every github: package.yes
refusedYour organization refuses version (with its reason), or the catalog names different files than the index. Also cargo: helpers and Rust missing from the index.yes
withdrawnThe version was withdrawn from the index. The reason names the newest available one.yes
not-in-indexThe index doesn't carry the tool.yes
unavailableNo approved build for the host or a required platform.yes
excluded, blocked, unknownSame as without a catalog.yes

The command exits 1 if anything would be refused. JSON adds catalog (org, built, source and any saved-copy warning).

tools versions​

oyzu tools versions <tool> lists, newest first, the versions the catalog approves and serves for your platform.

  • A version your organization refused appears under excluded with TOOL_REFUSED and the reason, in a "Refused by the catalog" table.
  • A version whose catalog SHA-256 disagrees with the index shows TOOL_CATALOG_MISMATCH. A withdrawn one shows TOOL_VERSION_WITHDRAWN.
  • Versions never approved aren't shown.
  • A tool the catalog doesn't list fails with TOOL_NOT_IN_CATALOG.
  • In JSON, source is organization catalog, and catalog shows org, built and whether the copy was fetched or cached.

tools request​

oyzu tools request <tool>@<version> [--reason TEXT] asks your organization's administrators to approve a version. The version can be a prefix (kubectl@1.31).

oyzu tools request yq@4.44.3
oyzu tools request kubectl@1.31 --reason "cluster upgrade"
oyzu tools request --status 7
oyzu tools request --cancel 7
oyzu tools requests

What you need:

  • toolCatalog.adminUrl (or OYZU_TOOL_CATALOG_ADMIN_URL). Without it the command fails with TOOL_CATALOG_ADMIN_URL_MISSING.
  • A personal sign-in: oyzu auth login (with platform.url and platform.account) or OYZU_PLATFORM_TOKEN. Your personal token is sent to the admin URL, not the organization token. You need the catalog.request permission.
  • OYZU_TOOL_CATALOG_TOKEN, to read the catalog.

What it reports:

  • The request's id, state and what to do next. The state is pending, or approved if one of your organization's auto-approve rules accepts it immediately.
  • Asking again for the same tool and version returns the pending request. A version the catalog already serves reports served.
  • A tool missing from the index, or a version with no verified download, fails with TOOL_REQUEST_INVALID.

A request stays pending until an administrator approves or denies it, you cancel it, or it expires after 30 days (unless your organization sets another limit). An expired or cancelled request can be asked for again.

  • --status ID shows a request's state (pending, approved, denied, cancelled or expired), when it was made and expires, who asked, who decided and why.
  • --cancel ID cancels your own pending request. Only the person who asked can cancel it.
  • oyzu tools requests lists the newest 50 requests made from this machine with the current organization token, with their state read now. Oyzu remembers only the IDs, tools and versions, in the default store under state/tool-catalog/. A request the edge no longer has shows as unknown.
  • Neither command waits for a decision. Run it again later.

Signed catalog​

The edge serves the catalog as a DSSE envelope with payload type application/vnd.oyzu.tool-catalog+json. Each signature is Ed25519, and its keyid is the hex SHA-256 of the public key. Oyzu accepts the catalog when one signature verifies with a pinned key; anything else fails with TOOL_CATALOG_UNTRUSTED.

Payload fieldMeaning
orgThe organization the token belongs to.
revisionSHA-256 of the catalog's content; changes whenever the catalog does.
index{serial, sha256} of the signed index the catalog was built from.
policy_revisionRevision of the organization's policy.
built, expiresWhen the edge signed it, and when a fetched copy stops being accepted (24 hours later by default).
entriesApproved entries: ID, aliases, version, platform, sha256, delivery, state, refusal and upstream URL.

Oyzu checks, in order:

  1. The signature.
  2. For a fetched copy, that it hasn't expired (TOOL_CATALOG_STALE; also check your clock).
  3. If Oyzu's index has the same serial as the catalog's index, that both have the same SHA-256 (TOOL_CATALOG_MISMATCH).

A catalog built from a neighboring index release is accepted, since the edge and Oyzu update on their own schedules. Every entry is still checked against Oyzu's own index.

Key rotation​

To rotate keys, the edge's operator adds the new key next to the old one (the edge signs with both), you update toolCatalog.keys to the new key, and the operator removes the old key.

When the edge is unreachable​

Oyzu keeps each verified catalog in the default tool store under catalogs/tool-catalog/<key>/catalog.json (~/.local/share/oyzu/tools/... on Linux), exactly as the edge sent it.

  • The signature is checked every time the copy is read. An edited copy, or one signed by a key you no longer pin, is refused.
  • The <key> comes from the catalog URL and a hash of the token, so switching edges or organizations never reads another catalog's copy.
  • Only a newer catalog replaces the saved copy.

When fetching fails with a network error or HTTP 5xx:

  • The saved copy is used if the edge built it no more than toolCatalog.maxOfflineAge ago, and you see TOOL_CATALOG_CACHED with its age. Its expires time doesn't apply offline.
  • Entries are still checked against the signed index.
  • An older copy fails with TOOL_CATALOG_STALE.
  • A refused token (401, 403), a missing catalog (404), a bad signature or a malformed document is never replaced by the saved copy.
  • When less than a quarter of maxOfflineAge remains (under 42 hours at the default 7d), you also see TOOL_CATALOG_EXPIRING.

Oyzu also records when the newest catalog it ever fetched was built. A saved copy older than that fails with TOOL_CATALOG_STALE, so restoring an old backup can't bring back a version your organization has since withdrawn.

oyzu tools versions --offline uses the saved copy and the cached index without contacting the edge. oyzu install --offline replays the lock.

Limitations​

  • Oyzu accepts index records for Linux amd64 and arm64 (GNU), macOS arm64 and Windows amd64 (MSVC). macOS amd64 records in the index aren't installable. Tailscale has Linux archives only.
  • Someone who can write to your own tool store can put back an older genuine catalog and use a withdrawn version offline, but only until maxOfflineAge after that copy was built.
  • Someone between you and the edge with a valid token can replay a genuine catalog until its expires (24 hours by default).
  • While offline, a withdrawal made after the last fetch isn't seen until the next fetch.
