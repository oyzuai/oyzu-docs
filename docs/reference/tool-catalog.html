Organization tool catalog (toolCatalog)

CLI reference

Published from the canonical docs/reference/tool-catalog.md file. Features marked experimental remain experimental; check support limitations before relying on them.

An organization that manages its developers' tools approves which tools and versions they may install. Use toolCatalog to make a client install registry packages and Oyzu's own archive providers (oyzu:java, …) only from the organization's signed catalog. The edge's side is the platform repository's delivery service (dl edge).

Status: experimental, provisional. Milestone M4 of the tools catalog plan (client half), with the N3 governance additions (catalog-filtered tools versions, the kept copy for an unreachable edge, governed oyzu: providers). The client is implemented and has run end to end against the delivery edge from the platform repository. No production edge exists yet. Setting names, codes and the catalog document are drafts pending maintainer review.

Quick start​

Point the client at the signed tool index and the delivery edge, and pin the edge's public signing key:

# ~/.config/oyzu/config.toml
[toolIndex]
url = "https://index.example.test/"

[toolCatalog]
url = "https://dl.example.test/"
keys = ["ed25519:7sb4o1W0lRKR712+E7DQ8uYEeTX2sUXSzJMTpKc0lzI="]

Put the organization token in the OYZU_TOOL_CATALOG_TOKEN environment variable. Then:

  • oyzu tools versions <tool> lists the versions the organization approves.
  • oyzu tools check --catalog judges the declared tools as an install would.
  • oyzu tools request <tool>@<version> asks for a version the catalog does not serve.

Purpose​

The edge publishes the organization's decision as its catalog: the signed public tool index narrowed to the approved versions, with each entry's lifecycle state and how its bytes are delivered. A client configured with the catalog installs registry packages and Oyzu's own archive providers (oyzu:java, …) only from it:

  • Only versions the catalog approves resolve. Any other version fails before anything is downloaded.
  • A blocked or quarantined version fails with the organization's reason.
  • The catalog is signed by the edge, and only a catalog signed by a key pinned in toolCatalog.keys is used, fetched or kept.
  • The catalog can only narrow the index. An entry whose SHA-256 differs from the signed index record is refused, so the edge cannot substitute other bytes.
  • Artifacts the catalog delivers through the edge are downloaded from the edge with the organization token. Artifacts it marks direct (a license that forbids redistribution) come from the publisher, and the client still checks the catalog's SHA-256.
  • There is no local recipe fallback, and no registry file, GitHub release listing or provider publisher API (such as Adoptium's) is read.
  • tools versions lists only what the organization approves and serves.
  • When the edge cannot be reached, the last good catalog is used for a bounded time (toolCatalog.maxOfflineAge), with a warning. It never adds anything the edge did not approve.

Node's moving lts alias​

Node's moving lts alias needs publisher LTS markers, which the signed tool index does not yet contain.

  • Governed resolution refuses it with TOOL_LTS_METADATA_UNAVAILABLE; catalog-only checks report it unavailable.
  • Select an approved exact version or named line (lts/krypton) instead.

Without an organization catalog, an unpinned Node requests lts even with engines.node:

  • Select the greatest stable release whose publisher-index lts field is a non-empty string and that satisfies every engine constraint.
  • If none matches, fall back to the greatest stable release satisfying them.
  • The requirement reason in the plan explains this fallback rule.
  • Standalone indexed resolution uses that same exact selection.
  • Explicit latest, major, exact and named LTS pins keep their behavior and must satisfy engines; frozen lts locks validate offline without refreshing publisher LTS facts.

Prerequisites​

  • A signed tool index (toolIndex.url). The catalog approves versions of index records; it is not an index on its own.
  • An organization token from the edge's operator.
  • The public key of the edge's catalog signing key (ed25519:<base64>), from the edge's operator (delivery catalog-keygen prints it when the key is made).

How the client talks to the edge:

  • It reads GET <url>v1/catalog once per command, sending the ETag of its kept copy so an unchanged catalog answers 304 and is not downloaded again.
  • A proxied artifact is fetched from <url>v1/upstream/<host><path> for its original URL, so the edge can look it up.
  • The client does not call v1/versions or v1/resolve; it applies the same rules to the catalog document, so a cached copy behaves exactly like a fetched one.

Lockdown​

To make the catalog mandatory on a machine, set it as a locked administrative setting in the machine's protected admin-settings.json (see configuration). User and project files then cannot remove or change it:

{
  "schemaVersion": 1,
  "kind": "local-admin-policy",
  "settings": {
    "toolCatalog.url": { "locked": true, "value": "https://dl.example.test/" },
    "toolCatalog.keys": { "locked": true, "value": ["ed25519:7sb4o1W0lRKR712+E7DQ8uYEeTX2sUXSzJMTpKc0lzI="] },
    "toolCatalog.maxOfflineAge": { "locked": true, "value": "3d" },
    "toolIndex.url": { "locked": true, "value": "https://index.example.test/" }
  },
  "profiles": {},
  "requiredCapabilities": []
}

Pair it with a network allowlist that permits the edge and the index host but not the publishers' hosts. Distribute both through device management.

Behavior​

For an aqua: package, after the lock:

  1. The index selects the version, considering only versions the catalog approves (on any platform), so every platform of a lock gets the same version.
  2. The record for each platform must be admitted: approved for that platform, not refused, and naming the index's SHA-256. A version approved for other platforms only is treated like a release without a build for this platform. A version the publisher did not build for some platform is judged the same way on the platforms it has; the missing platform is left out of the lock, as without a catalog.
  3. Downloading follows the catalog's delivery for the artifact URL: proxy through the edge, direct from the publisher. A URL the catalog does not list is refused.

Reinstalling and the lock:

  • Reinstalling from a cached archive still checks admission against the current catalog before staging an installation.
  • An admitted, verified blob is reused without another artifact download.
  • If a portable lock omits the archive size, the store recovers it from the digest-verified cached bytes.
  • With install --offline, admission uses the kept catalog under the age and signature rules below and never contacts the edge; both the catalog and archive must be available locally.
  • The lock is the same as without a catalog. It records the publisher URL and the published SHA-256, never the edge's host or the token.
  • github: packages are refused under a catalog because the catalog does not list their artifacts.

Withdrawn versions​

A version the signed index withdrew (its withdrawn reason; see the index) stays in the catalog with state withdrawn, the reason in withdrawn and a refusal, and the edge refuses to serve it. The client refuses it with TOOL_VERSION_WITHDRAWN, the reason and the newest version the catalog serves for this host:

TOOL_VERSION_WITHDRAWN: oyzu:golang-migrate 4.20.0 was withdrawn from the tool index: upstream release assets were deleted (404). The newest version the acme tool catalog serves for linux/amd64/gnu is 4.19.1.
  • With nothing else servable, the message says to ask with oyzu tools request. The same holds when the index withdrew the version and the catalog has not caught up.
  • A prefix or latest skips withdrawn versions, and an existing lock naming one is refused on the next install (before reuse or download).
  • tools versions lists it under excluded with TOOL_VERSION_WITHDRAWN and the reason, and tools check --catalog reports it as withdrawn.
  • An older client refuses it through the refusal (TOOL_REFUSED).

Oyzu's own providers (oyzu:java)​

Oyzu's archive providers (Java, Node, Go, Python, Maven, Gradle, kubectl, k3d, Helm, Liquibase, Tailscale, npm and pnpm) follow the same three steps under a catalog instead of reading their publisher's live metadata.

  • The index carries them under their oyzu: id with origin core:<name> (oyzu:java from core:java); the catalog may name them by either.
  • The version comes from the index narrowed by the catalog, the SHA-256 from the verified index record, and the provider only rebuilds the archive layout from the record's publisher URL.
  • The lock records oyzu:java, the publisher URL and the SHA-256, exactly as without a catalog.

Requests use the index's selection:

  • An exact release (21.0.8), a release-line prefix (21, 1.25) or latest.
  • For Java, lts and * select the newest approved long-term-support release (8, 11, and every fourth feature release from 17: 17, 21, 25, …).
  • Node's named aliases (lts/jod, lts-iron) name their release line; the moving lts alias is refused under an organization catalog as described above.
  • Any other request, such as a range (^20, ~1.24, >=3.12 <3.14), selects the newest approved release it matches.
  • Native constraints (>=17) narrow every request.

Providers and helpers the index does not carry:

  • A provider the index does not carry is refused with TOOL_NOT_IN_INDEX. The client can now produce and consume records for all archive providers above. The separate index job must publish them before managed installations can use them.
  • oyzu:rust uses an approved indexed channel manifest, its component digests and pinned rustup bootstrap. Each selected download is verified before entering rustup's local mirror; see indexed Rust. An unapproved exact version remains TOOL_NOT_IN_CATALOG, including on reuse.
  • cargo: helpers (cargo:cargo-nextest, cargo:cargo-llvm-cov) remain refused with TOOL_NOT_IN_INDEX; governing their releases is deferred.

tools check --catalog​

With toolCatalog.url set, oyzu tools check --catalog fetches the catalog (or, with --offline, reads the kept copy) and judges each declared registry package and provider as an install would: the request selects among the versions the catalog approves, and the selected version must be admitted for the host and every explicit tools.platforms entry. The default pin matrix is optional coverage: missing records for other hosts do not refuse an install on this host.

tools versions​

oyzu tools versions <tool> lists, newest first, the indexed versions the catalog approves and serves for this platform, for registry packages and providers alike.

  • A version the organization refused (blocked, quarantined, below a floor) appears under excluded with TOOL_REFUSED and the reason, and the human output shows it in a "Refused by the catalog" table.
  • One whose catalog SHA-256 disagrees with the index appears as TOOL_CATALOG_MISMATCH, and one withdrawn from the index as TOOL_VERSION_WITHDRAWN with the reason.
  • Versions the organization never approved are not shown.
  • A tool the catalog does not list fails with TOOL_NOT_IN_CATALOG, the same error as installing it.
  • The JSON source is organization catalog, and catalog gives the org, built and whether the copy was fetched or cached.

tools request​

oyzu tools request <tool>@<version> [--reason TEXT] asks the organization's administrators to approve a version the catalog does not serve. The version may be a prefix (kubectl@1.31).

Where the request goes:

  • It posts to the delivery admin API, which has its own host (not the platform gateway and not the edge): POST <toolCatalog.adminUrl>/v1/orgs/<org>/requests with {"tool", "version", "reason"}, where <org> is the organization named by the signed catalog the CLI already reads from the edge.
  • The call is made as the signed-in person: it needs oyzu auth login (platform.url, platform.account) or OYZU_PLATFORM_TOKEN, and sends that access token as Authorization: Bearer to the admin URL, not OYZU_TOOL_CATALOG_TOKEN; the person needs the catalog.request permission.
  • Without toolCatalog.adminUrl (or OYZU_TOOL_CATALOG_ADMIN_URL) it fails with TOOL_CATALOG_ADMIN_URL_MISSING; no URL is guessed.
  • Reading the catalog for the organization still needs OYZU_TOOL_CATALOG_TOKEN.

What it reports:

  • The command shows the request: its id, state (pending, or approved when one of the organization's auto-approve rules admits it at once) and what to do next.
  • Asking again for the same tool and version returns the request already pending (HTTP 200, created: false); a new request is HTTP 201 (created: true). Both are success.
  • A version the catalog already serves reports served.
  • The admin API checks the tool against the signed index; a tool it lacks, or a version with no verified artifact, fails with TOOL_REQUEST_INVALID and its reason.
  • A person without catalog.request (HTTP 403) fails with TOOL_REQUEST_FORBIDDEN; no or a refused sign-in fails with TOOL_REQUEST_UNAUTHENTICATED.
  • TOOL_NOT_IN_CATALOG refusals name the command.
  • Administrators list and decide requests through the delivery admin API.

A request is pending until an administrator approves or denies it, its requester cancels it (cancelled), or it expires (expired).

  • A pending request expires 30 days after it was made unless the organization configures another limit; the edge says when in expires_at (RFC 3339).
  • An expired or cancelled request can no longer be decided, and the same tool and version can be asked for again.

Other forms:

  • oyzu tools request --status <id> reads one of the organization's requests back from the edge (GET /v1/requests/<id>): its state (pending, approved, denied, cancelled or expired), created_at, expires_at, who asked, who decided and why, and what to do next. An id the organization does not have fails with TOOL_REQUEST_UNKNOWN.
  • oyzu tools request --cancel <id> withdraws a pending request (POST <toolCatalog.adminUrl>/v1/orgs/<org>/requests/<id>/cancel with {}, as the signed-in person like the request itself) and shows it, now cancelled. Only its requester can: the platform refuses anyone else with TOOL_REQUEST_FORBIDDEN (HTTP 403). A request that is no longer pending fails with TOOL_REQUEST_NOT_PENDING (HTTP 409), naming its state when the edge gives it.
  • oyzu tools requests lists the requests made from this machine, newest first, each with its state read from the edge now.

How tools requests remembers requests:

  • The edge lists no requests by requester, so the client remembers the ids it was given (the newest 50, per catalog URL and token) in state/tool-catalog/<key>.requests.json of the default store; the file holds ids, tools and versions only, never a state.
  • A pending request shows when it expires (pending, expires 2026-11-10).
  • A remembered request the edge no longer has shows as unknown.
  • Neither command polls; run it again to see a decision.

Signed catalog​

The edge serves the catalog as a DSSE envelope, {"payloadType": "application/vnd.oyzu.tool-catalog+json", "payload": <base64>, "signatures": [{"keyid", "sig"}]}.

  • Each signature is Ed25519 over the DSSE pre-authentication encoding, and its keyid is the hex SHA-256 of the 32-byte public key.
  • The client accepts the envelope when one signature verifies under a pinned key; anything else (another key, an edited payload, a plain JSON document) fails with TOOL_CATALOG_UNTRUSTED.

The payload is:

FieldMeaning
orgThe organization the token belongs to
revisionSHA-256 of what the catalog says; changes exactly when the catalog does
index{serial, sha256} of the signed public index the edge built it from
policy_revisionThe organization policy's revision (0 for an edge reading policy files)
built, expiresWhen the edge signed it, and when a fetched copy stops being accepted (24 hours later by default)
entriesThe approved entries: id, aliases, version, platform, sha256, delivery, state, refusal, upstream URL

Checks, in order:

  1. The signature.
  2. For a fetched copy, that it has not expired (TOOL_CATALOG_STALE, which also points at a wrong clock).
  3. When the client's verified index has the same serial as the catalog's index, that both name the same SHA-256 (TOOL_CATALOG_MISMATCH).

The edge and the client each pick up a new index release on their own schedule (the edge hourly, the client after an hour's reuse), so a catalog from a neighbouring serial is accepted; every entry is still matched against the client's own index record.

Key rotation​

  • The edge reuses one signed envelope until half its lifetime has passed or the catalog changes, and its ETag is the SHA-256 of the envelope bytes.
  • To rotate the key, the edge's operator adds the new key beside the old one (the edge signs with both), clients move toolCatalog.keys to the new public key, and the operator then removes the old key.

When the edge is unreachable​

Each successfully fetched and verified catalog is kept in the default tool store, under catalogs/tool-catalog/<key>/catalog.json (~/.local/share/oyzu/tools/… on Linux): the signed envelope exactly as the edge served it, with the time it was fetched.

  • The signature is checked again every time the copy is read, so an edited copy, or a copy after the pinned keys changed, is refused (TOOL_CATALOG_UNAVAILABLE naming TOOL_CATALOG_UNTRUSTED).
  • The key is derived from the catalog URL and a SHA-256 of the token (never the token itself), because one edge serves many organizations: switching edges or organizations never reads another catalog's copy.
  • In-process reuse includes this token-specific cache path, the resolved store, settings and offline mode, so loads from different user data roots cannot share a catalog. See the default store location for disposable-home isolation on Windows.
  • A copy is replaced only by a newer fetched document; one the edge built earlier than the kept copy does not replace it.

When fetching fails with a network error or an HTTP 5xx:

  • The kept copy is used if the edge built it no longer than toolCatalog.maxOfflineAge ago (its signed built, not the local fetch time), and the command reports TOOL_CATALOG_CACHED with the copy's fetch time and age.
  • Its signed expires does not apply offline; maxOfflineAge does.
  • Its entries go through the same index cross-check: an entry whose SHA-256 differs from the signed index record is still refused.
  • A copy older than the limit fails with TOOL_CATALOG_STALE.
  • A refused token (401, 403), a missing catalog (404), a bad signature or a malformed document is the edge's answer and is never replaced by the copy.

Newest-seen record:

  • The built time of the newest catalog fetched from the edge is also kept, apart from the copy, in state/tool-catalog/<key>.json of the default store.
  • A kept copy built earlier than that fails with TOOL_CATALOG_STALE ("older than the newest one this client fetched"), so a restored backup, a copy synced from another machine or an older copy put back into the cache cannot bring back a version the organization has since withdrawn.

Warnings and offline commands:

  • While a kept copy stands in, a command whose copy has less than a quarter of toolCatalog.maxOfflineAge left (under 42 hours at the default 7d) also reports TOOL_CATALOG_EXPIRING with the time left, before installs start failing with TOOL_CATALOG_STALE.
  • oyzu tools versions --offline never asks the edge: it uses the kept copy under the same age and newest-seen rules, with the cached index, and reports catalog.source as cached.
  • oyzu install --offline replays the lock and needs neither.

Limitations​

  • Native installation admits Linux amd64/arm64 GNU, macOS arm64 native and Windows amd64 MSVC. The five-platform index includes an unsupported macOS amd64 record. Tailscale provides standalone Linux archives only. Publication of new provider records belongs to the separate index repository.
  • Provider/Rust catalog installation fixtures require Linux amd64. See implementation status for verification results; live evidence and native Linux ARM64 installation remain unverified.
  • The kept copy is signed, so editing it fails, and an older genuine copy is refused. A person who can write both it and the newest-seen record in their own store can still put back an older genuine copy and use a withdrawn version offline, but only until maxOfflineAge after the edge built that copy.
  • A replayed genuine catalog (someone between the client and the edge with a valid token) is accepted until its signed expires, 24 hours by default.
  • While offline (or with the edge down) a withdrawal made after the last fetch is not seen until the next fetch, for at most maxOfflineAge.
  • Only Linux x86-64 has been run.

  • Unit tests in src/tools/org_catalog.rs for the kept copy: used while young enough with its age, refused when stale or disabled, never read for another catalog URL, never replaced by an older document, and refused when older than the newest catalog fetched (a_cached_copy_older_than_the_newest_fetched_catalog_is_refused).
  • Compiled-CLI tests (tests/integration/tool_catalog.rs) against a stand-in edge and the signed terraform fixture index:
    • An unapproved version is not downloaded, an approved one is requested from the edge by host and path with the token, a blocked version fails with its reason, a mismatched SHA-256 is refused, a missing or rejected token fails closed, and a version with no build for another lock platform is still judged on this one.
    • tools versions lists only approved versions, shows the refused one with its reason and refuses an unlisted tool.
    • With the edge answering 503, the kept catalog is used with a TOOL_CATALOG_CACHED warning; another token finds no copy; 401, 404 and a malformed document are not replaced by it; maxOfflineAge = "0" disables it.
    • tools versions --offline lists from the kept copy without a request to the edge and refuses an older copy put back into the cache (offline_listing_uses_the_cached_catalog_and_never_an_older_one).
    • Only a catalog signed by the pinned key is used: another key, an unsigned document and a missing toolCatalog.keys fail with TOOL_CATALOG_UNTRUSTED, and a project file cannot pin a key (only_a_catalog_signed_by_a_pinned_key_is_used).
    • A catalog naming another index under the client's serial is refused for listing and install, and an expired one is refused (a_catalog_from_another_index_or_past_its_expiry_is_refused).
    • A second command sends the kept copy's ETag and uses it on 304 (an_unchanged_catalog_is_not_downloaded_again).
    • For oyzu:java (a signed fixture index with core:java records): tools versions java lists approved releases only, a refused release and an unapproved feature are not installed, and java@lts selects 21.0.8 over the approved non-LTS 24.0.2, downloads the archive through the edge, locks the publisher URL and the index SHA-256, and oyzu exec -- java runs it (Linux).
    • The same for oyzu:node, oyzu:go and oyzu:python: node@lts/jod, go@~1.24 and python@3.13 select the newest approved release of their line, install it through the edge and run it, while a blocked release and an unapproved line are refused (Linux).
  • install_through_the_delivery_edge (ignored by default) runs against the real edge. On 2026-10-10 it passed on Linux x86-64: with only 1.15 approved, terraform 1.16.5 was refused, and 1.15.3 installed through the edge, which filled it from releases.hashicorp.com; the lock held the publisher URL and SHA-256 and terraform version ran.
  • managed_client_against_the_compose_stack (ignored by default) runs against the platform's whole Compose stack, driven by its deploy/compose/e2e.sh. On 2026-10-10 it passed on Linux x86-64 through the s3:// edge: jq 1.7.1 installed and ran, and the blocked jq 1.7 (with the organization's reason), the unapproved yq and a github: spec were refused.
  • managed_client_installs_each_provider_through_the_compose_stack (ignored by default) runs against the same stack, which approves one version of each Oyzu provider.
    • On 2026-10-11 on Windows x86-64 through the s3:// edge: an unapproved version of every provider was refused, and Maven 3.9.11, Gradle 9.1.0, Helm 3.19.0, kubectl 1.31.0, k3d 5.8.3, Liquibase 4.33.0, npm 11.6.2 (with Node 22.20.0) and pnpm 10.18.2 installed with the publisher URL in the lock.
    • Rust 1.90.0 installs once the edge serves the components its channel manifest pins (oyzuai/platform#258); the full test passed with that change.
    • On an edge with nothing stored, Gradle and Liquibase (134 and 354 MB) install on the first run once the edge answers 503 FILL_PENDING while it fills them (oyzuai/platform#263) and the client waits for it (#344); the test passed that way on 2026-10-11 with all three changes.
    • Tailscale is checked on Linux hosts only.
