Release provenance verification

CLI reference

Published from the canonical docs/reference/release-provenance.md file. Features marked experimental remain experimental; check support limitations before relying on them.

oyzu inspect can check a downloaded artifact against its detached Sigstore provenance and a build profile you choose independently. Use it to confirm that a file was built by the exact GitHub repository, commit and workflow you expect. Verification runs offline and never runs the artifact or any project code.

Note: This is experimental. Only one evidence format is supported: public GitHub Actions provenance (in-toto Statement v1, SLSA provenance v1, GitHub workflow/v1) in a Sigstore bundle v0.3. A passing check doesn't assess the producer's build controls or establish a SLSA level.

oyzu inspect application.tar.gz --provenance application.sigstore.json \
  --release-profile expected-build.json

For a file inside an Oyzu build bundle, name its recorded path:

oyzu inspect dist --artifact app/linux/x86_64/application \
  --provenance application.sigstore.json --release-profile expected-build.json --json

Options​

OptionDefaultMeaning
--provenance <FILE>noneThe detached Sigstore bundle. Turns on provenance verification and requires --release-profile.
--release-profile <FILE>noneJSON file with the exact producer, source and build parameters you accept. Never read from the artifact.
--artifact <PATH>noneThe recorded file path inside a bundle directory. Required for a bundle; not used for a plain file.
--trusted-root <FILE>the built-in public Sigstore rootA Sigstore trusted-root JSON file you supply. Never taken from the artifact or its evidence.

Each input file can be at most 1 MiB. Keep profiles and trusted roots somewhere you control, separate from downloaded content. Oyzu never fetches or refreshes trust material over the network.

The release profile​

A release profile lists exact values. It isn't a policy language. Unknown fields and duplicate JSON keys are errors. Every field is required except stagingBuilderWorkflow.

FieldMeaning
signerThe signing workflow's certificate identity: https://github.com/OWNER/REPO/.github/workflows/FILE.yml@COMMIT, pinned to a full 40-character lowercase commit.
signerRevisionThat same commit.
stagingBuilderWorkflowOptional. A separate workflow URL, pinned to a full commit, that ran the build job. Used only by oyzu build --release-profile (see below). When absent, the signer is assumed to have built. null, empty or branch references are errors.
builderIdhttps://github.com/actions/runner/github-hosted
sourceRepositoryThe application repository, as https://github.com/OWNER/REPO.
sourceCommit, sourceRefThe application commit and its full Git ref.
repositoryId, repositoryOwnerIdGitHub's numeric IDs, as decimal strings.
workflowPath, workflowRevisionThe calling workflow under .github/workflows/ and its commit in the application repository.
eventNameThe GitHub event, such as push.
externalParametersThe exact JSON object of build parameters you accept. Its workflow.repository, workflow.ref and workflow.path must agree with the source and workflow fields.

The signer workflow's commit and the application's commit are different things. A valid signature from an unexpected repository, fork, workflow commit, builder or set of parameters fails.

If your build job can mint its own OIDC token, the signer has to be a different workflow file. Separate jobs in one workflow don't give you that separation. Use stagingBuilderWorkflow for the build workflow and signer for the attesting one:

{
  "stagingBuilderWorkflow": "https://github.com/example/builders/.github/workflows/build.yml@1111111111111111111111111111111111111111",
  "signer": "https://github.com/example/builders/.github/workflows/attest.yml@2222222222222222222222222222222222222222",
  "signerRevision": "2222222222222222222222222222222222222222"
}

These fields go alongside the other required fields.

What is checked​

  1. For a bundle, ordinary bundle inspection and the required native report checks run first. A valid attestation can't rescue a failed build or a missing required report.
  2. The actual file is hashed.
  3. The certificate, issuer, signature and transparency-log or timestamp evidence are verified.
  4. The signed subject must match the file's digest.
  5. The signed source, repository IDs, calling and called workflows and build parameters must match the profile.

Standard GitHub provenance doesn't name an intermediate build workflow. If stagingBuilderWorkflow differs from signer, the result reports that workflow as not-covered-by-standard-provenance, and human output says it wasn't authenticated.

A plain file has no report inventory, so a passing check on one says nothing about tests or other reports.

Output​

With --json, the inspection result gains a releaseVerification object:

FieldMeaning
passedAll standard provenance checks passed.
expectationsScopestandard-provenance.
signature, subject, expectationsEach check's own result. Replaced bytes with genuine evidence show a verified signature and an unmatched subject.
profileDigest, evidenceDigest, trustRootDigestIdentify the exact inputs used.
stagingBuilderWorkflowPresent when a separate staging workflow was named; see above.
builderAssuranceAlways unassessed.
productionEligibleAlways false.

Verification never changes manifests, versions, source, trust stores or publishing permissions. oyzu inspect without these options behaves as before.

Failures and recovery​

A failed verification exits nonzero. Invalid input and ordinary bundle failures use the usual error output.

FailureFix
Missing or invalid profile, unsafe --artifact path, unreadable fileCorrect the input. Nothing is rewritten.
Replaced bytes or invalid signatureGet the expected artifact and its genuine evidence. Don't edit the profile to accept the mismatch.
Wrong source, signer, workflow, IDs, build type or parametersCheck the profile against the producer you approved. A valid signature alone isn't enough.
Missing or wrong trusted rootSupply a complete trusted root. There is no network fallback.
Failed build or missing required reportFix the producing build.

Staging a release build with a profile​

oyzu build --release-profile expected-build.json uses the same profile while building, for authenticated release staging. A reusable-workflow job must present signed job_workflow_ref and job_workflow_sha values that match stagingBuilderWorkflow (or signer when that field is absent). The calling source, tag, workflow and run checks still apply, and a job that doesn't match the profile is refused rather than built without it. --require-release still refuses a build when release evidence is missing. Profiles can't be forwarded to --remote builds.

Limits​

  • Only public GitHub Actions provenance is supported. GitHub Enterprise Server, private GitHub trust services, other CI providers and self-hosted runners are not supported.
  • SLSA provenance doesn't authenticate each tool or test result recorded in the bundle.
  • This doesn't sign anything, attest local builds or grant permission to publish.
