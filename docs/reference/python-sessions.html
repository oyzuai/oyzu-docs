Managed Python launch sessions (prototype)

CLI reference

Published from the canonical docs/reference/python-sessions.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Oyzu can prepare pip and uv acquisition automatically through oyzu exec and activated Bash. An Oyzu-owned subprocess keyring helper supplies a session's password to the native tool in memory. No Python keyring package or per-project authentication file is needed. This opt-in prototype uses a fixture local agent; it does not implement platform login or captured oyzu build integration.

Setup and commands​

Configure an agent in user or administrative Oyzu configuration and provision Python/pip or uv on PATH:

[python]
sessionEndpoint = "http://127.0.0.1:43199/session"

The port is illustrative. The endpoint is absent by default, leaving standalone behavior unchanged. The normal configuration cascade resolves it. Project, local, invocation and profile settings cannot select agent authority. User configuration is excluded in CI under existing rules. The laboratory endpoint must use numeric loopback HTTP with no credentials, query or fragment.

oyzu exec -- python3 -m pip install --require-hashes -r requirements.txt
oyzu exec -- uv lock
oyzu exec -- uv sync --locked
eval "$(oyzu activate bash)"
pip install --require-hashes -r requirements.txt

The measured native versions are Python 3.12.14, pip 25.0.1 and uv 0.12.21 on Linux. Native Windows/macOS execution is unqualified; managed-session Windows shell shims are not implemented. The shell installs launch aliases for python, python3, pip, pip3 and uv when their native executable is present. Explicit exec also recognizes versioned Python/pip executable names. Plain interpreter execution is unchanged; python -m pip is routed through pip admission.

Managed operations are pip install, download, wheel; uv lock, sync, pip install, pip sync. Help/version bypass admission. Other operations fail explicitly. uv run, Poetry and arbitrary Python scripts that internally invoke package managers are not qualified by this adapter. Publication belongs to oyzu publish; native uv publish is rejected.

Admission, configuration and credentials​

Each supported invocation requests admission with its working directory, tool and arguments before starting native acquisition, including warm/offline operations. Directory is an unverified context hint. The experimental response supplies index, username and numeric-loopback credentialEndpoint. The index must be credential-free HTTP(S) with no query or fragment. Oyzu adds the username alone to the native index URL and stages its own executable under the keyring name. The helper implements keyring get <service> <username> and asks the agent for a password for that service and username. The agent must validate the request against its admitted source; native URL handling remains native-owned.

This is an explicit single-index configuration replacement mode:

  • Pip receives PIP_CONFIG_FILE set to the null device, PIP_INDEX_URL and PIP_KEYRING_PROVIDER=subprocess. It uses noninteractive acquisition.
  • Uv receives UV_NO_CONFIG=1, UV_DEFAULT_INDEX and UV_KEYRING_PROVIDER=subprocess.
  • Inherited alternate-index/find-links variables are removed; UV_CONFIG_FILE is removed. Explicit source, provider, config-file, isolation and directory override arguments are rejected instead of combined with managed settings.

Persistent resolver configuration is not merged, including unrelated options inside disabled pip/uv configuration. Ordinary package metadata remains native; Oyzu does not rewrite requirements, pyproject.toml, uv.toml or locks. Native CLI/environment options unrelated to routing remain native-owned. This choice uses pip's documented null-config behavior and uv's configuration controls.

Passwords are returned through the native helper pipe, never placed in generated configuration, launcher arguments or launcher environment. The session locator is access-sensitive; this fixture transport is not production authenticated IPC. Native processes can read credentials in memory. Read-only access is enforced by the upstream identity, not client network filtering or hostile-code containment.

Outputs, failures and limits​

Native results and exit status follow oyzu exec; --json captures native output in the structured result. Package caches, installed packages and generated locks remain native-owned. Temporary helper files live until the child exits and are removed after normal success/failure. Abrupt-termination cleanup is deferred.

NATIVE_SESSION_* identifies authority/admission failures; PYTHON_SESSION_INVALID identifies malformed session data; PYTHON_ROUTING_CONFLICT rejects explicit configuration conflicts; PYTHON_OPERATION_UNSUPPORTED identifies an unsupported command. Helper errors are generic. Denied/unavailable admission prevents native work without a direct or cached offline fallback. Restore agent availability before retrying.

The qualified flow is ordinary named packages from one admitted index, including hash-pinned requirements and uv locks retaining upstream wheel URLs. Direct URL, VCS/path dependencies, requirements-file source directives, uv source/workspace overrides, alternative credentials in existing netrc/native auth stores, and arbitrary native parser aliases are not qualified source-policy enforcement. Disabling persistent resolver configuration is not a network sandbox. These inputs need explicit admission/configuration composition before broader support is claimed; the agent must never grant credentials solely because a client asks.

See the launch qualification. Platform and CI identity integration remain deferred. No Oyzu schema version was introduced.
