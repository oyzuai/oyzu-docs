Maven builds

CLI reference

Published from the canonical docs/reference/maven.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Oyzu detects a pom.xml without any build YAML and treats a Maven reactor as one target. Maven still owns inheritance, active profiles, module order, dependency resolution and the lifecycle. Oyzu captures the inputs, assigns snapshot versions, runs the build in isolation and collects reports. The reactor example includes unit and integration test variations.

Note: The Maven builder is experimental and runs captured builds on Linux (Docker required). It's the Maven side of the java/app builder, supplied by the oyzu/java plugin, which selects Maven for a folder with a pom.xml (or with.build-tool: maven); see plugin catalog and selecting a role. It doesn't publish, sign or promote anything.

Quick start​

oyzu -C examples/builds/java-maven-reactor/project run list
oyzu -C examples/builds/java-maven-reactor/project build

Captured builds need Docker and the base execution image. Oyzu pulls the image when it's missing. The JDK and, for a project without a Maven wrapper, Maven itself are restored from oyzu.lock.

Development tasks use your provisioned Maven or the project's Maven wrapper. oyzu run list doesn't run Maven.

JDK inference accepts literal root compiler-plugin release/source/target and testRelease facts and their corresponding root properties. Configuration wins for each parameter, then release overrides source and target; otherwise both production floors are retained. A separate testRelease floor is also retained: production release 17 and test release 25 select JDK 25 or newer. Literal release/testRelease configuration requires a canonical compiler-plugin 3.x declaration at version 3.6 or newer. Incompatible explicit Java selections stop before native compilation. This does not evaluate the effective reactor model: relevant managed, profile, execution, other test-compiler and toolchain overrides report an unsupported inference location. Parent-based projects retain partial root-property discovery. java.version alone supplies a default hint without asserting a compiler floor. See JDK selection and its limits for precedence, canonical property references and recovery.

TaskRunsNotes
install (implicit)Dependency preparation
build (implicit)mvn -B verifyChecks bound to verify run under Maven.
test (implicit)mvn -B testThe test task isn't repeated during a build.

The shared Java quality defaults add lint and read-only formatting checks. You can replace them with your own tasks.

Image requirements​

  • The base image has no JDK or Maven. Both come from the lock. A project without a locked JDK stops with the oyzu pin command that fixes it.
  • The Maven extension and the Oyzu worker come with the Maven plugin and the CLI, so no image supplies them.
  • A custom --image maven=<image> only has to meet the bring-your-own contract.
  • Isolated Maven builds on the base execution image are not supported yet.

Locked JDK in isolated builds​

The execution image has no JDK. Your project selects one, through [tools] java or the root POM's declared level (see how versions are chosen), and build preflight locks it. The container uses it. Preparation:

  1. Reads the Linux (linux/amd64/gnu) Temurin archive recorded in oyzu.lock.
  2. Downloads it through the tool broker, unless a copy in your user data directory still matches the locked SHA-256.
  3. Verifies it.
  4. Restores it read-only at /scratch/jdktool.

Then JAVA_HOME and the front of PATH point at it for preparation and every build action, so Maven and the compiler run on it.

  • The plan records the archive, so a different JDK changes the action identity.
  • A selected JDK older than 17 is refused with TOOL_UNSUPPORTED_VERSION. Maven and Oyzu's Java integration in the container need JDK 17. JDK 17 and newer can compile for older levels with --release.
  • An oyzu.lock without a JDK entry stops the build with the oyzu pin command that fixes it.

Preparation and outputs​

Preparation captures the POMs and evaluates the reactor inside the container. Version inference combines native versions with scoped Git tags and relevant commit changes, and the Maven versions plugin applies each module's version, and local reactor references, in private copies of the POMs. Your checkout is unchanged.

  • Supported packaging: pom, jar and war. Other types fail.
  • Outputs keep their native final names, and the bundle records the planned snapshot versions.

Version decisions​

Oyzu reads the Maven model first, decides each module's version, and freezes the result in version-plan.json.

  • The final coordinates must match those decisions. If the facts change or the projection fails, the build stops.
  • Maven evaluates version expressions. Oyzu never interprets POM expressions itself.
  • A scoped tag uses the module's artifact ID when it is unique. A root tag doesn't coordinate a whole reactor.
  • The reactor graph supplies each module's local upstream modules, including reactor parents. A library change therefore affects its consumers without advancing unrelated modules.
  • Shared root inputs affect every module.
  • A snapshot version never authorizes publishing.

For a module with no version element of its own, preparation first writes the version Maven resolved into the private POM, so the versions plugin can set it independently of the parent. This may normalize the private POM's formatting. The POM in your checkout is never rewritten.

Dependency acquisition​

Maven downloads through a local mirror backed by Oyzu's scoped Maven Central broker. Upstream requests happen during acquisition. The captured repository is then copied into a private workspace for the offline build.

  • Custom or private repositories and corporate credentials are not supported. The only other public source is an administrator-approved snapshot repository.
  • There is no Maven lockfile. The prepared repository records what was actually captured, which doesn't guarantee that a later download resolves identically.
  • Maven resolves parent dependency management, BOMs and conflicts first. Dependencies on other reactor modules are not fetched, so preparation needs no prebuilt JARs and doesn't compile or test.
  • project-dependencies.xml in the prepared tree lists the external coordinates that were fetched. Plugin and go-offline downloads may add more versions to the repository, so it is not a minimal repository or a complete dependency report.
  • Missing required bytes fail preparation, before any plan is frozen.
  • Transient download failures are retried within limits (acquisition transport). A failed download blocks the build.

Lifecycle and coverage​

One offline lifecycle runs verify and JaCoCo reporting. Your project's JaCoCo version and prepare-agent execution take precedence, including inherited configuration, phase, skip settings and property names.

  • Oyzu adds an initialize preparation only when the project declares none.
  • Inherited pluginManagement version, configuration and executions are respected. JaCoCo 0.8.13 is used when nothing manages a version.
  • Preparation fetches every effective JaCoCo plugin version, because go-offline alone can leave one module's plugin dependencies incomplete in a reactor with mixed versions.
  • If you disabled preparation, it stays disabled and no agent is added.
  • After a failed lifecycle, Oyzu still tries to produce the coverage report without rerunning tests, and keeps the failure.

Bundle contents​

  • Required reports, logs and artifacts, with their digests, are listed in dist/manifest.json.
  • A failed check, or an invalid or missing required report, blocks artifact collection.
  • oyzu inspect dist checks the bundle's integrity. It doesn't say whether a build may be released.

Native test reports​

After acquisition, Oyzu asks Maven for the effective verify plan and records the report directories of the bound Surefire test and Failsafe integration-test goals. Defaults, inherited and execution-specific configuration, and paths with spaces all follow Maven.

JaCoCo and argLine​

If a Surefire or Failsafe argLine is a literal string, Oyzu prefixes it with @{argLine} in the private model. The JaCoCo agent can then add its flags while your JVM flags and execution-specific overrides stay in place. Your POM is unchanged.

  • Where Oyzu adds this, a missing default property keeps its native user or system value or is set empty. Existing values are never replaced.
  • Property expressions, custom JaCoCo property names and non-forking tests keep Maven's behavior, and Oyzu can't promise coverage for them.
  • Missing coverage still fails the required report check.

Collecting reports​

  • Before the run, Oyzu removes old TEST-*.xml files from the declared directories in the private workspace.
  • After the lifecycle it copies the XML unchanged into .oyzu-maven/reports/<reactor-index>/, using hashes of the source path to avoid name collisions.
  • Every XML file is validated and its results recorded. Duplicate directories are collected once.
  • A Surefire or Failsafe directory can be empty. A module with only integration tests doesn't need unit-test XML.
  • A module with test sources needs at least one JUnit file across both directories, plus a JaCoCo report. If tests are skipped or reporting is off and no XML exists, the check fails. Malformed XML fails too.
  • If a custom reporter suppresses some output, Oyzu can't tell which engine's files are missing. It never invents a passing report.

Limits:

  • Report paths must stay inside the captured workspace, outside the reserved .oyzu-maven folder, and not be redirected.
  • Different modules need different report directories. Shared paths fail planning rather than credit the same tests to several modules.
  • One XML file can be up to 16 MiB, and one module's reports up to 64 MiB.
  • If a test fails, its XML and any coverage are kept and no artifacts are produced. Fix the test, the report configuration or the missing evidence, and rebuild.
  • Reports from both engines are combined. Use the report records in the manifest, not assumed Surefire paths.
  • JaCoCo reports are read from target/site/jacoco/jacoco.xml under the module's build directory. Custom coverage destinations, aggregate reactor coverage and test source roots added only during the lifecycle aren't supported yet.

Direct test bundles​

oyzu run test writes a test-only bundle to dist/. Each module with test sources gets named JUnit and JaCoCo reports, and oyzu inspect dist checks them.

  • The implicit mvn -B test command (or the wrapper equivalent) is reported automatically, with no configuration.
  • Qualified task names and hooks work as in the shared task engine.
  • Custom task replacements keep their commands and must produce the required reports.
  • Extra forwarded arguments and other lifecycle selections aren't supported for this automatic reporting.

Prerequisites​

  • Maven 3.9.11, a JDK 17 with java, javac and jar, and your project's plugins and test dependencies, including JaCoCo 0.8.13.
  • MAVEN_HOME pointing at Maven and JAVA_HOME at the JDK, or the JDK executables on PATH.
  • A wrapper must already have its distribution installed. Oyzu doesn't install wrapper distributions.
  • Your Maven settings and environment apply.
  • Oyzu runs Maven offline. A missing plugin or dependency fails instead of going online.

How it runs​

After task checks, a temporary Oyzu extension reads the effective reactor and the test plan in a dedicated Maven process, which exits before validate bindings or the default lifecycle run.

  • Maven can load extensions while it builds its model, so this is ordinary execution on your machine. It is not a sandbox. oyzu run list stays static and doesn't run Maven.
  • Captured builds look at the wider verify plan, which includes Failsafe integration tests.

The run then clears old XML in the declared test directories and old JaCoCo execution and XML files, and runs prepare-agent, test and report.

  • After a test failure it still tries to generate reports without rerunning tests.
  • Native XML suites are wrapped into one JUnit document per module, and JaCoCo XML is copied to fresh private paths.
  • Reports are validated and the bundle is finished after post hooks run.
  • Empty suites and missing outputs never get invented passing reports.

Limits:

  • Direct tests don't run verify, package snapshots, run quality checks or run integration-only Failsafe suites. Use oyzu build for that.
  • Missing tests or reports, failed tests and unmet coverage constraints fail the command and keep the current evidence.
  • See direct tests for output handling and provenance.
  • Custom JaCoCo destinations and aggregate reactor coverage aren't supported.

Plugin dependencies during acquisition​

Captured preparation also fetches the dependencies declared on build plugins in Maven's effective model, in addition to dependency:go-offline.

  • Oyzu gets the coordinates from the model and downloads them through the broker. It doesn't run the plugin to discover them.
  • System-scoped plugin dependencies aren't supported.
  • A dependency that a plugin chooses only while it runs is not found and can fail the offline build. Oyzu doesn't retry online.
  • Spotless's Eclipse-based formatter steps are one such case: they download Eclipse P2 bundles from download.eclipse.org and fail with java.net.UnknownHostException. They aren't supported (Spotless Eclipse P2 artifacts).
  • For private repositories, use the optional Maven session endpoint. Without it, downloads come from Maven Central.
  • Ordinary JAR plugin dependencies are supported. A plugin's overridden or excluded dependency graph may fetch more than needed, and plugin dependencies produced by the reactor itself aren't supported.

Plugin-configuration artifacts​

Some plugins download an artifact named in their own configuration while they run. Oyzu fetches these ahead of time for a short list of known plugin parameters, read from Maven's effective model after property expansion:

PluginParameterRequested type
org.codehaus.mojo:animal-sniffer-maven-pluginsignaturesignature
com.github.siom79.japicmp:japicmp-maven-pluginoldVersion/dependencyConfigured type, default jar

Both plugin-level and execution-level configuration are read. Animal Sniffer accepts the structured form and the groupId:artifactId:version[:classifier] shorthand:

<plugin>
  <groupId>org.codehaus.mojo</groupId>
  <artifactId>animal-sniffer-maven-plugin</artifactId>
  <executions>
    <execution>
      <goals><goal>check</goal></goals>
      <configuration>
        <signature>
          <groupId>org.codehaus.mojo.signature</groupId>
          <artifactId>java15</artifactId>
          <version>1.0</version>
        </signature>
      </configuration>
    </execution>
  </executions>
</plugin>

For japicmp, give an explicit old-version dependency inside the plugin's or execution's <configuration>:

<oldVersion>
  <dependency>
    <groupId>org.jsoup</groupId>
    <artifactId>jsoup</artifactId>
    <version>1.23.2</version>
    <type>jar</type>
  </dependency>
</oldVersion>
  • An optional classifier and the artifact type are kept. A missing type means jar.
  • Maven's artifact handler supplies a missing classifier (test-jar maps to jar:tests). An explicit classifier wins.
  • The old artifact is fetched before the offline run so japicmp can compare it with the new one. A successful build alone doesn't prove the comparison happened: check japicmp's output for a warning that the old version was unavailable.
  • File-based versions, newVersion, version ranges and versions japicmp computes aren't supported.
  • The fetched signature file or old JAR is listed in the dependency snapshot's package inventory.
  • A coordinate with a missing field, or an expression Maven didn't resolve, fails preparation and names the plugin. Fix the POM or its properties and rebuild.
  • Other plugins, and parameters set only on the command line or computed by plugin code, aren't found and can fail the offline build.

Snapshot repositories and OS-detected properties​

Snapshot repositories​

Some projects inherit a parent that exists only as a snapshot. For example, jackson-core has a -SNAPSHOT jackson-base parent published to the Sonatype Central Portal snapshot repository and declared in the project's own <repositories>. Captured builds send every repository through one mirror to Maven Central, which serves no snapshots, so by default such a build fails preparation.

SettingValuesDefaultMeaning
maven.snapshotRepositoriesA set of HTTPS repository base URLs ending in /Empty (off)The snapshot repositories Oyzu may use. Only corporate policy or the protected local admin-settings.json can set it. Project, local, user, machine and invocation configuration can't enable or widen it.

For example, inside the settings object of admin-settings.json:

"maven.snapshotRepositories": {
  "locked": true,
  "value": ["https://central.sonatype.com/repository/maven-snapshots/"]
}

When the set isn't empty:

  • Each URL becomes its own download source, maven-snapshots-<n>, numbered in sorted URL order. A URL with credentials, a query or a fragment, a plain HTTP URL, or one without a trailing / fails preparation. Admitted repositories can't carry credentials.
  • The mirror and the repository identity stay the same, so the offline build reads snapshots from the captured repository exactly as it reads releases.
  • Only snapshot version paths (group/.../artifact/<version>-SNAPSHOT/...) go to the approved repositories, which are tried in order until one returns the file. Every other path keeps the Central (or session-approved) route.
  • The approved repositories, not the URLs your project declares, serve every snapshot. Maven only asks for snapshots when a declared repository enables them, so your project still declares its snapshot repository, as jackson-core does. The mirror replaces its URL.
  • Each captured .pom, .jar, .module or .signature file under a snapshot version directory is listed in the dependency snapshot's package inventory with the maven-snapshots-<n> source that served it. The approved repositories are listed under extensions."oyzu.dev/maven".snapshotRepositories.
  • Acquisition fails if one snapshot directory was served by two repositories.

Release builds never use snapshot inputs. If any snapshot input was captured and any module's version decision isn't a development snapshot, or is production eligible, preparation fails with MAVEN_SNAPSHOT_RELEASE, even with the setting on. Today every captured build is a development snapshot build. A build without snapshot inputs is unaffected by the setting.

Code or messageCauseFix
Maven's "could not find artifact" error naming the snapshotThe setting is off, and a snapshot parent or dependency can't be fetchedAsk an administrator to admit its repository, or depend on a released version
MAVEN_SNAPSHOT_REPOSITORYA captured snapshot package wasn't served by an approved repository. This applies whether or not the setting is on, so a snapshot served by a session-approved repository is refused too. The error names the file.Follow the approved-repository rules above
MAVEN_SNAPSHOT_RELEASEA snapshot input was captured and a version decision isn't a development snapshot, or is production eligibleThe setting doesn't override this. Release builds never use snapshot inputs.
CONFIG_SCOPEA project file sets maven.snapshotRepositoriesRemove it from the project file. Only corporate policy or the protected local admin-settings.json can set it.

OS-detected properties​

Some POMs use os-maven-plugin properties to pick platform-specific artifacts, such as Netty's parent with <tcnative.classifier>${os.detected.classifier}</tcnative.classifier>. A project that only imports Netty's dependencies doesn't run the extension, so the expression is never resolved. Where the extension does run, it detects the machine Maven runs on.

Captured preparation and execution therefore pass fixed Maven user properties taken from the job's target platform, not from the host or the execution image:

Propertylinux/amd64linux/arm64darwin/arm64windows/amd64
os.detected.namelinuxlinuxosxwindows
os.detected.archx86_64aarch_64aarch_64x86_64
os.detected.bitness64646464
os.detected.classifierlinux-x86_64linux-aarch_64osx-aarch_64windows-x86_64
  • Names follow the plugin's own normalization (kr.motd.maven.os.Detector). Other platforms the plugin names, such as linux/ppc64le (ppcle_64) and linux/s390x (s390_64), map the same way. A target the plugin can't name fails preparation.
  • os.detected.release* and kernel os.detected.version* aren't set, because a target platform has neither. A POM that needs them keeps Maven's behavior.
  • Maven user properties win over the extension's detected values in interpolation, profile activation and plugin parameters, so ${os.detected.classifier} resolves the same way in every run, including in dependency POMs.
  • A project that declares the extension still runs its own detection. Only these four properties are fixed.
  • The properties are frozen in the prepared tree (properties.json) and listed in the dependency snapshot under extensions."oyzu.dev/maven".userProperties.
  • Artifacts a plugin downloads from such a property while it runs, outside declared dependencies, aren't fetched ahead of time.
  • Direct tests (oyzu run test) keep native detection.

What each stage reads​

With the next Java plugin release and a compatible CLI supporting private stages, native host format-check reuses independently through its fixed reads and empty private-output declaration. Editing an existing README's contents does not change its source-read key, but a source-derived snapshot version can change the action definition and still cause a miss. Whole-target projection identity can also cause conservative misses. Editing a formatted Java file reruns it. Lifecycle builds (including tests) and Checkstyle currently have unbounded output contracts and rerun even on unchanged native builds. This mixed pipeline cannot restore a whole-target result. Captured copy/export behavior is unchanged. See Java quality for the read boundary.

The Maven build action runs verify, including tests and lifecycle plugins. It stays unbounded: tests can read arbitrary files at run time, and Maven does not report a complete read set for the effective reactor's plugins. Conventional src/ directories alone cannot bound this lifecycle. Reactor POMs, configured source/resource roots, .mvn/ configuration and plugin-specific files remain covered by the whole-target key.

The separate test action is also unbounded. Packaging reads only its explicit copy inputs: reactor POMs and generated archives. It also depends on the build producer's outputs. Since it copies POM bytes, it is not a source-free export. Shared Java formatting and lint have their own read boundaries. These declarations are supplied by the Java plugin; older plugin releases retain their earlier conservative behavior.

TestNG and reactor coverage​

Surefire tests using TestNG (including suiteXmlFiles pointing to a testng.xml suite) use the same TEST-*.xml collection as JUnit. Maven selects the provider and runs the suite. Oyzu requires genuine Surefire XML; providers or configuration that suppress these reports fail the required-report check. TestNG through Failsafe alone, JUnit 3 and Spock/Groovy are outside the supported scope.

Native and captured builds combine conventional per-module target/site/jacoco/jacoco.xml reports into one reactor report. Its counters sum the tested modules, and module groups retain source/package ownership. It is a weighted total of covered and missed lines, not an average of module percentages. If every module lacks line debug metadata, the total uses instructions instead; mixed line/instruction reports fail with a request for consistent debug metadata. Oyzu does not add report-aggregate or measure cross-module execution that is absent from the individual module reports. The merged XML has the shared JaCoCo report limit of 16 MiB.

A project may already configure org.jacoco:jacoco-maven-plugin, including through its effective parent, profile or plugin management. Oyzu preserves an existing prepare-agent execution and its configuration instead of adding another agent. Otherwise it adds one preparation execution. The project's plugin version and report configuration remain Maven-owned; Oyzu requests the plugin's report goal after verify and reuses the conventional XML output. A disabled agent, a custom agent property that Surefire does not consume, a skipped XML report or a different output path does not waive required coverage: restore conventional XML output and agent wiring to build successfully. Literal Surefire JVM flags are retained through late argLine replacement.

This behavior requires the next Java plugin release and a CLI supporting the maven-reactor-coverage feature. Existing plugin releases retain their previous native coverage behavior.

Limits​

  • Not supported yet: test providers beyond JUnit through Surefire/Failsafe and TestNG through Surefire, custom coverage tools or custom/aggregate report layouts, test sources generated during the lifecycle, private repositories and release builds.
  • Captured builds run on Linux. Conventional reactors can also build natively; see native Maven builds.
