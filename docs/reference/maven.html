Maven builds

CLI reference

Published from the canonical docs/reference/maven.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Status: experimental. Oyzu detects a pom.xml without a build YAML file and treats a native Maven reactor as one target. Maven owns inheritance, active profiles, module order, dependency resolution and lifecycle execution; Oyzu captures inputs, projects snapshot versions, enforces isolated execution and collects evidence. The reactor example includes unit/integration reporting variations.

Tools and commands​

Development tasks use provisioned Maven or the native Maven wrapper. Static oyzu run list does not execute Maven. Implicit install runs dependency preparation, build runs mvn -B verify, and test runs mvn -B test. The explicit test task is not separately repeated during the build lifecycle. Checks already bound to verify run under Maven. Shared Java quality defaults add native lint and read-only formatting gates, with explicit task replacements available.

Captured builds require Docker and the explicitly provisioned Maven 3.9.11/JDK 17 image:

docker build -f tooling/images/builder-worker.Dockerfile -t oyzu-toolchain/builder-worker:v1 .
docker build -f tooling/images/maven.Dockerfile -t oyzu-toolchain/maven:3.9.11-jdk17 .
oyzu -C examples/builds/java-maven-reactor/project run list
oyzu -C examples/builds/java-maven-reactor/project build

Locked JDK in the captured worker​

The image's JDK 17 is used only when nothing selects another. A JDK chosen by the project, either by [tools] java or by the root POM's declared level (see how versions are chosen), is locked by build preflight and restored in the worker: preparation reads the Linux (linux/amd64/gnu) Temurin archive recorded in oyzu.lock, downloads it through the tool broker unless a copy cached under the user data directory still matches the locked SHA-256, verifies it and restores it read-only at /scratch/jdktool. JAVA_HOME and the front of PATH point at it for preparation and every build action, so Maven and the compiler run on it. The plan records the archive under oyzu.dev/locked-tool, so a different JDK changes the action identity. A selected JDK older than 17 is refused with TOOL_UNSUPPORTED_VERSION, because Maven and Oyzu's Java integration in the worker need JDK 17; JDK 17 and newer compile older levels with --release. An existing oyzu.lock without a JDK entry keeps the image's JDK.

Rebuild this image for the native test-plan extension; an older image with the same tag cannot produce the required metadata. Oyzu does not pull a missing image or install Maven. Custom --image maven=<image> toolchains need the matching extension, native tools and the matching compiled Oyzu worker at /usr/local/libexec/oyzu/oyzu. Windows native metadata/lifecycle probes and Linux captured builds are separate verification scopes; a portable CLI does not establish a native isolated executor on every host.

Preparation and outputs​

Preparation captures native POMs and evaluates the reactor inside the constrained toolchain. Version inference combines native versions with scoped Git tags and relevant commit impacts, then the native versions plugin projects each selected version and local reactor references into private POMs. The checkout stays unchanged. Supported artifact packaging is pom, jar and war; other packaging types fail explicitly. Outputs retain native final names and carry planned snapshot versions in the bundle.

The native model is captured before projection. The host resolves per-module decisions and freezes version-plan.json, then preparation continues in the same private workspace. The final native coordinates must agree with those decisions; changed native facts or failed projection stop the build. Native version expressions are evaluated by Maven, never by a host-side POM expression interpreter. Scoped tags use the module's artifact ID when unique. Root tags do not automatically coordinate a reactor. The native reactor graph supplies local upstream projects, including reactor parents, to the shared transitive version-impact resolver. A library change therefore affects its consumers without automatically advancing an unrelated module. Shared root inputs conservatively affect all modules. Prepared layout version 4 requires these graph facts; regenerate older captures and reprovision the toolchain image with the current metadata extension. Snapshot intent does not authorize publishing.

For modules without their own version element, private preparation first uses Maven's raw model writer to make the originally resolved version explicit. The versions plugin can then project that module independently of its parent. This serialization may normalize private POM formatting; the checked-in POM is never rewritten. The final native reactor must match all selected coordinates before dependency acquisition continues. Host metadata observation disables this mutation.

The standalone source profile routes Maven through a loopback mirror backed by Oyzu's scoped Maven Central broker. Upstream requests occur during acquisition; the captured repository is then copied into a private workspace for offline execution. Custom/private repositories, corporate connector credentials and complete dependency-edge evidence are not implemented by this profile; administratively admitted snapshot repositories are the only additional public source. Maven has no general lockfile here: the prepared repository identity records the actual captured inputs and is not a claim that independent future acquisition resolves identically.

Project dependency acquisition uses Maven's effective project resolver after private version projection. Maven applies parent dependency management, imported BOMs and transitive conflict mediation before it acquires the external graph. Exact reactor group/artifact/version identities are excluded from artifact resolution, so preparation does not require prebuilt local JARs or execute compilation/tests. Unused dependency-management entries are not fetched merely because they are declared. The private prepared project-dependencies.xml retains the acquired external coordinates alongside native reactor metadata. Existing go-offline and plugin/provider acquisition remain; their additional versions can coexist in the captured repository. This is not a globally minimal repository or complete dependency-edge report. Missing required external bytes fail preparation before an executable plan is frozen. An older provisioned metadata JAR that does not acknowledge project dependency acquisition also fails preparation; reprovision the Maven metadata extension rather than reuse an incomplete capture. Every expected projected reactor coordinate must be present, including an explicit empty acquisition record for dependency-free projects. The managed-transitive qualification records the observed gap and current verification status.

The shared acquisition transport applies bounded retries to eligible transient failures without treating transport errors as permission denials. Maven runs with native error traces (-e) so nested plugin/dependency-resolution causes can appear in the retained failure diagnostic; debug logging is not enabled. An exhausted or terminal acquisition failure blocks planning and requires successful preparation before any build artifact can be collected.

One offline lifecycle runs native verify and JaCoCo reporting. The effective project's JaCoCo version and existing prepare-agent execution own native preparation, including inherited configuration, phase, skip controls and property names. Oyzu adds an initialize preparation only where no such execution is declared. Activation preserves effective inherited pluginManagement version, configuration and executions; JaCoCo 0.8.13 is the fallback when no managed version supplies one. Captured preparation observes this same effective plugin model. Preparation explicitly prefetches every effective JaCoCo plugin version through the existing broker-routed transitive dependency:get, alongside its declared dependencies. Native go-offline alone can leave a different module's plugin dependency closure incomplete in a mixed-version reactor; the selected plugin JAR and POM alone do not establish offline usability. Explicitly disabled native preparation is preserved and does not receive a replacement agent. Reporting uses the same effective native plugin version, rather than a competing version. No source POM is rewritten. A failed lifecycle attempts coverage reporting without rerunning tests and preserves failure. Required reports, logs, artifacts and their digests are recorded under dist/ and in dist/manifest.json. Any failed gate or invalid/missing required report prevents final artifact collection. oyzu inspect dist verifies bundle integrity, not release eligibility. Publishing, signing and production promotion are outside this builder increment.

Native test reports​

After acquisition, the extension asks Maven for the effective verify execution plan. It records report directories for bound Surefire test and Failsafe integration-test goals using Maven's plugin configuration and expression evaluator. Defaults, inherited configuration, execution-specific settings and paths with spaces remain native Maven behavior. The directory plan is frozen in prepared metadata; shared planning does not parse POM expressions or guess test-class filename patterns.

For captured builds and direct tests, the native extension prefixes an explicitly configured literal Surefire/Failsafe argLine with @{argLine} in the private effective model. This lets the selected JaCoCo prepare-agent supply its default agent while preserving the project's JVM flags and execution-specific overrides; the source POM is unchanged. Where a bridge is added, a missing default property retains the native user/system value or is initialized empty so the late token remains resolvable; existing project values are never replaced. Existing property expressions, custom JaCoCo property names and nonforking test configuration retain native Maven behavior; this literal bridge does not establish their coverage outcome. Absent coverage still fails the required report gate.

Before execution, the adapter removes old TEST-*.xml outputs from those declared directories in the private workspace. After the lifecycle it copies produced XML unchanged into .oyzu-maven/reports/<reactor-index>/, using source-path hashes to avoid filename collisions. The shared report collector validates every retained XML file and records its actual results. Duplicate native directories are collected once. Individual Surefire/Failsafe directories may be empty: a module with only integration tests does not need fabricated unit-test XML. Modules with captured test sources require at least one native JUnit file across the combined group, plus their JaCoCo report. If every engine leaves no XML, disabled reporting or skipped tests fail that obligation; malformed XML also fails. The combined group records available native files and does not prove per-engine completeness when a custom reporter suppresses some outputs. No passing report is synthesized.

Report paths must remain inside the captured workspace, outside reserved .oyzu-maven state, without redirected directories. Different modules must use distinct native report directories; shared paths fail planning rather than attributing the same tests to multiple modules. Each XML file is bounded to 16 MiB and each module's group to 64 MiB. Native test failures retain XML and available coverage while blocking artifacts. Fix the test, native report configuration or missing evidence and rebuild; prior successful bundles remain history rather than satisfying the current invocation. Native goals within one module may rewrite a shared report filename; Oyzu retains the final native files, not invented per-execution copies.

Prepared layout version 2 requires the frozen directory plan; regenerate older prepared inputs and rebuild the toolchain image. Retained test-report paths change because collection now combines native engines. Consumers should follow manifest report records rather than assume Surefire-specific paths. JaCoCo remains at the module's conventional target/site/jacoco/jacoco.xml beneath its effective build directory; custom coverage destinations, aggregate reactor coverage and test source roots added only during later lifecycle execution need further integration.

Verification and limits​

Direct test bundles​

oyzu run test now produces a test-only dist/ bundle for a native Maven reactor. Each module with discovered test sources receives named JUnit and JaCoCo reports; oyzu inspect dist validates the result. The exact implicit mvn -B test command (or the discovered wrapper equivalent) receives automatic reporting without project configuration. Qualified tasks and hooks retain their shared task-engine behavior. Arbitrary task replacements keep their command bodies and required report obligations. Additional forwarded arguments and alternate lifecycle selections are not yet integrated into this direct adapter.

Provision Maven 3.9.11, JDK 17 with java, javac and jar, and the project's plugins/test dependencies, including JaCoCo 0.8.13. Set MAVEN_HOME to the installed Maven distribution and JAVA_HOME to the JDK, or put the JDK executables on PATH. Wrappers require an already provisioned distribution; Oyzu does not implement wrapper installation. Native Maven settings and environment remain in effect. The product passes Maven's offline flag for model observation and execution; an unavailable plugin or dependency fails instead of falling back to online resolution.

After shared task admission, a temporary compiled extension reads the effective reactor and the native test execution plan. It exits its dedicated Maven process after writing the model, before validate bindings or default lifecycle tasks run. Native Maven model evaluation can load extensions; this is explicit host execution, not static discovery or sandboxing. run list remains static and does not invoke Maven. Captured builds continue to observe the broader verify plan, which includes bound Failsafe integration tests.

The direct action clears prior XML in its declared native test directories and prior conventional JaCoCo execution/XML files, then runs prepare-agent, test, and report. On test failure it attempts report generation without rerunning tests. The adapter wraps native XML suites unchanged in meaning into one JUnit document per module and copies JaCoCo XML to fresh private output paths. The shared collector validates the reports and finalizes the bundle after post hooks. No successful reports are invented for empty suites or missing outputs. Native compilation output remains in the project; POMs and versions are not rewritten, and native module build files are not claimed as newly published artifacts.

Direct tests do not invoke verify, package snapshots, run quality gates, or include integration-only Failsafe suites. Use oyzu build for that full captured flow. Missing tests/reports, failed native tests or unmet coverage constraints fail the command and retain available current evidence. See direct test boundaries for host output preservation and provenance. Custom JaCoCo destinations and aggregate reactor coverage retain the limitations above.

The real Windows probe passed with Maven 3.9.11/JDK 17.0.20.1: the authored reactor, a custom Surefire directory, per-module reports, repeated tests without stale evidence, hooks, a failed assertion, unchanged POMs and inspection. Run python tooling/test-maven-direct.py --cli <compiled-path> --maven-home <maven-home> --repository <native-repository> with tooling/design-requirements.txt installed. Its optional --acquire explicitly provisions fixture dependencies before product execution. CI provisions a pinned Maven distribution with tooling/provision-maven.py and runs this probe on all three hosts after CLI compilation; the direct step passed on all three hosts at 343c682 in run 37052623343 (Linux job 110991301336, macOS 110991301392, Windows 110991301544). These step outcomes do not establish whole-workflow success.

Captured and native adapter checks​

The native extension can be exercised with provisioned Maven/JDK tools:

python tooling/test-maven-metadata.py --maven-home <maven-home> --java-home <jdk-home>
python tooling/test-maven-metadata.py --maven-home <maven-home> --java-home <jdk-home> --test-lifecycle --repository <prepared-native-repository>

The default check needs no downloaded plugins. The lifecycle variant needs its pinned fixture plugins/dependencies in that native repository; adding --acquire explicitly permits a native online clean verify fixture run to provision them before the offline checks. That test setup is distinct from Oyzu's captured acquisition protocol.

The lifecycle probe reads effective Surefire/Failsafe directories and checks native XML after offline clean verify: successful tests, a failed integration test and an integration-only module. Native clean removes prior XML and compiled test classes; source preservation, disabled executions and directory containment are also checked. Its coverage cases run forked tests that count actual JaCoCo agents, preserve literal JVM flags and inherited properties, and check paired module coverage with fallback 0.8.13 and inherited active or managed-only native 0.8.15. Native disabled preparation and skip controls remain disabled, without fabricated coverage. This probe does not invoke the compiled report collector or prove normalized bundle reports. Use tooling/test-maven-direct.py with a compiled CLI for direct report collection and the captured Maven acceptance suite for the complete build/report/artifact flow.

Historical Windows testing passed the native custom-directory and lifecycle cases. The later captured/full reactor qualification at source 99096a93 passed all nine authored cases through the compiled worker, including normalized reports, coverage ownership, failure gates, source preservation and delivered-JAR consumption. That result is distinct from this native model/XML probe and does not qualify subsequent source changes. Java quality defaults are documented in the shared Java quality reference. Remaining work includes broader test providers, custom/aggregate coverage, generated test roots, private repositories, release policy and complete corpus qualification.

The compiled Oyzu worker owns process sequencing and native report composition. Native Java integrations remain embedded assets; Python is not required to execute these builder operations. Rebuild captured images after updating the worker.

Declared plugin dependencies during acquisition​

Captured preparation explicitly fetches dependencies declared on build plugins from Maven's effective model, in addition to dependency:go-offline. The native metadata extension supplies coordinates using Maven's artifact type/classifier mapping; Rust sequences dependency:get through the acquisition broker. The plugin's build goal is not run to discover those dependencies.

Reprovision Maven images with the current metadata extension and CLI together; older metadata without plugin dependency facts fails with a reprovision message. System-scoped plugin dependencies are unsupported by this acquisition path. A dependency selected only by executing plugin code remains undiscovered and can fail the offline build. No online retry is introduced. Spotless's Eclipse-backed formatter steps are one such case: they provision Eclipse P2 bundles from download.eclipse.org and fail with java.net.UnknownHostException. They are unsupported; see Spotless Eclipse P2 artifacts. Private source selection uses the optional Maven session endpoint; without it, standalone Central acquisition remains unchanged.

The qualification covers ordinary JAR plugin dependencies. Per-coordinate transitive prefetch can acquire a superset of a plugin's overridden/excluded graph; those configurations and reactor-produced plugin dependencies remain unqualified. See the measured proof.

Plugin-configuration artifacts​

Some plugins resolve an artifact named in their own configuration while they run, not through declared plugin dependencies. Oyzu prefetches these for a small owned table of known plugin parameters, read from Maven's effective model after native interpolation. The table currently covers:

PluginParameterRequested type
org.codehaus.mojo:animal-sniffer-maven-pluginsignaturesignature
com.github.siom79.japicmp:japicmp-maven-pluginoldVersion/dependencyConfigured type, default jar

Both plugin-level and execution-level configuration are read after native inheritance and property expansion. Animal Sniffer accepts the structured form and the groupId:artifactId:version[:classifier] shorthand:

<plugin>
  <groupId>org.codehaus.mojo</groupId>
  <artifactId>animal-sniffer-maven-plugin</artifactId>
  <executions>
    <execution>
      <goals><goal>check</goal></goals>
      <configuration>
        <signature>
          <groupId>org.codehaus.mojo.signature</groupId>
          <artifactId>java15</artifactId>
          <version>1.0</version>
        </signature>
      </configuration>
    </execution>
  </executions>
</plugin>

For japicmp, the supported form is an explicit old-version dependency:

<oldVersion>
  <dependency>
    <groupId>org.jsoup</groupId>
    <artifactId>jsoup</artifactId>
    <version>1.23.2</version>
    <type>jar</type>
  </dependency>
</oldVersion>

Place this inside the plugin or execution's <configuration>. Optional classifier and native artifact type are preserved; omitted type means jar. Maven's artifact handler supplies an omitted classifier (test-jar maps to jar:tests); an explicit classifier takes precedence. Acquisition captures the old artifact before offline execution so the native comparator can actually compare it with the new artifact. A successful build alone does not prove comparison: retain japicmp's native output and check that it resolved the configured old version rather than warning that it was unavailable. File-based versions, newVersion, version ranges and versions computed by japicmp are outside this bounded support.

The extension reports org.codehaus.mojo.signature:java15:1.0:signature, with the extension from Maven's type mapping, and acquisition fetches it with the same broker-routed dependency:get as declared plugin dependencies. The signature file, or japicmp's old-version JAR, is listed in the dependency snapshot's package inventory. A configured coordinate with a missing field or an expression Maven did not resolve fails preparation and names the plugin; fix the POM or its properties and rebuild. Plugins outside the table, and parameters supplied only on the command line or computed by plugin code, are not discovered and can still fail the offline build. Reprovision the Maven image with the current metadata extension together with the CLI. Run python tooling/test-maven-metadata.py --maven-home <maven-home> --java-home <jdk-home> for the native extension check. The unchanged pinned JUnit4 corpus now has a captured offline build and delivered-JAR consumer proof: the configured signature was prefetched and consumed offline, with native test and coverage reports. Its separate full build failed the native quality gates and exported no artifacts; this is not a full-check or general plugin-closure qualification.

Snapshot repositories and OS-detected properties​

Both behaviors follow the decisions of 2026-10-10. Captured Jsoup execution has measured target-derived OS properties and a usable JDK 17 product. Jackson's protected administrative configuration, snapshot-parent/BOM acquisition and default captured offline product/report/consumer flow pass at source 9ec5efb2 after the native coverage ownership repair. Earlier agent-collision and resource failures remain in the corpus qualification, with exact revisions and limits. These bounded results do not establish full-quality checks, all platform properties or other JDKs.

Snapshot repositories​

Some projects inherit a parent that exists only as a snapshot, for example jackson-core, whose jackson-base -SNAPSHOT parent is published to the Sonatype Central Portal snapshot repository and declared in the project's own <repositories>. Captured acquisition routes every repository through one native mirror (mirrorOf *) to Maven Central, which serves no snapshots, so such a build fails preparation by default.

An administrator can admit snapshot repositories with the administrative maven.snapshotRepositories setting. It is a set of HTTPS repository base URLs ending in / and is empty, meaning off, by default. Only corporate policy or the protected local admin-settings.json can supply it; project, local, user, machine and invocation configuration cannot enable or widen it, and a project file that names it fails with CONFIG_SCOPE. For example, inside the settings object of admin-settings.json:

"maven.snapshotRepositories": {
  "locked": true,
  "value": ["https://central.sonatype.com/repository/maven-snapshots/"]
}

When the set is non-empty:

  • Each URL becomes its own broker source, maven-snapshots-<n> in sorted URL order. URLs with credentials, a query or a fragment, plain HTTP and URLs without a trailing / fail preparation. Admitted repositories cannot carry credentials.
  • The native mirror and its repository identity stay unchanged, so the offline build reads snapshots from the captured repository exactly as it reads releases. The compiled adapter sends only snapshot version paths (group/.../artifact/<version>-SNAPSHOT/...) to the admitted repositories, trying them in order until one returns the file; every other path keeps the Central (or session-approved) route. The admitted repositories, not the URLs the project declares, serve every snapshot the build requests. Maven only requests snapshots when some declared repository enables them, so the project still declares its snapshot repository, as jackson-core does; the mirror replaces its URL.
  • Snapshot inputs are recorded in the dependency snapshot like any other input: each captured .pom, .jar, .module or .signature file beneath a snapshot version directory is listed in the package inventory with the maven-snapshots-<n> source that served it. The admitted repositories are listed under extensions."oyzu.dev/maven".snapshotRepositories.
  • Preparation fails with MAVEN_SNAPSHOT_REPOSITORY, naming the file, when a captured snapshot package was not served by an admitted repository, and acquisition fails when one snapshot directory was served by two repositories. This applies whether or not the setting is on, so a snapshot that a session-approved repository serves on the ordinary route is refused too.

Release builds never use snapshot inputs. Preparation checks every module's version decision: if any snapshot input was captured and any decision's intent is not a development snapshot or is production eligible, preparation fails with MAVEN_SNAPSHOT_RELEASE, even when the setting is on. Oyzu has no release-build operation yet, so every captured build is a development snapshot build today; this check fails closed for the release intent that OEP-0013 will add. A build without snapshot inputs is unaffected by the setting.

Recovery: without the setting, a snapshot parent or dependency fails native acquisition with Maven's "could not find artifact" error naming the snapshot. Ask an administrator to admit its repository, or depend on a released version.

OS-detected properties​

POMs that use os-maven-plugin properties, such as Netty's parent with <tcnative.classifier>${os.detected.classifier}</tcnative.classifier>, select platform-specific artifacts. A project such as jsoup that imports Netty's dependencies does not run the extension itself, so the expression is never resolved. Where the extension does run, it detects the machine Maven runs on.

Captured preparation and execution therefore pass fixed Maven user properties derived from the job's target platform, not the host or toolchain image:

Propertylinux/amd64linux/arm64darwin/arm64windows/amd64
os.detected.namelinuxlinuxosxwindows
os.detected.archx86_64aarch_64aarch_64x86_64
os.detected.bitness64646464
os.detected.classifierlinux-x86_64linux-aarch_64osx-aarch_64windows-x86_64

Names follow the plugin's own normalization (kr.motd.maven.os.Detector); other platforms the plugin names, such as linux/ppc64le (ppcle_64) and linux/s390x (s390_64), map the same way, and a target the plugin cannot name fails preparation. The classifier has no Linux distribution suffix (os.detection.classifierWithLikes). The distribution-derived os.detected.release* and kernel os.detected.version* properties are not supplied, because a target platform names neither; a POM that needs them keeps Maven's native behavior.

Maven user properties take precedence over the extension's detected values in model interpolation, profile activation and plugin parameters, so ${os.detected.classifier} resolves the same way in every run, including in dependency POMs. A project that declares the extension still runs its host detection; only the four properties above are fixed. The properties are frozen in the prepared tree (properties.json) and listed in the dependency snapshot under extensions."oyzu.dev/maven".userProperties. Artifacts that a plugin downloads from such a property while it runs, outside declared dependencies, are still not prefetched. Direct host tests (oyzu run test) keep native detection.

Run python tooling/test-maven-metadata.py --maven-home <maven-home> --java-home <jdk-home> for the native interpolation check of a plugin dependency classifier.
