Writing and testing builder plugins

CLI reference

Published from the canonical docs/reference/plugin-development.md file. Features marked experimental remain experimental; check support limitations before relying on them.

A builder plugin is a separate program that tells oyzu how to build one kind of project: which tasks it has, which tools it needs, which command builds it and where the output lands. This page shows how to run a plugin from a local path while you develop it, how plugins work, what a plugin has to provide, and how to package it. It also covers the Node plugin's behavior, since it's the largest first-party plugin.

Note: The plugin interface (plugins-v1alpha1) is experimental. It's edited in place and can change without a new version. The Rust crates in the oyzu repository that help write plugins are internal and not a supported SDK. You can write a plugin in any language that speaks the JSON contract below.

Run a local plugin​

Bind your executable to a builder reference in your user configuration (~/.config/oyzu/config.toml on Linux, ~/Library/Application Support/Oyzu/config.toml on macOS, %APPDATA%\Oyzu\config.toml on Windows, or the file OYZU_USER_CONFIG names):

[plugins.development]
"go/app" = "/home/me/src/oyzu/target/debug/oyzu-plugin-go"
"node/app" = "/home/me/src/oyzu/target/debug/oyzu-plugin-node"

Then build as usual:

oyzu build
oyzu build --full
oyzu run test

Oyzu runs your executable for that reference instead of a catalog package. The build shows the plugin-owned output directory in its commands (for example go build -trimpath -buildvcs=false -o .oyzu/native/plugin/…), the Context facts in dist/logs/events.jsonl include Plugins go/app → local development <path> (sha256:…), and the plan, envelope and manifest carry extensions["oyzu.dev/plugins"] (see plugin packages).

Remove the entry to stop using the local executable. The next build then has to find the package some other way: the catalog, a plugins.packages binding or the lock. There's no built-in fallback.

Setting​

KeyTypeDefaultWhere
plugins.developmentTable of builder reference to absolute executable or package archive pathnoneUser, machine or administrative configuration
  • Keys are short builder references without a major version (go/app, not go@1/app or an OCI reference). Values are absolute paths. At most 64 entries.
  • The setting selects code to run, so a project oyzu.toml, oyzu.local.toml or a profile is refused with CONFIG_SCOPE: plugins.development is not permitted in this scope.
  • In CI, user configuration is ignored as usual; a machine-level binding still applies. Pass --ci-machine-binding to the repository bootstrap to create one on an ephemeral runner (see CI machine binding).
  • The table is replaced as a whole by a later source.
  • Bindings are read once per command, before targets are discovered. A missing or unreadable executable fails with PLUGIN_BINDING_INVALID; a malformed or versioned key fails with CONFIG_INVALID_VALUE.
  • A local binding has no download, signature check or oyzu.lock entry. An executable is recorded by file name and SHA-256 digest only, with no manifest check.

Binding a package archive​

A development binding can also name a plugin package archive (a .tar.gz with plugin.json and its members). Use this when you want --isolated builds with your plugin: a raw executable has no Linux member or captured-plan manifest, so an isolated build refuses it with PLUGIN_ISOLATED_UNSUPPORTED.

[plugins.development]
"rust/app" = "/home/me/src/oyzu/.oyzu/bin/oyzu-plugin-rust.tar.gz"
  • Oyzu recognizes the archive by its gzip header and installs it, with the manifest, layout and host-member checks a bound package gets, into a private folder that is removed when the command ends. Nothing goes into the shared package store or oyzu.lock, and no digest is pinned, so rebuilding the archive takes effect on the next command.
  • The host member runs host builds; the member for the execution image's platform runs isolated ones. The binding is still recorded as local development, with the host member's digest.
  • An archive that isn't a valid package for that reference fails with PLUGIN_BINDING_INVALID and the reason.

Independent profiles​

A plugin doesn't have to match a built-in family. To develop a new profile such as independent/app, bind its id and name it in build.yaml. The names and path are illustrative:

[plugins.development]
"independent/app" = "/home/me/src/plugin/target/debug/independent-plugin"
builds:
  app:
    uses: independent/app

Run oyzu build app to build with it. An independent profile must be named in uses; the binding adds no detection, no with options, no dependency preparation and no isolated execution. Tool versions still come from your configuration or native files, and oyzu installs the tools the plugin's requirements answer names under the usual policy. A local binding can't ask oyzu to run task-command observations (see below), even for an installed tool.

When tools.allowed is set, oyzu run admits a task of a plugin-built target only if every tool the plugin's requirements declare for that task is on the list. A task whose binding declares no tool for it is refused with CONFIG_OVERRIDE_DENIED before anything launches. Registry routes and approved catalogs stay fail-closed for local bindings, as for any other builder.

How a plugin works​

For every operation, oyzu starts your executable once, with no arguments, a minimal environment and a fresh scratch directory as its working directory. It writes one JSON request to standard input and reads one JSON result from standard output. The process gets no credentials.

StreamContent
Standard inputOne request, then end of input
Standard outputOne result and nothing else
Standard errorDiagnostic lines as JSON. Other lines are kept only for troubleshooting
  • Documents use snake_case, schema_version: "v1alpha1" and a constant type. Unknown members, duplicate keys, null members and numbers written with a fraction or exponent are invalid.
  • A request carries an operation_id, role (builder), operation, required_features, deadline_ms, the target (name, uses, whether the reference was inferred or explicit, absolute source root for reading, and the base version) and the operation's input. Your result echoes operation_id and operation and has an outcome: completed (with output), failed (with error{code, message}), unsupported (with reason) or, for task-command, observe.
  • Oyzu accepts a result only if it's valid, the process exited with status 0 and the ids match. A valid result followed by a nonzero exit is a failure.
  • Limits: 16 MiB for a request or result, 1 MiB of kept diagnostics, at most 64 observations. Oyzu never truncates and accepts.
  • Each operation has a deadline (60 seconds by default). At the deadline, or when the build is cancelled, oyzu terminates the whole process tree (SIGTERM, then SIGKILL after 2 seconds on Unix; the job object on Windows). Termination is a failure whatever the process wrote.
  • Plugins keep no state between calls. Oyzu supplies every fact each time.
  • Target-relative paths use /, never .. or spaces, and at most one leading dot per segment.

Operations​

An operation you don't implement answers unsupported.

OperationCalled toYour answer
describeConfirm identity and rolesProtocol generations, plugin identity, roles with their profiles, operations and features
tasksDiscover conventional tasksThe package manager, optional native package name and version (with the file they came from), and tasks (name, argv, build stage, whether it changes source, optional environment defaults)
requirementsFind the tools a target needsTools (for example oyzu:go), stages, components, version constraints with their source files, and why. Read-only
native-admissionDecide whether the plugin can build this target on the host{admitted, reason}. Read-only
native-buildPlan a host buildThe build operations and the artifacts. Oyzu supplies the version, a fresh output_dir, offline and the execution platform
native-testPlan the direct test runAn optional test command and the reports it must write, into a fresh report_dir
task-commandAdjust a task's commandAn optional replacement command, or observe to ask oyzu to run tool commands and call again once
captured-planPlan an isolated buildBuild and test intent, from read-only source. No observations or downloads

What oyzu keeps for itself: the build version (the plugin must echo it), where output is written, scheduling, tool installation, running processes, collecting artifacts and the report gates. The plugin supplies intent: tasks, requirements, commands, artifact paths and report formats. Report formats are junit, cobertura, lcov, go-cover and jacoco; sources are file, go-test-events, jest-json and jest-lcov. A plugin that needs nonempty with options must declare the build-options feature.

A task-command observation names a core tool identity and its command line. Oyzu checks that the tool is one the builder may use and that argv[0] is that tool's command, runs it once on the task's PATH (stdout up to 1 MiB, stderr up to 64 KiB), then calls task-command again in a new process with the results. One round only. A local development binding may not use observations.

Artifacts must have unique names and sources (compared without regard to case). A default artifact lives inside output_dir. An artifact marked executable is promoted to .oyzu/bin after a successful build.

Project-written outputs​

Some builds decide their own output location: npm run build writes dist, and the plugin can't steer it into output_dir. For those, the plugin marks the artifact "origin": "target" with a target-relative source, and the build operation runs the task's own command (oyzu sends it as input.task.argv):

{"name": "primary", "producer": "build", "kind": "directory",
 "filename": "application-1.4.0", "media_type": "application/octet-stream",
 "source": "dist", "executable": false, "origin": "target"}

Before any build action runs, oyzu checks the source and refuses it otherwise:

RuleRefused with
It names something below the target: not ., no segment that starts or ends with a dot (.git, .oyzu), is node_modules (any case) or is a Windows device name (con, nul, COM1.txt)PLUGIN_OPERATION_FAILED: … invalid result
Sources are unique, ignoring casePLUGIN_OPERATION_FAILED: … invalid result
It doesn't equal, contain or lie inside output_dirPLUGIN_OPERATION_FAILED: … overlaps the output directory
It doesn't equal, contain or lie inside a file or directory of the target's source selectionPLUGIN_ARTIFACT_REFUSED: … overlaps the frozen source selection at <path>
No existing segment is a symbolic link or reparse point, and none above the last is a filePLUGIN_ARTIFACT_REFUSED: artifact … names …

Oyzu then moves anything already at the path into a fresh directory beside the output (never deleting in place) and discards that directory after collection. The plan records moved paths under extensions["oyzu.dev/retired-outputs"]. A build whose script writes nothing fails with native artifact collection failed rather than republishing an old output. Collection then applies the usual rules: no links, no reserved names.

On the native host lane the target directory is a private copy rebuilt from the selected source before each build, so nothing is ever moved there and previous is always false. In an isolated build, the output is moved aside in the private execution workspace, never in your project. To recover from a refusal, name a project output that isn't source, version control state or a dependency tree, and remove any link in its path.

Native package facts​

tasks can report native_package with an optional name and version and the file (origin{path,digest,location}) they came from. Oyzu checks that the file is inside the supplied source and that its digest matches. A missing declaration stays unknown, even when the target's version is 0.0.0. The Node plugin reports package.json; the Go plugin doesn't. See version inference.

Caching and cost​

Targets built by a plugin are reused from the local action cache like other targets. The cache key includes the plugin's executable digest and runtime, so rebuilding the plugin reruns its targets. Bind the executable itself, not a wrapper script, because a script's digest doesn't cover the program it starts (see external builder targets). An unchanged one-module rebuild launches the plugin five times (tasks, requirements, native-admission, native-build, and one task-command per command; two when the command asks for an observation). Launches scale with the number of plugin targets.

Per-operation source contracts​

Every BuildOperation must carry contract, a SourceContract. Declare a non-empty reads list, unbounded_reason with a non-empty explanation such as "not analyzed yet", or upstream_only: true for an operation that reads no source and only consumes declared upstream outputs. The SDK constructor source::upstream_only() sets empty reads and bounded outputs. This explicit form forbids source reads and an unbounded reason and requires bounded_outputs: true. An ordinary empty list without a reason remains invalid. The declaration grants no execution authority: native narrowing still requires complete observations or core-admitted fixed command semantics.

For compatibility with older published plugins, core accepts results without a declaration and treats those operations as unbounded. Their whole-target source keys retain the existing conservative behavior. The build records plugin <reference> <version> declared no reads, and one PLUGIN_READS_UNDECLARED warning per plugin per build asks users to update it. oyzu build --plan never runs a plugin, so it can't show this reason. This runtime fallback does not satisfy conformance for new or updated plugins.

Each read selector has kind (path or glob), a target-relative value, and confidence (exact or over-approximate). Paths cover their subtrees. Required writes, bounded_outputs, confinable and bound_dependencies fields retain their meanings. Optional env contains environment dependency names, never values. The internal Rust SDK supplies source::reads(selectors) and source::unbounded(reason) helpers; authors still declare output bounds and confinement explicitly.

A read prediction alone does not permit a narrow native key. A native stage needs complete observed reads after execution, unless its tool's own rules fix its read set. An observed path outside the prediction prevents storage and reports confined-read-outside-contract with the additive inputs fix. Unbounded stages retain the whole-target key. See action cache. The existing experimental wire version evolves in place; there is no legacy empty-read format to preserve.

Package and sign your plugin​

A package is the archive described in plugin packages: plugin.json plus one executable per platform.

The manifest (schema) requires:

FieldMeaning
identitypublisher, name and version. A builder reference is <name>/<profile>. The publisher oyzu is reserved for official releases (see below)
protocol_generationsMust include v1alpha1
profiles, rolesThe builder profiles you serve and, per role, the contract and features (for example go-test-events, captured-plan, build-options)
runtimesOne entry per platform: os (linux, darwin, windows), arch (amd64, arm64), optional abi (gnu, musl, msvc), entrypoint and its SHA-256 digest
requirementsBaseline tools needed whatever the project contains, with stages and a reason
effectsWhat the plugin needs: source-read, output-write, native-process, native-network. These limit what oyzu brokers; they don't remove a native executable's own operating system access
provenanceSource revision and maintainer

Example manifests for each first-party plugin are in the repository. tooling/package-plugin.py in the oyzu repository packages one built executable for the host platform and prints the archive digest:

python3 tooling/package-plugin.py --executable target/debug/oyzu-plugin-go --out go.tar.gz
# prints sha256:<archive digest>

To distribute your plugin through an OCI registry, publish a release root laid out as in the OCI package contract, with a Sigstore signature attached. Users then have two ways to trust it:

  • Bind it by tag. A tag outside ghcr.io/oyzuai/plugins/ needs a plugins.packages entry with the exact signer identity to require. Binding by digest trusts the digest instead. See OCI sources.
  • List it in an organization catalog. Your organization's tool index can list your package. For a publisher other than oyzu, the signed catalog's digest is the trust.

A package named oyzu/* always needs the official signature, on any registry. You can't publish under that publisher yourself.

Check it​

Before you ship a plugin, run it against the sample requests in the repository. oyzu-plugin-conformance <plugin-executable> docs/contracts/plugins-v1alpha1/examples (from the oyzu repository) sends every request.*.json through oyzu's real plugin launcher, so limits, deadlines and acceptance are the same as in a build. It checks that each result is valid and echoes its request, that the outcomes match the operations describe declares, and that the plugin is stateless (every request runs again in a new process in reverse order and must answer the same). It checks the protocol only. It runs no native tools, so it can't tell you whether your commands build anything. Then try the plugin in a real project through a local binding.

Where a refusal reason appears​

A plain oyzu build tries the host build first. If the plugin declines a target, the build continues on the isolated path, as oyzu build --isolated would, with the engine that path mounts. Without an [engine] pin in oyzu.lock or an installed engine, a Linux oyzu mounts its own executable (see execution image); on Windows and macOS the build stops with ENGINE_ASSET_UNAVAILABLE and how to install the Linux engine (oyzu engine install --linux). A pinned engine is installed only by an explicit isolated build, so a plain build with a pin stops with ENGINE_ASSET_UNAVAILABLE naming the pin and oyzu build --isolated.

If the isolated path can't take the target either (a raw executable binding has no isolated package, for example), the build fails during preparation, before any build action or tool installation, with the code above and the plugin's reason. The message lists every target the plugin kept off the host build, not only the first. A plugin that fails native-admission is named the same way. Human and --json output carry the same message. oyzu build --plan doesn't fail; its "Unresolved until preparation" list (unresolved in JSON) adds a Target <id> was not admitted to the native host lane: <reason> line for each one.

With --isolated or --all-platforms, oyzu selects the engine first without launching plugins, so you see the engine's own refusal until an engine is available: ENGINE_PIN_MISMATCH for a pin no admitted engine archive supplies, or ENGINE_ASSET_UNAVAILABLE on a host that can't mount itself. After that, a target that can't be planned fails with its PLUGIN_ISOLATED_UNSUPPORTED message and the same clauses. This asks each selected plugin for native-admission once if it isn't cached, and a hanging plugin can cost its full 60-second deadline per target.

Trust​

A binding runs the named executable with your user's permissions whenever oyzu discovers a workspace. Bind only executables you built or trust. The recorded digest says which bytes ran; it isn't a signature and grants nothing. The plugin gets no credentials and no inherited environment.

Limits​

  • The Go plugin builds only go/app with one module and one package main on the host. go/library and workspaces keep task execution through the plugin, but oyzu build refuses them.
  • Per-command env in native-build operations and the native-test command is refused.
  • Observation commands are matched by tool short name (go for oyzu:go) on the task's PATH. Oyzu doesn't verify that the resolved file belongs to the locked tool.
  • Ctrl-C (or SIGTERM and SIGHUP on Unix) stops a running plugin and its child processes. oyzu build reports a cancelled build.
  • If oyzu run or oyzu build --plan ends from a signal, the private copy of the bound executable (an oyzu-plugin-* temporary directory) isn't removed.
  • Diagnostics from successful operations aren't shown.

The Python plugin​

The Python plugin (python/package) builds pip and pyproject.toml projects into wheels with pytest and Ruff checks, using the same binding. It adds no installer, PATH change or PYTHONPATH bridge: dependencies, pytest, coverage and quality tools must already be in the project's environment, and a target-local .venv is used when present. A mismatched environment is refused. Direct oyzu run tasks don't use this binding. Tested on Linux amd64 (GNU). No Python plugin is published yet. See Python preparation and, for the isolated path, captured pip Python packages.

The Node plugin​

The Node plugin serves node/app for npm, pnpm and Yarn (Classic and Berry). It's experimental and isn't published yet, so you supply the package or a local binding.

The host build takes a node/app target that is declared with uses: node/app, isn't a workspace root, and has a non-empty scripts.build that writes dist. Anything else is refused with the plugin's reason, and because a plugin-served id has no fallback, that target can't build until it's changed or the binding is removed. Workspace projects and package output are covered on npm workspaces, pnpm, Yarn and plugin packages.

It builds on Windows and Linux x86-64. Windows ARM64, macOS and Linux ARM64 aren't tested.

What it runs​

ActionCommandWhen
<target>:installnpm ci, pnpm install --frozen-lockfile, Yarn Classic yarn install --frozen-lockfile or Berry yarn install --immutable. Offline handling follows the managerThe project has dependencies, devDependencies or optionalDependencies
<target>:buildThe selected build task, normally <manager> run buildAlways
<target>:testYour test script, or the detected defaultTests are selected
<target>:lintYour lint script, or the native ESLint or Biome adapterLint is selected
<target>:format-check or <target>:format:checkYour check script, or the native Prettier or Biome adapterFormat is selected. A script that changes files is never selected

The shared check levels decide which checks run, and --full runs every check that isn't off. Your own scripts win over the defaults. format:check, build:prod and similar names are kept; unsupported names fail discovery with an explicit error. An authored install task in oyzu.toml replaces npm ci, and disabling the install stage drops it. Authored tasks run with your ambient environment, not oyzu's pinned tools, so an authored npm ci can fail where the plugin's own install works (on Linux without a global npm: cannot execute npm: No such file or directory).

The artifact is the dist directory your build script writes (project-written outputs), named application-<version> from the version oyzu resolved (0.0.0-dev.g<source hash> for an unversioned checkout), not the version in package.json.

Lock files​

Dependencies need the manager's lock file, or planning fails before any action with a diagnostic like node.lock-file: host npm dependency preparation requires package-lock.json; create it with npm before building.

  • npm: package-lock.json (an npm-shrinkwrap.json alone isn't enough).
  • pnpm: pnpm-lock.yaml. A stale lock fails the install (--frozen-lockfile) and isn't rewritten. Update it with pnpm, then retry.
  • Yarn: yarn.lock.

pnpm​

  • If packageManager is present it must be an exact stable release such as pnpm@10.11.0. Oyzu checks it against explicit tool configuration, and a conflicting release fails before any action. Ranges, tags and prereleases are refused. Without packageManager, select pnpm in [tools].
  • A pnpm-workspace.yaml that contains only settings is allowed. A packages key, or anything oyzu can't classify as settings, makes the project a workspace and it's refused. Competing manager evidence is also refused.
  • pnpm owns install scripts and their policy. Oyzu adds no script approval.
  • Offline builds add --offline and need the dependencies already in pnpm's own store. Missing bytes fail without going online. This is the host's ordinary pnpm configuration and store, not a hermetic replay, and --no-cache doesn't clear it.

Yarn​

  • Accepted exact releases: yarn@1.22.22 (Classic) and yarn@4.17.1 (Berry). Berry needs nodeLinker: node-modules in .yarnrc.yml (a quoted value is fine). Plug'n'Play is refused. See managed Yarn.
  • Direct tests need dependencies installed in the source project. A full build installs into a private workspace. For Berry, run yarn install --immutable, then oyzu run test.
  • Not supported: isolated Yarn builds, extra rc settings, workspaces on this path, project plugins, yarnPath, custom registries and non-registry sources.

Vite​

An npm project whose build script is recognized vite build, with an optional literal --outDir, Vite as a dependency and a native Vite 8 configuration, builds as an application. Oyzu keeps the npm lifecycle around one Vite build and stages the output after the native postbuild step. Tested with Vite 8.3.3. Other Vite flags, pnpm or Yarn with Vite, SSR, library and multi-environment builds, and watch or no-write modes aren't supported. See Node applications.

Tests and quality checks​

For non-workspace npm, pnpm and Yarn targets, oyzu run test adds JUnit and LCOV reporting to a default node --test, to flag-only test scripts it recognizes, and to exact vitest and vitest run commands. See Vitest and Jest for those frameworks (Vitest was tested with npm and Vitest 5.0.3; Jest with npm and Jest 29.7.0). The matching coverage provider must already be installed, because oyzu doesn't download it. pnpm and Yarn pass reporter flags directly after <manager> run test, with no npm-style -- separator.

  • Other test commands run unchanged. They can write to OYZU_TEST_REPORT and OYZU_COVERAGE_REPORT or to report paths you declare.
  • A missing optional report makes the evidence incomplete. A missing required report, a malformed report or a failing test fails the command.
  • Workspace tests and other managers fail with node.test-lane.
  • Lint and format checks use your project's installed ESLint, Prettier or Biome. A directory you point OYZU_NODE_QUALITY_HOME at can supply packages the project doesn't declare. A declared but uninstalled package fails instead of falling back. Native configuration and ignore files are authoritative. oyzu run format changes source; format-check doesn't.
  • To run a named task such as format:check, use oyzu run app:format:check or [tasks."app:format:check"]. Environment defaults from native files go through the normal configuration and policy checks; reserved OYZU_* names stay unavailable.

Repository source bootstrap​

This section is for people working on the oyzu repository itself. Releases use the shared package store instead.

tooling/bootstrap-oyzu.sh uses an oyzu on PATH or in .oyzu/bin that can read this checkout's configuration. Without one it downloads the newest release's oyzu and oyzu-shim into .oyzu/bin, checking each against the digest the release reports, and builds from source only when no release executable can be used here (--source never downloads, so it builds whenever no usable oyzu is already there). On Linux it then installs the published rust/app and node/app releases that oyzu.lock selects into the plugin store, from the release digests pinned at the top of the script, through a temporary user file that binds only them; your own configuration isn't changed. A failed install is only a warning. A source build makes the CLI, native shim, Rust plugin and Node plugin (this repository declares both a cli and a docs build, so both builders must resolve before oyzu build cli). It compiles with the pinned Rust, locked and offline, and honors CARGO_TARGET_DIR and CARGO_BUILD_TARGET. It needs no Python, Node or jq just to read configuration; only the Linux plugin installation above and the read-back in the CI machine binding below use Python.

On a machine with no user configuration file and no existing plugin choices, the script writes the two development bindings to .oyzu/bootstrap/config.toml and prints the OYZU_USER_CONFIG export (or records it through CLAUDE_ENV_FILE, or through GITHUB_ENV for later GitHub Actions steps). It doesn't touch your own user configuration, project or local files, or shell profiles. If any step fails, it removes the file it created. Running it again with the same unchanged file prints Reusing this checkout's unchanged bootstrap USER file and the same export.

oyzu run bootstrap (on macOS and Windows, or with --source) uses the same file, but once it has packed .oyzu/bin/oyzu-plugin-rust.tar.gz the file binds rust/app to that package archive so isolated builds work (see refreshing the oyzu on your PATH). An earlier file with the executable binding is rewritten then; the script above keeps using whichever binding the file has.

If you already have a user configuration file or other plugin choices, the script refuses instead of merging. Bind the two plugins yourself, then run it again; with both present it passes them through. From the checkout root:

oyzu=.oyzu/bin/oyzu        # .oyzu/bin/oyzu.exe on Windows
bin="$(pwd -W 2>/dev/null || pwd)/.oyzu/bin"
"$oyzu" config set --global plugins.development.rust/app "$bin/oyzu-plugin-rust"   # add .exe on Windows
"$oyzu" config set --global plugins.development.node/app "$bin/oyzu-plugin-node"   # add .exe on Windows
tooling/bootstrap-oyzu.sh

Or edit the user file by hand:

[plugins.development]
"rust/app" = "/home/me/src/oyzu/.oyzu/bin/oyzu-plugin-rust"
"node/app" = "/home/me/src/oyzu/.oyzu/bin/oyzu-plugin-node"

In CI the user file is ignored, so the script refuses fresh user setup there; a CI job uses the machine binding below instead.

CI machine binding​

Pass --ci-machine-binding (used by the repository's own setup action and release workflows) to bind the Rust and Node plugins in machine configuration on a GitHub Actions runner (GITHUB_ACTIONS=true; anywhere else the switch does nothing). Before the configuration check above, the script:

  1. Checks that the runner is ephemeral: a GitHub-hosted runner (RUNNER_ENVIRONMENT=github-hosted), or a runner image that declares itself ephemeral with a root-owned, read-only /etc/oyzu-runner-ephemeral and provides a machine directory owned by the runner user, as the repository's self-hosted runner image does with /etc/oyzu. Owning the machine directory alone isn't enough. Otherwise it fails and writes nothing.
  2. Refuses an existing machine config.toml or an existing plugin copy. It never merges into or replaces machine configuration.
  3. On Linux, binds the published rust and node plugin releases: it creates the machine config.toml with only [plugins.packages] entries for rust/app and node/app, each an oci reference to ghcr.io/oyzuai/plugins/<name> pinned by release root digest (the digests live at the top of tooling/bootstrap-oyzu.sh). Oyzu downloads each release on first use and checks its official signature; nothing is built, and a Linux run with no recorded digest fails instead of building. The script then runs oyzu build for a target that does not exist, which installs the bound plugins during plugin selection and stops before building anything (a plan or task only replays installed plugins), and requires oyzu plugins current to report both installed. oyzu.lock must hold their selections. Update the digests and lock when a new plugin release is published.
  4. On macOS and Windows, which have no published plugin payload yet, builds both plugins from this checkout (and the CLI too, unless a published release's oyzu is in use), copies oyzu-plugin-rust and oyzu-plugin-node into the machine directory's plugins/ folder (/Library/Application Support/Oyzu/plugins on macOS and %ProgramData%\Oyzu\plugins on Windows) and creates the machine config.toml with [plugins.development] entries naming those copies. The script says that it is building from source.
  5. Reads the configuration back with oyzu --json config explain for plugins.packages or plugins.development (parsed with Python, which GitHub-hosted runners and the runner image provide) and requires exactly those two values, from machine scope only. The configuration check must then report the choices complete (unchanged), or the script fails.

Machine configuration isn't personal configuration, so CI keeps it. The binding lasts as long as the runner, and a GitHub-hosted runner or runner container is discarded after its job. This applies only to these executable bindings on ephemeral runners.

A refused source-built run keeps the executables it built in .oyzu/bin. If it used an oyzu already on your PATH, it built nothing, so check that both plugin files exist. Remove those entries to stop using the checkout's plugins; the script never edits or removes them.

Bootstrapping without plugins​

Pass --no-plugins instead (it cannot be combined with --ci-machine-binding) when a job needs only the bootstrapped oyzu for oyzu install and oyzu exec and builds its own plugin payload, as the plugin release build does. The script then writes no machine configuration, creates no bootstrap USER file and builds no plugin from source, on any platform. Commands that select the Rust or Node plugins (oyzu build, oyzu run) fail in such a job until the plugins are bound.
