Writing and testing builder plugins

CLI reference

Published from the canonical docs/reference/plugin-development.md file. Features marked experimental remain experimental; check support limitations before relying on them.

A builder plugin is a separate program that tells oyzu how to build one kind of project: which tasks it has, which tools it needs, which command builds it and where the output lands. This page shows how to run a plugin from a local path while you develop it, how plugins work, what a plugin has to provide, and how to package it. It also covers the Node plugin's behavior, since it's the largest first-party plugin.

Note: The plugin interface (plugins-v1alpha1) is experimental. It's edited in place and can change without a new version. The Rust crates in the oyzu repository that help write plugins are internal and not a supported SDK. You can write a plugin in any language that speaks the JSON contract below.

Run a local plugin​

The same plugins-v1alpha1 process envelope also defines a deployer role. Its target-plan, target-apply and target-read-back operations take frozen opaque JSON settings, core-resolved tool paths and a staged tree inventory. A target's kind resolves <kind>/site, or explicit uses selects its binding and profile. The selected deployer validates target-specific settings. Planning returns the current revision and added, changed and removed paths; read-back returns the complete observed file digests. Core owns evidence enforcement, signed intent and records, and the comparison with the subject. A deployer never decides that verification passed. Builder plugins return unsupported for these operations. A credential-free plan may return credential_url with an empty diff before reading live state.

Deployer descriptions declare credential_hosts, for example [{"origin":"https://github.com","setting":"repository"}]. The setting field names a target setting, following the publisher host-to-setting binding. The description comes from the admitted package's executable, whose bytes are covered by package admission. An omitted or empty list authorizes no credential origin. Core validates each declared HTTPS origin and refuses any credential URL outside that list or inconsistent with an explicit URL in the named setting, before resolving tokenEnv. Shorthand is checked against the declared origin.

Core admits the recipient, opens transport, and repeats planning; the intermediate plan is never signed or applied. Transport environments contain only the host-bound reverse proxy URL, never credential values. Git uses OYZU_DEPLOY_PROXY_URL; core attaches the tokenEnv credential upstream without an OIDC fallback. Only target-apply receives write authority. Read-back must use fresh core observations after writes close; core also fetches and compares the Git inventory independently. Requests outside the declared destination and bodies above 64 MiB are refused. See deployment limits.

Bind your executable to a builder reference in your user configuration (~/.config/oyzu/config.toml on Linux, ~/Library/Application Support/Oyzu/config.toml on macOS, %APPDATA%\Oyzu\config.toml on Windows, or the file OYZU_USER_CONFIG names):

[plugins.development]
"go/app" = "/home/me/src/oyzu/target/debug/oyzu-plugin-go"
"node/app" = "/home/me/src/oyzu/target/debug/oyzu-plugin-node"

Then build as usual:

oyzu build
oyzu build --full
oyzu run test

Oyzu runs your executable for that reference instead of a catalog package. The build shows the plugin-owned output directory in its commands (for example go build -trimpath -buildvcs=false -o .oyzu/native/plugin/…), the Context facts in dist/logs/events.jsonl include Plugins go/app → local development <path> (sha256:…), and the plan, envelope and manifest carry extensions["oyzu.dev/plugins"] (see plugin packages).

Remove the entry to stop using the local executable. The next build then has to find the package some other way: the catalog, a plugins.packages binding or the lock. There's no built-in fallback.

Setting​

KeyTypeDefaultWhere
plugins.developmentTable of builder reference to absolute executable or package archive pathnoneUser, machine or administrative configuration
  • Keys are short builder references without a major version (go/app, not go@1/app or an OCI reference). Values are absolute paths. At most 64 entries.
  • The setting selects code to run, so a project oyzu.toml, oyzu.local.toml or a profile is refused with CONFIG_SCOPE: plugins.development is not permitted in this scope.
  • In CI, user configuration is ignored as usual; a machine-level binding still applies. Pass --ci-machine-binding to the repository bootstrap to create one on an ephemeral runner (see CI machine binding).
  • The table is replaced as a whole by a later source.
  • Bindings are read once per command, before targets are discovered. A missing or unreadable executable fails with PLUGIN_BINDING_INVALID; a malformed or versioned key fails with CONFIG_INVALID_VALUE.
  • A local binding has no download, signature check or oyzu.lock entry. An executable is recorded by file name and SHA-256 digest only, with no manifest check.

Binding a package archive​

A development binding can also name a plugin package archive (a .tar.gz with plugin.json and its members). Use this when you want --isolated builds with your plugin: a raw executable has no Linux member or captured-plan manifest, so an isolated build refuses it with PLUGIN_ISOLATED_UNSUPPORTED.

[plugins.development]
"rust/app" = "/home/me/src/oyzu/.oyzu/bin/oyzu-plugin-rust.tar.gz"
  • Oyzu recognizes the archive by its gzip header and installs it, with the manifest, layout and host-member checks a bound package gets, into a private folder that is removed when the command ends. Nothing goes into the shared package store or oyzu.lock, and no digest is pinned, so rebuilding the archive takes effect on the next command.
  • The host member runs host builds; the member for the execution image's platform runs isolated ones. The binding is still recorded as local development, with the host member's digest.
  • An archive that isn't a valid package for that reference fails with PLUGIN_BINDING_INVALID and the reason.

Independent profiles​

A plugin doesn't have to match a built-in family. To develop a new profile such as independent/app, bind its id and name it in build.yaml. The names and path are illustrative:

[plugins.development]
"independent/app" = "/home/me/src/plugin/target/debug/independent-plugin"
builds:
  app:
    uses: independent/app

Run oyzu build app to build with it. An independent profile must be named in uses; the binding adds no detection, no with options, no dependency preparation and no isolated execution. Tool versions still come from your configuration or native files, and oyzu installs the tools the plugin's requirements answer names under the usual policy. A local binding can't ask oyzu to run task-command observations (see below), even for an installed tool.

When tools.allowed is set, oyzu run admits a task of a plugin-built target only if every tool the plugin's requirements declare for that task is on the list. A task whose binding declares no tool for it is refused with CONFIG_OVERRIDE_DENIED before anything launches. Registry routes and approved catalogs stay fail-closed for local bindings, as for any other builder.

How a plugin works​

For every operation, oyzu starts your executable once, with no arguments, a minimal environment and a fresh scratch directory as its working directory. It writes one JSON request to standard input and reads one JSON result from standard output. The process gets no credentials.

StreamContent
Standard inputOne request, then end of input
Standard outputOne result and nothing else
Standard errorDiagnostic lines as JSON. Other lines are kept only for troubleshooting
  • Documents use snake_case, schema_version: "v1alpha1" and a constant type. Unknown members, duplicate keys, null members and numbers written with a fraction or exponent are invalid.
  • A request carries an operation_id, role (builder), operation, required_features, deadline_ms, the target (name, uses, whether the reference was inferred or explicit, absolute native-context source root, an optional relative path, and the base version) and the operation's input. Your result echoes operation_id and operation and has an outcome: completed (with output), failed (with error{code, message}), unsupported (with reason) or, for task-command, observe.
  • target.root is the dependency owner's native context source view. target.path selects the declared target folder relative to it, using / separators and an empty string when they are equal. Core omits an empty path, preserving the existing request bytes for target-local contexts. Absolute paths, drive prefixes, backslashes, ./.. components and repeated or trailing separators are refused.
  • A nonempty path requires the builder role's target-path feature in the selected package manifest and request. Captured planning also requires captured-plan. Core checks the manifest before sending the target. The SDK refuses nonempty paths by default; a builder opts in only when it implements this root/path distinction. Go supports command packages below a module root; other first-party builders retain their existing target-local behavior.
  • Manifest role features are requirements on the engine for the entire package; they are not optional advertisements. Request required_features names what that individual call requires from the plugin. A package declaring target-path therefore needs an engine implementing it even for an empty target path. Older engines must use a compatible plugin release; omitting path preserves the request format but does not bypass package preflight.
  • Rust packages that emit native private_outputs require the builder role's native-private-outputs engine feature in both their manifest and describe response. The catalog and cold/warm package preflight use the same engine capability check, so an older engine excludes such a release before invoking a plugin role and can select an older compatible preview. This requirement identifies implemented wire/host-stage support; it grants no execution, source, cache or publishing authority. Release a core implementing the feature before publishing the marked Rust package.
  • Oyzu accepts a result only if it's valid, the process exited with status 0 and the ids match. A valid result followed by a nonzero exit is a failure.
  • Rust packages implementing deferred captured version projection require captured-cargo-projection in both their manifest and describe builder features. A compatible engine supplies the optional captured_projection control map and requires that feature on the captured-plan request. The package must copy those exact controls before every Cargo consumer, retaining mutation-carrying prerequisites. The engine validates the complete mapping and graph. Unmarked packages retain their existing projected-overlay preparation; they receive no optional projection facts. Publish a compatible core before publishing the marked package. This feature grants no acquisition or arbitrary filesystem-copy authority and changes no host finalization behavior.
  • Limits: 16 MiB for a request or result, 1 MiB of kept diagnostics, at most 64 observations. Oyzu never truncates and accepts.
  • Each operation has a deadline (60 seconds by default). At the deadline, or when the build is cancelled, oyzu terminates the whole process tree (SIGTERM, then SIGKILL after 2 seconds on Unix; the job object on Windows). Termination is a failure whatever the process wrote.
  • Plugins keep no state between calls. Oyzu supplies every fact each time.
  • Target-relative paths use /, never .. or spaces, and at most one leading dot per segment.

Operations​

An operation you don't implement answers unsupported.

OperationCalled toYour answer

Native and captured test operations may declare test_units in the existing v1alpha1 contract. During preparation, report each compiled test executable with its digest and an executable_digests map from runtime executable name to digest. The native inventory is authoritative: core runs undeclared compiled units without reuse and keeps per-unit reuse for known compiled units. Malformed names, duplicate names and invalid digests still fail validation.

Bounded runtime reads require an enforced captured view; native units must give an unbounded reason. Shared setup reads belong to every affected unit. The combined JUnit report labels each suite with oyzu.unit and oyzu.outcome properties (ran, reused or failed) so its summary preserves each unit's counts. Core never stores failed units. Hooks and authored tasks keep the ordinary stage cache instead of per-unit reuse. See test-unit caching.

What oyzu keeps for itself: the build version (the plugin must echo it), where output is written, scheduling, tool installation, running processes, collecting artifacts and the report gates. The plugin supplies intent: tasks, requirements, commands, artifact paths and report formats. Report formats are junit, cobertura, lcov, go-cover and jacoco; sources are file, go-test-events, jest-json and jest-lcov. A plugin that needs nonempty with options must declare the build-options feature.

Captured intent permits textual version interpolation only when the complete core version contains its recorded per-build source hash. Core can narrow that hash after the final read contracts are known, then rebind command, environment, native payload and artifact strings with the decisions before computing action keys. An unmarked plain version such as 1.0.0 retains the whole-target version and plan: the same text may identify a dependency or be part of a path. oyzu cache explain records this fallback rather than treating those occurrences as interpolation sites. Plugins must keep native version projection in executable intent, so output bytes embed that same bound version. Helm's captured stage command carries the version it writes into its private chart; it never rewrites the source chart.

A task-command observation names a core tool identity and its command line. Oyzu checks that the tool is one the builder may use and that argv[0] is that tool's command, runs it once on the task's PATH (stdout up to 1 MiB, stderr up to 64 KiB), then calls task-command again in a new process with the results. One round only. A local development binding may not use observations.

Artifacts must have unique names and sources (compared without regard to case). A default artifact lives inside output_dir. An artifact marked executable is promoted to .oyzu/bin after a successful build.

Project-written outputs​

Some builds decide their own output location: npm run build writes dist, and the plugin can't steer it into output_dir. For those, the plugin marks the artifact "origin": "target" with a target-relative source, and the build operation runs the task's own command (oyzu sends it as input.task.argv):

{"name": "primary", "producer": "build", "kind": "directory",
 "filename": "application-1.4.0", "media_type": "application/octet-stream",
 "source": "dist", "executable": false, "origin": "target"}

Before any build action runs, oyzu checks the source and refuses it otherwise:

RuleRefused with
It names something below the target: not ., no segment that starts or ends with a dot (.git, .oyzu), is node_modules (any case) or is a Windows device name (con, nul, COM1.txt)PLUGIN_OPERATION_FAILED: … invalid result
Sources are unique, ignoring casePLUGIN_OPERATION_FAILED: … invalid result
It doesn't equal, contain or lie inside output_dirPLUGIN_OPERATION_FAILED: … overlaps the output directory
It doesn't equal, contain or lie inside a file or directory of the target's source selectionPLUGIN_ARTIFACT_REFUSED: … overlaps the frozen source selection at <path>
No existing segment is a symbolic link or reparse point, and none above the last is a filePLUGIN_ARTIFACT_REFUSED: artifact … names …

Oyzu then moves anything already at the path into a fresh directory beside the output (never deleting in place) and discards that directory after collection. The plan records moved paths under extensions["oyzu.dev/retired-outputs"]. A build whose script writes nothing fails with native artifact collection failed rather than republishing an old output. Collection then applies the usual rules: no links, no reserved names.

On the native host lane the target directory is a private copy rebuilt from the selected source before each build, so nothing is ever moved there and previous is always false. In an isolated build, the output is moved aside in the private execution workspace, never in your project. To recover from a refusal, name a project output that isn't source, version control state or a dependency tree, and remove any link in its path.

Selected native tasks​

A host native-build operation with neither command nor engine selects the target's existing task of that name. For build, this is the actual selected build task, including its working directory, environment and report obligations; it does not create a task or allow an unavailable task to run. Explicit plugin commands keep their existing native invocation bindings.

Native package facts​

tasks can report native_package with an optional name and version and the file (origin{path,digest,location}) they came from. Oyzu checks that the file is inside the supplied source and that its digest matches. A missing declaration stays unknown, even when the target's version is 0.0.0. The Node plugin reports package.json; the Go plugin doesn't. See version inference.

Caching and cost​

Targets built by a plugin are reused from the local action cache like other targets. The cache key includes the plugin's executable digest and runtime, so rebuilding the plugin reruns its targets. Bind the executable itself, not a wrapper script, because a script's digest doesn't cover the program it starts (see external builder targets). An unchanged one-module rebuild launches the plugin five times (tasks, requirements, native-admission, native-build, and one task-command per command; two when the command asks for an observation). Launches scale with the number of plugin targets.

Per-operation source contracts​

Every BuildOperation must carry contract, a SourceContract. Declare a complete locked command set with optional tools, including commands launched indirectly. A complete stage keys only these admitted commands, not sibling stages' tools. Managed sibling PATH entries are omitted from computation identity unless the stage explicitly declares a PATH data read. The selected builder's verified package identity always remains bound. Complete stages also omit sibling check selection (checks.run) and unrelated package bindings (plugins.packages) from computation configuration; execution and policy constraints stay binding. Omit tools when completeness is unknown; core retains whole-lock cache keys. An explicit empty array declares that no locked command is resolved. Core binds named commands to its own retained verified installations; a plugin cannot supply an installation identity or grant itself tool access. Missing admitted commands keep the fallback. The SDK's source::tools(contract, names) helper records this declaration. Source-read bounds remain a separate claim.

Declare a non-empty reads list, unbounded_reason with a non-empty explanation such as "not analyzed yet", or upstream_only: true for an operation that reads no source and only consumes declared upstream outputs. The SDK constructor source::upstream_only() sets empty reads and bounded outputs. This explicit form forbids source reads and an unbounded reason and requires bounded_outputs: true. An ordinary empty list without a reason remains invalid. The declaration grants no execution authority: native narrowing still requires complete observations or core-admitted fixed command semantics.

An unbounded_reason must contain 1 to 4000 Unicode characters and must not be blank. Rust plugins can use source::unbounded_reason(reasons) to trim, deduplicate and sort explanations, supply a fallback for an empty or blank set, and summarize long sets with an (and N more) suffix. It keeps complete reasons where possible; a single oversized first reason gets a character-safe preview and also counts toward omitted reasons. source::unbounded(reason) uses the same formatter. Summarizing the explanation does not narrow the source boundary.

For compatibility with older published plugins, core accepts results without a declaration and treats those operations as unbounded. Their whole-target source keys retain the existing conservative behavior. The build records plugin <reference> <version> declared no reads, and one PLUGIN_READS_UNDECLARED warning per plugin per build asks users to update it. oyzu build --plan never runs a plugin. Its source reasons describe the stage contracts in that target's last retained build plan, so a later preview can show the recorded reason. Without a recorded contract, it says reported when the builder answers. Historical reasons do not prove current source completeness or cache admission. This runtime fallback does not satisfy conformance for new or updated plugins.

Each read selector has kind (path, glob or listing), a target-relative value, and confidence (exact or over-approximate). Paths cover their subtrees. A listing covers direct entry names and kinds, without file contents or descendants; listing-only captured entries are empty placeholders. Read and write selectors must remain target-relative: .. is refused for paths, globs and listings. A source projection narrows the target's own folder and does not admit parent traversal. Required writes, bounded_outputs, confinable and bound_dependencies fields retain their meanings. Optional env contains environment dependency names, never values. The internal Rust SDK supplies source::reads(selectors) and source::unbounded(reason) helpers; authors still declare output bounds and confinement explicitly.

Native Cargo admission checks full-target input authority separately from output bounds. Compile and quality stages retain bounded outputs. The deferred test stage retains the same input authority with unbounded outputs, so arbitrary test effects use the existing always-run path rather than reusable results. Neither declaration permits narrower confinement or substituted native controls.

A read prediction alone does not permit a narrow native key. A native stage needs complete observed reads after execution, unless its tool's own rules fix its read set. An observed path outside the prediction prevents storage and reports confined-read-outside-contract with the additive inputs fix. Unbounded stages retain the whole-target key. See action cache.

For native host stages, use oyzu_plugin_sdk::source::observed(selectors) when the action reports its complete reads after each successful run. Core sets OYZU_OBSERVED_READS to a fresh output file path. Write this JSON there:

{"complete": true, "paths": ["src/main.rs"], "listings": ["assets"], "reasons": []}

Both path lists are relative to the action cwd; core rebases them to the target and captured workspace before prediction checks and evidence recording. Set complete: false and explain unknown reads in reasons when the tool cannot account for them. Missing, invalid, empty or incomplete reports, and nonempty reasons, keep whole-target behavior and retire prior admission. The protocol's ObservedReads type and report schema own this format. Core saves a complete report only within the declared prediction and only for the same action definition. Outside-prediction reads prevent sealing a narrowed result. On a whole-target run, they retire admission without failing that covered run.

Use source::fixed(selectors, rule) for tools whose own rules fix their reads; name the rule in a short, nonblank string. This needs no runtime report. Without either basis, native predictions stay whole-target. A basis requires a native command and cannot accompany unbounded_reason or upstream_only. Source-free exports use the separately admitted upstream-output contract.

For native host execution, set BuildOperation.private_outputs to the exact regular files the stage must retain in the target workspace for its consumers. Paths are target-relative; glob patterns and directory outputs are unsupported. Some(vec![]) opts in a check with no retained files; omission keeps the shared workspace. Reports and artifacts still use their existing collection contracts. This is a builder fact, not an execution capability: core requires a stage contract with bounded outputs and admitted producers. Private execution and narrow keying are separate: a stage without a native read basis can still run privately with its whole-target key and action configuration identity. Only observed or fixed reads without an unbounded reason admit a narrow key. Source-free copy/export stages instead declare upstream_only. Every producer must also be admitted; a consumer of an unadmitted producer remains shared. Declare all generated inputs through the existing action relations. Core validates portable file paths and retains files through the existing contained output collector. A producer feeding a private consumer must declare nonempty private_outputs, and its referenced output port must exist. Only that producer's named paths consumed by the consumer must be covered; the consumer's own source reads and another producer's paths need not be outputs of this producer. Multiple producers contribute their respective files. A source-free export consumes its producer's complete output port, so every named write must be covered. Uncovered paths or selectors whose complete coverage cannot be established keep the consumer shared. A source-free export still requires empty reads/writes, no confinement or dependency-bound authority, and no private-output or dependency-file command capability.

The prepared source projection remains immutable throughout execution. Shared stages and cache restores use a separate retained root, so an executing private fork can be populated lazily from the pre-run source even after shared writers have run. Projection digests transfer with unchanged bytes and metadata; copied inode/ctime identities do not cause another content hash. A reused producer shares its verified staged bytes without copying output payloads; a consumer that executes requests the handoff. An unexecuted retained fork is never a fallback for a missing verified handoff. Private completion captures only its finite files, so concurrent shared writers cannot enter that action's result.

Mixed targets retain each shared stage's whole-target source key while admitted private stages use their own native read keys after read admission, or retain the whole-target key without a read basis. Missing output declarations and unadmitted producers refuse private execution; unknown reads only refuse narrow keying. Hooks, replacements and materialized inputs keep the target-wide fallback. Shared native actions follow every dependsOn edge, including OrderOnly. Private branches with a native read basis do not inherit producers through order-only siblings; real producer edges still count. Private stages without a read basis preserve the existing whole-target dependency closure. For a bounded private stage with a native read basis, omitted relations refines the default mutable-workspace sequence to order-only edges. This lets a source-only formatter follow an unbounded build or test without importing their results or their producers into its key. Explicit Produced and Sequence relations, authored task dependencies, hooks and replacement boundaries retain their data dependencies; the private opt-in does not erase them. Declare generated inputs explicitly rather than relying on the default pipeline sequence.

For example, a Zig formatter with fixed reads and no retained files opts in with operation.private_outputs = Some(vec![]); build and test can remain unbounded. The same opt-in works for source-only Go build and vet stages with observed reads, and gofmt with fixed reads. An observed stage needs a complete read report from its own successful execution before publishing a narrow result. The next unchanged build can reuse that result. These examples describe the core contract; each plugin must emit its own opt-in and read declarations. Release core support for private_outputs before plugins that emit it; older cores reject unknown wire fields. No new schema version is introduced.

SourceSelectorKind::Listing declares only direct entry names and kinds in the named directory (. for the cwd). It reads neither contents nor descendants. Use a separate path or glob selector for contents. A captured listing exposes empty files and directories, preserving names and kinds while hiding contents. Observed listings require an exact listing selector, a path on the directory or an ancestor, or a glob that provably matches every direct child (dir/*, dir/**, or an ancestor **). A glob matching only the directory name does not predict its listing. These contract additions reach users with each plugin's next release. Release core first: older cores reject unknown native fields, including native_reads, Cargo final_projection and development_compile. The Rust core and plugin must both support the declared-version compile/final projection graph. A Rust plugin emitting it must follow a core release supporting it.

On the native host path, core omits final_projection only for an admitted plain local development result. The plugin still names its stage compile-development and exports its indexed binary directly. Core records its actual compiledVersion separately from the inferred artifact version; stamped consumers reject that marker. When final_projection is present, the exported binary must follow the final stage. Plugins cannot choose development eligibility or remove the inferred OYZU_VERSION binding.

The existing experimental wire version evolves in place; there is no legacy empty-read format to preserve.

Package and sign your plugin​

A package is the archive described in plugin packages: plugin.json plus one executable per platform.

The manifest (schema) requires:

FieldMeaning
identitypublisher, name and version. A builder reference is <name>/<profile>. The publisher oyzu is reserved for official releases (see below)
protocol_generationsMust include v1alpha1
profiles, rolesThe builder profiles you serve and, per role, the contract and features (for example go-test-events, captured-plan, build-options)
runtimesOne entry per platform: os (linux, darwin, windows), arch (amd64, arm64), optional abi (gnu, musl, msvc), entrypoint and its SHA-256 digest
requirementsBaseline tools needed whatever the project contains, with stages and a reason
effectsWhat the plugin needs: source-read, output-write, native-process, native-network. These limit what oyzu brokers; they don't remove a native executable's own operating system access
provenanceSource revision and maintainer

Example manifests for each first-party plugin are in the repository. tooling/package-plugin.py in the oyzu repository packages one built executable for the host platform and prints the archive digest:

python3 tooling/package-plugin.py --executable target/debug/oyzu-plugin-go --out go.tar.gz
# prints sha256:<archive digest>

To distribute your plugin through an OCI registry, publish a release root laid out as in the OCI package contract, with a Sigstore signature attached. Users then have two ways to trust it:

  • Bind it by tag. A tag outside ghcr.io/oyzuai/plugins/ needs a plugins.packages entry with the exact signer identity to require. Binding by digest trusts the digest instead. See OCI sources.
  • List it in an organization catalog. Your organization's tool index can list your package. For a publisher other than oyzu, the signed catalog's digest is the trust.

A package named oyzu/* always needs the official signature, on any registry. You can't publish under that publisher yourself.

Check it​

Before you ship a plugin, run it against the sample requests in the repository. oyzu-plugin-conformance <plugin-executable> docs/contracts/plugins-v1alpha1/examples (from the oyzu repository) sends every request.*.json through oyzu's real plugin launcher, so limits, deadlines and acceptance are the same as in a build. It checks that each result is valid and echoes its request, that the outcomes match the operations describe declares, and that the plugin is stateless (every request runs again in a new process in reverse order and must answer the same). It checks the protocol only. It runs no native tools, so it can't tell you whether your commands build anything.

The examples include ecosystem-specific intent. Prepare a fixture directory for the plugin's supported profiles: retain the describe request, supply real source roots when the plugin reads source, and translate generic examples only where their intent applies. Preserve profile-specific facts and inferred/explicit selection; an inferred Node package may intentionally omit its build task. Do not translate another ecosystem's workspace or prepared facts by merely renaming its profile. describe must list itself among the builder's supported operations.

To check all nine in-repository builder plugins, activate oyzu's shell and run cargo test --locked -p oyzu-plugin-conformance --test first_party -- --nocapture from the repository root. This builds their plugin executables, prepares temporary projects and native facts for the applicable canonical requests, and prints each plugin's verdict through the same harness. Go's native-context and multi-binary regressions stay with the Go fixtures; other ecosystems do not inherit Go-specific target-path requirements. It runs no native application builds. Python's translated test tasks use python -m pytest; the native and captured fixtures require its pytest adapter and mandatory JUnit/Cobertura report intent.

Then try the plugin in a real project through a local binding.

Failures and recovery​

ErrorCauseRecovery

Where a refusal reason appears​

A plain oyzu build tries the host build first. If the plugin declines a target, the build continues on the isolated path, as oyzu build --isolated would, with the engine that path mounts. Without an [engine] pin in oyzu.lock or an installed engine, a Linux oyzu mounts its own executable (see execution image); on Windows and macOS the build stops with ENGINE_ASSET_UNAVAILABLE and how to install the Linux engine (oyzu engine install --linux). A pinned engine is installed only by an explicit isolated build, so a plain build with a pin stops with ENGINE_ASSET_UNAVAILABLE naming the pin and oyzu build --isolated.

If the isolated path can't take the target either (a raw executable binding has no isolated package, for example), the build fails during preparation, before any build action or tool installation, with the code above and the plugin's reason. The message lists every target the plugin kept off the host build, not only the first. A plugin that fails native-admission is named the same way. Human and --json output carry the same message. oyzu build --plan doesn't fail; its "Unresolved until preparation" list (unresolved in JSON) adds a Target <id> was not admitted to the native host lane: <reason> line for each one.

With --isolated or --all-platforms, oyzu selects the engine first without launching plugins, so you see the engine's own refusal until an engine is available: ENGINE_PIN_MISMATCH for a pin no admitted engine archive supplies, or ENGINE_ASSET_UNAVAILABLE on a host that can't mount itself. After that, a target that can't be planned fails with its PLUGIN_ISOLATED_UNSUPPORTED message and the same clauses. This asks each selected plugin for native-admission once if it isn't cached, and a hanging plugin can cost its full 60-second deadline per target.

Trust​

A binding runs the named executable with your user's permissions whenever oyzu discovers a workspace. Bind only executables you built or trust. The recorded digest says which bytes ran; it isn't a signature and grants nothing. The plugin gets no credentials and no inherited environment.

Limits​

  • The Go plugin builds only go/app with one module and one package main on the host. go/library and workspaces keep task execution through the plugin, but oyzu build refuses them.
  • Per-command env in native-build operations and the native-test command is refused.
  • Observation commands are matched by tool short name (go for oyzu:go) on the task's PATH. Oyzu doesn't verify that the resolved file belongs to the locked tool.
  • Ctrl-C (or SIGTERM and SIGHUP on Unix) stops a running plugin and its child processes. oyzu build reports a cancelled build.
  • If oyzu run or oyzu build --plan ends from a signal, the private copy of the bound executable (an oyzu-plugin-* temporary directory) isn't removed.
  • Diagnostics from successful operations aren't shown.

The Python plugin​

The Python plugin (python/package) builds pip and pyproject.toml projects into wheels with pytest and Ruff checks, using the same binding. It adds no installer, PATH change or PYTHONPATH bridge: dependencies, pytest, coverage and quality tools must already be in the project's environment, and a target-local .venv is used when present. A mismatched environment is refused. Direct oyzu run tasks don't use this binding. Tested on Linux amd64 (GNU). No Python plugin is published yet. See Python preparation and, for the isolated path, captured pip Python packages.

The Node plugin​

The Node plugin serves node/app for npm, pnpm and Yarn (Classic and Berry). It's experimental and isn't published yet, so you supply the package or a local binding.

The host build takes a node/app target that is declared with uses: node/app, isn't a workspace root, and has a non-empty scripts.build that writes dist. Anything else is refused with the plugin's reason, and because a plugin-served id has no fallback, that target can't build until it's changed or the binding is removed. Workspace projects and package output are covered on npm workspaces, pnpm, Yarn and plugin packages.

It builds on Windows and Linux x86-64. Windows ARM64, macOS and Linux ARM64 aren't tested.

What it runs​

ActionCommandWhen
<target>:installnpm ci, pnpm install --frozen-lockfile, Yarn Classic yarn install --frozen-lockfile or Berry yarn install --immutable. Offline handling follows the managerThe project has dependencies, devDependencies or optionalDependencies
<target>:buildThe selected build task, normally <manager> run buildAlways
<target>:testYour test script, or the detected defaultTests are selected
<target>:lintYour lint script, or the native ESLint or Biome adapterLint is selected
<target>:format-check or <target>:format:checkYour check script, or the native Prettier or Biome adapterFormat is selected. A script that changes files is never selected

The shared check levels decide which checks run, and --full runs every check that isn't off. Your own scripts win over the defaults. format:check, build:prod and similar names are kept; unsupported names fail discovery with an explicit error. An authored install task in oyzu.toml replaces npm ci, and disabling the install stage drops it. Authored tasks run with your ambient environment, not oyzu's pinned tools, so an authored npm ci can fail where the plugin's own install works (on Linux without a global npm: cannot execute npm: No such file or directory).

The artifact is the dist directory your build script writes (project-written outputs), named application-<version> from the version oyzu resolved (0.0.0-dev.g<source hash> for an unversioned checkout), not the version in package.json.

Lock files​

Dependencies need the manager's lock file, or planning fails before any action with a diagnostic like node.lock-file: host npm dependency preparation requires package-lock.json; create it with npm before building.

  • npm: package-lock.json (an npm-shrinkwrap.json alone isn't enough).
  • pnpm: pnpm-lock.yaml. A stale lock fails the install (--frozen-lockfile) and isn't rewritten. Update it with pnpm, then retry.
  • Yarn: yarn.lock.

pnpm​

  • If packageManager is present it must be an exact stable release such as pnpm@10.11.0. Oyzu checks it against explicit tool configuration, and a conflicting release fails before any action. Ranges, tags and prereleases are refused. Without packageManager, select pnpm in [tools].
  • A pnpm-workspace.yaml that contains only settings is allowed. A packages key, or anything oyzu can't classify as settings, makes the project a workspace and it's refused. Competing manager evidence is also refused.
  • pnpm owns install scripts and their policy. Oyzu adds no script approval.
  • Offline builds add --offline and need the dependencies already in pnpm's own store. Missing bytes fail without going online. This is the host's ordinary pnpm configuration and store, not a hermetic replay, and --no-cache doesn't clear it.

Yarn​

  • Accepted exact releases: yarn@1.22.22 (Classic) and yarn@4.17.1 (Berry). Berry needs nodeLinker: node-modules in .yarnrc.yml (a quoted value is fine). Plug'n'Play is refused. See managed Yarn.
  • Direct tests need dependencies installed in the source project. A full build installs into a private workspace. For Berry, run yarn install --immutable, then oyzu run test.
  • Not supported: isolated Yarn builds, extra rc settings, workspaces on this path, project plugins, yarnPath, custom registries and non-registry sources.

Vite​

An npm project whose build script is recognized vite build, with an optional literal --outDir, Vite as a dependency and a native Vite 8 configuration, builds as an application. Oyzu keeps the npm lifecycle around one Vite build and stages the output after the native postbuild step. Tested with Vite 8.3.3. Other Vite flags, pnpm or Yarn with Vite, SSR, library and multi-environment builds, and watch or no-write modes aren't supported. See Node applications.

Tests and quality checks​

For non-workspace npm, pnpm and Yarn targets, oyzu run test adds JUnit and LCOV reporting to a default node --test, to flag-only test scripts it recognizes, and to exact vitest and vitest run commands. See Vitest and Jest for those frameworks (Vitest was tested with npm and Vitest 5.0.3; Jest with npm and Jest 29.7.0). The matching coverage provider must already be installed, because oyzu doesn't download it. pnpm and Yarn pass reporter flags directly after <manager> run test, with no npm-style -- separator.

  • Other test commands run unchanged. They can write to OYZU_TEST_REPORT and OYZU_COVERAGE_REPORT or to report paths you declare.
  • A missing optional report makes the evidence incomplete. A missing required report, a malformed report or a failing test fails the command.
  • Workspace tests and other managers fail with node.test-lane.
  • Lint and format checks prefer your project's installed ESLint, Prettier or Biome. Otherwise they use the default set pinned in oyzu.lock, prepared by the shared tool store. A declared but uninstalled package fails instead of falling back. Native configuration and ignore files are authoritative. oyzu run format changes source; format-check doesn't.
  • To run a named task such as format:check, use oyzu run app:format:check or [tasks."app:format:check"]. Environment defaults from native files go through the normal configuration and policy checks; reserved OYZU_* names stay unavailable.

Repository source bootstrap​

This section is for people working on the oyzu repository itself. Releases use the shared package store instead.

tooling/bootstrap-oyzu.sh uses an oyzu on PATH or in .oyzu/bin that can read this checkout's configuration. Without one it downloads the newest release's oyzu and oyzu-shim into .oyzu/bin, checking each against the digest the release reports, and builds from source only when no release executable can be used here (--source never downloads, so it builds whenever no usable oyzu is already there). An oyzu older than the plugin protocol of the pinned rust/app and node/app plugins (plugin_protocol_release at the top of the script) can't be used either, because it refuses their results. The current minimum is 0.2.4: Rust preview.3 emits native_reads, which older CLI versions reject. --no-plugins, which runs no plugin, skips that check. On a platform with no release that new yet, the script builds the CLI from source once, until such a release publishes an executable there. With --require-release (CI's setup action) it fails instead, before invoking a plugin. Raising the minimum does not provide a compatible executable: strict CI must wait for one to be published. The release workflow's existing non-strict --ci-machine-binding bootstrap can build only the CLI and shim for that first compatible release; it still uses signed published plugins. On Linux it then installs the published rust/app and node/app releases that oyzu.lock selects into the plugin store, from the release digests pinned at the top of the script, through a temporary user file that binds only them; your own configuration isn't changed. A failed install is only a warning. A source build makes the CLI, native shim, Rust plugin and Node plugin (only the CLI and shim with --ci-machine-binding, which binds the published plugins) (this repository declares both a cli and a docs build, so both builders must resolve before oyzu build cli). When an older CLI supplies the compiler, it resolves only the checkout's [tools] requests in a temporary project using its normal trusted tool resolver. The repository's oyzu.lock stays unchanged; newer build or plugin lock fields are not copied into that tool-only project. It compiles with the pinned Rust and Cargo's --locked dependency graph, and honors CARGO_TARGET_DIR and CARGO_BUILD_TARGET. It needs no Python, Node or jq just to read configuration; only the Linux plugin installation above and the read-back in the CI machine binding below use Python.

On a machine with no user configuration file and no existing plugin choices, the script writes the two development bindings to .oyzu/bootstrap/config.toml and prints the OYZU_USER_CONFIG export (or records it through CLAUDE_ENV_FILE, or through GITHUB_ENV for later GitHub Actions steps). It doesn't touch your own user configuration, project or local files, or shell profiles. If any step fails, it removes the file it created. Running it again with the same unchanged file prints Reusing this checkout's unchanged bootstrap USER file and the same export.

oyzu run bootstrap (on macOS and Windows, or with --source) uses the same file, but once it has packed .oyzu/bin/oyzu-plugin-rust.tar.gz the file binds rust/app to that package archive so isolated builds work (see refreshing the oyzu on your PATH). An earlier file with the executable binding is rewritten then; the script above keeps using whichever binding the file has.

If you already have a user configuration file or other plugin choices, the script refuses instead of merging. Bind the two plugins yourself, then run it again; with both present it passes them through. From the checkout root:

oyzu=.oyzu/bin/oyzu        # .oyzu/bin/oyzu.exe on Windows
bin="$(pwd -W 2>/dev/null || pwd)/.oyzu/bin"
"$oyzu" config set --global plugins.development.rust/app "$bin/oyzu-plugin-rust"   # add .exe on Windows
"$oyzu" config set --global plugins.development.node/app "$bin/oyzu-plugin-node"   # add .exe on Windows
tooling/bootstrap-oyzu.sh

Or edit the user file by hand:

[plugins.development]
"rust/app" = "/home/me/src/oyzu/.oyzu/bin/oyzu-plugin-rust"
"node/app" = "/home/me/src/oyzu/.oyzu/bin/oyzu-plugin-node"

In CI the user file is ignored, so the script refuses fresh user setup there; a CI job uses the machine binding below instead.

CI machine binding​

If this mode must build the CLI and shim from source, an authentic older Oyzu must supply managed Rust through its ordinary trusted tools-only resolver. Missing older driver refuses before host Cargo is queried or invoked. Non-CI source bootstrap retains its fallback, and --require-release still refuses source CLI builds. Any separately authorized one-time workflow source-bootstrap exception must be restored to --require-release afterward; it does not permit source-built plugins, general CI fallback or another run.

Pass --ci-machine-binding (used by the repository's own setup action and release workflows) to bind the Rust and Node plugins in machine configuration on a GitHub Actions runner (GITHUB_ACTIONS=true; anywhere else the switch does nothing). Before the configuration check above, the script:

  1. Checks that the runner is ephemeral: a GitHub-hosted runner (RUNNER_ENVIRONMENT=github-hosted), or a runner image that declares itself ephemeral with a root-owned, read-only /etc/oyzu-runner-ephemeral and provides a machine directory owned by the runner user, as the repository's self-hosted runner image does with /etc/oyzu. Owning the machine directory alone isn't enough. Otherwise it fails and writes nothing.
  2. Refuses an existing machine config.toml. It never merges into or replaces machine configuration.
  3. Binds the published rust and node plugin releases on every platform: it creates the machine config.toml with only [plugins.packages] entries for rust/app and node/app, each an oci reference to ghcr.io/oyzuai/plugins/<name> pinned by release root digest (the digests live at the top of tooling/bootstrap-oyzu.sh). The pinned releases carry Linux amd64 and arm64 (musl), macOS amd64 and Windows amd64 payloads. The Rust pin selects 0.1.0-preview.3, which also carries a macOS arm64 payload. Oyzu downloads each release on first use and checks its official signature. Nothing is built from source: a run with no recorded digest, or on a platform the release has no payload for, fails instead. The script then runs oyzu build for a target that does not exist, which installs the bound plugins during plugin selection and stops before building anything (a plan or task only replays installed plugins), and requires oyzu plugins current to report both installed. oyzu.lock must hold their selections. Update the digests and lock when a new plugin release is published.
  4. Reads the configuration back with oyzu --json config explain for plugins.packages (parsed with Python, which GitHub-hosted runners and the runner images provide) and requires exactly those two values, from machine scope only. The configuration check must then report the choices complete (unchanged), or the script fails.

Machine configuration isn't personal configuration, so CI keeps it. The binding lasts as long as the runner, and a GitHub-hosted runner or runner container is discarded after its job. This applies only to these bindings on ephemeral runners.

Bootstrapping without plugins​

Pass --no-plugins instead (it cannot be combined with --ci-machine-binding) when a job needs only the bootstrapped oyzu for oyzu install and oyzu exec and builds its own plugin payload, as the plugin release build does. The script then writes no machine configuration, creates no bootstrap USER file and builds no plugin from source, on any platform. Commands that select the Rust or Node plugins (oyzu build, oyzu run) fail in such a job until the plugins are bound.

Publisher plugins​

The publisher role extends the existing plugins-v1alpha1 framing. The npm implementation is crates/oyzu-plugin-npm; bind its compiled executable from user, machine or administrative configuration, never project configuration:

[plugins.development]
"npm/publish" = "/absolute/path/to/oyzu-plugin-npm"

This development binding records the actual executable digest in the native destination plan, signed publication intent and receipt. It does not confer the official oyzu package trust of a separately signed release. First-party publisher packages use the signed catalog and lock admission path used by builders; offline CLI bundling is deferred. See npm publishing for configuration and execution limits.

Each of describe, destination-plan, destination-inspect, destination-publish and destination-read-back starts a fresh supervised process with a deadline, minimal environment and fresh scratch directory. describe declares destination settings, accepted artifact kinds, hosts, credential slots, tool requirements and pointer effects. Any non-built-in kind resolves <kind>/publish unless uses overrides it. Kind settings pass through opaque: core reads only shared destination keys and declared host settings. Tools declare a name, tool identity, command and optional default version; core provisions them through the ordinary admitted tool contract. Credential slots declare their scheme and optional provider (npm-trusted) and subject JSON pointer. Each plan entry has exactly one inspect and distribute on its native coordinate; pointer effects must be declared and bind readPath, jsonPointer and the expected value. Planning is read-only; inspection and read-back receive read-only proxies. Only a frozen publish effect allows the proxy to forward a write. The plugin uses admitted tool paths and local proxy URLs supplied by core; it never resolves credentials itself.

The publisher schemas and wire contract define the records. The conformance harness accepts a publisher-only fixture directory and uses the same core process host as builders.

Publisher planning and destination evidence​

A publisher host declaration selects either a destination setting (setting) or a literal provider URL (url). credential_slot is optional: hosts without it are always anonymous. Core validates every URL and exposes only capability-bearing loopback proxy bases. It rewrites redirects only to declared bases, never follows them itself, and never adds authentication to anonymous hosts. GET/HEAD may run during planning, inspection and read-back; write permits exist only for publish.

destination-plan receives core-selected native facts in context and read-only proxies when credentials do not depend on a not-yet-planned subject. Execution receives original signed evidence in evidence, staged read-only by digest after core signs the intent. An acknowledgement's optional receipt is not verification: destination-read-back.files binds each evidence/payload ID to a fresh proxy observation. Core compares every planned file and reconstructs verification from those observations. GitHub's repository visibility also requires its own observed metadata read. The plugin never receives a credential, signing key or authority.

The GitHub publisher includes X-Oyzu-Publication-Target on proxy requests. Core accepts a read target only when it is the frozen release or one of its byte-bound assets, and reauthorizes that exact target. The proxy consumes this header locally; it is never forwarded to GitHub. Writes additionally match the frozen upload URL, filename and complete staged bytes before authorization.

Protected workers plan from their frozen release facts with proxy requests denied until intent authorization. The admitted publisher identity and every native coordinate must match the frozen request before the worker can publish.
