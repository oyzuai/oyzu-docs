Local development plugin bindings (experimental)

CLI reference

Published from the canonical docs/reference/plugin-development.md file. Features marked experimental remain experimental; check support limitations before relying on them.

A local development binding makes oyzu build and oyzu run use an external builder plugin executable in place of a built-in builder profile. It exists to develop and compare external builders against the draft plugins-v1alpha1 builder contract before plugin packages, sources and locks exist. Two plugins are developed this way: oyzu-plugin-go, the Go host lane extracted from the built-in Go builder (Milestone A of issue #582), and oyzu-plugin-node, the built-in Node builder's native npm application lane (slice N1 of Node externalization, issues #743 and #772).

Without a binding nothing changes: every builder id resolves to its built-in builder exactly as before.

Status and scope​

  • Experimental, for builder development. The setting, the protocol and the recorded fields are draft and may change in place.
  • Native host lane only. A bound target builds with native host tools through native-admission, native-build, native-test and task-command. A raw executable binding cannot establish an execution-platform payload for captured builds. That path requires an admitted multi-platform package with captured-plan and exact engine assets; otherwise it fails before preparation or build actions. There is no fallback to the built-in builder. When the plugin declines a target for the native host lane, the failure carries the plugin's own reason (see Failures and recovery).
  • Replaces a built-in profile. The bound id must be one a built-in builder serves (for example go/app). Detection, builder settings and dependency providers stay with that built-in builder; tasks, requirements, admission, build, test and task-command answers come from the plugin.
  • No plugin packages. There is no download, signature, manifest admission or oyzu.lock entry. The executable is local development content, recorded by path and SHA-256 digest only.

Prerequisites​

  • An Oyzu CLI built from a revision containing this feature.

  • A plugin executable. Build the Go or Node plugin from this repository:

    oyzu exec -- cargo build --locked -p oyzu-plugin-go --features plugin
    # target/debug/oyzu-plugin-go (oyzu-plugin-go.exe on Windows)
    oyzu exec -- cargo build --locked -p oyzu-plugin-node --features plugin
    # target/debug/oyzu-plugin-node (oyzu-plugin-node.exe on Windows)

    The executable requires the plugin feature so the repository's own cli build, which collects every enabled workspace binary, never ships it. Check the plugin against the contract with its conformance test, which runs the canonical requests through core's process host against temporary Go projects:

    oyzu exec -- cargo test --locked -p oyzu-plugin-go --features plugin

    The Node plugin's tests (--features plugin) also drive the compiled CLI, so build it first (oyzu exec -- cargo build --locked --bin oyzu) or set OYZU_CLI. CI does not run them.

  • The native tools the target needs, provisioned as usual. Core resolves, locks and installs oyzu:go or oyzu:node from the plugin's requirements answer, as it does for the built-in builder.

For a verified, locked package instead of a local path, see plugin packages.

Usage​

Add the binding to your user configuration (~/.config/oyzu/config.toml on Linux, ~/Library/Application Support/Oyzu/config.toml on macOS, %APPDATA%\Oyzu\config.toml on Windows, or the file OYZU_USER_CONFIG names):

[plugins.development]
"go/app" = "/home/me/src/oyzu/target/debug/oyzu-plugin-go"
"node/app" = "/home/me/src/oyzu/target/debug/oyzu-plugin-node"

Then build or run tasks as usual in a Go project:

oyzu build
oyzu build --full
oyzu run test
oyzu run build

The build shows the core-allocated plugin output directory in its build command (go build -trimpath -buildvcs=false -o .oyzu/native/plugin/…). The Context facts in dist/logs/events.jsonl include Plugins go/app → local development <path> (sha256:…), and the retained inventory records {"reference","content":"local-development","executable","digest"} for each binding. The executable that runs is a private per-invocation copy of the file whose digest was recorded, and the plan, envelope and manifest carry extensions["oyzu.dev/plugins"]; see plugin packages.

A Node project builds when it is an npm application declared uses: node/app in build.yaml whose own build script writes dist; see the Node plugin for what it runs and how it differs from the built-in builder.

Remove the table (or the entry) to return to the built-in builder.

Setting​

KeyTypeDefaultScopes
plugins.developmenttable of builder id to absolute executable pathnoneuser, machine, administrative
  • Keys are short builder references without a major version (go/app, not go@1/app or an OCI reference). Values are absolute paths. At most 64 entries.
  • The setting selects executable code, so project oyzu.toml, oyzu.local.toml and profile overlays are refused with CONFIG_SCOPE: plugins.development is not permitted in this scope. Administrative constraints apply as for any setting.
  • In CI, user configuration is excluded as usual; a machine-scope binding still applies.
  • The table is atomic: a later source replaces the whole table.

Bindings are resolved once per invocation, before targets are discovered. A missing or unreadable executable, or an id no built-in builder serves, fails discovery with PLUGIN_BINDING_INVALID.

Project-written outputs​

A plugin whose ecosystem's build script decides where its output goes, as npm run build writes dist, cannot steer that output into the core-allocated output directory. Its native-build or captured-plan result instead marks the artifact "origin": "target" with a target-relative source, and its build operation runs the selected task's own command (core sends it as input.task.argv):

{"name": "primary", "producer": "build", "kind": "directory",
 "filename": "application-1.4.0", "media_type": "application/octet-stream",
 "source": "dist", "executable": false, "origin": "target"}

The default origin, output-dir, is omitted when encoded, so an existing plugin's results (the Go plugin's) are unchanged. Core enforces, before any build action runs:

RuleRefused with
The source names something below the target: not ., and no segment that starts or ends with a dot (.git, .oyzu), is node_modules (any case) or is a Windows device name (con, nul, COM1.txt)PLUGIN_OPERATION_FAILED: … invalid result
Sources are unique, ignoring casePLUGIN_OPERATION_FAILED: … invalid result
The source neither equals, contains nor lies inside output_dirPLUGIN_OPERATION_FAILED: … overlaps the output directory
The source neither equals, contains nor lies inside a file or directory of the target's frozen source selection, ignoring casePLUGIN_ARTIFACT_REFUSED: … overlaps the frozen source selection at <path>
No existing segment of the path is a symbolic link or reparse point, and none above the last is a filePLUGIN_ARTIFACT_REFUSED: artifact … names … with the cause

Then core retires the path: whatever exists there is renamed into a fresh core-owned directory beside the output directory, never deleted in place, and is discarded with that directory after collection. The build plan records each retired path under extensions["oyzu.dev/retired-outputs"], for example {"web":[{"artifact":"primary","path":"dist","previous":false}]}. A build whose script writes nothing fails with native artifact collection failed rather than republishing an earlier output. Collection then applies the usual rules (no links, no reserved names, a directory inventory or a regular file).

On the native host lane, retirement never moves anything and previous is always false: the target directory is a private projection that core rebuilds from the frozen source selection before each build, so anything already at the path would be source, which the overlap rule refuses first. What keeps an earlier output from being republished here is that rebuild; retirement is kept so the guarantee does not depend on it. The record is not part of action cache keys. Captured planning checks the frozen source selection without changing it. The frozen plan retires output in the mutable private execution workspace before dependency setup and authored operations, then exports the fresh artifact through the common containment and no-link checks. It never retires files in the original project or the read-only planning mount. To recover from a refusal, have the plugin name a project output that is not source, not core or version-control state and not dependency trees, and remove any link at that location.

Each operation runs one fresh plugin process through core's plugin process host: no arguments, a minimal environment, a fresh scratch working directory and a 60-second deadline, after which the whole process tree is terminated.

Bound targets are reused from the local action cache like built-in ones: the action key binds the plugin's executable digest and runtime, so rebuilding the plugin re-runs its targets. Bind the plugin executable itself: a binding to a wrapper script is never reused, because the digest covers only the script and not the program it starts (see external builder targets). An unchanged one-module repeat build launches the plugin 5 times: tasks, requirements (asked once per distinct request and stage set and reused for the invocation), native-admission, native-build and one task-command per frozen command (two when it asks for an observation). Core asks task-command for every command, including the ones the plugin produced, because the plugin may expand them (the Go plugin expands its own instrumented test command under a go.work). Launch counts scale with the number of bound targets.

The Node plugin​

oyzu-plugin-node serves node/app only, for the lane the built-in Node builder already runs natively: manager npm, the target declared uses: node/app, no workspaces, and a non-empty scripts.build that does not start with vite build. Any other node/app target is refused with the plugin's reason (admission reasons); while the binding exists such a target cannot build at all, because a bound id has no fallback to the built-in builder. node/package stays built in.

For non-workspace npm targets, oyzu run test instruments a default node --test or the existing recognized flag-only npm test script with native JUnit and lcov reporters. Opaque commands keep their exact argv and may write reports to OYZU_TEST_REPORT and OYZU_COVERAGE_REPORT or declared report paths. Missing optional reports produce incomplete evidence; required missing reports, malformed present reports and native failures fail the command. Other managers and workspace tests fail explicitly with node.test-lane. Direct tasks require already prepared native dependencies and a selected Node runtime.

An admitted application build offers these ordered actions. The shared check levels decide which checks run; --full selects every check that is not off.

ActionCommandWhen
<target>:installnpm ci, plus --offline when requestedNonempty dependencies, devDependencies or optionalDependencies
<target>:buildSelected authored build task, normally npm run buildAlways
<target>:testAuthored test script or detected defaultTests selected
<target>:lintAuthored lint script or native ESLint/Biome adapterLint selected
<target>:format-check or <target>:format:checkAuthored check script or native Prettier/Biome adapterFormat selected; mutating format is never selected

Default quality commands reuse the built-in native API adapter. Install the project's selected ESLint/Prettier/Biome dependencies first; an explicitly provisioned OYZU_NODE_QUALITY_HOME may supply undeclared fallback packages. Declared-but-uninstalled packages fail rather than falling back. Native config and ignores remain authoritative; generated output and symlinks are excluded by the existing adapter. oyzu run format mutates source; format-check does not. Authored scripts win over defaults. format:check, build:prod and other portable colon names are retained; unsupported names fail discovery explicitly. Use oyzu run app:format:check or [tasks."app:format:check"] when qualifying a name. Native task environment defaults enter the ordinary configuration and policy pipeline; reserved OYZU_* names remain unavailable to authored config.

Recognized-runner qualification in this slice is Node's built-in runner only. Jest/Vitest/Mocha detection and default commands are available, but their native report adapters are not exported by this plugin: they behave as opaque commands and must produce authored reports to satisfy required gates. No framework, pnpm/yarn or workspace support is implied. See the native checks qualification and the separate captured npm proof.

The plugin echoes the build task's argv in its build operation because the host requires a command for build ("native build invocation missing" otherwise). This contradicts the wire contract, which says an operation without command runs the target's own task; the mismatch is tracked as a follow-up issue.

The artifact is the dist directory the build script writes (origin: target, subject to fresh-output checks), named application-<version> from the version core resolved. Dependencies without package-lock.json fail at plan time, before any action, with PLUGIN_OPERATION_FAILED: … (NativeBuild): node.lock-file: host npm dependency preparation requires package-lock.json; create it with npm before building (an npm-shrinkwrap.json alone is not enough, as for the built-in). A failed npm ci blocks the build action and collects nothing.

Differences from the built-in builder for the same project:

  • The artifact name uses core's resolved version (for an unversioned checkout 0.0.0-dev.g<source hash>), not package.json's version. The directory inventory and content digests are the same.
  • The install action is <target>:install, the target's install task (npm ci with a lock file), where the built-in runs an internal <target>:prepare action: core runs a plugin operation only when the target has a task of that name. Its environment is the install task's admitted environment, where the built-in gives npm ci the build task's; they are the same unless the two tasks' environments differ. Because it is a task, an authored install task in oyzu.toml replaces npm ci, and disabling the install stage drops it; the built-in's prepare can be neither replaced nor disabled. Core runs an authored task on its host path with the ambient environment, not the pinned tool environment the plugin's install operation gets, so an authored npm ci can fail where the plugin's own install works (on Linux without a global npm: cannot execute npm: No such file or directory).
  • Report integration labels and framework adapters. The plugin supplies command/report intent but not the built-in's integration-mode metadata or Jest/Vitest/Mocha adapters. Core still records command, report and acceptance evidence independently.
  • Each bound target launches a plugin process for its discovery/planning operations and command adaptation. Earlier N1 timings remain historical measurements; this checks slice does not claim new performance results.

The complete list, with the differential test that holds it, is in known differences.

Failures and recovery​

ErrorCauseRecovery
CONFIG_SCOPE: plugins.development is not permitted in this scopeThe setting is in a project file or profileMove it to user or machine configuration
PLUGIN_BINDING_INVALID: … cannot read plugin executableThe path is missing or not a regular fileBuild the plugin or correct the path
PLUGIN_BINDING_INVALID: … is not a builder id a built-in builder servesThe id is unknownUse an id such as go/app
PLUGIN_OPERATION_FAILED: <id> plugin <path> (<operation>)The plugin failed, answered unsupported, broke the protocol, exited nonzero, wrote no result or exceeded its deadline; the cause follows, with the plugin's warning and error diagnosticsFix the plugin; the cause names the rule broken
PLUGIN_ISOLATED_UNSUPPORTED / ENGINE_ASSET_UNAVAILABLECaptured execution lacks an admitted package capability, platform member, supported profile or exact engine assets. When the plugin also declined the target for the native host lane in native-admission, the message ends with one clause per such selected target, ; target <id> was not admitted to the native host lane: <reason> (for example ENGINE_ASSET_UNAVAILABLE: no admitted execution assets selected; target hello was not admitted to the native host lane: host Go builds require exactly one main package). If native-admission itself failed, it ends with ; target <id>: its plugin failed native-admission: <cause>Fix what the reason names so the plugin admits the target for the native host lane, or supply the documented captured package and engine prerequisites
plugin … sets command env, which the native host lane does not carry yetA build operation or test command carried envUse native-build output env; per-command env is a Milestone A limit
PLUGIN_ARTIFACT_REFUSED: artifact … names …An origin: target artifact overlaps the frozen source selection, passes through a link or reparse point, or lies below a file; or core could not move a previous output asideName a project output that is not source and has no link in its path (project-written outputs)

A failed operation fails the build or task like any preparation failure; no partial plugin result is used.

Where a refusal reason appears​

A plain oyzu build routes a bound target to the native host lane first. When the plugin declines it, the build cannot continue on the captured path without execution assets, so it fails during preparation, before any plugin build action or tool installation, with the code above and the plugin's reason appended. The message names every selected bound target the plugin kept off the native host lane, one clause each, not only the first target that failed: with an admitted api and a refused tools, it ends ; target tools was not admitted to the native host lane: <reason>. A plugin that fails native-admission is named the same way. The human and --json outputs carry the same message (in JSON, the failed result's diagnostic message). oyzu build --plan does not fail: its "Unresolved until preparation" list (unresolved in JSON) adds the same clause for each such target (Target <id> was not admitted to the native host lane: <reason>).

A refused target that captured planning would admit still gets its clause when a different target is the one that fails; the remedy in the table applies to the refused targets named, not to the one that happened to fail first.

The clauses are asked of the plugins only after a failure. A target that captured planning takes is planned exactly as before, and a build in which every bound target is admitted launches nothing extra. The answers are the ones native selection already cached for this invocation; a target native selection never reached (it stops at the first refusal) costs one native-admission launch.

With --isolated or --all-platforms, engine selection runs first and does not launch plugins, so the engine's own refusal (ENGINE_PIN_MISMATCH when no matching engine archive is admitted) is what you see until the engine is admitted. Once it is, a target that cannot be planned on the captured path fails with its PLUGIN_ISOLATED_UNSUPPORTED message and the same appended clauses. That failure now launches each selected bound target's plugin on the host for native-admission if the answer is not cached, once per target; a failing or hanging plugin can add up to its 60-second deadline per target. A target the plugin admitted natively gets no clause. The reason is only ever added to a failure: a target that captured planning admits proceeds to captured planning exactly as before.

Trust​

A binding runs the named executable with your user's permissions whenever Oyzu discovers a workspace. Only bind executables you built or trust. The digest records which content ran; it is not a signature and grants nothing. The plugin receives no credentials and no inherited environment.

Limits​

  • Go go/app with one module and one package main is the only admitted Go host build, as for the built-in host path. go/library and workspaces keep task execution through the plugin but are not admitted to native builds, so oyzu build refuses them while bound.
  • Node: npm node/app applications only, including native check/report intent (the Node plugin). The captured npm extension in #789 has a passing local Linux proof. pnpm, yarn, workspaces and frameworks are not served by that extension; remove the binding to build such projects with the built-in builder (a bound id has no fallback).
  • Per-command env in native-build operations and the native-test command is refused (see above).
  • Observation commands are matched by tool short name (go for oyzu:go) on the task PATH; core does not yet verify the resolved file belongs to the locked tool.
  • Ctrl-C (or SIGTERM/SIGHUP on Unix) terminates a running plugin and its descendants on every command. oyzu build reports a cancelled build. On Unix, commands without build interrupt handling (oyzu run, oyzu build --plan) stop the plugin first and then end with the signal as before. A plugin that fails native-admission fails oyzu build --plan as it fails the build.
  • If oyzu run or oyzu build --plan ends from a signal, the private copy of the bound executable (an oyzu-plugin-* temporary directory) is not removed.
  • Successful operations' diagnostics are not shown.

Verification​

Milestone A was demonstrated on Linux x86_64 with the compiled debug CLI and examples/builds/go-app/project: the bound and unbound builds produced the same artifact name and byte-identical content, the same test and coverage reports, and the bound build recorded the plugin path and digest. A two-module Go workspace exercised task-command with one observation round through oyzu run build and oyzu run test. Commands and results are in the wire contract's verification section and in implementation status. Windows and macOS were not exercised.

Project-written outputs (issue #746) were demonstrated through the compiled CLI on Windows (Linux pending) with the reference plugin bound to node/app (its project-output target runs the project's own script and names the dist it writes): oyzu exec -- cargo test --locked --test integration plugin_artifact_origin. See the qualification record.

The Node plugin's npm application build (issue #772) was demonstrated through the compiled CLI on Windows and Linux (WSL): the bound and built-in builds of the same project produced the same directory digest, npm ci ran as the install action, and the preparation-boundary cases above pass: oyzu exec -- cargo test --locked -p oyzu-plugin-node --features plugin. See the qualification record.
