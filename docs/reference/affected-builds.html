Affected target builds

CLI reference

Published from the canonical docs/reference/affected-builds.md file. Features marked experimental remain experimental; check support limitations before relying on them.

oyzu build --affected <git-ref> builds only the targets that changed since a Git commit, plus the targets that consume them and whatever those need to build. Use it in pull requests and CI to skip unchanged parts of a monorepo.

oyzu build --affected HEAD --plan
oyzu build --affected origin/main
oyzu inspect dist
  • The ref must already exist locally; Oyzu doesn't fetch it.
  • Git must be on PATH.
  • --affected can't be combined with target names.
  • No project configuration is needed. Without --affected, every target builds as usual.

How targets are selected​

Oyzu compares your current source with the committed files at the ref, including deleted files and executable-bit changes. A project nested inside a repository is compared with its own subtree. The usual source exclusions apply to both sides, so changes in dist, .oyzu, dependency folders and other excluded folders don't trigger builds. Checkout filters and line-ending conversion can make working files differ from committed ones; such differences count as changes.

  1. A changed file selects targets whose bounded stage read sets or declared build.yaml inputs include it. Declared inputs are relative to build.yaml, including paths outside the target folder. Selection uses the same analysis contracts as action-cache source keys. If any stage has no complete read contract, every change inside its target folder selects that target.
  2. Selection then follows consumers through depends_on, materialize.from and cross-target task prerequisites, transitively.
  3. The producers and task dependencies those targets need are added.

Each selected target runs its normal checks and packaging. A native workspace (for example a Cargo workspace) is one target; individual members aren't selected separately. Declare cross-project file reads with inputs and build relationships with the normal dependency fields. Unbounded stages can keep a root target selected for every repository edit; selection never assumes unknown reads are empty.

Execution follows the plain-build rules: native when every selected target supports it, otherwise the container executor.

When nothing changed​

--plan returns an empty preview and leaves dist alone. A build writes an empty, inspectable bundle with no tools, actions or artifacts. Old artifacts aren't copied into it, and unselected targets aren't reported as successful.

What the build records​

The plan and manifest record oyzu.dev/selection with mode: "affected", the impacted targets, the final selection and the excluded targets. Its affected object records the ref, the resolved commit, the source digest, changed paths, the reason each target was selected, and any fallback to a full build.

affected.inputModel: "stage-reads" identifies read-set-aware selection. affected.tasks lists affected root tasks, including consumers of other affected tasks. Root tasks use their declared inputs (paths or globs relative to their working directory); a task with no declared inputs is conservatively selected. When an affected root task feeds a target hook, selection also includes that target and its consumers, including through intermediate task dependencies. This records which repository checks to run without executing them during preview. Older CLIs without this input model must not be used to skip CI jobs.

For --plan --affected only, an absent declared input does not fail the preview. Generated, ignored inputs need not be prepared just to select work. The JSON facts list them by build in affected.absentDeclaredInputs, and the human Selection section marks them as required for execution. Absence alone adds no change; deleting a tracked input still selects its consumer, even when a later ignore rule also matches it. The comparison retains its committed bytes without adding it to the live inventory. Changes to a preparation task's declared inputs select that task and its consumers as usual. Execution and previews without --affected still require every selected input; prepare the input before running the build.

The human output shows a Selection section: counts of changed, dependent and unaffected targets, the base and its short commit, or a Not narrowed notice with the fallback reason. See result output.

These records describe the selection. They aren't release or CI evidence.

Falling back to a full build​

Oyzu builds everything when it can't safely narrow the selection:

  • the ref can't be read locally;
  • a file is new compared with the ref;
  • a changed file belongs to no target;
  • build, configuration or lock files changed;
  • inputs of a root task with cross-target prerequisites changed;
  • the configuration is managed by policy;
  • the source read analysis cannot be completed;
  • Git object limits or unsupported entries prevent comparison.

The recorded fallback says which. If the ref was missing, fetch it and run again. A fallback may need tools that a no-change build wouldn't.

Blobless clones​

--affected works in a clone made with git clone --filter=blob:none, which has full history but only the file contents a checkout needs. Git fetches the contents of changed files from the remote on demand, so the clone needs read access to the repository. If that fetch fails, Oyzu falls back to a full build. Git fetches these one file at a time, so a very large change takes longer to plan. This is how a platform pool plans a remote run.

Limits​

  • Changes to external configuration, tools or environment aren't seen by Git. Run a full build when those change.
  • Reuse of cached actions isn't part of --affected itself; see the action cache.
  • Discovery and validation still cover the whole workspace.
  • Reading the baseline needs no network, but preparing selected targets may download dependencies.
  • Git metadata never grants signing or publication rights.
