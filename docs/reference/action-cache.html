Local action cache

CLI reference

Published from the canonical docs/reference/action-cache.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Status: experimental. Implements the first milestone of the draft OEP-0011 (local cache) and, since 2026-10-10, a standalone development-scope remote OCI cache for per-action results (handoff K3). The proposal stays draft until maintainer review. Managed-platform cache policy, signing and every CI trust claim are later milestones and are not implemented here.

A repeat oyzu build skips targets whose inputs have not changed and restores their earlier results. Nothing is configured: users never write cache keys or per-language cache paths. Reuse is local to one user on one machine, and every output says plainly that a restored result was not executed now. When known, reuse.source records the serving local or remote tier, independently of the original producing run. Receipts separate reused test evidence from fresh tests. An unavailable cache is distinct from explicit --no-cache; permitted native execution continues with a warning and fresh action evidence. Lookup metadata distinguishes hit, miss, rejected restoration and unavailable store; it does not change cache admission.

What is reused​

The unit of reuse depends on what Oyzu knows about the target:

  • Per action for targets whose actions carry a stage contract (today node/package on the captured path). Each action (for example api:version, api:build, api:package) has its own key and result; see Per-action reuse. The target's group record is kept as a view that lists its action results, so an unchanged repeat still restores the whole target in one step.
  • Per target group for every other builder: one key per target, restoring all its actions together or none. The actions of one target share a single private workspace.

Native builder actions can also bind exact prepared-resource files. The plan's dependency input records those files and their content-tree digest; execution mounts and revalidates that same selection even with --no-cache. An absent selection keeps the whole prepared input, while an empty selection exposes an empty directory. Export-only injected defaults may be omitted from commands that do not consume them; explicit native or user values remain effective. Authored replacements clear these native bindings.

The bounded Go application path additionally isolates native tests in fresh original-capture workspaces and empty report output roots. Their ephemeral writes are discarded; the collector retains the actual roots until report gates finish and captures validated reports into the invocation bundle. Reused reports retain their original producer evidence. Generated/artifact workspace consumers and --verify-contract with private roots are currently unsupported on that path. Native runtime qualification remains in the Go proof record.

A reused target or action keeps:

  • its artifacts, byte for byte (each is re-verified against its recorded digest);
  • its original JUnit, coverage and other reports and their producer evidence;
  • the original run identifier, key and completion time, in a reuse record (for an action reused individually, the run in which that action really executed).

A target is stored only after all of its actions succeeded and its reports were collected. Failed, blocked and cancelled targets are never stored.

Not cached by default (the target simply runs, and the output says why):

  • targets containing authored tasks or task overrides that do not ask to be cached, and targets whose hooks ([tasks."api:pre_build"]) declare no outputs, because their effects are not visible to Oyzu. An authored task with cache = true and outputs is cached (see Authored tasks); a hook that declares outputs is followed on targets reused action by action (see Hooks);
  • targets with hooks on a path that reuses a target only whole (the native host path, and captured targets without stage contracts): restoring the target would skip its hooks, which run on every build;
  • targets using secret environment values ({ secret = "…" });
  • targets on the native host path that declare additional source inputs (inputs), whose scope is not modeled there yet. On the captured path declared inputs are part of the scope (see Declared inputs).

Built-in builders declare their own actions, so their stages are cacheable without configuration.

Prerequisites and platforms​

  • Captured executor path: oyzu build and oyzu build --affected on targets that use it (for example node/package). This needs the Docker executor the captured path already requires and its provisioned toolchain images.
  • Native host path: builds that run on the host with Oyzu-provisioned tools (node/app dist applications, Go, Rust, Python wheels) reuse unchanged targets the same way; see Native host builds. Targets built by a host-coordinated image worker are not cached yet and say so. Direct oyzu run task executions are never cached.
  • Standalone use needs no account. Ephemeral CI runners start with an empty local store; with a remote OCI cache configured they reuse per-action results other checkouts pushed. A remote hit is a development result, not trusted CI evidence.
  • Existing regression verification is Linux (see Verification). The bounded shared-source baseline also measured Windows-host/Linux-Docker seed/repeat reuse and native package results. Shared edits conservatively re-execute unrelated work there; full Windows/macOS cache qualification remains pending. The bounded Linux shared-source proof passed; its named remaining qualification cases stay explicit in that record.

Usage​

oyzu build                       # first build executes and stores; repeats reuse
oyzu build --affected HEAD       # Git-selected targets also reuse unchanged results
oyzu build --full                # quality stages and their reports are reused too
oyzu build --no-cache            # run every action; read and write nothing
oyzu cache status                # where the store is, how large, how many entries
oyzu cache clear                 # remove every cached result (bundles are untouched)
oyzu build --explain             # after the build, why each stage was reused or ran
oyzu cache explain api           # why target api's key (and its stages' keys) last changed

Every oyzu cache command is headless, reads no project beyond configuration, and supports the global --json flag before or after the subcommand.

Example (EX-033 declared-targets project, Linux, one run each):

$ oyzu build                         # cold
✓ Build succeeded   4 targets · 4 executed · 9.4s
$ oyzu build                         # unchanged repeat
  ↺ api    build                                   reused   was 1.2s
✓ Build succeeded   4 targets · 4 reused · 1.8s
$ echo "// edit" >> api/src/greeting.mjs && oyzu build
✓ Build succeeded   4 targets · 3 reused · 1 executed · 3.1s

Per-action reuse​

Status: experimental, node/package on the captured path. Draft design: stage/action contract (steps A and B of OEP-0020 slice S5). Nothing is configured; step B added one flag, build --verify-contract (its name is provisional until the maintainer confirms it).

Planning attaches a stage contract to each action of an analyzed target (extensions["oyzu.dev/stage-contract"] in plan.json): the reads, writes, environment names and tools the static analysis found for the stage, the actions it follows, the fallback rung and whether its outputs are bounded (no unknown write). A target whose actions all carry a contract is reused action by action:

StepBehavior
Lookupthe target's group record is tried first (unchanged target: one step). On a miss, each action is looked up when it becomes ready
Action keythe action's own frozen definition (command, environment, working directory, platform, limits, report contracts, configuration digest), the target scope digest, toolchain, builder, variant, platform, prepared dependencies (only for an action that reads them), materialized artifacts and the output digests of the earlier actions of the target it follows
Action resultthe files the action published to the bundle (artifacts, reports), the records describing them, and its observed workspace changes (created and modified files with digests, deleted files, new directories)
Reuserecords enter the manifest as succeeded with a reuse record; reports are parsed again and gated by the current contract; the workspace changes are restored before the next action that has to execute, so dependents see the files executing it would have left. A fully reused target never touches its workspace
Early cutoffa re-run action that produces the same workspace changes leaves its dependents' keys unchanged, so they are still reused
Always runsan action without bounded outputs (a stage contract with an unknown write) is never reused on its own; it runs every time and its observed output still feeds what follows. A target holding such an action is not restored whole
Storingresults are committed only after the whole target succeeded and its reports were collected; the group view is written last and lists actionResults (action id and key)

Keys: target scope, or the contract's reads for a confined action. An action's key hashes the target scope unless the action is confined (next section); a confined action hashes only the source entries its contract reads. The configuration digest is part of every action, so changing an execution setting such as --full re-keys all actions (see Deferred).

A builder with no analysis, and any target containing an authored task or task override that does not set cache = true with outputs, or a hook without declared outputs, keeps the group behavior and wording described above. A symbolic link or special file created by an action makes its changes unrestorable: the action still runs and feeds its dependents but is not stored. The manifest records each action's outcome (reused, executed, always-run) under manifest.extensions["oyzu.dev/action-cache"].targets.<target>.actions; executed actions also carry their actionKey.

Hooks as always-run actions​

Status: experimental (stage/action contract step C), per-action targets only (node/package on the captured path). A hook ([tasks."api:pre_build"], post_<stage>) that declares outputs no longer makes its target not-cached:

[tasks."api:pre_build"]
argv = ["node", "hook.mjs"]
outputs = ["generated"]      # workspace paths, directories or globs the hook writes
AspectBehavior
The hookruns on every build; it is never restored and its record never carries reuse. The per-action record shows it as always-run
Its outputthe files it actually changed are recorded (like any action's workspace changes) and their digest enters the key of every later action of the target, so a hook that writes something else re-runs what follows it and a hook that writes the same bytes leaves it reused
Target outcomereused when every other action was reused (the hook running does not count against it); otherwise executed. The target's group record is not stored, as for any always-run action
Undeclared effectsa hook that changes a file outside its declared outputs is not followed: nothing of the target is stored and the target outcome carries a rejected note naming the files, so the next build executes it again
No outputsunchanged: the target is not-cached ("hooks without declared outputs"). --no-cache is unchanged
Whole-target pathon the native host path, and on captured targets without stage contracts, a target is restored only whole, which would skip its hooks. Such a target is not-cached ("runs hooks, which run on every build, and its actions are not reused one by one here") and its hooks run on every build. (Before this was fixed, a hook that declared outputs on that path was restored without running on an unchanged repeat.)

On hosts without view support (Windows today) no action is confined, so every action keeps the target-scope key and any source edit, including a hook edit, re-runs the whole target; the hook still runs every build and an unchanged repeat is still reused. The hook_reuse and generated_source scenarios assert confined (and the selective reuse that depends on it) only where views are supported and the target-scope behavior elsewhere; every other assertion runs unchanged on all hosts.

Hook outputs are relative to the hook's working directory (the target, unless cwd says otherwise), written with / or \; the cache resolves them against the project root before judging the files the hook changed. Editing a hook script is a source edit: it changes the target scope, so it re-runs the target-scope-keyed actions and any confined action whose reads include the script (the default lint and format-check read every JavaScript and TypeScript file of the target). Whether it also changes the development version, which is in every action's environment, depends on the hook:

HookDevelopment versionA comment-only edit of its script (same output)
pre_build with outputs, on a builder that finalizes versions (Node)finalized after the hook (below): the script leaves the version scope and what the hook wrote enters itkeeps the version; the confined api:build is reused. api:test re-runs in EX-033 because its contract reads api/**
any other hook (pre_test, post_build, …), or another builderthe script stays in the version scopechanges the version, which re-keys every action of the target

Version finalization after hooks (OEP-0011 handoff K2, captured path):

  1. Planning moves the target's version action after its followed pre_build hooks, so nothing that writes the version runs before them, and records every action in plan.json with the pre-hook source version (the version scope without the hook's script). The target record carries extensions["oyzu.dev/version-finalization"] with the hooks and the actions that follow them. The actions before the hook (prepare, the hook itself) run with the pre-hook source version.
  2. When the hooks succeed, the files under their declared outputs are digested (from the workspace, not the cache, so --no-cache gives the same result) and folded into the version. The target is planned again with that version, and the actions after the hooks run from this post-hook plan: the same actions and edges, with the final version in their environment, artifact names and target record. It is written to plans/<target>.post-hooks.json (evidence kind post-hook-plan); plan.json is never changed.
  3. The manifest's target record is the post-hook one, and manifest.extensions["oyzu.dev/version-finalization"].<target> gives preHookVersion, version, hookOutputs, planPath and planDigest.

A hook edit that changes what the hook writes changes the version and the package. A script stays in the version scope when it is not named as an argument of the hook's command (for example run = "node hook.mjs" through a shell) or when a builder stage reads or writes it; such an edit then changes the version as before. The hook still runs on every build. Limits: the hook's other reads stay in the source scope as usual; a package that ships the hook script without the analysis seeing it (an npm package with no files field) gets a new package under the same version after a script-only edit, the same limit the test-only exclusion has; other builders, other hook phases and the native host path are not finalized.

An authored task such as EX-010's api:test is reused around a hook when it sets cache = true (next section). Limits: effects outside the workspace (network, global state) are invisible and are the hook author's to declare away.

Authored tasks cached on request​

Status: experimental (OEP-0011 handoff K1). An authored task or task override is not cached by default, because its effects are not visible to Oyzu. It opts in with the existing cache and outputs task fields:

[tasks."api:test"]
run = "node --test"
cache = true
inputs = ["src/**", "test/**"]   # optional; may only add to the target scope
outputs = [".events"]            # workspace paths, directories or globs the task writes
AspectBehavior
Opt-incache = true and at least one outputs entry. The plan marks the action cacheable: true and records the declaration in extensions["oyzu.dev/authored-cache"]. Hooks always run: cache on a hook is ignored
Keythe task's own frozen definition (command, environment names, working directory, report contracts, configuration digest) and the target scope, as for a builder stage; so editing a file in the target, or the task itself, re-runs it. It is never keyed on, or confined to, the builder's analysis of a stage it replaces
inputsrelative to the task's directory. Entries inside the target are already covered by its scope. An entry outside the target is a scope the cache does not model yet: the target is not-cached ("declares inputs outside its target (…), which are not scoped yet") rather than keyed on less than the task reads
Per-action targets (captured node/package)the task is a reusable action. Its observed workspace changes are its result and must lie inside its declared outputs; changes outside them store nothing for the target and the outcome carries a rejected note naming the files, as for a hook. Around a hook it is reused while the hook's output digest is unchanged and re-runs when that output changes (EX-010)
Whole-target path (native host, other builders)the target is reused whole when every action is a builder stage or a cached authored task; reports are restored and re-gated. Declared outputs are not checked there: the private workspace is discarded after the build and nothing runs after a restored target. A target with hooks is not cached on this path (see the hooks section)
cache = true without outputsnot-cached with the reason "<task> sets cache = true but declares no outputs, so it is not cached"
--no-cache, cache.local = falseunchanged: nothing is reused or stored

Limits: a task that leaves nothing in the workspace must still name an output (for example the directory its tool writes logs to); reusing an authored task around hooks needs per-action reuse, which only captured node/package targets have; inputs outside the target are not honored; a command that a builder does not recognize for report instrumentation keeps today's reporting behavior (on the native path such an override fails its report gate whether or not it is cached).

Confined actions and narrow keys​

Status: experimental (stage/action contract step B). Prerequisites: the captured executor path and a Unix host (views recreate installed command shims as symbolic links; Linux was run, macOS was not). Windows has no view support yet, so narrow keys stay off there and every action keeps its target-scope key.

A narrow key is only sound if the action cannot see anything the key left out. Oyzu therefore keys an action on its contract's reads only when the action also runs confined to them:

StepBehavior
Eligiblethe contract is confinable: the analysis modeled that stage's own command (stage-specific facts exist), no fact of the stage is an unbounded unknown (a bounded one adds its bound to the reads; see bounded unknowns), and its outputs are bounded. For an analyzed Node package these are build and test from its scripts, and the builder's own commands: the version stamp (version), the npm install (prepare), npm pack (package) and the default ESLint and Prettier checks (lint, format-check) of a package without such scripts. A builder command's facts name it (runner) and apply only to an action running that command, so pnpm and Yarn installs and packs, workspace plans, application packages, Biome and authored replacements keep the target-scope key. See builder-owned stages
Keythe digest of the captured source entries the contract's reads select, plus the output digests of every earlier action of the target (not only the ones it names) except a check ordered before it only to share the workspace (see checks that run at once), the frozen action, toolchain, prepared dependencies and materialized artifacts. Editing a file the stage does not read leaves its key unchanged only when the edit also leaves the development version unchanged: a test-only file, or the script of a pre_build hook whose version is finalized after it. Any other edit in the target changes the version, which is in every action's environment, so it re-keys every action
Viewbefore the action runs, the executor builds a private view of the target workspace holding only the declared reads, what the earlier actions its key follows created, and the artifacts materialized for it, and mounts it as /workspace. Files outside it do not exist for the action
Mergewhen the action ends, what it created, changed or deleted in the view is merged back into the target workspace, so the next action and the change tracker see what an unconfined run would have left
Not confinedany action without a contract, with an unbounded unknown fact or an unknown write, on a builder without analysis, on the native host path, and on hosts without view support. Each keeps the target-scope key; narrow keys never exist without confinement

The EX-033 api target, oyzu build --full, after appending a comment to api/test/greeting.test.mjs:

  · api:build              Reused from an earlier run · not executed now · originally ran … (key 0452eeca9fb2)
  › api:test               Running
  Cache    active · 3 targets reused

Since the builder's own stages are confined too (2026-10-10), the same edit also reuses api:version, api:prepare and api:package (it packs only files: ["dist"]) and re-runs api:lint and api:format-check, which read every JavaScript file of the target.

manifest.extensions["oyzu.dev/action-cache"].targets.<target>.confined lists the actions run confined, and actions shows each one's outcome.

--no-cache and cache.local = false disable result lookup and storage, while eligible actions keep the same private views and predecessor effects. A fresh oracle therefore executes the same admitted file boundary as a reusable run. Disabling reuse does not expose undeclared files.

Bounded unknowns​

Status: experimental (OEP-0020 NSA-02, 2026-10-10; design: bounded unknowns). An unknown fact may carry a bound: the files, globs, task environment or installed packages the construct cannot read outside of. A stage whose unknown facts are all bounded has the rung widened: its contract's reads gain each bound, it stays confinable, and it runs confined with a narrow key like any other. One unbounded unknown keeps the whole stage on the target-scope key, unconfined, as before.

BoundCoversExample
Hardwhat the tool's own rules allownpm pack files entries (the package directory), an unexpanded test pattern (the runner's root), a computed environment mode (<envDir>/.env*), a missing relative import (the files resolution probes), a tsconfig extending a package (installed packages and the configuration's directory), computed process.env access and Nitro provider detection (the task's environment)
Heuristicwhere a tool usually staysa command with no tool profile (prettier, biome, oxlint, tsup) or an unmodeled subcommand or flag of a modeled one (next lint, ng test, vitest --coverage): its directory, the files directly in each directory above it, and installed packages. Task runners (turbo, nx, lerna, ultra, wireit) are never bounded

A bound that relies on installed packages counts only for an action that reads the prepared dependencies, which key them. If a confined widened action reads outside its bound, it fails with the path and the inputs declaration that fixes it (below); declared inputs add to the bound but never bound an unbounded unknown. oyzu build --plan shows the rung (scope: widened) and each bound in the Why column of the Unknown (widens scope) group; --why <path> answers covered-by-bound for a path only a bound covers.

Checks that run at once​

Status: experimental (parallel block WS2, 2026-10-10). The check stages of one target (test, lint, format-check, scheduled by --full or CI) leave nothing another check consumes, so the plan marks the edge between two consecutive ones as order only (extensions["oyzu.dev/order-only"] on the later action). A hook between them, or a declared depends_on, keeps the edge a real dependency.

When build.jobs is above 1, the executor starts a check as soon as what it really needs (for example build) has finished, beside the checks ordered before it, if all of these hold:

  • the check runs confined (its contract is confinable, the host has view support, and --verify-contract is not set);
  • every action of its target already running is a check running confined;
  • no two of them declare writes that could meet (a glob counts as its literal directory).

Otherwise it waits for its turn as before. Order-only edges change three things, in serial and parallel runs alike, so both give the same keys and outputs:

Behavior
Viewa check's view leaves out what the checks ordered before it left, even where its read globs match, and checks that may overlap get copied files instead of hard links, so one check's in-place write cannot reach another
Keya check's key follows the actions its view shows, not the checks ordered before it; package still follows every check
Failurea failed check no longer blocks the next check; it still blocks package and everything after it

A check that finishes before the checks ordered ahead of it is recorded after them, so the target workspace changes in plan order. The build prints overlapping checks as running at the same time. Not covered: the independent-targets pipeline still runs one action per target at a time (each branch holds one worker), the native host path and Windows have no views, and oyzu run stays serial.

Development versions and test files​

For a captured target whose complete final selected commands are bounded, cacheable and confinable, the development source suffix now uses the positive read boundary of its shipping commands, together with captured configuration and lock paths and declared inputs. A check's reads stay included if its writes can feed a shipping command, including through another check. This can keep an unrelated target's version unchanged after a shared-source edit that none of its commands reads. It uses the same rule with reuse enabled or disabled.

This final binding currently requires Unix view support. Targets with hooks, authored replacements, source projections, materialized artifact inputs or cross-target prerequisites retain their established conservative version scope. Missing or unstable final command evidence also keeps that scope atomically; preparation is not rerun. See version inference.

A development snapshot version (1.2.3-dev.g<digest>) is written into package.json by the version action, so it is an input of every later action. The earlier conservative path derived from the whole target scope, which made build impossible to reuse after any edit. It now derives from the same scope minus files that only a quality stage (test, lint, format-check) is known to read exactly: a file the analysis lists as an exact read of test and that no other stage reads, writes or is covered by. An unknown fact of a shipping stage (build, package) counts as reading its bound, or every file when it has none, so a test-only file a computed import of build may reach stays in the version. The reads of the builder's own commands (npm pack packing a package without files, for example) do not count here, so modeling those stages did not change any version. A test-only edit therefore changes neither the version nor the artifact names; a new test file, which only a glob finds, still does. This holds for a target at the project root too (EX-031). When several targets share the directory holding a file, such as a package and an image at the root, the file is left out only if every one of them reads it only from a quality stage; otherwise each version still covers it. The script of a followed pre_build hook also leaves its own target's scope (not when another target shares that directory), and what the hook wrote is folded in after it runs (version finalization). Tagged and history-derived versions are unchanged. The version reaches every action as OYZU_VERSION, so any other edit in the target re-keys all of them.

When a confined action reads something undeclared​

If a confined action fails and its output names a file that exists in the target but not in the view, the build reports the stage, the path, the missing fact and the smallest fix, in human, NO_COLOR and --json output (diagnostic confined-read-outside-contract; structured detail in manifest.extensions["oyzu.dev/contract-violations"]):

ERROR  api:build read extra.txt, which its stage contract does not declare, so the confined view hid it.
         Missing fact: reads-path extra.txt
         Fix: declare it as an input of api in build.yaml:  inputs: ["api/extra.txt"]
         (Or make the reference static so the analysis sees it.)

The fix is to declare the path (see Declared inputs): the declaration in the message is relative to build.yaml, as inputs are, while the read path is shown as the target's own files write it. --json carries the same declaration as fix.declare.inputs. Making the reference static removes the need for it. Disabling the cache preserves the admitted view. The file is found by scanning the action's output for paths, so a tool that fails without printing the path is reported only as a failed action. The builder's node --test stage writes JUnit and coverage to report files, which do not carry a test file's own error output, so it also runs the spec reporter on the action's stderr: a test file that reads an undeclared file is explained like any other stage. The behavior is the same when targets run in parallel; see the parallel soundness gate.

Declared inputs​

A target's inputs in build.yaml name extra source paths it reads (files or directories, relative to build.yaml; see target workspaces). On the captured path each one:

  • joins the target's input scope, so the target-scope key and the development snapshot version cover it;
  • joins the reads of every stage contract of the target (source: "build.yaml", confidence exact), so a confined action sees it and its narrow key covers it. A target-level input therefore also re-keys test when the file changes, even if only build reads it;
  • only adds. It never removes an inferred read, and it never makes an action confinable: an action whose contract has an unbounded unknown fact keeps the target-scope key whatever is listed.

An input that leaves the workspace (the directory holding build.yaml) or names no captured file is a CONFIG_INVALID_VALUE error before anything runs, so a typo cannot silently declare nothing. Globs are not accepted; a directory covers everything beneath it. --affected does not yet treat a change under another target's declared input as affecting the declaring target.

Verifying a contract​

oyzu build --verify-contract     # also: --json, --full

The flag name is provisional (confirmed direction, name pending maintainer confirmation). It cannot be combined with --no-cache or --plan. A normal build runs; additionally, for every confined action:

  1. the action starts from a copy of its target workspace and runs confined, as usual;
  2. the same action runs again from an identical copy with the whole target visible;
  3. the results are compared: exit code, every workspace file created, changed or deleted, and the artifacts collected. Test and coverage report files are not compared, because they carry timing.

Equal results pass. If they differ, Oyzu runs the action again with subsets of the hidden files (at most twelve extra runs) to find a minimal set that explains the difference, and names those files and the declaration that fixes them:

  Contract check  failed · 8 confined actions run again with their whole target visible · 7 equal · 1 diverged · 20 not confined (not checked)
  api:build                 Diverged · also reads optional.json · declare inputs: ["api/optional.json"]

A divergence fails the build, also when independent targets run in parallel (diagnostic contract-diverged; manifest.extensions["oyzu.dev/contract-verification"] carries status, counts and one record per action). The check reuses and stores nothing (it uses a throwaway store), does not use a tracer and does not run on the native path. It runs each confined action at least twice with copies of the workspace, so it is slow on large installed trees. Actions that are not confined are counted, not checked. If the search stops at its budget the record says minimal: false.

Remote OCI cache​

Status: experimental (OEP-0011 milestones 2 and 3, handoffs K3 and K4; registry sign-in added 2026-10-10). Unsigned: a CI repository is trusted only because its registry refuses writes without the CI credential (see CI and development repositories); no producer is verified. Verified on Linux against zot 2.1.18 (anonymous), CNCF Distribution 3.1.2 behind a registry token service with an S3-API store, and a Harbor 2.13.1 proxy-cache project in front of that registry. The entry format is frozen (2026-10-10, under its v1alpha1 identifiers); design: the object-count rules.

# oyzu.toml (project): where results are shared
[cache]
remote = "oci://registry.example.com/team/oyzu-cache"

cache.remote and cache.ciRemote are accepted only in user/global, machine or administrative scope. Project/local files that set either key fail with a scope diagnostic. Use OYZU_CACHE_REMOTE and OYZU_CACHE_CI_REMOTE for invocation or CI configuration; they override ordinary files and remain subject to administrative constraints. These restrictions apply even to trusted project folders.

# user configuration: this machine also publishes what it builds
[cache]
write = true

A registry that requires sign-in is supported through the registry token flow. The credential is an environment variable, never a setting:

export OYZU_CACHE_TOKEN=…   # the token your registry's token endpoint accepts

In a CI job that offers OIDC ID tokens the way GitHub Actions does (OYZU_ID_TOKEN_URL and OYZU_ID_TOKEN_REQUEST_TOKEN, which the Oyzu runner sets), leave OYZU_CACHE_TOKEN unset: the client signs in with the job's own ID tokens and asks for a new one when it needs it (see sign-in below).

Reading is on by default once cache.remote is set (cache.read = true); writing is off until cache.write = true. Both are per-machine preferences; neither changes an action key, so readers and writers share entries. A loopback host (localhost, 127.0.0.0/8, ::1) is reached over plain HTTP, every other host over HTTPS with the shared proxy and trust settings. The remote is used only while the local cache is active: --no-cache, cache.local = false and --verify-contract use no remote.

What is shared: per-action results on targets reused action by action (captured node/package and node/app targets with stage contracts), and whole-target results on targets reused only whole (the native host path, other builders), one entry under the target key. A per-action target's group view is never pushed; a client rebuilds it locally from the action results, so an unchanged repeat after a remote hit makes no registry request. In the build record a whole-target entry is listed under the target's id where an action id would be.

Sign-in and redirects:

  • The credential is first sent as a bearer token. The first 401 carrying a Bearer challenge names the registry's token endpoint. It is used only when it is on the registry's own origin (scheme, host and port); otherwise the request is a denial and the credential is never sent elsewhere.
  • The client then asks that endpoint for one token per repository, before its first request there, with OYZU_CACHE_TOKEN as the Basic password (user name oyzu), or with no credential when the variable is unset or empty. Tokens ask for pull, plus push when cache.write is true. A rejected or expired token is fetched again once; a second refusal is a denial.
  • Without OYZU_CACHE_TOKEN, when OYZU_ID_TOKEN_URL and OYZU_ID_TOKEN_REQUEST_TOKEN are both set, the Basic password is a CI job ID token instead: GET $OYZU_ID_TOKEN_URL with ?audience=<configured registry origin> (scheme, host and non-default port) and the request token as a bearer, answered with {"value": "<jwt>"}. The ID token is reused until 30 seconds before its exp, then fetched again, and fetched once more when the token endpoint refuses it. ID tokens live minutes (five on Oyzu runners), so a build that pushes for longer than that keeps signing in to each shard it reaches later. The request token goes only to that URL; neither is recorded. Each fetch is counted as GET id token in the request counts.
  • With the sharded layout below, a build asks for at most one token per shard it touches (7 for EX-034's seven actions).
  • A blob response may redirect to another host, for example a registry that serves large blobs from a separate blobs hostname through short-lived signed links. Redirects are followed without the Authorization header when they change origin, at most 5, and never from HTTPS to HTTP.
  • An empty Docker-Content-Digest header (Harbor's proxy cache sends one on its first fetch) is treated as no claim; the manifest is still checked against its key annotation and every blob.

Layout (frozen 2026-10-10 under its draft identifiers): repository <prefix>/v1alpha1/<first two key hex>, tag lookup-<64-hex key>, an OCI image manifest with artifactType application/vnd.oyzu.action-result.v1alpha1, the action-result descriptor as config (application/vnd.oyzu.action-result.config.v1alpha1+json) and one layer (application/vnd.oyzu.tree.v1alpha1.tar+zstd) holding every blob the descriptor references, named sha256/<hex>, sorted, mode 0644, owner and time 0. Annotations: dev.oyzu.action.key, dev.oyzu.action.output and, on the layer, dev.oyzu.tree.uncompressed-digest.

What makes the CI repository trusted is the registry, not Oyzu. The registry must refuse writes to it without the CI credential; detecting CI only narrows what a build accepts and grants nothing. A build that sets CI without the credential is refused (403), keeps building and writes nothing. A CI build never reuses a developer's upload: it does not read cache.remote, and a result in its local store that came from a development remote is looked up again in the CI repository. A remote hit is recorded with its scope (ci or development), in the hit list and in the local result's remote-origin. Nothing is signed, so a hit from the CI repository says where it was read, not who produced it.

The registry credential is OYZU_CACHE_TOKEN or, without it, the CI job's ID tokens (never a setting). OYZU_CACHE_TOKEN is sent as a bearer token on every request to the configured registry host, over HTTPS or to a loopback host, and dropped when a redirect leads elsewhere (blob storage). When the registry answers with a token-flow challenge instead, it is exchanged for a per-repository token as described under sign-in above. It is never written to a record or a log.

Immutable tags. cache.immutableTags = true says every configured cache repository refuses to replace a tag, as the platform build cache registry does. A push then skips the racing-writer read, so a pushed action costs 6 requests instead of 7, and a refused manifest PUT (409 or 412) is the conflict. Do not set it for a registry that replaces tags: the last writer would then win silently. Without it the read stays, which is how customer-run registries are used; a refusal there is still a conflict. Either way a tag is only how an entry is found: a hit is used only after the digests its manifest names verify.

Limits (not covered)​

Sign-in uses only OYZU_CACHE_TOKEN, as a bearer token or through the registry token flow, or a CI job's ID tokens through the token flow (no Basic auth to the registry itself, credential helpers, Docker configuration or login command, and no OAuth2 POST token form); no capability probes, so immutable tags are declared, not detected; no signing or producer verification; no batched lookup (rule 7: an action's key includes the outputs of the actions it follows, so lookups can be grouped only across actions whose predecessors have all resolved), minimum entry size (rule 3) or strict tag enumeration (rule 6); no remote retention or pruning; a damaged remote entry is rejected by every reader but never repaired or replaced; an entry pushed before the format freeze (no keyComponents in its config) is rejected like a damaged one; entries above 256 MiB are not pushed; transfers are sequential, so the four-transfer parallel limit is not exercised; verified only on Linux against zot, Distribution behind a token service and a Harbor proxy-cache project (no Artifactory, Nexus, Docker Hub, GHCR, Windows or macOS); no CACHE-04 or any producer trust: a remote hit says which run produced it, never that this run executed it.

Inputs and what invalidates a target​

A target's action key is a SHA-256 over frozen plan values and captured inputs only:

InputNotes
The target's actionscommand, environment, working directory, platforms, limits, report contracts, configuration digest (scheduling settings such as build.jobs and transport settings are not part of it)
Scoped source digestthe target's own directory, the directories of every target it declares as a prerequisite (depends_on, materialize, task dependencies — the same edges --affected uses) and every file no target owns (root build.yaml, oyzu.toml, locks)
Toolchain identitythe resolved image's content digest, not its tag
Prepared dependenciesthe dependency snapshot's content (lock digests, prepared tree, manager identity), not where or when it was prepared
Builder identitythe builder's digest
Materialized inputsthe digests of artifacts consumed from producer targets, available only after producers finish

Host paths, run identifiers, timestamps, credentials, the number of parallel jobs and the whole-tree source digest never enter a key, so a serial build, a --jobs N build and a host with a different core count share hits. Different checkouts, worktrees and branches therefore share hits: a second checkout at a different path reused all four EX-033 targets in the measured run.

Changing any of those inputs for a target re-runs exactly that target; the rest are reused. unused stayed reused across every EX-033 edit, and an API-only edit left shared, web and unused reused.

Native host builds​

The native path has no plan of captured inputs, so its key is built from what the host build actually saw:

InputNotes
The target's actionscommand line (per-invocation locations such as temporary output directories become fixed tokens), environment variable names, working directory, report contracts, configuration digest — never environment values or host paths
Sourcethe target's private source projection digest: its own directory plus any explicitly declared inputs. Isolation makes this sound by construction — the build cannot read anything outside the projection
Toolsthe digest of oyzu.lock (the resolved tool identities) and the host platform
Builderthe Oyzu executable's digest
Materialized inputsthe digests of artifacts consumed from producer targets

Because tools are identified through the lock, a tool that is not in the lock (for example a system C compiler used by cgo, or sh) is not part of the key; use --no-cache after changing such a tool. A restored native target also keeps its materialization receipts. Promoted local binaries (.oyzu/bin) are refreshed from the restored artifact exactly as after an execution.

Trust model and its limit​

The cache trusts the declared target graph, like --affected. An action that reads another target's directory without a declared edge is invisible to the key:

  • the checked-in future-syntax variants/targets/build.yaml declares no edges, so editing shared/ does not invalidate api or web, although their build scripts copy ../shared. Measured: api, web and unused were reused after a shared edit, while oyzu build --no-cache rebuilt them. Native cross-root dependency discovery (the fixture's "inferred" relationships) is not implemented;
  • the runnable overlay used by the regression tests declares depends_on: [shared] for api and web, and there a shared edit re-runs shared, api and web.

Declare relationships in build.yaml, or use --no-cache, for builds that read across target directories.

Unused execution-only settings (for example build.jobs, and --full, which sets the full-checks mode) are part of the configuration digest and therefore also invalidate every key, including each action's; narrowing that is deferred hardening.

Explaining reuse​

Two read-only views answer "why did this stage run or get reused?" (OEP-0020 inspection tier B). Both name the first key component that differs from the last build of the same target or stage, so a miss points at what changed rather than only saying it missed.

Recorded data. Every stored result carries its components in the top-level keyComponents field, an ordered list of {name, digest, parts?} (source also records rung); they travel with a remote entry because the entry's config is the descriptor. (Results written between WS2 and the format freeze kept them in extensions["oyzu.dev/key-components"].) Independently of storage, each lookup records the subject's key in history/<sha256 of subject>.json under the store: the latest key with the run that first and last used it, and the distinct key before it (kind: "action-key-history"). Subjects are a target's group key and, for targets reused action by action, each action's key. History is written even when nothing is stored (a failed build, an always-run target), is a few kilobytes per subject, is removed by oyzu cache clear and is not subject to retention.

A failed local result lookup is recorded as lookup: unavailable, with its actual filesystem/lease cause and execution fallback. It is distinct from a stored result rejected by artifact/report validation. Broad/group scopes retain their conservative membership; native selectors annotate actual changes without narrowing a key. An affected-selection Git baseline and a previous cache-key observation may differ; their contexts remain separate. Explicit --no-cache writes no source history metadata. Retention​

At the end of a build, if the store exceeds 10 GiB, least-recently-used results are evicted until it fits and blobs no remaining result references are removed. A hit refreshes an entry's recency. Eviction touches only the cache directory: bundles in dist hold their own copies and are never affected. The budget is fixed in this milestone; there is no setting for it.

Builds take a shared cross-process lease on store.lock at the first cache read or write and retain it through blob/descriptor publication and deferred restores. Opening an unused store creates neither its directory nor its lock file. Disabled cache runs and runs with nothing cacheable leave the store untouched; end-of-build retention also skips an unused store. Clear and eviction require an exclusive lease. oyzu cache clear fails with a retry diagnostic while a build uses that cache; it leaves active staging and unpublished blobs alone. Retry after the build finishes. End-of-build eviction reports a retention warning on contention, so the store may temporarily exceed its budget; a later build can retry retention. Accessing a store during maintenance reports that it is busy; builds can proceed without that cache, while cache commands return an error. An unsuccessful first lease attempt stays unavailable for that store handle; a subsequent invocation can retry. Do not delete store.lock to resolve contention: the persistent file is the coordination point, and the OS releases a process's lease when it exits. The lease protects cooperating Oyzu processes, not external deletion or filesystems without working OS locks. No new setting or cache-format migration is required.

Copying and verifying cached bytes​

Cache capture hashes file bytes while copying them into private staging and uses that digest for the workspace delta and blob identity. Size and modification-time checks reject observed source changes during the copy. Restore likewise hashes while staging the copy. All files in an action's deferred workspace delta are verified before accepting the hit, and those private verified copies are retained until apply; apply does not reopen or re-hash the cache blobs. Each destination is replaced only after staging succeeds, preserving the previous file when a blob is missing or corrupt. A cross-filesystem restore can require an additional copy into destination-local staging, without another digest pass.

Artifact and report records reuse the digests verified during restore. Directory artifact verification and native report gates still run; this is not a claim that every build file is hashed only once. There is no new option. Corrupt cache data is rejected/quarantined and recomputed as below; disk or permission failures need space/access repaired before retrying. Multi-file apply is not a transactional workspace rollback on later filesystem errors. This applies to build outputs, not installed-tool verification or launch. No capture/restore throughput numbers have been measured for this change.

Maintenance regression tests cover competing-process clear/eviction, human/JSON busy errors, corrupt-blob destination preservation and deferred restore from retained verified bytes. These new tests have not run on the desktop; see verification status.

Compatibility and lifecycle​

  • Contracts change in place at v1alpha1; no version was added. The manifest action gained the optional reuse object, plan actions now set cacheable: true for builder-declared stages (the field existed and was always false), and the manifest and plan schemas accept extensions on artifacts, which the implementation already emitted.
  • Development snapshot versions are now scoped to each target's inputs. Previously the -dev.g… suffix came from the whole captured tree, so any edit renamed every target's outputs. It now derives from the same per-target scope as the key, so an unrelated edit no longer changes a target's version, artifact name or OYZU_VERSION. Tagged and history-derived versions are unchanged. Dependency evidence still records the whole-tree source digest.
  • Upgrading Oyzu invalidates entries (the builder digest is part of the key); nothing is migrated and old entries age out by retention.
  • Python application targets pass the whole-tree digest to the build in the environment (OYZU_SOURCE_DIGEST); they are safe but miss on any edit until that is scoped.
  • Native Python builds now set PYTHONDONTWRITEBYTECODE=1. Previously the first build wrote __pycache__ files into the verified Python installation, and every later build failed with installed payload differs from receipt (also on main), which made repeat native Python builds, and therefore reuse, impossible.

Parallel soundness gate (2026-10-10)​

Parallel builds block P4. Linux x86_64 (cloud container), Docker 29.8.2, Node 22 toolchain image, debug build of the compiled CLI:

python tooling/test-build-scenarios.py --cli target/debug/oyzu --suite node --only parallel-soundness
# longer stress: OYZU_STRESS_TARGETS=10 OYZU_STRESS_ROUNDS=6 OYZU_STRESS_SEED=20261010

The registered parallel-soundness check builds a project of N independent npm packages (default 6) with --full --jobs N and asserts: a parallel build has the same action keys, outcomes, artifacts and confined actions as a serial one; in each seeded round (default 3, seed printed for replay) an undeclared read seeded into the build or test stage of random targets (the first round always seeds a test stage) fails exactly the seeded actions, and every seed is reported with confined-read-outside-contract, the right action, path and fix, while no unseeded action reports a violation; a running action never sees a sibling target's workspace; and --verify-contract reports exactly the seeded divergences. Each round records how many actions overlapped across targets and within one target, so the check shows which concurrency it exercised. Result: passed, 9 seeded undeclared reads over 3 rounds (seed 7) each failed exactly their action and the 8 build seeds were explained; a 10-target, 6-round run (seed 20261010) failed exactly all 30 seeds and explained the 12 build seeds. Up to 5 actions overlapped across targets (worker-memory admission bounds it below --jobs) and 1 within a target, since parallel stage admission (P2) had not landed. Re-run on 2026-10-10 after node --test gained the spec reporter on stderr (6 targets, 3 rounds, seed 200643300): passed, all 9 seeds explained, 5 of them in test stages.

Fixed by this gate: build.jobs was part of the configuration digest, so every key changed with --jobs (or the host's core count, its default) and a serial build was never reused by a parallel one; and branches of independent targets dropped contract violations and --verify-contract records when collected, so a divergence did not fail a parallel build.
