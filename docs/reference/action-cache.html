Action cache

CLI reference

Published from the canonical docs/reference/action-cache.md file. Features marked experimental remain experimental; check support limitations before relying on them.

A repeat oyzu build skips targets whose inputs haven't changed and restores their earlier results. You configure nothing: you never write cache keys or per-language cache paths. This page covers what is reused, what invalidates it, how to see why a stage ran, and how to share results through a registry.

Note: The action cache is experimental. The remote cache is unsigned, so a remote hit tells you which run produced a result, not that the result was verified.

Usage​

oyzu build                       # first build runs and stores; repeats reuse
oyzu build --affected HEAD       # Git-selected targets also reuse unchanged results
oyzu build --full                # quality stages and their reports are reused too
oyzu build --no-cache            # run every action; read and write nothing
oyzu cache status                # where the store is, how large, how many entries
oyzu cache clear                 # remove every cached result (bundles are untouched)
oyzu build --explain             # after the build, why each stage was reused or ran
oyzu cache explain api           # why target api's key (and its stages' keys) last changed

Every oyzu cache command supports the global --json flag before or after the subcommand. They read no project beyond configuration.

Output shortened. A project with four targets, one run each:

$ oyzu build                         # cold
✓ Build succeeded   4 targets · 4 executed · 9.4s
$ oyzu build                         # unchanged repeat
  ↺ api    build                                   reused   was 1.2s
✓ Build succeeded   4 targets · 4 reused · 1.8s
$ echo "// edit" >> api/src/greeting.mjs && oyzu build
✓ Build succeeded   4 targets · 3 reused · 1 executed · 3.1s

Reuse is local to one user on one machine unless you configure a remote cache. Every output says plainly that a restored result was not executed now:

  • Receipts keep reused test evidence apart from fresh tests.
  • When known, reuse.source records whether the local or remote store served the result.
  • An unavailable cache is different from --no-cache. If the store can't be used, permitted native builds continue with a warning and run everything.

Controls​

ControlEffect

cache.dirAbsolute directory that replaces the default store location. User or system scope only. A project oyzu.toml or oyzu.local.toml that sets it is rejected with CONFIG_SCOPE. User-scope configuration is ignored in CI.

See configuration. Keys and cache paths are never user-authored.

Native builds work from a private copy of each target's source, kept in a host-workspaces folder next to the action store. It follows the platform cache location, not cache.dir. If that folder is on a different drive than your checkout (for example the cache on C: and the repository on E:), Oyzu parks the copy in the repository's Git directory instead (.git/oyzu/host-workspaces, or the linked worktree's Git directory), so parking stays a rename rather than a full copy. The first such build moves a copy parked at the old location. Use build.host-workspaces-dir to choose the folder yourself. It must be outside the source tree; the Git directory counts as outside. The path must not pass through a symbolic link, except root-owned top-level links in a root-owned filesystem root that is not writable by group or others, such as macOS /tmp and /var. Oyzu renames the copy into place when it can, and otherwise copies only the pruned source, keeping file times and permissions so native tools such as Cargo still see unchanged files as fresh. A real source edit still invalidates native compilation. Oyzu never copies compiler, dependency or tool caches. Changing the setting doesn't move existing parked workspaces.

Location​

HostDefault store
Linux$XDG_CACHE_HOME/oyzu/actions (fallback ~/.cache/oyzu/actions)
macOS~/Library/Caches/Oyzu/actions
Windows%LocalAppData%\Oyzu\cache\actions

The store is per user and shared across projects. It holds blobs/sha256/ (file bytes), results/<key>.json (result descriptors), quarantine/ (rejected data) and tmp/. Output trees are stored as a manifest plus one file per blob, not as a compressed archive.

Retention​

At the end of a build, if the store is over 10 GiB, Oyzu removes the least recently used results until it fits, then removes blobs no result references. A hit refreshes an entry. Eviction touches only the cache. Bundles in dist hold their own copies. The budget is fixed.

  • Builds hold a shared lock on store.lock while they read or write the cache.
  • An unused store isn't created. Runs with the cache disabled, or with nothing cacheable, leave it alone.
  • oyzu cache clear needs exclusive access. While a build uses the cache it fails with a retry message and leaves active staging alone. Retry when the build finishes.
  • If end-of-build eviction hits contention it warns, and the store may briefly exceed its budget. A later build retries.
  • If a store is busy with maintenance, builds proceed without it and cache commands return an error.
  • Don't delete store.lock to clear contention. The lock protects cooperating Oyzu processes, not external deletion or filesystems without working locks.

Copying and verifying cached bytes​

Oyzu hashes file bytes while copying them into the cache and again when restoring them. It checks every file of a restored action before accepting the hit, and it replaces each destination file only after its copy succeeded, so a missing or corrupt blob leaves the previous file in place. Corrupt cache data is rejected, quarantined and recomputed (see Failures and recovery). A restore that touches several files isn't rolled back if a later file operation fails. Artifact and report gates still run after a restore.

What is reused​

The unit of reuse depends on what Oyzu knows about the target:

  • Per action for targets whose actions carry a stage contract (today node/package on the captured path). Each action (for example api:version, api:build, api:package) has its own key and result. See Per-action reuse. The target's group record lists its action results, so an unchanged repeat restores the whole target in one step.
  • Per target for every other builder: one key per target, restoring all its actions together or none.

A reused target or action keeps:

  • its artifacts, byte for byte (each is checked against its recorded digest);
  • its original JUnit, coverage and other reports and their producer evidence;
  • the original run ID, key and completion time, in a reuse record.

Oyzu stores a target only after all its actions succeeded and its reports were collected. Failed, blocked and cancelled targets aren't stored.

Built-in builders declare their own actions, so their stages are cacheable with no configuration. Declared source inputs are included in the target's key on both native and captured paths.

Not cached by default​

These targets simply run, and the output says why:

  • Targets with authored tasks or task overrides that don't ask to be cached, and targets whose hooks ([tasks."api:pre_build"]) declare no outputs. An authored task with cache = true and outputs is cached (see Authored tasks). A hook that declares outputs is followed on targets reused action by action (see Hooks).
  • Targets with hooks on a path that reuses a target only whole (native host targets with hooks, and captured targets without stage contracts). Restoring them would skip hooks that must run on every build.
  • Targets that use secret environment values ({ secret = "…" }).

Native npm applications​

For native npm applications with dependencies, the target includes the prepare action (npm ci). A hit restores the successful result without reinstalling. A miss installs into the private target workspace before pre-build hooks. Results stored by an older Oyzu simply miss. Nothing needs clearing.

Isolated npm downloads​

Before looking up actions, the captured npm path validates native metadata and downloads locked dependency bytes with lifecycle scripts turned off. That script-free step can be reused from the local store.

  • The key covers the full source and target tree, the worker image and platform, the admitted tools, the command and environment, configuration and the download routes. Any change to the source, lock, tools, routes or configuration needs a new download.
  • Tools are checked before lookup, and restored files are verified before use.
  • The later offline install and lifecycle scripts aren't cached.
  • The journal records a reused step as not executed now, with its original time and key.
  • These entries share the local store, lock and 10 GiB budget. They are never uploaded to a remote cache.
  • A missing or damaged entry falls back to a fresh download. Partly restored trees are discarded.
  • --no-cache, cache.local = false and --verify-contract turn this reuse off. Builds with managed configuration, secret environment values or authenticated routes don't use it. Offline builds can reuse earlier captures.

Prepared resources and Go tests​

  • Native builder actions can bind exact prepared-resource files. The plan records those files and their content digest, and execution mounts the same selection even with --no-cache.
  • Native Go tests run in fresh copies of the captured workspace with empty report folders. Their writes are discarded, and validated reports are captured into the build bundle. Reused reports keep their original producer evidence. Workspace consumers of generated files, and --verify-contract, aren't supported on this path. See Go.

Prerequisites and platforms​

  • Captured path: oyzu build and oyzu build --affected on targets that use the Docker executor and its toolchain images (for example node/package).
  • Native host path: builds that run on the host with Oyzu-provisioned tools (node/app dist applications, Go, Rust, Python wheels) reuse unchanged targets the same way. See Native host builds. Targets built by a host-coordinated image worker aren't cached yet and say so. oyzu run executions are never cached.
  • No account is needed. Ephemeral CI runners start with an empty local store. With a remote cache they reuse results other checkouts pushed.
  • Tested mainly on Linux. On a Windows host, shared edits conservatively re-run unrelated work. macOS isn't supported yet.

On Windows, action tracking records native symbolic links and the Linux links Docker creates in a captured workspace without following them, so pnpm links stay usable by later native actions. A change that contains links can't be restored from the cache. Other Windows reparse formats fail with an error.

Output​

In the live Build section, restored actions show ↺ (the word reused without color) in place of executed. The summary counts them apart from executed work (2 targets · 3 reused · 1 executed). With -v and in JSON you also get each target's reuse origin and the Cache line. The final receipt marks test and coverage lines from restored reports as reused from an earlier run, not run now.

In the build bundle a reused action keeps status: "succeeded", so every gate applies unchanged, and gains:

"actionKey": "sha256:…",
"reuse": { "actionKey": "sha256:…", "originalRunId": "…",
           "originalCompletedAt": "2026-10-07T08:43:02Z", "originalDurationMs": 812 }
  • manifest.extensions["oyzu.dev/action-cache"] records the mode, whether the cache was active or disabled (and why) and each target's outcome: reused, executed (with stored, and rejected if a damaged entry was replaced) or not-cached with the reason.
  • Journal events in logs/events.jsonl use the finish status reused. Logs for reused actions aren't recreated.

A hit never skips a gate. On restore, every report is parsed again from its stored bytes and judged by the current contract (for example the coverage minimum). A report that fails there rejects the entry, and the target runs normally. Preflight, policy and required-check enforcement are unchanged.

Explaining reuse​

Two read-only views answer "why did this stage run or get reused?". Both name the first key component that differs from the last build of the same target or stage, so a miss points at what changed.

Each key is made of named components, compared in this order:

ComponentWhat it coversParts named on a change
builderThe builder ID and digest (an Oyzu upgrade changes it)
platform, variantThe target platform and variant
toolchainThe toolchain: image content digest or resolved tool lock, host platform
dependenciesThe prepared dependencies (for Node, node_modules)
sourceThe source digest in scope: the whole target scope, or a confined action's predicted reads
definitionThe frozen action definitions, field by field and environment variable by variable: argv, env.<NAME>, cwd, limits, report contracts, configuration digest, input mountsapi:build env.MODE (group key) or env.MODE (action key)
materializedDigests of artifacts consumed from producer targetsThe artifact ID
upstreamOutput digests of the earlier actions an action followsThe action ID

When several components differ, the first is the reason and the rest are listed after it. The key alone decides reuse. Components only explain it. source comes before definition because an action's environment can carry values derived from source, such as the development version.

Every lookup also records the subject's latest key in history/ under the store: the run that first and last used it, and the distinct key before it. A subject is a target or, for targets reused action by action, each action. History is written even when nothing is stored (a failed build, an always-run target), is a few kilobytes per subject and is removed by oyzu cache clear.

oyzu build --explain​

After the receipt, it shows at most eight action decisions, with a count of the rest. The manifest has complete detail. A blocked or failed action keeps its failure cause. An expanded entry looks like this:

  Why each stage ran or was reused
  api:build — Executed
    Recorded selection: api (requested)
    Reuse: source files in scope changed
    Source comparison: run previous-observation
    changed: shared/greeting.mjs (reads-source)
      Native provenance: applications/api/build.mjs:2 (path, exact)

Other reasons you may see:

  • no earlier build of it is recorded in this cache (first build, or after cache clear)
  • inputs unchanged since run …, but no result is stored (not stored, evicted or cleared)
  • the stored result was rejected: … (damaged entry)
  • a hook runs on every build…
  • a note that the result came from a remote

A stage of a target that is reused or run whole shares the target's reason. A target that isn't cacheable shows its not-cached reason.

--explain conflicts with --plan and --remote. It changes only the human output. The reasons are always in the manifest, under manifest.extensions["oyzu.dev/action-cache"].targets.<target> as explain ({reason, changed?, previousRunId?, sourceChanges?}) and, per action, actionExplain.<action>, so --json carries them without the flag. A failed local lookup is recorded as lookup: unavailable with the cause, which is different from a stored result that failed validation.

Source comparison​

Oyzu keeps a source inventory per captured context in the cache history. sourceChanges compares the previous build's file identities with the current ones under the action's read scope (or the whole target scope), including added and removed files.

  • Exact reads are labeled reads-source, approximate bounds bounded-read, and unmodeled relationships scope-input.
  • sourceChanges.status is available, unavailable or scope-changed. Oyzu never guesses file names when the inventory is missing or the boundary changed.
  • These inventories follow the history rules: --no-cache writes none, and cache clear removes them.
  • Windows has no confined actions, but captured whole-scope comparison works. Native builds without captured context explain at target level only.

oyzu cache explain <target>​

Reads the key history for a target ID (its group key and every recorded action) or one action ID such as api:build. For each it shows the latest key, the runs that first and last used it, whether a result is stored and the first component that differs from the previous key. It reads no project and runs nothing, so it works between builds and on another checkout that shares the store. An unknown name exits non-zero with no key history for <name> in this cache.

$ oyzu cache explain api
Cache key explanation  api

  api (whole target)
    Key        3608cd663130 · since run 26520-… · last seen run 26520-… (2026-10-10T10:04:22Z)
    Result     stored · the next build with these inputs reuses it
    Changed    since run 25996-…: source files in scope changed (also: action definition: api:build env.OYZU_VERSION, api:build env.PROOF_VALUE added and 7 more)

  api:build (stage)
    Key        f700515a6d9c · since run 26520-… · last seen run 26520-… (2026-10-10T10:04:23Z)
    Result     stored · the next build with these inputs reuses it
    Changed    since run 23970-…: source files in scope changed (also: action definition: env.OYZU_VERSION, env.PROOF_VALUE added and 1 more; output of an earlier action: api:version)

--json returns kind: "action-cache-explain" with subjects[] (id, kind, target, actionKey, firstRunId, lastRunId, lastSeenAt, stored, previous, reason, changed).

Limits:

  • History keeps two distinct keys per subject, so cache explain compares the latest keys, not an arbitrary older build. To look at a finished build, use history.
  • A stage's previous run can be older than its target's, because a build that restores a target whole doesn't look up its actions.
  • Builds that share one store at the same time can interleave history writes. Each write is atomic and the later one wins.

Inputs and what invalidates a target​

Every builder operation declares source reads, an explicit unbounded reason, or explicit upstream-only output consumption. A bounded stage keys on its selected files, unowned workspace files, configuration and locks, and the target's declared inputs. A directory read includes its listing: adding a source or test file changes the key. An unbounded stage retains the whole-target source key; its reason explains why narrowing is unavailable.

An admitted upstream_only export reads no source files. Its key uses its own definition, tool/configuration identity and declared upstream output digests, without the target source scope or implicit source inputs. Native admission requires complete observations or fixed command semantics; an empty read list alone never authorizes this. Native Rust binary exports use core-admitted typed copies from the producer's indexed binaries, with stable export paths in each fresh private workspace. Equal producer bytes therefore give equal export output identities despite per-run temporary allocations. Later unconfined checks retain their conservative dependency edges, including the export.

Older published plugins may omit this declaration. Oyzu accepts their results and treats each undeclared operation as unbounded, with the reason plugin <reference> <version> declared no reads. The build reports it once the plugin answers, with one PLUGIN_READS_UNDECLARED warning per plugin per build that asks you to update the plugin. oyzu build --plan never runs the plugin, so its Why column (JSON sourceReason) shows only what Oyzu can tell without it. These operations retain whole-target keys; the SDK and conformance suite require declarations from new and updated plugins.

A target's key is a SHA-256 over these inputs and nothing else:

InputNotes
The target's actionsCommand, environment, working directory, platforms, limits, report contracts and configuration digest. Scheduling settings such as build.jobs aren't part of it.
Source in scopeThe target's own directory, the directories of every target it declares as a prerequisite (depends_on, materialize, task dependencies, the same edges --affected uses) and every file no target owns (root build.yaml, oyzu.toml, locks)
ToolchainThe resolved image's content digest, not its tag
Prepared dependenciesThe dependency snapshot's content (lock digests, prepared tree, manager identity), not where or when it was prepared
BuilderThe builder's digest
Materialized inputsDigests of artifacts consumed from producer targets, known once producers finish

Host paths, run IDs, timestamps, credentials and the number of parallel jobs never enter a key. A serial build, a --jobs N build and a host with a different core count share hits, and so do different checkouts, worktrees and branches.

Changing one target's inputs re-runs exactly that target. One thing to know: execution-only settings such as --full are part of the configuration digest, so changing them re-keys every action.

Native host builds​

The native path has no plan of captured inputs, so its key is built from what the host build actually saw:

InputNotes
The target's actionsEach eligible Rust action, otherwise the whole group: command line (per-invocation locations such as temporary output folders become fixed tokens), environment variable names, working directory, report contracts and configuration identity
SourceThe digest of the target's private source copy: its own directory plus declared inputs. Native tools are host processes, so ambient reads outside this are not in the key.
ToolsThe digest of oyzu.lock and the host platform
BuilderThe Oyzu executable's digest. For a target built by an external builder plugin, also that plugin's identity.
Materialized inputsDigests of artifacts consumed from producer targets
  • A tool that isn't in the lock (a system C compiler used by cgo, or sh) isn't part of the key. Use --no-cache after changing such a tool.
  • A restored native target keeps its materialization receipts, and promoted local binaries (.oyzu/bin) are refreshed from the restored artifact as after a run.
  • Conventional native Rust stages have independent results. Adding --full to an unchanged build reuses the existing executable and runs only the new checks, and a repeat full build restores the checks with their original reports and compiler warnings (labeled as reused). A compile that succeeded stays reusable if a later check fails. Stdout and stderr logs stay available after reuse.
  • Independent Rust stages get separate private source copies and Cargo target folders and can overlap within --jobs. Coverage has its own instrumented compile. Hooks, task replacements and materialized inputs stay serial and whole-target. This is host execution, not a sandbox.
  • The pinned tools must include the selected check helpers. An incomplete lock reports TOOL_LOCK_STALE; run oyzu pin and retry.

Trust model and its limit​

The cache trusts the declared target graph, like --affected. An action that reads another target's directory without a declared edge is invisible to the key. For example, if api and web copy ../shared but declare no relationship to it, editing shared/ reuses their old results, while oyzu build --no-cache rebuilds them. Native cross-root dependency discovery isn't implemented. Declare relationships in build.yaml (depends_on: [shared]), or use --no-cache, for builds that read across target directories.

External builder targets​

A target built by an external builder plugin (a plugins.development or plugins.packages binding) is reused like a built-in target. Oyzu writes the plugin's verified identity on the target record as extensions["oyzu.dev/builder-plugin"] and includes it in the target and action keys next to the Oyzu executable digest:

{"reference":"go/app","source":"package","package":"oyzu/go","version":"0.1.0",
 "release":"sha256:…","executableDigest":"sha256:…","runtime":{"os":"linux","arch":"amd64","abi":null}}
{"reference":"go/app","source":"local-development","executableDigest":"sha256:…",
 "runtime":{"os":"linux","arch":"amd64","abi":null}}
  • runtime uses the plugin package names (linux/darwin/windows, amd64/arm64, gnu/musl/msvc). A development executable's ABI is unknown and recorded as null.
  • A changed plugin executable, package release or version, runtime or reference re-runs the target, and explain reports builder identity changed. Reverting reuses the earlier result.
  • How the plugin was selected (resolved now or locked) doesn't change a key. A plugin-built target never shares a key with the built-in builder it replaces.

A native plugin's private executable copy can have a different path on each run. That execution location does not change the cache key: the key retains the full verified plugin identity instead. Changes to command arguments and plugin bytes still invalidate the result; the private copy and fresh output staging remain. When several builder references share one executable, each target keeps its own verified binding identity; adding another binding does not change that target's key.

For a development binding, the digest covers only the bound file. If that file isn't a native executable (a wrapper script or .cmd file, for example), what it runs is outside the key, so its targets are not-cached with the reason "is built by a development plugin binding that is not a native executable". Bind the plugin executable itself to get reuse. A native wrapper executable is keyed on its own digest alone, so rebuild or rebind it after changing what it starts.

A target built by an installed plugin package (a plugins.packages binding, or a package oyzu.lock selects) shares its results through cache.remote and cache.ciRemote like a built-in target: the key binds the package release and executable digest, so only a machine running the same package release reuses them. A development binding's results stay in the local store, because its executable exists only on that machine. A slice hands plugin-built results off through its --handoff repository like any other. The usual exclusions still apply: --no-cache, cache.local = false, --verify-contract, secret environment values and hooks without declared outputs keep a target out of the cache.

Per-action reuse​

Planning attaches a stage contract to each action of an analyzed target: the reads, writes, environment names and tools the static analysis found for the stage, the actions it follows, and whether its outputs are bounded. A target whose actions all have a contract is reused action by action. Today that is node/package on the captured path.

StepBehavior
LookupThe target's group record is tried first (unchanged target: one step). On a miss, each action is looked up when it becomes ready.
Action keyThe action's frozen definition, the target scope, toolchain, builder, variant, platform, prepared dependencies (only if the action reads them), materialized artifacts and the output digests of the earlier actions it follows
Action resultThe files the action published to the bundle (artifacts, reports), their records and the workspace changes it made (files created, modified and deleted, new folders)
ReuseRecords enter the manifest as succeeded with a reuse record. Reports are parsed again and gated by the current contract. Workspace changes are restored before the next action that has to run, so later actions see what running it would have left. A fully reused target never touches its workspace.
Early cutoffA re-run action that produces the same workspace changes leaves its dependents' keys unchanged, so they are still reused.
Always runsAn action without bounded outputs never gets reused on its own. It runs every time, and what it produces still feeds what follows. A target holding such an action isn't restored whole.
StoringResults are saved only after the whole target succeeded and its reports were collected.

Without a confining contract (see below), an action's key uses the whole target scope. Targets with an authored task or override that doesn't set cache = true with outputs, or a hook without declared outputs, are not cached. An action that creates a symbolic link or special file can't be restored, so it still runs and feeds its dependents but isn't stored. The manifest records each action's outcome (reused, executed, always-run) under manifest.extensions["oyzu.dev/action-cache"].targets.<target>.actions.

Hooks as always-run actions​

A hook ([tasks."api:pre_build"], post_<stage>) that declares outputs doesn't make a per-action target uncacheable:

[tasks."api:pre_build"]
argv = ["node", "hook.mjs"]
outputs = ["generated"]      # workspace paths, folders or globs the hook writes
AspectBehavior
The hookRuns on every build. It is never restored and its record never has reuse. The action record shows always-run.
Its outputThe files it changed are recorded, and their digest enters the key of every later action of the target. A hook that writes something else re-runs what follows. A hook that writes the same bytes leaves it reused.
Target outcomereused when every other action was reused. Otherwise executed. The target's group record isn't stored.
Undeclared effectsA hook that changes a file outside its declared outputs isn't followed. Nothing of the target is stored, and the outcome carries a rejected note naming the files, so the next build runs it again.
No outputsThe target is not-cached ("hooks without declared outputs").
Whole-target pathOn the native host path and on captured targets without stage contracts, a target is only restored whole, which would skip its hooks. It is not-cached and its hooks run every build.

outputs paths are relative to the hook's working directory (the target, unless cwd says otherwise). Use / or \. Editing a hook script counts as a source edit, so it re-runs actions keyed on the target scope and any confined action that reads the script. On Windows no action is confined, so any source edit re-runs the whole target, though an unchanged repeat is still reused.

Whether a script edit also changes the development version, which is in every action's environment, depends on the hook:

HookDevelopment versionComment-only edit of its script
pre_build with outputs, on a builder that finalizes versions (Node)Finalized after the hook (below)Keeps the version. A confined api:build is reused.
Any other hook (pre_test, post_build, …) or another builderThe script stays in the version scopeChanges the version, which re-keys every action of the target

Version finalization after hooks​

On captured Node targets, Oyzu moves the version action after the followed pre_build hooks, so nothing that writes the version runs before them:

  1. Planning records every action in plan.json with the pre-hook source version (the version scope without the hook's script). The target record carries extensions["oyzu.dev/version-finalization"]. The actions before the hook run with the pre-hook version.
  2. When the hooks succeed, the files under their declared outputs are digested from the workspace (so --no-cache gives the same result) and folded into the version. The target is planned again, and the remaining actions run from that post-hook plan, written to plans/<target>.post-hooks.json. plan.json itself isn't changed.
  3. The manifest's target record is the post-hook one. manifest.extensions["oyzu.dev/version-finalization"].<target> gives preHookVersion, version, hookOutputs, planPath and planDigest.

A hook edit that changes what it writes changes the version and the package. A script stays in the version scope if it isn't named as an argument of the hook's command (for example run = "node hook.mjs" through a shell) or if a builder stage reads or writes it. Other builders, other hook phases and the native host path aren't finalized. Effects outside the workspace (network, global state) are invisible to Oyzu, so declare them away yourself.

Authored tasks cached on request​

An authored task or task override isn't cached by default, because Oyzu can't see its effects. Opt in with the cache and outputs task fields:

[tasks."api:test"]
run = "node --test"
cache = true
inputs = ["src/**", "test/**"]   # optional; may only add to the target scope
outputs = [".events"]            # workspace paths, folders or globs the task writes
AspectBehavior
Opt-incache = true and at least one outputs entry. The plan marks the action cacheable: true and records the declaration in extensions["oyzu.dev/authored-cache"]. cache on a hook is ignored: hooks always run.
KeyThe task's frozen definition (command, environment names, working directory, report contracts, configuration digest) and the target scope, as for a builder stage. Editing a file in the target, or the task, re-runs it.
inputsRelative to the task's directory. Entries inside the target are already covered. An entry outside the target isn't supported yet: the target is not-cached ("declares inputs outside its target …").

--no-cache, cache.local = falseNothing is reused or stored.

A task that leaves nothing in the workspace must still name an output (for example the folder its tool writes logs to). Reusing a task around hooks needs per-action reuse, which only captured node/package targets have. A command the builder doesn't recognize for report instrumentation keeps today's reporting behavior.

Confined actions and narrow keys​

A narrow key is only sound if the action can't see anything the key left out. So Oyzu keys an action on the files its contract reads only when the action also runs confined to them. This needs the captured path and a Unix host. Linux is tested. macOS isn't supported yet. Windows doesn't support confinement, so every action there keeps the whole-target key.

StepBehavior
EligibleThe stage's own command was modeled by the analysis, none of its facts is an unbounded unknown (a bounded one adds its bound to the reads, see bounded unknowns), and its outputs are bounded. For an analyzed Node package that covers build and test from its scripts, plus the builder's own commands: version, the npm install (prepare), npm pack (package) and the default ESLint and Prettier checks (lint, format-check) of a package without such scripts. pnpm and Yarn installs and packs, workspace plans, application packages, Biome and authored replacements keep the whole-target key. See builder-owned stages.
KeyThe digest of the source files the contract reads, the output digests of every earlier action of the target (except a check ordered before it only to share the workspace, see checks that run at once), the frozen action, toolchain, prepared dependencies and materialized artifacts. Editing a file the stage doesn't read leaves its key alone only if the edit also leaves the development version unchanged. Any other edit changes the version, which is in every action's environment, and re-keys every action.
ViewBefore the action runs, the executor builds a private view of the workspace with only the declared reads, what the earlier actions created, and the artifacts materialized for it, and mounts it as /workspace. Other files don't exist for the action.
MergeWhen the action ends, what it created, changed or deleted in the view is merged back into the workspace.
Not confinedAny action without a contract, with an unbounded unknown fact or write, on a builder without analysis, on the native host path and on hosts without view support. These keep the whole-target key.

Example: oyzu build --full on a Node api target after appending a comment to api/test/greeting.test.mjs:

  · api:build              Reused from an earlier run · not executed now · originally ran … (key 0452eeca9fb2)
  › api:test               Running
  Cache    active · 3 targets reused

The same edit also reuses api:version, api:prepare and api:package (it packs only files: ["dist"]) and re-runs api:lint and api:format-check, which read every JavaScript file of the target. manifest.extensions["oyzu.dev/action-cache"].targets.<target>.confined lists the confined actions.

--no-cache and cache.local = false turn off lookup and storage, but eligible actions keep the same private views, so a fresh run sees exactly the files a reusable run would.

Bounded unknowns​

Static analysis sometimes meets a construct it can't resolve, an unknown fact. An unknown can carry a bound: the files, globs, task environment or installed packages the construct can't read outside of.

  • A stage whose unknowns are all bounded has scope widened. Its reads gain each bound, and it still runs confined with a narrow key.
  • One unbounded unknown keeps the whole stage on the whole-target key, unconfined.
BoundCoversExample
HardWhat the tool's own rules allownpm pack files entries (the package folder), an unexpanded test pattern (the runner's root), a computed environment mode (<envDir>/.env*), a missing relative import (the files resolution probes), a tsconfig extending a package (installed packages and the config's folder), computed process.env access (the task's environment)
HeuristicWhere a tool usually staysA command with no tool profile (prettier, biome, oxlint, tsup) or an unmodeled subcommand or flag (next lint, ng test, vitest --coverage): its folder, the files directly in each folder above it, and installed packages. Task runners (turbo, nx, lerna, ultra, wireit) are never bounded.

A bound that relies on installed packages counts only for an action that reads the prepared dependencies. If a confined widened action reads outside its bound, it fails with the path and the inputs fix (see below). Declared inputs add to a bound but never bound an unbounded unknown. oyzu build --plan shows scope: widened and each bound in the Why column. --why <path> answers covered-by-bound for a path only a bound covers.

Checks that run at once​

The check stages of one target (test, lint, format-check, scheduled by --full or CI) don't produce anything another check consumes, so the plan marks the edge between two consecutive checks as order-only. A hook between them, or a declared depends_on, keeps the edge a real dependency.

When build.jobs is above 1, a check starts as soon as what it really needs (for example build) has finished, beside the checks ordered before it, if all of these hold:

  • the check runs confined (and --verify-contract isn't set);
  • every action of its target already running is a confined check;
  • no two of them declare writes that could meet (a glob counts as its literal folder).

Otherwise it waits its turn. Serial and parallel runs give the same keys and outputs:

Behavior
ViewA check's view leaves out what the checks ordered before it left, and checks that may overlap get copied files instead of hard links, so one check's in-place write can't reach another.
KeyA check's key follows the actions its view shows, not the checks ordered before it. package still follows every check.
FailureA failed check doesn't block the next check. It still blocks package and everything after it.

A check that finishes early is recorded after the checks ordered ahead of it. Different targets still run one action at a time per branch. The native host path and Windows have no views, and oyzu run stays serial.

Development versions and test files​

A development snapshot version (1.2.3-dev.g<digest>) is written into package.json by the version action, so it feeds every later action. Oyzu derives it from the target's source scope, minus files that only a quality stage (test, lint, format-check) is known to read exactly.

  • A test-only edit changes neither the version nor the artifact names. A new test file, which only a glob finds, does.
  • An unknown fact of a shipping stage (build, package) counts as reading its bound, or every file if it has none, so a test-only file that a computed import of build may reach stays in the version.
  • If several targets share the folder holding a file, the file is left out only if every one of them reads it only from a quality stage.
  • The script of a followed pre_build hook leaves its own target's scope, and what the hook wrote is folded in after it runs (version finalization).
  • For a captured target whose final commands are all bounded, cacheable and confinable, the suffix uses the files its shipping commands read, plus configuration, lock files and declared inputs. This needs Unix view support. Targets with hooks, authored replacements, source projections, materialized inputs or cross-target prerequisites keep the wider scope. See version inference.
  • Tagged and history-derived versions don't change. The version reaches every action as OYZU_VERSION.

When a confined action reads something undeclared​

If a confined action fails and its output names a file that exists in the target but not in the view, the build reports the stage, the path, the missing fact and the smallest fix, in human, NO_COLOR and --json output (diagnostic confined-read-outside-contract, with details in manifest.extensions["oyzu.dev/contract-violations"]):

ERROR  api:build read extra.txt, which its stage contract does not declare, so the confined view hid it.
         Missing fact: reads-path extra.txt
         Fix: declare it as an input of api in build.yaml:  inputs: ["api/extra.txt"]
         (Or make the reference static so the analysis sees it.)

Declare the path as an input. The declaration is relative to build.yaml, while the read path is shown as the target's own files write it. --json carries the same declaration as fix.declare.inputs. Oyzu finds the file by scanning the action's output for paths, so a tool that fails without printing the path is reported only as a failed action. The builder's node --test stage also runs the spec reporter on stderr, so a test file that reads an undeclared file is explained like any other stage. The behavior is the same when targets run in parallel.

Declared inputs​

A target's inputs in build.yaml name extra source paths it reads (files or folders, relative to build.yaml; see target workspaces). On captured and bounded native paths each one:

  • joins the target's source scope, so the whole-target key and the development version cover it;
  • joins the reads of every stage contract of the target, so a confined action sees it and its narrow key covers it. A target-level input re-keys test too when the file changes, even if only build reads it;
  • only adds. It never removes an inferred read, and it never makes an action confinable.

An input that leaves the workspace (the folder holding build.yaml) or names no captured file is a CONFIG_INVALID_VALUE error before anything runs, so a typo can't silently declare nothing. Globs aren't accepted. A folder covers everything beneath it. --affected doesn't yet treat a change under another target's declared input as affecting the declaring target.

Native Rust source reads​

Rust predicts each stage's reads from Cargo workspace manifests and target source folders, Cargo and Rust configuration, build scripts, and literal include_str!, include_bytes!, include! and #[path] references. Manifest-relative concat!(env!("CARGO_MANIFEST_DIR"), ...) references with literal suffixes are resolved too. Source and discovery directories remain conservative directory reads.

Native Cargo paths are resolved against the workspace recorded in Cargo metadata, including when Cargo ran in a parked source projection. Manifests, source files, build-script watches and dep-info are mapped to target-relative read selectors; the projection's location does not become part of those paths. A Cargo source outside that workspace is reported with the offending path.

Native compiling stages also need complete Cargo dep-info and build-script records. Until those records are available, they keep the whole-target key. After execution, a read outside the prediction prevents result storage and reports confined-read-outside-contract, naming the path and the inputs declaration that adds it. Human, no-color and JSON diagnostics carry the same fix. A missing or incomplete observation never authorizes storage under a narrow key.

format-check uses rustfmt's fixed module-tree and configuration rules and does not need a runtime observation. Native test and coverage remain unbounded: tests may read files at run time.

Cargo dep-info never records a proc macro's reads. Rust uses an allowlist of reviewed implementations identified by package name, version and checksum in Cargo.lock. A name match or registry provenance alone grants no allowance. File-free implementations qualify only at their reviewed identity. Changing the version or checksum requires reassessment. Output-affecting environment must also be covered by the key; rustversion binds RUSTC and RUSTC_WRAPPER in addition to the selected compiler identity.

The macro set comes from Cargo's target-filtered resolved graph, following only dependencies reachable from the selected workspace packages. It does not come from every package in the lock or Cargo's general inventory. A wasm-only macro therefore does not affect Linux or Windows host lint. A macro that really builds for the host still needs an allowance. Missing or mismatched target resolution keeps native compiling stages unbounded until preparation refreshes it.

Reviewed manifest-only readers are bounded when the caller's manifest is already covered by a registry checksum or by the workspace stage's source reads, and the workspace root Cargo.toml and Cargo.lock are also in the key. This covers zbus_macros 4.4.0 and zvariant_derive 4.2.0 with their reviewed proc-macro-crate 3.5.0 helper, including cargo locate-project. The check includes possible downstream callers through macro re-exports. A caller manifest outside these bounds prevents the allowance and appears in the unbounded reason.

Other file-reading macros need a reviewed rule establishing fixed reads inside reviewed callers' unpacked, checksummed registry source. The caller identities are pinned too, including their re-export behavior. The lock already covers those files, so they need no extra digest. Currently the reviewed combination is document-features 0.2.12 used by crossterm 0.29.0, with both checksums pinned: it reads only crossterm's Cargo.toml and Cargo.toml.orig, and crossterm does not re-export the macro to downstream callers. Other consumer identities need their own read-rule assessment. A path dependency, workspace member, Git dependency, missing checksum or local source replacement does not qualify under this registry-source rule. Workspace manifests already in the key can qualify under the separate manifest-only rule. Unknown implementations and reads outside a reviewed rule stay unbounded and name the macro. For example, wasm-bindgen-macro reads caller-selected JavaScript and stays unbounded if it actually builds for the stage's target. Other unresolved include expressions name their source file and line.

An OUT_DIR include is generated output: its source inputs are the build script and its rerun-if-changed paths. A watched directory includes all its contents. Without any rerun-if-changed, the stage is unbounded because Cargo uses package changes as the default. rerun-if-env-changed names contribute their effective environment values to the key without publishing those values. Acquired compiler and dependency inputs retain their separately admitted identities.

Git metadata watched by a build script is a real input, including in linked worktrees. A script that watches .git/HEAD or its branch reference prevents compiling-stage reuse when that identity changes, even for a documentation-only commit. Unstaged edits outside predicted reads can still reuse a bounded stage. Changing build identity is a project decision; Oyzu does not remove those watches.

Verifying a contract​

oyzu build --verify-contract     # also: --json, --full

This can't be combined with --no-cache or --plan. A normal build runs. In addition, for every confined action:

  1. The action starts from a copy of its target workspace and runs confined, as usual.
  2. The same action runs again from an identical copy with the whole target visible.
  3. Oyzu compares the results: exit code, every workspace file created, changed or deleted, and the artifacts collected. Test and coverage report files aren't compared, because they carry timing.

Equal results pass. If they differ, Oyzu re-runs the action with subsets of the hidden files (at most twelve extra runs) to find a minimal set that explains the difference, and names those files and the declaration that fixes them:

  Contract check  failed · 8 confined actions run again with their whole target visible · 7 equal · 1 diverged · 20 not confined (not checked)
  api:build                 Diverged · also reads optional.json · declare inputs: ["api/optional.json"]

A divergence fails the build, including when independent targets run in parallel (diagnostic contract-diverged; manifest.extensions["oyzu.dev/contract-verification"] has status, counts and one record per action). The check uses a throwaway store, so it reuses and stores nothing. It doesn't run on the native path. Each confined action runs at least twice with copies of the workspace, so it is slow on large installed trees. Actions that aren't confined are counted, not checked. If the search stops at its budget, the record says minimal: false.

Remote OCI cache​

You can share action results through any OCI registry. Share them from CI to developers, or between a team's machines.

# oyzu.toml (project): where results are shared
[cache]
remote = "oci://registry.example.com/team/oyzu-cache"
# user configuration: this machine also publishes what it builds
[cache]
write = true

Supported registries: zot, CNCF Distribution behind a token service, and a Harbor proxy-cache project, on Linux. Other registries (Artifactory, Nexus, Docker Hub, GHCR) aren't supported yet, and neither are Windows and macOS clients.

Settings and scope​

SettingDefaultMeaning
cache.remoteunsetThe OCI repository to share results. Accepted only in user/global, machine or administrative scope.
cache.readtrue once cache.remote is setLook results up.
cache.writefalsePublish results.
cache.ciRemoteunsetThe CI repository, see CI and development repositories. Same scope rule as cache.remote.
cache.immutableTagsfalseThe registry never replaces a tag. See CI and development repositories.
  • A project or local file that sets cache.remote or cache.ciRemote fails with a scope error, even in trusted project folders. Use the environment variables OYZU_CACHE_REMOTE and OYZU_CACHE_CI_REMOTE for one invocation or CI. They override ordinary files and stay subject to administrative constraints.
  • cache.read and cache.write are per-machine preferences and don't change action keys, so readers and writers share entries.
  • A loopback host (localhost, 127.0.0.0/8, ::1) is reached over plain HTTP. Every other host uses HTTPS with the shared proxy and trust settings.
  • The remote is used only while the local cache is active. --no-cache, cache.local = false and --verify-contract use no remote.

What is shared​

  • Per-action results, for targets reused action by action (captured node/package and node/app targets with stage contracts).
  • Whole-target results, for targets reused only whole (the native host path, other builders). These appear under the target's ID in the build record where an action ID would be.

A per-action target's group record is never pushed. A client rebuilds it from the action results, so an unchanged repeat after a remote hit makes no registry request.

Request flow​

StepBehavior
LookupAfter a local miss, one GET of the manifest under the action's tag. On a hit, two blob GETs (config and layer). No HEAD requests, no tag listing.
VerifyManifest shape, media types, key annotation, config and layer size and SHA-256, the uncompressed archive's SHA-256, every archive entry against its name, and the entries against the blobs the config references. Only then is the result committed to the local store.
PushAfter an action's result is committed locally and cache.write is true: one GET of the tag (to check for a racing writer), config and layer uploads, then the manifest PUT, which is the only write that makes the entry visible.
Offering a reused resultIf a build reuses a result this machine produced but never sent to this remote (stored before the remote was configured, or while it was down), it is pushed the same way. The store then marks it sent, so later reuses ask nothing. Results that came from a remote aren't offered.
Racing writersEqual output identity (artifact digests and workspace changes; reports are excluded because they carry timing) converges and writes nothing. A different one is a conflict: recorded, never replaced.

Sign-in and redirects​

A registry that requires sign-in is supported through the registry token flow. The credential is an environment variable, never a setting:

export OYZU_CACHE_TOKEN=…   # the token your registry's token endpoint accepts

In a CI job that offers OIDC ID tokens the way GitHub Actions does (OYZU_ID_TOKEN_URL and OYZU_ID_TOKEN_REQUEST_TOKEN, which the Oyzu runner sets), leave OYZU_CACHE_TOKEN unset. The client signs in with the job's ID tokens and asks for a new one when needed.

  • The credential is first sent as a bearer token. A 401 with a Bearer challenge names the registry's token endpoint. Oyzu uses it only if it is on the registry's own origin (scheme, host and port). Otherwise the request is denied and the credential is never sent elsewhere.
  • The client then asks that endpoint for one token per repository, with OYZU_CACHE_TOKEN as the Basic password (user name oyzu), or with no credential if the variable is unset or empty. Tokens ask for pull, plus push when cache.write is true. A rejected or expired token is fetched again once. A second refusal is a denial.
  • With ID tokens, the Basic password is the job's ID token: GET $OYZU_ID_TOKEN_URL with ?audience=<registry origin> and the request token as a bearer, answered with {"value": "<jwt>"}. It is reused until 30 seconds before it expires. The request token goes only to that URL, and neither token is recorded.
  • A blob response can redirect to another host (for example a separate blobs host with short-lived signed links). Redirects are followed without the Authorization header when they change origin, at most 5 times, and never from HTTPS to HTTP.

Entry layout​

  • Repository <prefix>/v1alpha1/<first two key hex>, tag lookup-<64-hex key>.
  • An OCI image manifest with artifactType application/vnd.oyzu.action-result.v1alpha1.
  • The action-result descriptor as config (application/vnd.oyzu.action-result.config.v1alpha1+json) and one layer (application/vnd.oyzu.tree.v1alpha1.tar+zstd) holding every blob the descriptor references, named sha256/<hex>.
  • Annotations: dev.oyzu.action.key, dev.oyzu.action.output and, on the layer, dev.oyzu.tree.uncompressed-digest.

Build record​

The build record gains manifest.extensions["oyzu.dev/action-cache"].remote: location, read, write, status (active, unavailable with reason, or unusable for a cache.remote the client can't use), counts of hits, pushed, converged, conflicts and rejected, the requests sent by kind, and per target the actions in each list. A result materialized from the remote carries extensions["oyzu.dev/remote-origin"] in the local store. The summary line adds the remote part, for example remote 7 reused · 0 pushed.

CI and development repositories​

A project can name a second repository that only CI writes:

# oyzu.toml (project)
[cache]
ciRemote = "oci://registry.example.com/team/oyzu-cache/ci"   # CI writes, everyone reads
remote = "oci://registry.example.com/team/oyzu-cache/dev"    # optional: developers share here
immutableTags = true                                           # the registry never replaces a tag
write = true                                                   # CI ignores user configuration
BuildReads (after a local miss)Writes (with cache.write)
CI (the execution context detects a CI provider or CI)cache.ciRemote only. cache.remote is recorded as skipped.cache.ciRemote
Anywhere elsecache.ciRemote, then cache.remotecache.remote only, never cache.ciRemote
No cache.ciRemotecache.remotecache.remote

The registry, not Oyzu, makes the CI repository trusted. It must refuse writes to that repository without the CI credential. Detecting CI only narrows what a build accepts.

  • A build that sets CI without the credential is refused (403), keeps building and writes nothing.
  • A CI build never reuses a developer's upload. It doesn't read cache.remote, and a result in its local store that came from a development remote is looked up again in the CI repository.
  • A remote hit is recorded with its scope (ci or development). Nothing is signed, so a hit from the CI repository says where it was read, not who produced it.

The registry credential is OYZU_CACHE_TOKEN or, without it, the CI job's ID tokens. It is never a setting, and it is never written to a record or log. OYZU_CACHE_TOKEN is sent as a bearer token on every request to the configured registry host (over HTTPS or to a loopback host), and dropped when a redirect leads elsewhere.

Immutable tags. cache.immutableTags = true says every configured cache repository refuses to replace a tag. A push then skips the racing-writer read, so a pushed action costs 6 requests instead of 7, and a refused manifest PUT (409 or 412) counts as the conflict. Don't set it for a registry that replaces tags, or the last writer silently wins. Either way, a hit is used only after the digests its manifest names verify.

Requests per build​

Counted from the registry's own log for a project with one node/app target and seven cacheable actions (oyzu build --full):

BuildManifest GETBlob GETUpload POSTBlob PUTManifest PUTTotal

A hit costs 3 requests per action. A miss that pushes costs 7. Signing in adds one token request per repository the build touches. With a storage-backed registry, a push can cost many more storage operations than the 3 objects an entry consists of (about 25 write-class operations per entry on CNCF Distribution's S3 driver), which matters if your object store bills per operation. Harbor's proxy cache revalidates every manifest with the upstream registry, so it saves blob traffic, not manifest requests.

Remote failures​

Remote failures never fail a build:

SituationBehavior
404 under the tagA miss. The action runs (and is pushed when writing).
5xx, 408, 429, timeout, connection failureRetried up to 3 times with exponential backoff and jitter. Then the remote is off for the rest of the build and everything is computed.
401 / 403After sign-in (one token renewal), not retried. The remote is off for the build and no other route is tried. A wrong OYZU_CACHE_TOKEN, no credential where one is required, and a read-only credential with cache.write = true all end here. The build computes and succeeds.
409 / 412 on the manifest PUTThe registry refused to replace the tag: a conflict. Not retried. The entry there is kept and not read back. The remote stays on.
Digest, size or shape mismatch, missing blob, conflicting configThe entry is rejected and its bytes are quarantined in the local store (quarantine/remote-<key>-<part>). The action runs. The remote entry isn't repaired.
Push failureThe build succeeds. The record says why the entry wasn't pushed.
Push interrupted before the manifest PUTUploaded blobs stay unreferenced. Nothing is visible under the tag.

Remote limits​

  • Sign-in uses only OYZU_CACHE_TOKEN (as a bearer token or through the registry token flow) or a CI job's ID tokens. There is no Basic auth to the registry itself, credential helpers, Docker configuration, login command or OAuth2 POST token form.
  • Immutable tags are declared, not detected. Results aren't signed and producers aren't verified.
  • Lookups aren't batched. Transfers are sequential. Entries above 256 MiB aren't pushed.
  • There is no remote retention or pruning. A damaged remote entry is rejected by every reader but never repaired or replaced. An entry pushed by an older Oyzu without keyComponents in its config is rejected like a damaged one.

Failures and recovery​

SituationBehavior
No entryThe target runs and is stored.
Damaged blob or descriptor, mismatched key, unreadable entryRejected and quarantined. The target runs and replaces it. The summary notes the rejection.
Report gate fails on restoreThe entry is rejected and the target runs normally.
Cache location missing, unwritable or unusableThe build runs normally and stores nothing.
cache.local = false / --no-cacheEverything runs.
Cancelled or failed buildCompleted actions that are valid on their own can still be reused. Failed or interrupted actions and failed targets have no stored result.

Writes are atomic (stage, then rename), and a descriptor is published only after every blob it references. After a failed build, an eligible action's outputs, workspace changes and reports are sealed when it completes, so a later writer or target failure can't change them. An action whose required reports are missing or malformed isn't stored.

Upgrading Oyzu invalidates entries, because the builder digest is part of the key. Nothing is migrated, and old entries age out through retention. Python application targets pass the whole-tree digest to the build (OYZU_SOURCE_DIGEST), so they miss on any edit.

Limits​

  • The cache trusts the declared target graph (see Trust model).
  • Targets built by a host-coordinated image worker, and authored tasks around hooks on the native host path, aren't cached.
  • Version finalization after hooks covers only pre_build hooks on captured Node targets.
  • Narrow keys require a confined action or an admitted native read contract. Stages with an unbounded reason retain the whole-target key.
  • Python targets miss on any edit until their source digest is scoped.
  • Execution-only settings such as cache.local and cache.nativeMaxMiB currently change keys.
  • Windows has no confined actions. macOS isn't supported yet.
