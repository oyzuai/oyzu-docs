Action cache

CLI reference

Published from the canonical docs/reference/action-cache.md file. Features marked experimental remain experimental; check support limitations before relying on them.

A repeat oyzu build skips targets whose inputs haven't changed and restores their earlier results. You configure nothing: you never write cache keys or per-language cache paths. This page covers what is reused, what invalidates it, how to see why a stage ran, and how to share results through a registry.

Note: The action cache is experimental. The remote cache is unsigned, so a remote hit tells you which run produced a result, not that the result was verified.

Usage​

oyzu build                       # first build runs and stores; repeats reuse
oyzu build --affected HEAD       # Git-selected targets also reuse unchanged results
oyzu build --full                # quality stages and their reports are reused too
oyzu build --no-cache            # run every action; read and write nothing
oyzu cache status                # where the store is, how large, how many entries
oyzu cache clear                 # remove every cached result (bundles are untouched)
oyzu build --explain             # after the build, why each stage was reused or ran
oyzu cache explain api           # why target api's key (and its stages' keys) last changed

Every oyzu cache command supports the global --json flag before or after the subcommand. They read no project beyond configuration.

Output shortened. A project with four targets, one run each:

$ oyzu build                         # cold
✓ Build succeeded   4 targets · 4 executed · 9.4s
$ oyzu build                         # unchanged repeat
  ↺ api    build                                   reused   was 1.2s
✓ Build succeeded   4 targets · 4 reused · 1.8s
$ echo "// edit" >> api/src/greeting.mjs && oyzu build
✓ Build succeeded   4 targets · 3 reused · 1 executed · 3.1s

Reuse is local to one user on one machine unless you configure a remote cache. Every output says plainly that a restored result was not executed now:

  • Receipts keep reused test evidence apart from fresh tests.
  • When known, reuse.source records whether the local or remote store served the result.

Moving an unchanged checkout on the same platform does not by itself change its action keys. Before hashing, Oyzu replaces known checkout, private-workspace and per-run scratch locations in command arguments, environment values and declared paths with stable relative locations. This includes paths inside native JSON arguments and Windows drive, separator and verbatim-prefix forms. Paths to inputs outside those known roots still affect the key; resolved tool and plugin identities remain part of it. Source bytes, build profiles and platforms must still agree. Root matches require the end of the value or a directory separator. A sibling such as C:\ws)external\input.rs stays distinct from the root C:\ws. This also applies inside command text: punctuation alone does not establish containment, so ambiguous text retains its original identity. Entries written by versions that retained checkout-specific paths can miss once after upgrading; the existing cache need not be cleared.

  • An unavailable cache is different from --no-cache. If the store can't be used, permitted native builds continue with a warning and run everything.

Flaky tests and quarantine​

Automatic flaky-test detection and quarantine are not available yet. A failed test remains a failure under the configured check level; cache reuse does not retry it until it passes. There is no quarantine setting, flaky-test output section or persisted same-input test history.

Same-input detection requires independently keyed test units and fresh native pass/fail reports. A reused result or skipped case is not a new execution, and a different input key cannot establish flakiness. A case-level finding requires an explicit pass and failure for the same native case identity; missing case evidence must not be treated as a pass. See the proposed test-unit contract.

See configuration. Keys and cache paths are never user-authored.

Native builds work from a private copy of each target's source, kept in a host-workspaces folder next to the action store. It follows the platform cache location, not cache.dir. If that folder is on a different drive than your checkout (for example the cache on C: and the repository on E:), Oyzu parks the copy in the repository's Git directory instead (.git/oyzu/host-workspaces, or the linked worktree's Git directory), so parking stays a rename rather than a full copy. The first such build moves a copy parked at the old location. Use build.host-workspaces-dir to choose the folder yourself. It must be outside the source tree; the Git directory counts as outside. The path must not pass through a symbolic link, except root-owned top-level links in a root-owned filesystem root that is not writable by group or others, such as macOS /tmp and /var. Oyzu renames the copy into place when it can, and otherwise copies only the pruned source, keeping file times and permissions so native tools such as Cargo still see unchanged files as fresh. A real source edit still invalidates native compilation. Oyzu never copies compiler, dependency or tool caches. Changing the setting doesn't move existing parked workspaces.

The Git fallback requires an existing repository, recognized by the same metadata checks as project discovery. Outside Git, parking stays in the native cache even across filesystems, unless you set build.host-workspaces-dir. Empty .git markers and directories holding only Oyzu state do not expand the host source boundary or select the fallback. Oyzu never creates a .git directory for host-workspace state. If a configured parking path would require one, the build fails with host workspace storage cannot create a Git directory; select a cache folder outside the source tree.

The store is per user and shared across projects. It holds blobs/sha256/ (file bytes), results/<key>.json (result descriptors), quarantine/ (rejected data) and tmp/. Output trees are stored as a manifest plus one file per blob, not as a compressed archive.

Workspace changes and merge-back from private native or confined views are detected against a content baseline. The tracker compares size, modification time, executable status and link target. On Unix it also compares change time (ctime), device and inode; on Windows it reads ChangeTime and the volume/file ID through attribute-only handles without following links. These native facts detect same-length rewrites even when a tool restores an old modification time.

Each baseline starts with a temporary probe in the workspace, removed before scanning, whose modification time supplies the filesystem clock. An otherwise unchanged regular file is content-compared if either its modification time or native change time is not strictly older than that stamp. This includes equal clock ticks and future timestamps. Unchanged older files keep the stat-only fast path. If native change information or a timestamp is unavailable, regular files are conservatively content-compared: the modification-time rule alone cannot detect a rewrite that restores an old timestamp. Views keep baseline digests only for regular files with racy or unavailable clocks. An equal-size, equal-mtime write is merged back before delta capture; unchanged older files require no content read. Identical content produces no delta. Symbolic links, special files and executable changes retain their existing handling; a delta containing links or special files is not restorable.

Serial confined actions may share files with their private target workspace through hard links. Creating and removing those views changes native metadata without changing content, so those files still require hashing. Before staging a candidate, the tracker compares its digest, executable status and link kind with the content baseline. An identical entry produces no delta or staging copy. An executable-only change still stores its bytes so it can be restored. Changed files use the digest and size returned by verified store admission, which may read the file again after the preliminary hash. This avoids unnecessary staging; it does not remove link-induced hashing. Preserved-mtime writes and racy or unavailable clocks retain their content-comparison rules.

Workspace restores verify every cached file into private staging before accepting a hit. Deferred restores retain those staged files without keeping a file handle open per file, so large results such as Python virtual environments do not require raising the process file-descriptor limit. Staged files are removed after restore or when the pending restore is discarded. A corrupt blob rejects reuse before the workspace is changed.

Retention​

At the end of a build, if the store is over 10 GiB, Oyzu removes the least recently used results until it fits, then removes blobs no result references. A hit refreshes an entry. Eviction touches only the cache. Bundles in dist hold their own copies. The budget is fixed. Cache history metadata, including definition-keyed native observations, has a separate 64 MiB ceiling (bounded further by a smaller maintenance budget). Every retention pass prunes its least recently used records, even when result bytes are below budget. Pruned observations return native stages to whole-target keys.

  • Builds hold a shared lock on store.lock while they read or write the cache.
  • An unused store isn't created. Runs with the cache disabled, or with nothing cacheable, leave it alone.
  • oyzu cache clear needs exclusive access. While a build uses the cache it fails with a retry message and leaves active staging alone. Retry when the build finishes.
  • If end-of-build eviction hits contention it warns, and the store may briefly exceed its budget. A later build retries.
  • If a store is busy with maintenance, builds proceed without it and cache commands return an error.
  • Don't delete store.lock to clear contention. The lock protects cooperating Oyzu processes, not external deletion or filesystems without working locks.

Copying and verifying cached bytes​

Oyzu hashes file bytes while copying them into the cache and again when restoring them. It checks every file of a restored action before accepting the hit, and it replaces each destination file only after its copy succeeded, so a missing or corrupt blob leaves the previous file in place. Corrupt cache data is rejected, quarantined and recomputed (see Failures and recovery). A restore that touches several files isn't rolled back if a later file operation fails. Artifact and report gates still run after a restore.

What is reused​

The unit of reuse depends on what Oyzu knows about the target:

  • Per action for targets whose actions all carry a stage contract (including captured node/package and node/app). Each action (for example api:version, api:build, api:package) has its own key and result. See Per-action reuse. The target's group record lists its action results, so an unchanged repeat restores the whole target in one step.
  • Per target for every other builder: one key per target, restoring all its actions together or none.

A reused target or action keeps:

  • its artifacts, byte for byte (each is checked against its recorded digest);
  • its original JUnit, coverage and other reports and their producer evidence;
  • the original run ID, key and completion time, in a reuse record.

Oyzu stores a target only after all its actions succeeded and its reports were collected. Failed, blocked and cancelled targets aren't stored.

Built-in builders declare their own actions, so their stages are cacheable with no configuration. Declared source inputs are included in the target's key on both native and captured paths.

Targets with a builder-selected source projection are cacheable too. A projection narrows the target's own folder to selected target-relative files; it does not declare additional source outside that folder. Whole-target keys include the projection definition and the captured identities of its selected entries (paths, types, content digests and executable bits).

A stage with an admitted read set keys only its selected reads, including directory listings used for discovery. The whole candidate projection is not a second input to that stage. Native reuse first finds observations for the same command, engine and prediction, then validates a complete observation against the current admitted source and computes the result key from those reads. Missing, incomplete or out-of-prediction observations cannot narrow a key: the stage keeps the whole-target projection and runs normally. Confined captured actions use the files available in their view. Key construction reuses captured entry digests; it does not walk or hash source files again.

Explicit builder reads and writes are scoped from the target folder on both captured and native paths. Parent traversal (two dots) is refused for paths, globs and listings. Declared workspace inputs remain a separate source-admission mechanism.

Conventional native Go compilation writes a stable intermediate executable. A final export copies it to the inferred-version filename. An unread README content edit can reuse build, vet and format-check; a commit with unchanged source reuses those stages. If version metadata changes without source changes, only the versioned export runs again. A plain empty commit leaves the source-content snapshot version unchanged, so export can reuse too. Artifact metadata and receipts retain the current inferred version. Go does not inject a version variable into the program. Authored version-bearing commands and environment values remain inputs, and other builders need their own final-stage version boundary.

Not cached by default​

These targets simply run, and the output says why:

  • Targets with authored tasks or task overrides that don't ask to be cached, and targets whose hooks ([tasks."api:pre_build"]) declare no outputs. An authored task with cache = true and outputs is cached (see Authored tasks). A hook that declares outputs is followed on targets reused action by action (see Hooks).
  • Targets with hooks on a path that reuses a target only whole (native host targets with hooks, and captured targets without stage contracts). Restoring them would skip hooks that must run on every build.
  • Targets that use secret environment values ({ secret = "…" }).

Native npm applications​

For native npm applications with dependencies, the target includes the install action (npm ci). A hit restores the successful result without reinstalling. A miss installs into the private target workspace before pre-build hooks. Results stored by an older Oyzu simply miss. Nothing needs clearing.

This native path currently reuses whole targets, including when the plugin declares bounded install reads. An unread README edit still invalidates the target result. A source declaration alone does not enable per-action admission.

Isolated npm downloads​

Before looking up actions, the captured npm path validates native metadata and downloads locked dependency bytes with lifecycle scripts turned off. That script-free step can be reused from the local store.

  • The key covers the full source and target tree, the worker image and platform, the admitted tools, the command and environment, configuration and the download routes. Any change to the source, lock, tools, routes or configuration needs a new download.
  • Tools are checked before lookup, and restored files are verified before use.
  • The later offline install and lifecycle scripts aren't cached.
  • The journal records a reused step as not executed now, with its original time and key.
  • These entries share the local store, lock and 10 GiB budget. They are never uploaded to a remote cache.
  • A missing or damaged entry falls back to a fresh download. Partly restored trees are discarded.
  • --no-cache, cache.local = false and --verify-contract turn this reuse off. Builds with managed configuration, secret environment values or authenticated routes don't use it. Offline builds can reuse earlier captures.

Prepared resources and Go tests​

  • Native builder actions can bind exact prepared-resource files. The plan records those files and their content digest, and execution mounts the same selection even with --no-cache.
  • Native Go tests run in fresh copies of the captured workspace with empty report folders. Their writes are discarded, and validated reports are captured into the build bundle. Reused reports keep their original producer evidence. Workspace consumers of generated files, and --verify-contract, aren't supported on this path. See Go.

Prerequisites and platforms​

  • Captured path: oyzu build and oyzu build --affected on targets that use the Docker executor and its toolchain images (for example node/package).
  • Native host path: builds that run on the host with Oyzu-provisioned tools (node/app dist applications, Go, Rust, Python wheels) reuse unchanged targets the same way. See Native host builds. Targets built by a host-coordinated image worker aren't cached yet and say so. oyzu run executions are never cached.
  • No account is needed. Ephemeral CI runners start with an empty local store. With a remote cache they reuse results other checkouts pushed.
  • Tested mainly on Linux. On a Windows host, shared edits conservatively re-run unrelated work. macOS isn't supported yet.

On Windows, action tracking records native symbolic links and the Linux links Docker creates in a captured workspace without following them, so pnpm links stay usable by later native actions. A change that contains links can't be restored from the cache. Other Windows reparse formats fail with an error.

Output​

In the live Build section, restored actions show ↺ (the word reused without color) in place of executed. The summary counts them apart from executed work (2 targets · 3 reused · 1 executed). With -v and in JSON you also get each target's reuse origin and the Cache line. The final receipt marks test and coverage lines from restored reports as reused from an earlier run, not run now.

In the build bundle a reused action keeps status: "succeeded", so every gate applies unchanged, and gains:

"actionKey": "sha256:…",
"reuse": { "actionKey": "sha256:…", "originalRunId": "…",
           "originalCompletedAt": "2026-10-07T08:43:02Z", "originalDurationMs": 812 }
  • manifest.extensions["oyzu.dev/action-cache"] records the mode, whether the cache was active or disabled (and why) and each target's outcome: reused, executed (with stored, and rejected if a damaged entry was replaced) or not-cached with the reason.
  • Journal events in logs/events.jsonl use the finish status reused. Logs for reused actions aren't recreated.

A hit never skips a gate. On restore, every report is parsed again from its stored bytes and judged by the current contract (for example the coverage minimum). A report that fails there rejects the entry, and the target runs normally. Preflight, policy and required-check enforcement are unchanged.

Explaining reuse​

Two read-only views answer "why did this stage run or get reused?". Both name the first key component that differs from the last build of the same target or stage, so a miss points at what changed.

Each key is made of named components, compared in this order:

ComponentWhat it coversParts named on a change
builderThe builder ID and digest (an Oyzu upgrade changes it)
profileThe applied build profile, development or optimizedprofile development vs optimized
platform, variantThe target platform and variant
toolchainThe toolchain: image content digest or resolved tool lock, host platform
dependenciesThe prepared dependencies (for Node, node_modules)
projectionThe source projection definition and selected content digest for whole-target fallback keys

definitionThe frozen action definitions, field by field and environment variable by variable: argv, env.<NAME>, cwd, limits, report contracts, configuration digest, input mountsapi:build env.MODE (group key) or env.MODE (action key)

When several components differ, the first is the reason and the rest are listed after it. The key alone decides reuse. Components only explain it. source comes before definition because an action's environment can carry values derived from source, such as the development version.

Every lookup also records the subject's latest key in history/ under the store: the run that first and last used it, and the distinct key before it. A subject is a target or, for targets reused action by action, each action. History is written even when nothing is stored (a failed build, an always-run target), is a few kilobytes per subject and is removed by oyzu cache clear.

Key-history persistence is best-effort. A lookup continues if recording its history fails, and its action or target explanation includes historyWarning with the cause. Fix the backing-store permissions or filesystem issue, then build again to record history.

oyzu build --explain​

After the receipt, it shows at most eight action decisions, with a count of the rest. The manifest has complete detail. A blocked or failed action keeps its failure cause. An expanded entry looks like this:

  Why each stage ran or was reused
  api:build — Executed
    Recorded selection: api (requested)
    Reuse: source files in scope changed
    Source comparison: run previous-observation
    changed: shared/greeting.mjs (reads-source)
      Native provenance: applications/api/build.mjs:2 (path, exact)

Other reasons you may see:

  • profile development vs optimized (the recorded build used a different applied profile)
  • source projection changed (its selection definition or selected content changed)
  • no earlier build of it is recorded in this cache (first build, or after cache clear)
  • inputs unchanged since run …, but no result is stored (not stored, evicted or cleared)
  • the stored result was rejected: … (damaged entry)
  • a hook runs on every build…
  • a note that the result came from a remote

A stage of a target that is reused or run whole shares the target's reason. A target that isn't cacheable shows its not-cached reason.

--explain conflicts with --plan and --remote. It changes only the human output. The reasons are always in the manifest, under manifest.extensions["oyzu.dev/action-cache"].targets.<target> as explain ({reason, changed?, previousRunId?, sourceChanges?, historyWarning?}) and, per action, actionExplain.<action>, so --json carries them without the flag. A failed local lookup is recorded as lookup: unavailable with the cause, which is different from a stored result that failed validation.

Source comparison​

Oyzu keeps a source inventory per captured context in the cache history. sourceChanges compares the previous build's file identities with the current ones under the action's read scope (or the whole target scope), including added and removed files.

  • Exact reads are labeled reads-source, approximate bounds bounded-read, and unmodeled relationships scope-input.
  • sourceChanges.status is available, unavailable or scope-changed. Oyzu never guesses file names when the inventory is missing or the boundary changed.
  • These inventories follow the history rules: --no-cache writes none, and cache clear removes them.
  • Windows has no confined actions, but captured whole-scope comparison works. Native builds without captured context explain at target level only.

oyzu cache explain <target>​

Reads the key history for a target ID (its group key and every recorded action) or one action ID such as api:build. For each it shows the latest key, the runs that first and last used it, whether a result is stored and the first component that differs from the previous key. It reads no project and runs nothing, so it works between builds and on another checkout that shares the store. An unknown name exits non-zero with no key history for <name> in this cache.

A build cached only as a whole target records that target ID. If its builder supplies no bounded action contract, use the target ID rather than an action ID; whole-target caching does not create per-action history.

Limits:

  • History keeps two distinct keys per subject, so cache explain compares the latest keys, not an arbitrary older build. To look at a finished build, use history.
  • A stage's previous run can be older than its target's, because a build that restores a target whole doesn't look up its actions.
  • Builds that share one store at the same time can interleave history writes. Each write is atomic and the later one wins.

Inputs and what invalidates a target​

Every builder operation declares source reads, an explicit unbounded reason, or explicit upstream-only output consumption. A bounded captured stage keys on its declared read selection. Native source selection also conservatively includes unowned workspace entries. Configuration, tool and prepared-input identities remain separate key components. A directory read includes its listing: adding a source or test file changes the key. An unbounded stage retains the whole-target source key; its reason explains why narrowing is unavailable.

Analyzed native builders include Rust and Zig. Zig's format-check declares fixed .zig/.zon file reads and recursive directory listings. Its build and test stages remain unbounded because build.zig and runtime tests can read arbitrary files without a complete tool-reported read set. See Zig stage reads. Zig opts its fixed-read formatter into a private workspace with no retained files and order-only build/test edges, allowing independent formatter reuse. Build and test retain whole-target source keys.

The Helm plugin also declares per-stage chart read bounds, including conservative chart and formatter scan trees and specific reasons for image bindings and helm-unittest suites. Its captured execution path retains whole-target caching; declaring reads alone does not admit individual stages to the action cache.

An admitted upstream_only export reads no source files. Its key uses its own definition, tool/configuration identity and declared upstream output digests, without the target source scope or implicit source inputs. Native admission requires complete observations or fixed command semantics; an empty read list alone never authorizes this. Native Rust binary exports use core-admitted typed copies from the producer's indexed binaries, with stable export paths in each fresh private workspace. Equal producer bytes therefore give equal export output identities despite per-run temporary allocations. Later unconfined checks retain their conservative dependency edges, including the export.

Older published plugins may omit this declaration. Oyzu accepts their results and treats each undeclared operation as unbounded, with the reason plugin <reference> <version> declared no reads. The build reports it once the plugin answers, with one PLUGIN_READS_UNDECLARED warning per plugin per build that asks you to update the plugin. oyzu build --plan never invokes a builder. Its Why column (JSON sourceReason) describes stage contracts recorded in that target's last retained build plan, across current, legacy and historical bundles. Reasons are language-neutral and marked as facts from the last build; they do not establish current source completeness or cache admission. Stages without a recorded contract say reported when the builder answers. A later build of another target does not replace this target's recorded reasons. These operations retain whole-target keys; the SDK and conformance suite require declarations from new and updated plugins.

Read-only preview distinguishes a stage without a retained declaration from a plugin that answered without one in the last build. The former says reported when the builder answers; the latter names the plugin and missing stage contract as a fact from the last build. Node lifecycle fallbacks name arbitrary project/package reads, while script-free single-root npm installs can declare their manifest, lock and manager controls. Rust's final declarations come from Cargo read facts, with specific reasons when native inputs cannot be bounded. These explanations do not relax confinement or native-observation requirements.

A target's key is a SHA-256 over these inputs and nothing else:

When a build pins missing tools or quality sets, planning uses the validated, newly published lock capture. Its tool inputs therefore match later builds that reuse the unchanged lock. Incomplete tool declarations continue to bind the captured lock bytes; a real lock-file edit changes that conservative identity.

Host paths, run IDs, timestamps, credentials and the number of parallel jobs never enter a key. A serial build, a --jobs N build and a host with a different core count share hits, and so do different checkouts, worktrees and branches.

Source ownership comes from the full static build inventory, even when a named build resolves only the builders it needs. Unselected builds keep ownership of their folders without loading their plugins.

Changing one target's inputs re-runs exactly that target. One thing to know: execution-only settings such as --full are part of the configuration digest, so changing them re-keys every action.

Prepared dependency identity excludes whole-source provenance, version decision evidence and the frozen plugin planner request/answer. The frozen action definition still keys version-bearing arguments and OYZU_VERSION; source reads have their own key component. Dependency locks, manager/tool identities and prepared content remain in the dependency identity. A changed lock or prepared payload therefore remains a prepared-dependency cause in oyzu cache explain.

This exclusion does not remove a version written into a prepared file: those bytes remain prepared content. Helm retains the authored Chart.yaml version during preparation and projects the resolved version into its private stage workspace. Its bounded captured stages use their admitted read contracts; a root README outside those reads can change without invalidating the shipping actions. A README inside the chart ships unless .helmignore excludes it, so editing it normally invalidates the build.

Prepared capture can record source provenance using the copy roots supplied by preparation. A nonempty regular file is copied source only when its prepared root-relative path maps to the same source root-relative path, and its captured bytes, size and executable mode match. Empty files, dependency locks, files outside the declared roots and rewritten files (including stamped chart metadata) remain generated. Equal names or bytes elsewhere never establish a copy coordinate. Helm keeps dependency-build charts/ directories acquired, including committed subcharts reproduced byte-for-byte. If preparation has no workspace-relative source inventory, it declares no copied files rather than using target-relative coordinates that could hide a nested chart's templates.

Provenance is computed from inventories already produced during capture and is stored with the dependency record. Reuse reads that record; it adds no prepared tree scan or source-byte hashing. Planning decodes it once per prepared target. If an action hides no copied files, it retains its ordinary dependency input and mount: no extra file list, view, rehash or copy is introduced.

When a confined captured action must hide a copy outside its source reads, dependency identity covers the generated/acquired entries and all (prepared path, source path) names. Visible copied bytes and modes remain in the bound physical view digest. Each action carries hidden-copy paths and a digest reference to a shared table of read-copy diagnostics, not an inventory per action; an explicit prepared-file selection still applies. Opening a filtered view verifies its selected content, copies it and verifies the resulting tree, even with --no-cache. This cost applies only to actions that actually hide copies (or already request an explicit prepared-file view). Upstream-only actions that consume prepared resources retain the whole prepared input and its whole-content identity. An empty source-read set does not mean those actions can run with copied files removed from their dependency payload.

oyzu cache explain lists copied source paths as added, removed or changed, showing up to three and an and N more count. Whole prepared inputs, including upstream-only staging, also separate verified copies from generated dependencies in the explanation: for example, copied source chart/templates/pod.yaml changed (whole prepared input). This diagnostic split uses the captured inventory once per target; it does not narrow the input, materialize a view, or change its key. Locks, acquired files and rewritten bytes still report prepared dependencies. Unbounded actions, native host actions and prepared trees containing links retain whole-tree behavior. Native observed reads do not yet map prepared copies back to source coordinates.

Test-unit evidence​

A plugin can declare native test units through the optional test-unit plan. Captured Python package tests use one pytest file per unit and can select cases inside a changed file; see Python cases inside a bounded unit. The Rust-specific Cargo executable producer is deferred to issue #1201. The built-in Rust worker does not emit per-executable unit plans; its existing native test, coverage and doctest pipeline remains unchanged.

Core owns unit keys, lookup and passing-result storage. A failed unit is never stored. The native adapter prepares its inventory, runs the selected units and combines fresh and reused evidence into the operation's existing required reports. Cancelled preparation preserves the executor's cancellation status and stops before unit execution or report finalization. An unbounded AlwaysRun stage does not gain reusable result storage merely by exposing a unit plan.

The combined report retains each unit's contribution. Summary totals put cases from executed units under Tests run now and reused cases under Reused test evidence, marked not run now. JSON build reports retain each contribution in reports[].summary.units. Invocation summaries (oyzu history <id> --json) use tests.fresh and tests.reused for the same counts. Even when all units reuse results, the action still executes preparation and finalization. It counts in actions.succeededNow; only whole-action reuse counts in actions.reused.

Each unit's key includes the stage's non-source inputs, the native artifact's digest, its runtime-read digest and the declared companion executable digests. Runtime reads narrow the key only when the captured-path view enforces them. Declared inputs widen reads without enforcing a boundary. Runtime listing selectors conservatively include the selected directory's contents in unit keys and views. Without an enforced boundary, a unit key retains the whole target's source digest and the ordinary stage's admitted upstream outputs. Untracked host files retain the native cache limitations described below. Per-run inventory paths and coverage environment are not bounded key inputs.

Targets with hooks or authored tasks retain their existing stage or whole-target cache behavior. Their outputs are never narrowed to unit identities. If per-action cache facts are unavailable, the ordinary test stage runs instead. The native inventory determines what runs: undeclared units execute without reuse, known units retain their own entries, and missing predicted units do not fail an otherwise valid native inventory.

The existing test action row shows N ran, M reused, including in redirected and no-color output. Its JSON action record lists units, each with name, key and outcome (ran, reused or failed). An operation without a unit plan retains its existing whole-stage behavior.

Trust model and its limit​

The cache trusts the declared target graph, like --affected. An action that reads another target's directory without a declared edge is invisible to the key. For example, if api and web copy ../shared but declare no relationship to it, editing shared/ reuses their old results, while oyzu build --no-cache rebuilds them. Native cross-root dependency discovery isn't implemented. Declare relationships in build.yaml (depends_on: [shared]), or use --no-cache, for builds that read across target directories.

External builder targets​

A target built by an external builder plugin (a plugins.development or plugins.packages binding) is reused like a built-in target. Oyzu writes the plugin's verified identity on the target record as extensions["oyzu.dev/builder-plugin"] and includes it in the target and action keys next to the Oyzu executable digest:

  • A changed plugin executable, package release or version, runtime or reference re-runs the target, and explain reports builder identity changed. Reverting reuses the earlier result.
  • How the plugin was selected (resolved now or locked) doesn't change a key. A plugin-built target never shares a key with the built-in builder it replaces.

A native plugin's private executable copy can have a different path on each run. That execution location does not change the cache key: the key retains the full verified plugin identity instead. Changes to command arguments and plugin bytes still invalidate the result; the private copy and fresh output staging remain. When several builder references share one executable, each target keeps its own verified binding identity; adding another binding does not change that target's key.

For a development binding, the digest covers only the bound file. If that file isn't a native executable (a wrapper script or .cmd file, for example), what it runs is outside the key, so its targets are not-cached with the reason "is built by a development plugin binding that is not a native executable". Bind the plugin executable itself to get reuse. A native wrapper executable is keyed on its own digest alone, so rebuild or rebind it after changing what it starts.

A target built by an installed plugin package (a plugins.packages binding, or a package oyzu.lock selects) shares its results through cache.remote and cache.ciRemote like a built-in target: the key binds the package release and executable digest, so only a machine running the same package release reuses them. A development binding's results stay in the local store, because its executable exists only on that machine. A slice hands plugin-built results off through its --handoff repository like any other. The usual exclusions still apply: --no-cache, cache.local = false, --verify-contract, secret environment values and hooks without declared outputs keep a target out of the cache.

Per-action reuse​

Planning attaches a stage contract to each action of an analyzed target: the reads, writes, environment names and tools the static analysis found for the stage, the actions it follows, and whether its outputs are bounded. A target whose actions all have a contract is reused action by action. Captured node/package and node/app operations use these contracts when the final command matches the analyzed script or builder-owned command. Ordinary SDK-style dotnet/sdk projects also declare stage reads on the captured path. See .NET stage reads for the SDK audit, resolved-package checks and conservative MSBuild fallbacks. Captured .NET targets cannot see ancestor configuration files above their target folder; future native admission must treat those files as unbounded until covered by read evidence. Fixed core-owned stages can supply a contract alongside analyzed builder stages. Docker also declares per-stage reads for its captured operations. Projection-aware caching and captured version rebinding require a supporting core release before the updated Docker plugin. Source projections retain conservative version scope, and copied source in prepared dependencies can still prevent reuse after an unread edit. Core prepared-input staging​

Core's prepare-dependencies action can carry a source-free stage contract when its provider declares every destination written by its fixed staging command. The Cargo overlay copies manifests and lock data into those declared paths; Helm declares .oyzu-build, including its prepared chart copy and the parent directory it creates. These copies read no workspace source and have bounded outputs; the prepared-input selection remains keyed, so changing a staged manifest or lock invalidates staging. A source-only edit can reuse staging independently of compilation when the prepared bytes are unchanged.

With a Rust package declaring captured-cargo-projection, dependency staging copies declared manifests and the original lock from its exact prepared-file view. Frozen projected controls are applied in a separate project-version action before every Cargo consumer. A source edit changing only the inferred version can therefore reuse staging; manifest and lock changes still invalidate it. Staging excludes the engine-injected OYZU_VERSION default, while explicit user environment values retain their normal precedence and remain keyed. Unmarked Rust packages keep the projected overlay, so edits changing the projected version still rerun their staging. Local verification of a source package does not establish public package adoption.

Other provider setup commands keep their existing behavior unless they declare an equivalent bounded, source-free staging contract. This does not turn staging into a network fetch or vendor operation.

Version finalization after hooks​

On captured Node targets, Oyzu moves the version action after the followed pre_build hooks, so nothing that writes the version runs before them:

  1. Planning records every action in plan.json with the pre-hook source version (the version scope without the hook's script). The target record carries extensions["oyzu.dev/version-finalization"]. The actions before the hook run with the pre-hook version.
  2. When the hooks succeed, the files under their declared outputs are digested from the workspace (so --no-cache gives the same result) and folded into the version. Checks that run at once​

The check stages of one target (test, lint, format-check, scheduled by --full or CI) don't produce anything another check consumes, so the plan marks the edge between two consecutive checks as order-only. A hook between them, or a declared depends_on, keeps the edge a real dependency.

When build.jobs is above 1, a check starts as soon as what it really needs (for example build) has finished, beside the checks ordered before it, if all of these hold:

  • the check runs confined (and --verify-contract isn't set);
  • every action of its target already running is a confined check;
  • no two of them declare writes that could meet (a glob counts as its literal folder).

Otherwise it waits its turn. Serial and parallel runs give the same keys and outputs:

Development versions and test files​

Version narrowing follows the execution admission: all selected actions must have contracts, and every shipping action must actually run confined. Non-check steps that can feed shipping reads join the version read closure. Source-free shipping exports also include their transitive producers. Every omitted check needs a complete write bound proving its effects cannot feed shipping. Unconfined checks are checked against their observed workspace changes when the target has a narrowed version scope; a write outside the declared bound fails that build, including when cache storage is disabled. Whole-target version scopes retain ordinary check behavior. An unbounded generator therefore retains the whole-target version even if build and package are bounded. Prepared charts retain their native version; runtime staging projects the final version. This change does not supply declared-read prepared-content or hidden-copy dependency views. Those are separate work in #1253; source confinement alone cannot hide copies in a dependency mount.

A development snapshot version (1.2.3-dev.g<digest>) is written into package.json by the version action, so it feeds every later action. Oyzu derives it from the target's source scope, minus files that only a quality stage (test, lint, format-check) is known to read exactly.

  • A test-only edit changes neither the version nor the artifact names. A new test file, which only a glob finds, does.
  • An unknown fact of a shipping stage (build, package) counts as reading its bound, or every file if it has none, so a test-only file that a computed import of build may reach stays in the version.
  • If several targets share the folder holding a file, the file is left out only if every one of them reads it only from a quality stage.
  • The script of a followed pre_build hook leaves its own target's scope, and what the hook wrote is folded in after it runs (version finalization).
  • For a captured target whose version-carrying commands (build, package, export, or artifact producers) are bounded, cacheable and confinable, the suffix uses the files those commands read, plus configuration, lock files and declared inputs. Unbounded quality stages retain their own whole-target keys without widening this suffix. This needs Unix view support and per-action eligibility, with the same confinement predicate used by execution. Targets with hooks, authored replacements, source projections, materialized inputs or cross-target prerequisites keep the wider scope. See version inference.
  • Tagged and history-derived versions don't change. The version reaches every action as OYZU_VERSION. The core rebinds accepted captured commands, native payloads and artifact paths with the decisions before computing keys, so an action that embeds the version still keys on the version it executes.
  • Textual rebinding requires the old core version's recorded per-build hash component. An unmarked plain version such as 1.0.0 keeps the whole-target version and plan, so equal dependency versions and path fragments remain untouched. oyzu cache explain and build --explain include this fallback reason. This diagnostic does not change the action key.

When a confined action reads something undeclared​

If a confined action fails and its output names a file that exists in the target but not in the view, the build reports the stage, the path, the missing fact and the smallest fix, in human, NO_COLOR and --json output (diagnostic confined-read-outside-contract, with details in manifest.extensions["oyzu.dev/contract-violations"]):

ERROR  api:build read extra.txt, which its stage contract does not declare, so the confined view hid it.
         Missing fact: reads-path extra.txt
         Fix: declare it as an input of api in build.yaml:  inputs: ["api/extra.txt"]
         (Or make the reference static so the analysis sees it.)

Declare the path as an input. The declaration is relative to build.yaml, while the read path is shown as the target's own files write it. --json carries the same declaration as fix.declare.inputs. Oyzu finds the file by scanning the action's output for paths, so a tool that fails without printing the path is reported only as a failed action. The builder's node --test stage also runs the spec reporter on stderr, so a test file that reads an undeclared file is explained like any other stage. The behavior is the same when targets run in parallel.

Declared inputs​

A target's inputs in build.yaml name extra source paths it reads (files or folders, relative to build.yaml; see target workspaces). On captured and bounded native paths each one:

  • joins the target's source scope, so the whole-target key and the development version cover it;
  • joins the reads of every stage contract of the target, so a confined action sees it and its narrow key covers it. A target-level input re-keys test too when the file changes, even if only build reads it;
  • only adds. It never removes an inferred read, and it never makes an action confinable.

An input that leaves the workspace (the folder holding build.yaml) or names no captured file is a CONFIG_INVALID_VALUE error before anything runs, so a typo can't silently declare nothing. Globs aren't accepted. A folder covers everything beneath it. --affected doesn't yet treat a change under another target's declared input as affecting the declaring target.

Go source-read coverage​

The Go builder predicts conventional native build and vet reads from preparation's Go package file lists and writes observed-read reports after successful execution. format-check uses fixed gofmt rules, content globs and directory listings. Native runtime tests and authored build invocations stay unbounded. Incomplete package facts, overlays, cgo headers and unsupported embed discovery retain explicit fallbacks. Native Java source reads​

The Java builder declares the default Maven and Gradle format-check file inventory: each selected Java file and each scanned directory's listing. google-java-format's fixed explicit-file rule establishes this boundary. Existing documentation-file content edits do not change those reads; Java source edits and new source files do. Configuration, declared inputs, command definitions and producer results also contribute to the complete key.

Gradle configuration scripts and Ant build files are programs whose complete reads are not reported. Runtime tests and Checkstyle retain specific unbounded reasons. Captured Gradle and Ant exports consume their producer's archives; Maven packaging reads its explicit POM and archive copy inputs and depends on its build producer.

Native Maven and Gradle formatting uses a private stage with no retained outputs and order-only lifecycle edges. Private execution alone does not admit narrow keys. Inferred versions or whole-target projection identity can still cause conservative misses after an unread edit. Native host read admission​

A builder's source contract can declare native_reads: {kind: observed} or native_reads: {kind: fixed, rule: "…"}. Omission leaves the native stage on its whole-target key. Fixed admission names the tool rule that establishes the complete boundary; a prediction alone is insufficient.

For observed stages, core allocates an action-specific report path inside the invocation's scratch directory, beside its report directories, in OYZU_OBSERVED_READS. The exact file is cleared before every process attempt, including retries. The action writes a JSON report with complete, paths, listings and reasons, relative to its working directory. Core retains up to four recent complete observations within the prediction in local action-cache metadata, keyed by the structural action definition and core engine identity. Environment names belong to that history subject; their current values remain bound to each result key. This lets branches share observation history when a source-derived value such as OYZU_VERSION changes, without reusing a result built with a different value. Known per-invocation argv and environment paths are normalized before deriving those identities. A subsequent run can use a narrow native key only when that structural definition has an admitted observation. Planning declares observed-read intent before compiler records exist; missing or malformed completion records never authorize reuse. When an execution completes a valid observation and passes the ordinary result-storage checks, core also stores its result under the narrow key computed from the pre-execution snapshot and that report. The next unchanged run can hit that key immediately, including after the first cold compilation.

A native key covers the reported files and directory listings, required configuration and declared inputs, shared source inputs, and the declared environment and resolved tool identities. An edit outside those inputs keeps the observation and narrow key. A changed read or listing produces a narrow miss, then successful execution records its new observation and result; the next unchanged run can hit again. Each execution is stored only under narrow keys computed from its own completed report. A lookup key based on an older report is not populated when the execution reads a different set, even if another build changes the shared observation history concurrently. Whole-source results retain their complete source boundary.

History tries observations in most recently used order, checking each against the current prediction, files, listings, environment and tools through the same narrow lookup gates. The first valid result wins. Switching between branches with different read sets can therefore reuse either branch's result after each has built once. Each lookup hashes at most four observed sets; a hit or valid completion moves its observation to the front, deduplicated by observation digest. Adding a fifth evicts the least recently used observation. Concurrent updates merge atomically, preserving different observations within this bound.

oyzu cache explain <action> summarizes each attempted candidate's miss or rejection and names the candidate that hit. JSON also includes nativeCandidates and nativeLookupMicros (elapsed candidate lookup time, including result admission and restore preparation). Candidate probes do not advance key history. Only the selected hit key, or the ordinary request key when every candidate misses, is observed. The comparison baseline comes from an earlier invocation, never another candidate of this lookup. The same choice owns the invocation's execution and publication state.

A cache hit preserves admission without requiring a new report. A missing, invalid, empty or incomplete report, or a report with reasons, cannot add an observation or authorize narrow publication; other complete observations remain available. The prediction remains the admission boundary for every report, and required report, artifact and policy checks still apply. Core rebases cwd-relative reports by the action cwd and target before checking the prediction, including configuration files and declared inputs. On a narrowed run, an observed read outside prediction refuses result storage with confined-read-outside-contract. A whole-target run retains its covered result without adding an observation. These reports grant no isolation or authority.

A listing selector keys the names and kinds of entries directly in a directory. Adding, removing or renaming an entry changes the key; changing its contents alone does not. Nested entries are excluded. Captured views expose empty file placeholders and empty directories for listing-only entries, so undeclared file contents remain hidden. A path on the directory or an ancestor also predicts its listing. A glob must provably match every direct child, such as dir/*, dir/**, or an ancestor's **; merely matching the directory name (for example * matching src) is insufficient. Ordinary file reads still require a covering path or glob.

Native Rust source reads​

Rust predicts each stage's reads from Cargo workspace manifests and target source folders, Cargo and Rust configuration, build scripts, and literal include_str!, include_bytes!, include! and #[path] references. Manifest-relative concat!(env!("CARGO_MANIFEST_DIR"), ...) references with literal suffixes are resolved too. Source and discovery directories remain conservative directory reads.

Cargo metadata paths are resolved against the preparation workspace. Compiler and build-script records instead use Cargo's actual execution workspace, recorded beside each build or Clippy target directory before execution. These projections can differ: preparation uses a source-only workspace while actions use retained private source trees. Manifests, source files, build-script watches and dep-info map to target-relative read selectors; projection locations do not become part of those paths. Records without an execution-workspace record use the metadata workspace conservatively; an unmappable source makes reads incomplete. Unbounded source diagnostics show a bounded sample and the omitted count within the plugin protocol's message limit. Shortening a diagnostic never admits an incomplete observation. On Windows, dep-info drive, UNC and verbatim (\\?\) paths retain their prefixes when mapped to source selectors. Unparseable dep-info paths or unreadable records make the observation incomplete with a reason; they cannot silently authorize a narrow key.

Rust native compiling stages declare observed admission. The Rust plugin writes the neutral read report from complete Cargo dep-info and build-script records, plus Cargo manifests and configuration controls that dep-info does not list. Until a previous run of the same action definition has an admitted report, they keep the whole-target key. After execution, a read outside the prediction prevents result storage and reports confined-read-outside-contract, naming the path and the inputs declaration that adds it. Human, no-color and JSON diagnostics carry the same fix. A missing or incomplete observation never authorizes storage under a narrow key.

format-check uses rustfmt's fixed module-tree and configuration rules and does not need a runtime observation. Native Rust tests and coverage remain unbounded: tests may read files at run time. They retain the current native stage's conservative execution and cache admission; the Rust per-executable producer remains deferred to issue #1201.

Cargo dep-info never records a proc macro's reads. Rust uses an allowlist of reviewed implementations identified by package name, version and checksum in Cargo.lock. A name match or registry provenance alone grants no allowance. File-free implementations qualify only at their reviewed identity. Changing the version or checksum requires reassessment. Output-affecting environment must also be covered by the key; rustversion binds RUSTC and RUSTC_WRAPPER in addition to the selected compiler identity.

The macro set comes from Cargo's target-filtered resolved graph, following only dependencies reachable from the selected workspace packages. It does not come from every package in the lock or Cargo's general inventory. A wasm-only macro therefore does not affect Linux or Windows host lint. A macro that really builds for the host still needs an allowance. Missing or mismatched target resolution keeps native compiling stages unbounded until preparation refreshes it.

Reviewed manifest-only readers are bounded when the caller's manifest is already covered by a registry checksum or by the workspace stage's source reads, and the workspace root Cargo.toml and Cargo.lock are also in the key. This covers zbus_macros 4.4.0 and zvariant_derive 4.2.0 with their reviewed proc-macro-crate 3.5.0 helper, including cargo locate-project. The check includes possible downstream callers through macro re-exports. A caller manifest outside these bounds prevents the allowance and appears in the unbounded reason.

Other file-reading macros need a reviewed rule establishing fixed reads inside reviewed callers' unpacked, checksummed registry source. The caller identities are pinned too, including their re-export behavior. The lock already covers those files, so they need no extra digest. Currently the reviewed combination is document-features 0.2.12 used by crossterm 0.29.0, with both checksums pinned: it reads only crossterm's Cargo.toml and Cargo.toml.orig, and crossterm does not re-export the macro to downstream callers. Other consumer identities need their own read-rule assessment. A path dependency, workspace member, Git dependency, missing checksum or local source replacement does not qualify under this registry-source rule. Workspace manifests already in the key can qualify under the separate manifest-only rule. Unknown implementations and reads outside a reviewed rule stay unbounded and name the macro. For example, wasm-bindgen-macro reads caller-selected JavaScript and stays unbounded if it actually builds for the stage's target. Other unresolved include expressions name their source file and line.

An OUT_DIR include is generated output: its source inputs are the build script and its rerun-if-changed paths. A watched directory includes all its contents. Without any rerun-if-changed, the stage is unbounded because Cargo uses package changes as the default. rerun-if-env-changed names contribute their effective environment values to the key without publishing those values. Acquired compiler and dependency inputs retain their separately admitted identities.

Git metadata watched by a build script is a real input, including in linked worktrees. A script that watches .git/HEAD or its branch reference prevents compiling-stage reuse when that identity changes, even for a documentation-only commit. Unstaged edits outside predicted reads can still reuse a bounded stage. Changing build identity is a project decision; Oyzu does not remove those watches.

Verifying a contract​

oyzu build --verify-contract     # also: --json, --full

This can't be combined with --no-cache or --plan. A normal build runs. In addition, for every confined action:

  1. The action starts from a copy of its target workspace and runs confined, as usual.
  2. The same action runs again from an identical copy with the whole target visible.
  3. Oyzu compares the results: exit code, every workspace file created, changed or deleted, and the artifacts collected. Test and coverage report files aren't compared, because they carry timing.

Equal results pass. If they differ, Oyzu re-runs the action with subsets of the hidden files (at most twelve extra runs) to find a minimal set that explains the difference, and names those files and the declaration that fixes them:

  Contract check  failed · 8 confined actions run again with their whole target visible · 7 equal · 1 diverged · 20 not confined (not checked)
  api:build                 Diverged · also reads optional.json · declare inputs: ["api/optional.json"]

A divergence fails the build, including when independent targets run in parallel (diagnostic contract-diverged; manifest.extensions["oyzu.dev/contract-verification"] has status, counts and one record per action). The check uses a throwaway store, so it reuses and stores nothing. It doesn't run on the native path. Each confined action runs at least twice with copies of the workspace, so it is slow on large installed trees. Actions that aren't confined are counted, not checked. If the search stops at its budget, the record says minimal: false.

Remote OCI cache​

You can share action results through any OCI registry. Share them from CI to developers, or between a team's machines.

Targets built by an installed plugin package participate in cache.remote and cache.ciRemote. Keys include the verified package release, executable digest and runtime; changing the plugin identity causes a miss. Remote hits pass the same digest, artifact and report checks as local hits.

plugins.development bindings never read or write these shared remotes, including bindings to native executables or package archives. Their reusable results stay local. A slice's --handoff repository has its separate handoff contract.

# user or machine configuration: where results are shared
[cache]
remote = "oci://registry.example.com/team/oyzu-cache"
# user configuration: this machine also publishes what it builds
[cache]
write = true

Supported registries: zot, CNCF Distribution behind a token service, and a Harbor proxy-cache project, on Linux. Other registries (Artifactory, Nexus, Docker Hub, GHCR) aren't supported yet, and neither are Windows and macOS clients.

Settings and scope​

Use the environment variables OYZU_CACHE_REMOTE and OYZU_CACHE_CI_REMOTE for one invocation or CI. They override ordinary files and stay subject to administrative constraints.
  • cache.read and cache.write are per-machine preferences and don't change action keys, so readers and writers share entries.
  • A loopback host (localhost, 127.0.0.0/8, ::1) is reached over plain HTTP. Every other host uses HTTPS with the shared proxy and trust settings.
  • The remote is used only while the local cache is active. --no-cache, cache.local = false and --verify-contract use no remote.

What is shared​

  • Per-action results, for targets reused action by action (captured node/package and node/app targets with stage contracts).
  • Whole-target results, for targets reused only whole (the native host path, other builders). These appear under the target's ID in the build record where an action ID would be.

A per-action target's group record is never pushed. A client rebuilds it from the action results, so an unchanged repeat after a remote hit makes no registry request.

Sign-in and redirects​

A registry that requires sign-in is supported through the registry token flow. The credential is an environment variable, never a setting:

export OYZU_CACHE_TOKEN=…   # the token your registry's token endpoint accepts

In a CI job that offers OIDC ID tokens the way GitHub Actions does (OYZU_ID_TOKEN_URL and OYZU_ID_TOKEN_REQUEST_TOKEN, which the Oyzu runner sets), leave OYZU_CACHE_TOKEN unset. The client signs in with the job's ID tokens and asks for a new one when needed.

  • The credential is first sent as a bearer token. A 401 with a Bearer challenge names the registry's token endpoint. Oyzu uses it only if it is on the registry's own origin (scheme, host and port). Otherwise the request is denied and the credential is never sent elsewhere.
  • The client then asks that endpoint for one token per repository, with OYZU_CACHE_TOKEN as the Basic password (user name oyzu), or with no credential if the variable is unset or empty. Tokens ask for pull, plus push when cache.write is true. A rejected or expired token is fetched again once. A second refusal is a denial.
  • With ID tokens, the Basic password is the job's ID token: GET $OYZU_ID_TOKEN_URL with ?audience=<registry origin> and the request token as a bearer, answered with {"value": "<jwt>"}. It is reused until 30 seconds before it expires. The request token goes only to that URL, and neither token is recorded.
  • A blob response can redirect to another host (for example a separate blobs host with short-lived signed links). Redirects are followed without the Authorization header when they change origin, at most 5 times, and never from HTTPS to HTTP.

Entry layout​

  • Repository <prefix>/v1alpha1/<first two key hex>, tag lookup-<64-hex key>.
  • An OCI image manifest with artifactType application/vnd.oyzu.action-result.v1alpha1.
  • The action-result descriptor as config (application/vnd.oyzu.action-result.config.v1alpha1+json) and one layer (application/vnd.oyzu.tree.v1alpha1.tar+zstd) holding every blob the descriptor references, named sha256/<hex>.
  • Annotations: dev.oyzu.action.key, dev.oyzu.action.output and, on the layer, dev.oyzu.tree.uncompressed-digest.

Build record​

The build record gains manifest.extensions["oyzu.dev/action-cache"].remote: location, read, write, status (active, unavailable with reason, or unusable for a cache.remote the client can't use), counts of hits, pushed, converged, conflicts and rejected, the requests sent by kind, and per target the actions in each list. A result materialized from the remote carries extensions["oyzu.dev/remote-origin"] in the local store. The summary line adds the remote part, for example remote 7 reused · 0 pushed.

REAPI servers​

Use a stock Remote Execution API action cache in place of the OCI registry:

[cache]
remote = "grpc://127.0.0.1:9092/oyzu"
write = true

grpcs://host[:port]/<instance> uses TLS (default port 443). Plaintext grpc://host[:port]/<instance> is accepted only on loopback (default port 80). The instance can be empty or contain /. Credentials, queries and fragments are forbidden in locations. Standard proxy variables, loopback bypass and SSL_CERT_FILE additional trust follow the shared outbound transport settings. The user/machine scope restrictions, CI/development selection, offer behavior, local verification and report gates are unchanged. cache.immutableTags is ignored for REAPI; every push checks for an existing result first.

Qualification is limited to the provider, client platform and capabilities below. It covers cache uploads and reuse in a fresh checkout with an empty local store, including the existing artifact and required-report gates. Authentication coverage is limited to the modes listed below; remote execution and cross-platform keys are not qualified.

The client requires advertised SHA256 support. It uploads the Command and Action before updating the action cache. Empty blobs are already present by protocol. CAS batches account for the encoded request and gRPC framing within the server's size limit (4 MiB when unset). Read batches also reserve encoded response headroom. Blobs that do not fit use ByteStream. Entries are limited to 256 MiB. Every digest, size, descriptor and referenced blob set is checked before local publication. Corrupt content is quarantined and the action runs normally. CAS eviction is an ordinary miss, including when the action-cache record remains: it is not counted as a rejection or quarantined. A later push repairs that entry when its descriptor or any output blob is missing. Readable, valid entries with equal output identities converge without writes; different identities are conflicts and stay in place. Worker metadata is not an identity or trust check; the output layout and verified descriptor/key identify an entry. REAPI has no atomic create-only AC update, so this check does not provide an immutable-tag server guarantee against simultaneous writers. Concurrent uploads of the same valid output can both write or converge. A writer that sees a different output records a conflict, but racing updates can still replace one another after that check. Every read verifies the result's embedded action key, shape, CAS digests, sizes and complete blob set before committing it locally; normal restore and report checks still apply. A conflicting AC update that fails those checks is rejected, including during concurrent reads. A valid but nondeterministic result for the same key can be last-writer-wins: integrity checks do not authenticate a producer or prove that a computation was honest.

The credential is an environment variable, never a setting. OYZU_CACHE_TOKEN, when set, is sent as authorization: Bearer <token> metadata. A server requiring an API-key header can select its non-secret name with cache.remoteHeader; the same token value is then sent verbatim, without a bearer prefix. This setting applies only to REAPI and accepts a lowercase application metadata header, not reserved grpc-*, binary *-bin, host, content-type or te headers.

Without that token, OYZU_ID_TOKEN_URL and OYZU_ID_TOKEN_REQUEST_TOKEN use the same CI sign-in flow as OCI. The requested audience is the cache endpoint's origin (scheme, host and port), excluding the instance path. ID tokens always use bearer authorization, regardless of cache.remoteHeader. They are reused until within 30 seconds of expiry, then fetched again. A denial never triggers an anonymous retry. GET id token appears separately in request counts.

For mutual TLS, set both cache.remoteClientCert and cache.remoteClientKey to absolute PEM file paths and use grpcs://. The key must be unencrypted and readable by the build account; restrict access to that file. These paths and the header name belong only in user, machine or administrative configuration, not project files or profiles, and resolve once per build. They apply to all configured REAPI remotes; OCI is unchanged. The certificate authenticates to the cache server, not to a CONNECT proxy. SSL_CERT_FILE still supplies additional server trust.

Client identity setup errors name the relevant setting and file path and retain the filesystem or PEM parsing cause. Correct the path, file permissions or PEM contents before trying again; private-key contents are not included in the error.

Illustrative user configuration for a header-based server with mTLS:

[cache]
remote = "grpcs://cache.example.com/team"
remoteHeader = "x-api-key"
remoteClientCert = "/home/developer/.config/cache/client.pem"
remoteClientKey = "/home/developer/.config/cache/client.key"

Set OYZU_CACHE_TOKEN through the shell or CI secret facility. No token value, request token or private-key bytes are written to configuration, logs or build records. Server messages are omitted from failure records to protect secrets. Do not interpret a successful build as proof that credentials were accepted: check the remote status and the build's Warnings section.

Remote failures never fail a build. NOT_FOUND on lookup is a miss. UNAVAILABLE, DEADLINE_EXCEEDED, RESOURCE_EXHAUSTED, ABORTED, timeouts and connection failures get at most three attempts with exponential backoff and jitter, then disable this remote for the invocation. UNAUTHENTICATED and PERMISSION_DENIED disable it without retry. FAILED_PRECONDITION on update records a push failure and computation continues. When capabilities report update_enabled = false, writes are skipped with a read-only reason; reads remain available. Authentication denial appears in the remote build record as status: unavailable with a denied reason while the build computes normally. One warning names the location, gRPC status and credential inputs or permissions to fix. Transient outages also warn and compute locally. A read-only capability skips uploads without disabling reads; a write permission denial disables that remote for the build. Fix permissions, provide a fresh token or correct the certificate paths, then start a new invocation. Denial does not fail the build. TLS handshake failures can surface as gRPC Unknown rather than an authentication status. They also disable the remote and warn; check the CA and client certificate configuration rather than assuming the token was rejected.

A project can name a second repository that only CI writes:

The registry, not Oyzu, makes the CI repository trusted. It must refuse writes to that repository without the CI credential. Detecting CI only narrows what a build accepts.

  • A build that sets CI without the credential is refused (403), keeps building and writes nothing.
  • A CI build never reuses a developer's upload. It doesn't read cache.remote, and a result in its local store that came from a development remote is looked up again in the CI repository.
  • A remote hit is recorded with its scope (ci or development). Nothing is signed, so a hit from the CI repository says where it was read, not who produced it.

The registry credential is OYZU_CACHE_TOKEN or, without it, the CI job's ID tokens. It is never a setting, and it is never written to a record or log. OYZU_CACHE_TOKEN is sent as a bearer token on every request to the configured registry host (over HTTPS or to a loopback host), and dropped when a redirect leads elsewhere.

Immutable tags. cache.immutableTags = true says every configured cache repository refuses to replace a tag. A push then skips the racing-writer read, so a pushed action costs 6 requests instead of 7, and a refused manifest PUT (409 or 412) counts as the conflict. Don't set it for a registry that replaces tags, or the last writer silently wins. Either way, a hit is used only after the digests its manifest names verify.

Remote failures​

Remote failures never fail a build:

Remote limits​

  • Sign-in uses only OYZU_CACHE_TOKEN (bearer or the OCI registry token flow; verbatim API-key metadata when REAPI cache.remoteHeader is selected) or the CI job's ID-token flow. REAPI can additionally use mTLS through the two client certificate/key file-path settings. There are no credential helpers, Docker configuration, login command or OAuth2 POST token form; Basic auth to an OCI registry itself remains unsupported.
  • Immutable tags are declared, not detected. Results aren't signed and producers aren't verified.
  • Lookups aren't batched. Transfers are sequential. Entries above 256 MiB aren't pushed.
  • There is no remote retention or pruning. A damaged remote entry is rejected by every reader but never repaired or replaced. An entry pushed by an older Oyzu without keyComponents in its config is rejected like a damaged one.

Writes are atomic (stage, then rename), and a descriptor is published only after every blob it references. After a failed build, an eligible action's outputs, workspace changes and reports are sealed when it completes, so a later writer or target failure can't change them. An action whose required reports are missing or malformed isn't stored.

Upgrading Oyzu invalidates entries, because the builder digest is part of the key. Nothing is migrated, and old entries age out through retention. Python application builds receive the prepared-tree content identity in OYZU_SOURCE_DIGEST; source and version changes remain separate key inputs.

Limits​

  • The cache trusts the declared target graph (see Trust model).
  • Targets built by a host-coordinated image worker, and authored tasks around hooks on the native host path, aren't cached.
  • Version finalization after hooks covers only pre_build hooks on captured Node targets.
  • Narrow keys require a confined action or an admitted native read contract. Stages with an unbounded reason retain the whole-target key.
  • Execution-only settings such as cache.local and cache.nativeMaxMiB currently change keys.
  • Windows has no confined actions. macOS isn't supported yet.

Python cases inside a bounded unit​

Captured pip/pytest package tests can keep passing case results inside a changed file-level unit. Native collection supplies each full node ID, including parameters. Only the selected cases run, in their original relative order. The step combines native IDs, outcomes, durations and failure reasons with reused evidence in one JUnit report. Fresh native JUnit contributions are also retained with their configured output capture; the combined report does not add captured passing output. The action row shows, for example, 12 of 140 cases ran, 128 reused.

A case key compares five inputs: shared unit configuration and tool/dependency identities; non-code runtime inputs; code executed during import and collection; the case's executed code; and its native ID. Shared-input changes rerun every case. A changed import-time input reruns the whole unit. Within the bounded source shape below, a function-body edit reruns cases that executed that function. For supported captured development-source tests, the shared identity names that test subject and its genuine editable environment, including native metadata, RECORD and import mapping. It does not inventory the separate inferred-version wheel environment or inject its unused version default. Built-package tests keep actual wheel-installed facts; subject identities never share passing records. Required runtime-read confinement and the guards below apply to both subjects. Unsupported source layouts retain built-package testing. New cases and cases whose last result did not pass always run. Missing input or coverage facts also run the case. The stored passing record, rather than diagnostic history, authorizes reuse. Its case ID and all current key components must match the requested case. A history pointer to a different existing record is a miss, so the requested case runs instead of borrowing unrelated passing evidence.

Coverage facts come from an Oyzu-supplied pytest adapter using coverage.py's test_function contexts. For parameterized tests, a static native node-ID context keeps parameter identities separate. Core hashes admitted source bytes; the Python adapter never chooses cases or keys. Python's AST supplies current UTF-8 byte ranges and stable names for plain top-level functions. Rust hashes each executed function's entire definition from the admitted runtime view, including branches the previous run did not take. It resolves names against the current collection instead of reusing old line offsets. An unchanged function can move when another body grows or a new case is inserted; reused line/arc evidence is relocated to its current position for the combined coverage report.

This separation currently accepts modules consisting of imports, literal constant assignments, docstrings and plain top-level functions. Import statements and whole literal assignments, including multiline values, remain shared. Merely creating a function during collection does not make its body shared; executing it outside a case does. Modules with classes, computed module setup, colliding top-level bindings (including native import aliases, constants and function names), one-line definitions, decorators, defaults, annotations or unsupported source encoding retain whole-file identity. Python's native encoding detection honors coding cookies; only UTF-8 without a BOM supports function ranges. Other encodings stay opaque and execute with their native interpretation, even when their raw bytes also happen to decode as UTF-8. Missing location facts and case execution outside located functions also retain whole-file identity. Syntactic references to namespace inspection or evaluation (globals, locals, vars, dir, eval, exec, __globals__, __dict__ or __builtins__), including imported aliases and qualified attributes, keep every source in the bounded unit opaque. The adapter does not attempt to resolve which module an observer can inspect. For example, an unchanged assert 'test_added' not in globals() can fail when a new function is added; an unchanged assert 'added' not in vars(api) can likewise observe a new function in api without executing it. Both retain whole-file import/collection identities. Explicit source reads such as inspect.getsource remain shared runtime reads. This is a bounded native source contract, not general Python dependency analysis.

Shared tool, environment and runtime-artifact changes remain binding, including the actual installed package version and all .dist-info bytes (METADATA and RECORD included). A source edit that changes those inputs still reruns the whole unit; function regions do not normalize or discard them. File membership, kinds, executable facts and frozen non-code inputs stay shared; only inventoried code bytes move into the coverage components. The supported Linux development flow has demonstrated selective function-level reuse; see the measured acceptance and limits. Those results do not qualify full, CI, package or release validation or other platforms.

Selection currently requires Linux crun (--isolated --no-docker), enforced captured runtime-read bounds and coverage.py in the project environment. Coverage.py is not currently an independently acquired Oyzu tool. Missing or incomplete coverage runs the entire unit and gives a one-line reason. Native host tests and authored test tasks retain their existing whole-unit or whole-stage behavior. Python application archives and other languages do not use case selection.

The release context runs every case when its unit key changes. If fresh selective and full executions disagree on an identical case key, the result is reported as order-dependent, with both run IDs and which run was selective. Selection stays disabled for that unit key. A disagreement blocks the unit even if the selective child passed; the next build runs it fully. Native outcomes remain in the report. Detection does not turn a failure into a pass or run an automatic retry.

oyzu cache explain <target> lists each case's deciding component or the original run record used for reuse. JSON action records add caseSelection inside each unit, including fresh/reused counts, decisions and any order-dependence finding. Reused cases remain evidence not run now in test summaries. Existing v1alpha1 records are extended in place; records without case facts continue to use unit-level behavior.

Compiler-state seeds​

Captured Rust compilation can start from a compiler-state seed in an OCI cache.ciRemote repository. REAPI remotes do not supply or publish compiler seeds: they skip seed filesystem work and requests while ordinary action-result caching remains available. This is native compiler state, not a successful action result: Cargo still runs, artifacts are validated and the selected checks still execute. It does not enable cross-path reuse for host-native builds or change their compiler-cache retention.

Seed keys include the compiler archive digest, native Cargo lockfile digest, target triple, absolute compiler-visible workspace and Cargo home, selected worker and command, effective-environment digest, tool-lock identity and tool archives. Raw environment values are not stored in the seed inventory. A path mismatch selects a different lookup before any compiler-state download. When native read completeness is unknown, the key also binds the complete final staged source and preparation identity: changed inputs then build cold, even at matching paths. There are no fingerprint edits, filesystem aliases or new sandbox mappings.

The seed is an OCI manifest with content-addressed inventory and archive blobs, under the configured CI repository's compiler-state/v1alpha1 segment. For example, a CI repository prefix of oyzu-cache/ci keeps seed manifests and blobs under oyzu-cache/ci/compiler-state/v1alpha1/<key-shard>.

Seed publication is disabled in this client, including CI and pool jobs with write credentials. There is no configuration or environment switch to enable it. Enabling publication and qualifying a trusted producer require a separate change; client environment hints cannot authenticate that producer. Developer remote repositories are never seed sources. The registry owner manages retention.

Restoration verifies the key, blob sizes and digests, archive member inventory, file contents and containment before committing compiler state. Symlinks, hard links and special files refuse the seed. An existing local directory is never overwritten. A refusal or unavailable remote causes a cold build; offline builds do not contact the seed remote. A seed manifest or blob request that fails after transport retries, or is denied, disables that remote for the rest of the invocation, including subsequent action-result lookups. A missing manifest is an ordinary miss; a missing blob rejects that seed. Neither missing response disables the remote. A seed does not provide missing tool or dependency archives.

The inventory preserves native compiler metadata and records source contents and times. Identical source contents regain their recorded times; changed inputs remain newer than restored compiler work. Compiler fingerprints and dep-info retain their original bytes. Capture and restore read the compiler tree to verify it and inspect source contents to bind freshness; this work happens only for an active, readable OCI CI seed consumer. REAPI-only remotes skip it, and installed-tool use does not trigger it. Archive bounds are 1 GiB compressed, 12 GiB expanded and 32 MiB for the inventory; an oversized seed is refused.
