Action cache

CLI reference

Published from the canonical docs/reference/action-cache.md file. Features marked experimental remain experimental; check support limitations before relying on them.

A repeat oyzu build skips targets whose inputs haven't changed and restores their earlier results. You configure nothing: you never write cache keys or per-language cache paths. This page covers what is reused, what invalidates it, how to see why a stage ran, and how to share results through a registry.

Note: The action cache is experimental. The remote cache is unsigned, so a remote hit tells you which run produced a result, not that the result was verified.

See stage reuse for builder and execution-path admission rules.

Reading newer reports and history​

Cache explanations accept additional descriptive JSON fields. Updating an explanation preserves annotations on its envelope, subject and retained observations, including component annotations when the action key is unchanged. History still retains only the latest and previous observations. Explanations never authorize reuse: action keys, content digests and trust checks remain binding.

Annotations on test-unit and case-history envelopes are retained only while their identity key and subject remain unchanged. A new key starts a new record; facts from an earlier identity do not carry over. Annotation-only lookup data does not replace the current explanation or its version-scope fallback.

oyzu history reads recorded build and test summaries without rewriting their files. It locates logs/events.jsonl as an opaque journal; additional event kinds or descriptive fields do not affect that lookup or establish verification. Paths remain confined to the bundle. Installation lease journals and interrupted configuration-edit journals remain strict because recovery can remove locks or replace files.

Usage​

oyzu build                       # first build runs and stores; repeats reuse
oyzu build --affected HEAD       # Git-selected targets also reuse unchanged results
oyzu build --full                # quality stages and their reports are reused too
oyzu build --no-cache            # run every action; read and write nothing
oyzu cache status                # where the store is, how large, how many entries
oyzu cache clear                 # remove every cached result (bundles are untouched)
oyzu build --explain             # after the build, why each stage was reused or ran
oyzu cache explain api           # why target api's key (and its stages' keys) last changed

Every oyzu cache command supports the global --json flag before or after the subcommand. status and clear inspect the configured store; explain reads its recorded key history.

Output shortened. A project with four targets, one run each:

$ oyzu build                         # cold
✓ Build succeeded   4 targets · 4 executed · 9.4s
$ oyzu build                         # unchanged repeat
  ↺ api    build                                   reused   was 1.2s
✓ Build succeeded   4 targets · 4 reused · 1.8s
$ echo "// edit" >> api/src/greeting.mjs && oyzu build
✓ Build succeeded   4 targets · 3 reused · 1 executed · 3.1s

Reuse is local to one user on one machine unless you configure a remote cache. Every output says plainly that a restored result was not executed now:

  • Receipts keep reused test evidence apart from fresh tests.
  • When known, reuse.source records whether the local or remote store served the result.

Compile-stage cache misses annotate the existing action row with missed: <reason>. The same reason appears on the running task event in events.jsonl and in cache explanation history, including builder identity changed when that component changes.

Development plugins report plugin.source_digest through describe. First-party plugins embed the digest of their Cargo package source and local build/runtime dependency closure at compilation, including the dependency lock and runtime assets. Private per-invocation plugin executable locations and frozen invocation tokens use that verified identity in output-location keys and native-read definitions; checkout and native compiler-cache locations remain significant. Replacing linked executables from the same inputs does not invalidate reuse, including when a self-host build installs its newly built CLI. A plugin without this identity can still build, but its development results are not reused. Published packages keep their admitted release digest in the key. Executable verification, private invocation copies and package admission remain required independently of cache identity.

Moving an unchanged checkout on the same platform preserves keys only for stages whose builder declares every retained output relocatable. Before hashing, Oyzu replaces known checkout, private-workspace and per-run scratch locations in command arguments, environment values and declared paths with stable relative locations. This includes paths inside native JSON arguments and Windows drive, separator and verbatim-prefix forms. Paths to inputs outside those known roots still affect the key; resolved tool and plugin identities remain part of it. Source bytes, build profiles and platforms must still agree. Root matches require the end of the value or a directory separator. A sibling such as C:\ws)external\input.rs stays distinct from the root C:\ws. This also applies inside command text: punctuation alone does not establish containment, so ambiguous text retains its original identity. Entries written by versions that retained checkout-specific paths can miss once after upgrading; the existing cache need not be cleared. An unavailable cache is different from --no-cache. If the store can't be used, permitted native builds continue with a warning and run everything.

Output relocation​

The builder's relocatable_outputs command promise covers intermediate trees and reports as well as delivered artifacts. Without that promise, the key also binds the actual checkout, execution working directory, arguments and environment before location normalization. Moving the checkout or changing those native locations causes recomputation instead of restoring files that refer to the old location. The location input is stored as a digest. This is automatic; there is no project setting to override the builder's promise. Core-allocated temporary report directories do not change this digest between invocations; checkout, working-directory and native compiler-cache paths still do.

On Windows, leased tool locations use the on-disk spelling captured from the already-pinned store-root handle. Case aliases (including drive-letter case), 8.3 short names and \\?\ paths for that same store do not change the tool location or its command-derived extension digests. This does not lowercase paths: different case-sensitive directories keep different location keys. Store roots and ancestors still refuse reparse points: junction aliases fail closed, even when their target is another store directory. Publication locks and installation leases continue to protect the same pinned store entries through admitted aliases. If handle-path retrieval or lexical normalization fails, normalization changes the drive prefix, or the path has a different number of components from the pinned ancestor chain, the existing exact path spelling remains significant and an alias may miss. In particular, subst and mapped drives keep their drive spelling rather than expanding to a longer path or UNC location. No path is reopened or resolved to obtain this identity after pinning.

Native Windows refusal​

There is no merged Windows complete-read backend for Vite or uv lifecycles. Native stages with incomplete reads must execute again; copying the source into a private workspace does not change that. Python 0.1.3 refuses Windows uv before actions start; later releases admit it and run it again each time. Supported isolated Linux reuse requires a Linux crun host; it does not enable native Windows reuse.

On native Windows, Maven/Gradle lifecycles and arbitrary npm scripts have incomplete runtime reads. They run again on unchanged builds; a whole-target cache hit cannot skip them. Independently admitted complete-read stages and native tool/download caches may still reuse their own results.

Use oyzu build --explain or oyzu cache explain app (replace app with your build target) to see the named refusal: native reads are incomplete on this host. For a whole-target refusal, query the target name rather than an action name; the refusal is recorded even though no reusable result is stored. This is a safe execution decision, not a damaged cache. Clearing the cache or adding known inputs cannot establish complete runtime reads. For Maven/Gradle and npm stage reuse, use the isolated Linux crun path: oyzu build --isolated --no-docker. Windows does not provide that boundary. --no-cache runs the same native commands without reading or writing action-cache results; changed external inputs must affect both cached and uncached execution.

Inherited native environment​

Native host builds preserve the compiler/runtime controls declared by their builder and freeze their inherited values into the action environment before cache lookup. Changing one of these values invalidates both whole-target and individual-stage reuse. Explicit project/task environment settings still take precedence; configuration removals and environment policy validation still apply. Human output and --json report the same executed/reused actions.

The Rust builder declares Cargo/rustc flags (including encoded flags), compiler and documentation executables, compiler wrappers, toolchain/build-target controls, Cargo/Rustup home locations, the selected target's Cargo flags/linker/runner, native C/C++ compiler and linker controls, and reproducible-build stamps. The Node builder declares NODE_ENV, NODE_OPTIONS, NODE_PATH, NODE_ICU_DATA, OPENSSL_CONF, TZ, native C/C++ compiler and linker controls, and SOURCE_DATE_EPOCH. The lists live beside each builder's stage declarations. npm installation also retains its existing binding of discovered npm_config_* controls.

Native build actions receive their frozen declared and configured environment, plus shared launch, home and Windows machine-discovery controls. HOME, USERPROFILE, APPDATA and LOCALAPPDATA are passed through when set and keyed with their exact values, alongside PATH, SYSTEMROOT, SYSTEMDRIVE, PROGRAMDATA, WINDIR, COMSPEC, PATHEXT, ProgramFiles, ProgramFiles(x86), ALLUSERSPROFILE, OS, PROCESSOR_ARCHITECTURE and PROCESSOR_ARCHITEW6432. Explicit configuration overrides inherited values. Changing a passed home/profile value between shells changes the action key, even if the native tool ultimately does not use it. This preserves native Go, .NET and Helm home-directory defaults without guessing which tools read home.

Home inputs are a single set: HOME, USERPROFILE, APPDATA and LOCALAPPDATA. Go, .NET/NuGet, Helm, Cargo/Rust and npm/Node all retain this set, including formatting commands. Other builders and commands with no home declaration retain the same default. Home values identify the environment; they do not establish complete filesystem reads or authorize reuse of files discovered through passwd, Windows known folders, registry or JVM properties.

The SDK also retains home for pnpm/Yarn, pip/uv/Poetry, Maven/Gradle/Ant, Zig and Docker contracts. Their tool-specific cache and configuration variables keep their existing environment and key semantics.

Builder source contracts may declare home: "required" or home: "none". Missing declarations mean required. An unqualified none claim retains the home environment and prevents native action, whole-target and shared-cache reuse. Fixed source rules and compiler read reports alone do not cover home discovery or descendants. Explicit home environment settings or declared home names cancel the claim and retain ordinary home-required behavior. Replacement commands and hooks use their own contracts.

On Windows the declaration recognizes these four names without regard to case. Existing environment precedence and policy validation remain binding; case-colliding aliases are refused with CONFIG_INVALID_VALUE. Configure one spelling per name and retry. No native host scope omits home on Linux, Windows or macOS. This requires no new user setting or network access.

The scoped exception is first-party packaged Rust format-check under the Linux crun executor (oyzu build --full --isolated --no-docker). Core admits the package identity and bounded Cargo formatter command separately from the claim, then freezes an enforced boundary in the action identity. The formatter and its descendants can read only admitted image, tool and source inputs and private outputs; ambient host home is not mounted. Passwd/account fallback sees keyed image facts, not the host account database. Image defaults cannot restore the omitted variables. Explicit CARGO_HOME and RUSTUP_HOME remain inputs. Only that action loses home; a compilation or other receiving sibling retains its own home values in its key and the enclosing target key. Native hosts, development plugins and third-party declarations do not acquire this exception.

Windows shell lookup uses these frozen launch inputs, including a configured Path, rather than consulting the host environment again. The corrected lookup advances Oyzu's internal cache identity, so older action results are rebuilt.

TEMP, TMP and TMPDIR are executor-owned: native actions always receive private temporary paths in place of inherited, configured or builder-declared values. These overwritten values are omitted from native host action keys, declared environment reads and command-derived extension digests, including when supplied by configuration or a builder. Changing only those values preserves reuse. Authored inputs and the final allocated environment still undergo policy validation. Configuration files read as ordinary program data remain source inputs; editing their bytes can still invalidate those reads. The private paths never enter keys or extension digests. Other undeclared shell variables are absent, even with --no-cache; declare project-specific inputs in configuration. Complete read admission remains required: removing an unused ambient variable never makes incomplete reads reusable. Native .NET stages still run on every build because their reads are incomplete. Native Helm packaging and archive normalization also rerun without complete observed reads. Development tasks retain host inheritance. Ordinary host stages do not provide filesystem or network isolation; admitted authored tasks use the per-action boundary described below.

Regular-file permissions​

On Unix, source and output inventories record ordinary regular-file permission bits as unixMode (0 through 511, the octal 0777 mask), retaining the existing executable fact. Mode-only changes participate in both coarse target and selected-content action keys. Listing-only selectors still identify names and entry kinds; source-version scopes remain permission-independent.

This is conservative invalidation for captured source too: raw observed modes can change a key even when the selected captured execution view normalizes its permissions. That execution behavior is unchanged. Prepared-file copy provenance requires mode equality as well as bytes and executable intent.

Cached group and workspace-delta files carry the admitted mode from the same file handle as their bytes. Verification rejects absent, out-of-range or executable-inconsistent Unix mode evidence before accepting a restore; older records follow normal cache refusal/recompute behavior. It never substitutes a canonical 0644 or 0755. Verified bytes remain readable during cross-device staging, and the final mode is applied before atomic publication. A failed file restore preserves its existing destination.

On hosts that cannot observe Unix modes, the optional fact is absent. Directory output modes, ACLs, ownership and special bits are not added to the cache contract. Use --no-cache when those properties affect the required output.

Directory output trees retain empty roots and nested empty directories as well as regular files. Restore verifies the complete directory inventory against the artifact record; missing directories are corruption, even when no file bytes are missing. Directory artifacts reject symbolic links, including links to directories and linked artifact roots. Cache capture does not follow them.

Private action-output collection converts native relative path components to portable /-separated names before validation. Nested files and empty directories retain their layout; nonportable names, links and special files are rejected. Unix executable permission bits are preserved where the host supports them.

Flaky tests and quarantine​

The test-attempt controller can retry genuine test failures within a build. Rust case reruns use exact nextest selection and retain native retry attempts without adding Oyzu retries on top. A recovered case is reported as flaky, and its unit is never stored as a clean reusable result, including when nextest performs the retries. Native pytest reruns exact failed node IDs; detected pytest native retries have unknown attempts, prevent storage and receive no additional Oyzu retry. Missing requested cases stay failed. --no-cache preserves the same retry and completeness rules.

Eligible test units also retain actual executed outcomes in local cache history. An exact unit input key and test identity with both a pass and a failure proves flakiness. Named native cases are compared individually. A legacy report with unnamed cases uses the whole unit when it declares a dedicated assertion exit and retries are disabled. Findings retain both outcomes, run IDs and machine names. Machine names come from the operating system on Unix and Windows, independently of ambient environment variables such as COMPUTERNAME, including in native build actions with a cleared environment. A cache hit adds no execution evidence. Different keys, skipped cases, missing reports, setup failures and executor/resource errors do not prove a flaky test.

By default every current failure still fails under its configured check level. Opt in explicitly with [checks] quarantineFlaky = true in the configuration cascade. Policy can forbid it. Quarantine executes tests freshly, keeps their failures and required native reports, and makes only a proven same-key flaky assertion failure non-blocking. Release context and governed main CI always ignore quarantine, including an explicit true value under [context.ci.checks] on a main-CI run in ci context. Coverage, required reports and the existing order-dependence guard remain binding. Separate native test and doctest reports are matched to the complete contributions of their named units; unknown or missing contributions still fail.

Human and no-color receipts list Flaky tests and Quarantined failures. JSON and retained manifests include unit executions, flaky, quarantined, nativeExitCode and nativeCases; each unit's native outcome remains failed when quarantine changes its step disposition. The build's tests section also collects executions, sameInputFlaky, sameInputFlakyCount, quarantinedFailures and quarantinedCount. flakyCount continues to count attempt flakes; sameInputFlakyCount counts historical same-input findings separately and defaults to zero when absent in an older record. Native JUnit failures remain failures.

History requires an already admitted input key and the existing local cache store; quarantine grants no missing read bounds or cache authority. It works offline with installed tools and needs no account. --no-cache retains visible retries but reads/writes no cross-build outcome history and applies no history quarantine. History is local: another machine or an evicted store may lack earlier outcomes. There is no platform quarantine integration. A known conflict revokes clean-pass reuse for that key even after a later pass; healthy siblings retain normal reuse. See quarantine configuration.

Native builds work from a private copy of each target's source, kept in a host-workspaces folder next to the action store. It follows the platform cache location, not cache.dir. If that folder is on a different drive than your checkout (for example the cache on C: and the repository on E:), Oyzu parks the copy in the repository's Git directory instead (.git/oyzu/host-workspaces, or the linked worktree's Git directory), so parking stays a rename rather than a full copy. The first such build moves a copy parked at the old location. Use build.host-workspaces-dir to choose the folder yourself. It must be outside the source tree; the Git directory counts as outside. The path must not pass through a symbolic link, except root-owned top-level links in a root-owned filesystem root that is not writable by group or others, such as macOS /tmp and /var. Oyzu renames the copy into place when it can, and otherwise copies only the pruned source, keeping file times and permissions so native tools such as Cargo still see unchanged files as fresh. A real source edit still invalidates native compilation. Oyzu never copies compiler, dependency or tool caches. Changing the setting doesn't move existing parked workspaces.

For disposable native projects, set both cache.dir and build.host-workspaces-dir in a private user configuration selected with OYZU_USER_CONFIG. Setting only cache.dir does not isolate source parking. On Windows, changing HOME does not redirect the native cache location.

The Git fallback requires an existing repository, recognized by the same metadata checks as project discovery. Outside Git, parking stays in the native cache even across filesystems, unless you set build.host-workspaces-dir. Empty .git markers and directories holding only Oyzu state do not expand the host source boundary or select the fallback. Oyzu never creates a .git directory for host-workspace state. If a configured parking path would require one, the build fails with host workspace storage cannot create a Git directory; select a cache folder outside the source tree.

The store is per user and shared across projects. It holds blobs/sha256/ (file bytes), results/<key>.json (result descriptors), history/, pushed/ (remote publication markers), quarantine/ (rejected data), preparation-locks/ and tmp/. Output trees are stored as a manifest plus one file per blob, not as a compressed archive.

Workspace changes and merge-back from private native or confined views are detected against a content baseline. The tracker compares size, modification time, executable status and link target. On Unix it also compares change time (ctime), device and inode; on Windows it reads ChangeTime and the volume/file ID through attribute-only handles without following links. These native facts detect same-length rewrites even when a tool restores an old modification time.

Each baseline starts with a temporary probe in the workspace, removed before scanning, whose modification time supplies the filesystem clock. An otherwise unchanged regular file is content-compared if either its modification time or native change time is not strictly older than that stamp. This includes equal clock ticks and future timestamps. Unchanged older files keep the stat-only fast path. If native change information or a timestamp is unavailable, regular files are conservatively content-compared: the modification-time rule alone cannot detect a rewrite that restores an old timestamp. Views keep baseline digests only for regular files with racy or unavailable clocks. An equal-size, equal-mtime write is merged back before delta capture; unchanged older files require no content read. Identical content produces no delta. Symbolic links, special files and executable changes retain their existing handling; a delta containing links or special files is not restorable.

Serial confined actions may share files with their private target workspace through hard links. Creating and removing those views changes native metadata without changing content, so those files still require hashing. Before staging a candidate, the tracker compares its digest, executable status and link kind with the content baseline. An identical entry produces no delta or staging copy. An executable-only change still stores its bytes so it can be restored. Changed files use the digest and size returned by verified store admission, which may read the file again after the preliminary hash. This avoids unnecessary staging; it does not remove link-induced hashing. Preserved-mtime writes and racy or unavailable clocks retain their content-comparison rules.

Workspace restores verify every cached file into private staging before accepting a hit. Deferred restores retain those staged files without keeping a file handle open per file, so large results such as Python virtual environments do not require raising the process file-descriptor limit. Staged files are removed after restore or when the pending restore is discarded. A corrupt blob rejects reuse before the workspace is changed.

Retention​

At the end of a build, if the store is over 10 GiB, Oyzu removes the least recently used results until it fits, then removes blobs no result references. A hit refreshes an entry. Eviction touches only the cache. Bundles in dist hold their own copies. The budget is fixed. Cache history metadata, including definition-keyed native observations, has a separate 64 MiB ceiling (bounded further by a smaller maintenance budget). Every retention pass prunes its least recently used records, even when result bytes are below budget. Pruned observations discard narrowed lookup shapes. Native stages can still discover stored complete-prediction results; otherwise they return to whole-target keys.

The same pass bounds the store's other expendable state, so a long-lived laptop or runner cache doesn't grow without limit:

StateKept
quarantine/ (rejected data)7 days, and at most 256 MiB; the oldest goes first.
pushed/ (remote publication markers)7 days. A missing marker only makes the next push recheck the remote.
tmp/ (staging)Files older than 24 hours are abandoned leftovers and are removed. Active staging is newer and protected by the build lease.
preparation-locks/Removed when no process holds them. A held lock is never unlinked.

oyzu cache status reports these together with history as auxiliary bytes (auxiliaryBytes in --json), separately from the result budget, and oyzu cache clear removes them too. store.lock and history.lock are never removed. Installed tools and bundles in dist are outside the store and are never touched.

  • Builds hold a shared lock on store.lock while they read or write the cache.
  • Preparation publishers and history writers release their operation locks when they finish, including on failure. Unrelated child processes do not extend those locks' lifetimes.
  • An unused store isn't created. Runs with the cache disabled, or with nothing cacheable, leave it alone.
  • oyzu cache clear needs exclusive access. While a build uses the cache it fails with a retry message and leaves active staging alone. Retry when the build finishes.
  • If end-of-build eviction hits contention it warns, and the store may briefly exceed its budget. A later build retries.
  • If a store is busy with maintenance, builds proceed without it and cache commands return an error.
  • Don't delete store.lock to clear contention. The lock protects cooperating Oyzu processes, not external deletion or filesystems without working locks.

Copying and verifying cached bytes​

Oyzu hashes file bytes while copying them into the cache and again when restoring them. It checks every file of a restored action before accepting the hit, and it replaces each destination file only after its copy succeeded, so a missing or corrupt blob leaves the previous file in place. Corrupt cache data is rejected, quarantined and recomputed (see Failures and recovery). A restore that touches several files isn't rolled back if a later file operation fails. Artifact and report gates still run after a restore.

What is reused​

The unit of reuse depends on what Oyzu knows about the target:

  • Per action for targets whose actions all carry a stage contract (including captured node/package and node/app), or which contain an independently admitted native authored cached action. Each eligible action (for example api:version, api:build, api:package) has its own key and result. A companion without a stage contract always executes; its output digest still keys actions that follow it, and it blocks storing or restoring a whole-target group. See Per-action reuse.
  • Per target where individual actions are not admitted: one key per target, restoring all its actions together or none. Native whole-target reuse requires every stage to have complete admitted reads and bounded outputs; it cannot bypass a stage that must run.

A reused target or action keeps:

  • its artifacts, byte for byte (each is checked against its recorded digest);
  • its original JUnit, coverage and other reports and their producer evidence;
  • the original run ID, key and completion time, in a reuse record.

Oyzu stores a target only after all its actions succeeded and its reports were collected. Failed, blocked and cancelled targets aren't stored.

Built-in builders declare their own actions; no user-authored cache key is needed. Reuse still requires admitted reads, bounded outputs and valid results. Declared source inputs are included in the target's key on both native and captured paths.

Targets with a builder-selected source projection are cacheable too. A projection narrows the target's own folder to selected target-relative files; it does not declare additional source outside that folder. Whole-target keys include the projection definition and the captured identities of its selected entries (paths, types, content digests and executable bits). For native captures, whole-target fallback keys retain both the frozen selection rules and the captured content digest, even when the caller's source scope is unchanged. A workspace member edit therefore invalidates the fallback key. Native capture keys use the existing engine cache contract; invalidation follows the captured inputs.

A stage with an admitted read set keys only its selected reads, including directory listings used for discovery. The whole candidate projection is not a second input to that stage. Native reuse first finds observations for the same command, engine and prediction, then validates a complete observation against the current admitted source and computes the result key from those reads. Successful admitted native results are also stored under a key covering the complete current prediction. A remote reader with empty local result and observation history can derive that key without receiving or trusting a remote read list. It uses the same tool, environment, profile, platform, upstream, artifact and report checks as other action results. A valid narrow hit also offers a result for its current complete prediction, so an edit to a predicted but unread input does not leave subsequent empty readers without a lookup. This discovery key matches only the current prediction's inputs; it does not provide observation history across different source snapshots. Existing remote scope and producer trust limits still apply.

Missing, incomplete or out-of-prediction observations cannot authorize new prediction or narrowed results. Without an existing admitted result, the native stage runs without restoring or storing a coarse result. A whole-source key cannot cover files read outside the source root. Confined captured actions use the files available in their view. Key construction reuses captured entry digests; it does not walk or hash source files again.

The same rule applies to an export or copy stage without a stage contract: the target still runs, but cannot fall back to caching the whole target. With complete contracts, eligible stages can retain their separate cache entries.

Explicit builder reads and writes are scoped from the target folder on both captured and native paths. Parent traversal (two dots) is refused for paths, globs and listings. Declared workspace inputs remain a separate source-admission mechanism.

Conventional native Go compilation writes a stable intermediate executable. A final export copies it to the inferred-version filename. An unread README content edit can reuse build, vet and format-check; a commit with unchanged source reuses those stages. If version metadata changes without source changes, only the versioned export runs again. A plain empty commit leaves the source-content snapshot version unchanged, so export can reuse too. Artifact metadata and receipts retain the current inferred version. Go does not inject a version variable into the program. Authored version-bearing commands and environment values remain inputs, and other builders need their own final-stage version boundary.

Not cached by default​

These targets simply run, and the output says why:

  • Targets with authored tasks or task overrides that don't ask to be cached, and targets whose hooks ([tasks."api:pre_build"]) declare no outputs. An authored task with cache = true and outputs is eligible only with complete read admission (see Authored tasks). A hook that declares outputs is followed on targets reused action by action (see Hooks).
  • Targets with hooks on a path that reuses a target only whole (native host targets with hooks, and captured targets without stage contracts). Restoring them would skip hooks that must run on every build.
  • Targets that use secret environment values ({ secret = "…" }).

Native npm applications​

Linux crun npm stages use complete-read enforcement through the existing isolated/container selection (oyzu build --isolated --no-docker). Successful stages can reuse their workspace changes, artifacts and required reports on unchanged runs. Their keys include admitted source reads, prepared dependency identities, the locked Node runtime, other tool/runtime identities, command, environment and producer outputs. A source edit invalidates the stages that read it and their consumers. Script-free installation omits only the generated OYZU_VERSION default when the admitted model proves it is unread, allowing reuse across shipping edits. Lockfile, npm config, tool identity and other execution inputs remain keyed. Explicit version environment values remain keyed, and every build/test stage keeps its version input. Root/dependency install scripts (including scripts with reviewed file reads), implicit native compilation, incomplete facts and runtime loaders retain the variable and refuse install reuse. Arbitrary lifecycle scripts conservatively read the entire admitted source view. Lock/dependency and locked tool changes invalidate the affected stages.

These actions share the enforced boundary with the captured Maven experiment: live proc/sys and undeclared host paths are hidden, network is denied, and each lifecycle starts with private output state. Fixed core retirement/export helpers retain their existing bounded contracts. Failed unsupported reads cannot publish reusable success. A handled absence is stable within this view. The closed non-keying device allowance below also applies; entropy must not affect retained outputs. --no-cache runs under the same boundary and report gates. No extra setting is needed. Native npm on Linux, Windows and macOS still refuses incomplete reads; Docker and other Node package managers retain their existing captured rules.

For native npm applications with dependencies, the target includes the install action (npm ci) in the private target workspace before pre-build hooks. Arbitrary build and package lifecycle scripts have no complete native read report, so their results cannot be reused, even with unchanged source.

An incomplete native stage also prevents whole-target restoration. Bounded install declarations alone do not enable native per-action admission. This does not disable the separate tool and dependency download caches, or the admitted captured actions described below. Nothing needs clearing after a CLI update.

Isolated npm downloads​

Before looking up actions, the captured npm path validates native metadata and downloads locked dependency bytes with lifecycle scripts turned off. That script-free step can be reused from the local store.

  • The key covers the full source and target tree, the worker image and platform, the admitted tools, the command and environment, configuration and the download routes. Any change to the source, lock, tools, routes or configuration needs a new download.
  • Tools are checked before lookup, and restored files are verified before use.
  • This download entry does not cache later offline install or lifecycle work. Those stages can reuse separately under the Linux crun boundary described above.
  • The journal records a reused step as not executed now, with its original time and key.
  • These entries share the local store, lock and 10 GiB budget. They are never uploaded to a remote cache.
  • A missing or damaged entry falls back to a fresh download. Partly restored trees are discarded.
  • --no-cache, cache.local = false and --verify-contract turn this reuse off. Builds with managed configuration, secret environment values or authenticated routes don't use it. Offline builds can reuse earlier captures.

Prepared resources and Go tests​

  • Native builder actions can bind exact prepared-resource files. The plan records those files and their content digest, and execution mounts the same selection even with --no-cache.
  • Captured Go tests run in confined workspaces with fresh report folders. Validated reports are captured into the build bundle; restored reports keep their producer evidence. Test manifests and compiled tests are explicit build outputs consumed through producer relationships. See Go.

Go compile actions and exports retain separate captured source/dependency keys. Source, module/lockfile, prepared dependency and selected Go identity changes invalidate consuming actions. On Linux crun, isolated go/app builds reuse complete-read stages, including generated test preparation and unit results. Generated manifests and compiled tests enter the observed read set and stage key; changed manifest bytes miss, and undeclared carried files are refused. Every invocation gets fresh writable /out, with only selected phase inputs and identified unit contributions mounted read-only. --no-cache executes every stage with these same boundaries and required report gates. Incomplete native-host reads continue to refuse stage and whole-target reuse on Linux, Windows and macOS. There is no complete Go runtime-read enforcement backend on Windows or macOS. See Go.

Prerequisites and platforms​

  • Captured path: oyzu build and oyzu build --affected on targets that use the Docker executor and its toolchain images (for example node/package).
  • Native host path: builds that run on the host with Oyzu-provisioned tools reuse only stages with complete admitted reads and bounded outputs. Unchanged source alone does not guarantee reuse. See Native host builds and current native read coverage. Targets built by a host-coordinated image worker aren't cached yet and say so. oyzu run executions are never cached.
  • No account is needed. Ephemeral CI runners start with an empty local store. With a remote cache they reuse results other checkouts pushed.
  • Tested mainly on Linux. On a Windows host, shared edits conservatively re-run unrelated work. macOS isn't supported yet.

On Windows, action tracking records native symbolic links and the Linux links Docker creates in a captured workspace without following them, so pnpm links stay usable by later native actions. A change that contains links can't be restored from the cache. Other Windows reparse formats fail with an error.

Output​

In the live Build section, restored actions show ↺ (the word reused without color) in place of executed. The summary counts them apart from executed work (2 targets · 3 reused · 1 executed). With -v and in JSON you also get each target's reuse origin and the Cache line. The final receipt marks test and coverage lines from restored reports as reused from an earlier run, not run now.

In the build bundle a reused action keeps status: "succeeded", so every gate applies unchanged, and gains:

"actionKey": "sha256:…",
"reuse": { "actionKey": "sha256:…", "originalRunId": "…",

Explaining reuse​

oyzu build --explain explains decisions after running the build; oyzu cache explain <target> reads recorded history without running anything. They report reuse refusals as well as the first key component that changed. A stage can be refused reuse even when its key is unchanged.

Native action explanations include skipped history discovery and candidates in nativeCandidates, with basis: "history", lookup: "skipped" and a reason. Reasons cover disabled observation, a missing HISTORY subject or unreadable record, missing or malformed reports, the four-report history limit, incomplete observations, reads outside the current prediction, missing source snapshots, and unavailable admission or key derivation. Outside-prediction reasons show the first five sorted paths, listings or external inputs and count any remainder. History is also skipped for an uncacheable action, a missing stage contract, unbounded outputs, or an authored replacement without admitted observation.

A missing-record reason names the current HISTORY subject digest. Reports under another subject are not considered; a record can also be absent, unreadable or invalid. Skipped entries describe why no lookup occurred and never admit a hit. nativeHistory includes the lookup subject, sorted storedSubjects for the same action ID, and unattributedRecords for older native records without action and subject metadata. Human output names these alongside the gate reasons; other subjects remain diagnostic only and never supply candidates.

A native action restored through a whole-target hit still has an actionExplain entry with its current nativeHistory.subject. Its winning nativeCandidates entry has basis: "whole-target" and lookup: "hit"; no independent action candidate was probed on that shortcut.

Set OYZU_DEBUG_NATIVE_SUBJECT=<dir> to write best-effort lookup-<pid>-<random>.json and store-<pid>-<random>.json receipts with action ID, frozen HISTORY digest and pre-digest payload structure (scalar values hashed to protect secrets); disabled by default, with no cache behavior change. For example (illustrative):

{"basis":"history","candidate":1,"lookup":"skipped","reason":"observation outside prediction: extra.rs"}

A failed local lookup is recorded as lookup: unavailable with the cause, which is different from a stored result that failed validation.

Source comparison​

Oyzu keeps a source inventory per captured context in the cache history. sourceChanges compares the previous build's file identities with the current ones under the action's read scope (or the whole target scope), including added and removed files.

  • Exact reads are labeled reads-source, approximate bounds bounded-read, and unmodeled relationships scope-input.
  • sourceChanges.status is available, unavailable or scope-changed. Oyzu never guesses file names when the inventory is missing or the boundary changed.
  • These inventories follow the history rules: --no-cache writes none, and cache clear removes them.
  • Windows has no confined actions, but captured whole-scope comparison works. Native builds without captured context explain at target level only.

oyzu cache explain <target>​

Reads the key history for a target ID (its group key and every recorded action) or one action ID such as api:build. For each it shows the latest key, the runs that first and last used it, whether a result is stored and the first component that differs from the previous key. It reads no project and runs nothing, so it works between builds and on another checkout that shares the store. An unknown name exits non-zero with no key history for <name> in this cache.

A build cached only as a whole target records that target ID. If its builder supplies no bounded action contract, use the target ID rather than an action ID; whole-target caching does not create per-action history.

Inputs and what invalidates a target​

Every builder operation declares source reads, an explicit unbounded reason, or explicit upstream-only output consumption. A bounded captured stage keys on its declared read selection. Native source selection also conservatively includes unowned workspace entries. Configuration, tool and prepared-input identities remain separate key components. A directory read includes its listing: adding a source or test file changes the key. An unbounded stage retains the whole-target source key for identity and explanation. On the native path, incomplete reads prevent reuse rather than enabling a coarse fallback.

Analyzed native builders include Rust and Zig. Zig's format-check declares fixed .zig/.zon file reads and recursive directory listings. Its build and test stages remain unbounded because build.zig and runtime tests can read arbitrary files without a complete tool-reported read set. See Zig stage reads. Zig opts its fixed-read formatter into a private workspace with no retained files and order-only build/test edges, allowing independent formatter reuse. Build and test retain whole-target source keys for explanation, but their incomplete native reads prevent result reuse.

A whole-target source key covers captured project files, not arbitrary files outside the project. Native configuration and scripts can read such files even when a builder does not declare them. When diagnosing suspected stale reuse, compare the edited build with oyzu build --no-cache; matching source keys alone do not establish that an external native input stayed unchanged. Native stages with incomplete reads execute again instead of restoring a result; see native external reads.

The Helm plugin also declares per-stage chart read bounds, including conservative chart and formatter scan trees and specific reasons for image bindings and helm-unittest suites. Its captured execution path retains whole-target caching; declaring reads alone does not admit individual stages to the action cache.

An admitted upstream_only export reads no source files. Its key uses its own definition, tool/configuration identity and declared upstream output digests, without the target source scope or implicit source inputs. Native admission requires complete observations or fixed command semantics; an empty read list alone never authorizes this. Native Rust binary exports use core-admitted typed copies from the producer's indexed binaries, with stable export paths in each fresh private workspace. Equal producer bytes therefore give equal export output identities despite per-run temporary allocations. Later unconfined checks retain their conservative dependency edges, including the export.

Older published plugins may omit this declaration. Oyzu accepts their results and treats each undeclared operation as unbounded, with the reason plugin <reference> <version> declared no reads. The build reports it once the plugin answers, with one PLUGIN_READS_UNDECLARED warning per plugin per build that asks you to update the plugin. oyzu build --plan never invokes a builder. Its Why column (JSON sourceReason) describes stage contracts recorded in that target's last retained build plan, across current, legacy and historical bundles. Reasons are language-neutral and marked as facts from the last build; they do not establish current source completeness or cache admission. Stages without a recorded contract say reported when the builder answers. A later build of another target does not replace this target's recorded reasons. These operations retain whole-target key definitions; native stages still require complete read admission before reuse. The SDK and conformance suite require declarations from new and updated plugins.

Read-only preview distinguishes a stage without a retained declaration from a plugin that answered without one in the last build. The former says reported when the builder answers; the latter names the plugin and missing stage contract as a fact from the last build. Node lifecycle fallbacks name arbitrary project/package reads, while script-free single-root npm installs can declare their manifest, lock and manager controls. Rust's final declarations come from Cargo read facts, with specific reasons when native inputs cannot be bounded. These explanations do not relax confinement or native-observation requirements.

Host paths, run IDs, timestamps, credentials and the number of parallel jobs never enter a key. A serial build, a --jobs N build and a host with a different core count share hits, and so do different checkouts, worktrees and branches.

Changing one target's inputs re-runs exactly that target. One thing to know: execution-only settings such as --full are part of the configuration digest, so changing them re-keys every action.

Prepared dependency identity excludes whole-source provenance, version decision evidence and the frozen plugin planner request/answer. The frozen action definition still keys version-bearing arguments and OYZU_VERSION; source reads have their own key component. Dependency locks, manager/tool identities and prepared content remain in the dependency identity. A changed lock or prepared payload therefore remains a prepared-dependency cause in oyzu cache explain.

This exclusion does not remove a version written into a prepared file: those bytes remain prepared content. Its bounded captured stages use their admitted read contracts; a root README outside those reads can change without invalidating the shipping actions. A README inside the chart ships unless .helmignore excludes it, so editing it normally invalidates the build.

Prepared capture can record source provenance using the copy roots supplied by preparation. A nonempty regular file is copied source only when its prepared root-relative path maps to the same source root-relative path, and its captured bytes, size and executable mode match. Empty files, dependency locks, files outside the declared roots and rewritten files (including stamped chart metadata) remain generated. Equal names or bytes elsewhere never establish a copy coordinate. Helm keeps dependency-build charts/ directories acquired, including committed subcharts reproduced byte-for-byte. If preparation has no workspace-relative source inventory, it declares no copied files rather than using target-relative coordinates that could hide a nested chart's templates.

Provenance is computed from inventories already produced during capture and is stored with the dependency record. Reuse reads that record; it adds no prepared tree scan or source-byte hashing. Planning decodes it once per prepared target. If an action hides no copied files, it retains its ordinary dependency input and mount: no extra file list, view, rehash or copy is introduced.

When a confined captured action must hide a copy outside its source reads, dependency identity covers the generated/acquired entries and all (prepared path, source path) names. Visible copied bytes and modes remain in the bound physical view digest. Each action carries hidden-copy paths and a digest reference to a shared table of read-copy diagnostics, not an inventory per action; an explicit prepared-file selection still applies. Opening a filtered view verifies its selected content, copies it and verifies the resulting tree, even with --no-cache. This cost applies only to actions that actually hide copies (or already request an explicit prepared-file view). Upstream-only actions that consume prepared resources retain the whole prepared input and its whole-content identity. An empty source-read set does not mean those actions can run with copied files removed from their dependency payload.

oyzu cache explain lists copied source paths as added, removed or changed, showing up to three and an and N more count. Whole prepared inputs, including upstream-only staging, also separate verified copies from generated dependencies in the explanation: for example, copied source chart/templates/pod.yaml changed (whole prepared input). This diagnostic split uses the captured inventory once per target; it does not narrow the input, materialize a view, or change its key. Locks, acquired files and rewritten bytes still report prepared dependencies. Unbounded actions, native host actions and prepared trees containing links retain whole-tree behavior. Native observed reads do not yet map prepared copies back to source coordinates.

  • A restored native target keeps its materialization receipts, and promoted local binaries (.oyzu/bin) are refreshed from the restored artifact as after a run.
  • Eligible native host targets try configured remote whole-target results before executing individual actions. Incomplete native stages prevent that shortcut. Per-action cache workspaces are selected once for the target; a target without a private root uses whole-target caching.
  • Profile-dependent shared-cache writers (Rust and .NET) produce both development and optimized compile stages when the selected output is optimized. A plain reader looks up compile-development; an optimized reader looks up compile-optimized. Each stage records its actual profile and never substitutes the other profile's binaries. Both use one preparation and build plan. Rust uses host-native stages; .NET uses captured stages with separate Debug and Release commands and requires a compatible package declaring dotnet-compile-stages. Profile-independent builders (Java/Maven/Gradle/Ant, Go, Zig, Node and Python) keep one entry.
  • Stage reuse also requires matching admitted tool environments and computation settings. Full CI writers and plain readers can still differ in those inputs, even when their compile profiles match. Publishing both profiles does not by itself guarantee a shared-cache hit.
  • Rust test, lint and format stages use declared Cargo manifests and locks, without consuming final binary exports. Their applied profile reflects the actual native command: Cargo's development/test profile for checks, independently of the exported binary's profile.
  • Final native compilation applies inferred controls only for that operation, validates them around Cargo, then restores and revalidates declared controls before later checks. This also applies when hooks require stages to share one workspace. A failed native guard remains a failure after restoration; restoring controls never legitimizes a changed manifest or lock.
  • Rust compile-stage keys bind declared Cargo versions. Plain local development readers export the declared-version compile result directly, recording compiledVersion separately from the inferred artifact version. Stamped paths (full, CI, optimized, shared-cache writer, packaged, handed-off and release) require a separate final Cargo stage binding the inferred version map and projected manifests/lock. Development results cannot satisfy that stage or stamped packaging/publication gates. The final projection is absent from compile-stage payloads. The engine-injected OYZU_VERSION default (inferred or tagged) is not passed to host compile, test, lint and format-check commands, so env!("OYZU_VERSION") fails to compile there and option_env! is unset; use CARGO_PKG_VERSION. The final stage still receives it. Explicit environment values remain keyed (oyzu#2364). Stage restores do not transfer Cargo compiler state; the final stage can still recompile affected crates.
  • Conventional native Rust stages have independent results. Adding --full to an unchanged development build may reuse compilation, but also requires the inferred-version final stage and selected checks, and a repeat full build may restore bounded checks with their original reports and compiler warnings (labeled as reused). Arbitrary tests always execute and produce fresh required reports. A compile that succeeded stays reusable if a later check fails. Stdout and stderr logs stay available after reuse.
  • Rust test stages can reuse individual test executables. See test-unit evidence for keys, reports and the native runtime-read limit.
  • Builders can opt individual native stages into private source copies by declaring a finite output-file handoff. Core admits private execution when outputs are bounded and producers are admitted. An observed or fixed native read basis separately enables narrow keying. Source-free exports use upstream_only and retain their producer dependencies. A private copy still contains the full target; narrow keys require the separate native read admission described below. This is host execution, not a sandbox.
  • Private branches start from the frozen pre-run source projection plus the finite outputs of their admitted producers. They never copy later shared-stage changes, even inside their declared reads. The prepared source projection stays immutable while shared stages and deferred cache restores use a separate retained execution root. Private branches are populated only on execution and carry the projection's admitted digests without hashing copied source again. Reused private stages do not populate their forks; reused producer bytes are handed off only when a consumer executes. Producer files come from their executed fork or verified cached bytes, not from the live shared root.
  • Native artifacts are collected from the workspace of their declared producing stage, including shared execution roots beside private checks.
  • A target can mix private and shared stages. Cached shared-stage changes are captured from and restored into the shared execution root. If a later stage fails, retrying can reuse a successful producer and restore its files before the consumer executes, without changing the source of later private forks. Editing a check's declared reads reruns that check. Shared, unconfined native actions follow every dependsOn edge, including order-only edges. Private branches retain the existing order-only non-observation rule and follow real producer dependencies.
  • Cargo declares these neutral facts for its host stages and indexed binary exports. Compilation and Clippy need complete observations before reusing results; rustfmt uses its fixed tool rule. The separately lowered test has no complete native read basis. Its unbounded outputs keep it on the shared execution path with AlwaysRun; unit results require the explicit native Rust trust opt-in described below. By default, it retains conservative action configuration and whole-target source identity. Hooks, task replacements and materialized inputs keep their separate restrictions. Maven and Gradle formatter admission additionally requires their plugin's fixed-read declarations; a private-stage request alone grants no reusable key. Native compile, test and package stages cannot fall back to whole-target reuse when their read or output contracts do not qualify.
  • A fixed-read formatter can reuse independently of unbounded build and test stages when its builder opts into a private workspace. Its default pipeline edges are order-only; explicit data dependencies still invalidate it when their outputs change. An unrelated file edit can still change inferred version or whole-target projection identity and cause a conservative miss. The same mechanism admits Go build and vet with complete observed reads and gofmt with fixed reads once their plugin opts in. A successful completion binds its own complete observation before publication, so the next unchanged build can reuse that narrow result.
  • Admitted test-unit plans can expose independent results; see test-unit evidence. Unit reuse remains subject to the stage's native read and cache admission.
  • Cargo integration-test scratch is removed before native compiler cache retention, even under budget. Compiler state remains available for incremental work, and action results retain their normal reuse rules.
  • The pinned tools must include the selected check helpers. An incomplete lock reports TOOL_LOCK_STALE; run oyzu pin and retry.

Test-unit evidence​

Oyzu's own main CI keeps test-result reuse disabled pending independent OVH execution-binding security acceptance. Main executes the full suite with cache reuse disabled, including when using an older released driver. The guarded consumer additionally refuses whole-target, whole-test-stage and per-case hits that would bypass unit admission. Ordinary project caching keeps the rules below. The CLI captures this policy once for Oyzu's own main, scheduled and release jobs and retains it for that invocation. The private build worker captures it from GITHUB_* at startup. The library's build::run convenience entry also captures this policy when it creates build options. Lower-level library cache operations use explicit invocation inputs, including the consumer checkout used for ancestry; ambient CI variables do not change their test-reuse policy or the behavior of unit-test fixtures. Remote-write trust separately reads CI variables, including GITHUB_*, by design to restrict cache publication to trusted pushes.

After security acceptance, the guarded path requires an original signed actual execution from a main-push or main-line nightly run, within 24 hours of startedAt, plus fresh independent mismatch state. The execution commit must be an ancestor of both the consumer checkout and its fetched origin/main; missing history runs the tests. Execution and mismatch-state keys have separate purposes. A controller nonce binds state to the current journal view, so an older clean state cannot override a later mismatch within the same attempt. The host supplies state and nonce through a read-only /run/oyzu mount. PR, dev, manual, failed, cancelled and stale evidence cannot satisfy it. Every required unit is validated before any reuse; an input or evidence mismatch runs the full enclosing suite. Reuse preserves the original execution receipt under sourceRecord.ovhExecution and never refreshes its age. Missing evidence, offline state or unavailable trust data causes execution. Main admission refuses trust-native-test-reads keys even when local or user configuration enables package trust. It requires captured bounded reads or a key covering the whole target scope. There is no user setting that can enable this internal policy. Exact-commit green main CI and the full native Windows release-like suite remain release gates.

A plugin can declare native test units through the optional test-unit plan. Captured Python package tests use one pytest file per unit and can select cases inside a changed file; see Python cases inside a bounded unit. Rust stages declare Cargo test executables as units and preserve native coverage and fresh doctest reporting during finalization. Cargo-supplied companion executables (CARGO_BIN_EXE_*) are keyed by variable name and digest.

Core owns unit keys, lookup and passing-result storage. A failed unit is never stored. The native adapter prepares its inventory, runs the selected units and combines fresh and reused evidence into the operation's existing required reports. Cancelled preparation preserves the executor's cancellation status and stops before unit execution or report finalization. An unbounded AlwaysRun stage does not gain reusable result storage merely by exposing a unit plan.

An enclosing stage with unbounded outputs still runs on every invocation. Its test units may reuse results independently only when core admits the stage's frozen tool, dependency, environment, materialized-input and predecessor facts and enforces each unit's bounded runtime view, or the native Rust trust opt-in below explicitly admits package-file reads. This does not admit a reusable whole-stage result. Missing predecessor or materialized-input bindings keep the ordinary stage path. Under an unbounded stage, units without proven runtime bounds run without reuse.

A newly stored test-unit result also records the producing run's wall time in milliseconds (durationMs) as optional timing history for later shard planning. Readers that don't know the field ignore it, and a missing or malformed value means no history; it never affects keys, reuse or result validity.

Test-unit execution stays sequential by default. OYZU_TEST_SHARDS=N explicitly requests concurrent shards when N is an integer above one. The effective count is at most the unit count, four, and the worker CPU budget divided by the existing per-step CPU allocation (with a minimum of one). Each shard retains that CPU allocation. A diagnostic reports any reduction from the requested count; an invalid value runs sequentially. This override never changes cache keys.

Concurrency requires every unit to have an enforced, private confined runtime view. If any unit lacks one, including units with unbounded outputs, the entire step runs sequentially in manifest order using the ordinary workspace for non-confined units, preserving hard-link aliases and in-place writes. Main-CI governed runs remain sequential. Shard view storage is created beside the actual execution workspace, including temporary native-tool-control workspaces. Confined views copy their files, without hard links to the workspace. Creation failures are reported without falling back to a different filesystem. Results and failure selection retain manifest order; the step's duration measures elapsed wall time across preparation, units and finalization.

Cargo integration-test targets (kind = "test") retain a conservative runtime contract: Cargo target metadata does not establish their complete runtime reads or nested helper compilation and writes. They use the ordinary test stage's admitted workspace, tools, materializations and scratch, retaining whole-source and upstream key inputs. Without the native trust opt-in below, they are not independently stored or reused under an unbounded enclosing stage. Captured library and binary unit tests keep their bounded runtime contracts and remain eligible for independent reuse. Declared inputs add reads; they do not establish a missing integration-test write closure.

The combined report retains each unit's contribution. Summary totals put cases from executed units under Tests run now and reused cases under Reused test evidence, marked not run now. JSON build reports retain each contribution in reports[].summary.units. Invocation summaries (oyzu history <id> --json) use tests.fresh and tests.reused for the same counts. Even when all units reuse results, the action still executes preparation and finalization. It counts in actions.succeededNow; only whole-action reuse counts in actions.reused.

Each unit's key includes the stage's non-source inputs, the native artifact's digest, its runtime-read digest and the declared companion executable digests. Runtime reads narrow the key only when the captured-path view enforces them. Declared inputs widen reads without enforcing a boundary. Runtime listing selectors conservatively include the selected directory's contents in unit keys and views. Captured unit views also include preparation's finite version-control inputs. Core checks their original identities against the admitted source and their projected identities against the private workspace. Keys cover the actual projected bytes and observed absence; the worker's version-control guard remains binding inside the unit view. These paths are resolved from the prepared context root, independently of an individual test's working directory. On the native host path, runtime reads remain unbounded. By default, unbounded Rust test stages do not reuse unit results. oyzu cache explain <target> records the refusal and names cache.trustNativeTestReads.

To opt in, set this in project, user or local oyzu.toml:

[cache]
trustNativeTestReads = true

This explicitly trusts native Rust tests to read only the owning crate's full Cargo package file set, its resolved local dependency package files, and the declared environment. Cargo's package include/exclude rules apply; tests/, fixtures, build.rs and README files participate when packaged. Undeclared host files, excluded files, network state and undeclared environment are outside this trust contract. Policy can lock the setting to false; profiles cannot grant it. It does not enforce isolation or relax acquisition or report validation.

A Rust adapter supplying Cargo package identities is required. Each unit key binds its package closure and lockfile, compiled test executable, companion executables, declared environment, toolchain and prepared dependencies. An unchanged repeat can reuse every successful unit; a packaged fixture edit reruns the owning crate and units depending on it. Unrelated builds retain their keys when their admitted environment and stage definition remain unchanged. A shared workspace stage can invalidate multiple crates when those common facts change. For example, a library test and an independent integration test in the same crate both rerun after a packaged README or source edit: their admitted package file identity changes even if an executable's bytes stay identical. An unchanged repeat can report 0 ran, 2 reused (trusted native reads).

To check selective reuse, use independent Cargo packages declared as separate builds with no local dependency between them. Run oyzu build --full twice with native-read trust enabled, then edit a packaged source file in one package and repeat. The unchanged run should reuse both test units; the edit should rerun only the edited package's unit. Keep required doctests and coverage enabled: reused executable results do not replace those report obligations. On MSVC targets, instrumented test compilation requests reproducible linking (/Brepro) and disables incremental codegen for those instrumented tests so clean builds can retain the same executable identity. Executable digests remain mandatory; this does not make Rust outputs portable across paths. Only unit reports are restored. Finalization still combines JUnit and coverage and runs required doctests. Receipts and cache explanations name trust-native-test-reads; human build output identifies reused trusted native reads. Hooks always run; authored tasks still require complete reads of their own command. Native test-read trust does not admit an authored replacement's reads.

The isolated execution path continues to require its enforced runtime views. Without an individually enforced view or explicit native trust admission, unbounded unit keys retain whole-target source and upstream output identities. Executor support alone does not narrow an unbounded or nonconfinable unit. Per-run inventory paths and coverage environment are not bounded key inputs.

Targets with hooks or authored tasks follow their complete-read reuse rules. Their outputs are never narrowed to unit identities. If per-action cache facts are unavailable, the ordinary test stage runs instead. The native inventory determines what runs: undeclared units execute without reuse, known units retain their own entries, and missing predicted units do not fail an otherwise valid native inventory.

The existing test action row shows N ran, M reused, including in redirected and no-color output. Its JSON action record lists units, each with name, key and outcome (ran, reused or failed). An operation without a unit plan retains its existing whole-stage behavior.

Trust model and its limit​

The cache trusts the declared target graph, like --affected. An action that reads another target's directory without a declared edge is invisible to the key. For example, if api and web copy ../shared but declare no relationship to it, editing shared/ reuses their old results, while oyzu build --no-cache rebuilds them. Native cross-root dependency discovery isn't implemented. Declare relationships in build.yaml (depends_on: [shared]), or use --no-cache, for builds that read across target directories.

Per-action reuse​

If an action carries a stage contract that Oyzu cannot decode, external-input admission and cache key computation reject it with the action ID and decoding reason. Oyzu never treats that contract as absent or keys the action without its declared inputs. Correct the contract in the producing builder before retrying.

Native ancestor-file inputs are resolved from the canonical target directory, including targets reached through directory symlinks. If an ancestor cannot be keyed (for example, it is a directory, a symlink or larger than 4 MiB), native execution continues without cache reuse. ANCESTOR_INPUT_UNKEYABLE reports the action and cause as a warning, also retained in the build manifest's diagnostics when no invocation logger is supplied.

Planning attaches a stage contract to each action of an analyzed target: the reads, writes, environment names and tools the static analysis found for the stage, the actions it follows, and whether its outputs are bounded. A target whose actions all have a contract is reused action by action. Captured node/package and node/app operations use these contracts when the final command matches the analyzed script or builder-owned command. Ordinary SDK-style dotnet/sdk projects also declare stage reads on the captured path. See .NET stage reads for the SDK audit, resolved-package checks and conservative MSBuild fallbacks. Captured .NET targets cannot see ancestor configuration files above their target folder; future native admission must treat those files as unbounded until covered by read evidence. Fixed core-owned stages can supply a contract alongside analyzed builder stages. Docker also declares per-stage reads for its captured operations. Projection-aware caching and captured version rebinding require a supporting core release before the updated Docker plugin. Source projections retain conservative version scope, and copied source in prepared dependencies can still prevent reuse after an unread edit. Host-coordinated image workers remain excluded from caching.

Core prepared-input staging​

Core's prepare-dependencies action can carry a source-free stage contract when its provider declares every destination written by its fixed staging command. Version finalization after hooks​

On captured Node targets, Oyzu moves the version action after the followed pre_build hooks, so nothing that writes the version runs before them:

  1. Planning records every action in plan.json with the pre-hook source version (the version scope without the hook's script). The target record carries extensions["oyzu.dev/version-finalization"]. The actions before the hook run with the pre-hook version.
  2. When the hooks succeed, the files under their declared outputs are digested from the workspace (so --no-cache gives the same result) and folded into the version. The target is planned again, and the remaining actions run from that post-hook plan, written to plans/<target>.post-hooks.json. plan.json itself isn't changed.
  3. The manifest's target record is the post-hook one. manifest.extensions["oyzu.dev/version-finalization"].<target> gives preHookVersion, version, hookOutputs, planPath and planDigest.

A hook edit that changes what it writes changes the version and the package. A script stays in the version scope if it isn't named as an argument of the hook's command (for example run = "node hook.mjs" through a shell) or if a builder stage reads or writes it. Other builders, other hook phases and the native host path aren't finalized. Effects outside the workspace (network, global state) are invisible to Oyzu, so declare them away yourself.

Authored tasks cached on request​

An authored task or task override isn't cached by default, because Oyzu can't see its effects. Request reuse with the cache and outputs task fields:

[tasks."api:test"]
run = "node --test"
cache = true

Reuse requires complete reads of the authored action itself. On Linux, ordinary native Node application/package builds can select the existing crun boundary for an authored task without making the whole build isolated. Oyzu freezes selected target source and bounded predecessor outputs, retains the locked native Node payload, and probes it against an admitted Linux runtime root before lookup. The action sees those identified bytes read-only, empty private output/report and temporary roots, and no host home, package cache, network or general proc/sys view. The closed startup allowance remains subject to the ambient output-independence rule. cache = true asserts that clocks, entropy and permitted startup values do not influence retained outputs; the boundary does not detect semantic nondeterminism.

The first native slice supports the retained Node command and an equivalent runtime-root sh/bash, literal directory output roots, and the existing Node report adapters. A shell is admitted only when its selected native bytes match the identified runtime shell. File/glob output allocation, other tool payloads, worker plugins and unbounded dependency/generated trees have no native binding in this slice. Their optional boundary is unavailable; they execute ordinarily with NATIVE_AUTHORED_BOUNDARY_UNAVAILABLE and remain nonreusable. Windows and macOS have no native authored backend and follow that same explained-rerun rule. Offline admission requires an already unpacked runtime root and retained tools. Captured Node targets also retain oyzu build --isolated --no-docker support.

Removing cache = true does not relax separately required isolation or policy controls.

Ignored .env and local configuration remain hidden; supported explicit source inputs can admit nonsecret ignored files, subject to fixed exclusions and containment. The live checkout is never a fallback. Declared bounded hook outputs are frozen only after their writers retire, and their consumed bytes enter the key.

Confined actions and narrow keys​

A narrow key is only sound if the action can't see anything the key left out. So Oyzu keys a captured action on the files its contract reads only when the action also runs confined to them. This needs the captured path and a Unix host. Linux is tested. macOS isn't supported yet. Windows doesn't support captured confinement. Native stages on every host instead require complete fixed or observed reads; incomplete native stages run every time.

  • One unbounded unknown keeps the whole stage on the whole-target key, unconfined.

Checks that run at once​

The check stages of one target (test, lint, format-check, scheduled by --full or CI) don't produce anything another check consumes, so the plan marks the edge between two consecutive checks as order-only. A hook between them, or a declared depends_on, keeps the edge a real dependency.

When build.jobs is above 1, a check starts as soon as what it really needs (for example build) has finished, beside the checks ordered before it, if all of these hold:

  • the check runs confined (and --verify-contract isn't set);
  • every action of its target already running is a confined check;
  • no two of them declare writes that could meet (a glob counts as its literal folder).

Otherwise it waits its turn. Serial and parallel runs give the same keys and outputs:

Behavior
ViewA check's view leaves out what the checks ordered before it left, and checks that may overlap get copied files instead of hard links, so one check's in-place write can't reach another.

FailureA failed check doesn't block the next check. It still blocks package and everything after it.

Development versions and test files​

Version narrowing follows the execution admission: all selected actions must have contracts, and every shipping action must actually run confined. Non-check steps that can feed shipping reads join the version read closure. Source-free shipping exports also include their transitive producers. Every omitted check needs a complete write bound proving its effects cannot feed shipping. Unconfined checks are checked against their observed workspace changes when the target has a narrowed version scope; a write outside the declared bound fails that build, including when cache storage is disabled. Whole-target version scopes retain ordinary check behavior. An unbounded generator therefore retains the whole-target version even if build and package are bounded. Prepared charts retain their native version; runtime staging projects the final version. Narrowed reuse also requires dependency views that hide unselected prepared files; narrowing source alone cannot hide copies in a dependency mount.

A development snapshot version (1.2.3-dev.g<digest>) is written into package.json by the version action, so it feeds every later action. Oyzu derives it from the target's source scope, minus files that only a quality stage (test, lint, format-check) is known to read exactly.

  • A test-only edit changes neither the version nor the artifact names. A new test file, which only a glob finds, does.
  • An unknown fact of a shipping stage (build, package) counts as reading its bound, or every file if it has none, so a test-only file that a computed import of build may reach stays in the version.
  • If several targets share the folder holding a file, the file is left out only if every one of them reads it only from a quality stage.
  • The script of a followed pre_build hook leaves its own target's scope, and what the hook wrote is folded in after it runs (version finalization).
  • For a captured target whose version-carrying commands (build, package, export, or artifact producers) are bounded, cacheable and confinable, the suffix uses the files those commands read, plus configuration, lock files and declared inputs. Unbounded quality stages retain their own whole-target keys without widening this suffix. This needs Unix view support and per-action eligibility, with the same confinement predicate used by execution. Targets with hooks, authored replacements, source projections, materialized inputs or cross-target prerequisites keep the wider scope. See version inference.
  • Captured Cargo builds retain the whole-target version scope. Preparation admits projected manifests, lock coordinates and Cargo metadata together; command-only version refinement cannot change those native facts. Executable test caching still applies, but an unread source edit can change the projected version and invalidate otherwise unchanged executables.
  • Tagged and history-derived versions don't change. The version reaches every action as OYZU_VERSION, except host Rust compile, test, lint and format-check stages, which use the declared Cargo versions. The core rebinds supported captured commands, native payloads and artifact paths with the decisions before computing keys, so an action that embeds the version still keys on the version it executes.
  • Textual rebinding requires the old core version's recorded per-build hash component. An unmarked plain version such as 1.0.0 keeps the whole-target version and plan, so equal dependency versions and path fragments remain untouched. oyzu cache explain and build --explain include this fallback reason. This diagnostic does not change the action key.

When a confined action reads something undeclared​

If a confined action fails and its output names a file that exists in the target but not in the view, the build reports the stage, the path, the missing fact and the smallest fix, in human, NO_COLOR and --json output (diagnostic confined-read-outside-contract, with details in manifest.extensions["oyzu.dev/contract-violations"]):

ERROR  api:build read extra.txt, which its stage contract does not declare, so the confined view hid it.
         Missing fact: reads-path extra.txt
         Fix: declare it as an input of api in build.yaml:  inputs: ["api/extra.txt"]
         (Or make the reference static so the analysis sees it.)

Declare the path as an input. The declaration is relative to build.yaml, while the read path is shown as the target's own files write it. --json carries the same declaration as fix.declare.inputs. Oyzu finds the file by scanning the action's output for paths, so a tool that fails without printing the path is reported only as a failed action. The builder's node --test stage also runs the spec reporter on stderr, so a test file that reads an undeclared file is explained like any other stage. The behavior is the same when targets run in parallel.

Native external reads​

Native execution can read host files outside the captured source tree. A whole-target source key does not track changes to those files. Native stages without complete admitted reads execute on every build, including Rust build scripts with external reads and arbitrary Node, Maven or Gradle lifecycle code. This applies on plain Linux as well as Windows and macOS. Native Python application preparation, assembly and packaging also run when their native read admission is incomplete. Captured Python preparation, upstream packaging and generated distribution-application assembly declare their own source-view contracts; requirements applications and authored application build tasks still run assembly with the whole target as its read set. Neither local nor remote whole-target entries can bypass this rule, including entries saved by an older CLI. --no-cache executes these stages too.

Independently bounded stages still reuse their results. Complete native reads retain stage and whole-target reuse where all other cache requirements hold. Restoring a check does not release dependent work while an earlier required parallel check is still pending; its success or failure remains a gate. Rerunning a native stage preserves its compiler's incremental cache: an unchanged Rust build can run Cargo without recompiling unchanged crates. --explain names the incomplete read admission; an unchanged source digest alone does not prove that native inputs are unchanged.

For Rust, missing active build-script records and unassessed proc-macro reads remain incomplete even when the compiler and linker are pinned. Tool identity binds the selected tool; it does not establish which other files a build script or macro can read. oyzu build <target> --explain reports these refusals separately from a changed toolchain key.

Host Cargo finalize keys include the final package versions, compilation identity, and the digest of each projected manifest and lockfile in the native build command. Narrowing the source key to observed reads retains those command inputs: changing any projected control changes the final action key even when dep-info is unchanged. Finalize observes the shared compiler target with final metadata. Earlier declared-version dep-info can widen the observed source set, but cannot replace the keyed final controls. Missing observations or reads outside the prediction prevent publication; editing an observed source invalidates the final result. With complete native read admission and unchanged keyed inputs, finalize can reuse its result whether lint and compilation executed or reused their results. Its key retains the compiler, plugin, dependency and environment identities alongside source reads and projected controls. The target source digest alone cannot admit a native result with incomplete reads, because files outside that target can still affect Cargo or its build scripts.

A build-script record restored from earlier compiler state can name a file in a toolchain install that is no longer on this machine. Planning does not count that vanished path as an uncovered read, because Cargo re-runs the script for this build. Observation after the build never ignores it: a vanished path recorded by a stage with no executed-script list (such as lint), or any other path outside the source root keeps the stage always-run.

A build-script or dep-info record that names a file in another install that still exists is covered only when the file is a regular, non-symlinked file in that install's payload and has exactly the same bytes as the same relative file in the active sysroot, which the toolchain identity already binds. A differing, missing, symlinked or ..-escaping file keeps the stage always-run. Only the file the record names is compared; other files the script reads in that install are not, the same limit the active sysroot has. Restored dep-info can retain absolute paths to compiler libraries used by proc macros. It uses the same verification as build-script records before a complete compile or lint observation can be saved; a matching install-shaped path alone does not authorize reuse.

A record can also name a file in an earlier run's private copy of the checkout (<checkout>/.oyzu/native/host-actions/<hash>/...). That copy was the source snapshot, so the read maps to the same relative path of the current source, but only when the old copy is gone (Cargo then re-runs the script) or the file there (or, for a watched directory, its whole tree: same entries, no links, bounded) has exactly the current bytes. A surviving copy with different bytes, a nested copy, a .oyzu remainder, a lookalike elsewhere or a .. escape stays an uncovered read.

Inferred test-input bounds​

Rust library and binary test units infer a runtime bound from their package folder. On Linux crun (oyzu build --full --isolated --no-docker), a fixture beside the package is visible and participates in its test-unit key without an inputs declaration. An edit inside that bound reruns the unit; an edit outside it preserves reuse when its executable and other keyed inputs are unchanged. Dependency and build-output directories are excluded from the source bound; prepared dependencies and compiled artifacts retain their own identities.

The bound also includes ancestor Cargo manifests, lockfiles, toolchain pins and Cargo configuration, plus package and ancestor .config/nextest.toml locations. The framework layer extracts no extra paths from nextest configuration contents. Ordinary and raw relative path strings reaching outside the package can add workspace files with over-approximate confidence. Detection reads configuration and source bytes; it does not execute project code. Computed paths, including env!("CARGO_MANIFEST_DIR") joined with .., need inputs when they reach beyond the detected bound.

oyzu build --plan lists static package candidates under Test input bounds, with a Why column identifying convention, shared configuration, framework configuration, literal paths and exclusions. Cargo resolves actual executable units during preparation; unexpanded workspace member patterns are labelled unresolved in the preview. An unparseable nextest configuration retains its known paths, the package folder and other detected inputs, and adds a plan note. Fixing that configuration changes the keyed input. Native framework validation still applies when the tests run.

Source-read failures (including non-UTF-8 Rust source), unsupported string tokens and paths that cannot safely be represented leave that package unbounded with a named reason; they do not fail planning for other packages. This includes glob-character literals, overlaps with excluded output, and ../ literals that leave the workspace. An outside literal never grants access beyond the captured workspace. The preview shows the fallback reason in its note.

Integration tests and doctests retain their conservative contracts. Native host runs gain no confinement or complete-read guarantee from the inferred bound; Windows keeps rerunning these tests and macOS is unsupported. A confined test that reads outside its bound still fails. When its output prints the missing path, Oyzu reports confined-read-outside-contract with the exact target-level inputs declaration below. The sandbox hides undeclared files even when a test tolerates their absence.

Pure-Go package test units also infer their package folder, including testdata and embed discovery membership. Their bounds retain ancestor go.mod, go.sum, go.work and go.work.sum locations, workspace vendor trees, and native EmbedFiles, TestEmbedFiles and XTestEmbedFiles. Ordinary and raw parent-path strings in selected test and production GoFiles, including reachable checkout helpers, widen the bound within the workspace; literal os.Getenv and os.LookupEnv names join the keyed environment. Bare parent elements in joins, such as filepath.Join("..", "shared", "x.json"), use the same parent-path rule and retain refusal when that bound is unsafe. Absolute literals retain refusal on every planning host, including uncertain route-like strings such as /healthz; detection never probes the host filesystem to distinguish routes from files. Windows drive-rooted and backslash-rooted paths also retain refusal. URLs and colon data such as k:v add no filesystem evidence. Changing, adding or deleting a fixture invalidates every unit whose bound contains that path. Independent sibling package bounds can retain reuse.

On the captured pure-Go lane, preparation compiles each test executable once. Execution runs that admitted executable in its package directory through Go's test2json, retaining case filters, retries, JUnit and coverage reports. Each executable invocation uses Go's default 10-minute timeout. The current test-unit contract has no configurable timeout field. Core hashes the executable, its package-directory metadata and prepared manifest as generated runtime artifacts. Prepared package executions must leave workspace bytes and membership unchanged; workspace writes fail before a successful attempt is reported. Write temporary test files through Go's t.TempDir or the sandbox's scratch directory instead. This is a confined runtime contract, not a claim that go list -test observes runtime I/O. Native host tests remain unbounded. The static plan shows source package candidates and their inferred layers; native package identities, selected sources, workspace/vendor/embed facts and flags remain unresolved until preparation. The preview never runs Go or project code and supplies no cache-admission authority.

Missing package/source facts, unsafe source links, unsupported strings, outside-workspace or excluded-output literals, computed environment lookups, cgo and unsupported flags retain conservative execution. A package whose detector refuses a bound also refuses test-result reuse; a healthy sibling can remain bounded. The admitted flag subset is empty GOFLAGS or combinations of -mod=readonly, -mod=vendor and -p=2. Computed file paths within the confined view work normally; paths beyond that view require the existing target inputs. Custom subprocesses retain the complete existing tool/environment identity rather than claiming a complete statically detected tool list. Static scanning is limited to native checkout source inventories: missing nonstandard helper sources, runtime imports (including runtime.Caller roots), and aliased or dot-imported os retain refusal rather than infer their reads.

Declared inputs​

A target's inputs in build.yaml name extra source paths it reads (files or folders, relative to build.yaml; see target workspaces). On captured and bounded native paths each one:

  • joins the target's source scope, so the whole-target key and the development version cover it;
  • joins the reads of every stage contract of the target, so a confined action sees it and its narrow key covers it. A target-level input re-keys test too when the file changes, even if only build reads it;
  • only adds. It never removes an inferred read, and it never makes an action confinable.

An input that leaves the workspace (the folder holding build.yaml) or names no captured file is a CONFIG_INVALID_VALUE error before anything runs, so a typo can't silently declare nothing. Globs aren't accepted. A folder covers everything beneath it. --affected doesn't yet treat a change under another target's declared input as affecting the declaring target.

Go source-read coverage​

The Go builder predicts conventional native build and vet reads from preparation's Go package file lists and writes observed-read reports after successful execution. format-check uses fixed gofmt rules, content globs and directory listings. Native runtime tests and authored build invocations stay unbounded. Incomplete package facts, overlays, cgo headers and unsupported embed discovery retain explicit fallbacks. Conventional native contracts must cover core's prepared file and listing facts; missing coverage is rejected. A main-module manifest outside the target root makes prediction incomplete. Conventional build and vet also require matching resolved task environments before sharing frozen predictions. Conventional native builds use -buildvcs=false; Git commits do not add compiler stamping reads. The compiler output path is stable and its injected version default is omitted. The final export alone carries the inferred version in its filename and receipt. Complete native reads allow build, vet and format-check reuse across unread README content edits. Captured per-package actions keep confined reads; source-free exports and grouping gates use upstream_only.

Native Java source reads​

The Java builder declares the default Maven and Gradle format-check file inventory: each selected Java file and each scanned directory's listing. google-java-format's fixed explicit-file rule establishes this boundary. Existing documentation-file content edits do not change those reads; Java source edits and new source files do. Configuration, declared inputs, command definitions and producer results also contribute to the complete key.

Native Maven verify includes runtime tests and lifecycle plugins without a complete read report, so it stays unbounded. Gradle configuration scripts and Ant build files are programs whose complete reads are not reported. Runtime tests and Checkstyle retain specific unbounded reasons. Captured Gradle and Ant exports consume their producer's archives; Maven packaging reads its explicit POM and archive copy inputs and depends on its build producer.

Native Maven and Gradle formatting uses a private stage with no retained outputs and order-only lifecycle edges. Private execution alone does not admit narrow keys. Inferred versions or whole-target projection identity can still cause conservative misses after an unread edit. Unbounded lifecycle and lint outputs prevent whole-target restoration, so unchanged builds can still rerun those stages. Fast builds also rerun an unbounded lifecycle when format and lint are omitted: dropping those checks does not make the lifecycle safe to cache. Native whole-target lookup and remote fetching cannot bypass the stage's output bounds, including entries saved by an older CLI. Captured execution is unchanged.

oyzu build --explain identifies the stage and its incomplete read report. The stage stays uncached until the builder can establish complete reads and bounded outputs. Adding declared inputs covers those files but cannot bound arbitrary runtime reads by tests, plugins or build scripts. --no-cache also executes the lifecycle; required tests and reports apply in both cases.

Use a Java plugin that supplies these declarations and a CLI with compatible private native-stage support. Older plugin declarations do not acquire complete reads by running on a newer CLI. See Maven, Gradle, Ant and Java quality.

Native host read admission​

A builder's source contract can declare native_reads: {kind: observed} or native_reads: {kind: fixed, rule: "…"}. Omission prevents native stage reuse. Fixed admission names the tool rule that establishes the complete boundary; a prediction alone is insufficient.

When a builder supplies bounded source predictions but omits native read admission, --explain says it declares source read predictions but no complete native read observation or fixed read rule. Native Helm packaging and archive normalization use this conservative refusal: their predictions exist and retain home, but neither stage declares complete native reads or stores a reusable native result.

Native lifecycle programs can read external files through tests, scripts, plugins or child processes. A whole-source digest covers captured source; it cannot detect changes to files outside that boundary. Declared paths and tool identities establish known inputs but do not prove a lifecycle's reads are complete. A private working directory or read-only root also does not establish complete observations of every mounted filesystem.

Isolated Linux Maven and Gradle lifecycles use an enforced complete input boundary under crun. It keys the admitted source and dependency inputs, locked tools, runtime and boundary facts. It hides live proc/sys data and starts each lifecycle with private output state. Unsupported ambient input requirements fail within that restricted view and cannot publish a successful reusable result. An unchanged compatible lifecycle reuses its compilation, archive and test evidence together. With a compatible Java plugin, multi-module Maven and single-build Gradle projects use one coupled lifecycle action per module/project, including its declared producers. Compile and test-class results stay coupled inside that unit. Reports retain the producer's identity and are validated again on reuse. Source, dependency and locked JDK identity changes invalidate the affected action. Fixed archive-copy exports follow their producer's content identity.

Use the existing oyzu build --isolated --no-docker selection, or select crun with build.isolation and run oyzu build --isolated. No internal environment gate or new setting is needed. Preparation and tool/input admission still run before a lifecycle hit. Other executors and Windows/macOS do not supply this complete Java boundary. Native-host Maven/Gradle lifecycles keep refusing reuse when their reads are incomplete, including with unchanged sources. Plain Java builds still select native execution; making isolation the Java default is a later product decision. See Maven and Gradle. The .NET consumer uses the same boundary automatically on Linux crun, without a new gate or user option; see .NET stage reads. The closed ambient allowance is /dev/random, /dev/urandom, /dev/null, /dev/zero, and the startup files /proc/self/maps, /proc/self/status, /proc/self/stat, /proc/self/cgroup, /proc/self/limits and /proc/self/mountinfo, plus readlink of /proc/self/exe for executable discovery/identity checks. Opening the executable through proc is not allowed. Other processes' proc entries and all other proc/sys entries stay inaccessible. Self-proc files are supplied as read-only descriptors for the requesting process; the proc tree stays hidden. Successful enforced actions retain that allowance as non-keying facts under extensions["oyzu.dev/ambient-reads"]; the device bytes are never sampled for cache lookup. Self-proc facts record presence only, never contents. Ambient values must not influence retained outputs. Workloads whose outputs depend on entropy remain outside this reuse contract. Other ambient reads receive no allowance.

Linux crun Helm stages use the same enforced boundary. Packaging/rendering, lint, validation and helm-unittest can reuse unchanged successful actions with valid reports. The plugin's bounded chart reads are retained; suites without complete observations key the full admitted source view. Helm and helm-unittest are typed locked-tool inputs. The latter uses its normal github:helm-unittest/helm-unittest recipe in oyzu.lock, including publisher archive and resolution identities. A changed selected tool misses; a legacy fixed download is not lock admission. Native-host chart stages still refuse incomplete reads. Helm outputs remain location sensitive unless explicitly declared relocatable.

Ordinary source selectors and observed paths must stay within the source root; absolute paths and parent traversal are rejected. They cannot bind ambient JDK or SDK directories, dependency caches outside the workspace, or external test data by naming their paths. Locked tools have separately admitted identities. The Java formatter declares its JDK as an external locked-tool input. Core binds it to the current admitted oyzu.lock identity before cache lookup and publication: changing that identity invalidates reuse even with unchanged source. An unchanged identity permits reuse subject to the other cache inputs. Missing admitted tool identity stops the build with external input <tool> has no admitted oyzu.lock tool identity; run oyzu pin and oyzu install for the required tool, then retry. Do not supply an external path or digest. This does not make arbitrary Java lifecycle or test reads bounded. Only locked-tool external inputs are supported; arbitrary external files and directories have no typed content binding. The tool identity participates in stage and whole-target keys and read-history identity. A changed version, artifact or lock binding invalidates reuse even with unchanged source; the declaration alone does not establish a complete tool set or complete reads. Adding a known input does not establish completeness for arbitrary reads by tests, build scripts or plugins; those stages remain unbounded without a complete read record or fixed tool rule.

For observed stages, core allocates an action-specific report path inside the invocation's scratch directory, beside its report directories, in OYZU_OBSERVED_READS. The exact file is cleared before every process attempt, including retries. The action writes a JSON report with complete, paths, listings and reasons, relative to its working directory. Core retains up to four recent complete observations within the prediction in local action-cache metadata, keyed by the structural action definition and core engine identity. Environment names belong to that history subject; their current values remain bound to each result key. This lets branches share observation history when a source-derived value such as OYZU_VERSION changes, without reusing a result built with a different value. Known per-invocation argv and environment paths are normalized before deriving those identities. A subsequent run can use a narrow native key only when that structural definition has an admitted observation. Planning declares observed-read intent before compiler records exist; missing or malformed completion records never authorize reuse. When an execution completes a valid observation and passes the ordinary result-storage checks, core also stores its result under the narrow key computed from the pre-execution snapshot and that report. The next unchanged run can hit that key immediately, including after the first cold compilation.

A native key covers the reported files and directory listings, required configuration and declared inputs, shared source inputs, and the declared environment and resolved tool identities. An edit outside those inputs keeps the observation and narrow key. A changed read or listing produces a narrow miss, then successful execution records its new observation and result; the next unchanged run can hit again. Each execution is stored only under narrow keys computed from its own completed report. A lookup key based on an older report is not populated when the execution reads a different set, even if another build changes the shared observation history concurrently. Whole-source results retain their complete source boundary.

On Windows, read coverage matches paths without case sensitivity, including literal paths, globs and directory listings. A reported DATA.TXT read binds the captured data.txt file, so changing its contents invalidates reuse. Directory membership changes likewise invalidate a differently cased listing. Snapshot capture rejects case-colliding paths. Linux and macOS read coverage remains case-sensitive.

History tries observations in most recently used order, checking each against the current prediction, files, listings, environment and tools through the same narrow lookup gates. The first valid result wins. Switching between branches with different read sets can therefore reuse either branch's result after each has built once. Each lookup hashes at most four observed sets; a hit or valid completion moves its observation to the front, deduplicated by observation digest. Adding a fifth evicts the least recently used observation. Concurrent updates merge atomically, preserving different observations within this bound. When no observed candidate hits, one complete-prediction candidate can discover a stored result without local observation history.

oyzu cache explain <action> summarizes each candidate's skip, miss or rejection and names the candidate that hit. JSON also includes nativeCandidates and nativeLookupMicros (elapsed candidate lookup time, including result admission and restore preparation). Candidate probes do not advance key history. Only the selected hit key, or the ordinary request key when every candidate misses, is observed. The comparison baseline comes from an earlier invocation, never another candidate of this lookup. The same choice owns the invocation's execution and publication state.

A cache hit preserves admission without requiring a new report. A missing, invalid, empty or incomplete report, or a report with reasons, cannot add an observation or authorize narrow publication; other complete observations remain available. The prediction remains the admission boundary for every report, and required report, artifact and policy checks still apply. Core rebases cwd-relative reports by the action cwd and target before checking the prediction, including configuration files and declared inputs. On a narrowed run, an observed read outside prediction refuses result storage with confined-read-outside-contract. An incomplete native report cannot publish a coarse whole-source result instead. These reports grant no isolation or authority.

Node check commands, including captured npm aggregate tests and conventional workspace quality tasks, omit the generated version default. Stable command inputs do not establish complete reads: arbitrary lifecycle code can still read any file or listing in its admitted view. Captured whole-target fallback keys retain that inventory, and incomplete native observations still make the stage run. Shipping Vite workers also retain their version and source-path inventory for output metadata and source/output overlap validation.

A listing selector keys the names and kinds of entries directly in a directory. Adding, removing or renaming an entry changes the key; changing its contents alone does not. Nested entries are excluded. Captured views expose empty file placeholders and empty directories for listing-only entries, so undeclared file contents remain hidden. A path on the directory or an ancestor also predicts its listing. A glob must provably match every direct child, such as dir/*, dir/**, or an ancestor's **; merely matching the directory name (for example * matching src) is insufficient. Ordinary file reads still require a covering path or glob.

Python source reads​

The Python plugin analyzes captured setuptools package builds, pip preparation and pytest, with output-only packaging. Quality task binding, unknown backends, executable configuration and native operations retain specific unbounded reasons. See what each Python stage reads. Python package snapshot versions still use the whole-target source digest, so an unread edit can change build/package definitions even with a narrow read list. Supported development-source case tests use their separate native editable subject rather than that unused inferred wheel-version default. Captured Python prepare and build record their environment and normalized distributions in .oyzu-build/python inside the private workspace. Cache hits restore these outputs; built-package tests and packaging depend on the built wheel bytes, including package data. Development-source tests inventory their own editable environment instead. Wheel member timestamps and sdist timestamps are normalized before capture so native mtimes do not change downstream output keys. Additional setuptools build requirements keep the build unbounded because they may install backend plugins.

Native Rust source reads​

Learned build-script file and environment names remain admission inputs, while the native definition and history subject contain only base/configured facts. Observed native source keys bind base env names plus ObservedReads.env, with values from the environment the process actually received; an absent name binds None. Bound build actions do not inherit undeclared host values. The narrow action recipe omits learned prediction metadata; whole-target and group keys continue to bind effective environments and output locations. The observedEnv payload marker prevents reuse of older path-only observations. Prediction candidates are published or backfilled only when their frozen env declarations cover every name in the admitted report, including names whose values were unset. An uncovered name prevents both local and remote prediction aliases; the complete observed result remains reusable with matching observed inputs. The same rule applies when a history hit could backfill a new prediction after an unread file changes. A reader without native history must execute if that prediction alias is unavailable. Per-run TMP, TEMP and TMPDIR reads are excluded.

With learned names unset on the host, an unchanged second run can reuse the first result. If a learned name is set, the cold process did not receive it, while a later planned process does: that environment change requires a miss before reuse can converge. cache explain lists names (never values) in nativeHistory.learnedEnvSetOnHost and in its text reason. Output-location identity still binds compiler flags, tool homes, the checkout and the effective environment. Unset, empty-string and nonempty values are distinct inputs. Removing local Cargo records cannot authorize restoring a result that requires an environment name missing from the new prediction. Scripts must declare their env dependencies through cargo:rerun-if-env-changed or cargo::rerun-if-env-changed; undeclared script reads remain outside this guarantee. Missing, malformed or incomplete observations refuse result storage; they do not become empty successful read sets.

Rust predicts each stage's reads from Cargo workspace manifests and target source folders, Cargo and Rust configuration, build scripts, and literal include_str!, include_bytes!, include! and #[path] references. Manifest-relative concat!(env!("CARGO_MANIFEST_DIR"), ...) references with literal suffixes are resolved too. Source and discovery directories remain conservative directory reads.

Cargo metadata paths are resolved against the preparation workspace. Compiler and build-script records instead use Cargo's actual execution workspace, recorded beside each build or Clippy target directory before execution. These projections can differ: preparation uses a source-only workspace while actions use retained private source trees. Manifests, source files, build-script watches and dep-info map to target-relative read selectors; projection locations do not become part of those paths. Records without an execution-workspace record use the metadata workspace conservatively; an unmappable source makes reads incomplete. Unbounded source diagnostics show a bounded sample and the omitted count within the plugin protocol's message limit. Shortening a diagnostic never admits an incomplete observation. On Windows, dep-info drive, UNC and verbatim (\\?\) paths retain their prefixes when mapped to source selectors. Unparseable dep-info paths or unreadable records make the observation incomplete with a reason; they cannot silently authorize a narrow key.

Rust native compiling stages declare observed admission. The Rust plugin writes the neutral read report from complete Cargo dep-info and build-script records, plus Cargo manifests and configuration controls that dep-info does not list. Until a previous run of the same action definition has an admitted report, they can discover a stored complete-prediction result; otherwise they keep the whole-target key and execute without restoring a coarse stage result. After execution, a read outside the prediction prevents result storage and reports confined-read-outside-contract, naming the path and the inputs declaration that adds it. Human, no-color and JSON diagnostics carry the same fix. A missing or incomplete observation never authorizes stage result storage, under either a narrow or a whole-source key.

format-check uses rustfmt's fixed module-tree and configuration rules and does not need a runtime observation. Native Rust tests and coverage remain unbounded: tests may read files at run time. They retain the current native stage's conservative execution and cache admission. Independently bounded Rust executables can reuse results under the test-unit contract; the enclosing unbounded stage still executes.

Cargo dep-info does not record a proc macro's runtime file reads. Native Rust builds assess registry proc macros and registry build scripts as identity-bound: the exact registry package name, version, source and checksum must match Cargo.lock, and the action also binds its selected toolchain and target. This assessment applies to registry implementations without a version allowlist. Workspace/path macros, Git macros, local source replacements and implementations without an identifiable locked registry checksum remain unassessed and refuse stage reuse. Compiler and Cargo locator environment selectors remain keyed. Native target-scoped read names such as CC_x86_64-pc-windows-msvc and CFLAGS_x86_64-pc-windows-msvc are keyed without renaming their hyphens. The managed Rust installation is also bound through the typed locked-tool external-input class; this declaration does not admit arbitrary external paths.

Residual risk: a registry proc macro can read ambient files without reporting them to Cargo. The identity-bound assessment trusts that implementation; it is not a complete operating-system read trace or native filesystem confinement. Changing an unreported ambient file can therefore leave a registry macro result reusable. --no-cache bypasses action-result reuse; Cargo's own freshness rules still apply. Workspace/path macros do not inherit this registry assessment, even if they have the same name.

Active-unit membership comes from Cargo's successful execution message stream, including fresh units, for the selected target, features and profile. Units excluded by feature or fixture gates do not require build-script records. Before each execution, the old membership is cleared; a failed or incomplete execution cannot publish replacement membership. Active build scripts still need their Cargo records. Existing registry script records contribute environment reads; package-local registry files are covered by the lock checksum, and explicit reads outside the source or admitted tool roots retain an incomplete reason. Missing records during planning request observation rather than claiming completeness. The current execution's report remains the admission decision. Before script records exist, the native prediction covers the local package directory so discovery of package-owned assets does not fail a cold build. Completed observations can still narrow the key to the actual script watches.

Native Clippy also records compiled-unit membership from Cargo's JSON messages. An uncompiled fixture package therefore needs no build-script record for lint. Lint still checks every retained script record for each compiled package; a compiled package's build script with no matching record leaves reads incomplete. Lint does not record which script directories ran, so a retained record can mask a missing current record. Membership matches by manifest path. If any compiled manifest matches no metadata package, membership cannot narrow reads: every package is checked and reuse remains blocked.

The macro prediction uses Cargo's target-filtered resolved graph, following reachable dependencies rather than every downloaded package. Missing or mismatched target resolution remains unbounded. Other unresolved include expressions still name their source file and line.

An OUT_DIR include is generated output: its source inputs are the build script and its rerun-if-changed paths. A watched directory includes all its contents. Without any rerun-if-changed, a workspace/path script keeps the stage unbounded because Cargo uses package changes as the default. rerun-if-env-changed names contribute their effective environment values to the key without publishing those values. Acquired compiler and dependency inputs retain their separately admitted identities.

Git metadata watched by a build script is a real input, including in linked worktrees. A script that watches .git/HEAD or its branch reference prevents compiling-stage reuse when that identity changes, even for a documentation-only commit. Unstaged edits outside predicted reads can still reuse a bounded stage. Changing build identity is a project decision; Oyzu does not remove those watches.

Verifying a contract​

oyzu build --verify-contract     # also: --json, --full

This can't be combined with --no-cache or --plan. A normal build runs. In addition, for every confined action:

  1. The action starts from a copy of its target workspace and runs confined, as usual.
  2. The same action runs again from an identical copy with the whole target visible.
  3. Oyzu compares the results: exit code, every workspace file created, changed or deleted, and the artifacts collected. Test and coverage report files aren't compared, because they carry timing.

Equal results pass. If they differ, Oyzu re-runs the action with subsets of the hidden files (at most twelve extra runs) to find a minimal set that explains the difference, and names those files and the declaration that fixes them:

  Contract check  failed · 8 confined actions run again with their whole target visible · 7 equal · 1 diverged · 20 not confined (not checked)
  api:build                 Diverged · also reads optional.json · declare inputs: ["api/optional.json"]

A divergence fails the build, including when independent targets run in parallel (diagnostic contract-diverged; manifest.extensions["oyzu.dev/contract-verification"] has status, counts and one record per action). The check uses a throwaway store, so it reuses and stores nothing. It doesn't run on the native path. Each confined action runs at least twice with copies of the workspace, so it is slow on large installed trees. Actions that aren't confined are counted, not checked. If the search stops at its budget, the record says minimal: false.

Remote OCI cache​

You can share action results through any OCI registry. Share them from CI to developers, or between a team's machines.

Targets built by an installed plugin package participate in cache.remote and cache.ciRemote. Keys include the verified package release digest, protocol and runtime; changing the plugin identity causes a miss. Remote hits pass the same digest, artifact and report checks as local hits.

plugins.development bindings never read or write these shared remotes, including bindings to native executables or package archives. Their reusable results stay local. A slice's --handoff repository has its separate handoff contract.

# user or machine configuration: where results are shared
[cache]
remote = "oci://registry.example.com/team/oyzu-cache"
# user configuration: this machine also publishes what it builds
[cache]
write = true

Supported registries: zot, CNCF Distribution behind a token service, and a Harbor proxy-cache project, on Linux. Other registries (Artifactory, Nexus, Docker Hub, GHCR) aren't supported yet, and neither are Windows and macOS clients.

  • cache.read and cache.write are per-machine preferences and don't change action keys, so readers and writers share entries.
  • A loopback host (localhost, 127.0.0.0/8, ::1) is reached over plain HTTP. Every other host uses HTTPS with the shared proxy and trust settings.
  • The remote is used only while the local cache is active. --no-cache, cache.local = false and --verify-contract use no remote.

What is shared​

  • Per-action results, for targets reused action by action (captured node/package and node/app targets with stage contracts).
  • Whole-target results, for targets reused only whole (the native host path, other builders). These appear under the target's ID in the build record where an action ID would be.

A per-action target's group record is never pushed. A client rebuilds it from the action results, so an unchanged repeat after a remote hit makes no registry request.

Sign-in and redirects​

A registry that requires sign-in is supported through the registry token flow. The credential is an environment variable, never a setting:

export OYZU_CACHE_TOKEN=…   # the token your registry's token endpoint accepts

In a CI job that offers OIDC ID tokens the way GitHub Actions does (OYZU_ID_TOKEN_URL and OYZU_ID_TOKEN_REQUEST_TOKEN, which the Oyzu runner sets), leave OYZU_CACHE_TOKEN unset. The client signs in with the job's ID tokens and asks for a new one when needed.

  • The credential is first sent as a bearer token. A 401 with a Bearer challenge names the registry's token endpoint. Oyzu uses it only if it is on the registry's own origin (scheme, host and port). Otherwise the request is denied and the credential is never sent elsewhere.
  • The client then asks that endpoint for one token per repository, with OYZU_CACHE_TOKEN as the Basic password (user name oyzu), or with no credential if the variable is unset or empty. Tokens ask for pull, plus push when cache.write is true. A rejected or expired token is fetched again once. A second refusal is a denial.
  • With ID tokens, the Basic password is the job's ID token: GET $OYZU_ID_TOKEN_URL with ?audience=<registry origin> and the request token as a bearer, answered with {"value": "<jwt>"}. It is reused until 30 seconds before it expires. The request token goes only to that URL, and neither token is recorded.
  • A blob response can redirect to another host (for example a separate blobs host with short-lived signed links). Redirects are followed without the Authorization header when they change origin, at most 5 times, and never from HTTPS to HTTP.
  • A manifest lookup for an entry in the cache carries an advisory X-Oyzu-Cache-Rung header: target for a whole-target entry, action for a single action's entry. A cache gate may count the two apart, because a whole-target key moves with any source change and its 404 is routine. Registries ignore the header, and lookups from other clients or for other purposes (plugin and bundle reads) send none.
  • The build record's remote (and ciRemote) section reports lookups as {target: {hits, misses}, action: {hits, misses}}, counted the way a cache gate counts them (a 404 is a miss; an answered entry, even one rejected after verification, is a hit), so a CI summary matches the gate. A lookup during which the remote went off counts as neither, even if the gate already saw a 200, and REAPI lookups are counted by the client only because there is no OCI gate in front of them. An entry fetched from an OCI registry records its rung in its origin, and oyzu cache explain says whether it came as a whole-target or a stage entry.

Entry layout​

  • Repository <prefix>/v1alpha1/<first two key hex>, tag lookup-<64-hex key>.
  • An OCI image manifest with artifactType application/vnd.oyzu.action-result.v1alpha1.
  • The action-result descriptor as config (application/vnd.oyzu.action-result.config.v1alpha1+json) and one layer (application/vnd.oyzu.tree.v1alpha1.tar+zstd) holding every blob the descriptor references, named sha256/<hex>.
  • Annotations: dev.oyzu.action.key, dev.oyzu.action.output and, on the layer, dev.oyzu.tree.uncompressed-digest.

Build record​

The build record gains manifest.extensions["oyzu.dev/action-cache"].remote: location, read, write, status (active, unavailable with reason, or unusable for a cache.remote the client can't use), counts of hits, pushed, converged, conflicts and rejected, the requests sent by kind, and per target the actions in each list. A result materialized from the remote carries extensions["oyzu.dev/remote-origin"] in the local store. The summary line adds the remote part, for example remote 7 reused · 0 pushed.

REAPI servers​

Use a stock Remote Execution API action cache in place of the OCI registry:

[cache]
remote = "grpc://127.0.0.1:9092/oyzu"
write = true

grpcs://host[:port]/<instance> uses TLS (default port 443). Plaintext grpc://host[:port]/<instance> is accepted only on loopback (default port 80). The instance can be empty or contain /. Credentials, queries and fragments are forbidden in locations. Standard proxy variables, loopback bypass and SSL_CERT_FILE additional trust follow the shared outbound transport settings. The user/machine scope restrictions, CI/development selection, offer behavior, local verification and report gates are unchanged. cache.immutableTags is ignored for REAPI; every push checks for an existing result first.

The client requires advertised SHA256 support. It uploads the Command and Action before updating the action cache. Empty blobs are already present by protocol. CAS batches account for the encoded request and gRPC framing within the server's size limit (4 MiB when unset). Read batches also reserve encoded response headroom. Blobs that do not fit use ByteStream. Entries are limited to 256 MiB. Every digest, size, descriptor and referenced blob set is checked before local publication. Corrupt content is quarantined and the action runs normally. CAS eviction is an ordinary miss, including when the action-cache record remains: it is not counted as a rejection or quarantined. A later push repairs that entry when its descriptor or any output blob is missing. Readable, valid entries with equal output identities converge without writes; different identities are conflicts and stay in place. Worker metadata is not an identity or trust check; the output layout and verified descriptor/key identify an entry. REAPI has no atomic create-only AC update, so this check does not provide an immutable-tag server guarantee against simultaneous writers. Concurrent uploads of the same valid output can both write or converge. A writer that sees a different output records a conflict, but racing updates can still replace one another after that check. Every read verifies the result's embedded action key, shape, CAS digests, sizes and complete blob set before committing it locally; normal restore and report checks still apply. A conflicting AC update that fails those checks is rejected, including during concurrent reads. A valid but nondeterministic result for the same key can be last-writer-wins: integrity checks do not authenticate a producer or prove that a computation was honest.

The credential is an environment variable, never a setting. OYZU_CACHE_TOKEN, when set, is sent as authorization: Bearer <token> metadata. A server requiring an API-key header can select its non-secret name with cache.remoteHeader; the same token value is then sent verbatim, without a bearer prefix. This setting applies only to REAPI and accepts a lowercase application metadata header, not reserved grpc-*, binary *-bin, host, content-type or te headers.

Without that token, OYZU_ID_TOKEN_URL and OYZU_ID_TOKEN_REQUEST_TOKEN use the same CI sign-in flow as OCI. The requested audience is the cache endpoint's origin (scheme, host and port), excluding the instance path. ID tokens always use bearer authorization, regardless of cache.remoteHeader. They are reused until within 30 seconds of expiry, then fetched again. A denial never triggers an anonymous retry. GET id token appears separately in request counts.

For mutual TLS, set both cache.remoteClientCert and cache.remoteClientKey to absolute PEM file paths and use grpcs://. The key must be unencrypted and readable by the build account; restrict access to that file. These paths and the header name belong only in user, machine or administrative configuration, not project files or profiles, and resolve once per build. They apply to all configured REAPI remotes; OCI is unchanged. The certificate authenticates to the cache server, not to a CONNECT proxy. SSL_CERT_FILE still supplies additional server trust.

Client identity setup errors name the relevant setting and file path and retain the filesystem or PEM parsing cause. Correct the path, file permissions or PEM contents before trying again; private-key contents are not included in the error.

Illustrative user configuration for a header-based server with mTLS:

[cache]
remote = "grpcs://cache.example.com/team"
remoteHeader = "x-api-key"
remoteClientCert = "/home/developer/.config/cache/client.pem"
remoteClientKey = "/home/developer/.config/cache/client.key"

Set OYZU_CACHE_TOKEN through the shell or CI secret facility. No token value, request token or private-key bytes are written to configuration, logs or build records. Server messages are omitted from failure records to protect secrets. Do not interpret a successful build as proof that credentials were accepted: check the remote status and the build's Warnings section.

Remote failures never fail a build. NOT_FOUND on lookup is a miss. UNAVAILABLE, DEADLINE_EXCEEDED, RESOURCE_EXHAUSTED, ABORTED, timeouts and connection failures get at most three attempts with exponential backoff and jitter, then disable this remote for the invocation. UNAUTHENTICATED and PERMISSION_DENIED disable it without retry. FAILED_PRECONDITION on update records a push failure and computation continues. When capabilities report update_enabled = false, writes are skipped with a read-only reason; reads remain available. Authentication denial appears in the remote build record as status: unavailable with a denied reason while the build computes normally. One warning names the location, gRPC status and credential inputs or permissions to fix. Transient outages also warn and compute locally. A read-only capability skips uploads without disabling reads; a write permission denial disables that remote for the build. Fix permissions, provide a fresh token or correct the certificate paths, then start a new invocation. Denial does not fail the build. TLS handshake failures can surface as gRPC Unknown rather than an authentication status. They also disable the remote and warn; check the CA and client certificate configuration rather than assuming the token was rejected.

If the OCI gate refuses push scope (401/403), the client requests pull-only scope once with the same credential. It disables writes for that CI cache client for the rest of the invocation, preserves admitted reads and explains the fallback. It never tries another credential or falls back to anonymous access. A refused upload also disables further writes while preserving reads. If pull is refused too, the remote is disabled and the build continues locally. Artifact publication retains its separate failure behavior.

The build record's ciRemote.write is false when the event guard or registry refuses writes, and ciRemote.writeSkippedReason explains why. Human output shows the same reason as writes skipped: ...; JSON retains the structured fields. This also covers reused local results and the native compiler-result tier.

  • A build that sets CI without the credential is refused (403), keeps building and writes nothing.
  • A CI build never reuses a developer's upload. It doesn't read cache.remote, and a result in its local store that came from a development remote is looked up again in the CI repository.
  • A remote hit is recorded with its scope (ci or development). Nothing is signed, so a hit from the CI repository says where it was read, not who produced it.

The registry credential is OYZU_CACHE_TOKEN or, without it, the CI job's ID tokens. It is never a setting, and it is never written to a record or log. OYZU_CACHE_TOKEN is sent as a bearer token on every request to the configured registry host (over HTTPS or to a loopback host), and dropped when a redirect leads elsewhere.

Immutable tags. cache.immutableTags = true says every configured cache repository refuses to replace a tag. A push then skips the racing-writer read, so a pushed action costs 6 requests instead of 7, and a refused manifest PUT (409 or 412) counts as the conflict. Don't set it for a registry that replaces tags, or the last writer silently wins. Either way, a hit is used only after the digests its manifest names verify.

With a storage-backed registry, a push can cost many more storage operations than the 3 objects an entry consists of (about 25 write-class operations per entry on CNCF Distribution's S3 driver), which matters if your object store bills per operation. Harbor's proxy cache revalidates every manifest with the upstream registry, so it saves blob traffic, not manifest requests.

For legitimate local producer results, a fresh publication marker suppresses offer requests for 24 hours across invocations. Each completed offer explicitly refreshes the marker timestamp, including on Windows; an expired or future-dated marker allows revalidation. After expiry, an OCI offer costs one manifest GET when the key remains occupied, or six requests when it is missing (one manifest read, two uploads and the manifest write). This is eventual refill on eligible local reuse, not immediate eviction detection. Missing, unreadable, non-file or future-dated markers permit re-offer; failed/skipped offers do not refresh the marker. Marker updates are best effort. A completed conflict also refreshes suppression: the marker records a recent offer, not proof that our result is remotely available.

Remote limits​

  • Sign-in uses only OYZU_CACHE_TOKEN (bearer or the OCI registry token flow; verbatim API-key metadata when REAPI cache.remoteHeader is selected) or the CI job's ID-token flow. REAPI can additionally use mTLS through the two client certificate/key file-path settings. There are no credential helpers, Docker configuration, login command or OAuth2 POST token form; Basic auth to an OCI registry itself remains unsupported.
  • Immutable tags are declared, not detected. Results aren't signed and producers aren't verified.
  • Lookups aren't batched. Transfers are sequential. Entries above 256 MiB aren't pushed.
  • There is no client-managed remote retention or pruning. An evicted OCI tag can be refilled by an authorized local producer after its offer marker expires. A present damaged OCI entry is rejected by readers but never repaired or replaced; the offer preflight checks manifest shape/key/output identity rather than verifying its blobs. An entry pushed by an older Oyzu without keyComponents in its config is rejected like a damaged one.

Independent test results​

Eligible passing test units and supported Python cases use the same OCI and REAPI remotes as action results. Core computes each key from current inputs; the remote transports its immutable descriptor and referenced report bytes. Unit restores validate exact key facts and components, stage only that unit's files, and require a passing JUnit report before accepting the hit. Unit JSON records include the original execution producer in sourceRecord when known. Report timings and producer metadata are evidence, not racing-writer outputs. CI/development origin restrictions and ordinary outage fallback apply to these entries too. Failed units are never reusable as successful units.

Passing cases can still be reused independently when another case in the same unchanged unit fails. A reader without history looks up a reference using the full locally computed unit key and current native case ID, then validates the separate immutable passing record and current components. References contain no input or coverage lists. Failed, new, missing or incompatible cases execute; latest local failure and order-dependence records take precedence over remote successes. Combined reports preserve original case producers and distinguish reused evidence from work executed now. Incomplete local executions also refuse older remote successes. Case outcomes remain recorded when coverage is incomplete. A unit assembled from remote case contributions is not stored as a new locally produced unit, preserving its contributors' remote-origin restrictions.

This discovery is deliberately conservative. A remotely discovered trace stays bound to the full unit input key even after it is recorded locally. When that key changes, its historical coverage cannot authorize omitting current inputs. For a deliberately smaller plain-Python subset, a reader can instead compute a complete current native function closure before lookup. It hashes the current case and every transitively referenced function locally, retaining all module setup, file membership, non-code inputs, environment, tools, locks and configuration. The exact resulting key finds the immutable passing record; remote coverage never determines that closure. An unrelated body edit can then reuse an independent case even with no local history. Existing guarded traces remain guarded.

This path accepts direct calls, primitive expressions and immutable literal constants in plain top-level functions. Native import facts carry actual loaded origins and aliases, including relative package imports. Rust resolves only origins in the current admitted source inventory. Fixtures, marks, decorators, dynamic calls, introspection, mutable setup, unresolved origins or custom pytest plugins retain conservative execution. Native plugin registrations are observed historically, so unregistering a custom plugin cannot make the run eligible. Fresh records require complete native coverage within the computed closure and matching prepared/runtime observations. The core and normally admitted Python package must have matching native runtime identities; an older package is rejected rather than treated as compatible.

If execution adds reads or invalidates the current native facts after a partial selection, the existing unit runner retries the complete unit once in a fresh view. It retains the initial native case/JUnit contributions and logs. An initial failure remains a failure even if the full selection fallback passes; combined reports explain both observations. Only validated complete conservative results can be stored.

Local coverage-based selection continues for its existing supported shapes. This transport does not add Rust executable discovery, test sharding or quarantine, or qualify new test subjects or platforms.

Python cases inside a bounded unit​

Captured pip/pytest package tests can keep passing case results inside a changed file-level unit. Native collection supplies each full node ID, including parameters. Only the selected cases run, in their original relative order. The step combines native IDs, outcomes, durations and failure reasons with reused evidence in one JUnit report. Fresh native JUnit contributions are also retained with their configured output capture; the combined report does not add captured passing output. The action row shows, for example, 12 of 140 cases ran, 128 reused.

A case key compares five inputs: shared unit configuration and tool/dependency identities; non-code runtime inputs; code executed during import and collection; the case's executed code; and its native ID. Shared-input changes rerun every case. A changed import-time input reruns the whole unit. Within the bounded source shape below, a function-body edit reruns cases that executed that function. For supported captured development-source tests, the shared identity names that test subject and its genuine editable environment, including native metadata, RECORD and import mapping. It does not inventory the separate inferred-version wheel environment or inject its unused version default. Built-package tests keep actual wheel-installed facts; subject identities never share passing records. Required runtime-read confinement and the guards below apply to both subjects. Unsupported source layouts retain built-package testing. New cases and cases whose last result did not pass always run. Missing input or coverage facts also run the case. The stored passing record, rather than diagnostic history, authorizes reuse. Its case ID and all current key components must match the requested case. A history pointer to a different existing record is a miss, so the requested case runs instead of borrowing unrelated passing evidence.

Coverage facts come from an Oyzu-supplied pytest adapter using coverage.py's test_function contexts. For parameterized tests, a static native node-ID context keeps parameter identities separate. Core hashes admitted source bytes; the Python adapter never chooses cases or keys. Python's AST supplies current UTF-8 byte ranges and stable names for plain top-level functions. Rust hashes each executed function's entire definition from the admitted runtime view, including branches the previous run did not take. It resolves names against the current collection instead of reusing old line offsets. An unchanged function can move when another body grows or a new case is inserted; reused line/arc evidence is relocated to its current position for the combined coverage report.

This separation currently accepts modules consisting of imports, literal constant assignments, docstrings and plain top-level functions. Import statements and whole literal assignments, including multiline values, remain shared. Merely creating a function during collection does not make its body shared; executing it outside a case does. Modules with classes, computed module setup, colliding top-level bindings (including native import aliases, constants and function names), one-line definitions, decorators, defaults, annotations or unsupported source encoding retain whole-file identity. Python's native encoding detection honors coding cookies; only UTF-8 without a BOM supports function ranges. Other encodings stay opaque and execute with their native interpretation, even when their raw bytes also happen to decode as UTF-8. Missing location facts and case execution outside located functions also retain whole-file identity. Syntactic references to namespace inspection or evaluation (globals, locals, vars, dir, eval, exec, __globals__, __dict__ or __builtins__), including imported aliases and qualified attributes, keep every source in the bounded unit opaque. The adapter does not attempt to resolve which module an observer can inspect. For example, an unchanged assert 'test_added' not in globals() can fail when a new function is added; an unchanged assert 'added' not in vars(api) can likewise observe a new function in api without executing it. Both retain whole-file import/collection identities. Explicit source reads such as inspect.getsource remain shared runtime reads. This is a bounded native source contract, not general Python dependency analysis.

Shared tool, environment and runtime-artifact changes remain binding, including the actual installed package version and all .dist-info bytes (METADATA and RECORD included). A source edit that changes those inputs still reruns the whole unit; function regions do not normalize or discard them. File membership, kinds, executable facts and frozen non-code inputs stay shared; only inventoried code bytes move into the coverage components. Selective function-level reuse is limited to the supported Linux development flow. Full, CI, package and release validation retain their broader inputs; other platforms do not support this selective flow.

Selection currently requires Linux crun (--isolated --no-docker), enforced captured runtime-read bounds and coverage.py in the project environment. Coverage.py is not currently an independently acquired Oyzu tool. Missing or incomplete coverage runs the entire unit and gives a one-line reason. Native host tests and authored test tasks retain their existing whole-unit or whole-stage behavior. Python application archives and other languages do not use case selection.

The release context runs every case when its unit key changes. If fresh selective and full executions disagree on an identical case key, the result is reported as order-dependent, with both run IDs and which run was selective. Selection stays disabled for that unit key. A disagreement blocks the unit even if the selective child passed; the next build runs it fully. Native outcomes remain in the report. Detection does not turn a failure into a pass or run an automatic retry through case-selection fallback. The separate in-build test-attempt controller may retry a genuine native test failure, reporting a pass on retry as flaky and refusing unit storage.

oyzu cache explain <target> lists each case's deciding component or the original run record used for reuse. JSON action records add caseSelection inside each unit, including fresh/reused counts, decisions and any order-dependence finding. Reused cases remain evidence not run now in test summaries. Existing v1alpha1 records are extended in place; records without case facts continue to use unit-level behavior.

Native Rust compiler outputs​

The experimental native Linux and Windows compiler tier reuses individual already non-incremental library compilations beneath a Cargo build. Linux also supports build-script and admitted application binary compilation reuse. Use the normal oyzu build entry point and existing cache settings. --no-cache disables this tier too. Action records include localReasons alongside compiler outcome totals in extensions["oyzu.dev/rustc-invocations"]. Local receipts distinguish unsupported arguments, incremental state, unresolved inputs/linkers and cache/input rejection. These reasons explain native fallback without treating it as reuse.

The tier also reuses Cargo's exact empty-stdin capability query for the native Linux x86-64 toolchain. The supported request prints file names, sysroot, split-debuginfo modes, crate name and target cfg, with Cargo's conventional crate types and optional x86_64-unknown-linux-gnu target. Its exact arguments, empty source, compiler identity, compiler environment and physical compiler/workspace placements are keyed. Successful stdout is restored byte for byte through the verified store. Failed queries or queries producing diagnostics are not stored. Other flags, custom targets and nonempty stdin retain native execution; a nonempty source is forwarded intact and reported as nonempty-capability-query-source.

Cargo still creates consumer-local bookkeeping and decides whether an invocation is needed; its freshness messages do not count as compiler-cache hits.

Compiler admission uses the exact canonical managed rustc retained by native preparation, independently of whole-stage tool completeness. Build scripts still execute locally; their presence and proc macros do not prevent invocation reuse. Whole-stage caching retains its existing tool-completeness checks. Opaque native stages bind the full selected tool environment without gaining source or PATH narrowing; missing preparation retains the whole-lock fallback. Cargo configuration may supply rustflags and target settings; effective rustc arguments and encoded rustflags remain keyed. Compiler or wrapper substitutions in the environment or .cargo/config* keep the stage's compiler invocations local. Proc-macro and build-script compilation keys also bind resolved linker file contents and linker arguments. Unresolved linkers and explicit linkers outside retained managed tools stay local; rlib/rmeta invocations do not require a linker identity. Proc-macro and build-script compiler invocations also stay local if PATH contains any empty or relative entry, including .:/usr/bin on Unix. Rustc's linker subprocess receives that PATH unchanged and can search its working directory; filtering entries only during key generation would bind a different linker. Use only absolute entries to allow reuse of these compiler outputs. On Windows, .dll proc-macro extern inputs are keyed by content. Proc-macro and build-script compilation and native -l library closures remain local with unresolved-windows-linker-closure or unresolved-windows-native-library: MSVC linker discovery, SDK libraries and auxiliary inputs are not yet admitted. Windows support covers native x64/MSVC library invocations. Locally rebuilt proc-macro DLLs can change bytes between builds, including PE timestamps and CodeView/PDB identity or age fields. Those bytes remain part of the extern digest: changed DLLs invalidate dependent library results even when their Rust sources are unchanged. Oyzu does not strip or normalize them to force a cache hit.

A candidate must use supported library, proc-macro, build-script or application binary arguments and admitted workspace or lock/archive-bound crates.io inputs. Fresh local rustc dep-info supplies source and environment dependencies before lookup. Keys bind file/extern contents, compiler/profile/lock controls, actual consumed environment values and the invocation's admitted Unix creation mask. Builds under masks 0022 and 0077 cannot share compiler results. Cache descriptors retain environment digests rather than their raw values. Windows has no Unix creation mask; its not-applicable value is keyed with the host platform. Missing Unix mask evidence still prevents admission. Windows compiler invocations use rustc response files so large registry remap lists fit within the native process command-line limit. The native owner's explicit RUSTC is accepted only when it is the exact canonical selected managed compiler path. Custom compilers, aliases and alternate path spellings retain local execution. Frozen source facts come from the immutable projection; reads are bound to the core-reserved executing action fork, including any nested workspace prefix. Only those verified RUSTC, RUSTDOC and RUSTUP_TOOLCHAIN placements use tool role identities in the compiler-control digest, so the same admitted tool can be installed in different user stores. Other compiler environment values and actual consumed env! values retain their data semantics and path fallback. The private worker removes its injected wrapper/binding variables before invoking rustc, including native fallback. Authored wrappers outside this hook are unchanged.

Native Cargo preparation freezes Cargo.lock and Cargo metadata without inventorying registry archives. When a native action misses the finished-result cache and is admitted for compiler reuse, Oyzu can admit crates.io source files from a cached .crate archive only after verifying its checksum against the frozen lock. Task listing, finished-result hits, builds with --no-cache and actions that cannot use the compiler cache do not compute this inventory. The inventory covers regular archive entries; the extracted cache directory and .cargo-checksum.json never grant authority. The package manifest and each consumed file must match those frozen facts before reuse. Every compiler-cache binding still reads each compressed archive and verifies its SHA-256 against the lock checksum, including when file facts are cached. A changed or corrupted archive cannot use cached facts.

After that verification, Oyzu reuses the decompressed file inventory from the local action-cache store, keyed by the lock checksum. Only relative file paths and digests are retained; the current Cargo metadata supplies the physical source root. The same facts can serve copied trees and different registry locations. Concurrent bindings use the store's existing per-key lock and atomic publication. Evicted or invalid records are rebuilt from verified archive bytes. If the store is busy or unavailable, Oyzu inventories the already-verified archive buffer instead. A failed cache write keeps those computed facts usable. When a compiler consumer detects mismatched or missing registry facts, it refuses reuse and quarantines that archive's facts record. A later binding rebuilds the facts from verified archive bytes and checks consumed files again. These records remain local; no registry or toolchain bytes are uploaded.

Missing archives, unsupported entries or changed consumed files retain local compilation. Archive admission remains bounded to 64 MiB compressed, 128 MiB of files and 20,000 files per package; it does not scan the extracted source tree.

For a non-empty registry inventory, the compiler binding records elapsed time as Registry compiler inputs. JSON diagnostics and event logs retain the timer; use -v to show fast steps that ordinary human output may collapse.

Registry admission compares canonical filesystem paths, including Windows verbatim paths and registry roots reached through symbolic links. Only the exact admitted package manifest qualifies; similarly named directories do not. Admission resolves registry roots before launching Cargo and freezes those physical paths in the compiler binding. Absolute source arguments must use the physical spelling; an unresolved source alias keeps the invocation local.

Only expected rlib/rmeta files, host proc-macro dylibs and compiled build-script executables and admitted application binaries pass through the existing verified result store. Metadata-only library invocations restore rmeta outputs; linked library invocations restore both rlib and rmeta. Build-script invocations restore their executable; proc macros restore their dylib. Extern inputs retain their exact file kind and content identity. Their modes are preserved. A CI reader treats development-origin local results as misses before probing its CI remote. Existing read/write permissions, remote scope, integrity checks and failed-output/report gates still apply; a compiler hit is not successful test or target evidence.

An exact admitted workspace prefix produces logical /oyzu/source debug and compiler metadata paths. Admitted absolute registry source arguments map to /oyzu/registry/<archive-sha256> in compiler paths, including file!() output. Workspace and registry containment use canonical filesystem paths, including Windows verbatim spellings and registry roots reached through symlinks. This does not authorize sibling paths with a shared text prefix. Compiler source arguments retain their original spelling. Relative source filenames remain unchanged; relative and absolute source spellings have distinct keys. Oyzu does not rewrite CARGO_MANIFEST_DIR, environment values or source text. A consumed absolute environment path stays local, except admitted OUT_DIR under the physical location contract below. Dep-info is freshly generated on the consumer and never restored from the producer. Only typed artifact notifications may replay with consumer output paths; diagnostics prevent publication.

Sources containing declarative macros, proc-macro declarations outside a proc-macro crate, absolute path literals or standalone env!("OUT_DIR") use an explicit physical location contract alongside the native source remapping. Their keys additionally bind the layout of the working directory, target root and generated-output directory relative to the source root, and the admitted registry archives. Moving a whole checkout keeps the key, because the native source remapping already names those roots logically; changing the layout selects a different key. Standalone OUT_DIR observations retain their exact value and keep the physical generated-output directory in the key. Restored bytes are never rewritten. Receipt reasons name keyed-physical-location-contract; localReasons includes that contract count for compiled and reused invocations as well as reasons for local execution.

Cargo runs build scripts itself. A library consuming its own build-script output can reuse compiler results when generated file reads appear in fresh dep-info under its contained OUT_DIR. Those files are keyed by content and an OUT_DIR-relative name. Consumed cargo:rustc-env values are keyed through rustc's environment dependencies. --cfg, --check-cfg and --env-set arguments remain key inputs. Native -l inputs must resolve to exactly one regular file in admitted -L directories inside the target tree; unresolved, ambiguous or unsupported libraries retain local execution. Search-directory and generated output placements use logical paths. Dependencies of build-script and proc-macro packages are admitted independently; extern contents bind their compiled inputs. Build-script binary compilation can reuse its executable, preserving its bytes and executable permissions; Cargo still runs that script and owns its generated outputs. Editing build.rs invalidates its compilation key. The physical location contract also applies when the script source needs it, so same-path repeats can hit. Application binary links can reuse on the same physical paths with the native Linux x86-64 GNU cc driver and Rust-provided lld. Their keys bind every candidate rlib/rmeta in the Rust dependency search directories and native sysroot by content, including transitive dependencies. This conservative inventory can invalidate a link when an unused candidate changes; only application links pay this cost. The compiler's actual linker arguments supply a discovery hint. Successful links publish it through the same local and remote result caches as compiler outputs, so an empty local store and history can discover a remotely cached link. Before lookup, the native linker resolves libraries again and reports the files it opens, including ordered -L/-l choices, linker scripts and crt objects. Changing a native library or adding a library that shadows an earlier choice changes the key. The resolved driver, linker, support programs and their ELF runtime libraries, built-in driver specifications, link arguments and native search environment also enter the key by content or value. The full physical location contract applies to every application link.

A crate whose dependency closure holds a proc-macro target, directly or through a re-exporting dependency, also keeps the full physical location contract: expansion can read CARGO_MANIFEST_DIR or another path and emit it without a dep-info env-dep line, so the key must not omit the checkout and cache directories. The closure comes from the Cargo resolve graph (normal, build and development edges), not from build state, so identical runs agree. Results are reused only where those directories match. The contract covers checkout and cache roots only; a macro that emits another unobserved variable such as HOME is not keyed.

A first link, or a missing discovery hint, executes locally before publishing its result and hint. Failed links publish neither. Discovery hints use the same read/write and CI-origin admission as compiler outputs; they do not restore outputs. Native inputs are checked before and after linking. Successful repeat hits restore the executable's verified bytes and permissions, then regenerate local dep-info; the executable is never rewritten. Existing compiler-cache read/write, artifact validation and report requirements remain binding.

Unknown driver specifications, linker controls, nonempty generated raw-dylib search paths, thin archives, native autolink/GNU LTO inputs and unresolved libraries keep the application local with a specific refusal reason. Custom shell linker wrappers, ambiguous parent traversal through directory symlinks, parent-traversing linker scripts, other linker families, cross targets and other host platforms are not admitted. Conventional supported linker flags remain keyed; unknown arguments retain native execution. Cargo capability queries outside the exact empty-source request above remain local (cargo-capability-probe). Build-script feature probes such as autocfg remain local (unfrozen-stdin-source): their generated stdin source and LLVM IR outputs are outside the frozen source and compiler-artifact contract. autocfg also generates a fresh crate name for each probe; the name and LLVM IR output identity cannot be erased or rewritten to manufacture a hit.

Incremental invocations, active/unknown Cargo configuration, authored wrappers, unknown compiler arguments and inputs outside the admitted source or generated-output roots retain native execution. Incremental arguments are never removed. This repository sets CARGO_INCREMENTAL = "0" in [context.ci.env] through normal configuration resolution so CI dev-profile compilations can qualify. Local development keeps Cargo's incremental default; it trades cross-checkout compiler reuse for local incremental compilation. Frozen Cargo configuration containing only exact target tables for neither the selected target nor compiler host may be admitted: those tables have no compilation effect, and their captured digests remain keyed. Conditional cfg(...) tables and other settings retain local execution. Linux x86-64 OCI consumers can reuse admitted compiler results across checkout roots. After a source edit, unchanged dependency compilations can reuse their results while changed crates compile locally. Development readers restore only their matching profile, even when the writer also stores optimized entries. Registry reuse follows the same location contract and retains local fallback for other consumed absolute environment paths. Registry support does not establish reuse for every crate, REAPI compiler-result transport or another host platform. The compiler summary reports reused, compiled and local invocation counts separately from whole-action reuse. Both compiled and local execute rustc; local means the invocation did not qualify for shared compiler reuse. Action receipts retain these counts under extensions.oyzu.dev/rustc-invocations, including in the JSON build manifest. The receipt also includes timingsMs for source-compilation invocations, summed separately for compiled, reused and local, plus up to eight slowest invocations with their phase timings. Capability-query outcomes remain counted without source-compilation phase timings. Phases separate binding preparation, argument/extern classification, the fresh dep-info probe, input admission, lookup, verified restore, output installation, compilation and publication/rechecks. Native compilation includes linker work. These are elapsed times per compiler process: concurrent invocations overlap, so their sums are not the build's wall time. Store lookups use a nonblocking maintenance lease; contention refuses reuse rather than waiting for a lock. A whole-action hit retains its original receipt; those original counts and timings do not represent new compiler work.

Toolchain reinstall key sweep​

Contributors can run tooling/key-stability-sweep.sh --reinstall-toolchain NAME PROJECT_DIR from a Bash shell with oyzu and Python 3 on PATH. It copies the fixture into scratch, builds twice with one private tool store, then rebuilds with a second store and the same action cache. This needs network access and space for two toolchain installations. Both stores must list the same non-empty set of installed tool identities.

REINSTALL_STAGES selects space-separated stage names, defaulting to compile-development lint. Every selected action in the second build must retain its non-empty actionKey after reinstall and be reused. Missing actions and missing, empty or changed keys always fail. Extra new actions are ignored: the sweep guards the baseline actions, rather than requiring identical action inventories. Unrelated optional manifest fields are tolerated.

The sweep judges reuse misses against NAME-reinstall in tooling/key-stability-known-leaks.json: recorded misses print XFAIL, new misses print FAIL, and resolved recorded misses print XPASS until the entry is removed. Exit 0 means PASS or XFAIL; exit 1 means a key failure, unexpected reuse miss or XPASS. Exit 2 means a failed build or missing comparison prerequisite, including a selected stage absent from the baseline.

SDK_PIN rewrites only the scratch copy's global.json, materializing a private regular file if it was a symlink. The source fixture stays untouched. Scratch and logs are removed on exit unless KEEP=1 is set. SWEEP_BUILD_ARGS replaces the default --full; BUILD_ARGS appends execution options.

Compiler-state seeds​

Captured Rust compilation can start from a compiler-state seed in an OCI cache.ciRemote repository. REAPI remotes do not supply or publish compiler seeds: they skip seed filesystem work and requests while ordinary action-result caching remains available. This is native compiler state, not a successful action result: Cargo still runs, artifacts are validated and the selected checks still execute. It does not enable cross-path reuse for host-native builds or change their compiler-cache retention.

Seed keys include the compiler archive digest, native Cargo lockfile digest, target triple, absolute compiler-visible workspace and Cargo home, selected worker and command, effective-environment digest, tool-lock identity and tool archives. Workspace and Cargo home paths must be canonical and absolute. Dot and parent aliases are refused, including slash-separated aliases inside Windows verbatim path components. Raw environment values are not stored in the seed inventory. A path mismatch selects a different lookup before any compiler-state download. When native read completeness is unknown, the key also binds the complete final staged source and preparation identity: changed inputs then build cold, even at matching paths. There are no fingerprint edits, filesystem aliases or new sandbox mappings.

The seed is an OCI manifest with content-addressed inventory and archive blobs, under the configured CI repository's compiler-state/v1alpha1 segment. For example, a CI repository prefix of oyzu-cache/ci keeps seed manifests and blobs under oyzu-cache/ci/compiler-state/v1alpha1/<key-shard>.

Seed publication is disabled in this client, including CI and pool jobs with write credentials. There is no configuration or environment switch to enable it. Enabling publication and qualifying a trusted producer require a separate change; client environment hints cannot authenticate that producer. Developer remote repositories are never seed sources. The registry owner manages retention.

Restoration verifies the key, blob sizes and digests, archive member inventory, file contents and containment before committing compiler state. Symlinks, hard links and special files refuse the seed. An existing local directory is never overwritten. A refusal or unavailable remote causes a cold build; offline builds do not contact the seed remote. A seed manifest or blob request that fails after transport retries, or is denied, disables that remote for the rest of the invocation, including subsequent action-result lookups. A missing manifest is an ordinary miss; a missing blob rejects that seed. Neither missing response disables the remote. A seed does not provide missing tool or dependency archives.

The inventory preserves native compiler metadata and records source contents and times. Identical source contents regain their recorded times; changed inputs remain newer than restored compiler work. Compiler fingerprints and dep-info retain their original bytes. Capture and restore read the compiler tree to verify it and inspect source contents to bind freshness; this work happens only for an active, readable OCI CI seed consumer. REAPI-only remotes skip it, and installed-tool use does not trigger it. Archive bounds are 1 GiB compressed, 12 GiB expanded and 32 MiB for the inventory; an oversized seed is refused.

Windows native actions freeze platform installation, home/profile and architecture inputs used by SDK discovery, alongside the declared compiler controls. They remain explicit action inputs; native launches do not recover undeclared values from the parent environment.
