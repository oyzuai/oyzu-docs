The public tool index (toolIndex, tools check --catalog, tools migrate, tools trust)

CLI reference

Published from the canonical docs/reference/tool-index.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Status: experimental, provisional. Milestone M3 of the tools catalog plan. The client is implemented and tested against signed fixtures and a real public-good Sigstore bundle. By default it reads the public index published as GitHub releases of oyzuai/tool-index. Field names, settings, codes and exit statuses are drafts pending maintainer review.

Purpose​

Oyzu publishes one public, signed tool index built by a scheduled job in the oyzuai/tool-index repository: every registry package's versions, with per-platform download URLs and the SHA-256 Oyzu verified. install and tools versions for registry packages read it instead of the pinned aqua registry file, the GitHub releases API and the publisher's checksum file. Only the artifact download itself still goes to the vendor.

The design is in the platform repository (OEP-draft-configuration-and-tool-lifecycle, public-tool-index.md). The file format is tool-index.schema.json.

Oyzu provider coverage​

The client accepts indexed Java, Node, Go, Python, Maven, Gradle, Helm, kubectl, k3d, Liquibase, Tailscale, npm, pnpm and Rust. Archive records name the exact URL the installation adapter uses. Rust records approve the channel manifest and carry its component digests plus a pinned rustup bootstrap; see Rust installation. Without an organization catalog, a matching verified index record is preferred over live publisher metadata. Under a catalog, a missing tool remains TOOL_NOT_IN_INDEX, and an unapproved version is TOOL_NOT_IN_CATALOG. Cargo helpers remain unavailable under a catalog.

The index producer can obtain these records with oyzu --json tools evidence --provider <name> --version <exact-release>. The default evidence matrix has five entries: Linux amd64/arm64 GNU, macOS arm64/amd64 native and Windows amd64 MSVC. macOS amd64 is emitted as unsupported; Tailscale also emits unsupported macOS arm64 and Windows records. This preserves index coverage without adding unsupported installation hosts. The evidence reference owns the publisher sources and checksum formats.

Client support does not publish index records. The separate tool-index job still needs its provider configuration and pinned Oyzu revision updated. See implementation status for automated verification; live publisher evidence and native ARM64 installation remain unverified.

A network that blocks the asset host needs a mirror.

Trust and caching​

Large indexes validate independent tool records with up to four workers, bounded by available CPUs. Every record digest is still recomputed; signature, freshness, withdrawal and rollback checks remain required. Failures are reported in document order. This changes preparation cost without adding a setting or trusting an unverified persistent parsed index.

Each release is a few files in one flat directory: index.json, index.json.zst (the same bytes compressed with zstd, about a twentieth of the size; transport only) and index.json.sigstore.json, a Sigstore bundle v0.3 written by cosign attest-blob --statement in the index repository's release workflow, signing an in-toto v1 statement of predicate type https://sigstore.dev/cosign/sign/v1 that names index.json's SHA-256. The workflow signs keylessly: Fulcio issues a short-lived certificate for the workflow's GitHub Actions identity, and the signature is recorded in the public Rekor transparency log. Oyzu verifies the bundle itself (no cosign or network call) against the trusted root.

Both Rekor generations are accepted, because the public Sigstore service decides which log cosign writes to and can move signing to Rekor v2 without notice:

  • Rekor v1 entries (dsse 0.0.1) carry a signed entry timestamp (SET). The signing time is the entry's integrated time.
  • Rekor v2 entries (hashedrekord 0.0.2, as cosign logs a DSSE envelope there) carry an inclusion proof up to a checkpoint the log signed, and no time. The signing time comes from an RFC 3161 timestamp in the bundle, signed by a timestamp authority in the trusted root.

The checks:

  1. The bundle is v0.3 with exactly one log entry and one DSSE signature.
  2. The signing time: for Rekor v1 the integrated time; for Rekor v2 the first RFC 3161 timestamp whose CMS signature is by a trusted timestamp authority's certificate (valid for time stamping then, and within the authority's validity period) and whose message imprint is the hash of the DSSE signature.
  3. The log: the Rekor key whose log id matches the entry and that was valid at the signing time. For Rekor v1, its ECDSA P-256 SET over the entry verifies, and the entry records this payload, this signature and this certificate. For Rekor v2, the entry is rebuilt from the bundle (SHA-256 of the DSSE pre-authentication encoding, the signature and the certificate); its RFC 6962 inclusion proof leads to the root hash of a checkpoint whose origin is the log's host name and that the log key (Ed25519 or ECDSA P-256) signed.
  4. The certificate chains to a Fulcio CA valid at the signing time, for code signing, validated at that time, which must fall within the certificate's validity.
  5. The certificate names the expected identity: SAN URI toolIndex.identity, OIDC issuer https://token.actions.githubusercontent.com and runner environment github-hosted. An index signed on a self-hosted runner is refused.
  6. The DSSE signature verifies with the certificate's key.
  7. The payload is an in-toto statement (cosign's https://sigstore.dev/cosign/sign/v1 predicate) whose subject has the SHA-256 of the exact index.json bytes.

Then the document is checked strictly. Unknown fields are refused, tools must be sorted with lowercase oyzu: ids (names are matched without regard to case), and every record's digests must recompute with the artifact-set rules. Finally freshness: the document's expires must be in the future, and its serial must not be lower than the highest accepted one, nor equal to it with different bytes (rollback).

Oyzu fetches index.json.zst and decompresses it (at most 256 MiB); only when the server answers 404 for it, as a mirror holding just index.json does, is index.json fetched. The signature is checked against the decompressed bytes, so the compressed file needs no trust of its own.

The last verified pair is kept under <store>/catalogs/tool-index/<key>/ (the key covers the URL, trusted root and identity). The highest accepted serial and the SHA-256 of that copy are kept apart from it, in <store>/state/tool-index/<key>.json (keyed by URL and identity only), so deleting the cache or refreshing the trusted root does not reset rollback protection, and a cached copy older than that serial is refused too. Both paths are scoped to the resolved store: separate stores have independent histories, even for the same URL and signer. In-process reuse also includes the store, settings and offline mode. See the default store location for disposable-home isolation on Windows. A copy fetched less than an hour ago is verified again and used without any request (index.source is recent); the job publishes once a day, and without this every command downloaded the whole index. After an hour the source is asked again. When a newer copy cannot be fetched or fails verification, the cached pair is verified again and used while it is unexpired. Output says so: index.source is cached, and index.warning gives the reason. With --offline (tools versions, tools check --catalog, tools migrate) only the cached copy is read and nothing is fetched; install --offline replays the lock and resolves nothing. If no valid copy exists, the command fails with TOOL_INDEX_UNAVAILABLE, naming both the fetch failure and the cache state.

Not checked: signed certificate timestamps from the CT log; for Rekor v1, the inclusion proof and RFC 3161 timestamps (the SET is the log evidence); for Rekor v2, the timestamp authority's ESS signing-certificate attribute (the signer is identified by its key, which must be a trusted authority's).

Resolution order​

For a registry package (oyzu: ids and their aqua: aliases, not github:), after the lock:

  1. The index. The package matches an index tool by its origin. The request (1.16.5, v1.16.5, 1.16 or latest) selects a version that has a resolved record for the platform. Prefixes and latest skip pre-releases. The lock receives the record's artifact URL and its verified SHA-256, with no other request.
  2. Local recipe evaluation (standalone only), as before, when the index does not list the package, has no matching release, or has only a discovery-tier record without a verified SHA-256.

With managed configuration, step 2 never runs. The miss fails with TOOL_NOT_IN_INDEX. An index the tool lists as excluded fails with TOOL_EXCLUDED. A listed version without a build for the platform fails as an unavailable platform. A configured index that cannot be verified is always an error and never falls back silently.

With an organization tool catalog configured, step 1 considers only the versions the organization approved, and step 2 never runs.

Withdrawn versions​

The index can withdraw a version (its upstream assets were deleted, the release was broken). The version keeps its records, so a lock or digest still matches it by name, and gains a reason:

{ "version": "4.20.0", "released": {...}, "sets": [...],
  "withdrawn": { "reason": "upstream release assets were deleted (404)" } }

The reason is 1 to 512 characters; an index without withdrawals has no such field. The index repository lists withdrawals in config/withdrawn.toml.

  • A prefix or latest skips withdrawn versions, for registry packages and for Oyzu's providers that read the index (Java, Node, Go, Python).

  • An exact request naming a withdrawn version, a prefix whose every match is withdrawn, and an existing lock naming one are refused, never handed to local recipe evaluation or the publisher's live metadata:

    TOOL_VERSION_WITHDRAWN: oyzu:golang-migrate 4.20.0 was withdrawn from the tool index: upstream release assets were deleted (404). The newest available version is 4.19.1.

    The last sentence names the newest stable, non-withdrawn version with a build for this host, and is left out when there is none. A lock is checked against the index the install can read (fetched, or with --offline the cached copy); when no index can be read, a locked install goes ahead as before.

  • tools versions lists a withdrawn version under excluded with TOOL_VERSION_WITHDRAWN and the reason, and tools check --catalog reports it as withdrawn.

Under an organization catalog the catalog marks the version withdrawn too, and the message names the newest version the catalog serves; see the catalog reference.

tools versions aqua:owner/repo lists an indexed package from the index: newest first, with tags, release time (publisher or first-seen) and versions excluded for this platform. With --offline it reads only the cached copy, and it needs no GITHUB_TOKEN. The JSON source is tool index, and index describes the URL, version (the document's serial), expires and whether the copy was fetched or cached.

oyzu tools check --catalog​

The command checks every tool declared here (project, or global outside a project) against the index. It installs and writes nothing. With toolCatalog.url set it judges governed tools against the organization catalog instead, with the statuses in the catalog reference. By default, availability is judged on this host. Explicit tools.platforms entries add required coverage; the default multi-platform pin matrix does not. An omitted record on another host does not prevent installation here.

oyzu tools migrate [--write]​

This command moves declarations onto Oyzu names. It reads mise.toml (or .mise.toml) [tools] and the project's oyzu.toml. By default it is a dry run: the result shows every change and the complete proposed oyzu.toml (after). --write replaces oyzu.toml atomically, keeping its comments and formatting. mise.toml is never modified.

mise spellingBecomes
node, go, … (built-in tools) and core:<name>The bare name
A short name that resolves to a supported backend (gh, terraform)Unchanged; bare names resolve against the index
aqua:owner/repo (also already in oyzu.toml)The tool's index name (terraform), or oyzu:owner/repo (lowercased) when the index does not list it or none is configured

A version array keeps its first entry, and a table keeps its version; anything dropped is noted. An entry whose name oyzu.toml already declares is reported as a conflict, and the existing declaration is kept. Running the command again after --write reports no change. Resolving short names reads the pinned mise name catalog, which is downloaded once into the store.

oyzu tools trust refresh and status​

The trusted root compiled into the CLI is a copy of Sigstore's trusted_root.json (target version 14 of Sigstore's root-signing TUF repository). When Sigstore rotates a key or adds a log, oyzu tools trust refresh takes the newer root without an Oyzu release:

oyzu tools trust refresh                          # from https://tuf-repo-cdn.sigstore.dev/
oyzu tools trust refresh --from /media/sigstore   # from a copy, on a machine without network
oyzu tools trust status                           # which root verifies the index now

--from takes an HTTPS URL of a TUF repository mirror or a directory. A directory may hold the repository's files as Sigstore serves them (16.root.json, timestamp.json, 166.snapshot.json, 14.targets.json, targets/<sha256>.trusted_root.json) or be a checkout of github.com/sigstore/root-signing (metadata/…, targets/trusted_root.json).

The refresh runs the TUF client checks, starting from Sigstore's TUF root version 15 that is compiled in (or from the last refresh):

  1. Each newer root (N.root.json, N+1, N+2, …) must be signed by the threshold of the previous root's root keys and of its own; the final root must be unexpired.
  2. timestamp.json, the snapshot it names and the targets file the snapshot names must be signed by the threshold of their role's keys in that root (ECDSA P-256 over the canonical JSON of signed), have the named versions, be unexpired, and not go below the versions accepted before. A targets version below the built-in root's (14) is refused.
  3. trusted_root.json must have the length and SHA-256 the targets file lists, and parse.

The result is kept in <store>/state/sigstore-root.json (the rotated roots, the targets metadata and the bytes) and verified again, offline, every time it is read: its roots must chain from the compiled-in TUF root and its targets metadata must list the bytes, so editing the file cannot change trust (it fails with TOOL_TRUST_INVALID; delete it to return to the built-in root). It verifies the index instead of the built-in root only while its targets version is newer; a later Oyzu release with a newer built-in root takes over again. toolIndex.trustedRoot, when set, wins over both.

refresh reports status (refreshed or unchanged), the TUF root and targets versions with their expiry, the trustedRoot SHA-256 and whether it is inUse (refreshed or built-in). status reports inUse (built-in, refreshed or configured), the built-in root and the kept refresh. Expiry is checked only when refreshing: Sigstore's timestamp expires within about a week, so an offline copy must be recent when it is used.

Every command that loads the index with Sigstore's production root also warns with TOOL_TRUST_ROOT_EXPIRING while the newest TUF root it holds (the compiled-in version 15, or the one a kept refresh rotated to) expires within 30 days, or has expired. Index verification does not depend on it; the warning says to run oyzu tools trust refresh while the anchor it starts from is current.

Limitations​

  • A release published within the last hour can go unseen until the hour is up; there is no flag to force a fetch.
  • The two files are fetched separately from the latest release. If a new release is published between the two requests, the pair does not verify and the cached copy is used (with its warning) until the next run.
  • The compiled-in trusted root is Sigstore's production root as published through its root-signing TUF repository on 2026-10-10 (third_party/sigstore-rs/). It is updated with Oyzu releases or by oyzu tools trust refresh, never fetched automatically. The refresh has been run against a checkout of root-signing (2026-10-10); a run against tuf-repo-cdn.sigstore.dev has not been recorded yet. tools evidence still verifies GitHub attestations against the compiled-in root.
  • The trust anchor of tools trust refresh is TUF root version 15, which expires 2026-11-20; a refresh after that needs the repository to carry version 16 or later (Sigstore re-signs its root before expiry). Commands warn with TOOL_TRUST_ROOT_EXPIRING from 2026-10-21 until a refresh rotates past it.
  • Rekor v2 support is verified against bundles built in the tests (and checked with sigstore-go), not yet against a public-good Rekor v2 bundle: none existed for a cosign DSSE signature when it was written. Only ECDSA (P-256 or P-384) timestamp authorities are supported.
  • Oyzu's archive providers carried by the index (oyzu:<name>, origins core:<name>) resolve from it under an organization catalog; their records are oyzu tools evidence --provider <name> output (see recipe resolution and evidence). Without a catalog, a provider request takes the newest verified index record it matches and reads the publisher's live metadata only when the index has none (no index, a provider the index does not carry, or no verified record for the request). Once an exact indexed version is selected, an omitted or unsupported platform is unavailable; it does not trigger a publisher lookup. A version the index lists with no records at all (not yet verified, or older than the versions whose records the index keeps) falls back to the publisher like a version the index does not list. Portable pinning keeps that version's available platforms, so a missing Linux ARM64 record does not prevent installation on another supported host. This matches standalone registry-package resolution. An index that cannot be verified is an error, as for registry packages.
  • A registry package matches an index tool by the tool's id (oyzu:terraform) or by the package of its origin (oyzu:hashicorp/terraform, aqua:hashicorp/terraform), ignoring case.
  • Release dates come from the index (released). There is no minimum-release-age rule yet.
  • Only Linux x86-64 has been run.

Verification​

  • Verifier tests (src/tools/index/sigstore/tests.rs) on a real public-good bundle (a cosign v3 DSSE in-toto bundle, kubewarden-controller release.yml@refs/tags/v1.34.0) with Sigstore's production trusted root: it verifies for its subject digest and signer, and is refused for another identity, issuer or runner environment, another digest, a tampered payload, signature, SET, log entry body, integrated time or certificate, and a trusted root without the CA or the Rekor key.
  • Rekor v2 tests (src/tools/index/sigstore/rekor_v2_tests.rs) build a bundle the way cosign v3 logs a DSSE signature to Rekor v2: a Fulcio-style certificate, an Ed25519 log with a signed checkpoint and an RFC 6962 proof (from an independent tree builder), and an RFC 3161 timestamp. It verifies at the stamped time, and is refused without a timestamp, with no trusted timestamp authority, for a timestamp over another signature, after the certificate expired or before the authority was trusted, with a tampered timestamp, checkpoint, proof hash, log index or log origin, without an inclusion proof or a trusted log key, and for an edited or unsigned payload. On 2026-10-10 the same fixture verified with sigstore-go v1.3.0 (WithTransparencyLog(1), WithSignedTimestamps(1), the pinned identity and the artifact digest), and sigstore-go refused it with one proof hash flipped. The production trusted root parses with its Rekor v2 log (log2025-1.rekor.sigstore.dev, Ed25519) and its timestamp authority.
  • Withdrawals: withdrawn_versions_are_skipped_and_refused_by_name and withdrawal_reasons_are_bounded_and_strict (src/tools/index/tests.rs); the compiled CLI against a signed fixture index with terraform 1.16.5 withdrawn (tests/integration/tool_index.rs withdrawn_versions_are_skipped_listed_and_refused: tools versions excludes it and offers 1.15.3, install of it fails before anything is locked, tools check --catalog reports withdrawn for the exact version and for 1.16), and a_locked_withdrawn_version_is_refused (ignored, downloads terraform; run on 2026-10-11): an installed, locked 1.16.5 is refused once the index withdraws it.
  • Client tests (src/tools/index/tests.rs): lookup and version selection, malformed documents, fetch and cache, tamper fallback, rollback (lower serial, same serial with other bytes), expiry of the fetched and the cached copy, foreign trusted roots, other identities, self-hosted runners and offline cache reads. Bundles are signed in-process by a test-only Sigstore instance (tests/support/tool_index_fixture.rs: a P-384 CA chain, P-256 leaf and log key).
  • Rollback state (rollback_state_survives_deleting_the_cache_and_holds_old_cached_copies_to_it): after serial 5, deleting the cache and serving serial 2 is a rollback, and so is an older genuine copy put back into the cache (offline, or looking freshly fetched).
  • Trust refresh (src/tools/index/trust_root_tests.rs): with real root-signing metadata (root 14 to 15 rotation, timestamp 804, snapshot 166, targets 14 and the compiled-in trusted_root.json, tests/fixtures/sigstore-tuf/) the refresh verifies and reports the built-in root unchanged, and refuses the same files a week later (expired timestamp). Throwaway repositories with generated keys cover a root rotation that replaces the built-in root, a tampered kept file (TOOL_TRUST_INVALID), a short threshold, rollback of targets, targets older than the built-in root, wrong target bytes, a root signed only by its own keys and one key listed under two ids. On 2026-10-10 the compiled CLI refreshed from a checkout of root-signing at fa6fe20 and reported targets 14, the built-in root. the_tuf_root_warns_thirty_days_before_it_expires checks the TOOL_TRUST_ROOT_EXPIRING window against the compiled-in root 15.
  • Expiry warnings: an_index_within_three_days_of_expiry_warns (unit) and the compiled-CLI an_index_close_to_expiry_warns (tests/integration/tool_catalog.rs): an index two days from expires reports TOOL_INDEX_EXPIRING, a 14-day one does not.
  • Compiled-CLI tests (tests/integration/tool_index.rs): the index is real tools resolve + tools evidence output for terraform 1.16.5 and 1.15.3 (tests/fixtures/tool-index/terraform.index.json), signed with the test instance and served over loopback HTTP. The tests cover tools versions, the tamper fallback, expiry, the trust settings' scope rule, an index from another identity, tools check --catalog and tools migrate.
  • install_resolves_from_the_index_and_locks_its_digest (ignored by default; needs releases.hashicorp.com) installs terraform 1.16.5 from the index and runs it. On 2026-10-10, with the earlier TUF-signed fixture, it passed through a proxy that refused github.com, raw.githubusercontent.com, api.github.com, release-assets.githubusercontent.com and static.crates.io. The only hosts contacted were releases.hashicorp.com and, from terraform itself, checkpoint-api.hashicorp.com. It passed again on Linux x86-64 with the Sigstore-signed fixture the same day (that run did not restrict GitHub hosts).
