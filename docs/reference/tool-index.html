The public tool index (toolIndex, tools check --catalog, tools migrate, tools trust)

CLI reference

Published from the canonical docs/reference/tool-index.md file. Features marked experimental remain experimental; check support limitations before relying on them.

The tool index is a public, signed list of every registry package's versions, with per-platform download URLs and the SHA-256 Oyzu verified for each file. oyzu install and oyzu tools versions read it instead of asking GitHub or each publisher, so only the download itself goes to the vendor. You don't need to configure anything to use it.

Note: Experimental. Settings, error codes and exit statuses may change. Supported on Linux x86-64; Windows and macOS are not supported yet.

By default Oyzu reads the index published as GitHub releases of oyzuai/tool-index, refreshed daily. The file format is tool-index.schema.json.

Oyzu provider coverage​

The index can carry Oyzu's own providers: Java, Node, Go, Python, Maven, Gradle, Helm, kubectl, k3d, Liquibase, Tailscale, npm, pnpm, Yarn and Rust.

  • Archive records name the exact download URL the provider uses.
  • Rust records approve a channel manifest and carry its component digests; see Rust installation.
  • Without an organization catalog, a provider request uses the newest verified index record that matches. It reads the publisher's live metadata only when the index has nothing for it (no index, a provider the index doesn't carry, or no verified record). Once an indexed version is selected, a platform it has no record for is unavailable; Oyzu doesn't look it up at the publisher.
  • Under a catalog, a tool missing from the index fails with TOOL_NOT_IN_INDEX, and an unapproved version with TOOL_NOT_IN_CATALOG. Cargo helpers aren't available under a catalog.

Index records are produced with oyzu --json tools evidence --provider <name> --version <exact-release>. See provider records for the publisher sources and checksum formats. The default matrix is Linux amd64 and arm64 (GNU), macOS arm64 and amd64, and Windows amd64 (MSVC). macOS amd64 records exist for Rust, Node, Go, Python, npm, pnpm, Yarn and Zig when the publisher provides them; other providers report it unsupported. Tailscale reports macOS and Windows as unsupported.

Configuration​

SettingValuesDefaultMeaning
toolIndex.urlHTTPS URL (HTTP only on loopback), or falsehttps://github.com/oyzuai/tool-index/releases/latest/download/Where the index is. false reads no index, and registry packages are resolved locally from their recipes (refused under managed configuration).

Settings marked "user or machine configuration only" fail with CONFIG_SCOPE in a project file.

# ~/.config/oyzu/config.toml
[toolIndex]
# A mirror instead of the public index (or `false` for no index):
url = "https://index.example.test/"
# Only for an index signed by another workflow or another Sigstore instance:
# identity = "https://github.com/example/tool-index/.github/workflows/release.yml@refs/heads/main"
# trustedRoot = "/etc/oyzu/sigstore-trusted-root.json"

The URL can point at a GitHub release directory, an Oyzu host or your own mirror. Trust comes from the signature and the pinned identity, not from the host.

The default URL redirects to the newest release (releases/download/index-v<serial>/) and then to release-assets.githubusercontent.com. If your network blocks that host, use a mirror.

Trust and caching​

Each index release has three files: index.json, index.json.zst (the same content compressed, used only for transfer) and index.json.sigstore.json, a Sigstore bundle. The index is signed keylessly by the index repository's GitHub Actions release workflow, and the signature is recorded in the public Rekor transparency log.

Oyzu verifies the bundle itself, offline, against the trusted root (no cosign and no extra network call). It checks that:

  • the bundle has exactly one log entry and one signature;
  • the log entry is signed by a Rekor key that was valid at signing time (Rekor v1 signed entry timestamps and Rekor v2 inclusion proofs with RFC 3161 timestamps are both accepted);
  • the certificate chains to a Sigstore Fulcio CA valid at signing time;
  • the certificate names toolIndex.identity, the GitHub Actions OIDC issuer and a GitHub-hosted runner (an index signed on a self-hosted runner is refused);
  • the signed statement names the SHA-256 of the exact index.json bytes.

Oyzu doesn't check certificate transparency timestamps, the Rekor v1 inclusion proof, or the timestamp authority's signing-certificate attribute. Only ECDSA (P-256 or P-384) timestamp authorities are supported.

Then the document itself:

  • Unknown fields are refused, tools must be sorted with lowercase oyzu: IDs, and every record's digests must recompute.
  • expires must be in the future.
  • serial can't go below the highest one accepted before, and the same serial can't have different content (rollback protection).

Oyzu downloads index.json.zst (up to 256 MiB uncompressed), or index.json if the server returns 404 for the compressed file. The signature is checked on the uncompressed bytes.

Cache​

  • The last verified index is kept under <store>/catalogs/tool-index/<key>/. The highest accepted serial is kept separately in <store>/state/tool-index/<key>.json, so deleting the cache doesn't reset rollback protection.
  • Each store has its own history.
  • A copy fetched less than an hour ago is used without a request (index.source is recent). After an hour, Oyzu checks for a new one.
  • If a newer copy can't be fetched or fails verification, the cached copy is verified again and used while it hasn't expired. index.source is cached and index.warning says why.
  • With --offline (tools versions, tools check --catalog, tools migrate), only the cached copy is read. install --offline replays the lock and doesn't read the index.
  • With no valid copy, the command fails with TOOL_INDEX_UNAVAILABLE, naming the fetch failure and the cache state.

Resolution order​

For a registry package (oyzu: IDs and their aqua: aliases, not github:), after checking the lock:

  1. The index. The package matches an index tool by ID (oyzu:terraform) or by its origin package (oyzu:hashicorp/terraform, aqua:hashicorp/terraform), ignoring case. The request (1.16.5, v1.16.5, 1.16 or latest) picks a version with a record for the platform. Prefixes and latest skip pre-releases. The lock gets the record's URL and verified SHA-256.
  2. Local recipe evaluation (standalone only), when the index doesn't list the package, has no matching release, or has no verified SHA-256 for it.
  • Under managed configuration, step 2 never runs; a miss fails with TOOL_NOT_IN_INDEX.
  • A tool the index lists as excluded fails with TOOL_EXCLUDED.
  • A listed version with no build for the platform fails as an unavailable platform.
  • A configured index that can't be verified is always an error, never a silent fallback.
  • With an organization tool catalog, step 1 considers only approved versions, and step 2 never runs.

Withdrawn versions​

The index can withdraw a version, for example when its upstream files were deleted or the release was broken. The version keeps its records, so a lock still matches it by name, and gains a reason (1 to 512 characters):

{ "version": "4.20.0", "released": {...}, "sets": [...],
  "withdrawn": { "reason": "upstream release assets were deleted (404)" } }

  • A prefix or latest skips withdrawn versions, for registry packages and for the providers that read the index (Java, Node, Go, Python).

  • An exact request for a withdrawn version, a prefix whose every match is withdrawn, and an existing lock entry for one are all refused:

    TOOL_VERSION_WITHDRAWN: oyzu:golang-migrate 4.20.0 was withdrawn from the tool index: upstream release assets were deleted (404). The newest available version is 4.19.1.

    The last sentence names the newest stable version with a build for your platform, if there is one.

  • A lock is checked against whatever index the install can read (fetched, or cached with --offline). If no index is readable, a locked install proceeds.

  • tools versions lists a withdrawn version under excluded with the reason, and tools check --catalog reports it as withdrawn.

  • Under an organization catalog, the message names the newest version the catalog serves; see the catalog reference.

Listing versions​

oyzu tools versions aqua:owner/repo lists an indexed package's versions, newest first, with tags, release time (publisher or first-seen) and versions excluded for this platform. With --offline it reads only the cached copy. It needs no GITHUB_TOKEN. In JSON, source is tool index, and index gives the URL, version (the serial), expires and whether the copy was fetched or cached.

oyzu tools check --catalog​

Checks every tool declared here (the project, or your global configuration outside a project) against the index. It installs and writes nothing. With toolCatalog.url set, it checks against the organization catalog instead (see the catalog statuses).

Availability is judged for this host plus any platforms listed in tools.lockPlatforms. Missing records for other default lock platforms don't count against a tool.

Exit status: 0 when nothing is refused, 1 when something is, 2 when toolIndex.url is false (TOOL_INDEX_NOT_CONFIGURED). JSON has tools[], the refused count, outcome and index.

oyzu tools migrate [--write]​

Moves tool declarations from mise.toml (or .mise.toml) into oyzu.toml under Oyzu names. By default it's a dry run that shows every change and the complete proposed oyzu.toml (after). --write replaces oyzu.toml atomically, keeping comments and formatting. mise.toml is never changed.

oyzu tools migrate          # show what would change
oyzu tools migrate --write  # apply it
mise spellingBecomes
node, go, ... and core:<name>The bare name.
A short name for a supported backend (gh, terraform)Unchanged; bare names resolve against the index.
aqua:owner/repo (also when already in oyzu.toml)The tool's index name (terraform), or oyzu:owner/repo (lowercased) if the index doesn't list it.
github:owner/repoUnchanged.
ubi:owner/repogithub:owner/repo.
asdf:, vfox: and short names only available through themLeft out, with the reason.
Other backends (npm:, pipx:, cargo:, go:, ...)Left out, with the reason.
  • A version array keeps its first entry, and a table keeps its version. Anything dropped is noted.
  • A tool oyzu.toml already declares is reported as a conflict, and the existing declaration is kept.
  • Running it again after --write reports no change.
  • Short names are resolved from mise's name list, downloaded once into the store. --offline reads only the cached index.

oyzu tools trust refresh and status​

Oyzu ships with a copy of Sigstore's production trusted_root.json. When Sigstore rotates a key or adds a log, oyzu tools trust refresh fetches the newer root without waiting for an Oyzu release:

oyzu tools trust refresh                          # from https://tuf-repo-cdn.sigstore.dev/
oyzu tools trust refresh --from /media/sigstore   # from a copy, on a machine without network
oyzu tools trust status                           # which root verifies the index now

--from takes an HTTPS URL of a TUF repository mirror or a directory. The directory can hold the repository files as Sigstore serves them (16.root.json, timestamp.json, 166.snapshot.json, 14.targets.json, targets/<sha256>.trusted_root.json) or be a checkout of github.com/sigstore/root-signing.

The refresh runs the standard TUF client checks, starting from the TUF root built into Oyzu (or the last refresh): each newer root must be signed by the previous and its own root keys; the timestamp, snapshot and targets files must be properly signed, unexpired and not older than before; and trusted_root.json must match the length and SHA-256 the targets file lists.

  • The result is saved in <store>/state/sigstore-root.json and verified again, offline, every time it's read. An edited file fails with TOOL_TRUST_INVALID; delete it to go back to the built-in root.
  • A refreshed root is used only while it's newer than the built-in one. A later Oyzu release with a newer built-in root takes over.
  • toolIndex.trustedRoot, when set, wins over both.
  • Expiry is only checked when refreshing. Sigstore's timestamp expires within about a week, so an offline copy must be recent.

refresh reports status (refreshed or unchanged), the TUF root and targets versions with their expiry, the trusted root's SHA-256, and inUse (refreshed or built-in). status reports inUse (built-in, refreshed or configured), the built-in root and the saved refresh.

While the TUF root Oyzu starts from expires within 30 days (or has expired), commands that load the index warn with TOOL_TRUST_ROOT_EXPIRING. Index verification still works; run oyzu tools trust refresh to clear it. The built-in TUF root (version 16) expires on 2027-04-22.

Limitations​

  • A release published in the last hour may not be seen until the hour is up. There is no flag to force a fetch.
  • If a new release is published between Oyzu's two downloads, they won't verify together, and the cached copy is used (with a warning) until the next run.
  • The built-in trusted root is never refreshed automatically. Update Oyzu or run oyzu tools trust refresh. tools evidence always uses the built-in root.
  • There is no minimum-release-age rule.
  • Supported on Linux x86-64 only.
