Platform secrets

CLI reference

Published from the canonical docs/reference/secrets.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Status: experimental client. oyzu secrets list|create|set|rm implement the CLI side of the draft secrets contract. They are verified against a scripted local server. That client evidence does not qualify CLI login or deployment against a live platform. Use the endpoint's advertised authenticated caller setup; this page does not establish deployment or provisioning status.

Purpose​

A secret is a named value your platform account keeps for the account, one of its organizations or one of its projects: a token a build job needs (build exposure) or a webhook secret the platform verifies deliveries with (internal exposure). Values are write-only: you set or replace a value and nothing ever shows it back, to anyone, including account owners. No command or API operation returns a stored value. For a custom webhook secret, --generate makes the value on your machine and shows it to you once, to paste into the sender.

Everything else Oyzu does stays local and works without an account; these commands are an optional platform path.

Prerequisites​

The same settings and token as remote runs:

  • platform.url and platform.account in configuration (user scope is the usual place), for example oyzu config set --global platform.account payments.
  • A platform credential from the shared credential provider: the session stored by oyzu auth login (used from a terminal, or when platform.authentication.provider is session), or a bearer in OYZU_PLATFORM_TOKEN. The token is a credential, so it is read from the environment and never from a configuration file.

The draft authentication contract describes the intended credential-provider behavior. A supplied token is used as is and never created or refreshed; do not obtain one by copying a browser session or hand a person's session to unattended automation. Unattended runs need an explicit provider or token and never use a developer's stored session. Possession alone does not authorize a Secrets operation.

No Git checkout is needed.

Usage​

CommandDoes
oyzu secrets listThe account's secrets: name, type, exposure, value version, description
oyzu secrets list --project webA project's secrets (--org <org> for an organization)
oyzu secrets create <name> --exposure internalCreate a secret with no value. --exposure build for one jobs receive; --type file for exact bytes such as a key file (default text); --description
oyzu secrets set <name> < value.txtSet or replace the value from standard input
oyzu secrets set <name> --file key.pemSet or replace the value with a file's exact bytes
oyzu secrets set <name> --generateGenerate a value, set it and print it once
oyzu secrets set <name> … --overlap 24hKeep the replaced value valid for 24 hours (at most 168h; h, m or s)
oyzu secrets rm <name> --previousEnd an overlap now, for a replaced value that leaked
oyzu secrets rm <name>Delete the secret and all its values

--org and --project work with every command; without them the command acts on the account itself. Organizations and projects are named by their identifier within the account. set and rm look the name up in that scope (a secret id works too) and fail with SECRETS_NOT_FOUND, naming the create command, when there is no such secret; set never creates one.

A typical custom webhook:

oyzu secrets create release-webhook --exposure internal --description "Release tool deliveries"
oyzu secrets set release-webhook --generate

Rotating it without dropping deliveries: oyzu secrets set release-webhook --generate --overlap 24h, update the sender, then oyzu secrets rm release-webhook --previous once it uses the new value.

Where a value comes from​

A value is read from standard input or --file, or generated with --generate; never from a command-line argument, so it does not land in shell history or process listings. Standard input must be piped or redirected: when it is a terminal, set fails with SECRETS_VALUE_REQUIRED instead of echoing what you type. The bytes are sent exactly as read, so echo token | oyzu secrets set x stores a trailing newline; use printf '%s' "$TOKEN" or a file without one. A value must not be empty and is at most 64 KiB; a text secret must be UTF-8 (the platform checks). Both are checked before anything is sent.

--generate draws 32 bytes from the operating system's cryptographically secure random source and uses them as 64 lowercase hexadecimal characters, which every webhook sender accepts. The value is printed once, after the platform has stored it. If the platform refuses the request, the value is discarded and never shown.

Output​

Text mode leads with the outcome. A listing is a table; the Value column shows the version, and during an overlap when the previous one stops being valid, or not set:

Secrets · project web of payments

Name       Type  Exposure  Value                                                   Description
npm-token  text  build     version 2 (version 1 valid until 2026-10-11T09:05:00Z)
hook       text  internal  not set                                                 Release tool

Values are write-only: no command shows a stored value. Replace one with `oyzu secrets set <name>`.

A generated value is shown once with a warning:

✓ Set the value of release-webhook (version 1)

Generated value

  3f9c…(64 hexadecimal characters)

Copy it into the sender's webhook settings now. It cannot be shown again; if it is lost, set a new one.

With --json, stdout carries one record with kind, account and scope: secrets (with secrets, the contract's metadata), secret-created and secret-overlap-ended (with secret), secret-value-set (with secret, and generated_value only for --generate) or secret-deleted (name, id). Treat the JSON output of --generate as sensitive: it holds the value.

Errors and recovery​

Exit status is 0 on success and 2 on any refusal. Platform refusals keep the contract's code with a SECRETS_ prefix and the platform request id, for example SECRETS_RESOURCE_CONFLICT (name taken, no previous value, or a sign-only secret, which only the platform manages), SECRETS_PERMISSION_DENIED, SECRETS_UNAUTHENTICATED (run oyzu auth login, or set a current OYZU_PLATFORM_TOKEN) or SECRETS_VALIDATION_FAILED (with the failing field). Client-side failures are SECRETS_NOT_CONFIGURED, SECRETS_NOT_FOUND, SECRETS_VALUE_REQUIRED, SECRETS_VALUE_EMPTY, SECRETS_VALUE_TOO_LARGE, SECRETS_VALUE_UNREADABLE, SECRETS_OVERLAP_INVALID and SECRETS_UNREACHABLE.

Listing retries a 503 or a transport failure with backoff, like remote runs. A create, set or delete is sent once: retrying a value could create a second version and, with an overlap, retire the value it was meant to keep. If one fails in transit, run oyzu secrets list to see what happened.

Creation requires HTTP 201 and metadata with a valid id, the requested name, scope, type and exposure, a description and valid creation/update timestamps. Malformed responses fail with SECRETS_RESPONSE_INVALID in human and JSON modes instead of reporting creation. The server may have created the secret: use oyzu secrets list to check before retrying, and check platform/client compatibility. A returned secret value is rejected rather than printed.

Security​

  • No command reads a value back; the contract has no such operation.
  • Values are never taken from arguments, never logged, and never written to disk by the CLI. A generated value exists only in memory until it is printed.
  • The credential is sent only to platform.url, over the shared outbound transport (proxy and extra trust settings apply); redirects are not followed.
  • sign-only secrets (the platform's own integration keys) are listed but cannot be created or changed with these commands.

Limitations​

  • Not qualified against a deployed platform; portal entry and per-project permissions are not implemented yet, and login is verified only against a local conformance fake.
  • No interactive hidden prompt for typing a value; pipe it or use --file.
  • Exposure, type and scope are fixed at creation; to change one, create a new secret.

Verification​

cargo test --test integration secrets_cli runs the compiled CLI against a scripted server: stdin bytes reach the server exactly once and never appear in output, --generate prints exactly the value it sent, names resolve per scope, and refusals keep their code and request id. Unit tests cover value sources and limits, overlap syntax, generation, argument parsing (no value argument, no sign-only) and the human layout.
