How oyzu compares

CLI reference

Published from the canonical docs/reference/how-oyzu-compares.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Oyzu gives teams one workflow for tools, tasks and builds across existing native projects. It runs ecosystem tools and collects artifacts and reports into a build bundle. Standalone builds, tool management and tasks need no Oyzu account.

Status: experimental. Support depends on the builder, project shape, platform and installed plugin. Planned marks capabilities not shipped for the stated scope; check the ecosystem support matrix before adopting a workflow.

Choose by the problem you need to solve​

These are workflow tradeoffs, not performance rankings. No speedup or feature parity across these tools is promised.

For supported isolated Linux builds, Oyzu can use crun, a container runtime that needs no Docker daemon.

AlternativeWhere it is stronger or simplerWhere Oyzu fits today
Bazel / Buck2Choose an explicit rule-based build graph when you need control over individual build actions and remote execution. Both Bazel and Buck2 support executing actions on remote workers.Oyzu discovers supported native projects and runs their own build tools. Its REAPI integration stores cache results. Planned: REAPI remote execution.
Gradle / MavenKeep the native tool when your needs are inside its project model: Gradle caches eligible task outputs locally and remotely, and Maven provides a plugin-driven lifecycle.Oyzu wraps Gradle or Maven, selects tools and collects artifacts and reports. On Linux crun, compatible Java plugins reuse eligible module/project lifecycles independently, keeping compilation, archives and test evidence together. Unbounded module views retain the whole lifecycle. Native Java lifecycles with incomplete reads rerun.
Nx / TurborepoNx and Turborepo already cache task results. They are a more direct fit when your main requirement is scheduling and caching package tasks in a JavaScript workspace.Oyzu combines supported Node builds with other native targets, tools, artifacts and report requirements. Isolated npm stages and package-local npm/pnpm/Yarn Classic workspace members can reuse on Linux crun. Root aggregate scripts retain workspace-wide reads. Package-manager and workspace limits still apply, including unsupported Yarn Plug'n'Play and per-member workspace application artifacts.
Cargo and other native toolingCargo, Go, pip and other native tools remain the direct route to their own commands and configuration. For one ecosystem with an adequate existing workflow, using them directly avoids an orchestration layer.Native Oyzu builds invoke those tools and gather their outputs. Rust builds retain Cargo incremental state in private workspaces; Oyzu adds common selection, check and bundle handling. It does not replace Cargo dependency resolution or promise identical support for every native command.
mise / asdfmise manages tools, environment variables and tasks; asdf offers plugin-based tool version switching. Keep them when those capabilities satisfy the requirement or a needed tool is outside Oyzu's supported providers.Oyzu offers tool installation and locking, shell activation and tasks, connected to supported builds and bundles. It does not support every tool-manager plugin. Planned: general macOS support; the Intel Zig exception is listed below.
CI-only cachingA CI cache that restores selected files, such as workflow dependency caching, can be enough when you only need to avoid repeated downloads in an existing pipeline. It requires less adoption than adding a build orchestrator.Oyzu's action cache derives keys from build inputs and restores eligible outputs and reports locally, with optional shared storage. It distinguishes reused checks from fresh execution. A hit does not prove a test ran now, and the experimental remote cache is unsigned.

What the cache distinction means​

Oyzu's action identity includes source inputs, commands, configured environment, toolchain, prepared dependencies and builder identity. Cache keys and per-language cache paths are not user-authored. This is useful when you want the same reuse rules in local builds and CI, rather than maintaining archive keys in pipeline scripts.

Oyzu reuses a stage only when it can account for all its inputs and bound its outputs. Rust has native stage and compiler-result reuse with documented limits. On isolated Linux crun, npm stages, supported Node workspace members, Helm, eligible Go application stages and Java lifecycles can reuse results. Compatible Java plugins reuse eligible Maven modules and Gradle projects independently and keep Ant's selected targets together. See stage reuse for each builder's limits and action caching for admission rules.

The .NET implementation supports admitted compile/test/pack reuse, per project for eligible solutions, but the current catalog package lacks a capability required by this CLI. Use a compatible plugin as described in .NET builds. Delivery through the catalog is Planned. Full Python complete-read reuse is also Planned.

An unchanged build can execute unbounded stages again. Moving a checkout can also invalidate stages whose retained outputs contain location-specific data. Native builds run with your account's file and network access; caching adds no sandbox. Choose isolated execution when that boundary is required.

Native Windows stages with incomplete reads run again, including arbitrary Node scripts and Maven/Gradle lifecycles. Windows Vite/uv complete-read enforcement is Planned. Python 0.1.3 refuses Windows uv; later plugin releases admit it, rerunning each time. Clearing the cache cannot make those stages eligible. Native temporary-directory changes alone do not invalidate eligible actions: Oyzu replaces TEMP, TMP and TMPDIR with private paths. Home/profile values remain keyed. See temporary-directory keying.

Planned capabilities and current limits​

CapabilityAvailability
Stage reuseExperimental for admitted stages and compatible plugins. Planned: full Python complete-read reuse and Windows Vite/uv complete-read enforcement. Node member invalidation depends on the package manager and shared installation bytes; see workspace reuse.
Plugin delivery for implemented featuresPlanned: a .NET catalog package compatible with this CLI, and independent native Maven/Gradle formatting reuse in the next Java plugin release. Updating the CLI alone does not update plugin declarations. See .NET requirements and Java formatting.
Persistent Oyzu daemonPlanned. Do not choose Oyzu expecting a resident build graph or file-watching service. Existing native incremental state is a separate capability.
REAPI remote executionPlanned. Current REAPI support is action-cache storage for the server/client combinations in remote caching.
Additional publication supportPublishing has an experimental built-in OCI destination and GitHub/npm publisher implementations; plugin destinations require an available catalog package or binding. Planned: signed catalog delivery of those publishers, PyPI and offline plugin bundling. OCI publishing uses digest coordinates; mutable tags are not supported.
macOS supportPlanned for general use. The current exception is native Zig builds on Intel macOS. Apple silicon and other ARM64 hosts and targets are unsupported. Linux and Windows support is x64 and builder-specific. See platforms.

Start with your existing project​

Check its exact project shape in ecosystem support, then follow native local builds or the owning ecosystem reference. Use tool commands if installation and version selection are all you need, or build tasks for a shared task workflow. Keep the native tool when it already meets your needs; adopt Oyzu where the common workflow removes work for your team.
