Recipe resolution and evidence (oyzu tools resolve, oyzu tools evidence)

CLI reference

Published from the canonical docs/reference/tool-resolve.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Many tools are single-binary releases described only by community recipes (the public aqua registry). These two commands turn a recipe into a file that lists exactly what to download for each version and platform, and then check those downloads against what the publisher published. Use them to build or audit an artifact set or tool index records. Neither command installs anything.

Note: Experimental. Command and field names, exit code 3 and limit values may change. Supported on Linux x86-64; Windows and macOS are not supported yet.

  • oyzu tools resolve evaluates a recipe snapshot offline and writes one record per tool, version and platform (the discovery tier). It reads only the snapshot file you name and its flags, and writes to stdout.
  • oyzu tools evidence takes that output, downloads each artifact and its checksum file from the publisher, records the SHA-256 and size, compares them with the published checksum and fills in the verified tier. With --provider, it first builds the records for one of Oyzu's own providers from the publisher's listing.

Neither command reads or changes configuration, locks or the tool store, and neither needs an account. They ignore oyzu.toml, oyzu.lock, -C and --root.

Usage​

# 1. Download a registry snapshot yourself (resolve never fetches one)
curl -sSLO https://raw.githubusercontent.com/aquaproj/aqua-registry/v4.573.0/registry.yaml

# 2. Evaluate offline, pinned to the snapshot digest
oyzu --json tools resolve --registry registry.yaml \
  --registry-digest sha256:52a43b0b2817a56fe7566625809d7cca41a1178ccae2b152941221b516e70228 \
  --snapshot-tag v4.573.0 \
  --tool hashicorp/terraform --version v1.16.5 > terraform.discovery.json

# 3. Download and check the real files (needs the network)
oyzu --json tools evidence --set terraform.discovery.json > terraform.verified.json

Without --json, both commands print a summary: the outcome, a table of records, unsupported platforms and errors with reasons, and next steps.

tools resolve inputs​

FlagMeaning
--registry FILEThe merged registry.yaml. A directory (the per-package tree form) is rejected with SNAPSHOT_INVALID.
--registry-digest sha256:HEXReject the snapshot unless its SHA-256 matches (SNAPSHOT_DIGEST_MISMATCH).
--snapshot-tag, --snapshot-commitLabels recorded in the output. Not checked.
--tool NAME (repeatable), --tools-file FILERegistry package names such as hashicorp/terraform. The file has one name per line; # starts a comment.
--version V (repeatable)Exact upstream version as the recipe sees it, including any prefix (v1.16.5). Required.
--platform OS/ARCH/ABI (repeatable)Default: linux/amd64/gnu, darwin/arm64/native, windows/amd64/msvc, whatever the host. OS: linux, darwin, windows. Architecture: amd64, arm64. Other ABIs (for example musl) give an error record, PLATFORM_ABI_UNSUPPORTED.
--limit NAME=VALUE (repeatable)Lower a limit: recipe_nodes, recipe_bytes, recipe_depth, recipe_overrides, string_bytes, expression_steps, url_bytes, record_urls, regex_bytes, snapshot_bytes, output_bytes. Limits can't be raised.

Every tool and version is evaluated for every platform. The output is sorted by tool ID, version and platform, so flag order doesn't matter. Tool IDs are aqua:<package> (for example aqua:cli/cli), the same spelling mise uses.

What is evaluated​

Packages of type github_release and http. Oyzu has its own evaluator for the registry's data format, which supports:

  • Version selection: version_constraint, the first matching version_overrides entry, version_prefix and version_filter. The record's version.branch is top-level, override[N], or null when no branch applied.
  • Expressions: Version, SemVer, string and list literals, semver("..."), ==, !=, in, matches, startsWith, endsWith, contains, not/!, and/&&, or/||. semver() is false for a non-semver version. Pre-release versions only satisfy constraints that name a pre-release.
  • Templates: {{.Version}}-style fields, pipes, parentheses, if/else/end, and the functions trimV trimPrefix trimSuffix replace title semver regexFind index splitList eq ne.
  • supported_envs (with rosetta2 and windows_arm_emulation), replacements, platform overrides (first match), no_asset, error_message, complete_windows_ext, files, checksum, cosign, minisign, slsa_provenance, github_artifact_attestations.

Anything else (a loop, an unknown function, recipe vars) is reported as RECIPE_FEATURE_UNSUPPORTED for that record, never guessed.

Output​

One JSON document (format: 1, kind: "artifact-sets") matching artifact-set.schema.json. It holds the engine, the snapshot (its digest plus your labels), the limits used and the records. Each record has a status:

StatusMeaningExit
resolvedURLs (artifact, checksum, signatures, ...), archive facts and declared evidence.0
unsupportedA normal result: PLATFORM_EXCLUDED, NO_ASSET, RECIPE_MESSAGE, SOURCE_KIND (build-from-source packages), VERSION_NOT_COVERED, PRIVATE_PACKAGE.0
errorCouldn't decide: LIMIT_EXCEEDED, RECIPE_INVALID, RECIPE_FEATURE_UNSUPPORTED, RENDER_FAILED, URL_NOT_HTTPS, PLATFORM_ABI_UNSUPPORTED.3

Each record carries digests.declared (the record without its verification results) and digests.full (everything except digests), computed over canonical JSON (RFC 8785). The output contains no time, host, user or path, so the same inputs always produce identical output.

GitHub release downloads are stored as the recipe renders them (github.com/...). Redirect targets are never stored.

Exit codes and errors​

ExitMeaning
0Complete; every record is resolved or unsupported.
1Bad input, no records: SNAPSHOT_INVALID, SNAPSHOT_DIGEST_MISMATCH (and for evidence: SET_INVALID, SET_SCHEMA_INVALID, SET_FORMAT_UNSUPPORTED, SET_DIGEST_MISMATCH). With --json, the standard error object (error, code, nextStep, exitCode) is on stdout.
2Usage problem, no records: FLAGS_CONFLICT, REQUEST_EMPTY.
3Complete, but at least one record is error (resolve) or a resolved record stayed at the discovery tier (evidence).
5Not found, no records: TOOL_NOT_IN_SNAPSHOT.

A process killed by the system (memory, time limit) writes nothing. Run one tool per process if you need to contain that.

tools evidence​

FlagMeaning
--set FILE or -A tools resolve document (or standard input). Every record's digests are checked first; a mismatch is SET_DIGEST_MISMATCH and nothing is downloaded.
--allow-host HOST (repeatable)Allow a host beyond those in the set's own URLs.
--verify METHOD (repeatable)Run only these methods; others are reported not-run.
--provider NAMEBuild the records for one of Oyzu's providers from its publisher instead of reading a set, then verify them the same way. Can't be combined with --set.
--version V (repeatable, with --provider)Exact provider release, such as 21.0.8. Required with --provider.
--platform OS/ARCH/ABI (repeatable, with --provider)Default: linux/amd64/gnu, linux/arm64/gnu, darwin/arm64/native, darwin/amd64/native, windows/amd64/msvc. Platforms the provider doesn't install get an unsupported record.

How files are checked​

For each resolved record, evidence downloads the artifact (hashed as it streams, never stored, up to 2 GiB) and the checksum file (up to 4 MiB, once per URL), and records verified.artifact (digest, size, publisher_digest, agree).

  • Up to five redirects are followed. Each hop must be an allowed host, or github.com to release-assets.githubusercontent.com. The hosts seen are listed in verified.observed_redirect_hosts.
  • HTTPS_PROXY, NO_PROXY and SSL_CERT_FILE are honored (see acquisition transport).
  • Each download is retried up to twice on network errors and HTTP 408, 429 and 5xx.
  • Credentials are never sent to publisher hosts. GITHUB_TOKEN, if set, goes to api.github.com only.

Each evidence entry gets an outcome in verified.results[].outcome:

OutcomeMeaning
verifiedFor checksum: the checksum file lists the artifact's name with a matching sha256 or sha512. For attestations and provenance: see below.
failedThe checksum file lacks the name, has conflicting or malformed values, couldn't be fetched, or doesn't match; or no attestation or provenance verifies. The detail says which.
verifier-unavailableOyzu has no verifier for the method (cosign, minisign, openpgp), or the algorithm (md5, sha1) or format (regexp) isn't supported. Never counted as verified.
not-runExcluded by --verify.

A record becomes tier: verified only when at least one entry verified and none failed. verified.lock then holds the strongest result: attestation when a GitHub attestation or SLSA provenance verified, otherwise digest-only. Otherwise the record stays discovery with verified.status: failed, and the command exits 3.

What a result means:

  • A checksum-verified record means these bytes match what the publisher's checksum file listed when fetched. It doesn't prove the checksum file is authentic, that a signature holds, or that you're allowed to use the tool.
  • An attestation-verified record also means a GitHub Actions workflow in the release's repository attested these exact bytes, or, for SLSA provenance, that a slsa-github-generator release built them from that repository. It says nothing about whether the workflow's source is trustworthy.

GitHub artifact attestations​

For github-attestation evidence (aqua's github_artifact_attestations), Oyzu asks GitHub for the attestations of the artifact's digest (GET https://api.github.com/repos/<owner>/<repo>/attestations/sha256:<digest>?predicate_type=https://slsa.dev/provenance/v1). The repository comes from the artifact's GitHub release URL; other URLs fail. Set GITHUB_TOKEN to raise GitHub's anonymous limit of 60 requests an hour.

Each Sigstore bundle is verified offline against Sigstore's public-good trusted root built into Oyzu. A bundle verifies when:

  • its Rekor entry timestamp is signed by a trusted Rekor key, and its certificate chains to a Fulcio CA valid at that time;
  • the certificate's issuer is GitHub Actions, its source repository is https://github.com/<owner>/<repo>, and, if the recipe names a signer_workflow, the certificate names that workflow (like gh attestation verify --repo --signer-workflow);
  • the signature verifies and the signed statement names the artifact's SHA-256 with an SLSA v1 provenance predicate.

The first bundle that verifies wins; identity shows its signing workflow and verifier is sigstore-public-good. Not checked: certificate transparency timestamps, inclusion proofs, RFC 3161 timestamps (so bundles from GitHub's private Sigstore instance, used for private repositories, don't verify), the runner environment and the provenance contents.

SLSA provenance files​

For slsa-provenance evidence (aqua's slsa_provenance, typically {{.Asset}}.intoto.jsonl), Oyzu downloads the provenance file published by slsa-github-generator (up to 4 MiB, same host rules as checksum files). As slsa-verifier does, it finds the matching log entries in Rekor's public API by the artifact's digest (rekor.sigstore.dev, at most 16 entries, no credentials sent). Everything Rekor returns is verified offline against the built-in trusted root:

  • the file is an in-toto statement with an SLSA v0.2 or v1 provenance predicate naming the artifact's file name and SHA-256;
  • a Rekor entry with a trusted signed timestamp records this envelope;
  • the certificate chains to a Fulcio CA and was valid at that time;
  • the issuer is GitHub Actions, the certificate names a slsa-framework/slsa-github-generator workflow at a v* release tag, and the source repository is the recipe's source_uri (or the release's repository); with source_tag, the source ref must be refs/tags/<source_tag>;
  • the signature verifies.

identity shows the builder workflow. Not checked: certificate transparency timestamps, inclusion proofs and the provenance contents (builder ID, build type, materials). Any generator workflow at a v* tag is accepted, and for delegated (BYOB) builds the delegated builder isn't checked.

Provider records (--provider java)​

For Java (Eclipse Temurin), Oyzu reads the publisher's GA release list for each feature release once (api.adoptium.net, the newest 20 releases) and writes one record per version and platform:

  • tool.id is core:java (the index tool oyzu:java lists it as its origin). The version is the release (21.0.8).
  • A resolved record names the archive and its .sha256.txt file on github.com/adoptium/temurin<feature>-binaries, the same archive the Java provider installs.
  • release carries the publisher's release time when known.
  • A platform the provider doesn't install is unsupported (PLATFORM_UNSUPPORTED); a release with no build for the platform is unsupported (NO_PLATFORM_ARTIFACT); a release not in the list is an error (VERSION_NOT_FOUND); an unreadable list gives error records (SOURCE_UNAVAILABLE).
oyzu --json tools evidence --provider java --version 21.0.8 --version 17.0.16 > java.verified.json

Only Temurin JDK builds are recorded, and only the newest 20 GA releases of a feature; an older release is VERSION_NOT_FOUND.

Provider records (--provider node, go, python)​

These follow the same rules (tool.id is core:<name>, the same status codes, and each record names the archive the provider installs):

  • Node reads nodejs.org/dist/index.json for the release and its date, then the release's SHASUMS256.txt.
  • Go reads go.dev/dl/?mode=json&include=all. The release must be stable and list the platform's archive. The checksum is the archive's .sha256 file on dl.google.com.
  • Python reads python-build-standalone's latest-release pointer, then that release's SHA256SUMS. Only versions that release ships as install_only builds for all four install platforms are recorded; any other is VERSION_NOT_FOUND. The archive URL includes the release tag, so a lock doesn't depend on the pointer.

Additional archive providers and Rust​

--provider also accepts maven, gradle, helm, kubectl, k3d, liquibase, tailscale, zig, npm, pnpm, yarn and rust (optionally prefixed with oyzu: or core:). Versions must be exact stable three-part releases. Without --platform, all five index platforms are recorded. Intel macOS records are produced for Rust, Node, Go, npm, pnpm, Yarn and Zig when the publisher supports that release; other providers record it as unsupported.

ProviderSource and check
MavenApache archive listing, binary tarball and SHA-512 file.
Gradleservices.gradle.org release list's SHA-256 and binary ZIP.
Zigziglang.org stable index's tar.xz URL and SHA-256.
Helmget.helm.sh archive and its SHA-256 file.
kubectldl.k8s.io binary and its SHA-256 file.
k3dGitHub release binary and its checksums.txt entry.
LiquibaseThe digest GitHub's release API reports for the asset (no publisher checksum file).
Tailscalepkgs.tailscale.com stable Linux tarball and its SHA-256 file.
npm, pnpm, Yarnnpm registry tarball metadata and SHA-512, converted to SHA-256 after the archive is verified.
Ruststatic.rust-lang.org channel manifest and its SHA-256 file, every available component URL and digest, plus a checksum-verified rustup bootstrap.
  • Registry metadata is limited to 64 MiB; checksum files to 4 MiB.
  • Liquibase 5.x records carry params.license = "FSL-1.1-ALv2", a source-available license. This records the license; it isn't a legal approval.
  • For Rust, the artifact is dist/channel-rust-<version>.toml. Its checksum entry's params.rust_distribution lists each component and target with its URL and digest, plus the rustup bootstrap. evidence verifies the manifest checksum, checks the component list against the manifest and verifies the bootstrap. Component tarballs are checked when installed, not downloaded here.
  • An unreachable publisher produces error or discovery records, never a verified result.
oyzu --json tools evidence --provider kubectl --version 1.34.1
oyzu --json tools evidence --provider helm --version 3.22.0
oyzu --json tools evidence --provider rust --version 1.95.0

Trust and safety​

  • tools resolve makes no network calls, starts no processes and writes no files. It doesn't add an operating-system sandbox; run it in one (for example an empty network namespace) if you need that.
  • Recipes are untrusted data. Recipe text in human output has control characters escaped.
  • The evaluator contains no registry data or code from another project.
  • Credentials are never sent to publisher hosts.

Limits and known gaps​

  • Only merged-file snapshots are supported, not the per-package tree form.
  • Checked: checksums, GitHub artifact attestations and SLSA provenance. Not checked: cosign, minisign and OpenPGP. Rekor's search is best effort; an artifact whose entries it doesn't list fails.
  • evidence runs downloads one at a time, has no stall timeout, and doesn't refuse private or loopback addresses after DNS resolution. Its allowed hosts come from the set's own URLs.
  • On Windows, .exe is only added for raw assets, not for files entries.
  • Edge cases of pre-release and build-metadata versions in semver() may differ from the registry's own engine. Duplicate YAML keys fail the whole snapshot.
  • version.branch is null when no branch was selected (PLATFORM_ABI_UNSUPPORTED, a limit hit on the whole entry, or VERSION_NOT_COVERED).
  • Supported on Linux x86-64 only.
