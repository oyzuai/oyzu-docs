Recipe resolution and evidence (oyzu tools resolve, oyzu tools evidence)

CLI reference

Published from the canonical docs/reference/tool-resolve.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Status: experimental, provisional. First proof (P1) of the draft recipe ingest engine; command names, field names, the exit code for partial results and every limit value are drafts pending maintainer review. Nothing here installs a tool. See the qualification record for exactly what ran.

Purpose​

Many tools are single-binary releases described only by community recipe data (the public aqua registry). For an exact version and platform, a client needs the URLs to fetch, the evidence the publisher offers and whether the platform has an asset at all.

  • tools resolve evaluates a recipe snapshot offline and emits one record per (tool, version, platform): a discovery-tier artifact set. It reads two things — the snapshot file you name and the flags — and writes stdout.
  • tools evidence takes such a document, downloads each resolved artifact and its checksum file from the real publisher hosts, records sha256 and size, compares them with the published checksum and fills the verified tier. With --provider java it builds the discovery records of Oyzu's Java provider from the publisher's listing first, so the public index can carry Java the same way.

Both are read-only with respect to configuration, locks and the tool store. Neither needs an account. They ignore oyzu.toml, oyzu.lock, -C and --root.

Usage​

# 1. Fetch a registry snapshot yourself (resolve never fetches one)
curl -sSLO https://raw.githubusercontent.com/aquaproj/aqua-registry/v4.573.0/registry.yaml

# 2. Offline evaluation, pinned to the snapshot digest
oyzu --json tools resolve --registry registry.yaml \
  --registry-digest sha256:52a43b0b2817a56fe7566625809d7cca41a1178ccae2b152941221b516e70228 \
  --snapshot-tag v4.573.0 \
  --tool hashicorp/terraform --version v1.16.5 > terraform.discovery.json

# 3. Download and check the real bytes (needs the network)
oyzu --json tools evidence --set terraform.discovery.json > terraform.verified.json

Without --json both commands print a readable summary (outcome, a table of records, unsupported platforms and errors with reasons, next steps). Colour follows NO_COLOR and terminal detection; the plain text carries the same meaning.

--limit NAME=VALUE (repeatable)Lower a counted limit (recipe_nodes, recipe_bytes, recipe_depth, recipe_overrides, string_bytes, expression_steps, url_bytes, record_urls, regex_bytes, snapshot_bytes, output_bytes). Values above the default ceiling are rejected

Every (tool, version) pair is evaluated for every platform. Flag order and repetition do not change the output, which is sorted by (tool.id, version.requested, platform). Tool ids are aqua:<registry package name>, the same backend spelling mise uses (aqua:cli/cli), so a declaration written for mise's aqua backend keeps its form. Provisional until install is wired to it.

What is evaluated​

github_release and http packages. The evaluator is a closed, Oyzu-owned interpreter of the registry's data format, implemented in the oyzu-recipe crate:

  • Version branch: the entry's version_constraint, otherwise the first version_overrides item whose constraint is true (the record's version.branch is top-level or override[N], or null when no branch was selected); version_prefix and version_filter.
  • Expression language: Version, SemVer, string and list literals, semver("…"), ==, !=, in, matches, startsWith, endsWith, contains, not/!, and/&&, or/||. semver() is false for a version that is not a semantic version, so recipes fall through to exact Version == "…" branches. Pre-release versions satisfy only constraints that name a pre-release.
  • Templates: {{.Version}}-style fields, pipes, parentheses, if/else/end and the functions trimV trimPrefix trimSuffix replace title semver regexFind index splitList eq ne.
  • supported_envs (with rosetta2 / windows_arm_emulation), replacements, platform overrides (first match), no_asset, error_message, complete_windows_ext, files, checksum, cosign, minisign, slsa_provenance, github_artifact_attestations.

Anything else is reported, never guessed: a loop, an unknown function or the recipe vars feature gives RECIPE_FEATURE_UNSUPPORTED for that record.

Output​

One JSON document (format 1, kind artifact-sets), validated by artifact-set.schema.json and described field by field in the draft. It contains the engine, the snapshot (its computed digest plus your labels), the effective limits and the records. A record has status:

StatusMeaningExit
resolvedURLs (artifact, checksum, signatures …), archive facts and declared evidence0
unsupportedA normal result: PLATFORM_EXCLUDED, NO_ASSET, RECIPE_MESSAGE, SOURCE_KIND (build-from-source packages), VERSION_NOT_COVERED, PRIVATE_PACKAGE0
errorThe engine could not decide: LIMIT_EXCEEDED, RECIPE_INVALID, RECIPE_FEATURE_UNSUPPORTED, RENDER_FAILED, URL_NOT_HTTPS, PLATFORM_ABI_UNSUPPORTED3

Digests use the domain oyzu.artifact-set.v1, a zero byte and RFC 8785 canonical JSON. recipe_digest covers the parsed entry (so comments and key order do not matter); digests.declared covers the record without verified, tier and digests; digests.full covers everything except digests. The document carries no time, host, user or path, so the same snapshot digest, request, limits and engine build produce byte-identical output on every run.

A GitHub release download is stored as the recipe renders it (github.com/…). The signed redirect target is never stored.

Exit codes and errors​

ExitMeaning
0Complete document; every record is resolved or unsupported
1Evidence problem, no records: SNAPSHOT_INVALID, SNAPSHOT_DIGEST_MISMATCH (and, for evidence, SET_INVALID, SET_SCHEMA_INVALID, SET_FORMAT_UNSUPPORTED, SET_DIGEST_MISMATCH). With --json the shared error envelope (error, code, nextStep, exitCode) is on stdout
2Usage problem, no records: FLAGS_CONFLICT, REQUEST_EMPTY
5Not found, no records: TOOL_NOT_IN_SNAPSHOT
3Complete document in which at least one record is error (resolve) or a resolved record stayed at the discovery tier (evidence). Exit 3 is provisional

A process killed by the environment (memory, wall clock) emits no document. Run one tool per process when you need that blast-radius control.

Provider records (--provider java)​

For Java (Eclipse Temurin) the command reads the publisher's GA release listing of each feature release once (api.adoptium.net/v3/assets/feature_releases/<feature>/ga, at most 16 MiB, the newest 20 releases) and writes one record per version and platform:

  • tool.id is core:java (the index tool oyzu:java carries it as its origin), source_kind is github_release, and version.requested and version.normalized are both the release (21.0.8).
  • A resolved record names the archive and the publisher's per-archive SHA-256 file (….tar.gz.sha256.txt) on github.com/adoptium/temurin<feature>-binaries, with one checksum#0 evidence entry for the archive's file name. These are the archive URLs the Java provider installs from, so the record matches what a client locks.
  • release carries the publisher's release time when the listing has one.
  • A platform the Java provider does not install (anything outside the four installation defaults) is unsupported with PLATFORM_UNSUPPORTED; a release without a build for the platform is unsupported with NO_PLATFORM_ARTIFACT; a release missing from the listing is an error record (VERSION_NOT_FOUND), and an unreadable listing gives error records (SOURCE_UNAVAILABLE).
  • The document's snapshot is {source: "api.adoptium.net", form: "merged-file"} with the SHA-256 of the listings read; recipe_digest names the provider's record rules.

The resolved records are then downloaded and checked exactly as for a set, and exit codes are the same.

oyzu --json tools evidence --provider java --version 21.0.8 --version 17.0.16 > java.verified.json

Provider records (--provider node, go, python)​

The other index providers follow the same rules (tool.id is core:<name>, the platform and error codes are Java's, and each record names the archive the provider installs from):

  • Node reads nodejs.org/dist/index.json (at most 16 MiB) for the release and its day, which becomes release.time (precision: "day"), then each release's SHASUMS256.txt (at most 1 MiB). The evidence entry names the archive in that manifest.
  • Go reads go.dev/dl/?mode=json&include=all (at most 16 MiB). A release must be a stable catalog release that lists the platform's archive; the record's checksum is the archive's .sha256 sidecar on dl.google.com (file_format: "raw").
  • Python reads python-build-standalone's current-release pointer (raw.githubusercontent.com/astral-sh/python-build-standalone/latest-release/latest-release.json), then that release's SHA256SUMS on github.com. Only versions that release ships as install_only builds for all four installation platforms are recorded; any other is VERSION_NOT_FOUND. The archive URL carries the release tag, so a lock restores it without the pointer.

Additional archive providers and Rust​

--provider also accepts Maven, Gradle, Helm, kubectl, k3d, Liquibase, Tailscale, npm, pnpm and Rust (lowercase names, optionally prefixed with oyzu: or core:). Versions are exact stable three-part releases. Human output and global --json use the same records and exit semantics. Omit --platform to emit all five index platforms: linux/amd64/gnu, linux/arm64/gnu, darwin/arm64/native, darwin/amd64/native, windows/amd64/msvc. macOS amd64 remains unsupported.

ProviderPublisher authority and check
MavenApache archive directory listing, binary tarball and SHA-512 sidecar
Gradleservices.gradle.org release catalog's SHA-256 and binary ZIP
Helmget.helm.sh archive and SHA-256 sidecar naming that archive
kubectldl.k8s.io binary and SHA-256 sidecar
k3dGitHub release binary and its checksums.txt entry
LiquibaseGitHub release API's asset digest; no publisher checksum file
Tailscalepkgs.tailscale.com stable Linux tarball and SHA-256 sidecar
npm, pnpmnpm registry tarball metadata and SHA-512 SRI, converted to SHA-256 only after verifying the archive
Ruststatic.rust-lang.org channel manifest and SHA-256 sidecar; all available xz component URL/digest pairs, plus a versioned, checksum-verified rustup bootstrap

Archive names, layouts and publisher-document parsing use the same oyzu-tool-metadata adapters as installation. Checksum entries with params.file_format = "provider" are re-read using those adapters during verification; params.provider selects the adapter. Registry metadata is bounded at 64 MiB; ordinary checksum files retain the 4 MiB limit. Liquibase 5.x records carry params.license = "FSL-1.1-ALv2", a source-available license. This is a license fact, not a serving-class or legal approval.

For Rust, the artifact is dist/channel-rust-<version>.toml, not the generated installed sysroot. The checksum entry's params.rust_distribution contains inputs keyed by component/target, each with url and digest, and rustup with its versioned bootstrap URL and digest. Evidence verifies the manifest checksum, checks that the complete map matches the downloaded manifest, and verifies the bootstrap bytes against its publisher sidecar. Component tarballs are checked when selected for installation, not all downloaded by the evidence job. This supports extra components and targets without inventing a second authority. The existing artifact-set and tool-index schemas are unchanged.

Examples of provider evidence collection:

oyzu --json tools evidence --provider kubectl --version 1.34.1
oyzu --json tools evidence --provider helm --version 3.22.0
oyzu --json tools evidence --provider rust --version 1.95.0

Live publisher evidence is not yet recorded; see implementation status for automated verification. An unreachable publisher produces error/discovery records, never verified success. Human output lists unsupported and failed discovery platforms with their reasons; JSON retains the complete records and existing evidence exit semantics.

For each resolved record it downloads the artifact (streamed and hashed, never stored; at most 2 GiB) and the checksum file (at most 4 MiB, fetched once per URL), and records verified.artifact.{digest,size,publisher_digest,agree}. Redirects are followed manually, at most five, and every hop must be an allowed host or the reviewed pair github.com → release-assets.githubusercontent.com; the hosts seen are reported in verified.observed_redirect_hosts (host names only). Transport follows the broker's proxy and CA rules (HTTPS_PROXY, NO_PROXY, SSL_CERT_FILE; see acquisition transport); each transfer is retried at most twice on transport failures and 408/429/5xx.

Per evidence entry, verified.results[].outcome is:

  • verified: for checksum, the checksum entry for the artifact's file name exists and equals the computed digest (sha256 or sha512). For github-attestation, see GitHub artifact attestations; for slsa-provenance, see SLSA provenance files.
  • failed: the checksum file lacks the name, lists conflicting values, is not a hexadecimal value of the right length, could not be fetched, or disagrees with the artifact; or no attestation GitHub lists for the artifact verifies; or the provenance file or its Rekor entries could not be read or do not verify (the detail says which).
  • verifier-unavailable: this build has no verifier for the method (cosign, minisign, openpgp), or the checksum algorithm (md5, sha1) or file format (regexp) is unsupported. The evidence is declared but unchecked and is never counted as verified.
  • not-run: excluded by --verify.

A record becomes tier: verified only when at least one entry verified and none failed; verified.lock then carries the strongest verified kind in the lock's verification shape: attestation when an attestation verified (its evidence_digest is the SHA-256 of the verifying bundle; for a SLSA provenance file, of the file; a GitHub attestation is preferred when both verified), else digest-only (the checksum file's SHA-256). Otherwise the record stays discovery with verified.status: failed and the reasons in results, and the command exits 3.

A checksum-verified record establishes that these bytes equal what the publisher's checksum file listed at fetch time. It does not prove the publisher is who the recipe says, that the checksum file is authentic, that a signature holds, or that use is permitted. An attestation-verified record also establishes that a GitHub Actions workflow of the release's repository attested these exact bytes (below), or, for SLSA provenance, that a slsa-github-generator release built them from that repository; it says nothing about whether the workflow's source is trustworthy.

GitHub artifact attestations​

For github-attestation evidence (aqua's github_artifact_attestations), evidence asks GitHub's API for the attestations of the artifact's digest, GET https://api.github.com/repos/<owner>/<repo>/attestations/sha256:<digest>?predicate_type=https://slsa.dev/provenance/v1, where <owner>/<repo> comes from the artifact's GitHub release URL (other artifact URLs fail the evidence). A GITHUB_TOKEN in the environment is sent to api.github.com only, to raise the anonymous rate limit (60 requests an hour); listings are memoized per repository and digest. A 404 means no attestation. Each listed Sigstore bundle (v0.3) is read inline from the response or, when GitHub offers it only through bundle_url (as for the GitHub CLI's own releases), downloaded from that pre-signed https URL without the token and without following redirects, snappy-decompressed (block format, at most 8 MiB) and parsed the same way. Each bundle is verified offline, with the same verifier as the tool index's signature (tool index) and Sigstore's public-good trusted root compiled into the CLI:

  • one Rekor entry whose signed entry timestamp verifies against a Rekor key of the trusted root, and a certificate chaining to a Fulcio CA valid at the entry's integrated time;
  • the certificate's OIDC issuer is https://token.actions.githubusercontent.com, its source repository (Fulcio extension 1.3.6.1.4.1.57264.1.12) is https://github.com/<owner>/<repo> (case-insensitive), and, when the recipe names a signer_workflow, its SAN starts with https://github.com/<signer_workflow>@ (that workflow file at any ref), as with gh attestation verify --repo --signer-workflow;
  • the DSSE signature, the log entry's payload hash and signature, and an in-toto v1 statement with predicate https://slsa.dev/provenance/v1 whose subject names the artifact's SHA-256.

The first bundle that verifies wins; identity reports its signing workflow and verifier is sigstore-public-good. Not checked: SCTs, Merkle inclusion proofs, RFC 3161 timestamps (so bundles from GitHub's own Sigstore instance, used for private repositories, do not verify), the runner environment, and the provenance predicate's contents.

SLSA provenance files​

For slsa-provenance evidence (aqua's slsa_provenance, typically {type: github_release, asset: "{{.Asset}}.intoto.jsonl"}), evidence downloads the record's provenance URL (at most 4 MiB, same host and redirect rules as checksum files). The file is what slsa-github-generator publishes: one DSSE envelope whose signature carries its Fulcio certificate, with no transparency-log entry in the file. As slsa-verifier does, the log entry is looked up in Rekor's public API by the artifact's digest: POST https://rekor.sigstore.dev/api/v1/index/retrieve with {"hash":"sha256:<digest>"}, then GET https://rekor.sigstore.dev/api/v1/log/entries/<uuid> for at most 16 returned UUIDs (memoized per digest; no credentials are sent). Nothing Rekor returns is trusted unverified; verification is offline against the same compiled-in trusted root:

  • the envelope is an in-toto statement (v0.1 or v1) with predicate https://slsa.dev/provenance/v0.2 or v1, and a subject whose name is the artifact URL's file name and whose SHA-256 is the artifact's;
  • some returned entry has a signed entry timestamp from a Rekor key of the trusted root (the canonical {body, integratedTime, logID, logIndex}, as for bundles) and records this envelope: an intoto 0.0.1 entry with the envelope's certificate and its payload (or envelope) hash, an intoto 0.0.2 entry also recording its signature, or a dsse 0.0.1 entry; its integratedTime is the signing time;
  • the certificate chains to a Fulcio CA valid at that time and was itself valid then;
  • the OIDC issuer is https://token.actions.githubusercontent.com; the SAN is a workflow of slsa-framework/slsa-github-generator at a release tag, https://github.com/slsa-framework/slsa-github-generator/.github/workflows/<file>.yml@refs/tags/v*; the source repository extension is the recipe's source_uri (github.com/<owner>/<repo>), else the release's repository from the artifact URL, else the recipe's repo_owner/repo_name; and with source_tag, the source repository ref (1.3.6.1.4.1.57264.1.14) is refs/tags/<source_tag>;
  • the DSSE signature verifies with the certificate's key.

identity reports the builder workflow and verifier is sigstore-public-good. Not checked, as for bundles: SCTs and the Merkle inclusion proof (the signed entry timestamp is the log evidence), and the provenance predicate's contents (builder id, build type, materials). Unlike slsa-verifier, any generator workflow at a v* tag is accepted rather than a fixed builder list; for a delegated (BYOB) build the certificate names the generator's delegator workflow, and the builder it delegated to is not checked.

Trust and safety​

  • resolve has no network, process or file-write capability by construction: the oyzu-recipe crate depends on no HTTP client, TLS stack, process or temp-file crate and its sources name no such API (checked by a unit test and by the proof runner with cargo tree). The bare command adds no operating-system sandbox; supplying one (for example an empty network namespace) is the caller's job. The qualification run used unshare -rn.
  • Recipes are untrusted data. Recipe text shown in human output is control-character escaped. The registry's license obligations are open; see licensing and provenance. The evaluator is written independently against the registry's public data format and contains no registry data or code from another project.
  • Credentials are never sent to publisher hosts.

Limits and known gaps (P1)​

  • Merged-file snapshots only; the per-package tree form, --registry-tested-version, supplements (origin: supplement) and the curated batch are not implemented.
  • Verification: checksums, GitHub artifact attestations and SLSA provenance files. No cosign, minisign or OpenPGP verifier exists. The attestation check was proven with real bundles in unit tests; a live run against api.github.com happens in the tool index job (the development sandbox cannot reach the API). The provenance check was proven in unit tests on slsa-verifier v2.6.0's real provenance file against the production Fulcio CAs, with Rekor entries built in Rekor's response shapes and signed by a test log key: Rekor was unreachable from the development sandbox, so the live lookup and a real Rekor entry's body shape are unverified. Rekor's index search is best effort; an artifact whose entries it does not list fails the evidence.
  • evidence runs sequentially, has no stall timer, and does not refuse private/loopback addresses after DNS resolution; its host allow-list is derived from the set's own URLs. Windows executable-suffix handling for files is not applied (only raw assets get .exe).
  • semver() follows one specification implemented in this repository. Differences against the registry's own engine on pre-release and build-metadata edge cases are unmeasured (deferred differential testing). Aliases and YAML tags are handled by the YAML parser; duplicate keys fail the whole snapshot; alias-expansion bombs are limited only by snapshot_bytes before parsing (hardening deferred).
  • Linux x86-64 only has been run. Output is designed to be identical on Windows and macOS; that is unverified.
  • --provider java has not run against the live Adoptium API from this repository's sessions (no network route); its parsing is tested on a fixture listing in the API's documented shape. The listing covers the newest 20 GA releases of a feature, so an older release is VERSION_NOT_FOUND. Only Temurin JDK images are recorded; providers other than the supported provider list are FLAGS_CONFLICT.
  • --provider node and --provider python verified real releases from this repository's sessions (2026-10-10: Node 21 to 26 and CPython 3.10 to 3.15 on the three platforms, through the tool index job). --provider go has not run against go.dev from here (no network route); its records are tested on a fixture catalog in the publisher's shape.
  • version.branch is null when no branch was selected (PLATFORM_ABI_UNSUPPORTED, a limit trip on the whole entry, VERSION_NOT_COVERED). This differs from the client contract outline, which required a string; see the implementation notes.

Verification​

python tooling/test-tool-resolve.py --cli <oyzu> --workspace <dir> --registry <registry.yaml> drives the compiled CLI against the pinned snapshot and real publishers; compiled-CLI tests are in tests/integration/recipe_resolve.rs (including the --provider input checks); the Java provider's records are unit-tested in src/tools/recipe_evidence/java.rs (Node, Go and Python in providers.rs) and its listing parser in crates/oyzu-tool-metadata/src/jdk/tests.rs; schema fixtures in tests/fixtures/tool-artifact-set (python tooling/check-tool-contracts.py). Results and revisions are in the qualification record.
