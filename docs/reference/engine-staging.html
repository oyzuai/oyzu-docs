Engine staging

CLI reference

Published from the canonical docs/reference/engine-staging.md file. Features marked experimental remain experimental; check support limitations before relying on them.

The engine is the oyzu executable that runs a build. A project can pin an exact engine in oyzu.lock. When the oyzu you run is a different build, it hands the build to the pinned engine, which you supply as a local engine package.

Note: Engine packages are local archives that you build and verify yourself, or that the install scripts compose from a release's own executables. There is no separate release channel, public catalog or automatic upgrade for engines. Engine staging works on Linux x86-64 and Windows x64 (MSVC). macOS is not supported yet.

Isolated builds (--isolated) run the engine's Linux member inside the container. A Linux oyzu mounts itself. On Windows and macOS, oyzu needs an installed package that pairs it with the Linux oyzu built from the same source; see Installing this oyzu with its Linux member. The install scripts do this for releases.

Quick start​

Install a package you built and verified:

oyzu engine install --identity <BUILD_ID> --archive ./engine.tar.gz --sha256 sha256:<HEX>

Run the executable the command prints. It reports identity, release, executable, registration and admission; add --json for machine-readable output.

To make a project use a different engine, pin it in oyzu.lock and admit the archive in your user configuration:

# oyzu.lock
[engine]
identity = "0.1.0-local.0123456789ab"
# user configuration
[engines.packages]
"0.1.0-local.0123456789ab" = { archive = "/path/to/engine.tar.gz", sha256 = "sha256:<64 lowercase hex>" }

Pinning an engine​

An engine identity is the first version token that oyzu --version prints. It leaves out the build profile, target and timestamp, so different dirty builds can share an identity. The archive digest identifies the exact content.

Without a pin, the running oyzu is the engine. Every build records the engine identity it used and whether it was pinned.

With a pin that differs from the running oyzu:

  1. oyzu looks for an admitted archive for that identity in engines.packages.
  2. It installs the engine beside your oyzu and hands the build to it before configuration is read, tools are resolved or plugins load. Your oyzu and the project lock do not change.
  3. oyzu build --plan and oyzu plugins update do the same, so the update check runs under the pinned engine's capabilities.

A compatible engine change doesn't update plugin or tool selections, and a plugin update keeps the engine pin.

If no admitted archive supplies the pin, the build stops with ENGINE_PIN_MISMATCH before doing any work. The project's oyzu.lock must be readable, even for build --plan.

Captured builds (--isolated or an explicit --image) with a pin always need the admitted archive, even when the running oyzu already has the pinned identity. The archive supplies the Linux worker that runs inside the container. If the archive has no member for the platform, the build fails instead of using the worker built into the image. A build with no pin that you start from an installed engine (see below) uses that engine's package the same way.

Admitting an archive​

engines.packages maps exact build identities to archives:

FieldMeaning
keyThe exact engine identity
archiveAbsolute path to the archive
sha256Archive digest, sha256: plus 64 lowercase hex digits

The map holds at most 64 entries. There is no default source, tag lookup, newest cache lookup or network fallback. Set it in user or system configuration, never in a project file, local override or profile, so a project can't authorize its own engine. User configuration doesn't apply in CI. Edit it with oyzu config set --global (with --json-value) and oyzu config unset.

The build's --store option selects the tool store. Engines live in engines/<archive-sha256>/ inside it.

Installing a local engine package​

oyzu engine install --identity <BUILD_ID> --archive ./engine.tar.gz --sha256 sha256:<HEX>
oyzu engine install --identity <BUILD_ID> --archive ./engine.tar.gz --sha256 sha256:<HEX> --json
OptionMeaning
--identityThe exact build identity declared by the package's engine.json
--archiveLocal archive, with its platform members and notices
--sha256The archive digest you trust, with the sha256: prefix

The command checks the archive digest, every executable listed in the manifest, and that the package has a member for this machine's exact OS, architecture and ABI. It needs no network. It doesn't change PATH, install system-wide or touch project locks.

Payloads go in your per-user data directory under tools/engines/<archive-sha256>/. A separate registration file, tools/engine-installations/<archive-sha256>.json, binds the package to its installed executable. Only oyzu engine install creates it. Admitting an archive through engines.packages doesn't.

An unpinned build uses an installed package only when the running executable is that registered, installed member with the matching identity and platform. For isolated builds on Windows and macOS, a copy of that member counts too when its bytes are identical (same executable digest, identity and platform), such as the oyzu the install scripts and oyzu run bootstrap put on your PATH. Any other copy, and every copy on Linux, doesn't inherit the registration. Warm use doesn't need the original archive, and installed files aren't re-hashed on each command. --store changes the tool store but not where registrations live.

A registered engine can supply its own Linux worker for captured builds without any engines.packages setting. engines.requirePin and [engine] pins are still checked first, and engines.development doesn't affect registered packages.

Installing this oyzu with its Linux member​

oyzu engine install --linux ./oyzu-linux-x86_64
oyzu engine install --linux ./oyzu-linux-x86_64 --linux ./oyzu-linux-arm64 --json

This packs the oyzu you run together with the Linux oyzu executables you name into one engine package, then installs and registers it exactly like an archive (see above). Afterwards, isolated builds on this machine run the Linux member from the package, whether you start the installed executable or the oyzu on your PATH with the same bytes.

RuleDetail
Members1 to 4 --linux files; can't be combined with --archive
PlatformRead from the file: a 64-bit ELF for x86-64 or arm64. With a dynamic loader it is gnu (musl for musl's loader); statically linked it is musl
Same sourceEach file must carry this oyzu's build identity (the first token of oyzu --version), or the command stops with ENGINE_IDENTITY_MISMATCH before installing anything
ResultThe same fields as an archive install, plus platforms, every member of the package

The identity check catches a Linux oyzu from another release or commit. Two builds of the same dirty checkout share an identity, so build both members from the same state. The Linux worker checks its exact identity and platform again before each isolated build. Run the command again after you replace oyzu: the new executable has different bytes, so the old package no longer applies.

Policy-required pins​

An administrator can require every build in some contexts to have an exact engine pin and a complete lock, using the protected setting engines.requirePin. It is administrative-only, defaults to false, and can't be set in machine, user, project, local, invocation or profile settings. A nonbinding policy default doesn't require anything. For example, in a protected policy:

{
  "engines.requirePin": {
    "locked": true,
    "value": true,
    "when": { "context": ["ci", "pr", "release"] }
  }
}

Put this in the administrative policy file, not in oyzu.toml. The build root and the stricter of the detected and requested contexts decide whether it applies. A weaker --context, a profile or an ordinary override can't waive it. Without an applicable requirement, local, CI and release builds can be unpinned.

A build that requires a pin:

  • Stops with ENGINE_PIN_REQUIRED if oyzu.lock has no [engine].identity, before discovery, plugin roles or preparation.
  • Can't use --engine-development to skip the pin.
  • Replays existing plugin selections and refuses unpinned local development plugin bindings.
  • Checks that each selected tool has a portable lock entry before preparing tools.
  • Never adopts or writes a missing plugin or tool selection.

Prepare the whole lock before running the governed build. Removing --frozen doesn't remove the requirement. For a missing plugin selection, restore an approved complete lock, or run oyzu build in an approved context where policy allows adoption. Otherwise ask your policy administrator for a context where you can prepare the lock. oyzu plugins update replaces existing selections but doesn't adopt a missing first one, and oyzu pin and oyzu install don't repair a missing plugin selection.

The requirement carries over when the build is handed to another engine. An older engine that doesn't understand it refuses the handoff.

Explicit development engine​

To test a CLI you built from source while keeping the shared pin, first allow the override in user configuration (or ask your administrator to):

oyzu config set --global engines.development true

Then run that executable with --engine-development on each build:

./dist/cli/artifacts/oyzu -C ~/projects/app build app --engine-development
RuleDetail
Settingengines.development, boolean, default false. Not allowed in project or local files or profiles. Administrative constraints apply.
Per buildThe setting only permits the flag; you pass the flag for every build.
Where it worksLocal development only. Detected CI and requested CI, PR or release contexts refuse it, even with --context local.
CombinationsNot allowed with remote, isolated, image, all-platform or slice builds.
Undooyzu config unset --global engines.development

The flag keeps the executable you started. It doesn't look for another executable, install the pinned engine, change the pin, or change PATH.

Build inventory and local preview JSON record developmentOverride: true, pinned: false, the actual identity and executableDigest, and the requestedPin. The Context section of the human output names the override, its digest and the bypassed pin. Two builds with the same version label can have different content, so this record identifies bytes and is not a publisher attestation.

Captured builds with external builders need an admitted engine archive and refuse this override.

Execution image updates and replay​

For a captured build, --image go=<reference> picks the execution image for that ecosystem, separately from the engine, plugin and tool pins. Oyzu resolves the image to its immutable digest and platform once per build. Changing a tag later affects new builds, not one already running.

To use the exact images of an earlier build again, keep that build's bundle outside the source tree and run:

oyzu build app --isolated --platform linux/amd64 --full --frozen \
  --execution-images-from /retained/build-a

This reuses the images only. It doesn't re-run the old plan. Oyzu checks the bundle's integrity (not who produced it), then checks that the source, the target, variant and builder selection, the lock bytes and the engine selection match. It then prepares and plans as usual under your current policy and checks. The new plan records which earlier build it took its images from.

RuleDetail
Required--isolated and --frozen
Not allowed with--image, remote execution, previews, affected selection, slices, handoff, --engine-development, contract verification
SupportedCaptured builds with an admitted engine archive, for built-in and external builders
Not supportedDerived application containers, in-process image assembly, and bundles recorded without the comparison facts (you can still inspect them)
--offlineOrdinary offline rules apply. It never permits missing tools or dependencies.

Errors:

CodeCause and recovery
EXECUTION_IMAGES_SOURCE_CHANGED, EXECUTION_IMAGES_SELECTION_CHANGEDThe source or pins differ from the earlier build. Restore them, or run an ordinary new build.
EXECUTION_IMAGE_UNAVAILABLEThe recorded image isn't available, or your executor refuses it. The error names the target, digest and platform. Provide that exact image and retry. Oyzu never substitutes the current tag.

On Windows, the frontend oyzu stays attached during Ctrl+C until the staged engine finishes cleanup and returns its exit status. The engine reports the interruption and keeps the failed build bundle.

oyzu install --store <directory> and oyzu exec --store <directory> -- <command> use the same store when they read requirements from an already installed, locked external builder. Neither adopts a missing plugin; prepare it with a build first. On Windows, install oyzu.exe and oyzu-shim.exe together.

Isolated build image placement​

Captured builds run the engine, plugin and locked tools inside a Linux image. There are two ways they can get there:

  • mounted: Oyzu mounts them read-only into the container. This is the default.
  • image-installed: the exact files are already installed in the image, so Oyzu uses them in place without mounting or restoring anything.

Image labels and PATH never choose versions. The engine archive, the plugin lock and the locked tool distribution do. When you install a package, the store keeps a record of its verified contents next to it. If that record is missing (older installs, or an interrupted install), builds use mounted placement. Reinstalling a removed package renews the record.

Before a build, Oyzu compares the selected files with the image's filesystem once and caches the result for that image in your user cache. Only regular files and directories can be image-installed. A tree that contains links stays mounted. Anything that doesn't match stays mounted.

Docker volumes, scratch paths and explicit overlays can't hide admitted files. An overlay that conflicts with one stops the build with ENGINE_CONTROL_CONFLICT.

Evidence in the build records the selected engine member (identity, archive digest, platform and executable digest) separately from the engine baked into the image. Oyzu never runs the baked executable to observe it. The baked observation is for information only and never changes which engine is selected.

An image from the classic Docker store can lack an OCI Descriptor. Then placement can't be observed, the baked engine shows as unavailable, and builds use mounted placement. A descriptor that is present but invalid is an error, not a fallback.

Offline use and replay​

After a build has installed the exact engine, plugin and tools and filled the ecosystem's dependency cache, you can repeat it without the network. For Go:

oyzu -C <project> install --frozen --offline --store <store>
oyzu -C <project> exec --offline --store <store> -- go mod download
oyzu -C <project> build app --frozen --offline --no-docker --no-cache --store <store>

Keep the same GOMODCACHE, GOCACHE and GOPATH you used for preparation. To make Go itself refuse the network, also set GOENV=off, GOWORK=off, GOTOOLCHAIN=local, GOPROXY=off, GOSUMDB=off and GOVCS=*:off. --offline and these variables control the clients Oyzu and Go use. They don't block the network at the operating-system level, so an arbitrary project command could still reach it.

Missing engine or plugin installations are restored from their admitted local archives, and a cached tool archive can restore a missing tool. If neither an installation nor an archive exists, the command stops. A missing Go module reports module lookup disabled by GOPROXY=off. Restore the content with an online build first. Don't edit the lock to match whatever is cached.

Replaying means running the same command again with the same executable, arguments, directory, source, lock and package selections. There is no command that replays history. Current admission still applies: removing the engine's admission makes the build fail with ENGINE_PIN_MISMATCH, even if the bytes are cached. Matching evidence doesn't guarantee byte-identical output.

If you cancel a build, the staged engine records it as interrupted, prints BUILD_INTERRUPTED, keeps no artifact from the run and exits with status 130. Other builds that share the installed engine are not affected.

Engine package format​

An engine package is a gzip tar or ZIP archive with engine.json at its root and one executable per platform at the path the manifest gives. One admitted archive covers every platform member of the engine build.

{
  "contract": "oyzu.engine.v1alpha1",
  "identity": "0.1.0-local.0123456789ab",
  "runtimes": [{
    "platform": { "os": "windows", "arch": "x86_64", "abi": "msvc" },
    "entrypoint": "bin/windows/oyzu.exe",
    "executableDigest": "sha256:<64 lowercase hex>"
  }]
}
RuleDetail
Members1 to 16 platform members with unique platforms and entrypoints
ExecutablesEach must be a regular file whose digest matches the manifest
Platform matchOS, architecture and ABI must match the running engine exactly. Oyzu doesn't infer ABI compatibility.
IdentityThe running engine's compiled identity must match the manifest, so a manifest can't relabel a different build

The digest you supply covers the whole archive, including the manifest. Oyzu verifies the archive before extracting it, extracts it without following links, checks the manifest and executables, then publishes the installation atomically. Installed files are trusted afterward. Admitting an archive by digest is not a publisher signature check and says nothing about official provenance.

Errors​

CodeCause and recovery
ENGINE_PIN_MISMATCHNo admitted archive supplies the pinned engine. Run the pinned engine, or admit its archive in user or system configuration.
ENGINE_PIN_REQUIREDPolicy requires an engine pin and oyzu.lock has none. Pin the engine and prepare the full lock.
ENGINE_DEVELOPMENT_DENIED--engine-development isn't permitted here: the setting is off, the context isn't local, or policy requires the pin. Drop the flag or get permission.
ENGINE_DEVELOPMENT_UNAVAILABLEThe development executable couldn't be read. Make it readable and retry.
CONFIG_SCOPEA project, local or profile source tried to admit an engine. Move the setting to user configuration or the administrator.
ENGINE_PACKAGE_UNAVAILABLEThe archive can't be read. Restore it.
ENGINE_PACKAGE_DIGESTThe archive doesn't match the digest. Get the expected archive; don't just change the digest.
ENGINE_PACKAGE_INVALIDThe manifest or executables don't match the package rules above. Rebuild the package.
ENGINE_INCOMPATIBLEThe package's contract or platform isn't supported by this engine. Supply a matching build.
ENGINE_IDENTITY_MISMATCH, ENGINE_HANDOFF_MISMATCHThe manifest or the running build doesn't match the requested identity or entrypoint. Fix the package. No second handoff happens.
ENGINE_HANDOFF_CHANGEDThe pin or the admitted release changed during the handoff. Retry with consistent settings.
ENGINE_HANDOFF_INVALIDThe receiving engine can't take this handoff, for example an older engine that only supports builds, not updates. Run that engine directly or pick one that supports the operation.
ENGINE_INSTALLATION_INVALIDThe registration and the installed executable disagree. Reinstall the package. Don't copy registrations between installations.
ENGINE_START_FAILEDThe verified executable wouldn't start. Check host prerequisites and the package layout.
ENGINE_CONTROL_CONFLICTAn overlay or volume conflicts with an admitted engine file in a container. Remove the overlay.
ENGINE_ASSET_UNAVAILABLEAn isolated build on Windows or macOS found no package with a Linux member for this oyzu. Run oyzu engine install --linux with the Linux oyzu built from the same source, or reinstall the release with the install script.

A failure at this stage happens before the build does anything. Oyzu doesn't adopt plugins or tools or change selections. Complete engine installations stay in the store for reuse.

Limits​

  • Engine packages are local archives. No separate release channel, catalog or automatic upgrade exists.
  • oyzu run bootstrap doesn't build the Linux member on Windows or macOS yet; pass one with --linux.
  • A nested build uses its own lock, not the parent's.
  • Native (non-container) builds have no filesystem or network isolation from this feature.
  • Updating plugins through an engine handoff works only when both the frontend and the receiving engine support it.
  • macOS isn't supported yet.
