Exact native engine staging

CLI reference

Published from the canonical docs/reference/engine-staging.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Experimental implementation for the native-engine program (#703, deliveries #704, #705 and #706). This page describes the development archive route. It does not establish an official release channel, production distribution availability, or native sandboxing. The Windows x64/MSVC real Go flow has verified cold staging and independent selections and override with explicitly admitted development binaries. The later Windows lifecycle qualification covers native preparation, offline use, retained-input replay and cancellation.

Selecting an engine​

The draft isolated Go execution-assets slice also requires the coordinator to be the admitted host member of its exact archive, even when the running identity already equals the pin. Its Linux semantic workers use the Linux member of that archive and check compiled identity, platform and entrypoint before running. A missing or incompatible member fails without falling back to the environment's baked engine. Native-only builds retain the behavior below. The first mounted Windows-to-Linux Go flow and its offline replay have passed, as have the independent A/P1, B/P1, B/P2, warm A/P1 series and same-constituent preassembled reuse. Whole-build default B and exact A6 handoff also passed through the same image's actual default CLI. Candidate C also passed cold and frozen/offline replay with byte-identical complete placement/dependency evidence, using mounted C and the same image-installed P1/Go. Supported local repository gates and the corrected full-build reporting proof also passed; the qualification record retains unavailable validation prerequisites and wider qualification limits.

An optional [engine].identity in oyzu.lock selects an exact engine build. Captured builds with that pin require an explicitly admitted archive, including graphs containing only built-in builders and invocations whose current identity already matches. The coordinator and semantic workers use members of that same archive. A missing runtime member refuses before builder preparation; the image's baked worker is never the fallback. Native-only builds retain direct continuation when the active identity matches. Unpinned builds invoked through a registered installed executable use that executable's admitted package. Raw development and copied executables retain the provisioned worker route.

This also applies when an explicit --image or built-in native-routing metadata selects a captured worker without --isolated. Bootstrap uses the declared producer closure for requested logical target names, so an unrelated unselected captured target does not change a simple native build. Affected selections, concrete variant IDs not yet expanded, and materialized relationships are classified conservatively before full discovery: they can require the admitted archive even when later routing can execute natively. Full target selection still owns validation and execution; bootstrap never invokes an external plugin's admission role to decide this requirement.

Common captured target and dependency evidence records the selected member's identity, archive digest, platform and executable digest separately from the observed baked worker and asset placement. Dependency preparation inside a consumer image uses this selected member too, rather than acquiring the legacy builder-worker image. Exact assets still require the container process executor; unsupported executor controls refuse. Captured built-in image replay follows the same retained-input comparisons described below. Daemonless in-process image assembly records its admitted coordinator member, without inventing an OCI image, Linux worker member or baked-engine observation. Preparation and action reuse keys bind the selected archive/member identity; placement and baked observations do not grant reuse authority.

An explicitly permitted --engine-development invocation remains a non-exact local override, and evidence does not claim correspondence to a pinned archive. The existing CLI restrictions against combining it with --isolated, explicit images or remote execution remain binding. External captured builders still require admitted engine assets and refuse that override. The built-in integration status records the current verification boundary. A tiny Linux x86-64 Rust build has verified exact selected-engine execution over a different baked worker, required test/coverage/doctest reports, a runnable delivered binary and unchanged locks. Other built-in families share the selection contract but are not newly runtime qualified by that Rust proof.

Without a pin, the active executable remains the engine. A different pin requires an explicitly admitted archive; Oyzu installs that engine beside the frontend and hands the build invocation to it before execution preflight, discovery, plugin roles or planning. The frontend and project lock remain unchanged. build --plan and plugins update use the same bootstrap; updater preflight therefore runs under the selected engine's actual capabilities before adopting any plugin. A compatible engine change does not update plugin or tool selections. A deliberate plugin update retains the engine pin and native tool selections. Help, version and invalid command syntax finish before opening configuration.

Installing a local engine package​

For a development package whose identity and archive digest you have verified:

oyzu engine install --identity <BUILD_ID> --archive ./engine.tar.gz --sha256 sha256:<HEX>
oyzu engine install --identity <BUILD_ID> --archive ./engine.tar.gz --sha256 sha256:<HEX> --json

The archive uses the engine package format below. Installation verifies the archive, every declared executable member and the current host's exact OS/architecture/ABI. The result reports identity, release, executable, registration and admission. Run the returned executable directly; the command does not replace PATH, install system-wide or modify project locks. Human output uses labeled values and remains readable with NO_COLOR or redirection.

Payloads live in the native per-user data directory under tools/engines/<archive-sha256>/. Only this command creates the separate atomic tools/engine-installations/<archive-sha256>.json registration. It binds the verified package to its exact installed host entrypoint. Config-origin staging through engines.packages does not create a registration.

An unpinned build recognizes its package only when the running executable is that registered installed member, with the matching compiled identity and platform. Lookup derives one registration from that location; it does not scan project stores, search adjacent manifests, compare release labels or authorize a copied executable. The package lease remains held for the invocation. Warm use does not require the original archive and does not rehash installed payloads. Missing execution members refuse before builder semantics instead of falling back to an image's baked worker. Build --store overrides native tool storage, not the native per-user registration owner.

engines.requirePin and retained handoff requirements are checked first. An explicit project pin continues through the existing config-origin resolution path; registration is not a fallback for a missing or withdrawn pinned source. Likewise, a config-origin handoff must still revalidate its source. The engines.packages map is not a global installation allowlist: an absent or locked empty map does not prohibit this distinct standalone admission. The engines.development setting governs the explicit development override, not registered packages. Normal session validation and execution controls still apply.

This local archive operation needs no network and establishes no official release channel, public catalog, automatic upgrade or distribution eligibility. Current source and runtime qualification are recorded in the installed matching status. The Linux x86-64 qualification passed an unpinned installed Rust build over a different baked engine, with required reports and a runnable artifact while the original archive was unavailable. Policy/pin precedence, config-source withdrawal, copied-executable fallback and install/help output were also exercised; this is not a Windows/macOS or public-release qualification.

Policy-required pins​

The required-pin implementation for issue #792 is under qualification. A protected administrative policy can require a complete build lock with an exact engine pin using engines.requirePin. This Boolean is administrative-only, defaults to false, and is unavailable in ordinary machine, user, project, local, invocation or profile settings. A nonbinding policy default alone does not require the pin. For example, a protected policy's settings can contain:

{
  "engines.requirePin": {
    "locked": true,
    "value": true,
    "when": { "context": ["ci", "pr", "release"] }
  }
}

Use the existing administrative policy file and selectors; do not copy this into oyzu.toml. The actual build root and the stricter detected/requested context determine applicability. A weaker --context, profile or ordinary override cannot waive the mandate. Enrollment, CI hints and the mere presence of administrative settings do not require a pin. Standalone CI, release and local builds remain optionally pinned without an applicable mandate.

A required build refuses a missing [engine].identity before discovery, plugin roles or preparation, and cannot use --engine-development to bypass the pin. It replays existing plugin selections and refuses unpinned local development plugin bindings. Before tool preparation, it checks that selected tool requests have portable lock entries; execution owners retain the applicable platform, component and recipe checks. No missing plugin or tool selection is implicitly adopted or written. Deliberately prepare the complete lock before running the governed build; removing --frozen does not remove a policy requirement. For a missing plugin selection, restore a complete approved lock or deliberately adopt the bound package with oyzu build in an approved context where policy permits adoption. If none is available, ask the policy administrator for a lock-preparation context. oyzu plugins update replaces existing selections; it does not adopt a missing first selection. Tool pin/install commands do not repair a missing plugin selection. An engine handoff retains the required-lock state; an older receiver that does not understand that private handoff marker refuses it.

The qualification record records Windows native application proofs, focused policy/complete-lock checks, compiled handoff refusals, and Linux protected-policy application/refusal proofs. The Linux evidence uses an explicitly attributed combined development candidate. Protected Windows CLI qualification is unavailable with the current non-elevated token; this is not a claim of complete platform qualification.

Execution image updates and replay​

For a captured external-builder build, --image go=<provisioned-reference> selects the Go execution image independently of the engine, plugin and tool pins. Resolution captures its immutable digest and platform once. Preparation metadata, including the image's PATH, and accepted actions use that frozen identity. Changing a tag affects a new invocation; it does not redirect active work. This is the existing explicit image mapping, not a new configuration catalog or a deployment environment.

Retain the successful build bundle outside the application's captured source. To request its exact images again, use:

oyzu build app --isolated --platform linux/amd64 --full --frozen \
  --execution-images-from /retained/build-a

This performs execution image replay, not arbitrary historical-plan execution. Oyzu verifies bundle integrity (not producer authentication), compares the captured source, target/variant/builder selection, exact lock bytes and admitted engine selection, then runs ordinary current preparation and planning. Saved commands, environment variables, mount paths and image-placement receipts never grant execution authority. The new plan records the originating plan, envelope and image-selection digests separately from its current actual choices. Current policy, required checks and executor controls still apply; the entire old configuration is not restored.

The option requires --isolated --frozen. It cannot be combined with --image, remote execution, previews, affected selection, slices, handoff, --engine-development or contract verification. It supports captured built-in and external builders with an admitted engine archive. Derived application containers and synthetic in-process image records are explicitly unsupported: the latter name a coordinator executable, not an OCI image. The Linux x86-64 built-in Rust proof passed A-to-B tag replacement followed by retained-A replay, with fresh actions, native reports and independent executable consumption. This qualifies that bounded replay flow, not every builder/platform combination. Bundles without the required comparison facts are also unsupported. Existing bundles remain inspectable.

EXECUTION_IMAGES_SOURCE_CHANGED or EXECUTION_IMAGES_SELECTION_CHANGED requires restoring the recorded source/pins or making a new ordinary build. EXECUTION_IMAGE_UNAVAILABLE names the target, exact recorded digest and platform when it is unavailable or refused by the current executor. Provision that exact image under the existing image admission rules and retry; Oyzu does not substitute the current tag or default. --offline retains ordinary offline acquisition rules and never authorizes missing tools or dependencies. The Windows-to-Linux Go qualification demonstrates a new invocation selecting B after the tag changes, an active accepted A plan continuing on A, and historical image replay selecting A. Source/pins remain unchanged; incomplete pins, changed source, unavailable recorded images and a disabled current executor refuse before actions. The full candidate build, workspace tests, Clippy, formatting and nine compiled CLI task scenarios passed. The qualification retains an existing, separately owned Go feature-conformance failure and unavailable validation prerequisites; it does not claim complete plugin qualification. Other platforms and automatic replacement-image production are not qualified by this slice.

On Windows, the waiting frontend preserves console cancellation until the staged engine finishes its cleanup and returns its exit status. The staged engine owns interruption diagnostics and the failed build bundle; the frontend does not run a second cancellation watchdog. This does not add native process isolation.

For supported setup commands, install --store <directory> and exec --store <directory> -- <command> use that same store when discovering requirements from an already installed, locked external builder. Neither command adopts a missing plugin: first prepare it through the admitted build path. On Windows, install oyzu.exe and oyzu-shim.exe together. Setup publishes native shims through the shared shim owner, including when an ordinary store path makes the internal digest-named image exceed the legacy Windows path limit.

Updater handoff requires both frontend and receiver to implement that operation. The historical #704 qualification engine supports build handoff only and refuses an updater handoff with ENGINE_HANDOFF_INVALID. Invoke that engine directly for its updater or select an admitted receiver implementing update handoff; no fallback changes the pin or package selection.

The admission belongs in user or system configuration, never in a project file, local override, or profile. Mandatory constraints and normal CI source rules apply: user configuration is excluded in CI. No project setting can authorize its own engine executable. Example values below are illustrative:

[engines.packages]
"0.1.0-local.0123456789ab" = { archive = "E:/qualification/engine.tar.gz", sha256 = "sha256:<64 lowercase hex>" }

The map contains at most 64 exact build identities. Each binding contains exactly an absolute archive path and its sha256 digest. There is no default source, tag lookup, newest-cache selection, or network fallback. Configuration edits use the shared config set --global --json-value and config unset commands, including individual quoted map entries. The build's --store selects the existing tool store; engines occupy engines/<archive-sha256-hex>/.

Explicit development engine​

To test a project-built CLI while retaining the shared pin, first allow the override in user configuration (or ask the administrator to permit it):

oyzu config set --global engines.development true

Then invoke that compiled executable explicitly, or select it through your existing PATH/activation, with build --engine-development. For example:

./dist/cli/artifacts/oyzu.exe -C E:/projects/app build app --engine-development

The boolean permission defaults to false, is forbidden in project/local files and profiles, and remains subject to administrative constraints evaluated against the actual build root. Permission does not activate an override: the flag is required for each invocation. Overrides are restricted to local development; detected CI and requested CI, PR or release contexts refuse them, including a weaker --context local on detected CI. Remote, isolated, image, all-platform and slice invocations reject the flag. Removing the permission with oyzu config unset --global engines.development restores the default denial.

The flag retains the executable already running. It does not search for a different executable, stage the pinned engine, rewrite the pin, or change PATH, activation or the installed backstop. A staged private handoff cannot become a development override. An unreadable lock still fails before work.

Bootstrap hashes the active executable once, only for this explicit mode. Build inventory and local preview JSON record developmentOverride: true, pinned: false, actual identity, executableDigest, requestedPin, identityLabelComparison and pinnedContentComparison: "unknown". The human Context facts identify the override, its digest and the bypassed pin. Even an equal dirty version label does not establish equal pinned content. This evidence identifies development bytes; it is not a publisher attestation. Ordinary installed package payloads retain install-time verification and trust.

Development archive contract​

A gzip tar or ZIP contains engine.json at its root and each platform executable at its declared relative entrypoint. One admitted archive binds all members of the engine build. The manifest has exactly these fields:

{
  "contract": "oyzu.engine.v1alpha1",
  "identity": "0.1.0-local.0123456789ab",
  "runtimes": [{
    "platform": { "os": "windows", "arch": "x86_64", "abi": "msvc" },
    "entrypoint": "bin/windows/oyzu.exe",
    "executableDigest": "sha256:<64 lowercase hex>"
  }]
}

The configured digest authenticates the entire archive, including every manifest field. Every declared executable must be a regular file whose digest matches the manifest, verified at installation. A manifest has 1–16 unique platform members and distinct entrypoints. The unreleased single-member fields have been replaced in place: regenerate development packages; old installations are not new proof. Platform OS, architecture and compilation ABI must match the current engine's platform exactly; this lane does not infer ABI compatibility. The receiving engine also compares its independently compiled identity and its executable location with the admitted installed entrypoint. A manifest cannot relabel a different compiled engine and trigger another handoff.

An engine identity is the first version token printed by oyzu --version. It omits compilation profile, target and timestamp; different dirty builds can share that token. The archive and executable digests identify the actual admitted content. Explicit local digest admission is not publisher signature verification or official provenance. Release infrastructure and public publication retain their separate owners and gates.

The store verifies the archive before extraction, uses bounded no-follow extraction, checks the manifest and executable, then atomically publishes one installation under a per-digest transaction lock. Shared leases retain it while the frontend waits and the selected engine runs. Installed payloads are trusted after installation and are not rehashed on each command. Warm reuse still requires current admission; cached bytes alone never authorize an engine.

Invocation and evidence​

The child receives the original operating-system arguments and cwd, with inherited stdin/stdout/stderr. -C, --root, human/JSON mode and exit status retain their public meaning. Private handoff arguments carry only loop and correlation data: the child independently reads configuration and lock facts, checks current admission and refuses a second handoff. They do not propagate as an inherited environment variable to native build commands.

Every build retains the actual engine identity and pin state in its inventory. For a currently admitted staged executable, that inventory also records the archive release digest, executable digest, compilation platform and explicit-local-development admission. An unpinned registered executable records standalone-installation with its actual release/member facts in both coordinator inventory and captured execution evidence; it still records pinned: false. Plugin and tool identities remain under their existing report owners. Native execution supplies no filesystem/network isolation guarantee.

Failures and current limits​

DiagnosticMeaning and recovery
ENGINE_PIN_MISMATCHNo currently admitted source supplies the different pin. Run the pinned engine or admit its exact development archive in an allowed scope.
ENGINE_DEVELOPMENT_DENIEDThe explicit override lacks trusted-scope permission or is outside local context. Remove the flag or obtain applicable local permission.
ENGINE_DEVELOPMENT_UNAVAILABLEThe active development executable could not be read for content evidence. Restore/read the compiled executable and retry.
CONFIG_SCOPEA project/local/profile source attempted engine admission. Move admission to the user or responsible administrator.
ENGINE_PACKAGE_UNAVAILABLERequired archive bytes are missing. Restore the admitted archive.
ENGINE_PACKAGE_DIGESTArchive bytes differ from the admitted digest. Obtain the expected archive; do not blindly update the digest.
ENGINE_INCOMPATIBLEManifest bootstrap contract or platform is unsupported. Supply a matching build.
ENGINE_IDENTITY_MISMATCH / ENGINE_HANDOFF_MISMATCHManifest or running build does not establish the requested identity/entrypoint. Correct the package. No second handoff occurs.
ENGINE_HANDOFF_CHANGEDPin or admitted release changed across handoff. Retry with consistent selections.
ENGINE_INSTALLATION_INVALIDInstaller registration and the actual installed coordinator disagree. Restore the correct package/registration; do not copy registrations between installations.
ENGINE_START_FAILEDThe verified executable could not start. Check genuine host prerequisites and the package layout.

Bootstrap failure precedes build effects and does not adopt plugins or tools or rewrite selections. Complete verified engine installations may remain reusable. The selected project's lock must be readable even for build --plan: bootstrap cannot determine its engine from a malformed lock. An independent nested build uses its own lock; a malformed parent lock does not replace that selection. The local archive route itself needs no network. Prepared native offline use and replay are described below. Independent engine and plugin selection and the explicit development override belong to #705. Container and cross-platform semantic workers, release channels, broader host qualification, stress tests and automatic upgrades are outside this slice.

Running the Windows development proof​

The repository-owned verification harness tooling/test-native-engine-staging.py uses the real Go fixture in tooling/fixtures/go-registry: its go.mod and go.sum lock github.com/google/uuid 1.6.0. It creates a separate Git project, pins Go 1.24.13 through the supplied CLI, packages the actual engine/plugin executables, and admits their archive digests in a task-owned user config. It never implements a substitute engine or downloads a compiler itself.

Supply a bootstrap-capable development seed and a separately compiled engine with a different actual version identity. Build the selected engine with oyzu build and the plugin with oyzu exec -- cargo build --locked -p oyzu-plugin-go --features plugin. Wait for build completion before accessing its output. Then, from the repository:

oyzu exec -- python tooling/test-native-engine-staging.py `
  --seed E:/qualification/seed/oyzu.exe `
  --engine dist/cli/artifacts/oyzu.exe `
  --plugin target/debug/oyzu-plugin-go.exe `
  --source-revision <declared-plugin-source-reference> `
  --destination .oyzu/native-engine-program/proof

The destination must be new. The harness retains exact inputs, source commit, lock, archive/payload hashes, host facts, commands and output logs. Its cold build app --no-docker must install into an absent engine/plugin/tool store, produce the executable plus JUnit and Go coverage reports, and run the artifact to print 00000000-0000-0000-0000-000000000000. It checks unchanged seed and lock bytes and removes engine admission to verify both cold and warm refusal. It then runs the same project without an engine pin and checks that the active seed owns the JSON-mode build, before restoring the original pinned lock. --source-revision is a caller-declared source reference, not proof of the compiler invocation. Record the actual compile base, dirty state and any source-identical Cargo cache reuse separately, as the linked qualification does. These local development archives carry no official signing claim. Network access is required for initial tool and Go module acquisition.

Prepared native use and replay​

Captured image placement​

The experimental isolated external Go path can admit exact selected assets already installed in an immutable Linux image. The measured Windows-to-Linux proof establishes mounted composition, retained-input offline replay and the same selected B/P1/Go constituents in a locally assembled immutable image. Five fresh actions, required reports and the actual application run passed with all three assets image-installed and no asset overlays or tool restoration volume. This is a development Go application slice, not general image or platform qualification.

Selection still comes from the admitted engine archive, plugin lock/package and locked tool distribution. Image labels and PATH do not select versions. During package installation, the store retains verified contents in a store-owned package-contents sidecar outside the package payload. It binds the package kind, release, verified tree and full-archive or selected-platform payload basis. Older installs without these optional facts retain mounted placement; damaged optional metadata also leaves ordinary package use available. Installed files are never rehashed to manufacture a missing sidecar.

Reinstalling a removed package renews its optional sidecar from the newly verified archive or platform member under the installation lock. A retained sidecar does not block reinstallation or stand in for the new member's facts. If publication is interrupted while those optional facts are absent, placement remains mounted. The package payload itself still uses atomic no-replace publication.

The executor compares these facts, or the verified tool archive, against the immutable image's merged filesystem once. It checks the complete selected tree, regular executable entrypoints and directory ancestors. The current supported content trees contain regular files and directories; unsupported member kinds, including links, remain mounted rather than receiving image placement. Windows file-mode observations are not treated as Linux executable-mode facts. The resulting native user image-cache receipt binds image/index, selected manifest/configuration, platform, constituent identity, layout and installation path. Project action or preparation records contain evidence references only; they cannot grant image placement authority or choose receipt paths.

An admitted image-installed constituent uses its baked path without the corresponding mount or archive restoration. Tool admission occurs before volume lookup, creation or retention. Otherwise placement remains mounted. Docker declared volumes, scratch paths and explicit overlays cannot hide admitted assets. A conflicting overlay fails with ENGINE_CONTROL_CONFLICT. Required source/output scratch and execution controls remain enforced. Warm receipts are trusted without repeated installed-payload hashing; removing the trusted image cache requires fresh image admission, not a changed package selection. Reused dependency preparation still admits the current locked tool/archive placement before freezing asset evidence. Reusing captured dependency bytes does not skip placement registration or grant authority from cached records.

Captured execution-asset evidence records bakedEngine separately from the selected archive/member. A lazy image-owned observation records the immutable image, manifest, configuration, platform and the regular-file digest at Oyzu's known semantic-worker path, /usr/local/libexec/oyzu/oyzu. Directory ancestors must be valid. Missing, unsupported or unavailable observations are explicit; no readable build identity or source provenance is inferred from bytes or labels. The baked executable is never launched for this observation. The native user image cache retains the observation, so warm builds do not rehash or reprobe it. It provides evidence only and never changes engine selection. When an outside launcher starts a whole build inside a container, that launcher must pair its immutable-image evidence with the inner CLI's selected-engine evidence; the inner CLI does not automatically discover a trusted outer-container identity.

After a successful build has installed the exact engine, plugin and tools and populated the selected ecosystem's dependency cache, the qualified Windows Go flow supports these commands with the same project, store and admission:

oyzu -C <project> install --frozen --offline --store <store>
oyzu -C <project> exec --offline --store <store> -- go mod download
oyzu -C <project> build app --frozen --offline --no-docker --no-cache --store <store>

Preserve the explicit GOMODCACHE, GOCACHE and GOPATH used for preparation. The qualification sets GOENV=off, GOWORK=off, GOTOOLCHAIN=local, GOPROXY=off, GOSUMDB=off, and GOVCS=*:off; it also uses unavailable loopback HTTP proxies with empty proxy bypass lists. These are client and native tool controls, not OS network isolation. --offline alone does not establish that an arbitrary project command cannot contact the network.

Missing engine or plugin installations can still be restored from their exact admitted local archives. A cached tool archive can likewise supply an absent installation. If neither eligible installation nor required archive is present, the command refuses the missing package; a missing Go module reports module lookup disabled by GOPROXY=off. Restore the exact content through the approved online preparation path, then retry. Do not change the lock to whatever happens to be cached. Setup discovers an already installed plugin and does not provide independent plugin acquisition.

Replay here means executing the recorded command again with the same executable, arguments, working directory, source/lock, package selections and relevant environment/host facts. There is no new history-execution command or automatic historical environment restoration. Current admission still applies; removing engine admission refuses even retained bytes with ENGINE_PIN_MISMATCH. Incompatible platforms and unavailable required native prerequisites remain explicit errors. Matching evidence is not a byte-reproducibility guarantee.

The pure-Go fixture has no C compiler or SDK requirement. The qualified Rust companion uses the existing MSVC compile/link probe before project consumers; an unavailable selected linker produces EXECUTOR_PREREQUISITE_UNAVAILABLE with provisioning guidance. Discovery does not install host SDKs or elevate. On cancellation, the staged engine records interrupted, emits BUILD_INTERRUPTED, accepts no successful artifact and returns exit 130 through the frontend. The representative concurrent proof preserves the peer's active lease and shared installed content, then lets that peer finish successfully. See the linked qualification for reusable harness commands, exact identities, failures discovered during implementation and the limits of Windows coverage.
