Updating oyzu itself

CLI reference

Published from the canonical docs/reference/self-update.md file. Features marked experimental remain experimental; check support limitations before relying on them.

oyzu self keeps the oyzu you installed up to date. It follows a release channel (stable, beta or nightly), installs the newest version of that channel, installs one exact version on request, and rolls back to the version you had before. Every download is checked against the signed evidence oyzu's own releases carry before it replaces anything.

Note: Releases are previews. They are published on the public oyzuai/oyzu-releases repository, which oyzu self reads by default, so you need no account or token. Nightly builds and pull request builds are not published yet.

Commands​

CommandWhat it does
oyzu self or oyzu self statusThe installed version, channel or pin, whether updates are automatic, the install folder, the last check and the previous version. Uses no network.
oyzu self updateInstalls the newest version of your channel, including after rolling back to a local build when a channel is recorded. Prints that you are up to date when you are.
oyzu self update --checkOnly reports whether a newer version is available.
oyzu self channelShows the channel and mode.
oyzu self channel betaFollows beta from now on and installs its newest version. Also clears a pin. Moving to a narrower channel (nightly to stable) may install an older version; that is the only time an update goes backwards.
oyzu self channel --manual / --autoSwitches between notices only and automatic updates. Combine with a channel name to do both.
oyzu self versionsThe newest version in each channel, and which channel you follow. --all adds every recent version with its channel, date and whether it has an executable for your platform.
oyzu self install 0.2.1Installs exactly that version and pins it, so automatic updates stop until you run oyzu self channel <name>. oyzu/v0.2.1 and v0.2.1 work too.
oyzu self rollbackSwaps back the binaries you had before the last change and pins that version. Running it again swaps forward.

Every command supports --json. In JSON mode the result is one record with an operation field (status, update, channel, versions, install or rollback) and the same facts the human view shows.

Illustrative output (values and timings vary):

Updating oyzu                         linux/x86_64 · stable · 0.2.1 → 0.2.2
── Download ────────────────────────────────────────────────────────────────
✓ oyzu          oyzu-linux-x86_64 · 12.0 MB · verified                  1.1s
✓ Shim          oyzu-shim-linux-x86_64 · 0.4 MB · verified              0.2s
── Install ─────────────────────────────────────────────────────────────────
✓ Swap          oyzu replaced · 0.2.1 kept for rollback              0.1s
✓ Shims         unchanged (links to oyzu)                                0.1s

✓ oyzu updated: 0.2.1 → 0.2.2 (stable) · 1.8s
  Release     oyzu/v0.2.2 · sha256:1836d82c…09c1
  Verified    digest · release provenance · publication to
              oyzuai/oyzu-releases
  Runs        oyzu 0.2.2 (release; x86_64-unknown-linux-gnu)
  Folder      /home/you/.oyzu/bin
Next: oyzu self rollback undoes this. Running programs keep the old version
      until they restart.

Human output shares the sectioned step view used by oyzu build, at 80 columns or the terminal's narrower width. Downloads name each member, its downloaded size and verification result. Install rows report actual work; Linux needs no separate Linux engine. Live terminals show running rows; redirected output prints start and completion lines without redraws.

A non-fatal Linux-engine or shim failure has a warning row and a Warnings section with the reason, a short cause and a recovery command. The update stays installed. -v includes the complete child cause and full digests; ordinary human output abbreviates digests. --json keeps the original records and full values, with the additive previous.runs status field described below. Untrusted terminal controls are escaped in human output.

oyzu self status groups Installation and Updates, shows the last check as an age, and adds its absolute timestamp with -v. oyzu self versions marks the followed channel with both a symbol and a word; a pinned install shows its pin instead of a followed-channel mark. --all also reports whether each recent version is installed, available, or has no asset for this OS. With NO_COLOR, TERM=dumb, or no color capability, marks become words (ok, warn, FAIL) and rules use dashes. Tables become labelled records without color or when they do not fit, preserving every value.

Status names a previous local build as, for example, Previous local build (0.2.2-dev.gabc…) · oyzu self rollback. In oyzu --json self, previous.version remains null for a local build; previous.runs contains that previous binary's complete --version line, in the same form as an update result's runs. Status identifies the previous file on disk as rollback does, then reads its version only when it matches the recorded digest. This stays offline. runs is null if the file is missing, no longer matches, or its version cannot be read; the other status fields are unchanged.

Channels​

A version's channel comes from its version string. GitHub's prerelease flag is ignored, so the 0.2.0 Preview is a stable version.

ChannelContainsRelease tags
stablereleases without a prerelease partoyzu/v0.2.1
betastable releases plus release candidates and betasoyzu/v0.3.0-rc.1, oyzu/v0.3.0-beta.2
nightlyall of the above plus nightly buildsoyzu/v0.2.2-alpha.0.nightly.20261027, oyzu/v0.3.0-rc.1.nightly.20261028

A wider channel never runs behind a narrower one: beta takes 0.3.0 as soon as it is stable. oyzu self decides the newest version by semantic version order of the signed tag, and a release counts only when it has the executable for your platform and both of its evidence files.

A nightly's version names the release it was built after, so version order matches build order. After a stable 0.2.1, nightlies are 0.2.2-alpha.0.nightly.<date>, below any alpha, beta, candidate or release of 0.2.2. After a prerelease such as 0.3.0-rc.1, they are 0.3.0-rc.1.nightly.<date>, above rc.1 and below rc.2. A nightly follower therefore moves to each new prerelease or release and to every later nightly, in the order they were built:

0.2.1 < 0.2.2-alpha.0.nightly.20261027 < 0.2.2-beta.1 < 0.2.2-beta.1.nightly.20261028 < 0.2.2 < 0.3.0-rc.1 < 0.3.0-rc.1.nightly.20261029 < 0.3.0

Automatic updates​

Installs made by the install scripts or by oyzu self update themselves by default. At most once every 24 hours, an ordinary command you run in a terminal starts a background oyzu self update and carries on without waiting. The background run downloads, verifies and swaps in the newest version of your channel, or with --manual only records that one is available. The next command you run in a terminal then prints one line on standard error:

✓ oyzu updated 0.2.0 → 0.2.1 (stable) · undo: oyzu self rollback
! oyzu 0.2.1 is available on stable · run oyzu self update

Nothing is checked, started or printed when any of these is true:

  • OYZU_SELF_UPDATE=off is set, or the CI variable is set (to anything except false).
  • The version is pinned.
  • Standard error is not a terminal, or the command runs with --json.
  • The command is help, --version, a tool shim, shell activation or the prompt hook, oyzu env, oyzu exec, oyzu run, oyzu which, oyzu shell or oyzu self itself.
  • The folder has no install receipt, or the running binary is not the release the receipt records (a local build).

OYZU_SELF_UPDATE=off only turns off the automatic check; the oyzu self commands still work when you run them. A swap never interrupts work: programs that are running keep the binary they started with, and the next start gets the new one.

Verification​

Before a downloaded binary can replace anything, all of these must hold. Otherwise the command stops with SELF_UPDATE_UNVERIFIED or SELF_UPDATE_DIGEST_MISMATCH, and nothing in the folder changes.

  1. Its SHA-256 matches the digest the release reports for the asset.
  2. <asset>.provenance.sigstore.json is signed by oyzu's release builder key, names the release builder, and covers exactly that digest.
  3. <asset>.publication.sigstore.json is signed by oyzu's release publisher key, covers that digest, places it in oyzuai/oyzu-releases at this tag under this asset name, and names the provenance from step 2. An old signed binary moved under a newer tag or another name is refused.
  4. The new binary runs --version before it is swapped in.

The two public keys are built into oyzu; they are the ones in the [publish.requirements] of the repository's oyzu.toml. There is no option to skip a check. The same checks cover oyzu-shim and, on macOS and Windows, the Linux oyzu used for isolated builds.

What changes on disk​

oyzu self only changes the folder that holds the running oyzu, links resolved:

FilePurpose
oyzu, oyzu-shim (.exe on Windows)The installed binaries.
oyzu.previous, oyzu-shim.previous (oyzu.previous.exe, oyzu-shim.previous.exe on Windows)The binaries from before the last change, for oyzu self rollback. One generation is kept.
.oyzu-install.jsonThe install receipt: channel, pin, mode, repository, version, tag and digest, the previous version, the last check and a pending notice.
.oyzu-self.lockLocked by the operating system while a change runs, so two never overlap; the lock ends when that process exits, even if it crashed. The file stays.
.oyzu-update/Downloads before the swap. Removed afterwards.

The swap renames instead of overwriting: the old oyzu becomes oyzu.previous and the verified download takes its name. Every platform allows renaming a running executable, which is why this works on Windows too. If a rename fails, the binaries already swapped are put back.

After the swap:

  • On Windows, the new oyzu reshim runs (after a rollback too), because Windows shims are hard links to the old oyzu-shim.exe. On Linux and macOS, shims are links to oyzu and already reach the new binary.
  • On macOS and Windows, the new oyzu engine install --linux registers the release's Linux oyzu for isolated builds, as the install scripts do. A failure there is reported, and oyzu stays updated.

Local builds and other installs​

A folder whose oyzu matches no release, such as one built with oyzu build cli or installed by oyzu run bootstrap -- --source, is a local build. It is never updated automatically. When self-update settings record a channel, oyzu self update follows it again, just as oyzu self channel <that channel> would. This includes returning to a release after oyzu self rollback restored a local build; following the channel clears a pin and enables automatic updates. oyzu self update --check reports the available release without replacing the local build or changing its settings.

With no recorded channel, oyzu self update refuses with SELF_UPDATE_LOCAL_BUILD and Next: oyzu self channel stable. That command records stable and installs its newest release. oyzu self install <version> or oyzu self channel <name> also replaces a local build when you ask, keeping it as oyzu.previous.

An install from before oyzu self existed has no receipt. The first oyzu self update adopts it, as a stable install with automatic updates, when the running binary's digest equals a published asset's digest.

Sources, mirrors and tokens​

oyzu self reads the same variables as the install scripts:

VariableDefaultMeaning
OYZU_RELEASE_REPOthe receipt's repository, else oyzuai/oyzu-releasesRepository whose releases are read
OYZU_API_BASEhttps://api.github.comGitHub API base, for GitHub Enterprise or a test server
OYZU_DOWNLOAD_BASEhttps://github.comBase of anonymous release downloads
GH_TOKEN, then GITHUB_TOKENnoneSent only to the API origin, to lift the anonymous limit of 60 requests an hour or to read a private mirror

A mirror must serve the same signed evidence as oyzuai/oyzu-releases; the publication signature still has to name that repository. Downloads go through the proxy and certificate settings other oyzu downloads use. Plain HTTP is allowed only for loopback test servers.

Errors​

CodeCauseRecovery
SELF_UPDATE_LOCAL_BUILDself update has no recorded channel for the local buildoyzu self channel stable
SELF_UPDATE_PINNEDoyzu self update while a version is pinnedoyzu self channel <name> to follow a channel again
SELF_UPDATE_VERSION_UNAVAILABLENo such release, no release of that channel for your platform yet, or a PR build was requestedoyzu self versions --all
SELF_UPDATE_VERSION_INVALIDThe version is not a release versionUse a version such as 0.2.1 or 0.3.0-rc.1
SELF_UPDATE_PLATFORM_UNAVAILABLEThe release has no executable for this platformChoose another version
SELF_UPDATE_UNVERIFIED, SELF_UPDATE_DIGEST_MISMATCHA check in Verification failedDon't use that release; report it. Nothing was changed
SELF_UPDATE_UNRUNNABLEThe downloaded binary does not run on this hostChoose another version. Nothing was changed
SELF_UPDATE_HTTP, SELF_UPDATE_NETWORKThe release repository could not be readCheck the connection, HTTPS_PROXY or GH_TOKEN, then retry
SELF_UPDATE_WRITEThe install folder is not writable, or a rename failedCheck the folder's permissions; a package manager's folder is updated by that manager
SELF_UPDATE_BUSYAnother oyzu self operation holds the lockWait a minute and retry
SELF_UPDATE_NO_PREVIOUSoyzu self rollback with no oyzu.previousNothing to roll back

All of them exit with status 1.

Platforms and limits​

  • Linux, macOS and Windows on x86_64 and arm64 use the same rename swap. The flow is tested on Linux; Windows and macOS are not tested yet.
  • An x86_64 oyzu running under emulation (Rosetta, or x64 on Windows ARM64) updates to the x86_64 build; reinstall with the install script to move to the native one.
  • The channel list reads the newest 30 releases (100 with versions --all).
  • Release signing uses oyzu's self-managed release keys, not keyless Sigstore. Changing those keys needs a release, signed with the old keys, whose binary carries the new ones.
  • oyzu 0.2.0 predates oyzu self, so after installing it the command is missing. Run oyzu.previous self rollback (Windows: oyzu.previous.exe self rollback) from the same folder to go back, or reinstall with the install script.
  • Nightly builds, pull request builds and organization policy over the channel or automatic updates are not available yet.
