Node applications

CLI reference

Published from the canonical docs/reference/node-applications.md file. Features marked experimental remain experimental; check support limitations before relying on them.

The node/app builder builds a Node application and produces a directory artifact, normally the contents of its dist/ folder. Use it to ship a front-end site or another static application as a directory that other targets, such as a container image, can consume.

Note: Node application builds are experimental. They support a single package root (npm, pnpm, or Yarn, see Yarn builds), Vite 8 projects, and a private npm workspace root. See Limits.

Quick start​

If your package's native build script writes dist/, declare the build in build.yaml:

builds:
  frontend:
    uses: node/app
    path: frontend
oyzu run list
oyzu build
oyzu inspect dist

Oyzu runs the native build script with your package manager, then stages the contents of frontend/dist/ as the primary directory artifact application-<snapshot-version>.

A consumer that uses materialize: [{from: frontend, to: site}] receives site/index.html directly, without a nested dist directory.

A package with a vite dependency and "scripts": {"build": "vite build"} needs no build.yaml. Package discovery selects node/app for it (see Vite projects).

Builds use the Node builder plugin. See plugin packages for how plugins are installed and pinned in oyzu.lock.

How the output directory is chosen​

Selecting node/app is how you tell Oyzu that your build script follows the dist convention. Oyzu does not read your script to find out.

The output must be a freshly produced directory inside the package:

  • A missing output directory, a file where the directory should be, linked entries and special files fail the build. Contents left by an earlier build never count.
  • Build, test, lint and read-only format checks still run. The default quality checks skip the generated dist.
  • Browser globals are not assumed from the application selection alone.
  • The artifact keeps the platform it was built on. Reusing one artifact across platforms is not supported.

How Oyzu picks a builder:

  • Discovery reports builder_selection: explicit and the dist-application output profile.
  • A recognized framework such as Vite has its own output rules and validation.
  • uses: node/package always builds a package archive instead (see npm workspaces and plugin packages).
  • If discovery infers a Node target whose script is unknown, it builds a package archive. Add uses: node/app only when the script writes dist/.
  • A custom output directory other than dist is supported only for Vite (see below).

A single-root npm project with a package name and build script can build this inferred package archive on the native host, without build.yaml or Docker. It keeps npm package output rather than assuming your script writes a static site. With dependencies, include the native package-lock.json; generate it with npm before building. Run oyzu install and oyzu build, then consume the resulting .tgz as an ordinary npm package. Other inferred Node profiles retain their existing executor requirements.

Use the directory in an image​

A docker/image target can take the application directory as input:

builds:
  frontend:
    uses: node/app
    path: frontend
  image:
    uses: docker/image
    path: image
    materialize:
      - from: frontend
        to: site

The image's Dockerfile can use COPY site/ /site/. It receives site/index.html and the generated assets with no extra dist layer. The image build uses the recorded artifact and the matching platform.

The image build context is made from the selected source files plus the materialized directories:

  • Directory inputs keep all their files, including empty directories and names like dist that source capture normally skips.
  • Linked inputs, name collisions and paths outside the image target are rejected.
  • The combined inputs may hold at most 100,000 entries and 10 GiB of file data.
  • Oyzu checks that the copied content did not change during the copy.
  • Source ignore rules do not filter materialized artifacts.

Vite projects​

Discovery recognizes a vite build script and selects node/app without a build.yaml.

A different output directory​

To write somewhere other than dist/, use vite build --outDir public-site as the native script.

  • The script must be exactly vite build, optionally followed by one literal --outDir <path>.
  • The path must stay inside the project and use only ASCII letters, digits, /, _, - and .. Parent (..) segments, absolute paths, shell expansion, quoting and compound commands are not interpreted.
  • Any other Vite flag fails planning with a diagnostic.

Vite configuration files​

Oyzu uses Vite's own loader for vite.config.js, .ts, .mjs, .mts, .cjs and .cts. Your configuration can pick a mode, add plugins and emit extra assets. Discovery and dependency installation never run the configuration.

During the build, Oyzu replaces the private copy's build script with a small wrapper. Your checkout is not changed.

  • Your package manager still runs the prebuild, build and postbuild scripts.
  • The wrapper calls Vite 8's build API and records the resolved configuration and the files written.
  • A literal --outDir takes precedence over the configuration's output directory.
  • Files that postbuild adds to the output directory are included.

If your build script is replaced by something that writes no Vite output, the earlier site is not published.

External npm execution​

Select node/app with an installed Node plugin. No extra build option or helper file is needed. These commands build a Vite application:

oyzu --json build app --full --no-cache
oyzu --json build app --isolated --platform linux/amd64 --full --no-cache --image npm=<node-image>

The second command runs the build in an isolated Linux amd64 worker with network access disabled during execution (see Isolated builds).

The build checks that the resolved output path is inside the source, not linked, and was not left over from an earlier run. It then lets Vite write. After your npm command succeeds, Oyzu copies the output tree, including postbuild additions, into the planned artifact. A failed build leaves no usable artifact. Fix the command or configuration and rebuild.

Before a build finishes, the implicit lint and format checks may evaluate your Vite configuration separately to find generated-output paths to skip. This does not run the build.

Artifacts​

ArtifactNameNotes
Primaryapplication-<snapshot-version>The output directory. Consumers that don't name an artifact get this one.
build-metadatavite-output-<snapshot-version>.jsonMedia type application/vnd.oyzu.vite-output.v1+json. Records the Vite version, snapshot version, project root, output directory and mode.

Both artifacts are covered by the bundle's integrity checks.

Limits and failures​

  • One client environment and directory output only. Library and SSR builds, multiple environments, watch mode and write: false fail with a message.
  • The project root and output must stay inside the project, with no linked parent directories.
  • Rollup output options must agree with the resolved directory.
  • Vite versions other than 8 are not supported.
  • Your Vite plugins are project code. They run under the build sandbox but are not trusted release evidence.
  • A failed build produces no output record. Missing, malformed or version-mismatched metadata fails the build. Fix the cause and rebuild.

Isolated builds​

With --isolated, Oyzu captures your dependencies first and then builds in a Linux worker with no network access. Use the usual build options. To use your own image instead of the base execution image, add --image npm=<node-image>:

oyzu build app --full --no-cache --isolated --platform linux/amd64 --image npm=<node-image>

Docker and the base execution image are required. Tool versions belong in oyzu.toml, not in build.yaml. Isolated builds run on Linux amd64 workers, including from a Windows coordinator. A platform matrix can select matching images (see toolchain platforms).

Private npm workspace roots​

Isolated npm root-workspace applications​

Select node/app at the root of a private npm workspace that has a current package-lock.json. npm decides workspace membership and linking.

For example, a root that depends on a shared member and builds it first:

{"scripts":{"build":"npm run build --workspace @oyzu-example/shared && node build.mjs","test":"node --test"}}

The member builds its module before the root imports it, and the root writes a self-contained dist/.

oyzu build app --full --no-cache --isolated --platform linux/amd64 --image npm=<node-image>

How it behaves:

  • Your root build script runs once. Oyzu does not expand it into separate member builds.
  • Recognized Node tests at the root produce one aggregate JUnit and one LCOV report. Member tests may run inside that invocation, but members get no reports or versions of their own.
  • Before the build, Oyzu checks workspace membership, the lock and the installed links. Dependencies are replayed offline during execution.
  • Lifecycle scripts run in the private workspace.
  • If a member build fails, the rest of the root script and the artifact export are skipped. Read the native error and fix the member.

This produces one directory artifact. It does not create a package archive per member (see npm workspaces). Supported: private npm root with one shared member, isolated on a Linux amd64 worker. Native (non-isolated) workspace applications, member applications, and pnpm or Yarn workspace applications are not supported.

pnpm applications​

The Node plugin builds a single-root pnpm application whose build script writes dist/.

  • Declare an exact stable version in packageManager (for example pnpm@10.11.0), or configure pnpm under [tools] if there is no declaration.
  • Keep a current pnpm-lock.yaml.
  • Run oyzu build app --full.

Oyzu runs pnpm install --frozen-lockfile before the build and checks. Node tests get JUnit and LCOV reporters. Your lint and format checks stay as package scripts. An offline build reuses pnpm's prepared store and fails if bytes are missing.

Workspaces, conflicting package managers, and packageManager values that are ranges or prereleases are refused. Isolated pnpm builds are supported with pnpm 10.11.0 on Linux amd64 (see plugin packages). For pnpm settings and lock rules, see pnpm builds.

Yarn applications​

Single-root Yarn Classic 1.22.22 and Yarn Berry 4.17.1 applications are supported with node/app. See Yarn builds for requirements and commands.

Tasks, reports and output​

Tasks:

  • oyzu run list shows your native build and test scripts, inferred lint and read-only format checks, and explicit formatting. Listing runs nothing.
  • oyzu build installs dependencies, runs the build, test, lint and format-check steps, then packages.
  • For Vite projects, the fallback ESLint setup includes browser globals as well as Node globals.
  • The output directory is excluded from implicit quality checks. Your own scripts and configuration are never overridden.
  • After a build, implicit quality tasks use its recorded output directory. Before that, they resolve your Vite configuration in production mode. That can run your configuration code on the host for development tasks, or inside the sandbox for isolated tasks.

See Node quality for the lint and format defaults.

Reports and output:

  • Native Node tests produce JUnit and LCOV.
  • The artifact is at dist/<target>/<platform>/application-<snapshot-version> in the build bundle. Read its path from the manifest instead of building the path yourself (see bundle layout).
  • Only the selected output directory is staged. Source files, dependencies and tests are not copied into it.
  • Failed tests or quality checks stop the artifact from being published. Their reports stay in the bundle.

Integrity:

  • The manifest records kind: directory, the version, the producing action, a full file inventory and a content digest. oyzu inspect dist checks them (see directory artifacts).
  • materialize copies verified content into a fresh consumer context and keeps the producer's evidence references.
  • A failed operation can leave partial output. It is not recorded as an artifact.

Pinned Node in isolated builds​

If your project pins Node ([tools] node = "22.12", locked with oyzu install node@22.12), isolated builds run on that exact Node instead of the image's copy. Oyzu:

  1. Reads the Linux (linux/amd64/gnu) archive recorded for that version in oyzu.lock.
  2. Downloads it, unless a cached copy under the user data directory still matches the locked SHA-256.
  3. Verifies the bytes against the locked digest.
  4. Restores them read-only at /scratch/nodetool.

How it is used:

  • The directory is placed on PATH just before the image's system directories. The image's package manager (npm, pnpm or Yarn) keeps running and only the runtime changes. Preparation and every build action see the same environment.
  • A different pin or archive changes the action identity.
  • Without a pin, the Node that build preflight locks is used the same way (see Default Node selection). If an engine range has no matching LTS release, a newer stable runtime can be selected even though the image carries Node 22.
  • Projects whose oyzu.lock has no Node entry, managed builds and non-Linux workers use the image's Node.
  • To test other Node versions, use verification toolsets, which run natively and never in the isolated worker.

Limits:

  • Oyzu's test reporting passes Node 22 flags such as --test-coverage-exclude. With a pin older than Node 22, the build works but the native test stage fails with bad option. Pin Node 22 or later if you run tests.
  • Only linux/amd64 workers are supported, and offline builds need the archive already cached.
  • Pinning was tried with the npm image only. How the pnpm and Yarn images handle the changed PATH has not been tried.

A locked npm or pnpm release (from [tools] or an exact packageManager) replaces the image's manager the same way. See npm and pnpm installation.

Default Node selection​

Without a configuration pin, the default request is lts, whether or not engines.node is set.

  • Oyzu picks the greatest stable release marked LTS in Node's index.json that satisfies every engine constraint.
  • If no LTS release satisfies them, it picks the greatest stable release that does.
  • Example: if 24.x is LTS and 26.x is Current, >=22 selects 24.x and >=26 selects 26.x.
  • node = "latest", node = "26", exact pins and lts/<name> keep their usual meaning and must satisfy engines.
  • The nearest .nvmrc or .node-version above the build folder (up to the project root) with an explicit version (22, v22.14.0) is used as the request instead. If neither file exists, an exact devEngines.runtime version is used. An alias such as lts/* is refused with a hint, and a [tools] node value must agree with the file (see native pin files).

Explaining and locking:

  • oyzu build --plan shows the LTS default and fallback rule as the requirement source. Pin previews and locks keep the lts request.
  • A matching lock keeps its exact version, including a fallback, without checking today's LTS data. Engine constraints are still checked offline.
  • A lock from the old default (*) does not match the lts default. Resolve it online once before building offline.
  • Under an organization catalog, the signed index has no LTS markers. Use an approved exact version or a named line such as lts/krypton. The moving alias fails with TOOL_LTS_METADATA_UNAVAILABLE and does not contact a publisher outside the catalog.

Image requirements​

The base execution image installs libatomic1, which newer Node binaries need. An image you pass with --image npm=<ref> (or pnpm=, yarn=) must provide it too.

Prerequisites​

  • Node and a supported npm or pnpm release, installed through tool management.
  • Native builds need compatible tools and your project's dependencies already installed. Installing Node doesn't install your test or quality dependencies (see Node quality).
  • Isolated builds need Docker and the base execution image, with the locked Node and the pinned quality defaults.
  • Dependencies are captured through your package manager before isolated execution, then replayed offline. No new download route or credential channel is added.

For native builds on the host, see local builds.

Limits​

  • Platforms: native builds are supported on Windows and Linux. Native Vite configuration output is supported on Windows only. Isolated builds run on Linux amd64 workers, including from a Windows coordinator. macOS, Windows ARM64 and Linux ARM64 are not supported yet.
  • Vite SSR and library modes, compound Vite commands, native workspace application output and cross-platform reuse of one directory artifact are not supported.
  • Project build scripts are project code. They run under the build sandbox.
  • Executable file modes in directory artifacts are not preserved when a Windows coordinator transfers them (see directory artifacts).
  • The consumers tested read the output with a limited DOM, not a real browser. Browser behavior is not checked.
