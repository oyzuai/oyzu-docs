Node application directory artifacts

CLI reference

Published from the canonical docs/reference/node-applications.md file. Features marked experimental remain experimental; check support limitations before relying on them.

The experimental node/app builder declares a versioned directory artifact for a recognized Vite build or an explicitly selected application with a custom native build script. No output section or new Oyzu setting is required. This supports standalone package roots, including native Vite 8 configurations and the conventional dist/ contract below; native workspace application outputs and automatic custom-script output inference remain unfinished. Platform matrices can select matching provisioned Node images through toolchain selection; the Docker suite has verified the authored EX-050 graph with amd64 and ARM execution.

Custom build scripts and the dist convention​

For a project whose native script writes dist/, application intent is sufficient:

builds:
  frontend:
    uses: node/app
    path: frontend

The authored directory example uses "build": "node build.mjs". Oyzu runs the native script through its selected manager, then stages the contents of frontend/dist/ as the primary directory artifact application-<snapshot-version>. A consumer using materialize: [{from: frontend, to: site}] receives site/index.html, without a nested dist directory. This is a documented convention selected by explicit application intent, not static interpretation of arbitrary JavaScript. Custom scripts retain native lifecycle semantics and can use compound commands supported by their manager.

The output must be a freshly produced contained directory. Missing output, a file in place of the directory, linked entries or special files fail packaging; previous bundle contents cannot satisfy the new build. Build/test/lint/read-only format gates still apply, and the default quality checks exclude the generated dist. Browser globals are not inferred merely from the application selection. Static content alone does not prove platform independence: the current artifact retains its execution platform, and multi-platform reuse remains unimplemented.

The npm builder's own fixed dist collector has a native read contract for that tree and stages its artifact under the engine-owned output mount. On supported hosts it can run confined; a project command, another manager or a different output directory cannot borrow that model. Distributed safe repetition still requires every executed action's admitted facts, rather than inferring it from directory output or a successful cache lookup.

Discovery exposes builder_selection: explicit and the dist-application output profile. A recognized framework such as Vite has stronger output evidence and keeps its native adapter and validation. Explicit node/package retains native archive packaging. For compatibility, an automatically inferred Node target with an unknown custom script still uses native package output; add uses: node/app only when the script follows this directory convention. A custom non-dist output requires further native output integration; no new general-purpose output configuration is introduced here. Node workspaces continue to use native workspace package planning rather than this single-root application profile.

Minimal project and native customization​

A package with a captured vite dependency and "scripts": {"build": "vite build"} uses Vite's native dist output. Ordinary package discovery selects node/app, so a standalone project needs no build.yaml. The authored frontend/image variant demonstrates a grouped consumer:

builds:
  frontend:
    uses: node/app
    path: frontend
  image:
    uses: docker/image
    path: image
    materialize:
      - from: frontend
        to: site

The image's Dockerfile can use COPY site/ /site/. It receives site/index.html and the generated assets, with no extra dist layer. The consumer uses the producer's recorded artifact identity and matching execution platform.

The executor assembles the private BuildKit context from selected source files plus explicit materializations. Directory inputs retain all artifact descendants, including empty directories and names such as dist that source capture normally excludes. It rejects linked inputs, collisions and paths outside the image target; combined inputs are bounded to 100,000 selected entries and 10 GiB of file bytes. Directory copying uses the shared snapshot traversal and verifies that its content identity did not change during the copy. Native source ignore rules do not filter explicit artifact inputs.

For a different directory, use the native script vite build --outDir public-site. The currently recognized grammar is exactly vite build with an optional literal --outDir <path>. Paths must be contained, portable and use ASCII letters/digits, slash, underscore, hyphen or dot; parent/dot segments, absolute paths, shell expansion, quoting and compound commands are not interpreted. Vite defines the native default and outDir option; Oyzu does not assume that every Node build script follows that convention.

Static discovery records the output profile and configuration-file evidence without executing project code. Unsupported Vite flags still fail captured planning with an explicit diagnostic. Unknown custom scripts follow the intent/convention rules above, and explicit node/package retains a package archive even with a Vite script. These are compatibility limits, not complete application packaging support.

Native Vite configuration​

Existing vite.config.js, .ts, .mjs, .mts, .cjs and .cts files use Vite's own loader. For example, the configuration overlay selects web/production from the native mode and emits an extra asset through a Vite plugin. Neither discovery nor dependency acquisition evaluates that configuration.

After dependency installation in the private offline workspace, preparation replaces the private package's build script with an Oyzu wrapper. The native manager still invokes its prebuild/build/postbuild lifecycle. The wrapper calls Vite 8's native builder API and observes its resolved configuration and written output. The original checkout is unchanged. A literal --outDir retains native precedence over the configuration's output directory. Package-manager behavior still determines which lifecycle hooks run.

The plan names application-<snapshot-version> before execution. Native configuration determines an intermediate output location during execution; after a successful build, packaging copies that directory into the planned artifact. The second artifact, build-metadata, is vite-output-<snapshot-version>.json with media type application/vnd.oyzu.vite-output.v1+json. Its bounded record includes schema version, kind, Vite version, snapshot version, native root, output directory and mode. Both artifacts participate in bundle integrity checks. Consumers that omit an artifact name still select primary.

The current adapter requires one finite client environment and directory output. Native root/output must remain within the captured target without linked parents. Library/SSR builds, multiple environments, watch mode and write: false fail explicitly. Bundler output options must agree with the resolved directory; the adapter checks before writing and again when observing written output. Native plugins remain executable project code subject to the sandbox, not trusted release evidence. A failed build does not produce a successful output record. Missing, malformed or version-mismatched metadata fails packaging; correct the native configuration or failed operation and rerun the build. Vite versions outside major 8 require another qualified API adapter.

Tasks, reports and output​

oyzu run list exposes native build and test scripts, inferred lint/read-only format checks and explicit mutating formatting. oyzu build retains the existing dependency preparation, native build, test, lint and format-check gates before packaging. For recognized Vite projects, fallback ESLint includes browser globals alongside Node globals. The selected native output directory is excluded from implicit quality traversal; supplied native scripts/configurations remain authoritative. After a captured build, implicit quality tasks use its recorded output. Before that record exists, explicit quality execution resolves native configuration in production build mode; this can execute configuration code on the host for development tasks, or inside the sandbox for captured tasks. Listing tasks remains non-executing. See Node quality.

Native Node tests produce JUnit and LCOV through the existing reporting adapter. The versioned primary artifact appears beneath dist/<target>/<platform>/application-<snapshot-version> in the build bundle, for the platform the target was built for (see the bundle layout); consult its manifest path rather than constructing this path in consumers. Only the selected native output tree is staged. Source, dependencies and tests are not automatically copied into that artifact. Failed tests or quality checks block artifact publication to the bundle; collected failure reports remain available.

The manifest records kind: directory, version, producing action, complete inventory and logical tree digest. Collection and oyzu inspect dist use the shared directory integrity contract. Missing output, links, special file types and oversized staging fail packaging. A failed operation can leave partial unrecorded output; it is not a valid artifact. materialize copies verified content into a fresh consumer context and retains producer evidence references. This does not prove platform independence or production release eligibility.

Prerequisites and verification limits​

Oyzu can resolve and install Node and supported npm/pnpm releases through shared tool management. Automatic native build preflight is currently limited to npm node/app targets with the conventional dist-application profile; other application profiles retain the captured path. Development tasks require an existing compatible tool selection, native project dependencies and quality tooling. Installing Node does not install every project's test or quality dependencies. See native local builds for selection, offline behavior and admission limits, and fresh-checkout qualification for measured empty-store results.

The authored variant pins Vite 8.3.2 and npm 11.11.0, with Node >=22.12. Captured acceptance uses the provisioned Node 22/npm image, the quality image, Docker metadata tooling and the isolated BuildKit worker described in builder verification. CI provisions those tools explicitly before invoking the already compiled CLI; automatic acquisition covers only the published toolchain images.

Dependencies are acquired through the selected native manager's existing broker/capture flow before isolated execution. Build actions replay prepared dependencies offline; this output integration introduces no new download route or credential channel. Native project build scripts remain executable project code and receive the existing sandbox restrictions. Vite SSR/library modes and compound Vite-command recognition, native workspace application output and cross-platform directory reuse need further integration. Windows transfer of Unix executable directory metadata retains the shared directory limitation.

python tooling/test-node-conventional-application.py --cli <compiled-oyzu-path> exercises the custom script's actual native build/test/quality tasks and directory staging on the host, including missing/wrong-kind output failures. The captured Node suite also builds the authored frontend target, then a single-platform consumer variant, checks versioned directory and OCI contents, repeatability and missing-output failure. These are separate scopes: host staging does not prove isolated execution, and the single-platform variant does not establish full EX-050 matrix acceptance. See implementation status for revision-specific results.

Rust checks cover non-executing discovery, literal output arguments, package/application distinction and configured output declarations. tooling/test-node-application.py --cli <compiled-path> executes native Vite development tasks and staging, including browser lint, native configuration/plugin assets, npm lifecycle hooks, output overrides, quality exclusions and rejected failures. CI runs that probe on Windows, macOS and Linux. The Docker acceptance suite builds the plain and configured variants, verifies actual image bytes against the directory manifest, JUnit/coverage, repeatability, custom outDir, metadata, tampering and failed-producer rejection. The configured native probe uses Vite 8.3.2 with an ESM config; every supported native loader form and package manager still needs equivalent qualification. See implementation status for checks actually completed; test registration alone does not establish acceptance. The original custom script's two-platform execution is covered separately below.

The Docker suite additionally runs the original EX-050 two-platform configuration with matching provisioned amd64/ARM Node images. It requires independently executed tests/coverage and quality, two directory snapshots, exact Docker copies, a complete OCI index and repeatability. These checks passed at revision ad6cbf1 in Docker job 110868387899. This does not establish platform-independent directory reuse or complete every authored negative case.

Pinned Node in the captured worker​

A project that pins Node ([tools] node = "22.12", locked with oyzu install node@22.12) runs on that exact Node in the captured worker, not the image's copy. Preparation reads the Linux (linux/amd64/gnu) archive recorded for the pinned version in oyzu.lock, downloads it through the tool broker unless a copy cached under the user data directory still matches the locked SHA-256, verifies the bytes against the locked digest and restores them read-only at /scratch/nodetool. The directory is added to PATH just before the image's system directories, so the package manager the image provisions (its pinned npm, pnpm or Yarn, found earlier on PATH) keeps running and only the runtime changes; the same environment applies to preparation and every build action. The plan records the archive under oyzu.dev/locked-tool, so a different pin or archive changes the action identity. Without a pin, the Node that build preflight locks using the LTS preference and engine constraints described below is used the same way; an engine range with no matching LTS release can select a newer stable runtime even though the image carries Node 22. A project whose existing oyzu.lock has no Node entry, a managed build or a non-Linux worker uses the image's Node. Other Node versions are tested with verification toolsets, which run natively and never in the captured worker.

Oyzu's own test reporting passes Node 22 flags (--test-coverage-exclude), so a pin older than Node 22 builds but its native test stage fails with bad option. Pin Node 22 or later when tests run. Verified on Windows 11 with Docker Desktop and the npm image (Node 22.23.3, npm 11.11.0): with node = "22.12" locked, preparation observed Node 22.12.0 under npm 11.11.0 and the native test stage ran on it (a test asserting v22.12. passed and one asserting the image's v22.23. failed); with no pin the image's Node was observed; a changed lock digest was refused; the cached archive was reused. Only the npm image was exercised: the pnpm and Yarn images are not provisioned on that machine, so their PATH handling is untested. Only linux/amd64 workers are admitted, and offline builds need the archive already cached.

Without a configuration pin, the default request is lts whether or not engines.node is present. It selects the greatest stable release with a non-empty string in Node's index.json lts field that satisfies every engine constraint. If no LTS release satisfies them, it falls back to the greatest stable release satisfying them. For example, with 24.x marked LTS and 26.x Current, >=22 selects 24.x and >=26 falls back to 26.x. The preference follows publisher data without a compiled-in major. node = "latest", node = "26", exact pins and lts/<name> retain their existing selection behavior and must satisfy engines. .nvmrc and .node-version are not read yet. build --plan explains the LTS default and fallback rule in the requirement source; pin previews and locks retain the lts request. A matching lock keeps its exact version, including a stable fallback, without consulting today's LTS metadata; engine constraints still validate offline. A previous default * request does not match the new lts default; preflight must resolve the new request online before an offline build can use it. Standalone indexed resolution uses the same publisher selection, then looks for that exact release in the signed index. Under an organization catalog the signed index currently has no LTS markers: use an approved exact version or named line such as lts/krypton; the moving alias fails with TOOL_LTS_METADATA_UNAVAILABLE without contacting a publisher outside the catalog.

All repository Node image definitions (quality, npm, pnpm and Yarn) and the builder-worker image install Debian libatomic1, needed by newer Node binaries. Rebuild provisioned images to pick this up; existing tags and published digest pins do not change when a Dockerfile changes. Node 26 execution and worker-death qualification remain pending for the #289/#290 fix; see the qualification record.

Pinned npm and pnpm in the captured worker​

A locked npm or pnpm release, selected under [tools] or by an exact packageManager, runs in the captured worker in place of the image's manager, on the same Node the section above selects. It is restored read-only beside Node and recorded under oyzu.dev/locked-manager. See npm and pnpm installation for the paths and limits.
