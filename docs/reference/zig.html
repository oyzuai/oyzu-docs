Zig projects

CLI reference

Published from the canonical docs/reference/zig.md file. Features marked experimental remain experimental; check support limitations before relying on them.

The zig/project builder runs a native Zig project's build.zig and collects what it installs. Use it when your build.zig defines the programs, libraries and resources you want in the build bundle.

Note: Experimental. Zig 0.15.2 is the supported compiler. Native builds are supported on Intel macOS, and isolated builds with dependencies on Linux (x86-64, GNU). Other compiler versions and platforms aren't supported yet. Zig test reports and coverage aren't available.

Minimal project​

The Zig builder isn't in the plugin catalog yet. Build it from the Oyzu source checkout and bind it in your user configuration:

cargo build --locked -p oyzu-plugin-zig --features plugin

Create build.yaml beside your build.zig:

builds:
  hello:
    uses: zig/project

Pick the compiler in oyzu.toml:

[tools]
zig = "0.15.2"

Bind the compiled plugin by absolute path in a user configuration file:

[plugins.development]
"zig/project" = "/absolute/oyzu/target/debug/oyzu-plugin-zig"

Set OYZU_USER_CONFIG to that file's absolute path and run oyzu build from your project. The installation tree is collected as the install directory artifact in dist/manifest.json. On Intel macOS its bundle path is hello/darwin/x86_64/install. Check the manifest for the real path before running install/bin/hello.

See local plugin bindings and build bundles.

Inputs and tasks​

InputMeaning
build.yaml with uses: zig/projectRequired. Zig targets aren't detected automatically.
[tools] zig and oyzu.lockThe compiler request and the exact installation Oyzu selected.
build.zigThe native build program. Only Zig runs it, during the build.
build.zig.zonOptional. Oyzu reads the package name, version and minimum Zig version from it.
with.stepsNative build steps to run.
with.definitionsProject options passed to zig build as -Dname=value.
with.install-formatdirectory (default) or tar.gz.

.minimum_zig_version in build.zig.zon is a minimum, not a pin. Choose a compiler that satisfies it through [tools].

Manifest fields, package enum names and dependency names can use native Zig quoted identifiers, such as .name = .@"hello-world" and .@"local-dep" = .{ .path = "local" }. Oyzu preserves the decoded name when reading package and dependency facts. Metadata must remain literal; expressions and duplicate fields, including a quoted spelling of an existing bare name, are refused at their source location. Quoted names do not change dependency source admission or the supported execution platforms.

TaskCommandNotes
buildzig buildOyzu redirects the install prefix and both caches into its own output directory.
testzig build testRuns the command only. Zig test reports aren't supported, so a build that requires test reports fails with a message saying so.
formatzig fmt .Changes your source.
format-checkzig fmt --check .Read-only.

A build task you write yourself keeps its own command and working directory, and must produce the install artifact itself. Oyzu doesn't add arguments to it. Build options (with.steps, with.definitions, with.install-format) only work with the conventional build, so combining them with your own build task fails before anything runs.

What each stage reads​

StageSource boundary
buildUnbounded: build.zig is a program and may read arbitrary files or launch other programs. Zig 0.15.2's compiler dependency files and cache manifests do not account for all of those reads. An authored build command is likewise unbounded.
testUnbounded: zig build test runs the build program and tests may read files at run time. Existing required-report limitations still apply.
format-checkFixed: zig fmt --check . lists each non-dot directory recursively and parses regular .zig and .zon files. It does not evaluate imports or build programs, or follow symlink entries.

Formatting declares both file contents and directory listings, so adding a source file invalidates it. Editing an existing README does not change its read set. An incomplete or non-portable formatting inventory stays unbounded with a reason. The formatter's own rules establish this fixed boundary; no runtime observation is claimed. Build cache manifests are not treated as complete observed reads. Artifact collection consumes the build's installation tree, without a separate Zig export command. See native read admission for cache admission and version-related misses.

For dependency-free native targets, format-check opts into a private source workspace with no retained output files. Its edges to build and test are order-only, so those unbounded stages do not enter its cache dependency closure. With core private-stage admission, formatting reuses independently when its source and command identity stay unchanged. A README content edit leaves the formatter's source key unchanged, but a source-derived OYZU_VERSION can still change command identity and cause a miss. Changing a formatted source file reruns it.

Dependency-bearing native targets on Intel macOS keep formatting in the shared workspace with whole-target keying. This preserves the source path bound by the prepared dependency launcher; independent private formatting is not supported for these targets. Captured builds retain their existing formatting plan.

Build and test remain shared with whole-target source scope; their unbounded output contracts currently make them run on every invocation. The install prefix identifies the artifact to collect; it does not bound every file a build program or its children can write. Private-stage admission requires an exact list of retained regular files, so naming the installation directory alone does not make the build reusable. An incomplete formatter inventory also retains whole-target keying. Hooks, replacements and materialized inputs retain the target-wide fallback described in the action cache reference.

The Zig plugin using this opt-in requires a core release with native-read and private-stage admission support. These declarations do not add a Zig test report adapter.

Manifest parsing​

Oyzu reads build.zig.zon without running Zig. It accepts strings, enum package names, fingerprints, comments, literal containers, package versions, minimum compiler versions and string paths. A root .description string is accepted as plain metadata.

  • Duplicate fields, expressions, other unknown fields and unsupported escapes are errors, reported with file, line and column.
  • A package .version is a semantic version such as 1.0.0, 0.5.0-dev or 1.0.0-rc.1+build.1. It is limited to 32 bytes; major, minor, patch and numeric prerelease identifiers must fit unsigned 64-bit integers. Original spelling, including prerelease/build identifier case and build leading zeros, is preserved in package facts. Invalid versions are errors; correct the manifest before retrying.
  • Minimum compiler versions must still be stable major.minor.patch releases, without prerelease or build identifiers. A package version does not select or pin the compiler.
  • The manifest is limited to 1 MiB, 32 nesting levels and 20,000 values.

Tools your build needs​

Tools pinned in the target folder's oyzu.toml apply to every selected build in that folder. The Zig compiler stays first on PATH, and other tool directories follow it. For example, a build that runs Pandoc needs the GitHub provider named explicitly:

[tools]
zig = "0.15.2"
"github:jgm/pandoc" = "3.12.1"

Then pin, install and build:

oyzu pin zig@0.15.2
oyzu pin 'github:jgm/pandoc@3.12.1'
oyzu install --frozen
oyzu build --isolated
  • This works with Pandoc 3.12.1 on Linux x86-64 GNU. Plain pandoc has no entry in the tool index, so the GitHub provider is the way to ask for it.
  • Oyzu accepts complete publisher tar.gz or tar.xz trees. Interpreter commands, command aliases, partial payloads and other archive types are refused. Oyzu never changes file modes on downloaded bytes to make an archive executable.
  • Normal tool-index and download policy checks apply before a cached tool is reused. A missing tool or platform fails. The image or host never substitutes for a pin.
  • Offline builds need the tools prepared by an earlier online build, including the exact cached archives. An installed executable alone isn't enough, and TOOL_OFFLINE asks you to prepare online first.
  • Isolated builds run with the network denied. If the build step fails, nothing is exported.
  • Pandoc runs during the build but isn't part of the collected installation tree.

Native steps and linked installation archives​

with.steps selects native build steps and with.install-format: tar.gz collects the install tree as one archive. This works at an ordinary checkout root. Keep your build.zig and tracked files in place and move the bundle out of the way in oyzu.toml:

[tools]
zig = "0.15.2"

[build]
bundleDirectory = ".oyzu/bundle"
builds:
  ghostty:
    uses: zig/project
    inputs: [dist]
    with:
      steps: [lib-vt]
      install-format: tar.gz

Evidence and collected files go in .oyzu/bundle, and the native dist directory comes in as a declared source input. oyzu inspect picks that bundle by default. Git and source containment checks still apply, and an unowned destination is refused.

Oyzu doesn't translate your Zig build graph into YAML. build.zig owns the compile, documentation and install steps. The YAML says what to collect and which native entry point to run.

OptionValuesDefaultEffect
steps1 to 16 distinct names. Each starts with an ASCII letter and has at most 64 letters, digits, _ or -.Zig's default install stepSelects native build steps. Flags, paths, shell text and an empty list are refused.
definitionsMap of up to 16 option names to strings, booleans or signed 64-bit integersEmptyEach entry becomes one -Dname=value argument.
install-formatdirectory, tar.gzdirectorytar.gz packs the install tree into install.tar.gz before collection.

Definitions let you set project-defined Zig options:

builds:
  ghostty:
    path: ghostty
    uses: zig/project
    inputs: [ghostty/dist]
    with:
      definitions:
        xcframework-target: native
      install-format: tar.gz

The project decides what an option means. Here xcframework-target: native tells Ghostty to build only its host Mac application. Keep tool versions in oyzu.toml. Don't put ordered actions or commands in definitions.

Rules for definitions:

  • Names follow the same grammar and 64-byte limit as steps.
  • String values can be up to 1,024 UTF-8 bytes with no control characters. Empty strings are fine. Booleans become true or false, and integers become decimal numbers.
  • The rendered arguments total at most 4,096 bytes and are sorted by name. Spaces and punctuation stay inside one argument and are never run through a shell.
  • Null, floats, nested objects and arrays are refused.
  • Names that control the compiler, target and CPU, optimization, release or version, install prefix and caches, toolchain, system packages, fetching or job count are reserved (including case and underscore variants). Any other option goes to your project's own build.zig, and its failures show up normally.

Oyzu owns the Zig binary and the prefix, cache and --system paths. Steps and definitions don't grant tool, source, network or credential access. Native build exit codes stay separate from JUnit and coverage, and required-report checks still apply.

The tar.gz archive​

After the native build succeeds, Oyzu writes install.tar.gz and collects it as a regular file. It keeps relative links inside the tree and executable bits, and refuses links that escape, dangle or loop, and unsupported file types. Limits are 100,000 entries, 10 GiB of file content, and 64 nested link expansions. Plain directory collection rejects links, so use tar.gz for trees that contain them. oyzu inspect checks the archive's bytes. It doesn't unpack it.

Native macOS dependencies​

On Intel macOS, a Zig project with dependencies is prepared before the build, using the Oyzu-managed compiler. Oyzu downloads each original archive through its broker, checks the archive hash and Zig's package hash, and then builds with --system pointing at its prepared package tree and -j1.

  • A build task you wrote yourself doesn't get this preparation.
  • Required isolated execution is refused on this path. Native builds run with your account's access.
  • oyzu build --offline fails with OFFLINE_ASSET_UNAVAILABLE. The prepared packages aren't kept between builds, so dependency builds need to be online.
  • Preparation runs in a macOS sandbox with network and host-read access denied, a private HOME, and no registry credentials or inherited environment.
  • If your project refers to installed resources through zig-out, the build keeps zig-out available in its private workspace as a view of the real install prefix. An existing path or a case collision is refused, and your checkout is not changed.
  • XZ package metadata is checked with Apple's system liblzma from the selected SDK. If the SDK can't provide it, the build fails. There is no other decoder.

An Xcode flow is also supported for a nested project, limited to Xcode 26.3 (build 17C529), Apple Swift 6.2.4 and a finite Sparkle 2.9.0 binary package recipe on Intel macOS. One canonical Package.resolved is recognized. Unknown pins, manifests, layouts and multiple resolutions are refused, and arbitrary SwiftPM projects aren't supported. Packages come from the broker through a separate swiftpm route, SwiftPM runs with its network denied, and its caches stay private.

  • Only TZ=UTC, LC_ALL=C and the selected DEVELOPER_DIR are accepted as explicit environment for this flow. Other task environment values or PATH changes are refused before anything downloads.
  • Xcode tools write to temporary files under your user's Darwin temp root. Oyzu allows only the specific paths Xcode's tools use, on top of a sandbox that still denies network and unrelated reads. Other builds by the same user can share those temporary files, and Oyzu doesn't delete them. Required stronger isolation is refused.
  • Authored Swift or Xcode arguments for CLANG_MODULE_CACHE_PATH are refused, because Oyzu sets it.

Native documentation installation tree​

This configuration builds the installed documentation and C library of Ghostty (tested with upstream v1.3.1) as one native build:

[tools]
zig = "0.15.2"
"github:jgm/pandoc" = "3.12.1"

[build]
bundleDirectory = ".oyzu/bundle"
builds:
  ghostty-docs:
    uses: zig/project
    inputs: [dist]
    with:
      definitions:
        emit-docs: true
        emit-exe: false
      install-format: tar.gz

oyzu build ghostty-docs runs the project's default install step. There is no separate docs step. The tree has section 1 and 5 Markdown, standalone HTML, man pages, and the VT library with headers and pkg-config files. It leaves out the application resources that belong to the executable. The project's native build graph decides all of that.

  • The output keeps the version fallback 1.3.1-dev+0000000 and the pkg-config build prefix. pkg-config paths aren't relocated.
  • Two builds in one folder can't own the same native build unit, so a library build and a docs build need separate configurations.
  • The build reserves 4,096 MiB for its native action, so Docker needs more than its 4 GiB default. A 6 GiB Docker budget on an 8 GiB machine worked, with jobs set to 1. Keep at least 2 GiB of disk free.

Ghostty VT library​

Use the native steps example to select lib-vt and collect the public headers and versioned shared library in install.tar.gz. Set steps: [lib-vt, test-lib-vt] to require Ghostty's native VT tests as part of the same build.

The test-lib-vt step fails in unmodified upstream v1.3.1; it needs native repairs before that combined build can succeed. The native command produces no test totals or reports. Library installation does not include the Linux or macOS application.

Ghostty Linux desktop​

Select Ghostty's native Linux application installation in build.yaml:

builds:
  ghostty-linux:
    uses: zig/project
    inputs: [dist]
    with:
      definitions:
        gtk-wayland: false
        gtk-x11: true
        emit-docs: false
        emit-terminfo: true
        strip: true
      install-format: tar.gz

The native default install owns the executable, VT library and headers, compiled terminfo, shell integration, completions, themes, desktop metadata, icons and localizations. The native default is Debug; strip=true strips the executable without selecting an optimization profile. App metadata therefore uses the native com.mitchellh.ghostty-debug identifier. Documentation conversion and the required VT test suite use their own build configurations.

This configuration targets Debian 13 on Linux amd64 GNU. The image needs GTK 4.14 or newer, libadwaita 1.5 or newer, Blueprint compiler 0.16 or newer, glib-compile-resources, gettext, tic, pkg-config, a C/C++ toolchain, the X11 SDK, the Oniguruma development library and xmllint for XML resource preprocessing. These native prerequisites must be provisioned in the image before the build.

oyzu build ghostty-linux --isolated --jobs 1 --image zig=your-compatible-linux-image

Oyzu collects the installation archive; it does not launch a graphical session. Embedded version metadata can use Ghostty's no-Git fallback 1.3.1-dev+0000000. Wayland, desktop service activation, distribution packaging, musl and other Linux distributions are outside the supported scope of this configuration.

Output, trust and failures​

For the conventional build, Oyzu runs zig build --prefix <output>/install --cache-dir <output>/cache --global-cache-dir <output>/global-cache and exports only the install directory, keeping the executable bits of installed files. The directory isn't promoted into .oyzu/bin.

The plugin reads static source metadata and plans the build. It doesn't launch the compiler, download anything or use observation tools. Oyzu selects the compiler, verifies archives, runs the build, applies policy and reports, and collects the bundle. The plugin can't waive required checks.

  • Native host builds refuse declared dependencies (including path and lazy ones), except in the Intel macOS flow above. Use an isolated build, described below, for projects with dependencies on Linux.
  • Zig test reports, coverage and app packaging aren't supported.
  • A fast build proves only that it built and collected its artifacts.
  • A tree with links fails directory collection. Use install-format: tar.gz.
  • A build that installs nothing fails artifact collection. A failed Zig command never produces a successful artifact.
  • Fix invalid metadata at the reported location. Choose a compiler that satisfies the minimum, and keep the real failures from your build.zig. Don't replace them with an ambient compiler or remove required checks.

Using collected pkg-config metadata​

Collection preserves native .pc files, including their producer installation prefix. To use a collected library from another directory, point pkg-config at the collected metadata and override its standard prefix variable:

install_dir=/absolute/path/to/collected/install
metadata_dir="$install_dir/lib/pkgconfig"
PKG_CONFIG_LIBDIR="$metadata_dir" \
  pkg-config --define-variable=prefix="$install_dir" --cflags --libs your-library

Set metadata_dir to the actual collected .pc directory. Packages may install it under lib/pkgconfig or share/pkgconfig; Ghostty uses share/pkgconfig.

Pass the resulting compiler and linker flags to your native C consumer. The override applies to that pkg-config invocation; it does not modify the collected files or require the producer workspace. A package can instead emit relocatable metadata using prefix=${pcfiledir}/../.. when its .pc file is installed under lib/pkgconfig or share/pkgconfig.

This works when the native metadata derives its paths from prefix. Other hard-coded producer paths need a correction in the native package; Oyzu does not rewrite them. If the metadata names dependencies, provide their corresponding metadata directories and libraries too. Preserve the native toolchain, ABI and runtime-library requirements of the collected library.

Isolated dependency builds​

Isolated builds prepare every URL, transitive, contained path and lazy dependency before build.zig runs. This needs a Linux amd64 GNU compiler and a multi-platform Zig plugin build. A single local plugin binding can't do captured planning.

Oyzu's broker downloads the archives and records each archive's SHA-256 separately from Zig's package hash. Zig sees only local files. The build uses the prepared packages/p tree through --system with separate writable caches and serial -j1. Your own build task doesn't receive these arguments.

Package sources​

  • HTTPS archives: the URL can't contain user information, queries, fragments, percent encoding, control characters, backslashes or path traversal. Archive types are .tar, .tar.gz (.tgz), .tar.xz, .tar.zst and .zip, or their media types. Other types fail with ZIG_ARCHIVE_UNSUPPORTED.
  • GitHub commits: git+https://github.com/<owner>/<repository>#<40-hex-commit>. Oyzu downloads the commit tarball over HTTPS, with no Git executable and no branch or tag lookup, and the compiler must produce the exact hash you declared. Credentials, queries, abbreviated commits, .git suffixes, extra path segments and other hosts are refused. A matching native hash doesn't verify a Git object or signature.
  • Registry routes: registries.routes with protocol zig maps a source host[:port]/prefix/ (HTTPS implied) to an administrator-configured connector. Once any Zig route exists, all package routing is closed. A missing source or connector, an overlap, an unapproved redirect or an unavailable mirror is refused with no public fallback. Project and user configuration can't grant route authority. The connector's credentials stay in Oyzu and Zig never sees them. Authenticated downloads aren't reused from the cache.

Package manifests​

A dependency normally has a regular build.zig.zon. A dependency without one is accepted only after Zig's hash check and a bounded scan of the original archive proves no build.zig.zon appears anywhere in it. This works for gzip and XZ tars. The scan has limits of 64 MiB compressed, 256 MiB decoded and 10,000 members, runs in a separate worker for XZ (4,096 MiB and 120 seconds), and fails closed.

CodeMeaning and fix
ZIG_SOURCE_INVALIDThe dependency declaration isn't a supported exact source. Fix it.
SOURCE_DENIEDThe download or a redirect isn't on an approved route.
ZIG_HASH_MISMATCHThe downloaded bytes don't produce the declared hash. Oyzu doesn't substitute another source.
ZIG_ARCHIVE_UNSUPPORTEDThe archive type isn't supported.
ZIG_MANIFEST_UNAVAILABLEOyzu can't prove the dependency's manifest. Keep a regular build.zig.zon or use a supported original archive.
ZIG_CACHE_INVALIDReused data no longer matches its recorded receipt. Prepare again online.

Filenames and links in packages​

Linux dependency package trees keep regular filenames that end in a dot, such as ._., and direct symlinks from one regular file to a sibling regular file (the target is a single portable name). Chains, directory links, dangling links and absolute or traversing links aren't supported. Project sources, build artifacts, directories, trailing spaces and other filename rules are unchanged. Packaging for Docker image dependency contexts still applies portable names and can refuse these trees.

Reuse and limits​

  • Reuse needs identical dependency contents, compiler and plugin identities, and source mapping, and checks current routes again.
  • Offline builds replay prepared dependencies from an earlier online build.
  • Required test reports and coverage are refused before preparation until a Zig report adapter exists.
  • Private connector sessions and live organization endpoints aren't supported.
  • Zig's native caches are fresh for each executed isolated build, so native incremental compile speed isn't available there.
