Node lint and formatting

CLI reference

Published from the canonical docs/reference/node-quality.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Node packages get lint, format-check and format tasks without any Oyzu configuration. lint and format-check only read your files and run as build gates when selected by --full, CI or policy. format rewrites files and only runs when you ask for it.

Status: experimental. It works for single packages using npm, pnpm or Yarn, and for npm workspaces. Other workspace forms are not supported yet.

Quick start​

From the package or npm workspace root:

oyzu run list
oyzu pin
oyzu install --frozen
oyzu run lint
oyzu run format-check
oyzu run format

Your own scripts and oyzu.toml task replacements win. If package.json defines lint, format-check or format:check, Oyzu runs that script instead of the built-in check. A script named format:check is treated as the read-only formatting task.

Which tools run​

Oyzu picks one linter and one formatter from your project's files:

RoleDefaultChosen instead when
LinterESLintA biome.json or biome.jsonc selects Biome
FormatterPrettierA biome.json or biome.jsonc selects Biome

Your native ESLint or Prettier configuration counts as stronger evidence than the default. Oyzu reads configuration files without running JavaScript or launching tools. If your files point to two different tools for the same role, discovery fails instead of picking one. Resolve the conflict by removing one configuration, or choose in build.yaml:

with:
  linter: eslint
  formatter: prettier

Task overrides do not bypass this check. See discovery selectors.

Behavior​

TaskWhat it doesChanges files
lintRuns ESLint or biome lint on your source filesNo
format-checkRuns prettier --check or biome formatNo
formatRewrites files with Prettier or biome format --writeYes
  • A build that selects lint and format-check runs them before collecting artifacts. A failure stops the build and no artifacts are collected. format is never part of a build.
  • format is not transactional. If a later file or package fails, earlier edits stay.
  • The built-in lint and format-check reject extra arguments, so an argument cannot turn a check into a write. To pass custom flags, write a package.json script or an argv task. Oyzu does not guess whether a custom script is read-only from its name.
  • ESLint never applies automatic fixes. With no ESLint configuration, Oyzu uses recommended JavaScript and TypeScript rules.
  • Prettier uses your options, EditorConfig and ignore files.
  • Biome gets explicit file arguments and uses your Biome configuration and ignores. It does not read from stdin. Long file lists are split into batches, and a failure in any batch fails the task.
  • Native diagnostics are shown as they are, with the tool's own exit status. Files a tool ignores can produce no check.

What gets checked​

  • The built-in tasks check JavaScript and TypeScript files (.js, .jsx, .ts, .tsx, and their CommonJS and ESM variants). They do not format JSON, CSS or other files, even though Prettier and Biome can. To format those, write your own script.
  • Source discovery skips dependency folders, .git, .oyzu, .oyzu-build, dist, build and coverage output. It never follows symlinks and stops at 100,000 files.
  • In an npm workspace, the root checks skip member folders, and each member's checks skip nested members. See npm workspaces.
  • For a Vite application, the build output folder is skipped and browser globals are enabled in the default ESLint rules. If the output folder is not known yet, the task reads your Vite configuration in production mode to find it, which can run your configuration code. Discovery and oyzu run list never do this. An invalid or uncontained output path fails the check.
  • In a Mocha project, the default ESLint rules know Mocha globals in test and tests folders and in test and spec files. The default rules also know Jest globals in test files, and Node globals everywhere. A custom test location needs its own ESLint configuration.

Tools and versions​

ToolVersion Oyzu providesNotes
ESLint10.13.0, with recommended JavaScript and TypeScript rulesUses your configuration when you have one. Legacy eslintrc needs a compatible ESLint 8 or 9 installed in your project, or a move to flat configuration.
Prettier3.9.10Your configuration, EditorConfig and ignore files
Biome2.5.15Biome 2 only. Other major versions are rejected.

TypeScript 6.0.3 backs the default TypeScript parsing (typescript-eslint 8.72.0 supports TypeScript >=4.8.4 <6.1.0). TypeScript 7 is not supported by that parser. Your project can still compile with TypeScript 7.

The listed versions are the ones Oyzu provides and uses by default. Other versions in the same major range can work but are not guaranteed.

Where the tools come from​

Tools installed in your project win, including hoisted ones. If your package declares a tool that is missing from its installed dependencies, the task fails. Oyzu does not substitute a different version. Otherwise Oyzu uses the default.

  • oyzu pin records the exact default set under quality.node in oyzu.lock: every package version, upstream URL, upstream integrity and SHA-256, plus the default package files. Commit that lock. pin selects metadata; install --frozen prepares the selected runtime.
  • Host tasks, local full builds and isolated builds use the same locked set in the shared tool store. Preparation installs missing bundles and verifies downloaded bytes before publishing them. Installed tools are then trusted; reuse does not rehash their payloads. No manually provisioned checker directory is needed.
  • Isolated actions restore a read-only archive from that installation without a Node quality image. npm lifecycle scripts never run while the default quality bundle is installed. No build action downloads checkers.
  • New Oyzu releases ship new defaults. Ordinary builds, runs and oyzu pin retain an existing exact set. Use oyzu pin --refresh or a whole-project oyzu update to adopt the defaults shipped by your current CLI; the next task prepares the new installation. See tool commands.
  • Offline tasks need the project lock, selected runtime and quality bundle already available in the same store. Run one online check first. Administrative tool eligibility and fetches.sources restrictions apply during preparation, including reuse.
  • Biome's platform binary package is part of the locked bundle. A missing project-declared tool or unavailable platform fails preparation or execution; no stage is silently skipped.

Supported on Linux and Windows. macOS is not supported yet.

Jest execution​

Oyzu recognizes a single-root Jest command, either a jest script or the inferred test task, and asks Jest for JSON and LCOV output. Your Jest reporters, transforms and test selection stay as you configured them.

  • The native JSON result is converted to JUnit. It is written next to the JUnit destination with .jest.json added to the name.
  • Coverage goes to lcov.info beside the LCOV destination.
  • Failed tests or loading errors, and missing required reports, fail the task.
  • Oyzu refuses to overwrite an existing report file. Move or delete it, then retry.
  • A script that is not a plain jest command keeps its own body and must write its own declared and required reports.

If your test script is jest --ci and you want a different report location, declare the reports. An authored task needs run or argv; reports alone does not inherit a command.

[tasks.test]
argv = ["npm", "run", "test"]
reports = [
  {kind = "test", format = "junit", path = "reports/custom/junit.xml"},
  {kind = "coverage", format = "lcov", path = "reports/custom/lcov.info"},
]

Jest 29.7.0 with npm is supported on Linux and Windows (x86-64). Other versions and package managers are not supported yet.

Vitest execution​

Oyzu runs Vitest through your own Vitest configuration (or your Vite configuration as a fallback) and adds JUnit and LCOV output while keeping your reporters. Scripts that are exactly vitest or vitest run keep their package manager lifecycle. For a project without such a script, Oyzu runs the installed Vitest CLI. Custom scripts are left alone and must meet their own report obligations.

  • Oyzu requires Vitest 5 and a matching installed @vitest/coverage-v8 or @vitest/coverage-istanbul, whichever your configuration selects (V8 by default). A missing or mismatched provider fails before the tests run. Install your project's dependencies with its package manager and retry.
  • Native coverage is always on for the required report, even when your configuration leaves coverage.enabled off. Vitest may read source files that no test imports, so the test action keeps the whole target's source. Your include and exclude rules, reporters and thresholds still apply, and Oyzu does not waive their result.
  • Automatic Vitest commands skip .oyzu/** and .oyzu-build/**, so retained copies of your source do not add test suites.
  • The Vitest reporting adapter runs one worker at a time. This does not change test selection, your timeouts, coverage, reports or gates, but a large suite can take longer within the 600-second action limit.

Vitest 5 (tried with 5.0.3) and the V8 provider with npm are supported on Linux and Windows (x86-64). Istanbul, browser mode, other versions and package managers are not supported yet.

Errors and fixes​

SituationWhat to do
A tool is declared in package.json but not installedInstall your project's dependencies with your package manager, then retry.
QUALITY_LOCK_REQUIREDRun oyzu pin, then retry with the same tool store.
Offline preparation has no cached default bundleRun a check online with the same lock and store first.
Two tools are indicated for the same roleRemove one configuration, or set with: {linter: <name>} or with: {formatter: <name>} in build.yaml.
Extra arguments rejected on lint or format-checkUse a package.json script or an argv task for custom flags.
An existing Jest report file is in the wayMove or delete it and retry.
Invalid configuration or failed rulesFix them as the tool reports. The native diagnostics are authoritative.

Limits​

  • Native configurations and plugins can run their own code. Development tasks run on your machine with your task environment. Isolated builds run in the prepared offline environment. Preparation may acquire locked tools; isolated check actions run without network access.
  • Global inherited configuration, some plugin forms and configuration inherited across package managers are not supported.
  • Original-metadata formatting of files that a build rewrites is not supported. Built-in formatting does not cover JSON, CSS or other non-code files.
