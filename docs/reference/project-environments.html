Project environments (experimental)

CLI reference

Published from the canonical docs/reference/project-environments.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Every Oyzu build includes the mise library integration. Build with Rust 1.95 using cargo build --locked --bins; no integration feature flag exists. This page describes the experimental environment implementation, not a production-qualified release. Its scoped lifecycle checks passed on Windows PowerShell and Linux/macOS Bash and Zsh. See implementation status for measured results.

The opt-in OCI session prototype adds Unix launch shims for provisioned Helm/BuildKit clients. Activation itself does not contact its agent; the native invocation requests a session using its current context.

Declare an environment​

An environment-only project needs no tools, lock, install or account. Shell activation and oyzu exec apply its environment after the folder is trusted; explicit project tasks and builds always apply it:

[env]
APP_MODE = "development"
_.path = ["./bin", "./node_modules/.bin"]

The array prepends directories in order. To append as well, use this alternative:

[env]
_.path = { prepend = ["./bin"], append = ["./scripts"] }

The reserved env._ table is metadata, never an exported variable. Values and paths are literal: no variable expansion, scripts, dotenv discovery or command substitution. Plain env.PATH assignments are rejected with a migration message.

Relative paths belong to the file declaring them, including local/profile files. They do not change when you enter a subdirectory. Missing directories are allowed. Empty entries, NUL, unknown controls and an embedded host PATH separator are errors. Use "." explicitly for the declaring directory.

Normal configuration precedence applies. Each winning _.path declaration replaces the entire inherited control; [] clears project additions. Arrays preserve order. Selected tool shims precede project prepends, inherited PATH, then project appends. Existing occurrences are preserved rather than claimed as project-owned insertions.

Projects within Git use the repository root unless --root is explicit. Outside Git, the outermost applicable ancestor Oyzu configuration establishes the root. Nested files affect only their subtree. Installed tools live in the shared user store, independently of the project owning the configuration and lock. Activation can select an explicit store with --store; relative store paths resolve against the invocation directory. Use the same store for installation and activation. Relative parent components such as ../tools are normalized lexically on every host before the store's existing no-follow filesystem checks; normalization does not create directories or relax symlink/reparse-point validation.

Development tasks can select that store with oyzu run <task> --store <path>. The path follows the same invocation-directory resolution as build and install, and applies to the whole task sequence, including hooks and prerequisites. Tasks verify installed selections; this option does not install missing tools or fall back to another store. Preparation failures retain their original error and causes; shared stderr diagnostics give recovery guidance without replacing the error code. oyzu run list --store <path> remains discovery-only and does not open or create the store. Place task arguments after --; a --store after that separator is forwarded to the task instead.

Activate and unload​

In PowerShell 7.5+:

oyzu activate pwsh | Out-String | Invoke-Expression
Set-Location ./project-a
Set-Location ../project-b
oyzu deactivate

In Bash or Zsh:

eval "$(oyzu activate bash)" # substitute zsh for Zsh
cd ./project-a
cd ../project-b
oyzu deactivate

Activation can start outside any project. Directory hooks apply before the next command; configuration edits refresh at the next hook. Call _oyzu_hook to refresh explicitly in an activated shell. Hooks never install tools, run tasks or access the network. Tools declared in [tools] must already have a usable frozen selection.

Profile installation is explicit: oyzu shell install SHELL --profile-path PATH. Removing that profile block changes future loads; deactivate the current session separately. See the profile instructions.

Each activated terminal owns its state. A nested shell can call activate to obtain its own record and change projects without modifying its parent's record. Deactivation restores its inherited baseline. No shared global tool selection is changed.

Restoration and errors​

Switching first reverses the prior project delta. A scalar restores only when it still equals Oyzu's applied value; user edits and deletions are preserved. A new project's explicit assignment temporarily overrides that edited baseline, which is restored afterward. Empty strings and absent variables remain distinct.

Explicit removals use the existing configuration control:

[overrides]
remove = ["env.APP_MODE"]

The variable is unset for that project and restored on unload if the user has not changed it. PATH restoration preserves unrelated additions and removes owned unique entries even after reordering. Ambiguous duplicate edits are retained with a diagnostic.

Invalid configuration or unavailable required selection unloads the previous project's changes and reports OYZU_TOOL_STATUS=unavailable. Fix the configuration or explicitly install/update tools; the next hook retries. No failing project is partially applied. A usable environment reports ready.

Managed environments and development secret references remain unsupported in this milestone and fail explicitly. Hooks do not authenticate, refresh credentials or fall back around authorization. Applying project/local literal values through activation, hooks, shims or exec requires folder trust, because shells, loaders and interpreters can execute the contents of environment variables.

Trust a project folder​

Review the checkout's environment settings, then run oyzu trust [path]. With no path, this trusts the current project's root. oyzu trust --revoke [path] removes the record; oyzu trust --list lists records. Every form supports --json and human output. Trust is keyed by the canonical root folder, including resolution of symbolic links, and survives edits to oyzu.toml. It never writes into the checkout or contacts a service. Records live under trusted-projects in the native user state directory.

Untrusted folders never prompt or block tool selection: activation still exposes the tools but skips project/local [env], env._.path, and their removals. User/global environment values remain effective. Prompt hooks, shims, exec and one-shot env --shell use the same rule. A short stderr hint names oyzu trust once per invocation, or once per activated shell session. run, build, build planning and the build configuration digest always include project/local env and PATH settings under normal configuration precedence, regardless of folder trust. These commands explicitly execute or plan the repo's declared code and must agree with CI. config inspection also retains the configured environment.

User/global or administrative configuration can set [trust] enabled = false to disable the check, or parents = ["/absolute/projects"] to trust projects beneath selected canonical parent folders (for example E:\\CodexData\\projects on Windows). The default is enabled with no trusted parents. Project/local files cannot set these controls. OYZU_PROJECT_TRUST=false disables the check for an invocation; true enables it and overrides ordinary files. CI context is automatically trusted, including a true CI marker; platform executors run in that CI context. Local coding agents receive no exemption. Revocation removes only the explicit record: a parent rule, disabled check or CI exemption can still trust the folder.

This changes earlier literal-environment behavior. Trust existing checkouts once, or configure their parent directory in user scope. Dedicated regression coverage tests scope rejection and the compiled CLI trust lifecycle; Windows native state and real shell qualification still require running the checks on that host.

Headless execution and inspection​

oyzu env displays configuration sources, effective variable names and selected executables in separate tables. Names such as CARGO_HOME and cargo-llvm-cov are preserved literally. Configuration sources include env._.path, which is PATH metadata rather than a separate exported variable, and identify the winning source and profile from the resolved cascade (including oyzu.local.toml). Ordinary values are visible in human and JSON inspection. Credential-like names (including token, secret, password, API key, authentication and private-key names) and values rejected by the shared diagnostic sanitizer remain redacted. This is heuristic protection, not secret discovery: do not put secrets in innocuously named literal variables. Configuration/log inspection retains its separate, conservative redaction contract. Human output lists PATH entries in search order and removes Windows extended-path prefixes from displayed source paths. Tool-provided variables and inherited PATH also contribute to the composed environment. Inspection does not modify the calling shell. In an untrusted folder, oyzu env still shows configured values and provenance, with project entries marked skipped until trusted for activation, hooks, shims and exec. The displayed PATH describes the configured composition, including those entries; it is not a claim that activation has applied it.

oyzu env --json lists inspected environment values and selected commands, with configuration provenance in the configuration array. projectEnvironmentSkipped reports whether shell/exec use withholds project environment, and affected configuration rows carry the same skipped until trusted status as human output. To apply directory changes in an existing PowerShell session, run oyzu activate pwsh | Out-String | Invoke-Expression. Then where.exe oyzu includes the project-local executable before the bootstrap if env._.path contains its directory. Leaving the project restores the prior PATH. For future shells, use the explicit shell profile installation.

On Windows, directories Oyzu adds to PATH use ordinary drive or UNC notation, not the \\?\ prefixes used by internal filesystem canonicalization. Inherited PATH entries retain their original spelling for restoration. Windows PowerShell 5.1 can apply the initial activation, but the upstream directory-change hook requires PowerShell 7 or newer; use a supported PowerShell version for automatic switching (including the empty-variable requirement noted below). oyzu exec -- /absolute/path/to/program applies the trust-filtered environment, including unsets, to a child without changing the caller. Bare commands retain the existing declared-tool requirement. oyzu env --shell SHELL emits one-shot changes without installing lifecycle hooks; use activate for automatic rollback.

PATH metadata does not become a task environment variable or a hermetic build input. The existing build/task contracts still own their explicit execution environments.

Verification and remaining limits​

The repository's .oyzu/bin PATH declaration supports the in-development native CLI bootstrap workflow. Environment activation alone does not prove successful native compilation or repeated self-replacement. The activation wrapper dispatches ordinary CLI commands to the first oyzu application on the active PATH, falling back to the activating executable when none is found. Environment hooks and shell lifecycle commands retain the activating executable. This permits a successful local build to take over ordinary commands without reinstalling activation. The PowerShell lifecycle fixture verified this dispatch on Windows with the compiled limited-debug CLI on 2026-10-03. Native self-build and promotion remain separately unverified.

Run python tooling/test-project-environments.py --cli PATH --shell pwsh or select bash/zsh. The fixture exercises real shell entry/switch/leave, nested scopes, unset/restore, config refresh, failure cleanup and child-session independence. It provisions no tools and checks that no project lock or tool store was created. The native CI workflow also compares ordinary and no-default-features command help.

The intended shell matrix is Bash on Linux/macOS, Zsh on Linux/macOS and PowerShell 7.5+ where available. PowerShell 7.5 introduced support for preserving empty environment values; earlier versions cannot satisfy this environment contract (Microsoft documentation). Evidence is recorded separately; a test definition is not proof that every host passed. Additional shells, managed/secret integration, general shim expansion, active-installation retention, crash recovery, stress testing and performance tuning remain outside this environment milestone.
