Python test discovery and reports

CLI reference

Published from the canonical docs/reference/python-testing.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Python projects built with pip, uv or Poetry get an implicit test task that runs pytest. The task exists even if your project has no tests/ or test/ folder. It runs when tests are selected, such as with --full or in CI; a fast local build skips it. Pytest decides at run time which tests exist. Oyzu never imports conftest.py, runs Python or collects tests while it discovers your project.

Note: Python support is experimental. Direct oyzu run test is supported on Windows and Linux. Isolated builds run in Linux containers.

Commands​

oyzu run list
oyzu run test
oyzu build
oyzu inspect dist

Pass extra arguments to pytest after --: oyzu run test -- -k smoke.

How pytest is detected​

Oyzu looks for pytest settings in pytest.ini, .pytest.ini, [tool.pytest.ini_options] in pyproject.toml, [pytest] in tox.ini or [tool:pytest] in setup.cfg. With none of these, pytest is still the default. Several configuration files are not treated as competing frameworks.

Detection only records your intent. Pytest owns testpaths, file name patterns, markers and collection errors. This configuration needs no Oyzu setting:

[pytest]
testpaths = checks
python_files = spec_*.py

The implicit command depends on the project's manager:

ManagerCommand
pippython -m pytest
uvuv run --locked pytest
Poetrypoetry run pytest

Install Python, the manager and your dependencies first. Direct runs use the manager's own environment and behavior, including any synchronization it does, and are not isolated. TOML task replacements and pre/post hooks work as for any task.

Direct test runs​

oyzu run test runs the pytest command and writes JUnit and Cobertura reports into a test-only bundle in dist/. Pytest still collects the tests, and your manager picks the environment. See direct test reports for hooks, overrides, retention and inspection.

Requirements:

  • Python 3.11 or newer in the selected environment.
  • pytest and pytest-cov in that environment. Oyzu does not install them. It works with pytest 8.3.5 and 9.1.1 with pytest-cov 6.0.0. Other versions can fail with an error instead of producing partial reports.

Coverage​

A direct run measures your checkout, not an installed package. It keeps your coverage configuration (COVERAGE_RCFILE or the usual coverage files), including source settings, branches, exclusions and thresholds. Without source settings, it measures the task's working directory, including modules that no test imports.

  • Collected tests, files matching pytest's name patterns, conventional test file names, conftest.py files and .oyzu and .venv folders are left out of application coverage. Helper modules that tests import are not guessed to be tests. Use coverage exclusions for them.
  • Omissions apply below the measured source root. A project that Oyzu copied into .oyzu/host-workspaces is still measured.
  • Each run uses its own temporary coverage configuration and data file. An existing .coverage file or COVERAGE_FILE can't add old results and isn't overwritten.
  • pytest-cov source and output options on the command line don't override the report locations Oyzu sets. Selectors such as -k work normally.
  • Pytest caches and Python bytecode can still be written.

Which commands are wrapped​

Oyzu adds reporting to the exact python -m pytest, pytest, and the implicit manager commands. python -m pytest uses the python on PATH, even in a uv or Poetry project. Bare pytest also uses python from PATH.

Any other command (a custom shell program, for example) runs as written and must write the required reports to the declared paths or the report environment variables.

Assertion and collection errors, coverage thresholds and missing reports fail the run, and the reports that exist are kept. An empty suite keeps pytest's exit code 5 and a zero-test JUnit file. A zero-denominator coverage report is not rewritten to 100 percent.

Isolated builds​

oyzu build runs tests in a Linux container after dependency preparation. Preparation adds pytest 8.3.5 and pytest-cov 6.0.0 unless your project or lock already selects them. Your versions win, and an incompatible integration fails instead of downloading a replacement. Dependencies come from PyPI.

  • Packages in full, CI, pull-request and release contexts are tested as installed: pytest runs against the built wheel in importlib mode, and coverage measures the installed wheel's Python files. Your coverage settings, including thresholds, are kept.
  • Ordinary local development package tests use captured project source through a genuine native editable installation for the supported layout below. This evidence describes development source, independently of the inferred-version wheel and source archive. It does not validate their installed behavior.
  • Applications are tested from the sources extracted from the generated application archive. See Python applications.

Pytest creates JUnit and Cobertura reports. Oyzu stores them in dist/ and records their paths, digests and summaries in dist/manifest.json. You don't configure test or output paths. Artifacts are collected only when tests and quality checks pass.

An assertion failure, collection error or failed coverage threshold blocks the artifacts. An empty suite keeps pytest's exit code 5 and any zero-test JUnit file, and does not count as a pass. A suite with skipped tests keeps pytest's skip counts and exit code. A custom replacement that exits 0 can't satisfy a missing required report.

If a project had no test folder before, the build now runs pytest and fails when it collects no tests. Add tests or fix your pytest configuration.

Reuse within a test file​

The development-source contract is selected from the resolved local context and ordinary check mode; it has no additional public flag. --full, CI, pull-request and release contexts retain built-package validation. Its initial supported layout is pip with static declarative setuptools.build_meta, an explicit list of flat regular packages and no backend plugins or source-built dependencies. Dynamic metadata, namespace roots, custom backends, setup.py, package-directory mappings, native extensions and authored test replacements retain the existing built-package path. A native editable installation or mapping failure fails the development test action rather than falling back to a host source path.

To select tests and coverage in an ordinary local build, use the existing check levels in oyzu.toml:

[checks]
tests = "required"
coverage = "required"

Then run oyzu build --isolated --no-docker for the Linux crun case-selection path. Do not add --full or set checks.run = "all" when requesting the development-source subject: those select built-package checks instead.

The selected backend produces real PEP 660 metadata and pip installs it offline in a separate captured test environment. Native direct_url.json, import specs, distribution metadata and installer RECORD remain evidence inputs. Coverage and tests read only admitted captured source and that environment. No ambient PYTHONPATH selects the package. Required JUnit, coverage thresholds, isolation, acquisition and artifact validation gates remain binding.

Action and report metadata record oyzu.dev/python-test.subject as development-source or built-package; case keys bind this subject. The source subject omits the unused inferred wheel-version default and the wheel's separate installed environment from its case inputs. Explicit user environment values, native installed versions, metadata, backend/dependency/tool changes and editable mapping bytes remain binding. Full/package evidence continues to bind actual built-package version and wheel/RECORD facts. These identities cannot authorize reuse across the two guarantees. Native editable execution and selective captured reuse are limited to the supported Linux development flow. Full, CI, package and release validation retain their built-package inputs.

Captured pip package builds collect one test unit per native pytest file. With coverage.py in the project environment and enforced runtime-read bounds, core can rerun affected cases and retain earlier passing evidence for the rest. New and previously failed cases always run. The step keeps one combined JUnit and coverage report, and the action row gives fresh and reused case counts.

Import-time code, shared setup and runtime data changes rerun every case. Release builds run every case of a changed unit. Missing or incomplete coverage runs the whole unit with a one-line reason. Direct runs, native host builds, application archives and authored test replacements retain their existing behavior. See case selection for keys, explanations and order-dependence handling.

When coverage.py cannot be imported, case collection prevents pytest-cov's unusable plugin from stopping the test run. Its supported coverage options still parse, including addopts = --cov=api in pytest.ini, so collection and the full test run can proceed. This does not supply a coverage report: a required coverage check still fails, and existing test failures remain failures. A run requesting coverage through --cov or --cov-fail-under also fails with an unavailable coverage message even when all cases pass. --no-cov disables that optional request, but cannot satisfy Oyzu's required report checks.

Coverage.py currently comes from the prepared Python environment: pytest-cov depends on it, and a project requirement can select its version. This is Python dependency acquisition, with digest-only verification; it is not a separately managed tool with verified publisher provenance. oyzu tools info coverage and oyzu install pipx:coverage@<version> are unsupported. Oyzu has no admitted coverage.py tool provider or pipx: backend. Zero-setup acquisition with publisher evidence and a separate tool compliance record remains unavailable.

Test helpers and pythonpath​

Package tests can import ordinary test helpers, including namespace folders such as docs_src and test packages with relative imports. Pytest keeps your working directory, collection paths and test resources.

Built-package tests see your checkout's helper modules, but not the checkout's copy of the package being tested. Anything the installed wheel provides (modules, packages, namespace roots, native extension names, as listed in its RECORD) comes only from the install. A missing submodule never falls back to your source. Development-source tests retain the helper restrictions and obtain package imports exclusively through their native editable mapping into the capture.

  • Configured pythonpath entries inside your project (relative or absolute) work. Entries outside the project, file or ZIP entries, and entries that enter an installed package fail with an error.
  • Selected tests or conftest.py files inside a package that the wheel installs fail too. Move those tests into a separate test folder.
  • Oyzu keeps importlib mode even if you pass another mode to pytest.

These rules apply to package tests only, not to direct runs or application tests. Helpers are shared with shallow links (copies where Windows can't make symlinks). They don't grant network access, install packages or change your source.

Recovery​

ProblemWhat to do
No tests collectedCheck pytest's file name patterns and configuration, and run the same manager command to see what it collects
Reporters missingAdd pytest and pytest-cov to your declared dependencies or environment and prepare again
Report or coverage failureRead the native logs and report records in dist/
Coverage says No data to reportSee Coverage reports no data

Test configuration and plugins run during testing. In isolated builds they run offline. In direct runs they have your normal permissions.

Limits​

  • Pytest is the only supported framework. It runs unittest.TestCase suites, but there is no dedicated unittest runner, other frameworks, distributed pytest or other pytest and pytest-cov versions.
  • Coverage of native extensions is not measured. If no measurable Python source exists, that is a failure.

How Oyzu runs the tests​

Oyzu runs the test steps itself. It chooses the command, creates private coverage files and starts the selected interpreter. Small pytest and pytest-cov hooks are built into the oyzu executable. They only read your pytest configuration, source metadata and framework events. Oyzu never searches your project for its own scripts.

Python is required because you selected a Python build, not by the CLI. Pytest exit codes and report requirements are unchanged.

For a full native pip build, Oyzu binds one explicit interpreter, either the managed CPython or your validated target .venv. It uses that interpreter with -I and fresh JUnit and Cobertura paths, and ambient PYTHONPATH or an activated environment doesn't select one. See native preparation.

For package helpers, the pytest hook normalizes the resolved pythonpath list before pytest uses it, and guards conftest.py imports so that a protected package in your checkout is refused before either runs. Test selection stays with pytest. A pytest change that breaks this hook fails the run with an error.
