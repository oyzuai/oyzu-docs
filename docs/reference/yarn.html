Yarn builds

CLI reference

Published from the canonical docs/reference/yarn.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Oyzu builds and tests Node projects that use Yarn. Yarn Classic (1.22.22) projects and workspaces are discovered from native manifests and the lock with no Oyzu build file. Single-root applications also work with Yarn Berry 4.17.1.

Note: Yarn support is experimental. Each setup below lists the exact versions and platforms it supports. Anything not listed there is not supported yet.

Builds use the Node builder plugin, which must be installed and selected (see plugin packages). Native Yarn always owns dependency layout, peer behavior and lifecycle scripts.

Provisioning and commands​

The tested profile is Yarn Classic 1.22.22 on Node 22. Isolated builds run on the base execution image with Docker. Node and Yarn both come from oyzu.lock, so pin Node in [tools] and Yarn with an exact packageManager (or yarn in [tools]).

oyzu --root path/to/project run list
oyzu --root path/to/project build
oyzu --root path/to/project inspect dist
  • Oyzu never installs a replacement package manager during a build. --image yarn=<image> runs Yarn's isolated actions on an image of your own. Its immutable identity is recorded, and the locked Node and Yarn still run.
  • The @yarnpkg/lockfile 1.1.0 parser ships in the Node plugin package, and the default quality tools are restored from their pinned lock, so no image needs either.
  • An exact packageManager declaration must agree with native Yarn's version. A Corepack suffix such as yarn@1.22.22+sha512.<hex> is accepted and ignored in that comparison.
  • Incompatible Node engine requirements fail.

Your native scripts appear as tasks. During isolated builds, the conventional build and test work and read-only lint and format checks run. oyzu run uses host tools, and explicit formatting can modify your source (build format checks cannot). Node test scripts produce JUnit and LCOV. See Node quality.

Capture and installation​

Oyzu reads Yarn Classic v1 lock syntax with Yarn's own parser, including grouped selectors. It needs a lock that parses, current direct dependency selectors, conventional HTTPS registry archive URLs and an integrity value for every entry.

  • SHA-512 is the normal form. Older Classic locks also carry integrity sha1-... values for packages locked before the registry published SHA-512. Those are accepted only when the SHA-1 value matches the #<sha1> fragment of the resolved URL. They are verified against that SHA-1 and named in the dependency record. SHA-1 is weaker, so regenerate those entries with native Yarn if you need SHA-512 throughout.
  • Several selectors for one archive share its captured identity. Conflicting identities and ambiguous offline-mirror file names fail.
  • Every locked archive is captured, including optional and transitive ones. Git, file and other non-registry resolutions are refused.

Preparation uses the scoped broker routes for https://registry.npmjs.org/ and https://registry.yarnpkg.com/, recorded as npm-public and yarn-public. Redirects stay subject to broker authorization. Your lock keeps its original URLs and hashes. The archive inventory strips URL fragments from transport addresses and verifies the lock's SHA-512 before installation. Credentials never enter the inventory or mirror.

The snapshot holds content-addressed archives and an inventory, not Yarn's extracted cache. Each install creates a fresh private mirror and cache and a temporary Yarn configuration outside your source. Installation uses the mirror, includes development dependencies, and has no network in the worker.

  1. Before lifecycle scripts are allowed, Oyzu runs yarn install --offline --ignore-scripts --force in the private tree and compares the resulting lock with the captured one. Any change in dependency resolution fails. Cosmetic serialization changes are discarded, so your lock bytes stay as they were.
  2. During execution, yarn install --offline --frozen-lockfile --force runs the lifecycle without a broker.
  3. Acquisition never enables scripts. Native Yarn and Node versions must match the captured versions.

The comparison matters because suppressing lock writes alone doesn't show that changed resolutions agree with the lock. Registry version overrides in package.json resolutions are supported, including a different transitive version alongside a direct one:

{
  "dependencies": {"is-odd": "3.0.1", "is-number": "6.0.0"},
  "resolutions": {"is-odd/is-number": "7.0.0"}
}

Generate and commit the matching lock with native Yarn first (see the yarn-resolutions example). Yarn's own warnings and selective-resolution limits apply. File, Git, URL and alias-protocol resolution values are rejected before any native invocation. See Yarn's selective resolutions. Oyzu uses Yarn's offline mirror and does not reimplement package resolution or Yarn's cache layout.

Project settings​

Yarn Classic reads a project .yarnrc and .npmrc itself. Oyzu accepts these files only when every setting is on a fixed list that can't redirect archive sources, the offline mirror, caches, credentials or the Yarn executable:

FileAccepted settings
.yarnrcignore-engines, save-prefix, save-exact, disable-self-update-check, version-tag-prefix, version-git-message, version-git-tag, version-sign-git-tag
.npmrcpackage-lock, loglevel, progress, save-exact, save-prefix, fund, audit, update-notifier

For example, webpack's .yarnrc has ignore-engines true and its .npmrc has package-lock=false. Both are accepted and Yarn applies them.

Any other key fails acquisition with Yarn capture does not yet support <file> setting <key> before any native invocation. That includes registry, scoped @scope:registry, //host/:_authToken credentials, yarn-path, yarn-offline-mirror, cache-folder and ---prefixed command-line settings. The message names the key, not its value.

  • .yarnrc is read with Yarn's lock parser. .npmrc is read as key=value lines, and an ini section header is rejected as an unknown key.
  • Settings files inside workspace members are not supported.
  • .yarnrc.yml is Yarn Berry configuration. In a Classic build it fails with a message saying Berry needs its own setup.

Outputs, failures and migration​

To test other Node versions, use verification toolsets in oyzu.toml. matrix.node in build.yaml is refused. Toolset verification runs on the native host executor, and isolated Yarn builds use the isolated executor, so a build with verification runs fails with VERIFICATION_RUN_UNSUPPORTED.

A successful build emits snapshot .tgz packages with normalized archive metadata. The embedded package version matches the artifact version. dist/manifest.json lists artifacts, tests and coverage, with dependency snapshots and native logs beside it. Failed tests keep their reports and block packaging. oyzu inspect dist checks content integrity, not release trust.

Dependency records use adapter layout 2. They list names, versions, source IDs, SHA-256 digests and sizes. The oyzu.dev/yarn extension records lockfile-sha512 integrity and the all-locked-registry-tarballs inventory. If any archive was verified by a legacy SHA-1 value, integrity is lockfile-sha512-or-legacy-sha1 and legacySha1Packages lists those archives as name@version. Packages are classed as build inputs. Registry dependency edges and runtime or test classification aren't recorded, so this is not a runtime SBOM. Workspace captures also keep local package edges for build ordering and version projection.

FailureRecovery
Stale or conflicting lockFix it with native Yarn and commit the result.
Corrupt archive, missing captured input, disallowed source or runtime mismatchFails instead of downloading a replacement during execution. Fix the cause and rebuild.
Layout-1 dependency-free captureCapture again. It can't be replayed as layout 2.
Unsupported source configurationRejected before any native invocation, including version queries.

Workspace builds​

A Yarn Classic workspace has a private native root, a committed Classic lock and locally linked packages (see the Yarn Classic workspace example). Run the commands above from that root with no Oyzu configuration. oyzu run list includes build, test, lint and format-check. A plain oyzu run build runs yarn workspaces run build when there is no root script, so every member needs a build script. The isolated oyzu build also handles packages without build scripts.

  • Acquisition asks Yarn for its workspace list after lock validation. Member locations and local dependency edges become captured facts. Oyzu does not read Yarn's workspace globs itself.
  • Oyzu orders members by those edges, assigns snapshot versions and declares each package's reports. It rewrites versions and matching local references only in the private tree, before a fresh offline install. Your manifests and lock are unchanged.
  • An explicit root script owns its stage once. Otherwise build scripts run in dependency order, and tests and read-only quality checks combine member scripts with inferred defaults.
  • JUnit and LCOV are collected per package.
  • yarn pack --ignore-scripts creates each archive. Oyzu normalizes archive metadata and publishes the packages to dist only after the required stages pass. Failed assertions or quality checks block artifact collection and keep the failure evidence.
  • Hooks and overrides follow the shared task and report rules.

For a coarse root build, Oyzu checks the concrete public JavaScript entries selected by Node's import and require conditions before packing. It also checks declaration files selected by the types condition and literal legacy declaration paths. Existence is checked, not TypeScript validity. Missing regular files fail. Null exclusions and conditional alternatives are left to Node. The check doesn't look inside Yarn's archive, and skips browser or custom conditions and wildcard paths.

Limits: Classic needs a private workspace root. Cyclic local graphs, custom registry configuration, affected selection and member task groups are not supported. Direct host build and quality composition is less complete than the isolated build. Direct tests use the workspace report integration. Workspaces with external dependencies and broader framework setups aren't covered beyond a linked two-package project.

Isolated Classic application​

A single-root application with Yarn Classic 1.22.22 and Node 22.23.3 builds into an application directory plus Node-test JUnit and LCOV. It runs on a Linux amd64 worker, driven from a Windows x86_64 coordinator. Workspaces, other versions and other platforms are not supported.

Select node/app and keep the package manager declaration:

builds:
  app: {uses: node/app}
{"packageManager":"yarn@1.22.22","dependencies":{"semver":"7.7.2"}}

You need:

  • A current Classic yarn.lock.
  • Tool selections in oyzu.toml and oyzu.lock.
  • An installed Node plugin package that supports multiple platforms (see plugin packages).
  • Ordinary native build, test and quality scripts, an exact packageManager, public HTTPS registry dependencies with supported lock integrity, and no workspaces, project plugins, yarnPath or non-comment rc settings.
oyzu -C path/to/app --json build app --isolated --platform linux/amd64 --full --frozen --no-cache --image yarn=<image>
oyzu -C path/to/app inspect dist

The plugin and tool selections and your lock must already be in oyzu.lock for --frozen. On first adoption a normal build creates them. Don't delete an existing oyzu.lock to retry a failed build. You don't need installed project dependencies or a Yarn lock parser in the image. Oyzu orchestrates, and native Node and Yarn do installation and scripts.

Acquisition captures authorized registry archives with their original integrity data and without lifecycle scripts, then validates the lock with scripts off. Execution installs from the private mirror with network disabled, then runs lifecycle, build, test and quality steps. --frozen freezes selections but doesn't make acquisition offline.

On success, dist holds a versioned application directory and fresh required reports, with dependency and tool identity and action logs in the manifest. Failed assertions keep available reports and block export. A test that exits zero but writes no JUnit and LCOV still fails the build.

ProblemRecovery
Stale lockRun native Yarn to generate the intended lock, and keep it with the manifest.
Missing yarn.lockRestore it. Admission can report the generic PLUGIN_ISOLATED_UNSUPPORTED: no owned captured dependency provider.
A selected tool was lost during the buildRetry with the corrected coordinator. Don't purge caches by hand.

Both lock problems fail before lifecycle scripts run.

Isolated Berry application​

An isolated Berry build needs exact packageManager: yarn@4.17.1, Node 22.23.3, a current lock and an existing literal nodeLinker: node-modules:

nodeLinker: node-modules

It handles a single root with public registry dependencies. Plug'n'Play, child workspaces, yarnPath and project plugins are not supported. It runs on a Linux amd64 worker, driven from a Windows x86_64 coordinator. Other combinations, macOS, Windows ARM64 and Linux ARM64 are not supported yet. Use the same node/app declaration and isolated command as above.

Oyzu prefetches public-registry metadata and archives through the broker, with SHA-512 checks, and serves only those fixed local GET and HEAD routes. Yarn creates and validates its own ZIP cache with install --immutable --mode=skip-build. Execution copies that cache into private scratch and runs install --immutable --immutable-cache with network disabled, before your commands run. Your .yarnrc.yml, package.json and lock are not rewritten. Archive integrity and Yarn's ZIP checksums are separate checks.

The worker also gets an executable alias archive for yarn and yarnpkg, bound to the selected Node and Yarn. Executable modes survive Windows coordination, and the files are read-only for every action, including your commands and their child processes. The image's own Yarn is never used.

ProblemRecovery
Lock drift (YN0028)Regenerate the lock with the selected Yarn only when you intend to change dependencies.
Missing lockRestore it.
Plug'n'Play projectFails admission. Oyzu doesn't convert PnP projects.
Stale or missing lock, a checksum failure, or a request outside the prefetched routesFails preparation. Fix the lock or dependency and rebuild.
Child workspaces, yarnPath, project plugins, custom sources or extra rc settingsRefused.

Native Classic workspace packages​

Note: Experimental. Supported on Linux x86_64 (GNU) only. Windows, macOS and ARM64 are not supported for this setup.

A native build (without Docker) of a Classic workspace into package archives, using Node 22.23.3, Yarn Classic 1.22.22 and node/package. Your project needs:

  • A named, semver-versioned private coordinator (root) with two publishable members.
  • A genuine Classic yarn.lock, and local references such as *.
  • Flat cp source.cjs dist.cjs builds and implicit package-owned Node tests.

Select tools through normal configuration and the lock, and declare the output:

builds:
  package:
    uses: node/package
oyzu --json build package --full --no-cache --jobs 1

How it works:

  1. Oyzu runs the selected yarn install --frozen-lockfile task, after a script-free preparation with --ignore-scripts.
  2. Yarn's workspaces info supplies member links, and installed links confirm local targets. The private root is a build, test and report owner even though Classic leaves it out of its membership map.
  3. Oyzu rewrites versions and local references to exact versions in the private tree only. Classic packs each publishable member with --filename.
  4. Your manifests and lock keep their bytes. First adoption may add plugin and tool selections to oyzu.lock.

The output is two TGZ archives and six JUnit/LCOV reports. A failing root assertion blocks both member archives and all export. A replaced install task is refused before any action. Native build scripts and helpers keep their implicit pre/post lifecycle and the protected-path rules.

Not supported: pack hooks, peer dependencies and their metadata, active rc overrides, private members, aggregate builds and isolated Yarn workspaces. Empty or comment-only rc files are accepted.

Native Berry workspace packages​

Note: Experimental. Supported on Windows x64 with Node 22.23.3 and Yarn 4.17.1 only.

A native build of a Berry workspace into package archives. It needs an existing literal nodeLinker: node-modules, a named and versioned root, publishable app and shared members, literal workspace:* local dependencies, recognized package-local build bodies and implicit package-owned Node tests.

Declare the output in build.yaml, keep the genuine yarn.lock, and select tools through configuration and the lock:

builds:
  package: {uses: node/package}
oyzu --json build package --full --no-cache
{
  "status": "succeeded",
  "runId": "45292-1792727760814863500"
}

Output shortened. A root, app and shared project produces three .tgz archives and six owner reports. Oyzu runs the ordinary immutable install, does a script-free preparation, fixes native membership, links and versions, then builds and tests in the private tree. Yarn packs the archives. Private version projection leaves the lock untouched and lets Yarn translate workspace:* when packing.

Private roots​

A root with "private": true still builds, runs implicit tests and writes its JUnit/LCOV, using its Oyzu-resolved version. Only publishable members get archives. Two members mean two archives and six reports. A failing root assertion blocks member export. Keep the root named and semver-versioned. Private members are not supported.

Pack hooks​

  • Authored install replacements are refused.
  • prepack and postpack bodies are accepted only when Oyzu can show they have package-local effects before preparation or your commands. Recognized copy bodies and local Yarn helpers keep the protected-path rules. Coarse JavaScript bodies and foreign writes are refused. The whole script and helper map must match its analyzed value just before packing.
  • Yarn runs each accepted hook in one native pack. prepack can generate archive content. postpack runs after the archive is made and can't change it. A postpack failure blocks export of the target, including archives packed earlier.
  • Yarn's own postinstall stays ordinary native behavior. Berry doesn't run arbitrary pre and post build hooks automatically the way npm does.

Configuration checks​

  • Active .yarnrc.yml files in member directories and parents must be absent, comments, or the same node-modules setting. Other or malformed active settings fail before preparation. Settings changed by installation fail the frozen-facts comparison before member execution.
  • Managed environment admission also applies to the install task. An alternate rc file name doesn't bypass it.
  • Explicit npm or pnpm helper delegation is refused.
  • Yarn options before a helper's selected script that can change script or binary ownership, such as -T/--top-level and -B/--binaries-only, are refused. Arguments after the script or -- are forwarded.

Not supported: Classic, Plug'n'Play, isolated Yarn workspaces, aggregate scripts and other platforms.

Limits​

  • Supported versions and platforms are in Supported setups. Modern Yarn (Berry) is not supported for isolated workspace builds.
  • Isolated Berry configuration remains limited to literal nodeLinker: node-modules. Native configuration also admits the quoted linker and boolean enableTelemetry: false; other settings and telemetry values remain refused.
  • Custom registry layouts, private registry credentials, member settings files and other .yarnrc or .npmrc settings are not supported.
  • Lifecycle scripts that need external downloads fail in the isolated worker.
  • Yarn Plug'n'Play and project plugins are not supported.
