Verification toolsets and platform matrices

CLI reference

Published from the canonical docs/reference/runtime-matrices.md file. Features marked experimental remain experimental; check support limitations before relying on them.

To test a build on other runtime versions, add verification toolsets in oyzu.toml. To ship a build for several platforms, list platforms: in build.yaml. The two never mix: a toolset only changes how a build is checked, while a platform changes what ships. Runtime versions are never written in build.yaml; the old matrix.<runtime> axis is refused (see migration).

Verification toolsets​

The build that ships is built and tested once, with the [tools] versions. Each toolset adds a verification run: the build's runtime-dependent stages, repeated with the toolset's tools. A run never produces an artifact, so a release always has one artifact per output, however many toolsets run.

# build.yaml: nothing about runtime versions
builds:
  app:
    uses: node/app
# oyzu.toml
[tools]
node = "22.14.0"            # builds, tests and ships the app

[toolsets.node24.tools]
node = "24.14.1"            # also tested on Node 24, in pr, ci and release
oyzu pin                           # locks Node 22.14.0 and the node24 toolset's 24.14.1
oyzu build                         # local: the app alone
oyzu build --verify-with node24    # local: the app and its Node 24 run
oyzu build --context ci            # ci: the app and its Node 24 run

Which runs a build has​

QuestionRule
In which contexts?Every context except local, unless the toolset lists contexts = [...] (local, pr, ci, release). contexts = [] turns it (or an inherited definition) off. --verify-with NAME (repeatable) adds a toolset's runs in any context.
For which builds?Builds in the toolset's folder chain whose builder uses one of its tools in its build or test stages. A node toolset adds nothing to a Go build. The nearest definition of a name applies as a whole, as for --toolset.
On which platform?One run per toolset, on the build's first declared platform (the host if it declares none). A toolset that lists platforms = [...] gets one run per listed platform. Runs aren't multiplied by the build's platforms.
In which job?A job runs the runs assigned to the platform it builds: a plain local build runs the host's; a --platform job runs that platform's. Runs for other platforms are listed under Verification elsewhere and in the plan, never dropped.
What runs?The build's build and test stages and its hooks, with the toolset's tools. Never lint, format, packaging or publication. Every check that isn't off in some context runs, as with --full. Test and coverage reports are collected; outputs aren't.
What is verified?Each run records verifies: source (it rebuilt and tested the source). Every current builder does this. A builder that tested the built artifact instead would record verifies: artifact.

Errors before anything runs:

CodeCause
CONFIG_TOOLSET_UNKNOWNA named toolset isn't defined in any selected build's folder. Lists the defined ones.
TOOLSET_NOT_APPLICABLENo selected build uses the toolset's tools.
VERIFICATION_RUN_NOT_HERE--verify-with or --verify-only named a toolset none of whose runs is on the platform this job builds. Names each run, its platform and command.
TOOLSET_INVALIDPolicy refuses the toolset's tools. Only a build that would run it here fails; plans, --skip-verification jobs and jobs whose run is elsewhere list it and continue.

Plan, output and evidence​

A run is its own target, <build>-verify-<toolset> (with the platform appended when the toolset lists several), and its own Plan row:

-- Plan ------------------------------------------------------------------------
                      format   lint   test   build
  app                 off      off    run    run
  app-verify-node24   off      off    run    run

The Tools block lists each version once (node 22.14.0 and node 24.14.1). The run's target has no artifacts, and the manifest marks it with oyzu.dev/verification:

{"build": "app", "toolset": "node24", "platform": "windows/x86_64",
 "verifies": "source", "reason": "context", "tools": {"node": "24.14.1"}}

reason is context when the toolset runs in this context, and requested for --verify-with/--verify-only. tools are the toolset's requests as written; oyzu.lock resolves them. A failing test in a run fails the build, and the shipped build's evidence is kept.

Verification evidence. Every native build's manifest records what its builds and runs verified, under oyzu.dev/verification-evidence. oyzu publish checks it:

{"verifyOnly": false,
 "builds": [{"build": "app", "tests": "passed",
   "source": {"commit": "5f3b…", "tree": "9c1e…", "digest": "sha256:fc29…"},
   "tools": [{"tool": "go", "id": "oyzu:go", "request": "1.24.13", "version": "1.24.13",
     "ranges": [{"dialect": "go-minimum", "expression": ">=1.24.0", "file": "go.mod", "field": "go"}]}],
   "notApplicable": [{"tool": "go", "line": "1.23", "native": "go.mod go >=1.24.0",
     "requiredBy": "project constraint (oyzu.toml [constraints])"}]}],
 "runs": [{"id": "app-verify-go125", "build": "app", "toolset": "go125",
   "platform": "windows/x86_64", "verifies": "source", "status": "here",
   "command": "oyzu build app --verify-only go125",
   "subject": {"source": {"commit": "5f3b…", "tree": "9c1e…", "digest": "sha256:fc29…"}},
   "stages": ["build", "test"], "result": "passed",
   "tools": [{"tool": "go", "id": "oyzu:go", "request": "1.25", "version": "1.25.14"}]}]}
  • A build entry is each shipped build in this job: source is the source revision it built; tools are the tools its build and test stages use, with resolved versions and the native ranges that constrain them (package.json engines, go.mod go); tests is passed, failed or not-run (fast local builds skip tests); notApplicable lists required lines outside those ranges.
  • A run entry is every run of the selected builds, with status here (ran in this job), other-platform or skipped (--skip-verification), and the command that runs it. A run that ran here adds its subject (the source revision), the tools it used, the stages that ran, and result: passed only when every action passed and its tests ran.
  • verifyOnly is true for a --verify-only job; its bundle is evidence only.

Source revisions​

verifies: source evidence is tied to a source revision:

  • digest: always present. A SHA-256 over the selected files' paths and contents, with CRLF read as LF and executable bits ignored, taken before any action runs.
  • commit and tree: present when the build's folder is in a Git work tree and none of its selected files differ from HEAD or are untracked. The HEAD commit and the Git tree of the build's folder.

Two revisions are the same source when their digests match and, if both have a tree, their trees match. Because the digest is always compared, an edit hidden from Git's index (--assume-unchanged, --skip-worktree, a filter) still counts as different source. The commit is for reference only: another commit with the same tree and content is the same source. A Windows checkout with core.autocrlf and a Linux checkout of the same commit are the same source.

Fanning runs out in CI​

oyzu build --plan --json keeps .matrix for platform builds and lists runs under .verify. Each entry has id, build, toolset, platform, runner (OS and architecture), verifies, requested, source (the file defining the toolset), tools, status (here, other-platform, skipped) and the command for a dedicated job. The command includes --platform when the build declares platforms.

"verify": [{"id": "app-verify-node24", "build": "app", "toolset": "node24",
  "platform": "linux/x86_64", "runner": {"os": "linux", "arch": "x86_64"},
  "verifies": "source", "requested": false, "source": "oyzu.toml",
  "tools": {"node": "24.14.1"}, "status": "here",
  "command": "oyzu build app --verify-only node24"}]

By default, one job builds and then runs every verification run for its platform. To give runs their own jobs, read .verify in a planning job (GitHub Actions: fromJSON) and:

  • run each entry's command in a job on its runner. oyzu build app --verify-only node24 runs only that toolset's runs (the builds it depends on are still built);
  • build the platform jobs with --skip-verification, which runs no verification and warns VERIFICATION_RUN_SKIPPED for each run, with its command.

--verify-with and --verify-only can't be combined with --skip-verification, --isolated, --all-platforms, --image or --remote.

Pass every job's bundle to oyzu publish (--manifest once per bundle). Platform jobs supply the artifacts and their builds' evidence; verification jobs supply the runs' evidence. Publication never takes an artifact from a --verify-only bundle, so the same output isn't offered twice.

Required tool lines​

Policy requires tool lines, not toolset names. The setting verification.<tool> lists the lines of a tool ("22", "3.12", "1.24": one to three numbers) that must have passing verification evidence before a build is published. Name the tool without a namespace (verification.node, not verification.oyzu:node). It's an ordinary per-folder setting: central policy and a root oyzu.toml [constraints] table can require lines with required, limited by when/unless, and a project can list its own.

# root oyzu.toml
[constraints."verification.go"]
required = ["1.23", "1.24", "1.25", "1.26"]
when = { context = ["pr", "ci", "release"] }   # optional

For each required line of a tool the build uses, in the build's folder and context:

  • Not applicable. A line entirely outside the build's native range (package.json engines.node, the go.mod go minimum) is never run. The manifest records it under notApplicable with the native file and range (go.mod go >=1.24.0), and publication accepts it. Other native ranges (requires-python, rust-version) aren't evaluated: such a line runs, and tool resolution reports the conflict. To enforce a support floor, constrain tools.<name> instead.
  • Covered. The build's own [tools] version in that line covers it in every context. A toolset with a version in the line covers it only in the contexts its runs run in: contexts = [] never does, contexts = ["release"] only in release (or when named with --verify-with/--verify-only).
  • Otherwise, a run is added, as if the root oyzu.toml defined a toolset policy-<tool>-<line> (policy-go-1_26, dots become _). Its target is <build>-verify-policy-<tool>-<line>, listed in .verify with requiredBy and its command (oyzu build app --verify-only policy-go-1_26). It runs where toolset runs do: every context except local (unless the constraint's when names local), in contexts no toolset covers, on the build's first declared platform. --verify-with policy-go-1_26 adds it in any context.

oyzu pin locks a policy run's tools in a set labelled toolset = "policy-go-1_26" when the requirement applies in pin's context and some context has no covering toolset. For a release-only requirement, run OYZU_CONTEXT=release oyzu pin. A build whose lock lacks the line fails with TOOL_LOCK_STALE; run oyzu pin.

oyzu build --plan shows the requirement as a CONFIG_CONSTRAINT_OVERRIDE (or policy override) note. oyzu config explain verification.go shows where each line comes from.

Publication checks the required lines​

oyzu publish resolves verification.<tool> again at publish time, in each published build's folder and the publication's context, so a requirement added after the build still applies. Each required line must be settled by the bundles given with --manifest, in one of three ways:

  • Not applicable: outside the recorded native range.
  • The build's own tests: its bundle records tests passed with a version in the line. Fast local builds skip tests; build with --full, or in a ci or release context.
  • A run: a run of the same build in any given bundle that ran here, passed, used a version in the line, and verified the published build. For verifies: source, its subject must be the build's source revision; for verifies: artifact, its artifact digests must include the published artifact.

Otherwise publication fails before loading evidence, signing or any network access. The error lists every unsettled line, why, and the commands for runs left to other jobs:

✗ PUBLISH_VERIFICATION_MISSING: no passing verification evidence for app go 1.25 (required by project constraint (oyzu.toml [constraints])): no run with go 1.25 was given. … Run what is missing (the runs this build left to other jobs: oyzu build app --verify-only go125) and pass every bundle with --manifest. Nothing was sent

A bundle from the container executor has no verification evidence, so publication refuses its build when any verification.<tool> line applies in the build's folder.

The publish receipt lists how each line was settled under verification, and the output shows it under Required verification:

Required verification
  app go 1.23  not applicable: outside go.mod go >=1.24.0 · required by project constraint (oyzu.toml [constraints])
  app go 1.24  the build's own tests (1.24.13) · required by project constraint (oyzu.toml [constraints])
  app go 1.25  run app-verify-go125 (1.25.14) · required by project constraint (oyzu.toml [constraints])

Locking​

  • oyzu pin locks every toolset's tools beside the [tools] tools, each toolset in its own set labelled toolset = "NAME", whatever the context and whether or not a build uses them. oyzu --toolset NAME pin locks one toolset.
  • oyzu update re-resolves [tools] and then every toolset.
  • A build whose lock lacks a run's tools installs and locks them like any other tool. See toolset lock rules.
  • A toolset that can't be locked (defined in a nested folder, TOOLSET_NESTED_LOCK, or refused by policy) is listed under Toolsets not locked (toolsetsNotLocked in JSON) with the reason. The rest is still locked and the command succeeds. A run that needs that toolset fails when it runs.
  • Native ranges still apply: a toolset Node outside package.json engines fails when resolved, naming the constraint.

Limits​

  • Runs execute only on the native host executor. A build that uses the container executor (--isolated, --image, --all-platforms, slices, remote pool builds, or builders without a native path such as pnpm and Yarn Node builds) and has runs fails with VERIFICATION_RUN_UNSUPPORTED, and so does its --plan. Build natively, or add --skip-verification.
  • oyzu build --remote can't pass --skip-verification to the pool. A pool job runs as ci (or release), never local, so a toolset with default contexts makes a remote build fail. For remote builds, list contexts the pool doesn't use, such as contexts = ["local", "pr"]. oyzu build --remote --plan evaluates toolsets in your local context; pass --context ci to see what a pool job would refuse.
  • No builder records verifies: artifact yet.
  • Only native builds record verification evidence.
  • The check that the work tree matches HEAD covers the build's folder only. An uncommitted change to an inputs file outside it doesn't stop the revision naming the commit.
  • "Not applicable" is decided only for engines.node and the go.mod go minimum.
  • Every builder repeats the same stages (build and test) in a run.
  • When this job builds a platform with a cross toolchain, whether tests run follows the builder's cross-build rules.

Migrating from runtime matrices​

build.yaml no longer accepts matrix. A runtime axis is refused with CONFIG_INVALID_VALUE and the equivalent toolsets, built from the file's own values:

CONFIG_INVALID_VALUE: app: matrix.node is no longer accepted: build.yaml says what ships, and tool versions belong in oyzu.toml. The build ships once, built with [tools]; each other version is a verification-only toolset that tests the build in pr, ci and release (add one locally with oyzu build --verify-with NAME). Remove matrix from build.yaml and add to oyzu.toml:
  [tools]
  node = "22.14.0"
  [toolsets.node24.tools]
  node = "24.14.1"
See docs/reference/runtime-matrices.md

The old axis built and kept one artifact per runtime. A toolset builds one artifact and verifies the other versions, so a release no longer holds two artifacts for one output. Shipping a separate artifact per runtime ABI isn't supported. matrix.platform is also refused; use platforms:.

Platform requirements and producer selection​

builds:
  api:
    uses: go/app
    path: api
  image:
    uses: docker/image
    platforms: [linux/x86_64, linux/arm64]
    materialize:
      - from: api
        to: bin/server

This expands into two image variants, each using an api variant built for the same platform.

  • Platform requirements pass through materialize transitively, including named artifacts and directories. Ordering-only depends_on and other targets' task prerequisites don't pass them on.
  • A producer's own platforms list limits what consumers can ask for. A conflict names the consumer's required platforms and the producer's allowed ones.
  • platforms is the only way to declare artifact platforms. The old platform: <os/arch> and matrix.platform forms fail with CONFIG_INVALID_VALUE. Aliases are accepted and stored in canonical form.
  • Each builder checks the platforms against what it can actually run. Language builders need a toolchain that runs on the target platform, so the example fails before running if the only Go worker is x86-64. Cross-compiling a binary wouldn't prove its arm64 tests pass. See toolchain platforms.
  • Docker can assemble x86-64 and arm64 scratch images on one x86-64 worker when no target code runs; see Docker platform admission. A complete set of image platforms also produces an OCI index. A partial selection keeps the individual images without an index.

Standalone producers​

A producer with no platforms keeps a standalone instance for commands like oyzu build api. Selecting image builds only the matching producer variants. A full workspace build skips the extra standalone instance when consumers already need platform variants, unless an ordering or task dependency requires it.

If a standalone instance can't choose among a dependency's declared platform variants, selecting it fails with an ambiguity error before preparation. Resolve it with a platform declaration on the producer or consumer; Oyzu never guesses from the host.

Variant IDs​

  • A target that declares exactly one platform keeps its name. Several platforms give each instance a platform-qualified ID, and inferred producer variants always get one.
  • IDs are deterministic and portable, derived from the name and platform, with a digest suffix when needed. Don't assume the logical name is the artifact's target ID; use the selection record and materialization receipts.
  • Case-insensitive ID collisions are refused.
  • A workspace can have at most 256 target instances and 16,384 copied tasks. Standalone instances count.
  • Each instance gets its own copy of the build's tasks and hooks, including root hooks and stage replacements that reach it.
  • Expansion never rewrites build.yaml.
