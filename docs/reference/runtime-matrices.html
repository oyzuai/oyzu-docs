Verification toolsets and platform matrices

CLI reference

Published from the canonical docs/reference/runtime-matrices.md file. Features marked experimental remain experimental; check support limitations before relying on them.

A project tests its builds on other runtime versions with verification toolsets in oyzu.toml, and ships a build for several platforms with platforms: in build.yaml. The two never mix: a toolset changes only how a build was checked, a platform changes what ships (configuration split OD1, decided 2026-10-19; implemented in delivery step D4b, with the evidence publication checks in M6b). Runtime versions are never written in build.yaml: the former matrix.<runtime> axis is refused (see migration).

Verification toolsets​

The shipped build is built and tested once, with the [tools] versions. Each toolset adds a verification run: the build's runtime-dependent stages, repeated with the toolset's tools, recording what they verified. A run never produces an artifact, so release selection and publication see one artifact however many toolsets run.

# build.yaml: nothing about runtime versions
builds:
  app:
    uses: node/app
# oyzu.toml
[tools]
node = "22.14.0"            # builds, tests and ships the app

[toolsets.node24.tools]
node = "24.14.1"            # also tested on Node 24, in pr, ci and release
oyzu pin                           # locks Node 22.14.0 and the node24 toolset's 24.14.1
oyzu build                         # local: the app alone
oyzu build --verify-with node24    # local: the app and its Node 24 run
oyzu build --context ci            # ci: the app and its Node 24 run

The EX-032 fixture is this project; its scenario runs every case below with the compiled CLI.

Which runs a build has​

  • Contexts. A toolset runs in every context but local unless it lists contexts = [...] (local, pr, ci, release); contexts = [] turns it, or an inherited definition, off. oyzu build --verify-with NAME (repeatable) adds a toolset's runs in any context, whatever its contexts.
  • Builds. A toolset applies to the builds in its folder chain whose builder uses one of its tools (the builder's tool requirements for its build and test stages): a node toolset adds nothing to a Go build in the same folder. The nearest definition of a name applies whole, as for --toolset.
  • Platforms. One run per toolset, assigned to the build's first declared platform (the host's when the build declares none), unless the toolset lists platforms = [...], which makes one run per listed platform. A run is not multiplied by the build's platforms.
  • Jobs. A job runs the runs assigned to the platform it builds: a plain local build runs the host's, and a job restricted with --platform runs that platform's. Runs assigned to other platforms are named in the build's details (Verification elsewhere) and in the plan, never silently dropped.
  • What a run executes. The build's build and test stages, with the build's own hooks, with the toolset's tools; never lint or format checks (they do not depend on the runtime and run once, with the shipped build) and never packaging or publication. A run runs every check its levels do not turn off in any context, as --full does: it exists to test. Its outputs are not collected; its test and coverage reports are, apart from the shipped build's.
  • What it verified. Each run records verifies: source or verifies: artifact. Every builder implemented today rebuilds and tests the source with the toolset's tools, so runs record source; a builder that installs and tests the built artifact instead (a Python wheel under another interpreter) would declare artifact.

A named toolset that no selected build's folder defines fails with CONFIG_TOOLSET_UNKNOWN (listing the defined ones), and one whose tools no selected build uses fails with TOOLSET_NOT_APPLICABLE, before anything runs. A requested run never silently runs elsewhere: when none of a named toolset's runs of a build is assigned to the platform this job builds (the build's first declared platform is not the host, for example), --verify-with and --verify-only fail with VERIFICATION_RUN_NOT_HERE, naming each run, its platform and its command. A toolset whose tools policy refuses fails only a build that executes its run here (TOOLSET_INVALID): plans, --skip-verification jobs and jobs whose run is assigned elsewhere list the run with its requests as written and go on.

The stages a run repeats are one shared set (build and test) for every builder. OD1 rule 4 and its cost section call for each builder to declare its own verification stage set; the shared set is a deliberate simplification, accepted in review, and builder-declared stage sets are a named follow-up.

Plan, output and evidence​

A run is its own target, <build>-verify-<toolset> (with the platform appended when the toolset lists several), shown as its own Plan row:

-- Plan ------------------------------------------------------------------------
                      format   lint   test   build
  app                 off      off    run    run
  app-verify-node24   off      off    run    run

The Tools block lists each tool once per version (node 22.14.0 and node 24.14.1). The manifest records the run's target with an oyzu.dev/verification extension:

{"build": "app", "toolset": "node24", "platform": "windows/x86_64",
 "verifies": "source", "reason": "context", "tools": {"node": "24.14.1"}}

reason is context when the toolset's contexts include the build's context and requested for --verify-with/--verify-only; tools are the toolset's requests as written, which oyzu.lock resolves. The run's target has no artifacts. A failing test in a run fails the build, with the shipped build's own evidence kept.

Verification evidence. Every native build's manifest also records what its builds and their runs verified, under the extension oyzu.dev/verification-evidence, which oyzu publish checks:

{"verifyOnly": false,
 "builds": [{"build": "app", "tests": "passed",
   "source": {"commit": "5f3b…", "tree": "9c1e…", "digest": "sha256:fc29…"},
   "tools": [{"tool": "go", "id": "oyzu:go", "request": "1.24.13", "version": "1.24.13",
     "ranges": [{"dialect": "go-minimum", "expression": ">=1.24.0", "file": "go.mod", "field": "go"}]}],
   "notApplicable": [{"tool": "go", "line": "1.23", "native": "go.mod go >=1.24.0",
     "requiredBy": "project constraint (oyzu.toml [constraints])"}]}],
 "runs": [{"id": "app-verify-go125", "build": "app", "toolset": "go125",
   "platform": "windows/x86_64", "verifies": "source", "status": "here",
   "command": "oyzu build app --verify-only go125",
   "subject": {"source": {"commit": "5f3b…", "tree": "9c1e…", "digest": "sha256:fc29…"}},
   "stages": ["build", "test"], "result": "passed",
   "tools": [{"tool": "go", "id": "oyzu:go", "request": "1.25", "version": "1.25.14"}]}]}
  • A build entry is each shipped build this job built: source is the source revision its actions ran on, tools the tools its builder uses in the build and test stages with the version oyzu.lock resolves each request to and the native ranges that constrain them (package.json engines, go.mod go), tests whether its own test stage passed, failed or did not-run (a fast local build skips tests), and notApplicable the required lines outside those ranges.
  • A run entry is every run of the selected builds, with its status: here (it ran in this job), other-platform or skipped (--skip-verification), and the command that runs it. A run that ran here adds its subject, the tool identities it ran with, the stages that ran and its result: passed only when every one of its actions passed and its tests ran. A verifies: source run's subject is the source revision it ran on; a verifies: artifact run's subject would be the digests of the build's artifacts in its bundle (no builder declares artifact yet).
  • verifyOnly is true for a --verify-only job: its bundle is evidence only.

Source revisions​

verifies: source evidence binds to the source revision (OD1 rule 5, R8). A source revision has:

  • commit and tree: when the build's folder is in a Git work tree and no file of the build's source selection differs from HEAD (by Git's own comparison, after its line-ending conversion) or is untracked, the HEAD commit and the Git tree of the build's folder;
  • digest: always, a SHA-256 over the selected files' paths and contents with CRLF line endings read as LF and executable bits ignored, taken before any action runs.

Two revisions are the same source when their digests are equal and, if both record a tree, their trees are equal too. The digest is always required, so an edit Git's index does not show (git update-index --assume-unchanged, --skip-worktree, a filter) still makes a different source; the commit is recorded for provenance only, so another commit with the same tree and content (a change elsewhere in the repository) is the same source. A Windows checkout (core.autocrlf) and a Linux checkout of one commit are the same source, and so are an exported tree and a checkout with the same content.

oyzu build --plan --json keeps .matrix for platform builds only and lists every run under a separate .verify key, each with id, build, toolset, platform, runner (OS and architecture), verifies, requested, source (the file defining the toolset), tools, status (here, other-platform, skipped) and the command a dedicated job runs:

"verify": [{"id": "app-verify-node24", "build": "app", "toolset": "node24",
  "platform": "linux/x86_64", "runner": {"os": "linux", "arch": "x86_64"},
  "verifies": "source", "requested": false, "source": "oyzu.toml",
  "tools": {"node": "24.14.1"}, "status": "here",
  "command": "oyzu build app --verify-only node24"}]

The command adds --platform when the build declares platforms.

Fanning runs out in CI​

By default one job builds and then runs every verification run assigned to its platform. To give runs their own jobs, read .verify from a planning job (GitHub Actions reads it with fromJSON) and:

  • run each entry's command in a job on its runner: oyzu build app --verify-only node24 runs only that toolset's runs of the build, not the build's own stages (the builds it depends on are still built);
  • build the platform jobs with --skip-verification, which runs no verification run and names each one it skips as a VERIFICATION_RUN_SKIPPED warning with the command that runs it.

--verify-with and --verify-only conflict with --skip-verification, --isolated, --all-platforms, --image and --remote.

Pass every job's bundle to oyzu publish (--manifest once per bundle): the platform jobs' bundles supply the artifacts and their builds' evidence, the verification jobs' bundles the runs' evidence. A --verify-only job's bundle is evidence only: the builds its run depends on are built there too, but publication takes no artifact from it, so the same output is never offered from two bundles.

Required tool lines​

Policy requires tool lines, never toolset names (OD1 rule 3): the setting verification.<tool> lists the lines of a tool ("22", "3.12", "1.24": one to three numbers) a build must have passing verification evidence for before it is published. The tool is named without a namespace (verification.node, not verification.oyzu:node). It is an ordinary per-folder set, so central policy and a root oyzu.toml [constraints] table require lines with a required constraint, limited by when/unless like any constraint, and a project can list its own:

# root oyzu.toml
[constraints."verification.go"]
required = ["1.23", "1.24", "1.25", "1.26"]
when = { context = ["pr", "ci", "release"] }   # optional

For each line a build's builder needs the tool for (its build and test stages), in the build's own folder and context:

  • Outside the native range: not applicable. A line no version of which satisfies the build's native range (package.json engines.node, the go.mod go minimum) is never run. The manifest records it under notApplicable, naming the requirement and the native file and range (go.mod go >=1.24.0), and publication accepts it. Other native ranges (requires-python, rust-version) are not evaluated: such a line runs, and its tool resolution reports the conflict. An organization that needs a support floor constrains tools.<name> instead.
  • Covered. The build's own [tools] request in the line (its tests run with it) covers it everywhere. A toolset the build's folder sees whose request for the tool is in the line covers it only in the contexts its runs run in: a toolset with contexts = [] never does, one with contexts = ["release"] only in release builds (or when named with --verify-with/--verify-only).
  • Otherwise a run is added as if a toolset policy-<tool>-<line> (policy-go-1_26, dots becoming _) requesting the line were defined in the root oyzu.toml: target <build>-verify-policy-<tool>-<line>, listed in .verify with requiredBy (verification.go = 1.26 (project constraint (oyzu.toml [constraints]))) and its command (oyzu build app --verify-only policy-go-1_26). It runs where a toolset's runs do: in every context but local (a required constraint whose when names the local context also runs it locally), in the contexts where no covering toolset runs, on the build's first declared platform; policy still binds its tool. --verify-with policy-go-1_26 adds it in any context. oyzu pin locks it in a set labelled toolset = "policy-go-1_26" when the requirement applies in the context pin runs in and some context it runs in has no covering toolset (pin with OYZU_CONTEXT=release oyzu pin for a release-only requirement); a build whose lock already pins other tools but lacks the line fails with TOOL_LOCK_STALE and the remedy oyzu pin.

oyzu build --plan shows the requirement as a CONFIG_CONSTRAINT_OVERRIDE (or policy override) note; oyzu config explain verification.go shows where each line comes from.

Publication checks the required lines​

oyzu publish resolves verification.<tool> again when it publishes, in each published build's folder and in the publication's context, so a requirement added between build and release still applies. For every published build, each required line of each tool its record lists must be settled by the evidence of the bundles given with --manifest:

  • not applicable (outside the recorded native range);
  • the build's own tests: its bundle records its tests passed with a version of the tool in the line (a fast local build skips tests; build with --full, or in a ci or release context);
  • a run: a run of the same build in any given bundle that ran (status: here), passed, used a version in the line and verified the published build: its source subject is the build's source revision (verifies: source), or its artifact digests include the published artifact's (verifies: artifact).

Otherwise publication fails before evidence loading, signing or any network access, with every unsettled line, why, and the commands of the runs the build left to other jobs (a run another given bundle ran and that settled a line is not listed):

✗ PUBLISH_VERIFICATION_MISSING: no passing verification evidence for app go 1.25 (required by project constraint (oyzu.toml [constraints])): no run with go 1.25 was given. … Run what is missing (the runs this build left to other jobs: oyzu build app --verify-only go125) and pass every bundle with --manifest. Nothing was sent

A bundle without verification evidence (written by the isolated executor, which does not record it yet) does not say which tools its build uses, so publication refuses its build when any verification.<tool> line applies in the build's folder, whatever the tool. A published receipt lists how each line was settled under verification, and the human output under Required verification:

Required verification
  app go 1.23  not applicable: outside go.mod go >=1.24.0 · required by project constraint (oyzu.toml [constraints])
  app go 1.24  the build's own tests (1.24.13) · required by project constraint (oyzu.toml [constraints])
  app go 1.25  run app-verify-go125 (1.25.14) · required by project constraint (oyzu.toml [constraints])

Locking​

oyzu pin locks every toolset's tools beside the [tools] tools, each toolset's in its own set labelled toolset = "NAME", whatever the context and whether or not a build uses them; oyzu --toolset NAME pin locks one toolset. Plain oyzu update re-resolves [tools] and then every toolset. A build whose lock lacks a run's tools installs and locks them like any other tool request; the toolset lock rules apply. A toolset neither command can lock, one a nested folder defines (TOOLSET_NESTED_LOCK) or one whose tools policy refuses, is left out and named, with the reason, under Toolsets not locked (toolsetsNotLocked in JSON); the rest is still locked and the command succeeds. Decided before anything is written, so a command never locks one set and then fails on another. A build's run that needs such a toolset fails when it runs. Native ranges still constrain every run: a toolset Node outside package.json engines fails when its tools are resolved, naming the constraint.

Limits​

  • Runs execute on the native host executor. A build that takes the isolated (captured) executor (--isolated, --image, --all-platforms, slices and remote pool builds, or a builder without a native host path, such as pnpm or Yarn Node builds) and has runs fails with VERIFICATION_RUN_UNSUPPORTED, naming them, and so does its --plan. Build natively where the builders allow it, or add --skip-verification, which lists the runs as skipped in the plan and warns VERIFICATION_RUN_SKIPPED for each in the build. oyzu build --remote cannot pass --skip-verification to the pool (the request carries no build options). A pool job is a CI build: it runs in the context it detects or is pinned to, normally ci (release for a release), never local. So a toolset with the default contexts makes a remote build fail; for remote builds, list contexts the pool does not use, for example contexts = ["local", "pr"] to verify locally on request and in pull requests built by a host CI job. oyzu build --remote --plan evaluates toolsets in the context of the machine running the plan (local unless --context says otherwise), so it does not predict the pool's refusal; pass --context ci to see what a pool job would reject. Running verification runs on the pool is a named follow-up.
  • No builder declares verifies: artifact yet: every run tests the source, and the artifact binding is implemented but unexercised.
  • Only the native host executor records verification evidence; an isolated build's bundle has none, so publication refuses it when any verification.<tool> line applies in the build's folder.
  • The check that the work tree holds HEAD covers the build's folder: an uncommitted change to a declared inputs file outside it does not stop the revision from naming the commit.
  • Not applicable is decided for engines.node and the go.mod go minimum only.
  • Runs of a build whose platform this job builds with a cross toolchain are placed here as for any platform; whether tests run there follows the builder's cross-build rules.

Migrating from runtime matrices​

build.yaml no longer accepts matrix (in either shape). A runtime axis is refused with CONFIG_INVALID_VALUE and the toolset form built from the file's own values:

CONFIG_INVALID_VALUE: app: matrix.node is no longer accepted: build.yaml says what ships, and tool versions belong in oyzu.toml. The build ships once, built with [tools]; each other version is a verification-only toolset that tests the build in pr, ci and release (add one locally with oyzu build --verify-with NAME). Remove matrix from build.yaml and add to oyzu.toml:
  [tools]
  node = "22.14.0"
  [toolsets.node24.tools]
  node = "24.14.1"
See docs/reference/runtime-matrices.md

The old axis built and kept one complete artifact per runtime, each in its own provisioned image; a toolset builds one artifact and verifies the others, so a release no longer holds two artifacts for one output. matrix.platform remains refused in favor of platforms:. Shipping a separate artifact per runtime ABI (OD11) is a different, deferred job.

Platform requirements and producer selection​

builds:
  api:
    uses: go/app
    path: api
  image:
    uses: docker/image
    platforms: [linux/x86_64, linux/arm64]
    materialize:
      - from: api
        to: bin/server

This authored EX-027 shape expands into two image variants, each bound to a producer variant for the same platform. Requirements propagate transitively through materialize, including named artifacts and directories. A producer's own platforms list constrains those requirements; conflicts identify the consumer's required platforms and the producer's allowed platforms. Ordering-only depends_on and foreign task prerequisites do not propagate platform requirements. Same-target task prerequisites retain their variant identity.

An unconstrained producer retains a standalone instance for explicit commands such as oyzu build api. Selecting image selects only its matching producer variants. Building the whole workspace omits an extra standalone producer when its consumers already demand platform variants; an ordering/task dependency can still explicitly require that standalone instance. The selection record includes all concrete IDs and identifies excluded instances. Standalone instances also count toward the 256-instance bound.

If a retained standalone instance cannot uniquely choose among a dependency's declared platform variants, selecting it fails with an ambiguity error before preparation. This also applies when another selected build requires that instance through an ordering dependency; the ambiguity is reported before following its unresolved materialization. Its valid explicitly platform-bound instances remain usable. Resolve the ambiguity with a producer/consumer platform declaration; Oyzu does not guess from the host. Other invalid declarations and conflicting constraints remain workspace-wide validation errors.

platforms is the only way to declare artifact platforms: the platform axis is internal to expansion, and the retired platform: <os/arch> and matrix.platform spellings are refused with CONFIG_INVALID_VALUE naming platforms: [...] (configuration split M5). OS/architecture values with the usual aliases are accepted and stored canonically. Each builder admits those values separately against its actual executor capabilities. Native builders currently require matching toolchain execution, so the example above still fails before application actions when the only provisioned Go worker is amd64. Cross-compiling a binary would not prove ARM tests passed.

Docker can assemble separate amd64/arm64 scratch images on its amd64 worker when no target code is executed; see Docker platform admission. Complete selected families produce separate versioned image archives plus a complete OCI index. Automatic platform-independent producer reuse, ABI/runtime compatibility, remote worker selection and full EX-027/050 acceptance remain unfinished. Local platform-specific toolchain selection is described in toolchain platforms. Equal bytes, a directory artifact or a successful cross-platform assembly do not establish any of those capabilities.

Platform-constrained targets record a platform variant axis. Inferred producer variants receive deterministic concrete IDs, even for a single requested consumer platform. Resolve their identities through the selection mapping and materialization receipts instead of assuming that the logical producer name is its artifact target ID. A target that declares exactly one platform keeps its logical ID; several declared platforms give each instance a platform-qualified ID. Variant IDs are portable and deterministic, derived from the logical name and platform with a digest suffix when normalization is needed; expansion rejects case-insensitive ID collisions and bounds the workspace to 256 target instances and 16,384 copied tasks. A build's tasks and hooks are copied per instance, including the unqualified root hooks and stage replacements task binding gives it; in a workspace with one logical target, a root workspace task (neither a hook nor a stage) that an instance reaches through a prerequisite uses an internal root- task alias. Expansion uses the frozen build inventory and never rewrites build.yaml.

Complete selected OCI image platform families produce an additional OCI index artifact. Partial dependency selections keep their individual images without synthesizing an incomplete index. Aggregate targets are derived plan records outside the source-variant selection list.

Verification​

  • Verification runs: build::verification_runs tests (contexts, --verify-with, --verify-only, --skip-verification, platform assignment, nearest definition and contexts = [], unknown and inapplicable toolsets, the isolated-executor refusal and pin instances), build::variants tests (a run's tasks, bound root hooks and stage replacements and dependencies; a run is never a producer), config::sources toolset parsing, config::build_model matrix refusal, and the compiled-CLI configuration_cli tests for .verify, contexts and platforms. The EX-032 scenario runs the example with real Node 22 and 24 downloads: oyzu pin, a ci build with one artifact and a Node 24 run recording verifies: source, a local build without the run and with --verify-with, the --skip-verification and --verify-only fan-out, a test failing only on Node 24, and the refused matrix.node. Measured results are in the D4b status entry.
  • Verification evidence and required lines (M6b): config::verification tests (native ranges, lines, selectors), build::verification_runs (a required line no toolset covers becomes a labelled run, locally only on request), build::verification_evidence (which evidence settles a line), the publication presentation test, and the compiled-CLI publish_cli::a_build_lacking_evidence_for_a_required_tool_line_is_refused. The EX-032 scenario checks the evidence of the ci build and that the dedicated --verify-only job's run verifies the platform job's source. The compiled-CLI proof (a Go app built, verified on Go 1.25 in a separate job and on a policy-added Go 1.26 run, refused and then published to a local OCI registry) is in the M6b status entry.
  • Platform matrices: tests exercise transitive propagation, explicit constraint conflicts, ordering versus artifact dependencies, local/foreign task binding, stable IDs and standalone selection against the authored EX-050 project. The captured Docker suite requires two actual OCI images with matching architecture, separate JUnit/quality evidence and repeated snapshot identities; it also checks EX-027's missing target-execution and conflicting producer failures. The Go suite checks EX-049's inferred producer variant and named artifact bytes. OCI index assembly and its pending native verification are described in the index reference.
