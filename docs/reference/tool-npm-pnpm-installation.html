npm, pnpm and Yarn installation

CLI reference

Published from the canonical docs/reference/tool-npm-pnpm-installation.md file. Features marked experimental remain experimental; check support limitations before relying on them.

oyzu can pin and install npm, pnpm and Yarn as their own tools (oyzu:npm, oyzu:pnpm and oyzu:yarn), separate from the npm bundled with Node. Choose a release in [tools] or with packageManager in package.json; the lock records it with the registry's integrity hash.

Platform scope: Use an x64 host and supported x64 build targets. ARM64 is unsupported. Feature-specific limits are listed in the support matrix.

Usage​

[tools]
node = "22.12"
npm = "11.6.2"       # exact release, a range such as "11", or "latest"
# pnpm = "10.20.0"
oyzu install npm@11.6.2    # declares, locks, installs
npm --version
npx --version
oyzu install pnpm@10.20.0
pnpm --version

In an activated shell, which the install script sets up, the plain tool commands run the pinned versions. Where a shell isn't activated, prefix them with oyzu exec --.

oyzu tools versions npm and oyzu tools versions pnpm list the registry's stable releases.

Node's bundled npm​

Selecting Node also gives you its bundled npm and npx, through oyzu exec, activated shells and shims, with no separate npm declaration. Both run on the selected Node. Declare npm only when you want a different npm release; its npm and npx then take precedence over the bundled copy.

npm needs Node: when oyzu:npm is selected, select oyzu:node too. A lifecycle script that calls npm through PATH during oyzu exec still finds Node's bundled npm; in an isolated build it finds the locked one.

After upgrading oyzu, run oyzu reshim to refresh existing shims. A shim doesn't pick a version itself: it uses the project or global selection each time it runs.

pnpm versions​

pnpm releases combine the older platform packages and the pnpm 12 packages. latest follows the pnpm package's latest tag. If that release isn't available for your platform, latest fails, but exact pins and ranges still work.

packageManager​

A Node build uses the nearest package.json with a packageManager field, searched from the build folder up to the project root (as Corepack does). If it names an exact stable npm or pnpm release, such as "packageManager": "pnpm@10.20.0", that release becomes a tool requirement:

  • It's a native pin file. When the project has no oyzu.lock, the build locks it beside Node.
  • A [tools] npm or [tools] pnpm value must agree. A disagreeing value in the same folder or nearer the build fails with TOOL_NATIVE_PIN_CONFLICT; one further away loses to packageManager.
  • A Corepack hash suffix (+sha512.<hex>) is accepted but not compared. The lock records the registry's integrity hash instead.
  • A range, tag, bare major, pre-release or URL fails with TOOL_NATIVE_PIN_INVALID. Write an exact stable release, or remove the field and set [tools].
  • If oyzu.lock already exists without that release, add it with oyzu install npm@<version> or oyzu install pnpm@<version>.

When there's no packageManager, an exact devEngines.packageManager version with onFail: "error" is the request. For Yarn, see Managed Yarn.

engines.node constrains Node's version instead; see Node selection.

Builds​

Isolated builds use the locked release instead of the copy in the build image, for dependency installation and every action:

  • pnpm is placed at /scratch/pnpmtool and comes first on PATH.
  • npm is placed at /scratch/npmtool. Dependency installation writes npm and npx launchers to /dependencies/manager/bin, which comes first on PATH for every action.

The build's dependency record lists the locked release under the oyzu.dev/locked-manager extension. A changed digest in oyzu.lock is refused. Isolated builds run on linux/amd64 workers only, and an offline build needs the archive already cached.

On a Windows machine, pnpm workspace links stay inside the Linux build workspace. oyzu reads them without following them on the host, and doesn't restore cached action results that contain links.

Managed Yarn​

Note: Managed Yarn is experimental. It supports Classic 1.22.22 and Berry 4.17.1 with Node 22.23.3 for single-package applications on Linux and Windows (x86-64). Isolated builds don't support Yarn yet.

oyzu installs Classic Yarn from the yarn package and modern Yarn from @yarnpkg/cli-dist on the npm registry. latest follows the modern package's tag. Both yarn and yarnpkg run bin/yarn.js on the selected Node. Declare Node too: Yarn doesn't install its own runtime or use Corepack.

[tools]
node = "22.23.3"
yarn = "4.17.1"
oyzu pin
oyzu install --frozen
yarn --version
yarnpkg --version

Both commands print 4.17.1. Use yarn = "1.22.22" for Classic.

Building a Yarn application​

Yarn builds go through the Node plugin with a declared node/app target and a yarn.lock generated by Yarn. A full frozen build exports fresh dist output with JUnit and LCOV reports. A failed test or missing required report blocks the export. To run tests directly, install dependencies first (for Berry, yarn install --immutable).

Requirements:

  • packageManager names exactly yarn@1.22.22 or yarn@4.17.1.
  • Berry needs a .yarnrc.yml with nodeLinker: node-modules (or the quoted "node-modules"). oyzu never converts a Plug'n'Play project.
  • Berry needs Node >=18.12.0 as well as the project's engines.node.
  • Workspaces, Yarn plugins, yarnPath, custom registries and Git, file or patch dependencies aren't supported.

Dependency installation needs yarn.lock. Classic runs install --frozen-lockfile (plus --offline for offline builds). Berry runs install --immutable, with YARN_ENABLE_NETWORK=0 for offline builds. Offline builds need the tools and Yarn's cache already present. A failed install stops dependent actions and artifact collection.

Yarn configuration checks​

Before running Yarn, oyzu checks the project, parent-folder and home rc files. For native Berry, the admitted settings are nodeLinker: node-modules (including the quoted linker value) and YAML boolean enableTelemetry: false:

nodeLinker: "node-modules"
enableTelemetry: false

The opt-out alone does not select a linker; the project must still select node-modules. Other telemetry values, including the string "false", and other settings remain refused. The opt-out works for native single-root applications on Linux x86_64 (GNU) with Berry 4.17.1 and Node 22.23.4. Classic and isolated Berry configuration keep their existing rules.

For Classic, oyzu also checks .config/yarn/config, .config/yarn, .yarn/config, the XDG or Windows config location, /etc/yarn/config, /etc/yarnrc and npm's global npmrc under the selected Node's prefix. Directories at those paths are ignored, as Classic does.

Any other setting, an unusual or oversized rc file, or an environment override of the registry or linker (including YARN_CONFIG, YARN_REGISTRY, an alternate npm user config or DESTDIR) fails with YARN_CONFIG_UNSUPPORTED before Yarn runs. Remove the setting, then retry.

Yarn licenses​

Each tarball is checked against the registry's SHA-512 integrity and the original files and notices are kept. Classic includes a BSD-2-Clause LICENSE file. The Berry package has its bundled notices but no standalone LICENSE; its source license is BSD-2-Clause.

Sources and verification​

All three tools come from https://registry.npmjs.org/. oyzu reads the package's metadata and refuses a release whose tarball isn't at <registry>/<package>/-/<file>-<version>.tgz or that has no SHA-512 integrity. It downloads the tarball, checks it against that integrity and locks the SHA-256 of the checked bytes.

ToolReleases up to 11Releases from 12Commands
npmnpm, one tarball for every platformSame packagenpm and npx, run on the selected Node
pnpm on Linux x86-64@pnpm/linux-x64@pnpm/exe.linux-x64pnpm
pnpm on Linux ARM64@pnpm/linux-arm64@pnpm/exe.linux-arm64pnpm
pnpm on macOS Apple silicon@pnpm/macos-arm64@pnpm/exe.darwin-arm64pnpm
pnpm on Windows x86-64@pnpm/win-x64@pnpm/exe.win32-x64pnpm.exe

npm's own bin/npm and bin/npx launchers (and their .cmd and .ps1 forms) run Node's bundled npm, so oyzu leaves them out and runs bin/npm-cli.js and bin/npx-cli.js directly.

An administrator can route downloads through a corporate mirror with a tools route scoped to npm, oyzu:npm, pnpm, oyzu:pnpm or * (see proxy acquisition). Under an organization tool catalog, only approved releases install.

Limits​

  • pnpm is supported on Windows x86-64 for isolated builds. Other platforms for the dedicated npm and pnpm tools aren't supported yet, and neither is offline dependency installation.
  • Nested npm calls from lifecycle scripts inside builds aren't supported yet.
  • Linux ARM64 is recorded in the lock but not supported yet; musl isn't supported.
