Running builder acceptance checks

CLI reference

Published from the canonical docs/reference/build-verification.md file. Features marked experimental remain experimental; check support limitations before relying on them.

The repository's captured-build harness executes the compiled Oyzu CLI against native project fixtures, inspects actual artifacts and reports, and checks expected failures. It covers the implemented profiles recorded in implementation status. A passing harness run does not establish acceptance of every case in the 58 authored design-contract scenarios.

Select and run checks​

Use Python 3.12 with tooling/design-requirements.txt installed to inspect the current groups without running builds:

python tooling/test-build-scenarios.py --list-suites
python tooling/check-build-suites.py

The inventory check verifies unique registrations, conventional acceptance entry points, matching CI matrix coverage, compilation dependency and the aggregate gate. It neither provisions tools nor verifies native product behavior.

The focused Node check-selection group covers fast omitted checks, full native zero-test JUnit, required tests in fast mode, missing-required-report failure and retained human/JSON selection agreement. Run it with --suite node --only check-selection. Its acceptance remains pending; the previously qualified 84-observation build-explanations group is unchanged. See the selection qualification.

For real builds, supply a compiled CLI and provision the required toolchains. Captured-build acceptance currently runs on Linux with Docker and the toolchain definitions in tooling/images/. Node/core/Docker/dependencies checks also use host Node 22/npm; Java native adapter checks require host JDK 17. The provisioning script uses network access to obtain test tooling and images. Core/Go/Docker/Python/dependencies suites install the repository's explicit BuildKit AppArmor profile using sudo apparmor_parser; use a suitable Linux test machine. This is acceptance-fixture setup, not Oyzu's tool-installation feature or an implicit network fallback during a product build.

From the repository on that Linux test machine:

cargo build --locked
bash tooling/build-scenario-tools.sh provision docker
export OYZU_BUILDKIT_APPARMOR_PROFILE=oyzu-buildkit
.ci-python/bin/python tooling/test-build-scenarios.py --suite docker --cli target/debug/oyzu --evidence-dir docker-evidence

For suites with standalone native adapter probes, bash tooling/build-scenario-tools.sh native <suite> runs those additional checks. The Helm CLI probe expects the compiled binary at cli/oyzu, matching CI; copy your binary there before running that probe. The ordinary captured-build harness accepts any explicit --cli path. Native probes supplement captured builds; they cannot substitute for them.

The Helm native phase also runs tooling/test-helm-direct.py against the downloaded CLI and provisioned Helm/plugin. This verifies the separate host oyzu run test to JUnit/manifest/inspection flow, including application and root library charts, unittest suites and hooks. It does not replace captured chart packaging checks. See Helm direct-report behavior and test-only bundles.

Omitting --suite selects all and retains the original full-run ordering. Provisioning/native-probe scripts also accept all. A single-suite selection uses the same checks and assertions as the full run. Unknown suites and missing --cli arguments fail rather than selecting a fallback.

When tools were provisioned into an explicit verified store, pass --store <absolute-tool-store> to tooling/test-build-scenarios.py. The harness forwards it to compiled-CLI build and exec invocations, including raw and background builds, so the independent consumer uses the same tool selection. It does not add the option to inspect or child arguments after --, and an explicit invocation-specific store takes precedence. The store must already exist; the harness does not provision it. Without this option the CLI retains its ordinary default-store behavior. Managed syntax and registration checks pass. The installer companion and native node-gyp producer/consumer exercised explicit store propagation; this does not qualify the full scenario catalog.

The installer-recipe checks explicitly select each temporary fixture with --root <fixture> for builds and the independent consumer's exec. This bounds workspace discovery when the host's temporary directory has an ancestor Oyzu configuration. It preserves that configuration and the CLI's normal root-selection rules rather than scanning unrelated temporary projects.

For a selected check that needs a distinct provisioned image, repeat harness --image <manager>=<image> as needed. These options reach only child build commands; a scenario's explicit image options take precedence. The harness does not pull, build or retag images. The node-gyp-recipe check needs an explicit Linux/amd64 npm image with compatible Python, make/compiler and the normal Node quality tools; it uses that image for both compilation and independent captured consumption. The default npm image does not provide that compiler environment. The bounded Linux/amd64 producer/consumer check passed with the explicitly provisioned task image: both native seven-action builds, three tests each, wrapper coverage, inspected archives and independent addon consumption. See installer recipe qualification for the exact image, artifact identities and platform limits.

Maven and Gradle delivered-JAR consumers use the image digest recorded in that build's plan. Supply the actual candidate with --cli and retain its worker and component identities alongside the evidence. Their qualification summaries retain the actual consumer commands, exit codes and output streams.

The maven check runs the nine reactor/report scenarios. The separate maven-managed-coverage check runs the mixed native-managed/fallback coverage reactor with the same full captured execution and artifact/report assertions. Run both named checks for the Maven scope; the complete java suite includes each once.

CI and evidence​

The workflow builds the CLI on Linux, macOS and Windows first. Linux captured-build jobs download that run's compiled Linux binary, then run the ten suites with up to four concurrent jobs. Each job provisions only its required toolchain families. fail-fast: false allows unrelated suites to finish after one fails. The Captured build suite acceptance gate fails if any suite fails, is cancelled or is skipped. Three-host CLI/task checks and the separate isolated-worker job remain distinct checks with their own scope.

Explicit Java quality, Hadolint and yamlfmt provisioning shares tooling/provisioning.py. Downloads make at most three attempts for transient transport failures and HTTP 429/500/502/503/504, with one- and two-second backoff, a 60-second socket timeout per attempt and the existing asset-specific byte limits. A truncated response with a declared content length is discarded before retrying. Authorization/not-found errors and oversized responses are terminal. Pinned SHA-256 verification remains mandatory in each owning provisioner; digest mismatches are not retried or accepted. The timeout is per socket operation, not a total invocation deadline. This supports CI/toolchain setup only and adds no product tool-installation or build-time internet access. The three-host task job exercises loopback retry/size/failure tests before provisioning.

CI uploads each suite under oyzu-build-evidence-<suite> (including oyzu-build-evidence-dependencies for package contexts), replacing the former single oyzu-build-evidence artifact name. Evidence directories contain numbered build invocations, their available dist/ bundles, and a summary.json identifying the suite, selected groups, completed groups, verified assertions and success/failure. An exception preserves a failed summary with the active group; previously completed checks do not make an incomplete suite successful. Process termination can prevent final summary writing. The harness does not turn missing reports into passing evidence.

An evidence directory must be new; choose a fresh path for reruns. Inspect the failing invocation and native logs, correct the underlying behavior or fixture, and rerun the affected suite. Do not weaken assertions or mark authored scenarios complete based on inventory checks. Retained artifacts contain build logs and sample outputs and are kept for 14 days in CI; fixtures must not contain real credentials.

Local verification of this suite split includes inventory and shell/Python syntax checks, an AST comparison preserving existing baseline assertions and embedded source strings, retained provisioning/probe command checks, and failed-summary behavior after a missing executable. New Linux suite execution remains subject to the revision-specific CI evidence in implementation status. Windows/macOS execution of the full captured-build matrix and the remaining authored cases are still required work.

Local execution of this suite needs equivalent pre-provisioned execution support. The two producer platform-matrix invocations allow up to 2,400 seconds in the test harness for emulated compilation; product acquisition/action limits remain unchanged. Independent functional evidence after native conformance​

Captured-build jobs record native adapter conformance and end-to-end snapshot builds as separate step outcomes. When provisioning and inventory succeed, the compiled-CLI build step still runs after an earlier native conformance failure. The failed step remains failed, the job and aggregate gate remain red, and retained bundles show which actual build flows succeeded or failed. No assertion is disabled and no failure is converted to acceptance. This prevents a protocol/reproducibility check from hiding the functional result needed to guide implementation. Failed provisioning, invalid inventory or cancellation still prevent that dependent build step.

Within a captured suite, each registered group runs independently. A failed group records its name, error and traceback in summary.json under failedChecks; subsequent groups still run. completedChecks contains only groups that returned successfully, and any group failure makes the command exit nonzero and the suite status failed. Exceptions within a group still stop that group's dependent steps, and interruption still stops the runner. Fixture directories remain owned by each group. This preserves failures while obtaining evidence for unrelated functional paths.

Host task jobs also run tooling/test-node-framework-direct.py after CLI compilation and explicit native fixture provisioning. It proves implicit and npm-scripted Jest, Vitest and Mocha execution through test-only report bundles and inspection, including lifecycle/hooks and real failed assertions. Refer to direct test prerequisites for versions and current limits.

The same host CI step runs tooling/test-npm-workspace-direct.py against EX-020 to check per-package direct JUnit/coverage bundles, real failures and sibling evidence. tooling/test-npm-workspace-tests.py retains native mixed-framework/nested-scope checks and now inspects the resulting test-only bundle. Marker-only overrides are verified as command execution with missing required evidence, not accepted as successful tests.

The direct workspace probe now also accepts --manager pnpm and --manager yarn. It adapts EX-020's native workspace declarations, explicitly creates local native links offline, and checks a member script beside an inferred suite, failed/sibling reports, hooks, unchanged source/locks, root aggregation and inspection. CI runs all three managers after compiling the CLI and provisioning the pinned native packages. The npm mixed-framework probe checks the extracted shared scope/execution layer separately; pnpm/Yarn captured workspace artifacts and wider framework combinations are not implied by these direct tests.

The Helm native-reporting probe checks chart source bytes separately from the intentionally generated direct-test dist/ and .oyzu/ outputs, and inspects each resulting CLI bundle. Preparation fixture copies omit those outputs. This corrects the old source-equality expectation after direct test bundle integration without dropping chart-preservation assertions.

Host task jobs explicitly provision Rust 1.94.0 with LLVM tools, cargo-nextest 0.9.146 and cargo-llvm-cov 0.9.1, then run tooling/test-rust-direct.py using the compiled CLI. Live build logging​

With the Rust toolchain image already provisioned, run python tooling/test-build-logging.py --cli <compiled-cli> --evidence-dir <new-directory>. This executes parallel captured Rust builds and verifies live labeled streams, command records, final partial lines, snapshot artifacts, failure/blocked behavior, JSON mode and inspected retained bundles. CI runs it in the Rust suite after CLI compilation and explicit provisioning, retaining logging-evidence. It does not install tools or count as acceptance of every builder. The ordinary captured scenario harness now explicitly requests --json for builds because readable text is the default.
