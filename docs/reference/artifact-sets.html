Installing from resolved artifact sets

CLI reference

Published from the canonical docs/reference/artifact-sets.md file. Features marked experimental remain experimental; check support limitations before relying on them.

A resolved artifact set is a JSON file that lists, for each tool, version and platform, the download URLs, archive facts and verification evidence for a community-recipe tool. oyzu install --artifact-set reads such a file, decides which platforms are usable, writes their entries to oyzu.lock, and downloads and verifies the host artifact. Later installs replay the lock without the set file.

Note: Experimental. Flags and error codes may change. Installing from the signed tool index is the normal path; use artifact sets only when you have a set file to install from directly. Supported on Linux x86-64; Windows and macOS are not supported yet. Installed recipe tools are not runnable yet (see Limitations).

You can produce a set with oyzu tools resolve followed by oyzu tools evidence. No account is needed, and install and tools info never evaluate recipes themselves.

# Check eligibility only: nothing is written or downloaded
oyzu install --dry-run --artifact-set terraform.verified.json oyzu:terraform@1.16.5
oyzu --json tools info --artifact-set gh.verified.json aqua:cli/cli@2.102.0 --details

# Pin a record by its digests.full, lock its platforms, download and verify the host artifact
oyzu install --artifact-set go-task.verified.json --artifact-set-digest sha256:<digests.full> \
    oyzu:go-task/task@3.54.0

# Replay from the lock alone (the set file can be gone); --offline reuses the verified cache
oyzu install --frozen

Inputs​

FlagMeaning
--artifact-set FILEA set file (JSON, format: 1, kind: "artifact-sets"). Repeatable. Accepted by install SPEC and tools info. With --frozen it is checked against the lock.
--artifact-set-digest sha256:DTrusts one record by its digests.full. Repeatable. Without it, each file is a local set that you vouch for.
--connector-bindings FILEConnector endpoints for routes.
--details(tools info) Show every check and route.

The spec can be oyzu:<name>@version, oyzu:owner/name@version, aqua:owner/name@version or recipe:owner/name@version. It matches records whose tool.id is aqua:owner/name or recipe:owner/name. The version matches either the upstream form (v1.16.5) or the normalized form (1.16.5). core: records (Oyzu's own providers) can't be installed from a set (LOCK_ID_UNREPRESENTABLE).

Sets work in the project scope only; -g and --local aren't supported.

What a set file must look like​

The whole file is rejected, and nothing is written, if:

  • it is over 16 MiB, is malformed JSON or has a duplicate key;
  • format isn't the integer 1 or kind is wrong (SET_FORMAT_UNSUPPORTED);
  • it has unknown top-level fields, more than 4096 records, a duplicate record, or records not sorted by tool ID, version and platform (SET_SCHEMA_INVALID).

A single record is unusable (other records still count) if it has unknown fields or values, a URL that isn't plain https (no user info, fragment, backslash or dot segments), evidence that doesn't match its URLs, is over 1 MiB, or its recorded digests don't match its content (SET_DIGEST_MISMATCH).

A set doesn't vouch for itself. Each record needs an anchor: a --artifact-set-digest pin, or your choice to use a local set.

Eligibility result​

You get one result per platform. Checks run in this order:

CheckWhat it checksCodes
tool-admittedtools.allowedCONFIG_OVERRIDE_DENIED
set-integrityrecord is valid, anchored and not expiredSET_FORMAT_UNSUPPORTED, SET_SCHEMA_INVALID, SET_DIGEST_MISMATCH, SET_UNANCHORED, SET_ANCHOR_EXPIRED, SET_DISAGREEMENT
record-statusresolved passes; unsupported means unavailable; error means invalidthe record's own reason code
evidence-floorverification tier and evidenceTIER_BELOW_FLOOR, EVIDENCE_BELOW_FLOOR, EVIDENCE_VERIFIER_UNAVAILABLE, EVIDENCE_ORIGIN_NOT_ACCEPTED
routesevery download and evidence host can be reached through your routesROUTE_UNROUTABLE, ROUTE_EGRESS_UNROUTABLE
lock-representable(install only) the record fits in oyzu.lockLOCK_ID_UNREPRESENTABLE, DIGEST_NOT_SHA256, ARCHIVE_FORMAT_UNSUPPORTED, PLATFORM_ABI_UNSUPPORTED

Outcomes:

OutcomeMeaning
eligibleUsable.
deniedA rule blocks it; someone can change the rule.
unavailableThe set says there is no asset for this platform. It is left out of the lock and listed in unavailablePlatforms. Selecting that platform later fails with TOOL_PLATFORM_UNAVAILABLE.
invalidThe record can't be used.

If set-integrity or record-status fails, later checks show skipped. The exit status is 1 for denied, invalid or an unavailable host platform, and 2 for argument errors.

Human output starts with the outcome, then platforms, reasons and a "Denied by" table (rule, scope, reason, fix). --json prints the same result (outcome, results[].checks, denials, routes, code, written). Secrets, query strings and redirect targets are never shown.

The minimum tier is verified and there is no evidence minimum. You can't change these yet.

Source choice and anchors​

Oyzu uses the lock first, then an anchored set, then a local set. It never falls back to evaluating a recipe.

  • A record that matches a --artifact-set-digest is anchored. Without any digest, every record is local.
  • When you pass digests, only matching records are used. The host platform must match; other unmatched platforms are left out of the lock.
  • Two anchored records for the same registry snapshot with different content fail with SET_DISAGREEMENT, and neither is used.
  • In managed mode, local sets are refused (SET_UNANCHORED; use the catalog instead), and installs from sets are rejected.

Routes​

Artifact sets and recipe tools use the shared tool acquisition route contract. Administrative tools routes select a connector by exact host or tool family; a family wins over a host, and any configured route makes acquisition closed-world. The caller supplies the connector binding file with --connector-bindings.

The shared contract owns destination path/query mapping, duplicate-scope errors, client/server redirects, credential handling and offline behavior. Artifact-set eligibility checks all declared URL and evidence hosts before acquisition; routing does not replace anchoring, tier, evidence or digest checks.

Lock entries and replay​

Each accepted record becomes a normal oyzu.lock entry:

  • id is recipe:<owner>/<name>, whether the record said aqua: or recipe:.
  • version is the normalized version; digest and size come from the verified artifact.
  • The entry records the download URL and digest.

Direct and mirrored installs produce identical lock entries. Digests must be lowercase sha256:<64 hex>.

oyzu install --frozen downloads (or reuses the cached copy of) each locked recipe: tool and checks its size and digest. With --artifact-set, it fails with TOOL_LOCK_STALE if an anchored record disagrees with the lock.

Limitations​

  • Installing downloads and verifies the artifact into the tool store cache, but doesn't extract it, create shims or write [tools]. A recipe tool isn't runnable yet.
  • Signatures and attestations aren't re-checked at install; only the digest is compared. oyzu tools evidence verifies GitHub attestations when the set is produced.
  • No organization catalog source, no update for sets, and no settings for the minimum tier or evidence.
  • Supported on Linux x86-64 only.
