Installing from resolved artifact sets (client slice)

CLI reference

Published from the canonical docs/reference/artifact-sets.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Status: experimental, client side only. Implements the consumer half of the draft ingested artifact set client contract. Every flag, code and position below is provisional; the draft is not accepted. Most checks use sets hand-built from the contract schema (tests/fixtures/artifact-sets). On 2026-10-10 the client read real producer output (oyzu tools resolve + tools evidence for terraform v1.16.5, aqua: record ids), found it eligible on all three platforms, wrote the lock and downloaded and verified the Linux artifact, and install --frozen replayed it from the lock. SETC P1 is not claimed. Installing from the signed tool index is the supported path; this flag reads a set file directly. Platforms: developed and checked on Linux x86-64; Windows and macOS are unverified.

A resolved artifact set names, per (tool, version, platform), the URLs, archive facts and verification evidence of a community-recipe tool. This client reads one, decides whether each platform's record is usable, maps accepted records into oyzu.lock, downloads and verifies the host artifact, and later replays the lock without the set. No account is needed and recipes are never evaluated by install or tools info.

# Eligibility only: nothing is written or downloaded
oyzu install --dry-run --artifact-set terraform.verified.json oyzu:terraform@1.16.5
oyzu --json tools info --artifact-set gh.verified.json aqua:cli/cli@2.102.0 --details

# Pin a record by its digests.full, lock all pinned platforms, download and verify the host artifact
oyzu install --artifact-set go-task.verified.json --artifact-set-digest sha256:<digests.full> \
    oyzu:go-task/task@3.54.0

# Replay from the lock alone (the set file may be gone); --offline reuses the verified cache
oyzu install --frozen

Inputs​

FlagMeaning
--artifact-set FILEA set document (JSON, format: 1, kind: "artifact-sets"); repeatable. Accepted by install SPEC and tools info; with --frozen it cross-checks the lock
--artifact-set-digest sha256:DPins one record by its digests.full; repeatable. With none, each file is a local set anchored by its holder
--connector-bindings FILEHost binding file for routes (below)

The spec is oyzu:<name>@version (a curated name), oyzu:owner/name@version, aqua:owner/name@version or recipe:owner/name@version. It matches records whose tool.id is aqua:owner/name (what the producer writes and the schema requires) or recipe:owner/name (earlier hand-built sets). core: records (Oyzu's own providers) are read but not installable from a set (LOCK_ID_UNREPRESENTABLE). The version matches version.requested (v1.16.5) or version.normalized (1.16.5). -g/--local are not supported for sets (project lock only).

What the client requires of a set​

Document-level rejections (no record is used, nothing is written): size over 16 MiB, malformed JSON or a duplicate key, format other than the integer 1 or a wrong kind (SET_FORMAT_UNSUPPORTED), unknown envelope fields, more than 4096 records, a duplicate record, or records not sorted by (tool.id, version.requested, platform) (SET_SCHEMA_INVALID).

Record-level checks (an invalid record is unusable; other records stay usable): closed fields and enums, https URLs without userinfo, fragment, backslash, dot-segment or encoded separator, evidence[].lock_kind equal to the method's fixed mapping, evidence roles present in urls[], verified.lock present exactly when verification is ok, 1 MiB per record, and recomputed digests.declared / digests.full (domain oyzu.artifact-set.v1, canonical JSON; full is the record without digests, declared also drops verified and tier) — a difference is SET_DIGEST_MISMATCH. A set is not self-authenticating: a record needs an anchor.

Eligibility result​

One result per platform. Checks run in a fixed order and every failing check contributes its denials:

CheckMeaningCodes
E1 tool-admittedtools.allowedCONFIG_OVERRIDE_DENIED (rule, scope and source from configuration)
E2 set-integrityrecord valid, anchored, freshSET_FORMAT_UNSUPPORTED, SET_SCHEMA_INVALID, SET_DIGEST_MISMATCH, SET_UNANCHORED, SET_ANCHOR_EXPIRED, SET_DISAGREEMENT
E3 record-statusresolved passes; unsupported is unavailable; error is invalidthe ingest reason code, verbatim
E4 evidence-floortier and evidence floorsTIER_BELOW_FLOOR, EVIDENCE_BELOW_FLOOR, EVIDENCE_VERIFIER_UNAVAILABLE, EVIDENCE_ORIGIN_NOT_ACCEPTED
E5 routesevery urls[] entry and evidence egress host routesROUTE_UNROUTABLE, ROUTE_EGRESS_UNROUTABLE (all items listed)
E6 lock-representableinstall onlyLOCK_ID_UNREPRESENTABLE, DIGEST_NOT_SHA256, ARCHIVE_FORMAT_UNSUPPORTED, PLATFORM_ABI_UNSUPPORTED

Outcomes: eligible, denied (a rule someone can change), unavailable (the set says no asset; not an error, omitted from the lock and listed as unavailablePlatforms; selecting that platform fails TOOL_PLATFORM_UNAVAILABLE) and invalid (the set is not usable evidence). E2 or E3 failures mark later checks skipped. Exit status is 1 for denied, invalid and an unavailable host platform; argument errors use 2. Human output leads with the outcome, then Platforms, Reasons and a "Denied by" table with rule, scope, reason and remedy; --details adds every check and route (tools info --details). --json prints the same result object (outcome, results[].checks/denials/routes, code, written). Secrets, query strings and redirect targets never appear. Scope names follow configuration: administrative scopes print as managed, built-in marks rules defined by the contract.

Floors are not user-settable yet: the default requires the verified tier and sets no evidence floor. They are exercised by library tests only (open decision 3).

Source choice and anchors​

Precedence: the lock, then an anchored set, then a local set; there is no recipe-evaluation fallback. A record matching a --artifact-set-digest pin has a pin anchor; with no pins every record is local. With pins, only matching records are candidates: the host platform must match, other platforms that no pin matches are left out of the lock. Two anchored records of one snapshot_digest with different digests.declared fail closed with SET_DISAGREEMENT (both digests shown, neither used); a different snapshot is not a disagreement. In managed mode local sets are ineligible by default (SET_UNANCHORED, remedy: use the catalog); writes are rejected in managed mode. Catalog index anchors and valid_until freshness are implemented in the evaluator, but nothing feeds them: organization catalogs are read by index resolution (tool catalog), not by this flag.

Routes​

A tools route in registries.routes whose scope is an exact host (for example github.com) routes that host; its connectorId selects a host binding:

format = 1
[connectors.corp-github]
base_url = "http://127.0.0.1:8080/gh/"   # https in production; http only for loopback tests
redirects = "server"                      # or "client" (default)
authorization_env = "CORP_AUTH"           # optional; never printed
  • Destination = destination origin + prefix + the set URL's own path and query, byte for byte.
  • No tools route at all: standalone implies direct identity routes for the set's hosts and follows redirect hops to any https host. Any tools route (even a per-tool one) is closed world: only listed hosts route; two rules for a host are ROUTE_RULE_CONFLICT.
  • redirects = "server": one request; a 3xx reply is ROUTE_REDIRECT_UNEXPECTED and is not followed. client: each hop must have its own rule (ROUTE_REDIRECT_UNROUTABLE otherwise) and is fetched from that rule's destination. A redirect target is never stored, logged or printed.
  • Routes are administrative-only configuration like the rest of registries.routes.

Lock mapping and replay​

An accepted, verified record becomes a version-1 lock entry without a schema change: id = recipe:<package> (the client's own namespace for set-installed tools, whether the record says aqua:<package> or recipe:<package>), version = version.normalized, digest/size from verified.artifact, source_id = artifact URL host, artifact_id = percent-decoded file name, verification copied from verified.lock, resolution.inputs.artifact = the set's artifact URL and digest, backend_digest from the snapshot digest (provisional). Direct and mirror installs produce byte-identical locks. Digests must be lowercase sha256:<64 hex>; nothing is repaired. A publisher sha512 is covered by the sha256 the set recorded at ingest (not shown separately in the lock). install --frozen finds locked recipe: tools, downloads (or reuses the verified cache) and checks size and digest through the tool store; with --artifact-set it also fails with TOOL_LOCK_STALE when an anchored record disagrees with the lock.

Limitations​

  • Tests use hand-built fixtures and resealed copies with producer ids; real producer output has been consumed by hand once (above), not in CI.
  • Installing downloads and verifies the artifact into the tool store cache but does not extract it, publish a receipt or shim, or write [tools] configuration; a recipe tool is not yet runnable.
  • One layout fact (the first declared file) feeds layout_digest; multi-file layouts are the installer's.
  • Evidence is not re-verified at install (digest comparison only). GitHub attestations are verified by the producer (tools evidence), not by this client.
  • No catalog source, no index freshness input, no tier/evidence settings (floors are hard-wired), no update for sets.
  • Windows and macOS unrun.

Verification​

cargo test --lib artifact_set (parser, routes, eligibility, selection, lock mapping and loopback fetch tests), cargo test --test integration artifact_set (compiled CLI, no network) and tooling/test-artifact-set-client.py (real GitHub bytes, loopback mirror needing root for the administrative route file). See implementation status and the qualification record.
