Deploy a static site

CLI reference

Published from the canonical docs/reference/deploy.md file. Features marked experimental remain experimental; check support limitations before relying on them.

oyzu deploy <target> makes a verified directory artifact live on a GitHub Pages branch. It signs the planned change, pushes one commit, reads every file back, and signs a deployment record. No platform account is required.

Status: experimental. This branch protocol uses system Git. Build provenance must already be signed by your accepted builder; deploying does not create historical build provenance. The GitHub Pages deployment API, SSH remotes and Git-hosted build commands are unsupported.

Configure and deploy​

The following configuration is illustrative. Replace both public keys with base64-encoded raw Ed25519 public keys. Supply the corresponding deployment signing seed and repository token through the named environment variables.

[deploy.targets.docs]
kind = "github-pages"
artifact = "docs/primary"
repository = "example/docs"
branch = "gh-pages"
domain = "docs.example.com"
tokenEnv = "DOCS_DEPLOY_TOKEN"

[deploy.requirements.provenance]
bundlePath = ".oyzu/evidence/docs.sigstore.json"
publicKey = "BASE64_BUILDER_PUBLIC_KEY"
builderId = "https://example.com/builders/docs"

[deploy.requirements.signing]
keyEnv = "DEPLOY_SIGNING_SEED"
publicKey = "BASE64_DEPLOYER_PUBLIC_KEY"
oyzu build docs
oyzu inspect dist
oyzu deploy docs
oyzu deploy docs --status

The Node application builder records its static output as docs/primary, a directory artifact with a tree digest and per-file inventory. The native Windows build places it at docs/windows/x86_64/application-<version>; the recorded path and compatibility remain the builder's facts. Use the output name and path in your manifest. Deploy never reinterprets a loose native output folder as a bundle.

Options and settings​

InputDefaultMeaning
<target>RequiredOne named entry in deploy.targets.
--bundle <directory>build.bundleDirectory (dist)Existing successful build bundle.
--statusOffCompare live revision and complete file inventory with the last signed record.
--rollbackOffResolve the previous deployment's subject locally and deploy it under current requirements.
--jsonOffReturn structured facts or a structured failure on stdout.

--status, --rollback and --bundle cannot be combined. The configuration cascade accepts deploy.targets and deploy.requirements in root project, user and machine configuration, with policy constraints remaining binding. Component-folder settings fail with CONFIG_SCOPE.

Target settingAccepted valuesMeaning
kindDeployer nameResolves <kind>/site; github-pages is bundled.
artifactBuild/output name, or build for its primary outputSelect exactly one directory artifact.
usesOptional plugin referenceOverrides <kind>/site through the ordinary admitted package/development binding and profile contract.
repositoryowner/repository, HTTPS Git URL, absolute local bare repository pathTarget repository. URL credentials, SSH and hosted build integration are refused.
branchValid Git branch nameServing branch; required.
domainOptional domainRequire the build's CNAME to contain this domain.
tokenEnvEnvironment variable nameRepository-scoped token for HTTPS Git; no token is needed for a local bare repository.

Only kind, artifact, tokenEnv and uses are shared keys. Other target settings, including nested tables, numbers and booleans, pass unchanged to the selected deployer's target-plan for validation. repository, branch and domain above are specific to GitHub Pages. That plugin expands repository shorthand and enforces HTTPS and the build's CNAME.

deploy.requirements.provenance uses the same accepted self-managed-key profile as publication evidence: a Sigstore v0.3 DSSE bundle with SLSA v1 provenance, the accepted public key and exact builder identity. Its subject must match the directory's tree digest. bundlePath is relative to the configuration file that declares the requirements. byArtifact profiles use the configured artifact selector. Current required verification lines and build report gates apply before the deployer can access the target. deploy.requirements and publish.requirements are configured separately; publication requirements do not supply deployment defaults.

Release builds can carry the signed first-party deployer inside the CLI. It is verified and installed offline through the same package/lock contract as any plugin. Source builds without an embedded package need an admitted package binding or a trusted user/machine plugins.development."github-pages/site" binding; project-scoped code bindings are refused.

The deployment signer is the self-managed Ed25519 signer configured by deploy.requirements.signing.keyEnv and publicKey. The key environment variable contains a base64-encoded 32-byte seed. Both intent and record use this signer. Registry subject signing does not apply to deployment.

GitHub Pages behavior​

Core verifies the recorded directory inventory and provenance, stages the exact files, and supplies them read-only to the deployer process. The site's own output must leave /.well-known/oyzu/ free. Core serves two evidence files:

  • manifest.json: a public projection with schemaVersion = "v1alpha1", kind = "deployment-manifest" and one artifact object. Its fields are id, name, target, kind, digest, size and entries when recorded. Each entry contains only path, kind, digest, size and executable when present. Paths are relative to the served tree. Bundle locations, other artifacts, actions, environments, runner facts and extensions are omitted.
  • provenance.sigstore.json: the accepted signed build provenance, byte for byte. Its signature and subject tree digest can be checked against the public inventory. Provenance is public too; use a builder whose signed statements contain only information suitable for publication.

The deployer creates an orphan commit when the serving branch is absent. Authentication and network failures always fail; they never mean the branch is absent. Existing branches receive one normal fast-forward commit. A concurrent update fails with instructions to replan; there is no force push. An unchanged tree creates no commit. Core compares every read-back file digest and the applied revision before recording success.

Symlinks, .git, .env files, package manifests and package-manager locks are refused at every depth. CNAME and .nojekyll must come from the docs build output. The deployer does not synthesize them or run a site build.

HTTPS Git uses core's reverse credential proxy. The plugin and native Git receive a host-bound loopback URL; core alone loads tokenEnv and attaches authentication to the admitted upstream.

The GitHub Pages package declares only https://github.com as a credential origin, bound to the target's repository setting. Owner/repository shorthand uses that origin. An explicit repository URL must have the same origin, including its port; a different HTTPS host needs a deployer package declaring that host.

Core checks the planned URL against the package's describe.output.credential_hosts and the explicit setting before reading tokenEnv. Credential URLs must use HTTPS and contain no userinfo, query or fragment. A refusal sends no credential.

An empty or unset reference fails; there is no OIDC fallback. Writes are permitted only during target-apply. Core verifies read-back using observations made after write authority closes, and independently compares the fetched Git files with the plugin inventory. Credentials never appear in plugin environments, arguments or files. The proxy limits request and response bodies to 64 MiB and refuses redirects and requests outside the declared destination. Use a GitHub App installation token or a fine-grained token restricted to the repository and necessary content writes. Native host execution provides best-effort process/network separation.

Records, drift and rollback​

Local state lives under .oyzu/deploy/<target>/: signed intent, signed record, receipt, and signed subject history. The record names the subject digest, target, previous subject, signer, policy/verification facts, plugin identity and digest, applied revision and read-back inventory. A failed read-back leaves the prior successful record in place even though a remote commit may already exist; inspect the branch before retrying.

Accepted provenance is retained with each local subject record. Rollback searches the recorded bundle, current bundle locations and .oyzu/history, then re-verifies the exact tree and retained provenance against current trust.

--status returns unchanged or drift. Drift means the revision or any served file differs from the last record. GitHub Pages has no runtime signature gate: whatever lands on its serving branch may be served. Restrict writes to the deployer identity through repository permissions and branch protection, and run drift checks. A valid deployment record cannot prevent another authorized writer from changing the branch.

Rollback requires the previous subject's local bundle and accepted provenance to remain available. It repeats current evidence checks and produces a new commit and record. Local state is not a remote archive or a retention service.

Fresh CI containers have no deployment history unless .oyzu/deploy/<target> is restored from trusted persistent storage. With no last record, --status and --rollback fail, and a new record has no previousSubject. Deploying an identical live tree still creates no commit and writes a new local record. Remote record discovery and previous-subject retention are not implemented.

Failures and recovery​

DiagnosticCauseRecovery
DEPLOY_NOT_CONFIGUREDMissing or unknown target.Configure root deploy.targets.
DEPLOY_SUBJECT_AMBIGUOUSSelector finds zero or several outputs.Inspect the bundle and name one directory output.
DEPLOY_SITE_REFUSEDForbidden content or reserved evidence namespace.Correct the build output and rebuild.
DEPLOY_DOMAIN_MISMATCHBuilt CNAME does not match domain.Correct the native site configuration and rebuild.
PUBLISH_HOST_REFUSEDPlanned credential URL has an undeclared origin, mismatches the explicit repository URL, or is not a valid HTTPS endpoint.Correct repository or select a deployer declaring that origin. No credential was resolved or sent.
DEPLOY_PLUGIN_INVALIDInvalid declared credential origin or credential host setting.Correct the deployer description and the named target setting.
PUBLISH_CREDENTIAL_UNAVAILABLEHTTPS token variable unset, empty or invalid.Supply the repository-scoped token in the invoking environment.
DEPLOY_PLUGIN_MISSINGNo admitted deployer package or trusted development binding.Install the first-party package or configure a user/machine development binding.
DEPLOY_PLUGIN_FAILEDGit, target race, auth/network or plugin operation failed.Follow the nested diagnostic; check the branch before retrying.
DEPLOY_READ_BACK_MISMATCHLive bytes or revision differ after apply.Inspect remote changes; no new successful record was written.
DEPLOY_ROLLBACK_UNAVAILABLEPrevious bundle/digest unavailable.Restore the exact retained bundle and its accepted provenance.

Provenance and policy refusals retain their existing PUBLISH_, CONFIG_ or POLICY_ diagnostic. They do not authorize bypassing a gate. Local bare repositories work offline with installed tools/plugins and local signing material; HTTPS targets require network access.
