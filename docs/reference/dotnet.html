.NET builds

CLI reference

Published from the canonical docs/reference/dotnet.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Oyzu builds a directory that has a solution (.sln, .slnx) or an SDK-style project (.csproj, .fsproj, .vbproj) without any Oyzu configuration. The dotnet/sdk builder runs restore, build, test and pack in a network-denied container and delivers a versioned NuGet package directory.

Note: The .NET builder is experimental. It runs only in a Linux amd64 container (Docker required), so there is no host-native .NET build and no Windows or macOS build.

The .NET plugin package​

The dotnet/sdk builder is supplied by the oyzu-plugin-dotnet plugin. The plugin finds your projects, plans the build and runs the restore, test and pack steps. Oyzu itself still provides the SDK and source, the NuGet mirror, version resolution, credentials, and the checks on artifacts and reports. The plugin gets the NuGet mirror address from Oyzu and never sees your credentials.

Quick start​

oyzu run list
oyzu build --plan
oyzu build
oyzu inspect dist
  • Plain oyzu build selects the fast build and package path.
  • oyzu build --isolated --full also runs the native tests. --isolated alone doesn't select tests.
  • This builder has no host build path, so it always uses the container, with or without --isolated.
  • The container needs Docker and the locked SDK described under Provisioning.

Provisioning​

Builds run on the base execution image, which has no .NET SDK. The SDK comes from oyzu.lock and is restored read-only into every action (see Capturing a selected SDK). Without a [tools] dotnet setting, oyzu pin locks the default SDK, 10.0.401.

  • The base image carries the shared libraries the official SDK loads (OpenSSL, ICU, Kerberos and zlib) and a C toolchain.
  • Only Linux x64 GNU SDKs are supported, so .NET builds run on linux/amd64.
  • Pass --image dotnet=<ref> to run on your own image, for example one with OS packages a project links against. It must meet the bring-your-own requirements, and the locked SDK is still the one restored.
  • No image carries an Oyzu worker. Restore, test and pack run the engine and the .NET plugin that Oyzu mounts into the container, so updating the CLI never needs an image rebuild.

Discovery and entry selection​

A directory is claimed when it directly contains a solution, or a project whose root element names an MSBuild SDK (Sdk="...", an <Sdk> element or an SDK import). Legacy non-SDK projects are not claimed.

  • Discovery adds install, build and test tasks that run dotnet restore, dotnet build and dotnet test.
  • A literal SemVer Version or VersionPrefix in the entry project or the root Directory.Build.props becomes the native version. Computed values stay native.

Every native command receives one entry file: a single solution, otherwise a single SDK-style project. If there is more than one candidate, the build fails and lists them. Choose one:

builds:
  app:
    uses: dotnet/sdk
    with:
      project: src/App.slnx
OptionValuesDefaultMeaning
with.projectA solution or project file, relative to the targetThe single solution, otherwise the single SDK-style projectThe entry file every native command receives. Other with keys are rejected.

Capturing a selected SDK​

By default the build uses the default SDK (10.0.401). To use another one, name an exact stable Linux x64 GNU SDK. Oyzu downloads it from Microsoft's builds.dotnet.microsoft.com release metadata and archives. This is experimental.

[tools]
dotnet = "10.0.402"
lockPlatforms = ["linux/amd64/gnu"]

Run oyzu pin, then oyzu build --isolated --full --frozen.

  • Oyzu checks Microsoft's SHA-512 for the archive and records its SHA-256 in oyzu.lock.
  • The archive is restored read-only and unchanged. Installation keeps all archive notices.
  • DOTNET_ROOT, PATH and the exact version are fixed for restore, build, test and pack.
  • The dotnet --version seen inside the container must equal your selection and satisfy global.json. Another SDK is never picked silently instead.
  • Warm frozen or offline runs need the existing lock, the SDK archive and the NuGet inputs. They don't consult release metadata.

Limits:

  • The execution image provides the OS, linker and library prerequisites. An image of your own must provide them too.
  • Oyzu doesn't provide an OS, a separate runtime, Windows, macOS or ARM SDKs, or a GNU fallback for musl.
  • Prereleases and older SDK download layouts aren't supported.

If the build is refused, the cause is one of these:

ProblemWhat to do
Checksum mismatch, unsupported platform or archive layoutDon't edit the lock digest to accept unexpected bytes. Restore the missing inputs online and rerun.
global.json conflicts with the selected SDKMake the two agree, run oyzu pin, and retry the frozen build.
You need a different SDKChange [tools] dotnet and run oyzu pin. Changing only the image doesn't override a locked SDK archive.

Native SDK preference​

global.json in the target root selects the SDK the way the .NET host does: sdk.version, sdk.rollForward and sdk.allowPrerelease.

  • patch can keep an exact installed SDK even when a newer patch is available. latestPatch takes the latest available patch.
  • Oyzu runs dotnet --version in the target directory to see what the host would pick, instead of predicting it.
  • Without global.json, the .NET host chooses the SDK supplied to the build, which is the locked SDK.
  • A value that isn't an exact SDK version (10.0) is refused, with a hint naming an exact version such as 10.0.100.
  • Only the target root's global.json is read. The .NET host's upward search for a global.json in parent folders isn't followed.
  • global.json must be strict JSON. Comments are rejected.
  • Custom SDK search roots (sdk.paths) aren't supported.

oyzu build --plan lists the oyzu:dotnet tool requirement, with the global.json sdk.version as its constraint when there is one. The discovery record shows the request under sdk.

Before restoring, preparation lists the SDKs installed in the container and checks which one the host would select in the target directory. Each check has a 30-second timeout.

  • If no installed SDK is allowed, the build fails before restore. The message names the request, the SDKs provided and oyzu pin.
  • The selected version must be installed and allowed by the request.
  • The dependency record and the .NET SDK evidence record that version.
  • Offline restore checks the selection again and requires the same answer.
  • A failed or timed-out check, or an invalid answer, fails preparation.

Build, test and package​

Build actions run with the network denied:

  1. A prepare action restores offline from the prepared packages into /workspace/.oyzu-dotnet/packages (also NUGET_PACKAGES). It keeps --locked-mode when preparation used it.

  2. build runs dotnet build <entry> --configuration Release --no-restore --disable-build-servers -p:Version=<version>.

  3. When tests are selected (for example by --full), test runs dotnet test --no-build --no-restore and writes TRX results:

    • VSTest uses --logger trx.
    • Microsoft.Testing.Platform uses --report-trx and --solution or --project. Set test.runner: Microsoft.Testing.Platform in global.json to use it.

    All TRX files are converted into one JUnit report that keeps class names, failures and skipped tests. A passing run with no TRX results fails instead of reporting an empty suite. A custom test task must still produce the required JUnit report, or the action fails and no package is exported.

  4. dotnet pack --no-build --no-restore writes one directory artifact, nuget-packages-<version>. It fails if no project is packable.

Environment:

  • The version comes from version inference over the native version and your Git history. It is passed to restore, build and pack as -p:Version.
  • CI is removed from the action environment, because ContinuousIntegrationBuild source mapping needs a .git directory that the captured source leaves out.
  • Telemetry, first-run output, workload notices, MSBuild node reuse and online certificate revocation checks are off.
  • Actions reserve 4096 MiB and time out after 30 minutes.

Isolated restore​

Preparation runs dotnet restore <entry> once, with the network denied, through a local mirror that forwards only the NuGet V3 flat container and vulnerability data of https://api.nuget.org/ to Oyzu's download broker.

  • Restore reads only a generated NuGet.Config. Oyzu clears project RestoreSources, additional sources and fallback folders, so repository and user feeds, package source mappings and credentials are not used.
  • If any packages.lock.json exists in the target, restore runs with --locked-mode. NuGet applies each lock to its own project, and projects without a lock restore normally. The lock files are recorded.
  • Restored packages go into a NuGet global packages folder in the prepared tree. Each package's .nupkg digest and size is recorded.
  • The recorded package source is the public index, so the prepared tree doesn't depend on the mirror's port.

NuGet audit​

Preparation restores with NuGetAudit=true and keeps warnings NU1900 to NU1905 as warnings, even under TreatWarningsAsErrors or WarningsAsErrors. The findings come from NuGet's own logs. Oyzu:

  • shows a NuGet audit step with a summary, for example known vulnerabilities: 1 high;
  • logs each finding as a NUGET_AUDIT warning;
  • records them in the dependency record under oyzu.dev/nuget-audit, with complete: false when NuGet couldn't read vulnerability data.

Audit findings never fail preparation. Build actions restore with NuGetAudit=false, so audit warnings can't turn into later compile errors.

MSBuild project SDKs​

Some MSBuild SDKs come from NuGet, such as Aspire.AppHost.Sdk or Microsoft.Build.NoTargets. A project names them with Sdk="Id/Version", an <Sdk Name Version> element, or msbuild-sdks in the root global.json. MSBuild restores them itself while it evaluates a project and ignores the generated NuGet configuration, so with the network denied the evaluation failed and restore skipped the project (NU1503).

To avoid that, preparation scans the root global.json and every project, props and targets file for literal versions. It restores each SDK package through the broker into the prepared packages before restoring the entry, and the offline build restores them from there.

  • The ids and versions are recorded under msbuildSdks in oyzu.dev/dotnet, and each package appears in the dependency record.
  • SDKs bundled with .NET (Microsoft.NET.Sdk*) are never restored.
  • A version written as a property, range or wildcard isn't restored and fails in MSBuild.

Built-in checks​

Every build checks its own results:

  • A test failure keeps the JUnit report and blocks the package.
  • A test run that exits successfully without a report fails.
  • A changed dependency that doesn't match an existing lock fails restore.
  • A SDK request nothing satisfies fails before restore.

Run oyzu inspect dist to check the bundle, including the SDK, lock and package records and the test results.

Limits and possible changes​

These choices may change:

  • the builder id dotnet/sdk;
  • the default SDK;
  • audit is reported but never enforced;
  • CI is removed;
  • the action memory and timeout limits;
  • packing every packable project into one directory artifact;
  • failing on an ambiguous entry, an unsatisfiable SDK request or missing TRX results.

Not supported:

  • private feeds, credentials, package source mapping and nuget.sessionEndpoint in captured builds;
  • workloads, and MSBuild project SDKs whose versions MSBuild computes or a range names;
  • global.json and Directory.Build.* files above the target directory;
  • coverage, lint and format integrations;
  • per-package file artifacts, dotnet publish outputs and NativeAOT publishing as a build stage;
  • Windows and macOS builds;
  • repositories with several projects and no root solution, unless with.project selects one.

Resource limits:

  • The download broker allows 1 GiB and 4096 requests per session, and 256 MiB per response.
  • The prepared tree is limited to 100,000 entries and 10 GiB.
  • NuGet's HTTP cache and extraction scratch use /scratch/nuget, which can grow with the action's 4 GiB memory reservation instead of being limited by the 512 MiB /tmp mount. Large packages such as Microsoft.Playwright fit.

For managed NuGet sessions with oyzu exec, see NuGet sessions.
