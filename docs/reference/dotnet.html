.NET builds

CLI reference

Published from the canonical docs/reference/dotnet.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Status: bounded Linux captured fixture verified. The dotnet/sdk builder's full restore/build/test/pack flow, independent consumption of its delivered NuGet package and finite failure/report scenarios passed on Linux amd64 with SDK 10.0.401. Native selection/evidence also passed the finite SDK 400/401 and 301/401 matrix. Broader corpus and host qualification remain pending; see verification for the exact evidence boundary.

A directory with a solution (.sln, .slnx) or an SDK-style project (.csproj, .fsproj, .vbproj) needs no Oyzu configuration:

oyzu run list
oyzu build --plan
oyzu build
oyzu inspect dist

Plain oyzu build selects the fast build/package path. Use oyzu build --isolated --full to request the captured build and native test checks described below. Selecting isolation alone does not select tests. This builder has no host build adapter; it currently uses the captured executor even without an explicit --isolated flag.

Provisioning​

Captured builds use the explicitly provisioned image oyzu-toolchain/dotnet:10.0.401. It is built from the pinned definition, a digest-pinned mcr.microsoft.com/dotnet/sdk:10.0.401-noble-aot base plus the compiled Oyzu worker:

docker build -f tooling/images/builder-worker.Dockerfile -t oyzu-toolchain/builder-worker:v1 .
docker build -f tooling/images/dotnet.Dockerfile -t oyzu-toolchain/dotnet:10.0.401 .

The -aot variant adds clang and zlib, so NativeAOT projects have their native linker prerequisites. The image is not published by the toolchain-image workflow and is never downloaded automatically. Select a different SDK image with --image dotnet=<image>. Linux amd64 is the only provisioned platform.

Discovery and entry selection​

A directory is claimed when it directly contains a solution or a project whose root element names an MSBuild SDK (Sdk="...", an <Sdk> element or an SDK import). Legacy non-SDK projects are not claimed. Discovery adds install, build and test tasks that run dotnet restore, dotnet build and dotnet test. A literal SemVer Version or VersionPrefix in the entry project or root Directory.Build.props becomes the native version; computed values stay native.

Every native command receives one entry file: a single solution, otherwise a single SDK-style project. More than one candidate fails and names them. Select one explicitly:

builds:
  app:
    uses: dotnet/sdk
    with:
      project: src/App.slnx

with.project must be a relative solution or project file in the target. Other with keys are rejected.

SDK selection​

global.json in the target root selects the SDK as the native host does: sdk.version, sdk.rollForward (default patch with a version, latestMajor without one) and sdk.allowPrerelease (default true). Native preference matters: patch can retain an exact installed SDK even when a newer admitted patch is available; latestPatch chooses the latest admitted patch. The adapter observes dotnet --version in the unchanged target directory instead of predicting a maximum version. Without global.json the native host chooses the image's SDK.

oyzu build --plan shows the request and the default image SDK in its tool requirements, for example dotnet-sdk 10.0.300 rollForward latestFeature; default image SDK 10.0.401, or image default 10.0.401 (no global.json). The discovery record keeps the same choice under sdk.

The preparation container lists its installed SDKs from /, then observes native selection in the target directory. Both probes use the shared bounded native process runner with a 30-second timeout. It fails before restore when none is admitted, naming the request, the provided SDKs and --image dotnet=<image>. The observed version must be installed and admitted by the strict request. Dependency manager and .NET SDK evidence record that native version. Offline restore observes selection again and requires agreement with preparation. Native probe failures, timeouts and invalid observations fail preparation rather than producing package evidence. global.json must be strict JSON; comments are rejected rather than guessed.

Custom native SDK search-root provenance, including sdk.paths, remains unqualified: installed-version membership does not attest which filesystem SDK root supplied that version. The bounded multi-SDK qualification records actual policies, versions and measured limits.

Captured restore​

Preparation runs dotnet restore <entry> once, with network denied, through a loopback mirror that forwards only the NuGet V3 flat container and vulnerability data of https://api.nuget.org/ to the scoped acquisition broker. Restore reads only a generated NuGet.Config (--configfile), and project-declared RestoreSources, additional sources and fallback folders are cleared. Repository and user feeds, package source mappings and credentials are therefore not used.

When any packages.lock.json exists in the target, restore runs with --locked-mode. NuGet enforces each lock for its own project; projects without a lock restore normally. Lock files are recorded in lockDigests.

Restored packages are stored as a NuGet global packages folder in the prepared tree. Each package's .nupkg digest and size is recorded in the dependency record. The recorded package source is normalized to the public index so the prepared tree does not depend on the mirror's port.

NuGet audit​

Preparation restores with NuGetAudit=true and keeps NU1900–NU1905 as warnings, even under TreatWarningsAsErrors or WarningsAsErrors. Findings come from NuGet's own project.assets.json logs and are:

  • summarized as a NuGet audit preflight step, for example known vulnerabilities: 1 high;
  • logged per finding as NUGET_AUDIT warnings;
  • recorded under oyzu.dev/nuget-audit in the dependency record, with complete: false when NuGet could not read vulnerability data.

Audit findings never fail preparation. Build actions restore with NuGetAudit=false, so audit warnings cannot become later compile errors.

Build, test and package​

Captured build actions run with network denied and these steps:

  1. A prepare action restores offline from the prepared packages into /workspace/.oyzu-dotnet/packages, which is also NUGET_PACKAGES. It keeps --locked-mode when preparation used it.

  2. build runs dotnet build <entry> --configuration Release --no-restore --disable-build-servers -p:Version=<version>.

  3. When selected (for example by --full), test runs dotnet test --no-build --no-restore with TRX results:

    • VSTest uses --logger trx;
    • Microsoft.Testing.Platform uses --report-trx and --solution/--project. This mode is selected when global.json sets test.runner: Microsoft.Testing.Platform.

    All TRX files are converted into one JUnit report, keeping class names, failures and skipped tests. A passing run without TRX results fails rather than reporting an empty suite. A custom native test task retains the shared required-JUnit obligation; a zero exit without that report fails the action and blocks package output.

  4. The package step runs dotnet pack --no-build --no-restore into one directory artifact, nuget-packages-<version>. It fails when no project is packable.

The version is the shared version inference result over the native version and Git history. It is passed to restore, build and pack as -p:Version. CI is removed from the action environment, because ContinuousIntegrationBuild source mapping needs a .git directory that captured source excludes. Telemetry, first-run output, workload notices, MSBuild node reuse and online certificate revocation checks are disabled. Actions reserve 4096 MiB and time out after 30 minutes.

MSBuild project SDKs​

SDKs supplied by NuGet, such as Aspire.AppHost.Sdk or Microsoft.Build.NoTargets, are named by Sdk="Id/Version" on a project or import, an <Sdk Name Version> element, or msbuild-sdks in the root global.json. MSBuild's SDK resolver restores them while it evaluates a project, ignoring the generated NuGet configuration, so a network-denied evaluation failed and restore skipped the project (NU1503).

Preparation scans the root global.json and every project, props and targets file for literal versions and restores each SDK package through the broker into the prepared packages before restoring the entry. The ids and versions are recorded under msbuildSdks in oyzu.dev/dotnet, and the package appears in the dependency record. The offline build restores them from the prepared packages before the entry, so the resolver finds each SDK in the global packages folder. SDKs bundled with the .NET SDK (Microsoft.NET.Sdk*) are never restored. A version written as a property, range or wildcard is not seeded and fails in MSBuild as before.

Provisional decisions and limits​

These choices are provisional pending maintainer review:

  • the builder id dotnet/sdk;
  • the default SDK and image;
  • audit is reported but never enforced;
  • CI is removed;
  • the action memory and timeout limits;
  • packing every packable project into one directory artifact;
  • failing on ambiguous entries, unsatisfiable SDK requests and missing TRX results.

Not yet supported:

  • private feeds, credentials, package source mapping and nuget.sessionEndpoint in captured builds;
  • workloads, and MSBuild project SDKs whose versions MSBuild computes or a range names (see below);
  • global.json and Directory.Build.* files above the target directory, which are outside the captured source;
  • coverage, lint and format integrations;
  • per-package file artifacts, dotnet publish outputs and NativeAOT publishing as a build stage;
  • Windows and macOS images;
  • multi-project repositories without a root solution, unless with.project selects one.

Restores are bounded by the shared broker: 1 GiB and 4096 requests per session, and 256 MiB per response. The prepared tree is bounded at 100,000 entries and 10 GiB. NuGet's HTTP cache and extraction scratch use /scratch/nuget, whose engine tmpfs size ceiling follows the action's 4 GiB memory reservation, not the 512 MiB /tmp mount, so large packages such as Microsoft.Playwright fit. This does not raise the action's memory reservation; where cgroups are available, their limit covers process and tmpfs use together.

Managed NuGet launch sessions for oyzu exec remain separate; see NuGet sessions.

Verification​

Unit tests cover SDK roll-forward admission, entry selection, lock discovery, TRX to JUnit conversion, audit collection, mirror routing and plan shape. The dotnet suite in tooling/build_scenarios/dotnet.py exercises tooling/fixtures/dotnet-app through the compiled CLI:

  • SDK display in --plan;
  • full captured restore/build/test/pack, including recorded SDK/lock/package evidence and real test results with a skip;
  • independent offline restore, compilation and execution of a consumer using only the delivered versioned NuGet package and the recorded SDK image;
  • repeatability and source preservation;
  • a real failing test that retains JUnit and blocks package export;
  • a real passing native test override without required report evidence that fails its action and blocks package export;
  • native rejection of changed dependencies against the existing lock;
  • a reported audit finding retained in dependency evidence;
  • an unsatisfiable SDK request.

Run the bounded suite with a provisioned CLI and its matching worker image:

python tooling/test-build-scenarios.py --cli <compiled-oyzu> --suite dotnet --only dotnet --evidence-dir <new-evidence-directory>

The selected suite passed on Linux amd64 on 2026-10-16 at combined candidate 2986aa4a19ff25a29a830e3a87c98655281aa97c, tree a01a60ee0dad1d85a73fe821bb12fff4532a8654, with the compiled CLI and matching worker source. Its seven builds include expected failures, with no failed acceptance assertions. The normal fixture produced JUnit 3 total, 2 passed, 1 skipped, and the independent offline consumer printed Hello, Oyzu!. The completion record records exact source, binary/image identities, commands, outputs and failure gates.

That historical run proves its single-SDK fixture and selected scenarios. A later native correction at a640740520e0f982e2d2063983656fcf762df209 made recorded SDK evidence agree with native preference in complete SDK 400/401 and 301/401 images. Its 24 expected build outcomes and three real offline package consumers passed, including exact/default/latest/fallback policies and required refusals. The multi-SDK record owns exact source, images, commands, reports, consumers and measured limits.

These bounded fixtures do not resolve #181's eight-repository corpus. Windows/macOS, Microsoft.Testing.Platform, NativeAOT and other native inventories remain outside the measured scope. Broader support belongs in implementation status.
