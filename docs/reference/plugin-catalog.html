Plugin catalog and builder selection

CLI reference

Published from the canonical docs/reference/plugin-catalog.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Every build target in Oyzu is built by a builder plugin. The plugin catalog tells oyzu which plugins exist, how to recognize a project they can build and where to download them. This page explains how oyzu finds the catalog, detects your project, chooses a builder, and shows you what it chose and how to change it.

Note: Plugins are experimental. No builder is built into the CLI. Each target needs a plugin from a catalog, a package you bind yourself or a local development binding. When none is available, the build fails with advice; it never falls back to another builder. The official catalog lists Docker, .NET, Go, Helm, Java, Node, Python, Rust and Zig builders. Some releases require preview opt-in.

Quick start: build a Go project​

Opt in to preview releases in your user configuration (a project file can't set this):

[plugins]
preview = true

Then run oyzu build in a Go module. Oyzu detects go/app from the catalog, downloads the selected oyzu/go release from ghcr.io/oyzuai/plugins/go (anonymously, with its signature checked), records the release in oyzu.lock and builds with it. The build prints the choice in its Selection section with the source official default.

You don't need a binding or an account. A plugins.packages binding still works and takes precedence if you want to supply the package yourself.

A real oyzu build --isolated or oyzu build --no-docker adopts its selected plugins before checking executor placement. That first acquisition uses the same catalog verification and lock rules as an ordinary build. The placement preview then reads the installed selection offline. --offline still refuses a missing catalog package, and --frozen never adopts an unlocked selection. Plan-only commands remain offline and do not install plugins or write plugin selections.

The catalog snapshot​

Each command picks one catalog snapshot at the start and keeps it, so two lookups in one command never see different catalogs. The snapshot is the published catalog of your configured tool index: the official one, or your organization's. No catalog is built into the CLI.

Tool indexplugins.previewCatalog usedA real build fetches it
Official (default)onThe official catalog, plus the preview supplementYes. A copy fetched in the last 3600 seconds is reused
OfficialoffThe official catalog; cached preview supplement for lock replay only. No new preview selectionYes, primary catalog only. A copy fetched in the last 3600 seconds is reused
toolIndex.url = falseanyNoneNo
Organization (toolIndex.identity or toolIndex.trustedRoot set)anyYour organization's catalog onlyYes. A copy fetched in the last 3600 seconds is reused

When a builder in the build came from a catalog, build output names that catalog on the Selection heading, for example official catalog serial 17 or acme catalog serial 3. The serial is the catalog's version number. A build whose builders are all local development executables or direct bindings names no catalog. The Selection section lists only the builders of the builds being built: oyzu build cli doesn't list the docs build's builder.

How the catalog is verified. The catalog is plugins.json and plugins.json.sigstore.json, published next to index.json in the tool index release and signed with the same identity (tool index). Oyzu:

  • verifies the signature with the index's trusted root and identity;
  • checks the document's content digest, structure and size limits;
  • refuses a catalog at or after its expires_at;
  • refuses a rollback: a lower serial number, the same serial with different bytes, or a higher serial generated earlier.

The last verified copy is kept in <store>/catalogs/plugins/ and the rollback floor in <store>/state/plugins/. If a newly fetched copy is refused, oyzu ignores it and keeps using the last verified copy, including its withdrawals.

The 3600-second reuse window is separate from expires_at. A copy can expire sooner and still need a refresh. oyzu build --frozen refreshes catalog metadata the same way, so current withdrawals still apply, but it never changes the locked selection or downloads a missing package. --offline and read-only commands never fetch.

Organization catalogs replace the official one. With an organization identity, oyzu never consults the official catalog. If that catalog selects a release and its bytes are unavailable, the build fails. If it has no matching entry, the reference is refused. Another catalog never supplies it.

Without a usable catalog​

When no catalog is usable, the reason decides what happens. It's the same for uses: references you write and for detected ones.

Why there's no catalogLocked selectionReference not yet locked
Refused: a fetched copy failed signature, decoding, expiry or rollback checks and no verified copy is cached, or the cached copy fails those checksRefused on every command, including --plan: PLUGIN_CATALOG_UNAVAILABLERefused: PLUGIN_CATALOG_UNAVAILABLE
Expired: the last verified copy has expiredReplays oyzu.lock against that copy's withdrawals, with the warning PLUGIN_CATALOG_EXPIRED (newer withdrawals may be missing). JSON marks the catalog expired: trueRefused
Absent: nothing published, reachable or cached, and no catalog was ever verified in this store (a first run offline, or toolIndex.url = false)Replays from oyzu.lockNeeds a package or development binding; otherwise PLUGIN_UNAVAILABLE

A plugins.development or plugins.packages binding for the reference works without a usable catalog, but never past a withdrawal or revocation that the last verified copy (even an expired one) lists for that release.

If the network blocks the fetch on a machine that has never verified a catalog, the state is "Absent": a lock replays without any withdrawal check.

When a refresh fails and the last verified copy decides, the Selection section shows note using the last verified <catalog>: <reason>, and JSON carries it as catalog.note.

The official catalog​

The official catalog supplies signed first-party builder packages for Docker, .NET, Go, Helm, Java, Node, Python, Rust and Zig. Go, Java and Python have stable releases; the other builders currently require preview opt-in. A stable plugin release does not expand the platforms or features supported by its builder.

Use oyzu plugins search --refresh to see the current set, and oyzu plugins versions <reference> to check compatibility before adopting a release. Builds keep the exact selection in oyzu.lock. They refresh the primary catalog even with plugins.preview off, so stable releases and withdrawals can be discovered.

Offline on a machine that has never obtained the catalog, a builder reference needs a lock entry or a binding.

Local Preview supplement​

With the default tool index and plugins.preview on, oyzu can also read a second signed document, plugins-preview.json, from the public plugins-preview release of oyzuai/tool-index. This supplement isn't available yet: no supplement is published, so it adds nothing today. Organization catalogs never fetch it.

Once it's published, these rules apply:

  • It can add official preview releases. It can't add stable releases or another publisher's packages, and it can't change or replace anything in the main catalog.
  • Official withdrawals always win. A withdrawal in the supplement matches package, version and root digest together.
  • Each document has its own serial, expiry and rollback state.
  • A preview release found in it is signed by a person's identity (not the release workflow) under Sigstore's production roots. A release marked as a local preview but listed as stable is refused.
  • New downloads need a current verified entry. An expired copy can still refuse a release but can't permit a download. Turning plugins.preview off stops new preview selection; a locked, installed release still replays unless a current refusal applies.

Detection​

A catalog detection maps files in a directory to a builder reference. The matching is deliberately simple: exact marker file names, a few checks on JSON, TOML and go.mod fields (present, equals, prefix), and all, any and not. There are no globs, paths, expressions or commands.

  • Only detections for references this build could actually use take part: a reference with an eligible release, a lock entry or a binding.
  • Marker names match case-exactly. A symbolic link isn't a marker. A file that can't be parsed counts as having no field, not as an error.
  • The work is bounded: 100,000 directories, 512 parsed files, 32 MiB parsed and 1,024 findings. Reaching a bound fails with PLUGIN_DETECTION_INCOMPLETE; declare your targets in build.yaml to avoid it.
  • An explicit build.yaml is the full list of builds. Detection doesn't run, and an incidental file adds no target. Without one, a directory becomes a target when a catalog detection or a native convention recognizes it. Dependency and output directories are skipped, and nested repositories and build.yaml directories are boundaries.
  • If one directory matches different references (two catalog detections, or a catalog go/app beside a native-convention rust/app), discovery stops with PLUGIN_DETECTION_CONFLICT. It names the evidence for each candidate and the build.yaml line that settles it. If exactly one candidate is already locked, the lock wins and the others become a note.

How a builder is selected​

A reference gets its builder the same way whether you wrote it as uses: in build.yaml, the catalog detected it, or a native convention recognized it. Oyzu tries these in order:

  1. A plugins.development binding (plugin development).
  2. A plugins.packages binding. If its digest matches the catalog's selected release, it's that release's local archive route, and the package's publisher, name and version are checked against the catalog before installation. Any other digest is a local package binding. A binding for a withdrawn or revoked release is refused with PLUGIN_RELEASE_WITHDRAWN or PLUGIN_RELEASE_REVOKED before it's recorded or launched. A binding that names a different release than oyzu.lock fails with PLUGIN_LOCK_MISMATCH until you remove the lock entry.
  3. The release oyzu.lock already holds, replayed even if the catalog now lists a newer one. A locked release that a catalog has withdrawn or revoked is refused, naming the lock entry to remove so the next oyzu build can adopt an eligible release. If an organization catalog now binds the reference to a different package, the build fails with PLUGIN_BINDING_CHANGED so the change is adopted visibly, never silently.
  4. The catalog's newest eligible release of the reference's package and profile. A release is not eligible when it is withdrawn or revoked, is a preview and plugins.preview is off, is unsupported, doesn't support protocol generation v1alpha1 or the builder profile, or has no payload for this machine's OS, architecture and ABI.

A release is a preview when its version has a prerelease part or the catalog marks it as a preview. A stable release needs no preview opt-in. Selection orders eligible versions semantically, so 0.1.0 outranks its 0.1.0-preview.N releases even with previews enabled. A missing host payload excludes that release and the refusal names the package, version and reason; it never enables a preview implicitly. A lock of a preview stays usable after opt-out until withdrawn or revoked. To adopt a stable replacement, run oyzu plugins update; builds never move a lock silently. These rules describe selection when such releases are listed, not a claim that a stable release is published.

If nothing serves the reference, the build fails with PLUGIN_UNAVAILABLE and the catalog's reason.

Some packages need a supporting plugin. For example, a Python application container uses the Docker package, and a Docker dependency context uses its own ecosystem's package. Oyzu selects those through the same order and the same organization boundary before it writes the lock or starts any work. If selecting one fails, the lock isn't changed. A frozen or offline build needs the complete locked set.

Downloading a release​

A real oyzu build downloads a catalog-selected release from an OCI or HTTPS route in its catalog entry, using the same installer as an OCI binding. The download is anonymous, by the listed root digest, with the same package, platform and withdrawal checks. Oyzu records exactly that root in oyzu.lock. When both route types are listed, the first OCI route is used; otherwise the first HTTPS route. A failed route never falls back to another route or catalog. See HTTPS layout archives for the mirror format.

  • With an existing lock and an empty plugin store, an online, non-frozen build downloads the exact locked digest from its entry in the current catalog, even when a newer release is listed. It doesn't rewrite the lock.
  • A release already in the store is reused without a request.
  • Routes only ever come from the verified catalog, never from project files.

Only a real oyzu build adopts or installs a plugin. Every other command (build --plan, --check, run, discover) replays the lock and the store. An unadopted catalog selection there fails with PLUGIN_NOT_ADOPTED: nothing is downloaded, installed, launched or written. Help, --version, shell activation and oyzu exec never load a catalog or select a builder.

Who may sign a release​

The signature rule follows the package's publisher, on whatever registry serves it.

PackageWhat oyzu requires
Publisher oyzu (for example oyzu/go)A signature from the plugin-release.yml workflow of oyzuai/oyzu on refs/heads/main, from a GitHub-hosted or self-hosted runner, verified against Sigstore's production trusted root. This holds for the official ghcr.io/oyzuai/plugins/<name> route and for a company mirror. Nothing in a catalog or in configuration can name another signer or root
Any other publisher (for example acme/go on a company registry)Trusted by digest: the signed catalog lists the root digest. No signature is requested

A mirror of an official package must therefore serve the release's signature referrers as well as its root, manifests and blobs, and the root it serves must hash to the digest the catalog lists. A refused mirror reports one of:

  • PLUGIN_SIGNATURE_MISSING: no signature referrer.
  • PLUGIN_SIGNATURE_INVALID: no signature verifies for the official signer.
  • PLUGIN_PACKAGE_DIGEST: other bytes under the listed root.

Nothing is installed or recorded when a mirror is refused. A company catalog can't pass off its own build as oyzu/go; list it under its own package name instead.

plugins.preview​

plugins.preview = true makes preview releases eligible. Set it in user, machine or administrative configuration, never in a project file:

oyzu config set --global plugins.preview true

The Selection section​

A build with plugin-backed targets shows the choice in a Selection section, after Prepare and before Plan. When the build adopted a selection or installed a package, each target gets a full record. Output shortened.

Changing a choice​

Adoption happens only in a real build, always shows up as an oyzu.lock diff, and never prompts.

What went wrongFix
A stray file added the wrong ecosystemDeclare the targets you want in build.yaml (the printed line). The stray directory adds no target and its builder is never downloaded
Right ecosystem, wrong implementationRun the printed oyzu config set --global --json-value 'plugins.packages."<reference>"' … line to bind another package, and remove the lock entry
Right builder, wrong tool versionoyzu pin <tool>@<version> writes the pin to oyzu.toml
Ambiguous evidence (npm and pnpm lockfiles, two catalog detections)Discovery stops and names the smallest build.yaml selector. Nothing is guessed or installed
Undo an adoptiongit checkout -- oyzu.lock (or rm oyzu.lock if this build created it), then remove the reference's plugins.packages entry if it supplied the bytes, and turn plugins.preview off for a catalog preview

CodeCauseRecovery
PLUGIN_UNAVAILABLENo plugin serves the reference. The message gives the catalog's reason, for example "preview only"Turn on plugins.preview, or bind a package
PLUGIN_DETECTION_CONFLICTDifferent references match one directoryDeclare the target with uses: in build.yaml
PLUGIN_DETECTION_INCOMPLETEA detection work bound was reachedDeclare the targets in build.yaml
PLUGIN_RELEASE_WITHDRAWN, PLUGIN_RELEASE_REVOKEDA catalog (an expired copy included) withdrew or revoked the locked release, or the release a plugins.packages binding namesRun oyzu plugins update <reference> (it needs a binding or the store to supply the replacement), or remove the named [[plugin]] entry and build. For a binding, bind an eligible release or run the oyzu config unset --global … line the error prints. oyzu plugins list marks refused copies (withdrawn) or (revoked) and nothing can select them
PLUGIN_BINDING_CHANGEDThe organization catalog binds the reference to a different package than the lockRemove the named [[plugin]] entry and build to adopt the new binding
PLUGIN_LOCK_MISMATCHA plugins.packages binding names a different release than the lockRemove the lock entry, or restore the binding
PLUGIN_LOCK_MISSINGbuild --frozen needs a plugin selection that's not in the lockRestore the complete lock
PLUGIN_LOCK_UNUSABLEA locked release is missing and --frozen or --offline forbids downloading it, or no current catalog entry supplies itRun an online, non-frozen oyzu build that can reach the route
PLUGIN_ROUTE_UNAVAILABLEA new catalog selection has no usable download route, or this run forbids itRun online, or bind the archive with the release digest (plugins.packages)
PLUGIN_ROUTE_FAILEDThe release's route can't be used (registry unreachable, release missing, or an unusable address). Nothing was installed or recordedRestore access to the route. Signature, digest and package failures have their own codes

PLUGIN_PACKAGE_MISMATCHThe archive isn't the catalog's package and versionBind the right archive
PLUGIN_NOT_ADOPTEDA command other than oyzu build met an unadopted selectionRun oyzu build

Limits​

  • --frozen and --offline never download from a catalog route. A missing locked release needs an online build or a binding.
  • Builds refresh the primary catalog independently of plugins.preview. Only the preview supplement requires the opt-in to refresh. Inspection commands have an explicit --refresh, which doesn't grant preview selection.
  • A catalog entry lists the platforms a release was built for (macOS, Linux and Windows). Go builds through an HTTPS mirror have been tested on Linux x86-64 and Windows x86-64. Other platforms in a package aren't tested.
  • A revocation refuses selection and launch of an installed release, even from an expired copy. The bytes stay in the store until you run oyzu plugins prune SHA256... --apply.
  • @vN major selectors in uses aren't supported. Update with oyzu plugins update.
  • oyzu config validate only replays what's already locked. It never adopts a release or installs a package.
