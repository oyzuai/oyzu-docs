Plugin catalog, detection and builder selection

CLI reference

Published from the canonical docs/reference/plugin-catalog.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Experimental. Recognizes a project from a plugin catalog, resolves explicit and detected uses references through one resolver, and shows which builder each target got, why, and how to change it. The design is the draft discovery proposal and package sources; this page records what is implemented (issue #585). Installation, the store and lock records are described in plugin packages. What each release status does to selection, adoption and replay, and the preview's proposed support terms, is in Go builder preview.

Nothing here changes a build that has no plugin opt-in, no package binding, no organization catalog and no lock selection: built-in builders keep detecting and building as before, and the build shows no builder selection.

Quick start: the Go builder preview​

The preview builder for Go projects is in the official catalog and on GHCR. In user configuration (never a project file), opt in to preview releases:

[plugins]
preview = true

oyzu build in any Go module now detects go/app from the catalog, acquires oyzu/go 0.1.0-preview.1 from the release's own OCI route in that catalog (ghcr.io/oyzuai/plugins/go@sha256:…, anonymous, signature-verified), records the selection in oyzu.lock and builds with the plugin; Selection shows the source as official default. No binding is needed. A plugins.packages binding still works and takes precedence (a local archive or an OCI source); one whose digest equals the catalog's release is that release's local route.

The catalog snapshot​

An invocation chooses its catalog snapshot once, and the process keeps it, so two discoveries in one command never see different catalogs. The snapshot is the published catalog of the configured tool index: the official one, or the organization's. No catalog is compiled into the CLI; without a usable published copy there is no snapshot, and the rules under Without a usable catalog apply.

Every view names the snapshot that decided: official catalog serial 17 or acme catalog serial 3, on the Selection heading, on each target's selected by and source lines, and as label in the JSON records.

Published catalog. plugins.json and plugins.json.sigstore.json beside index.json in the configured tool index release, signed by the same identity (tool index). The client verifies the bundle with the index's trusted root and identity, decodes and checks the document with the protocol crate (content digest, structure, limits), refuses it at or after expires_at, and refuses a rollback against the highest verified serial (a lower serial, the same serial with different bytes, or a higher serial generated earlier). The last verified copy lives in <store>/catalogs/plugins/, the rollback floor in <store>/state/plugins/. A copy fetched less than an hour ago is reused without a request. An online build --frozen uses this same metadata refresh rule, so current withdrawals still apply; it neither changes the locked selection nor acquires a missing package from an OCI binding or catalog route. --offline and read-only previews never fetch. A fetched copy that is refused (untrusted, invalid, expired, rolled back) is ignored and the last verified copy stays in force, with its withdrawals and serial floor. If no acceptable copy is usable, there is no catalog and nothing stands in for it; the rules below apply.

Organization catalogs are exclusive. With an organization identity the official catalog is never consulted.

A local development binding (plugins.development) or package binding (plugins.packages) for the reference is exempt: it goes on without a usable catalog, but never past a withdrawal or revocation a catalog it does have (the last verified copy, an expired one included) states for the bound release. The refusal names the catalog and says oyzu never falls back to the official catalog (organization) or a bundled one (official; none is compiled in). These rules were agreed with the maintainer for the S3b review. Known gap: a network attacker who blocks the fetch on a store that never verified a catalog yields Absent, so a lock still replays unchecked (#601). The expiry warning is also a note in the Selection section. A build that fails before its receipt (and that section) renders shows it with -v and in --json only, a limitation of the shared receipt.

When a refresh is refused or fails and the last verified copy decides, the JSON catalog.note gives the reason and the Selection section adds note using the last verified <label>: <reason>.

The official catalog and the preview. The official published catalog lists the Go preview (oyzu/go 0.1.0-preview.1), its references go/app and go/library and the detections go-module (a go.mod with a module directive and no go.work) and go-workspace (a go.work). Without the opt-in a build reads the catalog from the verified cache only, since there is no stable release to find; with the opt-in a real build refreshes it, so its withdrawals apply. A preview is selectable only with plugins.preview, and a withdrawal or revocation refuses the release everywhere, matched by package and version or by root digest. The newest eligible release wins.

Nothing is compiled into the CLI as a stand-in. On a machine that has never obtained the catalog (a first run offline, or toolIndex.url = false) there is no snapshot: built-in builders work as before, and a plugin-backed reference needs the catalog or a local binding.

Detection​

A catalog detection maps observations in a directory to a logical reference. The grammar is fixed by core: exact marker file names, bounded field predicates of JSON, TOML and the module/go/toolchain directives of go.mod (present, equals, prefix), and all/any/not. There are no globs, paths, expressions or commands.

  • Only detections whose reference this invocation could use take part: a reference with an eligible release, a lock selection or a binding. Others add no target.
  • Rules are indexed by marker file name; a directory costs one existence check per marker and is evaluated only against rules whose markers are present. Markers compare case-exactly; a symbolic link is not a marker. Files are read through the discovery source view (contained, at most 4 MiB) once per directory; a malformed file is "no field", never an error.
  • Total work per invocation is bounded: 100,000 directories, 512 parsed files, 32 MiB parsed, 200,000 matcher steps, 1,024 findings. Reaching a bound fails with PLUGIN_DETECTION_INCOMPLETE naming the bound; it never reads as "no match".
  • An explicit build.yaml is the inventory: detection does not run and an incidental file adds no target (PLG-DISC-03). Without one, a directory is a target when a built-in detector or an applicable catalog detection recognizes it, with the existing walk rules (dependency and output directories skipped, nested repositories and build.yaml directories are boundaries).
  • In a directory, every catalog finding and every built-in detection is a candidate. Candidates with different references (two catalog detections, or a catalog go/app beside a built-in rust/app) are PLUGIN_DETECTION_CONFLICT, naming each candidate's evidence and the build.yaml declaration that settles it; oyzu does not guess (PLG-DISC-02). A built-in detection of the same reference is the same candidate. If exactly one candidate is already locked, the lock keeps the target and the others are a note (PLG-DISC-05).

How a builder is selected​

Every target's reference, whether written as uses: in build.yaml, detected by the catalog or recognized by a built-in detector, goes through the same sources in order (PLG-DISC-08):

  1. a plugins.development binding (development bindings);
  2. a plugins.packages binding. When its digest is the release digest of the catalog's selected release it is that release's local archive route and the selection is the catalog's (official default or company binding), with the package's publisher, name and version checked against the catalog before installation. Any other digest is a local package binding. A binding of a release any consulted catalog withdrew or revoked (matched by root digest before anything is installed, and by digest or package and version once the installer knows the release, which covers an OCI tag) is refused with PLUGIN_RELEASE_WITHDRAWN or PLUGIN_RELEASE_REVOKED before it is recorded or launched; oyzu plugins update reports the same refusal as PLUGIN_UPDATE_REFUSED. A binding never silently changes a lock: when it names a different release than the one oyzu.lock selects, the build fails with PLUGIN_LOCK_MISMATCH until the lock entry is removed;
  3. the selection oyzu.lock already holds, replayed and never replaced by a newer catalog, while it stays eligible. A locked release that any consulted catalog withdraws is refused with PLUGIN_RELEASE_WITHDRAWN, and one it revokes with PLUGIN_RELEASE_REVOKED (matched by package and version or by root digest; it never runs), each naming the lock entry to remove so that oyzu build adopts an eligible release. When an organization catalog binds the reference to a different package than the lock (and no local package binding names the locked one), the build fails with PLUGIN_BINDING_CHANGED: a changed company binding is adopted visibly, never replayed silently (PLG-PKG-06). An authentic expired copy also supplies this rebinding refusal; it never supplies an acquisition route;
  4. the catalog: the reference's canonical package and profile and its newest eligible release. A release is ineligible when it is withdrawn or revoked, a preview without plugins.preview, unsupported, without protocol generation v1alpha1, without the builder profile, or without a payload for this host's OS, architecture and ABI;
  5. the built-in builder serving the reference, if any. A reference no builder serves fails with PLUGIN_UNAVAILABLE and the catalog's reason.

A catalog-selected release with no binding is acquired by a real oyzu build from the OCI route in its verified catalog entry, through the installer an OCI binding uses: anonymous, by the listed root digest, with the same package, platform and withdrawal checks, and recorded in oyzu.lock as exactly that root. With an existing lock and an empty plugin store, an online, non-frozen oyzu build acquires the exact locked digest from that release's own entry in the current verified snapshot, even when a newer release is listed. It never rewrites the lock. Withdrawals and revocations are checked before routing; an unlisted digest, or a Refused, Absent or Expired catalog, supplies no route. Existing installed releases retain the replay rules above. A release already in the store is reused without a request, and is not verified again.

Route trust follows the package identity (decision of 2026-10-20). A release of a package of the official publisher oyzu (such as oyzu/go) must carry a signature from the fixed official signer (the plugin-release.yml workflow on main, GitHub-hosted runner), verified against Sigstore's production trusted root, on whatever registry the catalog routes it through: the official ghcr.io/oyzuai/plugins/<name>, or a company mirror an organization catalog lists. A mirror therefore has to serve the release's signature referrers as well as its root, manifests and blobs, and the root it serves must hash to the digest the catalog lists. Nothing in a catalog or in configuration can name another signer or trusted root for it, so a company catalog cannot pass off its own build as oyzu/go. A route in the official namespace always requires the official signer. A release of a package of any other publisher (such as acme/go on a company registry) is trusted by its digest, which the signed catalog lists, as a digest binding is; no signature is requested. A refused mirror reports PLUGIN_SIGNATURE_MISSING (no signature referrer), PLUGIN_SIGNATURE_INVALID (no signature verifies for the official signer against the production root) or PLUGIN_PACKAGE_DIGEST (other bytes under the listed root), and installs and records nothing. The real official signature through a mirror is proved by the mirror qualification; the loopback registry tests cannot hold a production signature and prove the refusals. Routes come only from the verified catalog, never from project files. A release with no OCI route (an HTTPS layout-archive route is not acquired from yet), or any release under --offline that is not in the store, fails with PLUGIN_ROUTE_UNAVAILABLE naming the binding that supplies it; a route that cannot be used (unreachable, incomplete, serving other bytes than the listed root) fails with PLUGIN_ROUTE_FAILED and installs and records nothing (only for access: an unreachable or incomplete registry, or an unusable listed address; a signature, digest or package failure keeps its own code and advice). A catalog-only builder (a reference no built-in builder serves, PLG-DISC-04) runs with only the tools its package manifest requires.

Only a real oyzu build adopts or installs. Every other command (build --plan, --check, run, discover, …) replays the lock and the store; an unadopted catalog selection there is PLUGIN_NOT_ADOPTED: the catalog selects <package> <version> (release …) for <reference> … this command downloads, installs, launches and writes nothing (PLG-DISC-06). Help, --version, shell activation and oyzu exec never load a catalog or select a builder (PLG-DISC-07).

plugins.preview​

plugins.preview = true makes preview releases eligible. It is accepted only from user, machine or administrative configuration, never from a project file, oyzu.local.toml or a profile (CONFIG_SCOPE), because it selects code to run:

oyzu config set --global plugins.preview true

Changing a choice​

Adoption happens only in a real build and always appears as an oyzu.lock diff. There are no prompts. Each wrong choice has a fix, verified through the compiled CLI after applying it (verification):

Wrong choiceFix
Wrong ecosystem from an incidental fileDeclare the targets you want in build.yaml (the printed line); the incidental directory adds no target and its builder is never acquired
Right ecosystem, unwanted implementationThe printed line binds another package for this reference only (oyzu config set --global --json-value 'plugins.packages."<reference>"' …) and reverts the lock this build wrote; for an older lock, remove its [[plugin]] entry, then build
Right builder, wrong tool versionoyzu pin <tool>@<version> writes the pin to oyzu.toml
Ambiguous evidence (npm and pnpm lockfiles; two catalog detections)Discovery stops with a focused conflict naming the smallest build.yaml selector; nothing is guessed or installed
Undo an adoptionThe printed line: git checkout -- oyzu.lock, or rm oyzu.lock when this build created it, then this reference's plugins.packages entry when it supplied the bytes, and plugins.preview for a catalog preview (global: it has no per-reference form)

Limits​

  • Only the OCI route is acquired from; an HTTPS layout-archive route is not. Locked acquisition needs a current verified catalog listing the exact root, or an explicit binding. Without either, a missing release remains PLUGIN_LOCK_UNUSABLE; Refused catalogs remain PLUGIN_CATALOG_UNAVAILABLE. --frozen and --offline never acquire from a catalog route. oyzu plugins current and explain install nothing and describe the pending acquisition; build --plan never downloads and stops with PLUGIN_ROUTE_UNAVAILABLE. See the lock replay qualification for the evidence and what is not proved. A route for a package of another publisher carries no signer identity: the signed catalog's digest is its trust. An official package needs the official signature on every route.
  • Without plugins.preview the official published catalog is not refreshed by builds; there is no --refresh yet.
  • The published entry lists the platforms the release was built for (darwin, linux and windows); only linux/amd64 musl is proved end to end.
  • @vN major selectors in uses, revocation of installed copies and policy admission are not implemented. Updates are oyzu plugins update.
  • oyzu config validate checks declared uses against built-in builders only, so it rejects a catalog-only reference a build would accept.
  • Windows and macOS are untested.

Verification​

Unit tests: src/plugins/catalog.rs (a published official catalog is the only snapshot; without one there is none; a refused refresh stays a refusal), src/plugins/resolve.rs (a published preview is selectable only with the opt-in; an official withdrawal by package and version, or by root digest, refuses the release and removes its detections), src/plugins/matcher.rs (go.mod directives, exact markers, symbolic links, JSON/TOML fields, malformed files, budget exhaustion). Compiled-CLI tests tests/integration/plugin_catalog.rs, with an organization catalog served over loopback and signed by a test-only Sigstore instance and a stand-in plugin: detected selection, --plan without acquisition, missing route, locked replay against a newer release and a competing detector, unlocked conflict (PLG-DISC-02, 05, 06); explicit and detected references give identical lock records (PLG-DISC-08); an explicit build.yaml keeps an incidental Go module out and nothing is installed (PLG-DISC-03); preview needs the user-scope opt-in and a project cannot set it; a catalog update adds a catalog-only builder (PLG-DISC-04); a refused organization catalog does not fall back; help, --version and exec neither fetch nor select (PLG-DISC-07); npm and pnpm lockfiles name the package-manager selector (PLG-DISC-02). Route acquisition, tests/integration/plugin_oci.rs (catalog_routes, a signed organization catalog and a loopback registry, no binding): adopt, lock and --frozen replay without the registry; a binding keeps precedence; a withdrawn release is never fetched; a route serving other bytes, an unreachable route and --offline fail without installing or recording; an official package (oyzu/go) through a company mirror is refused without the official signature (unsigned, signed by the company, signed with the official identity by another Sigstore instance, other bytes under the listed root) on first adoption, committed-lock replay and oyzu plugins update, in human and JSON output, while a plugins.packages binding keeps precedence and an installed release is reused without a request. Unit tests in src/plugins/resolve.rs and src/tools/plugin_package/oci.rs (route selected, no OCI route, offline, withdrawn and revoked, precedence, root mismatch, and the signer of a catalog route by package identity). The real official signature through a mirror: tests/integration/plugin_mirror.rs, ignored by default because it copies the published release from GHCR (see the mirror qualification).

End to end on linux/amd64 (2026-10-18) with the compiled CLI, the real preview Go plugin, scratch XDG directories (so the default store is scratch; oyzu pin has no --store), scratch user configuration (plugins.preview = true plus the local archive route) and a fresh Git checkout of examples/builds/go-app/project, with no plugin installed:

  1. oyzu build refreshed and verified the live official catalog (serial 17, production Sigstore trust root), detected go/app from the bundled preview source of that day (since replaced by the published catalog), installed oyzu/go 0.1.0-preview.1 and Go 1.27.2, showed the full Selection record, wrote the [[plugin]] entry (git status: new oyzu.lock) and produced dist/project/artifacts/project-0.0.0-dev.…, which prints Hello, Oyzu! (PLG-DISC-01).
  2. The printed undo line (rm oyzu.lock && oyzu config set --global plugins.preview false && oyzu config unset --global plugins.packages) run as printed: the next build used the built-in builder, showed no builder selection and wrote no [[plugin]] entry.
  3. Opting in again re-adopted the release from the store with no archive route; after committing the lock the rebuild showed the one-line form, and --json carried the same record (state: locked).
  4. oyzu pin go@1.24.5 wrote the pin to oyzu.toml; the next build installed and used Go 1.24.5 with the locked plugin, and the artifact ran.
  5. Binding another package of go/app was refused against the lock (PLUGIN_LOCK_MISMATCH); after removing the [[plugin]] entry the build adopted it as a local package binding.
  6. In a checkout with image/Dockerfile and an incidental tools/go.mod, the build adopted go/app for project-tools and printed build.yaml: {builds: {project-image: {uses: docker/image, path: image}}}; with that file, a build with a fresh store planned only project-image, installed no plugin and wrote no lock (PLG-DISC-03).
