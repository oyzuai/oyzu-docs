Ant builds and test reporting

CLI reference

Published from the canonical docs/reference/ant.md file. Features marked experimental remain experimental; check support limitations before relying on them.

The java/app builder, for a folder with build.xml, builds conventional and custom Ant projects on your machine or in a container and exports versioned JARs. oyzu run test produces test and coverage reports without packaging a JAR. Both use the same Ant reporting integration.

Status: experimental. Native host builds support Linux x64 and Windows x64; Windows qualification is pending. Captured builds run on Linux with Docker. The oyzu/java plugin selects Ant for a folder with build.xml (or with.build-tool: ant); see plugin catalog and selecting a role.

Native JAR builds​

With the native prerequisites provisioned, run:

oyzu build --full
oyzu inspect dist

Oyzu uses the managed JDK to evaluate your Ant project on the host, discovers its JAR targets and outputs, then runs the build, test, archive and quality stages. It copies versioned JARs into a fresh core-owned output directory and collects them with JUnit and JaCoCo reports into dist/. A model evaluation error fails preparation with Ant's diagnostic; it does not silently select a container.

The JDK comes from your native tool selection and [tools] configuration. Provision Ant and reporting libraries as described below; the native path does not download them. Native execution uses your machine's network and environment, including any effects of Ant's project configuration. Use --isolated when you need container isolation. ivy.xml remains unsupported.

What each stage reads​

Ant build, archive and check operations stay unbounded: build.xml, imported build files and custom tasks are programs whose complete reads are not reported. Native tests may read files at run time. The package operation consumes only its archive producer's JARs through an upstream-only contract. No conventional source layout is assumed. These declarations reach users with the next release of the Java plugin.

Native build, test, archive and quality actions currently run again on unchanged inputs because their output sets are unbounded. Packaging can reuse a result only when the upstream archive workspace is unchanged.

Isolated JAR builds​

oyzu build --isolated --full
oyzu inspect dist

You need Docker and the base execution image. Oyzu pulls the image when it's missing. Ant 1.10.18, JUnit 4.13.2, Hamcrest 1.3, JaCoCo 0.8.13 and the Java quality tools are pinned upstream files. Preparation fetches them, checks them and restores them read-only at /scratch/java-integration, so there is nothing to build or install yourself for this mode.

  • --isolated selects the container. --full adds the test and quality checks to build, archive and package. Isolation alone doesn't run all checks, and plain oyzu build keeps the fast defaults. Checks you marked required still run.
  • Oyzu chooses the archive targets and JAR paths from what Ant reports for your project. It doesn't assume a layout.
  • Ant projects with ivy.xml are refused, and arbitrary downloads from Ant aren't supported.
  • The bundle contains the versioned JARs and the reports from the checks that ran. A failed check or a missing required report blocks the JARs and keeps the available reports in the failed bundle.
  • A custom task that exits zero without writing its reports counts as incomplete reporting. To make the reports mandatory, add a [checks] section with tests = "required" and coverage = "required" (check levels). See direct reporting for how command success differs from verified results.

Selecting a JDK​

The JDK comes from oyzu.lock; the base image has none. It is used to evaluate the project and for every build action. For example:

[tools]
java = "21"

Run oyzu pin, then oyzu build --isolated --full --frozen.

  • The locked archive is restored read-only, and JAVA_HOME and PATH are fixed in the plan.
  • Oyzu's Java integration needs JDK 17 or newer.
  • Offline runs need the archives already captured. A missing or incompatible pin is refused before any action runs.

Versions​

Builds use version inference over the native version property and your Git history. Core evaluates Ant again with the chosen version and oyzu.version user properties before planning. ANT_ARGS and OYZU_VERSION carry that version into the build and checks. The artifact name, the bundle version and the JAR's Implementation-Version agree. Qualifiers that can't take part in SemVer inference are kept. An exact tag produces a snapshot, not a release.

Direct tests​

An Ant project with a conventional test target can run oyzu run test to write native test and coverage reports to a test-only dist/ bundle. It needs no Oyzu configuration.

oyzu run list
oyzu run test
oyzu inspect dist

To use a different Ant target, replace the task:

[tasks.test]
argv = ["ant", "verify-contract"]
  • One literal ant <target> command is instrumented, including the equivalent literal shell form.
  • Compound shell commands and other replacements run unchanged and must write the required JUnit and JaCoCo reports themselves, at the paths in OYZU_TEST_REPORT and OYZU_COVERAGE_REPORT.
  • Extra arguments forwarded to the automatic reporting aren't supported and fail with an error.
  • Target-qualified names and pre and post hooks work as in the common task engine. A failed test skips its success-only post hook.
  • Discovery always provides an implicit test task. Without a test target in build.xml or a replacement, running it fails with Ant's missing-target error. Oyzu doesn't invent a test suite.

Prerequisites​

Install these before running:

  • a JDK with java and javac, with JAVA_HOME set (or both on PATH);
  • Ant, with ANT_HOME set to its folder;
  • JaCoCo, with JACOCO_HOME set to a folder containing jacocoant.jar and jacocoagent.jar;
  • your test libraries. JUnit projects need JUnit and Hamcrest in Ant's lib folder.

Oyzu compiles its own Java integration into a temporary folder and starts Ant with your platform's classpath separator. It doesn't install tools or download dependencies.

Reports and native behavior​

The manifest links JUnit results and JaCoCo coverage for your application.

  • JUnit suites keep individual tests and skipped cases.
  • Forked Java assertion programs produce one case per run. They need fork="true" and failonerror="true".
  • Coverage follows the src folder convention and the javac output that Oyzu observes. Test classes are excluded.
  • Builds without line debug data keep the instruction counters they have instead of inventing line coverage.
  • Other source layouts, alternate task implementations and the JUnit Platform need explicit reports.

Direct tests keep your project's version properties, run the target's compile prerequisites, and can update your build output. They don't package snapshots or run lint and format checks. oyzu build --full applies versions, runs the quality checks and collects JARs; add --isolated to run in a container.

A missing tool, a compile error, a failed test, a missing or invalid report, or an unmet coverage constraint fails the command. The reports available at that point stay in the failed bundle. Fix the cause and rerun. See direct tests for output handling and provenance. Direct tests run on your machine with your network and environment, so they aren't isolated.

Checking the bundle​

Run oyzu inspect dist after a build or a direct test run to check the bundle. A failed check, or a required report that is missing or invalid, fails the command, and the bundle keeps the reports that exist so you can see what happened.

Limits​

  • Captured builds run on Linux only.
  • Other source layouts and test frameworks need explicit reports.
