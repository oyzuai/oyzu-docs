Tool Java, Maven and Gradle Installation

CLI reference

Published from the canonical docs/reference/tool-java-installation.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Indexed installation and pinning use the organization catalog contract. A matching verified index record is preferred without a catalog; with one, only approved indexed releases install. The provider evidence command uses the same metadata adapter as installation. Linux ARM64 GNU joins the native host/lock matrix (Tailscale remains Linux-only); macOS amd64 and musl are excluded. See implementation status for automated verification. Live publisher evidence and native ARM64 qualification remain pending.

Oyzu can prepare a JDK, Maven and Gradle itself, so a fresh checkout of a Maven or Gradle project needs none of them installed. See tool management for shared prerequisites and native host builds for which projects use them.

Usage​

Pinning is optional. For a project the native Maven build supports, oyzu build resolves a JDK and Maven, writes oyzu.lock, installs them into the shared tool store and builds:

oyzu build            # no Java or Maven on PATH, no pin needed
oyzu pin --dry-run    # preview: oyzu:java 17 and oyzu:maven 3.9, with their sources
oyzu exec -- mvn -version

An explicit request in oyzu.toml takes precedence:

[tools]
java = "21"           # latest 21.x; "lts" (the default without a declared level) or "21.0.8"
maven = "3.9"         # latest 3.9.x; any Maven release range

How versions are chosen​

ToolRequestSource
JDKThe literal maven.compiler.release, maven.compiler.target, maven.compiler.source or java.version in the root POM (1.8 means 8), raised to 17 when lower; otherwise lts, the newest long-term-support release[tools] java overrides
Maven3.9, the conservative line, which supports Java 8 and newer[tools] maven overrides

A property that is not a literal number is treated as undeclared. The declared level is a floor, not a JDK to run: a project declaring release 21 gets a JDK 21 and not the newest one, while a project declaring 8, 9 or 11 gets JDK 17, the oldest release Maven, Gradle and Oyzu's Java integration run on. JDK 17 compiles those older levels faithfully (--release 8 checks against the Java 8 API). Gradle levels follow the same rule. The lock records the exact build.

The same selection runs isolated builds: preflight locks it and the captured worker restores that JDK instead of the image's (see Maven). An explicit [tools] java below 17 still installs for host use, but an isolated build refuses it with TOOL_UNSUPPORTED_VERSION, naming the selected JDK.

Sources and verification​

  • JDK: Eclipse Temurin through the Adoptium API (available_releases and the newest asset per feature release and platform). The API declares each archive's SHA-256; the archive is downloaded from the adoptium GitHub organization and verified against it.
  • Maven: the release index (the maven-3 and maven-4 directory listings), the archive and its SHA-512 sidecar all come from the Apache distribution server, the publisher of record, which does not throttle shared addresses the way Maven Central does. Pinning verifies the archive against the publisher's SHA-512 and records the SHA-256 of the verified bytes in the lock. The one archive serves every platform and is downloaded once per resolution.

Archive downloads are fetched in 2 MiB ranges, each with its own 45-second deadline, so a slow publisher server (Apache's archive has measured about 180 KB/s) slows a first build but does not time it out.

Digests come from the publisher, not a signature. Oyzu does not redistribute these archives. Administrative tools routes scoped to java, maven, oyzu:java, oyzu:maven or * use the same host connector bindings as Node and Go; there is no public fallback from a configured route.

  • Gradle: the release catalog at services.gradle.org/versions/all lists each release's distribution URL and SHA-256; the zip is downloaded (the publisher redirects to its GitHub release assets) and verified against that digest. One archive serves every platform. Defaults to Gradle 8, or 9 when the project declares a Java level above 24. A project with a committed gradlew provisions no Gradle: the wrapper downloads its own.

The installed JDK sets JAVA_HOME to its verified payload so no ambient JDK is used (on macOS the payload root is Contents/Home). Commands launched through shims are java, javac, mvn and gradle. A build task sees JAVA_HOME, MAVEN_HOME and GRADLE_HOME from the provisioned tools; an ambient value is never inherited, so a machine-wide JDK cannot change which Java a build uses.

Limits and verification​

  • The native build covers Maven reactors only when every jar's name can be read from the POMs: literal or inherited versions, jar packaging, no finalName or classifier. Otherwise the project keeps the isolated (Docker) path.
  • Ant is not native. Ant projects (build.xml) have no native host build: Oyzu does not provision Ant, and an arbitrary build.xml does not declare its jar outputs statically the way POMs and Gradle's model do. Without Docker, oyzu build refuses before doing any work, naming the oyzu-toolchain/ant image it needs and pointing to native host builds; with Docker and the image provisioned the isolated path builds it as before. Native Ant is deferred work.
  • Wrappers (mvnw, gradlew): a committed wrapper is run instead of mvn/gradle and Oyzu provisions only the JDK, exposed as JAVA_HOME. The wrapper downloads its own Maven or Gradle with its own tooling (the Maven wrapper in bin form needs only Java plus unzip or tar; the only-script form also needs curl or wget on PATH). That download is the wrapper's own transfer, not the Oyzu broker, so connector routes, credentials and Oyzu's digest verification do not apply to it; pin distributionSha256Sum in gradle-wrapper.properties or distributionSha256Sum in maven-wrapper.properties to verify it.
  • The native Gradle build uses Gradle's own model (an Oyzu-supplied init script reports each project's archive tasks and test tasks), runs gradle --no-daemon --console=plain build, publishes the model's jar and archive outputs and collects each tested project's JUnit XML. An archive kind Oyzu does not register is refused with a reason; same-named archives are qualified by project path. Quality stages share the Maven limitation below.
  • The build runs Maven's own verify, as the authored build task and the isolated path do, so tests run inside the build. Each module with test sources owes its Surefire XML from the default target/surefire-reports directory, shown as Tests N passed · M failed; a failing test fails the build with Maven's output and publishes no artifacts. The build also runs JaCoCo 0.8.13 (prepare-agent before verify, report after) and collects each tested module's target/site/jacoco/jacoco.xml as its coverage. A module whose POM declares maven-failsafe-plugin and whose test sources hold an IT*, *IT or *ITCase class also owes its target/failsafe-reports XML, collected as that module's integration tests. Custom report directories are not collected, and an authored build command supplies its own reports.
  • The native Gradle build applies the same Oyzu coverage init script as the isolated path (Gradle's JaCoCo plugin 0.8.13) and collects each tested project's JUnit results and build/reports/oyzu/<test task>/jacoco.xml. Gradle's own integration-test source sets are collected only when they are Test tasks Gradle's model reports. Coverage tooling is downloaded by Gradle or Maven from Maven Central, so a failed or throttled download fails the build; offline builds need those artifacts already cached. --full lint and format checks still require the separately provisioned quality tools (OYZU_JAVA_QUALITY_HOME, Java quality); the failure names Checkstyle and google-java-format, the provisioning command and the alternatives, and is proven by the fresh-checkout harness.
  • Maven on Windows uses mvn.cmd; this launcher and the Windows JDK zip are unverified.
  • Verified on Linux x86_64 only (2026-10-07): the java-maven-reactor fixture built both module jars from an empty store with no Java or Maven on PATH in about 90 seconds, most of it downloading a 193 MB JDK and Maven from Apache's slower distribution server, and its two tests ran and passed. The java-gradle-multi-project fixture built its three jars and ran its test (Gradle 8, JDK 17 from the declared level) in about 40 seconds from an empty store. Windows, macOS, offline restoration, connector/proxy routing and review of the licenses of the downloaded distributions are not verified. Maven itself still resolves dependencies from Maven Central, which can throttle shared addresses.
  • Pinning derives Java requirements for every Maven target, including projects that later use the isolated path.

See the fresh-checkout record.
