Java, Maven and Gradle installation

CLI reference

Published from the canonical docs/reference/tool-java-installation.md file. Features marked experimental remain experimental; check support limitations before relying on them.

oyzu can install a JDK, Maven and Gradle itself, so a fresh checkout of a Maven or Gradle project builds without any of them on the machine. See native host builds for which projects build this way.

Note: Supported on Linux x86-64 only.

Usage​

Pinning is optional. For a Maven project that builds natively, oyzu build picks a JDK and Maven, writes oyzu.lock, installs them into the shared tool store and builds:

oyzu build            # no Java or Maven on PATH, no pin needed
oyzu pin --dry-run    # preview: oyzu:java 17 and oyzu:maven 3.9, with where each came from
mvn -version

In an activated shell, which the install script sets up, the plain tool commands run the pinned versions. Where a shell isn't activated, prefix them with oyzu exec --.

To choose versions yourself, set them in oyzu.toml. This takes precedence:

[tools]
java = "21"           # latest 21.x; also "lts" or an exact "21.0.8"
maven = "3.9"         # latest 3.9.x; any Maven release range

How versions are chosen​

ToolDefaultOverride
JDKThe root Maven compiler floor described below, raised to 17 if lower. Otherwise a literal java.version default hint, or lts: the newest long-term-support release[tools] java
Maven3.9, which supports Java 8 and newer[tools] maven
GradleGradle 8, or Gradle 9 when the root script or native daemon criteria declares a Java level above 24[tools] gradle

For Maven, Oyzu reads direct root maven-compiler-plugin configuration and root maven.compiler.release, maven.compiler.source, maven.compiler.target and maven.compiler.testRelease properties. Configuration wins over its corresponding property; release then overrides both source and target. Without release, both source and target floors are retained. A separate testRelease floor is retained alongside the production compiler facts; their highest floor chooses the default JDK. For example, production release 17 with testRelease 25 selects JDK 25 or newer, while a lower test release does not lower the production requirement. Values must be literal Java levels (1.8 means 8). A configuration reference to its corresponding literal root property, such as ${maven.compiler.release}, also works. An invalid or unresolved winning value stops discovery instead of falling back to a lower level.

Literal release/testRelease configuration requires an explicit literal compiler-plugin 3.x version of at least 3.6. The plugin must have artifact ID maven-compiler-plugin and group org.apache.maven.plugins (or omit the group). Foreign literal groups are ignored; ambiguous identities and duplicate compiler entries are refused. Root java.version alone is a legacy default hint, not a compiler compatibility constraint: it can be overridden by [tools] java.

This is partial root discovery, not Maven's effective model. Relevant profiles, executions, other test-specific levels (testSource/testTarget), executable/toolchain/compiler overrides and configuration merge directives need native evaluation and stop inference with their location. Managed compiler parameters that could supply or mask a level also stop inference, even without a direct plugin declaration. Make the compiler parameters explicit in a supported root declaration to resolve the diagnostic. The main release does not shadow a managed testRelease; only a direct testRelease declaration makes that managed value irrelevant. An inherited=false compiler entry in a pom root without executions is inactive and supplies no module floor. Parent and module POMs are not evaluated here; existing literal root-property facts remain available for parent-based projects. Unknown or older release-configuration semantics and Maven 4 are outside this inference subset. Maven still owns its effective configuration and compilation.

The compiler level is a minimum, not the newest JDK: a project declaring 21 gets JDK 21. A project declaring 8, 9 or 11 gets JDK 17, the oldest JDK that Maven, Gradle and oyzu's Java support run on. JDK 17 still compiles for older levels correctly (--release 8 checks against the Java 8 API). Gradle projects follow the same rule. The lock records the exact versions.

Gradle's static startup requirements come only from the root script and native daemon JVM criteria. Native preparation checks the effective compiler providers of standard Java tasks in nested members; see Gradle compiler availability. Unregistered sibling scripts do not select the JDK.

Isolated (Docker) builds use the same locked JDK instead of the image's (see Maven). An explicit [tools] java below 17 still installs for use on your machine, but an isolated build refuses it with TOOL_UNSUPPORTED_VERSION.

Where the tools come from​

ToolSourceCheck
JDKEclipse Temurin, found through the Adoptium API and downloaded from the adoptium GitHub organizationSHA-256 published by the Adoptium API
MavenThe Apache distribution server (maven-3 and maven-4 listings)The publisher's SHA-512; the lock records the SHA-256 of the checked bytes
GradleThe catalog at services.gradle.org/versions/all; the zip is served from Gradle's GitHub releasesSHA-256 from the catalog

Maven and Gradle use one archive for every platform. Downloads are fetched in 2 MiB pieces, each with its own 45-second timeout, so a slow server makes the first build slower but doesn't make it fail. Checksums come from the publisher; no signatures are checked.

An administrator can route downloads through a corporate mirror with a tools route scoped to java, maven, oyzu:java, oyzu:maven or * (see proxy acquisition). When a route is set, oyzu never falls back to the public site. Under an organization tool catalog, only approved releases install.

Maven and Gradle dependency downloads use the JVM's trust configuration. Behind a TLS-inspecting proxy, add your organization's CA to a Java trust store that retains the public roots and select it with JAVA_TOOL_OPTIONS=-Djavax.net.ssl.trustStore=/path/to/company-cacerts. Oyzu's acquisition trust bundle configures Oyzu's own downloads; it does not replace the JVM's trust store. A native PKIX path building failed error needs the JVM trust configuration corrected before retrying.

What oyzu sets when Java runs​

  • JAVA_HOME points at the installed JDK (on macOS, its Contents/Home).
  • Build tasks see JAVA_HOME, MAVEN_HOME and GRADLE_HOME from the installed tools. Values already set on your machine are ignored, so a machine-wide JDK can't change which Java a build uses.
  • Shims are provided for java, javac, mvn and gradle.

Wrappers​

If the project commits mvnw or gradlew, oyzu runs the wrapper instead of mvn or gradle and installs only the JDK. The wrapper downloads its own Maven or Gradle:

  • The Maven wrapper in bin form needs Java plus unzip or tar. The only-script form also needs curl or wget on PATH.
  • That download is the wrapper's own, so oyzu's mirror routes, credentials and checksum checks don't apply. Set distributionSha256Sum in gradle-wrapper.properties or maven-wrapper.properties to have the wrapper verify it.

What a native Maven or Gradle build runs​

Maven runs verify, so tests run as part of the build.

  • Each module with Java sources under src/test/java must produce Surefire XML in target/surefire-reports. Results show as Tests N passed · M failed. A failing test fails the build and no artifacts are published.
  • Files under src/test/resources alone do not require Surefire or JaCoCo reports. Java files stored as resources do not count as test sources.
  • JaCoCo 0.8.13 runs around verify, and each tested module's target/site/jacoco/jacoco.xml is collected as coverage.
  • A module that declares maven-failsafe-plugin and has an IT*, *IT or *ITCase Java test class under src/test/java must also produce target/failsafe-reports, collected as integration tests.
  • Automatic host report discovery covers this conventional Java test directory. Custom test source roots and other JVM languages need an authored build task with explicit reports.
  • Custom report directories aren't collected. An authored build command supplies its own reports.

Gradle runs gradle --no-daemon --console=plain build. oyzu adds an init script that reads Gradle's own model to find each project's archive and test tasks. It publishes the jar and archive outputs, collects JUnit XML and build/reports/oyzu/<test task>/jacoco.xml (JaCoCo 0.8.13). Archive types oyzu doesn't recognize are refused with a reason. Archives with the same name are told apart by project path. Integration-test source sets are collected only when Gradle reports them as Test tasks.

Coverage tools are downloaded by Maven or Gradle from Maven Central, so a failed or throttled download fails the build, and offline builds need them cached. --full lint and format checks need Checkstyle and google-java-format provisioned separately (see Java quality); the error says how.

Limits​

  • Native Maven builds need every jar's name to be readable from the POMs: literal or inherited versions, jar packaging, no finalName or classifier. Other projects use the isolated (Docker) build.
  • Ant isn't built natively. oyzu doesn't install Ant. Without Docker, oyzu build stops before doing any work and says it needs the isolated Docker executor (see native host builds). With Docker and the base execution image, the isolated build works.
  • Maven still downloads your project's dependencies from Maven Central, which can throttle shared IP addresses.
  • Pinning records Java requirements for every Maven target, including ones that build in Docker.
  • Windows (including mvn.cmd and the Windows JDK zip) and macOS aren't supported yet.
