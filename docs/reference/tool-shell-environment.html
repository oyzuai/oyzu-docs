Using tools in your shell

CLI reference

Published from the canonical docs/reference/tool-shell-environment.md file. Features marked experimental remain experimental; check support limitations before relying on them.

This page covers the ways to put a project's locked tools on PATH outside oyzu run and oyzu build: a one-time oyzu env --shell, an activated shell that switches tools as you change directory, a shell profile block, and a shims folder for IDEs and scheduled jobs. It also lists the settings that control when tools install themselves on first use.

For the overall model (provenance, PATH views, nested shells), see shell activation.

Note: Activation and env --shell are supported in Bash and Zsh on Linux and macOS, and in PowerShell 7 on Windows. Writing a shell profile with oyzu shell install is supported for Bash and Zsh on Linux; macOS and PowerShell profiles are not supported yet.

Environment inspection and shell application​

oyzu env shows the selected tools' executables and the effective environment variables. oyzu env --json returns the same as JSON.

  • Credential-like fields and values that look sensitive are redacted.
  • Tools that aren't installed are left out; env never installs anything. Invalid locks, damaged install records and policy denials still fail.
  • The environment is the same one oyzu exec uses: the literal values from [env] in your configuration, plus the selected tools' folders added to the front of your PATH.

To apply the environment to your current shell once, pick a shell:

# Bash (use --shell zsh for Zsh)
eval "$(oyzu env --shell bash)"
node --version
oyzu env --shell pwsh | Out-String | Invoke-Expression
node --version
  • With --json, the code is returned in a script field next to the shell name.
  • No network access and no installs.
  • Values stay literal: quotes, dollar signs and shell metacharacters are escaped, never interpreted.
  • Values must be valid UTF-8.
  • If you installed into a shared store, pass the same --store here.

This changes the current shell once. It doesn't add a prompt hook, switch on cd or restore old values. Use activation for that.

Folder trust​

Activation, env --shell, prompt hooks, shims and oyzu exec only apply a project's [env] and PATH additions after you trust the project folder, because those values end up executed by your shell. An untrusted project still gets its selected tools, without those additions and without a prompt. oyzu env marks such entries skipped until trusted.

oyzu run, oyzu build and build planning always apply those settings.

oyzu exec​

oyzu exec -- COMMAND runs a command with the project's environment. Put Oyzu flags before --. By default the command's output passes straight through; with --json, Oyzu captures it in stdout and stderr fields next to exitCode.

Development shell activation​

Activate a Bash or Zsh session from a project with installed tools:

eval "$(oyzu activate bash)" # use zsh for Zsh
node --version
cd ../another-installed-project
node --version                # the other project's Node
oyzu deactivate

In PowerShell: oyzu activate pwsh | Out-String | Invoke-Expression.

  • --store /absolute/store uses a shared store. Without it, the default user store is used.
  • --root, --profile and --toolset given to activate stay in effect for the session.
  • On every prompt, Oyzu checks whether the directory, relevant environment variables or configuration and lock files changed. If nothing changed, it does nothing. If something changed, it applies the new project's locked tools and [env] values.
  • The prompt hook never uses the network, installs tools or runs project tasks.
  • cd alone never installs anything or writes a lock. Running a missing command may install it, depending on the invocation controls.
  • In PowerShell, missing-command installs only trigger for a command you typed in the interactive session, not for lookups inside scripts.

The prompt check looks at file metadata only. Installed tools aren't re-checked on each prompt: they were verified when installed and are trusted afterward. oyzu env can take longer than oyzu config show because it fully reads the selection.

When the selection fails or is incomplete​

  • Invalid configuration or a denied tool clears the previous project's changes, sets OYZU_TOOL_STATUS=unavailable and prints a message once.
  • Missing installations don't stop a valid environment from applying. OYZU_TOOL_STATUS=ready means the environment was composed, not that every tool is installed. Check with oyzu tools current.
  • A trusted project's PATH additions come before the selected tool folders.

Session records and deactivation​

Oyzu saves what it changed in a private per-user shell-sessions folder so oyzu deactivate can undo it. The shell holds only a random token.

  • On Unix the folder is private (0700) and linked directories are refused. On Windows it lives under your LocalAppData and reparse points are refused.
  • oyzu deactivate restores a variable only if it still has the value Oyzu set, so your own edits survive. An unchanged PATH is restored exactly. Entries Oyzu added are removed even if you added or reordered others; ambiguous duplicates are kept with a message.
  • oyzu --json deactivate only previews; the session stays active.
  • If the record is missing or unreadable, you get a warning and the hooks are removed, but old values can't be recovered. Open a new terminal or activate again.
  • Activation cleans up records at most once a day: a record older than a day whose shell has exited, and any record unused for a week. An open shell marks its record as in use at its first prompt each day, so a terminal left without a prompt for more than a week loses its record; activate it again.
  • Activation adds the Oyzu executable's folder to PATH if it isn't there. That entry stays after deactivation.

The oyzu shell function that activation defines evaluates the output of oyzu deactivate for you. Running the binary by full path with deactivate only prints the code. Global flags such as oyzu -q deactivate work. --log-level and -q can't be combined; a rejected command leaves the session active.

Set up all shells and PATH​

oyzu shell install with no shell is the machine-level setup that the install scripts run. It does not install tools or use the network. It edits, once:

  • the activation block of each supported shell found: bash (login shell, or ~/.bashrc or ~/.bash_profile exists, including Git Bash on Windows), zsh (login shell, or $ZDOTDIR/.zshrc or ~/.zshrc exists) and PowerShell 7 (when pwsh is on PATH or in %ProgramFiles%\PowerShell\7);
  • the persistent PATH, with the fixed shims folder (STORE/shims/bin, refreshed first as oyzu reshim does) ahead of the folder holding the running oyzu. On Windows that is the user Path value in HKCU\Environment: entries such as %USERPROFILE%\bin keep their raw spelling, the value kind is kept (REG_EXPAND_SZ for a new value), entries already present are not duplicated (compared after expanding variables, ignoring case and a trailing separator) and WM_SETTINGCHANGE is broadcast so programs started afterwards, such as IDEs, see it. On Linux and macOS it is a marked PATH block in the login profile: the first existing of ~/.bash_profile, ~/.bash_login and ~/.profile (~/.profile when none exists), and $ZDOTDIR/.zprofile or ~/.zprofile when zsh is set up.

oyzu shell remove with no shell reverses it: it removes intact blocks from those files and the two folders from the user Path, and leaves other content. Only entries spelled exactly as install wrote them (the running oyzu and its store folders) are removed, so entries added by an oyzu installed in another location, and your own %USERPROFILE%\bin-style spelling of a folder, stay. A block that was edited is refused as below. Reports list each file or the registry value under entries with changed. Windows PowerShell 5.1 and fish are not configured. Programs already running keep the PATH they started with.

Checked by unit tests for planning, PATH list editing and (on Linux) install, repeat and remove over a temporary home, a unit test of the registry code on a scratch key, and the compiled CLI on Windows. macOS and fish are not checked.

Install activation in a shell profile​

oyzu activate never edits files. To activate in every new shell, add a block to your startup file:

oyzu shell install bash
oyzu shell remove bash --rc-file ~/.bashrc
oyzu shell install pwsh --rc-file $PROFILE
oyzu shell remove pwsh --rc-file $PROFILE

Default startup files:

ShellDefault
bash~/.bashrc
zsh$ZDOTDIR/.zshrc, or ~/.zshrc
pwshPowerShell 7's current-user console profile: Documents/PowerShell/Microsoft.PowerShell_profile.ps1 on Windows, $XDG_CONFIG_HOME/powershell/Microsoft.PowerShell_profile.ps1 on Unix (falling back to ~/.config/powershell/...)
  • --rc-file PATH picks another file. A relative path resolves against the current directory (or -C). For another PowerShell host or version, pass --rc-file $PROFILE.
  • The global --profile option selects an Oyzu configuration profile, not a shell file.
  • Oyzu creates missing folders and files, appends one marked block and leaves the rest of the file and its permissions unchanged.
  • The block calls the oyzu executable by its full path. If you move or upgrade it, run oyzu shell install again to update the block. Running it again with the same executable changes nothing.
  • If activation fails when a shell starts (for example, a configuration file can't be read), oyzu prints the error and the rest of the startup file still runs. The PowerShell block runs the activation code only when oyzu activate printed some.
  • The block uses the default store and configuration. It doesn't include a project, profile, credentials or store path. For a custom store, add your own oyzu activate <shell> --store PATH line outside the block.
  • Install the project's tools before opening a new shell. Editing the profile itself uses no network.
  • --json reports changed, shell, profile_path, installed, shims, activation, check and nextStep.

Install and remove refuse a block that is modified, incomplete, duplicated or written by a different oyzu. Fix or restore the block by hand first. A symlinked profile needs the real target path, and a non-UTF-8 profile must be converted first.

oyzu shell remove deletes only the intact block and leaves the rest of the file byte for byte. A file Oyzu created stays as an empty file. Removing the block affects new shells; run oyzu deactivate to end the current session.

Native executable shims​

oyzu install and oyzu activate create a launcher (shim) for every command of every installed tool, including companions such as npm, npx, kubectl and helm. Each shim works out the project, configuration and lock from the directory it runs in.

  • On Unix, shims are symbolic links to oyzu.
  • On Windows, oyzu-shim.exe is a small launcher that delegates tool execution to oyzu.exe. Install or copy both into the same folder. Published shims find the frontend through the adjacent .oyzu-frontend pointer; a launcher without a pointer looks for oyzu.exe beside itself. If that frontend is missing or invalid, restore the pair and run oyzu reshim.
  • Shims for activated shells live under STORE/shims/native/. Run oyzu install, oyzu activate or oyzu reshim to refresh them; oyzu install also refreshes shims in already activated shells, so newly installed commands appear there.
  • A shim keeps the command's arguments, exit status and signals unchanged.
  • On Windows x64 in PowerShell 7 and CMD, both fixed-folder and activated-session exe shims let the foreground child handle Ctrl-C. A handler that exits 42 reports 42; an unhandled Ctrl-C reports Windows -1073741510 (0xC000013A). The prompt returns after the child exits, and Oyzu closes its owned child job. These are console statuses, not Unix signal conversions.
  • A tool can call another shim (for example, a Node script starting another Node process); each call selects its tool again.
  • Prompt hooks don't create shims. Oyzu doesn't delete old shim folders automatically, since running shells may still use them.

The shims folder (no activation)​

IDEs, CI jobs and scheduled tasks never run a prompt hook. For them, put the store's shims folder on PATH. It holds one launcher for each installed command, and each launcher picks the right tool for the project it runs in:

oyzu reshim                                              # refresh launchers and print the folder
eval "$(oyzu activate bash --shims)"                     # put it first on PATH in this shell
oyzu shell install bash --shims --rc-file ~/.bash_profile
oyzu shell install zsh --shims --rc-file ~/.zprofile

On Windows, add it to your user PATH:

$shims = (oyzu reshim --json | ConvertFrom-Json).directory
[Environment]::SetEnvironmentVariable('Path', "$shims;" + [Environment]::GetEnvironmentVariable('Path', 'User'), 'User')
  • The folder is STORE/shims/bin.
  • The PATH line removes any existing copy of the folder and puts it first, so an unmanaged copy of a tool earlier on PATH can't win.
  • A store path containing the PATH separator (:, or ; on Windows) fails with SHIMS_PATH_INVALID.
  • On Windows, Bash and Zsh lines use Git Bash or MSYS/Cygwin path spelling (/c/Users/...). Generate Cygwin profiles from inside Cygwin.
  • activate --shims only prints the PATH line. Run oyzu reshim once first, and again after moving or upgrading oyzu. shell install --shims runs that refresh for you.
  • If a shim has no selected tool, it falls back to the next matching command on PATH, unless you turn that off (see invocation controls).

oyzu reshim refreshes the shims folder and the activation shims owned by the running oyzu, using local install records only. It downloads nothing and edits no startup file. --json reports the folder as directory and the command names as commands. On Windows, run it after updating both executables.

Invocation controls​

These settings control when a tool installs itself the first time you use it. They go in the usual configuration files (including profiles), and administrators can constrain them. The values shown are the defaults:

[settings]
auto_install = true
offline = false
exec_auto_install = true
not_found_auto_install = true
not_found_auto_install_registry = false
not_found_system_fallback = true
auto_install_disable_tools = []
windows_executable_extensions = ["exe", "bat", "cmd", "com", "ps1", "vbs"]
windows_shim_mode = "exe"

[settings.task]
run_auto_install = true
SettingMeaning
auto_installMaster switch. false turns off the exec, missing-command and task installs below.
offlineUse only cached downloads; never fetch. Same as oyzu exec --offline.
exec_auto_installoyzu exec installs configured tools that are missing.
not_found_auto_installA shim, or a command your shell couldn't find, installs its configured tool.
not_found_auto_install_registryA command the shell couldn't find, and that no configuration declares, is looked up in Oyzu's tool list, installed and added to your global configuration as latest.
not_found_system_fallbackA shim with no selected tool runs the next matching command on PATH.
auto_install_disable_toolsTools (short or full IDs) that never install themselves. oyzu install still works for them.
windows_executable_extensionsExtensions treated as executable on Windows.
windows_shim_modeHow shims are created on Windows (below).
task.run_auto_installoyzu run installs missing tools for the task.

How they behave:

  • A compatible lock entry always wins. Running a command never upgrades a locked version, and a missing locked tool isn't replaced by another installed version.
  • In a project with no compatible lock entry, shells, exec, tasks, env and which can reuse a matching version you already installed. This writes no lock.
  • A command may create a missing lock when it installs a configured tool.
  • With not_found_auto_install_registry, a name that matches more than one tool is skipped. A project declaration still overrides the global entry. Progress goes to stderr, so the command's stdout is unchanged.
  • To make unresolved shims fail instead of running a system command, set both not_found_system_fallback and not_found_auto_install to false. Fallback skips Oyzu shim folders and keeps PATH order.
  • A failed install, invalid lock, denied tool or unavailable managed integration is an error. It never silently falls back to a system command.
  • Prompt hooks, env, which and oyzu build --plan never install tools. which shows the selected tool; a shim on PATH doesn't mean the tool is installed.
  • oyzu build ignores these settings. It requires the full locked selection, and never accepts a system command in place of a locked tool or a denied tool.

Which tools a build prepares​

For each target, oyzu build prepares the tools its builder needs for the selected steps, plus the tools pinned in the oyzu.toml files from the project root down to that target's folder. A root pin reaches every target; a pin in docs-site/ reaches only targets in that folder. So oyzu build cli doesn't download a tool only docs uses. oyzu exec, shells and oyzu install still provide every pinned tool. Host prerequisites are checked, never installed.

Commands with several providers​

  • Node provides node, npm and npx. A separately configured npm takes over npm and npx.
  • On Windows, PATH lookup follows PATHEXT order. PowerShell and VBScript files run with their own interpreters. Bare bash and sh resolve to Git for Windows; WindowsApps aliases are skipped.
  • Unix commands get interrupts forwarded and keep terminal control. --json reports the numeric exit status.

Windows shim modes​

windows_shim_modeBehavior
exeA small native launcher (oyzu-shim.exe) per command, delegating to the frontend with native arguments and exit status. Default.
hardlinkHard links to oyzu. Needs a filesystem that supports them, on the same volume.
symlinkSymbolic links to oyzu. Needs symlink permission (usually Developer Mode).
fileCMD and Git Bash forwarder scripts. CMD's own rules apply: PowerShell's default argument passing can change empty arguments and embedded quotes, and delayed expansion changes ^ and !.

After changing the mode, run oyzu reshim (with the same --store). If the mode isn't available (missing permission or unsupported filesystem), Oyzu reports it instead of picking another mode. Other platforms always use symbolic links.
