Tool Shell Environment

CLI reference

Published from the canonical docs/reference/tool-shell-environment.md file. Features marked experimental remain experimental; check support limitations before relying on them.

See tool management for shared prerequisites, command conventions and qualification limits.

Environment inspection and shell application​

oyzu env and oyzu env --json inspect available selected installations and report selected executables and effective environment variables. Ordinary values are visible; credential-like fields and detected sensitive values are redacted. See shell activation for provenance and PATH views. Missing tools are omitted without installation; invalid locks, corrupt receipts and enforced denials retain their errors. Explicit project pins and commands with no configured tools do not read unrelated remembered developer selections. Those snapshots are loaded and validated only when an unpinned requirement actually needs installed-selection fallback. An invalid remembered snapshot still fails that fallback; it is never accepted as a usable pin or silently deleted. The environment composition is shared with exec: literal TOML values plus the selected binary directory prepended to inherited PATH. An already leading selected directory is not prepended again. exec --json captures application output in stdout and stderr fields alongside exitCode; default execution passes the streams through. Place Oyzu flags before the child argument separator --.

To explicitly print assignments with their actual values, select a shell:

# Bash
eval "$(oyzu env --shell bash)"
node --version

For Zsh use --shell zsh. For PowerShell 7 use:

oyzu env --shell pwsh | Out-String | Invoke-Expression
node --version

--shell with --json returns the rendered code in a script field alongside the shell name. Without --json, code remains directly evaluable. See the CLI output contract. Environment patches use the extracted mise diff operations in the internal oyzu-shell library. Bash, Zsh and PowerShell rendering run directly through that library, without initializing a mise backend worker. Windows POSIX path normalization retains the pinned upstream utility. It performs no network or installation. Values remain literal, including quotes, dollar signs and shell metacharacters; they are not interpreted as config code. Shell activation (including env --shell), prompt hooks, shims and oyzu exec require project/local environment and PATH additions to pass folder trust: environment consumers can interpret literal values as executable instructions. Untrusted projects keep their selected tools and skip those additions without prompting. oyzu run, oyzu build, build planning and the build configuration digest always retain those settings. oyzu env shows configured values and provenance, marking project entries skipped until trusted when shell/exec use would withhold them. PowerShell literals escape ASCII apostrophes and all four Unicode single-quote delimiters, including values and frontend/profile/shim paths. Rendering requires UTF-8 environment values. Pass the same --store used for installation when using a shared store.

This is a one-time application to the current shell. It does not install prompt hooks, automatically switch on directory changes or restore old values. Use the activation commands below when testing automatic transitions instead. The lookup/rendering lease ends when the command returns; this does not establish an active-shell retention lease. Those lifecycle capabilities remain unfinished.

Development shell activation​

From an installed project, start a session in Bash or Zsh:

eval "$(oyzu activate bash)" # use zsh for Zsh
node --version
cd ../another-installed-project
node --version
oyzu deactivate

For a shared store, pass --store /absolute/store to activate. Without that option each hook uses the default user-level store. Root/profile options from activation are retained for the session. The PowerShell equivalent is oyzu activate pwsh | Out-String | Invoke-Expression. The original PowerShell activation/switching/deactivation scenario passed on Windows at 83049fa in run 37050580618; native acceptance with the newly added shims remains pending.

The internal oyzu-shell library renders Bash, Zsh and PowerShell prompt/directory hooks and deactivation using extracted mise mechanics. Oyzu adapts the generated namespace before inserting the real frontend path through the renderer's literal quoting. The hooks call this same Oyzu binary, never a separate mise executable. A missing command may install its configured provider on invocation, subject to the controls below. The shell retries with the refreshed environment. Prompt/directory hooks use read-only local selection, with no network, installation or project task execution. PowerShell missing-command acquisition requires the command name to appear as a token in the initialized PSReadLine session's latest typed line, matching Mise; noninteractive script lookups do not trigger that hook's installation path. Explicit exec/tasks and already invoked native shims retain their separate invocation controls. Changing directories applies the new project's locked Node and literal TOML environment. Unchanged selection emits no environment changes.

Unchanged prompts compare the working directory, relevant environment inputs and source/lock metadata before resolving configuration or reading lock contents. Creation and deletion of sources also invalidate the cached selection, including changes to the user's trusted-project records. Installed executables, payloads and receipts are not watched or hashed: installation verifies them once, and subsequent use trusts the installation. The hook observes each prompt without a time-to-live delay or background service. Old records without freshness data refresh once. Unreadable inputs force resolution. Failed selection still clears the previous environment and reports unavailable.

This is prompt freshness, not an integrity cache: metadata checks do not detect all hostile/backdated content edits. exec, shim dispatch, tasks and builds continue obtaining verified leases. oyzu env also retains verified inspection; it can take longer than config show. Neither consumes a prompt cache as execution authority. The embedded mise revision is part of backend identity; after changing it, refresh pins and install through oyzu pin --refresh and oyzu install, never by rewriting receipts.

Oyzu records changed variable values and PATH under its native per-user state directory's shell-sessions folder; the environment carries a random token. Unix directories are private (0700), with ownership and ancestor protection checked; linked directories are rejected. Windows uses the user's LocalAppData state directory and rejects reparse points. Session files are atomically replaced. Deactivation removes the record after rendering cleanup; JSON deactivation is a preview and retains the record. Missing or unreadable records produce a warning and hook/marker cleanup, while shims fall back to ordinary configuration options. Values from a lost record cannot be reconstructed: open a new terminal for a clean environment, or activate again to begin a fresh session. On activation, records older than 30 days are reclaimed only when their shell is gone (or the activation was never consumed); records belonging to live shells are retained. Scalars are restored only when they still equal the value Oyzu applied, preserving user edits. An unchanged PATH is restored exactly. On Windows POSIX shells, restoration preserves the saved mount spelling when its ordered native entries match the rolled-back PATH (for example, /bin versus /usr/bin in Git Bash). This spelling restoration never replaces a changed list of paths. Compiled-CLI Git Bash qualification passed as recorded in the extraction audit. Unique owned entries can be removed after user additions or reordering; ambiguous duplicates are retained with a diagnostic.

Invalid configuration or denied selection clears the preceding project's delta, sets OYZU_TOOL_STATUS=unavailable and emits a diagnostic once per changed failure. Missing installations alone do not prevent applying a valid environment: existing selected executable directories lead the native shim fallback and inherited PATH. Trusted project PATH prepends precede selected tool directories, matching Mise; controlled build preparation retains tool directories first. The status ready describes a composed environment, not proof that every tool is installed. Use oyzu tools current to inspect availability. A command may install its configured provider when invoked; cd alone never installs or writes a lock. Deactivation removes the session's PATH insertion and restores the previous environment.

Install activation in a shell profile​

Profile editing is explicit; activate alone never edits a file. Choose the profile your shell loads, or use the default:

oyzu shell install bash
oyzu shell remove bash --rc-file ~/.bashrc

Use zsh with your .zshrc, or PowerShell:

oyzu shell install pwsh --rc-file $PROFILE
oyzu shell remove pwsh --rc-file $PROFILE

--rc-file PATH selects a shell startup file; the old --profile-path spelling remains a hidden alias. Global --profile NAME still selects an Oyzu configuration profile and never selects a shell startup file. Without --rc-file, Bash uses ~/.bashrc, Zsh uses $ZDOTDIR/.zshrc or ~/.zshrc, and PowerShell 7 uses its current-user console profile: the Windows Documents known folder followed by PowerShell/Microsoft.PowerShell_profile.ps1, or $XDG_CONFIG_HOME/powershell/Microsoft.PowerShell_profile.ps1 on Unix (fallback ~/.config/powershell/Microsoft.PowerShell_profile.ps1). For another PowerShell host or version, pass --rc-file $PROFILE. Override roots must be absolute.

An explicit relative path resolves against -C/the invocation directory. Oyzu creates missing parent directories and files, appends one marked block, and preserves surrounding UTF-8 content and existing permissions. The block invokes the absolute running Oyzu frontend with shell-specific quoting. Keep that frontend available; rerunning installation after moving/upgrading it replaces an intact block. Repeated installation with the same frontend is a no-op. Success explains how to open a new terminal or activate this one, and suggests oyzu which cargo (substitute another installed command) to inspect selection. --json reports changed, shell, profile_path, installed, shims, activation, check and nextStep.

The block uses ordinary activation defaults: the shared user tool store and configuration at shell startup. Install the project's locked tools before opening a new shell. It does not embed a project, profile selection, credentials or shared store path. Shell profile editing itself performs no networking or activation. To use an explicit store (oyzu activate <shell> --store PATH) or custom activation options, keep a separately maintained initialization command outside the managed block. oyzu tools list --json reports the effective store; pass the same --store to installation, inspection and activation when overriding the default.

Installation/removal refuses modified, incomplete, duplicate or differently owned blocks. Preserve any manual customization elsewhere and restore/reconcile the managed block before retrying. Symlink profiles require the explicit real target; non-UTF-8 profiles require conversion before use. Removal deletes only the intact block, including its inserted separator, preserving surrounding content byte for byte. A newly created profile remains as an empty file after removal. Removing the block affects future loads; run oyzu deactivate to end the current active session.

The real acceptance runner installs Node, loads each managed profile in its shell, executes the locked Node through its shim, deactivates, and checks idempotence, edited-block preservation and byte-exact removal:

python tooling/test-shell-profile.py --cli PATH_TO_FEATURE_ENABLED_OYZU --shell bash --shell zsh

Use --shell pwsh for PowerShell. The runner requires public Node access for its fresh installation and never edits the user's actual shell profile. Linux Bash and Zsh passed this complete flow on 2026-10-02. Native macOS and PowerShell profile acceptance remain pending in the three-host CI workflow.

Native executable shims​

Install and activation provision launchers for every command recorded by installed tools, including pnpm, kubectl, Helm and interpreter companion commands. Windows requires oyzu-shim.exe beside oyzu.exe; build/install both binaries. Its upstream-derived entry point calls the shared Oyzu execution library directly, preserving native arguments, exit status, invocation selection and installation leases without starting another oyzu process. The launcher is consequently larger than the earlier forwarding-only image. Windows defaults to one native image per release per shim directory, shared through internal hardlinks (copies when unavailable). Unix uses symbolic links to Oyzu. Windows also supports the configured publication modes below.

Shims live in STORE/shims/native/FRONTEND_PATH_ID/shared or .../cwd, shared by shell sessions. An adjacent pointer records the owning frontend; per-command manifests record the command, publication release and store mode. These are version-1 local records, not lock identities. Rebuilding at the same frontend path reuses the location. Run install or activate to refresh launchers. Missing companion executables fail explicitly. The main package currently builds both Cargo binaries on every platform; Unix uses links and does not need the companion to dispatch tools.

Dispatch validates the manifest/name and Unix link target, without reading or hashing launcher contents. Publication hashes its source image once, serializes writers, atomically replaces changed metadata and leaves identical records alone. On Windows, publication retries transient access/sharing failures for up to one second while readers finish. Readers continue to see complete records; publication never removes the old metadata first. A persistent failure is still reported. On Windows an executing launcher is renamed aside before replacement; a later refresh reclaims retired images once processes release them. Install also refreshes existing activation launchers, so newly installed commands become available in an already activated shell.

A shim resolves the current directory, configuration and lock, and retains verified installation leases. --store chooses a fixed store; otherwise the shared user store is selected. Active root/profile/toolset options come from the session. Outside a session, default configuration selection applies. Invocation-time acquisition uses the controls below and the existing verified installer. After selecting a verified installed tool, execution clears the private frontend recursion markers from that native child's environment. A tool may therefore invoke the same shim again (for example, a Node script launching another managed Node process), with fresh invocation selection and the nested command's exit status preserved. The Windows launcher's checks still reject an actual dispatch loop before tool selection. Resolved system and explicit-path children also have private dispatch markers removed, so nested commands can enter their own shim normally. Prompt hooks do not provision shims. Old full-image shim/session directories are not automatically deleted, since existing shell references must be preserved; reactivate old shells and clean only identified unused or byte-identical data.

The generated oyzu shell function evaluates deactivation output. Invoking the absolute binary with deactivate only prints it. No profile file is modified. Leading global flags such as oyzu -q deactivate are supported. Options taking values retain their original order; lifecycle commands use the frontend that activated the session even when another oyzu is on PATH. As with the bare CLI, --log-level and -q are incompatible: a rejected invocation leaves the session active. Use oyzu --log-level error -C /project deactivate or oyzu -q deactivate. --json deactivation is a preview: the wrapper prints the JSON without evaluating it and the active session record remains available. Run oyzu deactivate to apply the restoration and end the session. Help and failed commands are never evaluated. Environment-only and nested-shell activation are described in the shell activation reference. Active-shell installation retention and fully reversible PATH alignment remain unfinished. Profile installation/removal is explicit as described above. This is a controlled development integration.

The real Linux Bash/Zsh acceptance passed with networking disabled: activation, automatic cd switching between Node 22.15.0 and 22.14.0, unchanged-hook output, missing-selection cleanup, user-edited scalar preservation and deactivation. The subsequent native-shim replay also passed on Linux Bash/Zsh, including literal arguments and exit status. A direct offline probe put a real Node later on PATH and confirmed the former restrictive missing-selection behavior. That historical contract is superseded by issue #424; see the current invocation controls below. Native macOS and Windows native shim acceptance passed at e335d70 in CI run 37051685318, including their native activation/switching flows. Run it against the retained two-project workspace:

python tooling/test-tool-activation.py --cli PATH_TO_FEATURE_ENABLED_OYZU --workspace PATH --shell bash --shell zsh

Linux Bash and Zsh application passed with networking disabled on 2026-10-02: the shell launched the same Node executable as exec, literal metacharacters were preserved, inspection values were redacted and the lock was unchanged. PowerShell environment application passed on Windows at 3eefcc2 in CI run 37049209850; macOS Bash/Zsh environment application passed at e335d70 in run 37051685318. Reproduce against a retained acceptance workspace with Python 3.11+:

python tooling/test-tool-environment.py --cli PATH_TO_FEATURE_ENABLED_OYZU --workspace PATH --shell bash --shell zsh

Use --shell pwsh to require the real PowerShell interpreter. Requested shells must be installed; the runner does not skip a missing interpreter.

Tool-only directories do not require a native build manifest to select already pinned tools. Portable-lock lookup uses optional native discovery: present project manifests and explicit build declarations are still validated. Build and task commands retain their normal project-discovery requirements. Qualification of this extraction fix is tracked in the audit.

The shims folder (no activation)​

Non-interactive processes such as IDEs, CI jobs and scheduled tasks never run a prompt hook. For them, put the store's shims folder on PATH. It holds one launcher for each command of each installed tool, and each launcher resolves the project it runs in on every call, exactly as activation's shims do:

oyzu reshim                                              # refresh launchers and print the fixed folder
eval "$(oyzu activate bash --shims)"                     # put it first on PATH in this shell
oyzu shell install bash --shims --rc-file ~/.bash_profile
oyzu shell install zsh --shims --rc-file ~/.zprofile

The folder is STORE/shims/bin. The PATH line removes any copy of the folder already on PATH and puts it first, so an unmanaged copy of a tool earlier on PATH cannot win, and an empty PATH gains no empty (current-directory) entry. A store whose path contains the PATH separator (; on Windows, : elsewhere) is refused with SHIMS_PATH_INVALID, because on PATH it would split into other entries. Windows Bash/Zsh lines use the active MSYS/Cygwin mount mapping; when generated from a native terminal they use Git Bash drive spelling such as /c/Users/.... The rendered path is checked against : as well, so a Windows drive cannot create a relative C entry. Generate Cygwin profiles inside Cygwin to retain its mount table. Each launcher keeps its tool's command name exactly, .exe included. oyzu install keeps it current when it exists and belongs to the same Oyzu frontend; oyzu reshim refreshes it and makes the running frontend its owner. A launcher without a usable selected command searches eligible non-shim PATH entries by default; the strict setting below disables that fallback.

activate --shims only emits PATH code: it does not inspect installations or republish metadata at shell startup. Run oyzu reshim once before using that mode and after moving/upgrading the frontend. shell install --shims performs that initial refresh when it writes the profile.

On Windows, put the folder on your user PATH so every new process finds it:

$shims = (oyzu reshim --json | ConvertFrom-Json).directory
[Environment]::SetEnvironmentVariable('Path', "$shims;" + [Environment]::GetEnvironmentVariable('Path', 'User'), 'User')

oyzu-shim.exe must sit beside oyzu.exe; copy both when installing a build.

oyzu reshim also refreshes existing shims/native/FRONTEND_PATH_ID/cwd and shared activation launchers owned by the running frontend. Use it after updating both Windows binaries so an already activated shell can use the new launcher. It does not edit startup files or change the parent shell's PATH. --store PATH selects a store; otherwise the normal store selection applies. --json reports the fixed folder as directory and the recorded installed command names as commands. Refresh uses local installation records without acquiring tools; missing Windows launcher templates and publication failures return an error.

The shim refresh command is top-level reshim; the former shell shims spelling is removed without an alias. shell contains profile install and remove only.

Invocation controls​

Activation adds the Oyzu executable's directory if it is absent from PATH, matching Mise when activation is called by absolute path. That directory remains after deactivation; project tool directories and environment changes are restored.

Installation records a validated selection snapshot in the store's developer-selections directory. Developer shell/exec/task preparation and env/which inspection can reuse matching installed versions in a project without a compatible pin, through the same provider selector and verified receipt lease. This does not write a project lock. An existing compatible pin always wins; a missing pinned payload cannot be replaced with another stored version. Equivalent installed records from different selectors can be reused when their host artifacts, layout, verification and dependency facts agree; differing recipes remain ambiguous and require an explicit pin. Controlled builds continue through their admitted locked preparation. Older stores can record these reusable facts by running an explicit oyzu install; directory/prompt refresh does not upgrade store metadata or acquire tools.

Standalone developer commands follow the pinned Mise v2026.10.10 reference. Configure the controls through Oyzu's typed cascade, including profiles and administrative constraints:

[settings]
auto_install = true
offline = false
exec_auto_install = true
not_found_auto_install = true
not_found_auto_install_registry = false
not_found_system_fallback = true
auto_install_disable_tools = []
windows_executable_extensions = ["exe", "bat", "cmd", "com", "ps1", "vbs"]
windows_shim_mode = "exe"

[settings.task]
run_auto_install = true

The shown values are defaults. auto_install = false disables the subordinate exec, missing-command and task mechanisms. exec_auto_install prepares the configured exec environment; not_found_auto_install prepares the provider of an invoked shim or a command the shell could not find. The disabled-tool list accepts short or canonical Oyzu tool IDs and leaves explicit oyzu install available. Direct tasks use task.run_auto_install; controlled build preflight continues requiring its complete locked selection regardless of developer toggles.

Registry installation stays off by default. When enabled, a shell missing-command hook requires a unique advertised provider and uses the existing global declaration transaction to install and record it. Ambiguous names are skipped. Project declarations override the resulting global selector through the shared configuration cascade, including when the project uses a different admitted alias. Like Mise, this operation prefers the highest compatible installed version and retains latest as the global selector. Unlike Mise's extra stdout config status line, Oyzu keeps status/progress on stderr and leaves child stdout unchanged. The maintainer approved this narrow difference on 2026-10-14 so command substitution and machine consumers do not need to filter prose from native output. An already intercepted stale shim does not invoke registry discovery, matching the pinned Mise behavior; configured-provider installation remains available through either entry point. Registry support is limited to Oyzu's admitted provider catalog; broader upstream backends remain unqualified rather than implicitly authorizing another installer.

not_found_system_fallback controls shim fallback, not ordinary oyzu exec PATH lookup. To make unresolved shims fail, set it and not_found_auto_install to false. Lookup skips Oyzu shim farms and retains PATH order. A failed admitted installation, invalid lock/receipt, denied tool or unavailable managed integration is an error; it is not silently converted into ambient execution. oyzu exec --offline or settings.offline = true can use admitted cached bytes but cannot download missing inputs.

Node supplies bundled node, npm and npx; a configured separate npm owns npm and npx ahead of that bundle. Companion scripts use the selected Node interpreter. Separate npm installations include digest-bound native shell companions for ordinary activation. Windows developer PATH lookup uses native PATHEXT order, matching the pinned Mise implementation's which lookup even when windows_executable_extensions lists a different order. Receipt-recorded managed commands retain their exact executable/interpreter descriptions. PowerShell/VBScript use their native interpreters; Rust's native process API owns batch argument encoding. Bare bash/sh on Windows select native Git for Windows shells. WindowsApps aliases on inherited PATH are excluded even when the invocation uses a disposable HOME/AppData directory, keeping selected Windows tools available to that shell. Native Windows qualification found that Mise v2026.10.10 does not resolve an unmanaged bare .ps1 command. The maintainer approved Oyzu's native PowerShell execution as an explicit exception; see the qualification record below.

windows_shim_mode selects publication on Windows. exe is the default native launcher; hardlink links each command to the frontend and requires a compatible filesystem on the same volume; symlink links to the frontend and requires Windows symlink permission (typically Developer Mode); file publishes CMD and Git Bash forwarders. File forwarders call the private native shim entry point, which owns selection and execution, and recover native arguments from a dedicated CMD /c invocation. Interactive CMD and batch call retain their shell argument semantics. PowerShell's default Windows argument-passing mode uses legacy rendering for CMD files, which can change empty arguments and embedded quotes before dispatch. Direct CMD file forwarding applies delayed expansion, which changes caret and exclamation characters, matching the pinned Mise file-mode oracle. The differential runner also exercises Standard argument passing explicitly. No mode starts the public oyzu exec command. Other hosts retain their native symlink publication. The setting uses the regular configuration/profile cascade; rerun oyzu reshim --store PATH to replace the publication mode in the fixed farm and existing activation farms owned by this frontend. Publication reports unavailable link permissions/filesystems without silently choosing a different mode. Native qualification is recorded in the linked report.

An invocation may create a missing configured lock or materialize a newer admitted companion layout at the same exact selected version. It never upgrades a compatible pin merely to run a command. Prompt/directory refresh, env, which, and build --plan never acquire tools. which remains selected-receipt inspection; a shell finding a shim does not prove that the selected tool is installed. A build prepares, per selected target, the tools its builder detects for the selected stages plus the tools pinned in that target's folder oyzu.toml chain (a root pin reaches every target; a pin in docs-site/ reaches only targets at or below it). Targets sharing a folder share its pins. Pins elsewhere are not prepared, so oyzu build cli does not download a tool only docs uses; oyzu exec, shells and oyzu install still provide every pinned tool. Host prerequisites are checked, never installed. Rationale and acceptance: which tools a build gets.

No system fallback is accepted as a locked build tool or as a way around an enforced acquisition/management denial. Approved npm sessions require the selected Node-backed npm; npx uses that same routing inspection rather than bypassing it.

Native execution retains binary streams and OS-native arguments. Unix execution forwards interrupts to the child group, retains terminal foreground ownership, and preserves signal termination; captured JSON reports its numeric shell status. Windows execution uses the existing suspended job owner. See parity qualification for actual commands, measured cases and remaining native-host requirements. Full issue completion requires Windows/macOS evidence and the remaining differential acceptance matrix.
