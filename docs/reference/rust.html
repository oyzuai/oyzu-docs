Rust applications, libraries and workspaces

CLI reference

Published from the canonical docs/reference/rust.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Oyzu builds Cargo packages and workspaces with no Oyzu configuration. It finds Cargo.toml, runs Cargo, and collects binaries, crate archives, test reports and coverage into a build bundle. Use this page for what the Rust builder runs, the options it accepts, and how host builds differ from isolated (container) builds.

Note: The Rust builder is experimental. Private Cargo registries, private Git sources and Git LFS aren't supported in isolated builds. See Limits.

Platform scope: Use an x64 host and supported x64 build targets. ARM64 is unsupported. Feature-specific limits are listed in the support matrix.

Quick start​

oyzu build --plan          # preview the stages and tool requirements
oyzu build                 # build for this machine
oyzu build --full          # also run tests, doctests, Clippy and rustfmt
oyzu inspect dist          # check the bundle
  • Plain oyzu build builds natively for the host. --platform <os/arch> cross-compiles one other platform. --all-platforms builds the declared matrix in the container executor. See build selection and checks.
  • oyzu build --isolated runs the build in a Linux container. See Ordinary tasks and isolated build prerequisites.
  • oyzu run <task> runs a development task such as build, test, lint or format-check with the Cargo you have installed. oyzu run list shows them.

Cargo owns workspace membership, package metadata and dependency resolution. A checked-in Cargo.lock is required, and Oyzu runs Cargo with --locked.

The Rust plugin package​

The Rust builder is the oyzu-plugin-rust plugin. It reads your Cargo metadata, plans the build, and turns Cargo's output into binaries, crate archives and reports. Oyzu itself installs tools, downloads dependencies, projects versions, caches work and checks every artifact and report before it reaches dist/. Oyzu selects the plugin for rust/app and rust/library targets from its plugin sources (see plugin packages). There is no built-in fallback: if no Rust plugin is available, the build stops and says so. To use a locally built plugin, see local plugin bindings.

Published package compatibility​

The marked Rust 0.1.0-preview.4 package requires Oyzu 0.3.0 or newer, including native-private-outputs and captured-cargo-projection support. Enable preview selection in user configuration to select it from the official catalog. This release covers the native Linux x86_64 flow; other platform combinations are not covered by this release.

Existing projects retain their locked worker when the core or catalog changes. Before using the new core with a project locked to Rust preview.3, explicitly update the reference and then build:

oyzu plugins update rust/app@0.1.0-preview.4
oyzu build

Use rust/library@0.1.0-preview.4 for a locked library reference. Routine updates do not select previews, so this update names the exact published version. The older worker emits a different native Cargo operation graph and can fail with PLUGIN_CONTROL_CONFLICT on the new core. Updating uses normal signed package and engine admission; a build never silently changes a locked selection.

The published 0.3.0 core cut does not bind inherited Unix file-creation masks to native cache identity. Keep that mask unchanged across cached builds with this core: after a mask change, cached outputs can retain stale permissions. It also does not preserve every authored directory mode in native source projections. Changed-mask reuse and custom directory-mode fidelity are unsupported by that release.

Native builds retain Cargo compiler state for incremental work, but discard integration-test scratch under tmp/ and <target-triple>/tmp/ before measuring the retained cache. See native compiler cache retention for the budget and symlink checks.

Building Rust needs no Python or other unrelated runtime.

In isolated execution, Rust packages declaring captured-cargo-projection stage declared manifests and the original lock separately from inferred-version controls. The required project-version step then copies the exact frozen projected controls before compilation or checks. Source-only edits can reuse dependency staging without reusing stale version-bearing output. Authored manifests and locks remain unchanged. Older unmarked packages keep their projected staging overlay; native host finalization is unchanged. See prepared-input staging and plugin capabilities.

What each stage reads​

StageSource boundary
BuildCargo manifests, lock/config controls, selected package sources, reachable local path-dependency sources and predicted native inputs; compiler dep-info, build-script observations and macro resolution refine the boundary when available.
Test, lint and coverageThe same local source closure as build, including build and dev dependencies in Cargo's resolved graph, with stage-specific native observations. Unresolved build scripts or macros keep a specific conservative reason.
Format checkThe selected crates' own source trees and module/include closures, without following Cargo dependency edges.
Crate archiveCargo packaging inputs; an unbounded native packaging closure retains whole-target scope.
Native binary exportDeclared producer outputs only, through the admitted typed binary copy.

Local path dependencies include both workspace members and non-member packages under the build's source root. Their predicted reads include target source folders, build.rs and literal include closures. When the native read resolution is unavailable, compiling stages conservatively include every local package in the Cargo inventory. With resolution, unrelated members' source trees are excluded unless selected; workspace manifests remain declared.

If a local path dependency is outside the target root, compiling stages remain unbounded with the reason local path dependency <name> is outside the target root. This does not block planning or change format-check's selected-crate boundary.

Both native and isolated plugin planning attach Cargo read facts after the full operation graph is assembled. Intermediate construction defaults are never the final cache declaration. File-analysis facts are shared only within one planning request over the same source view; compilation and formatting still construct separate source closures. Later requests analyze their current source bytes. A read-only --plan uses stage contracts from the target's last retained build plan, marked as facts from the last build. Before a contract exists it says reported when the builder answers. It never runs Cargo or acquires tools to fill in that preview. An authored replacement cannot inherit a native command's narrow read contract. See action caching.

Native host builds​

A host build runs Cargo on your machine and keeps Cargo's state under .oyzu/native/, so repeat builds stay incremental. oyzu build followed by oyzu build --full can reuse declared-version compilation; the full build also requires inferred-version finalization and the extra checks. Each action uses a private source workspace and its own writable Cargo state. Clippy and tests use separate target directories, and coverage builds are kept apart from ordinary ones. Hooks and replaced tasks run without that reuse. See native action caching.

Shared-cache writers with optimized output run both compile-development and compile-optimized in one build plan. Readers reuse only the stage matching their requested profile. Check stages retain Cargo's development/test profile independently of the exported artifact.

Compile, test, lint and format stages use declared Cargo versions. Plain local development readers may export the cached compile result directly; its compiledVersion is recorded separately from the inferred artifact version. Full, CI, optimized, packaged, handed-off, shared-cache writer and release paths require final projection so the exported binary's CARGO_PKG_VERSION matches the artifact version. Development results are rejected by stamped packaging, publication and release gates. The inferred OYZU_VERSION default and explicit overrides remain keyed on compilation and checks. A final-stage receipt names its version map and projected-control digests; restoring compile binaries does not transfer Cargo compiler state.

Checkouts below /workspace, /out or /oyzu use their original native Cargo cache and inventory paths when a stage runs from its private source workspace. Those checkout names do not turn native cache paths into executor mount paths.

Tests, coverage, doctests and the other checks need their tools: rustfmt, Clippy, cargo-nextest, cargo-llvm-cov, and the compiler's LLVM tools and profiler runtime. See native execution for what Oyzu installs for you and what it checks first.

Tests can also launch admitted tools through std::process::Command. Their cache keys conservatively retain the complete admitted tool environment and managed PATH, including user-level pins. A simple manifest does not prove that test subprocesses use only Cargo and Rust reporting helpers.

Native Rust builds are supported on Linux (GNU) and Windows (x86-64, MSVC). macOS isn't supported yet.

Named build options​

A named build uses the shared fields in build inventory migration plus builder-owned with options.

builds:
  cli:
    uses: rust/app
    platforms: [linux/x86_64]
    with:
      features: [integration]
      artifacts: binaries
  server:
    uses: rust/app
    with:
      packages: [my-server]
OptionValuesDefaultMeaning
with.featuresList of unique Cargo feature namesnone (Cargo's default features stay on)Applied to metadata, builds, lint, tests, doctests and package verification.
with.packagesList of unique Cargo package namesnone (the whole workspace)Limits the build to these workspace packages: cargo build --package …, and the same for lint, tests, doctests and package verification. Binaries and crate archives come only from them. with.features then belong to each of these packages, so they must be plain feature names (not package/feature or dep:). A name that is not a member of the workspace fails.
with.artifactsall, binariesallall delivers the binaries and the crate archives of publishable workspace packages in isolated builds. binaries delivers only enabled Cargo binaries and never packages crates.
  • Unknown with keys fail. Options are never raw command strings.
  • Several builds can share one workspace root when each selects different packages. Two builds with the same selection fail with two targets own the same native build unit. The first-party plugins build this way: one build per plugin, each packages: [oyzu-plugin-<name>] with features: [plugin].
  • binaries fails if the build has no enabled binary. Feature-gated binaries need their Cargo features turned on.
  • binaries still compiles, runs the selected checks and validates the executables.
  • Conventional format and format-check tasks also honor with.packages, using cargo fmt --package for the selected members. Without a package selection they use --all. Formatting follows Cargo/rustfmt's native module traversal.
  • Cargo can't package a publishable crate that depends on an unpublished path dependency. If you only need executables, select binaries.

The old rust: object is no longer accepted. Cargo features go in with.features and cross-compilation targets go in platforms. Legacy language objects, tool versions, runtime matrices, unknown shared fields, and empty, repeated or suffixed platform entries are refused.

Running a named build​

  • oyzu build builds for the host. oyzu build --all-platforms builds every declared platform in the container executor.
  • Without platforms, a build targets the platform of the executor that runs it.
  • The container executor needs the Linux Rust image described below and downloads crates.io inputs before it runs offline.
  • Outputs and reports end up in the verified dist/ bundle.
  • To pin the compiler, see Locked Rust compiler.

Platforms instead of Cargo target triples​

Name the platforms a Rust build ships in platforms, not Cargo target triples.

builds:

oyzu build --platform <os/arch[/abi]> builds one of them on this host: the host platform as a host build, another one with the cross toolchain. oyzu build --plan --json lists every declared platform with the runner and executor it needs, so a CI matrix can build each on its own runner. A project that needs a particular executor declares it with build.executors.

  • with.features applies to every platform. Outputs go to dist/<target>/<platform>/.
  • Only x86_64 and arm64 on Linux, Windows and macOS have platform names. Other triples, such as riscv64gc-unknown-linux-gnu, can't be built yet.
  • A build isn't a raw cargo build --target: Oyzu also applies tool requirements and artifact collection.
  • A native executor builds one platform per target per run.

Cross-compiling on this host​

oyzu build --platform <os/arch[/abi]> builds for another platform with your pinned toolchain: cargo build --target <triple> with the target's linker. Planning only looks at the host and the files it can see. It installs and runs nothing. Platforms and executors shows how the Plan reports each platform.

  • The defaults are musl for Linux, MSVC on a Windows host and LLVM MinGW elsewhere. An ABI in the platform name (linux/arm64/gnu) overrides them.
  • The host's own machine and default ABI (GNU on Linux, MSVC on Windows) build as a host build. A musl build of the host's machine is a cross build.
  • The target's standard library must be in the pinned toolchain. A cross build adds rust-std@<triple> to its tool requirements, and fails with PLATFORM_UNAVAILABLE if the toolchain has none.
  • Output goes to dist/<target>/<platform>/ with the target's executable suffix. Oyzu checks the binary format and architecture against the target platform without running it.

A Linux musl build whose dependencies include the cc crate (such as ring) compiles that C with zig cc, as an isolated build does:

  • Oyzu fetches Zig 0.15.2 and cargo-zigbuild 0.21.2 built for your host (Linux, macOS or Windows, x86_64 or arm64), checks each against a SHA-256 pinned in Oyzu, and unpacks them once per machine in rust-cross beside the action cache (~/.cache/oyzu, ~/Library/Caches/Oyzu or %LOCALAPPDATA%\Oyzu\cache). Downloads are admitted by your fetch sources, and an offline build needs one earlier online build. The Preflight shows a Cross C compiler step.
  • CC_<triple>, CXX_<triple> and AR_<triple> run cargo-zigbuild's zig cc, which turns the cc crate's target into one Zig accepts, and CARGO_ZIGBUILD_ZIG_PATH names the fetched Zig. Zig's caches are kept in the target's native cache.
  • The cc crate can't run a compiler whose path has a space, so a cache folder with one (a Windows user name with a space) stops the build with PLATFORM_UNAVAILABLE; use --isolated there.
  • rust-lld still links. Cargo itself runs as cargo build, not cargo zigbuild.
  • Pure-Rust builds fetch nothing.

If compiler source access is denied or unavailable, or an archive is missing offline, preparation stops before compilation with PLATFORM_UNAVAILABLE. The diagnostic names the target C compiler, the missing archive and its URL, and an online oyzu build command to populate the cache. The original access error is retained. Integrity, corrupt-archive and filesystem failures keep their original diagnostics without this access recovery. Administrative fetches.sources denials require administrator approval; a host compiler does not replace the pinned compiler or bypass acquisition controls.

Limits:

  • C code for linux/<arch>/gnu, Windows and macOS targets needs that target's own C compiler on PATH (the linkers above). Otherwise use the container executor (--isolated, or "linux/arm64" = "container" under build.executors), which restores pinned cross linkers and C compilers for each target (details), or build on a runner of that platform.
  • C built through something other than the cc crate (a hand-written build script calling cc, or CMake) gets no Zig compiler.
  • Tests, coverage and doctests don't run for a cross-built platform.
  • A project can require a cross build with build.executors. A release then cross-compiles that platform as declared or fails.

Ordinary tasks and isolated build prerequisites​

oyzu run list shows the Rust tasks without running Cargo:

oyzu run list
oyzu run build
oyzu run test
oyzu run lint
oyzu run format-check
  • Tasks use the Cargo, rustfmt and Clippy you already have.
  • The implicit tasks are fetch (cargo fetch --locked), install (cargo install --path . --locked), build, test, lint, format, format-check and archive.
  • oyzu run format changes your source. Builds only run the read-only format-check.
  • oyzu build never runs fetch or install unless your tasks or hooks connect them.
  • Test tasks write JUnit, Cobertura and doctest reports under dist/<target>/<platform>/reports/, not relative to the Cargo workspace. Required reports must be collected. Cobertura coverage allows 32 MiB per file; JUnit and doctest reports retain their 16 MiB limit. XML node limits, path containment, freshness, digest verification and coverage acceptance remain enforced.

The isolated-build image​

Isolated builds need Docker and the base execution image, which has a C toolchain and no Rust. Host builds don't use it.

  • Rust, rustfmt, Clippy and the LLVM tools come from oyzu.lock (see Locked Rust compiler). cargo-nextest and cargo-llvm-cov are locked stage tools for the test stage. If a tool the enabled stages need isn't in the lock, the build stops with a message that names oyzu pin.
  • Oyzu mounts its engine and the Rust plugin into each action, so you never rebuild an image when the CLI changes. Python isn't needed.
  • Cross builds add the pinned linkers described under cross-platform execution:
TargetLinkerC code in build scripts
Linux musl (linux/x86_64, linux/arm64)The compiler's own rust-lldzig cc, through cargo-zigbuild
macOS (darwin/x86_64, darwin/arm64)cargo-zigbuild, against Zig's libSystem stubszig cc, through cargo-zigbuild
Windows gnullvm (windows/x86_64, windows/arm64)LLVM MinGW clangLLVM MinGW clang
  • Zig 0.15.2, cargo-zigbuild 0.21.2 and LLVM MinGW 20260616 are each fetched once, checked against a SHA-256 pinned in Oyzu, stored with your declared fetches and restored read-only under /scratch/rust-cross-*. They're fetched only for a build that targets those platforms, and they run on linux/amd64 workers.
  • The image has no Apple SDK. Crates that link Apple frameworks other than libSystem need your own image (--image cargo=<ref>) that provides one through SDKROOT.
  • A custom --image cargo=<image> must meet the bring-your-own requirements, including a working cc. Oyzu still uses the locked tools.

Docker dependency contexts use the narrower rust/cargo provider.

Isolated Rust builds run on Linux with Docker.

Installing project executables​

oyzu run install -- --root /path/to/bootstrap --force
oyzu run fetch -- --offline
  • oyzu run install runs cargo install --path . --locked in the target's directory. With several Rust targets, qualify it (oyzu run cli:install).
  • Arguments after -- go to Cargo. Installation uses Cargo's release profile. Use --bin to choose a binary and --force to replace an existing one.
  • --root and CARGO_INSTALL_ROOT choose the install root. Otherwise Cargo's default applies, and its bin directory must be on PATH.
  • Cargo reports its own errors for packages without installable binaries and for virtual workspace roots.
  • A lock selects dependencies but doesn't make Cargo offline. Forward --offline when your caches are enough.
  • Use oyzu run fetch for cargo fetch --locked.

oyzu install provisions tools, not this task.

Preparation and build gates​

Isolated builds first collect everything Cargo needs, then build offline.

Registry acquisition​

Oyzu reads the complete registry inventory from Cargo.lock before it makes any request.

  • Only crates.io is supported: index entries from https://index.crates.io/ and archives from https://static.crates.io/crates/. Another registry or an unsupported Git host fails. Oyzu never falls back to Cargo's own network access.
  • Every locked registry package needs a SHA-256 checksum. Oyzu requires the index metadata and archive bytes to match, then stores the archive and only the locked version's index entry in Cargo's local-registry format.
  • If a cached index entry lacks the locked version, an online run fetches it once and checks it again. An offline run fails and tells you to run online. Duplicate matching entries and checksum disagreements are errors.
  • Cargo extracts the archives, verifies checksums, resolves and compiles. No project code runs during acquisition.
  • If the lock contains only local workspace packages, no registry replacement is written.
  • Acquisition needs crates.io to be reachable on each fresh preparation. Once preparation succeeds, the build runs with the network denied.

Git sources​

  • Public GitHub sources need a full commit in Cargo.lock.
  • Cargo fetches them through a repository-scoped broker inside a container with no network. The broker allows only Git smart-HTTP discovery and upload-pack requests, within size, redirect and request limits.
  • Oyzu keeps the fetched object database and recreates the checkouts privately for the offline build. Repositories with Unix symlinks work on Windows hosts.
  • Private Git, other hosts, submodule routing and Git LFS aren't supported.

Which packages are archived​

Isolated builds archive only publishable workspace packages as .crate files.

  • A package with publish = false (or an empty publish list) never gets a .crate. A private application delivers its executables instead. A private library is workspace internals.
  • Private packages still build, lint and test.
  • Publishable packages keep Cargo's own packaging and verification. One that depends on a private library fails with Cargo's own message.

Packaging mixed workspaces​

For a workspace with local path dependencies and registry inputs, Oyzu packages members in dependency order. Each runs cargo package --locked --offline --allow-dirty --registry crates-io --package <name> with verification on.

  • Each archive's name, version and SHA-256 are checked before dependent members can use it.
  • Ordinary and build dependency cycles, and paths outside the workspace, fail planning.
  • The captured registry stays unchanged. A temporary registry copy is removed when the action ends.
  • An index over 4 MiB, an archive over 128 MiB, or an identity or checksum conflict fails packaging. Fix the manifest and rebuild.
  • Native manifest publish restrictions still apply, and only the crates.io profile is supported.

Development-dependency cycles between local members are supported when their ordinary and build edges are acyclic. Oyzu packages the cycle group together without verification, admits the results to a private registry, then packages and verifies every member separately and requires each final archive to match its provisional one byte for byte. Archives from a cycle group don't include Cargo.lock, so cargo install --locked doesn't work on them. If the original lock holds a different registry version of one of these members, Oyzu lets Cargo align its private lock with the verified workspace archives, offline, and restores the original lock afterward.

Before packaging, Oyzu checks the original lock offline and writes workspace versions and local requirements into private manifests with a regenerated private lock. Your source files stay unchanged. Registry packages keep their locked versions and aren't delivered as artifacts.

Versions​

Ordinary versions are snapshots with a source-derived suffix, such as 1.2.3-dev.g<source-prefix>. Workspace packages resolve independently unless they join a fixed version group. Snapshots are never marked eligible for release.

  • A package's version follows its path-dependency closure. A relevant dependency commit changes the consumer's version, and an unrelated member's commit doesn't. Changes to root workspace inputs affect every member.
  • Private manifests and packaged local requirements use each member's selected version.
  • See version inference for strategies and tags. In a supported GitHub Actions tag job, release staging can select exact release coordinates. It's experimental and covers Linux x86-64 Cargo projects without repository hooks. --require-release refuses when the event or source evidence is insufficient.

Cargo fixed version groups​

Workspace members can share one version using a subset of cargo-release's metadata. Oyzu reads the project-local settings and doesn't run cargo-release or its hooks. Fixed groups are supported on Linux x86-64.

  • shared-version = true joins the workspace's shared group. A nonempty string such as "suite" names a group (case-sensitive; boolean true and the string "true" differ).
  • shared-version = false opts a package out of an inherited group.
  • Without effective membership, packages stay independent, even when their versions match or use version.workspace = true.
  • Private and unselected members still count toward membership.

This workspace groups App and Core and keeps Helper independent. Each package uses version.workspace = true. The root has:

[workspace]
members = ["app", "core", "helper"]
resolver = "2"

[workspace.package]
version = "1.4.2"

[workspace.metadata.release]
shared-version = "suite"
tag-prefix = "suite/"
tag-name = "{{prefix}}v{{version}}"

helper/Cargo.toml overrides both inherited fields:

[package.metadata.release]
shared-version = false
tag-prefix = "helper/"

With tags suite/v1.4.2 and helper/v1.4.2, an App-only feat: add API commit moves both App and Core to base 1.5.0. Helper stays at 1.4.2. All of them are still source snapshots.

Each field merges separately, lowest to highest precedence:

  1. Workspace-root release.toml.
  2. Root Cargo.toml under [workspace.metadata.release].
  3. Member-directory release.toml.
  4. Member Cargo.toml under [package.metadata.release].

A missing field inherits. An explicit false or empty prefix is a value. Home-directory configuration and cargo-release command-line overrides aren't read. Release, publish, signing and push settings don't control groups.

For tag-based versions, every group member needs the same literal, slash-terminated tag-prefix (such as suite/). tag-name can be {{prefix}}v{{version}} (the default) or {{prefix}}{{version}}. An empty prefix means root tags and requires exactly one release subject at the Git root. Wildcards, crate-name templates and other tag formats are refused, as are partial prefixes, conflicting tags and unreadable controls. Fix the named declarations and rerun. --plan doesn't run Cargo or fetch history to fill in missing facts.

Every member must declare the same normalized version, including qualifiers. Full builds write the common version and local requirements into private manifests and the private lock. Host builds first compile declared versions, then compile the final version in a separate Cargo stage. A registry backreference that needs a different member version is refused rather than splitting the group.

The bundle records group membership, tag prefixes, where each setting came from and the resolved versions in oyzu.dev/version-subjects, beside each package's oyzu.dev/versioning entry. See Cargo groups in version inference for the strategy and conflict rules.

What a build runs​

Native host tests, Clippy and formatting use the declared Cargo versions, while binary export follows the final inferred-version projection. Tests do not read the stamped binary export; assert shipped version strings against the final artifact and receipt rather than expecting a stamped CARGO_PKG_VERSION in tests.

An isolated build runs release compilation of the workspace, native tests with reporting, Clippy, a rustfmt check, verified crate packaging and final collection.

  • Commands use locked, offline inputs and the executor denies the network. Build scripts and proc macros run in that environment and must work with the collected inputs.
  • The compiler's host target, the .oyzu-build/target output root, the private Cargo home and the offline setting are fixed by the plan. A task environment can't change them.
  • Custom Cargo source replacement isn't supported and can fail offline resolution. Other Cargo settings in the project still apply.
  • Compilation, tests, lint, formatting and archive verification are required. If one fails, no final artifacts are collected. The logs and any reports show which stage failed. Fix it and rerun. A bundle from an earlier successful build stays in .oyzu/history and isn't reused as this build's output.

Tests, coverage and doctests​

Tests run through cargo llvm-cov nextest. JUnit and Cobertura reports land under dist/ and are indexed with paths, digests and summaries in dist/manifest.json.

  • Test failures and coverage failures are reported separately. A missing or invalid required report fails collection. oyzu inspect dist checks the bundle's integrity.
  • The Cobertura report omits per-function records and keeps line and branch details to reduce its size. The report limit is 32 MiB per file; a larger report fails the build. Oyzu's coverage gate uses covered and valid source-line counts.

Cargo doctests run as part of the same test gate, since nextest doesn't run them.

  • Oyzu runs cargo test --doc --locked --offline --package <name> for each workspace package that has a doctest-enabled target (doctest = false is honored). Binary-only targets and registry dependencies don't run doctests.
  • doctest.xml has one case per package invocation, not per documentation example. A package with doctests enabled but no examples still passes.
  • A non-zero Cargo exit is a failure and a launch error is an error. Output streams live, and the report keeps the start of each diagnostic.
  • All selected packages run even if one fails. A failed doctest blocks artifact collection even when nextest passes.
  • Coverage covers nextest runs only. It doesn't include doctests or individual doctest cases. Custom nextest configuration isn't supported.

Direct test evidence​

oyzu run test produces nextest JUnit, LLVM Cobertura coverage and doctest reports, and you can follow it with oyzu inspect dist. It's supported on Windows (MSVC) and Linux. See direct tests for the bundle layout.

Prerequisites​

  • Rust with the llvm-tools-preview component and the compiler's profiler runtime, cargo-nextest 0.9.146 and cargo-llvm-cov 0.9.1.
  • On Windows, use an MSVC or windows-gnullvm compiler with its linker and SDK. The windows-gnu compiler isn't supported for coverage because it lacks profiler_builtins (see native build prerequisites).
  • Dependencies must already be installed so Cargo can resolve them offline with --locked. This task doesn't install tools. If the LLVM tools are missing, it fails before llvm-cov tries to download them. LLVM_COV and LLVM_PROFDATA can point at installed copies.

How the test task runs​

  • Cargo's metadata --no-deps --locked --offline supplies the workspace members and doctest-enabled packages. oyzu run list never runs Cargo.
  • The default cargo test --locked --workspace task is instrumented automatically. A task you replace keeps its own command and still has to produce the JUnit, coverage and doctest reports. No Oyzu configuration is needed for the default.
  • A temporary nextest profile inherits your default profile and writes fresh JUnit output. Your .config/nextest.toml isn't edited.
  • Compilation and coverage use private temporary target directories, so project build state isn't reused.
  • Extra command arguments go to nextest. Alternate nextest profiles, arbitrary cargo test arguments and filtered doctest selection aren't supported here.
  • The task runs nextest, generates coverage even if tests failed, and runs doctests. Any failing phase fails the task.
  • Build scripts and proc macros run normally. Cargo's offline flags aren't a network sandbox on the host. See direct tests.

Artifact selection and collection​

With the default with.artifacts: all, an isolated build produces <package>-<selected-version>.crate for each publishable workspace package, plus <binary>-<selected-version>-<compiler-host> for each enabled binary.

  • with.artifacts: binaries selects only executables and fails if there are none.
  • The selected version is normally a projected snapshot. See Registry backreferences for the exception.
  • Manifest names use the crate- and bin- prefixes.
  • A publishable library-only package gets a crate archive and no invented executable.
  • Duplicate binary names fail planning.

Feature-gated binaries​

Cargo's resolved features decide whether a binary with required-features exists. A binary whose features aren't on is left out. Turn the features on through Cargo's defaults or with.features to include it.

How binaries are collected​

  • Oyzu reads Cargo's JSON compiler messages and matches each expected binary by its manifest path and target name. It takes the executable path from Cargo's own compiler-artifact events rather than guessing filenames, and never publishes test binaries.
  • Cached results count as well as fresh compilation. A missing, unexpected or conflicting output, a failed Cargo process, or an executable outside the target root fails the build.
  • Oyzu clears its staging directory before each Cargo run, so an old executable can't stand in for a disabled feature or a failed compile.
  • A task you replace must still produce the planned artifacts.
  • This builder doesn't publish, sign or promote anything.
  • Crate archives don't include Oyzu's private .oyzu-build files.

Registry backreferences​

Cargo package verification re-resolves through a private registry. A projected prerelease version of a member can then conflict with a registry dependency of the same name. When the resolved graph has a registry dependency named after a workspace member, Oyzu keeps that member's declared version, and local path requirements use it.

  • Only affected members keep declared versions. Others get snapshot versions.
  • An inactive dependency declaration doesn't count.
  • These artifacts are still snapshots. oyzu.dev/versioning records reason: cargo-registry-backreference, the source digest, intent: snapshot and productionEligible: false, even if the version looks like a release. Use the bundle's source identity and artifact digest to tell apart snapshots with the same version.

Locked Rust compiler​

A [tools] rust = "1.95.0" declaration in oyzu.toml, installed into oyzu.lock, selects the compiler for isolated builds.

  • The container worker uses the linux/<architecture>/gnu installation from the project's .oyzu/tools store. That's the compiler's own platform. Artifact platforms in build.yaml don't change it.
  • Only a Rust-only tool selection works this way.

Before any package is downloaded or Cargo runs, Oyzu verifies the lock, the installer, the installation receipts and the payload. It copies the installation into the private dependency snapshot while holding a lease, and verifies the copy. The build uses that copy's Cargo, rustc and rustdoc. The live tool store is not mounted into containers. The dependency record keeps the identities of the request, the installation, the lock and the copy.

If anything is missing or stale, the build fails: a missing or stale lock, a missing worker distribution, an absent installation, an unsupported layout or a changed payload. Install the matching compiler first. Oyzu doesn't resolve versions, edit the lock or use the network to restore the compiler. oyzu install provisions only its own host, so installing a Linux compiler from a Windows host isn't supported yet. The base image has no Rust, so an isolated build without a locked compiler stops with a message that names oyzu pin.

The image provides only OS prerequisites and a C toolchain. Formatting, lint and test tools come from the lock too.

Tool requirements in the bundle​

Build manifests list oyzu.dev/tool-requirements for each Rust target.

  • Oyzu reads literal package.rust-version values and Rust toolchain channel constraints, with their source files and locations, in every form rustup accepts (details).
  • It lists compiler components, standard libraries for the platforms you build, and the formatting, lint and test tools that the selected stages need. Fast builds leave out the quality tools they don't run. Components named in your toolchain file stay required.
  • A rust-version inherited from the workspace needs workspace metadata. Without it, the build fails with a clear message instead of ignoring the value.

For a locked compiler, isolated builds choose their recipe from the same build-stage requirements as oyzu pin. A build with tests selected therefore needs the locked llvm-tools-preview component, even if the lock also holds a smaller recipe for fast builds. An incomplete lock stops the build. An environment override doesn't replace it. The helper tools cargo-nextest and cargo-llvm-cov are restored from the lock as stage tools.

Experimental cross-platform execution​

Declaring artifact platforms in build.yaml runs isolated builds on the execution image with the pinned cross linkers listed under the isolated-build image.

  • Supported platforms are linux/x86_64, linux/arm64, darwin/x86_64, darwin/arm64, windows/x86_64 and windows/arm64. Linux builds musl and Windows builds gnullvm. Other ABIs are refused.
  • Baselines: musl for Linux, Apple Darwin with a macOS 13 deployment target, and LLVM MinGW for Windows. They don't guarantee compatibility with older operating systems.

The locked compiler and target standard libraries are restored separately from the linkers.

Compiler and worker​

  • Declare the compiler in oyzu.toml and install it into oyzu.lock. On Windows, oyzu install also fetches the Linux compiler when the project declares a Rust build.
  • Equivalent locked selections in one build share one verified compiler extraction per archive digest and worker image. It's mounted read-only. Cargo homes, outputs and workspaces stay private.
  • The extraction is released when the build ends. The persistent oyzu-tools-* volumes are reused by identity, and superseded ones are pruned (see build logging). The build runs without network access.
  • Compiler sharing is automatic and adds no build.yaml options. It doesn't deduplicate crate downloads or preparation, and it isn't a persistent compiler cache.

Resources​

  • Each cross-platform Rust action reserves 8 GiB of memory and may run up to two hours. Oyzu limits concurrent targets by Docker's available memory and keeps 25% as headroom. A Docker engine needs about 11 GiB to run one such action. Preparing the locked compiler reserves 4 GiB.
  • Tests and coverage run on the Linux worker. Cross-compiled executables are checked for the right binary format and architecture, but not run on the target OS.
  • Cargo extraction and Git checkouts use a private Linux scratch filesystem of at least 2 GiB that grows with larger memory reservations. Only the Git object databases are copied back, which keeps registry extraction and symlinks off Windows host mounts.
  • Build inputs and workspaces live under the project's .oyzu directory on the same volume as the project, not in the system temp folder. They're private, and excluded from source snapshots and bundles.
  • cargo fmt runs with the same locked compiler and never receives feature arguments.

Limits​

Rust compilation stages declare OYZU_RELEASE_COMMIT and SOURCE_DATE_EPOCH as environment inputs, so their values affect cache keys. Native builds inherit them from the invocation; isolated builds require values in the configured environment, as with other build-script environment inputs. For Oyzu's own CLI, set both to a full commit ID and Unix build seconds to produce the explicit release label; leaving the commit unset produces the development display label. This does not authenticate a release or grant publication.

Native host builds retain a local Cargo producer evidence record in the build bundle. It binds the compiler identity, selected sysroot, original Cargo metadata, captured source inventory, final native command controls and original build streams. Restored actions retain their original record. Older cached actions without this completion contract are rebuilt once; the native Cargo compiler cache remains usable. The record contains private build paths and is local engineering evidence, with no release or legal approval. Core oyzu/plugin-package declarations have no external builder or additional native tools. oyzu exec, installation and pinning resolve the executable producer's tools while keeping package declarations available for reference validation.

  • Isolated builds support single packages and local workspaces, including libraries, binaries, proc macros and build scripts. Only crates.io registry dependencies and public GitHub Git dependencies work. Private or alternate registries, private Git and Git LFS don't.
  • Isolated Rust builds run on Linux with Docker. Cross-compiling needs the platform's linker or the container executor (see above).
  • Custom nextest configuration, doctest coverage and individual doctest cases aren't supported.
  • Release and registry publication aren't done by the Rust builder.
