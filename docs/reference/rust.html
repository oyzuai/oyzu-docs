Rust applications, libraries and workspaces

CLI reference

Published from the canonical docs/reference/rust.md file. Features marked experimental remain experimental; check support limitations before relying on them.

Oyzu builds Cargo packages and workspaces with no Oyzu configuration: it discovers Cargo.toml, runs the native Cargo tooling and collects binaries, crate archives, test reports and coverage into a build bundle. Use this page to see what the Rust builder runs, which options it accepts, and how it behaves on the host versus in an isolated (captured) build.

Status: experimental. The native local build is in development and its bootstrap milestone is not yet acceptance-verified. Plain oyzu build selects it for one inferred or explicitly declared Rust target. Use oyzu build --isolated for the captured behavior described below. Adding --plan produces a read-only preview, not dependency capture. Private/alternate registry and Git acquisition remain unfinished.

Quick start​

oyzu run list
oyzu run build
oyzu run test
oyzu run lint
oyzu run format-check
oyzu build --plan
oyzu build
oyzu inspect dist
  • oyzu run <task> runs development tasks with your already provisioned Cargo, rustfmt and Clippy.
  • Plain local oyzu build selects the host and retains quality gates. Use --platform <os/arch> to cross-compile one other platform natively, or --all-platforms for the declared matrix through the captured executor. See build selection and checks.
  • oyzu build --isolated runs the captured build in a container. See Ordinary tasks and isolated build prerequisites.

What the builder supports​

  • Cargo owns workspace membership, native package metadata and dependency resolution.
  • Captured builds currently support single packages and contained local workspaces, including libraries, binaries, proc macros and build scripts.
  • Locked crates.io dependencies are captured before execution. Private/alternate registry and Git acquisition, and cross-compilation, remain unfinished.
  • Rust build, test, doctest and packaging orchestration runs in compiled Oyzu adapters. Host and isolated plans select the private compiled entry point; the former Python adapter files have been removed, and Rust requirement discovery does not list Python.
  • Cargo, Nextest, LLVM coverage tools and the applicable linker/SDK remain prerequisites. Explicit task overrides retain their own requirements.
  • Broader host report-gate and rebuilt isolated-suite qualification remain pending; the registry-backreference corpus proof below qualifies that specific rebuilt flow. See the migration checkpoint.

Named build options​

The CLI accepts builds.<name> with the shared fields listed in build inventory migration and builder-owned with.

builds:
  cli:
    uses: rust/app
    platforms: [linux/x86_64]
    with:
      features: [integration]
      artifacts: binaries
OptionValuesDefaultMeaning
with.featuresList of unique Cargo feature namesnone (native default features stay enabled)Applies to native metadata resolution, builds, lint, tests, doctests and package verification.
with.artifactsall, binariesallall delivers the discovered binaries and eligible workspace crate archives on the captured path. binaries delivers only enabled Cargo binaries and does not schedule crate packaging.
  • Unknown options fail; options are not arbitrary command strings. Other proposed shared fields and other builders' with options fail explicitly until their adapters implement them.
  • Native local builds already deliver binaries; the explicit binaries choice additionally refuses an empty enabled-binary inventory on both paths. Feature-gated binaries require their native Cargo features.
  • binaries preserves compilation, selected checks, required reports and executable validation. It does not change Cargo publication rules or permit failed build outputs to be exported.
  • Publishable workspace packages with unpublished path dependencies can fail ordinary crate packaging, because Cargo does not register unpublished dependencies in its packaging registry. A target whose required output is an executable can explicitly select binaries.

Running a named build​

  • Run oyzu build for the native host, or oyzu build --all-platforms for the declared matrix.
  • The existing captured execution path still requires the provisioned Linux Rust builder image described below and captures crates.io inputs before offline execution. Outputs and reports remain in the verified dist bundle.
  • An omitted platform uses the existing executor platform; an explicit list expands every declared platform on the captured path. The native local default selects the current host from that list; --platform selects another one, built natively by a cross toolchain when this host has one.
  • Explicit Rust requests now use the locked-tool handoff. Pinned public GitHub acquisition is implemented through the scoped broker; private Git remains unsupported.
  • The repository's six-platform self-build is not yet working.

Removed rust: object​

The rust: object is gone (configuration split M4): Cargo features are with.features and cross-compilation targets are platforms entries (below). New named builds reject legacy language objects, tool versions, runtime matrices, unknown shared fields, and empty, repeated or suffixed platform declarations.

tooling/test-build-model.py --cli <compiled-cli> exercises the new authoring through a real Linux build, feature-required compilation, reports, packaging, bundle inspection and execution of the collected binary. It is not six-platform self-build evidence.

Platforms instead of Cargo target triples​

A Rust build names the platforms it ships in platforms, never as Cargo target triples. The former rust: object, whose targets list generated <target>:build-<triple> tasks for oyzu run, is refused with CONFIG_INVALID_VALUE naming this replacement; nothing generates those tasks any more (configuration split M4).

builds:
  cli:
    uses: rust/app
    with:
      features: [mise-integration]
    platforms: [linux/x86_64, linux/arm64/musl, windows/x86_64, darwin/arm64]

aarch64-unknown-linux-musllinux/arm64 cross-built (musl is the cross default) or linux/arm64/musl
x86_64-pc-windows-msvcwindows/x86_64 on Windows, or windows/x86_64/msvc
x86_64-pc-windows-gnu, -gnullvmwindows/x86_64/gnu, windows/x86_64/gnullvm

oyzu build --platform <os/arch[/abi]> builds one of them on this host: the host platform as a host build, another one with the native cross toolchain.

  • Routing checks only that the target's linker is present. A crate whose build script compiles C (ring, through the cc crate) also needs a C cross compiler for the target, which the rust-lld route does not provide, so such a build fails in that build script.
  • Build those platforms with the container executor instead (--isolated, or "linux/arm64" = "container" under build.executors), whose oyzu-toolchain/rust-cross:v1 image supplies the C cross compilers, or on a runner of that platform.
  • oyzu build --plan --json lists every declared platform with the runner and executor it needs, so a CI matrix builds each on its own runner; this repository's release workflow builds its six platforms that way.
  • A project that needs a particular executor declares it with build.executors.
  • The Cargo features in with.features apply to every platform's build, test, lint and archive stages. Outputs go to dist/<target>/<platform>/.

Limits

  • Only x86_64 and arm64 on Linux, Windows and macOS have platform names, so a triple outside them (for example riscv64gc-unknown-linux-gnu) has no replacement yet.
  • A build is not a raw cargo build --target, so it applies Oyzu's admission, tool requirements and artifact collection.
  • One run builds one native platform per target.

Cross-compiling on this host​

oyzu build --platform <os/arch[/abi]> builds a Rust target for another platform with this host's pinned toolchain: cargo build --target <triple> with the target's linker. Oyzu decides from host facts and file lookups alone (nothing is installed or run while planning) and shows the result in Plan for every declared platform (platforms and executors).

  • The defaults are musl for Linux, MSVC on a Windows host and LLVM MinGW elsewhere; an ABI in the platform name (linux/arm64/gnu) overrides them.
  • The host's own machine (and its default ABI: GNU on Linux, MSVC on Windows) builds as a host build; a musl build of the host's machine is a cross build.
  • The target's standard library must be in the pinned toolchain: a cross-built target adds rust-std@<triple> to its tool requirements, and preparation refuses with PLATFORM_UNAVAILABLE when rustc --print target-libdir --target <triple> has none.
  • Outputs go to dist/<target>/<platform>/ with the target's executable suffix, and static executable verification checks the format and architecture against the target platform without running it.

Limits

  • A crate that compiles C code (the cc crate) needs a C cross compiler the rust-lld route does not provide.
  • Tests, coverage and doctests are not run for a cross-built platform here (--full with --platform would try to run foreign executables).
  • cargo-zigbuild is not used.
  • A project can require a cross build for a platform with build.executors; a release then cross-compiles it as declared or fails.
  • Demonstrated on Windows 11 x86_64 for linux/arm64 (see the status entry).

Ordinary tasks and isolated build prerequisites​

oyzu run list
oyzu run build
oyzu run test
oyzu run lint
oyzu run format-check
oyzu build --plan

oyzu inspect dist

Development tasks

  • Development tasks use already provisioned Cargo, rustfmt and Clippy on the host. Static task listing reads native manifests without executing Cargo.
  • Implicit tasks include fetch (cargo fetch --locked), executable installation (cargo install --path . --locked), workspace build/test, Clippy, formatting, formatting checks and archive. Fetch and install are explicit development tasks, not automatic build stages.
  • oyzu run format modifies source; captured builds use read-only format-check.
  • Direct test execution uses native host state and the shared test-only dist/ report collector; platform-specific evidence is recorded below.
  • Native Cargo workspace ownership is distinct from separate Oyzu target groups.
  • Native test plans use the same platform-qualified output contract as captured plans: JUnit, Cobertura and doctest reports belong under dist/<target>/<platform>/reports/. The shared host executor translates that output contract to its private bundle and honors declared report destinations; report paths are not relative to the Cargo workspace. Required collection and the 16 MiB report limit still apply.

The captured-build image​

Captured builds require Docker and an explicitly provisioned Linux amd64 image. Run the following from the repository root: the image build copies Cargo.toml, Cargo.lock and src/ to compile its worker. The repository provisioning script uses the same root build context. Host development execution does not use this image.

docker build -f tooling/images/rust.Dockerfile -t oyzu-toolchain/rust:1.99.1-nextest0.9.146-llvmcov0.9.1 .
  • The image recipe selects Rust 1.99.1, rustfmt, Clippy, LLVM tools, cargo-nextest 0.9.146, cargo-llvm-cov 0.9.1 and the compiled Oyzu worker at /usr/local/libexec/oyzu/oyzu.
  • Its separate image-build stage compiles that worker with Rust 1.99.1; Python is not installed.
  • Custom --image cargo=<image> profiles must supply the same capabilities, including a compatible worker. Rebuild older images before using these plans.
  • Tool/image provisioning is explicit and separate from project execution. Oyzu does not download a missing toolchain image.
  • The updated image recipe has not yet completed isolated-build qualification.

Docker dependency contexts use the narrower rust/cargo provider. Its standard Rust 1.94.0 consumer image needs no Python, nextest or llvm-cov. It validates the original lock/workspace and exports only the native registry, without artifact version projection or report setup. The tool requirements above still apply to ordinary rust/app and rust/library builds.

The CLI supports Windows, macOS and Linux; that does not imply a native captured-build executor on each host. Current isolated Rust acceptance runs on Linux with Docker. The native artifact probe also runs separately on all three CI hosts. See implementation status for revision-specific evidence.

Installing project executables​

oyzu run list discovers Rust install and fetch tasks without running Cargo.

oyzu run install -- --root /path/to/bootstrap --force
oyzu run fetch -- --offline
  • For a single Rust target, oyzu run install runs cargo install --path . --locked in that target's directory. With several targets, qualify the task, for example oyzu run cli:install. Explicit task overrides retain their existing precedence.
  • This replaces the previous misleading install mapping to dependency fetching; use oyzu run fetch for cargo fetch --locked.
  • Trailing arguments are forwarded as argv to Cargo.
  • Installation uses Cargo's release profile by default. Cargo chooses package binaries and reports native errors for packages without installable binaries or virtual workspace roots. Use --bin to select a binary, and --force explicitly when replacement is wanted.
  • --root and CARGO_INSTALL_ROOT choose the installation root; otherwise Cargo's configured/default destination applies. Its bin directory must be on PATH.
  • Cargo and native build prerequisites must already be usable under Oyzu's existing tool-installation policy.
  • A lock selects dependencies but does not make Cargo offline: forward --offline when caches suffice.
  • Native output and failures use the existing task output/JSON contracts.

oyzu install still provisions development tools. oyzu build does not execute this installation task unless explicitly connected by authored task dependencies or hooks. This is not a substitute for required build/report gates or publication eligibility.

The inferred Windows Oyzu self-install with an explicit root uses staged bootstrap replacement: the current binary remains available during compilation, and successful results replace it while preserving an adjacent backup. Generic Cargo installations keep native behavior.

Preparation and build gates​

Registry acquisition​

A checked-in Cargo.lock is required. Preparation admits its complete registry inventory before issuing any requests.

  • The current standalone source profile permits crates.io index entries through https://index.crates.io/ and archives through https://static.crates.io/crates/, using the shared host transport and its redirect/size/request limits.
  • A different registry or an unsupported Git host fails explicitly; there is no direct Cargo network fallback. This fixed public profile is not yet enterprise connector routing or private Cargo authentication.
  • Each locked registry package must have a SHA-256 checksum. Acquisition requires matching index metadata and archive bytes, then captures the archive and only the locked version's index entry in Cargo's native local-registry format.
  • If a cached index entry omits a locked version, online preparation fetches that entry once through the approved broker source and checks it again. Offline preparation fails with a hint to rerun online; it never refreshes from the network. Duplicate matching entries and checksum disagreements remain errors.
  • Cargo owns extraction, checksum revalidation, resolution and compilation. No project code runs during host acquisition. This avoids implementing a second Cargo resolver or unpacking untrusted crates on the host.
  • When the lock contains only local workspace packages, preparation writes no registry replacement into the private Cargo home. Locked offline execution still applies. This preserves Cargo's native temporary registry for packaging unpublished workspace dependencies; replacing crates.io with an empty registry prevents that resolution. Single packages with captured registry dependencies retain source replacement.

Git sources​

  • Public GitHub sources must carry a full commit identity in Cargo.lock.
  • Native Cargo and Git fetch through repository-scoped broker routes inside a container with networking disabled. The broker admits only smart-HTTP discovery and upload pack requests, with the existing size, redirect and request limits.
  • Cargo checks out the pinned objects and resolves the package graph; Oyzu captures the bare object database and reconstructs checkouts privately for offline build actions. This preserves Git repositories containing Unix symlinks on Windows controllers.
  • Git evidence records object identity, not a publisher signature.
  • Private Git, other hosts, submodule routing and Git LFS are not qualified.
  • tooling/test-build-git.py exercises a real dependency from the pinned mise fork, compiles offline, executes the resulting binary and checks the build bundle. The Windows-hosted proof produced the binary and three reports; it is not evidence of the complete CLI platform matrix.

Which packages are archived​

Only publishable workspace packages are archived.

  • A publish = false package (an empty publish list) never gets a .crate. A private application delivers its executables instead, even when its only binary is feature-gated off (a test fixture or development tool is then neither archived nor shipped), and a private library is workspace internals that no registry accepts.
  • Private packages still build, lint and test with the workspace.
  • Before 2026-10-20 private libraries were archived too, which failed whenever one depended on another (this repository's oyzu-plugin-sdk on oyzu-plugin-protocol: no matching package named oyzu-plugin-protocol found), because Cargo leaves unpublishable packages out of its packaging registry.
  • Publishable packages retain native Cargo packaging and verification; one that depends on a private library still fails with Cargo's own message.
  • The archive inventory and the plan select the same packages.

Packaging mixed workspaces​

For a workspace combining local path dependencies and registry inputs, the Rust adapter packages acyclic members in dependency order using a private writable copy of the captured registry.

  • Each acyclic member runs native cargo package --locked --offline --allow-dirty --registry crates-io --package <name> with verification enabled.
  • Cargo generates the normalized archive and its temporary registry entry. The adapter checks their planned name/version and matching SHA-256 before admitting them into that private copy for dependent members. It does not generate Cargo index entries or resolve dependency versions.
  • Local ordering uses native manifest paths, including renamed/optional dependencies.
  • Development-cycle groups use the conditional native staging and verification flow described under Development-dependency cycles. Ordinary/build dependency cycles and paths without a workspace owner fail planning explicitly.
  • The original captured registry is immutable. The adapter restores the action's Cargo source configuration and removes its temporary registry on ordinary success or failure; sandbox cleanup owns abrupt termination.
  • Captured packages remain inputs, while only the workspace's planned artifacts can reach dist/.
  • Identity/checksum conflicts, a collision with an already captured name/version, an index over 4 MiB or an archive over 128 MiB fail packaging. Repair the native package input or manifest and rebuild; there is no network fallback.
  • The conditional provisional native command skips verification only while staging an affected development-cycle group; every final member archive must pass native verification and byte comparison before admission.
  • Registry publication restrictions in native manifests still apply to this explicit crates.io packaging profile; private-registry publication remains unfinished.

Preparation then checks the original lock using native offline Cargo resolution, projects workspace package versions and contained workspace dependency requirements into private manifests, and regenerates the private lock with Cargo.

  • Source files remain unchanged. Unresolved paths and paths outside the captured target fail preparation.
  • Registry packages keep their locked versions and remain inputs; they do not become this workspace's published artifacts.
  • Prepared input records contain each archive's name, version, digest and size. digest-only verification means matching recorded content, not a publisher signature or release authorization.
  • Dependency edges and per-package purpose distinctions are not yet modeled in this inventory.
  • Acquisition currently requires the approved upstreams to be reachable on each fresh preparation; persistent offline acquisition reuse is not implemented. Once preparation succeeds, build execution reads the captured registry with network access denied.

Versions​

Versions retain each package's base version and use a source-derived suffix, such as 1.2.3-dev.g<source-prefix>. Different workspace packages retain their individual base versions. These are snapshot versions; they do not establish release eligibility or production trust.

Artifact version selection uses the shared version inference resolver for native, exact-tag and nearest-tag/commit snapshots. Release authorization remains separate and unimplemented.

  • Workspace members resolve independently using their native path-dependency closure.
  • A relevant dependency commit participates in the consumer's version analysis; an unrelated member's commit does not. Root workspace inputs conservatively affect all members.
  • Private manifests and packaged local dependency requirements use each member's selected version; equal native version strings do not establish a release group.

What a build runs​

Build execution runs workspace release compilation, native tests with reporting, Clippy, rustfmt checking, native verified crate packaging and final collection.

  • Commands use locked offline inputs and the shared executor denies networking. Build scripts and proc macros execute inside that environment and must work with the captured inputs.
  • The selected compiler host target, .oyzu-build/target output root, private Cargo home and offline setting are fixed plan facts; a task environment cannot redirect them.
  • The owned command wrapper installs captured source configuration into that private home so Clippy, nextest and coverage subprocesses inherit it.
  • Custom native source overrides are not supported by this public profile and can fail offline resolution; other native Cargo settings remain in the captured project.
  • Compilation, tests, lint, formatting and archive verification are required gates. Their failures block final artifacts. Native logs and available reports explain the failed stage. Repair the native input and rerun; an earlier successful bundle is retained under .oyzu/history, not reused as this build's successful output.

Tests, coverage and doctests​

Tests run through cargo llvm-cov nextest; native JUnit and Cobertura are retained under dist/ and indexed with paths, digests and summaries in dist/manifest.json.

  • Test execution and coverage generation retain independent failure outcomes. Missing or invalid required reports fail collection. inspect dist checks bundle integrity, not release authorization.
  • The native Cobertura export uses --skip-functions to omit redundant per-function records while retaining source-line and branch details. Oyzu's coverage gate consumes covered and valid source-line counts; the report collector's 16 MiB limit is unchanged.
  • A real Windows MSVC full self-build accepted an 11,775,479-byte report. A same-profile export without --skip-functions was 23,068,338 bytes; all 595 source files and their complete source-line/branch records and metrics matched, including the collected report. Native branch totals were zero, so this does not qualify nonzero branch instrumentation. The full-build proof records pinned tools, driver/source attribution, unchanged controls and the earlier failed attempts.

Cargo doctests run as part of the same implicit test gate because nextest does not execute them.

  • Prepared native Cargo metadata selects workspace packages with a doctest-enabled target, honoring native doctest = false. Each selected package runs cargo test --doc --locked --offline --package <name> in the captured workspace. Binary-only targets and registry dependencies do not create doctest invocations.
  • Preparation layout version 5 retains the native doctest selection and relocatable binary inventory; old prepared metadata must be regenerated.
  • The additional required doctest.xml report has one case per Cargo invocation, identified by package name, with bounded native diagnostics. Its suite properties explicitly describe this scope. Counts are invocation outcomes, not the number of individual documentation examples: a doctest-enabled package with no examples can have a successful invocation.
  • Stable Cargo owns assertion semantics; Oyzu does not parse human console text into invented case counts. Native nonzero exits produce failures; launch errors produce errors.
  • Native doctest stdout and stderr stream through the host executor while the report retains bounded diagnostic prefixes. Compilation and doctest execution have no separate per-package timer; any enclosing executor deadline still applies.
  • Other selected packages still run after a package fails. Each invocation starts with fresh report output; prior success cannot satisfy a failed launch.
  • Doctest failures block artifact collection even if nextest and coverage generation succeed. Inspect the named report and native diagnostics to repair the example, compilation or provisioned rustdoc/linker environment, then rebuild. Task replacement retains this additional report obligation.
  • The existing coverage report measures nextest execution only: doctest coverage and individual doctest JUnit cases remain unfinished, as do every custom nextest configuration and broader framework support.

Direct test evidence​

oyzu run test produces nextest JUnit, native LLVM Cobertura coverage and Cargo doctest invocation reports, followed by oyzu inspect dist. The real app/workspace reporting step passed on Windows MSVC, Linux and macOS in run 37049720609 at bfa2b7c. This verifies the direct reporting step, not the entire still-running workflow.

Prerequisites​

  • Provision Rust/Cargo with its llvm-tools-preview component and compiler profiler runtime, cargo-nextest 0.9.146 and cargo-llvm-cov 0.9.1.
  • Existing Windows product qualification uses an MSVC compiler and its native linker/SDK for coverage. The local windows-gnu compiler is not supported by this flow: the local Windows GNU Rust 1.94.0 compiler lacks profiler_builtins, and its earlier coverage failure remains a toolchain limitation.
  • A separate windows-gnullvm tiny-project coverage experiment succeeded without MSVC; see native build prerequisites for its scope and remaining qualification limits.
  • Dependencies must already be installed for locked offline Cargo resolution. Tools are not installed by the product. Missing LLVM tools fail before llvm-cov can request a download; explicit LLVM_COV/LLVM_PROFDATA paths can identify provisioned binaries.

How the test task runs​

  • After shared task admission, Cargo's native metadata --no-deps --locked --offline supplies workspace membership and doctest-enabled packages. Static run list never invokes Cargo.
  • The exact implicit cargo test --locked --workspace command receives automatic instrumentation. Arbitrary task replacements retain their bodies and required JUnit/coverage/doctest obligations; they do not waive evidence collection. No Oyzu build/test configuration is needed for the default flow.
  • A temporary nextest profile inherits the project's default configuration and supplies fresh JUnit output; the native .config/nextest.toml is not edited. This uses nextest's native profile inheritance.
  • Project coverage/reporting state is not reused: compilation and coverage use private temporary target directories. Native nextest may retain its ordinary store output on the host.
  • Extra command arguments go to the nextest invocation; doctest selection remains the metadata-selected workspace packages. Alternate nextest profiles, arbitrary Cargo test argument compatibility and filtered doctest selection are not implemented by this initial direct adapter.
  • The compiled Rust adapter is shared by captured and direct execution. It runs nextest, attempts coverage generation independently of a failed test, and runs stable Cargo doctests. Any failed phase fails the task.
  • Doctest reports count package invocations, not individual examples, and doctest execution is not included in nextest coverage.
  • Custom native settings, build scripts and proc macros retain their normal execution semantics. Direct reports disclose host execution and unverified tool identity; Cargo's offline flags are not a host network sandbox. See direct test bundle boundaries.

python tooling/test-rust-direct.py --cli <compiled-path> uses EX-021 and EX-022: implicit task listing, default-profile settings, native JUnit/Cobertura, successful and failed tests, independent doctest failure, unchanged source/configuration and bundle inspection. It requires tooling/design-requirements.txt for report-contract validation. CI explicitly provisions the pinned reporters with tooling/provision-rust-reporting.py after downloading the compiled CLI. The three-host direct-reporting steps passed at bfa2b7c; broader native profile and argument combinations remain outside that probe.

Artifact selection and collection​

With the default captured with.artifacts: all, selected publishable workspace packages produce native <package>-<selected-version>.crate archives.

  • Packages declaring publish = false or an empty publish list do not produce crate archives.
  • Each enabled binary additionally produces <binary>-<selected-version>-<compiler-host>.
  • Explicit with.artifacts: binaries selects only executable outputs and refuses a library-only inventory.
  • The selected version is normally a projected snapshot; resolved registry backreferences retain the affected member's declared version as described below.
  • Manifest names use the existing scoped crate- and bin- identities.
  • Under the default choice, a publishable library-only package has a crate artifact without an invented executable.
  • Duplicate binary names currently fail planning instead of colliding in the output bundle.

Feature-gated binaries​

Cargo's resolved features determine whether a binary with required-features is enabled. An unmet feature gate omits that binary from the artifact plan; enabling the feature through native defaults or with.features includes it. This does not add a feature matrix or new CLI feature-selection syntax. Cargo documents required-features as native target selection.

How binaries are captured​

  • The build adapter consumes Cargo's JSON compiler messages. It matches opaque package IDs and binary target names against a prepared inventory and takes executable paths from native compiler-artifact events.
  • It accepts fresh Cargo cache results as well as newly compiled binaries, requires a successful native process and build-finished event, rejects missing/unplanned/conflicting outputs and verifies each executable is a regular file contained in the target root. It does not guess executable filenames or publish intermediate test binaries.
  • Native binary capture identifies a planned binary by its target-relative Cargo manifest path and target name. This preserves ownership when a prepared target rooted at /workspace executes under /workspace/<target> in a mixed repository. Cargo package IDs remain opaque; Oyzu does not rewrite or parse them. The change fixes the nested-target failure observed by the live logging acceptance probe. The sole version-1 inventory records relative manifest paths; the superseded package-ID inventory reader has been removed.
  • The adapter clears its reserved staging directory before invoking Cargo. Only after all expected binaries are verified does it stage them for the shared final collection step. This prevents a previous executable from satisfying a disabled feature or failed compilation.
  • Native source archive contents are checked in the scenario harness to exclude private .oyzu-build files. Cargo does not automatically exclude arbitrary custom output directories; the captured profile fixes its private output location. Exhaustive custom Cargo include/exclude packaging behavior remains unverified.
  • Task overrides and pre/post hooks retain their existing shared owners. Replacing a native build task must still satisfy its planned artifact obligations; an override does not waive collection checks.
  • No registry publication, signing or promotion is performed by this builder increment.

Registry backreferences​

Captured builds preserve a member's original declared version when Cargo's resolved registry graph contains a dependency on a registry package with that member's name. Cargo package verification re-resolves through the workspace's private packaging registry; a projected prerelease can otherwise conflict with the registry dependency's release range.

  • Only affected members retain declared versions, and local path requirements use those retained versions. Unaffected members still receive their normal snapshot versions.
  • Inactive dependency declarations alone do not trigger preservation.
  • These artifacts remain snapshots. The existing oyzu.dev/versioning evidence records reason: cargo-registry-backreference, the source digest and captured Git/input-scope facts, intent: snapshot and productionEligible: false even when the archive uses a release-shaped declared version.
  • Use the build bundle's source identity and artifact digest to distinguish snapshots with the same native version.
  • This correction does not authorize publication or repair other Cargo dependency cycles. See native qualification.

The pinned clap corpus now completes oyzu build --isolated --full using the rebuilt worker image and exact image override recorded in qualification, delivering eight native crates, a working Linux binary and all three required reports.

  • Installed/default images and public distribution were not updated.
  • Three members retain their declared versions while five retain normal snapshot projection; all eight decisions retain snapshot identity and no release authority.
  • Coverage collection passed at zero of 73 lines, which is not positive application coverage.
  • See the commands, artifacts and limits.

Development-dependency cycles​

Local development-dependency cycles can be packaged in captured builds when their ordinary and build-dependency edges remain acyclic. Oyzu groups only members involved in a development cycle and asks native Cargo to package that group together.

  • The provisional package command uses --locked --offline --exclude-lockfile --no-verify. The provisional archives are admitted only to an invocation-private registry after native index identities and archive checksums match.
  • Oyzu then packages every member separately with native verification enabled, --locked --offline --exclude-lockfile, and requires each final archive to be byte-identical to its provisional counterpart before admitting any group member as a final artifact.
  • Acyclic members retain ordinary per-member packaging and their existing archive contents.
  • Affected cycle archives omit Cargo.lock, so a consumer cannot use cargo install --locked against such an archive; use the source workspace with its original lock or resolve the published package normally. Declared versioned development dependencies remain in the normalized manifest.
  • Ordinary/build dependency cycles, unsupported registry backreferences in a cycle group, changed external identities and native verification failures still stop packaging. See the measured qualification.

When the original lock contains a different registry version of an affected member, the packaging adapter lets native Cargo align its invocation-private lock with checksum-verified workspace archives after their promotion.

  • It uses the original native registry package IDs and precise retained versions, offline; package verification remains --locked --offline.
  • Every resulting identity must be an original captured input or a verified owned archive. Native pruning is reported, and the execution copy's original lock/configuration are restored on success or failure. Source checkout files and the captured registry remain unchanged.
  • Same-version archive collisions, incompatible native ranges or uncaptured external changes still fail and block final artifacts.
  • Native Windows drive/UNC path prefixes are translated only at the Cargo configuration boundary; non-UTF-8 registry paths fail rather than losing identity.

Locked Rust compiler handoff​

A [tools] rust = "1.95.0" declaration in oyzu.toml selects the matching oyzu.lock environment for the captured target scope and profile.

  • The current container worker consumes a linux/<architecture>/gnu installation from the workspace's .oyzu/tools store. This is the compiler's execution platform; artifact platforms in build.yaml do not change it into a macOS or Windows tool.
  • Only a Rust-only declared tool selection is supported by this initial handoff.

What is verified and used​

Before package acquisition or Cargo execution, Oyzu verifies the locked request, current backend/installer identity, complete installation receipts and payload contents.

  • It leases the installation while copying it into the private dependency snapshot, then verifies the copied tree against the receipt.
  • Preparation and build actions use its Cargo, rustc and rustdoc; the plan fixes their command environment.
  • The dependency evidence records the request, selection, installation, backend, lock and copied-tree identities. The live tool store is not mounted in containers.
  • On Unix controllers, the Linux restoration container runs as the owner of its private input directory, following the shared executor's user mapping. Its input remains read-only and private; restoration keeps networking disabled, a read-only root filesystem and all capabilities dropped. This avoids permission failures when the controller's temporary files are inaccessible to the image's default user. Windows retains its existing Docker user behavior.

When it fails​

  • Missing or stale locks, missing worker distributions, absent installations, unsupported layouts and changed payloads fail without falling back to image Rust.
  • This path does not resolve versions, install tools, edit the lock or use the network for tool restoration. Provision the matching worker installation first.
  • Existing oyzu install currently provisions its host only; installing Linux compiler selections from a Windows host is still unfinished.
  • No new project-specific build flag is required. Builds without explicit tool requests retain the existing provisioned-image behavior.
  • The image continues to provide native OS prerequisites, format/lint and reporting utilities; this handoff does not qualify those as locked tools or establish cross-compilation support.

Verification​

  • A bounded Linux Rust 1.99.1 app proof passed two full isolated builds, native crate verification, JUnit 1/1 and application coverage 6/9 lines. The delivered binary ran read-only without networking and printed Hello, Oyzu!; both artifact digests and original source bytes were unchanged on repeat.
  • The flow reused a previously verified packaged compiler, then restored it into a read-only action volume. The new controller and unchanged worker have separately recorded source identities. See the qualification and limits; this does not establish fresh installation on every build, the full Rust corpus or Windows/full-Bookworm worker qualification.
  • On a Linux controller using the local Docker engine, python3 tooling/test-build-model.py --cli <compiled-cli> --locked-rust <Rust-1.95-sysroot> uses a real compiler with explicitly synthetic test lock/receipt provenance. It proves plain oyzu build produces and executes the feature-enabled binary, records compiler 1.95 despite image Rust 1.94, and rejects missing/stale locks and a corrupted payload before actions.
  • This fixture does not prove installation or download provenance. Native Windows cannot attest the Linux executable modes in its NTFS store; automatic Linux worker provisioning remains unfinished.

Tool requirement evidence​

Build manifests include oyzu.dev/tool-requirements for selected Rust targets.

  • The static detector reads literal package.rust-version and Rust toolchain channel constraints with source digests and field locations, in every toolchain-file form rustup accepts (details).
  • It reports compiler components, platform standard libraries, and selected formatting, lint and test requirements. Fast builds omit unselected quality helpers; explicit toolchain components remain requirements.
  • Inherited Cargo MSRV currently requires workspace metadata and fails with an explicit diagnostic rather than being ignored.

For a declared, locked Rust compiler, captured preparation uses the same resolved build-stage requirements as pinning and preflight when choosing its recipe.

  • A test-enabled build therefore requires the locked llvm-tools-preview component, even when the lock also contains a smaller fast-build recipe. A fast build can still select that smaller recipe.
  • An incomplete lock refuses preparation; adding an environment override or relying on the image's different compiler does not satisfy the declared Rust selection.
  • Requirement records alone do not prove installation. The selected compiler recipe goes through normal admission and materialization before capture.
  • The current captured test helpers (cargo-nextest and cargo-llvm-cov) remain supplied by the provisioned worker image.
  • The bounded exact-engine proof verified Rust 1.99.1 full-recipe selection, accepted native reports and a runnable Linux x86-64 artifact while preserving both locks.

Experimental cross-platform execution​

Explicit artifact platforms select the local Linux cross-compilation image.

  • The six supported selections are linux/x86_64, linux/arm64, darwin/x86_64, darwin/arm64, windows/x86_64 and windows/arm64 (the image builds musl and LLVM MinGW; another ABI is refused).
  • The curated native baselines are musl for Linux, Apple Darwin with a macOS 13 deployment target, and LLVM MinGW for Windows. These baselines remain experimental until the real CLI flow has passed; they do not establish older operating-system compatibility.

After building the standard reporting image above, provision the cross worker:

docker build -f tooling/images/rust-cross.Dockerfile -t oyzu-toolchain/rust-cross:v1 .

This is local environment setup. The build command uses that image automatically for explicit platforms; a missing image fails with a provisioning diagnostic. The image contains the native cross linkers and SDK prerequisites, while the project's locked compiler and target standard libraries are restored separately.

Compiler and worker​

  • The compiler must be declared in oyzu.toml and installed into oyzu.lock. oyzu install on Windows also provisions the local Linux compiler distribution when the project declares a Rust build.
  • The worker uses the embedded mise library; no separate mise executable is invoked.
  • Within one build, equivalent locked selections share compiler verification. The verified archive is extracted once per archive digest and worker image into a build-owned Linux volume, mounted read-only for preparation and execution. Each mount checks its archive digest; Cargo homes, outputs and workspaces remain private.
  • Normal build completion or failure releases the volume; the persistent oyzu-tools-* volumes are reused by identity and superseded ones are pruned (see build logging). Execution runs without network access.
  • The complete project entry point remains oyzu build, with platforms and builder options in build.yaml.
  • Shared compiler restoration is automatic and does not add build YAML options. Reuse is scoped to one invocation; it does not deduplicate target metadata, crate acquisition or complete preparation, and does not provide a persistent compiler cache.

Resources​

  • Explicit cross-platform Rust actions currently reserve 8 GiB and allow up to two hours per action. The executor caps target concurrency using Docker's available memory, retaining 25% for engine/controller headroom; a Docker engine needs about 11 GiB to admit one such action. These are builder-declared execution resources recorded in the plan, not additional project flags. Locked compiler preparation reserves 4 GiB.
  • The CLI project's native Cargo test profile retains line-level debug information instead of full type debug data, reducing linker pressure from the embedded mise dependency graph. Coverage instrumentation and required test/report gates remain enabled. An earlier cold self-build exceeded a one-hour test-action limit while linking and starting tests; that failed run is not a successful build.
  • Tests and coverage execute on the Linux worker. Cross-compiled executables are checked for the requested binary format and architecture before collection; this is compilation evidence, not a claim that tests ran on each target OS. macOS and ARM runtime qualification remain separate.
  • Rust uses a private Linux scratch filesystem for Cargo extraction and Git checkouts. It keeps a 2 GiB minimum size ceiling and grows to match larger action memory reservations; the reservation itself does not increase. Where cgroups are available, their limit covers process and tmpfs use together.
  • Git acquisition copies back only the bare object databases, keeping registry extraction and upstream symlinks off Windows host mounts. This accommodates the CLI's measured 1.27 GiB of unpacked locked registry inputs without imposing a smaller fixed scratch ceiling.
  • Captured build inputs and execution workspaces live under the repository's .oyzu state directory, on the same volume as the project, rather than filling the operating system's temporary volume. They remain private run state and are excluded from source snapshots and published bundles.
  • Formatting uses the same read-only locked compiler mount as compilation, tests and lint; it never adds Cargo feature-selection arguments to cargo fmt.

What the probes check​

  • Artifact probe: gated binaries disabled/enabled by Cargo defaults, exact executable bytes, launching collected executables, fresh cache results, source archive exclusions, missing outputs, redirected output paths and compiler failures. The Rust example variants supply the native inputs. Rust planner checks cover per-package versions, feature resolution and fixed output facts.
  • Doctest probe: real stable Cargo against a local workspace, checking successful examples, assertion/compile failures, independent package outcomes, missing-tool stale-report replacement and unchanged inputs.
    • Its --cargo option accepts a command on PATH or an executable path. Relative paths are anchored before changing into the fixture, and symlinks retain the Cargo invocation name required by rustup. Unix probes additionally execute through a temporary Cargo symlink.
    • Windows verification passed with Rust 1.94.0; the local GNU toolchain required its provisioned linker setting in RUSTDOCFLAGS as well as RUSTFLAGS.
    • Run 36971869232 passed all three CLI jobs, including the corrected native doctest probe and local-workspace packaging test.
    • The captured Linux suite requires failed doctests to block artifacts despite successful nextest results; isolated doctest acceptance is still pending.
  • Rust test suite: also gives native Cargo a fresh home and an acquired fixture registry, then runs tests, Clippy and verified packaging offline. It checks unchanged source lock bytes and rejection of corrupted archives from a fresh cache. Acquisition checks reject unsupported sources before fetching and mismatched index/archive checksums.
  • Mixed-packaging probe: uses native Cargo to create a registry fixture, then packages a three-member snapshot workspace against it with no downloads. It checks archive contents, locked external dependencies, repeatability, source/registry/configuration preservation, rejected index tampering and failures during native verification. GitHub Actions runs it on each CLI host. The checked-in EX-022 registry variation additionally exercises the captured CLI build, reports, delivered binary and failure-gated collection; passing the host probe alone does not prove that isolated scenario.
  • Compiled-CLI Linux scenario suite: builds applications, libraries and local workspaces, executes delivered binaries, checks snapshot crate contents, measures application coverage, verifies repeatability and confirms failed tests/formatting block collection. The registry example adds a locked public dependency with no Oyzu configuration; its CI checks require retained dependency identity, versioned outputs, JUnit/coverage, unchanged inputs and rejection of a modified lock checksum. New registry and feature-gate scenarios must pass that suite before being described as verified captured behavior. Native host checks alone do not prove isolated build acceptance.

Remaining work​

Remaining work includes private/alternate Cargo registries, private Git sources and credentials, persistent acquisition reuse, full feature/profile/platform matrices, doctest coverage/individual-case reporting and broader test-framework support, custom task artifact production, release policy, publication, remote caching and complete authored-scenario acceptance. The build goal remains broader than this implementation increment.
