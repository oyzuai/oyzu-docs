Artifacts, bundles and evidence

A build should still be explainable after the terminal scrollback is gone. Every oyzu build finishes by writing a bundle to dist/: the artifacts it produced, the reports its checks collected, and machine-readable records of what was planned and what actually happened. The previous bundle is kept in history. oyzu inspect checks a bundle, and oyzu history finds older ones.

The words​

TermMeaning
ArtifactAn output identified by its digest: a binary, a package, an image archive, a chart
ReportA collected test (JUnit) or coverage result, attributed to the action that produced it
BundleThe dist/ folder: manifest, plan, envelope, logs, artifacts and reports
Manifestdist/manifest.json, the record of actual outcomes, including failures and reused results
Plandist/plan.json, the frozen executable plan the build ran
ReceiptThe summary at the end of a build's output: outputs, tests, coverage, result and where the evidence lives
InvocationOne run of the CLI, with its own ID; a reused result keeps the ID of the run that originally produced it

The bundle layout​

dist/
  manifest.json  plan.json  envelope.json  logs/
  cli/windows/x86_64/oyzu.exe
  cli/windows/x86_64/reports/junit.xml
  docs/windows/x86_64/application-0.1.0/

Every artifact a target produces, and that target's reports, is written below dist/<target>/<platform>/, with the platform in canonical os/arch form. The layout is the same for local, multi-platform and CI builds, so bundles built on different machines merge without collisions. Output a builder declares platform-independent goes under any. The manifest and plan record each artifact's bundle-relative path, and every consumer (oyzu inspect, publication, the cache) reads that recorded path rather than assuming a layout. See the bundle layout.

Each artifact record also carries the build profile it was produced with, development or optimized. A native executable, such as a Rust or Go binary, is checked when it is collected: it must be a valid ELF, Mach-O or PE file for its target platform and architecture, without being run, so cross-built binaries are checked too.

Oyzu never overwrites a dist/ it did not create: an existing application-owned dist must be moved by its owner first. While a build is writing, it holds a lock on .oyzu/build.lock, so two builds in one workspace cannot interleave.

Reading the receipt​

The end of a build's output is a receipt. From a real two-target Go build:

Tests run now  2 passed · 0 failed · 0 skipped (2 collected reports)
Coverage    project-api: 50.0% (1/2 statements)
Coverage    project-worker: 50.0% (1/2 statements)

ok      Build succeeded   2 targets · 8 executed · 16.1s
  api/     ok      1 target  12.3s
  worker/  ok      1 target  12.3s
  Details  dist/manifest.json · dist/logs/events.jsonl · invocation 56104-1792534255028904600-1

(Captured on Windows 11, NO_COLOR=1, redirected.) The receipt follows a few strict rules:

  • Fresh and reused are separate. Tests from a restored result appear under "Reused test evidence … not run now", never under "Tests run now".
  • No coverage is not good coverage. A report with nothing measurable is not shown as a positive percentage.
  • Blocked is not failed. An action that never ran because something upstream failed is reported as blocked, not as a failure of its own command.
  • A failed build still leaves evidence. The manifest records what failed, its exit code and log path, alongside what succeeded.

Inspecting a bundle​

oyzu inspect dist
✓ Bundle contents verified · build succeeded
Run 48672-1792534299806619100 · source sha256:cc851a1f8e9e · uncommitted changes

Targets
Target          Builder  Platform       Path
project-api     go/app   windows/amd64  api
project-worker  go/app   windows/amd64  worker

Actions
Action                       Status     Exit  Gate
project-api:build            succeeded  0     required
project-api:test             succeeded  0     required
…

Reports
Report                   Path                                 Status
project-api:test         project-api/reports/junit.xml        collected
project-api:coverage     project-api/reports/coverage.out     collected
…

Verified: every recorded file matches its digest. This does not show who produced the build or that it may be released.

(Captured on Windows 11 with a development build of the CLI that predates the per-platform folders described above, so its report paths omit the platform; trimmed.) inspect does more than compare digests. It requires that every planned artifact and every required action and report is present, that the manifest agrees with the frozen plan, and it re-parses each report with the same parsers and gates the build used, so an edited or failing report fails inspection.

What it does not establish is just as important, and the last line says so on purpose: integrity of the recorded files is not proof of who produced them, that they were built in trusted CI, or that they may be released. Trust and release eligibility follow verified evidence and policy, not a passing local inspection.

History​

When a new bundle is finalized, the previous dist/ moves to .oyzu/history/<run-id> and the new one takes its place. Nothing is appended to an old manifest.

oyzu history
Invocation evidence
Invocation / run             Outcome    Scope                  Started
48672-1792534296043691800-1  succeeded  2 targets · 8 actions  2026-10-20T22:11:39.806619100+00:00
34752-1792534281771659800-1  succeeded  2 targets · 8 actions  2026-10-20T22:11:30.243954200+00:00
56104-1792534255028904600-1  succeeded  2 targets · 8 actions  2026-10-20T22:10:58.264140800+00:00
  0 older entries omitted · 0 incomplete bundles
  Next: oyzu history <ID> for a bounded summary and evidence paths
  Recorded observations; this summary does not verify artifact contents.

oyzu history <id> shows a bounded summary of one invocation: action counts, fresh and reused test totals, warnings, exceptional actions, the recorded selection, why each action ran or was reused, and the paths of its evidence. History reads recorded facts; a later source change or oyzu cache clear never rewrites what an earlier invocation decided. It lists at most twenty entries, and there is no automatic expiry: bundles stay until you remove them.

History is local. Nothing is uploaded or shared with another user.

The records, briefly​

FileContains
manifest.jsonTargets, actions and their outcomes (succeeded, failed, blocked, reused with a reuse record), artifacts with digests and profiles, reports, selection, policy overrides
plan.jsonThe frozen executable plan: actions, commands, inputs, outputs, platforms and executors
envelope.jsonThe execution envelope for the invocation
logs/Native stdout and stderr per action and events.jsonl, the structured event journal

Use oyzu inspect dist --json or oyzu build --json to read them programmatically; see the CLI output contract.

Early implementation

Bundles are written with two renames, which is not a power-loss-safe transaction, and history has no retention limit yet. Remote run history is not part of local history. See verification and limits.

Commands​

CommandUse it to
oyzu inspect or oyzu inspect distVerify a bundle's recorded files, plan agreement and reports
oyzu inspect <bundle-dir>Inspect a bundle in history or a retained staging directory
oyzu historyList retained invocations
oyzu history <id>Summarize one invocation with evidence paths
oyzu build --explainSee why each stage ran or was reused, after a build
