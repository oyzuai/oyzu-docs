The action cache and affected builds

Most builds change very little. Oyzu notices which targets' inputs are unchanged since an earlier successful build and restores their results instead of running them again, with no configuration: you never write cache keys or per-language cache paths. Separately, --affected narrows a build to the targets a Git change touches. Both depend on the same idea: the declared build graph.

What a cache key covers​

A target's key is a SHA-256 over frozen plan values and captured inputs:

InputNotes
The target's actionsCommand, environment, working directory, platform, limits, report contracts and the configuration digest
Source in scopeThe target's own folder, the folders of targets it declares as prerequisites, any declared inputs, and files no target owns (root build.yaml, oyzu.toml, locks)
ToolsThe resolved identities: on the host path, the digest of oyzu.lock and the host platform; in containers, the toolchain image's content digest
DependenciesThe content of the prepared dependency snapshot, not where or when it was prepared
BuilderThe builder's identity (the Oyzu executable's digest, or an external builder plugin's identity)
Consumed artifactsDigests of artifacts materialized from producer targets
ExecutorAny executor other than the host

Host paths, run IDs, timestamps, credentials and the number of parallel jobs never enter a key. Two checkouts of the same commit in different folders, worktrees or branches therefore share hits.

What is not reused​

The cache is conservative. A target simply runs, and the output says why, when:

  • it contains an authored task or task override that does not ask to be cached (cache = true with outputs), or a hook without declared outputs, because Oyzu cannot see their effects;
  • it uses secret environment values;
  • you pass --no-cache or set cache.local = false.

Failed, blocked and cancelled targets are never stored. A target is stored only after all its actions succeeded and its reports were collected. Direct oyzu run task executions are never cached.

A hit never skips a gate​

A reused action keeps its original artifacts byte for byte (each is re-verified against its recorded digest), its original reports and their producer, and a reuse record naming the original run, key and completion time. On restore, every report is parsed again and judged by the current contract: if your coverage minimum went up and the old report no longer passes, the entry is rejected and the target runs normally. Policy and required checks apply exactly as they would to fresh work.

What it trusts​

The cache trusts the declared target graph. If a build script reads another target's folder without a declared edge (depends_on, materialize, a task dependency), an edit there does not invalidate it. Declare the relationship, or use --no-cache, for builds that read across folders.

On the host path, a tool that is not in oyzu.lock, such as a system C compiler used by cgo, is outside the key too. Use --no-cache after changing one.

Asking why​

Two read-only views name the first key component that differs from the last build of the same thing:

$ oyzu cache explain project-worker
Cache key explanation  project-worker
​
  project-worker (whole target)
    Key        d2ffb95e8f68 · since run 43340-1792553125626099300 · last seen run 43340-1792553125626099300 (2026-10-21T03:25:25Z)
    Result     stored · the next build with these inputs reuses it
    Changed    since run 60260-1792553111917879400: source files in scope changed (also: action definition: project-worker:build argv, project-worker:build extensions and 3 more)
​
Keys come from the toolchain, dependencies, stage definition, source in scope and consumed outputs.
Use `oyzu build --explain` to see this for every stage of a build.

oyzu build --explain prints the same reasoning for every stage after a build, for example project-worker:build — Executed … Reuse: source files in scope changed. See explaining reuse.

Per target and per action​

For most builders the unit of reuse is the target: all its actions are restored together, or none. For targets whose actions carry a stage contract from static analysis (today node/package on the captured path), each action has its own key. A re-run action that produces the same workspace changes leaves its dependents' keys unchanged, so they are still reused. See per-action reuse.

Where the cache lives​

The local store is per user: %LocalAppData%\Oyzu\cache\actions on Windows, ~/Library/Caches/Oyzu/actions on macOS and $XDG_CACHE_HOME/oyzu/actions on Linux, with a 10 GiB retention budget. cache.dir in user configuration moves it.

$ oyzu cache status
Action cache
​
  Location   C:\Users\you\AppData\Local\Oyzu\cache\actions (default per-user location)
  Entries    552 results · 2841 blobs
  Size       9.9 GiB of 10.0 GiB retention budget
  Docker     5 images · 2.6 GiB of 20.0 GiB image budget (cache.dockerMaxMiB)
  Local use  enabled
​
Reuse is local to this user and machine. Ephemeral CI runners start empty; shared caching is a later milestone.
Use `oyzu cache clear` to empty it, or `oyzu build --no-cache` to bypass it once.

oyzu cache clear removes every cached result; build bundles are never touched.

Sharing results​

An experimental remote OCI cache shares per-action results through an ordinary container registry. cache.remote (an oci:// URL) is accepted only from user, machine or administrative configuration, or the OYZU_CACHE_REMOTE variable, never from a project file; credentials come from OYZU_CACHE_TOKEN or a CI job's ID tokens. cache.ciRemote names a repository that only CI writes and everyone reads first. Entries are not signed: a remote hit is a development result, not trusted CI evidence. See remote OCI cache.

Affected builds​

oyzu build --affected <git-ref> compares your working tree with a local Git commit, selects the targets whose files changed, adds their declared consumers, then adds the producers those need. Every selected target gets its normal checks.

$ oyzu build --affected HEAD
…

  changed     1 target   project-api · 1 changed path
  unaffected  1 target   not built · -v lists them

(A real capture after editing api/main.go; the Prepare, Facts and Plan sections are trimmed.) --affected and the cache complement each other: affected selection decides which targets to consider, and the cache can still reuse unchanged results among them.

Selection falls back to the whole workspace, and records why, when it cannot be precise: the baseline is not available locally, a changed file belongs to no target, or build, configuration or lock files changed. Oyzu never fetches the reference for you. Changes to tools or the environment outside Git are not inferred; run a full build after those. See affected target builds.

Early implementation

The action cache is experimental. Regression verification runs on Linux, with bounded Windows measurements; reuse is local to one user and machine unless you configure the experimental remote cache. See the local action cache reference for measured scope and named follow-ups.

Commands​

CommandUse it to
oyzu buildReuse unchanged results automatically
oyzu build --no-cacheRun every action; read and write nothing
oyzu build --explainSee why each stage ran or was reused
oyzu cache explain <target>See why a target's key last changed
oyzu cache status / oyzu cache clearInspect or empty the local store
oyzu build --affected <ref>Build only what changed since a commit
