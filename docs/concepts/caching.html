The action cache and affected builds

Most builds change very little. Oyzu notices which targets' inputs haven't changed since an earlier successful build and restores their results instead of running them again. There's nothing to configure: you never write cache keys or per-language cache paths. Separately, --affected narrows a build to the targets a Git change touches. Both rely on the declared build graph.

Note: The action cache is experimental. It works on Linux and Windows, and results are reused only on the same machine and user account unless you set up the remote cache.

Reuse in practice​

What a cache key covers​

A target's key is a SHA-256 hash over its planned actions and inputs:

InputNotes
The target's actionsCommand, environment, working directory, platform, limits, required reports and the configuration digest
Source it readsThe target's own folder, the folders of targets it declares as prerequisites, any declared inputs, and files no target owns (root build.yaml, oyzu.toml, locks)
ToolsOn your machine, the digest of oyzu.lock and the platform; in containers, the execution image's content digest and each locked tool's identity
DependenciesThe content of the prepared dependencies, not where or when they were prepared
BuilderThe builder's identity (the oyzu executable, or an external builder plugin)
Consumed artifactsDigests of artifacts placed from other targets
ExecutorAny executor other than your own machine

Paths, run IDs, timestamps, credentials and the number of parallel jobs never enter a key. Two checkouts of the same commit in different folders, worktrees or branches share results.

What isn't reused​

The cache errs on the side of running. A target runs, and the output says why, when:

  • it contains a task you wrote that doesn't ask to be cached (cache = true with outputs), or a hook without declared outputs, because Oyzu can't see what they do;
  • it uses secret environment values;
  • you pass --no-cache or set cache.local = false.

Failed, blocked and cancelled targets are never stored. A target is stored only after all its actions succeeded and its reports were collected. oyzu run task runs are never cached.

A reused result still passes every check​

A reused action keeps its original artifacts byte for byte (each checked against its recorded digest), its original reports, and a record naming the original run. Every report is checked again against the current rules: if you raised your coverage minimum and the old report no longer passes, the cached result is rejected and the target runs normally. Policy and required checks apply exactly as they would to fresh work.

What it trusts​

The cache relies on the declared target graph. If a build script reads another target's folder without a declared link (depends_on, materialize or a task dependency), an edit there doesn't invalidate it. Declare the relationship, or use --no-cache, for builds that read across folders.

On your machine, a tool that isn't in oyzu.lock, such as a system C compiler used by cgo, isn't part of the key either. Use --no-cache after changing one.

Asking why​

Two read-only views name the first part of the key that changed since the last build of the same thing:

$ oyzu cache explain project-worker
Cache key explanation  project-worker
​
  project-worker (whole target)
    Key        d2ffb95e8f68 · since run 43340-1792553125626099300 · last seen run 43340-1792553125626099300 (2026-10-21T03:25:25Z)
    Result     stored · the next build with these inputs reuses it
    Changed    since run 60260-1792553111917879400: source files in scope changed (also: action definition: project-worker:build argv, project-worker:build extensions and 3 more)

oyzu build --explain prints the same reasoning for every stage after a build. See explaining reuse.

Per target and per action​

For most builders, the target is what gets reused: all its actions are restored together, or none. Some targets (today, node/package builds in a container) give each action its own key, so an action that re-runs but produces the same result leaves the actions after it reusable. See per-action reuse.

Where the cache lives​

The local cache belongs to your user account: %LocalAppData%\Oyzu\cache\actions on Windows and $XDG_CACHE_HOME/oyzu/actions on Linux, with a 10 GiB size budget. Set cache.dir in user configuration to move it. oyzu cache status shows its size; oyzu cache clear removes every cached result and never touches build bundles.

Sharing results​

An experimental remote OCI cache shares results through an ordinary container registry. Set cache.remote (an oci:// URL) in user, machine or administrative configuration, or the OYZU_CACHE_REMOTE variable; a project file can't set it. Credentials come from OYZU_CACHE_TOKEN or a CI job's ID tokens. cache.ciRemote names a repository that only CI writes and everyone reads first. Remote entries aren't signed, so a remote hit counts as a development result, not a trusted CI result. See remote OCI cache.

Affected builds​

oyzu build --affected <git-ref> compares your working tree with a local Git commit, selects the targets whose files changed, adds the targets that depend on them, then adds what those need. Every selected target gets its normal checks.

$ oyzu build --affected HEAD
…
── Selection ───────────────────────────────────── compared with HEAD at 2f721a7
  changed     1 target   project-api · 1 changed path
  unaffected  1 target   not built · -v lists them
​
── Plan ───────────────────────────────────────────────────────── 1 of 2 targets
                format   lint   test   build   why
  project-api   skip     skip   skip   run     changed
…

--affected and the cache work together: --affected decides which targets to consider, and the cache can still reuse unchanged results among them.

Oyzu falls back to building every target, and says why, when it can't be precise: the commit isn't available locally, a changed file belongs to no target, or build, configuration or lock files changed. It never fetches the commit for you. Changes to tools or the environment outside Git aren't detected; run a full build after those. See affected builds.

Commands​

CommandUse it to
oyzu buildReuse unchanged results automatically
oyzu build --no-cacheRun every action; read and write nothing
oyzu build --explainSee why each stage ran or was reused
oyzu cache explain <target>See why a target's key last changed
oyzu cache status / oyzu cache clearInspect or empty the local cache
oyzu build --affected <ref>Build only what changed since a commit
