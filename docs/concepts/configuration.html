Configuration layers

Oyzu configuration is split by one question: does this setting change what ships, or only how it's built? What ships goes in build.yaml and is the same for everyone. How, where and how strictly go in the oyzu.toml cascade, which can vary by folder, build context and person, within limits an organization can set. Exact tool versions go in neither: Oyzu writes them to oyzu.lock.

Many projects need no configuration at all. Add a file only when you have a reason.

The files​

FileCommittedHolds
Native files (go.mod, Cargo.toml, rust-toolchain.toml, package.json …)yesWhat your ecosystem already says: modules, dependencies, toolchain pins
build.yamlyesWhich builds exist, their builders, platforms and connections
oyzu.tomlyesTools, checks, tasks, environment, executors and caching for its folder and below
oyzu.local.tomlnoYour personal overrides for that folder
User configuration (config.toml)noYour defaults for every project, and machine-only settings such as cache locations
Machine and administrative filesmanagedOrganization defaults and limits
oyzu.lockyesExact tool versions and archive digests, written by Oyzu

The user configuration file is %AppData%\Oyzu\config.toml on Windows and ~/.config/oyzu/config.toml (or under $XDG_CONFIG_HOME) on Linux. OYZU_USER_CONFIG points at another file. See files and persistent state.

Which file a setting belongs in​

Ask, in order:

  1. Does changing it change what ships (the artifact, its name, its platform or ABI, or how builds connect)? Put it in the native file if that file can say it, otherwise in build.yaml.
  2. Otherwise, could it differ by folder, context or person, or need an organizational limit? Put it in the cascade: oyzu.toml for the team, oyzu.local.toml or user configuration for you, and policy or [constraints] for limits.
You want toWrite it in
Ship cli for Linux x86_64 and arm64build.yaml: platforms: [linux/x86_64, linux/arm64]
Make worker wait for apibuild.yaml: depends_on: [api]
Use Go 1.27oyzu.toml: [tools] go = "1.27" (or the native go.mod)
Turn off format checks under legacy/legacy/oyzu.toml: [checks] format = "off"
Require tests in release buildsoyzu.toml: [context.release.checks] tests = "required"
Use two build jobs on your laptopoyzu.local.toml: [build] jobs = 2
Stop any folder lowering release testsroot oyzu.toml: [constraints."checks.tests"]

When one file names something another declares, such as a task key naming a build, Oyzu checks the name before anything runs and reports the file, line and nearest valid name.

How the cascade resolves​

Later sources win:

  1. Built-in defaults
  2. Organization defaults
  3. Machine configuration
  4. User configuration
  5. oyzu.toml files from the project root down to the target's folder, nearest last
  6. oyzu.local.toml files on the same path
  7. Flags and environment variables such as OYZU_BUILD_JOBS

Then constraints apply on top, first the project's own [constraints], then organization policy. A constraint is a limit, so a nearer file can't get around it.

Within a file, [context.<name>] values beat base values when that context applies, and a profile you choose explicitly beats both. Arrays replace rather than merge.

Most settings resolve per target, from that target's folder chain: a value in docs/oyzu.toml applies to the targets under docs/. A few apply to the whole run (such as build.jobs and the cache.* settings), a few may only be set in the root oyzu.toml (publish.* and [constraints]), and a few can never come from a project file, so a cloned repository can't redirect them (such as cache.dir, cache.remote and platform.url). See registered settings for every key.

oyzu config explain <setting> shows the effective value and every source that set it, in order.

Personal overrides​

oyzu.local.toml is for you: a smaller job count, a personal cluster to load images into. Keep it out of version control. In a detected CI context, Oyzu ignores local files and user build settings, so a CI run doesn't depend on whoever set up the runner. --local-overrides includes them anyway.

Checks and contexts​

Every build has one context: local, pr, ci or release. Oyzu detects it from CI variables (GITHUB_ACTIONS, GITLAB_CI, TF_BUILD, Jenkins, Buildkite and others), using pr for a pull or merge request and release for a tag. With no CI signal it is local. oyzu build --context <name> or OYZU_CONTEXT sets it; in detected CI you can raise the context but not lower it. The context is only a hint: it never grants credentials, cache access or permission to publish.

The context matters mostly for checks. Each check (tests, coverage, lint, format) has a level:

LevelRuns inA failure
offnever; its tools aren't even installednothing
advisorybuilds that run every checka CHECK_ADVISORY warning; the build still succeeds
enforce (default)builds that run every checkfails the build
requiredevery build, including fast local buildsfails the build

Local builds are fast builds that run only required checks. Builds in pr, ci and release, and oyzu build --full, run every check that isn't off.

# oyzu.toml
[checks]
lint = "advisory"
coverageMinimum = 50

[context.release.checks]
tests = "required"
coverageMinimum = 90

See check levels and per-context values.

Profiles and toolsets​

A profile is a named set of settings, chosen with --profile <name>, OYZU_PROFILE or profile.default. The built-in ci profile runs every check. A profile grants no extra permissions and can't change tools. To also test on another runtime version, such as Node 24, use a toolset.

Constraints and policy​

A constraint limits a setting after every ordinary value is applied. It can lock a value, set a minimum or maximum, add required members, or restrict allowed values (anything else is refused with CONFIG_OVERRIDE_DENIED). A project can make a rule hold in every folder with a [constraints] table in its root oyzu.toml:

# root oyzu.toml only
[constraints."checks.tests"]
minimum = "required"
when = { context = ["release"] }

A folder that sets tests = "advisory" still runs required tests in a release build, and Oyzu prints a CONFIG_CONSTRAINT_OVERRIDE warning. Organization policy works the same way and always wins over project constraints. A tool version outside an allowed set is refused, not quietly swapped. Every override shows in oyzu config explain, the plan and the bundle. See policy constraints and selectors and project constraints.

Secrets stay out​

Project configuration never holds secret values. [env] values are plain strings and can end up in build inputs and records. Credentials for caches, registries and the platform come from environment variables or sign-in. See trusted environment and credential destinations.
