Configuration layers

Oyzu configuration is split by one question: does this setting change what ships, or only how it is built? What ships goes in build.yaml and is the same for everyone. How, where and how strictly goes in the oyzu.toml cascade, which can vary by folder, by build context and by person, within limits an organization can set. Exact tool versions go in neither: Oyzu writes them to oyzu.lock.

Many projects need no configuration at all. Add a file only when you have a reason.

The files​

FileCommittedHoldsScope
Native files (go.mod, Cargo.toml, rust-toolchain.toml, package.json …)yesWhat your ecosystem already says: modules, dependencies, toolchain pinsTheir own rules
build.yamlyesWhich builds exist, their builders, platforms and connectionsWhole project, by build name
oyzu.tomlyesTools, checks, tasks, environment, executors, cachingThe folder it is in and everything below
oyzu.local.tomlnoYour personal overrides for that folderYour checkout only
User configuration (config.toml)noYour defaults for every project, and machine-only settings such as cache locationsEvery project you build
Machine and administrative filesmanagedOrganization defaults and protected constraintsEvery project on the machine
oyzu.lockyesExact resolved tool versions and archive digests, written by OyzuWhole project

The user configuration file lives at %AppData%\Oyzu\config.toml (the Roaming AppData folder) on Windows, ~/Library/Application Support/Oyzu/config.toml on macOS, and $XDG_CONFIG_HOME/oyzu/config.toml (falling back to ~/.config/oyzu/config.toml) on Linux. OYZU_USER_CONFIG can point at another absolute path, which is useful for disposable environments. See files and persistent state.

Which file a setting belongs in​

Ask, in order:

  1. Does changing it change what ships: the artifact, its name, its platform or ABI, or how builds connect? Then it belongs in the native file if that file can say it, otherwise in build.yaml.
  2. Otherwise, could it differ by folder, by context or by person, or need an organizational limit? Then it belongs in the cascade: oyzu.toml for the team, oyzu.local.toml or user configuration for you, and policy or [constraints] for limits.

Some examples:

You want toWrite it in
Ship cli for Linux x86_64 and arm64build.yaml: platforms: [linux/x86_64, linux/arm64]
Make worker wait for apibuild.yaml: depends_on: [api]
Use Go 1.27oyzu.toml: [tools] go = "1.27" (or the native go.mod)
Turn off format checks under legacy/legacy/oyzu.toml: [checks] format = "off"
Require tests in release buildsoyzu.toml: [context.release.checks] tests = "required"
Use two build jobs on your laptopoyzu.local.toml: [build] jobs = 2
Forbid lowering release tests anywhere in the reporoot oyzu.toml: [constraints."checks.tests"]

When one file names something another file declares, such as a task key naming a build or a publish selector naming an output, Oyzu checks the name before anything runs and reports the file, line and nearest valid name. See names that cross files.

How the cascade resolves​

Values are applied in this order; later sources win:

  1. Built-in defaults
  2. Verified corporate defaults and protected local administrative defaults
  3. Machine configuration
  4. User configuration
  5. oyzu.toml files from the project root down to the target's folder, nearest last
  6. oyzu.local.toml files on the same path
  7. Invocation inputs: flags and environment variables such as OYZU_BUILD_JOBS

Then constraints are applied on top of everything: first the project's own [constraints], then administrative policy. A constraint is a limit, not a value, so a nearer file cannot get past it.

Within one file, a value under [context.<name>] beats the base value when that context is in effect, and a profile you chose explicitly beats both. Arrays replace rather than merge, a task record replaces the whole task, and [overrides] remove = ["env.NAME", "tasks.NAME"] removes an inherited entry.

Per target, per build, or root only​

Most settings resolve per target, from that target's folder chain, exactly like tool pins: a value in docs/oyzu.toml applies to the targets under docs/. There are no target-keyed sections and nothing in build.yaml.

A few settings describe the whole run and resolve once per build: build.jobs, build.isolation, ui.color, profile.default and the cache.* family. A component folder may still set build.jobs; the build uses the smallest value among the root and the selected targets.

A few are root only: publish.* and [constraints] may appear only in the project root's oyzu.toml (and, for publish.*, its oyzu.local.toml). Anywhere else they are an error naming the file and line.

Some settings may never come from a project file at all, because a cloned repository should not be able to redirect them: for example cache.remote, cache.dir, platform.url and the tool index's trusted root. Set those in user or machine configuration. See registered settings for every key, its default and its scope.

Personal overrides​

oyzu.local.toml is for you: a smaller job count, a personal cluster to load images into. Keep it out of version control. When Oyzu infers a CI context, it excludes local files and user computation settings so a CI run does not depend on whoever configured the runner; --local-overrides asks for them explicitly, subject to administrative restrictions.

Checks and contexts​

Every build resolves one context: local, pr, ci or release. Oyzu detects it from CI provider variables (GITHUB_ACTIONS, GITLAB_CI, TF_BUILD, Jenkins, Buildkite and many more), raising it to pr for a pull or merge request and to release for a tag. With no signal it is local. oyzu build --context <name> or OYZU_CONTEXT pins it; under a vendor CI marker a pin can raise the context but not lower it. The context is an unverified hint: it never grants credentials, cache authority or publication rights.

The context matters mostly for checks. Each check has a level:

LevelRuns inA failure
offnever; its tools are not even prepared—
advisorybuilds that run every checka CHECK_ADVISORY warning; the build still succeeds
enforce (default)builds that run every checkfails the build
requiredevery build, including a fast local buildfails the build

Which builds run every check is the setting checks.run: required locally (a fast build), all in pr, ci and release. oyzu build --full runs every check that is not off in any context.

# oyzu.toml
[checks]
lint = "advisory"
coverageMinimum = 50

[context.release.checks]
tests = "required"
coverageMinimum = 90

oyzu config explain <setting> --context release --target <build> shows what a setting resolves to for a given context and build, including which context tables applied and which were overridden. See check levels and per-context values.

Profiles and toolsets​

A profile is a named overlay of settings, chosen with --profile <name>, OYZU_PROFILE or profile.default. Oyzu ships a built-in ci profile that runs every check. Profile names grant no authority, and a profile cannot change tools, so the tools a build uses never depend on which profile is selected. For "also test on Node 24", use a toolset instead.

Constraints and policy​

A constraint limits a setting after every ordinary value has been applied:

ConstraintEffect when the ordinary value is outside it
locked = true with valueThe lock replaces it, shown as an override
minimum / maximumThe bound replaces it (numbers, and check levels ordered off < advisory < enforce < required)
requiredMembers are added to a set
allowedThe value is refused with CONFIG_OVERRIDE_DENIED, naming the setting and the policy source

A project without central policy can make a rule hold in every folder with a [constraints] table in its root oyzu.toml:

# root oyzu.toml only
[constraints."checks.tests"]
minimum = "required"
when = { context = ["release"] }

A folder that sets tests = "advisory" still runs required tests in a release build, and Oyzu prints a CONFIG_CONSTRAINT_OVERRIDE warning saying so. Organization policy works the same way, from protected administrative files, and always wins over project constraints. A requested tool version outside an allowed set is refused, not silently replaced. Every override is visible in oyzu config explain, in the plan and in the bundle. See policy constraints and selectors and project constraints.

Secrets stay out​

Project configuration never holds secret values. [env] values are literal strings and can become part of build inputs and evidence. Credentials for caches, registries and the platform come from environment variables or sign-in, never from a setting. See trusted environment and credential destinations.
