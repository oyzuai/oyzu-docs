Tasks and builds

Oyzu has two ways to do work:

  • oyzu run <task> runs one named task now, with live output, the way you'd run go test or npm run lint yourself, but with the project's pinned tools.
  • oyzu build produces the project's outputs. It runs stages across every selected target in dependency order, reuses unchanged results, and leaves a bundle in dist/.

Both use the same tasks. The difference is what happens around them.

What a task is​

A task is a named operation on a target, written target:task, such as api:test. Builders infer the common ones from your native files, so most projects need no task configuration:

TaskPurposePart of builds
buildCompile or package the targetyes
testRun the tests and collect JUnit and coverage where supportedyes
lintRun the ecosystem's linteryes
format-checkCheck formatting without changing filesyes
formatRewrite files to the formatter's styleno, development only
installFetch dependenciesno, development only
$ oyzu run list
Available tasks · 13 across 2 targets
​
Task                 Source         Command
api · go/app (7)
api:build            Inferred · go  go build ./...
api:smoke            oyzu.toml      go run .
api:test             Inferred · go  go test ./...
…

The Source column shows where each task came from: inferred by a builder, or written in oyzu.toml.

Running one task​

$ oyzu run api:smoke
  · Setup  Loading configuration and discovering tasks
  › api:smoke  Running · native tool output follows
Hello, Oyzu!
  ✓ api:smoke  Succeeded (exit 0 after 1.16s)

oyzu run runs in the target's folder with the project's tools on PATH, streams native output as it happens, and uses your terminal's input. A bare task name works when only one target has it; otherwise write api:test. Arguments after -- are passed on: oyzu run api:test -- -run TestPrice.

Task runs are never cached. They're for the edit-run loop.

Building​

oyzu build runs the same tasks as stages, with more around them:

oyzu run <task>oyzu build
ScopeOne task (plus its prerequisites and hooks)Every stage of every selected target
OrderingThat task's prerequisitesThe whole build graph
ReuseNever cachedUnchanged actions are reused
OutputLive native outputLive progress, then a summary of outputs, tests and coverage
RecordTest runs can write a test bundleAlways a bundle in dist/
ChecksYou choose the taskChosen by check levels and context

Fast builds and full builds​

A plain local oyzu build is a fast build: it runs the build and package stages and only the checks set to required, and shows the rest as skip · fast local build. A full build runs every check that isn't off. You get one:

  • with oyzu build --full on any machine;
  • automatically in the pr, ci and release contexts, which Oyzu detects from CI variables, so CI needs no extra flags;
  • with oyzu --profile ci build.

Each check (tests, coverage, lint, format) has a level in oyzu.toml: off, advisory (a failure is a warning), enforce (the default; fails full builds) or required (runs in every build and fails it). No flag skips a check the project chose; turning one off is a committed change. See check levels.

Adding and replacing tasks​

Tasks go in oyzu.toml under [tasks]. Each one is either argv (an argument list, recommended) or run (a shell command):

[tasks."api:smoke"]
argv = ["go", "run", "."]

A task with the same name as a builder stage replaces that stage's command. The stage's requirements still apply: a replacement test stage must still produce the reports its builder needs.

Which builds a task applies to depends on its name:

KeyApplies to
[tasks."api:smoke"]Build api only
[tasks.post_build] (a hook)Every build below that file's folder that has a build stage
[tasks.test] (a stage name)Replaces test in every build the file reaches; refused if those builds use different builders
[tasks.lint-docs] (any other name)At the root, a workspace task: oyzu run lint-docs

Names are checked before anything runs. A misspelled build or hook target is an error naming the file and line and suggesting the nearest name. See which build a task belongs to.

Hooks and prerequisites​

A hook is a task named pre_<task> or post_<task>. It runs with that task, both in task runs and in builds. Prerequisites use depends_on:

[tasks."api:pre_test"]
argv = ["node", "scripts/check-api-inputs.mjs"]
depends_on = ["schema:verify"]

[tasks."schema:verify"]
argv = ["node", "scripts/verify-schema.mjs"]

schema:verify runs once per command even if several tasks need it, in the schema target's folder with that target's tools. A custom command never installs a new tool by itself: the tools it calls must be ones the project already uses.

Conditions and placeholders​

A hook can say when it applies with when and unless, using facts such as the build context, platform, whether the build is optimized, and for post_build hooks the artifact. It can receive values through placeholders like {artifact.path}:

[tasks."cli:post_build"]
argv   = ["{artifact.path}", "--version"]
when   = { optimized = true, platform = ["linux/x86_64"] }

Conditions choose behavior; they aren't a security control. Use check levels and constraints for checks that must run. See task and hook conditions.

Tasks and the cache​

Files that ship belong on the build in build.yaml, even when an authored task produces them. Use artifacts to name the qualified producer, exact relative file path and media type; keep the command and conditions in oyzu.toml. A release-only or skipped producer records not-produced with a reason and does not fail the build. Publication requires the file only when it is selected. See named file artifacts.

Builder stages are cached without any setup. Oyzu can't see inside a task you wrote, so a target containing one runs every time, unless the task sets cache = true with outputs, or the hook declares outputs. See authored tasks cached on request.
