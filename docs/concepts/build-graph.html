The build graph

When you run oyzu build, Oyzu does not run one big script. It turns every selected target into a sequence of stages, turns stages into actions, and connects them into a graph so independent work runs in parallel and dependent work waits. Knowing the graph explains why something ran, why it waited, and why it was skipped.

Targets, stages and actions​

LevelWhat it isExample
TargetOne buildable unit found by discovery or declared in build.yamlapi
StageA step every builder understands: format-check, lint, test, build, packageapi:test
ActionA planned unit of execution with a frozen command, environment, inputs and outputsgo test -json -coverprofile=… ./...

A builder supplies the stages for its ecosystem and the native commands behind them. One stage can contain several actions (a Node package, for example, has separate version, build and package actions), and one task you run by name can yield more than one action. The executable plan records every action with the details it will run with, and the bundle records how each one ended.

Two kinds of edges​

The graph has edges inside a target and edges between targets.

Inside a target, the builder's stage order applies. A test stage runs after the build it tests, and hooks such as pre_test or post_build attach to the stage they name. See Tasks and builds.

Between targets, edges come from what you declare:

Declared inEffect
depends_on: [api] in build.yamlOrdering only: api finishes before this target starts. No files move
materialize in build.yamlAn artifact api produces is placed into this target's inputs; the edge is inferred
depends_on = ["schema:verify"] on a task in oyzu.tomlThat task runs first, in its own target's context

Oyzu trusts the declared graph. If one target's build script quietly reads another target's folder without a declared edge, the cache and --affected cannot know. Declare the relationship. See the action cache.

Selection follows the graph​

oyzu build with no arguments builds every target. Name targets to build fewer:

oyzu build worker --plan

With worker declared as depends_on: [api], the preview includes api too and records the order:

api · go/app · windows/amd64
Executor: host
Placement: runs on windows/amd64 · no Docker engine needed · Runs as host processes without a container engine
Stage         Selection  Details
build         selected   Native commands and report bindings resolve during preparation
format-check  skipped    Not selected by the resolved check settings
lint          skipped    Not selected by the resolved check settings
test          skipped    Not selected by the resolved check settings

worker · go/app · windows/amd64
Executor: host
Placement: runs on windows/amd64 · no Docker engine needed · Runs as host processes without a container engine
After targets: api
Stage         Selection  Details
build         selected   Native commands and report bindings resolve during preparation
…

(Captured on Windows 11, NO_COLOR=1, redirected; trimmed.) Selection adds every producer a selected target needs, transitively, and each added target gets its full applicable sequence of stages, not only the helper that was asked for. Targets outside the selection get no tools, no dependency downloads and no actions in that invocation. Positional arguments are exact target names; an unknown name fails before anything is prepared.

oyzu build --affected <git-ref> selects targets another way: the ones whose files changed since that commit, plus their declared consumers. See affected builds.

The plan is intent, not evidence​

oyzu build --plan shows the graph without doing anything. It installs no tools, downloads no dependencies, runs no project code and never replaces dist/. It is deliberately incomplete: exact commands, artifact names and report bindings are only known after preparation, and the preview lists those under Unresolved until preparation.

A real build shows the same graph once, as a table, before it starts work. For a two-target project with every check selected:

-- Plan -------------------------------------------------------------- 2 targets
                     format   lint   test   build
  api/
    project-api      run      run    run    run
  worker/
    project-worker   run      run    run    run

Each cell is run, skip (with a footnote giving the reason, such as fast local build) or - when the stage does not apply. Which stages run depends on the build's check settings and context; see Configuration layers.

Running the graph​

Actions start as soon as everything they depend on has finished, up to the job limit (build.jobs, or oyzu build -j N). In the build above, both targets' build actions started together because nothing connects them:

-- Build -----------------------------------------------------------------------
  00:03  ..      project-api     build                                started
  00:03  ..      project-worker  build                                started
  00:08  ok      project-api     build         go build -trimpath -…  executed     5.4s
  00:08  ..      project-api     test                                 started
  00:08  ok      project-worker  build         go build -trimpath -…  executed     5.4s
  00:08  ..      project-worker  test                                 started

Failed, blocked and skipped are different​

When an action fails, Oyzu keeps the outcomes distinct:

  • Failed: the action's own native command ran and exited non-zero. Its log path and exit code are shown in a failure section.
  • Blocked: the action never ran because something it depends on failed. It is not reported as a failure of its own command.
  • Independent work continues: a target with no path to the failure can still succeed.

Cycles, whether through task prerequisites, hooks, stage order, target dependencies or materialized artifacts, fail before any action runs. Reordering YAML does not fix a cycle; removing the relationship does.

What is recorded​

The frozen plan (dist/plan.json) and manifest (dist/manifest.json) record the selection: which targets were requested, which were selected and which were excluded and why. oyzu inspect dist rejects a bundle whose manifest disagrees with its plan. Excluded targets are never reported as successful builds. See Artifacts, bundles and evidence.
