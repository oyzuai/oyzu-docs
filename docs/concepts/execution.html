Execution modes

The same build can run in different places. Oyzu calls the place an action runs its executor. The executor affects speed, isolation and how far you can trust the result, so Oyzu always shows the choice before work starts and records it in the bundle.

ModeSelected byRunsNeeds
Host (native)Default for supported targetsNative commands as normal processes, each target in its own view of the sourceThe pinned tools, plus native prerequisites such as a linker
Isolated (captured)--isolated, --all-platforms, or a target the host path doesn't supportA captured copy of source and dependencies, inside a container or sandboxDocker and the execution image, or the daemonless sandbox on Linux
Remote--remoteThe pushed commit on a platform pool, with full checks in isolationA platform account; experimental

Host execution​

A plain oyzu build runs on your machine when every selected target supports it: Rust, Go, Gradle, Maven, npm node/app and pip Python targets, plus supported image builds. This is the fast development path, and the one the tutorial uses.

$ oyzu build --plan
…
project-api · go/app · windows/x86_64
Executor: host
Placement: runs on windows/x86_64 · no Docker engine needed · Runs as host processes without a container engine
…

Host builds are native, with some guard rails:

  • Each target compiles in its own view of the source: its folder plus any inputs it declares. It can't read source outside that, which is what lets the cache trust its key.
  • Tools come from the lock, set up per action. A compiler that happens to be on your PATH isn't used for managed tools.
  • Compiler state worth keeping between builds, such as Cargo's target directory, lives under .oyzu/native/, within a size budget (cache.nativeMaxMiB).
  • Built binaries are collected into dist/ and also linked at .oyzu/bin/, which keeps the last successful build if a later one fails.

Host execution isn't a sandbox. The processes have your normal access, native package managers use their own registries and credentials, and a host build doesn't by itself qualify for publication. The plan, manifest and logs record that the build ran on the host.

Some builders check the environment before compiling. Rust, for example, compiles and links a tiny program first; a missing linker or SDK fails in under a second with EXECUTOR_PREREQUISITE_UNAVAILABLE and setup instructions instead of a raw compiler error. Oyzu doesn't install operating-system components.

Isolated execution​

oyzu build --isolated captures the source and the dependencies a build needs, then runs each target's actions in a private workspace inside a container, using that captured copy rather than your live checkout. Toolchain images are identified by content digest, not by tag. Use it for builds that shouldn't depend on the machine they run on. --all-platforms uses it to build platforms your machine can't.

$ oyzu build api --plan --isolated
Planning shop
Windows x86_64 (host) · Isolated · context local · Fast build requested
…
api · go/app · unresolved until executor selection
Executor: captured-worker
Placement: runs on any platform · Docker engine required · Isolated steps run in the captured worker on a Docker engine
Stage         Selection   Details
build         selected    Native commands and report bindings resolve during preparation
…
prepare       unresolved  Target environment setup is determined by native dependency preparation
package       unresolved  Artifact packaging is determined by native metadata

Note the extra prepare and package stages, and that the executor, not your machine, decides the platform.

The daemonless sandbox​

On Linux, the isolated steps of Node targets, and of go/app targets built by the external Go plugin, can run under crun, a rootless container runtime, instead of Docker. The sandbox is the same either way: no network, a read-only image, no extra privileges, a seccomp filter and a user namespace. build.isolation chooses: auto (the default) uses Docker when an engine answers and crun otherwise; docker and crun force one. Both produce the same cache keys, so a result cached by one serves the other. See the daemonless sandbox and, for the external Go plugin, plugin packages.

Runners without Docker​

oyzu build --no-docker (or OYZU_NO_DOCKER=1) never contacts a Docker engine. Before anything runs, it works out where each target would run; if a selected target needs Docker, it stops with exit status 3 and NEEDS_DOCKER_DAEMON. Exit 3 means "wrong kind of runner", distinct from a failed build (1) or a bad command (2), so CI can retry the job on a runner with Docker.

Remote execution​

oyzu build --remote asks the Oyzu platform to build the pushed HEAD on a pool, always with full checks in isolation, and streams the output back. The CLI exits with the remote exit code, and Ctrl+C cancels the run. oyzu build --remote --plan previews what the pool would run, with each target's platform and executor needs, without contacting the platform. Remote runs are an optional, experimental platform feature; everything else works without an account. See remote runs.

How Oyzu chooses​

  • A plain build uses the host when every selected target supports it, and the isolated path otherwise.
  • --isolated (and --image) always use the isolated path; --all-platforms uses the container executor for every declared platform.
  • If a target needs a platform other than your machine's, such as a Linux container image that packages a Go binary built on Windows, the build uses the isolated path so the binary is built for the right platform.
  • --affected works out its selection first, then follows the same rules.
  • A failed build never retries on another executor, and detecting CI doesn't change the choice. What the plan says is what runs.

The executor is part of the result​

The executor is recorded on every target in the plan and manifest, and any executor other than your own machine is part of the cache key. A container-built or cross-compiled result never stands in for a host build of the same platform, or the other way round. A project can also name the only executor allowed for a platform with build.executors; see Platforms and matrices.

Development and optimized builds​

Separately from where it runs, each target is built with a development profile (for a fast edit-build loop) or an optimized one. A build is optimized when its artifacts leave your machine (a release context, a write to a shared remote cache, a split-build slice, or packaging by another selected target), and development otherwise. oyzu build --optimized and --no-optimized choose for one run, and build.optimized in oyzu.toml chooses per folder. Rust runs cargo build --release when optimized; builders where optimization changes nothing stay development. Optimized and development results never stand in for each other in the cache. See optimized builds.

Limits​

  • Host execution is the most mature path.
  • Isolated execution needs Docker, which pulls the base execution image on first use, or the Linux daemonless sandbox. Which builders support it varies.

See Native local builds and Current capabilities.
