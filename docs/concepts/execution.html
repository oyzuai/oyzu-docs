Execution modes

The same build can run in different places. Oyzu calls the place an action runs its executor. Which executor runs a target changes speed, isolation and what the result can be trusted for, so Oyzu always shows the choice before work starts and records it in the bundle.

ModeSelected byRunsNeeds
Host (native)Default for supported targetsNative commands as host processes, in a private source view per targetThe pinned tools; native prerequisites such as a linker
Isolated (captured)--isolated, --all-platforms, or a target shape the host path does not supportCaptured source and dependencies inside a container or sandboxDocker and provisioned toolchain images, or the daemonless sandbox on Linux
Remote--remoteThe pushed commit on a platform pool, with full checks in isolationA platform account; experimental

Host execution​

A plain oyzu build runs on the host when every selected target is eligible: Rust, Go, Gradle, Maven, npm node/app and pip Python targets, plus admitted image workers. This is the fast development path and what the tutorial uses.

oyzu build --plan
project-api · go/app · windows/amd64
Executor: host
Placement: runs on windows/amd64 · no Docker engine needed · Runs as host processes without a container engine

Host execution is native but not careless:

  • Each target compiles in a private source projection: its own folder plus any inputs it declares. The action cache relies on that boundary, because a build cannot read source outside it.
  • Tools come from the lock and are activated per action; an ambient compiler on your PATH is not used for managed tools.
  • Compiler state that should persist between builds, such as Cargo's target directory, is kept under .oyzu/native/, within a retention budget (cache.nativeMaxMiB).
  • Successful binaries are collected into dist/ and also exposed at .oyzu/bin/, which stays at the last successful build if a later one fails.

What host execution is not: a sandbox. Host processes are unrestricted, native package managers use their own registries and credentials, and the result does not by itself confer publication eligibility. The plan, manifest and logs record that the build ran on the host.

Before compiling, some builders probe the environment. Rust, for example, compiles and links a tiny program first; a missing linker or SDK fails in under a second with EXECUTOR_PREREQUISITE_UNAVAILABLE and provisioning guidance instead of a raw compiler error. Oyzu does not install operating-system components.

Isolated execution​

oyzu build --isolated uses the captured executor. Oyzu first captures the source and the dependencies a build needs, then runs each target's actions in a private workspace inside a container, against those captured inputs rather than the live checkout. Toolchain images are identified by their content digest, not their tag. This is the path for builds that should not depend on the machine they run on, and the one --all-platforms uses to build platforms the host cannot.

oyzu build api --plan --isolated

The daemonless sandbox​

On Linux, the isolated steps of Node targets can run under crun, a rootless OCI runtime, instead of Docker. The step gets the same sandbox: no network, a read-only image root, no capabilities, no-new-privileges, a seccomp filter and a user namespace. build.isolation chooses: auto (the default) uses Docker when an engine answers and crun otherwise; docker and crun force one. Both backends produce the same cache keys, so a result cached by one serves the other. See the daemonless sandbox.

Runners without Docker​

oyzu build --no-docker (or OYZU_NO_DOCKER=1) never contacts a Docker engine. Before anything runs it works out the same placement as --plan; if a selected target needs a daemon, it stops with exit status 3 and NEEDS_DOCKER_DAEMON. Exit 3 means "wrong kind of runner", distinct from a failed build (1) or a refused invocation (2), so a CI system can requeue the job on a pool with Docker.

Remote execution​

oyzu build --remote asks the Oyzu platform to build the pushed HEAD on a pool, always with full checks in isolation, and streams the output back; the CLI exits with the remote exit code and Ctrl-C cancels the run. oyzu build --remote --plan previews what the pool would run, with each target's platform and executor needs, without contacting the platform or needing credentials. Remote runs are an optional, experimental platform feature; everything else on these pages works without an account. See remote runs.

How Oyzu chooses​

  • A plain build uses the host when every selected target is host-eligible, and the isolated path otherwise.
  • --isolated (and --image) always use the isolated path; --all-platforms uses the container executor for every declared platform.
  • A consumer that needs a platform other than the host's, such as a Linux container image that packages a Go binary built on Windows, makes the build use the isolated path so the producer is built for the right platform.
  • --affected computes its selection first, then follows the same rules.
  • A failed build never retries on another executor, and CI detection does not change the choice. What the plan says is what runs.

The executor is part of the result​

The executor is recorded on every target in the plan and manifest, and every executor other than the host is part of the action-cache key. A container-built or cross-compiled result therefore never satisfies a host build of the same platform, or the other way round. A project can also declare the only executor allowed for a platform with build.executors; see Platforms and matrices.

Development and optimized builds​

Separately from where it runs, each target is built with a development profile (fast edit-build loop) or an optimized one. Optimization follows where the output goes: a build is optimized when its artifacts leave the machine (a release context, a shared remote cache write, a split-run slice, or packaging by another selected target), and development otherwise. oyzu build --optimized and --no-optimized choose for one run, and build.optimized in oyzu.toml chooses per folder. Rust builds cargo build --release when optimized; builders where optimization changes nothing stay development. Optimized and development results never restore each other from the cache. See optimized builds.

Early implementation

Host execution is the most exercised path. Isolated execution needs Docker and provisioned toolchain images, and its platform coverage varies by builder; remote execution has been qualified only in bounded flows. See Native local builds and Current capabilities.
