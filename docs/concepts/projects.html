How Oyzu sees a project

Oyzu starts from the files your ecosystem already has. A go.mod is a Go module, a Cargo.toml is a Rust package, a package.json with a lockfile is a Node project. You don't have to describe your repository before Oyzu can build it. When you want the list of builds to be explicit and reviewed, add a small build.yaml; from then on that file decides.

The vocabulary​

TermMeaningExample
Project rootThe folder Oyzu treats as the top of your projectThe Git worktree root
Target (also called a build)One buildable unit with a nameapi, a Go module in api/
BuilderThe ecosystem support that finds, plans and builds one kind of targetgo/app, rust/app, node/app, python/app
DiscoveryReading native files to find targets and pick their builders, without running project codeoyzu discover
InventoryThe list of builds in build.yamlbuilds: {api: {uses: go/app, path: api}}

Where the project starts​

Inside a Git repository, configuration is inherited from the worktree root, and the nearest build.yaml above you decides the builds. Outside Git, the outermost folder with Oyzu configuration or a build.yaml is the project; failing that, the folder you ran the command in. --root <dir> sets the root explicitly, and -C <dir> runs from another folder as if you'd changed into it.

A nested project with its own build.yaml is independent: running Oyzu inside it uses that project, with its own oyzu.lock and dist/. Parent inventories aren't merged. See inspection and selection for the exact rules.

Discovery without configuration​

Without a build.yaml, Oyzu walks the tree from the root. When a builder recognizes a folder, that folder becomes a target and the walk doesn't go deeper there, because the builder owns everything below it. Dependency and output folders, nested Git repositories and folders with their own build.yaml are skipped.

A small repository with two Go modules and no Oyzu files:

shop/
  api/      go.mod  main.go  main_test.go
  worker/   go.mod  main.go  main_test.go
$ oyzu discover
2 targets · 12 tasks discovered without running project code
Project root: …\shop
​
project-api · go/app
  Chosen by          detected from project files
  Location           api
  …
​
project-worker · go/app
  Chosen by          detected from project files
  Location           worker
  …

Without configuration, names follow the folder: a target at the root is project, and one below it is project-<path>, here project-api and project-worker.

How a builder makes its choices​

Inside a target, a builder still has choices to make: which package manager, test runner or formatter. Each option comes with evidence, and the strongest evidence wins:

StrengthExamples
declareda test script that runs exactly one recognized test runner
nativea lockfile, packageManager in package.json, a [tool.*] table in pyproject.toml
conventionala declared dependency, a uv.lock that locks no packages
defaultthe documented default when nothing else applies, such as npm or Ruff

If two options have equally strong evidence, Oyzu doesn't guess. Discovery fails, names both, and prints the build.yaml line that settles it:

$ oyzu discover
✗ COMMAND_FAILED: conflicting Python formatter candidates black, ruff: black via pyproject.toml tool.black; ruff via pyproject.toml tool.ruff; declare the intended one for this target in build.yaml with `with: {formatter: black}` or `with: {formatter: ruff}`

oyzu build --plan shows every choice and its reason in a Discovered table. Each builder's options are listed in discovery decisions and build.yaml selectors.

When build.yaml takes over​

A build.yaml at the root turns discovery into an explicit list you can review. With one present, only its builds exist. Discovery never adds a build on its own.

builds:
  api:
    uses: go/app
    path: api
  worker:
    uses: go/app
    path: worker
    depends_on: [api]
FieldPurpose
usesThe builder. Optional when exactly one builder recognizes the folder
pathThe folder, relative to the root
depends_onBuilds that must finish first (ordering only)
materializeArtifacts from another build to place in this build's inputs
platformsThe platforms this build ships for, such as [linux/x86_64, linux/arm64]
inputsExtra source paths the build reads
withOptions for the selected builder, such as formatter: ruff

With that file, oyzu discover reports the names you chose (api, worker), shows Chosen by build.yaml, and confirms that build.yaml declares every folder where a build was discovered.

build.yaml holds only what changes what ships. Tool versions, check levels, tasks and environment variables go in oyzu.toml; see Configuration layers. A build.yaml that belongs to another tool (Dart's build_runner uses the same name) is recognized by its keys and skipped.

Keeping build.yaml complete​

Once you have a build.yaml, a folder someone adds later won't build unless it's listed. Oyzu helps you notice:

  • oyzu discover lists folders a builder recognizes that no entry covers, with the line to add for each.
  • oyzu build --plan names up to five of them under Not in build.yaml. A real build never builds them.
  • oyzu discover --check exits 1 with INVENTORY_UNDECLARED while such a folder exists. Add it to CI.
  • oyzu discover --write adds an entry, with uses written out, for every folder exactly one builder recognizes. It keeps your comments and order and adds an editor-schema comment.
  • exclude: lists folders that are deliberately not builds, for example exclude: [tools/scratch, tooling/**].

Folders that a declared build's native workspace already includes (Cargo members, go.work use, npm, Yarn or pnpm workspaces) are covered by that build. Inside Git, only folders with tracked files count, so files a CI job creates can't fail the check. See builds build.yaml leaves out.

Native files first​

If a native file already says something, Oyzu reads it there:

  • The go and toolchain lines in go.mod set the minimum Go version.
  • rust-toolchain.toml selects the Rust channel and components.
  • Lockfiles decide the Node package manager.
  • Native workspace manifests decide which folders belong to one build.

Oyzu configuration only adds what native files can't say, and when both mention the same thing they must agree. See Tools and toolchains.

Commands​

CommandUse it to
oyzu discoverSee targets, builders and how each was chosen
oyzu discover --jsonGet the full discovery record, including each task's environment
oyzu discover --checkFail CI when a recognized folder is missing from build.yaml
oyzu discover --writeAdd every undeclared folder to build.yaml
oyzu config schema build.yamlPrint the JSON Schema for build.yaml
oyzu run listSee the tasks each target offers
