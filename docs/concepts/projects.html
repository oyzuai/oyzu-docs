How Oyzu sees a project

Oyzu starts from the files your ecosystem already has. A go.mod is a Go module, a Cargo.toml is a Rust package, a package.json with a lockfile is a Node project. You do not have to describe your repository to Oyzu before it can build it. When you want the list of builds to be explicit and reviewed, you add a small build.yaml, and from then on that file is the authority.

The vocabulary​

TermMeaningExample
Project rootThe folder Oyzu treats as the top of your projectThe Git worktree root
Target (also called a build)One buildable unit with a nameapi, a Go module in api/
BuilderEcosystem knowledge that discovers, plans and builds one kind of targetgo/app, rust/app, node/app, python/app
DiscoveryReading native files to find targets and decide their builders, without running any project codeoyzu discover
InventoryThe list of builds in build.yamlbuilds: {api: {uses: go/app, path: api}}

Where the project starts​

Inside a Git repository, configuration is inherited from the Git worktree root, and the nearest ancestor build.yaml inventory selects the build. Outside Git, the outermost folder holding Oyzu configuration or a build declaration bounds the project; failing that, the folder you ran the command in. --root <dir> fixes the root explicitly, and -C <dir> runs from another folder as if you had changed into it.

A nested project with its own build.yaml is independent: running oyzu build --plan inside it selects that project, with its own oyzu.lock and dist/. Parent inventories are not merged. The configuration reference has the exact rules, including how linked worktrees and .git files are recognized.

Zero-configuration discovery​

Without a build.yaml, Oyzu walks the tree from the root. When a builder recognizes a folder, that folder becomes a target and the walk stops descending there, because the builder owns everything below it. Dependency and output folders, nested Git repositories and folders with their own inventory are skipped.

Here is a small repository with two Go modules and no Oyzu files at all:

shop/
  api/      go.mod  main.go  main_test.go
  worker/   go.mod  main.go  main_test.go

How a builder's choices are made​

Inside a target, a builder still has decisions to make: which package manager, which test runner, which formatter. Each detector reports a candidate with evidence of a certain strength, and the strongest evidence wins:

StrengthExamples
declareda test script that runs exactly one recognized test runner
nativea lockfile, packageManager in package.json, a [tool.*] table in pyproject.toml
conventionala declared dependency, a uv.lock that locks no packages
defaultthe documented default when nothing else applies, such as npm or Ruff

Two different candidates with equally strong evidence are a conflict, and Oyzu never breaks the tie silently. Discovery fails, names both inputs, and prints the exact build.yaml line that settles it:

conflicting Python formatter candidates black, ruff: black via pyproject.toml tool.black; ruff via pyproject.toml tool.ruff; declare the intended one for this target in build.yaml with `with: {formatter: black}` or `with: {formatter: ruff}`

oyzu build --plan shows every decision and its reason in a Discovered table. The selectors each builder accepts are listed in discovery decisions and build.yaml selectors.

When build.yaml takes over​

A build.yaml at the root turns discovery into an explicit, reviewable inventory. With one present, only its builds exist: discovery never adds a build on its own.

builds:
  api:
    uses: go/app
    path: api
  worker:
    uses: go/app
    path: worker
    depends_on: [api]

Each entry is a build name with a few fields:

FieldPurpose
usesThe builder. Optional when exactly one builder recognizes the folder; discovery then fills it in
pathThe folder, relative to the root
depends_onBuilds that must finish first (ordering only)
materializeArtifacts from another build to place in this build's inputs
platformsThe platforms this build ships for, such as [linux/x86_64, linux/arm64]
inputsExtra source paths the build reads
withOptions interpreted by the selected builder, such as formatter: ruff

With that file in place, the same repository reports the names you chose:

api · go/app
  Chosen by          build.yaml
  Location           api
  …

worker · go/app
  Chosen by          build.yaml
  Location           worker
  …

build.yaml holds only what changes what ships. Tool versions, check levels, tasks and environment variables belong in oyzu.toml; see Configuration layers. A build.yaml that belongs to another tool (Dart's build_runner uses the same name) is recognized by its keys and skipped, so it never hides the projects below it.

Keeping the inventory honest​

Once you have a build.yaml, a new folder someone adds would silently not build. Oyzu guards against that:

  • oyzu discover lists folders a builder recognizes that no entry covers, with the shortest line to add for each.
  • oyzu build --plan names up to five of them under Not in build.yaml. A real build never builds them.
  • oyzu discover --check exits 1 with INVENTORY_UNDECLARED while such a folder exists. Add it to CI.
  • oyzu discover --write appends an entry with uses written out for every folder exactly one builder recognizes, keeping your comments and order. It also adds an editor-schema comment so your editor can complete and validate the file.
  • exclude: lists folders that are deliberately not builds, for example exclude: [tools/scratch, tooling/**].

Folders that a declared build's native workspace already lists as members (Cargo members, go.work use, npm, Yarn or pnpm workspaces) are covered by that build and need no entry of their own. Inside Git, only folders with tracked files count, so files a CI job creates cannot fail the check. See builds build.yaml leaves out.

Native conventions first​

Oyzu's rule of thumb: if a native file already says it, Oyzu reads it there instead of asking you to repeat it.

  • A Go module's go and toolchain lines in go.mod set the minimum Go version (shown as oyzu:go minimum-version >=1.22 go.mod go in the build preview).
  • rust-toolchain.toml selects the Rust channel and components.
  • Lockfiles decide the Node package manager.
  • Native workspace manifests decide which folders belong to one build.

Oyzu configuration then adds only what native files cannot express, and when both speak about the same thing they must agree. See Tools and toolchains.

Commands​

CommandUse it to
oyzu discoverSee targets, builders and how each was chosen
oyzu discover --jsonGet the complete discovery record, including each task's environment
