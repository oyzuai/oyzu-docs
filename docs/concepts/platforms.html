Platforms and matrices

"Build it for Linux and macOS" and "test it on Node 22 and Node 24" sound alike, but they're different requests. The first changes what ships: there are two artifacts. The second changes only how the build is checked: there's still one artifact, tested twice. Oyzu keeps them apart. Platforms are declared in build.yaml; extra runtime versions to test against are toolsets in oyzu.toml.

Platform scope: Use an x64 host and supported x64 build targets. ARM64 is unsupported. Feature-specific limits are listed in the support matrix.

Platform names​

Every platform is written os/arch[/abi]:

PlatformMeaning
linux/x86_64Linux on Intel/AMD 64-bit
darwin/x86_64macOS on Intel
windows/x86_6464-bit Windows
linux/x86_64/musl, windows/x86_64/msvcWith an explicit ABI

You can also type amd64 and aarch64; output, records and dist/ folders always use the names above. The ABI is optional and only matters where an OS has several (gnu or musl on Linux; msvc, gnu or gnullvm on Windows). Without one, the builder picks its default. Rust cross builds for Linux default to musl, which can break code that relies on glibc features such as dlopen or NSS name lookup; declare linux/<arch>/gnu where that matters.

Target platform and executor​

Two terms stay separate:

  • The target platform is what an artifact is built for.
  • The executor is where its build actions run: your machine, a cross toolchain on your machine, the container executor, or a remote pool.

A Linux x86-64 binary can be built natively on a Linux machine or in a Linux container. The executor is recorded on every target and is part of its cache key, so these results never stand in for each other. See Execution modes.

Declaring platforms​

A build lists the platforms it ships for in build.yaml:

builds:
  cli:
    uses: rust/app
    platforms: [linux/x86_64, darwin/x86_64, windows/x86_64]

A build with one platform keeps its name. With several, each instance gets a platform-qualified ID, and each platform's output goes in its own folder, dist/<target>/<platform>/, so bundles from different machines merge without collisions. A build that declares nothing builds for your machine.

Which platforms a build builds​

CommandBuilds
oyzu buildYour machine's platform. If a target declares platforms but not yours, it builds the one declared platform your machine can build, asks for --platform if there are several, or is skipped with the reason if there are none
oyzu build --platform <p> (repeatable)Exactly those. A declared platform that can't be built here fails before anything runs, with PLATFORM_UNAVAILABLE
oyzu build --all-platformsEvery declared platform, through the container executor; fails if any can't be built

The plan says how each platform would be built. Platforms your machine could build are listed with the flag to use, and the rest are listed with the reason, such as "needs a macOS runner (Apple SDK and linker)". Today only Rust has a native cross toolchain. Go, Node, Python, Java, .NET and Helm build only for your own platform natively.

Where each platform is built​

By default, a platform is built on your machine if it matches, otherwise with a cross toolchain when the builder has one. You can instead set the executor per platform in oyzu.toml, per folder and per context:

[build.executors]
"windows/x86_64" = "cross-toolchain" # use the available Rust cross toolchain
"darwin/x86_64" = "host"             # only on an Intel macOS runner

[context.release.build.executors]
"linux/x86_64" = "container"        # release builds use the container executor

A declared executor is the only one used for that platform. When it's unavailable, the platform isn't built here and the plan says why; asking for it explicitly fails with PLATFORM_UNAVAILABLE. Nothing falls back to another executor, so a release builds each platform exactly as its plan says. See declaring a platform's executor.

A CI matrix from the plan​

You don't have to hand-write your CI matrix. oyzu build --plan --json includes a matrix with one entry per declared platform of every selected target: the runner that can build it natively (os as CI providers name it, and arch), the declared executor, and the targets that declare it. The matrix doesn't depend on what the planning machine can build, and with --affected <ref> it holds only the affected targets. Feed it to your workflow's matrix and run, in each job:

oyzu build <targets> --platform <platform>

Mapping each runner to your provider's runner labels is up to your workflow. When the artifacts are published, Oyzu checks that every declared platform is present. See a CI matrix from the plan for a complete GitHub Actions example.

Runtime versions are toolsets​

To check that an application also works on another runtime version, define a toolset in oyzu.toml. The shipped build is built and tested once, with the [tools] versions. Each toolset adds a verification run that repeats the build and test stages with its tools and records the result. A verification run never produces an artifact, so publishing still sees one artifact.

# build.yaml: nothing about runtime versions
builds:
  app:
    uses: node/app
# oyzu.toml
[tools]
node = "22.14.0"            # builds, tests and ships the app

[toolsets.node24.tools]
node = "24.14.1"            # also tested on Node 24
CommandRuns
oyzu pinLocks Node 22.14.0 and the node24 toolset's 24.14.1
oyzu buildLocally: the app alone
oyzu build --verify-with node24Locally: the app and its Node 24 run
oyzu build --context ciIn CI: the app and its Node 24 run
  • A toolset runs in every context except local, unless it lists contexts = [...].
  • Each run is its own target in the plan (app-verify-node24). It skips lint and format checks, which don't depend on the runtime, and never packages or publishes.
  • A failing test in a run fails the build.
  • Runs are listed under .verify in the plan JSON, so CI can give each its own job.
  • The global --toolset <name> option uses a toolset's tools for exec, run, env, activate, which and install, so you can reproduce a run's environment by hand.

A build can require passing verification on certain tool versions before publishing with verification.<tool> (for example verification.node = ["22", "24"]), and policy or [constraints] can make versions required. A version no toolset covers adds a run, and oyzu publish refuses a release without a passing result for each. A version outside the project's own range, such as below the go line in go.mod, is recorded as not applicable instead of failing the build. See verification toolsets.

Runtime versions never go in build.yaml: the old matrix.<runtime> field is refused with a message showing the toolset form. Profiles can't hold tools either. A toolset is the one place to define an alternative set of tools.

Limits​

  • Native cross toolchains exist only for Rust so far.
  • The container executor needs Docker.

See platform requirements and platforms and executors.
