Tools and toolchains

A build is only as reproducible as the compiler that ran it. Oyzu manages toolchains itself, so your laptop, a teammate's machine and CI use the same Go, Node or Rust without anyone installing it by hand. You say what you need, Oyzu picks an exact version, verifies the download once, records it in oyzu.lock, and puts it on PATH for builds, tasks and your shell.

Where requirements come from​

Oyzu collects tool requirements from three places and combines them, keeping track of each source:

SourceExampleWhat it adds
Native filesgo 1.22 in go.mod; rust-toolchain.tomlMinimums, channels and components the project already declares
The builderGo's builder needs a Go compiler; Rust's test stage needs nextest and cargo-llvm-covTools for the stages that will run
[tools] in oyzu.tomlgo = "1.24"Explicit requests, for tools with no native pin or to pick within a range

Tools follow checks: when a check is off, its tools aren't installed. With [checks] format = "off", the Rust builder no longer adds rustfmt.

oyzu build --plan shows the combined list without checking or installing anything:

$ oyzu build --plan
…
Tool requirements · availability not checked
Requirement  Kind             Constraint  Targets        Source
oyzu:go      minimum-version  >=1.22      all 2 targets  go.mod go
oyzu:go      request          1.22        all 2 targets  api/go.mod (native pin); worker/go.mod (native pin)
…

Native pins come first​

If a native file already pins a tool, that file is the request, and Oyzu configuration either adds nothing or must agree:

  • a [tools] value in the pin's folder, or nearer the build, must name the same version line, or preparation fails naming both files;
  • a [tools] value farther away loses to the pin and is shown as overridden;
  • native ranges, such as npm devEngines, stay constraints.

Today Oyzu reads the Rust toolchain files and the go and toolchain lines in Go's go.mod and go.work. Go's lines count as a minimum, not an exact pin, because Go treats the toolchain line as a suggestion. Oyzu requests that minimum when no [tools] go is set, and a configured version below it fails with TOOL_NATIVE_MINIMUM_CONFLICT. Support for other native pin files, such as global.json, Gradle and Maven wrapper properties and packageManager, varies by ecosystem; the build guide for your ecosystem says which it reads. See Go version selection and Rust toolchain files.

Resolve, verify, install, then trust​

Installing a tool takes the same steps whichever command starts it:

  1. Resolve the request ("1.24") to an exact version (1.24.13) for every platform in the lock, from the publisher's catalog or Oyzu's signed public tool index.
  2. Download the archive for this machine.
  3. Verify it: the archive digest against the publisher's checksum, the publisher's signature where available, and the unpacked layout.
  4. Store it in the shared tool store with an install record, and write oyzu.lock.

After that, the tool is trusted. Running a command doesn't re-hash the installed files, and a damaged installation may simply fail when run. Checking happens once, at install, which keeps every command fast.

$ oyzu install go@1.24
Installing requested tools
Resolving every platform, then installing this one
✓ Installed (reused existing installation) go 1.24.13
    Declared "1.24" in …\shop\oyzu.toml (project)
    Locked in …\shop\oyzu.lock for 4 platforms (darwin/arm64/native, linux/amd64/gnu, linux/arm64/gnu, windows/amd64/msvc)
​
Store: C:\Users\you\AppData\Local\Oyzu\tools

Configuration keeps what you typed ("1.24"). The lock records the exact version and an archive for each platform. Only this machine's archive is installed; here Go 1.24.13 was already in the store, so nothing was downloaded.

go@1.26 is a prefix, go@1.26.8 is exact, go@latest is the newest eligible version, and plain go keeps an existing declaration. Several tools in one command are applied together or not at all.

The shared store​

Installed tools live in one store per user, shared by every project: %LOCALAPPDATA%\Oyzu\tools on Windows and ${XDG_DATA_HOME:-~/.local/share}/oyzu/tools on Linux. Two projects that lock the same Go version share one installation. oyzu uninstall never deletes shared files; oyzu tools list shows what uses each installation.

Using the tools​

The selected tools reach every place you run commands:

WhereHow
BuildsThe build installs any missing pinned tool and uses the exact selection for each action
Tasksoyzu run <task> puts the selected tools on PATH
Your shelloyzu shell install (the install script runs it) adds the selection to PATH as you change directories, so plain go version works
One command without activationoyzu exec -- go version
Lookupoyzu which go prints the selected executable
$ go version
go version go1.24.13 windows/amd64

oyzu which and oyzu exec never fall back to a program elsewhere on your PATH when the selected tool is missing; they fail and tell you to install it. Shell activation applies a project's environment variables only after you trust the folder, because environment variables can run code in shells and interpreters.

Scopes​

CommandDeclares inLocks in
oyzu install go@1.24project oyzu.tomlproject oyzu.lock
oyzu install -g node@22your user configurationthe oyzu.lock beside it
oyzu install --local go@1.24oyzu.local.tomlproject oyzu.lock

Outside a project, a command without -g fails with TOOL_NO_PROJECT instead of guessing.

What Oyzu doesn't install​

Oyzu installs supported tools from their publishers: Node, Go, Python, Java, Maven, Gradle, Helm, kubectl, k3d, npm, pnpm, Rust and the Cargo helpers it needs, among others, plus experimental registry packages (aqua: and github:). It doesn't install operating-system components. A Windows Rust build that needs the MSVC build tools and SDK, or a system linker, reports it as an executor prerequisite with setup instructions; oyzu pin --dry-run lists these separately from managed tools.

Tool commands are supported on Linux and Windows (x86-64); support for individual tools varies. See tool commands.

Commands​

CommandUse it to
oyzu install <tool>@<version>Declare, lock and install a tool
oyzu installInstall everything declared; --frozen never changes the lock, --offline never uses the network
oyzu update [tool]Move to the newest version within each requirement; never edits configuration
oyzu uninstall <tool>Remove a declaration and its lock entries
oyzu pinLock requirements without installing
oyzu tools current / list / versions / infoSee what is selected, stored, available and why
oyzu which <command>, oyzu exec -- <command>Find or run a command with the selected tools
