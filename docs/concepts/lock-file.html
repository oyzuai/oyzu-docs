The lock file

oyzu.lock records the exact tools a project uses: which version each request resolved to, on each platform, and which archive (with its digest) provides it. Oyzu writes it and you commit it. Everyone who checks out the repository, and every CI runner, then installs exactly the same bytes, instead of whatever "latest" means that day.

Requests and resolutions​

Configuration says what you asked for. The lock says what that resolved to.

Lives inExample
Request[tools] in oyzu.toml, native files such as go.modgo = "1.24", go 1.22
Resolutionoyzu.lockoyzu:go 1.24.13, go1.24.13.windows-amd64.zip, sha256:40b1…

Exact versions never go in build.yaml or oyzu.toml; they live only in the lock.

What's inside​

The lock is TOML. A shortened example for a Go project after oyzu install go@1.24:

format = 1
environment = []
tool = []

[[resolved_environment]]
required_capabilities = []
request_digest = "sha256:5197…"
roots = ["sha256:1deb…", "sha256:8a42…", "sha256:dfd4…", "sha256:ff28…"]

[resolved_environment.requests]
"oyzu:go" = "1.24"

[resolved_environment.native_constraints]
"oyzu:go" = ["go-minimum:>=1.22"]

[resolution."sha256:8a42…"]
tool = "oyzu:go"
version = "1.24.13"
execution_platform = "windows/amd64/msvc"
components = []

[resolution."sha256:8a42…".inputs.archive]
url = "https://dl.google.com/go/go1.24.13.windows-amd64.zip"
digest = "sha256:40b16bc8f00540a2cb02dff4de72b73e966fdd8d65f95e33d8e4080b48a2459a"
  • resolved_environment is one set of requests (here "oyzu:go" = "1.24"), the native constraints that applied (go.mod asked for at least 1.22), and the resolutions that satisfy them.
  • resolution entries are one per tool, version and platform: the exact version, the archive URL and its digest. Each platform gets its own.
  • environment and tool entries describe installation details where a provider records them. A resolution doesn't mean anything is installed.
  • An entry locked for a toolset has toolset = "NAME".

The lock holds no machine paths, profiles or scopes, so it moves between machines unchanged. oyzu tools inspect-lock checks its structure without downloading or running anything.

Which platforms are locked​

When a tool is resolved, Oyzu locks it for every platform any build declares, plus the current machine, and installs only this machine's archive. Set tools.lockPlatforms to list the exact platforms instead (the current machine is always kept), for example to prepare for another build environment. See tool lock coverage.

Who writes it​

CommandEffect on the lock
First oyzu build with no lockResolves what the builders need and writes the lock, without editing your TOML
oyzu pinLocks requirements and installs nothing. --dry-run previews
oyzu install <tool>@<version>Declares the tool in oyzu.toml and locks it, together
oyzu update [tool]Moves to the newest version within each existing request; never edits configuration
oyzu uninstall <tool>Removes the declaration and its lock entries
oyzu pin --refreshRefreshes install recipes, keeping the selected versions

Configuration and lock change together: a failure leaves both files as they were, a simultaneous edit fails with PIN_EDIT_CONFLICT, and an interrupted write is recovered the next time you run install, update, uninstall or pin.

The lock stays as written until you change it​

Once a lock exists, builds and installs use it as written and never quietly re-resolve. If you change a request so the lock no longer covers it, Oyzu stops and tells you what to run. For example, after changing go = "1.24" to "1.23":

$ oyzu install --frozen
✗ TOOL_LOCK_STALE: configured tool request is not pinned; run oyzu pin, then oyzu install
  Next: Run oyzu pin --refresh to refresh the lock, then oyzu install.

Two flags make this explicit:

  • oyzu install --frozen needs an existing matching lock and never resolves a new version. Use it in CI.
  • oyzu install --offline uses no network. It needs the lock plus either an installed copy or a cached archive, which it checks against the locked digest before using.

A cached archive that doesn't match its locked digest fails instead of being replaced by a fresh download.

Locks and policy​

Organization policy can allow or lock tool versions. The lock is checked against those rules before anything is installed or used, so a hand-edited lock that maps an allowed 22 to 26.1.0 is refused, naming the rule and the lock file. When a policy applies only in some contexts (say, an exact Rust version for release), the lock keeps one entry per request, so local and release entries sit side by side. See policy constraints.

Locks and the cache​

On your machine, the action cache identifies tools by the digest of oyzu.lock. Changing a locked version re-runs the affected work, and changing it back can reuse earlier results. A tool that isn't in the lock, such as a system C compiler, isn't part of the cache key, so use oyzu build --no-cache after changing one. See The action cache.

Good habits​

  • Commit oyzu.lock. It's what makes other machines match yours.
  • Don't edit it by hand. Change requests in oyzu.toml or with oyzu install, and let Oyzu rewrite the lock.
  • One lock per project root. A nested project with its own build.yaml has its own lock. Your user-level defaults (oyzu install -g) use the lock beside your user configuration file.
  • Review lock changes like dependency updates. A changed version or digest is a changed toolchain.
