CLI reference

oyzu is one executable with one command per job: build, run tasks, manage tools, inspect configuration and verify results. This section has a page for every public command, with every option exactly as --help prints it, real output, the --json shape and the errors you are most likely to meet.

oyzu --help and oyzu <command> --help work offline, outside any project and without an account. oyzu help <command> prints the same text. Help never loads configuration, opens the tool store or contacts a service (CLI help).

How the examples were captured

Every output block in this section is real. It was captured on Windows 11 (windows/x86_64) from a development build of the CLI at the current main (oyzu 0.1.0-local.533e824153f7), with NO_COLOR=1 and the output redirected to a file, which is how Oyzu renders in CI and logs. An interactive terminal shows the same sections with color and live progress rows. To keep blocks readable, long absolute paths are shortened with …, the Windows user name is shown as you, trailing spaces are removed and long outputs are trimmed where marked. Times, versions, digests and identifiers on your machine will differ.

Global options​

Every command accepts these options, before or after the command name. oyzu --json build and oyzu build --json are the same. Arguments after -- belong to the child process and are never read by Oyzu.

OptionEffect
-C, --directory <DIRECTORY>Run from this directory, as if you had cd'd there first
--jsonReturn machine-readable results and errors
-v, --verbose...Show debug diagnostics; repeat (-vv) for trace
-q, --quiet...Hide routine Oyzu progress, preserving results and child output
--log-level <LOG_LEVEL>Set the diagnostic threshold: error, warn, info, debug or trace
--root <ROOT>Use an explicit project root (also stops configuration inheritance from parent folders)
--profile <PROFILE>Select a configuration profile
--no-profileDisable profile selection
--toolset <NAME>Use a toolset's tools ([toolsets.NAME.tools] in oyzu.toml) for exec, run, env, activate, which, install, update, uninstall and pin
--local-overridesInclude local configuration overrides
-h, --helpPrint help
-V, --versionPrint version (top level only)
oyzu -C services/api build --plan     # plan a nested project without cd
oyzu --root . discover                # ignore oyzu.toml files in parent folders
oyzu --toolset node24 exec -- node -v # use a toolset's Node instead of [tools]

See configuration for profiles, toolsets and local overrides.

Output modes​

Human (default). Results lead with the outcome, then aligned tables and named sections. Color is used only on capable terminals and never carries meaning on its own. Redirected output and NO_COLOR=1 give plain text. Human layout is for people; do not parse it.

JSON (--json). Standard output holds exactly one JSON result and nothing else: no headings, color or progress. Oyzu's own diagnostics go to standard error as JSON Lines. Errors are a JSON object with at least error and exitCode:

oyzu --json build --bogus
{"code":"CLI_USAGE","error":"unexpected argument '--bogus' found\n\n  tip: to pass '--bogus' as a value, use '-- --bogus'","exitCode":2,"nextStep":"Run oyzu <command> --help for supported arguments."}

Help and version return their text under output:

$ oyzu --json --version
{"exitCode":0,"output":"oyzu 0.1.0-local.533e824153f7 (debug; x86_64-pc-windows-msvc; build 1792533559)\n"}

Shell payloads (activate, deactivate, env --shell) print executable code by default and {"shell": …, "script": …} with --json. Result shapes are command-specific and may gain fields; consumers should ignore fields they do not know.

Quiet (-q). Hides routine progress and the interactive dashboard. Results, warnings, errors and native tool output are kept:

$ oyzu -q build

ok      Build succeeded   1 target · 1 reused · 3.1s

Verbose (-v, -vv, --log-level). Adds debug or trace diagnostics on standard error. Verbosity never changes what is built, cached or reported. The OYZU_LOG environment variable accepts a level or target=level directives when no command-line control is given. More than two -v, more than one -q, or combining these controls, is a usage error. Details: CLI output: diagnostic controls.

build also has --output auto|plain|interactive to choose between linear output and the live dashboard; it changes presentation only.

Errors​

Human errors start with ✗, the stable code and what to do next. The block also names the running executable, its version and the directory, so a pasted error is self-describing:

$ oyzu run nosuch
  · Setup  Loading configuration and discovering tasks
✗ TASK_NOT_FOUND: no task "nosuch" in …\hello. Available tasks: build, format, format-check, install, lint, test. Run oyzu run to list tasks, or oyzu -C <project> run nosuch
  Next: Check the selected directory and name; use oyzu -C <project> to select a project.
  Invocation: 46216-1792534865231284900-1
  oyzu 0.1.0-local.533e824153f7 (debug; x86_64-pc-windows-msvc; build 1792533559) · windows/x86_64
  Executable: …\oyzu.exe
  Directory: .

Exit status​

Scripts and CI can branch on the exit status without parsing text. A command page lists its own additions.

StatusMeaningTypical codes
0Success
1The operation failed: a build or check failed, a tool was refused, an error without a more specific classCOMMAND_FAILED, TOOL_INSTALLATION_MISSING
2The invocation was refused: bad arguments or conflicting flags; a failed or unfinished publicationCLI_USAGE, TOOL_FLAGS_CONFLICT, TOOL_SPEC_INVALID
3Configuration or policy is invalid, or the build cannot be placed on this machineCONFIG_*, POLICY_*, TOOL_NATIVE_MINIMUM_CONFLICT, NEEDS_DOCKER_DAEMON
4A lock is missing or stale, or a slice's upstream result is not cachedTOOL_LOCK_STALE, TOOL_LOCK_MISSING, PLUGIN_LOCK_MISSING, UPSTREAM_NOT_CACHED
5Something named was not found: a task, a declared tool, a project; or a slice's handoff write failedTASK_NOT_FOUND, TOOL_NOT_DECLARED, TOOL_NO_PROJECT, HANDOFF_PUSH_FAILED
130Interrupted with Ctrl+C (the build stops admitting work, terminates its processes and keeps logs)

oyzu run and oyzu exec return the child's own exit status. --json errors carry the same number in exitCode.
