Zig

Use the zig/project plugin to build a Zig project with its own build.zig and collect what the build installs: programs, libraries and resources. Zig keeps full control of the build graph. Oyzu selects the compiler, runs zig build with a private install prefix and caches, and records the installed files in a verified dist/ bundle.

Note: The Zig builder is experimental and uses the signed oyzu/zig plugin. Zig 0.15.2 is supported. Dependency-free native builds work on Linux x86-64 and Intel macOS; the Windows x86-64 path has limited support. Native builds with dependencies work on Intel macOS, and isolated builds with dependencies run on Linux x86-64. ARM64 is unsupported.

The Zig reference has the full details.

Set it up​

Oyzu doesn't detect Zig projects automatically. Declare the build in build.yaml beside your build.zig:

builds:
  hello:
    uses: zig/project

Choose the compiler in oyzu.toml:

[tools]
zig = "0.15.2"

The signed oyzu/zig package is in the official plugin catalog. Enable preview selection in your user configuration, then build:

oyzu config set --global plugins.preview true
oyzu build

The first build installs the package and records its exact release in oyzu.lock. Commit that lock. See plugin selection.

What a build does​

oyzu build runs:

zig build --prefix <output>/install --cache-dir <output>/cache --global-cache-dir <output>/global-cache

Oyzu collects the install directory as the build's artifact and keeps both Zig caches out of it. The path of the collected files is in dist/manifest.json (for example hello/darwin/x86_64/install), so run your program from there: install/bin/hello.

Discovery never evaluates build.zig or downloads anything. Oyzu reads build.zig.zon for the package identity, the compiler minimum and the declared dependencies. .minimum_zig_version limits which compiler Oyzu selects. It doesn't pin one.

TaskCommandNotes
buildzig buildInstalls into the private prefix
testzig build test --summary allDependency-free native builds collect one JUnit case for the test step
formatzig fmt .Rewrites files. Never part of a build
format-checkzig fmt --check .Native format check

If you replace the build task in oyzu.toml, your command runs exactly as written. It must produce the install directory itself and doesn't get the options below.

Options​

Put these under with in the build:

OptionValuesDefaultMeaning
steps1 to 16 step names (letters, digits, _, -; start with a letter; up to 64 characters)the native default installRun these build.zig steps. Flags, paths and shell text are refused
definitionsMap of up to 16 option names to strings, booleans or integersnoneEach entry becomes one -Dname=value argument. Compiler, target, cache and fetch options are reserved and refused
install-formatdirectory, tar.gzdirectorytar.gz packs the install tree into one install.tar.gz, keeping relative links and executable bits

String values can be up to 1,024 bytes with no control characters. All arguments together are limited to 4,096 bytes. Values are never evaluated by a shell. Other option names are passed to your build.zig, and its failures show up normally.

You can keep build.zig and a tracked dist/ folder in place and send Oyzu's own bundle elsewhere:

# oyzu.toml
[tools]
zig = "0.15.2"

[build]
bundleDirectory = ".oyzu/bundle"
# build.yaml
builds:
  ghostty:
    uses: zig/project
    inputs: [dist]
    with:
      steps: [lib-vt]
      install-format: tar.gz

inputs: [dist] adds your tracked dist folder as a source input. oyzu inspect then reads .oyzu/bundle by default. See bundle placement. definitions selects project options the same way, for example definitions: {xcframework-target: native}.

Dependencies​

Declared packages in build.zig.zon (URL, transitive, path and lazy dependencies) are prepared before build.zig runs. Oyzu downloads each archive through its scoped broker, checks it against the native package hash, and gives Zig only local files through --system.

  • Native macOS (Intel). Preparation needs network access on every invocation. It supports archives and GitHub repositories pinned to a full 40-character commit, within size and metadata limits. Nested Xcode projects are limited to the exact Xcode and Swift versions in the reference.
  • Isolated Linux (x86-64, GNU). The build runs with no network, -j1 and the install prefix described above. After one online build, the prepared packages let an offline build reuse them. This path needs a plugin package that includes the Linux executable, as the catalog package does. See the reference.

Native host builds that declare dependencies are refused unless they take one of these paths.

Tools your build calls​

If your build.zig runs other tools, such as Pandoc for documentation, pin them in oyzu.toml next to the compiler. Pins apply to every build in that folder. The compiler stays first on PATH, and the other tools follow.

[tools]
zig = "0.15.2"
"github:jgm/pandoc" = "3.12.1"
oyzu pin zig@0.15.2
oyzu pin 'github:jgm/pandoc@3.12.1'
oyzu install --frozen
oyzu build --isolated

Pandoc 3.12.1 works on Linux (x86-64, GNU). Oyzu accepts complete publisher tar.gz and tar.xz packages whose commands match their file names. Archives that need an interpreter, command aliases or missing executables are refused. Offline builds need the publisher archives cached by an earlier online build. The tools run during the build and aren't part of the collected install tree. See native documentation installation tree.

Resources​

The isolated build reserves 4,096 MiB of memory plus virtual machine overhead. The default Docker Desktop memory limit is too small, so raise it (6 GiB worked on an 8 GiB Mac) and keep at least 2 GiB of free disk.

Native JUnit reports require a plugin declaring zig-native-test-report; the catalog's 0.1.0-preview.3 does not yet declare it. See native test reports.

Common failures​

You seeCauseFix
Metadata error with a file, line and columnInvalid build.zig.zon (duplicate field, expression or unsupported escape)Fix it at the reported location
A build that installs nothing fails artifact collectionbuild.zig installs nothingAdd an install step, or select the right steps
Refusal about a required test reportThe selected execution path cannot produce the required reportUse a supported test path; required checks still apply
Dependency or hash refusalAn archive doesn't match its package hash, or the source form isn't supportedCorrect the hash, or use a supported source
Options refused next to a build task replacementwith options need the standard build commandRemove the replacement or the options

Native failures from build.zig are passed through as they are. A failed build never produces a successful artifact.

Limits​

  • Dependency-free native tests collect JUnit for the whole test step, not individual test functions. Test reports for projects with dependencies and isolated builds, and coverage for all Zig builds, are unavailable.
  • Only Zig 0.15.2 is supported. Other compiler versions and other platforms are not supported yet.
  • Isolated builds need Docker, the Linux plugin executable and the memory above.
  • Native macOS dependency preparation needs the network each time. There is no offline reuse.
  • Git dependencies other than a full-commit GitHub repository are refused.
  • Native dependency packages can't contain links other than a direct link to a sibling regular file.
  • An install tree with links fails the directory format. Use install-format: tar.gz, which keeps links that stay inside the tree.
