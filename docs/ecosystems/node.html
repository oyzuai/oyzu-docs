Build Node projects

Oyzu builds Node packages and workspaces from the files they already have: package.json, the lockfile and native configuration. You do not write an Oyzu build file. This guide covers npm, pnpm and Yarn Classic, single packages and workspaces, tests and coverage, lint and formatting, static analysis, tool pinning and the failures you are most likely to meet.

Node support is experimental. npm has the most complete coverage; pnpm and Yarn Classic have their own adapters with narrower evidence, and modern Yarn (Berry) is not supported. The limits are listed at the end.

Every output block below is a real capture from Windows 11 with Docker Desktop running and a development build of the CLI (0.1.0-local.564f462704df), color forced on and output piped to a file. Long local paths are shortened to …. Times, hashes and versions on your machine will differ.

What Oyzu detects​

Discovery reads files only. It never runs npm, project scripts or configuration code.

Signal in your projectWhat it decides
package.jsonA Node target. Packages are discovered as node/app; set uses: node/package in build.yaml to force package semantics
package-lock.json, pnpm-lock.yaml, yarn.lockThe package manager: npm, pnpm or Yarn Classic
packageManager in package.jsonThe manager and, for an exact npm or pnpm release, the version to pin
workspaces in package.json, or pnpm-workspace.yamlA native workspace, built as one target
scripts.build, scripts.test, scripts.lint, format-check or format:checkThe native commands for those stages. Root scripts always win over Oyzu's defaults
A node --test, Jest, Vitest or Mocha script, configuration or dependencyThe test framework, which decides how JUnit and coverage are collected
eslint.config.*, .prettierrc*, biome.jsonThe linter and formatter. ESLint and Prettier are the defaults; biome.json selects Biome for both
A vite build scriptA Vite application, whose dist/ output becomes a directory artifact
engines.nodeA constraint every selected Node version must satisfy

When two equally strong signals disagree (for example two test frameworks), discovery fails and the error names the with: selector to set in build.yaml, such as with: {test-framework: mocha}. See discovery and selection.

Your first Node build​

The example is examples/builds/node-package from the Oyzu repository, copied to an empty folder and initialized with git init: a package with a native build script and node:test tests. (The npm package recipe is a similar, separately maintained project.) Its package.json:

{
  "name": "oyzu-example-package",
  "version": "0.1.0",
  "private": false,
  "type": "module",
  "scripts": {
    "build": "node build.mjs",
    "test": "node --test"
  },
  "engines": {
    "node": ">=22"
  },
  "files": ["dist"],
  "exports": "./dist/greeting.mjs"
}

Where Node builds run​

The plan's Executor: line tells you. For Node it is normally captured-worker: Oyzu captures your source, acquires the locked dependencies through its broker, then runs every action in a sandbox with no network.

  • Windows and macOS need a running Docker engine for this.
  • Linux uses Docker when an engine answers, and otherwise the daemonless crun sandbox, which needs unprivileged user namespaces. --no-docker (or OYZU_NO_DOCKER=1) forces crun. The build.isolation setting in oyzu.toml chooses between them; see configuration.
  • Images. The npm image (node:npm11.11.0-node22) is published, and Oyzu pulls it by digest the first time. The pnpm and Yarn images are not published yet: build them yourself as described in the pnpm and Yarn references, or name one with --image pnpm=<image>. See published toolchain images.

One profile runs directly on your machine instead: an npm node/app whose build writes the conventional dist/ directory (for example a Vite application). That path installs Node itself and needs no Docker; see native host builds and Node applications.

pnpm workspaces (pnpm-workspace.yaml with packages) and Yarn Classic workspaces (private root) use the same planner with their own native installation and packing. Their captured builds need the hand-provisioned images above, and their isolated CLI acceptance is still pending. Details: npm workspaces, pnpm, Yarn Classic.

Tests, coverage and reports​

No reporting configuration is needed. Oyzu instruments the detected framework and collects JUnit and LCOV for every package:

FrameworkDetected fromNotes
Node's test runnernode --test script, or the defaultOyzu passes Node 22 flags, so pin Node 22 or later when tests run
JestScript, configuration or dependencyJest 29 is the verified family
VitestScript, configuration or dependencyNeeds its matching coverage provider installed; runs with one worker
Mochamocha script, .mocharc*, package.json section or dependencyMocha 11 with c8 10 for coverage; see Mocha

Reports land under dist/<target>/reports/ and are recorded, with digests and summaries, in dist/manifest.json. A failed test blocks packaging but keeps its reports.

To get the same evidence without a full build, run tests directly on your machine:

oyzu run test
oyzu inspect dist

This writes a test-only dist/ bundle from your installed dependencies. It does not package anything or isolate the run; see direct tests and workspace test bundles.

Lint and formatting​

lint and format-check are build stages; --full (or a CI context) selects them. format writes files, so it is never part of a build; run it yourself with oyzu run format.

ToolDefault versionBehavior
ESLint10.11.0Your configuration when present; recommended JS/TS rules otherwise; never fixes
Prettier3.9.9Your configuration, .editorconfig and ignore files
Biome2.5.15Selected by biome.json/biome.jsonc for both roles

A tool your project installs wins over the default. A tool you declare but have not installed fails rather than silently using another version. The defaults check JavaScript and TypeScript sources only, skipping node_modules, dist, build and coverage output. To pass your own flags, write a native script ("lint": "eslint . --max-warnings 0"); the defaults reject extra arguments. See Node quality.

To make a rule fail builds, set its level in oyzu.toml:

[analysis.rules]
phantom-dependency = "enforce"      # off | advisory (default) | enforce

[[analysis.suppress]]
rule = "escaping-reference"
path = "legacy/**"
reason = "vendored fork, tracked in the migration plan"

Only a warning backed entirely by exact facts can block. The recorded verification of rule levels is on Linux; the --check above ran on Windows and found nothing to report. See Node static analysis for every rule and its limits.

Pin Node and the package manager​

Native files come first. Oyzu reads them in this order:

  1. packageManager in package.json. An exact stable npm or pnpm release ("packageManager": "pnpm@10.20.0") becomes a tool requirement and is locked beside Node. A Corepack +sha512.… suffix is accepted and ignored. Ranges and tags select nothing. Yarn is not a pinned tool.

  2. engines.node constrains every Node selection; it does not pick one.

  3. No pin: the default is lts, the newest LTS release satisfying every engine constraint, falling back to the newest stable release when no LTS release does. In the run above, >=22 selected 24.22.0.

  4. oyzu.toml to choose explicitly. It must agree with packageManager and satisfy engines.node:

    [tools]
    node = "22.12"
    npm = "11.6.2"       # or pnpm = "10.20.0"

.nvmrc and .node-version are not read yet; set [tools] node instead. The first build writes the exact selections to oyzu.lock, and later builds reuse them, including offline. oyzu pin --dry-run previews what would be locked; oyzu install node@22.12 declares, locks and installs in one step. The isolated worker restores the locked Node and npm or pnpm and runs them in place of the image's copies. See Manage your first tool, Node selection and npm and pnpm installation.

Limits​

  • Modern Yarn (Berry, .yarnrc.yml) is not supported. pnpm and Yarn Classic do not support private registries, and only the listed settings files and keys are admitted.
  • pnpm and Yarn captured images must be provisioned by hand; their isolated workspace builds have pending CLI acceptance.
  • .nvmrc and .node-version are not read.
  • Cyclic workspace graphs, affected selection inside a workspace and member task groups are unfinished.
  • Default lint and formatting cover JavaScript and TypeScript only, not JSON, CSS or other files.
  • Vite support covers Vite 8 with one client environment; SSR, library mode and watch mode fail explicitly.
  • A green build is evidence that these stages passed on this source. It is not a release approval.
