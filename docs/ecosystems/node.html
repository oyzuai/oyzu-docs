Build Node projects

Oyzu finds Node packages and workspaces from package.json, the lockfile and your native configuration, so you don't need an Oyzu build file. It installs the Node version your project asks for, runs your build, tests, lint and format checks, and collects JUnit and LCOV reports and the packed or built output in a verified dist/ bundle.

Note: The Node builder is experimental. It runs as the oyzu/node plugin. It supports npm, pnpm and Yarn (Classic 1.22.22 and Berry 4.17.1 with nodeLinker: node-modules), with different limits for each (see Limits). Supported on Linux and Windows (x86-64). macOS is not supported yet.

What Oyzu detects​

Discovery reads files only. It never runs npm, project scripts or configuration code.

Signal in your projectWhat it decides
package.jsonA Node target. Packages are discovered as node/app. Set uses: node/package in build.yaml to force package behavior
package-lock.json, pnpm-lock.yaml, yarn.lockThe package manager: npm, pnpm or Yarn
packageManager in package.jsonThe manager and, for an exact npm or pnpm release, the version to pin
workspaces in package.json, or pnpm-workspace.yamlA workspace, built as one target
scripts.build, scripts.test, scripts.lint, format-check or format:checkThe commands for those stages. Root scripts always win over Oyzu's defaults
A node --test, Jest, Vitest or Mocha script, configuration or dependencyThe test framework, which decides how JUnit and coverage are collected
eslint.config.*, .prettierrc*, biome.jsonThe linter and formatter. ESLint and Prettier are the defaults, and biome.json selects Biome for both
A vite build scriptA Vite application, whose dist/ output becomes a directory artifact
engines.nodeA constraint every Node version Oyzu selects must satisfy

When two equally strong signals disagree (for example two test frameworks), discovery fails and the error names the with: setting to add in build.yaml, such as with: {test-framework: mocha}. See discovery and selection.

Your first Node build​

The example is examples/builds/node-package from the Oyzu repository. Copy it to an empty folder and run git init. It's a package with a build script and node:test tests:

{
  "name": "oyzu-example-package",
  "version": "0.1.0",
  "private": false,
  "type": "module",
  "scripts": {
    "build": "node build.mjs",
    "test": "node --test"
  },
  "engines": {
    "node": ">=22"
  },
  "files": ["dist"],
  "exports": "./dist/greeting.mjs"
}

Where Node builds run​

The plan's Executor: line tells you. For most Node builds it's captured-worker: Oyzu copies your source, downloads the locked dependencies through its broker, then runs every action in a sandbox with no network.

  • Windows and macOS need a running Docker engine for this.
  • Linux uses Docker when an engine answers. Otherwise it uses the daemonless crun sandbox, which needs unprivileged user namespaces. --no-docker (or OYZU_NO_DOCKER=1) forces crun. The build.isolation setting in oyzu.toml chooses between them; see configuration.
  • Image. Every manager runs on the base execution image, which Oyzu pulls on first use. Node and npm, pnpm or Yarn come from oyzu.lock, and the pnpm and Yarn lockfile parsers ship in the Node plugin. To run on your own image instead, pass --image npm=<image> (or pnpm=, yarn=).

Some applications build directly on your machine and need no Docker: npm and pnpm applications whose build writes the conventional dist/ directory (for example a Vite app), single-root Yarn applications, and explicitly declared single-root npm packages. Oyzu installs Node itself for these. See native host builds and Node applications.

Workspaces​

An npm workspace root is one target, and each member becomes its own versioned package. examples/builds/node-workspace has a private root and two members, @oyzu-example/shared and @oyzu-example/app, where app depends on shared:

{
  "name": "oyzu-workspace",
  "version": "0.1.0",
  "private": true,
  "workspaces": ["packages/*"]
}
$ oyzu build --full

Output shortened. Each member got its own archive and its own JUnit and LCOV pair. Inside the archives, app's dependency on shared points at shared's snapshot version. The private root produced no package. How the work is divided:

StageRoot script presentNo root script
buildRuns once with npm's lifecycle hooksEach member's build script, in dependency order
testRuns once and owns one report pairEach member's script or detected test framework, with its own reports
lint, format-checkRuns onceRoot-owned files are checked by default. Each member uses its script or the default tool

A failed member build stops its dependents. Test and quality failures continue through the other members so you see every problem, then fail the build. Every member needs a distinct package name and a real version (see member names).

pnpm workspaces (pnpm-workspace.yaml with packages) and Yarn workspaces use the same planner with their own installation and packing. Their isolated builds use the same execution image. See npm workspaces, pnpm and Yarn.

Tests, coverage and reports​

You don't configure reporting. Oyzu instruments the detected framework and collects JUnit and LCOV for every package:

FrameworkDetected fromNotes
Node's test runnerA node --test script, or the defaultOyzu passes Node 22 flags, so pin Node 22 or later when tests run
JestScript, configuration or dependencyJest 29 is supported
VitestScript, configuration or dependencyNeeds its matching coverage provider installed. Runs with one worker
Mochamocha script, .mocharc*, package.json section or dependencyMocha with c8 for coverage. See Mocha

Reports land under dist/<target>/reports/, with digests and summaries in dist/manifest.json. A failed test blocks packaging but keeps its reports.

To get the same reports without a full build, run the tests directly on your machine:

oyzu run test
oyzu inspect dist

This writes a test-only dist/ bundle from your installed dependencies. It packages nothing and doesn't isolate the run. See direct tests and workspace test bundles.

Lint and formatting​

lint and format-check are build stages, selected by --full or a CI context. format writes files, so it's never part of a build. Run it yourself with oyzu run format.

ToolDefault versionBehavior
ESLint10.11.0Uses your configuration when present, recommended JS/TS rules otherwise. Never fixes
Prettier3.9.9Uses your configuration, .editorconfig and ignore files
Biome2.5.15Selected by biome.json or biome.jsonc for both roles

A tool your project installs wins over the default. A tool you declare but haven't installed fails instead of silently using another version. The defaults check JavaScript and TypeScript sources only and skip node_modules, dist, build and coverage output. To pass your own flags, write a script ("lint": "eslint . --max-warnings 0"), because the defaults reject extra arguments. See Node quality.

Static analysis​

oyzu build --plan ends each Node target with a Static analysis section. For each stage it lists the files the stage is predicted to read and write, the tools it needs and anything it couldn't bound, each with a confidence level and a file:line source. It parses files and runs no project code. An excerpt:

$ oyzu build --plan
project:build · confidence: over-approximate · scope: predicted
9 exact, 1 over-approximate, 0 unknown
Reads
Path or name       Confidence  Source             Why
package-lock.json  exact       package-lock.json  lockfile
package.json       exact       package.json       manifest
src/greeting.mjs   exact       build.mjs:3        file-read · copyFileSync
Writes
Path or name       Confidence        Source           Why
dist/greeting.mjs  exact             build.mjs:3      file-write · copyFileSync

Narrow the view with --stage <name>, ask about one file with --why <path>, list only the uncertain facts with --unknown, or skip the analysis with --no-analysis. All of these need --plan.

The analysis also runs rules that catch problems visible only across files: phantom-dependency, escaping-reference, undeclared-env, public-env-secret-name, exports-target-missing, lockfile-manifest-drift and others. They're advisory by default. oyzu build --check applies them without preparing or running anything:

$ oyzu build --check
✓ Check passed: no blocking findings
Static analysis only: nothing was installed, downloaded or executed.

To make a rule fail builds, set its level in oyzu.toml:

[analysis.rules]
phantom-dependency = "enforce"      # off | advisory (default) | enforce

[[analysis.suppress]]
rule = "escaping-reference"
path = "legacy/**"
reason = "vendored fork, tracked in the migration plan"

Only a warning backed entirely by exact facts can block. See Node static analysis for every rule and its limits.

Pin Node and the package manager​

Native files come first. Oyzu reads them in this order:

  1. packageManager in package.json. An exact stable npm or pnpm release ("packageManager": "pnpm@10.20.0") becomes a tool requirement and is locked beside Node. A Corepack +sha512.… suffix is accepted and ignored. Ranges and tags select nothing. Yarn is pinned the same way with an exact yarn@1.22.22 or yarn@4.17.1; see managed Yarn.

  2. engines.node limits every Node selection. It doesn't pick one.

  3. No pin. The default is lts: the newest LTS release that satisfies every engine constraint, or the newest stable release if no LTS release does. In the run above, >=22 selected 24.22.0.

  4. oyzu.toml, to choose explicitly. It must agree with packageManager and satisfy engines.node:

    [tools]
    node = "22.12"
    npm = "11.6.2"       # or pnpm = "10.20.0"

.nvmrc and .node-version aren't read yet. Set [tools] node instead. The first build writes the exact choices to oyzu.lock, and later builds reuse them, including offline. oyzu pin --dry-run previews what would be locked, and oyzu install node@22.12 declares, locks and installs in one step. The isolated worker restores the locked Node and npm, pnpm or Yarn. The execution image has no copies of its own. See Manage your first tool, Node selection and npm and pnpm installation.

Outputs​

ProjectArtifact
Package (npm, pnpm, Yarn)An npm pack-style .tgz named <name>-<version>-dev.g<source>.tgz. The embedded package.json carries the same version
WorkspaceOne .tgz per member, plus one for a publishable (non-private) root
node/app with Vite or a dist/ build scriptA directory artifact application-<version> holding the built output. A configured Vite build also records the resolved output metadata

Versions come from your version field, Git tags and commits; see version inference. Artifacts appear only when every required stage passed. Creating an artifact never publishes it.

Common failures​

A test fails. If you change the greeting in the example and rebuild, the other checks still run so you see every problem, but package is blocked because no artifact comes from a failing build:

Limits​

  • Yarn Berry support is for exact 4.17.1 with a literal nodeLinker: node-modules. Single-root applications work natively and in the isolated executor. Workspace packages work natively only (publishable root, app and shared members, or a named private root). Pack hooks are limited to analyzed local copy and helper scripts. PnP, aggregates, project plugins, yarnPath and custom or non-registry sources aren't supported.
  • Yarn Classic 1.22.22 supports single-root applications natively and in the isolated executor. Classic workspace packages work natively only, with a private root and members. Project plugins, custom registries and extra rc settings aren't supported.
  • pnpm isolated builds support pnpm 10.11.0.
  • Vite builds need one written Vite 8 client environment. SSR, library, watch, multiple-environment and no-write modes fail with an explicit message.
  • npm TypeScript workspaces work natively on Linux (x86-64) with a literal tsc -p tsconfig.json and noEmitOnError.
  • .nvmrc and .node-version aren't read.
  • Cyclic workspace graphs, affected selection inside a workspace and member task groups aren't supported.
  • Default lint and formatting cover JavaScript and TypeScript only, not JSON, CSS or other files.
  • A green build shows that the stages passed on this source. It isn't a release approval.
