Rust

Point oyzu build at a folder with a Cargo.toml and it compiles with Cargo, runs your tests with coverage, checks Clippy and rustfmt, and writes a verified dist/ bundle. You don't write any Oyzu configuration for a normal Cargo project.

Note: The Rust builder is experimental. It runs as the oyzu/rust plugin, which Oyzu selects and records in oyzu.lock. If no release of it is available to your installation, the build stops with PLUGIN_UNAVAILABLE. Supported on Linux and Windows (x86-64). macOS is not supported yet.

The Rust reference has the full details.

What Oyzu detects​

Oyzu treats any folder with a Cargo.toml as a Rust target. It reads manifests without running Cargo or any of your code.

ProjectTarget
A single package, binary or libraryOne rust/app target
A Cargo workspace ([workspace] in the root manifest)One rust/app target for the whole workspace. Cargo decides the members

The target delivers every enabled binary. A package that is publishable also gets a .crate archive when you build in the isolated executor. A library-only package gets its .crate and no executable. You need a checked-in Cargo.lock, because Oyzu runs Cargo with --locked and a stale lock fails instead of being rewritten.

oyzu run list shows the tasks Oyzu infers. They are plain Cargo commands:

$ oyzu run list
Available tasks · 8 across 1 target
​
Task                  Source            Command
project · rust/app (8)
project:archive       Inferred · cargo  cargo package --workspace --locked --offline
project:build         Inferred · cargo  cargo build --locked --workspace
project:fetch         Inferred · cargo  cargo fetch --locked
project:format        Inferred · cargo  cargo fmt --all
project:format-check  Inferred · cargo  cargo fmt --all --check
project:install       Inferred · cargo  cargo install --path . --locked
project:lint          Inferred · cargo  cargo clippy --locked --workspace -- -D warnings
project:test          Inferred · cargo  cargo test --locked --workspace

oyzu run <task> runs one on your machine. build, test, lint and format-check are also the stages of oyzu build. format edits your source and is never part of a build. fetch and install are development tasks only, and oyzu run install -- --root <dir> passes its arguments to cargo install.

Build and test​

CommandWhat runs
oyzu build --planNothing. Shows the stages and the tools Oyzu read from your files
oyzu buildCompiles the workspace and collects the binaries. Checks are skipped locally
oyzu build --fullAlso runs tests with coverage, doctests, Clippy and cargo fmt --check
oyzu build --isolatedThe same build in a Linux container (needs Docker; see Isolated builds)

In CI the checks run without --full. See build selection and checks.

Tests run through cargo llvm-cov nextest, so the test stage needs cargo-nextest, cargo-llvm-cov and the llvm-tools-preview Rust component. Oyzu pins and installs the first two for you. Doctests run in the same stage, because nextest doesn't run them.

Pin the toolchain​

Oyzu reads the files Rust developers already use, in this order:

  1. rust-toolchain.toml (or the older rust-toolchain file). Everything rustup accepts is read, including components. A channel such as 1.99.1 is an exact pin.
  2. package.rust-version in Cargo.toml is a minimum.
  3. [tools] rust = "…" in oyzu.toml, only when you have no native file or want a different value in one folder. A native pin file wins over a farther oyzu.toml.

With none of these, Oyzu locks the newest stable Rust on the first build. Either way the exact choice goes in oyzu.lock, so commit it. After you change a pin, run oyzu pin to update the lock and oyzu install to download what it names. oyzu pin --dry-run previews the change. The Tools row of every build says which compiler ran and why, for example rust 1.99.1 already installed compilation (detected from rust-toolchain.toml).

You never install Rust yourself. You do need the platform's linker: on Windows, Microsoft Build Tools with the Windows SDK (MSVC) or LLVM-MinGW; on Linux, the system C toolchain. Oyzu checks the linker with a tiny test build before compiling.

Outputs​

A successful build writes one dist/ bundle. The Outputs section prints each artifact's path, and manifest.json records it with its digest. The bundle layout describes the directories.

OutputContents
<binary>[.exe]Each enabled Cargo binary
<package>-<version>.crateCrate archive for each publishable package (isolated builds)
reports/junit.xmlTest results from nextest (with --full or in CI)
reports/coverage.xmlLine coverage in Cobertura format
reports/doctest.xmlOne case per package that has doctests
manifest.jsonEvery file with its digest, plus the plan and build evidence

Packages with publish = false get no .crate, but their binaries are still delivered. A binary that needs required-features is delivered only when that feature is enabled. Versions are snapshots from your declared version and Git, such as 1.2.3-dev.g<source>. A snapshot isn't a release; see version inference.

Named builds and features​

You need a build.yaml only to change something Cargo can't express. The Rust builder accepts two options under with:

OptionValuesDefaultMeaning
featuresList of Cargo feature namesnone (default features stay on)Applied to build, test, lint, doctests and packaging
artifactsall, binariesallbinaries delivers only enabled binaries and skips crate packaging
builds:
  greeting:
    uses: rust/app
    with:
      features: [loud]

Unknown with keys are refused. To build for other platforms, declare platforms on the build; see cross-compiling.

Keep selected packages on one version​

In a workspace you can make chosen packages share one version number, using the same release metadata cargo-release reads. Oyzu only reads it and never runs cargo-release.

  • shared-version = true joins the workspace's shared group. A string such as "suite" joins that named group. false leaves a group.
  • Matching version strings, or version.workspace = true alone, don't group packages.
  • tag-prefix sets the Git tag namespace used to find each group's last release, for example suite/.
# Workspace root Cargo.toml
[workspace.metadata.release]
shared-version = "suite"
tag-prefix = "suite/"

# A package that versions on its own
[package.metadata.release]
shared-version = false
tag-prefix = "helper/"

Every member of a group must have the same native version and tag mapping. Private or unselected members count too. Conflicting versions or overlapping tag namespaces make the build fail. This applies to Cargo workspaces only. The Rust reference lists every inheritance rule and refusal.

Worked example​

This is a tiny binary crate with one unit test, from examples/builds/rust-app/project in the Oyzu repository. Create these files in a new folder and run git init there.

Cargo.toml:

[package]
name = "oyzu-greeting-example"
version = "0.1.0"
edition = "2021"

Cargo.lock:

version = 3

[[package]]
name = "oyzu-greeting-example"
version = "0.1.0"

src/main.rs:

fn greeting(name: &str) -> String {
    format!("Hello, {name}!")
}
fn main() {
    println!("{}", greeting("Oyzu"));
}
#[cfg(test)]
mod tests {
    use super::*;
    #[test]
    fn greets() {
        assert_eq!(greeting("Oyzu"), "Hello, Oyzu!");
    }
}

rust-toolchain.toml:

[toolchain]
channel = "1.99.1"
components = ["rustfmt", "clippy"]

Run oyzu build for a fast build. The first build also writes oyzu.lock, which you should commit. The binary is under dist/:

$ dist/project/windows/x86_64/oyzu-greeting-example.exe
Hello, Oyzu!

Isolated builds​

oyzu build --isolated runs the same stages in a Linux container with no network. Oyzu first downloads every locked crates.io dependency and checks each archive against the SHA-256 in Cargo.lock, then builds offline. Isolated builds also package publishable crates with cargo package and verify them.

You need Docker and the base execution image, which Oyzu pulls on first use. Rust and its test tools come from oyzu.lock, and cross builds fetch pinned linkers. See the isolated-build image.

Common failures​

You seeCauseFix
TOOL_LOCK_STALE: cargo:cargo-llvm-cov 0.9.1; run oyzu pin (exit 4)oyzu.lock came from a fast build and lacks the test-stage tools, or a pin changedRun oyzu pin, commit oyzu.lock, build again
COMMAND_FAILED: provision llvm-tools-preview before Rust tests: missing llvm-covThe Rust installation used for tests has no llvm-covSet LLVM_COV and LLVM_PROFDATA to the tools from a toolchain with the llvm-tools-preview component (under lib/rustlib/<host>/bin), or delete oyzu.lock, run oyzu pin and rebuild
LINK : fatal error LNK1104: cannot open file '…\linker-arguments' (Windows)The project path is too long for the MSVC linker. Compiler state lives under .oyzu/native/rust/ in the projectMove the project to a shorter path
invalid Rust with options: unknown field …A with key the Rust builder doesn't acceptUse features or artifacts, or remove the key
A test failsThe Cargo test failedThe failure section names the test, the log under dist/logs/ and the command to rerun one target. The previous good binaries are kept

Formatting and Clippy findings are build gates too. Fix them with oyzu run format and oyzu run lint, then rebuild.

Limits​

  • Private or alternate registries, private Git dependencies and credentials aren't supported. Locked crates.io dependencies and public GitHub sources pinned to a full commit are.
  • Coverage is line coverage from nextest. Doctests aren't measured, and the doctest report counts packages, not individual examples.
  • Isolated builds need Docker and the base execution image.
