Rust

Oyzu builds a Cargo project from the files it already has. There is nothing to configure: point oyzu build at a folder with a Cargo.toml and it compiles with native Cargo, runs your tests with coverage, checks Clippy and rustfmt, and writes a verified dist/ bundle.

The Rust builder is experimental. Host builds (the default) and captured container builds both work, with the limits listed at the end of this page. The Rust reference is the complete contract; this page is the practical guide.

Every output block below is a real capture from Windows 11 (windows/amd64) with a development build of the CLI (0.1.0-local.564f462704df), color forced on and output piped to a file. Long scratch paths are shortened to …. Times, hashes and paths on your machine will differ.

What Oyzu detects​

Oyzu claims a folder that contains Cargo.toml. Cargo owns everything else: workspace membership, package metadata, features and dependency resolution. Oyzu reads the manifests without running Cargo or any project code.

ProjectWhat discovery reports
A single package, binary or libraryone rust/app target
A Cargo workspace ([workspace] in the root manifest)one rust/app target for the whole workspace; Cargo decides the members

What the target delivers follows from Cargo's own metadata: every enabled binary, and in captured builds a .crate archive for each publishable package. A library-only package produces its crate archive without an invented executable.

A checked-in Cargo.lock is required. Oyzu runs Cargo with --locked, so a stale lock fails rather than being rewritten.

From the inferred targets Oyzu derives these tasks, all plain Cargo commands:

$ oyzu run list

Run one with: oyzu run <task>   (extra arguments go after --)
Commands show argv; task dependencies and hooks may also run. Use --json for full task records.

oyzu run <task> runs one of them directly on your machine. build, test, lint and format-check are also the stages of oyzu build. format edits your source and is never part of a build. fetch and install are development tasks only; oyzu run install -- --root <dir> forwards its arguments to cargo install.

Build and test​

CommandWhat runs
oyzu build --planNothing. Shows the stages and the tool requirements Oyzu read from your files
oyzu buildCompiles the workspace and collects the binaries. Checks are skipped locally
oyzu build --fullAlso runs tests with coverage, doctests, Clippy and cargo fmt --check
oyzu build --isolatedThe same build inside the captured Linux container executor (needs Docker; see Isolated builds)

In CI the build context is detected from your provider's environment variables, and the quality stages run without --full. See build selection and checks.

Tests run through cargo llvm-cov nextest. Oyzu needs cargo-nextest and cargo-llvm-cov plus the llvm-tools-preview Rust component for that stage. It pins and installs the first two for you (see below). Cargo doctests run in the same test stage, because nextest does not run them.

Pin the toolchain​

Pinning starts with the files Rust developers already use:

  1. rust-toolchain.toml (or the legacy rust-toolchain file). Every form rustup accepts is read, including components. A channel such as 1.99.1 is an exact pin.
  2. package.rust-version in Cargo.toml is a minimum.
  3. [tools] rust = "…" in oyzu.toml, only when there is no native file or you want a different value in one folder. A native pin file wins over a farther oyzu.toml value.

With none of these, Oyzu locks the newest stable Rust on the first build. Either way the exact selection is written to oyzu.lock; commit it so every machine builds with the same compiler. After you change a pin, run oyzu pin to update the lock, and oyzu install to download what it now names. oyzu pin --dry-run previews the change without writing anything.

The Tools row of every build says which compiler was used and why, for example rust 1.99.1 already installed compilation (detected from rust-toolchain.toml).

You never install Rust yourself. You do need the platform's native linker: on Windows, Microsoft Build Tools with the Windows SDK (MSVC) or LLVM-MinGW; on Linux and macOS, the system C toolchain. Before compiling, Oyzu checks the linker with a tiny probe build.

Artifacts and reports​

A successful build writes one dist/ bundle. The Outputs section prints each artifact's path and manifest.json records it with its digest; the build bundle layout describes the directories.

OutputContents
<binary>[.exe]Each enabled Cargo binary
<package>-<version>.crateNative crate archives for publishable packages, from captured builds
reports/junit.xmlnextest results (with --full or in CI)
reports/coverage.xmlLLVM Cobertura line coverage
reports/doctest.xmlOne case per doctest-enabled package (binary-only crates have none)
manifest.jsonEvery file with its digest, plus the plan and evidence

Packages marked publish = false never get a .crate; their binaries are still delivered. A binary behind required-features is delivered only when that Cargo feature is enabled.

Versions are snapshots derived from your declared version and Git: 1.2.3-dev.g<source>. A snapshot is not a release; see version inference.

Named builds and features​

You need a build.yaml only to change something Cargo cannot express on its own. The Rust builder accepts with.features, a list of Cargo features applied to build, test, lint, doctest and packaging:

builds:
  greeting:
    uses: rust/app
    with:
      features: [loud]

Native default features stay enabled. Unknown with keys are refused. The Rust reference also documents with.artifacts: binaries and declaring platforms for cross-compilation; the development CLI used for this page accepted features but refused artifacts, so check your version with oyzu build --plan.

Worked example: a Cargo application​

This uses example EX-021 from the Oyzu source tree (examples/builds/rust-app/project, listed in the example catalog): a tiny binary crate with one unit test. Copy it, or create the three files below, in a new folder outside any other Git repository, and make it a repository of its own with git init.

Cargo.toml:

[package]
name = "oyzu-greeting-example"
version = "0.1.0"
edition = "2021"

Cargo.lock:

version = 3

[[package]]
name = "oyzu-greeting-example"
version = "0.1.0"

src/main.rs:

fn greeting(name: &str) -> String {
    format!("Hello, {name}!")
}
fn main() {
    println!("{}", greeting("Oyzu"));
}
#[cfg(test)]
mod tests {
    use super::*;
    #[test]
    fn greets() {
        assert_eq!(greeting("Oyzu"), "Hello, Oyzu!");
    }
}

Pin the compiler with a native rust-toolchain.toml:

[toolchain]
channel = "1.99.1"
components = ["rustfmt", "clippy"]

Isolated builds​

oyzu build --isolated runs the same stages in a Linux container with networking denied. Oyzu first captures every locked crates.io dependency, verifying each archive against the SHA-256 in Cargo.lock, then builds offline. Captured builds also package publishable crates with cargo package and verify them natively.

Captured Rust builds need Docker and a provisioned Linux Rust toolchain image, which Oyzu does not download for you. The image recipe and the locked-compiler handoff are in the Rust reference. This page did not run an isolated Rust build.

Common failures​

You seeCauseFix
TOOL_LOCK_STALE: cargo:cargo-llvm-cov 0.9.1; run oyzu pin (exit 4)oyzu.lock was written by a fast build and lacks the test-stage tools, or a pin changedRun oyzu pin, commit oyzu.lock, and build again
COMMAND_FAILED: provision llvm-tools-preview before Rust tests: missing llvm-covThe Rust installation used for the test stage has no llvm-covSet LLVM_COV and LLVM_PROFDATA to llvm-cov and llvm-profdata from a toolchain with the llvm-tools-preview component (they live under lib/rustlib/<host>/bin), then rerun. If the fast build locked the compiler first, deleting oyzu.lock and running oyzu pin again also fixes it
LINK : fatal error LNK1104: cannot open file '…\linker-arguments' (Windows)The project path is too deep for the MSVC linker's path limit; compiler state lives under .oyzu/native/rust/ inside the projectMove the project to a shorter path
invalid Rust with options: unknown field …A with key the Rust builder does not acceptUse with.features, or remove the key
A test failsNative test failureThe failure section names the test, the log under dist/logs/ and oyzu build <target> to rerun one target. The previous good binaries are kept

Formatting and Clippy findings are build gates too: fix them with oyzu run format and oyzu run lint, then rebuild.

Limits​

  • Private or alternate registries, private Git dependencies and credentials are not supported; locked crates.io dependencies and public GitHub sources pinned to a full commit are.
  • Coverage is line coverage from nextest; doctests are not measured, and the doctest report counts package invocations, not individual examples.
  • Cross-compiling another platform from this host, and declaring platforms per build, are described in the Rust reference.
  • Measured support by platform is in capabilities and known limitations.
