Docker images and Helm charts

Oyzu builds container images from ordinary Dockerfiles and packages Helm charts from ordinary chart folders. Neither needs configuration. When you add a little build.yaml, the pieces connect: a binary built by one target is copied into an image, and the image's exact digest is written into the chart that deploys it.

Both builders are experimental. Image builds produce a verified OCI archive in dist/; they never push. Chart builds produce a packaged .tgz and a rendered manifest; they never contact a cluster. Publishing is a separate, explicit step (publishing).

The output on this page is a real capture from Windows 11 (windows/x86_64) with a development build of the CLI (0.1.0-local.564f462704df), color forced on and output piped to a file. Only discovery, task listing and --plan were run: no image or chart was built for this page, because those builds pull or build multi-gigabyte toolchain images. Everything about execution below comes from the reference pages linked in each section.

FilesBuilderTasks
Dockerfiledocker/imagebuild, lint (Hadolint), format-check and format (dockerfmt)

When both chart locations exist, discovery is ambiguous and fails; declare the path in build.yaml. For a Dockerfile in a folder that also looks like an application (a package.json or pyproject.toml), select the Docker builder explicitly with uses: docker/image.

Docker images​

Two ways an image is built​

Oyzu looks at the Dockerfile and picks the cheapest safe path, per target, with no setting involved:

  • Daemonless assembly. When the final stage only copies files onto one base and edits image settings (COPY, WORKDIR, USER, ENV, LABEL, EXPOSE, CMD, ENTRYPOINT, STOPSIGNAL), and the base is scratch or pinned by @sha256: digest, Oyzu writes the image itself, like ko or Jib. No Docker engine is needed for that build. Base images are fetched anonymously from their registry by digest and cached.
  • BuildKit in an isolated worker. Anything else (a RUN in the final stage, ARG, ADD, a tag-only base, .dockerignore) runs in Oyzu's rootless BuildKit worker with networking denied. Base images must already be in your local Docker image store; Oyzu does not pull them or read registry credentials on this path.
# Daemonless: a digest-pinned base and only COPY and settings
FROM gcr.io/distroless/base-debian12:nonroot@sha256:7f0c72cd138b442ae0deeb69c08b1acf5525439ba251a49ad93c320a061567e5
COPY bin/server /server
USER 65532:65532
ENTRYPOINT ["/server"]

The full list of admitted instructions is in daemonless assembly.

Requirements​

  • A Linux Docker engine for BuildKit builds and for the quality checks. Oyzu pulls its own oyzu-toolchain/docker image from ghcr.io/oyzuai by pinned digest the first time it is needed (published toolchain images); set OYZU_NO_TOOLCHAIN_PULL=1 to forbid that on an offline host.
  • Hadolint and dockerfmt are inside that image for builds. For oyzu run lint and oyzu run format on your machine, they must be on PATH.
  • oyzu build --no-docker builds a daemonless target without contacting Docker; a target that needs the engine stops with exit status 3 before anything runs.

Checks and outputs​

lint runs hadolint --no-color Dockerfile and honors a target-local .hadolint.yaml. format-check runs dockerfmt with --check and honors a target-local .editorconfig. Both are build gates with --full and in CI (Dockerfile linting and formatting).

A successful image build records:

OutputContents
<target>-<version>.oci.tarThe image as an OCI layout archive, with its digest in manifest.json
JUnit reportIntegrity and platform assertions on the archive
Dependency recordEach base image's requested reference and verified digests, the Dockerfile digest and the build path used

Every image is checked against its target platform; a valid image for the wrong architecture fails. Supported image platforms are linux/x86_64 and linux/arm64 (linux/amd64 and linux/aarch64 are accepted spellings). List both in platforms and Oyzu builds one image per platform plus an OCI index over them. A Dockerfile with RUN in a target-platform stage needs the worker and target platforms to match.

Naming and loading the image​

with.repository names the image's eventual registry repository, such as registry.example.com/team/app. Building never contacts it; a chart binding reads it (below). The reference also documents a docker.load setting and oyzu run load for loading a built image into Docker or a k3d cluster without a registry (loading the image locally). The development CLI used for this page did not recognize docker.load yet.

Helm charts​

Tests that need no cluster​

oyzu build packages the chart and renders it with helm template --dry-run=client and an empty kubeconfig, so you get both a .tgz and rendered.yaml. With --full or in CI it also runs:

  • Validation: rendering plus values.schema.json checks for an application chart, or strict lint for a library chart, reported as junit.xml.
  • helm-unittest, when the chart (or a subchart) has tests/*_test.yaml suites, reported separately as unittest.xml. Snapshot baselines are inputs: creating or changing one during a build fails it.
  • helm lint and a read-only yamlfmt check of the chart's YAML (templates are not formatted).

Coverage is recorded as not applicable rather than as an invented percentage.

Pinning Helm​

Charts build in the captured worker with the image's Helm (3.22.0). To pin another, declare it and install it, which records the exact archive in oyzu.lock:

# oyzu.toml
[tools]
helm = "4.3.0"
oyzu install helm@4.3.0

Helm takes an exact version only. The image still supplies yamlfmt and the helm-unittest plugin. This path is not yet verified end to end in a Docker worker (pinned Helm).

Binding an image into a chart​

A chart can consume the identity of an image built in the same oyzu build, so nobody passes --set image.digest=… at deploy time:

builds:
  image:
    uses: docker/image
    with:
      repository: registry.example.com/team/greeting
  chart:
    uses: helm/chart
    path: chart
    bindings:
    - from: image
      artifact: image
      type: image-reference
      repository: /image/repository
      digest: /image/digest

The destinations are JSON Pointers into the chart's values.yaml; each must already be a string there (an empty digest: "" is the usual shape). Oyzu writes the repository and the image's actual manifest digest into a private copy of the chart before packaging, so the packaged defaults and rendered.yaml carry the produced reference and your checked-in chart is never edited. A changed image rebuilds the chart; a failed image blocks it. See image bindings for the reference form and the limits.

Worked example: binary, image and chart​

This uses example EX-029 from the Oyzu source tree (examples/builds/image-and-chart/project), in a new folder of its own with git init. It has a Go command in app/, a Dockerfile at the root and a chart in chart/:

FROM scratch
COPY bin/server /server
ENTRYPOINT ["/server"]

build.yaml connects them. materialize copies the Go target's binary to bin/server in the image's build context, and the chart binds the image:

builds:
  app:
    uses: go/app
    path: app
  image:
    uses: docker/image
    with:
      repository: registry.example.invalid/team/greeting
    materialize:
    - from: app
      to: bin/server
    platforms:
    - linux/amd64
  chart:
    uses: helm/chart
    path: chart
    bindings:
    - from: image
      artifact: image
      type: image-reference
      repository: /image/repository
      digest: /image/digest

The chart's values.yaml holds the placeholders the binding fills:

replicaCount: 1
image:
  repository: registry.example.invalid/team/greeting
  tag: development
  digest: ""

(The stage tables, the platform table and the tool requirements are trimmed.) Read it from the bottom up:

  • The image's platforms: [linux/amd64] makes the Go binary a linux/amd64 build too, so the materialized file matches the image. Oyzu names those platform variants app-platform-linux_x86_64-… and image-platform-linux_x86_64-….
  • The image needs no Docker engine: FROM scratch plus COPY is assembled in process.
  • The chart waits for the image and receives its OCI archive as .oyzu-bindings/0.oci.tar, the data its binding reads.
  • The Go binary and the chart still run in the captured worker, which needs Docker.

With --full, the image also selects lint and format-check, and its placement changes to Docker engine required, because Hadolint and dockerfmt run in the toolchain image.

3. Build​

oyzu build would then produce the Linux binary, a versioned .oci.tar image archive with its JUnit report, and the chart .tgz plus rendered.yaml whose image.digest is the image's real manifest digest. This flow is covered by the chart-bindings scenario recorded in the Helm reference (Windows 11 with Docker Desktop); it was not rerun for this page.

Common failures​

You seeCauseFix
Preparation names a missing base image (BuildKit path)The base is not in the local Docker image storePull or provision it with your organization's usual mechanism; or pin it by digest and keep the final stage RUN-free so the daemonless path fetches it
A private base fails on the daemonless pathOnly anonymous registry pulls are supportedUse a public base, or provision it locally and use the BuildKit path
A foreign-platform RUN fails before any actionRUN in a target-platform stage that differs from the workerBuild on a matching worker, or move compilation to a FROM --platform=$BUILDPLATFORM stage and only COPY into the target stage
Hadolint or dockerfmt failsA native lint or format findingFix it, or run oyzu run format and review the change
helm lint reports missing dependenciesA vendored subchart under charts/ is not declared in the parent Chart.yamlDeclare it (name and version, no repository URL)
A unittest snapshot fails the buildA baseline under __snapshot__ would be created or changedUpdate baselines deliberately with native helm-unittest, review and commit them
A binding fails during configurationThe destination is missing from values.yaml, the image lacks with.repository, or both binding forms are setAdd the string field, set with.repository, or use one form
NEEDS_DOCKER_DAEMON with --no-docker (exit 3)A selected target needs Docker, such as lint or format checks under --fullRun with Docker, or select only daemonless work

Limits​

  • Image builds are Linux images only (linux/x86_64, linux/arm64); native Windows images and emulated RUN are not supported.
  • Registry credentials, private bases on the daemonless path, remote ADD, secret and SSH mounts are not supported.
  • Binding a multi-platform image (an OCI index) into a chart is refused for now.
  • Chart dependencies from remote or OCI repositories, Go-template formatting and chart publishing or signing are not implemented.
  • Measured support is in capabilities and known limitations.
