Build Python projects

Oyzu builds Python distributions from pyproject.toml, uv.lock, poetry.lock or requirements.txt. It selects and installs CPython for you, builds wheels with your native backend, runs pytest with JUnit and Cobertura coverage, and checks your code with Ruff. You do not write an Oyzu build file for a package.

Python support is experimental. There are two paths, and which one your project takes matters:

  • Native (on your machine): pip projects with a pyproject.toml. Oyzu installs CPython and builds a wheel. No Docker.
  • Isolated (in a Linux container): uv, Poetry, requirements-only and legacy projects, and anything you request with --isolated. Dependencies are captured first and every action runs offline. This needs Docker and toolchain images that you provision yourself.

Every output block below was captured from a real run on Windows 11, with NO_COLOR=1 and output redirected to a file. Long local paths are shortened to …. Times, hashes and versions on your machine will differ.

What Oyzu detects​

Signal in your projectWhat it decides
pyproject.toml with [build-system]A python/package target built with pip through your declared PEP 517 backend
uv.lockuv manages the project; the lock's hashed export owns the dependency closure
poetry.lockPoetry manages the project
requirements.txt onlyA requirements-only application, with no invented distribution metadata
uses: python/app in build.yaml with one [project.scripts] entryAn application; the isolated path also produces a runnable .pyz
requires-pythonA constraint every selected CPython must satisfy
.python-versionThe default CPython request
pytest.ini, [tool.pytest.ini_options], [pytest] in tox.ini, [tool:pytest] in setup.cfgpytest configuration (pytest is the default either way)

Discovery reads files only. It never imports conftest.py, runs Python or collects tests.

Your first build: a pip project​

The example is examples/builds/python-api from the Oyzu repository, copied to an empty folder and initialized with git init. It is a small setuptools project with one console script and two unittest tests that pytest runs:

[project]
name = "oyzu-api-example"
version = "0.1.0"
requires-python = ">=3.10"
dependencies = []

[project.scripts]
oyzu-example-api = "api:main"

[build-system]
requires = ["setuptools==80.9.0"]
build-backend = "setuptools.build_meta"

Its build.yaml contains only uses: python/app for the api target.

(Progress rows trimmed.) What happened:

  1. prepare downloaded binary wheels for the uv export --locked closure, the build backend and the test and quality tools, through Oyzu's broker to public PyPI. Each wheel's digest is recorded.
  2. build ran the native backend once in the private workspace, with a PEP 440 snapshot version 0.1.0.dev0+ge9df5717bf00. Your pyproject.toml was not edited.
  3. test installed that built wheel offline and ran pytest against it, so coverage measures the installed package, not your checkout.
  4. lint and format-check ran Ruff read-only.
  5. package published the wheel and source distribution, because every gate passed.

Tests and coverage​

pytest is the supported runner. It also runs unittest.TestCase suites, as in the pip example. Oyzu records JUnit and Cobertura for every build and stores them under dist/ with digests in dist/manifest.json. No report configuration is needed.

ManagerDevelopment command (oyzu run test)
pippython -m pytest
uvuv run --locked pytest
Poetrypoetry run pytest

oyzu run test runs on your machine with your installed environment and writes a test-only dist/ bundle; pass pytest arguments after --, as in oyzu run test -- -k health. pytest, pytest-cov and coverage must already be installed there; Oyzu does not install them for development tasks.

Native pytest owns collection: testpaths, file patterns, markers and conftest behavior. Your coverage settings, including fail_under, are kept. Some behavior to expect:

  • An empty suite keeps pytest's exit code 5 and fails the build. Add tests or fix collection; an empty directory is not a passing result.
  • A failed coverage threshold fails the build even when every test passed.
  • Assertion failures keep their reports and block packaging.

See Python testing.

Lint and formatting​

Ruff runs ruff check . --no-fix for lint and ruff format --check . for format-check, reading its own configuration as it always does. Both are selected by --full or a CI context and never modify files during a build. oyzu run format runs ruff format . and does write files. In the isolated path Ruff is captured during preparation; on the native path it must already be available, as shown above.

Choose the Python version​

The order is: an explicit oyzu.toml request, then .python-version, constrained by requires-python, and finally the newest stable CPython.

SourceRole
[tools] python in oyzu.tomlThe request, when present
.python-version (one release such as 3.12 or 3.12.4)The default request
requires-python in pyproject.tomlA constraint every selection must satisfy
None of theseThe greatest stable release available

Adding a .python-version containing 3.12 to the pip example and previewing:

oyzu pin --dry-run

Or set it in oyzu.toml:

[tools]
python = "3.12"       # latest 3.12.x; ranges such as ">=3.11 <3.14" also work

Run oyzu pin without --dry-run to write oyzu.lock, or let the next oyzu build do it. Commit the lock. Pre-releases, free-threaded and debug builds are never selected. requires-python specifiers using !=, === or pre-release versions cannot be expressed as a tool range and fail with the specifier named; set [tools] python instead.

Interpreters come from Python Build Standalone for Linux amd64 and arm64, macOS arm64 and Windows amd64, verified against the publisher's checksum manifest. oyzu exec -- python --version runs the locked interpreter; pip runs it with -m pip. Oyzu does not provision uv or Poetry; the isolated images bring their own. The isolated images use Python 3.12 regardless of this selection. See Python installation.

Artifacts​

ProjectArtifacts
pip with pyproject.toml (native)A wheels-<version> directory holding the built wheel
Package (isolated)Wheel and source distribution, named with the PEP 440 snapshot version such as 0.1.0.dev0+g<source>
python/app (isolated)Wheel, source distribution and a runnable <target>-<version>.pyz containing the wheel's files and runtime dependencies
Requirements-only application (isolated)A .pyz built from app.py or __main__.py, versioned 0.0.0-dev.g<source>

Versions come from your static version, Git tags and Conventional Commits; see version inference. A .pyz needs a compatible Python to run, requires pure-Python wheels, and is not a release approval.

Limits​

  • The native path covers pip projects with pyproject.toml and produces wheels only. Its recorded qualification is on Linux x86_64; the default build on this page succeeded on Windows 11, and macOS is unverified.
  • The isolated path needs Docker and hand-built images and runs Python 3.12 only. Private package indexes are not supported; dependencies come from public PyPI.
  • In this page's Windows run, oyzu build --isolated --full of the pip example passed its tests and checks but failed at package with environment variable not found. That combination is not verified here.
  • Source builds of Git, sdist-only and local dependencies work only for uv projects; Poetry and pip Git or path sources are refused.
  • Only the dev dependency group is selected.
  • A green build is evidence that these stages passed on this source. It is not a release approval.
