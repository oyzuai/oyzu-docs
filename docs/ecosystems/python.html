Build Python projects

Oyzu builds Python distributions from pyproject.toml, uv.lock, poetry.lock or requirements.txt. It selects and installs CPython for you, builds wheels with your own backend, runs pytest with JUnit and Cobertura coverage, and checks your code with Ruff. You don't write an Oyzu build file for a package.

Note: The Python builder is experimental. It runs as the oyzu/python plugin. If no release of it is available to your installation, the build stops with PLUGIN_UNAVAILABLE. Supported on Linux and Windows (x86-64). macOS is not supported yet.

Which of two paths your project takes matters:

  • Native (on your machine): pip projects with a pyproject.toml. Oyzu installs CPython and builds a wheel. No Docker.
  • Isolated (in a Linux container): uv, Poetry, requirements-only and legacy projects, and anything you request with --isolated. Dependencies are downloaded first, and every action runs offline. This needs Docker and the base execution image, with CPython in oyzu.lock. uv and Poetry builds also need an image of your own with that manager installed, passed with --image uv=<ref> or --image poetry=<ref>.

What Oyzu detects​

Signal in your projectWhat it decides
pyproject.toml with [build-system]A python/package target built with pip through your declared PEP 517 backend
uv.lockuv manages the project, and the lock's hashed export owns the dependency set
poetry.lockPoetry manages the project
requirements.txt onlyA requirements-only application, with no invented distribution metadata
uses: python/app in build.yaml with one [project.scripts] entryAn application. The isolated path also produces a runnable .pyz
requires-pythonA constraint every selected CPython must satisfy
.python-versionThe default CPython request
pytest.ini, [tool.pytest.ini_options], [pytest] in tox.ini, [tool:pytest] in setup.cfgpytest configuration (pytest is the default either way)

Discovery reads files only. It never imports conftest.py, runs Python or collects tests.

Your first build: a pip project​

The example is examples/builds/python-api from the Oyzu repository. Copy it to an empty folder and run git init. It's a small setuptools project with one console script and two unittest tests that pytest runs:

[project]
name = "oyzu-api-example"
version = "0.1.0"
requires-python = ">=3.10"
dependencies = []

[project.scripts]
oyzu-example-api = "api:main"

[build-system]
requires = ["setuptools==80.9.0"]
build-backend = "setuptools.build_meta"

Its build.yaml contains only uses: python/app for the api target.

Tests and checks on the native path​

oyzu build --full adds test (pytest) and lint and format-check (Ruff). On the native path, Oyzu doesn't install pytest, pytest-cov or Ruff for you, so on a fresh machine the checks fail:

$ oyzu build --full
── Failure: api · test ─────────────────────────────────────────────────────────
  ModuleNotFoundError: No module named 'pytest'
  Exit  1
  Log   dist/logs/0001.stderr
  Next  oyzu build api   re-run only this target
​
── Failure: api · lint ─────────────────────────────────────────────────────────
  cannot execute ruff: program not found
​
✗ Build failed   3 failed · 1 succeeded · 13.2s
  Note     Local binaries were not updated; existing binaries are from the previous successful
           build.

Output shortened. The wheel built, but required test evidence is missing, so the build fails and Oyzu keeps the previous good outputs.

To fix this, create a .venv in the target folder from the Python Oyzu selected, install your dependencies, pytest, pytest-cov, coverage and your quality tools into it, and build again:

oyzu exec -- python -m venv .venv
.venv/bin/python -m pip install pytest pytest-cov coverage ruff   # .venv\Scripts\python on Windows
# also install your project's own dependencies the usual way
oyzu build --full

Oyzu checks that the .venv was made from exactly the Python it selected. A .venv made from another Python, or with system site packages, is refused: recreate it from the selected base. Activation, VIRTUAL_ENV and PYTHONPATH don't select the environment. You can also replace a stage's command in oyzu.toml with [tasks.lint] and similar. A replacement test task must still produce the JUnit and coverage reports. See native preparation.

Your first build: a uv project (isolated)​

uv, Poetry and requirements-only projects use the isolated executor. The example is examples/builds/python-uv-library: a setuptools package with a committed uv.lock and a dev dependency group that holds pytest and pytest-cov.

$ oyzu run list
Available tasks · 6 across 1 target
​
Task                  Source         Command
project · python/package (6)
project:build         Inferred · uv  uv build
project:format        Inferred · uv  ruff format .
project:format-check  Inferred · uv  ruff format --check .
project:install       Inferred · uv  uv sync --locked
project:lint          Inferred · uv  ruff check . --no-fix
project:test          Inferred · uv  uv run --locked pytest

oyzu build --plan shows Docker engine required. The isolated Python path runs on the base execution image with the locked CPython 3.12. uv and Poetry aren't restored from the lock yet, so those projects need --image uv=<ref> or --image poetry=<ref> (Python applications). Image names in the output below may differ from what your version prints.

$ oyzu build --plan
project · python/package · unresolved until executor selection
Executor: captured-worker
Placement: runs on any platform · Docker engine required · Isolated steps run in the captured worker on a Docker engine
Discovered       Selection  Reason
package-manager  uv         native uv.lock lockfile
test-framework   pytest     default, no stronger evidence

Output shortened. A full build goes through these stages:

  1. prepare downloads binary wheels for the uv export --locked closure, the build backend and the test and quality tools, through Oyzu's broker to public PyPI. Each wheel's digest is recorded.
  2. build runs the backend once in a private workspace, with a PEP 440 snapshot version of the form 0.1.0.dev0+g<source>. Your pyproject.toml isn't edited.
  3. test installs the built wheel offline and runs pytest against it, so coverage measures the installed package, not your checkout.
  4. lint and format-check run Ruff read-only.
  5. package publishes the wheel and source distribution once every gate has passed.

The example folder contains a .python-version file with 3.12. Without it, requires-python = ">=3.10" selects the newest CPython, and prepare fails with coverage-… is not a supported wheel on this platform, because the lock holds wheels built for Python 3.12. See Choose the Python version.

Tests and coverage​

pytest is the supported runner, and it also runs unittest.TestCase suites, as in the pip example. Oyzu records JUnit and Cobertura for every build and stores them under dist/, with digests in dist/manifest.json. You don't configure reporting.

ManagerDevelopment command (oyzu run test)
pippython -m pytest
uvuv run --locked pytest
Poetrypoetry run pytest

oyzu run test runs on your machine with your installed environment and writes a test-only dist/ bundle. Pass pytest arguments after --, as in oyzu run test -- -k health. pytest, pytest-cov and coverage must already be installed there, because Oyzu doesn't install them for development tasks.

pytest owns test collection: testpaths, file patterns, markers and conftest behavior. Your coverage settings, including fail_under, are kept. Expect this behavior:

  • An empty suite keeps pytest's exit code 5 and fails the build. Add tests or fix collection, because an empty directory isn't a passing result.
  • A failed coverage threshold fails the build even when every test passed.
  • Assertion failures keep their reports and block packaging.

See Python testing.

Lint and formatting​

Ruff runs ruff check . --no-fix for lint and ruff format --check . for format-check, reading its own configuration as usual. Both are selected by --full or a CI context and never modify files during a build. oyzu run format runs ruff format . and does write files. In the isolated path Ruff is downloaded during preparation. On the native path it must already be installed, as shown above.

Choose the Python version​

Oyzu picks the version in this order: an explicit oyzu.toml request, then .python-version, always constrained by requires-python, and finally the newest stable CPython.

SourceRole
[tools] python in oyzu.tomlThe request, when present
.python-version (one release such as 3.12 or 3.12.4)The default request
requires-python in pyproject.tomlA constraint every selection must satisfy
None of theseThe greatest stable release available

Set it in oyzu.toml:

[tools]
python = "3.12"       # latest 3.12.x; ranges such as ">=3.11 <3.14" also work

Run oyzu pin --dry-run to preview the choice, or oyzu pin to write oyzu.lock (the next oyzu build also does it). Commit the lock. Pre-releases, free-threaded and debug builds are never selected. A requires-python specifier that uses !=, === or pre-release versions can't be turned into a tool range and fails with the specifier named. Set [tools] python instead.

Interpreters come from Python Build Standalone for Linux (amd64, arm64), macOS (arm64, amd64) and Windows (amd64), checked against the publisher's checksum manifest. oyzu exec -- python --version runs the locked interpreter, and pip runs it with -m pip. Oyzu doesn't provision uv or Poetry; the isolated images bring their own. Isolated builds use Python 3.12 regardless of this selection. On Intel macOS you can install Python 3.11 and run pip with it, but wheel builds there aren't supported yet. See Python installation.

ProjectArtifacts

Package (isolated)Wheel and source distribution, named with the PEP 440 snapshot version such as 0.1.0.dev0+g<source>
python/app (isolated)Wheel, source distribution and a runnable <target>-<version>.pyz containing the wheel's files and runtime dependencies
Requirements-only application (isolated)A .pyz built from app.py or __main__.py, versioned 0.0.0-dev.g<source>

Versions come from your static version, Git tags and Conventional Commits; see version inference. A .pyz needs a compatible Python to run, requires pure-Python wheels, and isn't a release approval.

Limits​

  • The native path covers pip projects with pyproject.toml and produces wheels only.
  • The isolated path needs Docker and the base execution image (plus your own image for uv and Poetry) and runs Python 3.12 only. Private package indexes aren't supported. Dependencies come from public PyPI.
  • On a Windows host, the package stage of isolated builds failed in earlier testing (No such file or directory or environment variable not found), so the wheel and source distribution weren't exported there. The checks before it ran normally.
  • Source builds of Git, sdist-only and local dependencies work only for uv projects. Poetry and pip Git or path sources are refused.
  • Only the dev dependency group is selected.
  • A green build shows that the stages passed on this source. It isn't a release approval.
