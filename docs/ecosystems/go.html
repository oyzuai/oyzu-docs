Go

Oyzu builds Go modules and workspaces from go.mod and go.work alone. It picks the Go version your module asks for, installs it, and runs the native go build, go test, go vet and gofmt commands, collecting a binary, JUnit results and statement coverage into a verified dist/ bundle.

The Go builder is experimental. Applications build on the host; libraries and workspaces use the captured container executor and need Docker. The Go reference is the full contract; this page is the practical guide.

Every output block below is a real capture from Windows 11 (windows/amd64) with a development build of the CLI (0.1.0-local.564f462704df), color forced on and output piped to a file. Long scratch paths are shortened to …. Times, hashes and paths on your machine will differ. The tutorial walks through the same kind of project step by step, including a failing test and reuse.

What Oyzu detects​

ProjectBuilderWhere it builds
A module with a main package (go.mod)go/appOn the host
A module with no main packagego/app, packaged as a moduleIn the captured executor (Docker)
A workspace (go.work)one target for the workspaceIn the captured executor (Docker)

Discovery reads the files and runs nothing. Native Go decides the rest during preparation: workspace members, which packages are main packages, dependencies and cgo. You can force module packaging for a module that also has commands with uses: go/library in build.yaml.

The inferred tasks are plain Go commands:

Run one with: oyzu run <task>   (extra arguments go after --)
Commands show argv; task dependencies and hooks may also run. Use --json for full task records.

format rewrites your files and never runs inside a build; the build uses format-check, which fails when gofmt -l lists anything.

Choosing the Go version​

Go's own files decide. Oyzu runs Go with GOTOOLCHAIN=local, so Go never downloads a toolchain behind your back; Oyzu selects and installs it instead.

  • The go line in go.mod (or go.work in a workspace) is a minimum. With go 1.22 and nothing else, Oyzu locks the newest stable release of that line (1.22.12 in the captures below).
  • A toolchain line is also honored, as Go reads it, and the newer of the two lines is the minimum.
  • [tools] go = "1.24" in oyzu.toml chooses a release at or above that minimum.

The exact selection goes into oyzu.lock with the minimum recorded beside it, for example go-minimum:>=1.22. Commit the lock. The Tools row of each build says what was used: go 1.22.12 already installed detected from go.mod.

Artifacts and reports​

Everything lands in the dist/ bundle; the Outputs section prints each artifact's path and manifest.json records it with its digest. The build bundle layout describes the directories.

OutputContents
<target>-<version>[.exe]The application binary, or one per named command
module-<n>-<version>.zip, .mod, .infoFor a library: the native module archive, its go.mod and proxy metadata
reports/junit.xmlTest results converted from go test -json
reports/coverage.outGo's native coverage profile
manifest.jsonEvery file with its digest, plus the plan and evidence

Versions are snapshots: 0.0.0-dev.g<source> without a tag, or a tag-derived base with the same suffix. For a /v2 module the snapshot is v2.0.0-dev.g…, so it satisfies Go's module path rules. A snapshot is not a release; see version inference.

Libraries and workspaces​

A module with no main package, or a go.work workspace, is planned for the captured executor. The preview of the example's library variant (examples/builds/go-app/variants/library, module example.com/oyzu/math/v2) says so before anything runs:

$ oyzu build --plan
…
Build preview
Execution: isolated · No tools installed, dependencies downloaded or build actions run.
​
Engine
  Actual   0.1.0-local.564f462704df
​
project · go/app · unresolved until executor selection
Executor: captured-worker
Profile: development · local dist only (no difference: the Go compiler always optimizes)
Placement: runs on any platform · Docker engine required · Isolated steps run in the captured worker on a Docker engine
Stage         Selection   Details
build         selected    Native commands and report bindings resolve during preparation
format-check  skipped     fast local build
lint          skipped     fast local build
test          skipped     fast local build
prepare       unresolved  Target environment setup is determined by native dependency preparation
package       unresolved  Artifact packaging is determined by native metadata

…

Captured builds download public modules through Oyzu's scoped Go proxy, verify them against go.sum, then build, test, vet and package with networking denied. Oyzu pulls the default Go toolchain image (oyzu-toolchain/go) from its published set when Docker does not already have it; offline hosts need it provisioned in advance. A Go version you pin is restored into the worker in place of the image's own Go. This page did not run a captured Go build; see the Go reference.

Limits​

  • Private module sources, direct VCS fetches and module publication are not implemented.
  • Cross-compiling with GOOS/GOARCH as a build option is not established; platform matrices select matching provisioned toolchains (toolchain platforms).
  • Full cgo portability is not qualified; cgo builds stay on the coarse captured plan.
  • Measured support is listed in capabilities and known limitations.
