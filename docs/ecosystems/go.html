Go

Oyzu builds Go modules and workspaces from go.mod and go.work alone. It picks the Go version your module asks for, installs it, and runs the native go build, go test, go vet and gofmt commands. It collects the binary, JUnit results and statement coverage into a verified dist/ bundle.

Note: The Go builder is experimental. It runs as the oyzu/go plugin, whose releases are previews: opt in once with oyzu config set --global plugins.preview true. Applications build on your machine. Libraries and workspaces build in the isolated executor and need Docker. Supported on Linux and Windows (x86-64). macOS is not supported yet.

The Go reference has the full details. The tutorial walks through a Go project step by step, including a failing test and reuse.

What Oyzu detects​

ProjectBuilderWhere it builds
A module with a main package (go.mod)go/appOn your machine
A module with no main packagego/app, packaged as a moduleIn the isolated executor (Docker)
A workspace (go.work)One target for the workspaceIn the isolated executor (Docker)

Discovery reads files and runs nothing. Go itself decides workspace members, which packages are main, dependencies and cgo during preparation. To package a module as a library even when it also has commands, set uses: go/library in build.yaml.

The inferred tasks are plain Go commands:

$ oyzu run list
Available tasks · 6 across 1 target
​
Task                  Source         Command
project · go/app (6)
project:build         Inferred · go  go build ./...
project:format        Inferred · go  gofmt -w .
project:format-check  Inferred · go  gofmt -l .
project:install       Inferred · go  go mod download
project:lint          Inferred · go  go vet ./...
project:test          Inferred · go  go test ./...

format rewrites your files and never runs inside a build. The build uses format-check, which fails when gofmt -l lists anything.

Build and test​

CommandWhat runs
oyzu build --planNothing. Shows the stages and the Go minimum read from go.mod
oyzu buildgo build with -trimpath and VCS stamping off, then collects the binary
oyzu build --fullAlso go test -json with a coverage profile, go vet and gofmt -l
oyzu run testOnly the tests, on your machine, writing a test-only dist/ bundle

In CI the checks run without --full. Arguments after -- go to the task's command, so you can select tests the Go way:

$ oyzu run test -- -run TestGreeting
  · project · Testing  TEST_EVIDENCE:
                       Test evidence project:test
                       Command passed
                       Results 1 passed · 0 failed · 0 skipped
                       Coverage 50.0% of statements (1/2)
                       Acceptance accepted
  ✓ project · Testing  Succeeded (exit 0 after 2.30s)

Output shortened. Oyzu adds -json, a fresh -coverprofile and -count=1 to the implicit go test ./..., converts the events to JUnit and keeps Go's coverage profile. Coverage is statement coverage, as Go measures it.

If checks.coverageMinimum is above zero, the test action supplies the target's coverage report, and the build fails if that report is missing or below the minimum. See build check requirements.

Choose the Go version​

Go's own files decide. Oyzu runs Go with GOTOOLCHAIN=local, so Go never downloads a toolchain behind your back. Oyzu selects and installs it instead.

  • The go line in go.mod (or go.work in a workspace) is a minimum. With go 1.22 and nothing else, Oyzu locks the newest stable release of that line.
  • A toolchain line is honored too. The newer of the two lines is the minimum.
  • [tools] go = "1.24" in oyzu.toml picks a release at or above that minimum.

The exact choice goes in oyzu.lock with the minimum recorded beside it (for example go-minimum:>=1.22). Commit the lock. The Tools row of each build says what ran: go 1.22.12 already installed detected from go.mod.

If you change [tools] go (say to 1.23), the next build refuses to guess and tells you to update the lock:

$ oyzu build
── Prepare ─────────────────────────────────────────────────────────────────────
  ✓ Configuration           Loaded and validated                           <0.1s
  ✗ Tools                   failed: preparation did not complete           <0.1s
✗ TOOL_LOCK_STALE: oyzu:go 1.23; run oyzu pin
  Next: Run oyzu pin --refresh to refresh the lock, then oyzu install.

A request below the module's minimum (here [tools] go = "1.21" with go 1.22) is refused before any work, naming both files:

$ oyzu pin
✗ TOOL_NATIVE_MINIMUM_CONFLICT: project: [tools] go = "1.21" in oyzu.toml is below the go minimum 1.22 that go.mod declares (go line); set [tools] go to 1.22 or later in oyzu.toml, or remove it so the native file decides

The Go reference has the complete rule, including toolchain lines, workspace files and oyzu.toml values in different folders.

Outputs​

Everything lands in the dist/ bundle. The Outputs section prints each artifact's path, and manifest.json records it with its digest. The bundle layout describes the directories.

OutputContents
<target>-<version>[.exe]The application binary, or one per named command
module-<n>-<version>.zip, .mod, .infoFor a library: the module archive, its go.mod and proxy metadata
reports/junit.xmlTest results converted from go test -json
reports/coverage.outGo's coverage profile
manifest.jsonEvery file with its digest, plus the plan and build evidence

Versions are snapshots: 0.0.0-dev.g<source> without a tag, or a tag-derived base with the same suffix. For a /v2 module the snapshot is v2.0.0-dev.g…, so it satisfies Go's module path rules. A snapshot isn't a release; see version inference.

Libraries and workspaces​

A module with no main package, or a go.work workspace, builds in the isolated executor. The plan says so before anything runs:

$ oyzu build --plan
project · go/app · unresolved until executor selection
Executor: captured-worker
Placement: runs on any platform · Docker engine required · Isolated steps run in the captured worker on a Docker engine

Output shortened. Isolated builds download public modules through Oyzu's scoped Go proxy, verify them against go.sum, then build, test, vet and package with no network. They run on the base execution image, which Oyzu pulls on first use. The image has no Go: the Go in oyzu.lock is restored into each action. See the Go reference.

Limits​

  • Private module sources, direct VCS fetches and module publication aren't supported.
  • Cross-compiling with GOOS and GOARCH as a build option isn't supported. Platform matrices select matching provisioned toolchains (toolchain platforms).
  • cgo builds work only through the coarse isolated plan. Full cgo portability isn't supported.
  • Libraries and workspaces need Docker.

See capabilities and known limitations for the whole product.
