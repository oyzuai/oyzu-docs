.NET

Oyzu builds an SDK-style .NET solution or project with no configuration. It honors global.json for SDK selection, restores NuGet packages through a controlled mirror, then builds, tests and packs offline in an isolated Linux container. Test results become JUnit and every packable project becomes a NuGet package in the dist/ bundle.

The .NET builder (dotnet/sdk) has a bounded verification: its full restore, build, test and pack flow passed on Linux amd64 with SDK 10.0.401, including an independent consumer of the delivered package. Windows and macOS images do not exist yet, and several builder choices are provisional. The .NET reference is the full contract.

The output below was captured on Windows 11 (windows/amd64) with a development build of the CLI, NO_COLOR=1 and output redirected to a file. Long paths are shortened to …. Only discovery and --plan were run for this page: a .NET build needs a locally built toolchain image (below), and no image was built.

Requirements​

.NET builds always run in the captured executor; there is no host build path. You need:

  • Docker with a Linux engine. The plan says so: Docker engine required.
  • The toolchain image oyzu-toolchain/dotnet:10.0.401. Unlike the Go, Helm and Docker images, Oyzu does not publish or pull it. It is built from the Dockerfiles under tooling/images/ in the Oyzu source tree (builder-worker.Dockerfile, then dotnet.Dockerfile), on a digest-pinned mcr.microsoft.com/dotnet/sdk:10.0.401-noble-aot base plus Oyzu's compiled worker. The exact commands are in the .NET reference.
  • To use another SDK image, pass --image dotnet=<image>.

You do not need the .NET SDK on your machine.

What Oyzu detects​

A folder is a .NET target when it directly contains a solution (.sln, .slnx) or an SDK-style project (.csproj, .fsproj, .vbproj whose root names an MSBuild SDK). Legacy non-SDK projects are not claimed.

The version 1.2.0 comes from a literal <Version> in the root Directory.Build.props; a literal Version or VersionPrefix in the entry project works the same way. The tasks are native dotnet commands:

Task             Source             Command
project · dotnet/sdk (5)

                                    integration was discovered

project:lint     Inferred · dotnet   — Unavailable: No native configuration or registered
                                    integration was discovered
project:test     Inferred · dotnet  dotnet test

Format and lint integrations do not exist for .NET yet, and the tasks list says so rather than inventing commands.

One entry per target​

Every native command receives one entry: the single solution, otherwise the single SDK-style project. If a folder has more than one candidate, the build fails and names them. Pick one in build.yaml:

builds:
  app:
    uses: dotnet/sdk
    with:
      project: Greeting.slnx

with.project is the only option; any other key is refused (invalid .NET with options: unknown field …, expected project).

Choosing the SDK​

global.json in the target folder selects the SDK exactly as the dotnet host does: sdk.version, sdk.rollForward (default patch with a version, latestMajor without one) and sdk.allowPrerelease. Without global.json the image's SDK is used.

Oyzu does not predict the result. During preparation it lists the SDKs in the image and observes what dotnet --version selects in your folder. If nothing installed satisfies the request, preparation fails before restore, naming the request, the SDKs that were available and --image dotnet=<image> as the remedy. global.json must be strict JSON; comments are refused.

--plan shows the request beside the image default:

Tool requirements · availability not checked

dotnet-sdk   tool  10.0.400 rollForward latestFeature; default image SDK   project  global.json /sdk

Build and test​

CommandWhat runs
oyzu build --planNothing. Shows the SDK request and the stages
oyzu buildRestore, dotnet build in Release, then dotnet pack
oyzu build --fullAlso dotnet test, with results converted to JUnit

In CI the test stage runs without --full. Inside the container:

  1. Restore runs once during preparation with networking denied, through a loopback mirror that reaches only the public https://api.nuget.org/ flat container (and its vulnerability data) via Oyzu's scoped broker. Feeds and credentials from NuGet.Config, user settings or RestoreSources are not used. If any packages.lock.json exists, restore uses --locked-mode.
  2. Build runs dotnet build <entry> --configuration Release --no-restore with -p:Version=<snapshot version>.
  3. Test (when selected) runs dotnet test --no-build --no-restore with TRX output (VSTest, or Microsoft.Testing.Platform when global.json selects it). All TRX files become one JUnit report. A test run that produces no TRX fails rather than reporting an empty suite.
  4. Pack runs dotnet pack --no-build into one directory artifact, nuget-packages-<version>. It fails when no project is packable.

NuGet audit​

Preparation restores with NuGet audit enabled and reports what it finds as a NuGet audit preparation step (for example known vulnerabilities: 1 high), as NUGET_AUDIT warnings and in the dependency record. Findings never fail the build, and they cannot turn into compile errors under TreatWarningsAsErrors.

Worked example: a library with tests​

This uses the .NET fixture from the Oyzu source tree (tooling/fixtures/dotnet-app): a solution with a packable Greeting library and an xUnit test project. Its files:

global.json:

{
  "sdk": {
    "version": "10.0.400",
    "rollForward": "latestFeature"
  }
}

Directory.Build.props:

<Project>
  <PropertyGroup>
    <Version>1.2.0</Version>
    <TargetFramework>net10.0</TargetFramework>
    <Nullable>enable</Nullable>
    <TreatWarningsAsErrors>true</TreatWarningsAsErrors>
  </PropertyGroup>
</Project>

Greeting.slnx lists src/Greeting/Greeting.csproj (with RestorePackagesWithLockFile and a checked-in packages.lock.json) and test/Greeting.Tests/Greeting.Tests.csproj (IsPackable false, referencing Microsoft.NET.Test.Sdk, xunit and xunit.runner.visualstudio).

Preview the full build:

oyzu build --plan --full

Even though this runs on Windows, the plan places the target in the captured Linux worker. The request 10.0.400 with latestFeature admits the image's 10.0.401. Running oyzu build --full with the image provisioned restores, builds, runs the tests and packs Example.Greeting; the recorded Linux run of this fixture produced JUnit with 3 total, 2 passed, 1 skipped, and an independent offline consumer of the delivered package printed Hello, Oyzu!. That evidence is in the .NET reference; it was not repeated for this page.

Artifacts and reports​

OutputContents
nuget-packages-<version>/One directory artifact with every packable project's .nupkg

Limits​

  • Linux amd64 only; no Windows or macOS images.
  • Private feeds, credentials, package source mapping and workloads are not supported in captured builds.
  • global.json and Directory.Build.* above the target folder are outside the captured source.
  • No coverage, lint or format integrations; no per-package artifacts, dotnet publish outputs or NativeAOT publishing stage.
  • A repository without a root solution needs with.project.
  • Provisional choices (builder name, default SDK image, audit never enforced, memory and timeout limits) are listed in the .NET reference.
