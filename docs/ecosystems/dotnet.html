.NET

Oyzu builds an SDK-style .NET solution or project with no configuration. It honors global.json for SDK selection, restores NuGet packages through a controlled mirror, then builds, tests and packs offline in an isolated Linux container. Test results become JUnit, VSTest runs collect Cobertura coverage, and every packable project becomes a NuGet package in the dist/ bundle.

Note: The .NET builder is experimental. It runs as the oyzu/dotnet plugin and builds only in the isolated Linux executor, so you need Docker. Supported on Linux (x86-64) containers, with SDK 10.0.401 by default. There are no Windows or macOS builds yet. You can start the build from Windows, but it still runs in the Linux container.

The current CLI requires a .NET plugin with dotnet-lock-admission. The catalog's 0.1.0-preview.1 package does not declare it, so it cannot build with this CLI. The workflows below require a compatible package; a routine update cannot add a release the catalog does not yet offer.

The .NET reference has the full details.

Requirements​

.NET builds always run in the isolated executor, with no host build path. You need:

  • Docker with a Linux engine. The plan says Docker engine required.
  • The base execution image. Oyzu pulls it on first use.
  • The SDK in oyzu.lock. Run oyzu pin. Without a [tools] dotnet setting it locks the default SDK, 10.0.401, and restores it into every action. See provisioning.
  • A compatible .NET plugin. Its builder role must declare dotnet-lock-admission. An older exact package selection is refused before private restore preparation; explicitly select an admitted capable package with oyzu plugins update dotnet/sdk. See isolated restore.
  • To run on an image of your own, pass --image dotnet=<image>. The locked SDK is still used.

You don't need the .NET SDK on your machine.

What Oyzu detects​

A folder is a .NET target when it directly contains a solution (.sln, .slnx) or an SDK-style project (.csproj, .fsproj, .vbproj whose root names an MSBuild SDK). Legacy non-SDK projects aren't claimed.

The version comes from a literal <Version> in the root Directory.Build.props. A literal Version or VersionPrefix in the entry project works too. The tasks are native dotnet commands:

$ oyzu run list

That capture shows the older plugin. With a compatible current plugin, lint runs dotnet format analyzers and the format check runs dotnet format whitespace --verify-no-changes, using your .editorconfig. See the reference.

One entry per target​

Every native command gets one entry: the single solution, otherwise the single SDK-style project. If a folder has more than one candidate, the build fails and names them. Pick one in build.yaml:

builds:
  app:
    uses: dotnet/sdk
    with:
      project: Greeting.slnx

with.project is the only option. Any other key is refused (invalid .NET with options: unknown field …, expected project).

Choose the SDK​

global.json in the target folder selects the SDK the way the dotnet host does: sdk.version, sdk.rollForward (default patch with a version, latestMajor without one) and sdk.allowPrerelease. Without global.json, the locked SDK is used. global.json must be strict JSON, so comments are refused.

Oyzu doesn't predict the result. During preparation it lists the SDKs in the container and asks dotnet --version which one your folder selects. If nothing installed satisfies the request, preparation fails before restore. The message names the request, the available SDKs and oyzu pin as the remedy.

--plan shows the request. Current versions list the SDK requirement as oyzu:dotnet; the output below may show an older image default.

$ oyzu build --plan
Tool requirements · availability not checked
Requirement  Kind  Constraint                                              Targets  Source
dotnet-sdk   tool  10.0.400 rollForward latestFeature; default image SDK   project  global.json /sdk
                   10.0.401

Build and test​

CommandWhat runs
oyzu build --planNothing. Shows the SDK request and the stages
oyzu buildRestore, dotnet build (Debug by default, Release with --optimized), then dotnet pack
oyzu build --fullAlso dotnet test, with results converted to JUnit

In CI the test stage runs without --full. Inside the container:

  1. Restore runs once during preparation with no network, through a loopback mirror. The mirror reaches only the public https://api.nuget.org/ flat container (and its vulnerability data) through Oyzu's scoped broker. Feeds and credentials from NuGet.Config, user settings or RestoreSources aren't used. If any packages.lock.json exists, restore uses --locked-mode.
  2. Build runs dotnet build <entry> --configuration Debug --no-restore (Release for an optimized build) with -p:Version=<snapshot version>.
  3. Test, when selected, runs dotnet test --no-build --no-restore with TRX output (VSTest, or Microsoft.Testing.Platform when global.json selects it). All TRX files become one JUnit report. A test run that produces no TRX fails instead of reporting an empty suite.
  4. Pack runs dotnet pack --no-build into one directory artifact, nuget-packages-<version>. It fails when no project is packable.

NuGet audit​

Preparation restores with NuGet audit on and reports what it finds as a NuGet audit step (for example known vulnerabilities: 1 high), as NUGET_AUDIT warnings and in the dependency record. Findings never fail the build, and they can't turn into compile errors under TreatWarningsAsErrors.

Worked example: a library with tests​

This is the .NET fixture from the Oyzu source tree (tooling/fixtures/dotnet-app): a solution with a packable Greeting library and an xUnit test project.

global.json:

{
  "sdk": {
    "version": "10.0.400",
    "rollForward": "latestFeature"
  }
}

Directory.Build.props:

<Project>
  <PropertyGroup>
    <Version>1.2.0</Version>
    <TargetFramework>net10.0</TargetFramework>
    <Nullable>enable</Nullable>
    <TreatWarningsAsErrors>true</TreatWarningsAsErrors>
  </PropertyGroup>
</Project>

Greeting.slnx lists src/Greeting/Greeting.csproj (with RestorePackagesWithLockFile and a checked-in packages.lock.json) and test/Greeting.Tests/Greeting.Tests.csproj (IsPackable false, referencing Microsoft.NET.Test.Sdk, xunit and xunit.runner.visualstudio).

nuget-packages-<version>/One directory artifact with every packable project's .nupkg

Common failures​

You seeCauseFix
Several entry candidates namedMore than one solution or project in the folderSet with.project in build.yaml
No installed SDK satisfies the requestglobal.json asks for an SDK the locked one doesn't satisfyChange global.json, or set a matching [tools] dotnet and run oyzu pin
Restore fails under --locked-modepackages.lock.json no longer matches the project's dependenciesUpdate the lock with dotnet restore and commit it
NU1503 or an MSBuild SDK not foundA NuGet-supplied MSBuild SDK whose version is a property, range or wildcardWrite a literal version (Sdk="Name/1.2.3" or msbuild-sdks in global.json) so Oyzu can restore it in preparation
Pack fails: no packable projectEvery project sets IsPackable to falseMake the library packable, or build a different target
A test failsThe test run failedJUnit is kept and the package isn't exported

Limits​

  • Linux (x86-64) containers only. There are no Windows or macOS builds.
  • Private feeds, credentials, package source mapping and workloads aren't supported.
  • global.json and Directory.Build.* files above the target folder aren't copied into the build.
  • VSTest collects coverage; Microsoft.Testing.Platform does not. There are no per-package artifacts, dotnet publish outputs or NativeAOT publishing stage.
  • A repository without a root solution needs with.project.
  • The default SDK, memory and timeout limits and the builder name may still change. See the reference.
