Build Java projects

Oyzu builds Maven reactors and Gradle builds from pom.xml and build.gradle alone. It provisions the JDK and Maven or Gradle itself, runs your normal lifecycle, collects JUnit and JaCoCo reports and records the jars it produced. You don't need Java installed, and you don't write an Oyzu build file.

Note: The Java builder is experimental. It runs as the oyzu/java plugin, whose one build kind, java/app, covers Maven, Gradle and Ant. Maven and Gradle build on your machine. Ant needs the isolated executor. Supported on Linux and Windows (x86-64). macOS is not supported yet.

What Oyzu detects​

Signal in your projectWhat it decides
pom.xmlA java/app target built with Maven. A reactor (parent POM with <modules>) is one target, and Maven owns module order, inheritance and profiles
build.gradle or build.gradle.ktsA java/app target built with Gradle. A multi-project build, including includeBuild composites, is one target, and Gradle owns membership and task dependencies
build.xmlA java/app target built with Ant, only in the isolated executor
mvnw or gradlew committedOyzu runs the wrapper instead of mvn or gradle and provisions only the JDK
Literal root Maven compiler-plugin release/source/target or corresponding maven.compiler.* propertiesThe compiler JDK floor; java.version alone is only a default hint
JavaLanguageVersion.of(…) or sourceCompatibility in the root Gradle build scriptThe static startup JDK minimum; nested compilers are checked through Gradle during native preparation
toolchainVersion in gradle/gradle-daemon-jvm.propertiesThe exact daemon Java feature release; unrelated sibling scripts do not contribute requirements

Discovery reads files only. It doesn't start Maven or Gradle.

More than one build file​

A folder with build files for two tools, such as a pom.xml beside a build.xml, stops discovery and asks you to choose. Declare the target and name the build tool:

builds:
  app:
    uses: java/app
    with:
      build-tool: maven

build-tool takes maven, gradle or ant, and it's the only with option for java/app. oyzu build --plan shows the decision as the build-tool row of the target's Discovered table.

Tests and coverage​

You don't configure tests or reports.

  • Maven. verify runs Surefire and, where a module declares maven-failsafe-plugin and has IT*, *IT or *ITCase classes, Failsafe. Each module with test sources must produce JUnit XML in target/surefire-reports (and target/failsafe-reports). JaCoCo 0.8.13 runs around verify, and each module's target/site/jacoco/jacoco.xml is collected.
  • Gradle. build runs your Test tasks. Oyzu collects each tested project's JUnit results and the JaCoCo report its init script writes under build/reports/oyzu/<test task>/jacoco.xml.

A failing test fails the build with the native output and publishes no jars. A module with test sources but no XML (for example because tests were skipped) fails its report requirement. Oyzu never invents a passing report.

To run only the tests on your machine and collect the same reports into a test-only bundle, use oyzu run test and then oyzu inspect dist. That path needs Maven or Gradle and the JDK already provisioned, and it runs them offline. See Maven and Gradle.

Lint and formatting​

lint and format-check are build stages, selected by --full or a CI context. The defaults are Checkstyle 10.26.1 (unused and redundant imports, empty statements, equals and hashCode consistency) and google-java-format 1.28.0. They check .java files under the target and skip target, build, .gradle, out, dist and similar directories. format rewrites files and runs only when you ask: oyzu run format.

Run oyzu pin to record the exact quality set in oyzu.lock. Preparation installs it in the shared tool store for local tasks and full builds; isolated builds restore the same installation read-only. No separate quality-tool home or provisioning script is needed. Offline runs need those locked tools already available in the same store.

An existing lock keeps its checker versions and default rules after you update Oyzu. Use oyzu pin --refresh or a whole-project oyzu update to adopt the defaults shipped by the current CLI. Downloads are verified at installation, and installed tools are trusted on reuse.

If the project already uses Checkstyle or Spotless, replace the defaults in oyzu.toml. The native tasks must exist in your project:

[tasks.lint]
argv = ["gradle", "--no-daemon", "checkstyleMain", "checkstyleTest"]

[tasks.format-check]
argv = ["gradle", "--no-daemon", "spotlessCheck"]

Oyzu doesn't infer Maven quality-plugin bindings or Gradle quality tasks, read your own Checkstyle XML, or run Kotlin or Groovy linters. See Java quality.

Choose the JDK, Maven and Gradle​

Native files come first, then oyzu.toml. The result is always recorded in oyzu.lock.

ToolDefault requestOverride
JDKThe root Maven compiler floor or Gradle Java level, raised to 17 if lower. Maven java.version alone is a default hint; otherwise Maven uses lts[tools] java
Maven3.9[tools] maven
GradleGradle 8, or 9 when the project declares a Java level above 24[tools] gradle

The declared level is a floor. A project declaring release 21 gets JDK 21, not the newest JDK. A project declaring 8 or 11 gets JDK 17, the oldest JDK that Maven, Gradle and Oyzu's Java support run on. JDK 17 compiles the older level correctly with --release.

Maven configuration wins over its corresponding root property, then release overrides both source and target. Without release, the higher source/target floor chooses the default. Canonical same-parameter references to literal root properties work without general interpolation. Literal release configuration requires a canonical compiler-plugin 3.x declaration at version 3.6 or newer. Relevant managed/profile/execution/test/toolchain overrides stop with a precise inference limitation; discovery does not evaluate parent or module POMs. See the full selection rules.

To choose explicitly:

[tools]
java = "21"       # latest 21.x, "lts", or an exact "21.0.8"
maven = "3.9"     # or gradle = "8"

oyzu pin --dry-run previews what would be locked, and in an activated shell mvn -version runs the locked Maven. JDKs are Eclipse Temurin, checked against the SHA-256 the Adoptium API declares. Maven comes from the Apache distribution server and Gradle from services.gradle.org, each checked against its published digest. A build sees JAVA_HOME, MAVEN_HOME and GRADLE_HOME from these tools only. It never inherits a machine-wide JDK. See Java, Maven and Gradle installation.

Wrappers. With a committed mvnw or gradlew, Oyzu runs the wrapper and provisions only the JDK. The wrapper downloads its own Maven or Gradle outside Oyzu's checks, so pin distributionSha256Sum in maven-wrapper.properties or gradle-wrapper.properties. The Maven wrapper's only-script form also needs curl or wget on PATH.

Outputs​

ProjectWhat lands in dist/
Maven reactor (native build)Each module's jar under its own name, such as library-0.1.0-SNAPSHOT.jar
Gradle build (native build)Each archive Gradle's model reports, such as app.jar and support-0.1.0.jar. Same-named archives are prefixed with the project path
Isolated Maven or Gradle buildpom, jar and war (Maven) or JAR, WAR, EAR, ZIP and TAR archives (Gradle), with snapshot versions from version inference written into private copies of your build files

dist/manifest.json records every artifact with its digest, the tests and coverage, and the logs. oyzu inspect dist verifies them. A build artifact isn't a publication or release approval.

Where Java builds run​

oyzu build runs Maven and Gradle on your machine when the project fits:

  • Maven. A reactor whose jar names can be read from the POMs (literal or inherited versions, jar packaging, no finalName or classifier).
  • Gradle. Any build whose archives Gradle's model reports.

Everything else, and every Ant project, uses the isolated executor: a Linux container with captured dependencies and no network during the build. It needs Docker. Oyzu pulls the base execution image on first use. The JDK and Maven or Gradle come from oyzu.lock, and Ant and its pinned integration files are fetched and restored for you (see the Maven, Gradle and Ant references). Isolated Maven and Gradle builds on the base image are not supported yet. Request the isolated path explicitly with oyzu build --isolated, for example oyzu build --isolated --full for Gradle. The isolated worker restores the JDK locked in oyzu.lock since the image has none, and refuses a selected JDK older than 17 with TOOL_UNSUPPORTED_VERSION.

Common failures​

SymptomCauseFix
QUALITY_LOCK_REQUIREDThe project has no locked default quality setRun oyzu pin, then retry; see Java quality
Build fails with a JUnit failure and no jars in OutputsA test failed, and jars are never published from a failing buildFix the test. The Surefire output and log path are in the failure section
A module fails its report requirementTest sources exist but no JUnit XML was produced (skipped tests, disabled reporting, or a custom report directory)Let the tests run, or move reports to the default directory. Custom report directories aren't collected on the native path
Dependency or JaCoCo download failsMaven Central was throttled or unreachable. Coverage tooling is fetched by Maven or GradleRetry. --offline builds need those artifacts already in the local repository
TOOL_UNSUPPORTED_VERSIONAn isolated build selected a JDK below 17Remove the low [tools] java pin. JDK 17 compiles older --release levels
Ant build refused before any workNo Docker, and Ant has no host buildStart Docker (Oyzu pulls the execution image itself)
Gradle refuses the daemon JDK vendorgradle-daemon-jvm.properties names a vendor other than Adoptium (isolated builds)Use Temurin, or provision a matching runtime yourself

For anything else, start with the Log path in the failure section and Troubleshooting.

Limits​

  • Default Java quality tools must be locked with oyzu pin before use.
  • Custom repositories require explicit source configuration and supported credential handling. See Maven repositories and Gradle dependencies.
  • Custom JaCoCo destinations, aggregate reactor coverage and custom test report directories aren't collected.
  • Isolated Maven and Gradle builds on the base execution image are not supported yet.
  • A green build shows that the stages passed on this source. It isn't a release approval.
