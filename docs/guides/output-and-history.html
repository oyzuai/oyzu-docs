Read output, receipts and history

What each part of the build output means, how to show more or less of it, how to use it from scripts, and how to look up a build days later.

You need: a project you have built at least once.

1. Read a build top to bottom​

A build prints the same sections in the same order in a terminal and in a CI log:

SectionWhat it tells you
Title lineProject, platform, local or CI, the build context (local, pr, ci, release), and fast or full
PrepareEach preparation step with its result and time: configuration, tool versions and installs, workspaces, dependencies, output bundle. The Tools row lists each tool and why it is there
SelectionOnly when the build was narrowed (--affected or named targets): what was requested, changed, needed or left out
PlanTargets by stage, marked run, skip or -, with a note per skip reason and needs for order between targets
BuildOne row per action: elapsed time, mark, target, stage, the native command, executed or reused, and duration
Failure / WarningsOne section each, with the cause, exit code, log file and the narrowest re-run command
OutputsEach artifact with its path and size
SummaryTests run now (or reused test evidence), coverage, the result line, and Details: the manifest, event log and invocation ID

Each row starts with a mark: ✓ succeeded, ↺ reused, ! warning, ✗ failed, .. started, ⊘ blocked. Without color the marks are paired with words, so the meaning never depends on color. A reused row shows how long the original run took (was 1.3s), and reused tests are reported as Reused test evidence … not run now. The tutorial shows a full failure section.

2. Show more or less​

Flag or variableEffect
-qHide routine progress; keep results, warnings, errors and native tool output
-v / -vvDebug / trace detail, such as per-target cache details and every unaffected target
--log-level <level>Set the threshold: error, warn, info (default), debug, trace
OYZU_LOG=warn,oyzu::executor=tracePer-area levels from the environment; any command-line flag overrides it
--output interactiveUse the live dashboard; the default auto prints line by line
NO_COLOR=1Plain text. Color is also off when output is redirected

None of these change what is built, cached or checked.

3. Use results as JSON​

Every command takes --json, before or after the subcommand:

oyzu --json build
oyzu build --plan --json
oyzu --json history

Standard output then holds exactly one JSON result; diagnostics go to standard error as JSON Lines. Errors are JSON too:

$ oyzu --json build nope
{
  "code": "COMMAND_FAILED",
  "error": "unknown build target nope; available targets: api, worker",
  "evidence": {
    "manifest": ".\\dist/manifest.json",
    "note": "Verify its invocation identity; it may describe an earlier operation",
    "status": "available"
  },
  "exitCode": 1,
  "invocationId": "38300-1792552823921616500-1",
  "nextStep": "Correct the reported cause and retry the command."
}

Parse the JSON, not the human output. Each command has its own JSON shape and may gain fields, so ignore fields you don't recognize.

4. List past builds​

Each build replaces dist/ and moves the previous bundle to .oyzu/history/. oyzu history lists the kept builds, newest first:

$ oyzu history
Invocation evidence
Invocation / run             Outcome    Scope                  Started
32916-1792552866585130800-1  succeeded  2 targets · 3 actions  2026-10-21T03:21:12.476057400+00:00
16232-1792552806550250500-1  succeeded  2 targets · 9 actions  2026-10-21T03:20:12.159576900+00:00
57240-1792552779758664800-1  succeeded  2 targets · 2 actions  2026-10-21T03:19:43.009968100+00:00
…

The list shows up to twenty builds. It only reads local files; it doesn't use the network or run anything.

The summary shows at most eight decisions, failures and diagnostics, and never native log contents or environment values. The full record is in the files it lists.

6. Check a bundle​

oyzu inspect                           # this project's bundle (dist/ by default)
oyzu inspect .oyzu/history/<run-id>    # an earlier build

If your project already uses dist/ for its own output, set [build] bundleDirectory = ".oyzu/bundle" in the root oyzu.toml. oyzu inspect and oyzu history then use that folder. See bundle destination.

Verified: every recorded file matches its digest. This does not show who produced the build or that it may be released.
Use --json for the full manifest, including the plan and execution envelope.

inspect checks every recorded file against its digest, the test reports against the build's rules, and the manifest against the plan. It doesn't tell you who built the bundle or whether it may be released. uncommitted changes means the source had local edits.

What is in dist/​

PathContents
manifest.jsonWhat was built: targets, actions with results and exit codes, artifacts with digests, reuse, selection, context
plan.jsonThe plan the build followed
envelope.jsonRun details, including the start time and invocation ID
logs/events.jsonlThe event log. Other files in logs/ hold each action's native output
Per-target foldersArtifacts and reports/ (JUnit, coverage)

A failed build still writes a bundle; read manifest.json for what actually happened. Full layout: build bundles.

When it fails​

SymptomFix
INVOCATION_NOT_FOUNDThe ID isn't in dist/ or .oyzu/history/. Run oyzu history for the kept IDs. Only recent builds are kept, so a missing entry doesn't mean a build succeeded.
INVOCATION_ID_INVALIDCopy the ID exactly from the Details line or the list.
inspect reports a mismatchA file in the bundle changed after the build. Rebuild, and don't ship from that bundle.
An error names a .oyzu/bundle-… folderThe build kept its results there because it couldn't finish writing dist/. Inspect that folder, fix the disk or permission problem, then rebuild.
No color in a terminalNO_COLOR is set, or output is redirected. CLICOLOR_FORCE=1 forces color.
