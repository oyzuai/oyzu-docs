Isolated (container) builds

An isolated build runs each action in a container, from a snapshot of your source, with no network. Use it when builds must not depend on what is installed on the machine. By default, supported builders run directly on your machine (the host path), which is faster.

Note: Isolated builds are experimental and supported on Linux hosts.

You need: a Docker engine that oyzu can reach and the base execution image, which every builder shares; Oyzu pulls it by pinned digest on first use. Oyzu mounts the engine, the builder's plugin and the tools in oyzu.lock into it; pass --image <manager>=<image> to use an image of your own instead.

Host or isolated​

Host path (default)Isolated path (--isolated)
Where actions runProcesses on your machine, with the pinned toolsContainers from the execution image, one private workspace per target
SourceYour working treeA read-only snapshot of it
Network during actionsWhatever the native tool doesNone; dependencies are downloaded before the build starts
NeedsOnly the pinned toolsDocker (or the crun sandbox for Node on Linux), the execution image and the tools in oyzu.lock
PlatformsThis machine, or a cross toolchain (Rust)What the image builds, or every declared platform with --all-platforms

Go applications, Rust, Node applications and Python wheels use the host path by default; Docker images always use a container. oyzu build --plan shows where each target runs.

2. Build isolated​

oyzu build --isolated                         # this machine's platform, in containers
oyzu build --isolated --image go=<image>      # on an image of your own
oyzu build --all-platforms                    # every platform build.yaml declares, in containers

--all-platforms is strict: if any declared platform can't be built here, the build fails before anything runs. Container and host results are cached separately, so one never stands in for the other.

3. Choose the executor per platform (optional)​

In oyzu.toml you can say which executor builds each platform, per folder and per context:

[build.executors]
"linux/arm64" = "cross-toolchain"   # always cross-compiled
"darwin/arm64" = "host"             # only on a macOS arm64 runner

[context.release.build.executors]
"linux/x86_64" = "container"        # release builds use containers

A declared executor is the only one used. If it isn't available, that platform isn't built and the plan says why. See platforms and executors.

4. Runners without Docker​

On runners with no Docker engine (for example Kubernetes pods), add --no-docker or set OYZU_NO_DOCKER=1, and Oyzu never contacts Docker. If a selected target needs Docker, the build stops before running anything, with exit status 3 so the runner can requeue the job:

$ oyzu build api --isolated --no-docker
Building shop            windows/x86_64 (host) · isolated · context local · fast
✗ NEEDS_DOCKER_DAEMON: api need a Docker engine, which this executor does not provide (--no-docker); nothing was run
  Next: Select an executor with a Docker daemon for these targets.

On Linux, the isolated steps of Node targets (npm, pnpm, Yarn) can run without Docker in a rootless crun sandbox with the same restrictions: no network, a read-only image, no capabilities and a seccomp filter. The build.isolation setting chooses:

ValueMeaning
autoDocker when an engine answers, otherwise crun
dockerAlways Docker
crunAlways crun

oyzu install downloads a pinned crun, or set OYZU_CRUN to one already on the machine. If the host doesn't allow unprivileged user namespaces, the build stops with NEEDS_USER_NAMESPACES (exit 3) rather than running without the sandbox. See the daemonless sandbox.

Use a pinned tool inside the container​

Every language toolchain and stage tool an isolated build runs comes from oyzu.lock; the execution image supplies only the operating system, native libraries and a C toolchain. Set the tool under [tools], run oyzu pin, then build with oyzu build --isolated --full --frozen. A tool missing from the lock stops the build with the oyzu pin command that fixes it. See what runs in a container action.

Reuse the images from an earlier build​

oyzu build --isolated --frozen --execution-images-from <bundle> uses the exact images an earlier build used. The source, Oyzu version, tool lock and targets must match, and Oyzu makes a fresh plan under your current settings. It doesn't replay old commands, and it won't substitute the current image tag for a missing image. See execution image replay.

What isolation gives you​

  • Dependencies are downloaded before actions start, from approved sources only (acquisition transport). A missing input never triggers a download during an action.
  • Git history for version inference is fetched before the build into a private store; your checkout is never changed.
  • Isolation doesn't prove who built something or grant permission to publish.
  • Host builds keep your machine's capabilities: Cargo's offline mode, for example, doesn't block build scripts from the network.

When it fails​

SymptomFix
NEEDS_DOCKER_DAEMON (exit 3)Use a runner with Docker, or drop --isolated for builders that support the host path.
NEEDS_USER_NAMESPACES (exit 3)The crun sandbox can't run here (for example kernel.apparmor_restrict_unprivileged_userns=1). Use a host that allows unprivileged user namespaces or has Docker.
An image can't be foundCheck that Docker can reach ghcr.io and that OYZU_NO_TOOLCHAIN_PULL is unset, or build the base image locally as the execution image page shows. Oyzu never pulls an image you pass with --image; load it into Docker first.
PLATFORM_UNAVAILABLEA platform's executor isn't available here. The plan names the runner it needs.
BUILDKIT_WORKER_UNAVAILABLE / BUILDKIT_BUILDCTL_FAILEDThe image worker stopped or ran out of memory. Restart it or give it more memory, then rebuild.
