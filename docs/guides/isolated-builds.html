Isolated (container) builds

Goal: run a build's actions inside containers, from a captured copy of the source, with networking denied during execution, instead of directly on your machine.

Status: experimental, and Linux is the qualified host. The default for supported builders remains the faster host path; isolation is something you ask for.

You need: a Docker engine the oyzu process can reach, and the toolchain images for the builders you use. Oyzu does not download or build images on its own: the default images are built from the toolchain definitions in the Oyzu source (tooling/images/), or you select a provisioned image with --image.

About the output on this page

Real captures from Windows 11 with an Oyzu development build (0.1.0-local.564f462704df), color forced on and output piped to a file, in a repository with Go targets. Only the read-only preview and the no-Docker guard were run; no container build was executed for this page.

Host or isolated: what differs​

Host path (default)Isolated path (--isolated)
Where actions runHost processes, with the pinned toolsContainers from toolchain images, one private workspace per target
SourceYour working treeA captured, immutable snapshot of it
Network during actionsWhatever the native tool doesDenied; dependencies are prepared before the plan is frozen
NeedsNothing beyond the pinned toolsDocker (or the crun sandbox for Node on Linux) and toolchain images
PlatformsThe host, or a native cross toolchain (Rust)What the toolchain image builds, or every declared platform with --all-platforms

Plain oyzu build uses the host path for Go applications, Rust, Node applications and Python wheels. Some target shapes (for example Docker images) always use a captured worker, and oyzu build --plan shows the placement of each target.

2. Build isolated​

oyzu build --isolated                         # this host's platform, in containers
oyzu build --isolated --image go=<image>      # with an explicitly provisioned image
oyzu build --all-platforms                    # every platform build.yaml declares, in containers

--all-platforms is strict: a declared platform the container executor cannot build here fails the build before anything runs. The executor is part of the build's identity, so a container result never satisfies a host build of the same platform from the cache, or the reverse.

3. Pin the executor per platform (optional)​

A project can state, in oyzu.toml, which executor builds each platform, per folder and per context:

[build.executors]
"linux/arm64" = "cross-toolchain"   # always cross-compiled
"darwin/arm64" = "host"             # only on a macOS arm64 runner

[context.release.build.executors]
"linux/x86_64" = "container"        # releases build it in containers

A declared executor is the only one used for that platform. When it is unavailable here, the platform is not built and the plan says why; nothing falls back to another executor. See platforms and executors.

4. Runners without Docker​

On a pool with no Docker engine (a Kubernetes or container runner), add --no-docker or set OYZU_NO_DOCKER=1. Oyzu then never contacts Docker. If any selected target needs it, the build stops before running anything, with exit status 3 so the runner can requeue the job elsewhere:

$ oyzu build api --isolated --no-docker
Building shop            windows/x86_64 (host) · isolated · context local · fast
✗ NEEDS_DOCKER_DAEMON: api need a Docker engine, which this executor does not provide (--no-docker); nothing was run
  Next: Select an executor with a Docker daemon for these targets.

On Linux, the isolated steps of Node targets (npm, pnpm, Yarn) can run without Docker in a rootless crun sandbox with the same restrictions: no network, a read-only image root, no capabilities, a seccomp filter. The build.isolation setting chooses: auto (Docker when an engine answers, else crun), docker, or crun. oyzu install fetches a pinned crun, or OYZU_CRUN names one the executor provides. If the host does not allow unprivileged user namespaces, the build stops with NEEDS_USER_NAMESPACES (exit 3) instead of running unsandboxed. See the daemonless sandbox.

What isolation does and does not give you​

  • Execution uses the captured source, frozen plan values and prepared inputs; a missing input never triggers a download during execution.
  • Dependency downloads happen before the plan is frozen, through admitted routes only (acquisition transport).
  • It does not grant publication rights or prove who built something; oyzu inspect still only checks integrity.
  • Host-path builds inherit your machine's capabilities: Cargo's offline mode, for example, is not network denial for build scripts.

When it fails​

SymptomFix
NEEDS_DOCKER_DAEMON (exit 3)Run on a runner with Docker, or drop --isolated for builders that support the host path.
NEEDS_USER_NAMESPACES (exit 3)The crun sandbox cannot run here (for example kernel.apparmor_restrict_unprivileged_userns=1); use a host that allows unprivileged user namespaces or has Docker.
An image cannot be foundImages are never pulled or built automatically. Provision it and pass --image <manager>=<image>.
PLATFORM_UNAVAILABLEA requested or declared platform cannot be built by its executor here; the plan names the runner it needs.
BUILDKIT_WORKER_UNAVAILABLE / BUILDKIT_BUILDCTL_FAILEDThe image worker stopped or ran out of memory; restore the worker or give it more memory, then rebuild.
