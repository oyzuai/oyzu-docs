Run tasks

oyzu run runs your project's everyday commands (test, lint, format, your own scripts) with the project's pinned tools, the same way in every repository.

You need: a project Oyzu discovers. Tools a task needs are installed from oyzu.lock the first time.

The examples use a repository with two Go targets, api and worker.

1. List the tasks​

$ oyzu run list
Available tasks · 13 across 2 targets
​
Task                 Source         Command
api · go/app (7)
api:build            Inferred · go  go build ./...
api:format           Inferred · go  gofmt -w .
api:format-check     Inferred · go  gofmt -l .
api:install          Inferred · go  go mod download
api:lint             Inferred · go  go vet ./...
api:smoke            oyzu.toml      go run .
api:test             Inferred · go  go test ./...
​
worker · go/app (6)
worker:build         Inferred · go  go build ./...
worker:format        Inferred · go  gofmt -w .
worker:format-check  Inferred · go  gofmt -l .
worker:install       Inferred · go  go mod download
worker:lint          Inferred · go  go vet ./...
worker:test          Inferred · go  go test ./...
​
Run one with: oyzu run <task>   (extra arguments go after --)
Commands show argv; task dependencies and hooks may also run. Use --json for full task records.

Tasks come from two places, shown in the Source column:

  • Inferred: the builder reads native files (go.mod, Cargo.toml, package.json scripts and so on).
  • oyzu.toml: tasks you add yourself.

There is no fixed task list for every project, so start from what oyzu run list shows.

2. Run one​

In a project with one target, the bare name works: oyzu run test. With several targets, add the target name:

To capture source and run the selected task in its builder's isolated image, use oyzu run --isolated api:test. Its prerequisites and hooks run too; other build and package stages are not added. The run collects logs, isolation evidence and required reports into the usual bundle, and never falls back to running the task on the host. See isolated tasks for supported ownership, outputs and current limits.

The native tool's own output appears unchanged (here, go test -json), with a few lines from Oyzu around it. If several targets define the same task, an unqualified name is refused rather than guessed:

$ oyzu run test
  · Setup  Loading configuration and discovering tasks
✗ COMMAND_FAILED: ambiguous task test; choose api:test, worker:test
  Next: Correct the reported cause and retry the command.

To run from another folder, use -C: oyzu -C services/api run test.

3. Pass arguments to the native command​

Everything after -- goes to the task's command:

oyzu run api:test -- -run TestGreeting

4. Add your own task​

Add a table under [tasks] in oyzu.toml. The command is an argv list and never goes through a shell.

# oyzu.toml at the repository root
[tasks."api:smoke"]          # belongs to build api, runs in api/
argv = ["go", "run", "."]
$ oyzu run api:smoke
  · Setup  Loading configuration and discovering tasks
  › api:smoke  Running · native tool output follows
Hello, Oyzu!
  ✓ api:smoke  Succeeded (exit 0 after 1.16s)

A task runs with its build's tools, environment and folder. cwd changes the folder, relative to the file that declares the task. Adding a task never installs a new tool: a task that runs node needs a target whose tools include Node.

Where a task applies depends on its key and file:

KeyApplies to
[tasks."api:smoke"]Build api only
[tasks.lint-docs] in the root oyzu.tomlThe whole repository: oyzu run lint-docs
[tasks.lint-docs] in a subfolder's oyzu.tomlEvery build below that folder
[tasks.test] (a stage name)Replaces that stage in every build the file reaches. Qualify it when those builds use different builders

A misspelled build name, or a task key in a file outside its build's folder, is an error naming the file and line.

5. Hook into builds​

A task named pre_<stage> or post_<stage> runs before or after that stage in oyzu build:

[tasks."worker:pre_build"]
argv = ["go", "vet", "./..."]
$ oyzu build
…

Output shortened. Tasks and hooks can depend on other tasks with depends_on = ["schema:verify"]. A prerequisite runs once per command, even when several tasks need it.

Two things to know:

  • Hooks run on every build. A hook without declared outputs means its target can't be reused from the cache, because Oyzu can't see what the hook changed. oyzu history <id> says so: contains authored tasks or hooks without declared outputs, which are never cached by default. See Cache build results.

  • Conditions choose when a hook runs; they don't make it mandatory. when and unless limit a hook to certain contexts, platforms, profiles or artifacts:

    [tasks."cli:post_build"]
    argv   = ["{artifact.path}", "--version"]     # smoke-test each built binary
    when   = { optimized = true, platform = ["linux/x86_64"] }

    For checks that must run, use check levels instead.

6. Use tasks from scripts​

oyzu --json run list           # the task list as JSON
oyzu --json run api:test       # a structured result; the exit status is kept

When a task fails, oyzu run exits with the task's own exit code. Tasks run with oyzu run run on your machine and are never cached; use oyzu build for cached, recorded results. oyzu run <task> --remote runs a task on a platform pool (Remote builds).

When it fails​

MessageFix
ambiguous task test; choose api:test, worker:testAdd the target name to the task.
TASK_NOT_FOUND: no task "nope" … (exit 5)Check oyzu run list and the folder you're in; use oyzu -C <project> run <task>.
CONFIG_REFERENCE_UNKNOWNA task key names a build or hook target that doesn't exist. The message suggests the nearest name.
CONFIG_TASK_AMBIGUOUSAn unqualified stage replacement reaches builds with different builders. Qualify it per build.
A format task is refused in a buildTasks that change files, such as format, are for oyzu run only. Builds use the read-only format-check.
