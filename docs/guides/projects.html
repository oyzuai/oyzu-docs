Adopt Oyzu in an existing repository

Build an existing repository with Oyzu without changing how it builds today. Start with no Oyzu files, check what Oyzu detects, and add configuration only where it can't decide on its own.

You need: oyzu on your PATH (Install Oyzu), a Git checkout of your project, and network access for the first build so Oyzu can download the tools your project asks for.

The examples use a repository called shop with two Go modules, api/ and worker/.

1. See what Oyzu detects​

From the repository root, with no Oyzu files:

$ oyzu discover
2 targets · 12 tasks discovered without running project code
Project root: …\shop
​
project-api · go/app
  Chosen by          detected from project files
  Location           api
  Manager            go
  Version            0.0.0
  Part of builds     build, format-check, lint, test
  Development tasks  format, install
​
project-worker · go/app
  Chosen by          detected from project files
  Location           worker
  Manager            go
  Version            0.0.0
  Part of builds     build, format-check, lint, test
  Development tasks  format, install
​
Target names are what `oyzu build <target>` accepts.
Next steps:
  oyzu run list      every task and the command it runs
  oyzu build --plan  preview the build stages without running them
Use --json for the complete discovery record, including each task's environment and dependencies.

Oyzu reads native files only (here, each go.mod); it runs nothing. Each folder a builder recognizes becomes a target, named project at the root and project-<path> below it.

Discovery stops at the first folder a builder recognizes, so a native workspace (Cargo workspace, go.work, npm or pnpm workspace) is one target built by its own tool. Nested Git repositories and folders with their own build.yaml are skipped.

3. Preview, then build​

oyzu build --plan     # preview only: installs, downloads and runs nothing
oyzu build            # fast local build: build and package stages, plus required checks
oyzu build --full     # also runs tests, lint and format checks

4. Commit the lock, ignore the outputs​

The first build writes these into the project root:

PathWhat to doWhy
oyzu.lockCommit itIt records exact tool versions and digests, so everyone and CI get the same tools
.oyzu-tool-lock-edit.lockIgnore itA coordination file for concurrent lock writes; it holds no data
dist/Ignore itThe output bundle of the latest build
.oyzu/Ignore itLocal state: build history, compiler state, .oyzu/bin outputs
# .gitignore
dist/
.oyzu/
.oyzu-tool-lock-edit.lock

If you commit the coordination file, builds warn SOURCE_TRACKED_IGNORED. Untrack it with git rm --cached .oyzu-tool-lock-edit.lock.

5. Decide which file a setting belongs in​

Most repositories need nothing more. When you do need configuration, each setting has exactly one home:

AskFileExamples
Does your ecosystem's own file already say it?The native fileThe go line in go.mod, rust-toolchain.toml, packageManager in package.json, global.json, Gradle and Maven wrapper properties
Does it change what is built or how builds connect: which builds exist, their names, builder, platforms, dependencies, builder options?build.yaml at the rootbuilds:, uses, path, platforms, depends_on, inputs, with
Could it differ by folder, context (local, PR, CI, release) or person, or need an organization-wide limit?oyzu.toml (and oyzu.local.toml for personal values)[tools], [checks], [tasks], [build.executors], [publish]

Write each tool version once, and never in build.yaml. If rust-toolchain.toml pins Rust, don't repeat it in oyzu.toml. A native minimum (Go's go line, Cargo's rust-version) is a constraint that [tools] can satisfy with an exact version.

6. Settle what discovery cannot decide​

Add a build.yaml at the root to name builds, connect them, limit platforms, exclude folders, or make a choice discovery won't guess. With a build.yaml, only the builds it lists exist.

builds:
  api:
    uses: go/app
    path: api
  worker:
    uses: go/app
    path: worker
    depends_on: [api]     # build api first; rebuild worker when api changes

Run oyzu discover again: each build now shows Chosen by build.yaml.

Each build accepts these fields: uses, path, platforms, depends_on, inputs, materialize, bindings, fetches and with. Any other field fails with CONFIG_INVALID_VALUE naming it. The root keys are builds and exclude. The full format is in configuration: build inventory.

Good to know:

  • uses is optional when only one builder recognizes the folder: web: {path: web} is complete.

  • Renaming changes identity. New names change output paths and cache keys, so those targets rebuild once.

  • Let Oyzu write it. oyzu discover --write adds every folder exactly one builder recognizes, keeping the default names. oyzu discover --check exits 1 while a build is neither listed nor excluded; run it in CI. See builds build.yaml leaves out.

  • Ambiguous choices fail with a fix. When native files point two ways (for example both black and ruff configured in pyproject.toml), discovery stops and names the setting to add under with:

    ✗ COMMAND_FAILED: conflicting Python formatter candidates black, ruff: black via pyproject.toml tool.black; ruff via pyproject.toml tool.ruff; declare the intended one for this target in build.yaml with `with: {formatter: black}` or `with: {formatter: ruff}`

    The settings each builder accepts are listed in selecting a role in build.yaml.

7. Add oyzu.toml for behavior​

oyzu.toml files apply from the root down to each target folder, and the nearer file wins:

# oyzu.toml at the root
[tools]
go = "1.27"            # exact team version; satisfies go.mod's minimum

[checks]
lint = "advisory"      # lint failures warn instead of failing the build

[context.release.checks]
tests = "required"     # release builds always run tests

Check it after every edit:

$ oyzu config validate
Configuration
​
Capabilities:
  • config.cascade/v1
  • config.profiles/v1
  • config.removal/v1
  • config.env-path/v1
  • policy.constraints/v1
Diagnostics:
  (none)
Valid: yes

oyzu config show, get <key> and explain <key> show resolved values and where they came from. Personal values go in oyzu.local.toml, which you don't commit.

Check the result​

oyzu discover          # every target you expect, with the right builder
oyzu build --plan      # the stages and tool versions you expect
oyzu build --full      # builds, tests, lints and format-checks everything

Then commit oyzu.lock, any build.yaml and oyzu.toml, and your .gitignore changes.

When it fails​

SymptomCause and fix
A folder is missing from oyzu discoverIt's inside another target or a nested Git repository, or no builder recognizes it. Add it to build.yaml with uses and path.
A folder is missing after you added build.yamlWith a root build.yaml, only listed builds exist. Add the entry, or run oyzu discover --write.
CONFIG_INVALID_VALUE naming an unknown field or root keybuild.yaml accepts only the fields listed above, and builds must be under builds:.
CONFIG_INVALID_VALUE for a folder several builders recognizeName the builder: both: {uses: docker/image, path: both}.
conflicting … candidatesAdd the with: setting the message names.
Another tool's build.yaml (for example Dart's)Oyzu only treats a file with a builds, members or exclude root key as its own. Others are listed as skipped.
