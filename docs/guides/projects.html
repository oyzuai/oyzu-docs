Adopt Oyzu in an existing repository

Goal: build an existing repository with Oyzu without rewriting its build. You start with no Oyzu files at all, let discovery read your native manifests, and add configuration only for the decisions discovery cannot make.

You need: the oyzu executable on PATH (Install Oyzu), a Git checkout of your project, and network access for the first build so Oyzu can fetch the tools your project asks for.

About the output on this page

Every output block was captured from a real run on Windows 11 with an Oyzu development build (0.1.0-dev.g54d773e20c1e), NO_COLOR=1 and output redirected to a file. The project is a scratch Git repository with two Go modules, api/ and worker/, each a copy of examples/builds/go-app. Long paths are shortened with …. Your times, hashes and paths will differ, and a build from newer source can print extra detail.

1. Let discovery read the repository​

From the repository root, with no Oyzu files present:

oyzu discover
2 targets · 12 tasks discovered without running project code
Project root: …\shop

project-api · go/app
  Chosen by          detected from project files
  Location           api
  Manager            go
  Version            0.0.0
  Part of builds     build, format-check, lint, test
  Development tasks  format, install

project-worker · go/app
  Chosen by          detected from project files
  Location           worker
  Manager            go
  Version            0.0.0
  Part of builds     build, format-check, lint, test
  Development tasks  format, install

Target names are what `oyzu build <target>` accepts.

Discovery reads bounded metadata (here each go.mod). It never runs a tool, a script or a configuration file. Each folder a builder recognizes becomes a target: one buildable unit with one builder. Zero-config names are project for a project at the root and project-<path> below it.

Discovery stops descending at the first folder a builder recognizes, so a native workspace (a Cargo workspace, a go.work, an npm or pnpm workspace) is one target that its native tool builds as a whole. Nested Git repositories and folders with their own Oyzu build.yaml are skipped.

3. Preview, then build​

oyzu build --plan     # read-only: installs, downloads and runs nothing
oyzu build            # fast local build: build and package stages, required checks only
oyzu build --full     # also runs tests, lint and format checks

A first oyzu build resolves the tool versions your native files ask for, installs them with digest verification, and builds every target on this machine:

A plain local build is deliberately fast: it skips tests, lint and format checks unless a check is required. In CI (detected automatically) or with --full, every check that is not off runs. See Run in CI.

4. Commit the lock, ignore the outputs​

The first build writes two things into the project root:

FileWhat to do
oyzu.lockCommit it. It records the exact tool versions and digests, so every teammate and CI job gets the same toolchain.
.oyzu-tool-lock-edit.lockIgnore it. It is a coordination file for concurrent lock writers; it holds no data.
dist/Ignore it. The output bundle of the latest build.
.oyzu/Ignore it. Local state: build history, native compiler state, the .oyzu/bin outputs.
# .gitignore
dist/
.oyzu/
.oyzu-tool-lock-edit.lock

If you commit the coordination file by accident, every build warns SOURCE_TRACKED_IGNORED and --affected selection can fall back to a full build. Remove it with git rm --cached .oyzu-tool-lock-edit.lock.

5. Decide which file a setting belongs in​

Most repositories need nothing more. When you do need configuration, there are exactly three places, and each setting has one home:

QuestionFileExamples
Does your ecosystem's own file already say it?The native filego.mod go line, rust-toolchain.toml, packageManager in package.json, global.json, Gradle and Maven wrapper properties
Does it change what ships or how builds connect: which builds exist, their names, builder, platforms, dependencies between them, builder options?build.yaml (root)builds:, uses, path, platforms, depends_on, inputs, with
Could it differ by folder, by context (local, PR, CI, release) or by person, or need an organizational limit?oyzu.toml cascade (oyzu.local.toml for personal values)[tools] versions, [checks] levels, [tasks], [build.executors], [publish]

Two rules follow from this:

  • Never say a tool version twice. If rust-toolchain.toml pins Rust, do not repeat it in oyzu.toml. A native minimum (Go's go line, a Cargo rust-version) is a constraint; [tools] may choose an exact version that agrees with it.
  • Tool versions never go in build.yaml. Resolved identities live only in oyzu.lock.

6. Settle what discovery cannot decide​

Add a build.yaml at the root when you need to name builds, connect them, restrict platforms, exclude a folder, or settle a choice discovery refuses to guess. With a build.yaml, only its builds exist: discovery never adds one.

builds:
  api:
    uses: go/app
    path: api
  worker:
    uses: go/app
    path: worker
    depends_on: [api]     # build api first; worker is rebuilt when api changes
oyzu discover
2 targets · 12 tasks discovered without running project code

api · go/app
  Chosen by          build.yaml
  Location           api
  …
worker · go/app
  Chosen by          build.yaml
  Location           worker
  …

What you can write per build: uses, path, platforms, depends_on, inputs, materialize, bindings, fetches and with. Any other field fails with CONFIG_INVALID_VALUE naming it. The root keys are builds and exclude (members is reserved and refused for now). The full contract is in configuration: build inventory.

Useful details:

  • uses is optional when exactly one builder recognizes the folder: web: {path: web} is a complete entry. Writing uses out makes the choice visible in review.

  • Renaming changes identity. Hand-written names (api) replace the zero-config ones (project-api), so output paths and cache keys change and the next build re-executes those targets once.

  • Generate it instead of writing it. A CLI built from current source can run oyzu discover --write, which declares every folder exactly one builder recognizes, with uses written out (starting from no build.yaml, it keeps the zero-config names, so nothing is renamed), and oyzu discover --check, which exits 1 while a folder holds a build that build.yaml neither declares nor excludes. Put the check in CI so a new folder cannot silently go unbuilt. See builds build.yaml leaves out.

  • Ambiguous roles fail loudly. When native evidence points two ways (for example black and ruff both configured in pyproject.toml), discovery stops and names the selector to add under with:

    conflicting Python formatter candidates black, ruff: black via pyproject.toml tool.black; ruff via pyproject.toml tool.ruff; declare the intended one for this target in build.yaml with `with: {formatter: black}` or `with: {formatter: ruff}`

    The available selectors per builder are listed in selecting a role in build.yaml.

7. Add oyzu.toml for behavior​

oyzu.toml files cascade from the repository root down to each target folder; a nearer file wins. Put team-wide values at the root and per-folder exceptions next to the code they affect. For example:

# oyzu.toml at the root
[tools]
go = "1.27"            # exact team toolchain; agrees with go.mod's minimum

[checks]
lint = "advisory"      # lint failures warn instead of failing the build

[context.release.checks]
tests = "required"     # release builds always run tests

Validate after every edit:

oyzu config validate
Configuration

Capabilities:
  • config.cascade/v1
  • config.profiles/v1
  • config.removal/v1
  • config.env-path/v1
  • policy.constraints/v1
Diagnostics:
  (none)
Valid: yes

oyzu config show, oyzu config get <key> and oyzu config explain <key> show the resolved values and where each came from. Personal values (a local tool override, extra verbosity) go in oyzu.local.toml, which you do not commit.

Verify the adoption​

Run these three; all should succeed with no surprises:

oyzu discover          # every target you expect, with the right builder
oyzu build --plan      # the stages and tool requirements you expect
oyzu build --full      # builds, tests, lints and format-checks everything

Then commit oyzu.lock, any build.yaml and oyzu.toml, and the .gitignore entries.

When it fails​

SymptomCause and fix
A folder is missing from oyzu discoverIt is below another recognized target, inside a nested Git repository, or no builder recognizes it. Declare it in build.yaml with uses and path.
A folder with a build.yaml is missingWith a root build.yaml, only declared builds exist. Add the entry (or run oyzu discover --write).
CONFIG_INVALID_VALUE naming an unknown field or root keybuild.yaml accepts only the fields listed above. Builds must be indented under builds:; the older flat shape is refused.
CONFIG_INVALID_VALUE for a folder several builders recognizeWrite the builder you want: both: {uses: docker/image, path: both}.
conflicting … candidatesAdd the named with: selector for that build.
Another tool's build.yaml (for example Dart's)Oyzu only treats a file with a builds, members or exclude root as its own; others are listed as skipped.
