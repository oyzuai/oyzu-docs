Remote builds (optional)

--remote runs oyzu build or oyzu run <task> on a platform or standalone pool instead of your machine, against the exact commit you pushed, and streams the output back to your terminal. A standalone pool needs access from its operator; platform pools use a platform account.

Note: Remote builds are experimental. Pools run on Linux.

You need:

  • A Git checkout whose HEAD is pushed to a github.com repository allowed by the pool (or linked to a project in your platform account), and git on PATH. The Actions workload flow below can run without a checkout.
  • The platform URL and your account name in your user (or machine, or administrative) configuration. Project files can't set them, so a checkout can't redirect your credentials.
  • A platform credential, or the standalone pool's network or Actions workload provider described below.

2. Configure access​

For a platform pool:

oyzu config set --global platform.url https://platform.example.com
oyzu config set --global platform.account payments
export OYZU_PLATFORM_TOKEN=…     # or: oyzu auth login

For a standalone pool, ask its operator for the URL, account name and network access. Configure once, then use the same build and task commands:

oyzu config set --global platform.url https://pool.example.com
oyzu config set --global platform.account example
oyzu config set --global platform.authentication.provider network

network sends no authorization header. The pool identifies you through its trusted network. Both kinds of pool require HTTPS except on loopback.

In CI, set OYZU_PLATFORM_URL, OYZU_PLATFORM_ACCOUNT and OYZU_PLATFORM_TOKEN in the environment instead. Without configuration, --remote stops before sending anything:

$ oyzu build --remote
Building shop remotely
Platform pool · pushed HEAD · full checks, isolated · Ctrl-C cancels the run
✗ REMOTE_NOT_CONFIGURED: set platform.url to the platform URL, for example `oyzu config set --global platform.url https://platform.example.com`
  Next: Correct the reported cause and retry the command.

3. Run it​

CommandWhat runs remotely
oyzu build --remoteEvery target
oyzu build cli web --remoteTargets cli and web and what they depend on
oyzu build --affected origin/main --remoteTargets affected since the merge base of origin/main and HEAD
oyzu run policy-check --remoteOne task (target:task also works)
… --remote --download outAny of the above, then downloads every output into out/

Push first: the pool checks out the pushed commit, so uncommitted changes are not included (you get a warning). Output streams back in the same layout as a local build, with each line labelled by target or task. It ends with a receipt: result, run ID, commit, project, Oyzu version and the outputs produced. Nothing is written locally unless you pass --download.

To build local changes on a standalone pool without pushing, use oyzu build --remote --worktree or oyzu run app:test --remote --worktree. The CLI uploads source from the Git repository root before creating the run, including every tracked file (even ignored files) and nonignored untracked files. It refuses links outside the tree before upload. Transporting a link does not extend the build engine's existing source-link support. Snapshot runs cannot publish or write shared caches. Both remote modes run at the repository root; select subprojects by target or qualified task name. See snapshot limits and source selection.

The first Ctrl-C asks the platform to cancel and keeps following the run until the pool confirms. A second Ctrl-C exits immediately. Closing the terminal doesn't cancel the run.

From GitHub Actions​

Give the job permission to request OIDC tokens and network access to the pool:

permissions:
  id-token: write
  contents: read
steps:
  - uses: oyzuai/setup-oyzu@v1
  - run: oyzu build --remote
    env:
      OYZU_PLATFORM_URL: https://pool.example.com
      OYZU_PLATFORM_ACCOUNT: example
      OYZU_PLATFORM_AUTH_PROVIDER: workload

No checkout step is needed for this flow. Without a checkout, the client takes the exact source from GITHUB_REPOSITORY, GITHUB_SHA and GITHUB_REF. With a checkout, the ordinary pushed-HEAD checks apply; --affected needs a checkout. The workload provider requests a fresh token for each API attempt, using the pool URL without trailing slashes as audience. It never stores the token and fails outside Actions. See source validation and credentials.

Exit status​

Remote resultExit
Succeeded0
Oyzu exited non-zero on the poolThat exit code
Failed before Oyzu ran, skipped, cancelled, timed out or unknown1
Refused before or while creating the run1
Interrupted with Ctrl-C130

If the client loses track of a run after creating it, the result is unknown, not failed: it exits 1 with the last state it saw and never starts local work instead. Check the run with the link it printed before starting another.

When it fails​

A refused remote run never falls back to a local build.

CodeFix
REMOTE_NOT_CONFIGUREDSet platform.url and platform.account in user configuration.
REMOTE_UNAUTHENTICATEDCheck the standalone pool's caller access rules, or use a current platform credential. Unattended runs never use a person's session.
AUTH_PROVIDER_UNAVAILABLEWorkload needs GitHub Actions with id-token: write and its token endpoint variables.
AUTH_WORKLOAD_*Check the job's OIDC permission and endpoint connectivity. No other credential is tried.
REMOTE_ACTIONS_SOURCE_INVALIDWithout a checkout, provide an exact owner/repository, full lowercase 40-character commit and full Git ref.
REMOTE_COMMIT_NOT_PUSHEDHEAD isn't on any branch of the remote. Push it.
REMOTE_COMMIT_NOT_FOUNDThe platform can't see the commit yet. Push and retry.
REMOTE_REPOSITORY_NOT_LINKEDLink the repository to a project in your platform account.
REMOTE_REPOSITORY_UNSUPPORTEDOnly github.com repositories are supported.
REMOTE_NOT_A_CHECKOUTRun from a Git checkout, or use the checkout-less Actions workload flow.

Limits​

  • You can't pass task arguments after -- to a remote run.
  • Standalone pools accept --worktree only when the server supports snapshots. Actions workload callers must use their signed commit. Output downloads remain unavailable; omit --download.
  • There is no --detach, and you can't list runs or re-attach to one from the CLI.
  • Retries honor Retry-After and reuse the same request key, so a retry never starts a second run.
  • The client works through HTTPS_PROXY and needs only outbound access.
