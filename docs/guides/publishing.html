Publish artifacts

oyzu publish takes the artifacts a build already produced and uploads exactly those bytes to an OCI registry or an existing GitHub release, with their provenance attached. It reads every upload back before reporting success. You don't need an account.

Oyzu's own Preview releases are binary-only, from oyzuai/oyzu-releases: the release audit checks the binaries, notices and source before publishing, and recipients use oyzu --licenses offline or download the platform's oyzu-notices-<os>-<arch>.txt from the same release.

Note: Publishing is experimental. OCI publishing is supported on Linux and GitHub release publishing on Windows x64; authenticated registries and GitHub Enterprise are not supported yet. npm, PyPI, OCI image archives and mutable OCI tags are not available, and kind = "npm" or "pypi" fails configuration validation.

You need:

  • A successful build bundle (dist/manifest.json).
  • A signed provenance bundle for each artifact, produced by your own signing step before you publish: a Sigstore v0.3 bundle with one DSSE envelope carrying in-toto SLSA build provenance, signed with an Ed25519 key you control. Oyzu checks it; it doesn't create it.
  • An Ed25519 publication signing seed in an environment variable. Oyzu signs a record of what it is about to publish with it.
  • Destination credentials in environment variables.
  • Network access. Publishing doesn't work offline.

1. Configure destinations in the root oyzu.toml​

[publish] is only accepted in the project root's oyzu.toml or oyzu.local.toml; anywhere else it fails with CONFIG_SCOPE. Never write secrets here, only the names of the environment variables that hold them.

[publish]
default = "registry"

[publish.destinations.registry]
kind = "oci"
registry = "https://registry.example.com"
repository = "team/artifacts"
artifacts = ["api"]                 # output IDs; optional when the bundle has one artifact
usernameEnv = "REGISTRY_USERNAME"
passwordEnv = "REGISTRY_PASSWORD"

[publish.destinations.github]
kind = "github-release"
apiUrl = "https://api.github.com"
repository = "your-org/your-repo"
tokenEnv = "GITHUB_RELEASE_TOKEN"
artifacts = ["api", "worker"]
[publish.destinations.github.evidence]
mode = "destination"

[publish.sets]
release = ["registry", "github"]

[publish.requirements.provenance]
bundlePath = "evidence/build.sigstore.json"
publicKey = "<base64 raw 32-byte Ed25519 builder public key>"
builderId = "https://ci.example.com/builders/release"

[publish.requirements.signing]
keyEnv = "PUBLICATION_SIGNING_SEED"
publicKey = "<base64 raw 32-byte Ed25519 publication public key>"

Replace the values in angle brackets and the example hosts with your own keys and endpoints.

Choosing artifacts. Each artifacts entry is an output ID: the target name for its main output (api), target/name for another output (app/archive), and optionally a platform (cli/bin-oyzu@linux/x86_64). oyzu config validate, oyzu build --plan and every build reject unknown names, so a typo shows up long before release day.

Different provenance per artifact. Use [publish.requirements.provenance.byArtifact."<output-id>"] entries instead of the single form. {artifact.platform} in bundlePath picks one bundle per platform. See publishing finalized artifacts.

Check the configuration:

oyzu config validate

2. Build, then publish​

oyzu build --full
oyzu inspect
oyzu publish --destination registry

Without --destination, Oyzu uses publish.default. Repeat --destination, or name a set (--destination release), to publish to several places.

Before uploading, Oyzu checks the selection, verifies each provenance bundle against your public key and builder ID, and signs the publication record. It reports success only after reading every object back by digest.

With no configuration, you get:

$ oyzu publish
Publishing the build
Verifying publication requirements and destination results
✗ PUBLISH_NOT_CONFIGURED: configure publish.destinations in oyzu.toml
  Next: Correct the reported cause and retry the command.

OCI registries​

The published reference is registry/repository@sha256:<manifest-digest>; tags are not used. The OCI artifact holds your file plus the provenance and publication record as separate layers. Publishing identical content again reports already-present. HTTPS is required (plain HTTP only for registries on localhost), and the registry's bearer-token challenge is supported.

GitHub releases​

Oyzu attaches assets to a release that already exists, at an existing tag. It never creates tags or releases, changes release details or deletes assets. The token needs Contents read/write on the repository. The release is chosen like this:

  1. --tag <tag>, if given (for example in a manually started release job).
  2. Otherwise, the exact version tag the build recorded for the built commit (v1.4.0, or api/v1.4.2 for one package in a workspace).

If the build recorded no tag, publishing stops with PUBLISH_TAG_UNKNOWN before contacting the network. Tag the commit, rebuild and publish again, or pass --tag. Asset names include the platform (oyzu built for linux/x86_64 becomes oyzu-linux-x86_64), so one release can hold every platform.

3. Publish several platforms as one release​

Build each platform in its own job, collect the bundles, and publish once:

oyzu publish --destination github \
  --manifest bundles/linux-x86_64/dist/manifest.json \
  --manifest bundles/darwin-arm64/dist/manifest.json

For targets that declare platforms in build.yaml, publishing in the release context without every declared platform fails with PUBLISH_PLATFORMS_INCOMPLETE, naming each missing one. To publish anyway, name each missing platform with a reason; the reason is recorded in the signed publication record:

oyzu publish --destination github --allow-incomplete windows/arm64="runner not available"

4. Read the receipt​

The output shows each destination's result with the reference and digest read back. oyzu --json publish … returns operationId, status, planDigest, artifacts and destinations; each destination is published, already-present, failed or unfinished.

ExitMeaning
0Every selected destination was published, or already had the content
1Refused before publishing: missing provenance, wrong subject, invalid selection, or a conflicting existing asset
2At least one destination failed or is unfinished. Destinations that succeeded stay published. Fix the cause and run the same command again; finished destinations are matched by digest

When it fails​

CodeFix
PUBLISH_NOT_CONFIGUREDAdd [publish.destinations.*] to the root oyzu.toml.
CONFIG_SCOPE[publish] is in a subfolder's oyzu.toml. Move it to the root.
PUBLISH_ARTIFACT_SELECTION_INVALIDAn output ID is unknown or ambiguous, or the bundle has several artifacts and none is selected. Use the IDs from the build's Outputs.
PUBLISH_EVIDENCE_MISSINGA selected artifact (or platform) has no provenance bundle. Produce it, or add a byArtifact entry.
PUBLISH_TAG_UNKNOWN, PUBLISH_TAG_CONFLICT, PUBLISH_TAG_COMMIT_MISMATCHOyzu can't tell which release tag to use. Tag the built commit and rebuild, or pass --tag.
PUBLISH_PLATFORMS_INCOMPLETEA declared platform has no artifact. Add its bundle with another --manifest, or use --allow-incomplete <platform>=<reason>.
PUBLISH_BINDING_UNPUSHEDA Helm chart that refers to an image is being published without that image. Add the image's destination to the same publish.
PUBLISH_VERIFICATION_MISSINGPolicy requires a verification run the bundles don't include. Pass that bundle with --manifest.
