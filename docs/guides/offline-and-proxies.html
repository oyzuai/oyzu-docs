Work offline or behind a proxy

Goal: build on a plane, in an air-gapped lab or a locked-down CI network, and route every download through your company's proxy, trusting its TLS-inspection certificate.

You need: the oyzu executable and network access once (directly or through the proxy) to fetch tools and dependencies the first time.

About the output on this page

Real captures from Windows 11 with an Oyzu development build (0.1.0-local.564f462704df), color forced on and output piped to a file, in a repository with two Go targets. A real proxy was not available for these captures; the proxy errors come from deliberately invalid settings, and working proxy behavior is from the acquisition transport reference, where it is verified on Linux.

Part 1: work offline​

What Oyzu needs from the network is tool metadata and archives (for pin, install and a build's preflight) and your project's dependencies (prepared by the native manager or Oyzu's broker before a build). Once those are on disk, you can forbid the network.

1. Prime while you are online​

oyzu pin               # resolve and write oyzu.lock (skip if it is committed)
oyzu install --frozen  # install declared tools from the lock
oyzu build --full      # installs native-file tools and prepares dependencies, test tools included

Run the same selection you will need offline: --full also prepares the tools for tests, lint and format checks, which a fast build skips.

--offline requires cached tools and dependencies and never acquires anything. It never resolves new tool versions or writes the lock either: if an input is missing, the build stops in preparation with a remedy (run an online build, or fix the manifest or lock) instead of reaching for the network.

The other commands have the same switch:

CommandOffline behavior
oyzu install --frozen --offlineRestores the locked selection from installed tools or cached archives; fails if an archive is missing
oyzu pin --offlineResolves only from existing locks and cached metadata
oyzu exec --offline -- <cmd>Uses installed tools and cached archives
oyzu tools versions <tool>Needs the network unless a configured tool index has a cached copy

One limit to know: for native Rust builds, cargo uses its own cache, and --offline skips the fetch step (missing crates are reported with guidance) but is not network denial for arbitrary build scripts.

Part 2: work behind a corporate proxy​

Oyzu's downloader (tool metadata and archives, helper archives, captured-build dependency fetches, the remote cache and remote runs) reads the standard proxy environment of the process that runs oyzu:

VariableEffect
HTTPS_PROXY / https_proxyProxy for HTTPS (CONNECT tunnel)
HTTP_PROXY / http_proxyProxy for HTTP
ALL_PROXY / all_proxyFallback when the scheme-specific variable is unset
NO_PROXY / no_proxyHosts, domains and CIDR ranges that bypass the proxy
SSL_CERT_FILEA PEM bundle of additional trust anchors, for a TLS-inspecting proxy; the built-in public roots stay trusted

1. Set the environment​

export HTTPS_PROXY=http://proxy.corp.example:3128
export NO_PROXY=.corp.example,10.0.0.0/8
export SSL_CERT_FILE=/etc/ssl/corp/inspection-ca.pem   # only if the proxy inspects TLS

On Windows PowerShell, use $env:HTTPS_PROXY = '…'. Credentials may be embedded in the proxy URL (http://user:password@proxy:3128); they are never printed.

2. Check that it works​

Run something that needs the network and nothing else:

oyzu tools versions go
oyzu install --dry-run go@1.27

Mistakes fail immediately and never fall back to a direct connection:

3. Know the boundaries​

  • Loopback always bypasses the proxy (localhost, 127.0.0.0/8, ::1), so local endpoints and their credentials never go through it.
  • A proxy adds a path, not authority. Oyzu still only contacts the sources it admits for each tool or dependency.
  • A TLS-inspecting proxy can see request headers, including any route authorization. Only configure a proxy you trust with those credentials.
  • Native tools keep their own settings. Cargo, npm, Maven and others that fetch for themselves on the native host path use their own proxy and certificate configuration; set those as you normally would.
  • Not supported: proxy authentication other than credentials in the URL, PAC files, the operating system's proxy store, and per-route proxies.

Part 3: an internal mirror for Node (administrators)​

An administrator can route Node tool acquisition through an internal mirror with the administrative registries.routes setting and a host-owned connector binding file passed explicitly with oyzu install --connector-bindings <file>. The mirror must serve the Node distribution layout; credentials come from an environment variable named in the binding. There is no fallback to the public source when the binding is missing or a request is denied. This is verified on Linux only; see tool proxy acquisition.

Verify​

  • oyzu build --offline succeeds with networking disabled after priming.
  • With the proxy variables set, oyzu tools versions go lists versions; with HTTPS_PROXY unset on a network that requires the proxy, it fails instead of succeeding directly.

When it fails​

MessageCause and fix
A preparation failure under --offline naming a tool or dependencyIt was never downloaded. Go online once and run the same build (with --full if you need checks).
TOOL_LOCK_MISSINGNo lock to restore from. Run oyzu pin or oyzu install online.
TOOL_OFFLINEtools versions needs the network for this tool.
PROXY_INVALIDFix the proxy URL (scheme, host, numeric port).
TRUST_BUNDLE_UNREADABLE / TRUST_BUNDLE_INVALIDPoint SSL_CERT_FILE at a readable, non-empty PEM file.
SOURCE_UNAVAILABLEThe transport failed after retries (408, 429, 502, 503, 504 and connection errors are retried twice). Check the proxy and connectivity.
SOURCE_TIMEOUTA 45-second fetch deadline expired.
SOURCE_DENIED (403)No admitted route allows that request or redirect. This is a source configuration issue, not a proxy setting.

Windows and macOS proxy behavior and real HTTP_PROXY/ALL_PROXY use are not yet qualified. Reference: acquisition transport, tool management, tool commands.
