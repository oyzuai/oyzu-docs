Cache build results

Oyzu skips work that hasn't changed by reusing earlier results from its action cache. You can ask why any stage ran, and share results between machines through an OCI registry.

You need: nothing for the local cache; it is on by default. A remote cache needs an OCI registry you control.

How reuse works​

Each stage gets a key from everything it depends on: builder and version, platform, tool versions, dependencies, the stage's command and settings, the target's source files, and earlier outputs it uses. When a key matches a stored result, Oyzu restores the outputs, checks their digests and skips the command.

Reused work is always labelled. A restored test report shows as reused test evidence, not run now.

3. Inspect, skip or clear the cache​

$ oyzu cache status
Action cache
​
  Location   C:\Users\you\AppData\Local\Oyzu\cache\actions (default per-user location)
  Entries    552 results · 2841 blobs
  Size       9.9 GiB of 10.0 GiB retention budget
  Docker     5 images · 2.6 GiB of 20.0 GiB image budget (cache.dockerMaxMiB)
  Local use  enabled
​
Reuse is local to this user and machine. Ephemeral CI runners start empty; shared caching is a later milestone.
Use `oyzu cache clear` to empty it, or `oyzu build --no-cache` to bypass it once.
ToRun or set
Run everything once, without reading or writing the cacheoyzu build --no-cache
Turn the local cache offcache.local = false
Empty the cache (bundles in dist/ are untouched)oyzu cache clear
Check that confined stages declare every file they readoyzu build --verify-contract (reuses and stores nothing)

The cache is per user and shared across projects:

PlatformLocation
Windows%LocalAppData%\Oyzu\cache\actions
macOS~/Library/Caches/Oyzu/actions
Linux$XDG_CACHE_HOME/oyzu/actions, else ~/.cache/oyzu/actions

Set cache.dir in user or system configuration to move it. Above 10 GiB, the least recently used results are removed at the end of a build. oyzu cache clear fails while a build is using the cache; don't delete store.lock, just retry.

What is never reused​

Some work always runs, and the output says why:

  • Targets with your own tasks or stage replacements, unless they set cache = true and declare outputs.
  • Targets with hooks that declare no outputs. oyzu history reports contains authored tasks or hooks without declared outputs, which are never cached by default.
  • Targets that use secret environment values.
  • Tasks run directly with oyzu run.
  • Failed, blocked or cancelled targets. Their results are never stored.

Optimized and development builds never share results, and upgrading Oyzu starts the cache fresh. A damaged entry is set aside and the stage runs. An unusable cache location never fails a build.

4. Share results through a remote OCI cache (experimental)​

Note: The remote cache is experimental and supported on Linux. It has been tested with zot, CNCF Distribution behind a token service, and a Harbor proxy-cache project.

A remote cache lets one machine reuse results another pushed to an OCI registry repository. Entries are checked against their digests before use. cache.remote and cache.ciRemote are refused in project files, so a checkout can't redirect your cache. Set them in user configuration or the environment:

export OYZU_CACHE_REMOTE=oci://registry.example.com/team/oyzu-cache   # read on a local miss
# user configuration (oyzu config set --global …)
[cache]
remote = "oci://registry.example.com/team/oyzu-cache"
write = true      # also push results this machine builds (off by default)
SettingDefaultMeaning
cache.remote / OYZU_CACHE_REMOTEunsetRepository to read from after a local miss, and to write to when cache.write is on
cache.ciRemote / OYZU_CACHE_CI_REMOTEunsetA repository only CI writes to (see below)
cache.writefalsePush results to the remote
cache.immutableTagsfalseSet only for a registry that refuses to replace tags
OYZU_CACHE_TOKENunsetRegistry token. Only from the environment, never a setting

A localhost registry uses HTTP; everything else uses HTTPS with your proxy and CA settings.

A CI-only repository that developers read​

# in CI
export OYZU_CACHE_CI_REMOTE=oci://registry.example.com/team/oyzu-cache/ci
BuildReads (after a local miss)Writes (with cache.write)
In CI (a CI provider is detected)cache.ciRemote onlycache.ciRemote
Anywhere elsecache.ciRemote, then cache.remotecache.remote only

The registry must refuse writes without the CI credential; that is what makes the CI repository trustworthy. Oyzu doesn't sign cache entries.

Remote problems never fail a build:

  • A 404 is a cache miss.
  • Repeated 5xx errors or timeouts turn the remote off for the rest of the build.
  • A 401 or 403 does the same after one token renewal.

The summary line adds remote counts, for example remote 7 reused · 0 pushed. Entries larger than 256 MiB are not pushed. Details: remote OCI cache.

When it fails​

SymptomCause and fix
Everything always runsRun oyzu build --explain. Common causes: a hook without outputs, a changed oyzu.toml (configuration is part of every key), a new Oyzu version, or --no-cache.
One target never reusesoyzu history <id> gives the reason, for example hooks or secret environment values.
cache clear says the cache is busyA build is running. Retry after it finishes.
The remote never hitsSet cache.remote in user configuration or OYZU_CACHE_REMOTE; project files are refused. In CI only cache.ciRemote is read.
Remote pushes are refusedThe token is read-only or missing. The build still succeeds and records why nothing was pushed.
