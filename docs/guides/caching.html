Cache build results

Goal: stop rebuilding what has not changed, understand every reuse decision, and (optionally) share results between machines and CI through an OCI registry.

You need: nothing for the local cache; it is on by default and has no configuration. A remote cache needs an OCI registry you control.

About the output on this page

Captured on Windows 11 with an Oyzu development build (0.1.0-dev.g54d773e20c1e), NO_COLOR=1, redirected, in a repository with two native Go targets, api and worker. Paths are shortened with …. The remote cache was not exercised for this page; its behavior is taken from the action cache reference, where it is verified on Linux.

How reuse works​

Every stage of a build has a key derived from what it depends on: the builder and its version, the platform, the toolchain identity, prepared dependencies, the stage's command and configuration, the source files in the target's scope, and the outputs of earlier stages it consumes. You never write keys or cache paths. When a key matches a stored result, Oyzu restores the outputs byte for byte (each re-verified against its digest) instead of running the command.

Reused work is always labelled as such. A restored test report counts as reused test evidence, not run now, and keeps the identity of the run that really executed it.

Edit a file in worker/ and build with --explain:

oyzu build --explain

  api:build — Reused
    Recorded selection: api (selected)

    …
  worker:build — Executed

Each line names the first key component that changed since the last build of that stage. To ask about one target without building:

oyzu cache explain worker
Cache key explanation  worker

  worker (whole target)
    Key        483b478bb5b7 · since run 8768-1792534734048601600 · last seen run 8768-1792534734048601600 (2026-10-20T22:18:54Z)
    Result     stored · the next build with these inputs reuses it
    Changed    since run 60156-1792534723340143900: source files in scope changed (also: action definition: worker:build argv, worker:build extensions)

Keys come from the toolchain, dependencies, stage definition, source in scope and consumed outputs.

The same decisions stay in the build record: oyzu history <invocation-id> lists up to eight of them for any retained build.

3. Inspect, bypass or clear the cache​

oyzu cache status
Action cache

  Location   C:\Users\<you>\AppData\Local\Oyzu\cache\actions (default per-user location)
  Entries    541 results · 2822 blobs
  Size       9.9 GiB of 10.0 GiB retention budget
  Docker     5 images · 2.6 GiB of 20.0 GiB image budget (cache.dockerMaxMiB)
  Local use  enabled

Reuse is local to this user and machine. Ephemeral CI runners start empty; shared caching is a later milestone.
Use `oyzu cache clear` to empty it, or `oyzu build --no-cache` to bypass it once.
NeedCommand
Run everything once, read and write nothingoyzu build --no-cache
Turn the local cache off by configurationcache.local = false
Empty the store (build bundles in dist/ are untouched)oyzu cache clear
Check that confined stages declare everything they readoyzu build --verify-contract (reuses and stores nothing)

The store is per user and shared across projects: %LocalAppData%\Oyzu\cache\actions on Windows, ~/Library/Caches/Oyzu/actions on macOS, $XDG_CACHE_HOME/oyzu/actions (else ~/.cache/oyzu/actions) on Linux. cache.dir moves it, from user or system configuration only. At the end of a build, a store above 10 GiB evicts least-recently-used results.

oyzu cache clear fails with a retry message while a build is using the cache. Never delete store.lock to get around that; the operating system releases it when the build exits.

What is not reused​

Some work always runs, and the output says why:

  • targets with authored tasks or stage replacements that do not opt in (cache = true with declared outputs);
  • targets with hooks that declare no outputs; on the native host path, restoring the target whole would skip its hooks, so it runs instead. oyzu history reports contains authored tasks or hooks without declared outputs, which are never cached by default;
  • targets using secret environment values;
  • direct oyzu run task executions;
  • failed, blocked or cancelled targets (never stored).

Optimized and development builds never restore each other's results, and upgrading Oyzu invalidates existing entries (the builder version is part of every key).

A damaged or mismatched entry is quarantined and the stage simply runs. An unusable cache location never fails a build; it just stores nothing.

4. Share results through a remote OCI cache (experimental)​

A remote cache lets one machine or CI job reuse results another one pushed. It is an OCI registry repository; entries are verified by digest before use.

Where to configure it matters: cache.remote and cache.ciRemote are refused in project files, so a checkout cannot redirect your machine's cache. Set them in your user configuration or through the environment:

export OYZU_CACHE_REMOTE=oci://registry.example.com/team/oyzu-cache   # read on a local miss
# user configuration (oyzu config set --global …)
[cache]
remote = "oci://registry.example.com/team/oyzu-cache"
write = true      # also push what this machine builds (off by default)

Reading is on as soon as cache.remote is set; writing stays off until cache.write = true. Neither changes a key, so readers and writers share entries. If the registry requires sign-in, provide a token through OYZU_CACHE_TOKEN (never a setting). A loopback registry is reached over HTTP, everything else over HTTPS with the proxy and CA settings.

A CI-only repository that developers read​

# in CI
export OYZU_CACHE_CI_REMOTE=oci://registry.example.com/team/oyzu-cache/ci
BuildReads (after a local miss)Writes (with cache.write)
CI (a CI provider is detected)cache.ciRemote onlycache.ciRemote
Anywhere elsecache.ciRemote, then cache.remotecache.remote only

What makes the CI repository trustworthy is the registry: it must refuse writes without the CI credential. Oyzu does not sign entries, so a remote hit says where a result was read, not who produced it. Set cache.immutableTags = true only for a registry that refuses to replace tags.

Remote failures never fail a build: a 404 is a miss, repeated 5xx or timeouts turn the remote off for the rest of that build, and a 401 or 403 does the same after one token renewal. The summary line adds the remote counts, for example remote 7 reused · 0 pushed.

The remote cache is verified on Linux against zot, CNCF Distribution behind a token service and a Harbor proxy-cache project. Other registries, Windows and macOS are not yet qualified, and entries above 256 MiB are not pushed. Details: remote OCI cache.

Verify​

  • An unchanged repeat build reports every stage as reused.
  • oyzu build --explain after an edit names that edit as the first changed component.
  • With a remote configured, a second clean machine reports reused with the remote counts on the summary line.

When it fails​

SymptomCause and fix
Everything always runsCheck oyzu build --explain. Common causes: a hook without outputs, a changed oyzu.toml (the configuration digest is part of every key), a new Oyzu build, or --no-cache.
One target never reusesoyzu history <id> shows its reason, for example hooks or secret environment values.
cache clear reports the store busyA build is running. Retry after it finishes.
Remote never hitsConfirm cache.remote is set in user configuration or OYZU_CACHE_REMOTE (project files are refused); in CI only cache.ciRemote is read.
Remote push refusedThe token is read-only or missing; the build still succeeds and records why nothing was pushed.
