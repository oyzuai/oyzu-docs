Run in CI

Run the same oyzu build in CI that you run locally. CI builds run every check with the tools in oyzu.lock and leave a bundle you can keep as a job artifact. No account or CI plugin is needed.

You need: a repository that already builds locally with Oyzu (Adopt Oyzu), with oyzu.lock committed.

What changes automatically in CI​

Oyzu detects the CI provider from its standard environment variables (GITHUB_ACTIONS, GITLAB_CI, TF_BUILD, JENKINS_URL, BUILDKITE, CIRCLECI and about twenty more; any enabled CI variable also counts). That sets the build context:

ContextWhenChecks that run
localNo CI detectedOnly checks set to required (a fast build)
ciA CI provider is detectedEvery check that isn't off: tests, lint, format check
prA pull or merge request (on GitHub: GITHUB_BASE_REF is set)Every check that isn't off
releaseA tag build (on GitHub: GITHUB_REF_TYPE=tag)Every check that isn't off, plus your [context.release] settings

So CI needs no extra flags. Here is a build with GITHUB_ACTIONS=true in a repository with two Go targets:

To set the context yourself, pass --context ci or set OYZU_CONTEXT=release (for a manual release job with no tag). Under a detected CI provider you can raise the context but not lower it.

1. Put oyzu on the runner​

Use the install script in the job, or preinstall oyzu and oyzu-shim in your runner image. Pin a release with OYZU_VERSION so every job uses the same Oyzu. While the release repository is private, the script needs a GitHub token that can read it in GH_TOKEN.

2. A complete GitHub Actions workflow​

Save this as .github/workflows/build.yml. It expects a repository variable OYZU_VERSION (an Oyzu release tag) and a secret OYZU_RELEASES_TOKEN (a token that can read Oyzu releases).

name: build

on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read

jobs:
  build:
    runs-on: ubuntu-24.04
    timeout-minutes: 60
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0          # --affected needs the base commit locally

      - name: Install oyzu
        env:
          OYZU_VERSION: ${{ vars.OYZU_VERSION }}
          GH_TOKEN: ${{ secrets.OYZU_RELEASES_TOKEN }}
        run: |
          curl -fsSL https://docs.oyzu.ai/install.sh | sh
          echo "$HOME/.oyzu/bin" >> "$GITHUB_PATH"

      - name: Restore installed tools
        uses: actions/cache@v4
        with:
          path: ~/.local/share/oyzu/tools
          key: oyzu-tools-${{ runner.os }}-${{ runner.arch }}-${{ hashFiles('oyzu.lock') }}

      - name: Check that every project is declared
        if: hashFiles('build.yaml') != ''
        run: oyzu discover --check

      - name: Build what the pull request changed
        if: github.event_name == 'pull_request'
        run: oyzu build --affected "origin/${{ github.base_ref }}"

      - name: Build everything
        if: github.event_name != 'pull_request'
        run: oyzu build

      - name: Verify the bundle
        run: oyzu inspect

      - name: Keep the bundle
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: oyzu-dist
          path: dist
          if-no-files-found: ignore

How it works:

  • Checks: the job is detected as pr or ci, so tests, lint and format checks run without --full.
  • Tools: oyzu build installs the tools in oyzu.lock, checking each download's digest. Caching ~/.local/share/oyzu/tools saves the downloads. A missing lock entry fails the build.
  • Pull requests: --affected origin/<base> builds changed targets and their dependents, or everything when it can't narrow safely. See Monorepos and affected builds.
  • Output: dist/ is uploaded even when the build fails, so you can read the failure log.
  • Docker: not needed for host builders (Go, Rust, Node applications, Python wheels). Isolated builds, Docker images and --all-platforms need it; see Isolated builds.

On Windows runners use install.ps1, and the tool store is %LOCALAPPDATA%\Oyzu\tools. On macOS it is ~/Library/Application Support/Oyzu/tools.

3. Any other CI system​

The same steps work on any runner with a POSIX shell. Put oyzu on PATH as in step 1, then:

#!/bin/sh
set -eu
oyzu --version                       # record which Oyzu ran
if [ -f build.yaml ]; then oyzu discover --check; fi
if [ -n "${BASE_REF:-}" ]; then      # set by your pipeline for merge requests
  git fetch origin "$BASE_REF"
  oyzu build --affected "origin/$BASE_REF"
else
  oyzu build
fi
oyzu inspect

Keep dist/ as the job artifact. If Oyzu doesn't recognize your CI system, set CI=true so the build runs every check. Pull-request and tag builds are also recognized on GitLab, Azure Pipelines, CircleCI, Buildkite, Travis CI, Bitbucket Pipelines, Drone, AppVeyor and Jenkins (build context).

4. Read results in scripts​

With --json, the result goes to standard output and diagnostics to standard error as JSON Lines:

oyzu --json build > build-result.json
oyzu --json inspect > inspection.json

A failed command still returns JSON, with error, code, exitCode and nextStep:

$ oyzu --json build nope
{
  "code": "COMMAND_FAILED",
  "error": "unknown build target nope; available targets: api, worker",
  "exitCode": 1,
  "invocationId": "38300-1792552823921616500-1",
  "nextStep": "Correct the reported cause and retry the command."
}

Use the exit status to decide what to do:

ExitMeaning
0Succeeded
1The build or command failed (a failing test, an unknown target)
2Invalid invocation (unknown flag, invalid platform name)
3Wrong runner or toolchain: a selected target needs Docker and this runner has none (NEEDS_DOCKER_DAEMON), user namespaces are unavailable, or a configured tool is below a native minimum. Requeue on a suitable runner or fix the configuration
4--slice build: a needed upstream result is not in the cache (UPSTREAM_NOT_CACHED)
5--slice build: writing the handoff repository failed (HANDOFF_PUSH_FAILED)

5. Optional extras​

  • Share results between jobs and runners: set OYZU_CACHE_CI_REMOTE to an OCI repository only CI can write to, cache.write = true in the runner's user configuration, and a registry token in OYZU_CACHE_TOKEN. See Cache build results.
  • One job per platform: oyzu build --plan --json includes a matrix for targets that declare platforms. See a CI matrix from the plan.
  • Limit parallel work on small runners with --jobs N (or OYZU_BUILD_JOBS).
  • Publish artifacts from a release job: Publish artifacts.

When it fails​

SymptomFix
Tests and lint don't run in CIOyzu didn't detect CI. Set CI=true or pass --context ci.
--affected always builds everythingThe base commit isn't in the clone. Use fetch-depth: 0, or git fetch origin <base> first.
TOOL_LOCK_STALEA native file now asks for a version the lock doesn't have. Run oyzu pin locally and commit oyzu.lock.
NEEDS_DOCKER_DAEMON (exit 3)A selected target needs Docker. Use a runner with a Docker engine.
discover --check fails with INVENTORY_UNDECLAREDA folder holds a project that build.yaml neither lists nor excludes. Add it to builds: or exclude:.
Passes locally, fails in CICI runs every check. Reproduce locally with oyzu build --full.
