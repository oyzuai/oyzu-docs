Pin tools for your team

Goal: every developer and every CI job builds with the same compiler, runtime and package-manager versions, without anyone installing them by hand.

You need: the oyzu executable, a project Oyzu discovers, and network access for the first resolution. No account.

About the output on this page

Captured on Windows 11 with an Oyzu development build (0.1.0-dev.g54d773e20c1e), NO_COLOR=1, redirected, in a two-target Go repository. Long paths are shortened with ….

How it fits together​

LayerHoldsWho edits it
Native pin filesWhat your ecosystem already says: rust-toolchain.toml, go.mod (go line as a minimum), global.json, packageManager in package.json, Gradle and Maven wrapper propertiesYou, as today
oyzu.toml [tools]Requests a native file cannot express, such as an exact Go version or a tool no native file namesoyzu install, oyzu uninstall, or by hand
oyzu.lockThe exact version, archive and digest of every tool, for every platform your team usesOnly Oyzu (pin, install, update)

Commit all three. Never write the same version in two places: if a native file pins it, leave it out of oyzu.toml.

--dry-run writes nothing and installs nothing. Add --json for each requirement's source and constraint.

2. Lock what the native files ask for​

If your native files already say everything (for example rust-toolchain.toml with an exact channel), you only need a lock:

oyzu pin        # resolve exact versions and write oyzu.lock; installs nothing

You can also skip this step: the first oyzu build in a project without a lock resolves and writes oyzu.lock itself. An existing lock is frozen: a build never silently re-resolves it. When a native minimum moves past the lock (for example go get raised go.mod), the build fails with TOOL_LOCK_STALE naming the file; run oyzu pin again.

3. Choose an exact version where the native file cannot​

Native files often state only a minimum or a release line. For Go, a toolchain go1.24.5 line selects exactly 1.24.5, while a go 1.22 line with no patch selects the newest stable 1.22.x (Go version selection). To standardize the team on a newer version, declare it:

oyzu install --dry-run go@1.27     # what would be declared, resolved and locked
oyzu install go@1.27               # declare, lock for every platform, install for this one
Installing requested tools
Resolving every platform, then installing this one
✓ Installed (reused existing installation) go 1.27.3
    Declared "1.27" in …\shop\oyzu.toml (project)
    Locked in …\shop\oyzu.lock for 4 platforms (darwin/arm64/native, linux/amd64/gnu, linux/arm64/gnu, windows/amd64/msvc)

oyzu.toml now holds what you typed and oyzu.lock the exact version:

[tools]
go = "1.27"

Version specs: go@1.27 is a prefix (newest 1.27.x), go@1.27.3 is exact, go@latest is the newest eligible, and a bare go keeps an existing declaration. Several specs in one command apply together or not at all. Supported providers today: node, go, python, java, maven, gradle, helm, kubectl, k3d, liquibase, tailscale, npm, pnpm, rust, cargo-nextest, cargo-llvm-cov, plus experimental aqua:<owner>/<repo> and github:<owner>/<repo> registry packages (tool commands).

The lock covers more platforms than the one you are on, so a teammate on macOS or a Linux CI runner gets a matching archive without re-resolving. A platform the publisher has no build for is omitted and reported (for example Node 14 has no macOS arm64 build).

4. Commit and let everyone else install​

Commit oyzu.toml and oyzu.lock. A teammate, or CI, then runs:

oyzu install --frozen
Installing tools
Checking pinned tools and verifying reusable installations
Tool installation

Tool  Version  Result
go    1.27.3   reused

Selected installations verified. Use oyzu tools current to inspect availability.

--frozen refuses to resolve anything new: if the lock does not match the configuration, it fails instead of changing the lock. Downloads are checked against the locked digest before use; installed tools are trusted afterwards and not re-hashed on every command.

oyzu install installs declared tools. When every requirement comes from native files (nothing in [tools]), it has nothing to do and says so:

✗ COMMAND_FAILED: configure a tool before running oyzu install

That is not a problem: oyzu build installs every missing pinned tool it needs by itself.

5. Check what is in effect​

oyzu tools current

Tool  Requested  Selected  Source   Status
go    1.27       1.27.3    project  ok

Use --details for paths and identities, --all for overridden declarations.

Store: C:\Users\<you>\AppData\Local\Oyzu\tools
Installed state comes from stored receipts; payloads are not re-hashed.

Other read-only views:

CommandAnswers
oyzu tools listWhich installations are in the shared store, their size, and whether this project or your global lock references them
oyzu tools versions goWhich versions could be installed (newest first)
oyzu tools info goProvider, accepted names, platforms, verification and eligibility
oyzu which goThe exact verified executable a command would run

Statuses in tools current: ok, not installed (locked but missing from the store; run oyzu install), stale lock (no matching lock entry; run oyzu pin), blocked (excluded by tools.allowed), ambiguous.

6. Run commands with the pinned tools​

oyzu exec -- go version     # anything after -- runs with the locked tools on PATH
oyzu run test               # tasks always use the locked tools

To have an ordinary terminal pick the tools up inside the project, set up shell integration once (oyzu shell install bash, zsh or pwsh); see shell activation.

7. Move versions forward​

oyzu update go       # newest version within the existing request ("1.27" -> latest 1.27.x)
oyzu update          # every declared tool
oyzu install go@1.28 # change the request itself
oyzu pin --refresh   # refresh installation recipes, keep the selected versions
oyzu uninstall go    # remove the declaration and its lock entries

update never edits oyzu.toml; it only re-resolves within what is declared and rewrites the lock. Review and commit the lock change like any dependency bump.

Scopes: project, personal, global​

FlagWritesUse for
(none)project oyzu.toml and oyzu.lockThe team's toolchain
--localoyzu.local.toml (lock stays the project's)A personal override you do not commit
-g, --globalyour user configuration and the lock beside itTools you want in every project

Outside a project, a command without -g fails with TOOL_NO_PROJECT rather than guessing.

Organizational limits​

An administrator can restrict which tools are eligible with tools.allowed; a request outside it fails with CONFIG_OVERRIDE_DENIED, naming the rule, and nothing is written. Policy constraints bind regardless of how a project spells the tool. See configuration for policy scopes.

When it fails​

CodeMeaningFix
TOOL_LOCK_STALEThe lock has no pin for a request, or a native minimum changedoyzu pin, then commit the lock
TOOL_NATIVE_MINIMUM_CONFLICTA configured version is below what a native file requires (exit 3)Raise the request, or lower the native minimum
TOOL_FLAGS_CONFLICTSpecs combined with --frozen, --offline or --updateRun two commands
TOOL_NOT_DECLAREDuninstall or update of a tool this scope does not declareThe message names the scope that does
PIN_EDIT_CONFLICT / PIN_RECOVERY_REQUIREDA concurrent or interrupted lock editRe-run oyzu install, update, uninstall or pin; they recover first
TOOL_LOCK_MISSINGinstall --frozen with no lockRun oyzu pin or oyzu install online once

Provider coverage is bounded and tool commands are verified on Linux x86-64; Windows and macOS are not yet qualified. Reference: tool commands, tool management, configuration. Offline and proxy setups: Work offline or behind a proxy.
