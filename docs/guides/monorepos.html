Monorepos and affected builds

In a repository with several projects, build one target with what it needs, or only the targets a change affects plus the targets that use them.

You need: a repository Oyzu already discovers (Adopt Oyzu), Git on PATH, and the commit you compare against available locally.

The examples use two Go targets, api and worker, where worker depends on api.

How Oyzu sees a monorepo​

Every folder a builder recognizes is one target. A native workspace (Cargo [workspace], go.work, npm, Yarn or pnpm workspaces) is one target built by its own tool; Oyzu doesn't split it into members. Relationships between targets come from what you declare:

DeclarationEffect
depends_on: [api] in build.yamlapi builds first, and a change to api also rebuilds this target. No files are passed between them.
materialize.from in build.yamlThis target uses another target's artifacts. Also followed by affected builds.
depends_on in an oyzu.toml taskOrders tasks across targets. Also followed by affected builds.

Oyzu doesn't detect that one project reads another project's files. If web/ imports code from shared/, declare depends_on so a change to shared/ rebuilds web/.

1. Declare the targets and how they connect​

# build.yaml
builds:
  api:
    uses: go/app
    path: api
  worker:
    uses: go/app
    path: worker
    depends_on: [api]

Check it with oyzu discover: each build should show Chosen by build.yaml.

3. Build only what changed​

--affected <git-ref> compares your working tree with a local commit. It selects every target that contains a changed file, adds the targets that depend on those (and so on), and adds the targets they need.

Preview first; it runs nothing:

oyzu build --affected HEAD --plan

Then build. Here only api/main.go changed since HEAD:

Each selected target runs its normal checks and packaging. If nothing changed, the build writes an empty bundle and runs nothing. You can't combine --affected with target names.

Use it in pull requests​

In CI, compare with the branch the pull request targets. The commit must be in the local clone; Oyzu never fetches it:

git fetch origin main
oyzu build --affected origin/main

With actions/checkout, set fetch-depth: 0 (or fetch the base branch). Blobless clones (git clone --filter=blob:none) also work. See Run in CI.

4. Know when it builds everything​

Affected builds play it safe. Oyzu builds everything, and records why, when:

  • the base commit can't be read (the ref isn't in the local clone);
  • a changed file belongs to no target, or a file is new since the base commit;
  • build, configuration or lock files changed (build.yaml, oyzu.toml, oyzu.lock, or a native manifest such as go.mod);
  • a root task with prerequisites in other targets has changed inputs, or managed configuration is active.

The plan shows a full selection; the JSON record says why:

$ oyzu build --affected origin/main --plan --json
{
  "selection": {
    "affected": {
      "baselineCommit": null,
      "changedPaths": [],
      "fallback": "baseline-unavailable",
      "reasons": {},
      "reference": "origin/main",
      "sourceDigest": "sha256:c88e4628600a31d68134b514eaa5230e725c4da1230e7f24efbefb219f817035"
    }
  }
}

A common surprise is line endings. On Windows with Git's core.autocrlf, files on disk can have CRLF endings while Git stores LF. Oyzu compares raw bytes, so every file counts as changed:

$ oyzu build --affected HEAD --plan --json
{
  "selection": {
    "affected": {
      "baselineCommit": "9a7d31fe0e4d48ba8e912063a39692e2777cf826",
      "changedPaths": [
        "api/go.mod",
        "api/main.go",
        "api/main_test.go",
        "build.yaml",
        "worker/go.mod",
        "worker/main.go",
        "worker/main_test.go"
      ],
      "fallback": "configuration-or-lock-change",
      "reasons": {},
      "reference": "HEAD",
      "sourceDigest": "sha256:d10ba07627a208004ce056654baf8d71567c7512392b3151c20dda7f382f96e5"
    }
  }
}

If affected builds keep selecting everything, compare changedPaths with git status, and add a .gitattributes file with explicit line endings so the working tree matches the committed bytes.

Changes outside Git, such as a new tool version in your user configuration or an environment variable, aren't detected. Run a full build when those change.

5. Keep the build list complete​

In a large repository, the risk is a new project that never gets built. With a build.yaml:

  • oyzu build --plan lists up to five folders a builder recognizes but build.yaml leaves out, under Not in build.yaml.
  • oyzu discover --check exits 1 while such a folder exists. Run it in CI.
  • exclude: [tools/scratch, tooling/**] marks folders that are deliberately not builds.

See builds build.yaml leaves out.

6. Split across platforms (optional)​

For targets that declare platforms in build.yaml, oyzu build --plan --json includes a matrix you can pass to a CI matrix, one job per platform. With --affected, it holds only affected targets. See a CI matrix from the plan.

When it fails​

SymptomFix
Everything rebuilds every timeRead selection.affected.fallback in --plan --json. Fetch the base commit, commit configuration changes, or fix line endings.
A target isn't rebuilt when its dependency changesDeclare the link with depends_on or materialize.from. Oyzu doesn't detect file reads across projects.
unknown build targetUse the names from oyzu discover. With a build.yaml, they are its build names.
A folder never buildsIt isn't in build.yaml. Add it, or run oyzu discover --check to list such folders.
