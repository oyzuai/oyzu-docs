Monorepos and affected builds

Goal: in a repository with several projects, build exactly what you need: one target and what it depends on, or only the targets a change affects and the targets that use them.

You need: a repository Oyzu already discovers (Adopt Oyzu), Git on PATH, and the baseline commit available locally.

About the output on this page

Every block is a real capture from Windows 11 with an Oyzu development build (0.1.0-local.564f462704df), color forced on and output piped to a file. The repository has two Go targets, api and worker, declared in build.yaml with worker depending on api. The Prepare and Facts sections are trimmed with …; JSON is trimmed to the selection.affected object.

How Oyzu sees a monorepo​

Every folder a builder recognizes is one target. A native workspace (Cargo [workspace], go.work, npm, Yarn or pnpm workspaces) is one target built by its own tool; Oyzu does not split it into members. Relationships between targets come from what you declare:

Declaration (build.yaml)Effect
depends_on: [api]Ordering: api builds first. An affected build of api also rebuilds this target. No files are transferred.
materialize.fromThis target consumes another target's artifacts; also followed by affected selection.
Task prerequisites (depends_on in an oyzu.toml task)Cross-target task ordering, also followed.

Oyzu does not infer that one project reads another project's files. If web/ imports code from shared/, declare depends_on so a change to shared/ rebuilds web/.

1. Declare the targets and their edges​

# build.yaml
builds:
  api:
    uses: go/app
    path: api
  worker:
    uses: go/app
    path: worker
    depends_on: [api]

Check it with oyzu discover; each build should say Chosen by build.yaml.

3. Build only what changed​

--affected <git-ref> compares your working tree with a local commit, selects every target that encloses a changed file, follows declared consumers transitively, and adds the producers they need.

Preview first; it runs nothing:

oyzu build --affected HEAD --plan

Each selected target runs its normal checks and packaging. If nothing changed, the build writes an empty, inspectable bundle and runs nothing. --affected cannot be combined with target names.

Use it in pull requests​

In CI, compare with the branch the pull request targets. The reference must exist locally; Oyzu never fetches it:

git fetch origin main
oyzu build --affected origin/main

With actions/checkout, set fetch-depth: 0 (or fetch the base branch) so the commit is present. Blobless clones (git clone --filter=blob:none) work too. See Run in CI.

4. Know when it falls back to a full build​

Selection is conservative. Oyzu builds everything and records why when:

  • the baseline cannot be read (the ref does not exist locally);
  • a changed file belongs to no target, or a file is new relative to the baseline;
  • build, configuration or lock metadata changed (build.yaml, oyzu.toml, oyzu.lock, a native manifest such as go.mod);
  • a root task with cross-target prerequisites has changed inputs, or managed configuration is active.

The human plan shows a full selection; the reason is in the JSON record:

$ oyzu build --affected origin/main --plan --json
{
  "selection": {
    "affected": {
      "baselineCommit": null,
      "changedPaths": [],
      "fallback": "baseline-unavailable",
      "reasons": {},
      "reference": "origin/main",
      "sourceDigest": "sha256:c88e4628600a31d68134b514eaa5230e725c4da1230e7f24efbefb219f817035"
    }
  }
}

Another real case: files written with Windows line endings (CRLF) were committed as LF through Git's core.autocrlf, so the working bytes differed from the committed bytes. Oyzu compares raw bytes, so every file counted as changed and the build fell back:

$ oyzu build --affected HEAD --plan --json
{
  "selection": {
    "affected": {
      "baselineCommit": "9a7d31fe0e4d48ba8e912063a39692e2777cf826",
      "changedPaths": [
        "api/go.mod",
        "api/main.go",
        "api/main_test.go",
        "build.yaml",
        "worker/go.mod",
        "worker/main.go",
        "worker/main_test.go"
      ],
      "fallback": "configuration-or-lock-change",
      "reasons": {},
      "reference": "HEAD",
      "sourceDigest": "sha256:d10ba07627a208004ce056654baf8d71567c7512392b3151c20dda7f382f96e5"
    }
  }
}

If affected builds keep selecting everything, compare changedPaths with git status and normalize line endings (for example with a .gitattributes file) so the working tree matches the committed bytes.

Changes outside Git (a new tool version in user configuration, an environment variable) are not detected. Run a full build when those change.

5. Keep the inventory complete​

In a large repository, the risk is a new project that silently never builds. With a build.yaml:

  • oyzu build --plan lists up to five folders a builder recognizes but build.yaml leaves out, under Not in build.yaml;
  • oyzu discover --check exits 1 while such a folder exists (add it to CI);
  • exclude: [tools/scratch, tooling/**] marks folders that deliberately are not builds.

These need a CLI built from current source; see builds build.yaml leaves out.

6. Fan out across platforms (optional)​

For targets that declare platforms in build.yaml, oyzu build --plan --json emits a matrix you can feed to a CI matrix strategy, one job per platform; combined with --affected, it holds only the affected targets. The workflow example and field list are in a CI matrix from the plan.

Verify​

  • oyzu build --affected HEAD --plan on a clean working tree selects nothing.
  • Touch one file in a leaf target: only that target is selected.
  • Touch a file in a producer: the producer and every declared consumer are selected.

When it fails​

SymptomFix
Everything rebuilds every timeRead selection.affected.fallback in --plan --json. Fetch the baseline, commit configuration changes, or fix line endings.
A consumer is not rebuilt when its dependency changesDeclare the edge with depends_on or materialize.from; file reads across projects are not inferred.
unknown build targetUse the IDs from oyzu discover; with a build.yaml they are its build names.
A folder never buildsIt is not in build.yaml. Add it, or run oyzu discover --check to list such folders.
