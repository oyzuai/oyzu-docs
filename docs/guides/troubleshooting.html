Troubleshooting

Find your symptom below. Every Oyzu failure starts with a code (such as TOOL_LOCK_STALE) or a plain cause, then a Next: line with the fix. Read those two lines first.

Start here: collect the facts​

oyzu --version                  # the exact Oyzu you are running
oyzu build --plan               # what Oyzu will do; runs nothing
oyzu -v build                   # debug detail; -vv for trace
oyzu history                    # past builds, with invocation IDs
oyzu history <invocation-id>    # result, why each stage ran, file paths

Every failure also prints the invocation ID, the Oyzu version, the executable and the directory:

$ oyzu build nope
…
✗ COMMAND_FAILED: unknown build target nope; available targets: api, worker
  Next: Correct the reported cause and retry the command.
  Invocation: 36620-1792552675147666000-1
  oyzu … · windows/x86_64
  Executable: …\oyzu.exe
  Directory: .

With --json, the failure is an object with code, error, exitCode and nextStep. For detail from one area, set for example OYZU_LOG=warn,oyzu::tools=debug. Areas: commands, config, discovery, tools, acquisition, executor, builders, reports.

Discovery: Oyzu doesn't see my project as expected​

A project folder is missing from oyzu discover. Discovery stops at the first folder a builder recognizes and skips nested Git repositories, folders with their own build.yaml, and dependency and output folders. With a root build.yaml, only listed builds exist. Add the folder:

builds:
  web:
    uses: node/app
    path: web

oyzu discover --write adds such folders for you (builds build.yaml leaves out).

Oyzu picked the wrong package manager, test runner, linter or formatter. oyzu build --plan shows each choice and why. Override it in build.yaml with the with key the plan names, such as with: {package-manager: pnpm} (selecting a role).

conflicting … candidates …; declare the intended one … with: {…} Two native files disagree equally. Add the suggested with: setting to that build, or remove the stale file (for example an old lockfile from another package manager).

… is recognized by docker/image and node/app, so discovery cannot choose Name the builder: both: {uses: docker/image, path: both}.

Another tool's build.yaml (for example Dart's) is in the way. Oyzu only treats a build.yaml with a builds, members or exclude root key as its own. Others are listed as skipped.

Run oyzu config validate after every edit, and oyzu config explain <key> to see where a value comes from.

CONTEXT_INVALID: an unknown --context or OYZU_CONTEXT value. It fails every command that reads configuration, including install and exec:

$ oyzu build --context nightly
✗ CONTEXT_INVALID: --context has unknown context "nightly"; use one of local, pr, ci, release
  Next: Correct the reported cause and retry the command.

Selection: the wrong things are built​

unknown build target nope; available targets: api, worker: build arguments are exact target names from oyzu discover, not task names, paths or patterns.

ambiguous task test; choose api:test, worker:test: several targets define the task. Add the target name: oyzu run api:test.

TASK_NOT_FOUND (exit 5): the task doesn't exist in this folder. The message lists the tasks it found; pick another project with oyzu -C <dir> run <task>:

$ oyzu run nope
  · Setup  Loading configuration and discovering tasks
✗ TASK_NOT_FOUND: no task "nope" in …\shop. Available tasks: build, format, format-check, install, lint, pre_build, smoke, test. Run oyzu run to list tasks, or oyzu -C <project> run nope
  Next: Check the selected directory and name; use oyzu -C <project> to select a project.

--affected builds everything. The JSON plan says why:

oyzu build --affected origin/main --plan --json
selection.affected.fallbackFix
baseline-unavailableThe ref isn't in the local clone. Run git fetch origin main, or use fetch-depth: 0 in CI.
configuration-or-lock-changebuild.yaml, oyzu.toml, oyzu.lock or a native manifest changed. Commit it and later builds narrow again. If changedPaths lists files you didn't edit, line endings differ between your files and Git; fix them with .gitattributes.

SOURCE_TRACKED_IGNORED: tracked source .oyzu-tool-lock-edit.lock is excluded …: an ignored file was committed. For Oyzu's coordination file, untrack it with git rm --cached .oyzu-tool-lock-edit.lock and keep it in .gitignore. If the build really needs the file, list it in the build's inputs.

Tools are checked when installed and trusted after that, so a damaged tool simply fails when it runs. Reinstall it.

Output shortened.

  • blocked actions didn't run because something they depend on failed. Fix the first failure.
  • After a failure, .oyzu/bin still holds the programs from the last successful build.
  • Passes locally, fails in CI: CI runs every check. Reproduce with oyzu build --full.
  • CHECK_ADVISORY warning: an advisory check failed, but the project set it to warn only, so the build succeeded.

Another build is running in this folder. A second build in the same folder fails before running anything. Wait for the first one. Don't delete .oyzu/build.lock; the lock is released when the build exits.

An existing dist/ blocks the build. Oyzu only replaces a dist/ that contains an Oyzu manifest. If your project writes its own dist/, move that output, or set [build] bundleDirectory (bundle destination). Oyzu never deletes it.

An error names a .oyzu/bundle-… folder. dist/ couldn't be written, so the results were kept there. Inspect that path with oyzu inspect, fix the disk space or permission problem, and rebuild.

Network, proxies and offline​

CodeMeaning
PROXY_INVALIDA proxy variable is set but isn't a valid URL. Oyzu never falls back to a direct connection
TRUST_BUNDLE_UNREADABLE / TRUST_BUNDLE_INVALIDSSL_CERT_FILE is missing, unreadable, empty or not PEM
SOURCE_UNAVAILABLEThe download failed after two retries. Check your connection and the proxy
SOURCE_TIMEOUTThe 45-second download deadline passed
SOURCE_DENIEDNo approved source allows the request or redirect
BYTE_LIMIT / REQUEST_LIMITA download or session went over its size or request limit
TOOL_OFFLINEThe command needs the network and --offline forbids it

With --offline, a missing tool or dependency stops the build instead of being downloaded. Go online once and run the same build. See Work offline or behind a proxy.

Windows notes​

  • A new PATH entry isn't picked up. An open terminal keeps the PATH it started with. Update the session ($env:Path = "C:\path\to\bin;$env:Path") or open a new terminal.
  • Line endings. With core.autocrlf, files on disk can differ from what Git stored, and --affected counts that as a change. Set explicit eol rules in .gitattributes.
  • Paths in messages may start with \\?\. It's the same path.

Still stuck​

Collect oyzu --version, your platform, the full failing command, its output with -v, and oyzu history <invocation-id> --json. Oyzu hides credentials in URLs, headers and key=value text, but native tool output is passed through unchanged, so check it for secrets before you share it.
