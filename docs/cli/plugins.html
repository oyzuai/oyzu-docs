oyzu plugins

Builders run as plugins: separate programs that Oyzu starts for each build. A plugin is a package such as oyzu/go, and the name you write as uses: in build.yaml (for example go/app) is a reference to one of its profiles. Use oyzu plugins to find plugins, see which one each target of your project uses and why, and update the selections recorded in oyzu.lock.

oyzu plugins [OPTIONS] <COMMAND>
SubcommandWhat it does
search [QUERY]Browse or search the references the catalogs offer
versions <REFERENCE>Show a reference's known releases and why each can or cannot be selected here
info <REFERENCE[@VERSION]>Show a release's package, platforms, download routes and verification
listList the plugin releases installed in the plugin store
currentShow this project's locked plugin selections, whether they are installed, and whether they can run here
explain [TARGET]Explain which plugin a target uses and why, with the ways to change it
update [REFERENCE[@SELECTOR]]...Update locked selections within their adopted major version
prune SHA256...Preview, then remove, installed copies of revoked releases

search, versions, info, list, current and explain only read: the cached catalog, the plugin store and oyzu.lock. They never download or start a plugin, run a project tool or change a file. Only --refresh updates the cached catalog. update changes oyzu.lock, and prune --apply deletes installed copies.

Note: Plugins are experimental. Releases published so far are previews. To let builds use previews, opt in once for your user account: oyzu config set --global plugins.preview true. A project file cannot do this, because the release is code that runs on your machine.

How a plugin is chosen​

For each target, oyzu build looks for a plugin in this order and uses the first match:

  1. A local development binding in your user configuration (see Develop a builder locally).
  2. A plugins.packages binding in your user configuration.
  3. The release already recorded in oyzu.lock. Locked releases are replayed, never replaced by a newer catalog entry.
  4. The newest eligible release in the plugin catalog.

The first oyzu build that picks a plugin from the catalog downloads it, verifies its signature and digests, installs it in the shared tool store and writes the choice to oyzu.lock. Commit the lock so everyone builds with the same release. Other commands (build --plan, run, discover) never download or install; they replay the lock.

If no plugin matches, the build stops with PLUGIN_UNAVAILABLE and says why. There is no built-in fallback.

Options​

All inspection subcommands (search, versions, info, list, current, explain) take:

OptionDescription
--store <DIR>Use this tool store instead of the shared user store
--refreshUpdate the verified catalog cache from permitted sources first. Installs no plugin
--offlineNever use the network. Read only the verified cached catalog

search also takes --type <TYPE>, which shows only plugins that serve one capability. The only value today is build. update takes --dry-run, --store and --offline. The global options apply to all subcommands.

plugins list​

Lists the plugin releases installed in the plugin store: package, version, the references it serves, platforms, whether this project locks it, and its release digest. It lists the store only. The store keeps no record of which projects use a release.

plugins current and plugins explain​

oyzu plugins current [OPTIONS]
oyzu plugins explain [OPTIONS] [TARGET]
ArgumentMeaning
[TARGET]A target, by name or path. Omit it for every plugin-backed target

current shows each locked selection with its install state and whether it can run here. explain prints the same Selection record oyzu build prints: which release, why it was chosen and how to change it.

$ oyzu plugins explain --offline
No target here uses a plugin
​
No package-backed target is selected. Declare uses: <reference> in build.yaml or supply the required admitted package; find catalog entries with oyzu plugins search.

plugins update​

oyzu plugins update [OPTIONS] [REFERENCE[@SELECTOR]]...
Argument / optionDescription
[REFERENCE[@SELECTOR]]...References to update, each optionally with @v<major>, @<version> or @sha256:<digest>. Omit it to update every locked selection
--dry-runCheck everything and show the lock change without writing oyzu.lock
--store <DIR>Use this tool store instead of the shared user store
--offlineNever use the network. Update from the cached catalog only
oyzu plugins update                  # every locked selection, within its major version
oyzu plugins update go/app@v2        # adopt major version 2 explicitly
oyzu plugins update go/app@1.4.2     # select exactly 1.4.2
oyzu plugins update go/app@sha256:…  # restore one exact release (the undo line a build prints)
oyzu plugins update --dry-run

A routine update moves to the newest eligible release inside the adopted major version. It never goes to an older release or to a preview. Each new release is installed and verified first, and oyzu.lock is rewritten only if every requested selection passes, in one step. A withdrawn or revoked release, or an unusable catalog, fails without changing the lock. With no plugin locked:

$ oyzu plugins update --dry-run --offline
oyzu.lock selects no plugin; nothing to update
​
Lock  …\hello\oyzu.lock (unchanged)
​
Nothing was launched and no file changed.

plugins prune​

oyzu plugins prune [--store DIR] [--apply] SHA256...

When a release is revoked, Oyzu refuses to run it but leaves its files in the store. prune removes them. Copy exact sha256: release digests from plugins list or plugins info. Without --apply it only shows what it would do.

  • --apply rechecks the cached catalog and the installation, then removes each selected revoked copy that no running Oyzu is using.
  • It never refreshes the catalog or downloads anything. Run oyzu plugins list --refresh first if you need current revocations.
  • An expired catalog, an ordinary withdrawal or an unavailable source cannot authorize deletion.
  • Copies in use, and installations Oyzu cannot inspect, are kept.
  • Project locks are not changed. A copy with no active user may still be locked by some project, so update that project with oyzu plugins update.

Each release gets a state (eligible, retained, removed, absent or incomplete) with a reason. Preview exits 0. --apply exits 1 if anything was retained or removal was incomplete. If a filesystem error interrupts a removal, a partial copy can remain; check the reason and the leftover files before retrying. There is no option to remove everything or to force removal.

$ oyzu plugins prune sha256:e6338a15… --store ~/store
Plugin cleanup preview
Release                     State     Reason
sha256:e6338a15a12b6442cf52…  eligible  Revoked release has no active cooperative use lease and
                                        is eligible for explicit removal.
Store  ~/store
Catalog  acme catalog serial 2
No installation was removed. Repeat the exact selected digests with --apply to recheck eligibility
and remove revoked copies without active use leases.

Output shortened.

Develop a builder locally​

You can bind a compiled plugin you built yourself to a profile that has no packaged plugin. Put the binding in user or machine configuration, never in the project, and select the same short id in build.yaml. The names and path here are examples. The executable must implement the builder operations for your project.

User or machine configuration
[plugins.development]
"independent/app" = "/absolute/path/to/independent-plugin"
build.yaml
builds:
  app:
    uses: independent/app
oyzu build app

The build runs on the host and collects the artifacts the plugin declares. Oyzu still resolves the tools the plugin asks for through your normal configuration, lock, tool policy and offline rules. A local binding does not add zero-config detection, with options, dependency preparation or isolated execution.

A target can also name an OCI package directly, for example uses: oci://registry.example/team/builder@sha256:<digest>#app. The package's manifest supplies its identity. Tags outside the official namespace need a user-level signer binding for the full URI. See direct OCI references and local plugin bindings.

Company catalogs and offline builds​

An organization can publish its own signed tool index with a plugin catalog. Configure it in user or machine configuration, following the tool index reference. A company catalog is exclusive: if it selects a release and that release's route fails, Oyzu does not fall back to the official catalog. If the company catalog has no matching entry, ordinary selection continues as usual.

A typical workflow:

oyzu plugins search --refresh
oyzu tools check --catalog --json
oyzu build --full
# Keep the approved oyzu.lock and the installed tools and plugins for this user.
oyzu build --offline --frozen --full --no-cache

The online build installs the selected release. The frozen offline build replays exactly the locked installation and also needs the tool metadata prepared by the online build. If you use --store DIR, prepare that store too. Native Go builds also read the default user metadata store.

ErrorMeaningFix
PLUGIN_LOCK_UNUSABLEA locked plugin is missing from the store and offline or frozen mode forbids downloading itRun an online, non-frozen build, or restore the store
PLUGIN_LOCK_MISSING (exit 4)--frozen needs a plugin selection that oyzu.lock lacksRestore the complete approved lock
PLUGIN_ROUTE_UNAVAILABLEA new catalog selection has no usable download route, or the build is offlineRun online, or bind the archive with plugins.packages
PLUGIN_RELEASE_WITHDRAWN, PLUGIN_RELEASE_REVOKEDThe catalog withdrew or revoked the releaseRun oyzu plugins update to adopt an eligible release
PLUGIN_UNAVAILABLENo plugin serves the referenceOpt in to previews, or bind a package

The 3600-second recent-catalog window does not extend a signed catalog's expiry. A locked, installed plugin can still replay against an expired catalog, with a warning that newer withdrawals may be missing. Retained withdrawals and revocations still block execution, and an expired catalog cannot authorize plugins prune.

See catalog selection and lock selections for the full rules.

Corporate TLS inspection​

If your organization catalog serves plugins from an HTTPS mirror behind an inspecting proxy, use the standard environment variables for the proxy and your extra CA bundle:

HTTPS_PROXY=http://proxy.example.com:8080 SSL_CERT_FILE=/absolute/company-ca.pem oyzu build --full

The bundle adds trust for the proxy's certificate. It does not replace the official plugin signer or admit a new route, and it never selects a different release. Loopback addresses always bypass proxies. If a download fails, restore access to the mirror and check that the bundle contains your inspection CA. This works for HTTPS mirrors on Linux and Windows. macOS and OCI registry routes behind an inspecting proxy are not supported yet. See HTTPS package routes and proxy and trust settings.

Exit status​

StatusWhen
0Success, including "nothing to update"
1An unknown target for explain (PLUGIN_TARGET_UNKNOWN), a refused or unusable catalog, or an update that failed verification
2Invalid arguments
4oyzu build --frozen found no plugin selection in oyzu.lock (PLUGIN_LOCK_MISSING)
