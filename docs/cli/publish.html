oyzu publish

Publish a finished build's file artifacts. Without an account, oyzu publish reads named destinations from oyzu.toml, checks the build's existing signed provenance, signs exactly what it is about to publish, uploads the unchanged bytes to an OCI registry or an existing GitHub release, and downloads them again to confirm. With --server, --account and --project, it instead registers the build with an Oyzu platform and requests governed publication.

oyzu publish [OPTIONS]

Note: Experimental. Standalone publishing to OCI registries and GitHub Releases works and has been tested on Windows (x86-64). npm and Python package publishing, OCI image archives and mutable OCI tags aren't supported. Governed publication through a platform isn't generally available yet.

Options​

Standalone publication:

OptionDescription
--destination <NAME>Named destination or publication set; repeat for several
--manifest <FILE>The build manifest to publish. Repeat it to publish several bundles (one per platform) as one publication, checked for completeness together. Default dist/manifest.json
--allow-incomplete <PLATFORM=REASON>Publish even though a declared platform has no artifact (repeatable), for example darwin/x86_64=no-intel-runner. Recorded in the signed publication evidence
--tag <TAG>The existing GitHub release tag to publish to. Without it, the tag is the exact version tag version inference recorded for the published builds (v1.4.0, or api/v1.4.2 for one package of a workspace)

Governed publication through a platform:

OptionDescription
--server <URL>The platform's URL (or OYZU_URL); https unless it is localhost
--account <ACCOUNT>The account to publish to (or OYZU_ACCOUNT)
--project <PROJECT>The project to publish to (or OYZU_PROJECT)
--provenance <FILE>Existing signed provenance bundle
--policy-evidence <FILE>Original signed policy report bundle for central admission
--version <VERSION>The build's version, when the pipeline names one
--commit <SHA>The built commit; defaults to the CI system's
--repository <OWNER/NAME>The repository as owner/name; defaults to the CI system's
--audience <AUDIENCE>The audience to request OIDC tokens for (or OYZU_AUDIENCE; default oyzu)
--token-env <NAME>Read the OIDC token from this environment variable instead of discovering one
--no-uploadReport artifacts without uploading them to the platform's registry (or OYZU_PUBLISH_UPLOAD=0)

--destination, --allow-incomplete and --tag can't be combined with --server, --account, --project or --no-upload. The global options also apply.

Configure a destination​

Destinations go in the project root's oyzu.toml. A [publish] table in any other folder's file is a CONFIG_SCOPE error. An example OCI destination, with credentials read from environment variables and never written in the file:

[publish]
default = "sandbox"

[publish.destinations.sandbox]
kind = "oci"
artifacts = ["app/archive"]          # optional when the bundle has exactly one artifact
registry = "https://registry.example.com"
repository = "team/artifacts"
usernameEnv = "REGISTRY_USERNAME"
passwordEnv = "REGISTRY_PASSWORD"

[publish.requirements.provenance]
bundlePath = "evidence/build.sigstore.json"
publicKey = "<base64 raw 32-byte Ed25519 public key>"
builderId = "https://ci.example.com/builders/release"

[publish.requirements.signing]
keyEnv = "PUBLICATION_SIGNING_SEED"
publicKey = "<base64 raw 32-byte Ed25519 publication public key>"

A GitHub destination uses kind = "github-release" with repository and tokenEnv, and attaches files to an existing release: the one named by --tag, or the exact version tag that version inference recorded for the built commit.

Examples​

oyzu build
oyzu publish                                  # the default destination
oyzu publish --destination sandbox
oyzu publish --destination gh --tag v1.4.0    # attach to an existing release
oyzu publish --manifest linux/dist/manifest.json --manifest windows/dist/manifest.json \
  --allow-incomplete darwin/x86_64=no-intel-runner

Every selected destination is required. Oyzu checks everything (selection, evidence, signatures) before the first upload. If a later destination fails, earlier ones stay published and the result names the unfinished ones. Running the same command again skips destinations that already have the exact bytes.

Governed publication from CI:

oyzu publish --server https://oyzu.example.com --account acme --project web --provenance evidence/build.sigstore.json

Output​

Each destination is reported as published, already-present, failed or unfinished, with the manifest, artifact and evidence digests that were checked. Outputs not selected for a destination are listed as unselected. --json returns the publication record with the same per-destination states. Publishing always needs the network.

Exit status​

StatusWhen
0Every selected destination published (or already had the exact bytes)
1Refused before publishing: missing configuration or evidence, a wrong subject, a conflicting existing file, or a build that didn't succeed
2A destination failed or is unfinished, or invalid arguments
3Invalid configuration, such as an unknown destination kind or an artifact selector that names no build (CONFIG_INVALID_VALUE, CONFIG_REFERENCE_UNKNOWN, CONFIG_SCOPE)

Common errors​

CodeFix
PUBLISH_NOT_CONFIGUREDAdd [publish.destinations.NAME] (and optionally publish.default) to the root oyzu.toml, or pass --destination.
PUBLISH_BUILD_NOT_SUCCEEDEDThe manifest records a failed or interrupted build. Fix it and build again.
PUBLISH_ARTIFACT_SELECTION_INVALIDThe bundle has several artifacts and the destination doesn't pick one, or a selector names an unknown output. Set artifacts = ["target/output"].
PUBLISH_TAG_UNKNOWNA GitHub destination, and the built commit has no version tag. Tag the commit and rebuild, or pass --tag.
