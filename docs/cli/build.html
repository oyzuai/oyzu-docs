oyzu build

Build native artifacts for every target, or the ones you name. oyzu build resolves and installs the pinned tools, runs each target's stages with its own native commands (go build, npm run build, cargo build and so on), reuses results that have not changed, and writes the outputs plus a manifest, logs and reports to dist/.

oyzu build [OPTIONS] [TARGETS]...
ArgumentMeaning
[TARGETS]...Target IDs; omitted means all targets. Required dependencies are included

Target names are the ones oyzu discover prints.

Common tasks​

You want toRun
Build every target for this machineoyzu build
Build one target (and what it depends on)oyzu build cli
See what would run, without running anythingoyzu build --plan
Run formatting, lint and tests toooyzu build --full
Report rule findings onlyoyzu build --check
Build for another platformoyzu build --platform linux/arm64
Build every declared platformoyzu build --all-platforms
Understand why a stage ran instead of being reusedoyzu build --explain
Build only what changed since a Git refoyzu build --affected origin/main

Options​

The global options (-C, --json, -v, -q, --log-level, --root, --profile, --no-profile, --toolset, --local-overrides) also apply.

What to build​

OptionDescription
--fullRun all quality stages locally (also enabled by CI context)
--context <CONTEXT>Pin the build context: local, pr, ci or release. Detected from CI provider variables by default; a pin can raise it, and can lower it only when no CI provider marker is present. Also OYZU_CONTEXT
--platform <OS/ARCH>Build for this target platform instead of the host (repeatable): os/arch[/abi] such as linux/arm64 or windows/x86_64/msvc; amd64 and aarch64 are accepted. A target that does not declare it skips it
--all-platformsBuild every declared platform with the container executor; fails before running when any declared platform cannot be built here
--affected <AFFECTED>Build targets affected since a local Git ref, including dependents
--optimizedBuild the optimized profile (cargo build --release) even when the artifacts stay local. Overrides build.optimized; policy still wins
--no-optimizedBuild the development profile even when the artifacts are packaged, handed off, cached remotely or published. Overrides build.optimized
--verify-with <TOOLSET>Also run this toolset's verification run (repeatable): test the builds that use its tools with them ([toolsets.NAME] in oyzu.toml), in any context. What ships is still built with [tools]
--verify-only <TOOLSET>Run only this toolset's verification runs (repeatable), not the selected builds' own stages: a dedicated verification job, as the commands under .verify in oyzu build --plan --json do
--skip-verificationRun no toolset verification runs here; a workflow runs each .verify entry of the plan in its own job. Each skipped run is named

Preview and check without building​

OptionDescription
--planPreview stages and requirements without installing, downloading or executing tools
--stage <NAME>With --plan: show only this stage's analysis (for example build or test)
--why <PATH>With --plan: explain whether a path is an input or output of each stage, and why
--unknownWith --plan: show only analysis facts that are unknown or over-approximate
--factsWith --plan: also list every raw analysis fact grouped by kind
--no-analysisWith --plan: skip static analysis; every stage uses whole-target scope
--checkRun static analysis and the project's rule levels without preparing or executing anything; exits non-zero on a blocking finding

Reuse and caching​

OptionDescription
--no-cacheRun every action: do not reuse or store action results for this build
--explainAfter the build, show why each stage was reused or ran: the first key component that changed since the last build of it
--verify-contractCheck each stage contract: run every confined action again with its whole target visible and compare the results. Reuses and stores nothing
-j, --jobs <N>Run at most N preparation and build workers at once. Overrides build.jobs and OYZU_BUILD_JOBS; the default follows available CPUs

Tools, executors and images​

OptionDescription
--offlineRequire cached tools and dependencies without online acquisition
--frozenReplay the plugin selections in oyzu.lock; fail rather than resolve or rewrite it
--store <STORE>Use this tool store instead of the shared user store
--isolatedUse the existing captured-source container executor explicitly
--no-dockerNever contact a Docker engine (also OYZU_NO_DOCKER=1). A selected target that needs one stops the build before anything runs, with exit status 3
--image <IMAGE>Select a provisioned toolchain image, e.g. npm=node:22-bookworm-slim
--execution-images-from <BUNDLE>Reuse exact execution images from a retained build bundle; source and engine/plugin/tool selections must match, and current controls apply
--engine-developmentRetain this development executable instead of the engine pin; requires local policy permission
--connector-bindings <CONNECTOR_BINDINGS>Host-owned connector endpoints and authorization environment references

Remote runs and split builds​

OptionDescription
--remoteBuild the pushed HEAD on a platform pool and follow it here. The pool always runs full checks in isolation; Ctrl-C cancels the remote run. With --plan: preview what the pool would run, with each target's platform and executor needs, without contacting the platform
--download <DIR>With --remote: download the run's outputs into this directory
--sliceBuild only the named targets, in isolation. Every other target they need is reused from the caches and never built; a missing one stops the build with UPSTREAM_NOT_CACHED (exit status 4)
--handoff <OCI_URL>With --slice: the OCI repository (oci://host/path) read first for upstream results and written with this slice's own. A failed write fails the build with HANDOFF_PUSH_FAILED (exit status 5)
--slice-plan <TARGET_ID>With --slice: a concrete target ID from the original preview. Repeat for every preview target, including targets folded into another slice

Presentation​

OptionDescription
--output <OUTPUT>Presentation only; auto/plain use linear output, interactive opts into the dashboard [default: auto] [possible values: auto, plain, interactive]
Status

Local host builds are the everyday path. Several options lead into experimental areas: static plan analysis and --check rules are advisory and experimental; --remote is an experimental client of the platform's remote-run API; --slice/--handoff, --verify-contract and the captured executor (--isolated) are experimental. See limitations.

The sections always appear in this order: Prepare (configuration, tools, workspaces), Facts (source and version identity), Plan (which stage runs for each target), Build (one row per action with the real command), Outputs, then the result. Failures and warnings get their own sections. The build output layout describes every row.

A failing build​

When an action fails, the build gets a Failure section with the failing test or compiler message, the exit code, the log path and the command that re-runs only that target. The tutorial shows a real one. A failed build exits 1, and local binaries from the previous successful build are left in place.

JSON output​

oyzu --json build prints the build-manifest record written to dist/manifest.json:

{ kind: "build-manifest", schemaVersion: "v1alpha1", status: "succeeded",
  invocationId, runId, source: { commit, dirty, treeDigest, projections },
  targets: [ { id, builder, path, platform, variant, builderDigest, extensions } ],
  actions: [ { id, target, status, exitCode, durationMs, required, enforced, producerEvidence, extensions } ],
  artifacts: [ { id, target, name, kind, path, size, digest, mediaType, producer, profile, version, variant } ],
  reports, evidence, diagnostics, planPath, planDigest, envelopePath, envelopeDigest, extensions }

oyzu --json build --plan prints a build-preview record instead: selection, targets[] (with executor, platform, needsDaemon, stages), tasks, requirements, analysis, matrix, verify, effects (all false: nothing downloaded, installed or executed) and unresolved. CI pipelines use targets[], matrix and verify to fan out jobs. See local builds: read-only build preview.

Exit status​

StatusWhen
0The build (or plan, or check) succeeded
1An action failed, a blocking --check finding, an unknown target, or another preparation failure
2Invalid arguments, or a handoff repository this client cannot use
3Invalid configuration (for example CONFIG_REFERENCE_UNKNOWN), or the build cannot be placed here (NEEDS_DOCKER_DAEMON with --no-docker, NEEDS_USER_NAMESPACES)
4UPSTREAM_NOT_CACHED in a --slice build, or a missing or stale lock
5HANDOFF_PUSH_FAILED in a --slice build
130Interrupted with Ctrl+C; logs and a failed bundle are kept

Common errors​

MessageCause and fix
COMMAND_FAILED: unknown build target nosuch; available targets: projectThe name is not a target. Run oyzu discover for the names.
TOOL_LOCK_STALEoyzu.lock has no pin for a requirement (for example go.mod changed). Run oyzu pin, then build again.
CONFIG_REFERENCE_UNKNOWNoyzu.toml names a build, output or task that build.yaml does not declare. The message gives the file, line, column and the nearest valid name.
NEEDS_DOCKER_DAEMONA target needs a container engine and --no-docker (or OYZU_NO_DOCKER=1) is set, or none is running. Start Docker or build that target elsewhere.
TOOL_NATIVE_MINIMUM_CONFLICTA configured tool version is below what a native file requires (such as the go line in go.mod). Raise the configured version.
