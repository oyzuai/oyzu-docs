oyzu build

Build every target, or the ones you name. oyzu build installs the pinned tools, runs each target's stages with its native commands (go build, npm run build, cargo build and so on), reuses results that haven't changed, and writes the outputs, a manifest, logs and reports to dist/.

oyzu build [OPTIONS] [TARGETS]...
ArgumentMeaning
[TARGETS]...Target IDs; omitted means all targets. Required dependencies are included

Target names are the ones oyzu discover prints.

Common tasks​

You want toRun
Build every target for this machineoyzu build
Build one target (and what it depends on)oyzu build cli
See what would run, without running anythingoyzu build --plan
Also run formatting, lint and testsoyzu build --full
Collect failures from independent actions in one runoyzu build --full --keep-going
Report rule findings onlyoyzu build --check
Build for another platformoyzu build --platform linux/arm64
Build every declared platformoyzu build --all-platforms
See why a stage ran instead of being reusedoyzu build --explain
Build only what changed since a Git refoyzu build --affected origin/main

Options​

The global options also apply.

What to build​

OptionDescription
--fullRun all quality stages locally (also enabled by CI context)
--context <CONTEXT>Pin the build context: local, pr, ci or release. Detected from CI provider variables by default; a pin can raise it, and can lower it only when no CI provider marker is present. Also OYZU_CONTEXT
--platform <OS/ARCH>Build for this target platform instead of the host (repeatable): os/arch[/abi] such as linux/arm64 or windows/x86_64/msvc; amd64 and aarch64 are accepted. A target that doesn't declare it skips it
--all-platformsBuild every declared platform with the container executor; fails before running when any declared platform can't be built here
--affected <AFFECTED>Build targets affected since a local Git ref, including dependents
--optimizedBuild the optimized profile (cargo build --release) even when the artifacts stay local. Overrides build.optimized; policy still wins
--no-optimizedBuild the development profile even when the artifacts are packaged, handed off, cached remotely or published. Overrides build.optimized
--require-releaseRequire authenticated exact-tag candidate or release coordinates. Missing evidence refuses the build before native actions run
--release-profile <FILE>Independent exact hosted builder and source expectations for this run
--verify-with <TOOLSET>Also run this toolset's verification run (repeatable): test the builds that use its tools with them ([toolsets.NAME] in oyzu.toml), in any context. What ships is still built with [tools]
--verify-only <TOOLSET>Run only this toolset's verification runs (repeatable), not the selected builds' own stages. For a dedicated verification job, like the commands under .verify in oyzu build --plan --json
--skip-verificationRun no toolset verification runs here, for a workflow that runs each .verify entry of the plan in its own job. Each skipped run is named

Preview and check without building​

OptionDescription
--planPreview stages and requirements without installing, downloading or running tools
--stage <NAME>With --plan: show only this stage's analysis (for example build or test)
--why <PATH>With --plan: explain whether a path is an input or output of each stage, and why
--unknownWith --plan: show only analysis facts that are unknown or over-approximate
--factsWith --plan: also list every raw analysis fact, grouped by kind
--no-analysisWith --plan: skip static analysis; every stage uses whole-target scope
--checkRun static analysis and the project's rule levels without preparing or running anything; exits non-zero on a blocking finding

Reuse and caching​

OptionDescription
--no-cacheRun every action: don't reuse or store action results for this build
--explainAfter the build, show why each stage was reused or ran: the first key component that changed since its last build
--verify-contractCheck each stage contract: run every confined action again with its whole target visible and compare the results. Reuses and stores nothing
-j, --jobs <N>Run at most N preparation and build workers at once. Overrides build.jobs and OYZU_BUILD_JOBS; the default follows available CPUs
--keep-goingSet build.failFast = false for every target and finish independent actions after a failure
--fail-fastSet build.failFast = true for every target and stop new and running actions at the first build-failing failure; mutually exclusive with --keep-going

Tools, executors and images​

OptionDescription
--offlineRequire cached tools and dependencies; download nothing
--frozenReplay the plugin selections in oyzu.lock; fail rather than resolve or rewrite it
--store <STORE>Use this tool store instead of the shared user store
--isolatedUse the container executor, which builds from a captured copy of the source
--no-dockerNever contact a Docker engine (also OYZU_NO_DOCKER=1). A selected target that needs one stops the build before anything runs, with exit status 3
--image <IMAGE>Run a manager's isolated work on your own execution image instead of the base image, e.g. npm=node:22-trixie-slim
--execution-images-from <BUNDLE>Reuse the exact execution images from a retained build bundle. Source and engine, plugin and tool selections must match, and current controls apply
--engine-developmentKeep this development executable instead of the pinned engine; requires local policy permission
--connector-bindings <CONNECTOR_BINDINGS>Host-owned connector endpoints and authorization environment references

Remote runs and split builds​

OptionDescription
--remoteBuild the pushed HEAD on a platform pool and follow it here. The pool always runs full checks in isolation; Ctrl+C cancels the remote run. With --plan: preview what the pool would run, with each target's platform and executor needs, without contacting the platform
--download <DIR>With --remote: download the run's outputs into this directory
--sliceBuild only the named targets, in isolation. Every other target they need is reused from the caches and never built; a missing one stops the build with UPSTREAM_NOT_CACHED (exit status 4)
--handoff <OCI_URL>With --slice: the OCI repository (oci://host/path) read first for upstream results and written with this slice's own. A failed write fails the build with HANDOFF_PUSH_FAILED (exit status 5)
--slice-plan <TARGET_ID>With --slice: a target ID from the original preview. Repeat for every preview target, including targets folded into another slice

Presentation​

OptionDescription
--output <OUTPUT>Presentation only: auto and plain use linear output, interactive opts into the live dashboard. Default auto

Note: Local host builds are the everyday path. These options are experimental: --check and plan analysis (advisory), --remote (needs a platform account or access to a standalone pool), --slice/--handoff, --verify-contract, --isolated and --require-release. See limitations.

When an action fails​

The first build-failing action stops new work and running actions by default, locally and in CI. The build fails with that action's exit code; an advisory warning does not stop it. Set build.failFast = false to let independent actions finish while dependents remain blocked. The setting resolves per target from its folder chain, with context over base in the same file. A failure in a false target blocks only dependents; a failure in a true target stops the whole build. [context.ci.build] failFast = false applies this behavior in CI. --keep-going (false) and --fail-fast (true) override OYZU_BUILD_FAIL_FAST=true|false, then files, subject to constraints. The flags also apply to --slice. The plan and record show each target's value and source; cache keys do not change.

Stopped actions are not-started or cancelled in both the manifest and JSON, with reason Stopped after <action id> failed. Their outputs are not collected or cached. Successful actions keep their normal cache entries for the next run. The receipt summarizes stopped work once and lists only real failures.

Fast and full builds​

A plain oyzu build on your machine is a fast build: it runs the build stage and only the checks set to required. --full, or a CI context, adds tests, lint and format checks. See check levels.

Full and CI builds, and the tags and conventional version strategies, can fetch missing Git history from public GitHub HTTPS remotes to work out the version. Your checkout and HEAD don't change. Fast local builds and --plan never fetch. See version inference.

A failing build​

When an action fails, the output gets a Failure section with the failing test or compiler message, the exit code, the log path and a command that re-runs only that target. The tutorial shows one. A failed build exits 1, and binaries from the previous successful build stay in place.

Exit status​

StatusWhen
0The build, plan or check succeeded
1An action failed, --check found a blocking finding, a target name is unknown, or preparation failed
2Invalid arguments, or a handoff repository this client can't use
3Invalid configuration (for example CONFIG_REFERENCE_UNKNOWN), or the build can't run here (NEEDS_DOCKER_DAEMON with --no-docker, NEEDS_USER_NAMESPACES)
4A missing or stale lock, or UPSTREAM_NOT_CACHED in a --slice build
5HANDOFF_PUSH_FAILED in a --slice build
130Interrupted with Ctrl+C; logs and a failed bundle are kept

Common errors​

MessageCause and fix
COMMAND_FAILED: unknown build target nosuch; available targets: projectThe name isn't a target. Run oyzu discover for the names.
TOOL_LOCK_STALEoyzu.lock has no pin for a requirement (for example, go.mod changed). Run oyzu pin, then build again.
CONFIG_REFERENCE_UNKNOWNoyzu.toml names a build, output or task that build.yaml doesn't declare. The message gives the file, line, column and the nearest valid name.
NEEDS_DOCKER_DAEMONA target needs a container engine and --no-docker is set, or no engine is running. Start Docker or build that target elsewhere.
TOOL_NATIVE_MINIMUM_CONFLICTA configured tool version is below what a native file requires (such as the go line in go.mod). Raise the configured version.
