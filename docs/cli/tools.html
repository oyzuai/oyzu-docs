oyzu tools

Inspect tool records without executing any tool. Use it to answer "which Go does this project use?", "what is taking space in my tool store?", "which versions could I install?" and "would my organization's catalog allow this?". To change what a project uses, see pin, install, update and uninstall.

oyzu tools [OPTIONS] <COMMAND>
SubcommandWhat it does
currentShow the tools in effect here: requested and selected versions, source and status
listList the installations in the tool store, and what references each
versionsList the versions of a tool that could be installed, and why others are excluded
infoShow a tool's provider, source, verification and eligibility
checkCheck the tools declared here against the signed tool index
requestAsk your organization's administrators to approve a tool version in its catalog
requestsList the approval requests made from here, with their state on the delivery edge
migrateMove mise.toml tools and aqua: ids to Oyzu names in oyzu.toml (dry run by default)
trust status, trust refreshShow or refresh the Sigstore trusted root the tool index is verified against
inspect-lockCheck that an oyzu.lock file is well formed (not that its tools are installed)
inspect-backendValidate a tool-backend descriptor file (an advanced, diagnostic check)
inspect-treeObserve an installed tool's file tree (an advanced, diagnostic check)
resolveEvaluate community recipe data offline into per-platform artifact sets (no network)
evidenceFetch an artifact set's files from their publishers and record and compare their digests

Every subcommand accepts the global options, including --json. All inspection is read-only: it installs nothing and never re-hashes installed payloads (installs are verified once, at install time, then trusted).

Status

current, list, versions and info are implemented for the tools Oyzu admits. The tool index client (check, migrate, trust), the organization catalog (request, requests) and recipe resolution (resolve, evidence) are experimental. See tool index, tool catalog and recipe resolution.

​
Store: C:\Users\you\AppData\Local\Oyzu\tools
Installed state comes from stored receipts; payloads are not re-hashed.

Statuses: ok, not installed (locked but not in the store; run oyzu install), blocked (refused by tools.allowed, naming the rule), stale lock (run oyzu pin), ambiguous and deprecated. In a project with nothing declared, it says No tools are declared here and suggests oyzu install <tool>@<version>.

tools versions​

oyzu tools versions [OPTIONS] <TOOL>
ArgumentMeaning
<TOOL>The tool, as [provider:]name
OptionDescription
--store <DIR>Use this tool store instead of the shared user store
--offlineRead only the last verified tool index and organization catalog; never fetch

Versions come newest first from the publisher's catalog, or from the tool index when it lists the package (which also works offline from its cached copy). A publisher catalog needs the network:

$ oyzu tools versions go --offline
✗ TOOL_OFFLINE: listing versions reads the publisher's catalog; retry without --offline
  Next: Correct the reported cause and retry the command.
  Invocation: 43608-1792552379629548300-1
  oyzu 0.1.0-local.564f462704df (debug; x86_64-pc-windows-msvc; build 1792551563) · windows/x86_64
  Executable: …\oyzu.exe
  Directory: .

Rust and the Cargo helpers have no version catalog (TOOL_VERSIONS_UNSUPPORTED).

tools check​

oyzu tools check [OPTIONS] --catalog
OptionDescription
--catalogCheck against the tool index and any organization catalog (the only check today; required)
--store <DIR>Use this tool store instead of the shared user store
--offlineRead only the last verified tool index and organization catalog; never fetch
$ oyzu tools check --catalog --offline
✓ All 1 declared tools can be installed
​
Tool     Request  Source  Reason
oyzu:go  1.22     direct  resolved by Oyzu's built-in provider for this tool
​
Checked against the tool index at https://github.com/oyzuai/tool-index/releases/latest/download/ (version 23, expires 2026-11-03T10:25:02Z).
using the last verified copy because a newer index could not be used: offline

For each declared tool it reports whether it installs from the tool index, would be evaluated locally from its registry recipe (standalone only), or is refused. With toolCatalog.url set, each tool is judged as an install would judge it. It installs and writes nothing, and exits 1 when any tool would be refused, so it fits in CI.

tools request and tools requests​

oyzu tools request [OPTIONS] [TOOL@VERSION]
oyzu tools requests [OPTIONS]
Argument / optionDescription
[TOOL@VERSION]The tool and version, as <tool>@<version>; the version may be a prefix such as 1.7
--reason <REASON>Why you need it, shown to the administrators
--status <ID>Show whether request ID has been decided, instead of asking for a tool
--cancel <ID>Cancel your pending request ID, instead of asking for a tool
oyzu tools request kubectl@1.31 --reason "cluster upgrade"
oyzu tools request --status 7
oyzu tools requests

These need an organization tool catalog: toolCatalog.url and OYZU_TOOL_CATALOG_TOKEN. Asking and cancelling go to the delivery admin API (toolCatalog.adminUrl or OYZU_TOOL_CATALOG_ADMIN_URL) as the person signed in with oyzu auth login, who needs the catalog.request permission. Asking again for the same tool and version returns the pending request. A pending request expires after 30 days unless the organization sets another limit. requests lists the newest 50 requests made from this machine with the current organization token.

tools migrate​

oyzu tools migrate [OPTIONS]
OptionDescription
--writeWrite oyzu.toml instead of only showing the result
--store <DIR>Use this tool store instead of the shared user store
--offlineRead only the last verified tool index; never fetch

Reads mise.toml (or .mise.toml) [tools] and oyzu.toml. aqua: ids become their tool index names, core: prefixes are dropped and github: stays. asdf and vfox plugins and unsupported backends are listed and left out. mise.toml is never modified. Without --write it only shows the result. With nothing to move:

$ oyzu tools migrate
✗ TOOL_MIGRATE_NOTHING: no mise.toml and no aqua: ids in oyzu.toml at …\hello; nothing to migrate
  Next: Correct the reported cause and retry the command.
  Invocation: 46792-1792552382175362300-1
  oyzu 0.1.0-local.564f462704df (debug; x86_64-pc-windows-msvc; build 1792551563) · windows/x86_64
  Executable: …\oyzu.exe
  Directory: .

tools trust​

oyzu tools trust status [OPTIONS]
oyzu tools trust refresh [OPTIONS]
OptionDescription
--from <DIR|URL>(refresh) A TUF repository mirror: a directory, or an HTTPS URL. Default: Sigstore's public repository
--store <DIR>Use this tool store instead of the shared user store
$ oyzu tools trust status
Tool index trust
​
Built In:
  Sha256: 6494e21ea73fa7ee769f85f57d5a3e6a08725eae1e38c755fc3517c9e6bc0b66
  Targets Version: 14
In Use: built-in
Refreshed: not specified

refresh runs the TUF client checks from the root built into this oyzu and keeps the verified trusted_root.json in the tool store, where it is used instead of the built-in root while it is newer. --from /media/sigstore refreshes an offline machine from a carried copy.

Diagnostic subcommands​

oyzu tools inspect-lock [OPTIONS] [LOCK_FILE]
oyzu tools inspect-backend [OPTIONS] <DESCRIPTOR_FILE>
oyzu tools inspect-tree [OPTIONS] <DIRECTORY>
ArgumentMeaning
[LOCK_FILE]Lock file to check; defaults to oyzu.lock in the current directory [default: oyzu.lock]
<DESCRIPTOR_FILE>Path to the backend descriptor file
<DIRECTORY>Directory to observe, usually an installation's payload
$ oyzu tools inspect-lock
Lock inspection
​
Environments: 0
Format: 1
Platforms:
  (none)
Resolutions: 4
Resolved environments: 2
Selections:
  (none)
Tools: 0
Validation: structure-and-identity-only

inspect-lock checks structure and identities only, not that the tools are installed. inspect-tree expects a directory (find installation paths with oyzu tools list --details). inspect-backend expects a descriptor file, not a tool name. Success exits 0; malformed, oversized or unreadable input exits 2.

tools resolve and tools evidence​

oyzu tools resolve [OPTIONS] --registry <FILE>
oyzu tools evidence [OPTIONS]

resolve options:

OptionDescription
--registry <FILE>Registry snapshot: the merged registry.yaml file
--registry-digest <DIGEST>Reject the snapshot unless its SHA-256 equals this value (sha256:HEX)
--snapshot-tag <TAG>Record the snapshot's release tag (a caller-asserted label)
--snapshot-commit <SHA>Record the snapshot's commit (a caller-asserted label)
--tool <NAME>Registry package name such as hashicorp/terraform (repeatable)
--tools-file <FILE>File with one package name per line
--version <VERSION>Exact upstream version as the recipe sees it, such as v1.16.5 (repeatable)
--platform <OS/ARCH/ABI>Platform OS/ARCH/ABI (repeatable); defaults to the three default platforms
--limit <NAME=VALUE>Lower a counted limit, NAME=VALUE (repeatable); limits cannot be raised

evidence options:

OptionDescription
--set <FILE>The tools resolve document to verify; - reads standard input
--provider <PROVIDER>Build and verify provider records: java, node, go, python, maven, gradle, helm, kubectl, k3d, liquibase, tailscale, npm, pnpm or rust
--version <VERSION>Exact provider release to record, such as 21.0.8 (repeatable; with --provider)
--platform <PLATFORM>Platform to record (repeatable; with --provider). Default: every platform the provider installs
--allow-host <HOST>Permit a host in addition to those named by the set's own URLs (repeatable)
--verify <METHOD>Run only these verification methods (repeatable); others are reported not-run
oyzu --json tools resolve --registry ./registry.yaml --tool hashicorp/terraform --version v1.16.5 > set.json
oyzu --json tools evidence --set set.json

These are maintainer tools for building the tool index. resolve reads only the named registry snapshot file; it never fetches one. evidence downloads each artifact and its checksum file and verifies attestations where they exist. Both exit 0 when complete, 2 on an input problem and 3 when the document is complete but some item could not be decided or verified.

Exit status​

StatusWhen
0Success
1check --catalog found a refused tool; a network or catalog failure; nothing to migrate
2Invalid arguments or an unknown tool name; malformed input to inspect-*, resolve or evidence
3resolve/evidence: complete, but some item undecided or unverified
