oyzu tools

Look up tool records without running any tool. Use it to answer "which Go does this project use?", "what's taking space in my tool store?", "which versions could I install?" and "would my organization's catalog allow this?". To change what a project uses, see pin, install, update and uninstall.

oyzu tools [OPTIONS] <COMMAND>
SubcommandWhat it does
currentShow the tools in effect here: requested and selected versions, source and status
listList the installations in the tool store, and what references each
versionsList the versions of a tool that could be installed, and why others are excluded
infoShow a tool's provider, source, verification and eligibility
checkCheck the tools declared here against the signed tool index
requestAsk your organization's administrators to approve a tool version in its catalog
requestsList the approval requests made from here, with their current state
migrateMove mise.toml tools and aqua: ids to Oyzu names in oyzu.toml (dry run by default)
trust status, trust refreshShow or refresh the Sigstore trusted root the tool index is verified against
inspect-lockCheck that an oyzu.lock file is well formed (not that its tools are installed)
inspect-backendValidate a tool-backend descriptor file (an advanced diagnostic)
inspect-treeLook at an installed tool's file tree (an advanced diagnostic)
resolveEvaluate community recipe data offline into per-platform artifact sets
evidenceDownload an artifact set's files from their publishers and record and compare their digests

Every subcommand accepts the global options, including --json. All of them are read-only. They install nothing and don't re-hash installed tools: a tool is verified once, when it is installed.

Note: current, list, versions and info are stable. The tool index client (check, migrate, trust), the organization catalog (request, requests) and recipe resolution (resolve, evidence) are experimental.

Used by is global, project or unreferenced. Other projects aren't indexed, so an installation shown as unreferenced here may still be used by another project. ID is the start of the installation digest; two installs of one version can differ by recipe or platform ABI.

tools versions​

oyzu tools versions [OPTIONS] <TOOL>
ArgumentMeaning
<TOOL>The tool, as [provider:]name
OptionDescription
--store <DIR>Use this tool store instead of the shared user store
--offlineRead only the last verified tool index and organization catalog; never fetch

Versions are listed newest first, from the publisher's catalog or from the tool index when it lists the package. The tool index also works offline from its cached copy. A publisher catalog needs the network, so --offline fails for those tools with TOOL_OFFLINE. Rust and the Cargo helpers have no version catalog (TOOL_VERSIONS_UNSUPPORTED).

tools check​

oyzu tools check [OPTIONS] --catalog
OptionDescription
--catalogCheck against the tool index and any organization catalog (the only check today; required)
--store <DIR>Use this tool store instead of the shared user store
--offlineRead only the last verified tool index and organization catalog; never fetch
$ oyzu tools check --catalog --offline
✓ All 1 declared tools can be installed
​
Tool     Request  Source  Reason
oyzu:go  1.22     direct  resolved by Oyzu's built-in provider for this tool
​
Checked against the tool index at https://github.com/oyzuai/tool-index/releases/latest/download/ (version 23, expires 2026-11-03T10:25:02Z).
using the last verified copy because a newer index could not be used: offline

For each declared tool it reports whether it installs from the tool index, would be evaluated locally from its registry recipe (standalone only), or is refused. With toolCatalog.url set, each tool is judged as an install would judge it: approved by the organization catalog, refused with its reason, or not in the catalog. It installs and writes nothing, and exits 1 when any tool would be refused, so it fits in CI.

tools request and tools requests​

oyzu tools request [OPTIONS] [TOOL@VERSION]
oyzu tools requests [OPTIONS]
Argument / optionDescription
[TOOL@VERSION]The tool and version, as <tool>@<version>; the version may be a prefix such as 1.7
--reason <REASON>Why you need it, shown to the administrators
--status <ID>Show whether request ID has been decided, instead of asking for a tool
--cancel <ID>Cancel your pending request ID, instead of asking for a tool
oyzu tools request kubectl@1.31 --reason "cluster upgrade"
oyzu tools request --status 7
oyzu tools requests

These need an organization tool catalog: toolCatalog.url and OYZU_TOOL_CATALOG_TOKEN. Asking and cancelling go to the catalog's admin API (toolCatalog.adminUrl or OYZU_TOOL_CATALOG_ADMIN_URL) as the person signed in with oyzu auth login, who needs the catalog.request permission.

  • Asking again for the same tool and version returns the request that's already pending.
  • The organization's auto-approve rules may approve a request at once.
  • A pending request expires after 30 days unless the organization sets another limit. Only the person who asked can cancel it.
  • requests lists the newest 50 requests made from this machine with the current organization token.

tools migrate​

oyzu tools migrate [OPTIONS]
OptionDescription
--writeWrite oyzu.toml instead of only showing the result
--store <DIR>Use this tool store instead of the shared user store
--offlineRead only the last verified tool index; never fetch

Reads [tools] from mise.toml (or .mise.toml) and oyzu.toml. aqua: ids become their tool index names, core: prefixes are dropped and github: stays. asdf and vfox plugins and unsupported backends are listed and left out. mise.toml is never changed. With nothing to move, it fails with TOOL_MIGRATE_NOTHING.

tools trust​

oyzu tools trust status [OPTIONS]
oyzu tools trust refresh [OPTIONS]
OptionDescription
--from <DIR|URL>(refresh) A TUF repository mirror: a directory, or an HTTPS URL. Default: Sigstore's public repository
--store <DIR>Use this tool store instead of the shared user store

status shows the trusted root built into oyzu, its digest and version, and which root is in use. refresh runs the standard TUF checks starting from the root built into oyzu and keeps the verified trusted_root.json in the tool store, where it replaces the built-in root while it is newer. To refresh an offline machine, carry a copy of the repository and run oyzu tools trust refresh --from /media/sigstore.

Diagnostic subcommands​

oyzu tools inspect-lock [OPTIONS] [LOCK_FILE]
oyzu tools inspect-backend [OPTIONS] <DESCRIPTOR_FILE>
oyzu tools inspect-tree [OPTIONS] <DIRECTORY>
ArgumentMeaning
[LOCK_FILE]Lock file to check; defaults to oyzu.lock in the current directory
<DESCRIPTOR_FILE>Path to the backend descriptor file
<DIRECTORY>Directory to look at, usually an installation's payload

inspect-lock checks structure and identities only, not that the tools are installed. inspect-tree expects a directory (find installation paths with oyzu tools list --details). inspect-backend expects a descriptor file, not a tool name. They exit 0 on success and 2 for malformed, oversized or unreadable input.

tools resolve and tools evidence​

These build and check the data behind the tool index.

oyzu tools resolve [OPTIONS] --registry <FILE>
oyzu tools evidence [OPTIONS]

resolve options:

OptionDescription
--registry <FILE>Registry snapshot: the merged registry.yaml file
--registry-digest <DIGEST>Reject the snapshot unless its SHA-256 equals this value (sha256:HEX)
--snapshot-tag <TAG>Record the snapshot's release tag (a label you assert)
--snapshot-commit <SHA>Record the snapshot's commit (a label you assert)
--tool <NAME>Registry package name such as hashicorp/terraform (repeatable)
--tools-file <FILE>File with one package name per line
--version <VERSION>Exact upstream version as the recipe sees it, such as v1.16.5 (repeatable)
--platform <OS/ARCH/ABI>Platform (repeatable); defaults to the three default platforms
--limit <NAME=VALUE>Lower a counted limit (repeatable); limits can't be raised

evidence options:

OptionDescription
--set <FILE>The tools resolve document to verify; - reads standard input
--provider <PROVIDER>Build and verify provider records: java, node, go, python, maven, gradle, helm, kubectl, k3d, liquibase, tailscale, npm, pnpm or rust
--version <VERSION>Exact provider release to record, such as 21.0.8 (repeatable; with --provider)
--platform <PLATFORM>Platform to record (repeatable; with --provider). Default: every platform the provider installs
--allow-host <HOST>Allow a host besides those named by the set's own URLs (repeatable)
--verify <METHOD>Run only these verification methods (repeatable); others are reported as not run
oyzu --json tools resolve --registry ./registry.yaml --tool hashicorp/terraform --version v1.16.5 > set.json
oyzu --json tools evidence --set set.json

resolve reads only the registry file you name and never downloads one. evidence downloads each artifact and its checksum file and verifies attestations where they exist. Both exit 0 when complete, 2 on an input problem, and 3 when the document is complete but some item couldn't be decided or verified.

Exit status​

StatusWhen
0Success
1check --catalog found a refused tool; a network or catalog failure; nothing to migrate
2Invalid arguments or an unknown tool name; malformed input to inspect-*, resolve or evidence
3resolve or evidence: complete, but some item undecided or unverified
