How Oyzu fits together

Oyzu is one command, oyzu, that looks at a repository, works out what it can build, installs the exact tools it needs, runs the native commands your ecosystem already uses, and leaves behind a record you can check later. You do not write a pipeline. You keep your go.mod, Cargo.toml, package.json or pyproject.toml, and Oyzu works from them.

This page is the map. Each section names one idea, says why it exists, and links to the page that explains it properly.

The journey of one build​

  your repository                          what Oyzu decides                     what you get
  ───────────────                          ─────────────────                     ────────────
  native files (go.mod, Cargo.toml …) ─┐
  build.yaml (optional)               ─┼─► targets and builders ─┐
                                       │   (discovery)           │
  oyzu.toml cascade, oyzu.local.toml  ─┼─► settings per folder ──┼─► plan: stages and   ─► actions ─► dist/ bundle
  user configuration, policy          ─┘   (configuration)       │   actions per target      │        manifest, plan,
                                                                 │                           │        artifacts, reports
  oyzu.lock                           ───► exact tool versions ──┘                           │
                                           (tools)                                           ▼
                                                                   action cache ◄──── reuse or execute
                                                                                     on the host, in a
                                                                                     container, or remotely
  1. Discovery reads your native files and finds targets: one buildable unit each, such as a Go module or a Cargo package. A builder (go/app, rust/app, node/app …) knows how to build each one. An optional build.yaml makes the list explicit. See How Oyzu sees a project.
  2. Configuration decides how strictly and where to build: which checks run, how many jobs, which executor. It comes from a cascade of oyzu.toml files, personal overrides and organization policy. See Configuration layers.
  3. Tools are resolved to exact versions and recorded in oyzu.lock, then installed and verified once. See Tools and toolchains and The lock file.
  4. Planning turns targets into stages (format-check, lint, test, build, package) and actions, the units of real work, ordered by the dependencies between targets. See The build graph and Tasks and builds.
  5. Execution runs each action on the host, in an isolated container, or on a remote pool. See Execution modes and Platforms and matrices.
  6. The action cache skips actions whose inputs have not changed and says so plainly. --affected narrows a build to what changed since a Git commit. See The action cache and affected builds.
  7. The bundle in dist/ records what actually happened: the manifest, the frozen plan, artifacts with digests, test and coverage reports, and logs. Earlier bundles move to history. See Artifacts, bundles and evidence.

One command per idea​

Every concept has a command that shows it. None of these change your project.

ConceptSee it withWhat it shows
Targets and buildersoyzu discoverEach target, its builder, and whether detection or build.yaml chose it
Tasksoyzu run listEvery task and the native command it runs
The planoyzu build --planStages per target, tool requirements, what is still unresolved
Configurationoyzu config explain <setting>The effective value and every file that set it, in order
Toolsoyzu tools currentRequested and selected versions and where each came from
The lockoyzu pin --dry-runWhat would be locked, for which platforms, without writing
The cacheoyzu cache explain <target>Why a target's cache key last changed
Evidenceoyzu inspect dist, oyzu historyWhether recorded files match their digests; retained runs

Every command also accepts --json for a structured result. See the CLI output contract.

The two files you might write​

Most projects start with neither. When you need them, each has one job (the decision behind this):

FileSaysAddressed byExample
build.yamlWhat the project produces and how builds connectBuild name; the same for everyonebuilds: {api: {uses: go/app, path: api}}
oyzu.tomlHow, where and how strictly: tools, checks, tasks, environmentFolder; can vary by context and person[tools] go = "1.27"

Exact tool versions never go in either file. They live in oyzu.lock, which Oyzu writes.

Principles you will notice​

  • Native conventions first. If your native files already say something (a Go minimum version in go.mod, a Rust channel in rust-toolchain.toml), Oyzu reads it there rather than asking you to repeat it.
  • Plans are intent, bundles are evidence. oyzu build --plan installs, downloads and runs nothing. Only an actual build produces evidence, and it records exactly what ran, what was reused and what failed.
  • Honest wording. A reused test result is labelled "reused from an earlier run, not run now". A blocked action is not reported as failed. oyzu inspect says it checks integrity, not authorship.
  • No account required. Everything on these pages works standalone. Optional platform features, such as oyzu build --remote, are separate and say so.
  • Policy wins visibly. When an organization constraint changes a value, Oyzu shows the override and where it came from rather than silently substituting it.
Early implementation

Oyzu is in active development and has not had a public release. These pages describe the behavior documented in the reference; where a capability is experimental or limited to certain platforms, the page says so. The measured record is summarized in Current capabilities.
